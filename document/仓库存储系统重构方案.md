## 一、背景与目标

### 1.1 现状

当前仓库系统通过 **GitHub Pull Request** 提交内容变更：

- 每次新增/编辑 Rule 或 Skill → 创建一个带时间戳的分支 → push → 调用 GitHub API 创建 PR
- 要求用户自行配置 Git 凭证（SSH 密钥 / credential helper）和 GitHub Token（`GH_TOKEN` / `gh auth token`）

### 1.2 核心痛点

- 使用者中包含大量**非开发背景的产品人员**，配置 Git 和 Token 对他们是巨大障碍
- 项目实际使用的是**自建 Git 服务**（Gitea / GitLab 类），不是 GitHub，无法直接沿用 GitHub App / OAuth 方案
- PR 的"审核 gate"对知识库类内容价值有限，换来的复杂度不值

### 1.3 目标

- **彻底废弃 PR 流程**
- 通过文件结构设计，让两次提交**在物理层面不可能冲突**
- 用户侧无需任何 Git / Token 配置（凭证由 app 统一管理，见 §5.5）
- 保留完整审计能力，用户能在 app 内看到任何一条内容的历史
- 长期可维护：即使历史累积到几千条也不会性能崩溃

## 二、核心设计原则

1. **Full snapshot，不做增量 patch**。每次修改都存一份完整快照，避免"前面历史被删导致后面还原不了"的依赖链问题。
2. **目录名三段式保证物理唯一**：`时间戳 + 用户 ID + 随机后缀`。两次提交不可能撞同一个文件名。
3. **不存在共享可写文件**。任何"所有用户都要写入的索引/汇总"都不入库，只在客户端本地缓存。
4. **"当前版本"由 history 目录里记录的 timestamp 决定**，后改赢、早改白改。接受这个语义。
5. **附件走 content-addressable 池（sha256 命名）**，同一附件无论被多少个版本引用，物理上只存一份。
6. **git 当存储引擎用**，不暴露 git 概念给用户（无 branch / PR / commit message 的用户界面）。
7. **所有 commit 用统一的机器人身份**，真实作者信息走应用层的 userId + displayName。
8. **Compaction 是系统必需品，不是可选项**。不做 compaction，长期一定性能崩溃。

## 三、数据结构定义

### 3.1 仓库目录树

```
<repo-root>/
├── rules/
│   ├── <ruleUuid>/                                    ← Rule 的永久 UUID
│   │   ├── meta.json                                   ← 出生证明，创建后永不修改
│   │   └── history/
│   │       ├── 20260418T100000Z__<userId>__<rand6>/   ← 一次完整快照
│   │       │   ├── snapshot.json
│   │       │   ├── main.md
│   │       │   └── attachments.json
│   │       └── 20260418T103000Z__<userId>__<rand6>/
│   │           └── ...
│   └── <另一个 ruleUuid>/
│       └── ...
├── skills/                                            ← 与 rules/ 同构
│   └── <skillUuid>/
│       ├── meta.json
│       └── history/
│           └── ...
└── attachments-pool/                                  ← content-addressable 附件池
    ├── ab/
    │   └── cd/
    │       └── abcd1234...<完整 sha256>              ← 文件名 = sha256 全串
    └── ef/
        └── 12/
            └── ef12...
```

**关键约束：**

- `rules/`、`skills/` 下每个一级子目录的名字 **必须是 UUID**（32 字符无横线），不是 slug、不是 title
- `history/` 下每个子目录的名字 **必须符合"三段式"格式**（见 §3.3）
- `attachments-pool/` 下用 **sha256 的前两字节做两级分片**（避免单目录文件数过多）
- 仓库里**绝不允许出现**以下任一文件：
  - `index.json` / `categories.json` / `authors.json` / 任何全局汇总文件
  - `latest.json` / `current.json` / 任何"当前版本指针"
  - 这些都是共享写入点，会破坏无冲突特性

### 3.2 文件 schema

所有 schema 都带 `schemaVersion` 字段，便于以后演进。当前版本统一 `schemaVersion: 1`。

#### 3.2.1 `rules/<ruleUuid>/meta.json`

```json
{
  "schemaVersion": 1,
  "id": "550e8400e29b41d4a716446655440000",
  "type": "rule",
  "createdBy": "a3f2b9c1d4e5f6a7b8c9d0e1f2a3b4c5",
  "createdByDisplayName": "张三",
  "createdAt": "2026-04-18T10:00:00.000Z"
}
```

- **创建后永不修改**。所有可变字段（title / description / category / icon / iconBg）都在 history 的 snapshot.json 里。
- `id` 与目录名一致（冗余存一份，便于迁移 / 校验）。
- `createdByDisplayName` 是**快照**，存的是创建时用户的 displayName，日后用户改名不影响这个字段。

#### 3.2.2 `rules/<ruleUuid>/history/<dirname>/snapshot.json`

```json
{
  "schemaVersion": 1,
  "title": "示例规则标题",
  "description": "一行描述",
  "category": "产品",
  "icon": "Sparkles",
  "iconBg": "#A78BFA",
  "modifiedBy": "a3f2b9c1d4e5f6a7b8c9d0e1f2a3b4c5",
  "modifiedByDisplayName": "张三",
  "modifiedAt": "2026-04-18T10:30:00.000Z",
  "deleted": false
}
```

- `modifiedAt` **由客户端本地时间生成**（ISO 8601 UTC），是后续判断"当前版本"的唯一依据。
- `modifiedBy` 是这次修改发起者的 userId（32 字符无横线）。
- `modifiedByDisplayName` 是快照，存的是**这次修改时**用户的 displayName。
- `deleted` 为 `true` 表示这次修改是软删除操作（见 §5.3）。软删 history 里其他字段保留最后一次有效快照的值。

#### 3.2.3 `rules/<ruleUuid>/history/<dirname>/main.md`

- Rule / Skill 的正文内容（markdown）。
- 每一条 history 都存**完整正文**，不是增量 diff。即使本次修改只改了标题，main.md 也要写入和上一条一样的内容（git pack 会自动 delta 压缩，不会真的重复存储）。

#### 3.2.4 `rules/<ruleUuid>/history/<dirname>/attachments.json`

```json
{
  "schemaVersion": 1,
  "files": [
    {
      "originalName": "架构图.png",
      "sha256": "ab12cd34ef56...（64 字符）",
      "size": 123456
    },
    {
      "originalName": "readme.md",
      "sha256": "ef12ab34cd56...",
      "size": 2048
    }
  ]
}
```

- 即使本次修改没有动附件，`attachments.json` 也要写一份（内容与上一条相同）。**每个 history 必须自足**。
- Rule 没有附件 → `files: []`，但 attachments.json 文件本身必须存在。
- `originalName` 保留用户上传时的原始文件名（允许中文 / emoji / 空格），展示用。
- 附件真正的物理存储在 `attachments-pool/<sha256[0:2]>/<sha256[2:4]>/<sha256>`。

#### 3.2.5 Skill 特殊性

Skill 的 `meta.json` 与 Rule 同结构，只是 `type: "skill"`。Skill 的附件全部走 `attachments.json` + pool，**不再**像当前实现那样把附件散落在 skill 目录下。

### 3.3 目录/文件命名规则

#### 3.3.1 history 目录名

```
<timestamp>__<userId>__<rand6>
```

- `timestamp`：UTC 时间，格式 `YYYYMMDDTHHmmssZ`（紧凑 ISO，去除分隔符）。例如 `20260418T103000Z`。
  - 不带毫秒。毫秒级碰撞交给 `rand6` 兜底。
- `userId`：32 字符无横线 UUID v4，全小写十六进制。
- `rand6`：6 字符随机十六进制，用 `crypto.randomBytes(3).toString("hex")` 生成。
- 三段之间用**双下划线** `__` 分隔（单下划线在 userId 里虽然不会出现，但双下划线更视觉分明）。

**完整示例：**
```
20260418T103000Z__550e8400e29b41d4a716446655440000__a3f2b9
```

#### 3.3.2 附件池文件

```
attachments-pool/<sha256 前 2 字符>/<sha256 第 3-4 字符>/<完整 sha256>
```

**示例：** sha256 为 `ab12cd34...` 的附件存在 `attachments-pool/ab/12/ab12cd34...`。

不带扩展名（扩展名信息已经在引用它的 `attachments.json` 的 `originalName` 字段里）。

#### 3.3.3 Rule / Skill 目录名

- UUID v4，32 字符无横线，全小写。
- 创建后**永不修改**（改了等于"删了重建一条"）。

## 四、用户 ID 系统

### 4.1 生成

- 每个客户端**首次启动**时生成一次 UUID v4（使用 Node.js 内置 `crypto.randomUUID()` 或浏览器内置同名 API）。
- **存储格式统一为 32 字符无横线全小写十六进制**。生成后立即去掉 `randomUUID()` 默认返回格式里的 `-`。
- 不带任何网络请求，纯本地生成。碰撞概率 10⁻¹⁷ 量级，实际上不可能。

### 4.2 存储

- 存在 Electron 的应用配置目录里（通过 `app.getPath("userData")`）。
- 专用文件：`<userData>/user-identity.json`，内容：

```json
{
  "schemaVersion": 1,
  "userId": "a3f2b9c1d4e5f6a7b8c9d0e1f2a3b4c5",
  "displayName": "张三",
  "generatedAt": "2026-04-18T10:00:00.000Z"
}
```

- `displayName` 初始值可以是空字符串或系统用户名（有 fallback），用户可以在设置页修改。
- 文件权限：仅当前用户可读写（macOS/Linux `0600`，Windows 默认 ACL 已经够）。

### 4.3 展示和编辑（设置页）

**设置页必须有一个"身份 ID"区块**，包含以下内容：

1. **只读展示当前 userId**（32 字符，等宽字体展示便于复制）
2. **一键复制按钮**（复制后有 toast 反馈 "已复制"）
3. **下方必须有一行提示**：
   > 这是你在 Synapse 中的唯一身份凭证。**请立即复制并备份到密码管理器或其他安全位置**。如果本地数据丢失且你没有备份，将无法恢复历史身份。
4. **"手动填入已有 ID"入口**（按钮 "恢复已有身份"）
   - 点击后弹模态框，输入框 + 校验（见 §4.5）
   - 二次确认提示："切换 ID 后，新提交的内容会被认作来自另一个人，确定吗？"
   - 确认后覆盖 `user-identity.json`，**但不要删除历史数据**（历史提交还在仓库里，带着老 userId）
5. **displayName 编辑入口**（简单输入框，实时保存）

### 4.4 校验规则（用户手动填入 ID 时）

- 长度必须恰好 **32 字符**
- 只允许 `[0-9a-f]` 小写十六进制字符
- 大写字母自动转小写后继续校验
- 带横线的标准 UUID 格式（36 字符）**自动去横线**转换，而不是报错（用户可能从别处复制过来就是带横线的）
- 格式不对 → 输入框下方红色提示 "ID 格式不对，应为 32 位十六进制字符"，保存按钮禁用

### 4.5 ID 丢失恢复流程

**检测时机：** 每次 app 启动时读取 `user-identity.json`。

**分支 A：文件不存在**（首次启动 or 用户彻底清了配置）

- **自动生成新 UUID**
- 立即进入"首次启动引导"流程（见 §10.4）
- 不弹错误框

**分支 B：文件存在但 `userId` 字段缺失 / 格式错误**（配置损坏）

- **不自动生成**。弹模态框，标题 "身份 ID 无法读取"，内容：
  > 检测到本地身份 ID 损坏。如果你之前备份过 ID，现在可以手动填回；否则可以生成一个新 ID 继续使用。
- 两个按钮：
  - **"生成新 ID"**：生成新 UUID，保存，关闭模态框
  - **"手动填入"**：切换到输入模式，让用户粘贴备份的 ID（走 §4.4 的校验）
- 模态框不可关闭（`dismissible: false`），用户必须二选一才能继续使用 app

## 五、内容提交流程

### 5.1 创建 Rule / Skill

**触发：** 用户在 UI 打开创建弹窗 → 填写字段 → 点确定。

**流程：**

1. 校验必填字段（title 等），失败立即弹错误模态框，**不写入任何东西**。
2. 生成 `ruleUuid = crypto.randomUUID().replace(/-/g, "")`。
3. 构建 history 目录名：`timestamp = nowUtc()`，`rand6 = randHex(6)`，拼接成三段式。
4. 在**工作副本的 tmp 目录**准备文件（不要直接写到仓库路径，避免半成品污染）：
   - `meta.json`
   - `history/<dirname>/snapshot.json`
   - `history/<dirname>/main.md`
   - `history/<dirname>/attachments.json`
5. 处理附件：逐个计算 sha256，写入 `attachments-pool/<分片>/<sha256>`。**如果池里已有同 sha256 文件，跳过写入**（content-addressable 的去重效果）。
6. 原子 `mv` tmp 目录到仓库正式路径：`rules/<ruleUuid>/`。
7. `git add rules/<ruleUuid>/ attachments-pool/<新增文件>`
8. `git commit -m "[synapse] create rule <ruleUuid>"`（统一的机器人身份见 §5.5）
9. **立即尝试 `git push`**（见 §5.6）。
10. 成功后刷新本地索引（见 §6.2）。

### 5.2 编辑 Rule / Skill

**触发：** 用户在详情页点编辑 → 弹窗改字段 → 点确定。

**流程：**

1. **保存前先 `git pull --rebase`**（见 §7.2 的冲突提示），更新仓库到最新状态。
2. 读取当前最新的 history 作为基线（获取 title/description/category/icon/iconBg/attachments 等）。
3. 弹窗里用户改完后，生成新的 history 目录（新 timestamp + 当前 userId + 新 rand6）。
4. 写入 `snapshot.json`、`main.md`、`attachments.json`。
   - **全字段完整写入**，不是只写改了的字段。即使只改了标题，main.md 也要完整写一份。
5. 处理附件增量：新增的附件进 pool，**不要删除 pool 里的旧附件**（GC 统一处理，见 §9）。
6. git add / commit / push，流程同 §5.1 步骤 7-10。

### 5.3 删除（软删）

**触发：** 用户在详情页点删除 → 二次确认 → 确定。

**流程：**

1. 同编辑流程（先 pull，读基线）。
2. 生成一条新 history，**`snapshot.json` 的 `deleted` 字段设为 `true`**，其他字段复制基线的值（确保该 history 自足）。
3. `main.md` 和 `attachments.json` 也要写，内容复制基线的（同样为了自足）。
4. git add / commit / push。

**读取端行为：**
- 列表页扫描所有 rule 时，**跳过最新 history 的 `deleted: true` 的**。
- 详情页如果直接用链接打开一个软删的 rule，**显示 "该内容已被删除" 的空状态**，不让进入编辑。
- 搜索也排除软删条目。
- **不做回收站**。软删之后，普通用户界面里彻底看不到。
- 维护者想真正清理磁盘时，靠 compaction 在 90 天后物理删除整个 `rules/<ruleUuid>/` 目录。

### 5.4 附件处理

**上传：**
- 计算 sha256（可以流式计算，大文件别一次读内存）。
- 查 pool 里是否已有 → 有就跳过物理写入；没有就写入。
- 在 `attachments.json` 的 `files` 数组里记一条 `{ originalName, sha256, size }`。

**读取：**
- 根据 `attachments.json` 里的 sha256 拼出 pool 路径 `attachments-pool/<前2>/<3-4>/<全串>`，直接读。
- 如果文件不存在（pool 损坏 / GC 误删），**降级显示 "附件已缺失"，不 crash**。

**"删除附件"（用户在编辑时移除了一个附件）：**
- **不要**从 pool 里删。只是在新 history 的 `attachments.json` 里不再引用它。
- 物理清理交给 GC（见 §9）。

### 5.5 git commit 规范

**统一机器人身份：**

- `git config --local user.name "Synapse Bot"`
- `git config --local user.email "bot@synapse.local"`
- 每次 app 初始化本地仓库时写入（只改 local config，不动用户全局 git config）。

**commit message 格式：**

```
[synapse] <action> <type> <ruleUuid 前 8 字符>
```

- action ∈ { `create`, `update`, `delete`, `compaction`, `gc` }
- type ∈ { `rule`, `skill` }
- 示例：`[synapse] update rule a3f2b9c1`
- **不需要**详细的 commit body，真实变更信息在 snapshot.json 里。
- compaction / GC 的 commit author 也用同样的 "Synapse Bot" 身份。

### 5.6 立即推送 + 本地失败队列

**成功路径（默认）：**

1. commit 完成 → 立即 `git push`
2. 成功 → 刷新本地索引 → UI 反馈完成

**失败处理：**

1. push 返回非零 / 网络错误 → **不弹立即的错误框**（避免打扰用户流程），改为：
   - 把这条 commit 的信息写入本地 SQLite 表 `pending_pushes`：
     ```
     id | commit_hash | action | target_ruleUuid | created_at | retry_count | last_error
     ```
   - 工具栏右侧的上传按钮亮起（三态见 §10.2）
2. 用户点击上传按钮 → 弹模态框 "本地有 N 条变更等待同步，现在推送？" → 点确定：
   - 后台批量 `git push`
   - 成功 → 队列清空 → 按钮熄灭
   - 失败 → 弹错误模态框（见 §11），队列保留

**网络常见错误分类：**

- `non-fast-forward`（有人在你之前 push 过）→ 先 `git pull --rebase` 再 retry
- 网络超时 → 直接标记失败进队列
- 认证失败 → 弹模态框提示 "无法连接仓库，请检查网络" 并记录到队列

**退出 app 时有未 push：**

- 不强制阻止退出。
- 弹一个提示模态框：
  > 还有 N 条变更未同步到仓库，下次启动时可以继续推送。确定退出吗？
- 按钮：[继续退出] [先同步]
- 默认选 [先同步]，但用户可以选 [继续退出]。

**启动时 reconcile：**

- app 启动时检查 `pending_pushes` 表：如果有条目，工具栏按钮直接亮起，不自动重推（避免用户不知情的情况下触发网络）。

## 六、内容读取流程

### 6.1 "当前版本"的判定

一条 rule 的当前版本 = **所有 history 子目录中，`snapshot.json.modifiedAt` 最大的那条**。

- **排序依据是 snapshot.json 里的字段，不是目录名里的时间戳**（虽然它俩应该一致，但以 snapshot.json 为准）。
- 如果目录名的 timestamp 和 snapshot.json 里的 modifiedAt 不一致，**信任 snapshot.json**（目录名可能被手动修改过）。
- 如果 `deleted: true`，rule 视为已删除，列表 / 详情不展示（见 §5.3）。

### 6.2 本地索引（SQLite）

- **绝对不入库**。索引是客户端本地缓存，路径 `<userData>/content-index.db`。
- 表结构（最小集）：

```sql
CREATE TABLE content_index (
  id              TEXT PRIMARY KEY,      -- ruleUuid / skillUuid
  type            TEXT NOT NULL,         -- 'rule' | 'skill'
  title           TEXT,
  description     TEXT,
  category        TEXT,
  icon            TEXT,
  icon_bg         TEXT,
  modified_by     TEXT,
  modified_by_name TEXT,
  modified_at     TEXT,                  -- ISO timestamp
  created_by      TEXT,
  created_at      TEXT,
  deleted         INTEGER DEFAULT 0,
  latest_history_dirname TEXT            -- 当前最新 history 的目录名，详情页加载用
);

CREATE INDEX idx_modified_at ON content_index(modified_at DESC);
CREATE INDEX idx_type_deleted ON content_index(type, deleted);

CREATE TABLE pending_pushes (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  commit_hash     TEXT,
  action          TEXT,
  target_id       TEXT,
  created_at      TEXT,
  retry_count     INTEGER DEFAULT 0,
  last_error      TEXT
);

CREATE TABLE index_meta (
  key             TEXT PRIMARY KEY,
  value           TEXT
);
-- index_meta 里至少存一条 { key: "last_synced_git_sha", value: "<commit sha>" }
-- 用于增量更新（git diff from last_synced_git_sha to HEAD）
```

### 6.3 列表页

- 完全从 `content_index` 表读，**不扫文件系统**。
- SQL: `SELECT * FROM content_index WHERE type = ? AND deleted = 0 ORDER BY modified_at DESC`
- 单次查询 O(log n)，1 万条 rule 也毫秒级返回。

### 6.4 详情页

- 先查 `content_index` 拿当前元数据和 `latest_history_dirname`。
- 读文件 `rules/<id>/history/<latest_history_dirname>/main.md` 作为正文。
- 读 `attachments.json` 渲染附件列表。
- 附件文件按需从 pool 读取。

### 6.5 历史面板（详情页内的 Tab）

**能力：v1 只做"查看"**，不做恢复、不做 diff。

- 列出该 rule 的所有 history：`readdir rules/<id>/history/`（不排除软删，软删本身也是一条记录）
- 按目录名排序（目录名里的 timestamp 是升序的，倒序展示最新在上）
- 每条显示：
  - 时间（友好格式：`今天 10:30`、`2026-04-15` 等）
  - 修改者 displayName + userId 前 8 位区分（如 `张三 #a3f2b9c1`）
  - 如果是软删操作，显示 "删除了此内容" 的标签
- 点击某条 → 进入只读视图，渲染那条 history 的完整快照
- **不提供"恢复到此版本"按钮**（v1 排除）

### 6.6 索引同步（增量更新）

**时机：**
- app 启动时
- 每次 `git pull` / 本地 commit 成功后

**算法：**
1. 读 `index_meta.last_synced_git_sha`
2. 执行 `git diff --name-only <last_synced_git_sha> HEAD`
3. 对每个变化的文件路径：
   - 匹配 `rules/<id>/meta.json` → upsert content_index 的出生信息
   - 匹配 `rules/<id>/history/<dirname>/snapshot.json` → 如果这条 snapshot 的 modifiedAt 比当前 index 里的还新，更新 content_index
   - 匹配 `attachments-pool/...` → 忽略（附件按需读）
4. 更新 `last_synced_git_sha` 为当前 HEAD
5. 首次启动或 index 被删除时，走全量扫描（遍历所有 `rules/*/history/*/`）

## 七、冲突处理

### 7.1 物理冲突（git 层）

**不存在**，这是方案的核心保证。原因：
- 每次提交都是"新增一个 history 子目录"，不修改任何已有文件
- 目录名三段式保证跨用户、跨时间都不重名

**唯一剩下的 git-level 事件：** push 时 `non-fast-forward`（别人抢先 push 了）→ 客户端自动 `git pull --rebase` + retry，不需要用户感知。

### 7.2 语义覆盖（无法彻底消除，软提示处理）

**场景：** A 和 B 都基于 v3 编辑，A 先 push v4，B 稍后 push v5。按 timestamp 最大者为当前版本，B 的 v5 赢，A 的 v4 视为"历史版本"。

**时钟漂移不处理。** 接受"某些情况下本地时钟晚的用户会总是'赢'"的事实。对知识库类弱协作场景，这是可接受的。

**UI 侧必须做的提示：**

1. 用户点"编辑"进入弹窗时，记录**当前读取到的 latestHistoryDirname**（即用户基于哪个版本编辑的）。
2. 用户点"确定"后，**保存前先 `git pull`**，然后重新读该 rule 的最新 history。
3. 比较本地记录的 latestHistoryDirname 和 pull 后的最新 history：
   - 相同 → 没人改过，直接写入新 history + push
   - 不同 → 弹一个轻量提示模态框：
     > "{displayName} 在你之后改过这条内容。你的修改会成为最新版本。"
     - 按钮：[查看对方修改了什么] [继续保存]
     - 查看按钮：临时打开一个对比视图（显示对方最新 snapshot 的字段），用户看完可以选择合并再保存 or 直接覆盖保存
     - 继续保存：按当前用户输入生成新 history
4. **不做字段级合并**，不做强制 diff，保持流程轻量。

### 7.3 多端同一用户

同一 userId 在两台电脑同时编辑 → 等价于"两个不同用户编辑"的场景，按 §7.2 处理。因为 history 目录名里有 rand6 后缀，即使两端同一毫秒也不会撞。

## 八、Compaction（历史压实）

### 8.1 触发条件

三个触发并存：

1. **后台定时**：app 启动时检查 `lastCompactionAt`，距今 ≥ 24h 则触发一次全量 compaction。不要做成每小时跑。
2. **push 后条件触发**：每次成功 push 后，检查刚被修改的那条 rule 的 history 数量是否 > 阈值（默认 20），超过就对这一条跑一次局部 compaction。
3. **手动**：设置页提供 "整理历史记录" 按钮，点击跑全量 compaction，带进度条。

### 8.2 Compaction 算法

**对每条 rule 的 history：**

1. 按 `snapshot.json.modifiedAt` 升序排列。
2. 如果总数 ≤ **保留阈值**（默认 10 条），跳过。
3. 计算"要合并的区间"：除最新 N 条（默认 5 条）之外的所有条目，视为**旧历史**。
4. 取旧历史中**最新的一条**（紧邻保留区的那条）作为 "合并基线" 的内容。
5. 生成一条新的 history，命名：`<合并基线 timestamp>__0000...<32 位 0>...0000__compact`
   - userId 段用全 0 表示 "合并操作，非自然人"
   - rand6 段固定用字面量 `compact`
6. 这条新 history 的 snapshot.json / main.md / attachments.json 完全复制合并基线的内容。
7. 物理删除被合并的所有旧 history 目录。
8. 保留区（最新 N 条）不动。

**软删的 rule：**

- 如果一条 rule 的最新 history 是软删、且该软删距今 > **90 天**，整个 `rules/<id>/` 目录物理删除。

**git commit 规范：**

- message: `[synapse] compaction <count> rules`
- 所有 compaction 操作合并成一个 commit（一次 compaction 跑完一次 commit + push，不要每条 rule 一次 commit）

### 8.3 并发安全

- compaction 也由客户端执行（没有独立服务端）。
- compaction 开始前先 `git pull --rebase`。
- compaction 完成后 `git push`。
- 如果 push 失败（有人抢先 push 了普通变更）→ **直接放弃本轮 compaction**，不要 rebase 重试（合并操作和普通提交混合 rebase 容易出错）。下次触发再来。
- 这种"opportunistic + abort on conflict" 策略的前提是 **compaction 是幂等的**：下次再跑同样产生一致的结果。

### 8.4 Compaction 的时机和影响

- **用户可能正在浏览某条即将被合并的旧历史** → 合并后目录名变了，用户刷新时那条历史消失。UI 要处理 "这条历史已被整理" 的空状态，不 crash。
- **合并不改变"当前版本"**（保留区没动），所以列表页和详情页展示不受影响。

## 九、附件池 GC

### 9.1 触发

和 compaction 同步触发（同一入口），但算法独立。

### 9.2 Mark-Sweep 算法

**Phase 1 - Mark：**

1. 遍历仓库所有 `rules/*/history/*/attachments.json`，收集所有被引用的 sha256 → 集合 `referenced`
2. 遍历 `attachments-pool/` 下所有文件，拿到 sha256 → 集合 `all`
3. `unreferenced = all - referenced`
4. 对 `unreferenced` 中每个 sha256，查文件的 `mtime`：
   - 如果 `mtime` 距今 < **24 小时**，跳过（保留安全窗口）
   - 否则加入候选删除列表 `toDelete`

**Phase 2 - Sweep：**

5. 对 `toDelete` 中每个 sha256，物理删除 `attachments-pool/<分片>/<sha256>`
6. 如果分片目录空了，删除空目录
7. git commit 所有删除，message: `[synapse] gc <count> attachments`
8. push（失败就放弃本轮）

### 9.3 安全性

- 24 小时窗口足够覆盖 "客户端 commit 了但还没 push" 的场景
- 读附件时，**如果 pool 里缺失，不 crash**，显示 "附件已缺失"

## 十一、错误处理规范

### 11.1 分类

| 类型 | 处理方式 | 例子 |
|---|---|---|
| **可重试网络错误** | 进 pending_pushes 队列，工具栏按钮亮起 | push 超时、non-fast-forward |
| **用户需立即感知的错误** | 全局错误模态框 | commit 失败、仓库损坏、ID 恢复失败 |
| **轻量反馈** | Toast | 复制成功、保存成功、已同步 |
| **可忽略错误** | 日志记录 | 附件 pool 里偶发缺失（降级显示） |

### 11.2 通用规则

- **所有 IPC 调用都必须包 try/catch**，不允许让异常穿透到 renderer 而没有明确处理
- **Electron main 里的每个 git 命令调用都要区分 stdout / stderr / exit code**，不要只看 exit code
- **从不吞错**：遇到不确定如何处理的错误，优先用全局错误模态框告知用户
- **从不用 alert()**：统一用 shadcn Dialog
- **从不在 console.log 做生产错误上报**，用项目统一的 logging（如果项目有的话；没有就加到 logger service 里）

## 十二、迁移方案

### 12.1 目标

把现有的仓库结构（老 PR 流程下的目录）迁移到新方案，**零数据丢失**。

### 12.2 老结构（当前）

根据 `electron/services/content-create-service.ts` 的逻辑推断：

```
rules/<id>/
  meta.json            ← 包含 title/description 等可变字段
  main.md
  <附件散落>            ← skill 才有

skills/<id>/
  meta.json
  main.md
  <附件>
```

### 12.3 迁移脚本

**独立脚本**，放在 `scripts/migrate-to-history-structure.ts`，手动由维护者跑一次。

**算法（对每条老 rule / skill）：**

1. 读旧 `meta.json`，拆分字段：
   - **固定字段** → 新 `meta.json`：`id`、`type`、`createdAt`、`createdBy`、`createdByDisplayName`
     - `createdBy` 没有对应数据 → 用全 0 UUID 作为 "legacy" 标识：`00000000000000000000000000000000`
     - `createdByDisplayName` → 复制旧 `author` 字段
   - **可变字段** → 首条 history 的 `snapshot.json`：`title`、`description`、`category`、`icon`、`iconBg`
2. 生成首条 history 目录名：
   - timestamp 用旧 `createdAt` 转 UTC 紧凑格式
   - userId 用 `00000000000000000000000000000000`
   - rand6 用固定字面量 `legacy`（或随机，都可以）
   - 例：`20260110T120000Z__00000000000000000000000000000000__legacy`
3. 把旧 `main.md` 移动到 `history/<dirname>/main.md`
4. 扫描旧 skill 目录下的附件：
   - 对每个附件计算 sha256
   - 写入 `attachments-pool/<分片>/<sha256>`
   - 原附件从老目录删除
   - 在 `history/<dirname>/attachments.json` 里登记
5. 删除老的 `meta.json`、`main.md`（已经迁到 history 里了）
6. 确保 `rules/<id>/` 下只剩 `meta.json` + `history/` 两项

**测试：**
- 迁移前先在测试仓库跑一遍
- 迁移后用 app 打开，验证每条 rule 列表可见、详情可读、历史面板显示 1 条"legacy" 历史
- git commit 所有变更，message: `[synapse] migration to history-based storage`

### 12.4 回滚

- 迁移脚本**必须**在独立分支跑，主分支先 tag 一个 `pre-migration`，有问题直接 git reset 回去

## 十四、反模式警告（不要这样做）

**以下列表里的每一条都有具体代价，已经在方案讨论阶段排除过。实施时不要"为了简化"又绕回去。**

### 14.1 数据层

- ❌ 把 history 列表存在 `meta.json` 里做索引 → 共享写入点，必然 merge conflict
- ❌ 用 patch/diff 存 history（只存变更字段） → 删除中间 history 后依赖链断裂
- ❌ 用 title / slug 做 rule 目录名 → 改名困难、同名创建冲突
- ❌ 附件散落在 rule / skill 目录下 → 无法跨版本复用、GC 困难
- ❌ 附件用原文件名做 pool key → 无法去重、容易撞名
- ❌ 仓库里有任何 "index.json" / "categories.json" 这种汇总文件 → 共享写入点

### 14.2 用户 ID

- ❌ 用 git config 的 user.name / user.email 作为用户身份 → 回到了要用户配置 git 的老问题
- ❌ userId 允许混合大小写 / 带横线 / 长度不固定 → 文件系统大小写敏感性差异会出事
- ❌ ID 丢失时自动合并到 "默认用户"  → 数据归属混乱
- ❌ 首次启动静默生成 ID 不强引导 → 用户很快就会丢失身份

### 14.3 冲突和并发

- ❌ 试图做 "自动字段级合并"（A 改 title、B 改 body、合并） → 复杂度极高，收益小
- ❌ 保存时不先 pull → 新版本覆盖了别人的修改，用户毫无感知
- ❌ push 失败自动无限重试 → 网络差时死循环

### 14.4 UI

- ❌ 历史面板 v1 就做 "恢复" 按钮 → 容易被误用覆盖别人的改动
- ❌ 历史面板做 diff 视图 → 非技术用户理解成本高，v1 不做
- ❌ 错误用 alert() 或 toast 报 → alert 丑，toast 一闪而过漏信息
- ❌ 推送按钮常亮不区分状态 → 用户不知道是不是有变更待同步
- ❌ 首次启动允许跳过 ID 引导 → 用户丢失后无法追溯

### 14.5 git 操作

- ❌ 用 isomorphic-git 替换当前的 spawn git 方式（除非用户要求） → 当前 spawn 方式工作良好，不要增加依赖
- ❌ commit message 里塞结构化信息（用户名、时间等） → 这些都在 snapshot.json 里了，commit message 保持简洁
- ❌ compaction 失败后 rebase 重试 → 合并操作和普通提交混合 rebase 不稳定，直接放弃
- ❌ 用 git submodule / git lfs → 过度复杂，附件池已经够用

### 14.6 Compaction / GC

- ❌ GC 立即删除无引用附件 → race condition，必须 24h 安全窗口
- ❌ compaction 每次 push 都无条件跑 → 增加 push 竞争，只在阈值触发
- ❌ compaction 跑成多个小 commit → 污染 git log，合成单个 commit

## 十五、附录

### 15.1 生成 UUID 无横线的代码示例

```typescript
function generateUserId(): string {
  // Node.js 14.17+ 和 所有现代浏览器
  return crypto.randomUUID().replace(/-/g, "")
}

function normalizeUserId(input: string): string | null {
  const cleaned = input.trim().toLowerCase().replace(/-/g, "")
  if (!/^[0-9a-f]{32}$/.test(cleaned)) return null
  return cleaned
}
```

### 15.2 生成 history 目录名的代码示例

```typescript
import { randomBytes } from "node:crypto"

function buildHistoryDirname(userId: string, at: Date): string {
  const ts = at.toISOString().replace(/[-:]/g, "").slice(0, 15) + "Z"
  // 从 "2026-04-18T10:30:00.000Z" -> "20260418T103000Z"
  const rand6 = randomBytes(3).toString("hex")
  return `${ts}__${userId}__${rand6}`
}
```

### 15.3 sha256 计算（流式）

```typescript
import { createHash } from "node:crypto"
import { createReadStream } from "node:fs"

async function sha256File(path: string): Promise<string> {
  return new Promise((resolve, reject) => {
    const hash = createHash("sha256")
    const stream = createReadStream(path)
    stream.on("data", (chunk) => hash.update(chunk))
    stream.on("end", () => resolve(hash.digest("hex")))
    stream.on("error", reject)
  })
}
```

### 15.4 附件池路径组装

```typescript
function poolPath(sha256: string): string {
  return `attachments-pool/${sha256.slice(0, 2)}/${sha256.slice(2, 4)}/${sha256}`
}
```

### 15.5 决策归档（供追溯）

| 决策 | 结论 | 依据 |
|---|---|---|
| 时钟漂移处理 | 不处理，按本地时间 | 用户接受 "后改赢" 的弱一致性，简化实现 |
| 编辑粒度 | 弹窗点"确定" = 一次修改 | 对非技术用户最直觉 |
| 修改说明字段 | 不要 | 增加摩擦，自动推断够用 |
| 历史面板能力 | v1 只做查看 | 恢复/diff v1 不做，控制复杂度 |
| 软删回收站 | 不做 | 列表彻底隐藏，90 天后物理清 |
| 归档形式 | 真压实合并，不归档 tar | 不会有频繁改几百次的内容 |
| Compaction 触发 | 定时+push 条件+手动，三者都做 | 兼顾自动和应急 |
| 冲突提示强度 | 中等（保存前 pull + 轻提示） | 非技术用户可接受，无强合并 UI |
| 多 ID 切换 | v1 不支持多 profile | 简化 |
| 推送模型 | 立即 push，失败进队列 | 协作即时性优先 |
| 退出时待推送 | 提示但允许退出 | 不强制阻塞用户 |
| 首次启动引导 | 强制引导，不可跳过 | 身份凭证的重要性要打到用户脸上 |
| ID 丢失恢复 | 文件不存在自动生成；字段损坏让用户选 | 避免意外覆盖备份 |

## 结束语

本方案的核心价值是：**用文件结构层面的严格约束，换取整个协作链路的简化**。一旦实施到位：

- 用户不需要知道 git、PR、Token、分支
- 非开发背景的用户也能安心使用
- 长期维护成本可控（靠 compaction 和 GC）
- 审计能力完整（每次修改都有 full snapshot）

如果实施过程中对任何细节不确定，**回来问清楚，不要自己做决定**。本方案的每一条约束都是有代价的选择，随意修改会破坏整体性。
