# 仓库单一来源集中管理改造方案

## 1. 目标

本次改造的目标只有三个：

1. 仓库域实现单一来源
2. 仓库相关行为集中管理
3. UI 只负责展示和交互，不直接编排仓库业务流程

这里的“仓库域”指：

- `repositories`
- `activeRepoUuid`
- `activeRepository`
- 仓库本地状态：`ready / missing / isGitRepository`
- 仓库操作状态：`sync / push / initialize / maintenance`
- `pending pushes`
- 切换仓库时的内容刷新与状态迁移

## 3. 已确认的问题

### 3.1 同一份仓库状态存在两套读法

这是当前最关键的问题。

以前 toolbar 的显示逻辑就因为一边读 `RepositoryManager`，一边别的模块读 `AppConfigProvider`，出现过：

- 内容已经按当前仓库显示
- 但 toolbar 仍然认为没有激活仓库
- 刷新按钮不显示

这类问题本质上不是“按钮逻辑写错了”，而是“状态来源分叉了”。

### 3.2 UI 直接改仓库配置

当前有多个 UI 组件直接调用：

- `useAppConfig().updateConfig(...)`

去修改：

- `repositories`
- `activeRepoUuid`

这意味着：

- UI 要知道仓库配置结构
- UI 要自己决定什么时候只改配置
- UI 要自己决定切换后是否 reload
- UI 要自己决定是否需要刷新仓库状态

这和“UI 只负责 UI”是冲突的。

### 3.3 切换仓库流程没有真正下沉

当前切换链路主要在：

- [src/app-shell/active-repository-switch.tsx](/Users/liyang/Documents/code/github/Synapse/src/app-shell/active-repository-switch.tsx)

现状是：

1. UI provider 做校验
2. UI provider 做 onboarding 前置判断
3. UI provider 直接改 `activeRepoUuid`
4. UI provider 触发 `window.location.reload()`

这说明真正的“切换仓库业务流程”还没有收口到仓库域中心。

### 3.4 仓库切换依赖整页 reload

当前切换后仍然依赖：

- [src/app-shell/active-repository-switch.tsx](/Users/liyang/Documents/code/github/Synapse/src/app-shell/active-repository-switch.tsx)

中的 `window.location.reload()`

这会带来几个问题：

- 状态初始化成本大
- tab、dialog、临时 UI 状态被整体重置
- 容易掩盖真实的状态同步问题
- 后续要做更平滑的壳层体验会被卡住

## 4. 改造原则

本次改造遵守以下原则：

1. 不新建第二套仓库架构
2. 以 `RepositoryManager` 为唯一仓库域中心
3. 先收口读写入口，再处理 reload
4. UI 不再直接写仓库配置
5. 改造过程分阶段，避免一次性大爆炸

## 5. 目标结构

### 5.1 唯一中心

仓库域唯一中心：

- [src/app-shell/repository-manager.ts](/Users/liyang/Documents/code/github/Synapse/src/app-shell/repository-manager.ts)

它负责：

- 仓库配置读写
- 激活仓库切换
- 仓库状态刷新
- operation 管理
- pending pushes 管理
- 内容刷新
- 仓库域订阅分发

### 5.2 UI 只通过 hooks / actions 访问

UI 只能通过仓库域 hooks 访问仓库信息，例如：

- `useRepositoryList()`
- `useActiveRepository()`
- `useActiveRepositoryState()`
- `useRepositoryState(uuid)`
- `useRepositoryOperation(uuid)`
- `usePendingPushes(uuid)`
- `useRepositoryActions()`

其中 `useRepositoryActions()` 统一暴露命令：

- `switchActiveRepository`
- `setActiveRepository`
- `clearActiveRepository`
- `addRepository`
- `removeRepository`
- `updateRepository`
- `replaceRepositories`
- `syncRepository`
- `pushRepository`
- `runMaintenance`
- `refreshRepositoryStates`

### 5.3 AppConfigProvider 退回到非仓库配置

`AppConfigProvider` 后续只负责：

- `global.themeMode`
- `global.projects`
- `favorites`
- 其他非仓库配置

不再作为仓库域读写入口。

## Phase 3：收缩 ActiveRepositorySwitchProvider

### 目标

让它只承担 UI 编排，不承担仓库切换业务写入。

### 具体修改

文件：

- [src/app-shell/active-repository-switch.tsx](/Users/liyang/Documents/code/github/Synapse/src/app-shell/active-repository-switch.tsx)

调整后职责只保留：

- `isSwitchingRepository`
- `switchingRepositoryUuid`

以下职责下沉到 `RepositoryManager`：

- 设置 active repo
- 清理旧内容快照

- 刷新内容列表

如果 onboarding 前置校验本质属于仓库切换业务，也建议逐步继续下沉。

### 验收标准

- provider 不再直接调用仓库域 `updateConfig`
- provider 不再自己决定仓库切换后的 refresh 链路

## Phase 4：去掉切换仓库对 reload 的依赖

### 目标

仓库切换变成一次正常的状态迁移，而不是整页重启。

### 具体修改

#### 6.5 切换逻辑改为纯状态迁移

`switchActiveRepository()` 内部统一完成：

1. 校验目标仓库
2. 更新 active repo
3. 清空旧内容快照
4. 刷新 repository states
5. 刷新内容列表
6. 通知 identity / profile 等依赖 active repo 的模块重新同步

#### 6.6 依赖 active repo 的模块改为订阅式刷新

重点检查：

- [src/app-shell/identity-context.tsx](/Users/liyang/Documents/code/github/Synapse/src/app-shell/identity-context.tsx)
- content browser
- content detail
- settings repository panels

要求：

- 依赖 `activeRepository` 变化自动刷新
- 不依赖 `window.location.reload()`

### 验收标准

- 仓库切换不再调用 `window.location.reload()`
- 切换后内容列表、toolbar、identity、history 相关 UI 自动跟随更新

## 8. 风险与注意事项

### 8.1 不要一把删掉 AppConfigProvider

它目前仍然承担非仓库配置职责，直接删会扩大改动面。

正确做法是：

- 先让仓库域退出 `AppConfigProvider`
- 再保留它处理剩余配置

### 8.2 不要先碰 UI 样式

本次改造是状态与职责收口，不是 UI 重设计。

### 8.3 不要一次性去掉所有 reload

先统一读写入口，再去掉 reload，风险更低。

## 9. 本次建议的实施顺序

建议实际执行顺序如下：

1. 先补齐 repository hooks，只读接口完整化
2. 把仓库相关读口从 `useAppConfig()` 迁到 repository hooks
3. 把仓库相关写口从 `updateConfig()` 迁到 repository actions
4. 收缩 `ActiveRepositorySwitchProvider`
5. 去掉仓库切换 reload

## 10. 最终状态定义

完成后应满足以下约束：

- 仓库域只有一个事实来源：`RepositoryManager`
- UI 只通过 repository hooks 和 actions 操作仓库域
- `AppConfigProvider` 不再承载仓库域读写
- 仓库切换、刷新、状态更新走一条统一链路
- UI 只负责展示、交互、提示，不负责仓库业务编排
