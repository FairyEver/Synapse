**Synapse**

### 品牌关键词

* 人工智能
* 连接

* 连接知识、规则、技能与工具
* 连接团队成员与共享内容

# 2. 产品定位

Synapse 是一个面向团队内部使用的桌面应用，围绕“本地目录 + Git 工作流”管理和分发两类内容：

* **Rules**
* **Skills**

它不是传统 CMS，也不是单纯知识库工具，而更接近一个：

> **基于本地目录与 Git 工作流的 AI Rules / Skills 分发与共享平台**

并且后续可以扩展为：

> **本地 AI 工作流平台**

当前阶段，Synapse 的核心用途是：

1. 从用户选择的本地目录读取并展示团队共享的 Rules 和 Skills
2. 允许用户创建自己的 Rule 或 Skill
3. 通过程序在后台创建 Git 变更并发起 PR
4. 由管理员在 Git 后台完成审核合并
5. 让团队成员把这些 Rules / Skills 下载或安装到本地编辑器环境中

# 7. 模块代码结构原则

Rules、Skills、Settings 三块代码必须做成高度独立的模块，原因如下：

* 未来可能增加第四个、第五个模块
* 每个模块有自己的逻辑、状态、读取方式和 UI
* 避免后期所有逻辑都耦合在一个大页面里

也就是说，软件架构上应采用：

> **壳层 + 独立业务模块**

而不是“一个页面里硬塞多个 Tab”。

# 8. 数据源与仓库模型

## 8.1 支持多个本地目录

软件允许用户配置多个本地目录作为内容源。

## 8.2 同时只激活一个目录

虽然可以配置多个目录，但任意时刻只能打开一个目录作为当前数据源。

## 8.3 目录直接来自用户电脑

软件不维护自己的仓库缓存目录，而是直接引用用户选择的本地目录。

## 8.4 Git 能力是附加能力

目录选择完成后，软件会进一步判断该目录是否位于 Git 工作区中。

最终方案：

* 在新增一个目录配置时，软件先生成一个 **uuid** 作为内部稳定标识
* 配置中保存 `localPath`，直接指向用户本地目录
* 如果目录具备 Git 能力，则启用刷新、创建、提交、PR 等流程
* 如果目录不是 Git 仓库，则仍可作为本地内容源浏览，但 Git 相关操作禁用

# 9. 设置项与仓库切换边界

切换仓库时，不是所有设置都跟着切换，必须区分“仓库上下文设置”和“全局设置”。

## 9.1 跟随仓库切换的设置

以下配置属于仓库上下文，应随仓库切换：

* 本地目录路径
* Rules 主目录名
* Skills 主目录名

## 9.2 不跟随仓库切换的设置

以下配置属于软件级全局设置，不应随仓库切换：

* 编辑器安装逻辑
* 编辑器适配规则
* 项目列表
* 软件自身其他全局行为设置

## 9.3 切换仓库的行为

当前方案：

* 切换当前激活目录后
* **直接 reload / 重载软件界面**

不做复杂的无缝热切换。

# 10. 本地目录接入与同步

## 10.1 首次使用

用户第一次配置目录后，需要先完成本地目录选择与 Git 状态识别。

## 10.2 目录接入后要立即反馈状态

选择目录后需要立即告诉用户：

* 目录是否存在
* 当前目录是否为 Git 仓库
* 是否可以执行同步与后续创建

## 10.3 软件不负责仓库下载

仓库下载、初始化、切换凭证等动作不在 Synapse 内完成。

这些事情交给用户自己熟悉的 Git 工具，例如：

* 终端
* SourceTree
* GitHub Desktop
* 其他 GUI Git 客户端

## 10.4 刷新机制

当前不做自动同步，使用手动刷新。

### 刷新按钮位置

顶部栏右侧操作区。

### 刷新行为

当前 MVP 中刷新只做：

* 拉取当前 Git 工作区主分支最新内容
* 刷新 Rules / Skills 列表
* 刷新分类统计

### 当前不做

* 不检查自己历史提交的 PR 状态
* 不展示待审核状态
* 不展示未合并内容

## 10.5 接入与同步失败场景

目录接入或同步失败时，必须：

* 清晰提示错误原因
* 支持用户重试或回到自己的 Git 工具继续处理
* 不要求在 Synapse 内补输账户信息
* 整体交互应更接近“检测本地目录 + 调用系统 Git”的体验，而不是软件内仓库下载向导

# 11. Git 凭证策略

当前软件是团队内部使用，用户使用自己公司的 Git 账号访问仓库。

## 11.1 用户身份显示

产品中显示的作者名，不直接显示 Git 账号，而是显示用户自己设置的称呼 / 昵称。

## 11.2 Git 凭证存储原则

软件尽量不自己明文保存用户名密码。

更合理的方向是：

* 依赖系统凭证
* 或使用 Git 环境已有凭证能力

## 11.3 元数据中保留 Git 身份

虽然 UI 显示昵称，但元数据里仍可保留 Git 账号信息，用于系统追踪和排查。

# 12. 内容模型总览

软件中管理两类内容：

## 12.1 Rule

* 纯文本内容
* 本质是 Markdown 文本
* 结构简单
* 不允许上传 md 文件
* 不允许上传其他附件
* 用户只能把内容复制粘贴到输入框中

## 12.2 Skill

* 多文件能力包
* 必须有主说明文本
* 除主说明文本外，允许拖入附件
* 支持多个文件
* 保留拖入时的原有目录结构

# 13. 仓库目录结构

Rules 和 Skills 对应当前激活目录中的两个主目录，这两个主目录名称由设置指定。

例如逻辑上是：

```text
repo/
  rules/
  skills/
```

但真实目录名可配置。

---

# 14. Rules / Skills 主目录内结构

Rules 和 Skills 主目录下都采用 **扁平结构**。

也就是说：

* 不再进行多层业务子目录嵌套
* 每个内容项占一个独立目录
* 所有内容项都平铺在主目录下

例如：

```text
rules/
  <id>/
  <id>/
  <id>/

skills/
  <id>/
  <id>/
  <id>/
```

---

# 15. 内容项唯一 ID 设计

## 15.1 ID 组成

最终确定使用：

> **uuid + timestamp**

## 15.2 目录命名格式

目录名格式为：

`uuid_timestamp`

中间使用下划线 `_`，不用横线。

## 15.3 ID 使用位置

同一个内容项的 ID 同时用于：

* 目录名
* `meta.json` 中的 `id`

并且要求两者 **强一致**。

---

# 16. Rule 目录结构

Rule 目录严格固定，只允许两个文件：

```text
rules/
  <id>/
    meta.json
    main.md
```

### 说明

* `main.md` 是正文
* `meta.json` 是元信息
* 不允许存在第三个文件
* Rule 内容由程序内部生成，不让用户自行上传 md 文件

---

# 17. Skill 目录结构

Skill 目录至少包含：

```text
skills/
  <id>/
    meta.json
    main.md
    ...其他文件
```

### 说明

* `main.md` 是 Skill 主说明文件
* `meta.json` 是元信息
* 其他文件是用户拖入的附件
* 保留用户拖入时原始目录结构

---

# 18. 固定文件名策略

Rule 和 Skill 的主文件统一采用：

* `main.md`

元数据文件统一采用：

* `meta.json`

这是最终确定的固定命名，不再变化。

---

# 19. Meta 结构设计

元数据存储在 `meta.json` 中。

## 19.1 结构形式

采用 **轻度分组**，不是完全平铺，也不做过度复杂嵌套。

## 19.2 meta 至少应包含的信息

必须能覆盖产品展示和系统处理所需字段，包括但不限于：

* `id`
* `type`（rule / skill）
* `title`
* `description`
* `category`
* `icon`
* `iconBg`
* `author`（展示昵称）
* `gitUser`
* `createdAt`

你后续要求中的原则是：

> 凡是产品展示或系统逻辑中会用到的信息，都应进入 `meta.json`

---

# 20. 分类体系

分类最终不再采用“用户自由输入 + 扫描归并”的方案，而改为更可控的方案。

## 20.1 Rules 和 Skills 拥有独立分类体系

* Rules 一套分类
* Skills 一套分类

两者分开管理。

## 20.2 分类来源

分类不再由扫描所有 `meta.json` 反推出集合，而应来自一个独立配置文件。

即：

* 软件内置分类配置
* 开发者维护分类
* 发新版时可增加分类

## 20.3 用户创建时的分类选择

用户创建 Rule / Skill 时，从预置分类中选择，不鼓励自由输入。

## 20.4 左侧分类栏来源

左侧分类栏的“分类集合”来自配置文件，再结合当前仓库内容统计数量。

也就是：

* 分类定义：配置文件
* 分类数量：扫描 `meta.json` 统计

# 26. Rule 创建表单

* 标题（必填）
* 简介（必填）
* 分类（必填）
* 图标（必填）
* 背景色（必填）

提交后不是直接写入主分支，而是：

* 程序在后台创建新目录

* 创建 PR

# 27. Skill 创建表单

Skill 创建时至少包含：

* 标题（必填）
* 简介（必填）
* 分类（必填）
* 图标（必填）
* 背景色（必填）
* 主说明文本输入框（必填）
* 附件拖拽区域（可附加多个文件）

## 27.1 附件规则

* 支持拖入多个文件

* 文件类型不限制

## 27.2 Skill 目录写入

提交后：

* 生成 `main.md`
* 生成 `meta.json`
* 写入所有附件
* 保留附件层级结构
* 创建 Git 变更并发起 PR

# 28. 提交流程与审核机制

Synapse 的提交机制基于 Git PR 流程。

## 28.1 用户提交不等于正式入库

用户在软件里点击提交后，只是生成一个待审核的提交候选。

## 28.2 正式入库条件

只有管理员在 Git 后台或管理界面中完成 PR 合并，这个 Rule / Skill 才算真正入库。

## 28.3 当前软件职责

软件只负责：

* 创建文件
* 创建 Git 变更
* 发起 PR

## 28.4 当前软件不做

* 不做管理员审核面板
* 不做 PR 状态管理
* 不做待审核内容列表
* 不展示未合并内容

## 28.5 提交成功反馈

当前只需要给用户一个简单反馈，例如：

* 提交成功
* 等待审核

当前不需要返回 PR 链接，不需要展示 PR 编号。

# 29. PR 分支规则

创建 PR 时需要自动创建分支。

你给出的方向是：

* 分支命名要有规则
* 第一层表示内容类型
* 第二层表示操作类型，目前只有 add
* 后面带用户名和时间戳

可抽象成类似：

`<type>/<action>/<displayName>/<timestamp>`

例如逻辑方向：

* `rule/add/用户名/时间戳`
* `skill/add/用户名/时间戳`

这里的用户名可使用用户给自己设置的昵称。

目标分支为当前仓库主分支（你讨论中说的是 main / 主分支）。

选择某个编辑器后，不能直接安装，还要再选择作用域。

如果该编辑器支持全局目录，则安装到全局目标位置。

## 34.3 项目安装

如果选择项目，则再选择某个本地项目路径，并把文件按该编辑器规则安装到项目目录中的对应位置。

# 35. 项目系统

## 35.1 项目的本质

项目就是用户电脑上的一个本地文件夹。

## 35.2 项目不绑定某个编辑器

项目列表是全局共享的，不按编辑器分组。

同一个项目路径可以同时用于：

* Cursor
* Codex
* 其他编辑器

因为现实里同一个文件夹可以被多个编辑器打开。

## 35.3 项目配置

用户可以在软件里维护多个项目路径，并给它们设置别名。

# 36. 编辑器适配策略

这是一个关键决策。

## 36.1 不做 UI 可配置安装规则

编辑器安装逻辑不放给用户在 Settings 中自由配置。

## 36.2 写死在代码里

每个编辑器的识别方式、全局路径、安装规则，都应该由代码中写死的 adapter 来处理。

可以采用类似：

* editorAdapters
* map / object
* 每个编辑器一个配置对象
* 内部可带字段或函数

## 36.3 原因

* 编辑器规则本身不应由用户手改
* 减少设置复杂度
* 降低错误配置风险
* 更适合后续由开发者统一维护

## 36.4 后续实现要求

真正编码时，需要调研各编辑器对 rule / skill 的真实目录规则，再写 adapter。

# 44. 安装覆盖策略

## 44.1 Rule

按目标位置写入对应文件。

## 44.2 Skill

Skill 安装时采用 **整体覆盖** 策略。

### 具体含义

如果目标目录中已经存在该 Skill 对应目录：

* 不做增量合并
* 不做只替换部分文件
* 而是把旧目录整体替换成当前 Skill 的完整目录结构

也就是说，如果旧 Skill 有 3 个文件，新 Skill 只有 2 个文件，那么安装后只保留这 2 个新文件，旧文件全部消失。

这是一个明确的 **破坏性覆盖策略**。

# 50. 当前方案的可行性判断

从产品和工程角度看，当前方案是 **可行的**。

## 成立的原因

1. Git 作为真相源，适合团队共享与版本追踪
2. PR 审核模型成熟，适合内部治理
3. Electron 非常适合本地文件、Git、安装分发场景
4. Rule / Skill 二分法清晰，符合不同内容形态
5. Adapter 写死在代码中，有利于控制复杂度
6. 分类配置文件化后，治理明显更稳

# 51. 当前方案的主要设计优点

## 51.1 数据源清晰

本地目录就是直接内容源，Git 是协作与同步通道，边界清楚。

## 51.2 协作边界清晰

用户负责提交，管理员负责合并。

## 51.3 产品范围收得合理

先只做“浏览 + 新建 + PR + 下载/安装”，避免一开始做得过大。

## 51.4 Skill 和 Rule 区分合理

把纯文本规则和多文件能力包分开，是这套产品里非常关键的设计。

## 51.5 编辑器安装规则写死是正确决策

避免用户配置混乱，减少大量维护成本。

# 52. 当前方案中已知且接受的限制

以下问题当前是明确存在但你接受的：

## 52.1 分类治理有限

虽然改成了配置文件驱动，但如果未来分类继续增加，仍需要人为维护。

## 52.2 不做 PR 可见性

用户提交后只能得到“已提交、待审核”反馈，不能在软件中看到更进一步状态。

## 52.3 Skill 覆盖策略是破坏性的

安装 Skill 时会直接替换整个旧目录。

## 52.4 不做草稿系统

当前阶段未正式纳入自动草稿恢复机制。

## 52.5 不做修改 / 删除流程

MVP 只允许新增。

# 53. 当前应特别注意的技术点

## 53.1 Git 能力只对 Git 目录启用

目录本身可以不是 Git 仓库，但这时刷新、创建、提交和 PR 能力都必须禁用。

## 53.2 本地配置与仓库上下文要严格分层

避免后面代码混乱。

## 53.3 编辑器适配必须基于真实规则调研

不能靠猜路径。

## 53.4 Skill 安装需要完整替换逻辑

不要误写成局部覆盖。

## 53.5 文件类型虽不限，但单文件大小必须限制 10MB

避免仓库和下载问题。

# 54. 最终产品骨架总结

Synapse 当前版本应被实现为：

一个基于 Electron 的桌面应用，使用 React + Tailwind + shadcn/ui 构建界面，支持配置多个本地目录但同时只激活一个目录。软件从当前目录中读取 Rules 和 Skills 两类内容，以应用商店式界面展示。若当前目录具备 Git 能力，则允许同步、创建内容、生成 Git 变更并发起 PR；若当前目录不是 Git 仓库，则保留本地浏览能力，但禁用 Git 相关操作。用户可将已入库内容下载到本地，或通过写死在代码中的编辑器适配规则安装到全局或项目目录中。Settings 使用左侧分类 + 右侧内容的可扩展结构，所有用户配置持久化到本地 JSON 文件中。软件自带更新检查，并通过 GitHub Actions 实现自动打包和发布。
