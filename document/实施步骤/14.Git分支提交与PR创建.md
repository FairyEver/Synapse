# 步骤 14：Git 分支提交与 PR 创建

## 目标

完成“写入内容之后如何变成待审核提交”的 Git 工作流，包括分支创建、提交、推送和发起 PR。这是产品设计文档第 28、29、46 节的实现。前提是当前激活目录已经是可用的本地 Git 工作区。

## 要做的事

### 14.1 Git 提交流程封装

- 在主进程中封装完整提交流程：
  1. 确认当前仓库工作区状态
  2. 基于主分支创建新分支
  3. 写入文件
  4. `git add`
  5. `git commit`
  6. `git push`
  7. 调用平台 API 创建 PR

### 14.2 分支命名规则

- 分支命名遵循产品约定：

```text
<type>/<action>/<displayName>/<timestamp>
```

- 例如：
  - `rule/add/zhangsan/20260416213015`
  - `skill/add/lucy/20260416213540`

- 其中：
  - `type` 只可能是 `rule` 或 `skill`
  - `action` 当前固定为 `add`
  - `displayName` 取用户昵称，但需要做分支名安全清洗

### 14.3 目标分支选择

- 当前 MVP 以仓库主分支为 PR 目标
- 默认按 `main` 处理
- 为了降低兼容风险，实际实现时最好预留一层“默认目标分支”配置或自动检测能力

### 14.4 Commit 信息规范

- Commit message 需要统一格式，便于后续审查，例如：
  - `feat(rule): add <id>`
  - `feat(skill): add <id>`

- 当前不必做复杂 commit body

### 14.5 PR 创建能力

- MVP 建议先以 GitHub 为首个支持平台
- 发起 PR 时至少包含：
  - PR 标题
  - 源分支
  - 目标分支
  - 简短描述

- 这里要在代码结构上预留 provider 抽象，避免以后支持 GitLab 时全部重写

### 14.6 提交成功反馈

- 用户提交成功后，只需要简单反馈：
  - 提交成功
  - 等待审核

- 当前不需要展示 PR 编号，也不需要展示 PR 链接

### 14.7 失败与重试

- 如果 `push` 或 PR 创建失败：
  - 保留可重试上下文
  - 给出明确错误原因
  - 允许用户重新提交

## 注意事项

- 当前阶段不做软件内 PR 状态查看，也不做待审核列表
- 提交成功但未合并的内容，不应出现在软件正式列表中
- 当前目录不是 Git 仓库时，整个提交流程不应被触发
- 分支名中的昵称必须做安全清洗，避免空格、中文符号、斜杠等直接进入 Git 分支名
- Git 操作和平台 API 调用都属于高失败率环节，错误提示必须足够具体
- 如果本地 Git 工作区未同步到最新主分支，提交流程前应先确认基线，避免在旧状态上开分支

## 验收标准

1. 创建内容后能自动生成新分支
2. 分支名符合 `<type>/<action>/<displayName>/<timestamp>` 规则
3. 内容能被提交并推送到远端
4. 系统能自动创建 PR
5. 用户端只看到简单成功反馈，不展示未合并内容到正式列表
