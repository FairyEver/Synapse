# 步骤 7：内容数据模型与解析

## 目标

定义 Rule 和 Skill 的数据模型，实现从当前激活本地目录中扫描、解析内容的能力。这是产品设计文档第 12-19 节的实现。

## 要做的事

### 7.1 数据模型定义

#### Rule 类型

```typescript
interface RuleMeta {
  id: string;                // uuid_timestamp 格式
  type: 'rule';
  title: string;
  description: string;
  category: string;
  icon: string;
  iconBg: string;
  author: string;            // 显示昵称
  gitUser: string;           // Git 账号，用于系统追踪
  createdAt: string;         // ISO 时间戳
}
```

#### Skill 类型

```typescript
interface SkillMeta {
  id: string;
  type: 'skill';
  title: string;
  description: string;
  category: string;
  icon: string;
  iconBg: string;
  author: string;
  gitUser: string;
  createdAt: string;
  files: string[];           // 附件文件列表（相对路径）
}
```

### 7.2 目录结构约定

根据产品设计第 13-17 节：

```
repo/
  rules/                     # Rules 主目录（目录名可配置）
    <uuid_timestamp>/        # 每个 Rule 一个目录
      meta.json
      main.md
  skills/                    # Skills 主目录（目录名可配置）
    <uuid_timestamp>/        # 每个 Skill 一个目录
      meta.json
      main.md
      ...其他附件
```

- 主目录下采用**扁平结构**，不嵌套子目录分组
- 每个内容项以 `uuid_timestamp` 作为目录名
- 目录名与 `meta.json` 中的 `id` **强一致**

### 7.3 目录扫描器

在主进程实现扫描逻辑：

1. 读取当前激活目录的本地路径
2. 进入 Rules 主目录（目录名从配置读取）
3. 遍历所有子目录
4. 读取每个子目录的 `meta.json`
5. 解析并校验数据，组装成 `RuleMeta[]`
6. Skills 同理

### 7.4 数据校验

- `meta.json` 解析失败时跳过该项，不要导致整体崩溃
- 必填字段缺失时记录警告日志
- `id` 与目录名不一致时记录警告

### 7.5 IPC 数据接口

- 提供 IPC 接口供渲染进程调用：
  - `get-rules` — 返回当前仓库所有 Rules 列表
  - `get-skills` — 返回当前仓库所有 Skills 列表
  - `get-rule-content` — 返回指定 Rule 的 `main.md` 内容
  - `get-skill-content` — 返回指定 Skill 的 `main.md` 内容
  - `get-skill-files` — 返回指定 Skill 的文件列表和内容

### 7.6 文件内容读取

- 文本类文件直接读取返回字符串
- 二进制文件只返回文件名和大小信息，不读取内容
- 文件预览区别对待（产品设计第 42.6 节）

## 注意事项

- 扫描和解析全部在主进程执行
- 扫描结果可以在主进程缓存，刷新时重新扫描
- 主目录名从配置读取，不要硬编码
- `uuid_timestamp` 中间使用下划线 `_`（产品设计第 15.2 节）
- 当前目录是否为 Git 仓库不影响本地扫描；只要目录存在，就应该允许读取内容
- 如果当前目录不存在，应返回空列表而非报错

## 验收标准

1. 能正确扫描当前激活目录并解析出 Rules 和 Skills 列表
2. 能读取单个 Rule/Skill 的 `main.md` 内容
3. 异常数据不会导致崩溃，只跳过并记录日志
4. 渲染进程可通过 IPC 获取数据
