# 步骤 16：编辑器适配器体系

## 状态：已完成

## 目标

建立“安装到编辑器”的代码级适配器体系，把每个编辑器的路径规则、安装规则、平台差异都封装起来。这是产品设计文档第 32、36 节的实现。

## 要做的事

### 16.1 定义适配器接口

- 建议抽象统一接口，例如：

```typescript
interface EditorAdapter {
  id: string;
  label: string;
  supportsGlobal: boolean;
  supportsProject: boolean;
  supportsRule: boolean;
  supportsSkill: boolean;
  resolveGlobalTarget(): Promise<string | null>;
  resolveProjectTarget(projectPath: string): Promise<string | null>;
}
```

- 后续 Rule / Skill 的安装逻辑都从这里取目标路径

### 16.2 首批支持编辑器

- 当前优先支持产品文档里明确提到的核心目标：
  - Cursor
  - Codex
  - Claude Code

- 其他候选（如 VSCode、Windsurf、Anti Gravity）可以先留注册位，后续再补

### 16.3 先调研真实规则再编码

- 每个编辑器的安装目录规则、全局目录、项目目录都必须调研真实行为
- 不要凭猜测写路径
- 调研结论应沉淀到代码注释或文档中，方便后续维护

### 16.4 内容类型差异

- Rule 安装通常对应“单文件写入”
- Skill 安装通常对应“目录整体写入”
- 适配器层至少要能告诉上层：
  - 安装目标位置
  - 目标是文件位还是目录位

### 16.5 平台差异处理

- macOS 和 Windows 的路径规则可能不同
- 同一个编辑器在不同平台可能支持度不一样
- 适配器要能明确返回“不支持”或“未检测到安装位置”

## 注意事项

- 编辑器安装规则必须写死在代码里，不做 Settings 可配置化
- 适配器注册表应集中管理，不要散落在不同页面组件里
- 适配器负责“识别规则”和“路径解析”，具体写文件动作可由上层安装服务执行
- 安装输入来自当前激活目录读取出的内容，而不是应用自己维护的仓库缓存目录
- 任何一个编辑器适配失败，都不应影响其他编辑器入口
- 后续新增编辑器时，应尽量只新增一个 adapter 文件，而不是修改大量 UI 逻辑

## 验收标准

1. 系统存在统一的 EditorAdapter 接口或等价抽象
2. Cursor、Codex、Claude Code 至少有清晰的适配器占位
3. 适配器能区分全局安装和项目安装
4. 不支持或未检测到的编辑器会返回明确状态
5. UI 层不直接硬编码每个编辑器的路径规则
