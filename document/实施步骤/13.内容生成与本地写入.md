# 步骤 13：内容生成与本地写入

## 目标

把 Rule / Skill 的创建、编辑、删除统一落到新的 history-based 仓库存储模型中。核心原则是：**永远追加新 history，不覆盖旧文件**。

## 要做的事

### 13.1 创建

1. 生成内容根 ID：`crypto.randomUUID().replace(/-/g, "")`
2. 生成 history 目录名：`<timestamp>__<userId>__<rand6>`
3. 创建 `meta.json`
4. 创建首条 history：
   - `snapshot.json`
   - `main.md`
   - `attachments.json`
5. Skill 附件逐个计算 sha256，写入 `attachments-pool/<分片>/<sha256>`
6. 用临时目录落盘，完成后再原子移动到正式路径

### 13.2 编辑

1. 保存前先拿到用户打开弹窗时的 `baseHistoryDirname`
2. 真正写入前先 `git pull --rebase`
3. 重新读取当前最新 history
4. 若最新 history 已变化：
   - 返回冲突结果
   - 由 UI 决定“查看对方修改”或“继续保存”
5. 若继续保存：
   - 新建下一条 history
   - 全字段重写 `snapshot.json`
   - 全量重写 `main.md`
   - 全量重写 `attachments.json`

### 13.3 删除（软删）

1. 删除不是移除目录
2. 写入一条新的 history
3. `snapshot.json.deleted = true`
4. 其余字段、`main.md`、`attachments.json` 复制当前基线，保证 history 自足

### 13.4 Skill 附件规则

- `attachments.json` 只存：
  - `originalName`
  - `sha256`
  - `size`
- 不保留目录相对路径
- 新上传附件按 `originalName` 去重
- 编辑时移除附件，只影响新 history 的 `attachments.json`，不直接删池文件

### 13.5 提交前安全校验

- 必填字段不能为空
- Rule 不接受附件
- Skill 附件名不能为空
- Skill 附件名不能重复
- Skill 附件大小受产品约束控制
- 非 Git 仓库不允许写入

### 13.6 失败回滚

- 所有新 history 先写临时目录
- 任一步失败都不能留下半成品 history
- 附件池写入失败时，本次提交整体失败

## 注意事项

- `meta.json` 创建后永不修改
- 任何修改都不能直接改旧的 `snapshot.json` / `main.md` / `attachments.json`
- `attachments.json` 即使为空也必须存在，内容为 `files: []`
- `main.md` 永远写完整正文，不做 patch

## 验收标准

1. 创建会生成 `meta.json + history/<dirname>/...`
2. 编辑只追加新 history，不覆盖旧版本
3. 删除会生成软删 history，而不是直接删目录
4. Skill 附件进入池存储，history 只保留引用
5. 写入失败不会留下半成品文件
