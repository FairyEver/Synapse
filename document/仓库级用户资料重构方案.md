## 一、背景与目标

### 1.1 现状

`document/仓库存储系统重构方案.md` 已经把 displayName 写成"提交时快照"：

- 本地 `<userData>/user-identity.json` 存 `{ userId, displayName }`，displayName 是全局的。
- 每条 rule/skill 的 `meta.json` 存 `createdByDisplayName`，每条 history 的 `snapshot.json` 存 `modifiedByDisplayName`。
- 用户改名后，**老数据仍然显示老名字**（因为是快照）。
- 不同仓库（个人 / 公司）**只能共用同一个 displayName**。

### 1.2 痛点

- **改名后历史记录不跟随**。用户在设置页把"张三"改成"向阳"，过去写的所有 rule/skill 依然显示"张三"。体验反直觉。
- **多仓库身份强耦合**。同一个人在个人仓库想叫"iroha"，在公司仓库想叫真名"李阳"，当前做不到。
- **本地文件丢失时，仓库里没有自描述**。即使仓库里有这个 userId 的历史提交，也无法在新设备上校验"我是不是以前的那个人"——因为仓库没存过任何 userId → 身份元数据的映射。

### 1.3 目标

- **displayName 从全局剥离，每个仓库独立一份**。
- **改名立即全局生效**，所有老数据一并显示新名（不再保留快照优先级）。
- **userId 不可由用户主动创建**。只有软件首次启动 / 本地文件丢失时自动生成。用户只能"接续已有身份"——填入一个**在当前仓库 users 目录下实际存在**的 userId。
- **保留老的快照字段作为最后兜底**（仓库里完全找不到该 userId 的 profile 时才显示），不作为主要来源。
- **身份伪造不防御**。任何人知道另一个人的 userId 都可以接续成对方，这是 by design。

## 二、核心设计原则

1. **本地 identity 只留 userId，不再持有 displayName。** displayName 不属于设备层，属于仓库层。
2. **仓库里有一份自描述的用户目录。** 结构 `<repoRoot>/users/<userId>/profile.json`，每个用户**只能写自己的子目录**（客户端层面约束，非安全边界）。
3. **onboarding 是仓库级事件。** 加入一个新仓库 = 必须先在该仓库里写下自己的 profile，否则无法提交内容。
4. **改名即 commit + push。** 不合并到下一次内容提交，不延迟。保持实时一致。
5. **userId 的生命周期严格化。** 自动生成是唯一合法来源；"接续"是唯一合法替换方式；replaceUserId 改名为 adoptExistingUserId，校验仓库里真的有这个 ID 才允许。
6. **displayName 快照字段保留作兜底。** 新建 / 修改内容时仍写入 `createdByDisplayName` / `modifiedByDisplayName`，但读取时优先级最低。
7. **展示解析统一走一个函数。** `resolveDisplayName(userId, repoProfileMap, snapshotFallback)`，不允许散落在组件里各自判断。

## 三、数据结构定义

### 3.1 仓库目录树（增量部分）

在现有方案 `document/仓库存储系统重构方案.md` §3.1 的基础上新增：

```
<repo-root>/
├── rules/               （不变）
├── skills/              （不变）
├── attachments-pool/    （不变）
└── users/                ← 新增
    ├── <userId-A>/
    │   └── profile.json
    ├── <userId-B>/
    │   └── profile.json
    └── ...
```

**关键约束：**

- `users/` 下每个子目录的名字必须是 **32 字符无横线全小写十六进制** userId。
- 每个 userId 子目录下当前只有一个文件 `profile.json`。未来可扩展 `avatar.png`、`preferences.json` 等，保留一级目录是为这个。
- **禁止**在 `users/` 下放任何跨用户的汇总文件（例如 `index.json`、`all-users.json` 之类）。和现有方案里"无共享写入点"的原则一致。
- 每个用户**客户端层面**只会写自己 userId 对应的子目录。仓库里理论上仍可能出现一个人写别人目录的提交，不防御。

### 3.2 文件 schema

#### 3.2.1 `users/<userId>/profile.json`

```json
{
  "schemaVersion": 1,
  "userId": "a3f2b9c1d4e5f6a7b8c9d0e1f2a3b4c5",
  "displayName": "李阳",
  "updatedAt": "2026-04-19T12:34:56.000Z"
}
```

- `schemaVersion` 固定 `1`，为未来扩展预留。
- `userId` **必须和所在目录名完全一致**。写入时两边必须匹配，读取时若不一致则视为损坏（profileMap 不收录该条目），由 §6.2 的 fallback 链兜底。
- `displayName` 为空字符串时，视为"该用户在本仓库尚未完成 onboarding"，读取侧退回到 fallback 链（见 §6.2）。
- `updatedAt` ISO 8601 UTC，客户端本地时间生成。单纯审计用，不参与"当前版本"判定（每个 userId 目录下只有一份 profile，不存在版本之争）。
- 未来若新增字段（avatar、timezone、bio），追加到 schema 并升 `schemaVersion`。

#### 3.2.2 `<userData>/user-identity.json`（修改）

```json
{
  "schemaVersion": 2,
  "userId": "a3f2b9c1d4e5f6a7b8c9d0e1f2a3b4c5",
  "generatedAt": "2026-04-18T10:00:00.000Z"
}
```

- **移除 `displayName` 字段。** 老版本（`schemaVersion: 1`）读取时自动忽略 displayName 字段，写回 `schemaVersion: 2`。
- schemaVersion bump 到 `2`，用于区分重构前后的本地文件。

#### 3.2.3 `meta.json` / `snapshot.json`（保留现字段不改）

继续写入 `createdByDisplayName` / `modifiedByDisplayName`。

**但语义变为"最终兜底"，不再是展示的主来源。** 读取优先级见 §6.2。

### 3.3 目录命名

- `users/<userId>/` 目录名规则：32 字符无横线全小写十六进制。
- 校验规则与 `document/仓库存储系统重构方案.md` §4.4 完全一致，复用 [electron/services/user-identity-service.ts:24](electron/services/user-identity-service.ts#L24) 的 `normalizeUserId` 函数。

## 四、用户 ID 生命周期（重新定义）

### 4.1 生成（自动，唯一合法来源）

触发时机只有两个：

1. **首次启动**：本地 `user-identity.json` 不存在 → 生成新 UUID v4 → 去横线 → 写入本地文件（`schemaVersion: 2`）。
2. **本地文件损坏 / 字段缺失**：按 `document/仓库存储系统重构方案.md` §4.5 分支 B 让用户二选一——生成新 ID 或手动接续。

**用户不能在设置页主动"生成新 ID"之外再创造 ID**。这点和现有方案相比收紧：现有方案允许任意时刻 `replaceUserId` 填入一个格式合法的 ID，即使仓库里没有也能写入。新方案禁止这个。

### 4.2 接续（adoptExistingUserId，替换 replaceUserId）

**场景：** 用户换了新设备 / 清了配置 / 想要把老账号接回来。

**流程：**

1. 用户在设置页点 "接续已有身份" 按钮。
2. 弹 Dialog，输入 userId（容许带横线 / 大小写，走 normalize）。
3. 客户端在**当前 active repository** 的本地 checkout 下查：`users/<输入的 userId>/profile.json` 是否存在。
   - 如果当前仓库是 git 仓库（[src/types/repository.ts:9](src/types/repository.ts#L9) `isGitRepository === true`）：查之前**强制 `git fetch` 一次**，以磁盘为准（fetch 后不做 reset，只保证数据新）。fetch 失败（无网 / 认证失败）弹错提示 "无法同步仓库，请检查网络后重试"，不允许接续。
   - 如果是纯本地仓库（`isGitRepository === false`）：**跳过 fetch**，直接读磁盘。没有远端可同步这一说。
4. 若文件存在且 schema 合法 → 覆盖本地 `user-identity.json.userId` → 触发 §7.2 的仓库 profile 状态重算 → 关闭 Dialog。
5. 若文件不存在 → 输入框下红字提示 "这个 ID 在当前仓库里不存在，无法接续"。

**不做的事：**

- 不接续时不扫"所有仓库"找匹配。只看**当前 active repository**。用户如果有多个仓库，想接续就切到对应仓库再操作。
- 不允许强制接续（"我就是知道这个 ID 是对的"）。没校验通过就拒绝。

### 4.3 存储

和现有方案一致：`<userData>/user-identity.json`，权限 `0600`，内容见 §3.2.2。

### 4.4 校验规则

字段级校验复用 [electron/services/user-identity-service.ts:24](electron/services/user-identity-service.ts#L24)：32 字符、小写、只允许 `[0-9a-f]`，带横线自动去除。

新增的仓库级校验：§4.2 第 3 步。

## 五、仓库级 onboarding

### 5.1 触发时机

以下任一情形，软件必须强制用户进入 onboarding：

1. **首次启动后配置第一个仓库**：本地 `user-identity.json` 已自动生成，但当前 active repository 下 `users/<myId>/profile.json` 不存在。
2. **切换 active repository**（或新增一个并切过去）：目标仓库下 `users/<myId>/profile.json` 不存在。
3. **通过 adoptExistingUserId 接续后**：接续的 userId 虽然在仓库里存在（§4.2 校验通过），但 profile.displayName 为空字符串——可能出现在接续后用户把自己 profile 删到只剩空壳的极端情况。这种情况同样强制走 onboarding。

### 5.2 Onboarding 流程

1. 进入主界面之前弹**阻塞式 Dialog**，标题 "设置你在『仓库名』里的显示名"。
2. 内容：
   - 展示当前 userId（只读，等宽字体）
   - displayName 输入框，非空必填
   - 提示文案："这是你在本仓库里的显示名。不同仓库可以使用不同名字。"
   - 底部按钮：[切换仓库]（次要样式） [确定]（主要样式，displayName 为空时禁用）
3. 用户填写后点击 "确定"：
   - 在本地 checkout 下创建 `users/<myId>/` 目录
   - 写入 `profile.json`（§3.2.1 schema）
   - **根据仓库类型分支（见 §5.4）**
4. 用户点击 "切换仓库"：
   - 关闭 Dialog
   - 跳转到仓库选择界面
   - 用户选完另一个仓库后，若新仓库下仍然没有自己的 profile，再次弹 onboarding Dialog

### 5.3 Onboarding 不允许"不填继续"

显示名不填就**不允许进入主界面**。"确定"按钮在 displayName 非空前保持禁用。

- 点击遮罩 / 按 Esc / 关闭按钮 → 不响应（Dialog 设 `modal: true`、`dismissible: false`）
- 唯一两条出路：**填完 displayName 点确定**，或 **切换到另一个仓库**
- 如果用户切到的所有仓库都没 onboard，软件永远卡在 onboarding Dialog —— 这是预期行为，不是 bug

### 5.4 Onboarding 的持久化（区分 git / 非 git）

- **git 仓库（`isGitRepository === true`）：**
  - `git add users/<myId>/profile.json`
  - 用机器人身份 `git commit -m "[synapse] user <myId 前 8 位> join"`
  - 立即 `git push`
    - 成功 → 刷新本地 user profile cache → 关闭 Dialog → 进入主界面
    - 失败 → 写入 pending_pushes 队列（和现有方案一致）→ 关闭 Dialog → 进入主界面 → 工具栏推送按钮亮起
- **纯本地仓库（`isGitRepository === false`）：**
  - 只做文件系统写入（原子 rename，tmp → 目标路径）
  - 不 `git add`、不 commit、不 push
  - 写入成功 → 刷新本地 user profile cache → 关闭 Dialog → 进入主界面
  - 写入失败（磁盘问题）→ 走 §10.5（现有方案的全局错误模态框）

## 六、显示名读取与缓存

### 6.1 每仓库 profile cache

新增 `electron/services/user-profile-cache.ts`：

- 每个 active repository 维护一份 in-memory `Map<userId, SynapseUserProfile>`。
- 启动时 / 切换仓库时 / 收到 users/ 下文件变更事件时重建。
- 重建算法：`readdir(<repoRoot>/users/)` → 对每个子目录读 `profile.json` → 解析校验 → 不合法的跳过并记日志 → 合法的放入 Map。

**不持久化到 SQLite。** 纯内存。原因：重建足够快（几百用户的小文件扫描在 ms 级），落盘只增加复杂度。

### 6.2 解析函数 `resolveDisplayName`

新增 `src/lib/display-name.ts`：

```typescript
export function resolveDisplayName(
  userId: string,
  profileMap: ReadonlyMap<string, SynapseUserProfile>,
  snapshotFallback?: string,
): string {
  const profile = profileMap.get(userId)
  if (profile && profile.displayName.trim().length > 0) {
    return profile.displayName
  }
  if (snapshotFallback && snapshotFallback.trim().length > 0) {
    return snapshotFallback
  }
  return "未命名用户"
}
```

**优先级链：**

1. 仓库 users/ 目录里有 profile 且 displayName 非空 → 用它
2. 否则，看传入的 snapshotFallback（即 meta.json 里的 `createdByDisplayName` 或 snapshot.json 里的 `modifiedByDisplayName`）非空 → 用它
3. 否则 → "未命名用户"

**所有展示点必须用这个函数，不允许散落。**

### 6.3 展示点改造清单

以下三处当前代码里直接用 `createdByDisplayName || "未命名用户"` 的，全部改为调用 `resolveDisplayName`：

- [src/modules/rules/components/rule-detail-dialog.tsx:349](src/modules/rules/components/rule-detail-dialog.tsx#L349)
- [src/modules/skills/components/skill-detail-dialog.tsx:356](src/modules/skills/components/skill-detail-dialog.tsx#L356)
- [src/modules/content/components/content-browser-page.tsx:214](src/modules/content/components/content-browser-page.tsx#L214)

### 6.4 搜索索引跟随改名

[src/modules/content/components/content-browser-page.tsx:94](src/modules/content/components/content-browser-page.tsx#L94) 的模糊搜索 weight 字段 `createdByDisplayName` 当前来自 meta.json 快照。新方案下搜索也要跟随改名。

**索引字段改造：**

- `content_index` 表的 `created_by_name` / `modified_by_name` 两列语义变更：存的**不再是 meta/snapshot 的快照值**，而是**索引构建那一刻从仓库 users/ 目录读到的 displayName**。
- 读不到 profile 时（userId 在 users/ 下不存在、或 displayName 为空），写入 meta/snapshot 里的快照字段作为兜底写入值（与 `resolveDisplayName` 的 fallback 链一致）。
- 索引字段只服务搜索匹配，**不**作为 UI 展示的数据源。UI 展示永远走 resolveDisplayName + 当前最新 profileMap（避免索引陈旧期内 UI 显示的名字和搜索命中的名字不一致，以 UI 为准）。

**索引重建触发时机：**

1. `git pull` 成功后（仓库数据更新）
2. 本地 commit 成功后（自己改了内容或自己改了 profile）
3. 用户在设置页点"手动重建索引"按钮（维护兜底）
4. 本仓库任意 `users/*/profile.json` 被观测到变更（FS watcher 或定期轮询，实施时择一）

实施上**以 1 和 2 为主**，这两个点已经是现有方案里处理本地索引增量的天然切入点（参见 `document/仓库存储系统重构方案.md` §6.6）。3 作为兜底按钮。4 如果实施成本高可以不做。

**重建策略：**

- 增量（仅 git 仓库）：如果触发源是 git pull / 本地 commit，按现有方案 §6.6 的 git diff 算法增量更新受影响的 rule/skill 行，并额外对 `users/` 下变更的 userId 做"反向扫描"——找出所有 `modified_by = <该 userId>` 的 rule/skill 行，重写这些行的 `modified_by_name`。
- 全量：
  - **纯本地仓库必须走全量**。没有 git 历史可 diff，只能遍历 `rules/*/` 和 `skills/*/` 以及 `users/*/` 重新写索引。
  - 增量路径里的 index 被删 / schema 变更 / 用户手动触发 "重建" 时也走全量。

**UI 提示：**

- 主界面右上角（工具栏）新增"索引状态"指示器。三态：
  - 空闲：不显示
  - 重建中：Spinner + 文案"正在重建索引"（遵循项目 UI 规则：shadcn 组件，无自定义样式）
  - 错误：红点 + tooltip 说明（罕见，索引服务内部错误）
- 重建时长超过 2 秒才显示指示器（避免闪烁）。

### 6.5 historyPanel 等其他派生数据

## 七、身份状态 API 拆层

### 7.1 现状问题

[electron/services/user-identity-service.ts:72](electron/services/user-identity-service.ts#L72) 的 `loadState()` 目前返回一个融合状态：

```typescript
type SynapseIdentityState =
  | { status: "ready"; identity: SynapseUserIdentity }
  | { status: "needs-onboarding"; identity: SynapseUserIdentity }
  | { status: "needs-recovery"; invalidUserId: string | null }
```

### 7.2 新的两层状态

  schemaVersion: 2
  userId: string
  generatedAt: string

  | { status: "ready"; identity: SynapseLocalIdentity }
  | { status: "needs-recovery"; invalidUserId: string | null }

  displayName: string
  updatedAt: string

## 八、改名流程（立即 commit + push）

### 8.1 触发

用户在设置页修改 "当前仓库显示名" 输入框，**失焦自动保存**（debounce 800ms，比现有的 500ms 保守一点，因为要 commit + push）。

### 8.2 流程

1. 前端调用 `userProfile.updateDisplayName(repoId, newName)`。
2. service 分支：
   - **git 仓库：**
     - `git pull --rebase`（对齐现有方案 §5.1/§5.2 规范）
     - 读 `users/<myId>/profile.json`（不存在则视为 onboarding 路径，不走这里；此函数假定已 onboard）
     - 覆写 `displayName`、更新 `updatedAt`
     - 原子写（先写 tmp 再 rename）
     - `git add users/<myId>/profile.json`
     - `git commit -m "[synapse] user <myId 前 8 位> rename"`
     - 立即 `git push`
     - 成功 → 刷新本地 cache → 前端重新订阅 repoProfileState → UI 反馈"已保存"
     - 失败 → 入 pending_pushes 队列 → 工具栏推送按钮亮起 → UI 反馈"已在本地保存，稍后同步"
   - **纯本地仓库：**
     - 读 `users/<myId>/profile.json`
     - 覆写 `displayName`、更新 `updatedAt`
     - 原子写（先写 tmp 再 rename）
     - 刷新本地 cache → 前端重新订阅 repoProfileState → UI 反馈"已保存"
     - 写入失败走全局错误模态框

### 8.3 多仓库的连带影响

用户只改当前仓库的 displayName。**其他仓库不自动同步**。

若用户切换到其他仓库，那个仓库的 displayName 可能仍然是老的（或从未 onboard）。软件按 §5.1 的规则决定是否弹 onboarding。

### 8.4 commit 规范

- message 格式：`[synapse] user <userId 前 8 位> <action>`，action ∈ `{ join, rename }`
- 不要在 commit message 塞 displayName 文本（避免 rename 循环里把老名字泄漏到 git log）
- 机器人身份 config 沿用 `document/仓库存储系统重构方案.md` §5.5

## 十三、仓库结构初始化

### 13.1 动机

当前代码在 "用户选择一个目录作为仓库" 之后完全不做结构校验：

- [src/modules/settings/components/repository-list-editor.tsx:99-116](src/modules/settings/components/repository-list-editor.tsx#L99-L116) 调用 `bridge.chooseDirectory()` 后直接保存。
- 如果这是个空目录或者只是一个普通文件夹，软件在第一次写入时才隐式创建 `rules/` / `skills/` / `users/` / `attachments-pool/`。
- 如果用户选了一个已有其他用途的目录（例如放简历的文件夹），软件不会警告。

需要一个**显式的"初始化仓库结构"操作**：把目录里的东西清掉（保留 git 相关文件），重建 Synapse 需要的骨架。

### 13.2 初始化 = 替换语义（不是补全）

**关键决策：初始化就是破坏性重置。** 不是"缺什么补什么"。点击按钮后，目录下除 git 相关文件之外的所有内容都会被删除，然后创建空骨架。

原因：

- 用户明确要求"不管之前有什么内容也好 ... 要把这个文件夹里的东西给初始化成这个软件需要的结构"
- 补全式初始化遇不到"如何对待已有无关文件"的决策点，但现实里肯定有这种目录（用户选错路径 / 历史遗留 / 重置一个旧 Synapse 仓库）
- 非空检测 + 3 秒延迟警告的设计本身就是为了破坏性操作提供闸门

### 13.3 保留清单（不被清空的文件）

**仅保留 `.git/` 目录**（git 的核心内部状态，删了会破坏 git 仓库）。其他一切都删。

**具体"会被删"的条目（常见举例，不穷尽）：**

- `.gitignore`、`.gitattributes`、`.gitmodules`、`.git-blame-ignore-revs` 等 git 配置文件 —— **都是可编辑文件，初始化会重新生成需要的配置**
- `.DS_Store`、`.idea/`、`.vscode/` 等 IDE / OS 的配置文件
- `README.md`、`LICENSE` 等常见项目文件
- 用户自己的任何其他文件和目录
- 已有的 `rules/` / `skills/` / `users/` / `attachments-pool/`（即使是有效 Synapse 结构也被清空——用户明确要求"不管之前有什么"）

**实施要点：** 白名单的唯一条目就是字符串 `".git"`（且必须是目录类型）。顶层 `readdir` 结果里除了这一项，全部 `rm -rf`。不要写 "以 `.git` 开头" 这种前缀匹配——`.gitignore` 这类文件不在保留范围内。

### 13.4 非空检测

"非空" 指除 `.git/` 之外存在任何顶层条目。

- 空目录（`readdir(repoRoot)` 返回 `[]`）→ 非空检测为 false，直接走 §13.6 的初始化
- 只有 `.git/`（典型场景：刚 clone 的空 git 仓库）→ 非空检测为 false，等同空目录对待
- 存在任何其他条目（包括 `.gitignore`、`README.md`、`.DS_Store` 等一切）→ 非空检测为 true，走 §13.5 的警告弹窗

### 13.6 初始化执行流程

用户点击 "确定初始化" 后的后端流程：

1. **再次校验目录存在且可写**（防止执行过程中被外部改动）。
2. **读 `<repoRoot>` 顶层条目清单**，区分保留清单和待删清单。
3. **删除待删清单**：逐项 `rm -rf`。**不要**试图 `rm -rf <repoRoot>/*` 一把梭，否则 git 隐藏文件可能被误伤（取决于 shell 的 glob 行为）。
4. **创建空骨架**：
   - `mkdir -p <repoRoot>/rules`
   - `mkdir -p <repoRoot>/skills`
   - `mkdir -p <repoRoot>/users`
   - `mkdir -p <repoRoot>/attachments-pool`
   - 每个目录下放一个 `.gitkeep`（空文件）——保证 git 仓库能追踪到这些空目录，也便于纯本地仓库的一致性
5. **git 仓库分支（`isGitRepository === true`）**：
   - `git add rules/.gitkeep skills/.gitkeep users/.gitkeep attachments-pool/.gitkeep`
   - 对被删的内容也要 `git rm -r --cached <paths>`（如果它们原本在 git 追踪里）
   - 用机器人身份 `git commit -m "[synapse] initialize repository structure"`
   - 立即 `git push`（失败入 pending_pushes 队列）
6. **纯本地仓库分支（`isGitRepository === false`）**：
   - 仅文件系统操作。不 commit 不 push。
7. **刷新本地 cache**：
   - 清空 SQLite 的 `content_index`（原来的索引已经失效）
   - 清空 users profile cache
   - 触发一次全量索引重建（纯本地仓库 = 空结果；git 仓库 = pull 后的最新结果）
8. **返回结果给前端**：成功 / 失败（含失败原因）。

**原子性：** 不做原子性保证。中途失败时留下半清理状态，用户再点一次初始化即可。不值得为这个加 staging 目录 + rename 的复杂度。失败时的 UI 文案："初始化未完成，请重试"。

### 13.7 初始化按钮入口

**位置：** 设置页每个仓库卡片的操作区。

当前仓库卡片的编辑入口在 [src/modules/settings/components/repository-list-editor.tsx](src/modules/settings/components/repository-list-editor.tsx)。按钮排列建议：`[编辑] [初始化] [删除]`。

**只有满足以下条件才显示 "初始化" 按钮：**

- `SynapseRepositoryLocalState.status === "ready"`（目录存在且可读）
- 不在 onboarding 流程中

**点击行为：**

1. 前端调用 `repository.checkInitializationPreview(repoId)` IPC → 后端返回 `{ isEmpty, nonGitEntries: string[] }`
2. `isEmpty === true` → 直接走 §13.6 的流程（无需警告，空目录没东西可丢）
3. `isEmpty === false` → 弹 §13.5 的延迟警告 → 用户点确定才走 §13.6

### 13.8 初始化与 onboarding / index 重建的联动

初始化完成后：

- 本用户在该仓库的 profile 被删（刚刚清空了 `users/`）→ 下次进入该仓库会触发仓库级 onboarding（§5）
- 索引全空 → 索引服务按 §6.4 自动重建（空仓库 = 空索引，瞬间完成）
- **不自动弹 onboarding Dialog**，让用户正常进入主界面后由 context 层检测到 `needs-onboarding` 再弹

### 13.9 "刷新按钮根据 isGitRepository 隐藏"（与初始化无关但同一批改动）

现状：[src/App.tsx:81-97](src/App.tsx#L81-L97) 非 git 仓库时把刷新按钮设为 `disabled=true` + tooltip 提示"当前目录不是 Git 仓库，无法同步"。

**本方案要求改为完全隐藏**（`showRefresh` 条件里加 `isGitRepository`）：

- [src/app-shell/components/app-shell-actions.tsx:56-67](src/app-shell/components/app-shell-actions.tsx#L56-L67) 的 `showRefresh` prop 由 `App.tsx` 传入
- `App.tsx` 里把 `showRefresh = activeRepositoryState?.status === "ready" && activeRepositoryState.isGitRepository`
- 去掉 disabled + tooltip 那套——纯本地仓库根本不存在"同步"这个操作概念，置灰反而制造疑惑

同理：工具栏里的 "推送" 按钮（现有方案 §10.2）在纯本地仓库也要隐藏。

## 十四、迁移方案

### 14.1 目标

把现有 history-based 结构里**已经散落的 displayName 信息**提取出来，作为每个用户在每个仓库的初始 profile 写回 `users/` 目录，零数据丢失。

### 14.2 迁移脚本

新建 `scripts/migrate-display-name-to-user-directory.ts`。

**算法（每个仓库单独跑）：**

1. 扫描 `rules/*/meta.json` 和 `skills/*/meta.json`，收集 `(createdBy, createdByDisplayName)` 对。
2. 扫描 `rules/*/history/*/snapshot.json` 和 `skills/*/history/*/snapshot.json`，收集 `(modifiedBy, modifiedByDisplayName)` 对。
3. 按 userId 聚合：每个 userId 选择**最新的** displayName 作为初始值（用 snapshot.modifiedAt 排序，最新为准）。
4. 对每个聚合出的 userId：
   - 如果 `users/<userId>/profile.json` 已经存在，跳过
   - 否则创建 `users/<userId>/profile.json`，内容：`{ schemaVersion: 1, userId, displayName, updatedAt: <当前时间> }`
5. `git add users/`
6. `git commit -m "[synapse] migrate user profiles"` (一条 commit)
7. 脚本执行者**手动确认后 push**。不自动 push。

**特殊情况：** 老数据里可能有全 0 的 `legacy` userId（来自 `document/仓库存储系统重构方案.md` §12.3 的迁移）。这个 userId 也生成 profile，displayName 沿用老数据里最后一次出现的那个名字（或 "legacy" 字面量）。

### 14.3 回滚

- 迁移前 tag 一个 `pre-user-directory-migration`
- 有问题直接 git reset 回去
- 如果 push 已经完成，需要团队协调（因为是多人仓库），这也是脚本执行者要手动 push 的原因

### 14.4 软件层面的向后兼容

在软件更新到新版本之后、迁移脚本还没跑之前：

- users/ 目录不存在 → `listRepoProfiles` 返回空 Map
- `resolveDisplayName` 全部走 fallback 链（第 2 级：snapshot 字段）
- 此时用户体验 = 老版本（改名不跟随），但不会崩

这允许"先升级软件、再挑时机跑迁移"，不强耦合。

## 十六、反模式警告（不要这样做）

### 16.1 身份与 profile

- 在本地 identity 文件里继续保存 displayName "作为默认值" → 等于没做重构
- 用 `replaceUserId` 之外的入口让用户主动创建新 ID（例如设置页加 "生成新 ID" 按钮） → 违反 §4.1 的唯一生成路径
- adopt 校验时扫所有 active repositories 找匹配 → 复杂度高且语义模糊，只看当前 active repository
- profile.json 里塞跨仓库的信息（比如一个数组列出所有仓库里的名字） → 回到了全局 displayName 的老路

### 16.2 多用户目录

- 在 `users/` 下放任何汇总文件（`index.json` / `all-users.json` 之类） → 共享写入点
- 用 profile.json 的 `updatedAt` 做"版本仲裁"（类似 snapshot.modifiedAt 的角色） → 每个 userId 目录下只有自己写，没版本之争
- GC 自动删除"长期未登录"用户的 profile → 离职等场景用户明确说不处理

### 16.3 resolveDisplayName

- 在组件里直接读 `createdByDisplayName` 不走 resolveDisplayName → 改名后不会跟随
- resolveDisplayName 的 fallback 顺序颠倒（快照 > profile） → 快照就是用来解决"仓库坏了找不到"的，不是主来源
- fallback "未命名用户" 改成 userId 前 8 位 → 非技术用户不理解

### 16.4 改名流程

- 改名合并到下一次内容 commit 一起推 → 用户改完名后看不到效果，体验糟糕
- 改名失败 silently（不入队列） → 用户以为改成功了，下次打开又变回去
- 改名时写全量 `users/` 目录而不是只写自己的 → 可能覆盖别人的 profile

### 16.5 UI

- 设置页保留"全局显示名"输入框 → displayName 不再是全局概念
- onboarding Dialog 允许 dismissible → 用户会跳过然后用户体验全面崩坏
- onboarding 提供 "跳过" / "稍后再说" 入口 → 没 profile 就不能提交内容，跳过等于软件半残
- 接续 Dialog 不做网络 loading → 用户以为卡死

### 16.6 git / 本地仓库差异

- 对纯本地仓库执行 `git fetch` / `git commit` / `git push` → 直接报错
- 在 profile 相关 service 里散落写 `if (isGit) ... else ...` → 应集中在 `persistProfileChange` 一处（见 §12.4）
- 搜索索引重建在纯本地仓库里依赖 `git diff` → 本地仓库没有 git 历史，必须有"非 git 仓库走全量扫描"的兜底路径
- 非 git 仓库的刷新按钮用 disabled + tooltip → 按 §13.9 改为隐藏；tooltip 说明"不是 git 仓库"只会制造疑惑
- `pending_pushes` 表对所有仓库无条件建表 → 纯本地仓库不应该有这张表，§12.5 要求条件建表

### 16.7 仓库结构初始化

- 做"补全式"初始化（只建缺失目录不删已有内容） → 违反 §13.2 的替换语义，且非空警告失去意义
- 初始化时用 `rm -rf <repoRoot>/*` 一把梭 → shell glob 行为可能连 `.git/` 一起删；必须按 §13.3 白名单逐项处理
- 保留清单用"以 `.git` 开头"前缀匹配 → 会把 `.gitignore` 等可编辑文件也保留下来，违反 §13.3 要求（仅保留 `.git/` 目录本身）
- 保留清单用黑名单实现（"不删这些"） → 漏掉 `.git/` 会损坏 git 仓库，必须白名单且只有这一项
- 警告弹窗自己写 Dialog 不用 shadcn `AlertDialog` → 违反项目 UI 规则（`src/components/ui/alert-dialog.tsx` 已存在）
- 警告弹窗的 "取消" / "关闭" 按钮也受 3 秒延迟限制 → 用户想反悔反而反悔不了，违反 §13.5 设计
- 延迟倒计时用 `setInterval` 但忘记 `clearInterval` → 组件卸载后内存泄漏
- 初始化按钮不做 loading 态 → 删除大目录需要时间，用户以为卡死会反复点
- 初始化期间允许其他写入 → 初始化过程不要求原子，但必须禁用该仓库的内容创建/编辑入口直到完成

## 十七、决策归档（供追溯）

| 决策 | 结论 | 依据 |
|---|---|---|
| displayName 存储位置 | 完全下沉到仓库 users/ 目录，本地 identity 不持有 | 支持多仓库不同名 + 改名全局生效 |
| 改名后历史展示 | 全部改为新名，不保留历史快照视图 | 用户明确要求 |
| 老快照字段 | 保留，新建时仍写入，仅作兜底 | 仓库坏了 / 找不到 profile 时有兜底文案 |
| userId 创建来源 | 仅自动生成（首次启动 / 损坏恢复），用户不能主动新建 | 避免仓库里出现未注册的 userId |
| userId 接续校验 | 必须在当前仓库 users/ 下存在才允许接续 | 防止胡乱填 |
| 接续时的仓库范围 | 只看当前 active repository，不扫所有 | 语义清晰 |
| 接续前是否 fetch | git 仓库强制 fetch；纯本地仓库跳过 | 纯本地无远端可同步 |
| onboarding 粒度 | 仓库级 | 没 profile 就不能提交内容 |
| onboarding 可否跳过 | 否。必须填 displayName 才能进主界面；允许切换到另一个仓库 | 用户明确要求 |
| 纯本地仓库 | profile 写入后不走 git，仅落盘 | 本地仓库本就没有远端推送语义 |
| 搜索索引 displayName | 跟随改名；pull / commit / 手动触发时重建；UI 显示"正在重建索引" | 用户明确要求搜索也跟随改名 |
| 索引重建粒度 | 增量为主（git diff + users/ 反向扫描）；仅手动触发和首次跑全量 | 兼顾性能和正确性 |
| 顶层目录名 | `users/`（不是 `user/`） | 用户明确要求 |
| 改名 commit | 独立 commit，不合并 | 语义清晰 + 立即同步 |
| 改名 push 时机 | 立即，失败进队列 | 对齐现有方案的推送哲学 |
| profile.json schema | 带 schemaVersion = 1，预留 avatar / bio 等 | 未来扩展 |
| users/ 下汇总文件 | 禁止 | 共享写入点原则 |
| 身份伪造 | 不防御 | 用户明确表态 |
| 离职用户清理 | 不处理 | 用户明确表态 |
| 本地 identity schemaVersion | bump 到 2 | 标记重构前后文件差异 |
| profile cache | 内存，不持久化 | 重建足够快 |
| 刷新按钮对纯本地仓库 | 完全隐藏（当前是 disabled + tooltip） | 纯本地无"同步"概念，置灰只制造疑惑 |
| 推送按钮对纯本地仓库 | 完全隐藏 | 同上 |
| `pending_pushes` 表对纯本地仓库 | 不创建（现有表保留，新初始化不建） | 无用表遗留不整洁 |
| 仓库初始化语义 | 替换（清空非 git 内容，重建空骨架） | 用户明确要求 + 补全式无法解释非空警告的存在 |
| 初始化保留清单 | 白名单只有 `.git/` 一项；`.gitignore` 等 git 配置文件也删 | 用户明确要求：git 配置可再生，只保核心内部状态 |
| 非空判定 | 除 `.git/` 外存在任意顶层条目即视为非空 | 清晰可判定 |
| 初始化警告弹窗组件 | 必须用现成 shadcn `AlertDialog` + 新封装的 `DelayedConfirmAlertDialog` | UI 规则 + 复用 |
| 确定按钮延迟 | 3 秒；取消和关闭不受限 | 给破坏性操作设置闸门，但允许立即反悔 |
| 初始化原子性 | 不保证；失败让用户重试 | 复杂度不值 |
| 初始化后的副作用 | 清 content_index + users profile cache + 全量重建 + 重走 onboarding | 结构被重置，旧状态全部失效 |

## 结束语

本方案在 `document/仓库存储系统重构方案.md` 建立的 history-based full-snapshot 架构之上，把 displayName 从"设备层全局字段"下沉为"仓库层自描述资源"。核心价值：

- 用户改名后，所有历史记录自然显示新名
- 多仓库身份解耦，个人仓库 / 公司仓库可以用不同显示名
- 身份在仓库里有自描述，新设备接续时可以校验 userId 是否真的是老用户
- 为将来扩展用户资料（头像 / 偏好 / bio）预留了目录结构

如果实施过程中对任何细节不确定，**回来问清楚**，不要自己做决定。本方案的每一条约束都是有代价的选择，随意修改会破坏整体性。
