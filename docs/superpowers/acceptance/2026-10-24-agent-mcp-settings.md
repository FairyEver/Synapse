# Agent MCP 设置实机验收

2026-10-24 用户明确授权启动应用、操作本机设置、新建测试对话及核对实际请求。使用当前工作区的 `pnpm dev:desktop`，没有切换分支、创建 worktree 或发布应用。

## 证据方法

通过 Electron 真实窗口操作设置和对话，使用现有 DeepSeek Provider。临时将该 Provider 的 SY 请求地址指向本机回环转发器，再以 HTTPS 转发至原端点；请求正文原样转发，认证头仅在内存中转发，不记录。记录的是实际 HTTP 请求正文的脱敏副本，不是根据启动参数推算的工具列表，也不把 SDK StreamEvent 当作原始 SSE。

本机证据位于仓库忽略目录 `work/agent-mcp-e2e/`：`evidence.json` 保存请求元数据，`wire-summary.json` 归纳正式推理请求，`<序号>-<阶段>-request.json` 保存脱敏正文。请求原始字节长度和 SHA-256 在脱敏前计算，避免将重排后的 JSON 当作原始字节。标题生成和 `/count_tokens` 请求单独存在，未计入下表的正式推理工具数。

创建了 3 个 `E2E-MCP-20261024` 测试对话，共 6 轮消息；第一个基线回合进行了只读 SY 工具索引搜索，之后均要求直接回复固定标记。没有发送邮件或外部消息，没有要求模型读取业务文件。

## 发现与修复

关闭 SY Figma 后，原实现仍将其放入“预期连接”清单，虽然 SDK 已正确禁用它，日志仍报 `expected-server-unavailable`。修复为从预期清单中排除 SDK settings 中按名称拒绝的服务器；原有拒绝策略仍传入 discovery 和正式查询。新增两个回归用例分别覆盖显式预期名称和从配置推导名称，两例先复现失败，修复后通过。实机复测中预期清单为空，未再出现这条误报。

## REA pending 后续追查与修复

本节覆盖本次用户要求继续追查后的新证据，取代首轮“REA 未加载”的验证边界。证据另存本机忽略目录 `work/agent-mcp-rea-e2e/`，沿用真实 HTTP 正文转发、脱敏副本、原始字节长度及摘要方法。新增两个 REA 测试对话，共七轮；所有提示均禁止调用工具、读文件和发送消息，只要求回复 `REA-E2E-OK`。

### 根因与边界

1. macOS 私有存储 sandbox profile 拒绝所有 outbound Unix socket，误拦系统解析器 `/private/var/run/mDNSResponder`。保护内 `npx` 访问 npm registry 报 `ENOTFOUND`，REA 无法初始化；不加保护时相同服务正常启动。逐项去掉 Mach 与 Unix 限制证实根因在 Unix socket，不是 REA 安装或用户全局配置。修复仅允许 root 所有的系统精确 socket；`/var/run` 别名未生效。任意同名 broker、私有文件、祖先重命名与跨沙箱进程仍被拦截。
2. DNS 修复后，全部原 MCP 并发启动时 REA 仍可能在 5 秒发现期限内 pending（请求 87），导致正式查询跳过。将初始化后的 pending 总等待调整为有界 10 秒，控制 RPC 仍限制为 5 秒；第六秒连接回归用例证明不再提前跳过。最后一次 status RPC 跨总期限时保留已连接服务，不误入空 MCP fallback。
3. 延长等待同时修复启动取消竞态：停止可取消 settings/init/status 等待，finally 关闭 discovery；停止后不能创建正式查询或 fallback，不能消费排队 prompt。已开始的正式查询保持原生停止协议；discovery 关闭失败继续报停止未确认，不伪称成功。
