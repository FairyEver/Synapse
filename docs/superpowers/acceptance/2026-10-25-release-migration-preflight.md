## 2026-10-25 隔离 PostgreSQL 预演

使用本机 PostgreSQL 16.15，在新建的临时数据目录中启动仅接受私有 Unix socket 连接的数据库。没有连接生产库，也没有读取生产数据或凭据。

1. 执行本次两项迁移之前的全部 86 项迁移，建立旧版完整结构。
2. 插入一个虚构用户和四条通知，覆盖已读/已删除状态、站内信原始链接、自定义分组、用户 URL、其他来源及空链接。
3. 用 `pg_dump` 备份旧库，再用 `pg_restore --exit-on-error` 恢复到另一个隔离库。
4. 在恢复库应用 `20261023000100_mail_internal_namespace` 与 `20261024060000_add_user_contact_email`。
5. 逐字段比较迁移前后的通知和用户记录：只有匹配的来源、分组和系统链接发生预期变化；投递去重键、已读/删除/创建时间及其他字段完全相同。新增联系邮箱为 null，已有用户字段不变。
6. 重复执行命名空间更新，结果不变；通知投递去重的唯一索引仍在。最后正常停止临时数据库。

结果全部通过。命令日志保存在本机 `/tmp/synapse-review-r4-postgres.log`。正式部署仍须由 `deploy.sh` 对当时的生产备份执行恢复预演、最终备份和恢复验证；本次虚构数据预演不能替代这些步骤。

## 2026-10-25 macOS 实际更新与恢复

用户明确授权实机验收后，先对本机约 9.5 GB 用户数据做私有 APFS 备份，并归档实际安装的 1.0.79；没有上传这些数据或凭据。候选是当前代码构建、签名并由 Apple 接受公证的 1.0.80。公开更新源没有改动，旧版进程仅在本次运行中使用回环地址候选源。

- 故障场景：通过原有权限、审计和受控执行器暂时禁用本应用 ShipIt，并设置独立恢复保护。交接在 120 秒硬上限拒绝后，1.0.79 进程和可见主窗口仍存在，1.0.80 下载保持 100%，待安装记录已回滚。随后恢复 ShipIt 原始启用状态，保护进程也确认恢复成功。
- 实际安装：旧版 Electron 41 的原生暂存约耗时 200 秒，超过交接上限；执行了已有受控 `ensureShipItStarted` 恢复入口，观察到 ShipIt 为 running 且有有效 PID，旧进程当时仍在。暂存完成后正常退出旧版，原生 ShipIt 日志确认安装成功，并启动真实的 1.0.80 / Electron 44.9.3。**该路径包含人工调用恢复入口，不能记为全自动更新成功**；未放宽交接上限或退出门。
- 升级后的实际安装通过 `codesign --verify --deep --strict`，窗口标题和已安装版本均为 1.0.80。
- 登录：旧版通过正常浏览器流程建立在线基线；升级后无需再登录即可保持同一账号在线。新版原生 safeStorage 成功读取旧版保存的加密刷新凭据，比较保存的 `lastProfile.user.id` 哈希确认同一身份，不记录或上传凭据明文。
- 终端数据：在创建测试会话之前，升级前后 21 个分组、2 条加密命令、全局启动设置、工具栏和工作区的摘要完全一致。
- 实际 PTY：在已安装新版中通过终端服务启动临时 shell，验证输入输出、`stty` 实际 100 × 30 尺寸及正常结束后的自动清理。临时会话已清理，没有改动既有命令内容。
- 实际脚本：对已安装应用执行 `verify-packaged-script-runtime.mjs`，Chromium Worker 与 Node.js 运行时检查通过。

本机候选在线公证为 Accepted，Gatekeeper 返回 Notarized Developer ID；本机写入离线票据被系统拒绝。正式 Release 的签名、公证、包结构与原生探针仍须独立通过，不能用本次本地在线结果替代正式制品门禁。测试用主进程 inspector 与回环源已关闭，应用已正常重开。

脱敏结果保存在本机忽略目录 `desktop/release/review-v1.0.80-acceptance/`；目录含私有备份，不提交、不上传。
