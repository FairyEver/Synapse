## 1. 意图与已确认边界

卡牌模式让随机得到的能力牌成为德州扑克的策略资源。玩家可以依靠下注与读牌，也可以使用换牌、情报、资源、防护及筹码效果改变局势；两种打法可以在同一局中共存。卡牌保留强弱差异和组合空间，不要求每张牌同等强度。

下列内容已经由用户明确确定：

1. 建房时设置卡牌开关，房间创建后固定。卡牌与 Roll 可以同时开启；两者通过公共领域能力合作。
2. 每局为所有参赛真人随机发 3 张能力牌；机器人不领牌、不用牌，但可作为合法效果对象，用于单人测试。完整的卡牌攻防面向 PVP。
3. 翻牌、转牌、河牌阶段开始时，仍可行动的真人各抽 1 张。弃牌、全下、未参赛及机器人不参与阶段补牌。
4. 本人行动回合内，可以连续使用多张卡牌，再完成正常德州行动。选择和使用共用当前服务端倒计时；时间类效果可以改变时间。
5. 本局结算时清空所有未使用能力牌、待选候选和持续效果；下局重新建立卡池。取消本局也清理运行态，但保留过程审计。
6. 全桌共用有限、抽取不放回的能力牌池。卡牌实例离开池后不供其他人重复抽取；消耗后不自动回池。明确的生成效果可以创建新的实例。
7. 每种卡的初始份数在代码定义中配置，未声明时为 1；不是房主或玩家可调整的设置。
8. 首批 60 种、初始 90 张，其中 30 种各 1 张、30 种各 2 张。六真人完整参与四阶段时，基础发放最多 36 张，余量供卡牌效果抽取。
9. 玩家仅知道本人持有的卡、全桌已使用的卡。剩余池内容、其他人的持牌内容不可见；私密效果结果按受众隔离。
10. 支持立即、持续、延迟及条件触发效果。卡牌通过声明注册到整局生命周期；新卡不逐一扩展 Roll、下注或页面分支。
11. 用牌后消耗该实例。默认免费，允许卡牌声明额外筹码代价。
12. 首阶段禁止外部 AI 参与卡牌房；预留未来开放策略，不要求程序机器人理解卡牌。
13. 第二摞筹码统一称为“暂存”。Roll 费用是暂存的一种来源，卡牌费用等可以使用同一机制；正常下注进入底池。
14. 暂存保留付款来源与待分配人。默认在存入时记录其他未弃牌参赛者的分配资格，包括全下者；后来弃牌不丧失剩余份额。
15. 盗取从其他人的待分份额按比例扣减，排除盗取者自己的份额；立即进入盗取者可用筹码。取回只取原笔剩余金额，不追回已取走的筹码、不从其他存款补足。
16. 筹码豁免适用于本人下一次需要支付筹码的场合，必须有最大额度。普通下注可以名义成立而实际减免；底池只接收真实投入。盲注在手动行动之前自动支付，通常没有提前打出卡牌的机会。
17. 每张卡有直观的法术式名称和一句明确规则，封面使用 GPT 生图，统一风格、少量元素、易懂精致。

**设计者补充、已随本稿整体确认的部分**：第 5 节的虚拟下注与边池算法，第 8 节完整 60 张的效果、份数和数值，第 9 节视觉方向，以及本文明确标为工程默认值的时限和运行预算。确认设计不表示这些参数已经过平衡测试。

## 2. 现状、方案与职责

已经阅读现有 `server/src/game/poker/engine/hand-runner.ts`、`betting.ts`、`pots.ts`、`roll.ts`，以及 `poker-roll.service.ts`、`poker-action.service.ts`、`poker-lifecycle.ts`、`poker-roll-ledger.ts`、大厅待转移逻辑和 Dashboard 牌桌入口。当前筹码扣款分散在下注、盲注和 Roll 中；Roll 在扣费时直接生成冻结补偿。现有事件接口是近期音画投影，不能直接充当可中断的规则执行器。

### Approaches

| 方式 | 优点与代价 | 本稿选择 |
| --- | --- | --- |
| 每张卡注册独立 TypeScript 生命周期处理器，调用领域操作 | 容易表达特殊效果；每张卡都需要更多代码，并自行协调条件、选择与表现 | 保留为特殊操作的扩展方式 |
| 声明条件、目标、代价、效果步骤及触发器，组合已注册的类型化领域操作 | 初始要建设执行器；常见新卡仅需定义，选择、隐私、恢复与审计共享 | 采用为主要方式 |

用户直接指定“整局生命周期、声明与注册、系统解耦”的方向。本稿据此采用第二种为主、第一种补充；这项具体组合由设计者提出。继续使用现有房间锁、数据库事务、快照和回执体系，不要求重写所有游戏为完整事件溯源，不增加依赖。

## 3. 生命周期与声明式运行时

### 3.1 操作与事件

每个操作遵循：校验意图 → 生成执行方案 → 执行前修正规则 → 重验合法性与预算 → 执行领域操作 → 记录事实 → 按序处理派生效果 → 保存及提交 → 投影与表现。

执行前接入点可以在自身声明范围内减免、替换、阻止或改选目标。执行后的事实不可被监听器篡改；监听器只能排入新的领域操作。普通报价与合法动作查询只做无副作用预演，不安装或消耗任何效果，也不取用随机结果。

建议注册以下事件族，而不是让所有业务监听一个含混的“抽牌”：

| 事件族 | 执行前/执行后的接入示例 |
| --- | --- |
| `hand.*` | 初始化、开局完成、准备结算、结算完成、取消 |
| `street.*`、`turn.*` | 阶段转换、阶段补牌、回合开始/结束、超时 |
| `poker.*` | 准备发牌/发牌完成、替换/交换、烧牌、洗牌、查看/公开底牌 |
| `ability.*` | 准备用牌、用牌结果、抽取、选择、消耗、生成、状态安装/触发/移除 |
| `chips.*` | 请求支付、支付修正、实付完成、暂存存入/取出、分配、返还 |
| `bet.*` | 下注提交、下注完成、名义匹配、真实投入变更 |

事件至少带本局、事件序号、操作者/目标的本局身份、来源、根动作 ID、父事件、可见范围和版本；不把账号 ID、暗牌或随机种子塞进公开表现事件。保留 `human`、`rules_bot`、`timeout` 等真实动作来源，派生效果另带来源卡与效果实例。

### 3.2 定义与实例

卡牌定义包含稳定 ID/版本、名称、规则文案、封面引用、标签、`copies`（默认 1）、使用窗口、目标与选择 schema、代价（默认零）、效果步骤、触发器、持续期/次数、叠加策略、可见性与表现引用。

独立运行实体包括：能力牌实例、持续效果实例、待选择实例、扑克牌操作保留区和暂存账本分录。消耗一张卡后，由它安装的效果独立存在，引用原卡实例作溯源；不会因为来源卡已消耗而丢失，也不把同一张卡同时算在两个区域。

能力牌实例区域为共享池、玩家手中、待选保留区、已消耗/已销毁区。任意时刻满足：初始实例数 + 已生成实例数 = 各区域实例数之和。已用实例不可复活；生成同名牌创建新实例。

房间保存不可变模式及规则版本；每局保存目录、配方、数值、操作语义版本的可验证快照引用。旧版本实现必须留到相关局完成与归档可读；服务升级不静默改写正在进行的卡池或持续效果。

### 3.3 顺序、触发与失败

同一事件按已注册优先级、安装序号、稳定效果 ID 排序；防护/替换、费用修正、执行、后置触发分别属于明确阶段。每个有限次数效果，只在它确实参与一次已提交的处理时扣次数。一次性豁免只针对正金额支付，未用满额度不结转。

派生事件进入同一根动作的有序队列，当前因果链收敛后才推进下一行动点、下一阶段或最终结算。记录 `(事件 ID, 效果实例 ID)` 去重；额外抽牌等派生操作标注原因，不能把自身生成的同类事件无限再增强。报价、拒绝、重复回执、回放与恢复都不重新触发规则。

工程预算提案：一条根动作最多 128 个派生操作、32 层因果深度；本局最多 1024 张生成后的能力牌实例、每人最多 64 个同时生效状态。注册时检查显式次数、金额、选择基数及终止条件。越界或实现异常时拒绝并回滚当前事务，保留先前成功动作，报告明确错误；不截断一半效果后宣称成功。这些是故障边界，不是每回合出卡张数限制。

区分输入无效与效果被防护：无效/过期请求无消耗；合法卡牌被护盾阻止属于已完成的出牌，正常消耗卡及已确认代价，记录“被阻止”，同时消耗实际触发的护盾。组合效果中可局部阻止哪些步骤必须在操作契约中声明；扑克牌整批交换/洗牌始终原子执行。

卡级反制先于具体领域操作的防护检查；同一接入点遇到首个有效阻止后停止，后续同类保护保留次数。公开单目标敌意操作先检查反制，再执行改牌/信息保护；群体牌不会因为只剩一个外部受影响者而变成单目标牌。敌意标签包括对他人改牌、查看/公开私牌、查看能力牌、盗取、加费和缩时；自愿公开本人底牌、群体补给和纯展示不属于敌意。

### 3.4 人的选择与事务

通常先在客户端收集本人底牌槽、目标玩家等已知选择，再一次提交。需要随机候选后再选的卡分成开始和选择两次提交，候选先保存到私有保留区；等待玩家期间不持有数据库事务或房间锁。

同一行动点最多一项规则选择待完成，Roll 候选和能力牌候选共用这项互斥。待选期间禁止开始另一种会改变牌堆的操作或正常下注；保留既有同槽 Roll 重抽入口。关闭面板不撤销已提交操作，不重置倒计时。

这里的互斥范围包含所有新的主动能力牌，不仅是改剩余牌堆的牌：03/58等只改底牌、51等改时间也不能在待选期间施放。原待选类型为Roll时，可以按原规则在原槽重抽；原待选为能力牌时，不能另起Roll。只读与既有离桌等管理入口保持可用，但管理必须先按原局状态完成必要的候选回退，不能借管理丢弃已承诺候选或换掉原实体。

待选绑定账号、原入座、本局、阶段、行动点和选择版本；选择请求使用当前状态序号和原选择 ID。超时选已持久化候选中的第一项，再依当前合法动作执行既有过牌/弃牌逻辑。第一版自动触发器仅执行不需要人即时选择的操作；未来注册交互触发器必须声明可用的本人回合窗口和服务端回退策略。

重复请求先核对原 actionId、完整意图散列及原受众，返回原回执；不会再抽牌、扣费、消耗状态或重播音画。随机结果与版本在成功事务中落盘，回放读取结果；失败前产生的临时熵不作为已发生的抽取向客户端公开。

## 4. 发放、持牌和参与者

每局先确定参赛身份、创建并洗匀 90 张共享池、处理扑克牌和实际盲注，然后给每名参赛真人分 3 张能力牌，再开启首个行动点。初始卡都需主动使用，不在持有时自动安装效果，因此盲注前没有手动使用赦免的窗口。

阶段转换先发出该阶段公共牌，处理相关已安装效果，再向仍可行动的真人补牌，处理补牌派生效果，最后开始正常行动回合。自动发完公共牌直接结算的情况下，不向已经无法行动的玩家补能力牌。阶段补牌每局每阶段至多一次，重读、重连和重启不补发第二次。

共享池不自动回收已消耗牌。请求抽 N 张但只剩 M 张时，实际抽 `min(N,M)` 张；零张时明确显示牌池已空，不凭空生成。多人同时补牌按庄家左侧的固定顺序轮流各取一张，直到本次额度用完或池空。后续生成入池后，未来抽取可以继续。

持有能力牌不另设玩法手牌上限，面板按内容滚动；生成总量仍受运行预算保护。弃牌后持牌留在本人区域直到本局清理，不返还共享池。全下后不新增主动行动点；被动效果仍按其有效期工作，即使随后获得暂存筹码也不解除本局已经成立的全下。

默认持续期为本局结束；单卡可更早到期。个人防护和已安装触发器在弃牌后按声明持续，但无法主动出牌；全局效果不会因施放者弃牌或离桌自动消失。来源与归属均绑定本局原入座，不由后来同座位的人继承。

首阶段模式能力策略为 `humanPlay=true`、`aiPlay=false`、`botReceivesCards=false`、`botUsesCards=false`。AI 入座、接受交接及参赛写操作（准备、开始、下注、Roll、用牌等）须服务端拒绝，不能只隐藏接入按钮。MCP 对卡牌房仅返回公开对局数据，不借本人身份导出私牌、持牌或候选；已有房间管理操作不授予参赛权。新用牌/选择操作仅接入私有 Web UI surface，不新增卡牌 MCP 工具。未来通过模式策略与受控观察契约开放 AI，不改写卡牌效果。

程序机器人沿用陪练房现有策略与资金边界；可以按现有规则下注、Roll，接收更改后的本人扑克牌及公开状态，但不读取对手私牌、真实牌堆、隐藏能力牌池或其他人的私密效果结果。卡牌改牌与保护照常作用于机器人，随机目标可以选中机器人。

## 5. 支付、豁免与真实底池

### 5.1 公共支付协议

支付请求包含付款人、资金域、筹码/钻石资源、用途、名义金额、去向（底池/暂存）、根动作和确认版本。返回原价、逐项修正、减免、实付、满足情况及账本引用。用途用于审计和特定效果筛选，不由 Roll 硬编码“是否持有某张卡”。

注册支付修正后，Roll 筹码费用、卡牌费用、普通下注、跟注、加注和盲注都通过同一筹码流程。钻石仍有自己的支付与次数协议；首批赦免只匹配筹码资源。无卡牌效果时沿用既有结果。

例：Roll 原价 20 筹码与 1 钻石，剩余豁免额度 100，则实付筹码 0、减免 20、钻石实付 1，Roll 成功并正常累计次数；没有真实筹码进入暂存，也不产生虚构待分份额。失败时不消耗豁免或钻石。报价展示预计实付与减免，提交绑定预演版本；不能展示减免价却按原价静默扣费。

第一版筹码代价都需整数且受版本化额度限制；非下注用途默认必须给付款人保留至少 1 颗可用筹码，以完成后续扑克行动。未来允许耗尽筹码的特殊代价需声明对应行动状态规则。费用先结算，再安装这次出牌新增的效果，因此卡牌不能回溯减免自己的费用。

同一次施放的基础卡费与49号等追加卡费，先合并为一笔卡牌支付再应用豁免，账本保留来源分项。例：38号2BB加49号2BB，遇32号3BB豁免，应付4BB、减免3BB、实付1BB；不能因内部函数将费用拆成两次调用而改变卡面结果。后续触发产生的独立支付属于新的支付事件，已用的一次性豁免不会复用。

### 5.2 名义下注与资金分开

用户已确定免付后正常下注可以成立，底池不凭空增加筹码。本稿提出以下完整语义：

- **名义下注**参与本轮跟注要求、最小加注、加注权、累计争池上限和边池资格。
- **实际投入**才计入真实底池、筹码动画、资金账本及正常投入统计。
- 每笔下注记录名义追加、实付、减免及来源。名义金额 = 实付 + 减免；减免不是额外筹码资产。
- 报价按实际可支付能力给出上限。首批只有有限的一次性固定额度豁免时，单次名义追加上限为可用筹码加本次可适用的豁免额度；豁免不会因为反复查询或下一轮下注重新获得。
- “全下”提交到使本次实付恰好耗尽当前可用筹码的合法名义上限。例：可用 500、一次豁免 100，则全下名义追加最多 600，实付 500，状态为全下。跟注 80 且豁免 100 时，名义跟注 80、实付 0，仍有实际筹码，所以不会误标全下。
- 未来支付修正器必须提供可终止、单调的支付能力预演契约，不能让下注上限依赖无限迭代或无界金额。

现有 `streetBet` 的下注匹配语义继续作为名义值；累计实际投入保留真实资金语义，并增加累计名义投入。`potContributions` 和现有实际 `amount` 统计继续投影实付，减免出现时附加名义与减免信息。不能将名义投入写进大厅资产。

### 5.3 边池与返还算法提案

按各玩家累计名义投入的不同正数建立层级。每名玩家在某层的名义贡献为该层上下界与其累计名义投入的交集长度；玩家自己的累计实付，按他在各层的名义贡献比例分摊到这些层。使用整数最大余数法，余数相同优先较低层，保证各层分配之和精确等于该玩家实付。弃牌人的真实资金参与分层，但不取得胜者资格。

每层的实际金额为所有玩家分摊到该层的实付之和；争池资格按达到该名义层的未弃牌玩家决定。零金额层不派钱、不制造资产；只有一个名义贡献者的最高层，只返还该层真实金额，减免没有可返还的实体筹码。胜者平分余数沿用现有庄家左侧规则。这个算法已随整体设计确认，实施时仍需用独立例子验证。

非摊牌而只剩一名未弃牌者时，沿用既有单人胜出的结算规则：真实未匹配最高层先返还，其余真实底池归该玩家，不因高层贡献者后来弃牌而留下无人可领取的资金。没有减免时，全部分层、返还与胜出行为应退化为现有规则。

例：A 名义 100/实付 0，B 名义 100/实付 100，C 名义 50/实付 50。第一层名义高度 50，真实金额 100，由 A/B/C 争夺；第二层真实金额 50，由 A/B 争夺。总池只有实际的 150，不产生 A 被豁免的 100。A 可以按名义资格争池，正是这张有限额度卡提供的增益。

### 5.4 资金守恒

运行中始终核对：`本局所有逻辑参与者的可用筹码 + 尚未派发的真实底池 + 暂存剩余金额 = 本局初始总筹码`。名义下注、减免额和待分份额不重复加到等式中。结算按底池派彩/真实返还 → 暂存最终分配 → 输光/离桌处理推进。陪练取消及离场销毁单独记录，点数不被取消操作销毁。

## 6. 通用暂存与账本

### 6.1 归属与变更

界面第二堆名称统一为“暂存”。每笔存入形成一批记录，含原付款入座、来源类型/动作、初始实付、剩余、待分配人及份额。Roll 和卡牌费用默认在实际存入时，给其他未弃牌参赛者（包括全下者）均分；余数按庄家左侧顺序分配。原付款人不在自己该笔默认分配中。来源类型及分配策略可注册，未来机制可以声明其他明确策略。

待分是可被本局卡牌改变的预分配。历史支付流水不可改写；盗取、退回、护盾拦截和最终释放各追加独立流水。每笔原始金额 = 现存金额 + 已盗取 + 已退回 + 已最终分配，任何部分不能分两次。

这明确取代新规则牌局中原“Roll 扣费时不可撤回确权”的假设。已按旧版本产生的冻结补偿仍按旧版本完成，不能把已经确定的历史权益静默改成可盗取的暂存。新房间/新局使用明确的资金规则版本；存量房间升级方式在迁移计划中写明，不修改正在进行的快照。

### 6.2 盗取

盗取对象是其他本局身份的剩余待分份额，包含后来弃牌或离桌者，排除盗取者本人份额。实际盗取量为卡牌上限与可盗余额较小者。先按受影响人的总份额比例分配损失，再在该人的各笔来源之间按剩余金额比例分摊；两级都使用整数最大余数法，同余依庄家左侧、再依原存入序号确定。这避免通过拆分小额支付改变谁受损。

只有实际被取走的筹码立即进入盗取者可用余额。防盗状态在分配之前剔除受保护份额；若该次原方案会影响该受保护人，则消耗一次保护，随后对其他可盗份额重新计算上限。无人可盗时，主动盗取卡不可新提交；已合法出牌被防护至零则记录被阻止并正常消耗。

主动卡的可用性检查按防护之前的原始合法目标/正额份额判断，防护在执行时结算，允许玩家主动用牌消耗对方的公开护盾。33/34针对全体其他份额，防护后可以继续从其余份额同比取出；39先锁定原始份额最多的一个其他身份，遇该人的防护后不自动改选次富者，可能本次实得为零。

### 6.3 取回

“最近一笔”指本次用牌动作开始之前，本人原入座最后一笔实际正额存入。自身本次用牌费用不会变成退款目标；被完全豁免的零额支付没有暂存批次。该笔已空时不可使用，不自动跳到更早批次。全额取回只退还该笔当前剩余，取消相应待分；部分取回按该笔各人剩余份额同比扣减。已经取走的资金不追回，也不从别的批次补偿。

例：A 存入 120，B/C/D 原各待分 40。B 盗取 60，C/D 各减少 30，留下 B40/C10/D10 共 60；B 已获得 60。若 A 此时全额取回，A 得到剩余 60，三人的待分清零，B 已得 60 保留。若没有取回，则结算时按 B40/C10/D10 派发。

### 6.4 通用持久化与大厅

新规则需要通用暂存批次、受益份额及追加转移流水（表名由实施计划按现有约定确定），通过游戏资金域服务维护，不让大厅读取扑克表。所有键绑定资金域、游戏、房间、本局、原入座和稳定来源，不能凭当前座位号分账。

现有 `GamePendingTransfer` 继续表示旧冻结资产与最终释放凭据，不能直接原地改写它的不可变意图来模拟盗取。新暂存剩余份额通过通用接口加入大厅 pending 投影；与旧 pending 去重，标明尚未确定的待分含义，可用余额不包括它。会话 inPlay 只计实际可用筹码与实际普通投入；盗取、退款和预分配变化与相关会话投影在同一事务更新。

结算将剩余预分配固化为唯一最终转移，再释放；引擎已经加入桌上余额的只标记到账，不再次增加。原入座已离开的点数份额进入原账号及盈亏；陪练遵守原入座离场清零，不兑现或转给后来入座。大厅总额、净变化与补助资格检查需要共同覆盖新旧 pending，不能重复统计或借暂存反复领取补助。

## 7. 扑克牌、目标和效果边界

扑克牌始终属于当前 variant 的唯一完整实体牌组：手牌、公共牌、剩余牌堆、烧牌和待选保留区之和守恒。卡牌模式不改变 52 张/32 张的合法牌、牌型比较和每名玩家最终两张底牌的基本形态。替换卡明确写“先取新牌再归还旧牌”或“先洗回再抽”；不凭空生成重复扑克牌。

默认可影响本局未弃牌的其他参与者，包含全下者和程序机器人；不影响候场、历史回显或后来复用座位者。全下者没有主动用牌机会，但其底牌仍可能被改变，这一行为已随整体设计确认。弃牌者的底牌默认不再作为目标，其暂存份额仍可被资金效果影响。

全局批量改牌先处理保护，将受保护玩家的整副底牌排除，再在剩余目标之间原子执行；不足两个可交换目标时记被阻止，不半交换。信息保护拦截相应查看/公开操作。反窥只生成一次新的有来源的查看，不反射交换或任意指令，不形成重定向循环。

未来牌堆预知是对当时牌序的私有观察记录，不是不可变发牌承诺。预览下一张公共牌需跳过将被烧掉的牌；预览完整下阶段时按阶段取 3/1 张。任何影响牌序的发牌、Roll、换牌或洗牌都使预览标注失效，历史观察仍可本人查看；不把旧预览当作已锁定结果。

公开标记绑定实体扑克牌和到期条件，换到别的玩家手中仍按规则公开；回到牌堆时不公开所在位置。长期公开持续到本局结束，阶段公开持续到本阶段结束。实现不得用槽位标记意外公开另一张新牌。

同族状态默认独立安装并按序消耗，卡面写明单次/两次。全场同族场地默认以新状态替换旧状态，不叠加；驱散只移除声明为可驱散的卡牌状态，不能驱散原生房规、控制权、真实下注或已完成转移。

首批所有仍在生效的卡牌状态默认可驱散，按以下粒度注册，不能把“是否可驱散”留给每个UI猜测：

## 9. 界面、封面与表现

### 9.1 功能交互

建房表单在 Roll 旁增加独立“卡牌模式”开关，不提供卡池数量、份数、概率、代价或单卡配置。开启时明确该房间当前仅支持真人操作，原 AI 接入入口按模式不可用。房间列表/入座摘要标识该模式。

底部操作栏提供“卡牌”及本人持牌数量。非本人回合可以查看持牌，使用操作禁用并给必要状态；本人有合法行动时可进入用牌。持牌缩略图展示名称、封面、明确规则和实际额外代价；不靠悬停才能读规则。

2026-11-03 用户确认[卡牌舞台原型](../../prototypes/2026-11-03-poker-card-selection-design.md)后，本段 UI 方向更新为专用游戏覆盖层，替代先前 HeroUI Modal 方案。八类选择由服务端 choices 驱动；顶底固定、左卡居中不滚动，只有右侧详情纵向滚动。卡面仅 hover 抬起；不自动聚焦、不恢复焦点、不添加自定义键盘交互。其它系统面板仍使用 HeroUI 默认浅色。选中 → 按 schema 选择本人底牌/玩家/状态 → 确认实际代价与目标 → 提交。无额外选择的卡也保留明确“使用”动作，点开卡面不等于施放。目标可以通过面板中的合法玩家列表选择，并在牌桌对应座位高亮；不要求只用拖拽、悬停或精准点击缩放后画布。

面板持续显示当前公共牌和原剩余时间。点击关闭/收起退出舞台，不设置键盘关闭与焦点返回；与金额、Roll、成员、对局信息、牌型及结算面板互斥。待选择可以关闭重开，状态不丢失；当前回合结束、房间/账号/手牌/视角改变时清理未提交选择，未知写结果保留原意图核对。

持续效果在相关玩家处提供必要状态标记，详细名称、次数与到期信息按需查看；全场效果放在单一场地状态入口，不堆叠常驻介绍。保护或豁免只有实际触发时播放对应反馈。本人私密情报只在本人面板显示，不通过全局 toast 或公共动画泄露。

第二摞筹码的标题、金额、动画锚点和明细统一为“暂存”。明细按来源/付款人/当前待分人查看存入、盗取、退回及最终分配；原始支出和后续取回分列，净额可核对。旧版局的旧冻结补偿按其版本明确呈现。底池入口仍只展示真实普通投入。

### 9.2 封面方向

现行方向见[德州扑克能力牌封面](../../agents/game-ui.md#德州扑克能力牌封面)，取代首版的浅底柔光物件提案。`cards-v1` 的 60 种牌沿用稳定封面路径，牌效不同的后续版本使用独立 `artId`。封面和溯源清单随 Dashboard 静态资源打包。

## 10. 契约、存储与兼容

### 10.1 契约范围

基于实际导出源 `shared/src/game.ts`、`game-ui.ts`、`game-poker-response-schemas.ts` 扩展规则与视图；`@synapse/shared/game-contracts` 是导出入口，不是同名源码文件。

拟议增加私有 `app.game.poker.card.play` 与 `app.game.poker.card.choose`，仅通过当前经过认证/同源与白名单控制的 Web 入口调用。请求绑定 roomCode、handId、street、expectedActionSeq、controlVersion、actionId，以及牌实例、已确认目标/选择、代价预演版本；选择另带持久化选择ID。客户端不能提交付款人、卡牌定义、效果代码、实际扣款结果、生成数量或任意操作名来绕过规则。

表状态/房间详情按授权追加卡牌模式版本、本人持牌和可用性、本人待选、公开已用卡、可见持续效果、本人私密结果及通用暂存投影。服务器决定可见性，public切换、账号切换、缓存和历史也必须删除本人字段。卡牌定义文本可公开，实例所在区域和剩余配方不可公开。

“已使用卡”只公开实际施放的卡，不把作为额外代价消耗或被销毁的其他手牌自动公开；后者仅展示发生了消耗，身份留在授权私有记录。卡牌房的AI模式检查在回执返回之前执行，不能通过重放真人请求读取私有选择结果。新的未知用牌/选牌意图沿用Roll的按账号/房间sessionStorage写入后读回、原UUID核对和迟到响应隔离约束；存储不可用时禁止新能力牌写入，已确认的普通行动仍按真实待选状态处理。

每个外部成功写操作只增加一次当前行动序号；内部事件使用同一根动作下的递增 eventIndex。卡牌房新增版本化“结算帧”承载该根动作的全部已授权派生事件，帧不能被分页从中切断，事件唯一键为本局/行动序号/eventIndex。公开和本人投影共享根游标，私密子事件按权限过滤。近期音画读取使用完整帧，历史/归档使用完整审计，不能用近期事件重建余额。非卡牌旧协议维持现有读取语义。

新客户端必须识别规则与响应版本才允许入座操作；旧客户端不能忽略未知卡牌规则继续下注。AI策略、控制权与版本检查在服务端统一校验，超时和规则机器人使用受信内部来源，不由客户端传入 caller。

### 10.2 持久状态

本局快照持久保存：目录/配方/操作版本、90张初始实例及新增实例、各区域归属、已经完成的阶段补牌标记、持续状态和剩余次数、正在等待的选择、扑克牌保留区、名义/真实投入、暂存分录及最后处理位置。公开定义和封面以稳定引用存储，不把图片字节写数据库。

根动作回执、领域事件事实、随机结果、付款/转移流水和最终分配为可重放的不可变审计。快照用于运行，账本用于核对；不能在正常查询时重新抽样或把截断日志当权威状态。归档包含完整版本、卡牌去向、选择与私密结果并按原权限投影；源卡已消耗或玩家离桌仍保留可定位信息。

不在本稿确定最终 SQL 表名和迁移编号；实施计划先检查现有 Prisma、归档结构、约束与资金服务，产出可审阅的迁移、备份/预演和回滚条件。所有本局查询带明确条件与结果上限，账本及归档按稳定键分页；运行决策依有界快照，不每次扫描全房历史。

### 10.3 部署与恢复边界

新建房间带明确卡牌/资金版本；存量已创建房间维持原版本直到关闭，不把进行中的旧冻结补偿改成可盗资产。新房未开卡牌时，暂存v2沿用无干预的默认分配结果；开启卡牌时允许受本稿效果修改。界面通用“暂存”名称可以承载两版，但必须保持对应金额语义。

上线前先备份并预演迁移，再执行迁移、部署兼容服务端和含60张封面的网页客户端。按用户后续要求，新版服务端移除环境开关；受支持的真人网页可直接创建点数或陪练卡牌房，仍须通过身份和规则版本校验。已有新暂存、名义免付下注或候选后，不得回退到不认识这些资产和状态的旧服务端；需要暂停创建时，使用可按原规则完成已有局的兼容修复版本。

取消与异常恢复：只回滚失败的当前事务；不能因表现失败撤回已成功的支付、盗取或换牌。点数房沿原关闭流程等本局正常结算，不提供销毁暂存的捷径；单人陪练立即取消只清理练习资金并保留已执行过程，不制造正式盈亏。

## 12. 最小充分验证与交付证据

必须在实施中新增有意义的专项与不变量验证，不能只断言注册条目存在：

1. 60种/90张、默认份数1、30个双份定义、真人初始3与阶段各1、机器人零发放、弃牌/全下不补、每阶段只发一次、空池/部分抽取/生成/选择归还的实例守恒。
2. 52/32张牌组，最紧牌量、烧牌、Roll与候选互斥、单张/整副/全桌换牌及保护、牌序预览失效、实体公开标记、两种牌型排序；全过程无重复/丢牌。
3. 正/零支付、单次与叠加有上限豁免、报价不消耗、失败不消耗、全下名义上限、实际筹码保留规则、盲注时序、普通投入统计和钻石独立扣款。
4. 无减免时新边池与既有算法完全一致；有减免时名义资格、真实金额、单人最高层返还、平手整数余数、弃牌投入、零金额层和多次减免分摊。用独立手算/枚举器核对第5.3节算法，不能用同一实现自证。
5. 暂存原始分配、两级同比盗取、排除自己、防盗份额、部分/全额取回、最近批次已空、当前卡费不改变退款目标、离座身份、旧冻结兼容、最终只分剩余。逐步核对总资金和每笔去向之和。
6. 当前/过期控制版本、迟到响应、相同UUID重试、同UUID不同意图、刷新和重启、并发/锁/跨账号、原入座离开重入、候选超时和当前事务回滚。
7. 持续效果次数与有效期、优先级、驱散、保护/反窥、全场批处理、卡牌被拦截时消耗、自动触发链终止、128操作/32深度预算、结算前清空因果队列。
8. 本人/public/MCP/旁观/历史/归档投影，私密情报不进入公开日志、toast、缓存或音画；AI接入各服务端入口均拒绝、机器人仅收到合法观察。
9. 60张卡逐张具备可执行定义、明确目标/窗口/代价/次数/隐私/失效语义和正式封面，覆盖对应操作族；额外做组合样例：补给→换牌、赦免→Roll、暂存→盗取→退款、窥牌→防护→反窥、全下后受换牌影响。
10. 共享契约/服务端/Dashboard相关typecheck与测试、UI边界检查；真实本地隔离PostgreSQL迁移/资金并发/归档验收；获得启动授权后进行第9.3节的真实展开验收。涉及Electron打包边界时追加packaged-asar检查，不用无关全量测试替代专项证据。

## 13. 评审与确认

用户于2026-11-03明确回复“确认设计，进入实施计划”。已确认的玩法见第1节，本次整体确认也包括以下设计者补充：
