# Capability Naming Unification Design

> Superseded note: Synapse-owned CLI and stdio MCP capability entrypoints were retired after this document was written. Current external capability access uses loopback HTTP MCP; local HTTP `/api` remains an authenticated internal API.

## Context

Synapse currently exposes agent-facing local capabilities through one shared surface:

```text
underlying service capability
  -> local HTTP API action
  -> CLI command
  -> MCP tool
```

The current names were added in phases. Database capabilities still use older Database names such as `databaseTableList`, `database_table_list`, and `synapse database table list`. Scheduler capabilities use newer names such as `schedulerTaskCreate`, `scheduler_task_create`, and `synapse scheduler create`.

This creates four naming systems for one capability. Future domains would drift unless Synapse makes one canonical manifest the source of truth.

There is no historical compatibility requirement for this rename. Old MCP tools, CLI commands, API actions, and public capability methods can be removed instead of aliased.

## Goals

- Make one canonical capability id the source for API, MCP, CLI, and public service method names.
- Rename current Database and Scheduler external capabilities to the same scheme.
- Prefer short, complete words over long compound names when the domain already provides enough context.
- Avoid opaque abbreviations such as `db`, `cfg`, `op`, or `exec`.
- Use `database` as the domain name instead of `data_store`.
- Keep `scheduler` as the domain name.
- Align public service and dispatcher handler method names with the same vocabulary.
- Update user-visible English UI copy from "Database" to "Database".
- Add tests and a human-readable naming matrix to prevent future drift.
- Remove old names directly. Do not add compatibility aliases or deprecated command paths.

## Non-Goals

- No renderer preload API rename unless it is part of the external capability chain.
- No directory, IPC channel, data-track, or type-name rename just because it contains `database` or `Database`.
- No rename of persisted Action Runtime type ids such as `builtin.command`, `builtin.script`, or `builtin.http-request`.
- No broad internal refactor beyond public service or dispatcher methods that represent external capabilities.
- No UI redesign. This only changes user-visible wording from Database to Database where applicable.

## Naming Principles

Use a canonical id for every external capability:

```text
<domain>.<resource>.<action>
```

Rules:

- Domain tokens should be one complete English word when possible.
- Resource tokens should be as short as possible without changing meaning.
- Multi-word tokens use snake_case.
- Actions come from a controlled vocabulary.
- Resource names normally use singular form.
- Plural resource names are allowed only when the distinction is the point of the capability, such as `rows.create` or `rows.update`.
- Do not use abbreviations unless they are the common product term, such as `sql`.

Controlled action vocabulary:

```text
list
get
create
update
delete
count
rename
describe
inspect
enable
disable
read
execute
```

`execute` is high-risk by default and is reserved for SQL, script, command, or similar execution capabilities. Capabilities using it must explicitly set `mutates: true` unless they prove otherwise.

## Derived Names

Every public name is derived from the canonical id.

For `database.table.list`:

```text
API action:     database.table.list
MCP tool:       database_table_list
CLI command:    synapse database table list
service method: databaseTableList()
```

For `scheduler.runtime.inspect`:

```text
API action:     scheduler.runtime.inspect
MCP tool:       scheduler_runtime_inspect
CLI command:    synapse scheduler runtime inspect
service method: schedulerRuntimeInspect()
```

Public JSON input and output fields use camelCase:

```text
tableName
columnName
rowId
taskId
projectId
createdAt
rowCount
```

CLI flags use kebab-case:

```text
--table-name
--column-name
--task-id
--project-id
--order-by
```

Key resource identifiers should be positional CLI arguments when the command remains clear:

```text
synapse database table describe <tableName>
synapse database row update <tableName> <rowId> --data '{...}'
synapse scheduler task get <taskId>
```

Complex data, filters, ordering, dry-run, and pagination stay as flags.

## Manifest Model

The shared capability manifest should be the only place where a capability id is hand-written.

Illustrative shape:

```ts
type CapabilityManifestItem = {
  readonly id: CapabilityId
  readonly title: string
  readonly description: string
  readonly mutates: boolean
  readonly inputSchema: McpInputSchema
  readonly outputShape?: string
  readonly risk?: "normal" | "high"
  readonly serviceMethod?: string
}
```

Derived fields should be generated by helpers:

```ts
deriveApiAction(item.id)
deriveMcpToolName(item.id)
deriveCliCommandPath(item.id)
deriveServiceMethodName(item.id)
```

The manifest should also expose domain ownership so the action router can dispatch by the first token:

```text
database.* -> Database dispatcher
scheduler.* -> Scheduler dispatcher
```

## Public Parameter Rules

Use explicit resource identifier names:

```text
tableName
columnName
fromTableName
toTableName
fromColumnName
toColumnName
rowId
taskId
projectId
```

Avoid generic `name` or `id` when the resource type is known.

Examples:

```json
{
  "action": "database.table.describe",
  "tableName": "contacts"
}
```

```json
{
  "action": "database.row.update",
  "tableName": "contacts",
  "rowId": 42,
  "data": { "status": "active" }
}
```

```json
{
  "action": "scheduler.task.get",
  "taskId": "task:..."
}
```

## Service Method Scope

Public methods that correspond to external capabilities should be renamed to the derived lower-camel-case form.

Examples:

```text
databaseTableList()
databaseRowsUpdate()
databaseSqlExecute()
schedulerTaskCreate()
schedulerRunList()
schedulerRuntimeInspect()
```

This applies to public service methods, dispatcher handler names, and adapter methods that form the external capability chain.

Private helpers can be renamed only when touched by the capability migration. Do not rewrite unrelated private implementation details only for naming symmetry.

## Action Runtime Type Ids

Action Runtime ids remain unchanged in this migration:

```text
builtin.command
builtin.script
builtin.http-request
```

They are persisted task configuration values and represent plugin or action type ids, not Synapse external capability ids. A later dedicated migration can define whether those ids should move to a canonical scheme.

## UI Copy

User-visible English copy should use `Database`.

Examples:

```text
旧资源名 -> Database
Synapse Database CLI -> Synapse Database CLI
Database mutations -> database mutations
```

Chinese copy that already says "数据库" should stay as-is.

The final migration is project-wide: paths, types, IPC/preload bridge names, tracking ids, scripts, generated bundle names, tests, and docs should all use the `database` naming family. Only true storage internals or legacy cleanup sentinels may keep historical values when changing them would break existing user data cleanup.

## Migration Strategy

Because there is no compatibility requirement, remove old names directly:

- Remove old MCP tool names such as `database_table_list`, `database_log_list`, and `scheduler_task_runs_list`.
- Remove old API actions such as `databaseTableList`, `databaseLogList`, and `schedulerTaskRunsList`.
- Remove old CLI commands such as `synapse database table list`, `synapse database log list`, and `synapse scheduler run list`.
- Update tests, docs, and generated copy to use canonical names.

Repository content can be changed automatically.

User-local content should be scanned and reported, not edited automatically:

- local `.codex` and `.agents` rules or skills
- editor MCP config files
- Synapse userData
- private project rules outside this repository

The report should list matched old names and suggested replacements.

## Tests And Verification

Add parity tests that enforce:

- Every manifest id is valid `<domain>.<resource>.<action>`.
- Every action token belongs to the controlled vocabulary.
- Every generated MCP tool name matches the manifest id.
- Every generated CLI path matches the manifest id.
- Every generated service method name matches the manifest id.
- API actions accepted by the external router are canonical ids.
- Old MCP tool names are not listed and return unknown tool errors.
- Old API actions are rejected by the action router.
- Old CLI command paths are rejected.
- Database and Scheduler remain separate domains.
- Hidden Scheduler capabilities such as delete, manual run, and stop-run remain hidden unless explicitly added to the manifest.

Add or update a naming matrix document containing:

```text
canonical id
MCP tool
CLI command
API action
service method
mutates
risk
```

The matrix can be generated from the manifest or kept as a checked-in snapshot tested against the manifest.

## Implementation Order

1. Introduce canonical id helpers and tests.
2. Upgrade the capability manifest shape.
3. Rename Database manifest ids and generated MCP tool names.
4. Rename Scheduler manifest ids and generated MCP tool names.
5. Route local HTTP API by canonical id.
6. Change CLI parsing to the domain/resource/action path style.
7. Rename public service and dispatcher methods that correspond to external capabilities.
8. Update UI-visible English copy from Database to Database.
9. Update docs and generated schema copy formats.
10. Add the naming matrix and migration scan/report.
11. Remove tests that assert old names and add rejection tests for old names.

## Success Criteria

- One manifest item is enough to derive API action, MCP tool, CLI command, and public service method names.
- Current Database and Scheduler capabilities use canonical ids.
- Old external names no longer work and are covered by negative tests.
- User-visible English UI says Database, not Database.
- Existing Chinese database copy remains stable.
- No unrelated preload API, IPC channel, type, directory, or tracking id churn is introduced.
- Tests document and enforce the naming scheme.
