# 手机端录音

> 原型（可点，浏览器打开）：`~/Desktop/手机端录音/原型.html`
> 状态：2026-09-19 设计定稿待实施
> 界面用词、状态口径全部沿用电脑端 `docs/superpowers/specs/2026-09-19-meeting-recording-redesign-design.md`。两份文档冲突时以电脑端那份为准，除了本文件第 3 节明确推翻的两条。

---

## 1. 为什么要做

手机端「录音」Tab 已经有列表和详情，但**只能看，不能录**——没有麦克风采集、没有上传、没有权限申请、没有编辑。用户原话是"它有录音这个 tab，但它实际上没有录音功能"。

这一版补上采集这一头，把详情页做成和电脑端一致的两个平级视图，并让录音住进 iOS 系统里（灵动岛、实时活动、控制中心、主屏快捷操作）。

## 3. 这一版推翻的两条旧结论

| 旧结论 | 出处 | 现在 |
|---|---|---|
| **手机端录音是非目标** | `docs/superpowers/specs/2026-09-19-meeting-recording-design.md` §9，被两栏重构 §8 沿用 | 就是这一次要做的事 |
| **手机端不做播放** | 同上 §4.7，以及 `MeetingDetailView.swift:4-7` 的注释 | 改成做「语音 / 文字」两个平级视图（见决策一） |

要认下来的四条链路：**麦克风权限与后台音频 mode**、**AVAudioSession 中断**、**挂起状态下的分块上传**、**两端共享同一条服务端记录**（手机录的和电脑录的在同一个列表里）。

## 4. 决策

实施时不要再问，除非发现了推翻它的新事实。

### 决策一：详情页做「语音 / 文字」两个平级视图

和电脑端右栏一致。切换粘性（切到别的录音仍保持当前视图）。**转写失败时默认落在文字视图**（沿用电脑端 §4.5）。

这是本次**代价最大**的一项：手机上要新增音频下载、边下边播、播放会话管理，而播放会话和录音会话在 `AVAudioSession` 上是相互打架的（要 `AVAudioSessionCategoryOptionMixWithOthers` 与路由切换处理）。

**被否决的替代方案**：只做文字视图（退回现状，`MeetingDetailView` 现在就是这样）。

> **这一项可以单独砍掉。** 如果实施时觉得不划算，砍掉「语音」视图等于砍掉实施计划的阶段 5，其余全部不受影响。砍之前问一次用户。

### 决策二：麦克风被别的 App 抢走 → 自动暂停、自动恢复、不询问

来电、闹钟、其他 App 放视频，iOS 会直接掐掉录音会话。电脑端不存在这个场景，没有先例。

- 中断发生：暂停采集，界面提示行写明「录音已暂停，麦克风被其他应用占用」
- 中断结束且 `AVAudioSession.interruptionEnded` 给出可恢复提示：自动继续录**同一条**
- **界面不出现任何询问**

**为什么不是直接结束这条**：一场四十分钟的会，一个电话就断了，而且不能续。
**为什么不是静默录进一段空白**：那会让转写结果里多出一段不存在的静音，而 0.8 元/时照算。

注意：**用户不能手动暂停**。暂停只由系统中断触发，所以和「没有暂停」这条产品口径不冲突。

### 决策三：不引入红色，全部用主题色

电脑端的口径是「语音备忘录的红色是它自己的品牌主色，Synapse 不引入自定义颜色」，桌面端波形用的是主题前景色。手机端跟随：滚动波形、取消/完成按钮、实时活动里的内容全部用 `Theme.ink` / 系统语义色。

唯一的例外是**状态栏那个橙色麦克风指示点**——那是 iOS 自己画的，App 不做也做不了。

### 决策四：录音中允许离开录音页

录音页下滑收起，录音继续，App 内顶部出现一枚玻璃胶囊（计时 + 完成）。灵动岛和锁屏实时活动同步。

**被否决的替代方案**：录音期间锁死在录音页。更简单、不会误操作，但四十分钟的会里用户什么都干不了。

### 决策五：开始录音是导航栏右上角的加号

和终端一致（`Features/Sessions/SessionListView.swift:65-78` 的 `.toolbar { ToolbarItem(placement: .topBarTrailing) { Button { } label: { Image(systemName: "plus") } } }`）。**不要自创悬浮按钮。**

点加号**直接进录音页，不先起名字**——电脑端也是点「开始录音」直接进，名字事后在详情页点标题改。

**和终端的一处不同**：终端的加号在「没选电脑 / 电脑离线」时置灰，因为终端得由电脑来建。录音不依赖任何一台电脑在线（手机上采集、服务端转写），所以这个加号**没有禁用条件**，不要照抄终端的 `disabled`。

### 决策六：系统集成的范围

做：**灵动岛三态**、**锁屏实时活动**、**控制中心控件**、**主屏长按 App 图标的快捷操作**、**转写完成的通知**。

不做：**桌面 Widget**（用户明确排除）、桌面小组件、待机模式。

暂缓（等决策一确认后再定）：**锁屏播放控件**（Now Playing）与 **Siri / 快捷指令 / 侧边按钮**。两者和实时活动上的按钮共用同一份 App Intent，加进来很便宜，但只有确定做播放才有意义。

### 决策七：谁本机还留着残片，谁负责收尾

**这不是设计偏好，是不改就会出 bug。** 详见 §6.7。

一言以蔽之：**只有本机还留着这次录音残片的那一端，才有权收尾它。** 桌面看本地 spool 目录里有没有这个 `recordingId` 的分片，手机看本地还有没有那次的 m4a。

## 5. 交互规格

### 5.1 列表

沿用现在的 `MeetingListView`，只加两样：

- 导航栏右上角的加号（决策五）
- 列表往下滚时导航栏收成玻璃条，内联标题「录音」淡入

行内容不变：标题 + 副标题（开始时间 · 时长）+ 状态徽标。**不加**搜索、不加筛选、不加分组标题以外的任何东西（与电脑端一致）。

**手势**：
- 点整行进详情
- 向左滑露出「删除」
- 长按：整行抬起 + 其余内容模糊 + 下方浮出三个玻璃圆按钮（重命名 / 复制全文 / 删除）——这是 iOS 的上下文菜单，**不要做成底部动作表**

### 5.2 录音页

```
              新录音
              00:42
     ┌────────────────────────────┐
     │              ▁▃▅█▇▅▃▂▁▃▅▇█ │  ← 贴右边缘，从右往左长
     └────────────────────────────┘
            没有听到声音              ← 只在一直没声音时出现
                                    
           录音会保存，用于转写
        [  取消  ]    [  完成  ]
```

**波形与电脑端同一套口径**（电脑端 §3.6，明确继续有效）：

- **必须是真数据**，麦克风流同时喂给编码器和分析节点，每 28 毫秒取一次时域数据算振幅。不是随机柱状图。
- **密度固定**：一个采样永远占同样宽的槽位，录得越久不会把整段压进同一个框，而是旧的从左边滚出去。
- **贴右边缘、从右往左长**：最新的在右边缘。
- **只回看最近 5 秒**：槽位数同时受时间窗口和画布宽度限制，取小的那个。
- 配色用主题前景色，随深浅色走。

**提示行**（高度固定，不跳）：

| 情况 | 文案 |
|---|---|
| 4 秒没听到声音 | 没有听到声音（听到过一次就永不再提示） |
| 麦克风权限被拒 | 未取得麦克风权限，波形为示意（不阻断录音） |
| 被别的 App 抢占 | 录音已暂停，麦克风被其他应用占用 |
| 分片上传失败 | 红色，带上下文原因 |
| 其余 | 空 |

**没有暂停按钮。** 只有取消和完成。

**点完成立刻回列表**，不出现等待界面。**界面任何位置都不体现上传**。

### 5.3 详情页

头部：标题（可点击就地改，回车提交 / Esc 取消）+ 「开始时间 · 时长」。导航栏右侧一个「⋯」（重命名 / 删除）。

两个平级视图，分段控件切换：

**语音视图**——整段铺满宽度的波形卡片 + 播放头 + 播放键 + ±15 秒 + 「当前 / 总时长」。点波形任意位置跳转。**没有**倍速、时间刻度、缩略图、当前句高亮。

**文字视图**——一张卡片 + 自然段（约 110 字一段，服务端已按此存储）。底部悬浮「复制全文」玻璃胶囊，**没有文字时置灰而不是隐藏**。

**状态**（沿用电脑端 §4.5 与 §4.8）：

| 状态 | 表现 |
|---|---|
| 转写中 | 卡片顶部进度条 +「识别中 · 已用 01:20」+「48 秒的录音，预计 1 分左右完成」+ 已转好的部分 |
| 转写失败 | **默认切到文字视图**，显示失败原因 +「重试」。重试不需要重新上传 |
| 已完成 | 正常 |
| 录音被删（历史数据） | 语音显示「录音已删除 / 文字仍保留，切到「文字」查看。」；文字正常 |
| 没有识别到语音 | 「还没有文字 / 这段录音里没有识别到语音。」 |

**交互**：从左边缘右滑返回（交互式，拖到一半松手会弹回）。

### 5.4 系统集成

全部按系统模板渲染，Synapse 只提供数据和动作。

**灵动岛三态**（`ActivityKit`）：

| 态 | 内容 |
|---|---|
| 紧凑 | 左：波形图标（跟着声音动）；右：计时 |
| 最小 | 同时有两个实时活动时收成一个圆点 |
| 展开 | 上排：App 图标 / 传感器挖孔 / 计时；中间：滚动波形；下面：取消、完成两个按钮 |

**锁屏实时活动**：录音名 + 计时 + 波形 + 取消 / 完成。

> 2026-09-20 补记（样式按 Apple 规范重做）：
>
> 排布不变，改的是尺寸、字重、边距和颜色。四条值得留下来的：
>
> 1. **计时是主角，名字不是。** 锁屏那张卡高度上限 160 pt（超了系统直接截），原来
>    名字和计时都是 `.headline`，谁也压不住谁。现在名字 `.subheadline` + `.secondary`，
>    计时 `.title2` + `.semibold`。Apple 对实时活动的要求是「大字号、中等以上字重」。
> 2. **波形和 App 内必须是同一套比例。** 原来锁屏上是「有几个采样就把宽度分几份」，
>    32 个采样在一整行里摊成 32 根又粗又扁的方块；录音页那条是 1.5 pt 宽、1.1 pt
>    间距的细柱。现在两边共用 `RecordingActivityLimits.barWidth / barGap`（`MeetingAudio`
>    直接读它），柱宽间距固定、一行放不下就少画几条。载荷随之从 32 个槽位提到 160 个，
>    并压到三位小数 —— 它**每秒推一次**。
> 3. **锁屏内容边距 14 pt**，不是随手写的 16：这是 Apple 给实时活动锁屏形态定的标准
>    布局边距（HIG「Live Activities」Specifications）。系统只画卡片和圆角。
> 4. **颜色只用语义色**（`.primary` / `.secondary`），不引入第二种。扩展里没有 App 的
>    accent（App 内是 `Theme.ink`，也就是 `.primary`），写 `.tint` 会落回系统蓝，压在
>    灵动岛那块纯黑上既不是这个 App 的样子也看不清。`keylineTint` 一并去掉 —— 硬漆成
>    纯白会变成一圈很重的白边，那是系统自己该判断的事。

**控制中心控件**（`ControlWidget`，iOS 18+）：一枚圆角方块，图标 +「录音」，点一下开始。

**主屏长按 App 图标**（`UIApplicationShortcutItem`）：「开始录音」排第一。

**转写完成的通知**：已有推送通道，本次只改正文文案（见第 6 节）。

**状态栏的橙色麦克风指示点**：iOS 自己画的，App 什么都不用做，但截图、客服话术、以及「为什么这里有个橙点」都要能解释。

### 5.5 状态与异常

| 情况 | 处理 |
|---|---|
| 录音中途进程被杀 / 强退 / 更新重启 | 已经录到的部分**按正常录音处理**：下次启动自动收尾、进列表、照常转写，**界面上不出现任何询问** |
| 手机端**没有**「波形丢失」这个缺陷 | 见第 6 节第 4 条 |
| 上传中断 | 分片重传即可，已确认写入的区间不重传 |
| 取消录音 | 服务端**中止**分块上传并丢弃已传分片，不留残留（`DELETE /meetings/recordings/:recordingId`） |
| 音频超过 5 小时 | 服务端按 `MEETING_MAX_DURATION_MS` 截断；手机端在达到上限时自动收尾并提示 |
| 单条超过 200 MB | 服务端拒绝（`MEETING_MAX_RECORDING_BYTES`）。64 kbps 单声道下约 78 小时，远早于 5 小时上限触发，实际不会遇到 |
| **在电脑上删掉了手机正在录的那条** | 用户可以这么做（两端是同一份数据）。手机后续的分片上传会失败，录音随之消失。**这是用户明确要求的删除，不要回滚、不要提示、不要试图恢复**——手机端按上传失败处理，提示行显示红色文案即可 |
| **在电脑上重命名了手机正在录的那条** | 手机端不知情，也**不需要**知情。手机端只在本地持有标题的临时值，收尾后以服务端为准 |

## 6. 平台能力与代价

> 这一节是本次的真正成本，实施前读完。

### 6.1 要推翻一条有意为之的决定

`SynapseMobile/SynapseMobile/Info.plist:72` 的注释写着：

> No UIBackgroundModes on purpose. The app never receives a silent push: the server sends every alert as `apns-push-type: alert`, and the app delegate has no `didReceiveRemoteNotification:fetchCompletionHandler:`. **Claiming a background mode nothing exercises is something App Review asks about.**

后台录音必须加 `UIBackgroundModes: [audio]`。这条注释和它给的理由要**一起改掉**，写成新的理由（录音在后台继续），而不是留一条自相矛盾的注释。

同时 `NSMicrophoneUsageDescription` 现在是「用于把说的话转成文字填进终端输入框，以及录像时收录声音。」——**没提录音**。权限弹窗是用户第一次见到录音功能的地方，要补。

### 6.2 要新建一个 Widget 扩展 target

灵动岛、实时活动、控制中心控件在 iOS 上**只能放在 WidgetKit 扩展里**，主 App 放不了。用户明确不要桌面 Widget——那个扩展里就是不放主屏 Widget——但 target 本身绕不开。

- 主 App 的 `Info.plist` 要加 `NSSupportsLiveActivities`
- 扩展的 `Info.plist` 要声明 `NSExtensionPointIdentifier = com.apple.widgetkit-extension`
- 扩展的 bundle id 必须是主 App bundle id 的前缀
- `SynapseMobile.xcodeproj` 是**手维护的**，仓库里没有 XcodeGen / Tuist。改 `project.pbxproj` 是本次风险最高的一步，见实施计划阶段 0

**这是本次唯一一处新增构建产物**，打包、签名、TestFlight 全跟着变。用免费开发者账号时，扩展会额外消耗一个 App ID 名额。

### 6.3 全仓没有 App Intents

实时活动的按钮、控制中心控件、主屏快捷操作、Siri 快捷指令都是 App Intent，要从零建一套。四个入口共用同一份 intent。

> 2026-09-20 补记（**强约束，不要改回去**）：实时活动上那两个按钮的意图**必须是
> `LiveActivityIntent`，不能是普通的 `AppIntent`**。
>
> 普通的 `AppIntent` 默认在 **Widget 扩展的进程**里执行。扩展里没有录音机，
> `RecordingIntentRouter.handler` 在那边永远是 nil，于是按下去等于什么都没发生，
> 而且不会有任何报错 —— 这就是它最初上线时的表现。`LiveActivityIntent` 让系统改在
> **App 的进程**里执行，必要时还会在后台把 App 拉起来（不打开界面）。Apple 对实时
> 活动上的可交互元素就是这么要求的。
>
> 配套两点：`RecordingIntentRouter.install(_:)` 会把比处理函数先到的动作攒下来补做
> （系统后台拉起 App 的那一刻，界面和模型都可能还没就位）；按在一条已经不存在的录音上
> 时由 `SynapseAppModel.handleRecordingIntent` 收掉那条孤儿活动，不留一个按了没反应
> 的按钮。
>
> 另外，**锁屏状态下 iOS 本来就不执行**实时活动上的按钮，要先认证解锁 —— 这是系统
> 规则（Apple：「On a locked device, buttons and toggles are inactive…」），不是本
> App 的缺陷，按了没反应时先分辨是哪一种。
>
> 2026-09-20 再补记（卡片点开）：卡片本身和那两个按钮是**两件事**，别让它们互相冒充。
>
> - **卡片点一下 → 落在录音界面**，不结束这条录音、也不起新的一条。机制是
>   `View.widgetURL(_:)` 贴 `synapse://recording`，App 侧在 `RootView.onOpenURL` 解析后
>   走 `NotificationRouter.Destination.liveRecording`。用 `synapse://` 是产品已有的
>   命名空间，App 的 `Info.plist` 因此新增了 `CFBundleURLTypes`（不注册 scheme，
>   `widgetURL` 交出去的链接没有 App 接得住，点一下就是什么都不发生，且无报错）。
> - `.liveRecording` 与 `.newRecording` **不能合并**：前者只在真的在录时把录音页浮
>   出来，后者才起新录音。卡片还在、录音却已经没了（App 被系统杀掉过）时，凭空起
>   一条正是用户没要的 —— 那时落回列表并把孤儿活动收掉即可。
> - Apple 的分工：**要开 App 用链接，要做事用 App Intent**（「An interaction with a
>   button or toggle should do more than open the app. If you want to offer an
>   interaction that opens the app, use `Link` and `View.widgetURL(_:)`」）。所以两个
>   按钮保持 `LiveActivityIntent`，卡片走 URL，两者各归各位。

现有代码里 `ActivityKit`、`ControlWidget`、`AppIntent` **零命中**（grep 命中的全部是 `SynapseMobile/build/` 下的构建产物）。

### 6.4 手机端没有「波形丢失」这个缺陷

电脑端有一个已知缺陷：波形只存在内存里，异常退出后恢复回来的那条录音在语音视图里是一条平线。

手机上不存在这个问题——`AVAudioRecorder` 必须落一个 m4a 文件，所以：

- 正常收尾：从内存的采样算 `peaks` 随 `complete` 上报
- 异常退出：下次启动从本地 m4a 文件重算 `peaks` 再收尾

**这是手机端比电脑端好的地方，实施时不要退化成电脑端那样。**

### 6.7 跨端收尾冲突（桌面端与服务端必须改）

手机端一上线，现有的「静默收尾」会出事。

**机制**：

- `GET /meetings/recordings/pending` 只按 `userId` 过滤，**没有设备维度**，而且 `findFirst({ orderBy: { updatedAt: "desc" } })` **只返回最新一条**（`server/src/meeting/meeting.service.ts:323-324`）
- 桌面端 `desktop/electron/bootstrap/descriptors.ts:697` 在启动时**无条件**调用 `finalizePendingRecording()`
- 它不检查那条是不是自己录的：`readSpooledParts` 读不到残片就跳过循环，但**仍然往下走到 `completeRecording`**，用 `receivedBytes` 估一个时长、带一个**空的 `peaks`**（`desktop/electron/modules/meeting/service.ts:189-198`）

**后果**：手机正在录音时，用户在电脑上打开 Synapse → 桌面把手机那条强行收尾。

1. 手机后续的分片上传失败——`uploadId` 已经被 complete 消费掉了
2. 时长是按已传字节估的，不是真实时长
3. **波形是空的**——而手机端本来能做到有波形（§6.4），这条优势被电脑端抹掉

**双向的**：电脑在录音、用户打开手机 App，手机同样会把电脑那条抢走。

**规则**：见决策七。残片只在本机，所以只有本机能续传——这本来就是桌面端 §6.5 的原意，只是原来只有一端，没暴露出来。

**要改的地方**：

| 位置 | 改动 | 为什么 |
|---|---|---|
| `server/src/meeting/meeting.service.ts` `findPendingRecording` | 从「返回最新一条」改成「能按 `recordingId` 定位」或「返回全部」 | 只返回最新一条的话，桌面即便加了本地残片判断，只要手机那条更新，桌面就**永远看不到自己那条**，自己那条反而没人收尾 |
| `server/src/meeting/meeting.controller.ts` `GET /recordings/pending` | 跟着上面改 | **线上还有旧版桌面端在调这个接口**，改形状必须兼容，不能直接换返回类型 |
| `desktop/electron/modules/meeting/service.ts` `runFinalize` | 拿到 pending 后先看本地 spool，没有残片就**直接返回，不要走到 complete** | 这一条是本次唯一的桌面端改动 |

**已知代价（要接受，不要试图消灭）**：手机录到一半崩了、之后用户只开电脑，那条会一直是 pending、不会转写。服务端的 `cleanupStaleUploads` cron（每天 4:37，中止超 24 小时的分块上传）会兜底清掉碎片，但**不转写**。用户下次打开手机 App 就会正常收尾。把这个写进已知限制。

## 9. 验收基线
