站内信

2026-09-28 起，抄送、回复、转发与往来规则以 往来体验升级设计 为准。

同一团队成员之间发送可阅读、可回复、可附文件的私有信件。人可以在桌面与 iOS 写信；AI 在对话中确认完整内容后，通过 MCP 从后台代用户发送。

现有能力与新增边界

团队

代码中已有 Team 与 TeamMembership，成员由管理员维护，用户可加入多个团队。这只是关系模型，不代表当前已配置任何具体团队；页面中的团队名和成员都是演示占位。当前普通用户没有团队查询入口，也没有团队协作权限。

云盘与 Agent

云盘能保存文件、版本与分享；Agent 已有文档生成及云盘 MCP。云盘文件可把分享链接写入信件正文；站内信附件由本地文件直接上传，并给收件人独立的信件访问权。

通知与跨端

账号消息中心负责提醒和未读，桌面与手机可接收实时变化及推送。信件正文、收发记录和已读状态需要单独持久化，通知只负责引导打开信件。

本方案是对 2026-09-19「团队不产生可见行为」阶段性边界的后续扩展：团队关系只用于站内信的收件人资格，不引入团队角色或团队级云盘权限。实现时须同步修订该专题规则。

产品规则

身份与收件人

每人只有一个账号收件箱，汇集所有所属团队的信件。写信时按姓名或 handle 搜索并逐个选择用户，不选择团队作为收件人。候选人须与发件人有共同团队；同一封信的发件人与全部收件人还须共同属于至少一个有效团队。多个共同团队由服务端按稳定规则确定信件归属，不按团队群发。没有团队时仍可读历史，但不能发新信。用用户 ID 寻址，不输入外部邮箱地址。

收发与会话

收到与已发送是信箱分类。支持主题、正文、多人收件、附件、回复、回复全部、同团队转发、搜索、已读/未读和按人删除。发送失败时保留当前写信界面的编辑内容，绝不显示「已发送」。发送请求使用幂等键。

附件

附件只接受本机或文件 App 中的文件直接上传到站内信专属存储，收件人经信件 ACL 读取。云盘文件通过分享链接放入正文，不提供云盘附件选择，也不自动复制云盘文件。

成员变化

禁用账号、已退出团队的用户不可成为新信收件人。发出后退出团队，历史信仍留在个人信箱，但不能再以原团队回复或转发，除非重新加入。删除团队保留历史信和发送时的团队名快照，阻止该团队的新发送；删除个人信件只隐藏自己的副本。

通知与隐私

新信及附件提交成功后才广播变更，并向收件账号发提醒。通知中心仅展示「收到站内信」与发件人，不复制主题、正文和附件名；点击按信件 ID 打开站内信，信已删除时回到收件箱。站内信未读数独立于通知未读数，显示上限沿用 99+。服务端日志和推送不记录信件内容。

首版范围

首版不接外部邮件，不提供邮箱地址、抄送/密送、团队或子组收件地址、群发名单、定时发送、撤回、团队角色或团队共享信箱。要发给多人，须逐个选定用户。团队内更细的组织划分留待以后设计。附件大小上限由服务端约束，前后端保持一致。

人和 AI 的链路复检

人的写信入口与 AI 的对话直发是两条路径，共用服务端权限与发送事务。AI 不打开桌面或手机写信页。表内接口与工具均为待实现契约，当前 SY 还没有站内信 API。

发送事务

服务端预览固定收件人 userId 数组、主题、完整正文、附件令牌、共同团队上下文，并返回短期有效的 previewId。提交携带 previewId 与 clientRequestId；事务再次确认预览未被改动、发件人和全部收件人仍是有效成员、令牌属于发件人且已准备完成，再写入信件、参与者、附件引用与 outbox 事件。失败时临时对象由清理任务回收。相同 clientRequestId 返回同一信件 ID。

失败与权限

成员退出、账号禁用、团队删除、附件失效、预览过期，都返回可识别错误和对象 ID，客户端保留编辑内容。回复全部出现失效成员时显示名单，让用户移除后重新预览并确认。读取、下载、回复、删除每次按当前 userId 与信件参与者关系校验。通知投递失败只影响提醒，收件箱仍可通过列表读取；客户端重连后增量同步。

拟议数据边界

MailThread 保存会话与 teamId、团队名快照；teamId 不设级联删除外键，团队删除后历史仍可读。MailMessage 保存发送者、主题、正文、发送时间和幂等键；MailParticipant 保存每位参与者的已读与隐藏状态；MailAttachment 存放直接上传的站内信专属对象。收件箱与发件箱由参与者身份投影，不复制正文。

拟议 MCP 工具组

app_mail_recipient_search、app_mail_attachment_create、app_mail_attachment_download、app_mail_send_preview、app_mail_send、app_mail_message_list/get/set_read/delete/reply/forward。工具名是方案，尚未注册。系统 Skill 要说明相似匹配歧义、对话中最终确认、回执及失败处理；工具经现有 search/invoke 路由、PermissionGuard 和 AuditSink。

拟议服务端接口

GET /api/mail/recipients?query 供人和 AI 搜索与自己同团队的有效用户；GET /api/mail/messages?box&query&cursor、GET /api/mail/messages/:id 读取个人信件。

PATCH /api/mail/messages/:id/read 与 DELETE /api/mail/messages/:id 只改本人状态。

PUT /api/mail/attachments/local 直接接收本地文件，不接受云盘 itemId 或版本。GET /api/mail/messages/:id/attachments/:attachmentId 校验参与者后下载。

POST /api/mail/send-previews 固定待发送内容并返回 previewId；POST /api/mail/messages 用 previewId 和幂等键提交。回复和转发携带原信 ID 与操作类型；回包含 messageId、实际 recipientIds、sentAt。

桌面端通过主进程的窄类型 bridge 调用上述账号接口；iOS 通过现有登录态直接调用。两端共用请求/响应契约。新增通知来源、桌面 System App、移动端 HomeRoute、MCP capability/tool 和 Skill 时，同步更新能力注册表、消息中心专题与团队专题；只有实施完成后才改变现有产品边界。

关键 MCP 入参与回执

recipient_search({query, cursor}) 返回 userId、nickname、handle、matchKind、similarity、sharedTeamIds。只有唯一精确匹配可暂定收件人；重名或模糊匹配必须列候选让用户选，分数不能代替选择。attachment_create({filePath}) 返回 attachmentToken、fileName、state=ready；未 ready 不可发送。

send_preview({recipientIds, subject, body, attachmentTokens, replyTo?}) 返回 previewId、已解析收件人、完整正文、附件名与团队上下文；多个共同团队时服务端确定归属，不将团队作为收件地址。send({previewId, clientRequestId}) 返回 messageId、recipientIds、sentAt。回复、转发也走预览与确认；读取附件按参与者权限。

AI 对话直发文档

  1. 1 生成并存文档AI 在当前对话按指令生成本地文档；需要作为附件发送时直接上传本地文件。已有云盘文件可取得分享链接放入正文。
  2. 2 搜索收件人从 SynapseSkill 得知 app_mail_recipient_search 的方法与参数并调用。唯一精确匹配可暂定；模糊或多个匹配时在对话中给出姓名、handle 等候选，让用户确定每一位收件人。
  3. 3 固定待发内容本地文件作为附件时调用 attachment_create，再调用 send_preview。在对话中展示实际收件人、主题、完整信件正文与附件名；AI 生成的文档也给出完整内容或可打开的精确预览。
  4. 4 取得最终确认明确问「是否按以上内容发送？」即使人名精确匹配、原指令已经说「发给某人」，也必须等用户对这一次完整预览明确说可以。任何收件人、正文或附件修改都重做预览并重新确认。
  5. 5 后台发送确认后，AI 直接调用 app_mail_send({previewId, clientRequestId})；服务端以当前用户身份校验并投递，不打开桌面或 iOS 的写信界面，也不要求用户点击发送按钮。
  6. 6 返回回执AI 将 messageId、实际收件人和发送结果告知用户。失败时保留待发内容并说明原因，不声称已发送；重试沿用幂等键。

对话确认是 SynapseSkill 与 Agent 宿主的行为约束；服务端能校验 previewId 对应内容未变、当前用户身份和发送权限，不能仅凭一个工具参数证明用户在对话中说过「可以」。实现时需在 Agent 宿主保留确认状态与审计关联。

实施与验收

实施顺序

  1. 1. 先定团队成员查询、信件 ACL、直接上传附件与数据库迁移。
  2. 2. 上线服务端 API、实时事件、推送与审计，再接桌面和 iOS 共享契约。
  3. 3. 桌面独立应用与 iOS 主页功能同时覆盖收、发、读和回复。
  4. 4. 注册 MCP、系统 Skill、能力清单并补齐 Agent 指南；同步修订团队旧规格。

必须通过的场景

  • 手动逐个选择一人或多人发送成功；全部参与者没有共同团队、禁用账号、离团成员时整封失败且写信界面保留内容。
  • 零团队用户能读历史且不能发；多团队用户可搜索与自己共享团队的用户，不出现团队群发选项；同名用户按 handle 区分。
  • 关闭写信界面后不保存未发送内容，不显示保存提示。
  • 本机文件可直接上传为附件；云盘文件的分享链接可放入正文，写信时没有云盘附件选项，也不复制云盘文件。
  • 回复、回复全部和同团队转发保留正确参与者；失效成员需要显式处理。
  • 桌面发送后手机离线重连可收到；搜索、未读与按人删除跨端一致；通知点击精确定位。
  • 手机在 iPhone、iPad 全屏、半窗和窄窗均能写信、读信、返回原列表。
  • AI 生成文档后搜索人；模糊或重名时让用户选；唯一精确匹配也展示完整待发内容并取得最终确认，再从后台 MCP 发送，不唤起写信界面。
  • AI 能查询、读正文、下载附件、回复、设已读和删除；发送工具重试不重复投递，失败不声称成功。
