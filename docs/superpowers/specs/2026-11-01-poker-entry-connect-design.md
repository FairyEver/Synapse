# 点数入座、等待邀请与 AI 接入

用户已在实测评审后明确批准三项直接实施，沿用当前 main，不重复设计审批。

- 点数房未入座时显示房间类型、可用点数及“带入 N 点入座”。读取失败可重试，服务端仍最终裁决资金和容量，不新增确认弹窗。
- 首局等待按实际可参赛成员计算，区分缺人、暂离、缺筹码和等待 AI，不把未开局标成下一手加入。等待区提供复制房间链接的邀请操作，不自动发送消息或入座。
- 列表与牌桌共用 HeroUI AI 接入面板，首次明确“允许 AI 接入并复制指令”，后续复制不写授权。正文用简短步骤、同账号/MCP前提、持续状态和可取消操作；完整 Agent 指令用HeroUI Accordion 按需展开。已有 AI 控制时可本人接管。
- 列表返回当前请求者自己的可选 myControl 投影，用有条件、有上限的批量查询；不得泄露其他用户的控制历史、身份或暗牌。刷新、返回、取消和跨端接管均由服务端状态驱动，不以 localStorage 授权标记代替权威数据。
- 复用当前 control.set/version、资金、出牌幂等、首局和每手准备屏障，不新增能力、依赖、数据库迁移或后台模型，不伪称 MCP 已连接。

方案选择：采用统一面板和服务端列表投影；分散入口会继续产生不同语义，本机缓存无法反映跨端取消。服务端先兼容发布后再发布 Web；旧服务端缺少可选字段时仍能进入房间读取实际状态。

验收覆盖资金提示、首局与中途加入区别、邀请复制、首次授权与再次复制、复制失败后的已授权状态、取消/接管/重进与账号切换、满员和窄屏展开；最后实际建立测试房间复验并清理。真正 MCP 认领和双账号对局取决于现场能力，不将未实测项写为已通过。游戏不进发布说明。
