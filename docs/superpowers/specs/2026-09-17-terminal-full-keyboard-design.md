## 1. 要解决什么

手机端终端底部有一条工具栏，最左边那个键盘图标点开，是一个从屏幕下方升起的**键盘面板**：顶上一排分类，下面是该分类的键位格。

面板里的「**控制**」分类现在是个死胡同：它画了一整张 QWERTY 键盘，只在 10 个字母上点亮了 Ctrl 组合，**其余 16 个字母是压暗的、点了完全没反应**。用户看到 `A S D F` 一整排，去点 `S`——什么都不发生，也没有任何解释。

更根本的是：它**不是键盘**。它是「10 个固定按钮摆成了键盘的形状」——每个字母被钉死在某一个 Ctrl 组合上，用户既不能选择要用哪个修饰键，也不能先按 Ctrl 再按任意字母。

同时，真实使用里最常按的一些键根本没有入口：**Shift+Tab**（Claude Code 切权限模式）、**Ctrl+B**（tmux 前缀）、**Ctrl+P/N**（历史上下翻）、**Ctrl+F/B**（vim 翻页）、**Ctrl+S/Q**（暂停输出）。

这次要把这一格改成一块真的键盘。

## 2. 现状

### 2.1 面板里的四个分类

| 分类 | 内容 | 几何 |
|---|---|---|
| 常用 | `esc` `⌫` `tab` `回车` | 照真键盘四角：esc 左上、⌫ 右上、tab 左、回车右且更宽 |
| 方向 | `↑` `←` `↓` `→` | 右侧倒 T |
| 功能 | `home` `end` `pgup` `pgdn` `del` | 右上六键簇，Insert 那格留空 |
| **控制** | QWERTY 幽灵，10 个 Ctrl 组合点亮 | 三行字母，其余 16 个压暗不可点 |

位是照真键盘摆的，这一点做对了，**本次全部保留**。问题在覆盖面。

### 2.2 「控制」为什么是个死胡同

1. **假的可点感。** 26 个字母画了 26 个键位，只有 10 个能按。用户没有任何办法从外观上分辨哪些是活的，只能一个个试。
2. **没有修饰键的概念。** 左上角那个 `^` 只是画上去的图例，不是控件。用户没法选择修饰键，更没法组合。
3. **名字没说清它是什么。** 「控制」听起来像「Ctrl 键」，实际它是一整块键盘。
4. **结构上是网格不是键盘。** 每个字母被钉死在某个组合上（`W` 就是 `^W`），不存在「按 Ctrl 再按任意字母」这件事。

### 2.3 三条决定性事实

这三条决定了本次改造的边界，都是查代码得来的：

**第一，控制字符不能伪装成文本。**
`desktop/app-capabilities/terminal/main/service.ts` 的 `hasForbiddenTextControl` 除 Tab 外**拒绝一切 `0x0b`–`0x1f` 和 `0x7f`**。所以方向键、Esc、Ctrl 组合**不可能**靠"发几个字符"绕过去，只能进按键白名单 `MOBILE_KEYS`。

**第二，白名单是一份五处同步的契约。**
同一个键名集合被写在五个地方，靠测试互相钉住：

| # | 位置 | 作用 |
|---|---|---|
| 1 | `shared/src/mobile-live.ts` 的 `MOBILE_KEYS` | ESM 真相源 |
| 2 | `shared/src/mobile-live-constants.cjs` 的 `MOBILE_KEYS` | CommonJS 镜像，Electron 主进程要读（Vite 无法从 `.cjs` 取命名导出，所以只能重复声明） |
| 3 | 同上文件的 JSDoc 类型列表 | 类型提示，也必须跟着改 |
| 4 | `desktop/app-capabilities/terminal/main/service.ts` 的 `KEY_BYTES` | 键名 → 字节 |
| 5 | `desktop/app-capabilities/terminal/shared/contract-schema.ts` 的 `terminalSemanticKeySchema` | zod 枚举，**手写死表**（同样因为 Vite/CJS 分裂没法 import 共享常量） |

**第三，`keys` 意图本来就收动作数组。**
`MobileIntentRequest.actions` 是 `[MobileKeyAction]`，上限 128 个（`MOBILE_FRAME_LIMITS.maxKeyActions`）。这意味着「一次发一串按键」今天就是合法协议，不需要新增任何消息类型。**Alt 组合靠的正是这一条**（见 §3.5）。

## 3. 决策

### 3.1 「控制」改名「全键盘」

`控制` → `全键盘`。名字要能自己说明白它是什么，而不是要求用户点进去才知道。

其余三个分类名不动。

### 3.2 修饰键行：Ctrl / Shift / Alt，没有 Command

修饰键行放在全键盘最上面一条，两端对齐——真键盘的修饰键本来就在两头，左右拇指都够得着。

**不放 Command。** 理由是一条硬事实，不是偏好：

> macOS 的终端里，**Cmd 是终端 App 自己吃掉的**（Cmd+C 复制、Cmd+V 粘贴、Cmd+K 清屏），**没有字节能送到 PTY**。

放在这个面板上只有两种结局——要么按了没反应（用户以为 App 坏了），要么它被解释成 App 自己的快捷键。而后者是另一个功能：这个面板的契约是**「发一个按键，不是一个命令」**，跟工具栏那排按钮是两种东西。

（产品负责人原本点名要 Command，看到这条事实后同意了不放。）

### 3.3 是「点一下锁住」，不是「按住不放」

需求原话是「先按住 Ctrl 再按 C」。在触摸屏上「按住不放」有两个硬问题：

1. **和 sheet 的关闭手势打架。** 面板是可下滑关闭的 sheet，按住再拖就是关闭手势。
2. **拿不到按下状态。** iOS 的 `Button` 是抬手才触发，长按期间没有「正在按住」这个状态可读。

所以做成**锁存（latch）**：

- 点一下修饰键 → 反色锁住；
- 再按一个字母 → 组合生效；
- 发完**自动弹回**；
- **双击修饰键 → 锁定**，用来连按（比如反复 Ctrl+C）。再点一下解锁。

这套语汇和 iOS 系统键盘按住 shift 的表现是同一套：锁住 Shift 时字母会真的变成大写。

### 3.4 一次只锁一个修饰键

能发出去的组合**全都只需要一个修饰键**：

- Ctrl + 字母
- Shift + 字母
- Alt + 字母
- ⇧tab（独立键，见 §3.7）

所以设计成**第二个修饰键按下时把第一个换掉**，而不是叠起来。

这样避免了一个死状态：如果允许 Ctrl+Shift 同时锁上，那一瞬间**整块键盘全暗**（没有任何一个「双修饰 + 字母」有对应字节），用户只会以为坏了。换掉之后这个状态根本不存在。

### 3.5 一个新 intent 都不加：Alt 用动作数组

Alt 在终端里的语义就是「ESC 前缀」，而 `keys` 意图本来就收数组，所以：

```
Alt+B  →  keys 意图，actions = [{key: "Escape"}, {text: "b"}]
```

**云端和桌面端一行都不用改**，只做手机端就能拿到 `Alt+B / Alt+F / Alt+D` 这一组（readline 的按词移动、删词）。

`Ctrl+I`（=0x09）和 `Ctrl+M`（=0x0d）同理今天就能用，因为它们和目标键是**同一个字节**——但它们的处理方式不同，见 §4.2。

### 3.6 按键白名单 23 → 38：用枚举，不用规则

**这一段推翻了初稿的一处口径，原因是新发现的事实。**

初稿的建议是「加一条 `Ctrl+<A–Z>` 的规则，而不是加 26 个表项」。当时不知道两件事：

1. `terminalSemanticKeySchema`（上面那张表的第 5 处）是**手写死表**，因为 Vite/CJS 分裂它没法 import 共享常量。走规则的话，这里要么手抄一份 50 项的枚举，要么把 `z.enum` 降级成 `z.string().refine(...)`——后者会让「五张表必须相等」这条测试的其中一处**失去意义**。
2. `KEY_BYTES` 同时扮演两个角色：既是「字节表」，也是「合法键名表」（`encodeSemanticAction` 靠查表失败来拒非法键）。规则进来后这两个角色必须拆开，否则校验会变松。

而枚举的代价只有 14 行**机械可推**的数据，换来的是：**校验架构一行不改，五处一致性测试全部保持原意**，只是里面的数字从 23 变成 38。

所以决定：**枚举。**

`MOBILE_KEYS` 从 23 项扩到 38 项：

- **原有 23 项一项都不删、不换序。** 它是 append-only 的：每个键名都是手机、云端、桌面三方按字符串匹配的标识符，删一项或改一次序，等于改变已发布的手机发出去的东西。
- **新增 15 项**：14 个 `Ctrl+字母` + `Shift+Tab`。明细见 §4.1。

### 3.7 Shift+Tab 做成常用页的独立键

画原型的时候才发现的：**Shift 在全键盘页、Tab 在常用页，跨页根本拼不出来**（切分类会清掉已锁的修饰键）。

所以 `Shift+Tab` 不做成组合，而是**常用页中间那颗独立键 `⇧tab`**。它值得这个位置——从手机驱动 Claude Code 时，它是和 `esc`、`回车` 一个量级的常按键（切权限模式就靠它循环）。

顺带把常用页原来那块空白填掉了。

### 3.8 面板高度按分类给

现状是两个写死的常量：键位格高度固定 `152`，面板静止高度 `280`。那是为四个小格子定的。

全键盘要 4 行（修饰键 + 数字行 + 三行字母），大约需要 **≈370**。所以 `gridHeight` 不能再是全局常量，要**按分类给**；sheet 的 detent 也跟着分类走。

切换分类时面板本来就会重排，多一个高度变化不会更突兀。

## 4. 协议

### 4.1 新增的 15 个键名与字节

| 键名 | 字节 | 是什么 |
|---|---|---|
| `Ctrl+B` | `\x02` | tmux 前缀 |
| `Ctrl+F` | `\x06` | 前进一个词 / vi 下翻页 |
| `Ctrl+G` | `\x07` | 取消（readline abort） |
| `Ctrl+H` | `\x08` | BS —— **不是 ⌫**，⌫ 是 `\x7f` |
| `Ctrl+J` | `\x0a` | LF —— **不是回车**，回车是 `\x0d` |
| `Ctrl+N` | `\x0e` | 下一条历史 |
| `Ctrl+O` | `\x0f` | readline operate-and-get-next |
| `Ctrl+P` | `\x10` | 上一条历史 |
| `Ctrl+Q` | `\x11` | 恢复输出（XON） |
| `Ctrl+S` | `\x13` | 暂停输出（XOFF） |
| `Ctrl+T` | `\x14` | 交换相邻两个字符 |
| `Ctrl+V` | `\x16` | 字面量插入（quoted-insert） |
| `Ctrl+X` | `\x18` | readline 前缀 |
| `Ctrl+Y` | `\x19` | 粘贴（readline yank） |
| `Shift+Tab` | `\x1b[Z` | 回退制表；**Claude Code 切权限模式** |

加上原有的 23 项，共 **38** 项，字节两两不同（`mobile-toolbar.test.ts` 有一条注入性断言钉住这一点，见 §4.4）。

### 4.2 为什么 `Ctrl+I` 和 `Ctrl+M` 不在表里

它们在终端里**等价于已有的键**：

- `Ctrl+I` = `\x09` = **Tab 的字节**
- `Ctrl+M` = `\x0d` = **回车（Enter）的字节**

把它们也加进表里，会造成 `KEY_BYTES` 的**字节冲突**——两个键名指向同一串字节，而 `mobile-toolbar.ts` 的 `reverseKeyBytes()` 正是靠"字节 → 键名"的反查来做投影的，冲突会让它静默取到列表里靠后的那个。现有的注入性测试会因此变红。

所以本次**不加**，手机端这样处理：

> 锁着 Ctrl 时按 `I` → 发 `Tab`；按 `M` → 发 `Enter`。

字节完全相同，用户可感知的行为完全正确，而契约保持干净。

**这是实现时最容易做错的一处**——无论是漏了这条映射（按 I 什么都不发），还是顺手把 `Ctrl+I` 也加进表里（测试变红）。验收基线 §9 第 6 条专门钉它。

### 4.3 五处同步

`MOBILE_KEYS` 的改动必须同时落到 §2.3 表里的**五处**。漏任何一处都是运行时才炸的错：

- 漏第 1/2 处 → 云端不认新键名；
- 漏第 3 处 → 类型提示与真值不符；
- 漏第 4 处 → 云端放行、电脑端抛异常，用户看到的是「按了没反应」；
- 漏第 5 处 → 电脑端服务层的 zod 校验先把请求拒掉。

`shared/src/mobile-live.test.ts` 与 `desktop/app-capabilities/terminal/main/__tests__/mobile-toolbar.test.ts` 里各有一组「这几张表必须相等」的断言，改完全部跑一遍即可验证。

### 4.4 投影不受影响

`mobile-toolbar.ts` 的 `reverseKeyBytes()` 会把 `KEY_BYTES` 反查成「字节 → 键名」。新增 15 项之后：

- `\x1b[Z` 会反查成 `Shift+Tab`。但桌面的内置工具栏里**今天没有任何按钮的序列是 `\x1b[Z`**，所以**不会多出按钮**——`Shift+Tab` 纯粹是手机面板自己的键。这是预期行为，不是漏配。
- 其余 14 个 `Ctrl+字母` 同理，桌面内置动作里没有对应序列。

## 5. 界面规格

**以 `docs/prototypes/2026-09-17-terminal-full-keyboard.html` 为准。** 下面是文字口径，冲突时以原型为准。

### 5.1 常用

```
[ esc ]        [ ⇧tab ]        [ ⌫ ]
```

```
[ tab ]                        [ 回车 ]
```

第一行三颗键两端对齐（esc 靠左、⌫ 靠右、⇧tab 居中）。**`⇧tab` 是本次新增的键。**

第二行 `tab` 靠左、`回车` 靠右，中间留空——保持原样。

### 5.2 方向 / 功能

**几何、内容、顺序全部不变。** 本次不动这两页。

### 5.3 全键盘（原「控制」）

从上到下四行：

```
[Ctrl] [Shift]                    [Alt]

 1  2  3  4  5  6  7  8  9  0

 q  w  e  r  t  y  u  i  o  p
  a  s  d  f  g  h  j  k  l
   z  x  c  v  b  n  m
```

- **修饰键行**：`Ctrl` / `Shift` 靠左成组，`Alt` 靠右。单个键宽 ≈62pt、高 ≈34pt。
- **数字行**：10 键等宽铺满，键宽 ≈32pt、高 ≈42pt。锁着 Shift 时显示 `!@#$%^&*()`——和系统键盘一致。
- **字母区**：三行，第 2、3 行整体居中做错位缩进（和 iOS 系统键盘一样）。锁着 Shift 时显示大写。
- **没有修饰键锁着时，按字母就是输入这个字符**（小写）。所以面板本身也能用来回答 `y` / `n` 和审批提示的 `1` / `2` / `3`，不用收面板再去点输入框。

### 5.4 读数条

全键盘页在分类选择器下面常驻一条读数：

- **左边**：当前锁了什么，如 `Ctrl + _`；什么都没锁时显示「未锁修饰键 · 按字母就是直接输入」。
- **右边**：**这次会发出去什么**，如 `→ 0x03 · 中断当前进程`。

这一条既是安全网（不会有"按了没反应"的键）也是教学（按两次用户就知道 `^C` 是什么了）。发不出组合时整条变黄并说明原因。

**其余三页不显示读数条。**

### 5.5 面板高度

| 分类 | 键位格高度 | 面板静止高度 |
|---|---|---|
| 常用 / 方向 / 功能 | 152（不变） | 280（不变） |
| 全键盘 | ≈240 | ≈370 |

数字是实现时的调参起点，以能放下四行且不挤压上方终端为准。

## 6. 上线顺序（硬约束）

**必须 服务端 → 桌面端 → 手机端。**

新键名要被三端同时认识。旧云端遇到不认识的新键名，会**切断整条连接**——用户看到的是「设备莫名离线」，日志里只有一句校验失败，非常难查。

服务端**代码一行都不用改**（它用的是 `shared` 里的 `isMobileIntent`），但**必须先部署**——因为它打包进去的是那个旧版本的 `shared`。

---

## 7. 失败与降级

| 情况 | 行为 |
|---|---|
| 旧手机 + 新桌面端 | 手机不认识新键名，面板上根本不会画出来。工具栏投影那条「单个按钮不认识就丢这一个按钮」的既有规则不变 |
| 新手机 + 旧桌面端 | 新键名会被电脑端拒绝，用户看到一次失败提示。**这正是必须先升级服务端与桌面端的原因**——顺序错了才会有这个状态 |
| 新手机 + 旧云端 | **走不通**。旧云端直接切断连接 |
| 锁着修饰键时切换分类 | 修饰键自动清空（切页 = 换一套键，不清会误发） |
| 锁着修饰键时面板被收起 | 同上，清空 |

## 8. 非目标

以下都是**有意不做**，不要顺手加：

- **F1–F12**。需要 Fn 层，面板要多一屏；手机上用到它们的 TUI 太少。
- **`Ctrl+\`（SIGQUIT）、`Ctrl+Space`、`Ctrl+]`**。它们不在 `Ctrl+A–Z` 的字母表里，而没有场景逼着要。将来要加就是同一张表里再补几项。
- **双修饰组合**（`Ctrl+Shift+X` 之类）。终端里没有对应字节，设计上也不给这个状态（§3.4）。
- **长按弹菜单、自定义面板按键、给面板做增删改**。面板是**按键**，不是命令；它没有"编辑"这个概念，跟工具栏是两种东西。
- **改方向 / 功能两页的几何**。
- **给手机端做工具栏的增删改入口**（上一轮已定，继续不做）。
- **iPad 专属布局**。本次所有尺寸都按 iPhone 宽度设计。

## 9. 验收基线

逐条走，每一条都要能说出"怎么验的"。

1. 面板分类名是 `常用 / 方向 / 功能 / 全键盘`，**没有**「控制」。
2. 全键盘页有 `Ctrl` / `Shift` / `Alt` 三个修饰键，**没有 Command**。
3. 点 `Ctrl` → 它反色；再点 `c` → 电脑端收到 `keys` 且键名是 `Ctrl+C`；发完 `Ctrl` 自己弹回。
4. 双击 `Ctrl` → 变锁定态；连按 `c`、`d` → 发出两个不同组合且 `Ctrl` 仍锁着；再点一次解锁。
5. 锁着 `Shift` 时字母显示为大写，按 `C` 发出的是**文本 `C`**（不是 `Ctrl+C`）。
6. **锁着 `Ctrl` 按 `I` → 电脑端收到的是 `Tab`；按 `M` → 收到 `Enter`。**（§4.2）
7. 锁着 `Ctrl` 再点 `Shift` → **Ctrl 被换掉**，读数条里只剩一个修饰键。
8. 不锁任何修饰键时按 `y` → 发出的是**文本 `y`（小写）**，终端里出现这个字符。
9. `Alt` + `b` → 电脑端收到的是**同一次 intent 里的两个动作**：Escape，然后是文本 `b`。
10. 常用页有 `⇧tab`，按它电脑端收到 `Shift+Tab`。
11. 常用页的 `esc` / `tab` / `⌫` / `回车` 发出的仍然是按键而不是文本。
12. 方向页、功能页的键一个不少、位置没变。
13. 切到全键盘时面板变高，切回常用时变矮，**上方终端始终可见**。
14. 未锁修饰键时按数字 `3`，发出的是文本 `3`。

## 10. 开放项

这几条本次**不定**，留给实施时按实际情况判断，但要在回报里说明怎么定的：

1. **全键盘的键位是否要更接近系统键盘的高度。** 原型里键高 42pt，系统键盘约 42–46pt，最终以真机手感为准。
2. **`Shift+字母` 是否要顺便把数字行的符号也做出来。** 原型里做了（`!@#$%^&*()`），如果实现上发现没地方放可以砍掉。
3. **读数条的文案长度。** `0x03 · 中断当前进程` 在窄机型上可能被截断，截断顺序由实现定（建议先保字节值）。
4. **面板在 iPad 上的表现。** 本次只按 iPhone 宽度设计，iPad 上按比例铺开即可，不做专门适配。
