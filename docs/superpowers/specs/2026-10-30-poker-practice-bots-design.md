# 德州扑克机器人陪练房设计

日期：2026-10-30。状态：待用户审阅，尚未实施。仓库 `/Users/liyang/Documents/code/github/Synapse`，当前分支 `main`，设计基于 `f7c35bab7`。

## 1. 已确认的需求与方案

用户希望一个人在正式游戏中也能给自己的 AI 找到对手，不依赖另一个真实用户、另一个 Synapse 账号或另一个大模型进程。用户已选择“机器人陪练房”：整桌使用练习筹码，不扣大厅点数，输赢不进入大厅余额或正式战绩。

已讨论两条路线：

| 路线 | 取舍 | 决定 |
|---|---|---|
| 机器人陪练房，整桌练习筹码 | 完全隔离点数，复用扑克规则，无须追踪筹码来源 | 用户选择 |
| 真人与机器人混合计分 | 须持续追踪不可兑换筹码的转手、边池及机器人赢走的真人点数，规则复杂 | 不实施 |

这是原三份定稿文件的需求变更，取代其中“完全不存在公共机器人”的限制，但仅允许陪练房内的程序机器人。原文件位于 `/Users/liyang/Desktop/德州扑克/产品设计文档.md`、`实施计划.md`、`提示词.md`；原文件不改写，本设计记录增量规则。计分房继续禁止机器人；不引入内置模型托管、不赋予人类出牌权。

下文机器人管理权限、补充方式、节奏、统计筛选及字段方案，是根据现有实现提出的实现建议，尚不冒称用户逐项确认。

## 2. 产品行为

- 建房选择“点数房”或“陪练房”，默认点数房。模式创建后固定，即使房间为空或移除所有机器人，也不能转换。现有房间全部保持点数房。
- 陪练房正式开放，可以一个真人账号带自己的外部 AI，对战一个或多个程序机器人；也允许多个真人账号各带自己的 AI 共同练习。无须第二个真人账号。
- 仅房主可以添加、移除机器人，无须房主先入座。添加/移除属于房间管理，不能选择机器人本轮动作、查看机器人暗牌或控制真人座位。
- 添加入口每次添加一个机器人；每次明确点击是新创建意图，同一次失败重试复用创建标识。容量最多 10 座，并始终为至少一位真人保留位置，机器人上限为 `maxSeats - max(真人座位数, 1)`。
- 机器人名称由服务端生成，例如“陪练 1”，座位和记录明确标识“机器人”，不伪装用户或 AI 模型。首版只有一种规则策略，不增加风格提示词、难度、模型或逐手操控入口。
- 所有参与者初始练习筹码与房间设置一致，沿用 500/1,000/2,000/5,000 档及 1/2 盲注。练习筹码不是另一种大厅钱包，不可兑换、转赠、跨房携带或领取点数补助。
- 赢得机器人筹码仅增加本桌练习筹码，离桌后清零；机器人赢走真人筹码也只影响练习筹码。离桌、超时、输光、解散、维护清理均不得产生大厅点数变动。
- 人类账号仍只能通过自己的外部 AI/MCP 入座和出牌。Renderer 不新增 act、seat_join、table_wait 桥接，不出现跟注、加注、弃牌、临时接管等控件。

## 3. 生命周期与边界

- 开新手必须至少有两位可参与者，且至少一位为可参与的真人账号座位；仅机器人不发新手。真人全部暂离也暂停，不让机器人自转。
- 在局添加机器人仅从下一手参与；进行中的机器人移除请求标记待离桌，继续自主完成本手后移除，不由房主强制弃掉其当前手。
- 机器人输光移出，不自动补充、不自动增筹；房主可再次添加一个新机器人。真人输光沿用离场规则，AI 获授权后可重新入座领取本桌初始练习筹码。
- 真人最后一个座位离场或超时后，进行中的手仍按规则收尾，随后暂停；不创建机器人对机器人的下一手。
- 真人沿用 600 秒行动窗口、60 秒掉线展示、超时当场撤出本手并离场。超时只能记录 check/fold，绝不自动跟注；陪练不改变这条规则。
- 机器人通常每轮在约 1 秒后行动；这是机器人主动决策的节奏，不是缩短真人行动窗口。暂不提供速度控件。
- 房间活动及 30 分钟无人维护只看真人活动；机器人调度不能延长房间寿命。只有机器人且从无真人入座的房间从建房时开始计算；已入座过则采用最后真人活动时间。
- 真人暂离不允许机器人擅自替打；重连仍唯一使用当前账号 + roomCode，从 overview 找回原座位。房主身份不自动赋予任何参赛座位。
- 服务器重启后从数据库继续机器人行动与当前手；客户端关窗不阻止服务端机器人推进，但无人维护规则仍有效。

## 4. 点数隔离与大厅边界

现有 `HallService.join/leave`、`saveHand` 与 `refund` 全部把筹码当大厅点数，不能仅在 UI 标记陪练，也不能只改最终退款。

扩展大厅的通用会话资金类型 `funding: points | practice`（最终命名可由实施者对齐），不加入具体扑克判断：

- 点数会话完全沿用现有锁账户、扣带入、更新占用及退还路径。
- 真人陪练座位仍有 GameSession，供跨游戏进行中、needsAction、deadline、重连和暂离维护使用。
- 陪练会话的大厅记账字段 `buyIn = 0`、`inPlay = 0`、`returned = null/0`，真实练习筹码只在扑克房间和座位中保存。不要把练习余额写入大厅占用字段再依赖查询过滤抵消。
- 入座不锁扣点账户；行动/结算不更新 GameAccount，也不把练习筹码写回 inPlay；离桌只关闭会话，丢弃桌面练习余额。通用关闭接口对 practice 收到非零点数退款应拒绝，防止错误调用绕回点数通道。
- 会话 funding 由受信服务端依据不可变房间模式决定；用户不能在 seat_join/act 中传值覆盖。建立数据库约束，practice 会话的记账字段必须为零或尚未结算的 null，不能把已创建会话改成另一种资金类型。
- overview 的 total/available/inPlay/netProfit 保持原点数含义，陪练只增加带类型的进行中项，不增加点数。大厅账户流水只显示 points 会话。
- 补助仍是点数账户零余额、无进行中的 points 会话且 24 小时一次；practice 会话不扣钱，也不阻止原本符合条件的点数补助。
- 一个账号同时参与陪练房、计分房、未来其它游戏，点数汇总和扣退必须相互独立。大厅只读通用 GameSession，不能读取扑克表或按 poker 分支。

## 5. 机器人身份与行动

- 机器人是扑克服务内部参与者，不创建 User、GameAccount、GameSession、登录凭据、MCP 会话或可领取补助的账号。
- 现有座位/快照/行动均有字符串 userId 且没有外键。机器人使用服务端分配的内部参与者标识，与真人 ID 命名域隔离，并以显式 participantKind 区分；内部标识不代表账号，不可登录或作为外部调用者身份。保留真人 `(roomId,userId)` 与座位号数据库唯一约束。
- 真人身份始终取认证上下文；外部请求不能传 robot 身份、participantKind 或指定 bot act。机器人管理中的 botId 仅定位管理对象，不作为座位凭据或授予行动权。
- 独立纯函数策略输入限于自己的底牌、公共牌、公开下注/筹码、合法动作及调用方注入的随机值；不能接收完整 HandState、牌堆、对手暗牌、提示词、note 或其它机器人的私密数据。
- 策略可以 check、fold、call、合法 raise/allin；这与“超时只能 check/fold”不同。首版使用简单保守规则：免费时通常 check；按公开底池/欠注与自身牌力控制跟注及少量合法加注。无网络、数据库、时钟或模型调用。
- 真人和机器人共用纯引擎、合法动作校验、房间锁、行动写入和结算；内部调用只放宽“来源是 MCP 真人”这一入口差异，不能绕过当前手、街道、轮次、身份种类与金额校验。不要为机器人复制第二份牌局引擎。
- 单个机器人不能向另一个机器人共享暗牌，房主也不能读取。摊牌、观战、弃牌暗牌等投影仍按原规则。
- 行动来源区分 MCP、timeout、rules_bot；已有 isAuto 的超时含义不拿来推断“所有机器人行动都等于超时”。来源/参与者类型写入当时快照与归档，记录页能区分机器人主动跟注和真人超时。
- 行动幂等凭据与正常成功动作同事务。机器人用当前 handId/actionSeq/seat 身份生成稳定的动作标识；多实例、定时器重入、提交成功后进程退出均不能重复下注。

## 6. 调度与负载

在扑克模块增加受控后台机器人任务及持久化下一行动时间。仅筛选 practice、running、当前行动者为机器人的房间；每轮最多取 100 房间，每房只提交一次动作。采用稳定游标与固定资格截止，单房失败不得阻塞其余房间，也不允许事务内无限循环打牌。

锁内重读 room/hand/seat 和当前行动点；若已变化则无副作用返回。提交时写入动作、幂等凭据、下一状态和下次调度时间，再唤醒 wait。进程重启只依靠数据库时间恢复，无长期内存队列或逐机器人永久定时器。

无人可参与的真人时，不发新手；空闲维护忽略机器人心跳。机器人异常也受既有 600 秒兜底，错误有定位信息但不记录牌面或私密输入。禁止跨房无上限读写及机器人互打造成的永久后台循环。

## 7. 存储、兼容与归档

新增迁移，旧数据默认 points/human，不能修改已经应用的迁移或重写不可变行动。

预期新增信息：

- GamePokerRoom：不可变 mode、机器人下一行动时间。
- GameSession：不可变 funding 与零记账约束。
- GamePokerSeat、GamePokerHandSeat：参与者类型，机器人创建幂等所需稳定 ID；机器人管理只针对该房间的机器人。
- GamePokerAction：可空新来源字段供旧记录兼容；旧记录来源按原 isAuto 映射，新记录显式写入。其他必要快照字段由实施者保持最少。

模式必须在热记录与冷归档中可判定，机器人类型和行动来源在归档后仍可展示。更新归档函数时仍须验证完整不可变副本后才删热表；历史归档缺少新字段默认 points/human，不能 UPDATE 旧行动或归档来补字段。

发布需先完成服务端迁移与 API，再发布桌面；本次开发不包含 push、业务库迁移、部署或发布。已有计分数据不转换。上线后若要停用陪练，停止新建/添加并让现存手合法结束；回滚需保留房间模式和资金防护，不能退回把所有座位当点数退款的旧服务端版本。

## 8. 接口、MCP 与 Skill

沿用 search/invoke，不给 tools/list 添加直接业务工具。

- room.create 增加可选 mode，默认 points，creationId 的创建意图必须包含 mode。已使用标识的重试恢复原房间，不转换模式。
- lobby.list 增加模式筛选，旧调用默认 points；新桌面提供点数/陪练筛选。
- 新增 `app.game.poker.bot.add`：roomCode、creationId(UUID)，仅房主在 practice 创建一个机器人；重复成功创建标识返回原结果，即使原机器人后来移除，也不得重试复活它。响应至少 botId、seatNo，当前状态由 room/table 查询确认。
- 新增 `app.game.poker.bot.remove`：roomCode、botId，仅房主移除本房间机器人；已移除重复请求无副作用，进行中返回 pending。本手新入座但尚未参赛的机器人可立即移除，不能影响前一位参赛者。
- bot.add/remove 是房间管理能力，桌面和 MCP 均可用；不新增真人行动/入座 bridge。计分房、非房主、机器人目标类型不匹配均由服务端拒绝，不能只藏按钮。
- room/table/lobby、详情、历史和 hall session 增加 mode/funding，seat 增加 participantKind，记录增加来源；已有字段保留。机器人 nudge 明确拒绝且不发真实通知。
- 正式统计与默认历史仅 points；practice 单独筛选显示练习结果。stats(mode=practice) 只统计练习；roomCode 对比采用该房间模式，显式模式冲突拒绝。机器人不出现在账号全局同桌战绩对比中，不建立公共机器人账号档案。
- 选手提示词与版本机制继续用于真人的外部 AI，practice 每轮也现读。档案版本 handCount 默认只统计 points；练习详情仍保留本人的版本和 note。
- wait 在非轮次仍只回 waiting/cursor 一行，不为了显示陪练标识膨胀轮询报文；模式从 overview、guide、room/table 得知。重连、结果补发、600 秒超时和成功 actionId 优先幂等维持。
- 同步共享类型、输入/响应 schema、服务端 UI 路由、preload、能力注册、Agent 指南及系统 Skill。预计游戏 MCP 索引 20→22、UI IPC 18→20；以实际注册检查为准，不能只更新文字数量。

## 9. 桌面呈现

复用现有大厅和牌桌布局，不重做视觉。App 顶栏继续使用 Synapse 统一壳，不增加主题切换按钮。

- 建房弹窗增加房间类型；点数房使用“带入点数”，陪练房使用“初始筹码”，旁边保留必要说明“不影响大厅点数”。
- 房间列表、进行中项、牌桌和记录显示“陪练”，避免把练习盈亏当正式点数。
- 房主在陪练房内容区可“添加机器人”，每个机器人提供移除管理入口；空位不足、等待移除、失败重试均给出状态。没有人类操作下注的入口。
- 机器人座位使用现有卡牌和筹码组件，标记“机器人”；轮到它时显示“机器人行动中”，不显示“AI 掉线”、催促通知或私密 AI 判断。
- 解散陪练房文案明确“本手结束后解散”，不承诺退回大厅点数。点数房原退款文案保持。
- 记录与统计按点数/陪练切换，切换重置分页并隔离旧请求、账号切换和迟到响应。大厅余额、净盈亏和正式战绩不会跳入练习结果。

具体组件组合、图标、字段最终命名、策略阈值、测试文件拆分由实施者在现有架构内决定，不增加依赖。若需要新 UI 视觉稿另行获得用户授权，不为本设计启动应用或浏览器。

## 10. 测试与完成标准

实施时按数据隔离→生命周期→策略/调度→接口/MCP→界面逐段先测试后实现，详细计划在设计确认后编写。

必须覆盖：

1. 真人赢机器人、输机器人、真人互赢、边池、全下、平局余数、退出、超时、解散、维护、重启恢复后，GameAccount 余额与累计净盈亏不受练习影响；GameSession 记账字段始终为零。
2. 同账号同时参加点数房和陪练房，大厅占用/总额/流水/补助只按点数会话，重连能分别找到两桌。
3. 新模式不可切换，计分房机器人请求被拒；伪造 funding、身份或外部 act 机器人均失败。
4. 非房主添加/移除被拒；满房并发真人 join/bot.add 不超容量，至少保留真人容量；创建丢响应复用标识不重复，机器人移除后重试不复活。
5. 只有机器人不发牌，最后真人暂离后暂停；最后真人超时后当前手合法收尾；机器人活动不阻止无人房维护。
6. 手中添加/移除不继承旧手牌或当前下注；输光移除，不擅自增筹/补机器人。
7. 策略只接收本人及公开字段，输出均在 legalActions/金额范围；纯函数不访问 IO/时钟，给定输入可重复测试。
8. 两个调度实例竞争只产生一次行动；旧调度不操作新手，单个坏房间不阻塞第 101 个；进程重启后继续，不在事务内无界循环。
9. 练习/正式历史和统计、版本计数、同桌比较、热表与归档一致隔离；归档后来源及类型还可识别，隐私不放宽。
10. Renderer 无出牌控件与 act/join/wait bridge；房主能创建陪练、加机器人、复制 AI 接入指令，外部 AI 通过正常 MCP 连续打完多手。

执行 server 测试、server API 构建、desktop hard constraints/typecheck/test，并针对专用本地 `_e2e` Postgres 验证新增迁移、并发、资金与归档。不得连接业务库。真实外部 AI 长局及桌面手动测试若未执行需明确列出，不能用程序机器人通过替代“两个真实 AI 50 手”的历史验收项。
