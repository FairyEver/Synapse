# Drive Upload Conflict Design

Date: 2026-06-12
Scope: `server/`, `desktop/`, `shared/`

## Goal

Make Synapse Drive upload conflicts explicit. When a user uploads a file whose name already exists in the target folder, Synapse should ask whether to replace the existing file or keep both files. Replacing updates the existing Drive item so share URLs stay valid; keeping both creates a new file with a timestamp suffix.

This design separates three product meanings:

- Upload as new: create a new Drive item.
- Replace file: update the content of an existing Drive item without changing its identity.
- Republish: update a published page or site snapshot after the source file or folder has changed.

## Current Behavior

Current Drive upload behavior is inconsistent for files and folders:

- File uploads call `prepareUpload()` and create a new `DriveItem` without checking for another active file with the same name in the same folder.
- Folder creation, folder rename, and folder move reject same-name folder conflicts.
- Desktop local upload passes only file/folder names and paths. It has no conflict strategy such as replace or keep both.

This means a user can upload a same-name file and end up with two visually identical rows. If the old file was shared or used as a publication source, those links still point to the old Drive item. The user may think they replaced the file, but they actually created another one.

## Product Rules

### Same-Name File Upload

When uploading into a folder that already contains an active file with the same name:

1. Show a conflict confirmation before the upload starts.
2. Offer three choices:
   - `替换`: replace the existing file content.
   - `保留两者`: upload as a new file with a timestamp suffix.
   - `取消`: stop the upload.
3. Do not silently create another file with the exact same name.

For single-file upload, the dialog names the conflicting file.

For multi-file upload, if one or more files conflict, the dialog offers one batch strategy:

- `全部替换`
- `全部保留两者`
- `取消`

The first version does not require per-file decisions inside one batch. That keeps the flow predictable and avoids turning upload into a file merge tool.

### Keep Both Naming

When the user chooses keep both, Synapse creates a new file with a timestamp suffix:

```text
report.md -> report_20260612_1430.md
archive.tar.gz -> archive_20260612_1430.tar.gz
README -> README_20260612_1430
```

The timestamp is generated by the service at final write time. If the generated name still conflicts, the service appends a short numeric suffix:

```text
report_20260612_1430.md
report_20260612_1430_2.md
```

### Replace Semantics

Replacing a file means:

- Keep the existing `DriveItem.id`.
- Keep existing share rows attached to that item.
- Keep existing publication records pointing at that item as their source.
- Update file content, size, MIME type, storage metadata, upload status, and updated time.
- Do not change file name unless the product later adds an explicit rename step.

If the file is shared, the existing share URL keeps working and shows the new file content.

If the file is the source of a published page or site, replacing the source file does not change the currently published deployment. The user must run `重新发布` to update the public page or site while keeping the publication URL stable.

### Folder Conflicts

The first version does not replace folders or merge folder trees.

Rules:

- Same-name folder conflicts remain blocked.
- Uploading a folder whose root folder name already exists returns a conflict that cannot be solved by `替换`.
- If files inside a newly uploaded folder conflict with existing files because the flow later supports folder merge, those file conflicts may use the same batch strategy. This is not required in the first implementation.

This keeps the first version focused on file replacement, which is the user-visible need for stable share and publication sources.

## UX Design

### Single File Dialog

Title:

```text
已有同名文件
```

Body:

```text
当前目录已有 report.md。
```

Actions:

- `取消`
- `保留两者`
- `替换`

Button meaning:

- `替换`: update the existing file so current links keep pointing to it.
- `保留两者`: upload a new file named with a timestamp suffix.

The dialog should avoid long implementation text. A concise secondary line is acceptable if needed:

```text
替换后，已发布内容需要重新发布。
```

### Batch Dialog

Title:

```text
发现同名文件
```

Body:

```text
有 {count} 个文件与当前目录内容重名。
```

Actions:

- `取消`
- `全部保留两者`
- `全部替换`

The dialog may show a compact list of up to five conflicting filenames and a remaining count. It should not show storage keys, item ids, owner email, or internal metadata.

### Upload Result

After upload:

- Replacement success counts as completed.
- Keep-both success counts as completed.
- Cancelled upload should not show as failed.
- If replaced files are publication sources, show a concise follow-up toast or row state that leads users to `重新发布`. Do not automatically republish.

## API Design

### Conflict Inspection

Add a Drive upload conflict inspection API.

Request shape:

```ts
type DriveUploadConflictInspectInput = {
  parentId: string | null
  entries: Array<{
    kind: "file" | "folder"
    name: string
    relativePath?: string
  }>
}
```

Response shape:

```ts
type DriveUploadConflictInspectResult = {
  conflicts: DriveUploadConflict[]
}

type DriveUploadConflict =
  | {
      kind: "file"
      name: string
      relativePath: string | null
      existingItemId: string
      existingUpdatedAt: string
      replaceable: true
    }
  | {
      kind: "folder"
      name: string
      relativePath: string | null
      existingItemId: string
      existingUpdatedAt: string
      replaceable: false
      reason: "folder-conflict"
    }
```

The service checks only active, non-deleted items owned by the current user under the relevant target parent.

### Upload Strategy

Add an explicit conflict strategy to upload prepare APIs:

```ts
type DriveUploadConflictStrategy =
  | { mode: "fail" }
  | { mode: "replace"; existingItemId: string }
  | { mode: "keep-both"; timestamp: string }
```

The client may omit the strategy for non-conflicting uploads. The service treats omitted strategy as `fail` if a conflict exists.

The service must validate strategy at final prepare time:

- `replace` requires that `existingItemId` belongs to the user, is active, is a file, is in the target folder, and has the same normalized name.
- `keep-both` generates a final safe name at the service layer.
- `fail` rejects if a same-name active file exists.

This protects against races between inspection and upload.

### Replace Upload Flow

Replacing should use the existing upload session model where possible:

1. Create an upload session associated with the existing file item.
2. Reserve quota for the new file size while accounting for the old file size.
3. Upload the new object to a staging key or new object key.
4. On complete, verify size and atomically update the existing item metadata to the new object.
5. Adjust used bytes by `newSize - oldSize`.
6. Mark session completed.

The old file must remain usable until completion succeeds. A failed replacement must not leave the item pointing at a missing or partial object.

Storage cleanup of old objects can be immediate after successful metadata switch or deferred through an existing cleanup path if available.

### Keep Both Flow

Keep-both uses the normal new-item upload path with a service-generated non-conflicting name.

The timestamp format is:

```text
YYYYMMDD_HHmmss
```

The timestamp should be based on server time. The user-facing filename uses the target folder's current collision state at prepare time.

## Desktop Flow

### Upload Entry Points

Apply the same conflict handling to:

- Button file upload.
- Drag-and-drop file upload.
- Folder upload when file-level conflicts are in scope.

Before starting upload:

1. Build the existing `DriveLocalUploadRequest`.
2. Inspect conflicts for the upload entries.
3. If no conflicts, upload normally with fail-on-conflict safety.
4. If conflicts exist, show the confirmation dialog.
5. Continue with the chosen strategy or cancel.

### Local Upload Bridge

Extend `uploadDriveLocalItems` input with a conflict policy:

```ts
type DriveLocalUploadConflictPolicy =
  | { mode: "fail" }
  | { mode: "replace-all" }
  | { mode: "keep-both-all" }
```

The desktop service maps this policy to per-file prepare calls:

- `replace-all`: use the inspected conflict's `existingItemId` when a conflict exists; non-conflicting files upload normally.
- `keep-both-all`: use keep-both for conflicting files; non-conflicting files upload normally.
- `fail`: current default for no-conflict upload, with server-side race protection.

The renderer should not infer ownership or resolve replacement targets by itself. It uses the inspection result returned by the backend.

## Publication Behavior

Replacing a source file does not mutate existing publication deployments.

Rules:

- Existing publication URL remains stable.
- Existing deployment content remains stable until republish.
- Drive item row may expose existing publication actions as it does today.
- After source replacement, the UI may show a concise prompt to run `重新发布` for existing page/site publications.

This keeps published pages and sites as explicit snapshots, while still giving users a clear path to update them.

## Error Handling

- If conflict inspection fails, fall back to upload failure rather than silently creating duplicates.
- If the user cancels the conflict dialog, no upload session should be created.
- If replacement prepare fails because the item changed or no longer exists, show a concise upload error and reload the current folder.
- If upload to storage succeeds but complete fails, cancel or expire the upload session using the existing cleanup path.
- Replacement must not delete or detach the old object before the new object is verified.
- Batch upload should continue non-conflicting files only if the user has chosen a strategy and the implementation already supports partial failures. Otherwise, abort the batch on unrecoverable strategy errors.

## Security And Audit

- Replacement requires the same ownership checks as delete, rename, and move.
- A file can replace only a file, never a folder.
- Folder replacement is not supported in the first version.
- MIME type and file size are derived from upload input and verified through storage completion.
- The API must not accept storage keys, owner ids, or arbitrary target item ids without validating them against the authenticated user and target folder.
- Logs and audit entries may record item ids, names, strategy, and counts, but should not log local file paths from the desktop client unless an existing upload log path already allows them.

## Testing Plan

Server tests:

- Inspect returns no conflicts for unique file names.
- Inspect returns replaceable file conflicts for active same-name files.
- Inspect returns non-replaceable folder conflicts for same-name folders.
- Default upload strategy rejects same-name file conflicts.
- Keep-both creates a timestamp-suffixed file and preserves extension.
- Replace updates the existing item id, size, MIME type, storage key/status, and updated time.
- Replace keeps share rows attached to the same item.
- Replace does not change publication deployment.
- Replacement quota adjusts by the size delta.
- Replacement failure before completion leaves the old file usable.
- Race condition: conflict appears after inspection and before prepare.

Desktop tests:

- File picker upload with conflict opens the dialog.
- Drag upload with conflict opens the dialog.
- Cancel does not call the upload bridge.
- Replace passes a replace-all policy.
- Keep both passes a keep-both-all policy.
- Batch conflict dialog shows conflict count and compact filenames.
- Upload success refreshes the current folder.

Shared type tests:

- Conflict strategy and DTO schemas accept the intended shapes.
- Keep-both filename helper preserves `.tar.gz`, normal extensions, and extensionless files.

## Non-Goals

- No folder tree merge UI in the first version.
- No per-file decision matrix for large batch uploads.
- No automatic republish after replacing a source file.
- No file version history UI.
- No diff preview for replacement.
- No automatic local file watcher or sync.
