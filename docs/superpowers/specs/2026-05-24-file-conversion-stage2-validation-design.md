# File Conversion Stage 2 Validation Design

## Goal

Stage 2 turns the file conversion core from an architecture-level implementation into a product-ready local ingestion capability.

The focus is not adding more formats. The focus is proving that real `.docx`, `.xlsx`, `.pdf`, and `.pptx` files convert correctly enough for downstream use, and that the chosen libraries are safe for Electron development, typecheck, build, and packaging.

## Background

Stage 1 added:

- A Knowledge Base-independent `desktop/electron/services/file-conversion/` service.
- Extractors for `.docx`, `.xlsx`, `.pdf`, and `.pptx`.
- A `.doc` / `.ppt` legacy helper boundary that returns `missing_local_helper` unless a local helper is explicitly configured.
- A Knowledge Base `source-staging.ts` adapter that archives originals under `_attachments/originals/` and writes generated Markdown under `.raw/<kind>/`.
- Focused mock and structural tests.

Those tests prove the boundaries and data flow. They do not yet prove that real-world files parse well, that generated Markdown is useful for `/wiki ingest`, or that the new parser dependencies package cleanly with Electron.

## Hard Rules

- Keep conversion local-only. Do not use online document parsers, OCR services, vision APIs, or remote conversion APIs.
- Keep `file-conversion` independent from Knowledge Base. Stage 2 may add fixture tests for Knowledge Base staging, but parser correctness belongs to the common conversion service.
- Do not write parser binaries, converter scripts, Agent skills, Agent hooks, Agent commands, plugins, or full runtime prompts into user knowledge-base folders.
- Do not add Workflow node UI in Stage 2.
- Do not add OCR or scanned-PDF support in Stage 2.
- Do not treat partial empty extraction as success unless the result contains an explicit warning or structured error.
- Do not silently accept encrypted, password-protected, malformed, or unsupported files as normal converted sources.
- Do not keep a parser dependency if it breaks Electron typecheck, build, packaging, or native binary distribution expectations.

## Scope

Stage 2 includes five workstreams:

1. Real fixture corpus.
2. Real parser behavior tests.
3. Markdown quality and truncation rules.
4. Error classification.
5. Electron build and packaging risk verification.

Stage 2 excludes:

- OCR for scanned PDFs or images.
- Visual preview UI.
- Workflow conversion node.
- Bundling Apache Tika or LibreOffice.
- Cloud fallback.
- Pixel-perfect document layout reconstruction.

## Fixture Corpus

Create a small local test corpus under:

```text
desktop/electron/services/file-conversion/__tests__/fixtures/
  docx/
  xlsx/
  pdf/
  pptx/
  malformed/
```

Fixtures must be small and safe to commit. They should contain synthetic content only.

Required fixtures:

| Path | Purpose |
| --- | --- |
| `docx/basic.docx` | Title, headings, paragraphs, bullets. |
| `docx/table.docx` | At least one simple table. |
| `xlsx/multi-sheet.xlsx` | Two sheets, headers, numbers, dates, blank rows. |
| `xlsx/wide-sheet.xlsx` | A sheet wide enough to exercise table rendering limits. |
| `pdf/text.pdf` | Text PDF with at least two pages. |
| `pptx/basic.pptx` | Two slides with title/body text. |
| `pptx/notes.pptx` | Speaker notes when supported by the parser. |
| `malformed/broken.docx` | Deliberately invalid file with `.docx` extension. |
| `malformed/broken.pdf` | Deliberately invalid file with `.pdf` extension. |

Fixtures can be generated by a test fixture script if the generated binaries are deterministic. If deterministic generation is too heavy, commit the binary fixtures and document how they were created in `fixtures/README.md`.

## Parser Acceptance Criteria

### `.docx`

The `.docx` extractor should:

- Extract non-empty text from real fixtures.
- Preserve headings as Markdown headings when feasible.
- Preserve bullets as Markdown list items when feasible.
- Preserve table content in readable Markdown or text form.
- Include parser warnings in `FileConversionResult.warnings`.
- Return `parse_failed` for malformed `.docx`.

If the current Mammoth raw-text path cannot preserve enough structure, Stage 2 should switch the `.docx` extractor to Mammoth HTML output plus a small deterministic HTML-to-Markdown normalization step.

### `.xlsx`

The `.xlsx` extractor should:

- Emit one Markdown section per sheet.
- Render small sheets as Markdown tables.
- Preserve obvious scalar values such as strings, numbers, dates, and formula display values.
- Apply a configured row and column limit.
- Emit a truncation warning when a sheet exceeds limits.
- Return `parse_failed` for malformed `.xlsx`.

Initial limits:

- Maximum rendered rows per sheet: 200.
- Maximum rendered columns per sheet: 30.
- Maximum rendered sheets per workbook: 20.

These limits are parser output limits, not upload size limits.

### `.pdf`

The `.pdf` extractor should:

- Extract non-empty text from a real text PDF fixture.
- Preserve page count in metadata when the parser exposes it.
- Add page boundaries when page-level extraction is available.
- Return `parse_failed` for malformed `.pdf`.
- Return a warning when text extraction succeeds but produces empty text.

Scanned PDFs remain out of scope. A scanned PDF should not be represented as a normal successful text conversion unless the output clearly warns that no text was extracted.

### `.pptx`

The `.pptx` extractor should:

- Extract non-empty text from real presentation fixtures.
- Preserve slide boundaries if the chosen parser exposes them.
- Preserve speaker notes if the chosen parser exposes them and notes are not explicitly ignored.
- Emit `presentation_structure_limited` only when slide boundaries are not available.
- Return `parse_failed` for malformed `.pptx`.

If `officeparser` cannot reliably expose slide boundaries or useful text, Stage 2 should run a narrow spike with a focused PPTX parser before keeping `officeparser` as the long-term dependency.

## Error Model

Stage 2 should make error behavior deterministic:

| Scenario | Result |
| --- | --- |
| Unknown extension | `unsupported_format` |
| Path missing or not a file | `read_failed` |
| File above configured byte limit | `size_limit_exceeded` |
| Malformed supported file | `parse_failed` |
| Encrypted or password-protected file when detectable | `encrypted` |
| `.doc` or `.ppt` without helper | `missing_local_helper` |
| Parser returns empty text from a valid file | success with `empty_extraction` warning, unless the parser reports a hard failure |

Knowledge Base staging should map conversion failures to `conversion-error` for upload results, while preserving enough internal detail for logs/tests.

## Markdown Quality Rules

Markdown output should be useful for `/wiki ingest`, not visually perfect.

Required shape:

- Every converted file starts with one `# <title>` heading.
- Documents preserve meaningful headings when parser output allows it.
- Spreadsheets use `## Sheet: <name>` sections.
- PDFs use `## Page N` sections when page-level text is available.
- Presentations use `## Slide N` sections when slide-level text is available.
- Tables must escape pipe characters.
- Empty rows should be skipped unless they separate meaningful blocks.
- Truncated content must include a warning in metadata, not a hidden omission.

Knowledge Base generated Markdown must keep the Stage 1 frontmatter:

```md
---
source_original: "_attachments/originals/YYYY/MM/DD/file.ext"
source_format: "docx"
converted_at: "2026-05-24T00:00:00.000Z"
---
```

## Build And Packaging Verification

Stage 2 must explicitly verify parser dependency risk.

Required checks:

```bash
pnpm --filter @synapse/desktop run typecheck
pnpm --filter @synapse/desktop run build:electron
pnpm --filter @synapse/desktop run build:renderer
pnpm --filter @synapse/desktop run check:hard-constraints
```

Packaging check:

```bash
pnpm --filter @synapse/desktop exec electron-builder --dir --mac --arm64 --publish never
```

If full packaging is too slow for routine CI, Stage 2 should at least define a local release-readiness command and document whether it was run.

Special attention:

- `pdf-parse` v2 depends on `@napi-rs/canvas` through its dependency graph. If this creates native binary packaging risk, replace PDF parsing with a lighter direct `pdfjs-dist` path.
- Verify whether any parser dependency needs `asarUnpack`.
- Verify Windows packaging implications for parser dependencies even if the local run is macOS.
- Confirm no parser requires network access during runtime conversion.
- Confirm no parser tries to run postinstall binaries that violate current app packaging rules.

## Knowledge Base End-To-End Acceptance

Stage 2 should include a service-level end-to-end test:

1. Create a temp Knowledge Base project.
2. Upload a real `.docx` fixture through `KnowledgeBaseService.uploadSources`.
3. Assert the original is copied to `_attachments/originals/YYYY/MM/DD/`.
4. Assert generated Markdown is written to `.raw/documents/YYYY/MM/DD/`.
5. Run `scanKnowledgeBaseSources()`.
6. Assert the generated Markdown appears as a supported `new` source.
7. Assert the original binary is not listed as a `.raw` unsupported source.

Equivalent tests should cover `.xlsx`, `.pdf`, and `.pptx`.

Stage 2 does not need to run a live Agent or `/wiki ingest`; it only needs to prove that the deterministic source pipeline produces files the existing ingest command can see.

## Observability

Parser failures should remain visible without leaking file content:

- Log error code, extension, file size, and parser name.
- Do not log extracted document text.
- Do not log full user file paths where existing logging policy avoids them; use path length or basename only when enough.
- Tests should assert structured error codes, not full stack traces.

## Dependency Decision Gate

At the end of Stage 2, each parser dependency must be classified:

| Dependency | Keep / Replace / Defer | Decision reason |
| --- | --- | --- |
| `mammoth` | undecided before Stage 2 validation | Must preserve enough `.docx` structure. |
| `xlsx` | undecided before Stage 2 validation | Must handle multi-sheet extraction and limits. |
| `pdf-parse` | high-risk until packaging check passes | Native dependency risk through `@napi-rs/canvas`. |
| `officeparser` | high-risk until real PPTX fixture quality is confirmed | PPTX ecosystem is weaker; slide boundaries matter. |

The implementation plan should update this table with final decisions after verification.

## Testing Strategy

Focused test suites:

- `electron/services/file-conversion/__tests__/file-conversion-fixtures.test.ts`
- `electron/services/file-conversion/__tests__/file-conversion-errors.test.ts`
- `electron/services/knowledge-base/__tests__/source-staging-fixtures.test.ts`

Existing suites that must continue passing:

- `electron/services/file-conversion/__tests__/file-conversion-service.test.ts`
- `electron/services/file-conversion/__tests__/markdown.test.ts`
- `electron/services/knowledge-base/__tests__/source-staging.test.ts`
- `electron/services/knowledge-base/__tests__/source-scan.test.ts`
- `electron/services/knowledge-base/__tests__/knowledge-base-service.test.ts`
- `electron/modules/knowledge-base/__tests__/ipc.test.ts`

## Success Criteria

Stage 2 is complete when:

- Real fixture tests pass for `.docx`, `.xlsx`, `.pdf`, and `.pptx`.
- Malformed fixture tests return structured errors.
- Empty extraction and truncation warnings are represented in `FileConversionResult.warnings`.
- Knowledge Base staging tests prove converted Markdown is scan-ready.
- Typecheck and hard-constraint checks pass.
- Electron build checks pass.
- Packaging risk for `pdf-parse` and `officeparser` is explicitly resolved as keep, replace, or defer.
- No converter files, parser runtime files, Agent skills, hooks, commands, plugins, or full prompts are written into user vault templates.

## Follow-Up After Stage 2

After Stage 2, the next likely spec is either:

- Stage 3 Workflow conversion node, if dependencies are accepted.
- PDF/PPTX parser replacement, if packaging or extraction quality fails.
- Legacy Office helper packaging, if `.doc` and `.ppt` become product priorities.
