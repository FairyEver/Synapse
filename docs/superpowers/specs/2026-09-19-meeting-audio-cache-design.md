# 录音 · 本机音频缓存

> 2026-09-19 定稿。桌面端与手机端同一套规则，差异只在存储位置和播放器实现。
> 与 `2026-09-19-meeting-recording-redesign-design.md` 冲突时以那一份为准。

## 1. 为什么要做

录音的音频存在云端，播放时每次现签一个地址去流式拉。这带来三件事：

1. **同一条录音反复听，就反复拉。** 40 分钟的会约 19 MB（64 kbps），在手机流量上这是真金白银。
2. **没网就完全听不了。** 哪怕五分钟前刚听过。
3. **手机端有个反直觉的地方。** 录音期间音频本来就落在本机，上传成功之后**立刻删掉**——用户想马上回听刚录的那条，反而要把它从云端再下回来。

顺带还有一个一致性问题：服务端把录音删了之后，本机不该还留着一份能播的副本——否则用户在另一台设备上删掉，这一台上还能听，「删除」就没真正生效。

## 2. 决策

### 2.1 缓存状态不出现在界面上

没有「已下载」「已缓存」「离线可用」这类字样，列表上也没有任何标记。快慢用户自己感觉得到。

产品既有口径里「上传中 / 上传进度 / 云盘 / 云端 / 服务器」一律不出现；说「已下载到本机」是同一个方向。缓存是**实现细节**，不是用户的心智模型。

### 2.2 播放即缓存，先下完再播

点开一条还没到本机的录音 → 显示「正在下载」→ 下完 → 播本机那份。在线时那一下通常短到看不见。

**不采用「一边流式播一边后台落盘」**：那要么双倍流量（`<audio>` 拉一遍、下载器再拉一遍），要么得在播放中途把 `src` 从网络地址换成本机地址（播放位置会丢）。下完再播的实现只有一条路径，语义也干净。

代价：头一次听长录音要等。1 小时约 28 MB，家用宽带几秒。可以接受。

**例外是刚录完的那条**：手机端录音期间音频就在本机（2.3），所以「录完马上回听」是秒开。

### 2.3 手机端录完不再删本机那份

收尾成功后只删待收尾记录（`pending.json`），**音频文件留下并归入缓存**。

这不是新增成本——文件本来就在那儿，删掉再下回来纯属浪费。

⚠️ 这两件事必须一起做：`PendingMeetingRecordingStore.loadAll` 的判据是「本机还有没有音频」，`pending.json` 照常删掉，否则下次启动会去收一条已经收完的录音。

桌面端**不做**这个改动：它现在完全不落盘，改成落盘是另一件事（见 §5）。

### 2.4 服务端删了，本机那份一并删掉

「删除必须真的删干净」是既有口径。本机缓存不能成为例外。两个触发点：

- **本机删的**：用户在这一台设备上删掉那条录音时，顺手清掉本机对应的缓存文件。
- **别的设备删的**：下拉刷新列表时，如果这次返回的**条数少于上限**（说明服务端把所有录音都给全了），那么本机缓存里那些不在这份列表中的条目就是被删掉的，一并清掉。

⚠️ **返回刚好等于上限时不判**——那说明还有更早的没返回，照这个规则会把它们误删。桌面端列表一次给 200 条（`server/src/meeting/meeting.service.ts` 的 `take: 200`），判据是 `items.length < 200`。这一条有单测，并把 `<` 改成 `<=` 反证过会红。

### 2.5 本机上限 2 GB，超了从最久没听的开始清

按「最后一次播放时间」排序，从最早的开始删，直到降回上限。

- 40 分钟的会约 19 MB，2 GB 大约能装 100 场。
- 上限本身是防跑飞的安全阀，不是日常会碰到的边界。
- 不设时间过期：听过就留着，用户下次想听就还在。

### 2.6 没到本机时显示「正在下载」，转满 10 秒给一个「重试」

真的一点网都没有时，「正在下载」会一直转下去——因为网一回来它确实会自己接着下完，所以**不该说成失败**。但它也不能永远只转不说话：用户盯着一圈转会以为卡死了。

**这个「重试」是手动催一下，不取代自动恢复。** 后台的下载尝试照旧继续，网回来自愈，用户不动手也能好。否则就变成「用户不操作就永远好不了」，与仓库既有的「错误必须自动恢复」相反。

### 2.7 缓存坏了不当回事

索引文件损坏、缓存文件被手工改坏、删除失败——一律当作「未命中」或静默跳过，**不抛错、不弹提示**。缓存永远不该让功能挂掉。

## 3. 缓存规则（两端同一套）

每条缓存记四个字段：`meetingId`、`size`、`lastPlayedAt`、`peaks`。索引是一个 JSON，音频本体是旁边的独立文件。

- **命中判据三件套**：文件存在 **且** 磁盘大小等于索引里记的 `size` **且** 等于服务端详情里的 `recording.size`。三者有任一不符就重新下载（重下前先删掉坏文件）。
  - 拿不到服务端大小时（离线）退化成「文件在、大小对得上」——否则离线就听不了听过的录音了。
- **`peaks` 跟音频一起缓存**：波形数据只有十几 KB，离线时不该因为拉不到它而画一条平线。
- **索引写入必须原子**：写临时文件再 rename。
- **清理是尽力而为的**：删不掉（文件被占用等）不报错、不打断任何用户操作，下一次清理再试。

清理时机：

| 时机 | 动作 |
|---|---|
| 每次播放开始 | 更新这条的最后播放时间 |
| 本机删除某条录音 | 删掉它的缓存文件 |
| 列表刷新（返回条数 < 上限） | 清掉本机有、这次列表里没有的那些 |
| 缓存总量超过 2 GB | 按最后播放时间从早到晚删，直到降回上限 |

## 4. 交互规格

### 4.1 语音视图的状态机

两端的语音视图（波形卡片 + 播放键 + ±15 秒 + 当前/总时长）按这四种状态渲染：

| 状态 | 触发 | 表现 |
|---|---|---|
| **就绪** | 本机已有这份音频 | 正常。播放、点波形跳转、±15 秒全部走本机文件 |
| **载入中** | 本机没有，正在下载 | 波形按真实形状占位、整体压暗，播放头收起来，播放键禁用，下面一行转圈 +「正在下载」 |
| **载入超时** | 载入中持续满 10 秒 | 在「正在下载」下面补一个「重试」；后台继续自动尝试 |
| **不可用** | 服务端说这条录音没了 | 保持现状：「录音已删除 / 文字仍保留，切到「文字」查看。」 |

沿用现状不变的部分：`语音 / 文字` 两个平级视图、切换粘性、点波形任意位置跳转、没有时间刻度尺/缩略图/倍速。

10 秒计时从进入载入态起算，用一个 `setTimeout`，离开这一屏要清掉。**按「重试」不会让计时重来**，所以那行字不会闪回去。

### 4.2 文案表

| 场景 | 文案 |
|---|---|
| 载入中 | 正在下载 |
| 载入满 10 秒 | 重试 |
| 录音已被删除 | 录音已删除 / 文字仍保留，切到「文字」查看。 |

**不出现的词**：已下载、已缓存、离线、本地、云端、服务器、上传。

### 4.3 列表

**一个字都不加。** 列表行不显示任何缓存标记，行的内容与现在完全一致。

## 5. 非目标

- **不做列表/详情的离线可读。** 那是另一件事（离线可用），要动的是列表与详情的缓存策略，不是音频缓存。
- **不改桌面端「不落盘」这件事。** 桌面端录完不写本机文件，所以刚录完那条首播仍要下载；改成落盘是另一个改动。
- **不做后台预取。** 不因为「用户可能想听」就提前下载，只在真正播放时下。
- **不做缓存管理界面。** 没有「清理缓存」按钮，也没有容量显示——上限和 LRU 全自动。
- **不做边下边播。** 见 2.2。
- **不引入新的状态色或图标。** 载入态用现有主题 token，转圈用共享 `Spinner`。
- **不动服务端。** 本次服务端零改动。

## 6. 已知限制

**离线冷启动时，列表本身读不出来。** 列表来自服务端，没网就是空列表加一句错误——这不是本次引入的，本次也不改。

所以「正在下载」这个状态实际出现在两种情形：

1. 窗口/列表已经在屏幕上（有网时拉的），网络随后断了，点一条没听过的；
2. 有网，但音频一时拉不下来（弱网、服务端慢）。

这是有意接受的边界，不是疏漏。

## 7. 实现要点

### 7.1 桌面端：自定义协议必须自己回 206

renderer 不能直接读任意路径的文件。主进程注册一个特权协议把本机缓存目录映射出去，`<audio src="synapse-meeting-audio://local/<meetingId>">`。

**唯一的风险点是 Range 请求。** 拖动进度条要发 Range，协议处理器必须应答 `206` + `Content-Range`，否则**波形能画出来、拖动却失效**——这类失败不报错，只是行为不对。

照 `agent-artifact-protocol.ts` 那样用 `net.fetch(pathToFileURL(file))` 转发是**不通的**。Electron 41 实测（90 秒 m4a，`<audio>`）：

| 写法 | 响应 | `audio.seekable` | 拖动 |
|---|---|---|---|
| `net.fetch(file://)` | 200，无 `Content-Range` | `[0, 0]` | 拖不动 |
| `net.fetch(file://, { headers: request.headers })` | 200，无 `Content-Range` | `[0, 0]` | 拖不动 |
| 处理器自己解析 Range、读文件流、回 206 | 206，带 `Content-Range` | `[0, 90]` | 正常 |

所以处理器自己解析 `Range`、用 `fs` 读对应区间、回 206；越界区间回 416（回 200 整份会让播放器以为区间被满足了，位置就对不上）。响应体是**文件流**而不是整段读进内存——Chromium 的头一个请求是 `bytes=0-`，也就是整个文件，一个小时的录音就是 28 MB。

协议 privileges 用 `{ standard: true, secure: true, supportFetchAPI: true, stream: true }`。实测 `stream` 不是范围请求必需的，但响应体确实是流，声明它才符合语义。

### 7.2 桌面端：缓存目录不走 DataRepository

音频缓存直接写 `userData/meeting-audio-cache/`，**不走 `DataRepository`**：

- `docs/agents/repository-guide.md` 明确禁止把图片或大文件字节写进 PostgreSQL、SQLite 或 DataRepository；
- 音频缓存是**派生产物**（随时可以重新下载），备份它没有意义；
- `agent-artifacts` 同样是直接写在 `userData/` 下的。

`check:hard-constraints` 第 5 条（禁止裸 `fs.writeFile`）只扫 `electron/bootstrap` 与 `src/runtime`，不含 `electron/modules`；协议处理器在 `bootstrap` 下但只读不写。

### 7.3 桌面端：只新增一个 operation

`app.meeting.audio.ensure({ meetingId })`：

```
-> { state: "ready", url: string }   // 命中，url 是本机协议地址
 | { state: "downloading" }          // 未命中，已经起了一次后台下载
 | { state: "unavailable" }          // 服务端说这条录音没了
```

- **幂等**：同一个 meetingId 重复调用（重渲染、用户点重试）不会起第二个下载。
- 下载完成推一条 `meeting.audioReady` 的 domain 事件（带 meetingId 与本机地址）。
- **下载失败不推失败事件**：设计上它不是失败，主进程按退避继续重试；renderer 侧由「10 秒给一个重试」兜住。
- **不新增 `audio.forget` 之类的 operation**：清理是主进程自己的事，不该让 renderer 参与。

`unavailable` 这一支是为「详情还停在旧状态、服务端已经说这条没了」这个竞态补的：那种情况既没有音频可给，也不能假装在下载一直转下去。渲染进程拿到它什么都不做，等下一次详情刷新把那一屏换成「录音已删除」。

回放地址是对象存储的签名直链，下载走不带令牌的 `fetchPublic`——令牌只该发给自己的服务端。

### 7.4 手机端：文件与下载

- 缓存目录沿用 `MeetingRecordingFiles.directory()`（Application Support/MeetingRecordings，已排除 iCloud 备份）。
- 下载用 `URLSession`，签名地址接口改成返回地址本身，不再直接喂给播放器。
- 播放用 `AVPlayer(url: 本机 file URL)`。`AVPlayer` 播本机 m4a 是原生能力。
- 录音落在 `MeetingRecordingFiles.audioURL(recordingId:)`，缓存按 meetingId 命名；收尾成功后做一次 `moveItem`（同目录内改名，零成本）归入缓存，并把索引写好。
- **取消录音那条路不变**：仍然是全部删掉，不留缓存条目。

## 8. 验收基线

逐条走查，不要只跑测试就收工。

1. 有网、第一次听一条录音：语音视图先出现「正在下载」，随后正常播放。
2. 同一条录音第二次点开：**不出现**「正在下载」，直接就是播放态。
3. 把网断掉，点开一条已经听过的：正常播放，波形、拖动、±15 秒都对。
4. 把网断掉，点开一条没听过的：显示「正在下载」，转满 10 秒出现「重试」。
5. 承上，点「重试」：仍然显示「正在下载」（不报错、不变成失败）。
6. 承 4，把网接回来：**不用点任何东西**，自己下完并开始播放。
7. 拖动进度条跳到录音中段：正常跳转。
8. 手机上录完一条，立刻进详情点播放：**秒开**，不出现「正在下载」。
9. 录制中途取消：本机不留下任何缓存条目。
10. 在桌面端删掉一条录音：本机缓存文件同时消失。
11. 在手机上删掉一条录音，回桌面端下拉刷新：那台电脑上的缓存文件也消失。
12. 一条录音的音频在服务端被删（`recording.status === "deleted"`）：语音视图显示「录音已删除 / 文字仍保留」。
13. 缓存总量超过 2 GB 后继续播放新录音：最久没听过的那几条被清掉，最近听过的还在。
14. 缓存文件被手工破坏（截断一半）后点开：判为未命中，重新下载，最终能正常播放。
15. 全程界面里**不出现**「已下载」「已缓存」「离线」「云端」「服务器」任何一个词。
16. 列表行与现在**完全一致**，没有任何新增标记。
17. 手机端「转写失败 / 转写中」等既有状态不受影响。
18. 桌面端语音视图与文字视图来回切换：播放不中断，播放头位置正确。
19. 下载过程中离开这一屏再回来：不重复下载，已经下好的部分不重来。
20. 弱网（用限速工具）下点开一条没听过的：出现「正在下载」，最终能下完并播放。
