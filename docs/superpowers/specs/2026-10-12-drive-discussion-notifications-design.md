# 云盘 Markdown 评论与留言通知设计

日期：2026-10-12

状态：用户已于 2026-10-12 确认本书面设计，包括旧评论缺少来源分享时的兼容策略。下一阶段编写并审阅实施计划；不表示功能已经实现，本轮不修改运行时代码。

## 1. 目标与已确认范围

用户将 Markdown 文档上传至云盘并分享后，新评论、新留言和新回复应通知相关账号。收件人可以先看到操作人、文档名和简短内容摘要，再点击链接打开文档并定位到具体内容。

复用现有账号通知中心、桌面系统提醒、手机实时连接和生产 APNs。已读、软删除、未读计数、90 天保留、本机呈现设置及手机系统通知设置继续沿用现有机制。

仅以下四种成功创建产生通知：正文锚点评论的新讨论、评论的新回复、文末新留言、留言的新回复。浏览器、桌面桥接、MCP 和开放 API 只要调用相同业务创建服务，均采用相同规则，不由入口自行发通知。

编辑、删除、解决或重新打开讨论不产生新通知。历史创建事件不补发；上线后对历史讨论发表的新回复属于新事件，仍按收件人规则处理。

### Non-Goals

- 不增加关注、订阅、取消订阅、全体参与者群发、提及或通知偏好设置。
- 不增加邮件、Bark、企业微信或其他外部渠道，也不为每个事件创建站内信。
- 不扩展到非 Markdown 文件，不改变评论锚点、讨论解决权限或留言删除权限。
- 不增加 System App、Dock、Workflow Node、Automation Action、MCP tool 或 `synapse://` 路由。
- 不扩展 System Notifier 的公开输入，不增加桌面原生横幅点击回调。
- 不新增依赖，不重构其他通知来源、站内信 outbox 或待办 outbox。

## 2. 收件人与去重

“讨论发起人”是评论讨论的创建人，或文末根留言的作者；“被直接回复的人”是明确父评论的作者。没有父评论的回复按根讨论或根留言处理，不根据正文中的姓名推断对象。

| 创建事件 | 候选收件人 |
| --- | --- |
| 新建正文评论讨论 | 文档所有者 |
| 新建文末留言 | 文档所有者 |
| 新增评论回复 | 文档所有者、讨论发起人、被直接回复的人 |
| 新增留言回复 | 文档所有者、根留言作者、被直接回复的人 |

服务端根据受权文件、讨论、父评论和登录主体计算账号 ID；客户端不能指定收件人。先按账号 ID 去重，再排除操作者本人和失效账号。没有剩余收件人时只保存内容，不创建通知或投递记录。

同一个事件、同一个收件人只有一条账号通知。同一人符合多个身份时，通知文案按“被直接回复的人 → 讨论发起人 → 文档所有者”的顺序选择。身份优先级只影响文案，不改变收件人集合。

| 场景 | 结果 |
| --- | --- |
| 你拥有文档，张三发起评论，李四回复张三 | 你和张三各一条，李四不收 |
| 王五继续回复李四 | 你、张三、李四各一条，王五不收 |
| 你回复张三 | 张三一条，你不收 |
| 你同时是所有者、发起人和被回复者 | 一条，优先使用“回复了你” |
| 李四回复自己的内容 | 李四不收，其他所有者和发起人仍按规则接收 |
| 所有候选人都是操作者本人 | 不产生通知 |

评论讨论创建时的首评属于同一个创建事件，不能再按“新回复”生成第二批通知。

## 3. 用户看到的通知

以下使用《需求方案》作示例。文案中的“你”始终指该条通知的收件人。

| 事件与收件人身份 | 标题示例 | 操作 |
| --- | --- | --- |
| 张三新建评论，收件人是所有者 | 张三评论了《需求方案》 | 查看评论 |
| 张三新建留言，收件人是所有者 | 张三在《需求方案》中留言 | 查看留言 |
| 李四直接回复收件人的评论 | 李四回复了你在《需求方案》中的评论 | 查看回复 |
| 李四直接回复收件人的留言或留言回复 | 李四回复了你在《需求方案》中的留言 | 查看回复 |
| 王五回复收件人发起的评论讨论中的其他人 | 王五回复了你在《需求方案》中发起的讨论 | 查看回复 |
| 王五回复收件人发起的留言讨论中的其他人 | 王五回复了你在《需求方案》中发起的留言讨论 | 查看回复 |
| 收件人仅是文档所有者，有新增评论回复 | 王五回复了《需求方案》中的评论 | 查看回复 |
| 收件人仅是文档所有者，有新增留言回复 | 王五回复了《需求方案》中的留言 | 查看回复 |

完整示例：

> 李四回复了你在《需求方案》中的评论
>
> “这里建议增加一个审核步骤，避免直接提交。”
>
> 查看回复

操作人沿用现有分享作者的安全显示名称，不新增邮箱展示。标题保留动作和收件人关系，优先缩短过长的文档名、其次缩短作者名，最终遵守现有 64 字符存储上限。

正文取本次新增内容的纯文本摘要，合并连续空白，最多 120 个 Unicode code point；截断时预留省略号，整体不超过现有正文上限。不复制整条讨论、被回复内容或 Markdown 正文。摘要作为纯文本展示，不执行 HTML，不将其中的任意 URL 变成业务直达目标。

标题、文档名和摘要是事件发生时的快照。之后改名、编辑或删除内容不重写历史通知。正文和作者信息不得写入日志或审计；通知库中的内容继续遵循现有明文通知存储边界。

桌面消息中心使用已有阅读区和标准操作按钮。拟增加来源 `drive-discussion`，显示为“文档互动”，归属显示为“云盘”；不进入终端待处理。手机沿用现有通知行及站内网页入口，不新增通知页面或文档原生编辑器。

## 4. 业务与通知的边界

推荐采用服务端事务内创建通知、提交后可靠投递的方案。保存后直接发送无法覆盖进程退出和网络失败；完整订阅系统超出本次固定收件人规则的需要。

| 单元 | 职责 | 依赖 |
| --- | --- | --- |
| 现有评论与留言创建服务 | 权限和父级校验、保存新内容、提供真实事件事实 | Drive、Prisma、现有审计与协同事件 |
| Drive 通知编排 | 计算收件人、选择文案、创建目标和通知、写投递记录 | 当前事务、NotificationService |
| Drive 通知目标解析 | 根据本人通知解析 owner/share 打开上下文与定位 ID | 当前账号、Drive 访问校验、通知目标记录 |
| Drive 通知投递任务 | 认领待投递记录、提交后发送、租约与失败重试 | 现有调度、NotificationService 和 Live/APNs |
| 现有客户端与阅读器 | 读取通知、标记已读、打开链接、定位内容 | 既有集中客户端和文档阅读组件 |

通知编排属于 Drive，不塞入 Renderer、MCP handler 或公共 System Notifier。评论和留言复用同一个编排入口，事件类型明确区分根评论、评论回复、根留言、留言回复。

`drive-discussion` 是服务端拥有的来源，只扩展 `shared/src/notifications.ts` 的共享来源定义，不加入 `DESKTOP_NOTIFICATION_SOURCES`，也不能由开放通知 API 冒充。其他来源的创建语义保持不变。

## 5. 事务、投递和重试

一次创建在同一个数据库事务中完成：保存内容、计算真实收件人、为每人写目标记录与 `UserNotification`、写对应的持久投递记录。任一步失败则整体回滚，不报告“内容已保存”却缺少通知。权限、目标和父评论必须在写入边界复验；已删除父级不能接收新回复。

复用 `NotificationService.createInTransaction` 和现有账号内 `userId + sourceKey` 唯一约束。来源键拟定为：

- 正文评论首评及回复：`drive:annotation-comment:<commentId>`。
- 文末根留言：`drive:message:<messageId>`。
- 文末留言回复：`drive:message-comment:<commentId>`。

通知级别为普通 `active`，分组为 `drive`。已有幂等创建返回历史结果时，不再次生成通知或投递记录。通知去重只保证同一个已保存事件不会多建账号记录，不将现有不具备幂等键的内容创建 API 宣称为恰好一次。

拟新增 Drive 专属投递记录，与通知一对一，至少包含通知 ID、收件人、创建时间、状态、尝试次数、下次尝试时间、租约期限、租约 token 和固定失败原因。它不依赖客户端在线，也不复用待办业务表。

提交后立即尝试认领并投递本次记录，后台每 30 秒扫描补偿，每批最多 100 条。采用数据库行锁和 60 秒租约，长投递期间每 20 秒续租；失去租约必须终止后续外部调用，只有持有当前 token 的任务能回写状态。

重试延迟从 1 分钟开始倍增，最多 15 分钟；从事件提交起超过 24 小时停止外部投递。已读、软删除或已清理的通知不再投递。成功、跳过和超期记录按既有 90 天通知保留周期清理，未完成工作不能被提前删除。

网络调用只能发生于事务外，通过 `NotificationService.deliverCommitted` 复用桌面广播、手机实时事件和生产 APNs。失败重试始终使用同一通知 ID。账号列表中的记录可以保证去重；设备断线、网络超时和系统展示不支持承诺物理横幅恰好出现一次或一定显示。

现有协同 `annotation.changed` / `message.changed` 和审计在提交后继续执行；它们不是账号通知，不能充当可靠投递记录。推送失败不回滚已提交的评论或留言。日志只包含事件 ID、通知 ID、账号 ID、尝试次数和固定原因，不包含摘要、文件名、URL、密码或 cookie。

## 6. 直达链接与分享上下文

通知 URL 使用同源 HTTPS。拟增加受保护的 `/notifications/<notificationId>/open` 定位入口，路径只携带通知 ID，不携带评论正文、分享密码、Bearer、refresh token 或网页会话凭据。该入口是网页定位入口，不注册新的桌面 Deep Link。

拟增加与通知一对一的 Drive 目标记录，保存目标类别、item ID、thread/message ID、具体 comment ID（根留言为空）、动作以及所需分享引用。`UserNotification.targetId` 指向该记录。通知响应可追加只读、可选的 `driveDiscussion` 描述，仅含类别和动作供客户端选择按钮文案；收件人和分享上下文由服务端决定，不允许调用者覆盖。

打开过程：读取当前账号本人可见的服务器通知，按现有流程标记已读，解析当前目标，再使用现有 owner 或 `/share/...` 文档入口。打开本人通知不意味着取得文档访问权限；阅读器仍执行原有 owner/share 校验。

所有者使用自己的文件入口，不依赖分享是否启用。其他收件人使用其参与讨论时实际使用的分享上下文；不创建新分享，也不选择其他分享来绕过旧分享的密码、过期或停用。

当前评论和留言记录未保存完整的参与来源，因此本次实现需在经分享访问成功的新评论、留言和回复中保存内部分享引用。回复通知给非所有者时，优先使用被直接回复记录的来源，发起人使用根记录的来源；多身份合并仍以直接回复角色优先。引用只表达定位来源，不构成免密权限，点击时继续校验该分享的当前状态和文件包含关系。

历史记录没有来源引用时，不从审计、当前公开链接、相同文件名或任意新分享猜测来源。新回复仍创建相关人的通知；所有者仍可直达，非所有者缺少可靠上下文时该链接明确返回“文档已删除或无法访问”。若后续该收件人在有效分享上下文中继续参与，其新记录可以作为后续直接回复的来源。这个兼容性限制必须在上线验收中单独覆盖，不能将缺少来源误报为可用直达。

分享上下文只用于打开文件，不能改变评论解决权限、编辑权限、留言删除权限、协同状态或文件版本。复制通知链接也不能让另一个账号读取该通知或获得文档授权。

桌面从消息中心的“查看评论／留言／回复”通过既有外部链接桥接打开网页。桌面原生横幅继续交给现有 System Notifier 呈现，不新增链接或回调。

手机通知列表与 APNs 点按共用按通知 ID 重取、标记已读、解析本次服务器记录的入口。站内网页沿用现有 `WKWebView`、网页身份查询与必要确认；不得在 URL 中注入原生登录凭据。冷启动等待账号就绪，新导航或身份变化取消旧目标，迟到请求不能打开旧账号的内容。

## 7. 阅读器定位与异常

owner/share 文档入口接收经校验的定位片段。片段使用结构化类别及完整 ID，例如评论的 `threadId + commentId`，留言的 `messageId + commentId`；这里只传定位信息，不接受任意 selector、脚本、跳转 URL 或权限参数。解析、构造和校验集中在共享 helper 中，非法组合不交给页面猜测。

文档与讨论数据加载完成后再定位：评论展开对应讨论并定位具体评论，留言滚到文末并展开对应回复。定位应支持深页根留言和长回复列表，不能仅搜索当前首屏数据。目标已解决时仍可打开，但不能改变解决状态或全局筛选偏好。

原文锚点投影与解析结果继续以服务端为权威。原文位置失效时展示已有未定位讨论，不通过浏览器文字搜索重新挂载。聚焦目标后，用户继续阅读、编辑或主动导航不应被后续刷新再次抢回。

| 当前情况 | 用户看到的结果 |
| --- | --- |
| 文档、讨论和目标内容正常 | 展开对应讨论并定位具体内容 |
| 评论对应的原文位置失效 | 仍打开讨论，沿用现有原文位置不可用提示 |
| 文档可读，但目标评论、留言或回复已删除 | “该评论／留言／回复已删除” |
| 文件已删除、分享过期或停用、无阅读权限或缺少可靠分享上下文 | “文档已删除或无法访问” |
| 分享需要密码 | 进入现有密码验证，成功后保留并继续处理定位目标 |
| 需要登录 | 沿用既有登录流程，账号就绪后继续；不能把链接当作授权 |
| 读取失败或网络不可用 | 使用现有错误与重试入口，不标记业务目标已处理 |

通知摘要作为已发生事件的历史保留，不因目标编辑、删除或分享失效而撤回；点击时读取当前状态。打开通知只影响通知已读，不解决讨论、不写正文、不替用户回复。

## 8. 实施时需要同步的表面

本轮只固定设计。实施时同步更新：

- `server/src/drive/` 的创建服务、通知编排、目标解析与专属投递任务，以及 Prisma 模型和迁移。
- `server/src/notifications/` 的只读目标描述与来源边界；不扩展桌面自有来源白名单。
- `shared/src/notifications.ts`、通知 DTO 和共享 Drive 定位解析 helper。
- `dashboard/src/features/drive-browser/` 的定位状态、评论展开和文末留言目标加载；复用现有组件、hooks、集中客户端和主题。
- 桌面消息中心的来源标签、按钮文案及当前服务器通知打开入口。
- 手机通知目标解析、通知 ID 打开流程和现有站内网页入口；保持当前导航结构、iPhone/iPadOS 行为及网页身份协议。
- `docs/agents/module-boundaries.md`、账号通知规格、Drive 评论规格、移动运行时约束和 `docs/agents/capability-registry.md` 的例外说明。
- Drive、通知 MCP 描述与权威系统 Skill 指南，说明写入成功后会自动通知相关人，Agent 不应再另发一条通知；工具数量和既有写入参数保持不变。
- 实际产品实现同次更新 `RELEASE_NOTES_PENDING.md`；纯设计阶段不写成已交付功能。

客户端可视修改必须先阅读项目 UI 规则和组件主题；涉及新的 iOS 界面结论时按 `apple-design` 阅读 Apple 官方依据。本设计只固定通知内容与业务定位行为，不引入新的视觉规范。

## 9. 验收与发布

| 验收领域 | 必须覆盖 |
| --- | --- |
| 收件人 | 四类创建事件、直接与嵌套回复、所有角色重合、排除操作者、自回复仍通知其他相关人、无剩余收件人 |
| 文案 | 八类模板、角色优先级、无邮箱展示、长作者名和文件名、摘要截断、多行和安全纯文本 |
| 不通知 | 编辑、删除、解决、重新打开、历史事件不补发；旧讨论的新回复仍生成通知 |
| 入口一致 | owner/share 浏览器、MCP、开放 API 留言使用同一编排；无客户端指定收件人或冒充来源 |
| 原子性 | 内容、所有收件人的通知、目标及 outbox 任一失败整体回滚；提交前无网络发送 |
| 幂等与并发 | 首评不双发、已有创建幂等回执不重发、相同事件并发只一条账号通知、多 worker 租约隔离 |
| 重试 | 提交后崩溃可补偿、网络/APNs 失败重试同一 ID、租约失效终止、已读或删除停止、24 小时截止 |
| 权限与分享 | 只能读取本人通知；owner 独立入口；有效分享、密码验证、过期、停用、子文件移出分享、账号切换 |
| 历史兼容 | 旧讨论新回复正常通知；没有来源上下文的旧参与者明确不可用，不误选新分享 |
| 具体定位 | 正文评论、文末留言、嵌套回复、深页目标、已解决讨论、原文锚点失效及目标删除 |
| 客户端 | 桌面来源与按钮、手机通知行和 APNs 同一路径、冷启动、取消、网页账号身份、旧端未知来源回退 |

按数据库迁移与服务端、网页阅读器、桌面端、手机端的顺序上线。迁移仅增加所需表、字段和索引，不清理评论、留言、文档、分享或历史通知。旧客户端的未知来源回退必须通过兼容性检查，不能使新通知丢失或导致通知列表解码失败。

实施验证至少包括服务端事务与投递测试、网页定位测试、shared/desktop/dashboard/server 类型检查、桌面硬约束检查，以及手机通知定位与身份隔离测试。真实系统横幅和手机网页打开属于跨端验收，不能以单测通过代替。

发版、部署、启动应用及设备验收只在相应任务授权后执行。设计文档审阅通过后再编写实施计划，本文件不授权跳过计划审阅直接实现。
