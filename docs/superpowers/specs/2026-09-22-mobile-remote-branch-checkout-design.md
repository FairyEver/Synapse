## 1. 要解决什么

上一轮把 Git 操作搬进了手机端终端页，但**分支这一块只做了一半**：能列本地分支、能切、能新建、
能合并，唯独**没有入口能到达「远端有、本地没有」的那条分支**。而「同事刚推了一条分支，我上手机
接着干」正是用手机连终端时最常发生的一件事。

一轮概括：

> 给面板加一个入口，能看见这个仓库所有远端分支，点一条就把它迁出来（建一条跟踪它的本地分支并切过去）。

只有这一件事。不做远端分支的删除 / 改名 / 上游配置，不做分支树。

## 2. 现状（实施前必须核对，不要凭印象）

这一节写的都是**查过代码、跑过命令的事实**。其中三条直接决定方案形态。

### 2.1 三层都堵死：没有任何入口能到达远端分支

| 层 | 位置 | 事实 |
|---|---|---|
| 手机 UI | `SynapseMobile/SynapseMobile/Features/Terminal/Git/TerminalGitBranchList.swift:15` | 注释写明「**只列本地分支**」，列表只有一段「本地分支 · N」 |
| 手机 flow | `Features/Terminal/Git/TerminalGitFlow.swift:192` | 只发 `branches` 一个动作 |
| 电脑服务 | `desktop/electron/services/terminal-git/terminal-git-status.ts:104` | `for-each-ref refs/heads` —— **连 `refs/remotes` 都不读** |
| 线协议 | `shared/src/mobile-live.ts:1059` | `MobileGitAction` 只有 8 个动作，没有列 / 迁出远端的 |
| 线协议 | `shared/src/mobile-live.ts:1119` | `MobileGitBranch` 只有 `{ name, current }`，没有「属于哪个远端」这一位 |

「新建分支」的起点选择（`TerminalGitNewBranch.swift:29` → `.branches(.startPoint)`）复用同一份本地列表，
所以**也不能拿远端分支当起点**。

面板里唯一能切分支的入口是「当前状态」段的 `分支` 行（`TerminalGitPanel.swift:101`，标识符 `git-panel-branch`）。

### 2.2 「远端的新分支由『同步』带回来」这句话不成立（**决定性**）

上面那条 UI 注释、`TerminalGitFlow.swift:191`，以及上一轮设计文档的 §4.4（`:331`）与 §6（`:432`），
都用这句话解释为什么只列本地分支。**它是错的。**

电脑端的同步（`terminal-git-workflow.ts:159`）跑的是：

```
git fetch --prune
git merge --ff-only --no-overwrite-ignore @{u}
```

`@{u}` 是**当前分支的上游**。`fetch --prune` 只更新 `refs/remotes/*`，**不创建任何本地分支**。
所以同步完之后，远端新分支依然不在本地分支列表里 —— 「同步带回来」这条路走不通，
`refs/heads` 也不会因此多出一条。

**本轮要把这几处说法一起改掉**（代码注释两处、文档两处），不能留着。

### 2.3 手打同名分支会得到一条静默分叉的分支（**决定性**）

用户在「新建分支」里手打一个远端已有、本地没有的名字（例如 `feature-x`），电脑执行的是
`checkout -b feature-x`（`terminal-git-workflow.ts:117-121`，起点缺席＝从当前 HEAD 起）。
本机实测：

```
$ git fetch -q --prune origin          # 远端有 origin/feature-x
$ git checkout -b feature-x            # 手机走到这里
Switched to a new branch 'feature-x'
本地 feature-x:   09d3c3f   ← 从当前 HEAD 建的
origin/feature-x: 1b7e180   ← 不是这个
上游: fatal: no upstream configured for branch 'feature-x'
```

**它建了一条同名新分支，不从远端起、也不建上游。** 用户以为拿到了远端那条，实际得到一条
静静分叉出去的分支。这比「没有这个功能」危险，所以本轮的 `checkoutRemote` **必须显式建上游**
（`--track`），不能依赖任何 DWIM。

### 2.4 桌面端已有整套规则可搬

`desktop/electron/services/git-client/git-branch-service.ts`：

- `:192` `listRemote`：`git remote` + `for-each-ref --format=%(refname:strip=2)%00%(symref) refs/remotes`，
  远端名**按最长前缀匹配**（远端名本身可以含 `/`），**排除符号引用与 `*/HEAD`**，按远端分组、组内按名字排序。
- `:268` `checkoutRemote`：脏工作区先拒 → 校验远端分支名与本地名（`check-ref-format`）→ 远端必须存在 →
  `refs/remotes/<remote>/<branch>` 必须存在 → 本地同名分支已存在时**要求它的上游正是该远端**，否则拒 →
  worktree 占用检查 → `assertCheckoutSafe` → `git checkout --no-overwrite-ignore -b <local> --track <remote>/<branch>`。

**落点不是它。** 它绑 `repositoryId` 与「代码仓库」注册表，而手机端走的是 `terminal-git`
（`terminal-git-service.ts:13-24` 写明「只认路径」）。所以是把**规则**搬过去，不是把函数搬过去。

### 2.5 新动作会经过三道校验，其中一道是**断连**（**决定性**）

一个 `git` intent 从手机到电脑要过三关，三关都用同一份 `isMobileGitAction`：

| 关 | 位置 | 遇到不认识的动作 |
|---|---|---|
| 服务端 | `server/src/mobile-live/mobile-live.gateway.ts:260-263`（`parseMobileMessage` → `shared/src/live.ts:151` `isLiveMobileClientMessage` → `isMobileIntentPayload` → `isMobileGitAction`） | `null` → **`socket.close(1003, "invalid_message")`** |
| 电脑端 | `desktop/electron/services/live-connection-service.ts:312` | **静默丢弃**，只记一条 warn |
| 手机端 | `SynapseMobile` 自己的 `RealtimeClient` | 只解自己认识的下行消息，其余 return |

**服务端这一关最重**：不是「点了没反应」，是**整条连接被切断** —— 用户看到终端掉线，
几秒后自动重连（`RealtimeClient.swift:491` 指数退避，最长 30 秒）。
所以「新手机 + 旧服务端」是一个必须靠**部署顺序**避免的状态，不是一次可接受的失败。

先例与口径：

- `2026-09-17-terminal-full-keyboard-design.md:303`、`2026-09-19-terminal-keyboard-todesk-design.md:192`：
  「新手机 + 旧桌面端：用户看到一次失败提示」，**接受**，不做能力协商。
- `2026-09-17-mobile-claude-code-conversation-design.md:179`：手机把 `timeout` 翻译成
  「电脑端版本太旧，请在电脑上升级 Synapse」。
- `2026-09-21-mobile-terminal-git.md` 的「升级顺序（贯穿全程的硬约束）」那一节：新 intent kind
  与新的下行消息都会让旧服务端断连，所以真正的顺序是**服务端 → 桌面端 → 手机端，一步都不能颠倒**。
  本轮新增的是**既有 kind 里的新 action 值**，断连机制逐字相同 —— 那条硬约束照旧成立。
- 协议版本号是**严格相等**校验（`shared/src/mobile-live.ts:1347`、`:1362`）：`v !== MOBILE_PROTOCOL_VERSION`
  就整帧不认。**所以本轮绝不动 `MOBILE_PROTOCOL_VERSION`** —— 动一下手机与电脑之间所有帧全废，
  比新增 action 还狠。

### 2.6 线协议的上界

`MOBILE_FRAME_LIMITS`（`shared/src/mobile-live-constants.cjs`）里有 `maxGitBranches: 512`、
`maxGitRefNameLength: 255`。`isMobileIntentGitResult`（`shared/src/mobile-live.ts:1460`）用
`boundedArray(value.branches, 512)` 校验 —— 也就是说**超过 512 条会被判为非法结果、整条结果被丢掉**，
手机上表现为「电脑一直没有回答」。远端分支数可以轻易超过 512，所以产生端必须截断。

无远端时 `git fetch --all --prune` 退出码 0、不报错；`git remote` 与 `for-each-ref refs/remotes` 都返回空
（本机实测）。

## 3. 决策

### 决策一：三个新动作，不把「读」和「联网」合成一个

`MobileGitAction` 新增 `remoteBranches`（只读缓存）、`fetchRemotes`（联网）、`checkoutRemote`（写）。

不合成一个带 `fetch` 开关的动作，理由是**鉴权是按动作名分的**：`git-intent.ts:111` 现在把
`status`/`branches` 归到只读的 `terminal.state.read`，其余归到写的 `terminal.git.manage`。
一个动作有时读有时写，就得按参数分叉审计名 —— 事后查审计的人会看到同一件事记在两个名字下。
代价是下拉刷新多一次往返，可接受。

### 决策二：列表只读缓存，下拉刷新才联网

远端分支列表打开时**不跑任何 git 命令之外的东西**，只读电脑上已有的 `refs/remotes`（快、离线可用）。
下拉刷新才跑 `fetch --all --prune`，跑完重取列表。

这沿用桌面端那条已有的规矩（`2026-06-17-git-module-design.md:301`：「打开列表只读取本地
`refs/remotes`，不得隐式访问网络」），也与面板已有的「下拉重取状态」同一个手势习惯
（`TerminalGitPanel.swift:167`）。**不在用户没要求的时候替他访问网络。**

选它而不是「另给一颗『获取远程分支』按钮」：少一颗按钮；选它而不是「只读缓存、刷新靠同步」：
当前分支没有上游时同步会直接失败（`terminal-git-workflow.ts:199`），那条路径上用户无法刷新远端列表。

### 决策三：同名本地分支已存在时，已跟踪就直接切，跟踪别的就问另一个本地名

点一条远端分支时的四条分支：

| 情形 | 做什么 |
|---|---|
| 本地没有同名分支 | 新建同名 tracking 分支并切过去 |
| 本地有同名分支，且它跟踪的正是这个远端 | **直接切过去**（这就是「切换分支」，复用既有 checkout 的判别） |
| 本地有同名分支，但跟踪的不是这个远端 | 电脑回「需要另一个本地名」，手机弹输入框，填完重发 |
| 本地有同名分支，且解析出来它就是当前分支 | 回一句实话「已经在 `<name>` 上，没有做任何操作。」 |

第三、四行要分清楚：`foo` 跟踪 `origin/bar` 是合法状态，此时点 `origin/bar` 应当是**新建本地 `bar`**，
不是「你已经在这条上了」。所以判别依据是**解析出来的本地分支名是否等于当前分支名**，
不是「当前分支的上游是否等于这条远端分支」。

第四行不能让手机来短路（手机算不出解析结果），由电脑回话；手机照既有的 `finish`
（`TerminalGitFlow.swift:508`）显示电脑给的那句 —— 成功但有话说，走 `accepted` 带 `message`。

### 决策四：要另一个本地名用一个新取值表达，不新开一条结果通道

`TerminalGitFailure.needsDecision`（`terminal-git-types.ts:45`）从 `"dirty"` 扩成
`"dirty" | "localBranchName"`。两个取值都是同一件事：**电脑说「这一步需要用户先给个东西」，
值说明是哪样东西** —— `"dirty"` 是选一个走法（三选一），`"localBranchName"` 是填一个名字（输入框）。

线协议上对应 `code: "local_branch_conflict"`（与既有的 `dirty_working_tree`、`merge_conflict` 同一层）。
手机必须能分辨这两种，否则分不清该弹三选一还是弹输入框。

### 决策五：脏工作区仍是三选一，这一次「丢弃」成立

上一轮给新建 / 合并少一个「丢弃」选项，理由是**协议里只有 `checkout` 带 `discardChanges`，
而 git 也没有「把改动丢掉、但留在原地新建一条分支」这条原语**（`TerminalGitDirtySheet.swift:14`）。

**这两条理由对本轮都不成立**：git 有原语（`git checkout -f --no-overwrite-ignore -b <local>
--track <remote>/<branch>`，本机实测：脏改动被丢弃、上游照样建立），而协议本轮就给它加上
`discardChanges`。更关键的是**说不通**：本地 `feature-x` 跟远端跟踪同一个远端时，
从「分支」行进去有三个选项、从远端列表进来只有两个，而这是同一件事。

所以 `TerminalGitPendingSwitch.canDiscardChanges` 对 `.checkoutRemote` 返回 `true`，
丢弃路径上 `-f` 的语义与既有那条完全一致：**只丢已跟踪文件的修改，不删未跟踪的新文件**
（丢弃路径不带 `--no-overwrite-ignore`，与既有 `checkout -f` 保持一模一样）。

### 决策六：入口是「操作」段的一行

面板现在是「当前状态」放状态、「操作」放动作。迁出远端分支是动作，排进「操作」段与那四行同构，
不必解释为什么状态段里多了一行不是状态的东西。

### 决策七：远端列表上不标「本地已有」

标它要往协议里多塞一份本地分支快照（或是每行多一个位），**只换来一个提示** ——
而点了本来就会正确切过去（决策三第一、二行）。YAGNI。

## 4. 交互规格

### 4.1 Git 面板（改一行）

```
导航栏：  Git                              [完成]

仓库目录
  目录                    /Users/liyang/…/Synapse

当前状态
  分支                    main                 ›
  远端                    origin/main
  同步                    领先 2 个提交
  改动                    3 个文件已更改

操作
  提交                                         ›
  推送                                         ›
  同步                                         ›
  合并分支                                     ›
  迁出远端分支                                 ›   ← 新增
```

- 标识符 `git-panel-remote-branches`，标题「迁出远端分支」，**没有 detail 文案**。
- 可用条件与「合并分支」一致：`!flow.isBusy`（手上还有一个动作在跑时按住，见 `TerminalGitPanel.swift:149`）。
- 它不显示任何状态值 —— 远端分支数不是抬头要看的东西。

### 4.2 远端分支列表

```
‹ 返回   远端分支

   搜索分支

origin · 12
  origin/main                          → 一点即迁出
  origin/dev
  origin/feature-x

  （只有一个远端时也照常显示分组头：它是「这条分支属于谁」的唯一说明）
```

- `.searchable` 常显（`placement: .navigationBarDrawer(displayMode: .always)`），
  与本地分支列表同一条做法与同一个理由（那一页是推进来的，默认 placement 不给搜索框）。
  **用户硬要求：只要涉及到选分支的地方，一定要有搜索框。**
- 搜索匹配**限定名**（`origin/dev`）：用户打 `origin/dev` 或 `dev` 都能命中。
- **按远端分组**，组头是「远端名 · 条数」，组内按名字排序，远端之间按名字排序 ——
  与桌面端 `listRemote` 的返回顺序一致（`git-branch-service.ts:229`）。
- 行文字是**限定名**（`origin/dev`）：与 git 自己的说法一致，用户能直接对照终端里的输出。
- **不打勾**：远端列表里没有「当前分支」这个概念 —— 那是本地概念（决策七）。
- 空态两种，说法不同（与本地列表同一口径）：
  - 搜不到：`ContentUnavailableView`「没有匹配的分支」+「没有名字包含「X」的分支。」，标识符 `git-remote-branches-empty`。
  - 这个仓库没有远端分支：「还没有远端分支」+「这个仓库还没有任何远端分支。先做一次获取，或者确认这个仓库有远端。」，
    标识符 `git-remote-branches-empty`。
- **下拉刷新 = 获取 + 重取**：先发 `fetchRemotes`，成功后重发 `remoteBranches`。
  fetch 期间列表留在原地（不闪空态），拉起的 spinner 由 `.refreshable` 自己管。
  fetch 失败时**不重取列表**，弹失败框（标题「获取远端分支失败」，正文是电脑原文），
  列表内容保持原样 —— 用户可以继续拿旧的挑。
- 加载远端分支失败 → 失败框标题「读取远端分支失败」，正文是电脑原文。
- **加载成功且带 `message` 时用提示条显示它**（就是 §5.2 那句截断说明）。
- 点一行 → 走决策三的四条分支。
- 标识符：行是 `git-remote-branch-<限定名>`（例如 `git-remote-branch-origin/dev`）。

### 4.3 填另一个本地名（重名时）

重名时**推进一页**，不是弹一张表。两条理由：

1. 上一轮决策五：「动作自己不在这里就地展开 —— 提交要写字、合并要选分支，都是各有导航栏和
   确认键的独立一页」。填一个分支名就是「要写字」，属于同一类。
2. **弹窗会被表挡住。** 失败弹窗挂在面板上（`TerminalGitPanel.swift:35`），而表是盖在面板
   之上的另一层 —— 表开着的时候弹窗在它底下，用户看不到，那正是「点了没反应」。
   推成一页就没有这个问题：弹窗浮在这一页之上。

```
‹ 返回   迁出远端分支                [迁出]

  本地已有 feature-x，它跟踪的是
  origin/other。                     ← 电脑的原话：这一页为什么在问

  另一个本地名                        ← 输入框自己的标签
  ┌──────────────────────────────┐
  │ feature-x-copy               │
  └──────────────────────────────┘
```

- 标题是动作名「迁出远端分支」（与面板那一行同名），不是「迁出 `origin/feature-x`」——
  远端与分支写在正文里，标题留着说这是哪件事。
- 正文分两层，**谁说的要分清**：
  - **电脑的原话**（`message`，不改写、不翻译）—— 它是唯一知道 git 状态的一方，
    这两种情形各有一句（由电脑端拼）：
    - 同名分支跟踪的是别的分支：「本地已有 `feature-x`，它跟踪的是 `origin/other`。」
    - 同名分支没有上游：「本地已有 `feature-x`，它没有上游。」
    - 用户填的名字已经被占：「本地已有 `feature-x`，换一个名字。」
  - **输入框自己的标签**：「另一个本地名」—— 它不是对电脑回答的转述，是这一页在说它要什么。
- 输入框默认**空**，不做任何猜测（猜一个名字然后建错分支，比让用户多打几个字糟）。
- 导航栏右侧「迁出」在名字为空时禁用。**本地名只做「非空」检查**，合法性交给电脑
  `check-ref-format`（`terminal-git-status.ts:137`）—— 与新建分支同一口径，不在手机上复刻一套规则。
- **失败时这一页不关**：走既有的失败弹窗（标题「迁出远端分支失败」+ 电脑原文），
  弹窗关掉之后用户仍在**这一页**，且**刚才打的名字还在** —— 名字存在 flow 上，不在视图的
  临时状态里。于是改一个再试就行；把页面也一起关掉等于让他从头再点一遍，而手机上不能给分支改名。
- 标识符：`git-remote-local-name`（输入框）、`git-remote-local-name-confirm`（导航栏那颗）、
  `git-remote-local-name-cancel`（返回那颗）。
- 用户填的名字**必须是一条新的本地分支**：如果这个本地名已经存在，电脑照样回
  `localBranchName` + 一句说明，用户接着改。规则简单可讲：「迁出会新建一条本地分支；
  本地已有同名分支时，另外起一个名字。」
- 这一页从远端列表页推进来。成功之后 `path` 清空、回到面板根部（与其它动作一致）。

### 4.4 成功与失败的说法

- 新建了本地分支：提示「已迁出 `<限定名>` 到 `<本地名>`」。
- 切到已存在的同名分支：提示「已切换到 `<本地名>`」。
- 解析出来就是当前分支：显示电脑给的那句「已经在 `<本地名>` 上，没有做任何操作。」—— 走成功提示条。
- 失败一律显示**电脑返回的原文**（`TerminalGitFlow.swift:495` 的既有口径），不改写、不吞掉；
  失败框的标题统一是「迁出远端分支失败」（标题是动作名，正文才是原文，与既有的
  「切换分支失败」「新建分支失败」同一形状）。
- 电脑没回答时，**这一条动作**的话要说成可照做的一句（决策见 §5）：
  「电脑端没有回答。如果电脑上的 Synapse 不是最新版，先升级它再试。」

## 5. 平台能力与代价

### 5.1 部署顺序与版本错配

**硬约束：服务端 → 桌面端 → 手机端，一步都不能颠倒**（理由见 §2.5 与
`2026-09-21-mobile-terminal-git.md` 的「升级顺序」一节）。本轮改完 `shared/` 之后要**先把服务端
单独部署一次**，再发电脑端，最后才可能有人装上新的手机包。

顺序颠倒时三种错配各自的症状：

| 组合 | 症状 | 处理 |
|---|---|---|
| 新手机 + **旧服务端** | **终端掉线**，几秒后自动重连（`close(1003)`） | 靠部署顺序避免；这是必须避免的状态，不是可接受的失败 |
| 新手机 + 旧电脑端 | 三个新动作被静默丢弃 → 手机超时 | 按既有先例**接受一次失败**，但话要能照做（见下） |
| 旧手机 + 新服务端 / 新电脑端 | 老手机不发新动作、`MobileGitStatus` 形状一个字不动 → **完全不受影响** | 无需处理 |

超时那句话（`2026-09-17-mobile-claude-code-conversation-design.md:179` 同一条口径）：
不写「电脑一直没有回答。」，写「电脑端没有回答。如果电脑上的 Synapse 不是最新版，先升级它再试。」

`fetchRemotes` 之后要回 `repositoryChanged: true`：fetch 会更新上游引用，从而改变
ahead/behind（`terminal-git-status.ts:66`），面板的「同步」那一行得跟着重算。

### 5.2 上界与截断

- 远端分支列表**在电脑端截到 `MOBILE_FRAME_LIMITS.maxGitBranches`（512）**，按「远端名 + 分支名」
  排序后取前 512 条。截断时用**既有的成功 `message`** 说明（`TerminalGitOutcome` 的
  「成功但有话说」就是这个语义，见 `terminal-git-types.ts:49-55`）：
  「远端分支过多，只列出了前 512 条。」
- 手机端在**加载成功且带 `message`** 时用提示条显示它。不新增线字段。
- 协议校验器同步放开：`isMobileIntentGitResult` 增加 `remoteBranches` 的 `boundedArray` 校验、
  `needsDecision` 增加 `"localBranchName"` 取值，并把那段「三个字段各自独立」的注释改成四个。

### 5.3 权限与审计

- `remoteBranches` → `terminal.state.read`（只读）。
- `fetchRemotes`、`checkoutRemote` → `terminal.git.manage`（写 / 联网）。
- 与 `git-intent.ts:111` 现有的按动作名分鉴权保持一致，不新增权限名。

## 6. 非目标

- **不做「新建分支」的起点支持远端分支。** 重名这件事已被 §4.3 的输入框兜住，
  不需要第二个入口做同一件事。
- **不做远端分支的删除 / 改名 / 上游配置。**
- **不做分支树。** 一律平铺 + 分组 + 搜索。
- **不做远端列表上的「本地已有」标记。**（决策七）
- **不做「获取远程分支」按钮。** 刷新只有下拉一个手势。（决策二）
- **不碰 `app.git.*` 既有 IPC 面**，不碰「代码仓库」注册表，不产生仓库条目。
- **不改桌面端 Git 工作台的行为**，不新增桌面端 UI。
- **不动 `MOBILE_PROTOCOL_VERSION`**。
- **不修 §2.3 那个「新建分支手打同名」的老陷阱。** 本轮只是让迁出这条路显式建上游；
  让新建分支识别出「你打的名字在远端有」需要在电脑端加一次远端查询，是另一件事，另开一轮。

## 7. 已定口径

1. 面板「操作」段新增一行「迁出远端分支」，与提交 / 推送 / 同步 / 合并并列。（决策六）
2. 点开是一张带搜索框的列表，只读电脑缓存的 `refs/remotes`，按远端分组。（决策二）
3. 下拉刷新 = `fetch --all --prune` + 重取列表。（决策二）
4. 点一条远端分支：无同名本地分支就新建同名 tracking 分支并切过去；已有同名且已跟踪该远端就直接切；
   跟踪别的就问一个本地名。（决策三）
5. 要本地名时用输入框，**失败留在原地**让用户改；本地名只做「非空」检查。（§4.3）
6. 脏工作区仍是三选一，**这一次「丢弃改动并迁出」给**。（决策五）
7. 远端分支列表不标「本地已有」，远端分支行不打勾。（决策七）
8. 三个新动作，读与联网分开，鉴权各归各的。（决策一）
9. 列表截到 512 条，截断时说一句。（§5.2）
10. 不动协议版本号；版本错配按既有先例接受一次失败，但把话说成可照做的。（§5.1）
11. **上线顺序：服务端 → 桌面端 → 手机端。** 新手机打旧服务端会让终端掉线，所以这一条不能颠倒。（§5.1）

## 8. 验收基线

### 入口

1. 面板「操作」段有五行，「迁出远端分支」排在「合并分支」下面。
2. 点它进远端分支列表页；导航栏标题「远端分支」，返回能回到面板。
3. 有动作在跑时这一行不可点（与「合并分支」一致）。

### 列表

4. 列表按远端分组，组头是「远端名 · 条数」；组内按名字排序。
5. 列表上方有搜索框，**一进页面就在**（不靠下拉才出现）。
6. 打 `dev` 或 `origin/dev` 都能过滤出 `origin/dev`。
7. 过滤后无结果 → 空态文案，不是空白列表。
8. 一个远端都没有的仓库 → 另一种空态文案。
9. 远端分支数超过 512 时，列表照常显示（**不是错误**），并有一条说明只列出了前 512 条。

### 迁出

10. 干净工作区、本地无同名分支 → 点一条远端分支，直接迁出；面板的分支、远端、同步三行都更新。
11. 迁出后终端里 `git status` / `git branch -vv` 显示：本地分支已建立，**上游正是那条远端分支**。
12. 迁出后工作区内容**与远端那条分支一致**（不是一个从旧 HEAD 起的空分支）。
13. 本地已有同名分支且它跟踪该远端 → 点它**直接切过去**，不新建任何分支。
14. 本地已有同名分支但跟踪别的远端 → **推进一页**「迁出远端分支」，正文是电脑给的原话
    （含那个本地名与它跟踪的对象），输入框是空的且「迁出」不可点。
15. 在那一页填一个**已经存在**的本地名并迁出 → 弹出失败框（标题「迁出远端分支失败」+ 电脑说明）；
    关掉弹窗后**仍在那一页、名字还在**，改一个再点「迁出」能成功。
16. 填一个非法名字（例如 `a b`）→ 同样弹失败框显示电脑原文，页面与名字都留着。
17. 在那一页点返回 → 什么都没发生，分支与工作区都不变。
18. 填一个合法的新名字 → 建成 tracking 分支并切过去，提示里两个名字都在。
19. 点当前分支跟踪的那条远端分支（本地就是当前分支）→ 提示「已经在 `<name>` 上」，**不产生任何 git 操作**，
    工作区不变。

### 脏工作区

20. 有未提交改动时点一条远端分支 → 弹出操作表，**恰好三个选项**：提交并迁出 / 丢弃改动并迁出 / 取消。
21. 选「提交并迁出」→ 进提交页；填信息提交后，**自动完成那次迁出**。
22. 选「丢弃改动并迁出」→ 有二次确认，确认键写「丢弃并迁出」；确认后改动消失、迁出完成、
    **未跟踪的新文件仍在**。
23. 选「取消」→ 分支没变，改动还在。

### 刷新与失败

24. 下拉 → 先跑 fetch 再重取列表；刚在另一台机器上推的分支**出现在列表里**。
25. 下拉时 fetch 失败（例如拔网线）→ 弹出电脑原文，**列表内容保持原样**，不变成空态。
26. 任何失败都在手机上显示电脑返回的**原文**，不改写、不吞掉。
27. 电脑端不是最新版时点「迁出远端分支」→ 超时后那句话说的是「如果电脑上的 Synapse 不是最新版，
    先升级它再试」，不是「电脑一直没有回答。」

### 通用

28. 全程不新增「代码仓库」条目；桌面端 Git 工作台的数据与状态不受影响。
29. 终端里正在跑 Claude Code 全屏界面时，上述操作照常可用，且**终端屏幕内容不被打断、不被写入任何字符**。
30. 三种错配各验一次（见 §5.1 的表）：老手机连新服务端 / 新电脑端**完全不受影响**；
    新手机连老电脑端，这一行超时且给出可照做的那句话，其余动作照常；
    新手机连老服务端是**终端掉线** —— 这一条只作为机制确认（`close(1003)`），实际靠部署顺序不让它发生。
