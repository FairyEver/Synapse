# Snap Skill Hub 首版设计

日期：2026-11-04

状态：设计待用户审阅；方案 A 已选择，尚未授权进入实现。

范围：网页登录后的 Skill 商店、服务端 API、本地 MCP、现有 Skill 安装器的 Hub 来源。

## 1. 目标与确认记录

Snap Skill Hub 只存储和分发 Agent Skill。用户可以让 Codex 等本地 AI 把已制作的 Skill 发布到所属团队的空间，团队成员在网页发现并安装到本机编辑器。Skill 是团队资产，不依赖创建者继续任职或保有账号。

已由用户确认：

- 产品全称为 **Snap Skill Hub**，简称 **Skill Hub**。保留用户给出的名称；不据此更改 Synapse 客户端名称或协议。
- 云端不编辑 Skill 正文、脚本、附件或目录；内容更新必须重新上传整个 Skill。
- 商店图标、显示名称和介绍允许在网页修改，也能通过 API 修改；包内 Skill 名称和介绍只从上传包读取，不在网页编辑。
- 上传接受单 Markdown 文件或 ZIP；本地 MCP 另外接受目录，由客户端处理为上传包。
- 只做团队资产，不做个人私有或公开模式；每个 Skill 必须归属一个团队，仅该团队的正常登录成员可访问。
- 用户没有团队时不能上传；只有一个团队时默认上传到该团队；有多个团队时必须选择目标团队。
- 创建者离开团队或账号停用不影响团队资产保留。管理员可以把维护职责指定给该团队的另一名用户，其他普通成员不自动获得编辑权。
- 成功更新包时自动记录版本；首版只展示、下载和安装最新版，不提供历史版本管理。使用者主动重新安装，不做自动更新或后台版本订阅。
- 删除为软删除，普通用户没有恢复入口，管理员可以恢复；恢复所需数据库记录及文件必须保留。
- AI 操作依赖本地客户端运行并登录。用户选择方案 A：客户端负责检查、整理和打包，通过本地 MCP 调用云端 API。
- Web 端使用 HeroUI，现有左侧导航新增一个 Skill Hub 菜单；内容区采用定制化样式，以美观、成熟的商店式体验为目标。

下文中的接口名称、数量限制及未单独讨论的行为是**本设计的建议**，随本文一起待审；不得描述为用户已经逐项确认。本文批准后再编写实施计划。

## 2. 方案选择

| 方案 | 分工 | 取舍 | 选择 |
| --- | --- | --- | --- |
| A | AI 创作和修正文件；客户端检查、准备包并上传；服务端校验、存储和鉴权 | 本地处理工作更多，但各 AI 共用规则、可复用预检查结果 | 用户已选择 |
| B | AI 自行检查并压缩；客户端接收成品并上传 | 客户端较薄，但易漏附件、错误嵌套目录或带入本机文件 | 不采用 |

网页和本地客户端共用云端业务 API。MCP 是本地能力适配层，不复制服务端业务规则，也不把云端凭据交给 AI。首版不增加独立远程 MCP 或 API Key 接入。

## 3. 首版范围

提供登录后的团队商店列表、搜索、详情、我上传的、上传和上传新版本、编辑展示资料、软删除、最新版包下载和安装到本机。详情提供当前包的只读 `SKILL.md`、文件清单、自动读取的调用名称/介绍和当前版本；没有在线代码编辑器或历史版本列表。管理员提供维护者指派和恢复能力。

不包含个人空间、公开目录、跨团队共享、评分、评论、收藏、付费、推荐算法、榜单、审核发布流程、全员共同编辑、跨团队转移资产、Fork、依赖安装、脚本运行、历史版本选装/删除/回滚、自动更新、桌面商店和 iOS Hub 入口。商店式展示表达图标、名称、介绍和安装关系，不照搬 App Store 的营销板块。

上传即发布，没有草稿条目或另一步上架。包未完整校验和存储成功前，列表中不出现新条目，旧条目的当前版本也不变化。

## 4. 对象、身份与权限

### 4.1 团队归属、创建者和维护者

每个条目保存永久 `skillId`、不可为空的 `teamId`、原创建者、当前维护者、商店资料、当前版本、资料修订号 `revision` 和软删除状态。一个 Skill 只归属一个团队，不设置个人 owner、多团队共同归属或可见范围字段。

`createdBy` 记录首次贡献者，不随维护职责转交而变化；`maintainerUserId` 初始为创建者，后续由管理员指派。原创建者离队、停用或删除账号不能级联删除 Skill、包或版本；引用需要允许身份失效并保留必要的显示名称快照，不能因 User 外键级联毁掉团队资产。

团队归属在首次发布时固定；更新资料、上传新版或重新指派维护者都不能改 `teamId`。首版不做跨团队迁移。不同条目可使用同名，身份只由 ID 决定，不按显示名称或包名自动合并。

### 4.2 上传时选择一个团队

| 当前所属团队数 | 网页和 MCP 行为 |
| --- | --- |
| 0 | 禁止上传、拒绝创建准备来源，提示先由管理员加入团队；不能创建个人条目 |
| 1 | 自动使用唯一团队，显示实际团队名称，不要求重复选择 |
| 多个 | 要求明确选定一个团队；已经在本次操作中明确指定的团队可直接使用，不猜第一个、不按历史上传静默选取 |

团队列表使用实时成员关系，只返回本人所属团队的 ID 和名称。多团队情况下用户说出的明确团队名可由 AI 唯一匹配；重名/歧义或未指定时再询问。浏览列表的“全部团队”不是合法上传目标。

云端创建和临时上传契约的 `teamId` 必填，网页或 MCP 根据上述规则填入；服务端仍独立复验当前成员关系。准备结果、临时上传和发布请求绑定同一个目标团队。中途被移出团队时拒绝发布，不能自动换另一个团队。请求不再接受 `visibility`、`teamIds`、个人 owner 等旧字段。

### 4.3 读取和日常维护权限

| 身份 | 普通 Hub 权限 |
| --- | --- |
| 当前团队正常登录成员 | 查看该团队未删除条目、读当前正文/图标、下载和安装最新版 |
| 当前维护者，且仍是活跃团队成员 | 上述权限，加修改商店资料、完整上传新版和软删除 |
| 原创建者，但已不是维护者 | 只有当前团队普通成员权限；贡献记录不授予额外维护权 |
| 已离开团队或被停用的用户 | 失去后续访问和维护权；资产继续由团队持有 |
| 平台管理员 | 经独立管理端身份查看治理元数据、指派维护者和恢复；不因该身份获得普通 MCP 或包下载权限 |

当前团队没有角色模型，首版的“管理员”建议明确采用既有平台管理员，不新增团队角色、邀请或自行组队能力。指派目标必须是该 Skill 所属团队当前有效成员；指派只改维护职责，不改归属、创建者或包版本。原维护者立即失去写权限，新的维护者可以继续维护其他人创建的资产。

列表、搜索、计数、详情、图标、当前正文、下载和安装准备共用实时团队权限，在数据库分页前过滤。未登录返回 401；无读取权、已删除和不存在统一返回不可用。创建者离职或被禁用不得使其他成员的查询隐藏该 Skill。

成员移除、维护者指派与写入事务必须协调检查，避免权限变化后的旧请求完成覆盖；需要在提交前验证当前维护者及成员资格，不能仅依赖上传开始时的判断。已经下载或安装的副本继续保留，不提供远程撤回或卸载。

### 4.4 两套独立的名称和介绍

| 数据 | 来源和用途 | 是否可在网页/MCP 改资料时编辑 |
| --- | --- | --- |
| 商店显示名称、商店介绍、图标 | 面向人浏览，可以使用中文 | 可以 |
| 包内 `name`、`description` | 从当次完整上传包的 `SKILL.md` 读取，代表实际安装和调用信息 | 只读；只能上传包含改动的新包 |

首次发布可用包内信息预填商店资料；后续上传刷新自动提取的包内信息，不覆盖已维护的商店名称和介绍。安装器必须使用包内名称/介绍，不能把商店名称或介绍写回 Skill 主文件。

新包里的 `name` 可以与旧包不同，Hub 仍按同一个 skillId 记录更新；不要求因此新建条目。名称变化后的重新安装需要处理原目录，见 §7.5，不能靠禁止解析新名称规避。

### 4.5 成员与团队生命周期

创建者离职、维护者停用、团队一时没有可维护成员，都不删除、隐藏或退回个人名下。成员仍可读取正常资产，维护职责显示为需要管理员处理，管理员可随时指派本团队的另一名有效成员。

建议禁止删除含有 Hub 资产（包括软删除资产）的团队，使用明确业务错误及数据库引用约束兜底，避免现有团队删除级联破坏可恢复性。空团队仍按现有流程删除；首版不为此新增跨团队资产转移或团队归档功能。实施时同步调整既有“团队不承载资源”的边界，只扩展 Hub 所需的团队归属关系。

## 5. 包格式与本地准备

### 5.1 输入与标准形式

- 单个 `.md` 文件：必须是带有效 Skill frontmatter 的 Skill 主文件，转换为包根 `SKILL.md`，保留正文和 frontmatter 字节，不将普通文章自动改写为 Skill。
- ZIP：接受根目录含 `SKILL.md`，或仅有一个外包目录且其中含 `SKILL.md` 的形式。只移除这一层外包目录，不递归猜测入口，不接收多个 Skill 的集合。
- 本地目录：必须有根 `SKILL.md`；目录本身不直接成为云端输入，由客户端生成 ZIP。
- 最终包只有一个根 Skill，可包含 `scripts/`、`references/`、`assets/` 等正常附件。云端只存储和读取，不执行其中任何程序。

校验 `SKILL.md` 为有效 UTF-8，frontmatter 至少有非空字符串 `name` 和 `description`，正文非空；`name` 使用项目已有 Skill 命名规则。保留其他合法 frontmatter 字段，Hub 不替作者重写内容。具体 YAML 能力和长度限制以实施时核对的现有解析器为基础，不能静默丢字段。

本设计建议沿用本地安装来源的量级：主文件最多 1 MiB，单附件最多 10 MiB，合计最多 50 MiB，最多 100 个附件，目录深度最多 8；上传压缩文件也最多 50 MiB。ZIP 中目录及被忽略条目同样有独立的计数、解析时间和解压预算，不能只约束最后保留的文件。数量、路径和字节限制放共享契约，UI、MCP、服务端一致。

### 5.2 本地预检查

客户端先确认登录和唯一上传目标团队，再按用户明确提供的来源路径进行有界读取；不扫描主目录寻找 Skill，不修改来源目录。没有团队或多团队尚未选择时不开始读取与准备包：

1. 解析主文件、枚举附件，检查文件类型、路径、大小、重复名称和跨平台兼容性。
2. 沿用现有发布排除规则：不打包 `.env`、`.env.*`（根 `.env.example` 除外）、其它隐藏项、符号链接、`node_modules` 和系统压缩元数据；Synapse 安装身份文件属于排除项。排除目录不递归读取，`.env` 不为预览而读取。
3. 指南要求 AI 检查实际发布内容并移除已知真实凭据；工具不得根据正文中的 token、Authorization、URL 参数模式或 `id_rsa`、`.pem`、`.key` 文件名硬阻断。若复用已有风险提示，只作为不含命中值的非阻断提示，首版不增加独立内容审查器，不复用问题反馈的宽泛脱敏模式作为发布准入。
4. 检查能静态解析的本地 Markdown 链接和资源路径，缺失时报告；不声称能验证脚本中的动态路径或远程依赖。
5. 给出主文件信息、文件清单、总字节、排除项、阻断问题及非阻断提示。AI 根据结果修改本地文件后重新准备。
6. 生成只含最终文件的不可变临时快照和包，计算内容指纹，返回 `preparedSourceId`，不通过 MCP 返回 ZIP/Base64 正文。

仅明确格式、路径和资源预算错误阻断；不以泛化“质量评分”作为发布门槛。客户端不运行 Skill 或安装第三方依赖来证明有效。

准备结果绑定当前账号、认证代次、目标 teamId、MCP 调用者及最终快照，建议 30 分钟过期。发布读取该快照，不重新读取可能已改变的来源目录；修过源文件后必须再次准备。切换账号、退出、重启或过期使句柄失效；成员变化时云端重新拒绝无权目标。临时资产由 DataRepository 管理并后台回收，不裸写业务文件或阻塞窗口启动。

服务端不相信客户端检查结论，重新校验每个上传。直接上传包内出现上述排除的 `.env`、隐藏项或控制文件时拒绝，并报告应在本地移除；除外包目录和系统压缩元数据外不静默丢文件。服务端也不得增加正文凭据模式准入。符号链接、硬链接/特殊文件、加密/多卷归档、路径穿越、绝对路径、重复条目及文件/目录冲突均拒绝；大小写及 Unicode 等价冲突按跨平台规则拒绝，不能在解压后靠覆盖解决。

## 6. 版本机制与并发

### 6.1 三种不同的版本信息

- `versionNumber`：服务端按 Skill 递增的整数，展示为 `v1 / v2 / v3`，不要求作者填写 SemVer。
- `versionId`：不可变云端发布快照标识，用于内部记录、并发检查及安装来源；不因此开放历史版本选择。
- `revision`：条目的并发修订号；包发布、资料修改、维护者指派、删除和恢复都推进它，展示资料及治理变化不增加包版本。

首版仅展示当前版本。后台保留完整发布记录及对象引用，不提供历史版本列表、历史包下载、选装、单独删除或回滚接口；版本机制只支持完整更新和重新安装时识别差异。

服务端以最终文件的相对路径、字节长度和 SHA-256 构造固定排序、无歧义编码的清单，再计算 `contentFingerprint`。外包目录名、ZIP 时间戳、压缩级别、条目顺序不参与；文件名和实际字节参与，不 trim 正文或改写换行。另保存 `archiveSha256` 校验下载包本身，不能混用两种摘要。

与**当前版本**内容相同的上传返回 `unchanged` 和当前版本，不产生新版本，不修改展示资料。重新上传曾经发布过、但不同于当前版本的内容仍创建下一版；不提供从后台历史记录恢复旧版的产品入口，也不能把 `(skillId, contentFingerprint)` 设为所有版本的唯一键。

### 6.2 写入与重试

首次发布要求稳定 `requestId`；上传新版要求 `skillId + expectedVersionId + requestId`；资料更新与删除要求 `expectedRevision + requestId`。新版本不携带资料更新，避免同时改变他人正在编辑的资料；发布事务只更新版本相关字段并推进当前 revision，不覆盖其他资料。

服务端在事务内锁定条目，协调实时团队成员与维护者检查，复验当前未删除状态、校验版本条件、分配编号并写入成功回执。两个更新同一基础版本的调用最多一个成功，另一个明确返回版本冲突。先检查基础版本，再判断 `unchanged`，不利用相同包绕过冲突。管理员指派和恢复同样执行 revision 条件、幂等与审计。

幂等作用域为账号、动作和 requestId；同键同请求返回原结果，同键不同请求拒绝。目标 teamId 和包摘要纳入请求摘要。服务端持久保存写入回执，至少覆盖 24 小时重试窗口；条目/版本保留首次创建请求标识，软删除后仍保留，防止回执清理后重复创建。恢复沿用原 skillId 和当前包，不能把旧删除请求重放成再次删除；幂等键复用仍只返回该次操作的原回执，不重放写入，后续读取重新校验当前状态。回执不保存包正文、介绍、凭据或签名下载地址。

网络中断不代表发布失败；AI 和客户端用同一 requestId 查询/重试，不能换 ID 自动再发。超出可确认窗口时先读取条目状态，不自动发布第二份。对象存储写入失败时不产生可见版本；对象已写入而数据库失败时保留可追踪的暂存对象，进入后台回收。

## 7. 操作链路

### 7.1 AI 首次发布

用户要求发布 → Synapse Skill 路由到 Hub 指南 → 查询登录和本人团队 → 没有团队则停止，唯一团队自动确定，多团队由用户明确选择 → 准备本地来源 → AI 处理阻断问题 → 向已确定团队发布完整包 → 返回 ID、详情链接、版本、内容摘要及实际归属团队。

用户已要求上传且目标团队唯一或已明确选择时，沿用授权直接发布，不强制增加一次确认。多团队不得猜默认值；不能因为本地仍留有某个旧 Skill 的 teamId，就替用户选择另一个条目的上传团队。返回结果和网页完成态应显示归属团队，不能再描述为“上传到我个人名下”。

### 7.2 AI 更新已有 Skill

优先使用用户给出的 Skill ID/详情链接，或可信的本地 Hub 安装来源；只凭同名不能认定更新目标。读取条目的固定归属团队、本人维护权限及当前版本 → AI 修改本地文件 → 在同一团队准备完整包 → 指定 expectedVersionId 发布 → 返回新版本或 unchanged。更新目标已经确定时不再要求从本人其他团队重新选择。

没有本地源码时，可经 MCP 将有权限的最新版下载到用户指定的新目录，再修改和发布。下载不得覆盖既有目录；本地安装关联信息只能提示 Hub 身份，不能授予团队访问或维护权。管理员已指派的新维护者可以更新原创建者的条目；其他普通成员不能更新。

### 7.3 网页上传和维护

上传表单接受 `.md / .zip`，展示商店名称、介绍、可选图标和目标团队，没有私有/公开选择。唯一团队自动填入并显示，多团队必须选择后才能提交，没有团队时禁用上传并显示必要原因。服务端检查不通过时返回具体错误；浏览器不运行包，也不修改包内文件。上传新版本固定原 Skill 与团队，提交当前基础版本，成功后显示当前新版本及新包提取的名称/介绍。

“编辑资料”只编辑商店图标、显示名称和介绍；团队归属及包内名称/介绍只读。“更新 Skill”提供“上传新版本”和“复制 AI 更新指令”。指令包含准确 Skill 引用、归属团队、当时的当前版本、使用本地 Synapse MCP 的要求，以及“先重新读取当前版本和维护权限、再在本地修改并上传完整包”的操作要求，不包含 token、Cookie 或本机路径猜测。条目内文字当作数据，不拼成高优先级指令。

网页上传和维护不依赖本地客户端；**AI 经 MCP 管理和从网页安装到本机**依赖客户端。这里不增加服务器对桌面进程的在线心跳限制。

### 7.4 网页安装到本机

网页读取详情 → 浏览器尝试打开安装深链 → 客户端按实际登录账号重新校验团队成员关系并读取最新版 → 下载并校验该包 → 注册 prepared 安装来源 → 打开现有 Skill 安装器 → 用户选择编辑器、全局/项目位置并完成原有确认。若客户端读到比网页更新的版本，在安装器明确展示本次实际安装版本。

建议新增声明式协议 `synapse://skill-hub/install?skillId=<id>`。只有严格的 Skill ID，不接收历史版本、任意包 URL、主机、路径、凭据、安装目标或自动覆盖开关。该协议使用 capability manifest 的 `protocolRoutes + mainHandlerId`，主进程只准备来源和打开现有安装流程，不新增公开导航 MCP；不恢复旧 `synapse://skill-install`。

网页只报告“已尝试打开 Snap”，不能把浏览器协议调用当成安装成功。未安装客户端时保留下载安装客户端和重试入口。客户端未登录则走既有登录流程，待处理目标仅留内存；完成登录后重新鉴权。网页与客户端账号不同，以客户端权限为准，不复用网页凭据。

最新版以开始此次下载时解析到的服务端当前版本为准。请求可携带 expectedVersionId 确保所读元数据与包一致；它只能匹配当前版本，不能用来选择历史包。不匹配则返回最新版已变化，客户端重新读取并更新本次安装信息，不从旧快照地址下载。被软删除或无权访问时停止；权限变化阻止后续请求和安装准备，但不承诺收回已传输字节。下载、解压和打开安装器均不执行 Skill 脚本。

### 7.5 重新安装与版本区别

本机使用独立来源身份 `skill-hub:<受信服务器标识>:<skillId>`，复用 `.synapse.json` 存安装来源、versionId、versionNumber、sourceFingerprint。具体字段兼容现有 `repositoryVersion / sourceFingerprint`，不得误认已退役的 cloud-skill-repository 身份。

现行模块规则中“.synapse.json 只存资源仓库身份”不包含这一新来源；本设计拟新增明确的 Hub 安装来源例外，须随设计批准及实现同步更新规则。旧 `.synapse.repository.json` 继续只作发布排除，不恢复旧云身份的读写或关联。

只有用户再次进入 Hub 安装链路时，才查询云端最新版并比较该安装位置；不增加全局 Hub 轮询、自动拉包或更新通知。网页不推测本机是否已安装。

| 本机与选定来源 | 安装器行为 |
| --- | --- |
| 没有安装 | 正常安装 |
| 同一 Skill、同一版本 | 显示当前版本，允许重新安装 |
| 同一 Skill、不同版本且内容不同 | 显示“已安装 v2，本次 v4”等信息，用户确认重新安装 |
| 版本不同但内容指纹相同 | 说明内容一致，允许重新安装以更新来源记录，不强称内容有更新 |
| 同名但来源身份不同 | 沿用同名冲突/替换确认，不能视为同一 Skill |
| 缺少或损坏来源元数据 | 标为来源/版本无法确定，不能猜成最新版或自动覆盖 |

第一版只有最新版安装入口。安装前快照是包内容指纹的依据，环境变量替换和安装器生成的身份文件不改变包身份；安装记录不证明本地文件后来没有被修改。覆盖处理和用户确认沿用现有安装器，安装过程继续保持原子写入及恢复约束。

包内 name 变化时，仍按来源身份找到原安装位置。安装器显示原目录和新名称/目标，完成现有冲突及覆盖确认后，先准备并验证新目录，再通过受控备份/切换完成旧目录处理；失败要保留或恢复原安装。不能留下同一个 Skill 的两份有效目录，不能覆盖同名但不同来源的目录，也不能用云端显示名称代替包内调用名称。

## 8. 网页信息组织

用户已明确 Web 端使用 HeroUI、左侧新增一个菜单、内容区定制化且尽量美观。首版视觉方向为清晰、留白充足的应用商店目录，通过真实 Skill 图标、排版、对齐和操作层级形成辨识度。下文为这一要求的具体设计建议；尚未制作网页原型或进行视觉验收。

### 8.1 导航与页面边界

- 在普通用户 Console 左侧导航新增 **Skill Hub**，建议位于“云端数据表”之后。复用现有侧栏的图标、选中态、尺寸、折叠和窄屏导航，不另做导航壳层。
- 建议入口为 `/console/skill-hub`，左侧导航内部 path 为 `/skill-hub`，详情使用其子路径；详情、上传或资料维护期间仍保持 Skill Hub 菜单选中。
- 团队选择与“全部 / 我上传的”筛选放在 Hub 内容区，不增加左侧子菜单。读取可聚合本人所属的全部团队；“我上传的”只按创建者过滤当前有权限的条目，不代表个人资产，也不能找回离队后的团队内容。
- 保留 Console 的登录守卫及登录后返回目标。详情返回列表时恢复原搜索和范围；直接访问详情时提供回到 Hub 的明确入口。

### 8.2 商店目录

- 页首保留 Skill Hub 标题、团队筛选、搜索和“上传 Skill”主操作。唯一团队可以直接展示名称，多团队读取允许“全部团队”；上传时仍须定位到一个具体团队，不把“全部团队”当成默认目标。不增加介绍横幅、统计卡片或装饰性大标题。
- 列表使用为 Skill 定制的图文条目网格：统一尺寸的图标、清晰的商店名称、最多两行商店介绍，归属团队和当前版本作为次要信息，安装操作位置一致。名称链接打开详情，安装按钮是独立控件，避免整项链接内嵌按钮。
- 条目通过间距、对齐和必要的轻分隔组织，不把整页套入大 Card，也不为每个条目堆叠阴影、边框、徽标和背景。Skill 图标承载内容差异，缺图使用统一默认图标，不随机生成装饰色。
- 依据侧栏之外的实际内容宽度，在宽屏采用两至三列图文条目，中等宽度减少列数，窄屏为单列；保证介绍可读、名称可截断且有完整可访问名称，安装按钮不挤压正文。
- 默认最近发布排序；全部团队、单个团队和我上传的复用这一布局，搜索只筛选当前有权限的名称与介绍，不做跨团队公开目录、虚构推荐位、安装量榜单或凑数内容。
- 首次加载用与实际条目结构一致的 Skeleton；搜索无结果、团队尚无 Skill、本人尚无上传分别使用简短状态和必要操作。没有所属团队时显示“加入团队后才能上传 Skill”等必要状态，上传不可用，不提供个人发布兜底。翻页加载保持已显示内容，错误允许原地重试。

### 8.3 Skill 详情与维护

- 详情采用应用商店式产品头部：较大的 Skill 图标、商店名称、商店介绍、归属团队和当前版本，主操作为“安装到 Snap”，包下载及维护动作降低层级；创建者与维护者在必要资料区分开显示。
- 正文区按“说明 / 文件”组织，只读主文件保持适合阅读的行宽，文件清单使用紧凑行式布局。包内调用名称和介绍以只读信息展示，不能与商店资料混为一组可编辑字段；不增加历史版本标签或列表。
- 当前版本号和发布时间作为元信息，下载/安装只有最新版入口。切换区不重复展示标题和介绍，也不把每一块正文再包进嵌套卡片。
- 只有当前有维护权的人显示“编辑资料”“上传新版本”和删除；删除放在次要操作菜单，网页用 HeroUI 确认浮层指明软删除目标。普通用户不提供回收站或恢复按钮，管理员可恢复。MCP 仍按对具体目标的删除授权执行，不额外强制对话确认。
- 上传、图标选择、资料编辑、团队选择和删除确认使用 HeroUI 标准控件与浮层，保留原生焦点、校验、加载、禁用和关闭语义。目标团队不能在上传新版本或资料编辑中切换。表单随内容自然伸缩，窄屏可滚动并完整露出操作区。

### 8.4 HeroUI 与定制范围

Web 固定使用 **HeroUI v3 + 现有 Dashboard 浅色主题与 Inter 字体**。定制的是目录与详情的内容编排、图文比例、网格、留白和响应式结构；按钮、输入、范围切换、菜单、表单与浮层复用 HeroUI，不另造或强行覆盖基础组件。

本次用户对 Hub 内容区定制化的明确要求，是商店目录和详情采用专属编排的依据；这两处不强套事务列表或后台管理表格。Console 导航壳层、通用表单、管理端治理列表及菜单继续遵守 `dashboard/CLAUDE.md` 和 `dashboard/DESIGN.md` 的组件与主题规则。实现时同步明确该局部边界，不扩大到其他页面。

配色、表面、圆角和交互使用已有语义 token 与组件变体，保留清晰的悬停和键盘焦点；不用页面专属字面色、装饰渐变、glow、营销插画或与其他 Console 页面不一致的控件尺寸。动效只服务状态变化，遵守减少动态效果设置；内容默认可见，不依赖入场动画才显示。

Web 继续复用集中 API 客户端和路由守卫。桌面只复用安装器，不新增 Hub System App、默认 Dock 项或桌面商店。普通用户不增加团队管理、成员编辑或全站团队目录。

### 8.5 管理员治理入口

建议在管理端现有团队详情中增加 Skills 资产区，不新增独立管理员左侧菜单。分页展示该团队资产的商店名称、包内调用名称、创建者、维护者、当前版本和删除状态；操作仅为指派维护者、恢复软删除条目。

指派使用该团队现有成员数据，候选限有效成员；恢复前核对条目、团队和当前包仍完整。两个操作均使用现有管理员认证、标准 HeroUI 表单、revision 冲突提示和审计。这里不做管理员在线改包、历史版本管理或读取所有包的后台浏览器。

正文沿用现有安全的只读 Markdown 渲染，不运行原始 HTML/脚本，不因预览自动请求外部图片或执行包内网页。附件首版只提供文件清单与完整包下载，不新增任意附件在线执行或编辑入口。

## 9. MCP 与 API 建议契约

以下为**拟新增**契约，当前仓库并不存在这些工具或路由；实施时按同一语义生成 schema、索引和参考文档。

本地新增 `skill_hub` domain，通过现有仅有的 `search / invoke` 暴露。建议 9 项 capability；MCP 名称由 action 将点转换为下划线生成，例如 `app.skill_hub.package.prepare` 对应 `app_skill_hub_package_prepare`。普通 MCP 不包含管理员恢复或维护者指派。

| capability action | 主要输入 | 作用 |
| --- | --- | --- |
| `app.skill_hub.skill.list` | 可选 teamId、createdByMe、query、cursor、limit | 只在本人当前团队中分页查询；可按创建者过滤 |
| `app.skill_hub.skill.get` | skillId 或详情引用 | 商店资料、包内名称/介绍、归属团队、当前版本及维护权限 |
| `app.skill_hub.team.list` | cursor、limit | 只列本人团队的 ID 和名称，不返回成员信息 |
| `app.skill_hub.package.download` | skillId、destinationDirectory、可选 expectedVersionId | 只导出最新版到新目录，返回本地路径、实际版本和摘要 |
| `app.skill_hub.package.prepare` | sourcePath、可选 teamId | 唯一团队时自动确定，多团队未选时返回需选择；绑定目标后检查、快照和打包 |
| `app.skill_hub.skill.create` | teamId、preparedSourceId、商店资料、requestId | 向准备结果绑定的团队首次发布，上传者成为初始维护者 |
| `app.skill_hub.version.create` | skillId、preparedSourceId、expectedVersionId、requestId | 当前维护者向原团队发布完整新版本 |
| `app.skill_hub.skill.update` | skillId、expectedRevision、requestId、变化的商店资料字段 | 只改图标、显示名称及商店介绍 |
| `app.skill_hub.skill.delete` | skillId、expectedRevision、requestId | 当前维护者软删除条目 |

图标更新输入使用可选本地图片路径，由客户端通过上传通道处理，不能把任意图片 URL 交给服务端抓取。复用项目现有图片解码/尺寸限制，只接收经实际解码确认的 PNG/JPEG/WebP，不保存主动脚本格式；无图标时使用 Hub 默认图标。初始资料 create 和后续 update 均走同一图片规则。

Skill get 默认返回元数据、自动提取的包内名称/介绍及读取定位，不默认夹带完整正文；需要完整源码时使用最新版 package.download，不把 ZIP 或全部附件注入模型。列表/详情 DTO 不包含内部对象 key、COS 凭据、邮箱、认证 token 或团队成员清单；不提供旧版本定位信息。

MCP 不接收 userId、个人 ownerId、visibility、teamIds、token、服务端地址或自定义认证头；teamId 是经校验的目标资源，不代表账号身份。调用开始绑定 AccountService 的 accountScope 和认证代次，所有网络请求及认证刷新使用同一 scope；切换账号取消请求并使准备句柄失效。已发送且可能成功的写请求保留原 requestId，不能自动改用新账号或另一个团队重试。

普通云端建议路由如下，均要求正常用户认证及实时团队资格；浏览器复用 Cookie 会话及同源写保护，桌面复用当前登录 Bearer。普通域不接入匿名、管理员会话或个人 API Key，也不要求用户手动取得 token：

| 路由 | 职责 |
| --- | --- |
| `GET /api/skill-hub/skills` | 本人团队内的列表及搜索 |
| `GET /api/skill-hub/skills/:id` | 商店和包内资料、固定归属、维护权限及当前版本 |
| `GET /api/skill-hub/teams` | 本人可选择的团队 |
| `POST /api/skill-hub/uploads` | 对指定 teamId 接收 Markdown/ZIP 或图标，校验后生成账号/团队绑定 uploadId |
| `POST /api/skill-hub/skills` | 向指定 teamId 使用包 uploadId 与可选图标 uploadId 原子发布 v1 |
| `PATCH /api/skill-hub/skills/:id` | 当前维护者修改商店资料及可选图标引用 |
| `DELETE /api/skill-hub/skills/:id` | 当前维护者软删除整条 Skill |
| `POST /api/skill-hub/skills/:id/versions` | 使用已校验的包 uploadId 发布新版 |
| `GET /api/skill-hub/skills/:id/package` | 鉴权后流式下载最新版，可用 expectedVersionId 保证当前元数据一致 |
| `GET /api/skill-hub/skills/:id/main` | 鉴权后读取最新版的有界只读主文件，同样支持当前版本条件 |
| `GET /api/skill-hub/skills/:id/icon` | 按条目权限读取当前图标 |

独立管理员 API 复用 AdminAuthGuard 及现有可信同源管理会话，不向普通 MCP、preload 或用户 API 开放：

| 路由 | 职责 |
| --- | --- |
| `GET /api/admin/skill-hub/skills` | 按 teamId 和删除状态分页列治理元数据，不返回包正文或下载能力 |
| `POST /api/admin/skill-hub/skills/:id/maintainer` | 指定本团队有效成员为维护者，要求 expectedRevision 和 requestId |
| `POST /api/admin/skill-hub/skills/:id/restore` | 恢复完整的软删除条目，要求 expectedRevision 和 requestId |

管理员读取、指派和恢复均记审计；不因治理入口把其他业务数据或包下载权限扩大给管理员身份。直接改数据库只作为受控运维兜底，产品恢复优先走有校验与审计的接口。

uploadId 只代表当前账号、目标团队、指定用途和已校验内容，建议 24 小时过期，不单独出现在商店；包与图标不能混用，不能跨团队绑定，不以知道 uploadId 代替鉴权。消费/绑定、维护权复验与写入回执同事务完成。上传失败、过期、未绑定或同内容未采用的对象由后台回收；已绑定到软删除资产的文件不属于可回收对象。

分页统一建议 cursor，默认 20、最大 100，固定排序键和 ID 次序；游标绑定筛选、身份及 scope。每个工具按仓库要求声明分页续页字段。删除/撤权后即使旧 cursor 仍有效，也重新过滤权限。

结构化错误至少区分未登录、没有团队、多团队需要选择、团队资格或维护权变化、目标不可用、包无效、来源过期、文件预算超限、资料冲突、包版本冲突、最新版变化、请求键冲突、恢复对象缺失、存储失败及客户端/服务端版本不支持。错误提供下一步操作，不输出原始文件内容、凭据或请求体。

## 10. 数据、存储与删除

逻辑数据包含团队 Skill 条目、内部不可变发布版本、受管对象及写入回执。不需要个人 owner、跨团队授权表或 visibility 枚举。Skill.teamId 必须关联现有 Team，禁止级联删除团队资产；创建者/维护者账号引用的失效与团队归属独立。版本对 `(skillId, versionNumber)` 唯一；条目状态、维护权、当前指针和回执在事务中维护。JSON 清单只包含有界的路径、大小及摘要，不存包字节。

新增专属 `SKILL_HUB_COS_*` 存储域及 `skill-hub/` 对象前缀，包、只读主文件派生对象和 Hub 图标统一归该域；不占 Drive 配额，也不混入 Platform Media。bucket 与旧 `SKILL_REPOSITORY_COS_*` 及其他运行域严格分离，配置校验必须拒绝复用。

保存最终标准包、内部版本清单及只读主文件，不保留在线可变文件树。对象包括 archiveSha256/size、归属团队、用途、状态和引用；包内容摘要由服务端重算。图标替换后，新对象绑定成功才回收不再被任何资产引用的旧对象。

删除只写 `deletedAt / deletedBy` 并推进 revision，普通入口立即不可读取或安装；条目、内部版本、包、主文件、当前图标和引用完整保留。首版不提供用户恢复入口、永久删除或自动到期清除策略，也不把已软删除条目交给孤儿清理。

平台管理员恢复时复验团队存在、当前版本及受管对象完整，再清除删除状态并写审计；沿用原 skillId、teamId 和当前包，不生成新包版本。原维护者若仍有效可继续维护，否则标明待指派并允许管理员另行指派；不能用“恢复”把职责授给已离队用户。对象不完整时明确恢复失败，不能只改数据库标记就声称恢复成功。

后台物理回收仅处理过期未绑定上传、失败暂存对象及真正无引用的替换图标，有界执行并保留失败重试信息。任何已绑定到现存资产（包括软删除资产和内部发布记录）的对象都不属于孤儿；后台历史版本保留，不在首版做清理或管理。

新域上线必须一起支持数据库备份、对象清单、**实际对象字节**复制和恢复验证，覆盖正常资产、软删除资产及内部版本。不能沿用现有“数据库和清单已备份”就宣称 Hub 包可恢复；灾备保留与产品软删除恢复分别定义，不能用备份到期作为自动清除产品资产的依据。不得在本设计任务中配置桶、读生产数据或执行旧域退役脚本。
