# 待办优先级 P0–P3 设计

日期：2026-11-17。

状态：按用户要求实施；涉及 PostgreSQL 枚举数据迁移和旧桌面客户端兼容。

## 目标

把待办优先级从 `high / medium / low` 改为 `p0 / p1 / p2 / p3`，继续保留“未设置”。一次数据迁移把旧数据映射为：

| 旧值 | 新值 |
| --- | --- |
| `high` | `p0` |
| `medium` | `p1` |
| `low` | `p2` |
| `NULL` | `NULL` |

`p3` 是新增档位，不需要从旧数据生成。

## 兼容策略

- 数据库只保存新值 `p0–p3`；迁移随服务端发布执行。
- 旧桌面客户端继续发送 `x-synapse-todo-priority: 1`，服务端接受并映射旧值输入和筛选条件。
- 新桌面客户端同时发送旧优先级请求头和新响应头 `x-synapse-todo-priority-v2: 1`。
- 新响应头返回 `p0–p3`；旧响应头返回 `high / medium / low`，其中 `p3` 对旧客户端显示为 `low`，因为旧协议没有第四档。
- 没有优先级请求头的客户端继续不收到 `priority` 字段。
- 新客户端也接受旧服务端返回的 `high / medium / low`，并在客户端边界映射为 `p0 / p1 / p2`，避免服务端先发布或回滚时解码失败。
- 新客户端写请求的新优先级要求服务端先升级；发布顺序固定为服务端/迁移在前，桌面端在后。

## 数据迁移

新增 Prisma migration，把 PostgreSQL 枚举替换为 `p0 / p1 / p2 / p3`，并在一笔事务中按上表更新全部 `TodoItem.priority`。迁移不删除待办、不改变未设置项，也不修改提醒或版本。

旧客户端的临时幂等回执仍在 24 小时窗口内；服务端响应映射同时兼容回执里可能保存的旧优先级字符串。迁移不尝试改写历史回执。

## 桌面界面

- 优先级文案统一为 `P0 / P1 / P2 / P3`，未设置仍显示“未设置”。
- 快速新建、编辑表单、行内菜单和筛选使用同一组值。
- 默认按截止时间排序不变；按优先级排序时，未完成项依次为 P0、P1、P2、P3、未设置。
- 优先级徽标使用现有 Badge 变体：P0 强调最高、P1 默认、P2 次级、P3 描边，不新增硬编码颜色。

## API 与 AI

- 新 API/MCP 值使用小写 `p0 / p1 / p2 / p3`，用户界面显示大写。
- MCP 描述、系统 Skill 和跨层 schema 同步更新。
- 旧值 `high / medium / low` 仅作为服务端兼容别名，不再作为新客户端或 MCP 的输入枚举。

## 验证

- 纯函数测试旧值别名到新值的映射和排序。
- 服务端测试新值 schema、旧值输入/筛选、旧/新响应头，以及数据库迁移后的 DTO。
- 桌面测试过滤器、快速新建、行菜单、编辑器和旧服务端响应的客户端兼容映射。
- 运行 shared/server/desktop 类型检查、Todos 测试、UI tracking coverage，并执行 Prisma validate/generate。
- 不在本次任务中直接对生产数据库执行迁移；部署时由既有 Prisma migration 流程执行。
