## 1. 要解决什么

手机连着电脑的终端时，用户最常想做的几件事都不在手机上：

- 我现在在哪条分支上？
- 这个目录有多少东西没提交？
- 提交、推送、同步。
- 换一条分支干活，或者把某条分支合进来。

今天这些只能切回电脑去做，而用户人不在电脑前 —— 这正是他用手机连终端的理由。

**这一轮要把这套操作搬进手机端终端页。** 一句话概括交互模型：

> 手机上的那几个按钮，等于替用户在**终端当前所在的那个目录**里敲 git 命令。

只有这一件事。不做 diff 阅读器，不做冲突解决，不做历史浏览，不做文件级暂存。

## 2. 现状（实施前必须核对，不要凭印象）

这一节写的都是**查过代码的事实**，其中三条会直接决定方案形态。它们不是背景介绍，是约束。

### 2.1 手机端终端页长什么样

三条栏：顶栏（返回 / 标题 + 状态行 / ⋯ 菜单）、工具栏（⌘ · 指令横滑区 · ⇧）、输入栏。
面板的既有范式是 `TerminalShortcutPanel`：`.sheet` + 自带 `NavigationStack` + `.insetGrouped` 列表 +
空态用 `ContentUnavailableView` + 反馈用 `Haptics`。**新面板照这一套做，不自创。**

顶栏竖屏的标题块是**两行**：第一行会话名，第二行 `● 状态圆点 · 状态文字 · 版本文本`。
这一轮的入口就落在这第二行上。

### 2.2 「终端当前目录」现在跟不上 `cd`（**决定性**）

终端的实时目录靠 shell 主动上报 OSC 7 序列（`\e]7;file://host/path\a`）。
消费端早就有了 —— `desktop/app-capabilities/terminal/main/emulator.ts:128-146` 注册了 OSC 7 处理器，
`service.ts:3439-3442` 的 `getCurrentWorkingDirectory` 会优先读它。

**但生产端不存在。** Synapse 从来没有让 shell 上报过：

- 环境变量里只设 `TERM=xterm-256color / COLORTERM / TERM_PROGRAM=Synapse / SHELL`，**没有 `VTE_VERSION`**；
- shell 启动参数只有 `["-l"]`，没有 `--init-file`；
- 唯一注入 `ZDOTDIR` 的地方是 Agent 通知的 shim，而它生成的 zsh 启动文件**只做 PATH shim，一行 OSC 7 都没有**。

后果：macOS 默认 zsh 下 `emulator.currentCwd` **恒为 undefined**，
`getCurrentWorkingDirectory` 一直回退到**创建会话那一刻的 cwd**。
用户 `cd` 到哪，电脑是不知道的。

> **这一条推翻了一个想当然的前提。** 「跟着终端目录走」这件事，不是接一根现成的线，是要先把这条线造出来。见决策三。

**这不是本轮才有的窟窿。** `docs/agents/capability-registry.md:67` 已经写着
「Terminal 优先使用 OSC 7 报告的实时目录并回退到会话启动目录」，桌面端 pane 的文件树
（`workspace-tree-ipc.ts:38`）用的就是 `getCurrentWorkingDirectory` ——
也就是说**文件树今天显示的也是会话启动目录，不是用户 `cd` 到的地方**，只是它回退得很自然，没人发现。
这一轮把 OSC 7 补上，两处一起对。

### 2.3 电话端的 Git 能力不缺，但缺用户要的那两块（**决定性**）

`desktop/electron/services/git-client/` 里已经有的：

| 能力 | 位置 |
|---|---|
| 状态快照（分支 / 上游 / 领先落后 / 改动数 / 冲突标记） | `git-status-service.ts:131` |
| 分支列举 / 切换 / 新建 / 远程分支 | `git-branch-service.ts:92,122,158,192,268` |
| 提交 | `git-commit-service.ts:35` |
| fetch / pull / push / sync | `git-sync-service.ts:259,275,297,324` |
| 丢弃改动 | `git-discard-service.ts:88` |
| 冲突文件解析 | `git-status-parser.ts:197-207` |

**没有的（用户点名要的就是这两块）**：

- **任意分支合并。** 唯一的 merge 是 `git merge --ff-only --no-overwrite-ignore @{u}`（`git-sync-service.ts:68-83`），
  目标写死为上游，只为同步服务。**没有**接任意分支的合并，**没有** `merge --abort`。
- **暂存。** 全仓 grep `stash` 零命中。

### 2.4 Git 能力只对「已注册的仓库」开放，而用户不要这条约束（**决定性**）

`git-client` 的领域层不认识 `repositoryId` —— 它的所有方法吃的是 `SynapseGitRepository` 对象（内含 `localPath`）；
`repositoryId` 只活在 IPC 边界与注册表（`<userData>/git-client/repositories.json`）里。
**仓库必须先 `addLocal` 注册**，之后才能拿到 id 调其它接口；没有「按路径解析出仓库」的函数。

产品负责人的口径是：**不区分有没有在 Synapse 里登记过。**

> 用户原话：「这个不区分有没有在 sy 里登记，走的是 git 命令，和 sy 内部的那个 git 应用没关系。」

这条口径有两个层面，**不要混为一谈**：

- **产品层面**：不接注册表、不产生仓库条目、不出现「先添加本地仓库」这一步。终端 cd 到任意 Git 仓库都能干活。
- **代码层面**：`git-client` 的领域方法本来就只吃 `{localPath}`，因此**按路径构造对象、复用它的命令封装与解析器**是允许的，也是应该的 ——
  这不是「和那个 Git 应用有关系」，只是不重复实现一遍 `status --porcelain=v2` 的解析。

### 2.5 手机端与电脑之间的通道

上行只有 `mobile.intent`（`shared/src/mobile-live.ts:774`），现有 19 种 kind，**没有任何 git kind**。
下行有 `mobile.summary / frame / intentResult / transferProgress / presence / toolbar / quickPhrases / clipboard`。

现有的终端动作全部走 intent：手机发 intent，电脑执行，结果经 `mobile.intentResult` 回来。

### 2.6 手机端没有任何 Git 界面

全仓 grep，`SynapseMobile` 里唯一命中 "git" 的是脱敏正则（`DiagnosticRedactor.swift:94`）。
手机端也没有本地化机制，中文字面量直接写在视图里 —— 本轮照做。

## 3. 决策

### 决策一：命令在电脑后台跑，**一个字都不写进终端**

手机点「同步」→ 电脑在终端当前目录直接执行 git → 结果结构化回传手机面板。

**不往 PTY 里打字。** 理由：

1. 终端前台可能正跑着 Claude Code、vim 这类全屏程序。往 PTY 里塞 `git checkout x\n`，
   那行字会被前台应用吃掉或弄乱它的界面 —— 而「刚跟 Agent 聊完就想提交」恰恰是最常见的时序。
2. 结果是文本流，手机推不出「现在在哪个分支」，顶栏那一行就只能靠正则去猜。
3. 不污染用户正在读的那一屏输出。

代价：终端里看不到 git 的原始输出。错误信息改由手机面板展示（电脑返回的原文照搬，不改写）。

### 决策二：按目录跑 git，不经过「代码仓库」注册表

见 §2.4。新建一条只认路径的执行通道。**不调用 `app.git.repositories.add_local`，不产生 `repositories.json` 条目。**

### 决策三：目录跟随 = shell 钩子 + 探测兜底（两条都做）

要让电脑知道用户 `cd` 到哪了：

- **主路：注入 shell 钩子。** 在 Synapse 自己开的终端里挂一段 shell 集成，让 shell 每次画提示符前发一次 OSC 7。
  **只影响 Synapse 开的终端，不碰用户的 `~/.zshrc`** —— 仓库里已有同类做法的先例（Agent 通知的 ZDOTDIR shim）。
  覆盖 zsh / bash / fish。
- **兜底：按需探测。** 在「手机 attach」「打开 Git 面板」「从后台回到前台」这几个时刻，直接去问一次 PTY 子进程的当前目录，
  应付钩子没装上的 shell（自定义 shell、被别的工具占用启动目录的环境等）。

**为什么两条都要**：只有钩子时，遇上不支持的 shell 会**静默失效** ——
顶栏第二行显示的会是一条**错误**的分支名。错误的信息比没有信息更糟。

### 决策四：入口 = 顶栏第二行的常驻显示 + ⋯ 菜单里的 Git

**第二行**（顶栏两行里的第二行）：

| 目录状态 | 第二行 |
|---|---|
| Git 仓库、有改动 | `● main · 3 个改动` |
| Git 仓库、干净但有未推送 | `● main · 领先 2` |
| Git 仓库、干净且已同步 | `● main` |
| Git 仓库、游离 HEAD | `● a1b2c3d（游离）` |
| **不是 Git 仓库** | **保持现状：`● 运行中 · 1.0.16 (13)`** |

- 状态圆点保留，它表示会话状态，与这一轮无关。
- **第二行是只读的，不可点。** 操作全部收在 ⋯ 菜单里（用户明确要求）。
- 版本文本在 Git 目录下让位给分支信息。这是**接受的代价**（版本号是报问题时引用的号，不是抬头要看的东西）；
  非 Git 目录下照旧显示，用户随时可以看到。
- **不显示「落后」**：落后是同步要处理的事，不是抬头要看的告警；放面板里。

**⋯ 菜单**：在既有那些行之间**新增一行「Git」**，排在那几个动作的最前面（全屏 / 重命名 / 复制全部输出 / 停止会话之前）。
点它打开 Git 面板。

**不是 Git 仓库时，「Git」这一行不出现** —— 与「列表为空时入口不出现」同一条口径，不摆一个点开是空的入口。

### 决策五：面板是一张 `List`，每个动作各自 push 到子页

沿用 `TerminalShortcutPanel` 的范式：`.sheet` + `NavigationStack` + `.insetGrouped`。
面板本身只做「看状态」和「选动作」，**不在面板里就地展开表单** —— 提交要写字、合并要选分支，都是有自己的
导航栏和确认键的独立页面。

`presentationDetents([.medium, .large])`，与兄弟面板一致。

### 决策六：手机端不接收文件清单，也不接收 diff

用户口径：**为省流量，手机端不看任何文件列表和具体文件变更。**

- 面板只显示**改动文件的数量**，不显示是哪些文件。
- 提交页只写「全部改动 · 3 个文件」，不列清单、不能挑文件（见决策七）。
- **唯一的例外**：合并冲突时，电脑**直接把一段拼好的冲突说明文本回传**，手机只负责把它放进剪贴板。
  传输的不是文件清单结构，是一段给人看的文字。

### 决策七：提交一律全量，提交后推送是默认关的开关

- 提交 = `git add -A` + commit，**不挑文件**。用户口径：「默认就都是全部，不去挑文件」。
- 提交页有「提交后立即推送」开关，**默认关**。推送是对外动作，不应该在用户没明确要求时发生。
  提交完面板上的推送行会显示「推送 1 个提交」，再点一下就是。

### 决策八：合并两个方向都给；方向二的链路写在脸上

用户在面板上选**方向**，再选**另一条分支**（带搜索框）：

| 方向 | 语义 | 实际链路 |
|---|---|---|
| 把其他分支合并到当前分支 | 合进当前分支，合完停在这里 | 在当前分支上 `merge <选中分支>` |
| 把当前分支合并到其他分支 | 把当前分支的成果并进选中分支 | **切到选中分支 → `merge <原分支>` → 切回原分支** |

**方向二必须离开当前分支**，因为 git 没有「留在原地、把成果合进别的分支」这条原语。
这不是实现偷懒，是 git 本身的形状。**合并页要把这三步写在脸上**，不能让用户以为终端没动过。

无论成功还是失败，方向二都回到原来那条分支。

### 决策九：一旦冲突 —— 自动取消合并、回退、给一段可复制的信息

**手机上解决不了冲突。** 所以冲突不是一条要用户处理的岔路，是一次**自动收尾**：

1. 检测到冲突 → 立刻 `merge --abort`，仓库回到合并前的状态；
2. 弹出一个框，说明发生了什么（把哪条分支合到哪条、哪些文件冲突）；
3. 给一个「复制冲突信息」的按钮，**把一段拼好的文本放进剪贴板**，用户粘给任意一个 Agent 去处理；
4. 手机端**不提供**任何解决冲突、继续合并、标记已解决的入口。

复制出去的文本必须包含：仓库目录、**把哪条分支合并到哪条分支**、已自动取消并回退的说明、
冲突文件清单、以及一句请对方处理的交代。原型里的格式：

```
【Synapse · Git 合并冲突】
仓库目录：/Users/liyang/Documents/code/github/Synapse
操作：把分支 feature/login 合并到 main
结果：检测到冲突，已自动取消合并并回退（git merge --abort），仓库回到了合并前的状态。
冲突文件（3 个）：
- desktop/src/modules/git/components/git-workbench.tsx
- server/src/mobile-live/mobile-push.service.ts
- shared/src/mobile-live.ts

请帮我解决这些冲突。
```

**同步永远不产生冲突**：同步走的是快进式（`--ff-only`），拉不动就整体失败并报「已分叉，请手动处理」。
会冲突的只有「合并分支」这一条路。这一条要写进验收，否则实施者容易给同步也加一套冲突处理。

### 决策十：脏工作区切分支给三个选项，**没有暂存**

有未提交改动时切分支（或新建分支、或合并方向二的第一步切换），先弹出一个操作表：

| 选项 | 行为 |
|---|---|
| **提交并切换** | 打开提交页 → 提交成功 → 自动完成那次切换 |
| **丢弃改动并切换** | 见下，要**二次确认** |
| **取消** | 什么也不做 |

**没有「暂存并切换」。** 初稿提过，产品负责人砍掉了 —— 手机上暂存了却没法恢复，等于把人卡在半路。

**「丢弃改动并切换」只丢弃已跟踪文件的修改，不删除未跟踪的新文件。**
也就是说它走的是 `checkout -f` 的语义，不是 `checkout -f && clean -fd`。
未跟踪文件里可能有用户根本没想提交的东西（草稿、笔记、临时产物），删掉是不可逆的。
二次确认的文案要把这一点说明白。

> 这一条与「工作区脏」的判定有一个已知的松紧差：判定「脏」时未跟踪文件也算（沿用桌面端的口径），
> 但「丢弃」时不动它们。所以可能出现「它说有 3 个文件未提交，我选了丢弃，那 3 个文件还在」的情况。
> **这是有意为之** —— 宁可多问一次，不可多删一个。实施时确认文案讲得通。

### 决策十一：一个 git intent + 一条 gitStatus 下行消息

- **上行**：`mobile.intent` 新增**一个** kind `git`，用 `action` 字段区分读状态 / 列分支 / 切分支 / 新建分支 /
  提交 / 推送 / 同步 / 合并 / 中止合并。**不新增九个 kind。** 理由：它们是同一件事的九个动作，
  共享同一个鉴权、同一个错误面、同一个结果信封；拆开只会让校验分支和 switch 各长出九份重复。
- **下行**：新增一条 `mobile.gitStatus`，把「当前目录 · 分支 · 改动数 · 领先/落后 · 是否冲突」推给手机，
  用于顶栏第二行的常驻显示。**不塞进 `mobile.summary`** —— 那个信封的字节预算已经很紧
  （这是上一轮快捷指令同步踩过的坑）。
- 操作结果走既有通道，不另造一套。

## 4. 交互规格

### 4.1 顶栏第二行

见决策四的表格。字数上限：这一行只有一行的宽度，**任何一项超长都要截断而不是换行**
（换行会多占一行，把终端挤矮），沿用既有 `lineLimit(1)` 的写法。

### 4.2 ⋯ 菜单

新增一行 `Git`，位置在那几个动作的最前面。**不是 Git 仓库时不渲染这一行。**

### 4.3 Git 面板

一张 `List`（`.insetGrouped`），三段：

```
导航栏：  Git                              [完成]

仓库目录
  目录                    /Users/liyang/…/Synapse

当前状态
  分支                    main                 ›
  远端                    origin/main
  同步                    领先 2 个提交       ›
  改动                    3 个文件已更改

操作
  提交                                         ›
  推送                                         ›
  合并分支                                     ›
```

- 「分支」那一行**可点**，右侧有 `›`，点开分支列表。这一行既是状态也是入口
  —— 设置类应用里「带值 + 尖括号」的行就是这个含义。
- 「同步」同样是带当前差异值的可点入口，避免半屏面板中状态行与下方操作重名。
- 「目录」用等宽字体、中间截断。**它是这个功能的信任基础**：用户必须能看到电脑在哪个目录上干活，
  尤其是他刚在终端里 `cd` 过之后。
- 四个动作行的可用态：

| 动作 | 可用条件 | 不可用时 |
|---|---|---|
| 提交 | 有改动 | 右侧写「无改动」 |
| 推送 | 有未推送提交，或没有上游 | 右侧写「无未推送提交」 |
| 同步 | 总是可用 | —— |
| 合并分支 | 总是可用 | —— |

- 没有上游时，「推送」的文案变成「**首次推送**」。
- **不用下拉刷新做主动作**。打开面板只读取本地状态；下拉刷新先获取远端引用，
  再重算状态，以发现其他电脑新推送的提交。获取失败时仍重取本地状态，
  让用户在电脑上 `cd` 到别处后能看到当前目录，并说明远端获取失败。

### 4.4 分支列表

- 导航栏：`‹ 返回` / 标题「分支」 / 右侧 `＋`（新建分支）。
- **搜索框**在导航栏下方（`.searchable`），**用户硬要求**：「只要涉及到选分支的地方，一定要有搜索框」。
- 列表只有一段「本地分支 · N」，每行是分支名，当前分支右侧打勾。
- 点非当前分支 → 干净就切；有改动就走决策十的三个选项。
- 点当前分支 → 提示「已经在这条分支上」，不做任何事。
- 搜不到时是空态（`ContentUnavailableView` 风格），不是空白列表。
- **只列本地分支。** 远端分支另有入口：面板「操作」段的「迁出远端分支」
  （见 `2026-09-22-mobile-remote-branch-checkout-design.md`）。**不要写「远端的新分支由『同步』
  带回来」** —— 同步只跑 `fetch --prune` 加 `merge --ff-only @{u}`，`@{u}` 是当前分支的上游，
  `refs/heads` 一条都不会多，这句话是错的。

### 4.5 新建分支

- 导航栏：`‹ 取消` / 「新建分支」 / 右侧「创建」（**分支名为空时禁用**）。
- 表单两段：分支名输入框；「从哪条分支开始」一行（可点，进分支选择页，**同样带搜索框**）。
- 建完直接切过去。
- **分支名合法性交给电脑校验**，手机端只做「非空」这一条。理由：`check-ref-format` 的规则不适合在手机上复刻一份，
  复刻了就一定会与电脑分叉。

### 4.6 提交

- 导航栏：`‹ 取消` / 「提交」 / 右侧「提交」（**提交信息为空时禁用**）。
- 三段：
  - 「将要提交」：`全部改动 · 3 个文件`（**不列文件**，见决策六）；
  - 「提交信息」：多行输入；
  - 「之后」：「提交后立即推送」开关，默认关。
- 提交成功 → 面板数据刷新、触感反馈、一条提示。若这次提交是「提交并切换」带过来的，**随后自动完成那次切换**。
- 无改动时这一页根本进不去（面板上的入口是禁用的）。

### 4.7 推送与同步

- **推送**：有上游就推；没有上游则「首次推送」，成功后建立远端跟踪。
- **推送被拒**（远端有新提交）：弹框「推送被拒绝」，正文写「远端有你还不知道的提交。先同步，再推送。」，
  并给一个「同步」按钮 —— 不只说不行，还给下一步。
- **同步** = 拉取 + 推送，把本地和远端对齐。没设上游时同步不可用（先首次推送）。
- **同步前有未提交改动**：弹框「同步不了」，正文写「当前目录里有未提交的改动，先提交再同步。」，给「去提交」按钮。
- **同步遇到分叉**（本地和远端各有提交）：不做合并、不做变基，直接报「已分叉，请手动处理」，
  把电脑返回的原文展示出来。手机上不提供解决分叉的入口。

### 4.8 合并

- 导航栏：`‹ 取消` / 「合并分支」 / 右侧「合并」。
- 三段：
  - 「方向」两行（带勾选），第二行下面用次要文字写清它的链路：`先切过去、合并、再切回 main`；
  - 「分支」一行，标签随方向在「来源分支 / 目标分支」之间变（可点，进分支选择页，**带搜索框**）；
  - 「将要执行」一行，把实际会发生的事写成一句话。
- **合并前也走脏工作区检查**（方向二涉及切分支，方向一不涉及；统一都查，行为一致）。
- 冲突 → 决策九的自动收尾。

### 4.9 冲突弹窗

- 标题「合并已取消」。
- 正文说明：把哪条分支合到哪条、已自动取消并回退、仓库回到了合并前的状态。
- 列出冲突文件（这一段是决策六的唯一例外，且**由电脑拼好文字回传**，手机不解析）。
- 主按钮「复制冲突信息」，右上角「好」关闭。
- 面板数据刷新回合并前的状态。

### 4.10 错误与结果反馈

- **成功**：靠面板数据刷新 + `Haptics` + 一条短暂提示（沿用 `model.notice`）。
- **失败**：用系统 `alert`，正文放**电脑返回的原文**，不做改写、不做翻译。标题是动作名（「推送被拒绝」「同步不了」「合并失败」……）。
- **错误必须给出下一步**（能给的都要给）：推送被拒 → 「同步」；同步遇脏 → 「去提交」。

## 5. 平台能力与代价

### 5.1 升级顺序：服务端 → 桌面端 → 手机端

新的 intent kind 与新的下行消息都进共享校验表。**旧服务端遇到新消息类型或新 intent kind 会直接切断整条连接**
（用户可见表现是「设备莫名离线」，日志只有一句校验失败）。
所以：先部署服务端（它打包的是 `shared`），再发桌面端，最后才是手机端。

### 5.2 网关的监听器预算

`mobile-gateway-service.ts` 上有一处注释明确写着监听器数量已顶到 Node 默认上限、这份清单不应再增长。
**实施时必须先核对这一处**，再决定 `mobile.gitStatus` 的下发时机：

- 首选：**搭在已有的 tick 上**（`sync` / `attach` / 摘要刷新），不新增 `terminal.events.on`。
- 顶栏第二行需要跟着 `cd` 变，而目录变化是终端侧的事件 —— 如果确实必须新增监听器，
  要先解决预算问题（而不是把注释删掉）。

### 5.3 权限与审计

手机发起的 Git 写操作会改动用户的仓库，属于敏感操作。**必须经过 `PermissionGuard` 与 `AuditSink`**
（仓库的 Phase 0 硬约束第 10 条），并复用 `intent-executor` 现有的 authorize 调用形态。
读操作（状态、列分支）按既有只读动作的口径处理。

### 5.4 命令安全

- 一律用 **argv 数组**执行，不拼 shell 字符串。
- 分支名等用户可影响的参数，在电脑侧用 `git check-ref-format` 校验后再使用（沿用 `git-branch-service.ts` 已有的做法）。
- 设 `GIT_TERMINAL_PROMPT=0` 之类的非交互环境，**避免命令在无 tty 时挂住**；挂住的命令在手机上的表现是「点了没反应」。
- 所有 git 调用要带**超时**（同步类操作天然慢，超时值参考既有的 120s）。

### 5.5 不新增的东西

- 不新增 MCP capability / tool、不注册 System App / Dock / Workflow Node / Automation Action / Deep Link。
- 不新增存储、不产生任何持久化文件（除了 shell 钩子那一份生成物）。
- 不新增「代码仓库」条目（决策二）。

## 6. 非目标

- **不做文件列表与 diff。** 手机端不接收、不渲染。（决策六）
- **不做冲突解决。** 不提供标记已解决、继续合并、放弃合并的按钮 —— 冲突一律自动中止，走复制粘贴。
- **不做暂存。** 没有 stash、没有 stash 列表、没有「暂存并切换」。（决策十）
- **不做文件级暂存 / 取消暂存 / 部分提交。** 一律全量。
- **不做历史提交浏览、不做 blame、不做撤销上一次操作、不做变基、不做 cherry-pick。**
- ~~**不做远程分支检出。** 分支列表只列本地分支。~~
  **这一条已被 `2026-09-22-mobile-remote-branch-checkout-design.md` 推翻**：那一轮加了
  「迁出远端分支」。本地分支列表本身仍然只列本地分支 —— 远端另有一页。
- **不给推送加强制选项。** 没有 `--force`、没有 `--force-with-lease`。
- **不在手机上新建 / 编辑 / 删除远端。** 远端配置归电脑。
- **不做桌面端的 Git 面板。** 桌面有真终端和 Git 工作台，本轮只做手机端。
- **不改桌面端 Git 工作台的行为。** 两条通道各走各的，共享的只有底层的解析器。
- **不碰 `app.git.*` 既有 IPC 面。** 不新增、不改签名。
- **不做 iPad 专门适配。** 沿用既有口径。

## 7. 已定口径

1. 命令在电脑后台跑，不写终端。（决策一）
2. 按目录跑 git，不经过「代码仓库」注册表，不产生仓库条目。（决策二）
3. 目录跟随靠 shell 钩子 + 探测兜底，两条都做。（决策三）
4. 顶栏第二行显示分支与改动数，只读；非 Git 目录保持现状。（决策四）
5. 操作收在 ⋯ 菜单的「Git」里；非 Git 目录时不出现这一行。（决策四）
6. 手机端不传文件清单与 diff，冲突信息是唯一例外且由电脑拼好文本。（决策六）
7. 提交全量、不挑文件；提交后推送是默认关的开关。（决策七）
8. 合并两个方向都给；方向二必然离开当前分支，链路写在脸上。（决策八）
9. 冲突 = 自动取消合并并回退 + 复制信息，手机不解决冲突。（决策九）
10. 脏工作区切分支给三个选项，没有暂存；丢弃不删未跟踪文件。（决策十）
11. 一个 `git` intent + 一条 `mobile.gitStatus` 下行消息。（决策十一）
12. 凡涉及选分支的地方都有搜索框。（用户硬要求）

## 8. 验收基线

### 目录跟随

1. 在手机连着的终端里 `cd` 到一个 Git 仓库 → 顶栏第二行在**几秒内**变成 `● <分支名> · <N> 个改动`。
2. 再 `cd` 到另一个仓库 → 第二行跟着变。
3. `cd` 到一个不是 Git 仓库的目录 → 第二行回到 `● 运行中 · <版本号>`。
4. `cd` 到 `~/` 这类非仓库目录 → 同上，不显示上一次的分支名（**不能残留旧值**）。
5. 换一个不受支持的 shell 起终端 → 靠探测兜底仍然能拿到正确目录，第二行不显示错误分支。

### 入口与面板

6. ⋯ 菜单里有「Git」一行，且在动作组的最前面。
7. 非 Git 目录时，⋯ 菜单里**没有**「Git」这一行。
8. 点「Git」弹出面板，第一段就是当前目录的完整路径。
9. 面板显示的目录与终端里 `cd` 到的目录一致（`cd` 完立刻打开面板即可验证）。
10. 有改动时「提交」可点；干净时不可点且右侧写「无改动」。
11. 干净且已同步时「推送」不可点且右侧写「无未推送提交」。
12. 没有上游时「推送」显示为「首次推送」且**可点**。

### 分支

13. 点「分支」那一行进入分支列表，当前分支右侧有勾。
14. 列表上方有搜索框；输入能过滤；过滤后无结果时有空态文案而不是空白。
15. 干净状态下点另一条分支 → 直接切换，面板与第二行都更新。
16. 有未提交改动时点另一条分支 → 弹出操作表，**恰好三个选项**：提交并切换 / 丢弃改动并切换 / 取消。
17. 选「取消」→ 分支没变，改动还在。
18. 选「提交并切换」→ 进提交页；填信息提交后，**自动切到目标分支**。
19. 选「丢弃改动并切换」→ 有二次确认；确认后改动消失、分支切过去、**未跟踪的新文件仍在**。
20. 新建分支：分支名为空时「创建」不可点；填好后创建并直接切过去；新分支没有上游。
21. 新建分支能选起点，起点选择页同样有搜索框。
22. 点当前所在的分支 → 给出「已经在这条分支上」的提示，不产生任何 git 操作。

### 提交 / 推送 / 同步

23. 提交页只显示改动**数量**，不显示任何文件名。
24. 提交信息为空时「提交」不可点。
25. 「提交后立即推送」默认关；开着时提交完直接推送，关着时提交完变成「推送 1 个提交」。
26. 没有上游时推送 → 成功后第二行与面板都显示已同步。
27. 远端有新提交时推送 → 弹「推送被拒绝」，且弹框里有「同步」按钮。
28. 有未提交改动时同步 → 弹「同步不了」，且弹框里有「去提交」按钮。
29. 同步遇到分叉 → 报「已分叉，请手动处理」，**不产生合并提交、不改动工作区**。

### 合并

30. 合并页两个方向都在，选方向时「来源/目标分支」的标签跟着变。
31. 选「把当前分支合并到其他分支」时，页面上写明了「切过去 → 合并 → 切回」这条链路。
32. 全部选分支的页面都有搜索框。
33. 无冲突的合并 → 成功，面板与第二行都更新；方向二结束后**回到原来那条分支**。
34. **冲突时**：不弹「要不要解决」之类的岔路，而是**自动中止并回退**，然后弹出「合并已取消」；
   仓库状态与合并前**逐项一致**（分支、改动数、领先落后都不变）。
35. 冲突弹窗里的「复制冲突信息」把文本放进剪贴板，文本包含：仓库目录、来源分支、目标分支、
   已回退的说明、冲突文件清单。
36. **同步产生冲突的路径不存在** —— 同步失败时不会出现「合并已取消」这个弹窗。

### 通用

37. 终端里正在跑 Claude Code 全屏界面时，上述所有操作照常可用，且**终端屏幕内容不被打断、不被写入任何字符**。
38. 任何失败都在手机上显示电脑返回的**原文**，不改写、不吞掉。
39. 所有操作不影响桌面端 Git 工作台的数据与状态；「代码仓库」列表**不新增任何条目**。
40. 手机端全程不接收 diff 或文件清单（抓包或日志核对）。
