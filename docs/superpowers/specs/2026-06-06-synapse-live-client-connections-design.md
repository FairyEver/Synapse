# Synapse Live Client Connections Design

Date: 2026-06-06
Scope: `server/`, `dashboard/`, `desktop/`

## Goal

Build Synapse Live, the first real-time connection layer between logged-in desktop clients and the Synapse server.

This phase must support:

- Desktop clients connect to the server through WebSocket after account login.
- One account can be online from multiple desktop devices at the same time.
- Each desktop installation has a stable client instance identity.
- Administrators can see every user's connected desktop clients.
- Normal users can see only their own connected desktop clients in the dashboard.
- Desktop users can see the current desktop client's server connection state in system settings.
- Clients automatically reconnect after network or server interruption without creating aggressive reconnect storms.

## Product Decisions

- Product name: **Synapse Live**.
- Backend route names use `live`, not `presence`.
- Desktop clients connect only after a normal user account is authenticated.
- Unauthenticated desktop clients do not open anonymous WebSocket connections.
- The server is expected to remain single-instance. Do not add Redis, shared pub/sub, or multi-instance state coordination in this design.
- Online state is runtime state. The server process memory is the source of truth for current online clients.
- HTTP snapshot APIs are kept for first load and degraded reads.
- Dashboard pages subscribe to a read-only live stream for status updates.
- The dashboard live stream is server-to-browser only. Dashboard pages do not need a bidirectional WebSocket in this phase.

## Identity Model

Synapse Live has three identity levels:

```text
userId -> clientInstanceId -> connectionId
```

### userId

The normal Synapse account identity. It comes from the existing user auth system.

Rules:

- One user can have multiple desktop client instances online simultaneously.
- Administrators can view clients across all users.
- Normal users can view only clients where `userId` is their own account id.

### clientInstanceId

A stable desktop installation identity.

Rules:

- Generated by the desktop app when needed.
- Stored locally in the desktop app's encrypted account or local state storage.
- Logging out closes the Live connection but does not delete `clientInstanceId`.
- Clearing app data or reinstalling can create a new `clientInstanceId`.
- Multiple `clientInstanceId` values for the same account can be online at the same time.
- If the same `clientInstanceId` opens a new connection, the server keeps the latest connection and closes or supersedes the old one.

### connectionId

A per-WebSocket-connection identity generated by the server.

Rules:

- Changes on every reconnect.
- Used only for runtime routing and diagnostics.
- Not shown as a primary product identity.

## Client Status Model

The server tracks client instances with this conceptual shape:

```ts
type LiveClientInstance = {
  userId: string
  clientInstanceId: string
  connectionId: string | null
  status: "online" | "stale" | "offline"
  appVersion: string
  platform: string
  deviceName: string
  connectedAt: string | null
  lastSeenAt: string | null
  disconnectedAt?: string
  disconnectReason?: string
}
```

Status meanings:

- `online`: WebSocket is connected and heartbeat is healthy.
- `stale`: WebSocket or heartbeat is suspicious, but the timeout grace window has not fully elapsed.
- `offline`: No active connection is available for that client instance.

The registry may retain recent offline records in memory so UI can show last online information, but current online truth comes only from active runtime connections.

## Backend Architecture

Add a `LiveModule` under the NestJS server package.

Main units:

- `LiveDesktopGateway`: owns `/api/live/desktop` WebSocket upgrade and desktop protocol handling.
- `LiveClientRegistry`: in-memory registry for connected client instances.
- `LiveClientQueryService`: returns admin and user-scoped snapshots from the registry.
- `LiveStreamService`: broadcasts status changes to dashboard read-only streams.
- `LiveController`: exposes HTTP snapshot and stream endpoints.

The registry should remain internally well-bounded so a future implementation could change storage, but this design does not introduce Redis or a multi-instance abstraction layer.

## WebSocket Protocol

Endpoint:

```text
GET /api/live/desktop
```

Authentication:

- Requires normal user bearer access token.
- Reuses `UserAuthService.verifyAccessToken()`.
- Admin dashboard cookies are not accepted for desktop Live connections.
- Invalid or expired credentials reject the upgrade or close the socket with a controlled auth failure.

Handshake flow:

1. Desktop opens WebSocket with bearer access token.
2. Desktop sends `hello` with client instance metadata.
3. Server verifies metadata, registers the client instance, and returns `welcome`.
4. Desktop sends periodic `ping`.
5. Server updates `lastSeenAt` and returns `pong`.

Client hello:

```ts
type LiveDesktopHello = {
  type: "hello"
  clientInstanceId: string
  appVersion: string
  platform: string
  deviceName: string
}
```

Server welcome:

```ts
type LiveDesktopWelcome = {
  type: "welcome"
  connectionId: string
  serverTime: string
  heartbeatIntervalMs: number
  heartbeatTimeoutMs: number
}
```

Heartbeat:

```ts
type LiveDesktopPing = {
  type: "ping"
  sentAt: string
}

type LiveDesktopPong = {
  type: "pong"
  serverTime: string
}
```

Future desktop downlink messages can reuse this WebSocket, but this phase only implements connection state.

## Reconnect Strategy

Desktop reconnect behavior:

- Reconnect only while the desktop account is authenticated.
- Do not reconnect while logged out.
- On transient network, socket, or server failures, use exponential backoff plus random jitter.
- Start near 2 seconds.
- Increase gradually to 30 seconds.
- After long failures, cap around 2 minutes.
- Add 0-30% random jitter to prevent synchronized reconnects.
- On 401 or 403, refresh the user token before reconnecting.
- If token refresh fails, stop reconnecting and move the account/Live state to unauthenticated or unavailable.
- On app quit or logout, close the socket intentionally.

The reconnect algorithm belongs in the Electron main process Live service, not in React components.

## Server Cleanup And State Changes

State transitions:

- Successful hello: client becomes `online`.
- Normal WebSocket close: client becomes `offline`.
- Unexpected close: client becomes `offline`, with the reason retained when safe.
- Missed heartbeat: client becomes `stale`.
- Heartbeat timeout after grace window: client becomes `offline`.
- Same `clientInstanceId` reconnects: old connection is superseded, new connection becomes the active one.

Every meaningful transition emits a Live status event to dashboard streams.

Sensitive data must not be logged:

- Access tokens.
- Authorization headers.
- Cookies.
- Raw WebSocket close payloads if they can include secrets.

## HTTP And Stream APIs

Admin APIs:

```text
GET /api/admin/live-clients
GET /api/admin/users/:id/live-clients
GET /api/admin/live/stream
```

Rules:

- Guarded by `AdminAuthGuard`.
- Admin snapshot endpoints can return all clients or a single user's client instances.
- Admin stream broadcasts all Live client status changes.

Dashboard user APIs:

```text
GET /api/dashboard/live-clients
GET /api/dashboard/live/stream
```

Rules:

- Guarded by the existing dashboard user session boundary.
- Return or stream only the authenticated user's client instances.

Desktop diagnostic HTTP API is out of scope for this phase. The desktop system settings display local Live state from Electron IPC instead of asking the server for its own view.

DTOs for snapshots and stream events must be shared or derived from the same mapper so HTTP and stream UI see the same status shape.

## Dashboard UX

Use the existing dashboard stack:

- `dashboard/src/lib/api.ts` owns Live API calls and response types.
- Server-side table pages continue using `ServerDataTable`.
- Existing shadcn/ui primitives and restrained Tailwind utilities are used.
- Do not add custom colors, inline styles, gradients, or a new visual system.

Administrator surface:

- User management gains a `客户端` column.
- The column shows a compact aggregate such as `2 台在线` or `离线`.
- A user action opens a client detail sheet or dialog.
- Detail rows show device name, platform, app version, status, connected time, and last heartbeat.
- Do not add a standalone top-level Live dashboard page in this phase.

Normal user surface:

- Settings gains a client section for the current user's desktop client instances.
- It shows all desktop clients under that account, not just the current browser session.
- It does not expose other users or admin-only diagnostics.

UI text should remain short:

- `在线`
- `离线`
- `连接异常`
- `最后心跳`
- `版本`
- `平台`

## Desktop UX

Live connection belongs in the Electron main process.

Main process responsibilities:

- Generate and store `clientInstanceId`.
- Observe authenticated account state from `AccountService`.
- Connect to `/api/live/desktop` after login or successful refresh.
- Refresh tokens and reconnect when auth expires.
- Maintain local Live connection state.
- Emit state changes through EventBus and IPC.

Renderer responsibilities:

- Read Live status through preload IPC.
- Display the current desktop client's server connection in the account/settings area.
- Never hold or transmit raw tokens directly for Live.

Desktop system settings states:

- `已连接`
- `重连中`
- `未连接`
- `未登录`

The settings view should show only the current desktop client instance state and the most recent safe error summary.

## Implementation Boundaries

- Do not introduce Redis, Socket.IO, or a second realtime framework unless a later requirement needs it.
- Use the `ws` protocol/library family for desktop/server WebSocket protocol compatibility. The desktop package already depends on `ws`; the server package may add the matching dependency during implementation.
- Do not store current online state as database truth.
- Do not revive old license, activation, device, or lease concepts. In this design, device names are display metadata for client instances, not a durable authorization model.
- Do not put WebSocket logic in React components.
- Do not expose raw Electron or IPC primitives to renderer.
- Do not add broad dashboard tokens to local storage; dashboard auth remains HttpOnly cookie based.
- Do not add implementation explanations or marketing copy to UI.

## Testing Strategy

Backend tests:

- Reject desktop WebSocket connections without valid user access tokens.
- Accept valid user access tokens and register `clientInstanceId`.
- Allow one user to have multiple client instances online.
- Supersede an old connection when the same `clientInstanceId` reconnects.
- Mark clients stale/offline on missed heartbeat.
- Admin snapshot returns all client instances.
- User snapshot returns only the current user's client instances.
- Stream events are scoped correctly for admin and normal users.

Desktop tests:

- Login or refresh success starts Live connection.
- Logout closes Live connection.
- Token auth failure attempts refresh before reconnect.
- Refresh failure stops reconnect attempts.
- Reconnect delay respects backoff cap and jitter.
- Renderer receives connection state through IPC.

Dashboard tests:

- User table shows client aggregate status.
- Client detail sheet renders device rows without extra explanatory copy.
- Normal user settings shows only that user's client instances.
- Loading, empty, and error states stay short and actionable.

Verification commands should be scoped to touched packages during implementation:

```text
pnpm --filter @synapse/server run test
pnpm --filter @synapse/server run typecheck
pnpm --filter @synapse/dashboard run tsc
pnpm --filter @synapse/dashboard run build
pnpm --filter @synapse/desktop run typecheck
pnpm --filter @synapse/desktop run test
```

Do not start local dev servers or browser previews unless explicitly requested.

## Acceptance Criteria

- A logged-in desktop client establishes a WebSocket connection to Synapse Live.
- A logged-out desktop client does not connect.
- One account can have multiple desktop clients online at once.
- The same desktop client instance cannot appear as multiple active online instances after reconnect.
- The desktop client reconnects after interruption with bounded, jittered backoff.
- Admin dashboard can see all users' connected desktop clients.
- Normal user dashboard can see only the current user's connected desktop clients.
- Desktop settings show the current desktop client's server connection state.
- WebSocket auth and logs do not leak tokens, cookies, Authorization headers, or secrets.
