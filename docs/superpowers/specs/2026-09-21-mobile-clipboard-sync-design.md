# 手机端剪切板同步

> 配套文档（都在 `~/Desktop/剪切板同步/`）：`原型.html`（可点）、`实施计划.md`（分阶段与改动面）、`提示词.md`（交给实施会话的入口）
> 一句话：电脑上复制一段文本，手机上就能取到。

---

## 1. 为什么要做

手机的输入能力弱，电脑强，这件事本身没法解决。但用户真正需要的那段字——一条命令、一段需求描述、一个报错——**常常已经在电脑的剪切板里了**。现在的路只有两条：发一条微信给自己，或者在手机上重打一遍。

Synapse 手机端已经把电脑的终端输出、Agent 会话、快捷短语都搬过来了，唯独剪切板没有路。这个功能就是把这条路修上。

## 3. 这一版推翻的三条旧结论

**推翻一：入口放「终端页底部工具条」。**
起草时先画的是终端底部工具条加一枚按钮，与键盘、短语、文件同级。被否，理由是剪切板**跟随电脑**——没有选定电脑就没有剪切板可看。底部工具条在终端内部，天然预设了「已经进了某台电脑的会话」，把一个属于电脑的能力挂在了属于终端的界面上。

**推翻二：做「填入终端输入框」。**
一度打算让点行直接把内容填进终端输入框，省掉「复制 → 关面板 → 点粘贴」两步。被否：行只做一件事，就是复制到手机剪切板。多一个动作就多一个要解释的东西，而系统粘贴本来就人人会用。

**推翻三：电脑一条历史都不留。**
最初定的是「历史只活在手机本地，电脑侧不留」，理由是避开 ADR 0211，代价是「电脑没连上时复制的东西手机拿不到，事后也补不回来」。随后用户提出「选定电脑后才请求**这台电脑**的剪切板历史」——电脑一条不留的话，这句话实际只能拿到当前那一条，切到一台没跟这台手机连过的电脑会看到空列表。改为电脑内存留 20 条。

## 4. 决策

### 决策一：只做电脑 → 手机，只做文本
反向（手机复制同步回电脑）不做。图片、文件不做——往 `UIPasteboard` 写图片是另一套东西，而剪切板能力本身已有 1 MiB 的文本上限可依。

### 决策二：剪切板跟随电脑，不是全局能力
一个账号可能同时登录多台电脑。剪切板必须在**选定一台确定的电脑之后**才请求，且列表按电脑分桶——A 电脑复制的东西不会出现在 B 电脑的面板里。

### 决策三：两个入口，一份数据
- **入口 A**：会话列表页的设备行行尾，一枚剪切板图标。
- **入口 B**：终端内快捷面板最左侧的新分段。

两者读同一个底层 store。入口不同只是「你从哪里想起来这件事」不同，不是两份数据。

### 决策四：保留量 —— 手机每台 50 条，电脑内存 20 条
- 手机本地**每台电脑**留最近 50 条，断连、杀 App、重启后都还在，离线时可看可复制。
- 电脑侧**只在内存里**留最近 20 条，不落盘，进程退出即消。它的唯一用途是回答「这台电脑最近的剪切板」——刚连上、刚切过去、手机重装过 App 时，靠它把列表立刻填上。
- 不落盘正是为了满足 ADR 0211：剪切板正文不得进持久化快照。

### 决策五：敏感内容在电脑侧就丢弃
macOS 上密码管理器复制内容时会打 concealed 标记。电脑侧识别到这个标记就不采集、不上传、不进列表。手机上完全无感——没有「这条被过滤了」的提示，也没有开关。判断依据在电脑侧，因为那是内容离开信任边界之前唯一的位置。

### 决策六：不给开关
不做「暂停同步」。能同步的前提是手机已经连上了这台电脑，这本身就是一次显式动作。多一个开关就多一个要维护、要解释、会被忘记的状态。

### 决策七：单条 128KB、快照 192KB
超过 128KB 的单条文本不同步。剪切板能力本身允许 1 MiB，但走 WS 帧不值得为超长文本破例。快照按「最新优先累加」装，装到 192 KiB 为止，装不下的条目这一轮不带——手机本地本来就存着它自己见过的那些，快照只用来补缺。

（快照预算从最初写的 256 KiB 降到 192 KiB，是实施时发现的：套接字的 `maxPayload` 正好是 256 KiB，一个 256 KiB 的载荷加上信封就超了。摘要那份也刻意压在 248 KiB，同一个理由。）

### 决策八：行只做一件事，详情照抄「快捷输入」段
点行 = 复制到手机剪切板（该行显示「已复制」+ 底部提示，面板不关，方便连着挑几条）。行尾眼睛 = 看全文，复用 `PhrasePreviewSheet` 的形态：从贴合内容的高度起，可上拉，正文可选中。**全文弹窗里不放「复制」按钮**——背后那行已经管这事了，这是「快捷输入」段已经写下的哲学，此处照抄。

## 5. 交互规格

### 5.1 入口 A：会话列表页的设备行

设备行现在画的是：`● 电脑名 ⌄ ⋯ 在线`。行尾加一枚剪切板图标。

两个必须处理的既有事实：

1. **多电脑时整行是 `Menu`**（点它切电脑）。图标必须自己接到手势——改法是把 `Menu` 的包裹范围收窄到左边的「绿点 + 名字 + 切换箭头」，让图标和状态标签留在 `Menu` 外面。
2. **没有电脑时不画设备行**（`SessionListView.swift:21-26` 的既有决定：同一屏里同一句话出现两次会像坏了）。图标跟着设备行一起消失，不需要额外判断。

点击 → 底部升起剪切板面板。

### 5.2 入口 B：终端里的快捷面板

`ShortcutPanelSegment` 在最左侧新增一个 case，顺序为 `剪切板 / 自定义命令 / 快捷输入`。

面板的既有形态一律不动：`presentationDetents([.medium, .large])`、拖条、`systemGroupedBackground` 底色、分段器与卡片左右对齐。

**一处必须改的规则**：分段器现在只在电脑答过 `mobile.quickPhrases` 时才画（`phrases == nil` 就永远只画第一段）。加了剪切板段之后这条站不住了——一台没配快捷短语的电脑会让整个分段器消失，连剪切板段也一起没了。**实施时的落法**：分段器改成总是画，但画哪几段由电脑答过什么决定（剪切板段与命令段恒在，短语段只在电脑答过时出现）。这样「这台电脑没有」和「这台电脑从没被问过」仍然是两个可分辨的答案：后者连可点的段都没有。记忆的分段（`@AppStorage("terminal.shortcutPanel.segment")`）允许记到剪切板段上；记忆值指向一个当前不存在的段时退回第一个。

### 5.3 列表

一行一条：正文两行截断 + 行尾相对时间（`刚刚 / 2 分钟前 / 今天 14:32`）+ 行尾眼睛。

- 点行 → `UIPasteboard.general.string = text` → `Haptics.success()` → **该行的时间位改成「已复制」**，同时底部浮出一条「已复制」。**面板不关**，接着点第二条是常态。
- 行上那两个字留到读者复制下一条、或离开面板为止，不是定时淡出。它是读者自己「刚拿的是这条」的记录，在还在挑的时候比一闪而过有用，顺带让已经拿过的那行不会被误当成没点过。
- 点眼睛 → 全文弹窗。正文可选中。
- 面板右上角「清空」→ iOS 确认弹窗 → 清掉**当前这台电脑**那一桶，电脑不受影响。列表为空时「清空」置灰而不是隐藏（沿用 `MeetingDetailView` 的既有做法）。
- 重复内容不新增条目：同一段文字再复制一次，把已有那条提到最前并刷新时间。这条规则同时解决了「重新连上时电脑补推当前剪切板」造成的重复。

**电脑推来的快照是「归并」进本地的，不是「替换」。** 这一条必须写死，否则会出一个很隐蔽的 bug：电脑内存里只有 20 条，手机本地有 50 条，整包替换会让手机那份凭空缩到 20。正确的规则是——快照里的条目按 id 并入本地那一桶，逐条去重、按时间倒序、封顶 50；快照里没有的旧条目继续留着。

**清空要记住「清掉了哪几条」。** 没有这一步的话，清空之后电脑下一次推快照（它内存里还留着那 20 条）会把刚清掉的内容原样顶回来。

**不能用挂钟做这件事。** 起草时写的是「记下此刻，之后只接收不早于它的条目」——那是拿手机的钟和电脑写下的时间戳比较：**两台机器的钟一歪，电脑新复制的条目会被判成「早于清空那一刻」而静默丢掉**。实施时改成按「被清掉的那批 (id, 时刻)」精确识别：电脑重发的是同一对，所以拦住；同一段文字重新复制是新时刻，所以放行。两侧的时钟都不参与。这个 bug 是手机端的单测逼出来的，测试里那批夹具的时间戳恰好落在未来，一下就把挂钟方案的洞露了出来。

### 5.4 什么时候请求

| 时机 | 动作 |
|---|---|
| 平时 | 电脑随复制随推增量，手机 append 到当前那台电脑的桶 |
| 打开面板 | 向当前选定的电脑请求一次快照（补齐离线期间漏掉的） |
| 切换电脑 | 换到那台电脑的桶，并向它请求一次快照 |
| 没有选定电脑 / 那台离线 | **不发请求**，只显示手机上已有的那份，面板挂一条「电脑未连接」 |

离线时列表照常可看可复制——这是「手机本地留 50 条」的意义所在。

### 5.5 状态与异常

| 状态 | 表现 |
|---|---|
| 这台电脑还没同步过任何东西 | 空态一行字，不画图标、不画插图 |
| 电脑未连接 | 面板顶部一条横幅「电脑未连接」，列表照常显示本地那份 |
| 复制成功 | 该行时间位显示「已复制」（留到复制下一条或离开面板）+ 底部一条「已复制」（1 秒后自己消失） |
| 单条超 128KB | 不同步，手机上不出现（**不提示**：这是一条防超长的闸，不是用户操作的结果） |
| 内容只有空白 | 不同步。它在列表里就是一行空白、看起来像坏了；协议那端的校验器也会先 trim 再判空，判据只放在电脑侧一处，两端才只有一个口径 |
| 电脑端内容是敏感的（concealed） | 同上，不同步、不提示 |
| 手机本地这一桶被清空 | 回到空态；电脑侧不受影响 |

## 6. 平台能力与代价

### 6.1 Electron 没有剪切板变更事件

Chromium 的 `clipboard` 模块不提供 change 事件，也没有 `NSPasteboard.changeCount` 那样的廉价探针（已核对 `desktop/node_modules/electron/electron.d.ts` 的 `Clipboard` 接口：有 `availableFormats / has / readBuffer / readText`，没有 `changeCount`）。检测只能靠**定时 `readText()` + 指纹比对**。

由此的代价，要写清楚：**监听必须一直跑**（只在有手机连着时才跑的话，刚连上时电脑的内存里一条历史都没有，「补 20 条」这个承诺就不成立）。轮询间隔定 1 秒，比对用内容哈希。典型文本的单次读取是微秒级；极端情况下（用户复制了一段几十 MB 的文本）会每秒读一次那个大字符串，直到剪切板被换成别的东西——这是这条路的固有代价，接受，不为此增加复杂度。

### 6.2 concealed 标记：探针已跑，结论与最初设想不同

**检测必须用 `clipboard.readBuffer(uti)`，不能用 `availableFormats()` 或 `has()`。** 2026-09-21 在 macOS 26 / Electron 41.2.1 上实测：

| 读法 | 对 `org.nspasteboard.ConcealedType` 的结果 |
|---|---|
| `availableFormats()` | 只返回 `["text/plain"]`——Chromium 把它转成自己的格式词汇表，**自定义 UTI 根本不列出** |
| `has(uti)` | `false` |
| `read(uti)` | `""` |
| **`readBuffer(uti)`** | **`Buffer(1)`——通的**，格式名被原样透传给 `NSPasteboard` |

所以判断条件是 `readBuffer(...).length > 0`，两个名字都要查（`org.nspasteboard.ConcealedType` 和 Qt 系看到过的 `application/x-nspasteboard-concealed-type`），顺带也可以查 `org.nspasteboard.TransientType`。**不需要打包任何原生助手。**

**做这个探针有两个坑，都会给出假的「做不到」：**

1. **不能拿 `availableFormats()` 当判据。** 它对自定义类型一律说谎，用它测会得出「Electron 看不见 concealed」这个错误结论。
2. **探针必须跑在标记还在的时间窗内。** 这台开发机上装了 PastePal，它会在**约 1 秒内**改写剪切板并抹掉 concealed 标记（实测 changeCount +1、typeCount 3→2）。Electron 冷启动要一两秒，等它起来再读，标记早就没了——第一次探针就是这么得出假阴性的。正确做法是让 Electron 常驻，用信号触发出读取，把读取压进那个窗口里。

**剪切板管理器可能让过滤失效（真实风险，不是理论）。** 上一条实测到的那件事本身就是产品风险：macOS 上有其它剪切板管理器在跑时，它们可能自行改写剪切板，把 concealed 标记抹掉。抹掉之后**任何**检测手段都看不见了——不是我们读得不对，是标记真的不在。

影响范围：装了这类工具的用户，密码有几率被同步到手机上。本设计不为此加复杂度（不可能枚举并适配所有管理器），但要知道这条边界存在，并且轮询间隔因此不宜再拉长——**间隔越长，落在「标记已被抹掉」之后才读到的概率越高**。1 秒是这个理由下的取值，不是随手定的。

### 6.3 云端只转发、不落库

云端的既有口径是「刻意保持薄」：终端输出从不存储，摘要只在内存里留 200 条。剪切板正文比终端输出更敏感，沿用同一条：云端只做白名单转发，不缓存、不落库。

### 6.4 协议镜像要手抄

`shared/` 是真源，Swift 侧 `LiveProtocol.swift` 是手抄镜像。新消息类型要在两边同时加，并且要记得先 `build` shared——它是**编译产物**，桌面主进程懒加载 `dist/`，不 build 就会两端行为不一致。手机侧还有一处容易漏：`RealtimeClient.swift` 的 `knownMessageTypes`，不加进去整条消息会被静默丢弃。

### 6.5 设备行的 `Menu` 手势要收窄

见 5.1。这不是「加个 Button」就完事的改动，动的是 `deviceSection` 的结构，改完要确认「切电脑」这个既有能力没被削弱——包括它存在的那个理由：手机停在一台已经走掉的电脑上时，另一台电脑是唯一的出路。

### 6.6 手机端：第一个「持久化的用户数据」，登出必须清

手机端此前所有按电脑归属的东西都是**单槽 + 归属过滤**：`TerminalToolbarState` / `TerminalQuickPhrasesState` 各持一份 + 一个 `ownerDesktopClientInstanceId`，读的时候对不上就当作没有，切换电脑不需要清任何东西。剪切板**不能**照抄这个形状——它要按电脑分桶，而且要在离线时还能翻。

更要紧的是清理责任。`SynapseAppModel.signOut()`（`SynapseAppModel.swift:439-490`）是本仓库唯一的「清空一切账号相关本地态」的收口，`MeetingAudioCache.clearAll()` 是它的先例。剪切板是本机持久化数据里第一个「内容属于账号、文件落在机器上」的东西——**不清就会让下一个登录的账号看到上一个账号的剪切板内容**。桶的 key 用 `clientInstanceId` 是安全的（它不跨账号复用，`ViewedDesktopPreference.forget()` 的注释已经写明这条），但整体仍必须在登出时清空。

### 6.7 剪切板段不能被 `isRunning` 门控

面板里 `isRunning` 从 `TerminalScreen` 一路传进来，命令段用它 `.disabled(!isRunning)`。剪切板段的三个动作——复制到手机剪切板、看全文、清空——**没有一个需要终端在跑**：它们要么只碰手机本地，要么只碰电脑的剪切板。整段跟着 `isRunning` 置灰，等于把手机本地的功能误绑到电脑上那个终端进程的状态上。

### 6.8 空态与「电脑没说过」要分开

短语段用一个三值语义：`nil`（电脑从没发过这条消息）/ `[]`（电脑发过，说没有）/ 有内容。剪切板段**不需要**这个三分——数据是手机本地攒的，电脑从不回「我没有剪切板」这种话。「这台电脑没有记录」就是一个空态，画一行字，和「自定义命令」段的空态同族。

### 6.9 ADR 0211 的确切范围：它管的是快照，不是内存

核对过了，那条 ADR 的约束对象是 **Workflow Engine 的剪贴板读取节点在持久化运行快照里的写法**（省略 `output`），并明确要求不能因此清空实时预览或 Engine 数据流。它**没有**说「桌面端内存里不许留剪贴板内容」，也没有禁止把内容送到同一个用户自己的手机上。

所以本设计的「内存 20 条、完全不落盘」是**满足**它的：没有写快照这个动作，那条规则就没有适用对象。反过来，如果为了做这 20 条而落盘（建一个 `app.clipboard.*` 的 namespace），才正好落进它想避免的那一类，需要另外找依据。同族的既有取向也一致——`docs/adr/0072` 把终端正文排除在普通备份之外。

### 6.10 采集不逐次审计，推送不经过 PermissionGuard

两件事要分开看，因为它们容易被一句「敏感操作要过 PermissionGuard 和 AuditSink」一起盖住：

- **手机主动要求桌面做的动作**才走 `mobile-gateway/controller.ts` 那套授权。本功能里手机**不要求**桌面做任何事——它只是收。所以没有授权调用点，也不需要往那三张策略表里加东西。
- **采集侧**（每秒读一次剪贴板）不能照抄 `ClipboardService.read()`：那条路每次都授权 + 记审计，1 秒一条会把审计日志写成一条没有信息量的洪流。本设计的取法是采集走底层读取、逐次不审计，只在服务启停各记一条。

这是本设计里唯一一处绕开 `ClipboardService.read()` 的剪贴板读取，理由写在这里备查。

### 6.11 一个「有没有手机在看」的信号都不存在

桌面端没有任何办法知道「有没有手机正在看这台电脑」：`mobile.summary` / `toolbar` / 快照类消息全是**广播 + 客户端按 `desktopClientInstanceId` 过滤**，桌面只在自己收到 `mobile.intent` 时才知道某台手机存在（那些状态还都是私有的，没有查询出口）。

好消息是本设计不需要这个信号：推送走到 socket 时，没有连着的手机就是一个静默丢弃，天然是空操作。**所以监听不必因为「没人在看」而停**——这也正好是 6.1 里「监听必须一直跑」所需要的。

## 7. 非目标

- 不做手机 → 电脑的反向同步。
- 不做图片、文件、富文本，只做纯文本。
- 不做剪切板内容的「发送到会话」「填入输入框」等二次动作。
- 不做电脑端的界面：剪切板同步不开设置页、不做开关、不做状态展示。
- 不做跨电脑的合并列表。
- 不做内容的编辑、收藏、置顶。

---

## 8. 已定口径

- 方向：电脑 → 手机，单向。内容：纯文本。
- 归属性：跟随电脑，选定一台才请求。
- 入口：会话列表页设备行 + 终端快捷面板最左分段。
- 行行为：点行 = 复制；行尾眼睛 = 看全文。不做「填入输入框」。
- 保留：手机每台 50 条；电脑内存 20 条，不落盘。
- 敏感内容：电脑侧按 concealed 标记丢弃，无开关、无提示。
- 上限：单条 128KB，快照 192KB。
- 轮询：1 秒，内容哈希比对。

---

## 9. 验收基线

1. 电脑上 `Cmd+C` 复制一段文本，1–2 秒内出现在手机面板顶部。
2. 手机点那一条 → 提示「已复制」→ 切到别的 App 长按，粘贴出来的就是那段文字。
3. 手机断网一段时间，期间电脑复制了若干条；手机恢复后打开面板，能看到期间复制的内容。
4. 电脑退出重开，手机上原本的 50 条仍在（本地）；电脑重新连上后，它内存里那 20 条回到面板。
5. 两台电脑：切到 A 看到的列表不含 B 复制的内容，反之亦然。
6. 从密码管理器复制一个密码，手机上完全不出现。
7. 复制一段超过 128KB 的文本，手机上不出现，且不影响后续正常同步。
8. 同一段文字连按两次 `Cmd+C`，手机上只有一条，且它被提到最前。
9. 手机没连电脑时打开面板：列表可看可复制，并显示「电脑未连接」。
10. 「清空」后手机那一桶为空、回到空态；电脑的剪切板与内存历史都不受影响。
