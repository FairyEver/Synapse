# 自动化新站内信与新邮件触发器

日期：2026-11-05。状态：用户已确认设计，进入实施计划阶段；不代表已经实现。

## 意图与范围

为已有 Automation 增加两个事件触发器：「收到新的站内信」「收到新的邮件」。收到后做什么由用户配置，沿用现有执行器和一个触发器对应一个执行器的模型。

### 用户已确认

- 默认任意新信触发，不增加发件人、主题、正文、附件等筛选。
- 外部邮件支持选择邮箱账号。
- 电脑休眠、应用退出或断网期间收到的新信，恢复后补触发；只处理自动化启用后收到的信件。
- 同一封信不能重复触发。
- 两个触发器都提供正文变量。外部邮件在执行前按需读取正文，不自动标记已读。
- 采用「实时接收 + 补查」，补触发和去重状态持久保存，同一自动化的信件排队执行。
- 首次启用和重新启用时必须联网确认接收起点；无法确认就保持未启用，不排队等待联网后自动启用。启用成功后的断网、退出和休眠不结束监听时间段，恢复后补触发。

### 非目标

- 不增加执行器、邮件内容分析或自动回复逻辑。
- 不增加多触发器、额外筛选、附件内容下载、手机外部邮箱或云端 Automation 执行。
- 不改变现有 Cron、Interval、Webhook 的投递、补跑或重试语义。
- 不新增依赖，不启动应用、浏览器、开发服务器，不进行部署或生产数据库迁移。

## 方案比较

| 方案 | 收益 | 代价 | 决定 |
| --- | --- | --- | --- |
| 实时接收 + 补查 | 复用接收链路，在线及时触发；启动、唤醒、重连后补偿遗漏 | 需要持久订阅、待处理记录、去重和补查进度 | 用户选择 |
| 定期轮询 | 在线和离线恢复共用查询流程 | 固定触发延迟，持续轮询开销 | 不采用 |

只监听实时事件不能覆盖离线信件，因此不能单独满足本次要求。

## 当前实现与需要补齐的部分

- 触发器包位于 `desktop/automation-trigger-packages/`，当前有 Cron、Interval、Webhook；共享 manifest、schema、main runtime、renderer 配置相互分离。
- `AutomationService.acceptEvent` 已支持事件匹配和同一自动化串行执行，但 `eventRunChains` 仅存在内存中，不能用它承担跨重启补触发。
- 运行记录当前每条自动化只保留最近 100 条，不能把运行历史作为永久去重账本。
- `core.mail` 按 SY 用户隔离账号和数据；收件箱增量已有通知去重及历史 UID baseline，但这是通知语义，不能直接作为自动化启用时间或补查边界。
- 外部邮件初始索引和 UIDVALIDITY 变化会重新建立 baseline；自动化必须单独查询启用时间后的实际收件记录，不能只接 `InboxDelta` 而漏掉初次同步或离线期间的新信。
- 站内信实时链路通过账号通知变化提供提示；正文和实际收件事实来自站内信 API。实时提示、已读状态和通知是否显示都不能作为是否收到了新信的权威依据。
- 站内信列表已有有界分页、稳定的 `(sentAt, id)` 排序；详情读取与设为已读是不同操作。当前 `MailRecipient` 没有独立投递时间，收件时间使用发送事务中的 `MailMessage.sentAt`。

## 触发器配置

新增包 ID 拟定为 `builtin.mail-internal-received` 与 `builtin.mail-received`，通过现有 Trigger Registry 注册，不在 Automation Core 内增加类型分支枚举。

- 「收到新的站内信」配置为空对象，监听绑定 SY 身份收到的所有站内信，包括 To、Cc、回复、转发和平台公告；不监听已发送箱。
- 「收到新的邮件」配置为 `{ accountId?: string }`。缺省是「全部邮箱账号」，也可选择一个指定账号；不增加多选配置。只监听账号映射的收件箱，不监听发件箱、草稿箱或回收站。
- 全部账号包括后续新增的本机邮箱账号。新增账号只有联网确认起点后才加入监听；确认失败显示该来源待接入，不影响原有账号，也不自动补收确认前的历史信件。
- 指定账号被暂停或认证失败时保留进度，恢复后补收；被移除后显示账号不可用，不回退为全部账号或其他账号。
- 不依赖邮箱通知开关、系统通知权限、通知是否被读取或删除。
- 沿用当前页面内编辑与变量展开方式；站内信不增加配置项，外部邮件仅增加账号选择。

## 启用与身份边界

启用前联网确认起点及以下具体生命周期规则均已随本文获得用户确认：

- 启用采用「联网确认来源起点 → 原子保存起点与启用状态 → 启动监听和补查」。站内信验证服务端当前身份和权威接收边界；外部邮件验证所选账号的真实收件连接及权威收件边界，不能只检查本机有无缓存。
- 初次启用「全部邮箱账号」时，必须至少有一个已配置账号，且当时纳入的每个账号都能确认起点；否则保持未启用并指出不可用账号，不悄悄排除。指定账号暂停、认证失败或无法连接时同样不能启用。
- 起点确认与本机保存之间收到的新信由首次补查接住。来源边界必须能区分边界附近的历史与新信，不能仅用请求往返时间推测；若无法可靠确认则失败，不能带时间误差强行启用。
- 联网确认失败、身份变化、超时或持久化失败都不提交启用状态、不启动接收；仅保存为停用状态不开始监听。失败后需要用户再次执行启用，不在联网恢复时自动完成旧请求。
- 启用状态及其起点必须一致持久化，不能在重启时重置。进程若在保存成功、启动监听前退出，下次启动按该起点正常补查；未提交成功的准备记录不形成有效时间段。
- 每次由停用转为启用建立新的有效时间段。停用期间收到的信件不补触发，之前有效时间段内已接收但未开始执行的待处理记录保留，重新启用后继续处理。
- 停用不自动中止已经开始的执行，沿用现有停止操作；后台不能启动下一封。
- 修改名称或执行器不重置去重或起点，排队信件在执行前使用最新有效配置；修改已启用任务的邮箱选择或触发器类型，必须先联网确认新来源起点，成功后原子切换订阅。失败保留原配置和订阅；成功后旧订阅尚未开始的记录标记为配置变化而跳过，新订阅从确认的起点开始。
- 每条订阅绑定创建它的服务端身份（包含服务端来源和用户 ID），不把自动化中的本机邮箱账号 ID 当作跨用户授权。切换用户、退出登录立即取消接收、补查和正文读取；新用户不能接管旧订阅。原身份重新登录后恢复其有效时间段的补查。
- 「同一封信」以来源可证明的收件身份为准：站内信为绑定用户收到的 message ID；外部邮件为绑定用户、邮箱账号及其稳定原始收件 locator。同一邮件分别投递到两个邮箱是两份收件副本。
- 去重按自动化 ID 和收件身份分别计算，不同自动化可以独立处理同一封信；重新启用不清空已处理身份。
- 一条自动化只在所在电脑执行；不承诺不同电脑或克隆配置间全局去重。

## 接收与补查

主进程提供独立的邮件触发协调服务，经 ServiceRegistry 注入 Automation、账号服务和邮箱服务的窄接口；通过 EventBus 或明确 service 回调接收提示。接收事件只用于促使查询，不直接授权或执行邮件内容。

1. 启用时先联网确认来源起点，再一致持久记录启用状态、订阅起点、绑定身份与邮箱范围；失败保持未启用。
2. 在线收到站内信变化或外部邮箱增量后，协调服务读取权威收件记录，验证身份、来源、时间段和去重键。
3. 待处理信件先持久入队，再推进对应的补查游标；写入失败不推进游标。
4. 每条自动化同一时间只处理一封，多封新信不会因上一封仍在执行而被 overlap skip 丢弃。手动运行占用执行槽时，邮件继续等待。
5. 实际执行前重新校验身份、启用状态、配置版本、源信可访问性并读取变量所需正文，然后交给原有 Automation 执行通道。
6. 启动、唤醒、账号重连和邮箱同步完成后恢复有界补查；再以低频补查弥补丢失的实时提示。默认兜底间隔 60 秒，由 `desktop/config.ts` 集中声明，不增加用户配置。

补查遍历全部有效启用时间段，范围为开始包含、结束不包含；持续启用且应用退出不结束时间段。先按接收时间、再按稳定身份处理；不承诺跨邮箱服务器的全局精确到达顺序。

### 站内信

- 查询当前用户的可见收件副本，不能从通知列表推断。先评估已有分页能否在有界扫描中完成；必要时给站内信核心服务增加内部增量查询，不另建公共 MCP 工具。
- 使用服务端 `sentAt` 与服务端确认的稳定收件边界判定范围，不使用通知提示时间、正文日期或未经校准的本机时钟。若现有接口不能给出可靠边界，补充经过本人鉴权的内部起点确认接口，与增量查询使用同一套边界契约。未联网确认时保持未启用，没有离线启用或等待联网自动启用状态。
- 分页中途断网或退出保存进度，重试允许覆盖已扫描边界，通过持久去重处理同时间多封、实时事件与补查并发。不得只查第一页或推进到未扫描区间。
- 用户已删除或已失去访问权的信件不绕过权限恢复正文；已入队的记录给出不可访问结果，未发现即被删除的信件无法补回。

### 外部邮件

- 仍通过 `core.mail` 的受控同步、元数据查询和正文服务，不直接访问 IMAP 凭据或扫描共享本机数据库。
- 收信时间使用服务器 INTERNALDATE 对应的 `receivedAt`，不使用发件人可伪造的 Date，也不用本机首次索引时间替代。
- 起点确认同时记录该账号收件箱世代与稳定 UID 边界，避免只比较本机时钟；世代稳定时，启用前已存在的 UID 不能因头部时间异常变成新信。实施者须将起点、时间和世代的联合判断落实为可验证的内部契约，不能沿用原生通知的历史 baseline 代替。
- 若覆盖范围尚未完成，继续有界同步并保留待补查状态，不能把只索引到的第一页视为已补完。
- 收件时间未知的记录不猜测、也不直接触发，保持可诊断的待核验状态；后续补齐时间后再判定。
- 移动、重建索引、UIDVALIDITY 或 IMAP 端点变化不能仅凭同 UID 或 Message-ID 重用身份。已有服务能证明是同一封时复用去重；不能证明的历史候选不自动重新投递，保留身份待核验诊断。该异常下不承诺无遗漏；不得以重放全部信件掩盖身份不确定。

## 持久队列、去重与失败

以下规则已随本文获得用户确认：

- 订阅、分源补查进度、待处理记录和去重凭据通过 DataRepository 存储，使用 schemaVersion 与声明式索引，不裸写文件或业务 SQL。
- 状态至少区分待准备、准备中、可执行、已提交执行、已完成，以及确定失败/结果不明；具体存储枚举交由实施者按既有状态模型收敛。
- 每条记录使用确定性去重 ID；并发实时接收与补查通过 CAS/原子批次保证只入队一次。处理进度与入队提交必须具备可恢复的一致性，不能用先更新内存再写盘承担保证。
- 待处理记录只保存信件引用、来源身份、收件时间及状态；不保存完整正文。运行日志裁剪、应用重启、通知删除或关闭均不清除去重凭据。
- 正文尚未取得时，临时网络失败保留待准备，使用有上限的退避重试；此时执行器尚未调用，不算重复触发。永久不可访问或正文超过既有读取上限则记录明确失败，不把空正文或被截断的内容当完整正文执行。
- 永久准备失败或提交后结果不明的失败记录，同步计入任务累计次数并更新最近状态；重复补查或细化已有失败原因不重复累计。
- 执行器调用前持久写入提交标记并绑定稳定 run ID；只有成功取得提交权的 worker 才能进入执行。与运行记录创建必须原子关联，或通过持久提交标记设计可证明的恢复协议。
- 执行器已开始后，失败、超时、取消或进程崩溃都不自动重新调用。崩溃后无法确认结果的记录显示结果不明，保留信件定位与运行关联，不自动重放。
- 通用执行器可能已经执行了外部副作用，无法同时承诺「崩溃任意时刻不漏执行」和「绝不重复」。本方案优先不自动重复；因此提交标记写入后、执行器调用前崩溃，可能留下未实际执行但不自动补跑的记录。
- 本次不新增逐信手动重放入口。现有运行记录页的「重试」是重新加载历史，不是重试执行，不能误用。无原信上下文的手动运行不能冒充一次真实收信，应提示需要信件上下文；结果不明记录保留原信定位，供用户核查实际执行结果。
- 删除自动化后停止监听和后续执行，并按现有删除生命周期处理其运行数据和本机队列；不能触碰实际邮件或站内信。

存储必须声明 `transferPolicy: local-only`，不进入云备份或导出。导入/恢复带有新邮件触发器的配置时必须停用，不能继承原机器启用时间或自动重播历史；同机还原配置不能清空已有去重状态。

## 信件变量

沿用既有 `{{trigger.xxx}}` 语法、manifest 变量发现和白名单字段替换，不在执行器界面增加特殊配置。下列为拟定变量契约，字段在执行器调用前准备完整。

### 共用变量

| 模板 | 值 |
| --- | --- |
| `{{trigger.payload.messageId}}` | 当前来源的信件 ID |
| `{{trigger.payload.subject}}` | 主题，可为空 |
| `{{trigger.payload.body}}` | 正文；站内信保留原正文文本格式，外部邮件为纯文本正文 |
| `{{trigger.payload.sender}}` | 可显示的发件人；站内信使用既有用户/系统发件人快照，外部邮件为姓名与地址 |
| `{{trigger.payload.to}}` | 格式化收件人文本，遵守来源的地址可见性 |
| `{{trigger.payload.cc}}` | 格式化抄送人文本，无抄送为空字符串 |
| `{{trigger.payload.receivedAt}}` | 来源收件时间，ISO UTC；与本机发现时间分开 |
| `{{trigger.payload.attachmentCount}}` | 附件数量，数字字符串 |
| `{{trigger.payload.attachments}}` | 可访问附件元数据的 JSON 文本，含名称、大小、MIME；不含附件字节、本地路径或存储密钥 |
| `{{trigger.payload.url}}` | 既有 `synapse://mail-internal/<id>` 或 `synapse://mail/em_<uuid>` 定位链接 |

外部邮件另提供 `accountId`、`accountName`、`accountAddress`（同为 `trigger.payload.*`）。沿用通用触发时间、自动化 ID/名称等变量。`trigger.receivedAt` 表示本机事件接收时间，不能覆盖信件自身的 `trigger.payload.receivedAt`。

站内信不将登录邮箱猜作联系邮箱，不展开仅显示组织名或「所有用户」的隐藏实际收件名单。空正文是合法值，读取失败不能伪装为空正文。附件元数据不可确认时同样给出准备错误，不能把未知当作零附件。

### 正文读取

- 站内信复用详情读取，保留服务端返回的 body，不额外调用设为已读。引用快照不自动拼入 body，也不附带不可见的往来内容。
- 外部邮件复用 message/get、正文资源及分块读取服务；正文按需获取而不提前为队列批量下载。
- 纯文本部分优先；只有 HTML 时复用现有不执行脚本、不加载远程资源的文本提取能力。不暴露原始 HTML 作为本次正文变量。
- 正文消费沿用现有 5 MiB 上限及分块契约；读取到 `truncated` 或未完成状态不能交给执行器冒充全文。模板构造与事件 payload 限制也必须适配这一上限，超限显式失败，不静默裁剪正文或变量。
- 不自动标记已读、不下载附件文件、不加载远程图片、不运行邮件脚本；读取和实际执行继续经过原有权限与审计。

## 安全与运行边界

- 邮件和站内信正文均为外部不可信数据；事件保留来源标记，正文作为执行器的用户数据传入，不提升为系统指令，也不让正文授予执行权限。不假设现有模板替换会自动提供 MCP 的 `externalData` 包装或防止提示注入；既有权限检查不能省略。
- 不改变既有模板对命令、脚本、HTTP 等字段的显式文本替换规则，也不声称自动进行 shell/URL/JSON 转义。
- 接收、正文读取和执行使用绑定身份与可取消上下文。异步结果在账号切换、订阅变化、停用后重新校验，迟到结果不能启动执行。
- 不将正文、收件人名单、凭据、完整邮件 payload 放入诊断日志、审计元数据或导出；原执行器用户配置导致的输出仍经过既有脱敏链路。
- 主窗口建立后后台恢复，不等待补查或正文读取才创建窗口；不增加服务器端收信或云端邮箱正文存储。

## 注册、兼容与交付

## 验收范围

1. 两个触发器注册、发现、编辑和变量复制；外部邮件默认全部/指定账号，站内信无多余筛选；既有执行器可消费变量。
2. 首次启用/重新启用必须在线确认；断网、认证失败、来源边界不可靠、部分账号不可用或保存失败都保持未启用，联网恢复不擅自启用。覆盖起点确认与本机保存间到信、两阶段间崩溃、客户端时钟偏移及边界同时间多封信。
3. 启用之前的历史不触发，首次索引不漏启用后新信；持续启用的离线信件在启动、唤醒、重连后补触发，已读信仍能补触发。
4. 多页、相同收件时间、同步中断、实时与补查并发、跨重启，以及超过 100 条运行历史后都不重复自动触发。
5. 多封邮件串行、慢执行器、手动运行占用执行槽、入队/游标写入失败、提交标记与执行调用前后崩溃的恢复。
6. 停用/重启用、修改邮箱范围、新增/暂停/删除邮箱、退出/切换 SY 账号、同一用户在不同服务端，以及导入配置的隔离。
7. 两类正文变量，纯文本/HTML-only/空正文/超限/分块不完整/读取失败；读取前后已读状态不变，无附件、远程图片或脚本的额外访问。
8. 未知收件时间、UIDVALIDITY/端点变化、已移动/删除信件、源权限失效有明确诊断；不通过重放或猜测身份掩盖异常。
9. 去重与执行历史保留周期相互独立，本机队列和正文不进入备份；日志与审计不带信件正文或敏感值。

按实现涉及范围运行针对性单元/集成测试、desktop typecheck、hard constraints、IPC/codegen 与 UI tracking 检查；若改动服务器接口，增加该接口权限与分页测试。不启动运行中应用做未授权验证。
