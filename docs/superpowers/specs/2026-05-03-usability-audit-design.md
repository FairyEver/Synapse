# Synapse 可用性审查设计

## 背景

Synapse 即将在团队内部小范围推广，目标用户为开发者同事。需要在推广前进行系统性的可用性检查，发现并修复功能缺陷和逻辑死胡同，确保核心流程顺畅。

## 方法

按用户旅程走查，模拟开发者从首次打开到日常使用的完整路径。每个环节同时检查正常流程和异常场景。发现问题直接修复。

## 已知问题

离线状态下打开已有 Git 仓库 → 设置用户身份 → 因无网络无法同步身份信息 → 界面卡死，无法继续也无法回退。

---

## 阶段 1：首次启动

检查从应用启动到进入主界面的完整链路。

### 1.1 授权激活（License Gate）

**正常流程：** 输入服务器 URL + 邮箱 + 激活码 → 激活成功 → 进入身份设置

**异常场景：**
- 无效激活码：表单应显示错误，允许重试
- 网络不可用：提交后应提示网络错误，不能卡住
- 服务器不可达：应有超时处理和明确错误信息

### 1.2 身份设置（Identity Gate）

**正常流程：** 生成新 ID 或恢复已有 ID → 进入仓库选择

**异常场景：**
- 恢复 ID 时无激活仓库：应提示"先选择目录"
- 生成 ID 失败：应显示错误，允许重试
- 网络不可用时的身份同步：**已知问题，需重点检查**

### 1.3 仓库打开/创建

**正常流程：**
- 选择已有目录 → 验证结构 → 添加并激活
- 新建仓库 → 选择父目录 → 输入名称 → 创建

**异常场景：**
- 选择的目录结构不完整：应提示初始化或显示具体缺失
- 仓库名称含特殊字符：表单验证应拦截
- 目录权限不足：应有明确错误信息
- 创建过程中取消：不应留下半成品目录

### 1.4 仓库 Onboarding（Repo Onboarding Dialog）

**正常流程：** 填写显示名称 → 提交 → 进入主界面

**异常场景：**
- 显示名称为空：表单验证应拦截
- 提交失败（网络/IO 错误）：应显示错误，允许重试
- **离线状态下提交：不能卡死，应允许本地保存或明确提示**
- 对话框无法关闭/回退：应有切换仓库或其他退路

---

## 阶段 2：内容管理

检查 Rule / Skill / Prompt 三种内容类型的完整 CRUD 流程。三者共享 `createContentModule` 工厂，检查一种即覆盖共性，再逐一检查差异。

### 2.1 内容浏览

**正常流程：** Tab 切换 → 分类筛选 → 搜索 → 查看详情

**异常场景：**
- 空仓库（无任何内容）：应显示空状态引导
- 仓库目录被外部删除：应显示"目录不存在"提示
- 搜索无结果：应有明确提示
- 已删除分类下无内容：应有对应空状态

### 2.2 内容创建

**正常流程：** 点击创建 → 填写表单 → 提交 → 列表刷新

**异常场景：**
- 重名内容：应弹出确认对话框（另存 or 修改）
- 表单验证失败：字段级错误提示
- 提交失败：显示错误，保留表单数据便于重试
- 未完成 onboarding 时创建：应禁用并提示原因

### 2.3 内容编辑与删除

**正常流程：** 打开详情 → 编辑 → 保存 / 删除

**异常场景：**
- 编辑中关闭对话框：未保存变更的处理
- 删除确认：应有二次确认
- 版本查看：历史版本是否可正常加载

---

## 阶段 3：安装到编辑器

检查从选择内容到写入编辑器配置的完整流程。

### 3.1 安装目标选择

**正常流程：** 选择编辑器 → 选择作用域（全局/项目）→ 确认目标路径

**异常场景：**
- 无可用编辑器：应显示"无安装目标"提示
- 项目作用域但未选择项目路径：应提示选择
- 编辑器配置目录不存在：应有明确错误

### 3.2 变量替换

**正常流程：** 检测占位符 → 显示替换对话框 → 用户填写 → 确认

**异常场景：**
- 无占位符：跳过此步骤
- 变量保存失败：应显示 warning 但继续安装

### 3.3 安装执行

**正常流程：** 写入文件 → 显示成功 → 关闭对话框

**异常场景：**
- 目标文件已存在（覆盖确认）
- Skill 冲突（备份旧文件）
- 写入失败（权限/磁盘空间）：应显示错误，保留对话框便于重试

---

## 阶段 4：同步与协作

检查 Git 同步的状态展示和错误恢复。

### 4.1 同步状态展示

**正常流程：** 状态 chip 显示当前状态（synced / pending / syncing）→ 点击查看详情

**异常场景：**
- 离线状态：应显示 offline 图标，允许手动重试
- 同步失败（attention）：应显示具体错误和重试按钮
- 待同步项过多：应有数量截断（9+）

### 4.2 手动同步

**正常流程：** 点击同步按钮 → 同步中 → 完成

**异常场景：**
- 离线时点击同步：应提示网络不可用
- 同步过程中断：应有恢复机制
- Git 冲突：应有明确提示和处理指引

---

## 阶段 5：辅助功能模块

### 5.1 Database 模块

**检查项：**
- 无表格空状态 + 创建引导
- 表格创建表单验证（表名格式、列名格式、保留字段、重复列名）
- 数据导入失败的错误信息是否具体
- 行编辑的增删改操作反馈
- 表格删除的二次确认

### 5.2 Task Scheduler 模块

**检查项：**
- 任务创建表单验证
- Cron 表达式验证错误信息是否具体（当前过于笼统）
- 任务运行历史查看
- 任务删除确认

### 5.3 Editor Scan 模块

**检查项：**
- 无编辑器/无项目时的空状态
- 扫描失败的错误信息和重试指引
- 快速发布流程的元数据识别提示

### 5.4 Agent 模块

**检查项：**
- 无 Agent 运行时的状态提示
- 会话创建/删除/切换
- 权限请求面板的交互
- 会话删除后的反馈

### 5.5 Settings 模块

**检查项：**
- 各面板的保存操作反馈（特别是失败时）
- 危险操作（重置、删除）的二次确认
- 仓库维护的进度反馈

---

## 全局检查项

### G1. React ErrorBoundary

当前 `App.tsx` 缺少 ErrorBoundary，任何未捕获的 React 错误会导致白屏。需要添加全局错误边界，显示友好的错误页面并提供恢复选项。

### G2. IPC 调用健壮性

各模块独立处理 IPC 错误，缺少统一的超时和错误拦截。长时间无响应的 IPC 调用应有超时提示。

### G3. 操作反馈一致性

部分操作成功/失败后缺少反馈（如设置保存失败无提示、会话删除无通知）。需要统一使用 `AppNotificationsProvider` 的 `promise()` 包装。

---

## 执行策略

按阶段顺序逐一走查代码。每个检查项：

1. **阅读相关代码**，确认当前实现
2. **判断是否存在问题**（死胡同 / 缺少反馈 / 错误处理不足）
3. **问题存在则直接修复**，修复后验证构建通过
4. **记录发现和修复**，作为最终报告

优先级排序：
- **P0 — 流程卡死**：用户无法继续也无法回退（如已知的离线 onboarding 问题）
- **P1 — 功能断裂**：核心操作报错或无响应
- **P2 — 体验缺陷**：缺少反馈、错误信息不清晰、空状态缺失

## 产出

- 修复后的代码（直接提交到当前分支）
- 问题清单（含严重程度、修复说明）
