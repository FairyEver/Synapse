# 团队 · 管理员专有的预备性基础设施

日期：2026-09-19
范围：`server/`、`dashboard/`
原型：`原型.html`（同目录）

## 1. 这个功能是什么

管理员在管理后台里**建团队、改团队名、删团队、设成员**。

就这些。团队本身不承载任何东西——不共享资源、不带权限、不影响云盘 / 内容 / 会话 / 终端 / 录音的任何可见行为。这一步只把「谁属于哪些团队」这个关系先立起来，供后续功能挂靠。

## 2. 为什么现在做

团队这个概念**在这个仓库里做过一轮又被拆干净了**：

| 时间 | 发生了什么 |
|---|---|
| 5/21–5/23 | 引入 `Team` / `TeamMembership` / `Invitation`，外加一整套团队权限（`TeamEntitlement`、三层角色表） |
| 5/25 | 团队权限被「个人模块权限」取代，团队降级成纯关系模型 |
| 6/13 | 连模块权限也撤出了产品面 |
| 7/31 | 团队关系域 + 邀请整体删除（表、枚举、审计历史、页面、路由、桌面账户字段） |

**这一版是收窄重来**，不是恢复旧设计。旧的失败点在于「团队」和「权限」绑得太死，拆的时候连着拆了两轮。这次只做最底下那层关系，权限一个字都不碰。

## 3. 做与不做

| 做 | 不做 |
|---|---|
| 管理员创建团队 | 用户自助建团队 / 申请加入 |
| 管理员改团队名 | 团队简介、头像、标签等描述性字段 |
| 管理员删除团队 | 团队转移、归档、恢复 |
| 管理员加人 / 移除人 | 用户主动退团 |
| 用户管理页显示某人所属团队 | 按团队筛选用户 |
| 团队列表展示成员数、创建时间 | 团队列表搜索（团队少，不需要） |
| | **成员角色**（队长 / 成员） |
| | 团队权限、团队级资源、团队内任何操作 |
| | 桌面端 / 手机端的任何团队界面 |

## 4. 决策

### 4.1 只有管理员，没有自助

团队是管理员单方面的管理动作。普通用户既看不到入口，也不能申请、不能退团、不能改名。

**理由**：这一步是预备性的，先由管理员把真实组织结构录进来。等将来真要开放自助，再决定谁有权建团——现在决定等于提前押注。

### 4.2 用户与团队是多对多

一个用户可以同时属于多个团队。

**理由**：以后要按团队做权限或资源隔离时，多对多是唯一不用改模型的形态。而且现实中「张三同时在产品组和研发组」很常见，一对一迟早要迁移。代价只是多一张关系表。

**连带影响**：团队列表里的成员数**不是互斥的**，所有团队的人数加起来会大于总用户数，这是正常的。

### 4.3 团队成员没有角色

团队下只有一份平铺的名单，没有队长 / 普通成员之分。

**理由**：现在没有任何地方会读这个角色，加了就是个没人用的字段。将来真需要「谁能管这个团队」时再加，比现在先埋一个空壳简单。

### 4.4 团队可以删除

管理员建错了能删掉。删除**只删团队和成员关系，不删用户账号**，也不影响成员在其他团队里的关系。

**理由**：只能建不能删的话，后台会持续堆积废弃团队，而这些团队一旦被后续功能引用就会变成噪音。

### 4.5 团队名称唯一

名称必填，去除首尾空白后 1–30 个字符，不能与已有团队重名（区分大小写）。

**理由**：重名团队在成员列、用户管理页的团队徽标、后续任何按团队筛选的地方都会变成歧义。唯一约束是数据库层的 `@unique`，不是靠界面提示。

### 4.6 禁用用户可以加入团队

用户的 `status = disabled` 只是账号级别的开关（不能登录）。它**不阻止**这名成员加入团队，成员列表里也照常显示，只多一个「已禁用」标记。

**理由**：禁用是「这个人现在不能登录」，不是「这个人在组织结构上不存在」。离职、停用期间把关系留着，回岗时不用重新配一遍。

### 4.7 用户管理页显示所属团队

`/admin/users` 表格新增一列「团队」，显示每名用户所在的团队（多对多，所以一个人可能有多个徽标；一个都没有时显示 `-`）。

**理由**：团队页是「这个团队里有谁」，用户页是「这个人在哪些团队」。加了团队页之后，排查「这个人为什么在团队里」只能反向查，没有这一列就得挨个团队点进去找。这是本次唯一一处对既有页面的改动。

### 4.8 团队列表不做搜索

**理由**：目标规模是几十个团队以内，一屏能看完。加搜索是没被要求的复杂度。

**已知代价**：团队数量真的涨起来时，这一列和列表都会先撑不住——到时候再加搜索和分页（分页在接口层已经按现有约定做好了，见 §6）。

### 4.9 团队不产生任何可见行为

这是**本设计最硬的一条**。团队存在之后：

- 不改变任何用户能看到的数据
- 不改变任何权限判断
- 桌面端和手机端**完全感知不到**它的存在

如果有人发现「建了团队之后某处行为变了」，那是 bug，不是特性。

## 5. 数据模型

```prisma
model Team {
  id        String           @id @default(cuid())
  name      String           @unique @db.VarChar(30)
  createdAt DateTime         @default(now())
  updatedAt DateTime         @updatedAt
  members   TeamMembership[]
}

model TeamMembership {
  id        String   @id @default(cuid())
  teamId    String
  team      Team     @relation(fields: [teamId], references: [id], onDelete: Cascade)
  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  createdAt DateTime @default(now())

  @@unique([teamId, userId])
  @@index([userId])
}
```

要点：

- `TeamMembership.createdAt` 就是界面上的「加入时间」，不再单开字段。
- 两侧都是 `onDelete: Cascade`：删团队清掉成员关系；用户万一被删也清掉关系（当前后台只能禁用用户、不能删，这条是兜底）。
- `@@unique([teamId, userId])` 保证同一个人在同一团队里不会出现两行。
- `@@index([userId])` 服务用户管理页的反向查询（按用户找团队）。
- `Team.updatedAt` 目前不在界面上显示，只为与 schema 其余模型保持一致。
- 需要给 `User` 模型加反向关系字段 `teamMemberships TeamMembership[]`。

**没有**：角色、权限、邀请、简介、头像、归属者。

### 迁移

新增一个**纯增量**迁移（建两张表 + 索引），不改动任何既有表。

- 目录：`server/prisma/migrations/20260919130000_team_foundation/`
- 命名在 `20260919120000_meeting_recording` 之后，保证顺序
- **不含** `DROP` 与 `ADD NOT NULL COLUMN`，所以不会被 `deploy-migration-risk.spec.ts` 的风险扫描标记为需要审批的迁移

## 6. 接口

全部挂在现有管理域下，统一用 `AdminAuthGuard`，沿用 `parsePagination`、`badRequestFromZodError` 和审计约定。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/teams` | 团队列表，分页 + 排序 |
| POST | `/api/admin/teams` | 创建团队 |
| PATCH | `/api/admin/teams/:id` | 重命名 |
| DELETE | `/api/admin/teams/:id` | 删除团队 |
| GET | `/api/admin/teams/:id/members` | 成员列表，分页 |
| POST | `/api/admin/teams/:id/members` | 批量添加成员 |
| DELETE | `/api/admin/teams/:id/members/:userId` | 移除单个成员 |
| GET | `/api/admin/teams/:id/member-candidates` | 添加成员时的候选用户 |

### 形状

**团队列表行**

```ts
{ id, name, createdAt, updatedAt, memberCount }
```

`memberCount` 用 Prisma 的 `_count` 直接取，不要取回全部成员再在内存里数。

排序字段白名单：`createdAt`、`updatedAt`、`name`、`memberCount`。

**创建 / 重命名**

请求 `{ name: string }`，走 zod：`.trim().min(1).max(30)`。

重名由数据库唯一约束兜底，服务层把 Prisma 的 `P2002` 映射成业务错误「已存在同名团队。」，**不要**先查后写（会有竞态）。

**添加成员**

请求 `{ userIds: string[] }`，数量上限 100。

- 先校验 `userIds` 全部存在，有一个不存在就整体拒绝（业务错误「部分用户不存在。」），不做部分成功。
- 用 `createMany({ skipDuplicates: true })`，已在本团队的直接跳过、不报错——界面已经过滤过，这里只是兜住并发。
- 返回 `{ added: number }`，界面据此提示实际加了几个人。

**候选用户**

`GET /api/admin/teams/:id/member-candidates?query=&page=&pageSize=`

返回**不在**这个团队里的用户，按 `query` 匹配邮箱或用户名，分页，行形状与用户管理页一致（`{ id, email, handle, status }`）。

**这条接口是必需的，不能省。** 不能在客户端拿用户列表再自己过滤——用户列表是服务端分页的，某一页可能整页都是已在团队里的人，客户端过滤会得到空列表。

**成员列表行**

```ts
{ userId, email, handle, status, joinedAt }
```

**用户管理页的团队列**

`GET /api/admin/users` 每行新增：

```ts
teams: { id, name }[]
```

按加入时间正序。实现时给 `adminUserSelect` 加嵌套查询即可。

> **已知规模上限**：这一列会随团队数线性增长，且不受分页约束（一个用户属于 20 个团队就返回 20 个）。按 §4.8 的判断，团队数在几十以内没问题。**如果哪天真到了要分页的量级，第一个该改的就是这一列**——改成只显示前 N 个 + 总数。

### 审计

所有写操作记审计，沿用现有 `action` / `targetType` 命名风格：

| action | targetType | detail |
|---|---|---|
| `admin.team.create` | `team` | `{ name }` |
| `admin.team.rename` | `team` | `{ from, to }` |
| `admin.team.delete` | `team` | `{ name, memberCount }` |
| `admin.team.member_add` | `team` | `{ count }` |
| `admin.team.member_remove` | `team` | `{ userId }` |
| `admin.teams.list` | `team` | 分页参数（读操作，沿用 `recordAdminRead`） |

审计写入失败**不能**让业务操作失败，沿用 `recordServiceManagedAuditSafely` 的吞错处理。

## 7. 交互规格

### 7.1 侧边栏

管理后台侧边栏在「用户管理」之后插入一项「团队」，指向 `/admin/teams`。

### 7.2 团队列表 `/admin/teams`

- 页头「团队」+ 右上「新建团队」
- 表格：团队名称 / 成员 / 创建时间 / 行尾 `⋯`
- 行**点击**进入团队详情
- 行尾 `⋯` 菜单：重命名、删除团队
- 成员列显示 `N 人`

### 7.3 团队详情 `/admin/teams/$teamId`

- 返回按钮 + 团队名 + 「N 名成员 · 创建于 …」+ 行尾 `⋯`（重命名、删除团队）
- 「成员」小节 + 右上「添加成员」
- 成员表：邮箱 / 用户名 / 状态 / 加入时间 / 移除
- 状态列：`正常` 或 `已禁用`

### 7.4 四类对话框

| 对话框 | 内容 |
|---|---|
| 新建团队 | 名称输入 + 取消 / 创建（空名称时创建禁用） |
| 重命名团队 | 名称输入（预填当前值）+ 取消 / 保存 |
| 删除团队 | 「删除团队「X」？」+ 「N 名成员不会因此被删除，只是不再属于这个团队。」+ 「此操作无法撤销。」 |
| 移除成员 | 「把 X 移出团队？」+ 「Y 的账号不受影响，其他团队的成员关系也不变。」 |
| 添加成员 | 搜索框 + 可多选列表 + 「已选 N 人」+ 取消 / 添加 |

名称校验失败时在输入框下方就地报错（「已存在同名团队。」/「团队名称不能超过 30 个字符。」），输入框描边转为错误色。

### 7.5 空态

| 场景 | 文案 |
|---|---|
| 一个团队都没有 | 还没有团队 / 创建一个团队，然后把用户加进来。/ 新建团队 |
| 团队没有成员 | 这个团队还没有成员 / 添加成员后，他们会出现在这里。/ 添加成员 |
| 候选里没有可加的人 | 没有可以添加的用户 |

### 7.6 文案表

界面文案只用必要的标题、标签、操作和空 / 错 / 加载状态，不写功能说明和重复状态。

| 位置 | 文案 |
|---|---|
| 侧边栏 | 团队 |
| 列表页头 | 团队 · 共 N 个 |
| 按钮 | 新建团队 / 重命名 / 删除团队 / 添加成员 / 移除 / 取消 / 创建 / 保存 / 删除 |
| 表头 | 团队名称 / 成员 / 创建时间 / 邮箱 / 用户名 / 状态 / 团队 / 加入时间 |
| 状态徽标 | 正常 / 已禁用 |
| 提示 | 已创建团队 / 已保存 / 已删除团队 / 已添加成员 / 已移出团队 |

## 8. 边界与异常

| 情况 | 行为 |
|---|---|
| 创建重名团队 | 拒绝，输入框下方报「已存在同名团队。」（唯一约束兜底，不是先查后写） |
| 名称全是空白 | 视为空，创建/保存按钮禁用 |
| 名称超 30 字 | 拒绝并就地报错 |
| 删除一个有很多成员的团队 | 弹窗里写明人数，确认后只清关系 |
| 移除一个已不是成员的人 | 返回「该用户不在这个团队中。」 |
| 添加一个已被删掉的 userId | 整体拒绝，不做部分成功 |
| 并发添加同一批人 | `skipDuplicates` 兜住，不报错 |
| 团队在详情页打开时被另一个管理员删掉 | 成员操作返回「团队不存在。」，界面退回列表 |
| 用户被禁用 | 成员关系不变，徽标显示「已禁用」 |
| 团队数超过一屏 | 走接口分页（列表页已按约定分页，只是不做界面搜索） |

## 9. 要拆掉的旧栅栏

团队当初下线时留下了一批**有意保留的防御**。新页面最自然的路径是 `/admin/teams`，正好会被其中几处拦成 404，实施时必须一并拆掉：

| 位置 | 现状 | 要改成 |
|---|---|---|
| `server/nginx.conf:65` | 正则把 `/admin/teams` 也 404 掉 | `/admin/teams` 放行；`/console/teams`、`/dashboard/teams` 继续 404 |
| `server/src/deploy-config.spec.ts` | 断言那段 404 块的内容 | 跟着 nginx 的新写法更新 |
| `dashboard/vite.config.ts` `isRetiredTeamRoutePath` | 开发环境同样 404 掉 `/admin/teams` | 同上，admin 放行、console/dashboard 保持 404 |
| `dashboard/vite.config.test.ts` | 断言 `/admin/teams` 属于退役路由 | 跟着改 |
| `dashboard/src/lib/admin-redirect.ts` | 白名单里没有 `/teams` | 加入 `/teams`（含详情路径） |
| `dashboard/src/lib/admin-redirect.test.ts` | 断言 `/teams` 会被拒绝 | 改成接受 |

**继续保留、不要动**：

- `/team-invite` 和 `/invitations` 的 404 兜底——邀请域没有回来，将来也不会。
- `server/src/admin/admin.controller.spec.ts` 那条「不再暴露 `listTeams` / `listInvitations`」的守卫断言——团队改由独立控制器承载，`AdminController` 上依然不该出现这些方法，这条断言保持原样即可。

另外要注意 `server/src/app.module.spec.ts` 里有一条断言：AppModule 的 imports **不含** `TeamsModule`。新模块叫 `TeamModule` 不会撞上这条断言，但这属于**蒙混过关而不是它想表达的意图**——实施时要把这条断言改成正面表述（明确断言 `TeamModule` 已被装配，`InvitationsModule` 仍然不被装配），而不是靠名字不同绕过去。

## 10. 验收基线

1. 管理员能在 `/admin/teams` 建团队、改名、删团队。
2. 能在团队详情里从既有用户里搜人、多选、添加；能移除单个成员。
3. 用户管理页的「团队」列正确反映每个人所属的团队；在团队页加人 / 删团队后切过去立刻一致。
4. 同一个用户可以同时在多个团队里（团队人数之和可以大于总用户数）。
5. 禁用用户可以加入团队，成员列表里显示「已禁用」。
6. 删除团队后：团队消失、成员关系消失、**用户账号和其他团队的成员关系不受影响**。
7. 重名团队被拒，且数据库层有唯一约束（绕过界面直接写库也写不进去）。
8. 所有这些操作在审计日志里各留下一条记录。
9. **普通用户、桌面端、手机端观测不到任何变化**——不新增接口、不新增界面、不改任何既有响应字段（唯一例外是 `/api/admin/users` 多了 `teams` 列，那是管理员专用接口）。
10. `/admin/teams` 在开发和正式环境都能正常打开（旧栅栏已拆），而 `/console/teams`、`/dashboard/teams`、`/invitations` 仍然 404。

## 11. 非目标

- 任何形式的团队权限、团队资源、团队内协作
- 用户自助建团、申请加入、退团
- 团队简介 / 头像 / 标签等描述性字段
- 按团队筛选用户、按团队统计
- 桌面端 / 手机端的团队界面
- 团队改名历史、成员变更历史（审计日志里能查到，但不做产品化的历史界面）
- 邀请链接（上一版的 `Invitation` 不回来）

## 12. 已定口径

- 一个用户**可以**属于多个团队。
- 团队**可以**删除，删除不动用户账号。
- 成员**没有**角色。
- 团队列表**不做**搜索。
- 用户管理页**要**显示所属团队。
- 禁用用户**可以**加入团队；禁用只是账号级别的设置。
