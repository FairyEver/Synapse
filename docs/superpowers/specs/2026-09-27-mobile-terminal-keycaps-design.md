# 终端键盘面板：键帽照那台电脑印 · 产品设计文档

日期：2026-09-27。上游：`2026-09-17-terminal-full-keyboard-design.md`（修饰键行）、
`2026-09-20-terminal-keyboard-high-frequency-design.md`（面板现状）。

## 1. 要解决什么

用户报：Codex 在终端里提示「`⌥ + ↑`」作答，他打开手机端的自定义键盘，**找不到那颗键**。

根因不在缺键，在命名：修饰键行印的是 `Ctrl` `Shift` `Alt` `⌘`，而终端里那个字形是 `⌥`。
用户在终端里读到的是符号，面板上写的是名字，两者对不上 —— 那颗键在他眼里等于不存在。

面板是一块**电脑**键盘的画像，却按 PC 的名字印、按 Mac 的符号摆（行末那颗 `⌘`）。
两个方向都只写一半。

## 2. 三条决定性事实

1. **电脑自己知道这件事。** 桌面端 `live.hello` 里一直带着 `platform`
   （`process.platform` 加架构：`darwin-arm64`、`win32-x64`，`live-connection-service.ts:735`），
   云端也一直存着它（`LiveClientPublicDto.platform`）。缺的只是云端到手机这一段。
2. **手机侧推不出来。** 会话、摘要、电脑名里都没有这件事；电脑名是用户自己起的自由文本。
   靠猜就是错。
3. **只能走 REST。** `mobile.presence` 刻意只带 id（广播给账号下所有手机，payload 有字节
   预算），所以这类「关于某台电脑的事实」一律搭 `GET /api/mobile/desktops` —— `deviceName`
   当初就是这么加上去的，理由与位置完全相同。

**结论：桌面端一行都不用改。** 要动的是云端把已有字段转发出来，和手机端拿它画键帽。

## 3. 决策

### 3.1 键帽照电脑印，不照手机印

| | Mac | PC |
|---|---|---|
| Control | `⌃ Ctrl` | `Ctrl` |
| Shift | `⇧ Shift` | `Shift` |
| Alt | `⌥ Alt` | `Alt` |
| 第四颗 | `⌘ Cmd` | `Win` |

三条理由，缺一条这个方案就不成立：

1. **符号是从终端里认回来的那一个。** 终端说「按 `⌥ + ↑`」，面板上就得有一颗印着 `⌥`
   的键 —— 这是这次改动的全部理由。
2. **名字始终在场。** 只印符号会让不认识符号的人彻底读不出来；两个都印，两个方向的人都
   找得到。这一条同时是 3.2 那条默认值的兜底。
3. **PC 键盘上没有 `⌥` `⌃` `⇧` 这些字形。** 在一台 PC 的画像上印它们是凭空多一颗不存在的
   键，所以那一边只印名字。

第四颗键（`⌘` / `Win`）两头的终端 App 都自己吃掉（macOS 的 ⌘C 复制、⌘V 粘贴、⌘K 清屏；
Windows 的 ⊞ 归系统），没有字节能送到 PTY，所以它照旧压暗、按下去只有拒绝触觉
（2026-09-17 §3.4 的结论不变）。

### 3.2 说不出来的时候按 Mac 印

`platform` 缺席（云端还没升到会带这个字段的版本）或两种都不是（Linux 桌面端）时，画 Mac
那一套。三条理由：

1. 这块面板**一直**就是一块 Mac 键盘 —— 修饰键行末那颗 `⌘` 画在那里就是这个来由 —— 所以
   这个默认值不比今天差。
2. 名字始终在场，所以「猜错」只是多印一个用不上的符号，不会让哪一颗键变得读不出来。
3. **升级顺序因此不改变用户看到的东西**：旧云端 + 新手机画出来的板子，与新云端一模一样。

### 3.3 `rawValue` 是身份，不是键帽

四颗键的 id 仍然是 `Ctrl` / `Shift` / `Alt` / `⌘`（`TerminalFlowUITests` 与
`ChromeAutoHideUITests` 都按 `panelkey-modifier-*` 找键，后者还拿它当「面板开着」的探针）。
**画什么现在随电脑变，而会变的东西不能同时当身份** —— 用户按的是同一颗键，测试找的也是
同一颗键，只有键帽在换。键帽由 `KeyboardPanelModifier.keycap(on:)` 给，表只有那一份。

### 3.4 只改键帽，不改任何一颗键发什么

面板的契约是「发一个按键」：`Alt` 的 ESC 前缀、`Ctrl` + 字母、`⇧tab`、`Ctrl+I`/`M` 换
`Tab`/`Enter`，一条都不动。电脑的操作系统不改变终端里那个字节。

## 4. 协议与上线顺序

- 一处 REST 字段：`LiveReachableDesktop` 加 `platform`，`listOnlineDesktops` 把注册表里
  电脑自己报的那个值**原样**带上（`server/src/live/live.types.ts`、`live-desktop.gateway.ts`）。
  云端对它没有意见，认不认得出来是手机的事。
- **不改 WS 协议、不改 `MOBILE_KEYS`、不改 `shared/`** —— 没有 1003 那条风险。
- 两端各自向后兼容：新手机 + 旧云端 = 按 Mac 印（§3.2）；旧手机 + 新云端 = 多出来的字段被
  `Codable` 忽略。**所以顺序不是硬约束，但服务端先上，手机才有东西可用。**
- 顺序：**服务端 → 手机端。桌面端不需要升级。**

## 5. 非目标

以下都是有意不做：

- 不改修饰键的语义（§3.4）。
- **不把工具栏那颗 `Ctrl+C` 改成 `⌃C`。** 那是手机自己的动作按钮（`interrupt`），不是电脑
  键盘上的一颗键 —— 工具栏一行是自己的词汇，面板一行是那台电脑的画像。
- 不按平台改命名键的文案：`Tab` `Esc` `Enter` `⌫` `PgUp` 两台电脑同名。
- 不给 Linux 另做一套键帽（走 `.unknown` 的 Mac 那一套）。
- 不改面板几何、页数、键位、锁存规则。

## 6. 验收基线

每一条都要能说出「怎么验的」。

1. 正在驱动的电脑是 Mac 时，修饰键行印 `⌃ Ctrl`、`⇧ Shift`、`⌥ Alt`、`⌘ Cmd`。
2. 是 Windows 时印 `Ctrl`、`Shift`、`Alt`、`Win`（无符号）。
3. 云端不说（旧服务端）时与第 1 条**逐字相同**。
4. 四颗键的 id 不变：`panelkey-modifier-Ctrl|Shift|Alt|⌘`，既有 UI 用例一条都不用改。
5. 锁存表现不变：点一下反色、发完弹回、双击挂点；「组合键」开关仍只影响锁存、不动版面。
6. `⌥` + 字母仍发「Escape + 文本」两个动作；`⌘` / `Win` 仍按不动（拒绝触觉）。
7. 读屏读的是名字（`Alt`），锁存态读作已选中。

**怎么验的**：1–3、7 的表由 `SynapseMobileTests/DesktopPlatformTests.swift` 逐格钉住（跑
`-only-testing:SynapseMobileTests`）；第 4 条是既有的 `TerminalFlowUITests` 与
`ChromeAutoHideUITests` 一条都不用改、按原 id 继续找键（它们要跑模拟桌面端，本轮未跑）；
第 5、6 条是既有决议，本次没有动这两条代码路径。
