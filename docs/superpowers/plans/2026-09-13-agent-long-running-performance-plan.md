# Agent 长时间运行性能修复计划

状态：部分执行，尚未完成 P1～P5 全部修复与性能验收。已核实工作区、建立合成存储基线，并完成并发写入、局部计时、React 诊断保留和全文查看器生命周期的一轮修复。逐阶段结果与未完成项见 [执行记录](2026-09-13-agent-long-running-performance-execution.md)，容量边界见 [容量设计](../specs/2026-09-13-agent-long-running-capacity-design.md)。

## 交给执行 Agent 的任务

在 Synapse 仓库执行本计划，解决长对话持续运行后界面越来越卡的问题。先核实当前实现与未提交修改，再按依赖顺序实现、验证并同步文档。不要仅优化 loading、添加若干 memo 或提高内存限制后就宣布完成。

用户目标：在相同输出速率、并发量、可见内容规模和设备条件下，Agent 运行时间及历史长度增加，不应导致 App 的内存、每次界面更新开销和交互延迟持续增长。完整历史必须可回看、导出和继续使用；淘汰的是显示缓存，不是用户数据。

本计划授权范围是该目标所必需的开发与常规验证。它不授权控制真实用户的 Agent 对话、改写真实历史、停止或重启正在运行的应用、启动 DevTools/浏览器/Playwright、安装新依赖、发布或破坏性 Git 操作。遵守执行时的用户授权与仓库规则；遇到需要额外授权的运行时验收，先完成独立可做的代码和测试，准确列出待验收项，不能假称通过。

## 1. 背景、证据与不确定性

2026-09-13，只读观察一个持续约 90 分钟的对话：

- MCP 显示运行中、859 条持久化时间线记录，没有等待权限确认。
- Synapse Renderer 两次进程采样约 8.6 GiB RSS、约 65% CPU。RSS 不是 JS 堆大小，不能据此认定泄漏来源。
- 现有 Renderer 诊断在多个约 10 秒的汇总窗口记录了累计约 5～8 秒长任务，观察到单次最长约 1.59 秒。
- 用户看到侧栏 loading 动画明显卡顿。该图标是普通 CSS `animate-spin`，长任务与高资源占用支持界面负载问题，但尚无性能调用栈证明具体热点占比，也未独立测量合成线程。
- 当时 MCP inspect 对超大单轮只返回 `truncatedTurn`，不能据此声称读取了完整对话、判定模型为何运行这么久，或证明 859 条记录全部挂载到了 DOM。

## 3. 必须形成的容量契约

在实现前，把以下预算落到一份设计文档，并统一定义常量、单位、所有者、溢出行为和测试。条数与字节数必须同时约束，预算必须覆盖全窗口/全应用聚合，而不只是单个对话。

| 层 | 必须保证 |
| --- | --- |
| 权威存储 | 历史可以增长；热路径按有界记录/分块增量读写，禁止每次重建完整历史 |
| 主进程缓存 | 活跃摘要、记录页、工具关联缓存有总预算与淘汰规则；不永久保留所有完整会话 |
| IPC | 沿用现有单批 128 条/64 KiB、每对话每 Renderer 一个未 ACK 批次、等待队列 512 KiB 上限；增加多对话聚合预算审计 |
| Renderer 数据 | 只保留视口附近页、有限尾部页和必要运行状态；超过总预算可重新加载的页被淘汰 |
| DOM | 只挂载可见范围及有限 overscan；超长一条消息/一个过程组内部也必须有界 |
| 活动文本 | 采用有界活动片段，冻结片段可卸载；不能用一个不断增长的完整字符串重复解析 |
| 更新调度 | 正文按现有 50ms 上限合并；后台会话不逐 token 渲染；状态无变化不通知订阅者 |
| 诊断与资源 | 性能记录、缓存、监听、定时器和积压任务有保留期限、容量和释放入口 |

工程模型：常驻工作集主要由“可见内容预算 + 有限缓存 + 有限队列 + 明确并发量”决定，而非总历史 H。允许数据库索引查找的对数成本，不要求磁盘空间恒定或承诺无限并发。对无法归属 Synapse 控制的 SDK 内存增长要独立测量和报告，不能静默重启会话掩盖。

## 4. 分阶段实施

### P0：建立可复现基线与归因

1. 列出事件从 SDK → 主进程 → 持久化 → 投影/IPC → reducer → Timeline → 滚动布局的调用路径，标出完整历史复制、全量扫描和对象保留点。
2. 用合成数据创建单轮超长运行、多轮长历史、超长单条思考、巨大工具结果、多个后台对话场景；不使用真实对话正文、凭据或付费模型流量作为默认测试夹具。
3. 用相同尾部、输出速率和视口，比较 1k/10k/100k 条历史；记录页面读取扫描量、读写字节、更新处理量、缓存/队列上限与组件提交范围。计数断言优先于易波动的单元测试耗时断言。
4. 具备运行时授权后，在测试数据环境采集 CPU/布局调用栈及多时点堆快照，区分 React、文本解析、GC、滚动测量、IPC、存储和诊断的开销，分别记录 Renderer、主进程、GPU 与 SDK 子进程。
5. 审计 React 开发性能记录的保留情况。现有 measure guard 去除 detail 不等于所有性能记录自动有界；仅在证实后处理，不能全局盲目清空其它诊断所需记录。

交付：有来源的基线、热点/保留路径与待证实项；无 UI profiling 授权时完成静态与合成基线，运行时项保留为未验证。

### P1：拆开历史存储与对话摘要

1. 在现有 DataRepository 内设计有索引的历史记录/文本分块存储。会话摘要只保留需要的元数据、计数、状态和引用；不复制一整份 history 到摘要。复用已有 namespace、事务、schema 和维护 Worker，禁止另建平行 SQLite/裸文件存储。
2. 保留稳定记录标识与顺序。并发追加、更新工具结果、权限响应、终态和标题更新必须有一致性策略；不能用最后一次全对象覆盖造成丢记录。
3. 提供按游标分页、按引用分块读取正文和增量更新摘要的窄接口。页面大小在查询阶段受限，不能先加载/脱敏/序列化全历史后裁剪。分页不能以“整轮不可切开”为由无限扩大。
4. 工具调用/结果跨页、阶段开始/结束跨页时通过稳定关联 ID 与有界摘要查询恢复；不得为补齐一条关系扫描/装载全部历史。
5. 梳理所有完整 history 消费者：恢复上下文、费用统计、导出、搜索、全文、MCP inspect、删除、备份/恢复、数据维护等。改为按用途分批读取或增量摘要；必要的模型上下文组装也要遵循既有上下文预算。
6. 制定旧数据迁移：版本标记、可中断续跑、幂等批次、原子切换和失败恢复；覆盖迁移中新增记录和应用崩溃。迁移在窗口创建后后台执行，不阻塞启动。
7. 旧格式是大 JSON 时，明确大对象解析的峰值风险；不能把迁移搬到 Worker 就声称内存已有上限。选择分块解析或其它经验证的受控策略，明确极端对象处理路径。
8. 使用隔离数据验证迁移，不自动迁移当前真实用户数据库。原始数据清理须有核验与授权边界；不要设计无损回退承诺却遗漏切换后新写入的数据。

验收：100k 历史下追加小记录不会重新读写完整历史；尾页查询不会物化完整会话；迁移中断恢复后记录、顺序、关联、附件引用、费用和导出内容一致。

### P2：有界页缓存与稳定分页

依赖 P1 的稳定游标/引用契约。允许先实现纯缓存逻辑测试，但不要保留与新接口冲突的第二套分页系统。

1. 把 `use-chat-connection` 的无限 prepend/merge 数组改为有界页缓存；可见页与必要尾部状态分离，同时限制条目、文本字节和会话数。
2. 无论向上回看还是持续接收，远离视口的数据都能卸载并重新读取。若单个可见页本身超预算，必须拆页/分块，不允许“可见就无限豁免”。
3. 滚动锚点基于稳定记录/片段 ID 与偏移，不能依赖被淘汰数组的下标。保持回看位置、返回底部、宽度变化和 prepend 后位置稳定。
4. 全文查看器也采用有界分块缓存；打开全文不能重新把整条巨大正文装进一个组件。
5. 快速切换对话、旧请求晚到、历史更新、resync 和分页并发有明确 epoch/版本处理，避免旧快照覆盖新尾部、重复项或断档。

验收：双向翻页与长时间持续追加后缓存仍受限；完整历史仍可达；不会为了加载尾部追补所有遗漏事件。

### P3：视口虚拟化与局部更新

1. 检查现有虚拟化能力及直接依赖；不擅自新增库或引用未声明的传递依赖。没有适用基础设施时实现任务所需的最小窗口化，若确需新依赖再提出具体理由。
2. 将可见时间线构造成稳定的行/片段模型，支持动态高度。超大活动过程组不能作为一个包含数千子项的虚拟行；单条巨大正文也不能规避窗口化。
3. 折叠组保存小摘要，展开时加载所需页；避免每个 token 重新分组全部历史。跨页工具关联由 P1/P2 提供。
4. 历史项保持引用稳定，正文预处理按内容版本缓存且受总预算控制。memo/selector 用来落实更新隔离，不作为容量限制的替代品。
5. 活动计时器移到局部订阅/组件；重复运行状态保持原状态引用。侧栏、输入框、历史区、当前活动文本独立订阅所需数据。
6. 活动 Markdown/思考按可稳定冻结的语义片段处理，保留未闭合代码块/表格等解析状态；终态展示与全文一致，不能用任意字符截断破坏文本语义。
7. 滚动测量合并到每帧，避免读布局—写布局循环、每次全文长度扫描和自动滚动触发额外全树更新。
8. 覆盖选择/复制、全文复制、链接、权限表单、焦点、搜索定位、可访问性和滚动恢复。明确虚拟化后的浏览器原生查找范围，保留或补齐既有产品搜索行为，不能静默声称原生查找仍覆盖未挂载历史。

验收：尾部更新不触发不变历史正文重算；计时器不触发整条 Timeline 重算；相同视口下挂载节点不随历史增长。

### P4：背压、批次恢复和资源生命周期

1. 以 `desktop/electron/services/agent-runtime/event-delivery.ts`、现有 EventBus、`use-chat-events.ts` 为入口复核既有 50ms/ACK/resync 实现，不再新建一套平行投递协议。
2. 明确 ACK 是接收到有界缓冲还是完成应用，确保预算覆盖已 ACK 但尚未消费的数据。Renderer 卡顿/暂停时不能通过提前 ACK 把积压转移到另一条无限队列。
3. 只能合并/跳过可恢复的显示增量；最终正文必须完整。持久化的语义事件与显示 delta 分开，权限/问题、错误、终态有可靠传递和状态查询恢复路径。
4. 用持久化高水位与投递序号衔接快照和后续事件；resync 不得回放无限积压，落盘晚于快照、重复批次、迟到 ACK、换窗口都要测试。
5. 背景会话只订阅摘要；控制事件不能被正文洪峰饿死。过载时减少显示刷新、分批处理和重新同步，正常持续运行不能靠停止 Agent 或周期重启 Renderer 维持。
6. 清理页缓存、组件缓存、计时器、观察器、订阅、pending Promise/队列、闭包大对象引用及过期 SDK 会话。诊断只记录有界聚合信息，不记录正文或原始大 payload。
7. 保留既有崩溃/无响应恢复契约及 Renderer 所属轮次边界；它是异常兜底，不能代替长期稳定性验收。

验收：生产速率持续高于展示消费速率时队列仍受限；恢复后最终内容与权威记录一致；切换/关闭重复执行后资源计数回落。

### P5：整体验证与交付

完成下述测试矩阵与性能门槛。凡需要运行应用且尚未获得授权，提供可执行入口与明确的待验证清单，不把实现完成写成已通过长时间验收。

## 5. 测试矩阵与验收口径

### 必须自动覆盖的行为

- 1k/10k/100k 历史，相同末尾和视口；既覆盖很多短消息，也覆盖少数超大消息。
- 单个用户轮次内持续产生大量工具调用和思考，不依靠下一条用户消息才能切页/回收。
- 工具调用与结果、权限请求与响应、阶段开始与完成跨分页边界。
- 高速 delta、消费停顿、重连/resync、重复/迟到批次、切换对话后的旧请求。
- 多对话后台运行与一个前台回看；预算同时覆盖每会话和聚合总量。
- 长消息复制/全文、未闭合 Markdown、动态行高、折叠展开、prepend 锚点、用户主动离开底部。
- 旧数据迁移、失败重试、中断后重启、并发追加和导出/恢复一致性。
- 反复打开/关闭/切换至少数百轮后，订阅、缓存及活动计时器数量不随轮次累积。

### 性能门槛

以下是计划提出的默认验收目标，不是已经测得的结果。执行 P0 时记录设备、应用构建、窗口尺寸、并发数、每秒事件数、字节速率和测试数据规模，固定条件后再评估；若发现目标不适用，先记录原因与修订依据，禁止修完后为通过而放宽。

| 指标 | 目标与测量方式 |
| --- | --- |
| 可控工作集 | 缓存/队列/挂载行始终不超过设计预算，含过载和极端单条内容 |
| 每次增量处理 | 不扫描或序列化完整历史；用扫描条目、序列化字节和更新组件范围验证 |
| 交互响应 | 固定基准负载下输入、滚动、切换、停止按钮本地响应 p95 ≤100ms；与 SDK 实际停止耗时分开 |
| 主线程长任务 | 稳态长任务累计占用目标 <5%；不得反复出现 >200ms 的历史重算任务 |
| 长期退化 | 第 8 小时与预热后的第 30 分钟相比，同负载交互 p95 不恶化超过 20%，且均满足绝对目标 |
| 内存 | 分别记录 RSS、JS heap、DOM、队列与缓存；预热后已回收堆低水位不持续随历史增长。最后一小时低水位相对预热稳态窗口增幅目标 ≤10%，结合保留路径判断，不用单次 RSS 或强制 GC 作为通过证明 |
| 数据正确性 | 完整语义记录/最终正文、顺序、关联和导出一致；显示增量合并不算数据丢失 |

运行短时确定性回归后，在隔离测试环境做至少 8 小时真实时间耐久测试，条件允许延长到 24 小时。加速回放用于覆盖大历史容量，不能替代真实计时器、GC 和资源释放的长时间测试。正式包性能为主要交付指标，同时回归开发版，避免开发诊断导致用户开发环境失稳。

## 6. 命令与变更同步

执行时先重新核对 `desktop/package.json`。当前基础命令：

```bash
pnpm --filter @synapse/desktop run typecheck
pnpm --filter @synapse/desktop run check:hard-constraints
pnpm --filter @synapse/desktop run test
```

开发阶段按真实测试文件选择最小充分专项，并使用单次执行模式；分开定位 Electron 与 Renderer 失败。最终范围涉及存储、IPC、Agent 生命周期与 UI 时运行完整 desktop 测试。新增性能脚本须有明确参数、合成数据目录、清理策略和结果格式，不能编造不存在的测试命令。

- IPC schema/preload 修改后按项目生成链生成，运行 `check:ipc-codegen`；不手改生成文件。
- 新增/移动 Worker 或改变打包边界时运行 `check:packaged-asar` 并验证实际构建产物。
- 如果后续获准启动应用，只用根 `pnpm dev:desktop`，并遵守已运行服务和真实会话保护规则。
- 实现阶段同步更新根 `RELEASE_NOTES_PENDING.md`，描述长对话流畅性与历史完整性；本计划文档本身不需要产品更新记录。
- 存储/分页/恢复的长期边界同步到对应设计和规则；MCP/注册表面发生变化时同步能力清单、schema、系统 Skill 和 Agent 指南，表格数量按实际变化维护。
- MCP inspect 若要从整轮分页改为记录游标分页，须明确兼容契约与客户端迁移，不能静默改变 `beforeIndex` 的合法边界。因存储改造触及该路径时一起处理必要兼容，不扩展为无关能力开发。
