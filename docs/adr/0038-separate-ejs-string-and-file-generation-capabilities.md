# Separate EJS string and file generation capabilities

HTML Generator exposes string-returning rendering as `app.html_generator.ejs.generate` and composed file generation as `app.html_generator.ejs_file.generate`, with matching `app_html_generator_*` MCP tools and separate `html_generator_*` Workflow nodes. The string capability returns `{ html, size }`, while the file capability returns only the shared Text File Writer `output` metadata and never duplicates the rendered HTML; their Workflow primary outputs are respectively the HTML string and normalized file path. Keeping two identities instead of a mode switch makes the generator-provided file side effect, permissions, share resources, risks, and output contract explicit, while both entries continue to use the same EJS rendering core and measure sizes as UTF-8 bytes.

The capability registry marks string generation as `mutates: false, risk: "high"` and file generation as `mutates: true, risk: "high"`. The first version does not add HTML-specific MCP annotations or metadata fields because the current common MCP tool definition exposes only name, description, and input schema; any future standard annotation support must be introduced horizontally for all tools. Both MCP descriptions state that trusted EJS JavaScript executes in a Worker that is not a security sandbox and that built-in include is disabled. The string tool additionally states that it returns complete HTML without saving, opening, or validating it. The file tool states that it writes only an absolute `.html` or `.htm` target as UTF-8 and that replacement requires `overwrite`. Individual field descriptions remain limited to their field contracts instead of repeating the complete risk statement.

`mutates: false` describes only the behavior supplied by the string-generation entry: HTML Generator does not invoke Writer, open a file, or initiate another system action. It is not a purity or no-side-effect guarantee for executable template code. Trusted EJS JavaScript can still access files, networks, environment state, or other Worker runtime capabilities under the existing `shell.exec` code-execution risk, without per-operation PermissionGuard interception; HTML Generator cannot fully identify or audit those template-originated effects. File generation remains `mutates: true` because the entry explicitly invokes Writer. MCP wording therefore says that HTML Generator does not automatically save or open output rather than implying that template code is sandboxed.

Both Workflow nodes use the existing variable-binding mechanism through exactly one reserved binding named `data`. This binding cannot be renamed or shadowed, its source must be an upstream `node_output`, and the executor strictly parses `resolvedVariables.data` as a top-level JSON object; skipped upstream nodes, empty output, or invalid JSON fail with `INVALID_DATA`. The pure rendering node accepts no other bindings. The file node may accept additional ordinary bindings, but they are used only to interpolate `outputPath`. The persisted EJS `template` is always passed through verbatim and is never processed by Workflow variable interpolation. The node panel therefore presents `data` as a dedicated upstream data-source selector instead of an editable variable name.

Registering the two new node types is a backward-compatible Workflow document extension, so `WORKFLOW_SCHEMA_VERSION` advances from `2.4.0` to `2.5.0` with an identity migration, a historical fixture, and an updated workflow schema contract. Existing documents change only in `meta.schemaVersion`; their business content is not rewritten. Correcting the generic runtime so it no longer preprocesses arbitrary `config.template` fields does not independently require a version change because Text and End retain their existing executor-owned interpolation semantics. The Workflow share package remains on its existing V4 format because its container and import protocol do not change. Each node declares its corresponding App Capability at minimum version `1.0.0`, and `requiredCapabilities` blocks import into clients that do not provide it.

The system UI registers one App with id `html-generator` and exposes centered top-bar tabs named “生成 HTML” and “生成文件”. The tabs call the two capabilities directly without constructing a mode request, retain the shared template and JSON data drafts when switching, and keep operation state, errors, and results independent. Only the file tab adds output path and overwrite controls. The first version adds no validation, preview, or open tab and follows the shared `SystemAppTopBar` centered layout and ghost-action rules.

The first App version accepts only inline inputs: an EJS template text editor and a JSON text editor. The renderer parses the JSON as a top-level object for immediate field feedback, while the main-process boundary still performs authoritative schema, JSON-value, and byte-limit validation. It does not expose `templatePath`, `dataPath`, template or JSON file pickers, drag and drop, automatic clipboard access, or remote imports. Only the file tab provides a system save picker for `outputPath`. The template field carries the concise warning “EJS 模板会执行 JavaScript，仅使用可信内容”.

The first App version uses the existing shadcn `Textarea` for template input, JSON input, and read-only HTML source. These areas use a monospace font, disable spell checking, preserve whitespace and line breaks, allow vertical resizing, and scroll within the content surface. JSON supplies only necessary parse feedback during editing and submission. The first version adds no syntax highlighting, completion, formatting, line numbers, search/replace, CodeMirror wrapper, or language dependency; any future rich editing experience must be a reusable component shared with other code-oriented surfaces such as Script rather than an HTML Generator-only editor.

The string tab renders the complete returned HTML only as read-only monospace source, exposes an explicit copy action and UTF-8 byte size, and never injects it into a DOM, previews it, repairs it, truncates it, or saves it automatically. The file tab shows only the actual absolute path, format, UTF-8 byte size, and overwrite outcome, with an explicit copy-path action and no open, preview, reveal, or locate behavior. Editing shared template or data input clears both tabs' prior result and error state; editing output path or overwrite clears only the file tab. Each tab owns independent running, error, and result state.

While either operation is running, the shared template and data editors are read-only so the visible inputs cannot diverge from an in-flight request. Every submission captures an immutable input snapshot plus a renderer revision and request id; a late response may update its tab only when it still matches the current revision. File side effects always use the submitted snapshot even if the renderer later moves on, and the UI must not label a late result as belonging to newer inputs. App unmount or window close propagates the existing cancellation signal to any render that remains cancellable.

Each App tab permits at most one active request, while the two tabs may concurrently submit the same frozen template and data revision. A running tab rejects duplicate submission; the other tab can still submit that shared snapshot. Shared editors remain read-only until both requests finish, file path and overwrite controls are locked only while the file request is active, and tab switching remains available. Results update independently under the existing revision check. Window close cancels both requests where cancellation is still possible. App requests receive no reserved capacity and continue to share the global two-Worker, four-waiter scheduler with MCP and Workflow.

Each tab uses the existing `Alert` component for its own run failure and displays only the normalized message, appending “第 N 行” when a reliable line is available. It never displays a column, error code, raw EJS exception, source context, generated function, or stack; codes remain available to IPC consumers and structured logs. Pre-submit template, data, and output-path failures appear beside their fields without a duplicate tab-level alert, and JSON parse feedback during editing remains local without dispatching a request. A failure does not rewrite the template, navigate, or select source text. Tab errors remain independent and clear under the same input-revision invalidation rules as results.

The App displays compact UTF-8 byte counters beneath the template and valid top-level-object data editors: current bytes against 256 KiB for the template, and bytes after parsing and reserializing against 512 KiB for data. Invalid JSON displays only its parse error rather than a misleading byte count. A single-field overage is reported beside that field; a serialized `{ template, data }` over 768 KiB is reported beside the actions. Either condition disables both submissions. The UI uses no percentage, progress bar, or warning scale and does not attempt to predict the five-MiB output limit; successful results show only the actual output byte size. Renderer checks are advisory UX and never replace the authoritative main-process validation.

The file tab uses the existing editable absolute-path field plus a system save chooser. The chooser filters only `.html` and `.htm`, uses the current nonempty value as `defaultPath` or `output.html` otherwise, and leaves all state unchanged when cancelled. The App accepts the returned path verbatim without adding an extension, changing case, or rewriting its directory; the Renderer immediately checks the absolute path and extension and the main process authoritatively repeats the check. Selecting an existing target never enables overwrite: only the user may toggle it, and its default remains false. Path or overwrite changes invalidate only the file tab's result and error.

On first open or reload, template and output path are empty, the data editor contains the neutral default `{}`, overwrite is false, the string-generation tab is active, and both tabs have no result, error, or running state. The template editor receives focus. `{}` is an initial value rather than a restored draft. The pristine form shows neither JSON nor required-field errors: an empty template only disables actions until submission or blur makes its required feedback relevant.

App drafts live only for the current window lifetime. Switching tabs retains template, JSON data, output path, and overwrite state, but closing or reloading clears all inputs, results, and errors and restores overwrite to `false`. The first version creates no DataRepository namespace and provides no autosave, recent-template list, history, or crash recovery. Any future template reuse feature must be an explicitly saved user asset rather than a silent cache of executable templates or potentially sensitive data.

The first version declares no `html-generator` App deep links. It does not place template text, structured data, or output paths in `synapse://` URLs and does not create an empty capability solely to open the UI. Users open the system App through Synapse, while MCP and Workflow remain the programmatic surfaces. Any future deep link requires a separately designed restricted action that does not carry template source and is never inferred automatically from the existing capabilities.

The string-generation Workflow node's share contract is not self-contained, requires built-in capability `app.html_generator.ejs.generate` at minimum version `1.0.0`, marks `template` with the `shell.execute` risk, and declares no file resources. The file node is likewise not self-contained, requires built-in capability `app.html_generator.ejs_file.generate` at minimum version `1.0.0`, marks `template` with the same risk, and declares `outputPath` as one writable file resource. Template source remains in the Workflow body and appears in the import risk step. The reserved data binding refers only to an upstream node inside the shared graph, so the central graph and id-rewrite machinery handles it. Neither node declares `runtime.shell.*`, models, projects, environments, or extra portability warnings, and neither performs import, mapping, ZIP, transaction, or other IO work inside its declarative share contract.

Newly dropped nodes may temporarily exist in the current editor as incomplete drafts: `{ template: "", variables: [] }` for string generation and `{ template: "", outputPath: "", overwrite: false, variables: [] }` for file generation. These drafts are not valid persisted configurations. Save, run, and export require the node-owned strict config schema: template has at least one character; the string-generation node has exactly one reserved `data` binding; the file node has exactly one such binding plus only ordinary bindings used by `outputPath`; the reserved source is a non-empty `node_output`; output path configuration is non-empty; and unknown fields are rejected. The file executor removes the reserved `data` value from the interpolation scope, strictly parses it only for EJS, and calls existing `interpolatePrompt` on `outputPath` with the remaining ordinary bindings. A `{{data}}` path placeholder is therefore unbound and fails before queueing instead of embedding JSON text. Other skipped bindings retain the existing empty-string behavior, after which the executor validates the final absolute `.html` or `.htm` path. The EJS template never passes through Workflow interpolation. Existing generic variable validation continues to enforce upstream reachability, and the generic Workflow Validator does not hard-code either HTML Generator node type.

Both Workflow nodes use capability-owned configuration panels. Each panel provides an EJS template `Textarea`, a dedicated data-source selector limited to currently reachable upstream `node_output` sources, and the concise trusted-code warning; users cannot rename the reserved binding or select param/static data. The file panel additionally provides output file, overwrite, and a separate path-variable list using the existing param, node-output, and static source types. Canvas cards never expose template source, snippets, rendered HTML, results, or repeated risk copy. The “生成 HTML” card summarizes the selected data source or “未选择数据”; the “生成 HTML 文件” card prioritizes output path or “未设置输出文件”. Technical node type ids remain internal.

Workflow editing, saving, export, and import planning never compile EJS or start a Worker. The panels validate only that the template is nonempty, well-formed Unicode, and at most 256 KiB, and display its UTF-8 byte count; the strict node schemas additionally enforce fields, the reserved data-binding cardinality and source type, unknown-field rejection, and required configuration. A syntactically invalid or data-dependent-failing template may therefore be persisted. The 512-KiB data and 768-KiB combined-request checks occur only after resolving and parsing the upstream output at execution. Compilation and rendering happen only during actual node execution and remain behind `shell.exec`, so editing, saving, import, and export cause neither a permission prompt nor render audit. The file panel checks only a nonempty output-path configuration and valid variable references; the executor validates the interpolated absolute `.html` or `.htm` path before queueing.

During one Workflow execution, `html_generator_ejs_generate` retains the complete output up to five MiB for downstream `node_output` bindings. Renderer events, run status, and persisted history snapshots reuse the existing approximately 10,000-byte UTF-8 history representation and append `[truncated]` when required; no HTML-specific history expansion, body file, or result repository is added. Structured outputs contain only `size`, while the file node retains only path and Writer metadata. An End node may likewise receive the complete in-memory value while its history representation remains bounded. HTML is neither specially classified as sensitive nor fully hidden in the first version, matching existing node-output history behavior. Documentation must state that `[truncated]` affects renderer and history representation only, never the value delivered to downstream nodes during that run.
