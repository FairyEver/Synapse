# Run each EJS render in a one-shot Worker

Every HTML Generator render compiles and executes EJS in a new Worker Thread rather than the Electron main process. The service owns scheduling, input and output limits, cancellation, memory limits, normalized errors, and unconditional Worker termination; Workers and EJS caches are never reused. Rendering has a fixed, caller-invariant five-second limit beginning when the Worker starts processing, after which the service returns `RENDER_TIMEOUT` and forces `worker.terminate()`; file persistence is outside that render timer but remains cancellable. Before launch, the service rejects templates over 256 KiB, strictly serialized JSON data over 512 KiB, or the combined serialized request over 768 KiB; after rendering it rejects HTML over 5 MiB, always measuring UTF-8 bytes and never truncating. Each Worker fixes `resourceLimits.maxOldGenerationSizeMb` at 128; an out-of-memory exit returns `RENDER_MEMORY_LIMIT` without retrying or falling back to the main process. Both public capabilities share one FIFO scheduler with two running Worker slots and four waiting render slots; excess work returns retryable `RENDER_QUEUE_FULL`, queue time is outside the five-second Worker timer, and cancellation or service shutdown removes waiting work and terminates running work. Once a render succeeds and passes the output limit, file generation releases its HTML rendering slot before invoking Text File Writer. File persistence therefore consumes neither a Worker slot nor an HTML queue position and remains governed by the Writer's target queue, permission, concurrent-change checks, and atomic commit. The file composition layer retains the entire request's cancellation and shutdown state and passes its signal to the Writer without adding HTML-specific file concurrency. Cancellation while queued, running in a Worker, or after rendering but before Writer invocation returns `RENDER_CANCELLED` and creates no file. Once Writer takes ownership, its native `ABORTED` error is preserved: cancellation observed before atomic commit cleans the temporary file and leaves the target unchanged, while a completed commit wins over a later cancellation and returns success. HTML Generator never deletes or rolls back an already committed file, and audit records the actual commit outcome. The legal worst accepted render path can approach 30 seconds when two active and three earlier waiting requests each exhaust a five-second startup watchdog plus five-second compile/execute window. Render failures use a closed normalized error protocol, preserve only a reliably extracted positive line number, and never expose raw EJS messages, source context, generated code, or stacks; file composition preserves Text File Writer errors instead of relabeling them as render failures. This isolates main-loop reliability failures but is not a security sandbox or a separate OS permission boundary, and packaged builds must keep the Worker, sourcemap, `app.asar`/`app.asar.unpacked` paths, and packaged-asar checks aligned.

Before queueing, the service recursively validates data instead of relying on `JSON.stringify` to discard unsupported values. The top level must be a plain object whose prototype is `Object.prototype` or `null`; nested values are limited to null, strings, booleans, finite numbers, arrays, and the same plain objects. It rejects dates, maps, sets, typed arrays, class instances, boxed primitives, functions, BigInts, symbols, undefined values, cycles, sparse arrays, custom array properties, accessors, symbol keys, and non-enumerable business properties. Repeated non-cyclic references are allowed but lose identity in normalization. Keys such as `__proto__`, `constructor`, and `prototype` remain ordinary JSON string keys and are never merged into options or assigned as prototypes. After validation, one serialization determines the data byte size, parsing that serialization creates the detached pure-JSON copy, and serializing `{ template, data: detachedCopy }` determines the full Worker request size. The validator never invokes `toJSON`, silently deletes a value, or coerces it to null; any violation fails the whole request with `INVALID_DATA`, and Workflow, App, and MCP all use this same path.

Each App IPC generation handler creates its own `AbortController`, subscribes it to `ctx.sender.onDestroyed`, passes the signal through rendering and, for file generation, into Writer, and removes the destroyed listener when the invocation settles. The two tabs therefore remain independently cancellable; switching tabs does not cancel either operation, while closing or reloading the system App aborts work when its WebContents sender is destroyed. The first version adds no cancel button, public cancel capability, MCP tool, request id, or cancellation field. Component unmount without WebContents destruction does not promise cancellation. Workflow continues to supply its run-context signal, while an MCP client timeout still does not imply server-side cancellation.

Workers use separate stdout and stderr pipes that the main process immediately drains and discards to avoid buffering and backpressure. Template `console` calls and direct standard-stream writes never enter application logs, audit, HTML results, or error responses, and no console-debug surface is exposed. Stream failures record content-free sanitized metadata only; continuous output remains subject to the same five-second termination. Canary tests prove that `console.log` and `process.stderr.write` payloads appear in neither logs nor returned results. This is a log-confidentiality boundary only: it does not prevent code from using files, networks, or other runtime capabilities and is not a sandbox.

Bootstrap registers exactly one `core.html-generator` service. That singleton owns normalization, `shell.exec`, render audit, the FIFO scheduler, Worker lifecycle, and `stop()`, and every App, MCP, and Workflow adapter resolves it from the registry instead of constructing a private instance. A separate singleton `core.html-generator-file`, created by `createHtmlGenerationToFileService`, is a stateless composition that calls the core render and then `core.text-file-writer`; it owns no scheduler, Worker, permission system, file queue, or stop behavior. The core accepts only an internal closed operation enum that maps to the two capability ids so each path records the correct render audit, never an arbitrary caller-supplied string. Registry dependencies and shutdown ordering are covered by tests; only the core cancels queued work and terminates Workers during shutdown.

Worker startup has a separate, caller-invariant `HTML_GENERATION_WORKER_START_TIMEOUT_MS = 5_000` watchdog configured with the required Chinese purpose and impact comment. The main process starts this watchdog immediately after creating a Worker. After module initialization and installation of both include blockers, the Worker sends exactly one `started` message immediately before compilation; the main process validates it, clears the startup watchdog, and only then starts the existing five-second compile-and-execute timer. Queue time counts toward neither timer. Startup expiry terminates the Worker and returns `RENDER_FAILED` with the safe message “渲染 Worker 启动失败”; cancellation that wins first remains `RENDER_CANCELLED`. Duplicate `started`, success before `started`, or any other protocol reordering is `RENDER_FAILED`. An abnormal task can therefore occupy a render slot for approximately five seconds of startup plus five seconds of compile/execute. Queue-batch budget tests cover the approximately 30-second render bound.

The internal Worker protocol is deliberately minimal and strict. `workerData` is exactly `{ template, data }` and contains no output path, overwrite flag, actor, source, capability, permission result, EJS option, or timeout. The Worker may send exactly one `{ type: "started" }`, followed by exactly one terminal `{ type: "success", html, size }` or `{ type: "error", code, line? }`. Worker error codes are limited to `TEMPLATE_COMPILE_FAILED`, `OUTPUT_TOO_LARGE`, and `RENDER_FAILED`; timeout, cancellation, memory exhaustion, queue rejection, and permission denial originate only in the main process. Worker messages never carry a message, stack, source, path, or raw exception, and the main process owns safe public message mapping. `line` is an optional positive integer. The main process applies a strict schema, treats unknown fields, types, ordering, or invalid sizes as `RENDER_FAILED`, and repeats type, Unicode, byte-count, and five-MiB checks before accepting success. Every terminal message ends the one-shot Worker. Protocol validation improves reliability but does not prevent same-authority malicious template code from forging Worker messages and is not a security boundary.

EJS 6.0.1 compile failures do not expose a reliable template line, so `TEMPLATE_COMPILE_FAILED` never carries `line` in the first version. For `RENDER_FAILED`, the Worker extracts a line only by matching `^ejs:(\d+)\n` at the beginning of the EJS `rethrow` message, requiring a positive integer no greater than the template line count computed with EJS's newline semantics. It retains only that number and immediately discards the complete message. An include blocker failure may therefore report the template line that invoked include after passing through `rethrow`. The implementation never parses a stack, `lineNumber`, column, generated-function location, or any other number, and omits rather than guesses a missing or out-of-range line. Template-authored error text cannot replace the real leading EJS line prefix. EJS upgrades must regress this exact behavior and temporarily omit line information if the format changes.

The shared error module is the only source of public render messages; App, MCP, and Workflow do not rewrite them. The fixed mappings are: `INVALID_TEMPLATE` → “模板必须是至少 1 个字符的有效 Unicode 文本。”, `INVALID_DATA` → “数据必须是可严格 JSON 序列化的顶层对象。”, `TEMPLATE_TOO_LARGE` → “模板超过 256 KiB 限制。”, `DATA_TOO_LARGE` → “数据超过 512 KiB 限制。”, `INPUT_TOO_LARGE` → “模板与数据合计超过 768 KiB 限制。”, `TEMPLATE_COMPILE_FAILED` → “EJS 模板编译失败。”, `OUTPUT_TOO_LARGE` → “生成的 HTML 超过 5 MiB 限制。”, `PERMISSION_DENIED` → “没有执行 EJS 模板的权限。”, `RENDER_QUEUE_FULL` → “HTML 生成队列已满，请稍后重试。”, `RENDER_TIMEOUT` → “EJS 模板渲染超过 5 秒限制。”, `RENDER_MEMORY_LIMIT` → “EJS 模板渲染超过 Worker 内存限制。”, `RENDER_CANCELLED` → “HTML 生成已取消。”, and `RENDER_FAILED` → “EJS 模板渲染失败。”. Startup-watchdog failure is the sole fixed override: `RENDER_FAILED` with “渲染 Worker 启动失败。”. Protocol errors, invalid output Unicode, size mismatches, ordinary runtime failures, and include failures use the generic render-failed message. `line` remains a separate field. Only `RENDER_QUEUE_FULL` is retryable, and Writer errors keep their own code and message.

The first release formally supports packaged macOS arm64 and Windows x64. Both platforms run shared unit and integration coverage and must launch a real packaged Worker render rather than merely checking file presence. `check:packaged-asar` verifies the Worker, sourcemap, EJS runtime entry, package metadata, and license on both. Output paths follow the current operating system's absolute-path semantics: POSIX rejects Windows drive paths and Windows rejects POSIX `/tmp` examples. Tests cover backslashes, drive letters, UNC and device-path safety on Windows and symlink plus real filesystem case behavior on macOS, while final target safety remains Writer-owned. Linux should remain source-portable where practical but is not a first-version release or acceptance commitment. Documentation and tests include both Windows and POSIX examples.

Acceptance is layered. Shared tests cover strict schemas, JSON normalization, Unicode, and exact byte boundaries. Real EJS Worker integrations cover tags, escaping, explicit `data`, ordinary JavaScript, empty and whitespace output, mutable detached data, and one-shot state isolation. Canary tests prove include cannot read relative or absolute files and stdout/stderr cannot leak content. At least one real infinite-loop Worker integration proves termination at approximately the five-second render limit; other timing and race matrices use fake timers and an injected Worker factory. CI never deliberately exhausts machine memory: an injected `ERR_WORKER_OUT_OF_MEMORY` verifies normalization. Scheduler tests cover FIFO, concurrency two, queue four, queue rejection, startup and render timers, first-terminal-state races, cancellation, shutdown, protocol ordering, and the approximately 30-second legal worst render path derived specifically from two active slots, four accepted waiters, and two five-second phases. Permission and audit tests cover pre-authorization validation, denial, success, failure, split Writer audit, and content-free logs. Real temporary-directory Writer tests cover UTF-8, zero bytes, case-insensitive HTML extensions, overwrite, error preservation, and the commit cancellation boundary. Workflow, App, and MCP tests cover their confirmed schemas, state, history, sharing, migration, UI races, action mapping, safety descriptions, and the revised 60-second MCP route timeout. Packaged macOS and Windows smoke tests render through the actual unpacked Worker and EJS runtime.

Template text, every string value and object key in data, and rendered HTML must be well-formed Unicode without isolated UTF-16 surrogates. Invalid template text fails with `INVALID_TEMPLATE`, invalid data text fails with `INVALID_DATA`, and invalid Worker output fails with `RENDER_FAILED`. The service never calls `toWellFormed()` or silently substitutes `U+FFFD`; it measures UTF-8 bytes and writes only after the check, keeping the returned string, reported size, and UTF-8 file content consistent. This additional restriction belongs only to HTML Generator and does not change shared Text File Writer behavior for existing formats.

Inside the Worker, the project-owned narrow `render(template, data)` wrapper performs two explicit EJS stages. It first calls `ejs.compile(template, fixedOptions)` and maps parsing, code-generation, or `new Function` failures to `TEMPLATE_COMPILE_FAILED`; it then invokes the returned one-shot function with detached data and maps all execution failures, including a template-thrown `SyntaxError` or the controlled include blocker, to `RENDER_FAILED`. The five-second limit covers both stages, the compiled function never leaves or outlives its Worker, and only a reliably extracted positive line number can cross the protocol boundary. Business code receives neither the compile API nor its output.

After execution, the Worker first verifies that HTML is well-formed Unicode and computes `Buffer.byteLength(html, "utf8")`. Output above five MiB returns `OUTPUT_TOO_LARGE` without posting the complete string; valid output posts `{ html, size }`. The main process independently rechecks message type, Unicode, UTF-8 byte count, and the limit before accepting the result. A size mismatch is a protocol failure reported as `RENDER_FAILED`, and the Core Service returns only the main process's confirmed size. File generation releases its render slot and invokes Writer only after this second check. Output construction that hits the Worker heap limit before a complete string exists remains `RENDER_MEMORY_LIMIT`, and the first version neither streams nor truncates output.

Worker completion uses one atomic terminal-state transition. An accepted success message wins over later cancellation or timeout and clears timers and listeners. Cancellation selected first returns `RENDER_CANCELLED` and terminates the Worker; the five-second timer selected first returns `RENDER_TIMEOUT`; both ignore all later messages, errors, and exits. With no explicit cancellation or timeout, `ERR_WORKER_OUT_OF_MEMORY` maps to `RENDER_MEMORY_LIMIT`, while other Worker errors, unexpected exits, or exit without a valid protocol message map to `RENDER_FAILED`. Near-simultaneous events use whichever transition atomically selects the terminal state first. A failure from `worker.terminate()` is recorded only in redacted structured logs and never replaces the selected business result. After file generation accepts a render result and enters Writer, the separate Writer commit boundary governs all later cancellation races.

The Worker follows the existing Text Extractor build and packaging pattern. Source and launcher live under `desktop/app-capabilities/html-generator/main/`; `tsconfig.electron.json` explicitly includes the standalone Worker source, and the existing TypeScript build emits `worker.js` and its sourcemap without a separate esbuild pipeline. Electron packaging unpacks the complete compiled HTML Generator capability and `node_modules/ejs/**`, resolves production paths from `app.asar` to `app.asar.unpacked`, and uses the existing development/test resolution strategy with an injectable Worker factory. `check:packaged-asar` verifies service, launcher, Worker, both JavaScript and sourcemap files, plus the EJS package metadata, license, and actual CommonJS runtime entry. A packaged smoke test starts the real Worker and completes a standard render. The design uses neither `extraResources` nor a duplicated EJS copy and never unpacks only the entry script while omitting its runtime closure.
