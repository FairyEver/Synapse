# Treat EJS templates as executable configuration

The HTML Generator uses the official EJS runtime as a direct production dependency to render a template string with structured data under fixed options, rather than maintaining a compatible parser. Desktop pins the direct runtime dependency exactly to `ejs@6.0.1`, does not reuse electron-builder's transitive `3.1.10`, and exposes only a project-owned narrow `render` type at the Worker boundary instead of adding the stale `@types/ejs` package or propagating EJS APIs through business code. The project records `6.0.1` only as the current latest release, not as an “official safe version”; every explicit future upgrade must re-run the fixed-option, standard-tag, data-root, include-blocking, normalized-error, timeout, termination, and packaged-build contract tests. It fixes `_with: false`, `strict: true`, `localsName: "data"`, standard `<% %>` delimiters, synchronous rendering, `compileDebug: true`, `debug: false`, `rmWhitespace: false`, `cache: false`, `filename: false`, empty root and views, the official `ejs.escapeXML`, no execution context, no output function, no destructured locals, `unsafePrototypeLocals: false`, and `legacyInclude: false`. This preserves whitespace, enables Worker-local line extraction without exposing source context, and does not support async templates or top-level `await`. The intended contract also fixes client compilation off; because EJS 6.0.1 does not actually read a `client` option, the implementation must omit that ineffective property and enforce the synchronous string-returning `render` surface through its narrow wrapper rather than inventing an option. Templates access the input object through an explicit `data` root without mistaking that convention for a security boundary. Callers cannot supply EJS options, custom delimiters, escaping functions, execution context, caching, filenames, roots, views, includers, or file loaders. EJS 6 can still resolve an absolute `include()` when path options are omitted, so the Worker supplies an internal includer that always throws a controlled error and replaces `ejs.fileLoader` with another throwing function for defense in depth. Relative, absolute, and indirect calls through EJS's include function all fail as sanitized `RENDER_FAILED` errors whose message may state that the first version does not support include but never reveals the attempted path or raw exception. Tests use a temporary canary file to prove that no include form can read it. This closes only EJS's built-in loading channel; ordinary JavaScript still has the Worker's application-level runtime authority, so the boundary is not a sandbox or general file-access prevention. Its Workflow node persists the EJS template as author-maintained executable configuration and binds only data from upstream instead of replacing or interpolating the template; the generic Workflow Engine no longer assumes every `config.template` uses Workflow `{{variable}}` interpolation, leaving template semantics to each executor while Text and End retain their own existing interpolation. App and MCP callers that explicitly submit templates are likewise requesting code execution. Both capabilities are high risk and request the existing `shell.exec` permission before queueing, while Workflow sharing reports the `template` path as `shell.execute`; these names classify the existing local-code execution boundary and do not mean EJS runs through a system shell. Workflow import reuses the existing mandatory risk step to identify the HTML Generator node and `template` field and state that EJS executes JavaScript. Local creation, editing, Automation, App, and MCP continue to use the same PermissionGuard and audit boundary as existing executable nodes such as Script; HTML Generator does not add a second trust database keyed by template content or digest. Any future requirement to reconfirm changed code must be designed uniformly for Script, EJS, and other executable configuration rather than introduced here as a special case. Every request first completes strict schema, Unicode, JSON, byte-limit, and final file-path validation; it then requests `shell.exec`, enters the shared scheduler only after authorization, and invokes Writer only after a confirmed render. Pre-authorization validation failures produce redacted operational logs but no shell permission audit. Permission denial records one denied event and creates no Worker. Once authorized, queue rejection, cancellation, timeout, memory exhaustion, compile failure, or runtime failure records one failed event for the corresponding capability, while successful rendering records allowed. File generation keeps this render audit separate from Writer's existing path-resource permission and audit; a later write failure never rewrites the render outcome. Render audit resources are capability ids, and metadata is limited to source, byte counts, duration, result, and normalized error code, never template, data, HTML, output path, or raw EJS error content. Rendering must run outside the Electron main process with a timeout and forced termination for reliability, without claiming a security sandbox, while arbitrary upstream-supplied templates remain a separate future high-risk capability.

The normalized detached data object remains ordinary mutable JavaScript data inside its one render. The Worker does not freeze, deep-freeze, or proxy it; template code may add, change, or delete fields and observe those changes later in the same execution. Such mutations never write back to the App or MCP caller, Workflow upstream output, or main-process object, and modified data is not returned. Every parallel or later render receives its own independent copy, and Worker termination discards both data mutations and template global state. Mutation-related execution failures remain `RENDER_FAILED`.

“Stable generation” describes a fixed EJS version and options, strict validation, bounded execution, termination, and reliable persistence; it is not a reproducible-build guarantee. Synapse does not replace or freeze `Date`, `Math.random`, locale, timezone, `process.env`, or other runtime state and does not inject timestamps, seeds, or a fixed timezone. Templates that read time, randomness, environment, files, or networks may produce different bytes from identical template and data inputs. One-shot Workers remove reused cache and global state between requests but do not remove nondeterminism within a render. Only templates authored to depend deterministically on data can expect identical inputs to produce identical outputs.
