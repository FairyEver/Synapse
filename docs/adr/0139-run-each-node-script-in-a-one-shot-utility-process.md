# Run each Node script in a one-shot Utility Process

Status: deprecated; replaced by accepted ADR-0204

Each Node.js Script Execution run receives a new Electron Utility Process that is never reused. User code does not run in the Electron main process or a Worker Thread. Workflow and Automation share one scheduler with two running slots, eight queued slots, a five-second startup handshake limit, and a sixty-second queue-wait limit. The user-configurable execution wall defaults to sixty seconds and ranges from one to nine hundred seconds. It starts when the child accepts the request and continues through finalization and process cleanup.

V1 fixes source at 256 KiB UTF-8, strict JSON input and result at 1 MiB each, logs at 1,000 entries, 16 KiB per entry and 1 MiB total, and outstanding broker calls at sixteen. Each child starts with V8 old-generation 256 MiB and semi-space 16 MiB limits; the supervisor terminates a process whose sampled RSS exceeds 512 MiB. The latter is an observed safety threshold rather than a hard cross-platform process-memory quota. The child receives a fixed platform-minimal environment rather than inheriting credentials, proxies, or user variables, and source, input, grants, and trusted identity never travel through argv, environment variables, or temporary files.

The main process sends work over a dedicated versioned MessagePort protocol and resolves every run token to trusted actor, Workflow or Automation identity, revision, node or Action, and resource grants. The child cannot self-assert those values. Every message is schema- and size-checked; malformed, unknown, replayed, or contradictory messages fail the run. On cancellation or timeout, the host freezes the broker, cooperatively cancels outstanding work that has not crossed its own commit point, requests child cancellation, calls `kill`, escalates to a platform force kill, confirms exit and reap, and only then releases the scheduler slot. Timeout, cancellation, crash, OOM, invalid IPC, and unexpected exit remain distinct stable outcomes.

Receiving the sole result candidate atomically moves the run into `finalizing`. From then on, the broker refuses every new timer, filesystem, fetch, or log side-effect message. The host validates the protocol, strict JSON value, result size, and absence of outstanding broker operations, actively terminates the Utility Process, and confirms exit and reap. Only then may it atomically commit `success` and `outputs.result`; the expected finalization termination is not a crash. Failure to confirm cleanup within the bounded escalation path returns `RUNNER_CLEANUP_FAILED`, leaves the affected scheduler capacity quarantined or occupied, and never reports success. Cancellation selected before finalization wins; once finalization begins, cleanup and its success-or-cleanup-failure decision win over later cancellation.

A script that explicitly returns while broker calls remain outstanding fails with `UNAWAITED_HOST_OPERATION`; effects already beyond their own commit points are not rolled back. Public APIs do not expose child processes, workers, clusters, shells, addons, WASI, Electron, raw sockets, file handles, or transferable broker ports. A conforming script therefore cannot create OS descendants, and one-shot process termination removes its timers and background handles. V1 guarantees reaping the Utility Process, not finding or cleaning arbitrary descendants created through a hostile host escape; stronger process-tree and hard-memory guarantees would require platform-native containment and constitute a separate scope.
