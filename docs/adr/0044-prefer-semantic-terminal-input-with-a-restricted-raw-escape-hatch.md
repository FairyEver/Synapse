# Prefer semantic terminal input with a restricted raw escape hatch

Terminal automation primarily sends an ordered sequence of semantic actions: control-character-free `text` and fixed-enum `key` actions such as Enter, Tab, Escape, arrows, Backspace, Ctrl+C, and Ctrl+D. The service owns key encoding so callers never construct platform control sequences. A command submission is only a convenience expression for `text` followed by Enter. Because explicit Enter is the submission boundary, ordinary `text` rejects CR, LF, ESC, NUL, and other prohibited control characters; future multiline paste must use a separately defined `paste` action or the restricted raw path.

After validating the session lease, the service writes the actions in order and without allowing another automated writer to interleave, but this is not transactional atomicity: a PTY can fail partway through. Every response therefore identifies the operation, resulting input revision, acceptance time, and the actions and bytes accepted before success or failure so callers never infer all-or-nothing delivery. A separate high-risk raw-input capability remains only as an advanced escape hatch with its own permission boundary, not as the normal command or TUI interface. Audits record caller, action types, key names, counts, byte counts, and outcome, but never text or raw bodies, passwords, or control-sequence contents.
