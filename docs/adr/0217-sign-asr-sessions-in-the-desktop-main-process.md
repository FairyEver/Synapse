# ADR 0217: Sign ASR Sessions in the Desktop Main Process and Hand Out the URL

## Status

Accepted

## Context

语音输入要把麦克风音频送到腾讯云的实时语音识别，而腾讯云的要求是：客户端在
WebSocket 握手时带上 `secretid` 和用 SecretKey 算出来的 `signature`。

两个客户端都拿不到 SecretKey，也不该拿到。iOS 包会被分发到设备上，包里的任何
东西都等于公开；桌面渲染进程是 web 技术栈，一份密钥放在那里迟早会出现在某个
日志、某个 devtools 面板或者某个前端包里。所以签名必须发生在持有密钥的这一侧，
而持有密钥的地方只有桌面主进程。

同样要回答的是：为什么不让后端签。理论上可以 —— 服务端也能存这份密钥，而手机
本来就连着服务端。但那会引入一条与现有链路平行、却更弱的路径：手机要终端功能就
必须连上自己的电脑，签名的可用性因此不会因为多一个服务端接口而变好；反过来，
密钥会多存在一个地方，多一套轮换与审计。腾讯云的这份凭据是用户自己在控制台建
的，放在用户自己的机器上比放在我们托管的服务上更符合这把密钥的归属。

### 签名能不能脱离音频流

这是整件事可行的前提。签名原文是**被签名的请求本身**：把除 `signature` 之外的
所有握手参数按字典序排好，拼成一条不带协议的 URL，再对这条字符串做 HMAC-SHA1。
音频走的是握手成功之后的 WebSocket 数据帧，不参与签名。所以签名与音频是解耦的：
可以先把整条 URL 签好，再拿着它去连。

另一条路是 STS 临时密钥，这里走不通：这个接口的鉴权是 URL 上的 `signature`
参数，不是云 API 的 TC3 签名，STS 凭证在协议里没有对应的传参位置。

## Decision

- **签名由桌面主进程完成。** 渲染进程与 iOS 从不接触 SecretKey，它们拿到的是一条
  已经带好 `signature` 的完整 URL，以及一个和它配套的 `voiceId`。
- **密钥分成两处存放。** `appid` 与 `secretid` 不是密钥（secretid 相当于用户名），
  放普通设置项 `app.voice.settings`，在设置界面里可见可改；`secretkey` 走既有的
  加密存储 `app.secrets.items`。设置接口只回传 `hasSecretKey`，不回传密钥值 —— 
  表单里那一格留空表示"不改"，要清掉得显式点清除。
- **URL 有有效期，一次一签。** 默认 5 分钟。每次建立连接都重新签一次，`voice_id`
  也每次换新的；连接中断后旧的 `voice_id` 一律作废。签名过期或鉴权被拒
  （腾讯云返回 4002）时，客户端换一条新签名重连一次；服务端明确拒绝
  （如 4003 服务未开通）则不重连，因为换个签名解决不了问题。
- **手机经既有 intent 通道要签名。** 新增 `asrSign` intent，结果里带
  `signedAsrUrl` / `asrVoiceId` / `asrExpiresAt`。不复用
  `terminal.session.control`，而是新增更窄的 `voice.asr.sign` 权限，并按文件中继
  的写法配一个资源（`voice:asr`）：能签一次语音会话不等于能往 PTY 里写东西。
- **没有服务端组件。** 语音识别是客户端直连腾讯云，签名的职责落在桌面主进程。
  这里说的"后台"就是主进程，不是 `server/`。
- **未配置时隐藏入口，不报错。** 缺 appid / secretid / secretkey 时
  `signSession` 抛 `VoiceNotConfiguredError`，输入区据此不显示麦克风，而不是让
  用户点一下再弹一个失败框。

## Consequences

麦克风入口的可用性跟着桌面端的配置走，而配置是用户自己填的 —— 与手机是否连上、
后端是否在线都无关。

密钥轮换只发生在一个地方：用户在设置里改，或者在他的腾讯云控制台换一把。

签名是短时凭据，但它仍然是一条可用的入场券：拿到它的人可以在有效期内开一路识别，
花的是账号的语音额度。所以它按 5 分钟签发，而且只发给已经与桌面配对的手机。
