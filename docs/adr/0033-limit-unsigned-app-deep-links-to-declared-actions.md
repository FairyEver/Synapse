# Limit unsigned app deep links to declared actions

Synapse application deep links use the extensible `synapse://app/<app-id>/<action>?<params>` shape, but only Actions explicitly exposed through `deepLinks` in a main-process-safe system application capability manifest may be invoked; registering an application or capability never exposes it automatically, and the protocol router must not hardcode application-specific branches. Existing authentication, update, and Skill-install protocol routes remain separate from this application-action frame. These links are intentionally unsigned, may be handwritten and long-lived, and execute without Synapse confirmation or Origin, source, or caller-trust checks; the accepted trade-off is that Action allowlisting, strict parameter validation, and runtime preconditions—not caller authentication—form the deep-link security boundary. The router requires host `app`, exactly two path segments, no credentials, port, or fragment, and each Action rejects duplicate, missing, empty, or unknown parameters before applying one standard URL decode and its shared capability schema. Once a URL enters the application-action frame, invalid applications, Actions, or parameters produce one sanitized native error and a structured warning without focusing the main window, recording the raw URL, guessing another target, or falling back to an application UI. Every accepted protocol event executes once in arrival order without deduplication, replay prevention, or deep-link-specific throttling; one failed event does not block later events. After an application/action pair is formally released, its existing parameter names and semantics remain stable and only backward-compatible extensions are allowed; an incompatible contract requires a new Action while the old Action remains available, whereas the current unreleased baseline may still be replaced in place.
