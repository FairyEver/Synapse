# Separate HTML generation from content execution

The HTML Generator treats literal active HTML and raw interpolated strings as text, and generation success means only that rendering and reliable file persistence completed. It does not sanitize, parse into a DOM, preview, execute, fetch resources from, validate the safety or standards compliance of, or automatically open the output; workflows that intentionally open a result must invoke the existing File Opener capability as a separate permissioned and audited step.

“Complete HTML” means the complete, untruncated EJS render result rather than a structurally complete HTML document. Empty strings, whitespace-only results, fragments, and full documents are all valid. The generator does not require or add a doctype, `html`, `head`, or `body` element, does not add line breaks or a final newline, and preserves rendered text and whitespace exactly. File generation may therefore create a zero-byte `.html` or `.htm` file. Apart from the agreed well-formed-Unicode and five-MiB checks, “HTML” remains a caller-declared use rather than content detection or structural validation.

The first version does not expose a generic `validate` capability, MCP tool, or Workflow node. Both generation entries perform complete request validation, compile EJS, and render against the real data, returning `TEMPLATE_COMPILE_FAILED` for syntax failures and `RENDER_FAILED` for data-dependent execution failures. The string-returning generation entry, which does not itself invoke Writer or open the result, is the supported way to test a template and data pair. Future HTML linting, accessibility analysis, security review, browser compatibility checks, or compile-only inspection require separately named capabilities with their own precise contracts rather than an ambiguous `validate` operation.
