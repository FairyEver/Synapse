# Do not hide uncertain problem-feedback outcomes

Problem-feedback submission returns `{ success: true }` only after the server has durably persisted the record, and it does not expose the record ID, receipt time, or body. Determinate validation and provable non-commit failures use stable HTTP errors; when timeout, disconnect, or ambiguous database commit prevents a determinate response, the server sends no fabricated unknown JSON and the desktop exposes `SUBMISSION_OUTCOME_UNKNOWN` rather than claiming failure. The Agent must not automatically retry an unknown outcome: it explains the duplicate risk, and only the user can choose to prepare, review, and confirm another submission. V1 adds neither an idempotency key nor body-based deduplication in order to preserve the strict three-field record contract.
