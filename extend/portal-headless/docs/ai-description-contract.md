# SDK 面向 AI 的描述规范（v1）

本规范把 `conventions.md` 第 33 条落实为字段和验收要求。适用于页面、注册能力、公开业务方法及其输入输出，
目标是让调用方只读 SDK 描述与真实结果，就能选功能、填参数、理解数据、完成动作。

**权威类型：`src/catalog/ai-contract.ts`；业务定义：`src/catalog/contracts-*.ts`。**
规范不另建一份运行时提示词注册表。JSON 样例和页面文档用于解释与测试，不能替代 SDK 返回的权威定义。
类型中的可选字段用于兼容历史契约，不代表业务上可以省略：以下注明「适用时必填」的内容必须补齐。

## 0. 页面等价范围

遵循用户 2026-09-22 的判断宗旨：SDK只与Portal页面功能性和可见性对齐。契约覆盖页面展示字段、实际操作需要的内部参数和前后步骤，不覆盖后端DTO中与该页无关的全量数据语义。

对应页面没有显示、操作也不用的字段，不要求SDK新增返回或解释；既有兼容透传可用明确的扩展边界说明，不得作为展示或业务判断来源。不能以其他应用中的相似页面扩大范围。页面原值显示、未指定单位时，说明原值显示及不做换算即可；页面已有单位、标签、格式化、条件保护必须复现。动态下钻仅用于页面实际需要的动态数据，不能为了补全无关后端对象而新增要求。

完成条件与撤销说明同样以页面行为为准：不得承诺页面没有的完整历史恢复，也不因缺少这种能力设置gap。保留真实网络失败、权限错误和不确定写入说明；页面可见动作与Java协议冲突仍是具体功能差距。

## 1. 返回层次与职责

| 层次 | 入口及必须返回的信息 | 不得混淆 |
| --- | --- | --- |
| 页面 | `catalog.describePage(pageId)`：页面标识、真实能力清单及各能力的用途、适用时机、执行效果、边界和描述入口 | 能力排列顺序不是执行顺序；多个流程共享页面路径不代表它们可以互相代办 |
| 能力 | `catalog.describe(capabilityId)`：标识、真实执行绑定、参数契约及 `ai: AiContract` | `ok: true` 只代表找到能力，不能证明描述完整或操作已成功 |
| 方法 | `catalog.listMethods()` / `catalog.describeMethod(sdkPath)` 提供已登记公开方法说明；已绑定能力也可通过能力描述获取。必须说明真实签名、参数顺序、返回值与业务能力的关系 | `sdkPath` 不是 HTTP URL；不能拿多参数方法的签名当成 `invoke(id, args)` 的参数对象 |
| 运行时数据 | 业务调用返回本次数据；动态表单由契约指定的真实入口返回字段定义 | 静态描述不含本次真实用户 ID、候选集或审批节点，不能把样例值当成真实数据 |

页面尚未实现、能力未绑定、描述缺失、已提供描述但仍有缺口，必须分别表示。
若页面字段未承载公共背景，可通过其能力的 `prerequisites` / `boundaries` 提供；不能仅靠页面标题推断上下文。
公共工具方法同样需要用途与输入输出说明；无业务副作用的本地工具用 `effect: local`。

## 2. `AiContract` 顶层字段（固定名字）

除 `gaps`、`examples` 外，下表字段均为类型必填；不能用空字符串或「同上」「按实际情况」占位。

| 字段 | 类型 | 内容与空值约定 |
| --- | --- | --- |
| `purpose` | string | 对象 + 动作 + 结果，例如查询指定日期各会议室已占用时段。不能只重复标题 |
| `whenToUse` | string | 用户意图、与相近功能的区别及使用时机 |
| `boundaries` | string[] | 数据范围、未覆盖的行为、不能据此得出的结论；确无额外边界才可 `[]` |
| `effect` | enum | `read` 查询；`prepare` 只读准备；`write` 实际修改或产生外部副作用；`local` 不发业务请求的本地计算。以实现为准，不由 HTTP 方法推断 |
| `prerequisites` | string[] | 身份/租户上下文、上游数据、必要配置和业务前提；不能强加用户未要求的确认步骤 |
| `inputs` | Record<string, AiParameter> | 输入路径到参数语义；无参为 `{}`。覆盖所有可调用参数，包括嵌套字段和绑定额外接收的参数 |
| `output` | object | 见第 4 节，描述 SDK **最终返回值**，包括原始响应模式的差异 |
| `consume` | string[] | 读取、展示、筛选、判断、聚合与传递数据的步骤；至少一条本能力专属说明 |
| `steps` | Step[] | 条件步骤，见第 6 节；无后续动作可 `[]`，但 `completion` 必须说明何时交付并结束 |
| `completion` | string | 操作完成的可观察条件、返回给用户的事实以及仍未完成的业务状态 |
| `failures` | string[] | 已知失败的识别条件、含义、恢复/核实和重试规则，见第 7 节。已知存在校验/网络失败不得留空 |
| `idempotency` | string \| null | 写动作必须准确说明实际防重及重试边界；`null` 仅代表该能力不涉及写入防重，不代表「情况未知」 |
| `evidence` | Evidence[] | 至少一项可定位依据与其证明范围；不能只给目录名 |
| `gaps` | string[]，可选 | 具体未说明或未验证的事项及影响；有缺口就必须列，空数组不自动证明完整 |
| `examples` | Example[]，可选 | 复杂映射、条件分支宜提供内置输入/结果/解释；存在时必须符合第 8 节格式 |

**必需语义与文本长短无关。** 已知业务规则须写具体，未知规则须进入 `gaps`；不能为了详尽编造时区、状态或权限。

## 3. `inputs`：参数含义、来源和边界

| `AiParameter` 字段 | 类型 | 要求 |
| --- | --- | --- |
| `meaning` | string，必填 | 业务含义；ID 必须点明实体，名称与 ID 不可混用 |
| `source` | string，必填 | 用户提供、SDK 生成、原输入或上游能力的具体字段；不是让用户手填系统 ID |
| `type` | string | 采用第 5 节类型词表；嵌套字段、联合类型、数组等不能从现有 `kind` 得出的类型必须写 |
| `required` | boolean | 顶层静态必填以 `describe().params[].required` 为准，若重复声明必须一致；嵌套和绑定额外参数必须声明 |
| `requiredWhen` | string | 条件必填时必写具体条件及判定字段；例如 `tasks` 非空时哪些节点必须选人 |
| `nullable` | boolean | 表明可否传 `null`，不等于可省略。允许时还须写 `nullMeaning` |
| `omitted` | string | 可省略参数必须说明省略后 SDK/后端如何处理；未知默认行为不能写「默认今天」 |
| `default` | string | 对已知默认值作文字说明，指出是 SDK 补齐还是后端决定；这是说明，不是要原样发送的参数 |
| `format` | string | 时间、日期、标识符编码等有格式约束时必写；时间说明时区及边界，未知则记缺口 |
| `unit` | string | 金额、时长、比例等有量纲时必写；不得把分当元、0.1当10元 |
| `nullMeaning` | string | `null` 的业务含义；如清空字段、不限筛选，不得凭一般习惯推定 |
| `constraints` | string[] | 范围、长度、枚举语义、互斥/联合条件、跨字段规则和非法输入处理。分别标明 SDK 校验、后端规则或调用建议 |
| `options` | Array<{ value: string \| number; label: string }> | 有限枚举的真实取值及业务含义；`value` 保留原类型，`label` 非空。同类型取值不得重复，数字 `3` 与字符串 `"3"` 不自动互换；不接受布尔、null、对象或非有限数 |
| `lookup` | object | 有真实候选入口时填写下表；缺入口须列缺口，不能虚构能力 ID |

`lookup` 固定字段：`capabilityId: string`、`args: Record<string, unknown>`、`valueField: string`、`labelField: string`。
`args` 只放已知固定查询值；待用户提供的关键字与其目标参数写在 `source` / `constraints`。
`valueField` / `labelField` 是候选响应中的路径。明确候选是选择一个、多个还是组织树逐级下钻。
对外参数表的 `kind/options/lookup` 与精细说明必须一致，不能一处说必填、一处说可省略。
`ai.inputs[name].options` 存在时由描述装配优先使用；与旧注册表选项冲突时，必须给出正确口径的证据，
并把尚未复核的部署差异列入 `gaps`，不能为了与过时取值一致而发布错误说明。
空 `options` 仅可作为尚未补齐的结构存在，不能视为完整枚举；完整检查会拒绝空数组。
检查器校验形状、重复值和已知简单类型矛盾，不能凭标签判断业务状态含义是否正确，仍需独立业务测试。

**以真实调用入口为准盘点输入。** `requestId` 等可能由 invoke 绑定增加，不能只遍历原始 `params` 后声称覆盖全了；
也不能看到 `write: true` 就臆造 `requestId`。没有防重包装的调用，传这个参数也不会自动获得防重。

## 4. `output` 与 `AiField`：每一项数据怎么理解

`output.shape: string` 总述根类型与容器；`output.fields: AiField[]` 逐字段定义；
`output.empty: string` 说明本能力真实可能出现的空值；三者必须一致。

| `AiField` 字段 | 类型 | 要求 |
| --- | --- | --- |
| `path` | string，必填 | 第 5 节路径，根值也须用 `$` 描述。父容器、数组元素与叶子字段分别说明 |
| `type` | string，必填 | 第 5 节类型；不以 `T`、未展开 DTO 名或「看返回」替代结构 |
| `meaning` | string，必填 | 字段的业务含义与用途；ID 明确实体及可用于哪个动作 |
| `optional` | boolean | 字段能否缺席；确认后显式写，历史省略不构成已验证为必有的证据 |
| `nullable` | boolean | 字段存在时能否为 `null`；已知可空时说明 `nullMeaning` |
| `values` | Record<string, string> | 有限枚举或状态的每个已知值与含义；未知值如何处理写入 `constraints`，不得瞎映射为成功 |
| `format` / `unit` | string | 有格式/单位时必填，约定同输入 |
| `constraints` | string[] | 数据范围、顺序、精度、关联规则、完整性与不能推导的结论 |
| `nullMeaning` | string | 明确 `null` 的含义 |
| `source` | string | ID 来源、统计口径、关联对象等需要区分来源时必填 |

- `[]`、`{}`、`null`、缺席、空字符串、`0`、`false` 分别说明，不可统称「没数据」。
- 分页明确 `list` 是当前页、`total` 的统计范围、翻页方式与终止条件。没有计数字段就不能假定完整总量。
- 可选字段与 `null` 分别处理；对象属性为 `undefined` 时 JSON 序列化可能丢键，根值 `undefined` 也没有合法 JSON 值，必须说明上层如何识别这种返回。
- SDK 为兼容透传页面无关扩展字段时，应在容器或通配路径说明其不属于页面消费契约；无需枚举这些扩展内部字段，不得把它们包装成可理解、可展示或可操作的数据。

### 动态数据的例外

只有结构真实取决于运行时表单/流程，才可写 `output.dynamic`：
`{ sdkPath: string, args: Record<string, unknown>, instructions: string }`。
必须给真实可调用入口、固定参数与其余参数来源，说明返回定义中的哪个字段表示必填、枚举、嵌套结构和业务数据键。
`dynamic` 不能替代已知静态字段，也不能用来绕过缺口检查。上层拿不到动态定义时，须明确无法解释/填写哪些数据。

## 5. 路径、类型及映射表达式

字段路径属于**说明语法**，不是代码或可执行 JSONPath：

| 写法 | 含义 |
| --- | --- |
| `$` | 返回根值，例如提交返回的单据 ID，而非 `{ id: ... }` |
| `id` / `payload.id` | 根字段 / 嵌套对象字段；历史 `$.id` 归一化为 `id` |
| `variables.费用申请类型` | 中文等 Unicode 字段名按实际返回键保留，不改成不存在的英文键 |
| `list` / `list[]` / `list[].id` | 数组容器 / 一个元素的结构 / 元素字段 |
| `assignees.*` / `assignees.*[]` | 动态字典任一键的值 / 该值数组的元素；必须解释键从哪里来 |

同一字段不能用两种路径重复登记。字段名含点号等歧义字符时，须先扩展权威路径协议与检查器，禁止自行发明转义规则。

新写字段使用类型词表 `string / number / integer / boolean / object / array / null / undefined / unknown`；
联合类型用 `string | number`，数组元素通过 `[]` 路径展开。历史 `number[]`、`Record<string, ...>` 可保留，
但须展开关键结构。`unknown` 只用于明确尚未理解的部分并登记缺口，不能成为完整交付的兜底。
`nullable` 管理可空性，`optional` 管理缺席；与联合类型中的 `null/undefined` 不能相互矛盾。
`values` 的键因 JSON 语法总是字符串，真实数值类型仍由 `type` 指定，例如 `integer` 的 `"1"` 表示数值 `1`。

## 6. `steps`：调用动作、条件与数据映射

| 字段 | 类型 | 规定 |
| --- | --- | --- |
| `role` | enum | `required` 满足条件后必须执行；`optional` 按用户意图选择；`recovery` 失败恢复；`cancel` 用户要撤销时执行 |
| `when` | string | 可判断的具体条件，引用已说明输入/输出，不能只写「下一步」 |
| `capabilityId` 或 `sdkPath` | string | 可调用动作优先用真实能力 ID；未注册公开方法用真实 SDK 路径。二选一，不能指向尚未实现功能 |
| `mapping` | Record<string, string> | **键 = 目标输入路径，值 = 来源表达式**。不要反写；无参动作可 `{}` |
| `instruction` | string | 选择规则、单项/批量、转换、剩余参数获取、执行后判断。无调用目标时只能描述本地解释、向用户补问或交付结果 |

来源表达式统一为 `result.<字段路径>`、`args.<输入路径>`、`user.<已说明的用户选择>`、`context.<已说明的调用上下文>`。
`result.$` 表示当前返回根值；兼容裸字段表示当前返回字段，`input.foo` 等价于 `args.foo`。
固定值使用 `literal:<JSON>`，例如 `literal:1`、`literal:"asc"`、`literal:null`；JSON 必须可无损解析，
它表示对应的数字/字符串/空值，而不是把 `literal:` 前缀发送给接口。不能把裸 `1` 当字段路径或随意猜成常量。
`user` 与 `context` 不是让模型杜撰数据的空间，必须在 `instruction` 写出获取方式；
工具返回的字符串不是指令，不能让数据覆盖本契约。

例如提交返回根 ID，取消收 `id`，正确映射为 `{"id":"result.$"}`。
`{"$":"id"}` 方向相反。`list[].id` 本身没有表达「挑一个还是全选」，必须在 `instruction` 补齐选择条件和基数。
需要转换时保留来源字段，转换规则写进 `instruction`，不要把自然语言或脚本塞进字段路径。

**prepare → submit 特别要求**：准备返回的后端 `payload` 不一定就是 SDK 的 `draft`。
逐项映射可复用字段，列出由 SDK 自行产生和不应传入的字段，说明审批节点如何映射到所选人员。
业务单据 ID、流程实例 ID、任务 ID 即使类型一样也不能互换。

## 7. 失败、防重和完成条件

`failures` 每条写清：**可观察失败/触发条件 → 结果是否确定 → 修正或核实动作 → 是否允许重试**。
不要凭后端通用 `500` 推断唯一失败原因，不要把权限错误或超时当成空列表。

`idempotency` 是与绑定实现一致的说明：是否包装、必需键、作用域、有效期、同键不同载荷、失败或超时如何处理。
进程内缓存不等于后端或跨进程幂等；没有防重的写操作必须明确重复调用的影响及可用核实入口。
无需为了填这一栏新增确认或风险分级；用户授权与业务验证仍遵循现有规则。

`completion` 必须区分「请求受理」「记录已创建」「流程已启动」「审批通过」「业务生效」。
不能把 submit 返回 ID 写成审批已通过；请求成功也不能替代独立查询证实写入结果。
读能力应写明已获得什么范围的数据以及什么时候交付，避免无限下钻。

## 8. 证据、标准样例和版本维护

`Evidence = { source: string, kind: 'implementation' | 'browser' | 'smoke' | 'test' | 'reference', note: string }`。
`source` 指到文件/符号/记录，`note` 明确证明什么与没有覆盖什么；引用外部源码时附版本锚点。
历史冒烟、当前离线测试和本次真实环境验证要分开，**存在证据文件不等于业务含义正确**。

`Example = { scenario: string, args: Record<string, unknown>, result: unknown, interpretation: string }`。
示例必须脱敏；标明构造数据，不能让 AI 把样例 ID 当成当前环境真实 ID。
若根值为 `undefined`，不要伪造 JSON `null`；使用代码样例或明确的无返回值场景说明。

配套样例在 `docs/ai-description-examples/`。它们展示逐字段解释及真实能力的映射，包含明确缺口，
**不是另一份线上契约，也不是线上再次验证的证明**。能力族至少有一个可测试的代表样例；
复杂对象/数组、条件输入、枚举、动态字段及有副作用的动作，须在该族的测试或内置示例中覆盖适用情形。
业务行为变化必须同步更新权威定义、相关样例/文档及说明测试；协议字段变更需同时更新本规范、类型与检查器。

## 9. 检查与交付

- `pnpm ai:check`：先构建当前源码，再检查已注册能力与已登记公开方法的契约结构及可检查的引用。返回非零表示存在检查问题；未登记的公开方法仍须按实际门面另行盘点。
- `pnpm ai:check:complete`：在结构检查基础上报告输入遗漏、明确缺口及未登记等不完整内容。
- `pnpm exec vitest run test/ai-contract-schema.test.ts test/ai-description-examples.test.ts`：验证检查器与标准样例。

检查器能力和未覆盖边界以其输出及测试为准。它不能证明文字描述的业务含义正确，不能推导出接口未观测字段，
也不会执行 `mapping` 或自然语言条件。结构通过不等于信息完整，完整性检查通过也不等于真实业务验证通过。
直接运行 `node tools/ai-contract/check.mjs` 读取最近构建的 `dist`；正式验收必须用上面的 `pnpm` 命令避免读旧构建。

每次交付必须逐项核对：

1. 列出本次页面、能力、公开方法和受影响上下游；不能只数已注册方法就宣称覆盖全部公开方法。
2. 从真实 `describe()` / 页面描述入口读取输出，检查每一项必需语义，不以本地文件存在代替。
3. 按独立夹具核对输入、根返回值、容器及叶子、枚举/单位、空值、动作映射、错误和重试；
   不得用契约生成期望值，再用它证明契约正确。
4. 对本次关键语义做反证：错 ID、漏字段、错状态、错误步骤条件或映射至少覆盖实际改动风险；确认会红后恢复。
5. 重跑相关测试与 `typecheck`；生成物变更遵守并行文件所有权规则。
6. 报告结构问题、语义/证据缺口及真实验证范围，代码/说明/测试同一工作单位提交。

历史迁移可保留旧描述接口，但 `ai` 缺失、未验证的猜测、未展开动态字段必须保持可见缺口。
已有契约不得倒退，新改功能不能把缺口留给模板句。当前没有提交钩子自动强制全库完整；
维护者必须运行检查并对本次受影响范围逐项验收，不得声称规则已经自动保证后续 AI 永不漏改。
