# 字典（基础数据能力 `base-dict-*`）

**这不是一个页面**。`GET /admin-api/system/dict-data/grouped-list` 是应用外壳级的基础数据：
Portal 的路由守卫在任何 dashboard 页面刷新时都会打它——而且是**一次刷新打 4 遍**。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/base-dept-dict-permission.ts`；
回归测试 → `test/base-dept-dict-permission.test.ts`；真实环境只读冒烟 → `smoke/read-base-data.mjs`。

它要回答的问题：

> 一张 **1.06 MB / 885 个 dictType / 5985 条**的查表数据，SDK 怎么给它才不至于冲掉调用方的上下文？
> 以及：`src/session/base-data.ts` 里已经有它了，为什么还要再建一个能力？

## 接口

| 项 | 值 |
| --- | --- |
| 路径 | `GET /admin-api/system/dict-data/grouped-list` |
| 参数 | **无** |
| 分页 | **没有** |
| 返回 | `[{ dictType, dataList: [{ id, dictType, value, label, colorType, cssClass, sort, remark, tenantId, platform }] }]` |
| 权限注解 | 无 |
| 后端数据范围 | 只由 `tenantId` 决定（`tenant_id IN (0, 当前租户)`）——**与 userId / 角色 / 组织 / module-type 全无关** |
| Portal 调用点 | `app/portal/utils/system.js` 里 **6 处**同一个 URL（L196 / L288 / L315 / L380 / L938 / L1345） |
| http 实例 | `platform` |
| 兄弟接口 | `GET /adminmanage-api/system/dict-data/list-all-simple`（扁平版，调查值 954 KB / 5983 条，**本单未重测**）——**不建议再建一条**，与 grouped-list 高度重叠 |

## 一次首屏打 4 遍（Portal 侧的浪费）

四个独立 store 各查各的 `ready`，没有跨 store 的 in-flight 去重：`fetchAllDicts`（HR）、
`fetchAllPlatformDicts`（平台）、`fetchAllSaleDicts`（销售）、`fetchMallAdminAllDicts`（商城管理）
并发打同一个 URL。这是 `docs/base-capabilities.md` §0 的 [实测] 记录。

**SDK 不照抄这个浪费**：单飞（`src/session/single-flight.ts`）+ 片级索引缓存，
同一份数据在同一个能力实例里只发一次。

## 能力定义与参数契约

三个入口都是**只读**（`write: false`），页面路径是合成的 `/base-data/dict-list`。

| 能力 id | 入口方法 | 参数 | 说明 |
| --- | --- | --- | --- |
| `base-dict-get` | `getDict(dictType)` | `dictType`（必填，`lookup` → `base-dict-search`） | **一次只取一个 dictType** 的全部选项。`dictType` 写错**报错**（不是静默返回 `[]`） |
| `base-dict-search` | `searchDictTypes({ keyword, limit })` | `keyword`（必填）、`limit`（默认 20，上限 50） | 找 dictType **名字**（不区分大小写），返回 `{ dictType, entryCount }`。885 个候选 = 长选项，**无关键字拒绝且不发请求** |
| `base-dict-translate` | `translateDict({ dictType, value })` | `dictType`（必填）、`value`（必填） | 只回答"这个码显示成什么"。查不到值返回 `{ label: null, found: false }`，**不抛错** |

**没有 `listAll()` / `getAll()`**：1.06 MB 一次性倒出去就是 conventions 第 11 条那一类问题
（会冲掉调用方上下文），只不过"长"的不是候选项而是整张表。

`getDict` 的错误语义是刻意的：**dictType 写错 → 报错；dictType 存在但没有条目 → 空数组**。
两者混在同一个 `[]` 里，调用方就分不清"名字写错了"和"这个字典是空的"——而 885 个名字猜不得。

## 逐字段基准（实测）

冒烟：`smoke/with-portal-token.sh node smoke/read-base-data.mjs`
（2026-09-20，`biz-api-test.wodecorp.cn`，租户 1；**全程只读 GET**）

```
字节 1063746 / dictType 885 个 / 条目合计 5985 条 / 耗时 655 ms（第二轮 705 ms）
条目最多的 5 个：hen_brand → 617 / system_category_dict → 241 / finance_payment_fee_item → 131 / item_column → 66 / nation → 58
条目最少的 3 个：sales_payment_method → 1 / Yukou_ShopId → 1 / chickVideoIntro → 1
样本（hen_brand）首条：{"id":"3056","dictType":"hen_brand","value":"1","label":"峪口禽业","colorType":"","cssClass":"","sort":10,"remark":null,"tenantId":0,"platform":true}
字典条目字段：["id","dictType","value","label","colorType","cssClass","sort","remark","tenantId","platform"]
value 的 JSON 类型分布：{"string":5985}
id 的 JSON 类型分布：{"string":5985}
label 带前导/尾随空格的条目数：24
status 字典：6 条，前 3 个值 ["WAIT_SELLER_CHECK","WAIT_BUYER_PAY","PROCESSING"]
```

**四条要记住的事实**：

1. **`value` 与 `id` 全部是 JSON string**（5985/5985，无一例外）。
   所以"字典值是 `1` 还是 `"1"`"不是风格问题——**要跟数字参数比对时必须 `String()`**。
   本能力的 `translateDict` 就是这么比的（`String(entry.value) === String(value)`），
   传 `1` 或 `"1"` 都能命中。
2. **`label` 有 24 条带前导/尾随空格**，SDK **原样返回、不 trim**。见下面「快照会漂」。
3. `dictType` 大小写混杂（`assignment_type` 与 `Yukou_ShopId` 并存），所以
   `searchDictTypes` 的匹配**不区分大小写**（`has` 式的精确比对是另一回事）。
4. **最大的 dictType 是 `hen_brand`：617 条**。`getDict` 一次给一条 dictType，
   所以最坏情况是 617 条，而不是 5985 条。

## 快照会漂：`assignment_type` 与硬编码的那份**不一致**

`src/capabilities/assignment.ts:127` 的 `ASSIGNMENT_TYPE_OPTIONS` 是从页面控件抄下来的快照。
把它与线上字典**逐条对**：

| value | 线上 label | `assignment.ts` 快照 |
| --- | --- | --- |
| 1 | `文件` | `文件` |
| 2 | ` 图片+文字`（**带前导空格**） | `图片+文字` |
| 3 | ` 图片`（**带前导空格**） | `图片` |
| 4 | ` 文字`（**带前导空格**） | `文字` |
| 5 | `视频` | `视频` |
| 6 | `视频+文字` | `视频+文字` |

**6 条值的取值完全一致，label 有 3 条不一致**（空格差异）。

这不是说 `assignment.ts` 错了：它的快照是从**页面渲染出来的控件**抄的，页面可能 trim 过。
它说明的是另一件事——**硬编码快照与数据源之间没有东西保证它们一致**，
而字典一变（加一个选项、改一个 label、多一个空格）就得重新生成逐页能力。
这正是"字典应该是基础能力"的直接理由：`base-dict-get` 拿到的永远是线上的那一份。

## 体积怎么切

| 入口 | 一次拿到多少 | 上限 |
| --- | --- | --- |
| `getDict(dictType)` | **一个** dictType 的全部选项 | 由 dictType 自身决定（实测最大 617） |
| `searchDictTypes(keyword)` | 名字命中的前 N 个，每个只带 `entryCount` | 默认 20 / 硬上限 50 |
| `translateDict(dictType, value)` | **一条** label | 1 |

切法是"**按一次调用能回答的那个问题**"切，不是"按表有多大"切：
问「作业类型有哪些」要的是 `assignment_type` 那 6 条；问「885 个字典里哪个是管品牌的」要的是名字候选；
问「`WAIT_BUYER_PAY` 显示成什么」要的是一个字符串。三种问题给同一张 1 MB 的表，是让调用方替 SDK 筛。

## 缓存

| 场景 | 行为 |
| --- | --- |
| 挂了会话 | 读会话里**已有的** `dict-hr`（缺则 `dict-platform`）。命中则一次请求都不发 |
| 没挂会话 | 实例内索引缓存，TTL `BASE_DATA_CACHE_TTL_MS` = 30 分钟（与 `DEFAULT_ABSOLUTE_TTL_MS` 同值） |
| 并发 | 单飞合并成一次请求 |
| 手动失效 | `invalidate('dict')` / `invalidate()` |

**为什么字典不新增会话基础数据键**：`src/session/base-data.ts:132-144` 已经为**同一个 URL**
注册了两个 key（`dict-hr` 与 `dict-platform`）。再注册第三个 `dict-list`，只会让同一个 1.06 MB
在一次会话里被打**第三遍**——那是在复刻 Portal 打 4 遍的毛病。
本能力因此只**读**已有的 key（`BASE_DICT_SESSION_KEYS`），并在测试里钉住这个约定。

会话里那份值的形状是 `{ [dictType]: [{label,value,id}] }`（`loadGroupedDicts` 的归一化结果），
与 HTTP 原始的 `[{dictType, dataList}]` 不同——`buildDictIndex` 两种都吃，
**形状完全认不出来时抛 `BaseDataShapeError`**，不静默当成空字典（静默会把"接线坏了"读成"没数据"）。

## module-type：**不发这个头**

- **浏览器侧**：与部门那条一样，`module-type` 由 `getCurrentModuleType()`（cookie `menuPath` =
  即将进入的页面）兜底决定（`app/portal/utils/system.js:825-833`），**不是这三个调用点传的**。
- **后端侧**：`DictDataController#getGroupedList` **零参数**，不读这个头；Service 里也没有
  `@DataPermission`；数据范围只由 `tenantId` 决定。
- **实测**：带 `module-type: 11` 与不带，都是 **885 个 dictType**，完全无差别。

所以对字典来说，"发不发"在观测上没有任何区别——SDK 选择不发（与 conventions 第 2 条一致），
并把这个判断写进了测试。需要时可以由接线方显式给 `moduleType`（`BaseDeptDictPermissionOptions.moduleType`），
但没有任何理由。

## 已知坑

- **`status` 是全平台共用的 dictType，装的是交易状态**（实测前 3 个值
  `WAIT_SELLER_CHECK` / `WAIT_BUYER_PAY` / `PROCESSING`），不是业务状态。
  `src/capabilities/base-image.ts:270-282` 已经踩过这个坑（那个下拉框因此是坏的）。
  **基础能力不替调用方猜 dictType 的含义**——这是能力描述里明确写着的。
- **不要拿 `getDict` 的返回值直接当 `options` 塞进逐页能力的 `enum` 参数**：
  `value` 是字符串，而多数页面参数的 `value` 是数字。要对齐得显式转换，这一层 SDK 不做。

## 没做 / 不确定

- **`list-all-simple`（扁平版）没有实测**：本单只测了 `grouped-list`。不建议再建一条的结论
  引用自 `docs/base-capabilities.md`（那里也是"内容高度重叠"的**判断**，没有逐条 diff）。
- **本能力的 `getDict` 没有做分页/分批**：617 条是实测最大值，直接返回。
  如果哪天出现几千条的 dictType，这个入口会变成问题——**目前没有观测到**。
- **字典的写入侧（维护字典）一个字都没做**，也没有试过任何写接口。
- **`colorType` / `cssClass` / `sort` / `remark` / `platform` 这五个字段被丢掉了**：
  它们只服务于"按颜色渲染标签"这类页面展示，对"码 → 名"的用途没有价值，
  而 885 × n 条上多带五个字段纯粹是体积。**这是一次有意的取舍**，不是遗漏——
  需要它们的时候要从 `grouped-list` 原始响应里另开一个入口。
