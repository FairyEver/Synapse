# 用户信息（基础能力 `base-user-info`）

**这不是一个页面**。`GET /admin-api/sys/user/info` 是 Portal 路由守卫里**第一个**打的接口
（`app/portal/utils/router/session.js:35-59` 的串行 4 步里的第 1 步，
调用点 `app/portal/utils/system.js:458` 的 `fetchSimpleUserBasic`），
而且是六个基础数据项里**两个 `critical: true` 之一**。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/base-shell.ts`；
回归测试 → `test/base-shell.test.ts`；真实环境只读冒烟 → `smoke/read-base-shell.mjs`。

## 它为什么是"半有"而不是"已有"——本单复核的结论

`docs/base-capabilities.md` 把这条判为「**已有**」，依据是 `src/session/base-data.ts` 里
有一个 `user-basic` 键。**这个判定不准确**：那份数据确实已经在会话里加载了，
但它**不是一个能力** —— 不在 `ALL_CAPABILITY_DEFINITIONS` 里、没有能力 id、
没有参数契约、AI 调不到它。`user-basic` 是"会话内部会加载的东西"，不是"能问的东西"。

所以本单把它**从会话内部数据提升为可调用能力**：复用已有的 `user-basic`（不新增键、
不让同一个请求在一次会话里打第二遍），只把出口开出来。这正是调查 §4.4 最后那条建议
（"把 `user-basic` 从会话内部数据提升为可调用能力，并在归一化时白名单字段"）。

## 接口

| 项 | 值 |
| --- | --- |
| 路径 | `GET /admin-api/sys/user/info` |
| 参数 | **无**（当前登录用户由 token 决定，不接受任何 id 参数） |
| 分页 | **没有** |
| 返回 | 单个对象，实测 **33 个字段** |
| http 实例 | `platform` |
| 权限注解 | 无（"我自己"不需要权限码） |
| Portal 调用点 | `app/portal/utils/system.js:458` 的 `fetchSimpleUserBasic` |

## ⚠️ 这个接口会吐回 `password2` 与 `salt` —— 这是本能力最要紧的一件事

实测原始响应里确实有这两个字段：

```
字段全集：["id","username","password2","salt","realName","headUrl","gender","email","mobile",
"gradeId","deptId","status","createDate","creator","superAdmin","roleIdList","gradeName",
"roleList","organizationCode","organizationName","organizationFullPathName","organizationId",
"updaterName","updateDate","creatorName","type","project","postId","tenantId","tenantAdmin",
"postName","staffId","setPwd"]
password2 形态：string（长度 60，bcrypt 哈希）；salt 形态：string（长度 29）
```

**`password2` 是 bcrypt 哈希、`salt` 是盐。** 它们跟用户信息没有任何关系，只是同一个
DTO 顺手带出来的。任何把它们放进缓存、日志或 AI 上下文的行为都是一次凭据泄漏。

### 做法：**白名单**，不是黑名单

`normalizeUserInfo()` 只挑出下面 18 个字段，其余一律不进返回值。
**没写在类型里的字段一定不会被返回**——包括 `password2`/`salt`，也包括后端将来新增的任何字段。

| 字段 | 实测取值（本账号） | 说明 |
| --- | --- | --- |
| `id` | `"18243"` | 字符串，不是数字 |
| `username` | `"2021070101"` | 工号形态 |
| `realName` | `"姚淼鑫"` | |
| `headUrl` | `http://appimgcdn.../g_55.png` | **注意是 `http://`**，跟上传那条链的坑同源 |
| `gender` | `1` | |

| `status` | `1` | |

| `tenantAdmin` | `1` → `true` | **调查 §4.4 漏了这个**，见下 |
| `postName` | `"高级产品经理"` | |

| `organizationName` | `"设计中心1236"` | |

**为什么白名单比黑名单稳**：黑名单要求"后端每次加字段都记得来加一条"，
漏一次就是一次凭据泄漏，而且**不会有任何测试变红** —— 那是本仓库最怕的失败形态。
白名单的失败方向相反：后端加了个有用字段，最坏结果是"暂时取不到"，看得见、可修。

### 两个出口都要过白名单

| 出口 | 载荷 | 是否过白名单 |
| --- | --- | --- |
| 没挂会话 | 直接发 `sys/user/info` 的响应 | ✅ |
| **挂了会话** | 会话里 `user-basic` 存的**就是原始响应**（`base-data.ts` 的 `load` 直接返回它） | ✅ |

**"读会话更安全"是错觉。** 会话里那份是**带 `password2` 的原始响应**，
少走一次归一化就是一次外流。`test/base-shell.test.ts` 里两个出口**各有一条断言**
（而不是合成一条只测一个），因为这条错**不会有别的症状**。

### `tenantAdmin`：调查漏掉的一个身份判据

`superAdmin` 是"是不是超管"，`tenantAdmin` 是"**是不是租户管理员**"。
后者不是可有可无：`permissionsNotBySystem` 的取值路径里 `tenantAdmin` 是**独立的一支**
（租户已购模块），与普通用户的角色菜单权限路径不同。认身份时两个都要看。

### 已知坑

- **`deptId` 本账号是 `null`**，而 `organizationId` / `organizationName` 有值。
  要部门树 / 部门名请走第一批的 `base-dept-*`（`system/dept/list-all-simple`，1551 个节点）。
- **`roleIdList` 本账号是 `null`**，`roleList` 也是 `null`。所以 `roleIds` 实际常为 `null`。
  `roleList` 的形状**没有验证过**（一直是 null），因此**不返回**它——
  不猜一个没见过的形状，需要时按原始响应处理。
- **`superAdmin` / `tenantAdmin` 归一成布尔时只认 `1` / `true` / `"1"`**，
  不用 `Boolean(value)`——那样 `"0"` 和 `"false"` 都会变成 `true`，是典型的静默反向错误。

## 体积怎么切

| 项 | 值 |
| --- | --- |
| 一次拿到多少 | 一个对象，**18 个字段 / 897 B** |
| 上限 | 不需要：这个接口的规模由"一个人有多少字段"决定，不随数据量增长 |

这是本批**唯一不需要切体积**的能力——它不是集合，是单个对象。
而且它是所有能力里第二小的（897 B，仅次于两个角标数）。

## 缓存

| 场景 | 行为 |
| --- | --- |
| 挂了会话 | 读会话基础数据键 **`user-basic`**（`src/session/base-data.ts` 已有，**不新增键**） |
| 没挂会话 | 实例内缓存，TTL = `BASE_SHELL_CACHE_TTL_MS`（30 分钟，与 `DEFAULT_ABSOLUTE_TTL_MS` 同值） |
| 并发 | 单飞合并 |
| 手动失效 | `invalidate('user-info')` / `invalidate()` |

**为什么不新增一个 `shell-user-info` 键**：`user-basic` 已经指向同一个 `sys/user/info`，
再加一个键只会让同一个请求在一次会话里被打第二遍（Portal 自己把字典打了 4 遍，
SDK 不照抄这个）。与第一批对字典的处理同一条理由。

## module-type：**不发这个头**

- **合成路径**：`/base-data/user-info`，规则表 88 条 prefix + 186 条 paths **全部**以
  `/dashboard/` 开头，所以 `resolveModuleType()` 返回 `null` → 不发（conventions 第 2 条）。
- **实测**：带 `module-type: 11` 与不带，`data` **逐字节相同**（897 B / 897 B，基线稳定）。
- **依据强度**：这是"本账号实测不敏感"，**没有核对后端实现**。
  一个数据范围不同的账号可能不一样。需要收窄时由接线方通过 `BaseShellOptions.moduleType` 显式给。

## 操作步骤（读能力）

这是一条**纯只读**能力，没有 `prepare → submit → cancel`，也不需要。

```bash
# 真实环境只读冒烟（A 段：用户信息）
smoke/with-portal-token.sh node smoke/read-base-shell.mjs
```

脚本会打印：字段全集（**用来核对 `password2`/`salt` 确实在原始响应里**）、
18 个白名单字段在本账号的取值、以及带/不带 `module-type` 的交错对照。

## 没做 / 不确定

- **没有把"我是谁"拼成一句话给 AI**：本能力返回结构化字段，不做"姓名（部门）"这种拼装。
  拼装是调用方的事，SDK 不该替它决定口径。
- **`roleList` 的形状没有验证**（本账号恒为 null），所以不返回它。
- **`staffId` / `setPwd` / `type` / `project` / `postId` / `gradeId` / `gradeName` /
  `creator` / `updater` / `updateDate` / `creatorName` / `updaterName` 刻意不返回**：
  前几个的含义没有查证，后几个是内部审计字段，对 AI 没有价值。
  **要加字段得先知道那个字段是什么意思**——白名单的价值就在于加字段是一个要动脑的动作。
- **用户信息不止这一个来源**。调查 §4.4 列了 5 个：本能力只覆盖第 1 个
  （`sys/user/info`）。另外四个是
  `{FM}/getUser`（产品侧）、`{CRM}/vue/getUserInfo`（销售侧）、
  `org/organization/getRoleOrganizationTree`（部门）、`sys/menu/permissionsNotBySystem`（权限）。
  **后两个本仓库已经有了**（第一批的 `base-dept-*` 与 `base-permission-*`）；
  前两个是异地 host 的产品/销售侧接口，按授权范围本单没有碰——见
  `src/capabilities/base-shell.ts` 文件头"明确没选的"一节。
