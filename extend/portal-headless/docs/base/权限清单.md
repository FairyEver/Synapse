# 权限清单（基础数据能力 `base-permission-*`）

**这不是一个页面**。`GET /admin-api/sys/menu/permissionsNotBySystem` 是这个用户"能干什么"的
唯一权威来源，也是应用外壳级的基础数据（路由守卫里打一次）。

> 名字的坑：用户口语里说的「Not by Permission 那个接口」就是它。
> **源码里没有 "Not by Permission" 这个字符串**，实际标识符是 `permissionsNotBySystem`。
> 另有一个长得很像但**完全不同**的接口 `GET /admin-api/sys/menu/menuListNotBySystem`（菜单树，
> 59 个根节点），那是后台菜单维护页用的，不是这个。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/base-dept-dict-permission.ts`；
回归测试 → `test/base-dept-dict-permission.test.ts`；真实环境只读冒烟 → `smoke/read-base-data.mjs`。

它要回答的问题：

> SDK 的每个能力都带一个 `permission` 字段（如 `BASE_IMAGE_PERMISSION = '/dashboard/base/image'`），
> 却**从来没有校验过**——那个字段是生成器从 `page-catalog.json` 抄来的静态值。
> 有了这个能力，SDK 才能回答「**这个用户到底能不能干这件事**」。

## 接口

| 项 | 值 |
| --- | --- |
| 路径 | `GET /admin-api/sys/menu/permissionsNotBySystem` |
| 参数 | **无** |
| 分页 | **没有** |
| 返回 | `data` 是**纯字符串数组** |
| 权限注解 | 无（该 Controller 里所有 `@RequiresPermissions` 都是注释掉的） |
| Portal 调用点 | **全仓唯一**：`app/portal/utils/system.js:697` 的 `fetchPermissions()` |
| http 实例 | `platform` |
| 后端数据范围 | `superAdmin`（全表）/ `tenantAdmin`（租户已购模块）/ 普通用户（角色菜单权限），另外并入 `DefaultMenuDO.moduleType` 与租户订阅模块匹配的结果——**与请求头 `module-type` 无关** |

⚠️ **外层包络不同**：它用的是 `com.wdbc.erp.framework.common.result.Result`（`ret/code/msg/data`），
不是另外两个接口的 `CommonResult`。SDK 的 `src/http/client.ts` 已经按 `ret === 'SUCCESS'` 处理，
所以拆出来的都是 `data`；这条记在这里是因为**同时比对三个接口的原始报文时容易看错**。

## 里面装的是两类东西

`data` 是**混装**的字符串数组，实测 2159 条里：

| 类别 | 判据 | 条数（实测） | 抽样 |
| --- | --- | --- | --- |
| 页面路径码 | 以 `/` 开头 | **1107** | `/dashboard/contract/code-rule`、`/dashboard/finance/value-added/calculation/fixed-asset-detailed-report` |
| 动作码 | 不以 `/` 开头 | **1052** | `investment:daily:account:export`、`material:store:point-setting:create` |

SDK 的能力定义里那个 `permission` 字段，**两种都可能**——`base-image.ts` 用的是页面码，
而页面上的"导出"按钮那种动作是动作码。所以能力不做"只查页面码"的假设，两类一视同仁。

## 能力定义与参数契约

三个入口都是**只读**（`write: false`），页面路径是合成的 `/base-data/permission-list`。

| 能力 id | 入口方法 | 参数 | 说明 |
| --- | --- | --- | --- |
| `base-permission-has` | `hasPermission(code)` | `code`（必填） | **精确匹配**，返回布尔 |
| `base-permission-check` | `checkPermissions(codes)` | `codes`（必填，逗号分隔字符串或数组） | 返回 `{ granted, missing, checked }`，自动去重 |
| `base-permission-search` | `searchPermissions({ keyword, limit })` | `keyword`（必填）、`limit`（默认 50，上限 200） | 按**片段**匹配（不区分大小写）。**前缀查询就是传前缀**：`investment:`、`/dashboard/base/` |

**没有 `listAll()`**：2159 条一次性给出去会冲掉调用方上下文。要"看规模"用
`searchPermissions` 的返回值——它同时给 `total`（2159）与 `matched`（命中的有多少）。

## 一条必须记住的结论：**不在清单里 ≠ 会 403**

拿这个能力去问本账号（测试环境，租户 1），实测：

| 权限码 | `has()` | 事实 |
| --- | --- | --- |
| `/dashboard/attendance/attendance-archive-sheet` | `true` | 考勤档案能力在这个账号上跑通过 |
| `/dashboard/attendance/attendance-sheet` | `true` | 同上（考勤统计） |
| `/dashboard/assignment/assignment` | `true` | 作业管理跑通过 |
| `/dashboard/contract/template` | `true` | 合同模板跑通过 |
| `/dashboard/base/management-center` | `true` | 组织结构跑通过 |
| **`/dashboard/base/image`** | **`false`** | **但图库能力在这个账号上是能跑的**（`docs/pages/图库管理.md` 记录：真机写链路冒烟 36 项全绿） |
| `/definitely/not/a/real/permission/code` | `false` | 随便编的码，当然是 false |

**这说明两件事**：

1. `has()` 不是摆设——它对 `false` 是真的会 `false`（否则这一列就全是 `true` 了）；
2. **但它不能当硬门禁**。`BASE_IMAGE_PERMISSION = '/dashboard/base/image'` 这个静态值
   在本账号的清单里不存在，而页面与接口都能用。这正与 conventions 第 15 条
   （"菜单树不是权限裁决"）同一个道理：**这份清单是"下发面"，不是"能不能调"的判据**。
   真实的鉴权在后端各个接口自己的注解上（而这三个接口连注解都没有）。

所以这个能力的描述里写着「**不在清单里不等于会 403**」，SDK 也不会拿它去自动拦截调用。

## 体积怎么切

| 入口 | 一次拿到多少 | 上限 |
| --- | --- | --- |
| `hasPermission` | 一个布尔 | 1 条 |
| `checkPermissions` | 几十个布尔，分成 granted / missing | 调用方自己给多少条就多少条 |
| `searchPermissions` | 片段命中的前 N 条 | 默认 50 / 硬上限 200（实测 `investment:` 只有 17 条） |

这是三个基础能力里**最不需要权衡**的一个：问"有没有"本来就不需要把 2159 条端出来。
`searchPermissions` 存在的意义是"我不知道这个动作的权限码长什么样"——那时传
`investment:` 这样的前缀，实测 17 条，比 2159 条好读两个数量级。

## 缓存

| 场景 | 行为 |
| --- | --- |
| 挂了会话 | 读会话基础数据键 **`permission-list`**（由 `baseDeptPermissionBaseData` 定义，接线方注册） |
| 没挂会话 | 实例内索引缓存，TTL = `BASE_DATA_CACHE_TTL_MS`（30 分钟，与 `DEFAULT_ABSOLUTE_TTL_MS` 同值） |
| 并发 | 单飞合并 |
| 手动失效 | `invalidate('permission')` / `invalidate()` |

**权限被回收了怎么办**：本地缓存最长 30 分钟后自然失效；急用可以 `invalidate('permission')`。
之所以敢缓存，是因为这份数据**变更频率极低**（角色调整不是每分钟发生的事），
而它 87 KB / 近 1 秒，是一次实打实的开销。

会话级基础数据项建议 `critical: false`（降级而非整份会话作废）——与 Portal 的
`softFetch*` 语义一致，也是 `baseDeptPermissionBaseData` 里的实际取值。

## module-type：**不发这个头**

- **浏览器侧**：同另外两个，由 `getCurrentModuleType()`（cookie `menuPath`）兜底决定，
  不是调用点传的。
- **后端侧**：`HrSysMenuController#permissionsNotBySystem` **无任何参数**，不读这个头；
  范围由 `superAdmin` / `tenantAdmin` / `tenantId` / `roleIdList` 决定；
  `LoginUser.getModuleType()` 在这个方法里**没有被引用**。
- **实测**：带 `module-type: 11` 与不带，都是 **2159 条**，完全无差别。

## 没做 / 不确定

- **没有把 `permission` 字段接进任何拦截逻辑**：本单只提供"查"的入口，
  要不要在调用前校验由接线方决定（而且上面那条结论说明**不该**硬拦）。
- **`page-catalog.json` 里 `permission` 字段的准确率没有系统核对**：
  只发现 `/dashboard/base/image` 这一个反例。全量比对（1000+ 页面 × 2159 条码）
  不在本单范围内。
- **1107 / 1052 这个分类只是"以 `/` 开头"**：可能有既不像页面码也不像动作码的杂项，
  没有逐条归类。
- **`superAdmin` / `tenantAdmin` 的返回差异没有实测**（本账号是普通用户路径）。
  换一个超管账号，2159 这个数字会变。
