# 上传（`base-upload`）—— 基础能力

> **这是基础能力，不是页面。** 所以它不在 `docs/pages/` 下，能力定义也不挂在任何菜单路径上。
> 四件套按同样的结构写：能力定义 / 参数契约 / 逐字段基准 / 操作步骤，
> 外加一节**真实环境验证**（2026-09-20 已在测试环境跑通，见 §6）。

它要回答的问题是：

> 所有带附件的表单（尤其是流程表单）都要先有一个「可访问的 url」才谈得上提交。
> 这个 url 从哪来？无头下这条路能不能走通？走通的代价是什么？
> **哪些是实测的结论、哪些只是协议推演？**

**一句话结论**：这条路**在测试环境真实跑通了**，零新依赖。
自己实现的 OSS **V1 签名被真实 OSS 接受**，上传后的 url **匿名读者真能打开**，
而且这三件事都有**反证**（把签名改错，真实 OSS 当场拒绝）——
不是"跑通过一次"就算数。跑法与凭据来源见 §6.3，逐条结论见 §6.2。

## 1. 为什么它是地基

`src/capabilities/base-image.ts` 的 `base-image-create` 要求调用方给 `url`，注释原话：

> **SDK 不覆盖上传**：页面是先把文件直传 OSS 再把这个地址 Post 过来的，所以要由调用方给出一个可用的地址

调用方拿不到 url，那个能力就是半残的：AI 只能让用户手动去页面上传。
这就是「上传是地基」最直接的证据 —— 它是这个 SDK 里**唯一一处把缺口写在代码注释里**的地方。

用量上的佐证（本单实测，`Projects_Js` 只读）：

| 组件 | 用法数 |
| --- | --- |
| `common-upload-image` | 157 |
| `common-upload-dragger` | 104 |
| `common-upload-file-plus` | 68 |
| `common-upload-image-multiple` | 21 |
| `common-upload-file` | 5 |
| `common-upload-video` | 1 |
| **合计** | **356** |

复现方法：`grep -roh --include='*.vue' '<common-upload-' app common | wc -l`（数的是开标签）。
⚠️ `docs/base-capabilities.md` §5.1 记的是 **322**（image 91 / dragger 86 / file 67 / file-plus 63 /
image-multiple 15）。两个数**对不上是口径差异**（那份用的是另一套匹配），不是谁抄错了。
**能复现的是 356 与上面这套方法**；「数百处」这个量级两份结论一致。

这 356 处最终都收口到**同一个文件**：`common/utils/oss.js`（全仓唯一 `import OSS from 'ali-oss'` 的地方）。
本能力复刻的就是它的 `ossPut`。

## 2. 能力定义

**五个**能力，全部落在 `src/capabilities/base-upload.ts`：

| 能力 id | 写？ | 做什么 | 对应 OSS 操作 |
| --- | --- | --- | --- |
| `base-upload-file` | **是** | 传一个文件、设成公开读、把 ACL 读回来复核 | `PutObject` + `PutObjectACL` + `GetObjectACL` |
| `base-upload-acl-get` | 否 | 查一个对象谁能读 | `GetObjectACL` |
| `base-upload-delete` | **是** | 删一个对象（写链路的 `cancel`） | `DeleteObject` |
| `base-upload-delete-multi` | **是** | 批量删（一次最多 1000 个，逐个回报） | `DeleteMultipleObjects` |
| `base-upload-acl-set` | **是** | 改一个对象的读权限（补跑用） | `PutObjectACL` |

### 删除是 2026-09-21 补的，起因是一个删不掉的测试产物

**在此之前 SDK 没有删除能力**，而上传能力已经存在 —— 于是"传上去就删不掉"。
真实踩到：调休流程那条线用 SDK 传了一个测试 PNG
（`HR/approval/2026/09/wftdvmcbwuqtdwcz.png`，69 字节），**没有任何出口能删掉它**。
测试产物越堆越多，下一个人还会踩同一个坑。

现在 `base-upload-delete` 补上了这个缺口，那个遗留对象**已经用它删掉**
（删前匿名 GET 200 / 删后 403，见 §6.4 的实跑记录）。

> ⚠️ 这两条**会真删东西，且不可撤销**。`deleteObject` 还是**幂等**的 ——
> 删一个不存在的 key 同样返回成功，所以"到底删掉了没有"**不能看它的返回值**，
> 要删完再读一次。`deleteMulti` 稍好：它**逐个回报** `deleted` 与 `errors`。

### 与 `base-image.ts` 里那句「SDK 不覆盖上传」的关系

`src/capabilities/base-image.ts` 的注释写着「**SDK 不覆盖上传**，`url` 必须由调用方提供」。
那句话**写在挂这个能力之前**，现在已经过时：

- **上传有了**（`base-upload-file`），所以 `base-image-create` 的 `url` 不再是"调用方自己想办法"，
  而是"先调 `base-upload-file` 拿回来"。
- ⚠️ 但 `base-image.ts` **不是本单的文件**，那句注释**没有改**（按纪律：发现别人的文件的问题只报告不代改）。
  改它属于图库管理那条线的 owner。**读那句注释时请以本文为准。**

类似地，`docs/pages/图库管理.md` 与 `docs/pages/作业管理.md` 里也有「SDK 不覆盖上传」的表述，
同样已过时 —— 一并留给各自的 owner。

### 挂在哪（`pagePath`）

`pagePath` 是哨兵值 **`common/utils/oss.js`**，**不是菜单路径**。

- 用真实菜单路径（比如 `/dashboard/base/image/list`）会让 CLAUDE.md 的
  「完成状态是推导的」把那个页面**误判成已完成** —— 那是谎报进度。
- 它匹配不到模块表，所以 `resolveModuleType()` 返回 `null`、**不发 `module-type` 头**。
  这是对的：本能力打的是 OSS，不是 Portal 后端，Portal 的 module-type 头在这里没有意义。
- 没有权限码：OSS 的鉴权是 AK/SK 签名，不走 Portal 的权限码体系。

## 3. 参数契约

### 3.1 凭据（**创建期**，不是每次调用）

凭据由**接入方创建能力时**注入，**不出现在 `params` 里** —— 它不是 AI 每次调用要填的东西，
也不该被模型看见。能力定义上用单独的 `credentials` 字段声明（`BaseUploadCapabilityDefinition`），
这样「契约里哪些是凭据」是**能看出来的**，而不是靠读注释猜：

| 字段 | kind | 必填 | 对应 Portal 的 env（`build/env/.env.build.test`） |
| --- | --- | --- | --- |
| `accessKeyId` | `credential` | 是 | `VITE_OSS_V2_ACCESS_KEY_ID` |
| `accessKeySecret` | `credential` | 是 | `VITE_OSS_V2_ACCESS_KEY_SECRET` |
| `bucket` | `target` | 是 | `VITE_OSS_V2_BUCKET` |
| `endpoint` | `target` | 是 | `VITE_OSS_V2_ENDPOINT` |
| `region` | `target` | 否 | `VITE_OSS_V2_REGION` |

> 上表只说「哪个字段对应哪个变量」，**没有、也不会**写出那些变量的值。

#### ⭐ 为什么是**一份**配置，而不是按页面分几份

Portal 前端里其实有**至少 5 套 OSS 凭据**（`grep -roh 'VITE_[A-Z_]*OSS[A-Z_]*' app common`）：

| env 前缀 | 定义处 | 用途 |
| --- | --- | --- |
| `VITE_OSS_V2_*` | `common/utils/oss.js:33-40` `ossConfigV2` | **默认，356 处上传组件实际都走它** |
| `VITE_EDUCATION_ADMIN_OSS_CONFIG_IMAGE_*` | `app/portal/utils/system.js:766` | 教育后台图片 |
| `VITE_MALL_ADMIN_OSS_CONFIG_IMAGE_*` | `app/portal` / `app/mall-admin` / `app/zhdj-admin` 的 `system.js` | 商城后台图片 |
| `VITE_MALL_ADMIN_OSS_CONFIG_APP_*` | 同上 | 商城后台 App |
| `VITE_SHOP_ADMIN_OSS_CONFIG_IMAGE_*` | `app/shop-admin/utils/system.js` | 店铺后台图片 |

**但真正生效的只有第一套。** 实测（`common/components/common/upload/dragger/index.vue`）：

```js
config: { type: Object },        // :42   声明了 config 这个 prop
...
url = await ossPut({ file, folder: props.folder })   // :85   但根本没把 config 传下去
```

而 `ossPut` 自己的 `config` 形参是**注释掉的**，正文写死 `cloneDeep(ossConfigV2)`
（`oss.js:134`「在新版不再需要」）。

⇒ 页面里那些 `:config="ossConfigForImage"` 是**失效的 prop**：
声明在、传了、**不影响文件落到哪个桶**。所以「哪套凭据」在当前版本里**不是一个按页面的决策**，
SDK 收**一份**配置是对的 —— 收多份反而是复刻一个已经不起作用的机制。

⚠️ **这条同时是一个陷阱**：如果按页面去对凭据，很容易以为图库管理页
（`create-multiple/create.vue:8` 确实传了 `:config="ossConfigForImage"`）用的是教育后台那个桶。
**它不用**。本 SDK 也因此不提供「按页面选桶」的入口。

### 3.2 调用参数

`base-upload-file`：

| 参数 | kind | 必填 | 说明 |
| --- | --- | --- | --- |
| `path` | text | 是 | 本地文件路径。**SDK 不做图片压缩 / 切割 / PDF 解析**，要处理过的字节请调用方先处理好 |
| `folder` | enum | 是 | 白名单，31 个取值，见 §4.1 |
| `fileName` | text | 否 | 文件名，**含扩展名**（角色等同 Portal 的 `file.name`）。扩展名与 content-type 都从它推 |
| `fixedName` | text | 否 | 固定对象名，**不含扩展名**。不给则随机。⚠️ 同名**直接覆盖** |
| `contentType` | text | 否 | 覆盖 content-type |

`base-upload-acl-get`：`objectKey`（text，必填）。

`base-upload-acl-set`：`objectKey`（text，必填）+ `acl`（enum，必填，4 个取值）。

`base-upload-delete`：`objectKey`（text，必填）—— 与 `getAcl` 的参数**对称**。

`base-upload-delete-multi`：`objectKeys`（text，必填）。
⚠️ `ParamSpec` 的 `kind` 里**没有数组类型**（`src/capabilities/types.ts`），
所以多个键用一段文本表达，**换行或逗号分隔**都认；空段丢掉、重复去掉
（`splitObjectKeyList`）。一次最多 **1000** 个（OSS 的限制），超了当场拒**不拆包** ——
拆包会把"部分成功"的语义藏起来。

### 3.3 程序化入口（不走 AI）

```ts
const upload = createBaseUploadCapability({ accessKeyId, accessKeySecret, bucket, endpoint })

// 只算不发：拿到 objectKey / url / canonical string
await upload.prepare({ content: Buffer, folder: 'HR/public', fileName: 'a.png', fixedName: 'x' })
// 真写：PutObject → PutObjectACL → GetObjectACL
await upload.upload({ content: Buffer, folder: 'HR/public', fileName: 'a.png', fixedName: 'x' })

// 撤销：删除（单个 / 批量）。都**不可撤销**，且单个那条是**幂等**的
await upload.deleteObject('HR/public/2026/09/x.png')
await upload.deleteMulti(['HR/a.png', 'HR/b.png'])   // 也收 'HR/a.png,HR/b.png' 这种字符串
```

`content`（Buffer）与 `path`（字符串）**二选一**，两个都给或都不给都当场报错（不猜优先级）。

### 3.4 缺凭据时的行为：**失败关闭**，但时机是「第一次真要用」

校验**不在创建能力时**，而在 `upload` / `getAcl` / `putAcl` / `deleteObject` / `deleteMulti`
**第一次被调用**时
（`createBaseUploadCapability` 内部的 `resolve()`）。

为什么：上传是**可选**能力，绝大多数调用方不配 OSS。若在创建时就校验，
`createPortalHeadless({ ..., oss: config.oss ?? {} })` 会把**每一个没配 OSS 的用户**
的 SDK 创建整个弄挂 —— 一个可选能力把主干拖死。这个时机由派单方 2026-09-20 拍板后移。

**失败关闭的性质没有变，只变了时机**。五个会发请求的方法**一个都没漏**，
而且凭据校验排在**参数校验与读本地文件之前**（两边都错时报的是凭据 —— 它才是拦路虎）；
五个方法都在**发出任何网络请求之前**抛错。`describeConfig()` 故意不校验（它是排查用的，
没配凭据时也必须能用）。

错误文案：

```
OSS 上传需要调用方提供凭据（缺失/非法字段：accessKeyId, accessKeySecret, bucket, endpoint）。
收到的是：{"accessKeyId":undefined,"accessKeySecret":undefined,"bucket":undefined,...}
SDK 不会自己去任何地方找凭据：不读环境变量、不读 Portal 前端仓库的 .env、不从浏览器抓。
```

与 `src/call.ts` 抛 `HttpInstanceResolutionError` 同一个立场：**宁可拒绝发起请求，
也不用一个"凑出来的"默认值打出去**。这条链上不存在「没有凭据也能跑」的分支。

## 4. 逐字段基准

### 4.1 `folder` 白名单（31 个）

逐条抄自 `common/utils/oss.js:42-95` 的 `ossFilePathOptions`，按源码分组顺序：

```
Public/public            Website/international
HR/public  HR/kpi  HR/study  HR/organize  HR/salary  HR/approval  HR/risk
Finance/public  Finance/expense  Finance/income  Finance/allocation
Finance/fund  Finance/increase  Finance/audit
Material/public  Material/assets  Material/store  Material/operation
Production/public
Procurement/public  Procurement/admittance  Procurement/plans
Procurement/purchase  Procurement/inbound  Procurement/payment
CRM/public  CRM/customer
Portal/public
Research/public
```

Portal 自己那段白名单校验是**被注释掉的**（`oss.js:151-153`），参数注释却写着
「只允许在 ossFilePathOptions 中取值」。**SDK 把它恢复成硬校验**：这是白名单，不是建议。

### 4.2 objectKey 生成

模板：`{folder}/{YYYY}/{MM}/{name}{.ext}`，逐字段复刻 `oss.js:171`。
随机名复刻 `oss.js:12` 的 `customAlphabet('abcdefghijklmnopqrstuvwxyz', 16)` —— **16 位小写字母**。

⚠️ **只复刻形状，不复刻 nanoid 的算法**：nanoid 用自己的 PRNG + 掩码，本实现用
`crypto.randomBytes` 取模 26。两者产出的都是「16 位小写字母」，但**同一次调用不会得到同一个串**，
不要拿它做跨实现的断言。

**一处刻意的不一致**：Portal 的 `renameRandom` 会把 `file.name.split('.').pop()` **原样**拼成扩展名，
所以 `a.evil?x=1` 会得到一个带 `?` 的对象名。本实现只接受一张扩展名白名单
（`SAFE_EXTENSIONS`，39 个：png/jpg/gif/webp/svg/pdf/doc/docx/xls/xlsx/ppt/pptx/csv/txt/
zip/rar/7z/mp3/mp4/mov…），**不在表里就不带扩展名**。
理由：那个字符串要被拼进 URL 路径与签名资源，原样透传等于让调用方决定请求的形状。

### 4.3 签名：**V1**（结论有出处）

调查 §8 留的问题 ——「ali-oss 6.x 在这个 Portal 里默认用 V1 还是 V4」—— **答案是 V1**。
三条证据，逐条可复核（`Projects_Js` 只读）：

| # | 出处 | 内容 |
| --- | --- | --- |
| 1 | `node_modules/ali-oss/lib/common/client/initOptions.js:50` | `authorizationV4: false // 启用v4签名，默认关闭` |
| 2 | `common/utils/oss.js:33-40`（`ossConfigV2`） | 只给 ak/sk/region/bucket/cname/endpoint，**没有 `authorizationV4`** |
| 3 | `node_modules/ali-oss/lib/common/utils/createRequest.js:31,101-102` | 该字段为假 → `x-oss-date` 用 RFC1123 格式、走 `this.authorization(...)`（V1 分支），V4 分支不执行 |

装的是 **ali-oss 6.20.0**（`node_modules/ali-oss/package.json`；Portal 的 `package.json:45` 声明 `^6.17.1`）。
**V4 的代码在包里存在**（`lib/common/signUtils.js:199` 起），但**默认关着**，Portal 也没打开。

canonical string（`sigutils.js:44-83`）：

```
VERB\n
Content-MD5\n
Content-Type\n
Date\n                     ← ali-oss 不发 Date 头，这里放 x-oss-date 的值（RFC1123 GMT）
CanonicalizedOSSHeaders\n  ← 排序后的 x-oss-*，形如 "k:v"
CanonicalizedResource
```

签名 = `base64(HMAC-SHA1(accessKeySecret, canonicalString))`，
头 = `Authorization: OSS {accessKeyId}:{signature}`。

**两个容易漏的点**（都已经有测试钉住）：

1. **`x-oss-date` 在 canonical string 里出现两次** —— 一次占 `Date` 的位置，一次在
   canonicalized OSS headers 里。ali-oss 不把它从后者排除（只按 `x-oss-` 前缀收集），
   OSS 服务端也是这么算的。**不是笔误。**
2. **URL 上是 `?acl=`（带等号），canonical resource 上是 `?acl`（不带）** ——
   这是 ali-oss 的真实行为：`url.format({acl:''})` 会补上等号（实测过），
   而 `buildCanonicalizedResource` 对空值不拼 `=`。两处都照抄。

`region` **V1 签名用不到**（它只出现在 V4 的 scope 里），收在配置里只为与 `ossConfigV2` 逐字段对齐。

### 4.4 URL

- cname 模式（**默认**，依据 `oss.js:37` 的 `cname: !!endpoint`）：`https://{endpoint}/{key}`
- 非 cname：`https://{bucket}.{endpoint}/{key}`
- **canonical resource 两种模式都是 `/{bucket}/{key}`**（ali-oss 的 `_getResource` 恒带桶名）

⚠️ **刻意不复刻的一处缺陷**：ali-oss 的 `secure` 默认 `false`，所以 `ossPut` 实际返回的是
**`http://`** 开头的 url，Portal 前端靠 91 处 `fixHttpsUrl` 兜底。
**SDK 直接给 https**，`secure: false` 要显式传。

### 4.5 `PutObjectACL` 不能省

`oss.js:176-177` 在 `put` 之后固定做 `getACL` + `putACL(path, 'public-read')`。
桶不是默认公共读，**省了这一步的失败方式是静默的**：上传返回 200，但 url 谁都打不开。

所以 `upload()` 把 put + putACL 做成**一步**，调用方没有机会漏掉后半步。
之后还会再 `GetObjectACL` 一次，把**OSS 答复的** ACL 放进 `result.acl` ——
第 2 步返回 200 只说明 OSS 收下了请求，不代表 ACL 真变成了 `public-read`。
（本项目「接口返回成功不算验证」那条规矩在上传链上的落地。）

## 5. 操作步骤（AI 侧）

```
1. 先问清楚：要传的是哪个本地文件？（base-upload 不产生字节，字节必须是现成的）
2. 选 folder —— 按文件属于哪个业务域选，拿不准就问用户。
   HR/* 人事、Finance/* 财务、Material/* 物料、Procurement/* 采购、
   CRM/* 客户、Portal/public 门户、Public/public 临时
3. base-upload-file { path, folder }
   → { url, objectKey, size, contentType, acl }
4. 检查 acl === 'public-read'。不是的话，这个 url 别人打不开，别急着提交表单。
5. 把 url 交给带附件的写能力（例：base-image-create 的 url 参数）。
6. **如果第 5 步失败或用户放弃了 → 把刚传的那个对象删掉**（不然就是孤儿）：
   base-upload-delete { objectKey }        // 一次一个
   base-upload-delete-multi { objectKeys } // 一次多个，换行或逗号分隔
```

**孤儿对象现在是可清理的了**（2026-09-21 起）：上传成功但业务表单没提交成功时，
调 `base-upload-delete` 把刚传的 `objectKey` 删掉即可 —— `base-upload-file` 的返回值里就带着它。

⚠️ 删除**不可撤销**，且 `deleteObject` **幂等**（删不存在的 key 也成功），
所以别拿它的返回值当"删掉了"的证据 —— **要删完再读一次**（`base-upload-acl-get` 会失败，
或直接匿名 GET 那个 url）。LIVE 测试就是这么做的。

| # | 原来的推断 | 实测结论 | 判据 |

**⑥（2026-09-21 追加）删除链路也在真实 OSS 上验过**：

- `deleteObject` 真删掉了那个遗留的测试对象（删前匿名 GET 200 → 删后 403），
  再跑一次是 403 → 403，**顺带证实了 `DeleteObject` 的幂等性**；
- `deleteMulti` 在 LIVE 组里真传 3 个、真批量删掉，**OSS 逐个回报了那 3 个键**，
  删完三个 url 都打不开（见 LIVE 组的 ⑤）。

**③ 的对照实验**（这是本单最值得记的一条，因为"必需"只能靠对照证明）：

1. 用签名发一次 `PutObject`，**刻意不调 `PutObjectACL`**；
2. 立刻匿名 GET 那个 url → **打不开**（非 200）；
3. 补一次 `PutObjectACL` → 同一个 url → **200，字节一致**。

同一个对象、同一个 url，**唯一的变量就是 ACL**。所以「桶不是默认公共读、
`putACL` 不能省」从推断变成了实测；`upload()` 把 put + putACL 做成一步是对的。

**④ 的顺序对照**：对象还不存在时就先 `putAcl` → OSS 直接拒绝（抛 `OssRequestError`）。
所以"先传字节、再设 ACL"这个顺序不是随便排的。

### 6.3 怎么复现（凭据从哪来、怎么跑）

**⚠️ 凭据绝不手工抄。** 抄进命令行会进 shell 历史，抄进文件会进提交。
走 `smoke/with-oss-credentials.sh`：它在**一个进程里**读字段 → 注入环境变量 → 执行命令，
凭据全程只在环境变量里，**不落盘、不打印、不进任何产物**：

因为带着半份配置往下跑，会把「少读了字段」伪装成「签名算错了」。

`smoke/upload.mjs` import 的是 `dist/`（要先构建），而 LIVE 组走 vitest 直接编译 TS。
两者跑的是**同一份能力实现**，`smoke/upload.mjs` 是给"没有 vitest 的场合"用的入口。

**LIVE 组会真写测试桶**，所以它自带两条纪律：

1. 只在 `OSS_ACCESS_KEY_ID` / `_SECRET` / `_BUCKET` / `_ENDPOINT` 四个都在时才跑
   （平时 `pnpm test` 里它是 skipped，不碰网络）；
2. **每个用例建的对象都在结束时删掉**，`afterAll` 还有一层兜底 ——
   **只删自己这次建的**（对象名带 `SDK-TEST-` 前缀 + uuid）。

**清理证据**（每次跑都会验）：最后一条用例把本次**曾经建过的每一个**对象都匿名 GET 一遍，
断言全部打不开。它同时钉住了「循环真的走过 ≥4 个对象」，
防止哪天退化成在空集合上空转的假测试（§6.4 记了这个坑）。

### 6.6 测试产物怎么清理（可复现）

**第一步：让 `base-upload-file` 的返回值被记下来。** 它带回 `objectKey` —— 那是清理的唯一凭据；
只有 url 也能反推（url 去掉 `https://{endpoint}/` 前缀就是 objectKey）。

**第二步：删。** AI 侧调 `base-upload-delete { objectKey }`；一次多个用
`base-upload-delete-multi { objectKeys }`（换行或逗号分隔，一次最多 1000 个）。

**第三步（可选，但建议）：确认删干净了。** `deleteObject` 是幂等的，返回值说明不了问题：

```bash
# 再读一次那个 url：403/404 才算删掉；200 就是没删掉
curl -s -o /dev/null -w '%{http_code}\n' '<上传时拿到的 url>'
```

**已经有过一个遗留对象，是这么清掉的**（2026-09-21，可作为这条 recipe 的实例）：

```bash
OSS_CLEANUP_OBJECT_KEY=HR/approval/2026/09/wftdvmcbwuqtdwcz.png \
  smoke/with-oss-credentials.sh pnpm exec vitest run test/base-upload.test.ts -t 遗留
```

实跑结果：**删前匿名 GET = 200（69 字节）→ 删后匿名 GET = 403**；
再跑一次是"删前 403 / 删后 403"，顺带证明了 `DeleteObject` 的幂等性。

⚠️ 这个入口**必须显式点名一个 key**（`OSS_CLEANUP_OBJECT_KEY`），一次只删一个。
**不提供"按前缀批量清"** —— 桶里有别人的东西，一个能按前缀扫射的删除入口迟早会误伤。
批量清理请走 `base-upload-delete-multi` 并**自己列出**要删的键。
