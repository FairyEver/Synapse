# 待办与角标（基础能力 `base-todo-list` / `base-todo-counts`）

**这不是一个页面**。它们是 Portal 布局组件在**每次路由变化**时打的那几条
（`app/portal/components/portal/layout/index.vue`），
是"外壳"这一层里最纯的一块：体量极小（53 B / 44 B / 5 KB），契约清晰，纯只读。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/base-shell.ts`；
回归测试 → `test/base-shell.test.ts`；真实环境只读冒烟 → `smoke/read-base-shell.mjs`。

## 它回答的问题

> 「我现在有什么要处理的？」——这是 AI 最常被问、也最该被答对的一句话。

## ⚠️ 它与 `backlog-task-examine-list` **不是一回事**（已核对）

两条接口长得很像，容易混：

| | `backlog-task-examine-list`（已存在） | 本能力 `base-todo-list` |
| --- | --- | --- |
| 路径 | `/admin-api/bpm/hr/task/list-by-category-web` | `/admin-api/bpm/task/list-by-category` |
| 参数 | `styleV2` 等**页面表单参数** | `finished` / `name` / 分页 |
| 定位 | HR 端的「待办事项」页面 | 布局组件的**角标** |
| Controller | `BpmHrTaskController` | `BpmTaskController` |

两条接口、两个 Controller。**本单没有改动前者**。

## 接口

| 能力 | 路径 | 参数 | 返回 |
| --- | --- | --- | --- |
| `base-todo-list` | `GET /admin-api/bpm/task/list-by-category` | `finished`、`name`、`pageNo`、`pageSize` | `{list, total}` |
| `base-todo-counts` | 上面那条（`finished=1&pageSize=1` 的 `total`）<br>+ `GET /admin-api/performance/basedata/kpimessageremind/getUnreadcount`<br>+ `GET /admin-api/finance/expense-review/pending-count` | 无 | `{todo, unreadMessages, expensePending, failures}` |

## ⭐ `finished` 是**三态**，不是两态 —— 这是本能力最容易写错的地方

调查 §8.5 留了「`finished=1` 与 `finished=2` 哪个是待办」没确认。
答案在**后端源码**里，两处：

```
erp-module-bpm/…/api/vo/task/BpmTaskPageReqVO.java:
    // @Schema(description = "待办/已办标识：1:待办，2:已办", required = true, example = "1")
    private Integer finished;

erp-module-bpm/…/service/task/BpmTaskServiceImpl.java:1578-1584（getTaskListByCategory）:
    if (pageVO.getFinished() != null) {
        if (pageVO.getFinished() == 1) { taskQuery.unfinished()... } else { taskQuery.finished()... }
    }
```

也就是说：

| `finished` 的值 | 后端行为 | 实测 `total` |
| --- | --- | --- |
| **不传（`null`）** | **不加任何状态过滤** | **562 ~ 563** |
| `1` | `unfinished()` → **待办** | **25** |
| `2` | `finished()` → 已办 | **415 ~ 416** |
| **`0`** | **也落进 `else` → 已办** | **415 ~ 416** |

三个后果：

1. **`0` 不是"全部"**，它被当成"已办"。谁要是以为 `finished=0` 是"不过滤"，就会拿到 415 条
   并以为是全部 —— 而那 415 条**看起来完全正常**。
2. **562 ≠ 25 + 415**。"不传"是**不做状态过滤**的那一份，与两类的口径不同，不是两类之和。
   （这是实测数字，不是笔误。）
3. 所以能力**不收 `finished` 的裸值**，只收 `scope: 'todo' | 'done' | 'all'`，
   在实现里映射成「1 / 2 / **不发这个参数**」——把那个坑关在 SDK 内部。

`test/base-shell.test.ts` 里有一条断言专门锁「`scope='all'` **一定不发** `finished`」，
因为这是本批**唯一的静默错**：写错了不会有任何报错，只有一份悄悄变成"已办"的数据。

## 参数契约

### `base-todo-list`

| 参数 | 类型 | 必填 | 默认 / 上限 | 说明 |
| --- | --- | --- | --- | --- |
| `scope` | `enum` | 否 | `todo` | `todo`(→`finished=1`) / `done`(→`finished=2`) / `all`(→**不发**) |
| `name` | `text` | 否 | — | **服务端**过滤，后端 `taskNameLike("%…%")`。实测 `name=审批` → 17 条；`name=用章` → 0 条 |
| `pageNo` | `number` | 否 | 1 | |
| `pageSize` | `number` | 否 | 默认 **20**，硬上限 **50** | `-1` 拒绝 |

返回：`Promise<{ list: TodoItem[]; total: number; scope: TodoScope }>`

`list[]` 是**摊平**过的（后端把流程信息放在 `processInstance` 里）：

| 字段 | 来源 | 实测 |
| --- | --- | --- |
| `id` | `list[].id` | uuid |
| `name` | `list[].name` | `"通用审批"` / `"用章审批"` —— 这是**任务名**，能用来做服务端过滤 |
| `createTime` / `claimTime` | 同上 | `"2026-09-10 10:08:05"` / `null` |
| `processInstanceId` / `title` / `processDefinitionKey` | `processInstance.*` | `title` 实测为 null |
| `startUserId` / `startUserNickname` | `processInstance.*` | `18243` / `"姚淼鑫"` |
| `result` | `processInstance.result` | 待办侧 `null`、已办侧出现过 `4`（**语义未核实**） |

### `base-todo-counts`

无参数。返回：

```ts
{
  todo: number | null             // bpm 待办数（finished=1&pageSize=1 的 total）
  unreadMessages: number | null   // 未读消息数
  expensePending: number | null   // 待审费用数
  failures: Array<{ key: string; message: string }>
}
```

**失败不整体抛**，逐条捕获：失败的那项为 `null` 并记进 `failures`。

> ⚠️ **`null` 不等于 `0`**。待审费用那条在 Portal 里是**条件请求**
> （侧边栏有那个菜单才打，实测耗时 588 ~ 1047 ms，是本批最慢的一条），
> 它失败是正常情况。若把失败折成 `0`，调用方会读成"没有待审费用" ——
> 那是把"不知道"说成"没有"。`test/base-shell.test.ts` 里有一条断言专门锁这件事。

## 体积怎么切

| 入口 | 一次拿到多少 | 上限 |
| --- | --- | --- |
| `listTodos({scope})` | 该 scope 的前 N 条 + `total` | 默认 20 / **硬上限 50** |
| `listTodos({name})` | **服务端**过滤后的前 N 条 + `total` | 同上 |
| `getTodoCounts()` | 三个数字 | 各 1 条 |

**没有 `listAll()`**。硬上限的理由是实测的：`pageSize=500` 会吐回 **314,395 B**。
要"看规模"看 `total`（待办 25 / 已办 415 ~ 416 / 全部 562 ~ 563）。

## 缓存：**不缓存**

待办**逐次带参数**（scope / 关键字 / 分页），而且它本质上"问一次就要最新的"
——角标的语义就是实时。与本批的菜单 / 工作台（有缓存）形成对照。

## module-type：**不发这个头**

- **合成路径**：`/base-data/todo` → `resolveModuleType()` 返回 `null` → 不发。
- **后端源码直读**：`BpmTaskController#getTaskListByCategory` 上没有 `@DataPermission`，
  查询条件是 `taskAssignee(登录用户)` —— 这条的依据是本批里最硬的一档。
- **实测**：带 `module-type: 11` 与不带，`data` **逐字节相同**（2,637 B / 2,637 B，基线稳定）。

## 逐字段基准（实测）

冒烟：`smoke/with-portal-token.sh node smoke/read-base-shell.mjs`
（2026-09-20，`biz-api-test.wodecorp.cn`，租户 1；**全程只读 GET**）

```

  item 字段：["id","name","claimTime","createTime","suspensionState","processInstance"]
finished=2（已办）：total 415 / 返回 10 条 / 5109 B / 377 ms；processInstance.result=4
finished=0：       total 415（← 落进"已办"那一支）
不传 finished：    total 562 / 6789 B / 278 ms
name=审批（服务端过滤）：total 17 / 返回 5 条
name=用章（服务端过滤）：total 0 / 返回 0 条
⚠️ pageSize=500：314395 B / 500 条 / 415 ms

getUnreadcount：53 B / 211 ms / data = 302（number）
expense-review/pending-count：44 B / 611 ms / data = 1
待办数（finished=1&pageSize=1 的 total）：25
```

> 记录的那一次为准，**不要把某个具体数字当成不变量写进断言**。

## 没做 / 不确定

- **`processInstance.result` 的语义没有核实**。实测待办侧是 `null`、已办侧出现过 `4`，
  但 4 代表什么（通过？驳回？）没有查到。本能力**原样返回、不解释**。
- **`finished` 只映射了三态，没有暴露**。若将来发现别的值有别的含义，
  要改的是 `TodoScope` 这个枚举，不是让调用方传裸值。
- **`expense-review/pending-count` 的 1047 ms 没有解释**：它是最慢的一条
  （44 B 的响应要 0.6 ~ 1 秒），慢在哪没有查（可能是后端聚合查询）。
  `getTodoCounts()` 用 `Promise.all` 并发打三条，所以整条链的耗时由它决定。
- **没有做「点进去看某条待办」**：那要流程详情能力，属另一条线。
- **`base-todo-counts` 没有把「已办数」一起读**：Portal 的布局组件只打三条
  （未读 / 待办 / 待审费用），本能力忠实复刻这三条。要已办数用
  `listTodos({ scope: 'done', pageSize: 1 })` 取 `total`。
- **`bpm/task/list-by-category` 的其它过滤参数没有暴露**：
  `processCategories` / `processDefinitionKey(List)` / `createTime` / `taskKey` /
  `startUserId` / `categoryList` 都存在（源码直读），但页面用不到、本单也没验证，
  所以不进契约。
