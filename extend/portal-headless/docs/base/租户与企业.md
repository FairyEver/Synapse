# 租户与企业（基础能力 `base-tenant-list` / `base-tenant-get`）

**这不是一个页面**。它回答的是「**我这账号属于哪些企业、每家开通了哪些系统**」——
Portal 首屏 `runLegacyFullInitTasks`（`app/portal/utils/router/session.js:35-59`）
的**串行 4 步里有 2 步**就是它，与用户落在哪一页无关。

四件套的其它三件：能力定义与参数契约 → `src/capabilities/base-tenant.ts`；
回归测试 → `test/base-tenant.test.ts`；真实环境只读冒烟 → `smoke/read-base-tenant.mjs`。

## 它为什么入选

派单给的三条标准逐条对：

| 标准 | 结论 | 依据 |
| --- | --- | --- |
| ① 别的能力依赖它 | **成立** | `tenant-context` 是会话基础数据里**两个 `critical: true` 之一**，`tenant-system` 还 `deps` 它（`src/session/base-data.ts`）。也就是说 SDK 早就要求每个会话先把这份数据拉下来，**却从没让 AI 看到过** |
| ② 是刷新时必打的「外壳」接口 | **成立** | `docs/base-capabilities.md` §2.1 的 **#4 / #5**，串行 4 步里的第 1、2 步 |
| ③ 契约清晰、能只读验证 | **成立** | 两条都是纯 GET；本页每个数字都是本单实测 |

它与第二批的 `base-user-info` 是**同一个形状的缺口**：数据已经在会话里，缺的只是一个能力入口。
省下来的不是请求次数，是**接线方不用自己再写一遍归一化**。

## 接口

| 项 | `base-tenant-list` | `base-tenant-get` |
| --- | --- | --- |
| 路径 | `GET /admin-api/hr/system-tenant/getUserTenantsByPage` | `GET /admin-api/system/tenant/get` |
| 参数 | `pageNo` / `pageSize`（本能力只用 `pageSize=200`） | `id`（**必填**） |
| 分页 | 有（后端支持）；能力内部翻页 | 没有 |
| 返回 | `{ list: [...], total }` | 单个对象（11 字段） |
| http 实例 | `platform`（补 `/admin-api`） | 同左 |
| Portal 调用点 | `utils/system.js:606-626` `fetchTenantList` | `utils/system.js:673` `fetchTenantSystem` |

### ⚠️ `base-tenant-get` 的 `id` 必须是**主键 id**

它走的是「按主键查」，**传企业名查不到**（实测租户 1 的 `id` 就是 `1`）。
候选入口由能力定义里的 `lookup` 指到 `base-tenant-list`。

## 参数契约

| 能力 id | 入口方法 | 参数 | 必填 | 默认 / 上限 |
| --- | --- | --- | --- | --- |
| `base-tenant-list` | `listTenants({keyword, limit})` | `keyword` | 否 | 匹配 `name` / `shortName` / `code`，**SDK 本地过滤**（请求里没有这个参数） |
| | | `limit` | 否 | 默认 **20**，硬上限 **100** |
| `base-tenant-get` | `getTenant({id})` | `id` | **是** | `null` / `undefined` / 空白串都拒绝，**且一个请求都不发** |

> **为什么列表不强制关键字**：实测本账号只有 **6 家**（`total: 6`），规模有界 ——
> 与第二批的 `base-menu-paths`（36 条）同类，不是 conventions 第 11 条针对的"几千个候选"。
> 判据是实测规模，不是"参数长得像什么"。

## 敏感字段：白名单出口（本能力最要紧的一条）

`getUserTenantsByPage` 实测返回 **21 个字段**，其中这三个是实名 / 联系信息：

| 字段 | 实测分布（6 家企业） | 是什么 | 处置 |
| --- | --- | --- | --- |
| `identityNumber` | 6 条都有键，**非空 1 条**（长度 18） | **身份证号** | **裁掉** |
| `identityImg` | 6 条都有键，**非空 5 条**（长度约 185） | 证件照 URL（`a:2:{…}` 序列化串） | **裁掉** |
| `contactMobile` | 6 条都有键，**非空 5 条**（长度 11） | 联系人手机号 | **裁掉** |

处置方式与第一批（`password2` / `salt`）、第二批（同）、本批 `base-sale`（`shopuserIdentity`）
**完全一致：白名单**，不是黑名单。

| 视图 | 输出字段 | 原始来源 |
| --- | --- | --- |
| `TenantSummary` | 9 个 | 原始 21 个里挑的，其中两个**改名**：`useSystem` → `systems`、`createTime` → `createDate` |
| `TenantDetail` | 9 个 | 原始 11 个里挑的，裁掉 `contactMobile` 与 `contactName` |

**为什么白名单而不是黑名单**：后端将来往这个对象里加字段时，黑名单要求"每次记得来加一条"，
漏一次就是一次外流，且**不会有任何测试变红** —— 那是本仓库最怕的失败形态。
白名单的失败方向相反：最多暂时取不到，看得见、可修。
`test/base-tenant.test.ts` 里有三条断言锁这件事（列表出口 / 详情出口 / "夹具里加新字段也漏不出去"）。

> ⚠️ **一条自我纠错**：本节初稿只看了列表第一条，写下"6 家里 1 家带证件号"。
> 实测分布出来后才知道那只对 `identityNumber` 成立 —— `identityImg` 与 `contactMobile`
> 是 **5/6 非空**。数字以冒烟脚本的输出为准，脚本每跑一次都会重打一遍分布。

## 体积怎么切

| 项 | 值 |
| --- | --- |
| 一页多少条 | `TENANT_PAGE_SIZE = 200`（与 `src/session/base-data.ts` 的 `TENANT_LIST_PAGE_SIZE`、`system.js:600-606` 的 loopFetch 配置同值） |
| 最多翻几页 | `TENANT_FETCH_MAX_PAGES = 5`（= 最多 1000 家），超出**如实置 `truncated: true`** |
| 出口上限 | `limit` 默认 20 / 上限 100 |
| `listAll()` | **没有** |

`listTenants()` 的返回带三个诊断字段：`total`（服务端给的 total）、`matched`（关键字命中数）、
`pages`（真的翻了几页）。`truncated` 是**两种情况的合成信号**：服务端还有没翻到的页，或本地按 `limit` 切掉了。

### ⚠️ 实测到的坑：`pageSize=-1` 不但不省事，还会把 `total` 归零

```
pageSize=200 → list 6 / total 6
pageSize=-1  → list 6 / total 0
```

也就是说它**不是**"全量拉取"，它只是**把总数弄丢了**（`list` 还是那一页）。
本能力**不暴露 `pageSize`**，所以调用方碰不到它；这条写在这里是为了别有人后来"顺手加个 pageSize 参数"。
`smoke/read-base-tenant.mjs` 把这条固定成每次都会跑的对照。

## 缓存：只缓存列表，**详情刻意不缓存**

| 数据 | 缓存 | 切片键 |
| --- | --- | --- |
| 列表 | 实例内 TTL，默认 **30 分钟**（与 `BASE_SHELL_CACHE_TTL_MS`、`DEFAULT_ABSOLUTE_TTL_MS` 同值，测试里钉死） | `tenant-list` |
| 详情 | **不缓存** | — |

三个决定：

- **切片键不并进 `limit` / `keyword`**：`limit` 是出口裁剪、`keyword` 是本地过滤，
  都不影响"拉什么"。并进去会让 `limit=5` 与 `limit=20` 各打一遍同一个请求。
- **详情不缓存**：263 B / 约 200 ms，按 id 查。为它多开一族 `tenant-detail:<id>` 切片键
  换不来什么，却让"这家企业的账号数变了没有"多一层陈旧窗口。这个不对称是有意的，测试里钉了。
- **并发**走 `src/session/single-flight.ts`，失败**不进缓存**（下一次会真的再试）。

### ⚠️ 为什么**不**复用会话里的 `tenant-context`（反直觉，但很重要）

直觉上该复用（那个会话项装的就是这个接口的返回）。**本能力刻意不复用**：

`src/session/base-data.ts` 的 `tenant-context.load` 是「**命中即停**」—— 找到当前租户就 `return`，
不再翻后面的页。拿它当「我属于哪些企业」会**静默少报几家**：当前租户排在第 1 页第 3 条时，
第 4 条以后就不会出现，而返回值看起来完全正常。

宁可多打一次 3.8 KB 的 GET。这条也是 `listTenants` 不能读会话的原因——
它和 `base-user-info` 复用 `user-basic` 的取舍**不一样**，差别就在"会话里那份是不是全量"。

## module-type：**不发这个头**

- **合成路径**：`/base-data/tenant-list` / `/base-data/tenant-detail` → `resolveModuleType()` 返回 `null` → 不发（conventions 第 2 条）。
- **实测（交错四次：不带 → 带 11 → 不带 → 带 11）**：

```
企业列表：不带 3784 B / 带 11 3784 B → data 完全相同（基线稳）
企业详情：不带  263 B / 带 11  263 B → data 完全相同（基线稳）
```

- **口径**：这是"**本账号实测**不敏感"，**不是**"后端不读这个头"。需要收窄时由接线方通过
  `BaseTenantOptions.moduleType` 显式给 —— SDK 不猜。

## 逐字段基准（实测）

冒烟：`smoke/with-portal-token.sh node smoke/read-base-tenant.mjs`
（2026-09-20，`biz-api-test.wodecorp.cn`，租户 1，**全程只读 GET，共 11 次**）

```
A. 企业列表 pageSize=200：3784 B / 418 ms / list 6 条 / total 6
   原始字段 21 个：["id","name","code","contactName","contactMobile","nickname","headImg",
     "shortName","contactUserId","isChinaResident","identityNumber","identityImg","useSystem",
     "packageId","status","creator","createTime","updater","updateTime","deleted","tenantAdmin"]
   敏感字段分布：identityNumber 非空 1/6（长度 18）；identityImg 非空 5/6（约 185）；
                contactMobile 非空 5/6（长度 11）
   能力白名单保留 9 个输出字段（对应原始键名 7 个 + 两个改名）
   被裁掉 14 个：["contactMobile","nickname","headImg","contactUserId","isChinaResident",
     "identityNumber","identityImg","useSystem","packageId","creator","createTime",
     "updater","updateTime","deleted"]
   useSystem 原值样例："1,2,3,4,5,6,10"
   tenantAdmin 原值分布：实测列表里出现过 null（能力归一成布尔：只有 1/true/"1" 为真）

B. 企业详情 id=1：263 B / 274 ms / 字段 11 个
   ["id","name","contactName","contactMobile","status","website","packageId","expireTime",
    "accountCount","createTime","useSystem"]
   useSystem="1,2,3,4,5,6,10"
   expireTime=null / accountCount=null —— ⚠️ 本账号这两项是 **null**，别读成"已过期"
   contactMobile 存在：true（能力裁掉它）
```

### `useSystem` 只给数字，**不贴标签**

`useSystem` 是逗号串。Portal 的加工只有 `split(',').filter().map(Number)`
（`app/portal/utils/system.js:677-683`），**它自己也不贴标签**。

前端源码里能查到的映射只有两处，且都是当查询参数用的：
`components/portal/finance/**` 写死 `useSystem=2`（财务）、
`components/portal/supply/**` 写死 `useSystem=5`（供应链）。

**其余数字（含实测出现的 `10`）与中文名的对应，本单没有找到权威出处**，所以返回值是
`systems: number[]`，**不提供中文标签** —— 贴错标签比不贴更糟（那是一个看起来完全正常的错值）。

## 没做 / 不确定

- **`expireTime` 不派生"有没有过期"**：它的格式 / 时区口径没核实，本能力只原样返回字符串。
- **`useSystem` 的中文标签表**没有（见上）。`10` 是什么，没查到。
- **多租户切换没有做**：本能力只"读"，不"切"。切租户是会话层的事（一个 axios 实例 = 一个用户的一个租户，
  conventions 第 5 条），本文件不碰 `src/session/**`。
- **`base-tenant-current`（"我在哪个企业"）刻意没建**：调用方创建 SDK 时**自己就传了 `tenantId`**
  （见 `smoke/with-portal-token.sh` 读的就是 cookie `hr-0.0.0-tenant`），所以这条能力是冗余的。
  要做也只能读会话，而会话键 `tenant-context` 的形状是 `{tenantId, tenants}`——那又把它绑死在
  `SessionBaseDataReader` 上，收益不抵耦合。
- **`org/sensitive/info`（调查 §2.1 的 #7）没有做，而且理由是安全性的**：
  实测 206 B，返回 `{ id, mobile: "…", isDel: 1, … }`。查源码，
  `app/portal/hooks/hr/useSensitiveAction.js:18-19` 的用法是
  `if (sensitive.state.isDel === 1) { 直接放行 } else { 弹验证框 }` ——
  **`mobile` 是"敏感操作二次验证"用的那个号码**。把它端给模型等于把验证码那条路的号码
  告诉被验证方，这是反特性，不是能力缺失。
- **`{CRM}/vue/getUserInfo`（#3）没有做**：它走 `crm` 实例
  （`https://biz-api-test.wodecorp.cn/admin-crm-api`，与 `sale` 同类），
  **本单没有实测过它的任何一条返回**。"没实测就不建"，不做半成品。
