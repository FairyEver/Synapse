# 人员候选（基础能力 `base-user-search`）

**这不是一个页面**。它是「人员选择器」那个组件的无头形态——用户的原话是
「公共的字典、人员组织……它在 Portal 中是一个组件，那么它在这个 SDK 中就应该是一个基础能力」。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/base-shell.ts`；
回归测试 → `test/base-shell.test.ts`；真实环境只读冒烟 → `smoke/read-base-shell.mjs`。

## 它回答的问题

> 「会议参会人选谁」「这条流程的审批人是谁」「这个单子指派给谁」——
> 一切 `kind: 'search' / 'tree'` 的人员参数，候选都从这里来。

`docs/base-capabilities.md` 把它判为「**部分**覆盖」，理由是已有
`meetingApplication.searchUsers`（挂在会议室申请页上）。**这个判定是准的**，
本能力做的就是把它**提升为公共 id**。

## 与 `meeting-user-search` 的关系：同一个接口，两条能力 id（刻意如此）

| | `meeting-user-search` | `base-user-search`（本能力） |
| --- | --- | --- |
| 接口 | `GET /admin-api/system/user/simple-page` | **同一个** |
| 参数 | `keyword`(必填) / `deptId` / `pageNo` / `pageSize` | `keyword` / `deptId` / `pageNo` / `pageSize` |
| 强制关键字 | 是 | 是（规则相同） |
| `pagePath` | 会议室申请页 | 合成的 `/base-data/user-search` |
| 定位 | **页面级**的兼容入口 | **公共** lookup id |

**这不是重复实现**，是刻意的双入口。合并任一边都有代价：

- 删掉 `meeting-user-search`：会议室申请的能力定义会失去它的候选入口
  （`meeting-application.ts:160` 的 `lookup.capabilityId` 指着它）。
- 把 `meeting-user-search` 改名叫 `base-user-search`：要动 `src/capabilities/meeting-application.ts`，
  那是**本单的可写文件集之外**。

所以本批的做法是给出公共 id，并在文档里点名接线方向：**后续所有 `lookup.capabilityId`
一律指 `base-user-search`**；`meeting-user-search` 保留为页面级兼容入口，
由它的 owner 决定何时收敛。**两者今天行为一致**（同一 URL、同一强制关键字规则）。

## 接口

| 项 | 值 |
| --- | --- |
| 路径 | `GET /admin-api/system/user/simple-page` |
| 参数 | `pageNo`、`pageSize`、`nickname`（关键字）、`deptId`、`postName` |
| 分页 | **有**（renren 默认分页名 `pageSize`） |
| 返回 | `{list, total, summary, summaryRows}` |
| http 实例 | `platform` |
| Portal 调用点 | 会议室申请表单的参会人选择器（`meeting-application.ts:292`），页面自己用 `pageNo=1..9&pageSize=500` **全量拉 4500 人** |

## ⚠️ 「必须先要关键字」是 **SDK 侧**的规则，不是后端强制的

这是本能力最容易写错的一句话。**实测**：

| 请求 | 结果 |
| --- | --- |
| `?pageNo=1&pageSize=10`（**无关键字**） | **200 OK**，`total` = **4225**，正常返回 10 条 |
| `?pageNo=1&pageSize=-1` | **200 OK**，**577,845 B**，返回 **4225 条** |
| `?pageNo=1&pageSize=500` | 200 OK，68,819 B，500 条 |
| `?nickname=张` | 200 OK，`total` = 436 |
| `?deptId=101` | 200 OK，`total` = 21 |

后端**一条都不拦**。所以：

> **拒绝逻辑写在 `searchUsers()` 里**：`keyword` 与 `deptId` 至少要给一个，
> 否则直接抛错、**一个请求都不发**。

**别把这条写成"后端要求关键字"**——那会让人以为可以省掉 SDK 侧的检查。
真实的理由是 conventions 第 11 条：4225 条塞进 AI 上下文会把前面的对话冲掉。

## 为什么 `pageSize = -1` 是**拒绝**而不是**截断**

- 无关键字时 `-1` 返回 **577,845 B**；
- `pageSize = 500` 返回 68,819 B。

对 `500` 这种"稍微大一点的页"，**截断成 50** 是合理的（调用方拿到的还是有效的一页）。
对 `-1` 不一样：**它不是一个"大一点的页"，它是一次全量请求**。
静默截断会让调用方以为"我拿到了全部，只是被 SDK 削掉了尾巴"，而它其实只拿到第 1 页。
**拒绝更好**——语义上没有歧义。

## 参数契约

| 能力 id | 入口方法 | 参数 | 必填 | 默认 / 上限 |
| --- | --- | --- | --- | --- |
| `base-user-search` | `searchUsers({keyword, deptId, pageNo, pageSize})` | `keyword`（→ 后端 `nickname`） | 与 `deptId` **二选一** | — |
| | | `deptId` | 同上 | 候选走 `base-dept-search`（第一批） |
| | | `pageNo` | 否 | 1 |
| | | `pageSize` | 否 | 默认 **20**，硬上限 **50**；`-1` 直接拒绝 |

返回：`Promise<{ list: SimpleUser[]; total: number }>`

`list[]` 的字段（实测）：

| 字段 | 本账号实测 | 说明 |
| --- | --- | --- |
| `id` | `197951` | 数字 → 归一成**字符串** |
| `nickname` | `"张洪量"` | 显示名 |
| `deptId` | `101` | 数字 |
| `code` | `"2026090101"` | 工号 |
| `deptName` | **`null`** | ⚠️ 恒为 null |
| `staffDuties` | **`null`** | ⚠️ 恒为 null |
| `realName` | **`null`** | ⚠️ 恒为 null |
| `staffCode` | **`null`** | ⚠️ 恒为 null |

> ⚠️ **只有 4 个字段真的有值**：`id` / `nickname` / `deptId` / `code`。
> **别指望这个接口回答"这个人的真名是什么"** —— `realName` 和 `deptName` 都是 null。
> 要部门名请拿 `deptId` 去问第一批的 `base-dept-get`。

## 体积怎么切

| 入口 | 一次拿到多少 | 上限 |
| --- | --- | --- |
| `searchUsers({keyword})` | 关键字命中的前 N 条 + `total` | 默认 20 / **硬上限 50** |
| `searchUsers({deptId})` | 该部门的前 N 条 + `total` | 同上 |

**没有 `listAll()`**。要"看规模"看 `total`：实测全公司 4225 人、
`nickname=张` 436 人、`deptId=101` 21 人。

## 缓存：**不缓存**

人员候选**逐次带参数**（关键字 / 部门 / 分页），缓存命中率极低，
而且它本质上"问一次就要最新的"。硬缓存只会制造"我明明改了名字却搜不到"这类幽灵。
与本批的菜单 / 工作台（有缓存）形成对照——判据是"这份数据的参数维度多不多、变不变"。

没挂会话时也不走实例缓存；能力实例本身仍然是"一个用户的一个租户"作用域
（conventions 第 5 条），所以不存在跨用户串味的可能。

## module-type：**不发这个头**

- **合成路径**：`/base-data/user-search` → `resolveModuleType()` 返回 `null` → 不发。
- **实测**：带 `module-type: 11` 与不带，`data` **逐字节相同**（784 B / 784 B，基线稳定）。
- **依据强度**：本账号实测不敏感，**没有核对后端实现**。

## 没做 / 不确定

- **没有做"按岗位 `postName` 精确筛"的入口**：`meeting-application.ts:300` 会发这个参数，
  但它的取值集合没有查证，本能力**没有把它暴露成参数**（`BaseShellOptions.request` 那条路
  仍然可以用它，只是能力契约里不承诺）。
- **没有核对后端 `simple-page` 是否有 `@DataPermission`**（会不会按 `module-type` 收窄范围）。
  实测本账号两次对照结果相同，但那是"本账号"。
- **`deptName` / `realName` / `staffDuties` / `staffCode` 为什么恒为 null 没有查**：
  可能是这个 DTO 分支没填充，也可能是本账号的数据特性。**只记录现象，不解释原因**。
- **没有把 `meeting-user-search` 收敛到本能力**：那要动 `meeting-application.ts`，
  在本单的可写文件集之外。收敛方向已写在本文件，交给它的 owner。
