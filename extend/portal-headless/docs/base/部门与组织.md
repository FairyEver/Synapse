# 部门与组织（基础数据能力 `base-dept-*`）

**这不是一个页面**。它是应用外壳级的基础数据：Portal 的路由守卫
（`app/portal/utils/router/session.js:35-59` 的 `runLegacyFullInitTasks`）在**任何 dashboard 页面刷新**时
都会打一串基础数据接口，部门列表就是其中一条。用户的原话是「它在 Portal 中是一个组件，
那么它在这个 SDK 中就应该是一个基础能力」。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/base-dept-dict-permission.ts`；
回归测试 → `test/base-dept-dict-permission.test.ts`；真实环境只读冒烟 → `smoke/read-base-data.mjs`。
（基础能力没有"页面基准"，逐字段基准这一件由**只读冒烟的实测输出**替代，见下面「实测记录」。）

它要回答的问题：

> 一个**没有页面**的接口，怎么在"能力必须绑一个页面上下文"（设计 H2 / F3b）的框架里落位？
> 以及：同一个"组织"概念下有三个接口，为什么这个能力只用了其中最不起眼的那个？

## 接口

| 项 | 值 |
| --- | --- |
| 路径 | `GET /admin-api/system/dept/list-all-simple` |
| 参数 | **无**（下面「浏览器发的那三个参数」一节说明为什么不发） |
| 返回 | `[{ id, name, parentId }]`，**扁平**，无分页 |
| 权限注解 | 无（后端只有 `@DataPermission`，那是数据范围不是鉴权） |
| Portal 调用点 | `app/portal/components/portal/material/select/corporation/index.vue:34`（`useAsyncState`，setup 顶层即发） |
| http 实例 | `platform`（`app/portal/utils/http/platform.js` 的 `http`；URL 已带 `/admin-api`，补前缀的拦截器不介入） |

## 为什么用这个接口，而不是另外两个组织接口

同一件事 Portal 里有**三个**接口，体量与形状差得很远：

| 接口 | 体量 | 参数 | 形状 | SDK |
| --- | --- | --- | --- | --- |
| `GET /admin-api/system/dept/list-all-simple` | **73,754 B / 1551 节点 / 347–475 ms**（本单实测） | 无 | **扁平** `{id,name,parentId}` | **本能力** |
| `GET /admin-api/org/organization/getRoleOrganizationTree` | 501 KB（引用 `docs/base-capabilities.md` 的调查值，**本单未重测**） | 无 | 树，节点约 60 字段 | 无 |
| `GET /admin-api/org/organization/getAllOrganizationByType?type=N` | type=1 → 17 节点（同上，引用） | `type` | 树，字段精简 | `attendance-org-search`（页面级） |

选它的三条理由：

1. **体量小一个数量级**，而"部门名 → id"这个最常见的用途它完全够用；
2. **扁平结构最好缓存、最好拼树**——树可以在 SDK 侧现拼（`getDepartment` 的 `path` 就是现拼的），
   反过来把树拍平则要看它每个节点里那 60 个字段；
3. 另外两个是**页面级**的：`getRoleOrganizationTree` 会被 `module-type` 影响（实测首屏一次发了 9 个变体），
   而本单实测 `dept/list-all-simple` **不受影响**（见下面 module-type 一节）。

⚠️ **不要把这个结论套到另外两个上**：它们各自有自己的形状、体量与数据范围规则，
本能力一个都没有覆盖。

## 能力定义与参数契约

三个入口都是**只读**（`write: false`），页面路径是合成的 `/base-data/dept-list`（见 module-type 一节）。

| 能力 id | 入口方法 | 参数 | 说明 |
| --- | --- | --- | --- |
| `base-dept-search` | `searchDepartments({ keyword, limit })` | `keyword`（必填）、`limit`（默认 20，上限 50） | 按名称**包含**匹配。候选 1551 个 = 长选项参数，**无关键字直接拒绝且不发请求**（设计 D6 / H35） |
| `base-dept-get` | `getDepartment(id)` | `id`（必填，`lookup` → `base-dept-search`） | 返回 `{ id, name, parentId, path, pathNames }`，`path` 是**从根到它**的链路 |
| `base-dept-children` | `listDepartments({ parentId, limit })` | `parentId`（必填，`lookup` → `base-dept-search`）、`limit`（默认 50，上限 200） | 直接下级。**传 `0` 取根** |

**没有 `listAll()`**：1551 个节点一次性给出去会冲掉调用方上下文，这是 conventions 第 11 条
在"整张表"上的同一性问题。`searchDepartments` 的 `limit` 是**硬上限**（超出被夹到 50），不是提示。

`getDepartment` / `listDepartments` 的 `lookup` 都指向 `base-dept-search`——
这样 AI 拿到的引导是"先按名字查候选"，而不是"猜一个 id"。

## 逐字段基准（实测）

冒烟：`smoke/with-portal-token.sh node smoke/read-base-data.mjs`
（2026-09-20，`biz-api-test.wodecorp.cn`，租户 1，会话 token；**全程只读 GET**）

```
字节 73754 / 条数 1551 / 耗时 347 ms（三轮：475 / 347 / 382）
首条字段：["id","name","parentId"]
抽样：[{"id":34,"name":"沃德辰龙","parentId":0},{"id":35,"name":"华都峪口","parentId":34},{"id":36,"name":"北京思玛特","parentId":34}]
父指针约定：parentId 为 null/undefined 的 0 个；根节点（parentId=0）1 个；按 parentId 计数最多的 3 个 → [["1122",18],["1525",18],["471",16]]
悬挂节点（parentId 指向不存在的 id，且不是 0）0 个
名称含「财务」的：18 条；名称含「生产」的：26 条
isCorporation=1 → 35 条（与全量差集 1516 条）
pageNo=-1&pageSize=-1&isCorporation=1（浏览器原样） → 35 条
```

**四条要记住的事实**：

1. **每条正好三个字段** `id` / `name` / `parentId`（`id` 与 `parentId` 是数字）。
2. **根节点的 `parentId` 是 `0`，不是 `null`**——`parentId === null` 的节点 **0 个**，
   而 `parentId === 0` 的恰好 **1 个**（id 34「沃德辰龙」）。所以 `listDepartments(0)` 才是"取根"。
3. **没有悬挂节点**（每条 `parentId` 要么指向存在的 id、要么是 0）。
   代码里向上取路径仍然带环检测与"父不存在就停"，那是**防御**（组织表全租户共用，别的租户未必干净），
   不是实测需要——测试里那条脏数据是**造**的，别读成现状。
4. 单个父节点最多 **18** 个直接下级（parentId=1122 与 1525）。

## 浏览器发的那三个参数，本能力**一个都不发**

Portal 唯一调用点（`corporation/index.vue:34`）发的是：

```
GET /admin-api/system/dept/list-all-simple?pageNo=-1&pageSize=-1&isCorporation=1&_t=…
```

`pageNo=-1&pageSize=-1` 是 renren 的"不要分页"标记；`isCorporation=1` 是那个组件要的
**"公司"下拉框**。实测这个参数把结果从 **1551 条收窄到 35 条**（差 1516 条）。

本能力**刻意不复刻这三个参数**：

- 它的定位是"部门名 → id"的**通用查表**，不是某一个下拉框的候选源；
  只给 35 条的话，`财务中心`（实测 18 条含"财务"）这类真正的部门大部分会查不到;
- 那三个参数里唯一有语义的是 `isCorporation`，而它是**那个组件的业务判断**，不是基础数据的属性。
  要按这个口径筛，应该由调用方拿到全量后自己筛，或另建一个能力。

这条差异**写进了回归测试**（断言请求的 `params` 是 `undefined`），不是靠注释维持。

## 体积怎么切

| 入口 | 一次拿到多少 | 上限 |
| --- | --- | --- |
| `searchDepartments` | 名称命中里前 N 个 | 默认 20 / 硬上限 50 |
| `getDepartment` | **1 个**节点 + 它的祖先链 | 链长 = 层数，天然很小 |
| `listDepartments` | 某个父节点的直接下级 | 默认 50 / 硬上限 200（实测最大 18） |

切法就是"**一次调用回答一个问题**"：查名字、看一个节点的完整路径、看一层下级。
三者都不需要把 1551 条端出来。

## 缓存

| 场景 | 行为 |
| --- | --- |
| 挂了会话（`createPortalServer` 这条路） | 读会话基础数据键 **`dept-list`**（由 `baseDeptPermissionBaseData` 定义，接线方注册）。命中则**一次请求都不发** |
| 没挂会话（`createPortalHeadless` 这条路） | 能力实例内缓存索引，TTL **`BASE_DATA_CACHE_TTL_MS` = 30 分钟**，与 `src/session/store.ts` 的 `DEFAULT_ABSOLUTE_TTL_MS` **同值**（测试里有一条断言钉着这个相等，漂开就红） |
| 并发 | `src/session/single-flight.ts` 合并，同一片数据只发一次真实请求 |
| 手动失效 | `invalidate('dept')` / `invalidate()` |

**为什么可以不拼缓存键**：一个能力实例 = 一份请求函数 = **一个用户的一个租户**
（conventions 第 5 条），作用域天然正确。

**为什么部门可以按租户缓存、而组织树不行**：`docs/base-capabilities.md` §4.5 记的
"组织树缓存键必须并进 module-type"针对的是 `getRoleOrganizationTree`。本接口实测**不吃**
module-type（见下一节），所以缓存键里不需要它。

## module-type：**不发这个头**

依据分三层，每层都有出处：

1. **浏览器侧**：这三个请求都走 `platform.js`，`module-type` 由
   `generateHttpHeaders()`（`app/portal/utils/system.js:825-833`）的兜底分支决定，
   取值来自 `getCurrentModuleType()`——读的是 **cookie `menuPath`（即将进入的页面）**。
   **不是无条件加、也不是这三条链路自己传。**
2. **无头侧**：这三个能力**没有落地页**，`pagePath` 是合成的 `/base-data/dept-list`；
   规则表（27 条）的 prefix 全部以 `/dashboard/` 开头，匹配不到 → `resolveModuleType()` 返回 `null`
   → 不发这个头。这与 conventions 第 2 条（算不出就不发）一致。
   回归测试断言了三个合成路径都解析为 `null`，并断言落到的 http 实例是 `platform`。
3. **后果**：这条接口**确实**会被 module-type 影响——后端 `DeptController#getSimpleDeptList`
   上有 `@DataPermission`，规则链（`OrganizationDataPermissionRule:108` →
   `HrPermissionServiceImpl.getOrganizationDataPermission`）会读 `LoginUser.getModuleType()`
   （由 `TokenAuthenticationFilter:276-280` 从请求头写入）。
   **不带头 = 不按模块过滤 = 该用户全部模块数据权限的并集**，正是 conventions 第 1 条说的"放大"。
   实测：本账号带 `module-type: 11` 与不带，都是 **1551 条、id 集合完全一致**。
   → **实测结论，不是保证**；需要收窄时由接线方在建能力时显式给 `moduleType`，SDK 不猜。

### 一条查到但没用上的事实

`HrOrganizationReqVo` 里有个 `moduleType` 字段，但它作为 **query 参数是无效的**——
`HrOrganizationMapper.selectList` 完全不引用它（后端源码直读）。
**只有请求头算数。** 所以这个能力没有"传个参数收窄范围"的假动作。

```bash
./smoke/with-portal-token.sh node smoke/read-base-data.mjs
```

## 没做 / 不确定

- **`getRoleOrganizationTree`（501 KB 那个）本单没有重测**，§「为什么用这个接口」表里它的数字是
  引用 `docs/base-capabilities.md` 的调查值，标着"引用"。
- **本租户的"干净"只是本租户的**：悬挂节点 0 个是实测，别的租户没测。
- **`module-type` 只对照了 11 这一个值**（该账号命中率最高的模块之一）。"带别的值也一样"是推断，
  没有逐个模块试。
- **`isCorporation` 的语义没有深挖**：只实测了它把 1551 收窄到 35，
  没有去后端确认"公司"的判据字段是什么。
- **写操作一个都没有**：这个接口只有 GET；部门的增删改在别的页面上（组织结构那一页），
  见 `docs/pages/组织结构.md`。
