# 可见菜单（基础能力 `base-menu-nav` / `base-menu-paths`）

**这不是一个页面**。它是「这个用户看得到哪些菜单」的**唯一后端来源**。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/base-shell.ts`；
回归测试 → `test/base-shell.test.ts`；真实环境只读冒烟 → `smoke/read-base-shell.mjs`。

## 它为什么入选：**它解锁了一个已经写好、但一直是死的模块**

这是本批"被依赖"证据最强的一个，而且是**可核实的**：

```
$ grep -rn "visibility" src/catalog/index.ts      → 不导出
$ grep -rn "visibility" src/index.ts src/server.ts → 一处都不引用
$ grep -n "visibility" src/catalog/visibility.ts   → 实现完整（433 行），只有 test/ 在用
```

`src/catalog/visibility.ts` 实现了「能力目录按用户可见性过滤」（设计 D8 / F18 / H36），
它的类型注释把输入来源写死成：

```
/** `GET /admin-api/sys/menu/nav?project=` 的 `data`，或同族接口的 `data` */
menuTree?: MenuNode[] | null
```

**但是没有任何能力能提供那棵菜单树** —— 所以那个模块只有 `test/visibility.test.ts`
拿夹具（`baseline/menu-nav.sample.json`）在喂它，门面上一次都没接上过。
本能力补的就是这个输入。

`test/base-shell.test.ts` 里有一条断言直接把 `getMenuNav()` 的返回值喂进
`createUserVisibility()` 并核对路径集合 —— **不验一遍等于没接上**。

## ⚠️ 一条必须如实说的事：`sys/menu/nav` **不是**观测到的首屏请求

调查 §2 的「首屏 21 个后端接口」清单里**没有它**。复核时全仓搜过：

```
$ grep -rn "sys/menu/nav" --exclude-dir=node_modules --exclude-dir=dist /path/to/Projects_Js
（零命中）
```

它是 F18 记下的接口，后来由 bsk **在页面内手工 fetch** 抓到的 ——
夹具 `baseline/menu-nav.sample.json` 自己写着抓法是「bsk evaluate 在页面内 fetch」。

所以：**它的入选依据是"被依赖"，不是"每次刷新都打"。**
别把它当成首屏请求来引用，也别拿它去支持"外壳 21 个接口"那个数字。

## 与此相关的另外两个接口（**都没有做**，这是刻意的）

| 接口 | 实测体量 | 为什么不做 |
| --- | --- | --- |
| `sys/menu/menuListNotBySystem` | **756,319 B / 59 个根 / 2809 个节点** | 是 `nav?project=2`（14,851 B）的 **50.9 倍**；它是**后台菜单维护页**（`views/dashboard/hr/setting/menu/list.vue`）的数据源，不是外壳。要建也得先有切片入口 |
| `sys/menu/selectRoleMenuListNotBySystem` | 夹具记载跨系统、跨项目 **1119 条路径** | 是"按角色收窄"的版本。本单**没有实测过它**，所以不做——宁可少做一条，不写没量过的东西 |

用户口语里的「**菜单的维护**」指的如果是对上面第一条做增删改，
那在无头下的正确形态**不是**把这个树端出来，而是
「静态目录（`generated/page-catalog.json`）× 可见菜单求交」——
这正是 `visibility.ts` 干的事（调查 §4.2 的结论，复核后同意）。
**写的那一半（`POST/DELETE /sys/menu`）本单一条都没碰。**

## 接口

| 项 | 值 |
| --- | --- |
| 路径 | `GET /admin-api/sys/menu/nav?project=` |
| 参数 | `project`（**必填**） |
| 分页 | **没有** |
| 返回 | 节点数组（树），节点 13 个字段 |
| http 实例 | `platform` |

### ⭐ `project` 必填，且「不传」不等于「全部」

**实测**：

| `project` | 字节 | 根节点 | 总节点 | 深度 |
| --- | --- | --- | --- | --- |
| `1` | 303 B | 1 | 1 | 1 |
| `2` | 14,851 B | 7 | **57** | 4 |
| `3` | 52 B | 0 | 0 | 0 |
| `0` | 52 B | 0 | 0 | 0 |
| **不传** | 303 B | 1 | 1 | 1 |

**不传时后端按 `project=1` 返回**（与传 1 完全相同）。所以"不传"不等于"全部"，
而是"悄悄变成另一个项目的菜单"。因此能力的 `project` 是必填的，
而且 `null` / `undefined` / `''` **单独挡掉**——`Number(null)` 与 `Number('')` 都是 `0`
（有限值），不挡的话"没传参数"会被静默当成 `project=0`（实测返回空树），
调用方会把"我漏了参数"读成"这个人一个菜单都没有"。

### 节点形状（实测）

```
字段全集：["children","createDate","icon","id","menuType","name","parentName",
          "permissions","pid","project","sort","url","useSystem"]
```

- **`url` 恒为 `null`**：57 个节点里 **0 个**有值。页面路径在 `permissions` 里。
- **`permissions` 从不是逗号分隔**：41 个非空里**含逗号 0 个**。
- 41 个非空 `permissions` 里，**36 个是 `/` 开头的路径码**
  （`/dashboard/agreement`、`/dashboard/attendance/attendance-team`…），
  其余是权限码形态（`hr:module:approval`、`hr:module:performance`…）。

后两条与 conventions 第 16 条完全一致（那条就是从这份夹具量出来的），
这里等于**用另一个账号 / 另一次抓取又验了一遍**。

`visibility.ts` 的 `MenuNode` 声明的 9 个字段**全都在**（9/9），
所以本能力的树可以直接喂给它。

## 参数契约

| 能力 id | 入口方法 | 参数 | 必填 | 默认 / 上限 |
| --- | --- | --- | --- | --- |
| `base-menu-nav` | `getMenuNav({project, keyword, maxNodes})` | `project` | **是** | — |
| | | `keyword` | 否 | 按节点名**或** `permissions` 片段裁剪；**命中节点的祖先会被保留** |
| | | `maxNodes` | 否 | 默认 **200**，硬上限 **500** |
| `base-menu-paths` | `listMenuPaths({project, keyword, limit})` | `project` | **是** | — |
| | | `keyword` | 否 | **片段**匹配（如 `/dashboard/finance/`） |
| | | `limit` | 否 | 默认 **100**，硬上限 **300** |

> **为什么 `base-menu-paths` 不强制关键字**：它的规模**有界** ——
> 实测 `project=2` 只有 36 条路径码。这跟人员候选（4225 人）不是一回事：
> conventions 第 11 条针对的是"候选有几千个"的长选项，这里的量级小两个数量级，
> 强制关键字只会让调用方多绕一步。**`base-user-search` 强制、这个不强制，判据是实测规模。**

### 两个入口的分工

| | `getMenuNav` | `listMenuPaths` |
| --- | --- | --- |
| 返回 | **树**（节点对象） | **扁平的路径数组** |
| 页面的 `permissions` 值 | **原始值** | **原始值** |
| 用途 | 喂 `createUserVisibility({ menuTree })` | "我大概能看到哪些页面"的快速一瞥 |

⚠️ `listMenuPaths` 返回的是**原始 `permissions` 值**，
**不是** `collectVisiblePaths()` 归一化之后的键。归一化有三步
（去 query、去结尾 `/list`、`platform-v2` → `platform`）。
**要做可见性求交请用 `getMenuNav` 的树**，别拿这个列表去比 —— 比出来的差异会全是归一化差异。

## 体积怎么切

| 入口 | 一次拿到多少 | 上限 |
| --- | --- | --- |
| `getMenuNav({project})` | 该项目的整棵树 | 默认 **200 节点** / 硬上限 **500**，超了**截断** |
| `getMenuNav({project, keyword})` | 裁剪后的树（**含线索祖先**） | 同上 |
| `listMenuPaths({project})` | 前 N 条路径码 | 默认 **100** / 硬上限 **300** |

**没有 `listAll()`**。实测 `project=2` 是 57 个节点 / 14,851 B，远在上限之内；
上限是为了 756 KB 那个同族接口的数据形状留的防线。

### ⚠️ `truncated: true` 时**不要**拿它去算可见性

被截断的树 = 缺节点 = 会误判"这个页面不可见"。所以截断是**显式报告**的，不是静默的：

```ts
{ project, tree, totalNodes, returnedNodes, truncated }
```

`totalNodes` 永远是**完整树**的节点数，`returnedNodes` 是这次真的给了多少个。
两个数不相等时 `truncated` 一定是 `true`。

> 反证时发现过一个**假截断**：最初的实现把"裁剪"和"截断"合成一步走同一个节点预算，
> 于是被关键字丢掉的子树也消耗预算，一棵本来放得下的树会被误报成 `truncated`。
> 而 `truncated` 是要被调用方当成硬信号的，误报等于让那个信号失去意义。
> 现在两步分开：先 `filterTree` 再 `truncateTree`。

### 返回值是**新建的节点对象**

`getMenuNav` 每次都返回新建的节点（`{...node, children}`）。
不这么做的话，调用方拿到的是缓存里那一份，随手改一个 `node.name` 就把缓存污染了，
而**下一个调用方会拿到改过的数据** —— 那种错查起来极其费劲。
多拷 57 个对象不贵。`test/base-shell.test.ts` 里有一条断言专门锁这件事。

## 缓存：**切片键必须并进 `project`**

| 场景 | 行为 |
| --- | --- |
| 没挂会话 | 实例内缓存，切片键 = `menu-nav:<project>`，TTL = `BASE_SHELL_CACHE_TTL_MS`（30 分钟） |
| 挂了会话 | 同左（**没有**合适的会话基础数据键：键要随 `project` 变，不是每次会话都该拉） |
| 并发 | 单飞合并 |
| 手动失效 | `invalidate('menu-nav')` —— **清掉所有 project 的切片** |

**这是本批唯一的"缓存键不是只按用户"的地方。** 实测 `project=1`（1 个节点）
与 `project=2`（57 个节点）返回的树不同。若切片键不带 `project`，
第二次调用会直接命中第一次的缓存并返回**另一个项目的菜单** —— 静默且完全合法。
这与调查 §4.5 说的 `module-type` 陷阱是同一类问题：**同一用户、不同上下文 = 不同数据**。

## module-type：**不发这个头**

- **合成路径**：`/base-data/menu-nav` → `resolveModuleType()` 返回 `null` → 不发。
- **实测**：带 `module-type: 11` 与不带，`data` **逐字节相同**（14,851 B / 14,851 B，基线稳定）。
- **依据强度**：本账号实测不敏感，**没有核对后端实现**。

## 没做 / 不确定

- **`project` 的取值语义没有查全**：实测 1 = 学习型组织（1 个节点）、2 = 人力绩效（57 个）、
  3 与 0 = 空。**3 代表什么、还有没有别的合法值，没有查**。
  所以能力的参数描述里只写了实测到的那几个，没有编一张"项目号表"。
- **没有接 `selectRoleMenuListNotBySystem`**（按角色收窄的那一份）：本单没实测过它，
  不写没量过的东西。它是"普通角色账号看不到全部菜单"这个问题的潜在答案，**值得下一批做**。
- **没有把 `visibility.ts` 接进任何门面**。本能力只提供输入，接线（`filterCatalog` 用在哪、
  是否默认开启）是门面的事，而且 D8 已经定了口径。**本文件不改 `src/catalog/**`。**
- **`menuListNotBySystem` 没有建能力**（756 KB / 2809 节点），理由见上。
- **`sys/menu` 的写接口（POST / DELETE / PUT）一条都没碰**——本单不许写。

## 追加（2026-09-21）：接线已经落地，上面「没有接进任何门面」那条**已被取代**

上面那一条记的是本能力交付时的状态（本能力只提供输入）。**同一天稍后，接线做了**，
方案与取舍写在 `src/catalog/README.md`（那一节是权威，本段只记结论与它对本页的影响）：

| 项 | 结论 |
| --- | --- |
| 过滤在哪一层 | **显式入口**，不自动生效。纯的那一半是 `catalog.withVisibility(visibility)`；取菜单那一半是门面上的 `visibleCatalog({ project })`（单用户 `portal.visibleCatalog()`、多用户 `forSession(...).visibleCatalog()`） |
| 为什么不自动 | ① conventions 第 15 条：菜单树不是权限裁决，自动过滤会把"不在菜单里但其实可调"的能力藏起来；② 目录 API 现在全是同步的，自动过滤会把它整层变成 async；③ 目录在多用户门面里是**服务级共享**的静态数据，可见性是 per-(用户, 租户, 项目) 的 |
| 拿不到菜单树 | **失败关闭**（抛 `MenuVisibilityUnavailableError`）。降级成全量 = 静默放大下发面；要用未过滤的目录请显式 `portal.catalog`，或显式 `onUnavailable: 'unfiltered'` |
| 树被截断 | 同样失败关闭。本页 §「`truncated: true` 时不要拿它去算可见性」这条告诫在门面上是**硬闸**，不是文档提醒 |
| 多用户 | `visibleCatalog()` 挂在**会话**上，走这份会话的 `baseShell`（菜单 per-user）。服务级 `PortalServer.catalog` 仍是全量，不参与过滤 |
| 不接受的输入 | 门面**不接受 `keyword`**：被关键字裁过的树缺路径，拿它算可见性会把"其实可见"的判成不可见 |
| `getMenuNav` 的契约 | 一个字段都没改。`test/base-shell.test.ts` / `test/visibility.test.ts` 全部照旧 |

另外还留了一条**未接**的线（上面「没做」里已经提过）：`selectRoleMenuListNotBySystem`（跨系统口径）。
它是普通角色账号的潜在正解，但**没有实测过它的真实响应**，所以门面里没有它的 `MenuTreeSource`。
要接的话只需换一个 `MenuTreeSource`，`visibility.ts` 与目录层都不用动。
