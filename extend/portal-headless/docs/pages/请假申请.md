# 请假申请（`/simple/hr/form/005`）

流程表单这一类的**第三条线**，也是 `docs/process-forms.md` §2.2 排在第一梯队第 2 位的流程
（「人人都会用；但有年假余额/时长计算等只读联动」）。

### 2.1 复合日期控件：一个控件，两个字段

```text
「开始时间」按钮 → a-modal → a-date-picker（value-format="YYYY-MM-DD"）
                          + 「时间段」下拉（1=上午 / 2=下午，硬编码 leaveTimeTypeList）
                 → 保存 → 同时写 formState.startDate 与 formState.startType
```

`startDate` 是 `YYYY-MM-DD` **字符串**，`startType` 是数字。两个都必填。

跨字段校验在 `005/utils.js`：

```js
export function startIsAfterEnd (startDate, startType, endDate, endType) {
  const start = dayjs(startDate), end = dayjs(endDate)
  return start.isAfter(end) || (start.isSame(end) && startType === 2 && endType === 1)
}
```

白话：开始日期晚于结束日期不合法；**同一天**里「下午 → 上午」也不合法。
`actionSubmit()` 在 `formRef.validate()` 之后立刻调它，不合法就
`message.error('结束时间不能早于开始时间')` 并**直接 return，不发任何请求**。

SDK 的 `assertPeriodOrder()` 逐字复刻这条（用字符串比较而不是 dayjs —— 入参已过严格的
`YYYY-MM-DD` 正则与"真实存在"校验，这个格式下字典序就是时间序，**零新增依赖**），
并且**排在 `profile()` / `getRestDuration` 之前**：写操作会惊动真人，能红在前面就红在前面。

> 第一版把这个校验和 `reason` 的校验都留在 `buildLeavePayload()` 里，那个函数在
> `getRestDuration` **之后**才跑 —— 于是「事由为空」这种输入会先打完两个请求才红。
> 被 `本地校验失败时一个请求都不发` 那条测试抓到，改成独立的 `assertDraft()` 前置。

### 2.2 `userId` 这四个字段**不给调用方填**

页面上它们是 `userStore.state` 直接抄下来的，用户改不了：

| 载荷字段 | 来源（`/sys/user/info`） | 实测值 |
| --- | --- | --- |
| `userId` | `id`（**字符串**） | `"18243"` |
| `userName` | `realName` | `"姚淼鑫"` |
| `staffCode` | `username` | `"2021070101"` |
| `fullPath` | **`organizationName`**（不是 `organizationFullPathName`） | `"设计中心1236"` |

三个理由：

1. **忠实**：这四格在页面上是只读的，调用方本来就没有入口去改。
2. **安全**：后端 `createAttendanceUserRel` 用 `createReqVO.getUserId()` 决定
   **给谁生成请假记录**，而流程发起人取的是 `getLoginUserId()` —— **两者不是一个来源**
   （`AttendanceUserRelServiceImpl:295`）。允许随便传 `userId` 就等于把能力变成
   「以我的身份替别人请假」，页面上做不到。
3. ⚠️ **`fullPath` 那个坑**：它取的是 `organizationName`（`"设计中心1236"`），
   **不是** `organizationFullPathName`（`"沃德辰龙-沃德博创-沃德博创-系统研发-设计中心1236"`）。
   后者只用在一个地方：「查看审批流程」预览的 `creatorOrgFullPath`。
   这正是 `docs/process-forms.md` §5.3 第 2 条说的那种「载荷不是表单字段直传」的坑。

> **一处刻意的偏离**：`GET /sys/user/info` 的响应里带 `password2`（bcrypt 口令散列）
> 与 `salt`（实测）。`profile()` **只投影这四项**，绝不整份透传 —— 这是本能力唯一一处
> 刻意"不原样返回后端响应"的地方。测试里有一条专门断言 `$2a$` / `salt` / `mobile`
> 都不出现在返回值里（改坏了会红 13 条）。

## 三、真实请求序列（浏览器抓包）

基准：`baseline/leave-application.browser.json`。与本流程相关的请求是：

```text
GET  /admin-api/bpm/process-definition/get?key=qingjia&_t=<ts>
POST /admin-api/hr/attendance-user-rel/getRestDuration
     body {"startDate":"2026-09-21","startType":1,"endDate":"2026-09-21","endType":2}
GET  /admin-api/system/dept/simple-list                      ← 预览组件
GET  /admin-api/system/user/simple-page?pageNo=1..9&pageSize=500   ← 预览组件，4500 人
POST /admin-api/bpm/process-instance/preview                 ← ★ 提交载荷就是从这里拿到的
```

### ★ 提交载荷是怎么抓到的（这一次比通用审批那条线拿到了更强的证据）

**没有点「提交」**。改走**「查看审批流程」**按钮：它的 `resolvePreviewVariables`
返回的就是 `buildPreviewPayload()` = `{ ...buildSubmitPayload(), creatorOrgFullPath }`，
而 `buildSubmitPayload()` 正是 `create` 的载荷。于是那一条
`POST /bpm/process-instance/preview` 的 `variables` 就是提交载荷的**真实产物**：

```jsonc
{"userId":"18243","userName":"姚淼鑫","staffCode":"2021070101","fullPath":"设计中心1236",
 "type":3,"startDate":"2026-09-21","startType":1,"endDate":"2026-09-21","endType":2,
 "reason":"…","attachments":[],"restDay":1,"creatorOrgFullPath":"沃德辰龙-…-设计中心1236"}
```

三个容易看漏、也正是本流程最容易"顺手改错"的点：

1. **`userId` 是字符串** `"18243"`（`/sys/user/info` 的 `id` 就是字符串，页面原样发）。
2. **`fullPath` 是 `organizationName`**，不是全路径（见 §2.2）。
3. **`restDay` 在最后**（`{ ...formState.value, restDay }` 那个展开），
   而 `creatorOrgFullPath` 是预览独有的、**不在提交载荷里**。

`create` 的 body = 上面那 12 个键 **再加一个 `startUserSelectAssignees`**（页面
`actionSubmit` 的最后一步 `{ ...submitData, startUserSelectAssignees }`）。

### 两条顺带记下来的现场

- **预览组件无关键字拉了 4500 人**：`simple-page?pageNo=1..9&pageSize=500`（该账号全量 4225）。
  它这么做是为了解析 BPMN 里 `candidateStrategy=30`（指定用户）那几个节点会落到谁头上。
  这正是设计 D6 / H35 说的长选项拉取。⚠️ **本 SDK 一个人员搜索参数都没有**
  （请假的表单上没有人员控件），所以也不存在照抄它的机会 —— 测试里有一条钉住这件事。
- **请求头里没有 `module-type`**（抓包实测），与 SDK 一致。

## 四、`restDay`：写链路里的"读 → 写"依赖

`buildSubmitPayload()` 是 `{ ...formState, restDay: actualLeaveDuration }`。
`restDay` **不是用户填的**，它来自 `POST /hr/attendance-user-rel/getRestDuration`，
而那个请求由页面的 watch 在「四个日期字段都齐了」时触发。

⇒ **`prepare()` 与 `submit()` 都会先打一次 `getRestDuration`**，把它的返回值当 `restDay` 发出去。
调用方不用（也不能）自己给这个数。

**为什么必须现算而不是让调用方传**：`restDay` 进的是**流程变量**，直接决定 BPMN 走哪条分支
（见 §五）。让调用方传一个数等于允许伪造流程走向；让调用方自己调 `duration()` 再回填，
等于把"别传错"这件事外包出去。两种都不如现算。

⚠️ 页面上的 `leaveDuration`（本地算的，`utils.js` 的 `calculateDays`）与
`actualLeaveDuration`（接口给的）**不是一回事**：本地那个**不扣法定节假日**，
接口那个扣（后端 `calculateLeaveDays` 跳过 `sys_holiday` 里 `is_holiday = 1` 的日子）。
但 **`restDay` 用的是接口那个** —— `buildSubmitPayload()` 里写的是
`actualLeaveDuration.value`，不是 `getActualLeaveDuration()`。

实测：2026-09-21 上午 → 2026-09-25 下午，本地算 **5**、接口给 **4**（9/25 是中秋节）。
`calculateLeaveDays()` 在能力里导出了，但**只用于对照/展示，不进载荷**。

## 五、审批人：**不用人工选**，而且调用方**选不了**

`prepare()` 打的 `POST /hr/attendance-user-rel/getRequiredStartUserSelectTasks`
实测返回 **`data: []`**（空数组）—— 与通用审批那条线**正好相反**。

原因在 BPMN 里：`qingjia` 的 4 个 `userTask` 的 `flowable:candidateStrategy` 全是
**`30` = `USER`（指定用户）**（`BpmTaskCandidateStrategyEnum`），审批人是**写死的用户 id**：

```text
开始 → 排他网关 ─┬─(creatorOrgFullPath 含「博创」)→ 请假审批(用户 15012 乔娜) ─┬─(restDay >= 3)→ 领导审核(用户 15170 刘爱巧) ─┐
                 │                                                            └─(restDay <  3)───────────────────────────┴→ HR(用户 17063 王威) → 结束
                 └─(不含「博创」)→ 直属上级(用户 15012 乔娜) → 结束
```

网关条件（BPMN 原文）与实测出的 id → 人对应用：

| 分支 | 条件 |
| --- | --- |
| 请假审批 / 直属上级 | `${creatorOrgFullPath.contains('博创')}` |
| 走不走领导审核 | `${restDay >= 3 }` |

```text
15012 = 乔娜（设计中心副总监）   15170 = 刘爱巧   17063 = 王威
```

（id → 人是用 `GET /system/user/simple-list` 全量 4225 人反查出来的，只读。）

`creatorOrgFullPath` 由**后端**从发起人的部门派生
（`AttendanceUserRelProcessInstanceVariableBuilder`），**不是请求体里的字段** ——
所以这个分支调用方改不了，SDK 也不假装能改。

⇒ 因为返回空数组，`startUserSelectAssignees` 恒为 `{}`。但**接口还是要打**：
`prepare()` 存在的意义就是"让后端告诉我们这次要不要人工选人"，换个流程或流程改版
答案就可能不是空的。`submit()` 里也照打（页面 `actionSubmit` 就是这么写的），
`assertAssigneesForTasks()` 才有节点可预检。

### ⚠️ 一条与通用审批**不同**的实测结论：不存在"选自己"的坑

通用审批那条线踩过一个坑：审批人由发起人选，选了自己就会触发后端
「流程发起人与审批人相同，自动审核通过」，流程当场走完、`cancel` 撤不掉。

**请假这里踩不到**：审批人是 BPMN 写死的，调用方**没有选择的入口**。
只有当**登录的那个人本身**是 15012 / 15170 / 17063 之一时，那一个节点才会自动通过。
所以冒烟脚本的守卫换了形态：不是"别选自己"，而是
**"别用这几个 id 的账号跑"** —— 提交之前直接拒绝（见 §七）。

## 六、操作步骤

```ts
// 0) 我是谁（载荷里那四项的唯一来源；只读）
const who = await sdk.leaveApplication.profile()
// → { id: '18243', userName: '姚淼鑫', staffCode: '2021070101', fullPath: '设计中心1236' }

// 1) 请假类型候选（只读；字典可运维改，以它为准，别信写死那张表）
const types = await sdk.leaveApplication.types()   // → [{ label: '事假', value: 3 }, …]

// 2) 两个只读联动
const restDay = await sdk.leaveApplication.duration({
  startDate: '2026-11-30', startType: 1, endDate: '2026-11-30', endType: 2,
})                                                 // → 1（天数，扣法定节假日）
const yearRest = await sdk.leaveApplication.yearRest()  // → { rest: 5, unRest: 0 }

// 3) 附件（可选；type ∈ {3,4,7,8,9} 时必填）
const uploaded = await sdk.baseUpload.upload({
  content: pdf, folder: 'HR/approval', fileName: 'x.pdf',
})
const attachments = [{ url: uploaded.url, name: 'x.pdf' }]

// 4) prepare（只读）：算出这次要人工指定哪些审批人节点
const draft = {
  type: 3,
  reason: 'SDK-TEST-…',            // ⚠️ 本表单**没有标题字段**，事由是唯一能看出是测试数据的地方
  startDate: '2026-11-30', startType: 1,
  endDate: '2026-11-30', endType: 2,
  attachments,
}
const { tasks, restDay: computed } = await sdk.leaveApplication.prepare(draft)
// → tasks = []（本流程没有自选节点）；restDay 现算

// 5) submit（写操作，会给真人推待办）。startUserSelectAssignees 必须是 {}，但**要显式传**
const businessKey = await sdk.leaveApplication.submit(draft, {})

// 6) 查（两条独立路径）
await sdk.leaveApplication.detail(businessKey)                    // 业务单据
const instance = await sdk.leaveApplication.findInstanceByBusinessKey(businessKey)

// 7) 撤销（写操作）
await sdk.leaveApplication.cancel({ processInstanceId: instance.id, reason: '不申请了' })
```

两条最容易踩的：

- **`cancel` 要的是流程实例 id**，而 `GET /hr/attendance-user-rel/get` 的响应里
  **没有 `processInstanceId`**（`AttendanceUserRelDO` 有，service 没往 VO 上 set）。
  唯一通路是「我的流程」按 `businessKey` 找 —— `findInstanceByBusinessKey()`。
  **这不是绕路**：页面上点「取消流程」用的 `record.id` 正是 my-page 那一行的 `id`。
- **只按 `businessKey` 认单子会认错**：`businessKey` 是各业务表自己的主键
  （后端 `setBusinessKey(String.valueOf(resultId))`），「请假 51」与「通用审批 51」是同一个
  字符串。所以还要看 `processDefinitionKey`。
  ⚠️ **不能用 `processType` 区分**（通用审批是 2、请假是 1，看着能分）：在请求里加一个
  页面从不发的过滤参数会白白偏离 D20。

### 三个实测出来的响应怪癖（都不是 SDK 漏读）

| 接口 | 怪癖 |
| --- | --- |
| `GET /hr/attendance-user-rel/get` | **`id` 恒为 `null`** —— `getAttendanceUserRel()` 从头到尾没 `setId(...)`。单据 id 是 `submit` 的返回值，别指望从详情读回来 |
| 同上 | **没有 `restDay`**（只进不出）。`typeName` 倒是真有值（后端现查 `absent_type` 字典）—— 与通用审批那个恒为 null 的 `statusName` 正相反 |
| `POST /hr/attendance-user-rel/create` | 返回的 `resultId` 是**多行里最后那一行的 id**（一天插两行：上午 + 下午；`resultId` 在循环里被覆盖），不是"这条请假的 id"这种东西 |

#### 第 1 轮：撞上后端那条日期冲突校验（**没有产生任何数据**）


## 九、尚未覆盖 / 不确定

**测到了的**（真实环境）

- `definition` / `profile` / `types` / `yearRest` / `duration` / `prepare` 六个只读能力：真实调用过。
- `submit` / `detail` / `myInstances` / `findInstanceByBusinessKey` / `cancel`：两轮端到端跑通，
  提交与撤销各有**三条独立证据**（其中第三条 `getWorkflowPath` 直接给出了"待办落到了谁头上"）。
- **带附件的提交是实测过的**：真传了一个 pdf 到 `HR/approval`，`detail()` 里附件的
  `url` 与 `name` 原样回来，上传对象用完删除。
- **后端那条日期冲突校验**：撞到过一次，并确认它**不产生任何数据**。

**没测到的（明确分开）**

- **「查看审批流程」预览没做**：`portal-hxr-flow-process-preview` → `/bpm/process-instance/preview`，
  只读的展示件，不影响能不能提交。它是**基准的来源**（§三），但没做成能力。
- **`getWorkflowPath`（审批链路）没做成能力**：它是只读的、价值明确（本轮就是靠它取证的），
  但不在本单范围内。冒烟脚本用 `sdk.call()` 直接打它，**没有**包装成能力。
- **`update` / `delete` 没做**：页面上根本没有编辑入口（`005/index.vue` 里连
  `isEditMode` 分支都没写），走不到的地方不实现。
- **`/hr/attendance-user-rel/page`（请假记录分页）与 `/export-excel` 没做**：
  全仓库 grep `attendance-user-rel` 只有 `form/005` 那几处调用点 —— **页面没有任何地方调它们**。
  要"查请假记录"，本能力给的是页面上真走了的那两条路（`detail` / `myInstances`）。
- **年休假（`type = 13`）的真实提交没跑**：规则实现了也测了（余额 ≤0 / 时长 > 余额都会拦），
  但**本账号的年假余额实测是 `unRest = 0`**，所以真实环境里它必然被拦、提交不出去。
  那条规则是**只读 + 本地断言**，没有真实写往返。
- **`restDay >= 3`（会多走「领导审核」节点）的真实提交没跑**：冒烟默认把它当硬拒绝，
  免得白多打扰一个人。那条分支的**判定**测了（`expectedRoute`），**真实流程走向**没测。
- **附件 50MB 上限本地拦不了**：页面 `beforeFileUpload` 拦，SDK 手上只有
  `{url, name}`、算不出字节数。如实留给后端。
- **`isZhdjApp`（智慧蛋鸡 App 内的上传分支）没做**：那是另一个宿主环境
  （`window.FlutterXxx`），无头 SDK 没有这个上下文。

## 2026-09-22 AI 说明契约同步

权威契约在 `src/catalog/contracts-workflow.ts`，经 `catalog.describe(id)` / `id-llm` 的 `ai` 实际返回；`describePage` 同步用途与功能区别。额外公开门面通过 `catalog.describeMethod(sdkPath)` 下钻，无需调用方读仓库。

| 能力 | 效果 | 最终 SDK 返回 | 完成判据 |
| --- | --- | --- | --- |
| leave-application-definition | read | 流程定义对象（已拆后端包络） | 已确认流程身份；填写流程继续准备，单纯查询定义则交付名称与配置即可。 |
| leave-application-profile | read | { id, userName, staffCode, fullPath } | 确认当前请假申请身份。 |
| leave-application-types | read | { label: string, value: number }[] | 保存选中的 value 作为 type。 |
| leave-application-year-rest | read | { rest?, unRest? } | 交付年假总额/剩余天数，或确认本次申请余额够用。 |
| leave-application-duration | read | number | 已获得当前日期时段的后端工作日天数。 |
| leave-application-prepare | prepare | { payload, tasks, restDay } | 草稿校验并得到所需自选节点后准备完成；实际发起须再提交。 |
| leave-application-submit | write | number（业务单据 ID；SDK 不返回 code/data 包络） | 回读确认业务记录及其流程后，向用户交付业务 ID 与当前审批状态；提交成功不等于审批完成。 |
| leave-application-detail | read | 业务单据对象（拆包后） | 用户查询详情时交付业务信息与可靠状态即可；需要取消则先确认对应实例仍运行。 |
| leave-application-my-instances | read | { list: 流程实例[], total: number } | 向用户展示流程名称、审批内容、状态与起止时间；有明确目标时只交付匹配实例。 |
| leave-application-cancel | write | boolean（后端成功回执；SDK 原样返回拆包后的值） | 流程实例 status=4，必要时详情也回读已取消，向用户报告撤销结果。 |

数据消费与分支：

- leave-application-definition：展示 name 与 key 核对业务；formFields 为 null 不代表免填，填写规则在 prepare/submit 的 SDK 描述中。
- leave-application-profile：只显示姓名、工号、部门；prepare 自动获取，不接受冒充申请人。
- leave-application-types：以实时字典展示选择；静态 options 仅作参考。
- leave-application-year-rest：年假 type=13 时比较申请天数 <= unRest 且 unRest>0；负数表示欠额，不截成可用天数。
- leave-application-duration：开始/结束为 YYYY-MM-DD + 1 上午/2 下午；用结果展示天数。 婚假 type=7 的 prepare 使用自然日半天算法，不能拿本通用接口结果覆盖婚假 restDay。
- leave-application-prepare：给用户核对 payload 的业务值；按 tasks[].id 建立 startUserSelectAssignees 的键，人员来自候选查询，人数、去重与顺序服从任务规则。 准备只读，不建单、不保留名额、不发送待办；任何草稿变更后应重新准备。 type=13 年假必须有足够 unRest；type=3/4/7/8/9 必须附 PDF/JPG/JPEG/PNG 证明。
- leave-application-submit：保存业务 ID、流程类型及原 requestId；回读业务字段并查询流程实例确认已创建。 取消属于用户改变决定时的可选操作，不是正常提交后的必做步骤。
- leave-application-detail：展示本次申请的业务字段与附件；原请求业务 ID 必须单独保存，详情不保证能提供流程实例 ID。 状态应区分业务单据与流程实例；需要可撤回性时查 my-instances，而不是只看详情 status。 本详情没有 restDay 与 processInstanceId；请假天数须用 duration 重算，流程实例须按提交返回 ID 查询。
- leave-application-my-instances：本接口没有自动限定 qingjia，按 processDefinitionKey 与 String(businessKey) 双重匹配；字段缺失时不可把跨业务重号当可靠确认。 页码默认 1、每页默认 20；逐页核对 total，列表局部不能用于全量汇总。
- leave-application-cancel：只取消自己发起且仍运行的流程；保留业务记录，不代表删除历史。 查实际流程 status=4 才认定撤销完成；会议预定则核对占用时间段消失。

本轮以 `test/ai-contract-workflow.test.ts` 核对真实 SDK 描述，复用既有浏览器基准，不重放真实写操作。逐项验证与缺口见 `docs/ai-contract-workflow-evidence.md`。
