「与通用审批同形」这句在**字段层面**是成立的。

### 2.1 差异一：审批人控件**位置不同**，字段相同

- **035**：表单主体里有一个行内 `a-form-item label="审批人"`，放 `common-flow-form-pc-start-user-select`。
- **045**：**没有这个行内控件**。那一块换成了只读的 `a-alert`。审批人选择**只在右下角
  「查看审批流程」那个弹窗里**（`portal-hxr-flow-process-preview` 收
  `:start-user-select-assignees="bpmStartUserSelectAssignees"`）。

⇒ **页面上用户仍然能选审批人**，只是入口在弹窗里。SDK 的 `startUserSelectAssignees` 参数
对两者是同一条契约。这条路是**页面观察 + 抓包**得到的【实测】：045 的空 assignees 预览
返回 `state: "START_USER_SELECT"`，说明这条流程确实卡在"等发起人选人"上。

### 2.2 差异二：045 **没有** `handleApprovalDependencyChange`

035 在两个输入框上挂了失焦钩子刷新审批人节点；045 没有。后果是【实测，抓包】：
**045 的 `getTemporaryRequiredStartUserSelectTasks` 只在点「提交」时发**，
035 上则由失焦也能触发。SDK 的 `prepare()` 把这一步单独摘出来，两边都一样。

### 2.3 「文档审核要求」那段**不表达为参数**（如实记为未覆盖）

`a-alert` 里写的是：A 文档（需求文档/验收标准/规则文档）**仅 1 份**、不支持文件夹；
B 文档（产品/设计/方案/说明书）**最多 10 份**、可含 Synapse 链接。

**为什么不编成一个 SDK 参数**：

- 它**不绑定任何字段**（模板里没有 `v-model`）；
- 045 的 `formRules` 里 `attachments: []` 是**空的**，页面上也没有第二个附件槽位；
- 后端没有对应的校验。

把它编成参数 = **凭空造一个后端不认的契约**。SDK 只按控件的 `:maxCount=10` 拦条数，
并在 `attachments` 参数的 description 里把那段业务约定如实转述给调用方。

## 三、逐字段基准（真实浏览器抓包）

`baseline/product-design-approval.browser.json`，2026-09-21 用 bsk 在测试环境抓的。
抓法：先 navigate 到入口（这步抓不到），装 `install-hook.js` 之后用 `location.hash`
在应用内切走再切回，让表单组件**重新挂载**。

### 3.1 字段契约的**两处独立佐证**

抓包里有两处各含一份 `buildSubmitData()` 的产物，**逐字节相同**：

```jsonc
// ① 点「提交」触发的审批人节点查询
//    POST /admin-api/hr/product-design-approval/getTemporaryRequiredStartUserSelectTasks
{"applicationItem":"SDK-TEST-baseline","applicationContent":"SDK-TEST-baseline content","attachments":[],"copyUserIds":[]}

// ② 点「查看审批流程」触发的审批链预览
//    POST /admin-api/bpm/process-instance/preview
{"processDefinitionKey":"hr_product_design_approval",
 "variables":{"applicationItem":"SDK-TEST-baseline","applicationContent":"SDK-TEST-baseline content","attachments":[],"copyUserIds":[]},
 "startUserSelectAssignees":{},"copyUserIds":[]}
```

**键顺序**：`applicationItem → applicationContent → attachments → copyUserIds`，
**没有 `id` 字段**（编辑分支在前端是注释掉的）。

这两条与 035 基准里那条 POST 的 body **逐字节相同** ——
「近乎照抄」这句是**独立抓出来的**，不是从 035 抄过来的假设。

### 3.2 请求头：**没有 `module-type`**

`getTemporaryRequiredStartUserSelectTasks` 的请求头实测只有：
`tenant-id / token / Accept-Language / Accept / Content-Type`。

`/simple/hr/form/045`、`/dashboard/flow/form/edit`、`/dashboard/flow/task/my/list`
三条路径在 `generated/module-type-rules.json` 里一条规则都匹配不到 ⇒
`resolveModuleType()` 返回 null、SDK **不发**这个头，与浏览器一致（conventions 第 2 条）。

### 3.3 ★ 长选项的现场：045 比 035 **更极端**

```text
GET /admin-api/system/user/simple-page?pageNo=1&pageSize=500
GET /admin-api/system/user/simple-page?pageNo=2&pageSize=500
… 一直翻到 pageNo=9
```

**无关键字、翻满 9 页、约 4500 人**（该账号全量 4200+）。
035 的基准里只看到 **1 页**；045 是**连翻 9 页**。

⇒ 「Portal 页面自己全量拉 4500 人」这句话（CLAUDE.md 硬约束里那句）在 045 上是
**字面成立**的。SDK 的 `searchUsers()` 强制要关键字、拒绝 `pageSize=-1`，
就是不照抄这条（设计 D6 / H35）。基准里 `抓到的每一条` 列了全部 9 页 URL，
测试逐页校验 1..9 齐全（少一页就说明「整组织拉完」这句不成立）。

**与源码不一致的一处**（如实记下）：045 的 `fetchCopyUserOptions()` 源码写的是
`GET /admin-api/system/user/simple-list`（一次全量），而真实页面上抓到的是
`simple-page` 翻 9 页。**两者都是「无关键字的大批量拉取」**，结论不变；
SDK 走 `simple-page` + `nickname=`（与浏览器同一个接口）。

## 四、审批人节点：**这条线与 035 差别最大的地方**

### 4.1 045 有 **2 个**自选节点，035 只有 1 个

【实测 2026-09-21，只读 `prepare`】

| # | 节点 id | 名称 | `minSelectCount` | `approvalMode` | `selectionOrderRequired` |
| --- | --- | --- | --- | --- | --- |
| 1 | `Activity_1qdzbtn` | 业务人员审批 | 1 | `SEQUENTIAL`（依次审批） | **true** |
| 2 | `Activity_1bkivtw` | 博创内部审批 | 1 | `OR_SIGN`（或签） | false |

⇒ **两个节点都必须给非空 assignees**，后端对**每个** `START_USER_SELECT` 节点都校
（`BpmProcessInstanceServiceImpl.validateStartUserSelectAssignees`）。
只填一个 ⇒ `create` 报 `PROCESS_INSTANCE_START_USER_SELECT_ASSIGNEES_NOT_CONFIG`。

⚠️ **照抄 035 的「只有一个节点」会直接错。** 这也是 `docs/process-forms.md` 那句
「可以复用通用审批那套」**需要修正的地方**：流程（sop）能复用，**节点不能**——
BPMN 的 activity id 是每个流程定义各自画的，跨流程不可复用。
能力里**一个节点 id 都没写死**（有一条测试专门扫能力定义里不许出现任何已知节点 id）。

### 4.2 还有一个**不由发起人选**的节点

用 `preview()` 看审批链时会看到一个 `Activity_03ebjts`「AI审核」节点：
`candidateStrategy: 30`（固定指派人）、`candidateUsers: [管理员(id=1)]`。
它**不出现在 `prepare()` 的 tasks 里**（那不是发起人自选），调用方不用管它。
【实测】它是流程启动后**第一个**真正产生的任务（见 §六「实际打扰了谁」）。

### 4.3 ⚠️ 审批人**不能选发起人自己**（与 035 同一个坑）

后端有一条「流程发起人与审批人相同，自动审核通过」（`BpmTaskServiceImpl:913-916`）。
选了自己 ⇒ 流程**当场走完** ⇒ `cancel-by-start-user` 必然报「流程取消失败，流程不处于运行中」
⇒ **永久留下一条撤不掉的单据**。

测试环境里已经有一批这样的遗留单据（见 §六.4 的实测统计）。本轮的冒烟脚本把这条做成
**提交之前的硬拒绝**（不是警告），判据两条、**fail closed**：

- **守卫 A**：从「我的流程」最近一条的 `startUser.id` 推出「我是谁」。
  推不出来就**拒绝提交**（没有基准就没法证明，而选错的代价是一条撤不掉的单据）。
- **守卫 B**：`preview()` 拿到的审批链里，发起人不能出现在任何 `USER_TASK` 节点的
  `candidateUsers` 里。注意只判 `USER_TASK`——开始/结束事件上出现谁都不算。

**守卫实测有效**：`PORTAL_SMOKE_APPROVER_KEYWORD=姚淼鑫`（= 本人）跑了一次，
脚本在**发出 `create` 之前**报错退出，没有产生任何单据（见 §六.3）。

## 五、操作步骤

### 5.1 只读（默认，一个字节都不写）

```bash
smoke/with-portal-token.sh node smoke/product-design-approval.mjs
```

跑四段：流程定义 / 按关键字搜人（含一次无关键字被拒的反证）/ `prepare` 拿节点 /
`preview` 拿审批链。

### 5.2 完整链路（会真的提交，**但要给关键字**）

```bash
PORTAL_SMOKE_APPROVER_KEYWORD=<审批人姓名关键字> \
  smoke/with-portal-token.sh node smoke/product-design-approval.mjs --submit
```

`prepare` → 两道守卫 → `submit` → 按 id 查详情 → 在「我的流程」里找到它 →
`cancel` → 撤销后再查一次。

### 5.3 带附件的完整链路（**两套凭据，嵌两层**）

```bash
PORTAL_SMOKE_APPROVER_KEYWORD=<关键字> \
  smoke/with-oss-credentials.sh smoke/with-portal-token.sh \
  node smoke/product-design-approval.mjs --submit --attachment
```

Portal 的会话 token 与 OSS 的 AK/SK 在两条不同的路上（一个从浏览器 cookie 取、
一个从构建期 env 读），**没法一次取全**，所以是嵌套的。

附件模式会：真传一个 CSV 到 `HR/approval` → 当附件提交 → 回读 url/name 逐字段比对 →
撤销 → **签名 DELETE 删掉对象** → **匿名 GET 复核**（删完打不开才算删掉）。
清理在 `finally` 里，**不留孤儿对象**。

### 5.4 直接用 SDK

```ts
// 1. 先查人（候选几千个，必须给关键字）
const users = await sdk.productDesignApproval.searchUsers({ keyword: '顾' })

// 2. 问这次要人工指定哪些节点
const { tasks } = await sdk.productDesignApproval.prepare(draft)

// 3.（可选）提交前看一眼审批链
await sdk.productDesignApproval.preview(draft, { [tasks[0].id]: [users.list[0].id] })

// 4. 提交 —— ⚠️ 两个节点都要给，且**审批人不能是发起人本人**
const businessKey = await sdk.productDesignApproval.submit(draft, {
  [tasks[0].id]: [users.list[0].id],
  [tasks[1].id]: [users.list[0].id],
})

// 5. 撤销（cancel 要的是**流程实例 id**，给 businessKey 也行，SDK 会去换）
await sdk.productDesignApproval.cancel({ businessKey, reason: '不办了' })
```

> ⚠️ `sdk.productDesignApproval` 这一处要等**组装点接线**才有。
> 本轮的改动范围不含 `src/index.ts` / `src/server.ts`，接线由派单方统一做。

### 6.5 ⚠️ 实际打扰了谁（如实列出，含一个**反直觉**的实测）

本轮提交了 **2 次**，每次起了 **1 条流程实例**、产生了 **1 个待办**。

| --- | --- | --- | --- | --- | --- |
| bk=91 的实例 | **1** | AI审核 | **管理员（id=1）** | **1478 ms** | 用户主动取消流程 |
| bk=92 的实例 | **1** | AI审核 | **管理员（id=1）** | **1370 ms** | 用户主动取消流程 |

## 八、尚未覆盖 / 不确定

### 8.1 确实没做的

- **附件上传本身不在这里**：本能力收 `[{url, name}]`，url 要用 `base-upload-file`
  （目录 `HR/approval`）先传。这条链本轮**端到端验证过**（§6.4）。
- **「文档审核要求」那段业务约定没有表达**（A 文档 1 份 / B 文档最多 10 份 /
  可含 Synapse 链接）。理由见 §2.3：它不绑定字段、后端不校验，编成参数就是造契约。
- **「重新发起」（reapply）没做**：`isReapply` 分支会从原流程实例抄抄送人再提交，
  是一条另起的写链路，需要单独验证。
- **`PUT …/update` 与 `DELETE …/delete/{id}` 没做**：045 的 `handleSubmit` 里
  编辑分支**前端已经注释掉了**（`apiSubmit` 写死成 `/create`），页面上走不到这两个入口。
  要造一条「已驳回」的单据得先让真人去驳回 —— 本轮做不到，所以这两条既没实现也没法验。

### 8.2 不确定的（**不要读成"已验证"**）

- **测试覆盖的盲区有 3 处**，逐条列在 §7.1 末尾（`ATTACHMENT_MAX_SIZE_MB` 与两个翻页
  默认值）。其中 `ATTACHMENT_MAX_SIZE_MB` 是**真盲区**：它的值改了测试不会红，
  因为这个限制 SDK **物理上校验不了**（见 8.2 末尾那条）。另外两个是行为等价的调参旋钮。

- **`preview` 的响应只摸到一条流程的形状**。`nodes[].*` 那几个字段（`nodeId` /
  `candidateStrategy` / `state` 等）是从**两次真实调用**里读出来的，不是全量穷举。
  `ProcessInstancePreview` 类型里只声明了实测见过的字段，其余 `[key: string]: unknown` 透传。
  另外**§6.3 那次守卫自证里，守卫 B 并没有被真正触发** ——
  真正拦下"选自己"的是守卫 A。守卫 B 的判据（`USER_TASK` 节点的 `candidateUsers`）
  在真实响应上**看得到结构、但没被走到拒绝那一支**，这一点如实记下。
- **`statusName` 恒为 `null`**：`045` 的响应 VO 声明了这个字段但没填（与 035 同一个情况）。
  单测里有断言锁这个事实。
- **50MB 单件上限 SDK 校验不了**：`buildSubmitData` 只保留 `url` 与 `name`，
  拿不到字节数。这条如实留给后端。
- **`getRequiredStartUserSelectTasks`（不带 Temporary）那个变体没试**：
  后端两个都写了，前端用的是 `getTemporary…`。SDK 跟前端走，
  有一条测试专门断言 URL 里**不能**出现 `/getRequiredStartUserSelectTasks`。
- **移动端表单没抓基准**：`page/mobile/edit/index.vue` 的控件与 PC 端一一对应
  （申请事项 / 申请内容 / 抄送人 / 附件），字段名相同，没有额外字段（源码直读，**未抓包**）。

权威契约在 `src/catalog/contracts-workflow.ts`，经 `catalog.describe(id)` / `id-llm` 的 `ai` 实际返回；`describePage` 同步用途与功能区别。额外公开门面通过 `catalog.describeMethod(sdkPath)` 下钻，无需调用方读仓库。

| 能力 | 效果 | 最终 SDK 返回 | 完成判据 |
| --- | --- | --- | --- |
| product-design-approval-definition | read | 流程定义对象（已拆后端包络） | 已确认流程身份；填写流程继续准备，单纯查询定义则交付名称与配置即可。 |

| product-design-approval-preview | read | { nodes, processDefinitionId?, processDefinitionKey?, processDefinitionName?, state?, copyUsers? } | 用户已知道当前变量下的审批路径；继续提交前仍需完整 prepare。 |

| product-design-approval-my-instances | read | { list: 流程实例[], total: number } | 向用户展示流程名称、审批内容、状态与起止时间；有明确目标时只交付匹配实例。 |
| product-design-approval-cancel | write | boolean（后端成功回执；SDK 原样返回拆包后的值） | 流程实例 status=4，必要时详情也回读已取消，向用户报告撤销结果。 |

数据消费与分支：

- product-design-approval-definition：展示 name 与 key 核对业务；formFields 为 null 不代表免填，填写规则在 prepare/submit 的 SDK 描述中。
- product-design-approval-user-search：展示姓名与工号给用户消歧；保存选中行 id 作为 userId。 keyword 或 deptId 至少给一个；pageSize=-1 被拒绝。
- product-design-approval-prepare：给用户核对 payload 的业务值；按 tasks[].id 建立 startUserSelectAssignees 的键，人员来自候选查询，人数、去重与顺序服从任务规则。 准备只读，不建单、不保留名额、不发送待办；任何草稿变更后应重新准备。
- product-design-approval-preview：依次展示节点名称、candidateStrategyName 与 candidateUsers 姓名；节点用 nodeId 区分。 将 USER_TASK 的 candidateUsers[].id 与当前用户 ID 比较，发起人=审批人可能自动通过而无法撤销。 预览不产生任务，nodeId 不能传 task-action 的 taskId。
- product-design-approval-submit：保存业务 ID、流程类型及原 requestId；回读业务字段并查询流程实例确认已创建。 取消属于用户改变决定时的可选操作，不是正常提交后的必做步骤。
- product-design-approval-detail：展示本次申请的业务字段与附件；原请求业务 ID 必须单独保存，详情不保证能提供流程实例 ID。 状态应区分业务单据与流程实例；需要可撤回性时查 my-instances，而不是只看详情 status。
- product-design-approval-my-instances：本接口没有自动限定 hr_product_design_approval，按 processDefinitionKey 与 String(businessKey) 双重匹配；字段缺失时不可把跨业务重号当可靠确认。 页码默认 1、每页默认 20；逐页核对 total，列表局部不能用于全量汇总。
- product-design-approval-cancel：只取消自己发起且仍运行的流程；保留业务记录，不代表删除历史。 查实际流程 status=4 才认定撤销完成；会议预定则核对占用时间段消失。

本轮以 `test/ai-contract-workflow.test.ts` 核对真实 SDK 描述，复用既有浏览器基准，不重放真实写操作。逐项验证与缺口见 `docs/ai-contract-workflow-evidence.md`。
