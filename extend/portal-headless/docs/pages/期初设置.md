# 期初设置（`/dashboard/finance/setting/initial-manage/list`）

本页覆盖 Portal「系统设置 → 财务设置 → 期初设置」的实际可达链路：六个期初页签、账套/月状态、明细分页、模板下载、Excel 导入、试算、对账、人工匹配、删除明细、期初入账、对账结果和操作日志。本页属于保留范围中的 Portal「系统设置」后代页面；不等同于被排除的独立顶层「财务」系统，也不扩展到独立财务菜单的其他页面。

证据边界：已逐页核对 Portal 入口、期初设置组件、页签筛选、按钮显隐与禁用条件、导入限制、对账结果导出脚本和 Java Controller/VO；SDK 请求投影、文件边界、写请求草稿、响应字段和坏输入反证有离线测试。当前没有在测试门户执行当前租户的真实导入、试算、对账或入账，因此本页不把离线请求断言称为真实写入证据。

来源锚点：Portal `CodeReview_Projects_Js@test/portal/main@acab69acc77b6d6c0da21310cdfd26b91a01641e`；Java `CodeReview_Mall_Platform_Java@test/test@0f1a55718ebc1987affb8bf245106e809dd51da4`。

## 三、表单、筛选和权限规则

### 3.1 账套、月份和状态

所有需要上下文的调用都要求 `accountingSetId` 和有效的 `periodMonth`。月份按 Portal 的 month picker 语义归一化到该月第一天，格式为 `YYYY-MM-DD`；无效日期、未知页签、非法分页或非法 ID 在请求前失败。

调用写能力前应先调用 `getStatus`。当状态 `locked=true` 或 `disabledReason` 非空时，Portal 会禁用操作；状态中的每个页签还会返回 `imported`、`batchId`、`rowCount`、`trialStatus`、`reconcileStatus` 和 `importTime`。账套或月份改变后必须刷新状态，不能复用旧月份的状态判断。

### 3.2 当前页签筛选的精确映射

Portal 只提交当前激活页签可见的字段，SDK 保持相同边界，不因为 Java 请求 VO 有字段就扩展请求：

| 页签 | 发送的筛选字段 |
| --- | --- |
| `SUBJECT` | `subjectCode` |
| `SUPPLIER` | `subjectCode`、`supplierCode`、`supplierName` |
| `CUSTOMER` | `subjectCode`、`customerCode`、`customerName` |
| `BIO_LAYING_HEN` / `BIO_GROWING_CHICKEN` | `orderNo`、`batchNo`、`materialCode`、`materialName` |
| `BANK_STATEMENT` | `subjectCode`、`bankAccountCode`、`bankAccountName` |

所有页签都发送账套 ID、月份、`pageNo` 和 `pageSize`；默认分页是 `pageNo=1`、`pageSize=50`，页面选项为 10/20/50/100。Portal 没有 `subjectName` 输入框，所以 SDK 不发送 Java VO 中存在的 `subjectName`。

两个生物资产页签的响应可能包含 `summary`/`summaryRows`。这些是页面底部汇总行，不是 `list` 明细；消费时要分别读取汇总字段和明细字段。

### 3.3 导入和文件规则

`prepareImport`/`importFile` 接受非空标准 Base64，文件扩展名必须是 `.xlsx` 或 `.xls`，解码后最大 20 MiB；省略 MIME 时按扩展名推导。提交时字段名固定为 `file`，查询上下文带 `tabType`、`accountingSetId`、`periodMonth` 以及 Portal 上下文中存在的账套信息。

导入返回 `{ batchId, success, successCount, failCount, errors[], periodResults[] }`。`success=false` 时必须逐项消费 `errors`，不能把 HTTP 成功或 `successCount` 当成导入已生效；成功或超时后用 `getStatus` 和当前页 `list` 回查批次、行数和明细。页面没有撤销导入接口，`prepare` 被取消只代表没有发送请求。

### 3.4 试算、对账、匹配、删除和入账

所有本轮新增写操作采用 `prepare → 用户确认 → submit` 两段式；取消只丢弃本地草稿，不伪造服务端回滚：

1. `prepareTrialBalance`、`prepareReconcile`、`prepareManualMatch`、`prepareDeleteLines`、`preparePostToLedger` 只生成严格草稿，不产生服务端副作用。
2. 用户确认后，submit 能力只接受对应 prepare 返回的完整 `draft`；SDK 会再次校验草稿，不允许调用方删改上下文或 ID。
3. submit 超时或返回后，按页面提供的状态、明细、结果和日志入口独立核对；这些操作没有通用 `requestId` 或 cancel 接口，不能伪造取消能力。

隐藏期初编辑页是独立的旧版可达表单：`prepareUpdate({ form })` 要求 `id` 和四个金额字段（空字符串/`null`按页面规则保留），再由 `update({ draft })` 发送 `PUT /admin-api/finance/initial-manage/update`，body 是 Portal `...form` 的完整字段。页面没有额外状态门禁，也没有服务端取消接口；用户在提交前取消时只调用本地取消语义，不发送 PUT。

页面的额外门控规则如下：

- 人工匹配和删除最多 1000 个 ID，ID 不能重复；人工匹配不应选择 `matchStatus=1` 或 `3` 的行。
- 删除要求当前页签已导入、有有效 `batchId`，且状态不是对账中/已完成匹配；Portal 还会阻止已匹配行删除。
- 期初入账要求至少一个页签已导入，并且所有已导入页签的 `reconcileStatus` 都为 `2`。`posted=true` 仍需通过日志或对应明细账能力核对业务生效。
- `matched=false` 时，应读取对账结果分页，按 `matchStatus`、差异金额和科目定位问题；`matched=true` 也不等于已入账。

## 四、对账结果导出和失败处理

Portal 的“导出结果”不是后端 export 接口，而是按 `pageSize=500` 循环读取对账结果，再在浏览器生成 SpreadsheetML `对账结果.xls`。SDK 生成相同文件名和 MIME，导出列为模块、科目编码、科目名称、来源系统、匹配状态、来源金额、财务金额和差异金额；导出只读，不改变对账状态。

网络、401/403、后端业务错误和响应结构错误均抛出。空列表表示当前筛选没有结果，不表示没有权限；导入失败保留逐行错误；写操作超时先查状态、明细、结果或日志，再决定是否重试，避免重复导入、对账或入账。
