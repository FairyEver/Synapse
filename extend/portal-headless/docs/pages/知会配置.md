# 知会配置（`/dashboard/product/operation/notice-config/list`）

Portal「产品运营 → 知会配置」包含配置列表、级联候选、保存、状态切换和删除按钮。保存会按“推送名称 + 模块”替换旧配置并为多个岗位批量建立关系；删除按钮当前存在 Portal 与 Java 路由不一致，SDK按页面实际请求复刻并明确标出风险。

## 页面标识

| 项 | 值 |

## 1. 能力定义

| 页面动作 | 能力 / 方法 | 请求或行为 |
| --- | --- | --- |
| 查询列表 | `product-notice-config-list` / `productNoticeConfig.list` | `GET /config/notification/page` |
| 模块候选 | `product-notice-config-module-list` / `productNoticeConfig.moduleList` | `GET /config/notification/getModuleList` |
| 岗位候选 | `product-notice-config-post-list` / `productNoticeConfig.postList` | `GET /config/notification/getPostList` |
| 级联候选 | `product-notice-config-choose` / `productNoticeConfig.choose` | `GET /config/notification/getChoose` |
| 本地准备保存 | `product-notice-config-prepare-save` / `productNoticeConfig.prepareSave` | 只校验，不发请求 |
| 保存 | `product-notice-config-save` / `productNoticeConfig.save` | `POST /flockSimu/config/notification/save` |
| 删除 | `product-notice-config-remove` / `productNoticeConfig.remove` | 忠实复刻 Portal 的 `DELETE /noticeConfig/delete?id=...` |
| 启用/停用 | `product-notice-config-toggle-status` / `productNoticeConfig.toggleStatus` | `GET /config/notification/enableOrDisable` |

后端的 `GET /get` 在 Java Controller 注释为“未使用”，Portal 编辑页通过列表行桥接数据，没有调用它，因此不新增 SDK 能力。

## 2. 参数契约与表单提交规则

### 列表

Portal 默认提交：

```json
{
  "order": "",
  "orderField": "",
  "title": "",
  "module": "",
  "postId": "",
  "status": "",
  "pageNo": 1,
  "pageSize": 20
}
```

`title`是推送名称前缀筛选；`module`、`postId`和`status`为空字符串表示不筛选；`status`取 `0=停用`、`1=启用`。分页只接受 Portal 页面支持的 `10/20/50/100`。

列表返回 `{ list, total }`。每行保留 `id`、`title`、`module`、`moduleName`、`indicatorName`、`params`、`postIdList`、`postName`、`task`、`jumpPage`、`status`和`statusName`。`postIdList`是编辑表单的岗位ID数组，`status`是数字 `0/1`。

### 候选和级联

- `moduleList()`返回模块 `{ value: string, label: string }[]`；表单把 `value`提交为`module`，不要提交中文`label`。
- `postList()`返回岗位 `{ value: number, label: string }[]`；Portal组件把后端原始岗位值转成数字，保存时组成非空`postIdList`。
- `choose()`返回递归的 `{ value, label, childList }[]`。层级依次是模块、推送名称、关联任务、跳转页面、指标名称、推送参数；改变上级选项时必须清空下级值。

### 保存表单

Portal 表单字段为：`module`、`title`、`task`、`jumpPage`、`indicatorName`、`params`、`status`、`postIdList`。八项均有必填规则；`status`为 `0/1`，页面新建默认值是字符串`'1'`，`postIdList`必须为非空岗位ID数组。

`prepareSave(form)`只做本地校验并返回 `draft`。用户取消时直接丢弃草稿，不调用网络。确认后将同一草稿交给 `save({ draft })`，请求体保留 Portal 表单字段并发送：

```json
{
  "module": "1",
  "title": "高产日报",
  "task": "日报生成",
  "jumpPage": "/production/report",
  "indicatorName": "产蛋率",
  "params": "{{value}}",
  "status": "1",
  "postIdList": [101, 102]
}
```

Java 保存服务先按 `title + module` 删除旧记录，再为 `postIdList`中的每个岗位批量插入。它不是按单个ID更新；保存前必须让用户明确知道会替换同标题同模块的旧配置。

### 启停与删除

`toggleStatus({ title, module, status })`复刻列表行操作：当前数字状态为 `1` 时发送字符串`status='0'`，否则发送字符串`status='1'`；Java 按 `title + module`批量更新相关岗位记录。成功或超时后必须重新查询同一组记录确认状态，不能只看请求完成。

删除按钮的 Portal 源码是：

```text
DELETE /noticeConfig/delete?id=<record.id>
```

而当前 Java `NotificationConfigController`实际声明的是：

```text
GET /flockSimu/config/notification/delete?title=<title>&module=<module>
```

两者路径、方法和参数都不一致，且 Java DTO 构造器未明确复制实体`id`。SDK不擅自把页面请求改成推断出的 Java 请求；`remove()`只复刻 Portal 实际请求，回查不到记录时必须报告“未验证删除”，不能把 HTTP 完成当成删除成功。

当前环境未启动浏览器，尚未执行真实测试环境的列表、保存、启停或删除请求；尤其删除接口的可用性不能由离线测试替代。

## 4. 操作步骤与未覆盖项

1. 调用 `moduleList()`、`postList()`和`choose()`构造候选；用户在级联树中逐级确认最终值。
2. 用确认后的八项字段调用 `prepareSave()`；用户取消则丢弃 `draft`。
3. 用户明确确认替换同 `title + module`旧配置后调用 `save({ draft })`；成功或超时都用 `list()`回查岗位、状态、任务、跳转页面、指标和参数。
4. 启停使用最新列表行的 `title/module/status`调用 `toggleStatus()`，再回查目标状态。
5. 删除仅在存在非空 `record.id`且用户明确确认时调用 `remove()`；由于 Portal/Java路由偏差，必须回查并如实报告结果。
