# 我的督办（`/dashboard/urge/my-urge/list`）

本页覆盖 Portal「人力 → 督办事项 → 我的督办」列表、关联详情、发起督办、撤销和提醒动作。列表只展示当前用户发起的督办任务；收到的督办任务属于“我的待办”，不能把两页当成同一个业务。

证据边界：已逐字段核对 Portal 列表、详情、发起表单、负责人选择器和督办公共字典，并核对 Java Controller、VO、Service、Mapper。SDK 请求投影、表单校验、状态门禁、提醒载荷和 AI 说明有离线测试。当前未启动测试门户，创建/撤销/提醒、消息送达、真实权限和写后回查仍未形成真实环境证据。

来源锚点：Portal `CodeReview_Projects_Js@test/portal/main@acab69acc77b6d6c0da21310cdfd26b91a01641e`；Java `CodeReview_Mall_Platform_Java@test/test@0f1a55718ebc1987affb8bf245106e809dd51da4`。

## 一、页面上下文、权限和数据范围

| 项 | SDK/Portal 事实 |
| --- | --- |
| 菜单与页面 | `hr/人力` → 督办事项 → 我的督办；列表 `/dashboard/urge/my-urge/list` |
| 页面权限 | `/dashboard/urge/my-urge` |
| HTTP 实例 | `platform`；SDK 使用逻辑路径 `/hr/oversee-task/...`，由实例补 Portal 的 `/admin-api` 前缀 |
| `module-type` | 无匹配规则；SDK 定义为 `null`，不主动发送该头 |
| 当前用户范围 | Java 列表服务强制把 `supervisor` 设置为当前会话用户；SDK 不提供查询其他发起人的参数 |
| 列表主键 | `id`；详情、撤销、群发提醒和详情逐人提醒分别把它映射为接口需要的 `id`/`taskId` |

所有能力的 `pagePath`、`permission`、`moduleType` 和 `httpInstance` 相同。会话、租户、菜单权限和服务端数据权限由 SDK 会话/HTTP 层处理；Java 的详情、删除和提醒实现没有显式的当前用户归属校验，SDK 的本地状态快照门禁不能替代服务端授权。

调用门面为 `sdk.myUrge.<method>`，目录能力 ID 以 `my-urge-` 开头。说明由 `catalog.describe(id)` 和 `catalog.describe(id, { format: 'llm' })` 返回。

| 能力 ID | SDK 方法 | 请求/效果 |

| `my-urge-list` | `list` | `GET /hr/oversee-task/page`，返回 `{ list, total }` |
| `my-urge-supervisor-search` | `supervisorSearch` | `GET /sys/user/pageInfo`，按关键字分页搜索负责人；Portal每页固定5条 |
| `my-urge-detail` | `get` | `GET /hr/oversee-task/get?id=...` |
| `my-urge-prepare-create` / `my-urge-create` | `prepareCreate` / `create` | 本地校验创建表单；`POST /hr/oversee-task/create` |
| `my-urge-prepare-delete` / `my-urge-delete` | `prepareDelete` / `remove` | 仅未完成任务允许；`DELETE /hr/oversee-task/delete?id=...` |
| `my-urge-prepare-send-message` / `my-urge-send-message` | `prepareSendMessage` / `sendMessage` | 仅未完成任务允许；`GET /hr/oversee-task/sendMessage?taskId=...` |
| `my-urge-prepare-send-personal-message` / `my-urge-send-personal-message` | `prepareSendPersonalMessage` / `sendPersonalMessage` | 仅未完成负责人允许；`POST /hr/oversee-task/sendPersonalMessage`，body为`null`、ID在query |

后端存在的 `PUT /hr/oversee-task/update`、统计、旧版 `/list` 和按业务查询接口未纳入：当前 Portal 页面没有调用它们。

## 三、列表、候选和详情规则

### 3.1 列表

Portal 初始筛选为：`taskName=null`、`superviseeName=null`、`endDate=null`、`isComplete=0`、`pageNo=1`、`pageSize=20`。请求还固定带 `order=''`、`orderField=''`：

| 参数 | 页面含义 | 规则 |
| --- | --- | --- |
| `taskName` | 督办内容 | 文本模糊筛选；空值按Portal初值发送 `null` |
| `superviseeName` | 负责人 | 文本模糊筛选；空值按Portal初值发送 `null` |
| `endDate` | 完成时间 | `YYYY-MM-DD`；空值不筛选 |
| `isComplete` | 督办事项/督办完成 | `0=督办事项`、`1=督办完成`；默认 `0` |
| `pageNo` / `pageSize` | 分页 | 默认 `1/20`；页面选项为 10/20/50/100 |

未完成列表显示任务、负责人姓名、紧急程度、计划完成日期、`tip`、详情、撤销和发起提醒；已完成列表只显示任务、负责人、计划完成日期和详情。紧急程度为：`1=重要紧急`、`2=不重要紧急`、`3=不重要不紧急`、`4=重要不紧急`。后端生成未完成提示：`已延期:N天`、`剩余:N天` 或 `剩余:0天`。

### 3.2 负责人候选

发起页的负责人弹窗实际请求：

```text
GET /sys/user/pageInfo
params: { name, pageNo, pageSize: 5 }
```

响应候选字段包括 `id`、`realName`、`username`、`organizationName`；Portal 将它们转换成选择器的 `cooperator`/`cooperatorName` 等本地字段，提交时只保留：

```text
superviseeList: [{ supervisee: Number(cooperator) }]
```

无头 SDK 不提供空关键字全量候选：`supervisorSearch` 要求非空 `keyword`，再把它映射为请求的 `name`，每页固定5条。这是长选项保护，不改变用户明确关键字后的字段和分页语义。

### 3.3 详情

`get({ id })` 发送 `GET /hr/oversee-task/get`，参数为 `{ id }`。详情根记录包含任务名称、详情文本、计划完成日期、紧急程度、发起人、当前完成状态、截止提示和负责人列表；负责人行包含 `supervisee`、姓名、完成状态、完成日期、完成说明、附件 URL/名称和 `isCanEdit`。

发起人可以看到所有负责人完成详情和附件；普通负责人只能看到自己的完成详情和附件，其他负责人的完成说明可能被后端置空。详情页的逐人提醒只对 `isComplete=0` 的负责人行显示。Java 静态实现没有先校验访问者是否为任务发起人/负责人，因此 SDK 不把 `get` 的返回当作通用任务授权证明。

## 四、创建、撤销和提醒提交规则

### 4.1 创建

创建表单字段和 Portal 校验：

| 字段 | 规则 |
| --- | --- |
| `taskName` | 必填，最多30字符 |
| `taskDescription` | 必填，最多200字符 |
| `superviseeList` | 必填，至少1名负责人；不能重复；ID来自负责人关键字搜索 |
| `endDate` | 必填，`YYYY-MM-DD`，不能早于Portal当天 |
| `degreeType` | 必填，1/2/3/4四种紧急程度 |

调用顺序：

```text
supervisorSearch({ keyword })
  → 用户选择 list[].id
prepareCreate({ taskName, taskDescription, superviseeList, endDate, degreeType })
  → 用户确认
create({ draft })
  → get({ id: createdId }) 回查
```

实际 POST body 只包含以下字段，顺序与 Portal 一致：

```text
{
  degreeType,
  taskName,
  taskDescription,
  superviseeList: [{ supervisee }],
  endDate
}
```

Java 会忽略客户端传入的 `supervisor`，用当前登录用户写入发起人；创建还会为负责人写关联记录并发送通知。后端没有 requestId，重复提交会产生重复任务和重复通知；创建返回 ID 或超时后，未回查前不能自动重试。

### 4.2 撤销

列表仅对 `isComplete=0` 显示“撤销”，确认文案说明撤回后无法恢复。SDK 的 `prepareDelete({ id, currentIsComplete })` 要求最新快照状态为0，`remove({ draft })` 发送：

```text
DELETE /hr/oversee-task/delete
params: { id }
```

`true` 只是接口回执；成功或超时必须重新 list/get 确认任务已撤回。Java 删除服务会删除主任务并软删负责人关联记录，但没有恢复接口，也没有显式校验当前用户归属或完成状态；本地门禁不替代服务端授权。

### 4.3 群发和逐人提醒

列表“发起提醒”只对未完成任务显示，实际是：

```text
GET /hr/oversee-task/sendMessage?taskId=<任务ID>
```

详情“发送提醒”实际是：

```text
POST /hr/oversee-task/sendPersonalMessage?taskId=<任务ID>&userId=<负责人ID>
body: null
```

SDK 两条链都先准备草稿并要求当前快照为未完成，再由用户确认提交。返回非空成功文本只能说明服务端接受发送请求，不代表消息送达；Java 未显式校验任务归属、负责人归属，也没有服务端去重，超时不能盲目重发。

## 五、操作步骤、失败处理和四件套证据

统一步骤：

1. `list` 查询当前用户发起的任务；长选项负责人用 `supervisorSearch({ keyword })` 分页搜索。
2. 用同一任务 `id` 调 `get`，获取最新状态和负责人行。
3. 创建走 `prepareCreate → 用户确认 → create → get回查`。
4. 撤销走 `prepareDelete → 用户确认 → remove → list/get回查`；提醒走相应 `prepare → 用户确认 → submit`。
5. 会话、租户、权限、网络、业务错误和响应结构错误均抛出；空列表不是无权限证明。
