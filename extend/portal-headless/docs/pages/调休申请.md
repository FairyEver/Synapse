# 调休申请（`/simple/hr/form/043`）

流程表单第七条线，**「加班申请」（042）的孪生流程**——同一族的 HR 日常单子，相邻的两个表单号。
模板是加班那条线（`src/capabilities/overtime-application.ts`，**只读**）。

**但它与加班那条线不是同构的**，四处形态差异见 §二：**明细行数组**、**附件控件**、
**剩余加班时长要打接口**、**后端会重算并有一条硬门槛**。

> 四件套：能力 `src/capabilities/rest-leave-application.ts` · 测试 `test/rest-leave-application.test.ts` ·
> 基准 `baseline/rest-leave-application.browser.json` · 冒烟 `smoke/rest-leave-application.mjs`。

### 3.1 请假类型只有一个选项，且是只读的

`043/page/common/define.js`：

```js
export const LEAVE_TYPE_REST = 0
export const LEAVE_TYPE_OPTIONS = [{ value: LEAVE_TYPE_REST, label: '调休' }]
```

后端 `fillLeaveTypeDefaults()` 更硬：`leaveType == null` 就填 0，**不是 0 就抛「请假类型必须为调休」**。
页面上它渲染成只读文本（`{{ leaveTypeLabel || '-' }}`），用户换不了 ⇒ SDK 也不做成参数。

### 3.2 ★ `userId` / `staffCode` / `departmentId` **都是字符串**

实测 `/sys/user/info` 返回的 `id` / `organizationId` / `username` / `staffId` 全是**字符串**
（`"18243"` / `"101"` / `"2021070101"` / `"1163"`），页面直接赋值不做转换，
浏览器抓包里就是 `"userId":"18243"`。SDK 也发字符串（D20 逐字段一致）。

⚠️ **工号是 `username`，不是 `staffId`**：实测 `username = "2021070101"`（页面上那个「工号」显示的
就是它），而 `staffId = "1163"`。后端 `fillApplicantDefaults()` 也写的是 `userDTO.getUsername()`。
测试里有一条变异专门把 `username` 换成 `staffId`，会红。

### 3.3 只读联动：调休时长怎么算

`043/page/pc/edit/index.vue:190-208`（mobile 版同名 computed，算法一致）：

```js
const totalLeaveHours = computed(() => {
  const items = formState.value.leaveDateItems || []
  const sum = items.reduce((acc, row) => {
    const v = Number(row?.leaveHours)
    return acc + (Number.isFinite(v) ? v : 0)
  }, 0)
  return Number(sum.toFixed(1))
})
watch(totalLeaveHours, (val) => { formState.value.leaveHours = val })
```

**`toFixed(1)` 与「四舍五入」在真实输入上是分叉的**：0..40 之间按 0.01 步进有 **160 组**分叉。
例如 `3 + 0.05 = 3.05`（二进制里是 3.0499999999999998）⇒ `toFixed(1)` 给 **3**；
而 `Math.round(3.05*10)/10` 给 **3.1**。测试里挑了三组（3.05 / 0.15 / 0.35）写死，
并**反向对照** `Math.round` 确实给别的值 —— 否则那三条钉不住任何东西。

### 3.4 只读联动：剩余加班时长**要打接口**

页面 `onMounted` 里 `tryPrefillRemainingOvertimeHours()`：

```
GET /hr/overtime-application/record/remaining-hours?userId=<当前用户 id>
```

⚠️ **它挂在 `overtime-application` 这个 controller 下**，不是 `rest-leave-application`
（`OvertimeApplicationController:126`）—— 不是笔误，后端就这么放的。
**这是调休表单自己要用的接口**，所以收在本能力里（挂在 `/simple/hr/form/043` 下），
**不**另开一个页面能力。

## 四、★★ 后端重算两个字段，还有一条 SDK 本地复刻不了的硬门槛

加班那条线是"前端算、后端不重算"。**本流程正好反过来**：

```java
// RestLeaveApplicationServiceImpl.createApplication()
LeaveSummary leaveSummary = calculateLeaveSummary(createReqVO);   // ← 按明细行重算
createReqVO.setLeaveHours(leaveSummary.getTotalLeaveHours());     // ← 覆盖调用方给的值

BigDecimal remainingOvertimeHours = calculateRemainingOvertimeHours(createReqVO.getStaffCode());
if (leaveSummary.getTotalLeaveHours().compareTo(remainingOvertimeHours) > 0) {
    throw exception("调休时长不能大于剩余加班时长");                  // ★ 硬门槛
}
createReqVO.setRemainingOvertimeHours(remainingOvertimeHours);    // ← 也覆盖
```

### 4.1 ★ 两个「剩余加班时长」是**两套算法**，可以不等

| | 页面显示的那个 | 后端 create 门槛用的那个 |
| --- | --- | --- |
| 出处 | `OvertimeApplicationServiceImpl.getRemainingOvertimeHours` | `RestLeaveApplicationServiceImpl.calculateRemainingOvertimeHours` |
| 入参 | `userId` | `staffCode` |
| 加班侧口径 | `subsidyType=0` 且 `status=已审批`，**不限年份** | `subsidyType=0` 且 `status=已审批`，**限当年** |
| 调休侧口径 | `status in (1 审批中, 2 已审批)`，**不限年份** | `status = 2 已审批`，**限当年** |
| 归零 | `< 0` 时归 0，`setScale(2, HALF_UP)` | 同 |

⇒ **两者在存在跨年单据或审批中单据时会分叉。** 所以 SDK **不拿页面那个值当本地门槛**：
那样既可能放过去（页面值 > 门槛值），也可能冤枉拦下（页面值 < 门槛值）。
如实做法是把页面那个值当**只读展示字段**照发，门槛交给后端如实报错。

失败时后端报的原文是「**调休时长不能大于剩余加班时长**」（冒烟脚本会把它翻译成一句人话，
但**不吞错**）。这是**本能力唯一一条没法在提交前本地拦下的门槛**，如实记在这里。

### 4.2 `leaveHours` 的两种算法在合法输入下必然相等

- 后端：每行 `setScale(2, HALF_UP)` 后累加，再 `setScale(2, HALF_UP)`
- 页面/SDK：每行累加后 `Number(sum.toFixed(1))`

页面那个 `a-input-number` 有 `:precision="1"`（移动端 `van-stepper :decimal-length="1"`），
**每行最多 1 位小数**，所以每行 `setScale(2)` 是恒等操作、总和的小数位也 ≤1
⇒ 两边必然相等。SDK 因此把「每行最多 1 位小数」也做成了一条本地校验
（它同时是页面行为，不是 SDK 自己发明的）。

## 六、★ 审批链：与加班那条线**形态相同**（同一条守卫，照抄）

### 6.1 实测：**没有「发起人自选」节点**

```
POST /hr/rest-leave-application/getRequiredStartUserSelectTasks   body = 完整载荷
→ { "code": 0, "ret": "SUCCESS", "data": [] }        ← 一个节点都没有

同一个接口传 {} → 400「请求参数不正确:请假事由不能为空」  ← ★ 它要收完整载荷（@Valid @RequestBody）
```

第 2 条与通用审批那条线不同（那条的后端把请求体整个忽略），与加班那条线**一致**。

### 6.2 那审批人是谁？—— `bpmnXml` 里的 `candidateStrategy="23"`

```xml
<userTask id="Activity_1ee4c6r" name="直属上级审批"
          flowable:candidateStrategy="23" flowable:candidateParam="__placeholder__"/>
```

`23 = BpmTaskCandidateStrategyEnum.DIRECT_LEADER（直属上级）`。
`POST /bpm/process-instance/preview` 的响应（实测）：

```
START_EVENT Event_1nue66s
USER_TASK Activity_1ee4c6r「直属上级审批」[strategy=23 直属上级] → 候选人 乔娜(15012)
END_EVENT Event_15m52e5
copyUsers: []
```

⇒ **审批人是后端按发起人所在组织算出来的，发起人既不知道、也选不了。**

### 6.3 ★★ 提交前的硬守卫：**审批链里不能有发起人本人**

**为什么必须有**：后端 `BpmTaskServiceImpl` 有一条「流程发起人与审批人相同，自动审核通过」。
命中时流程**当场走完**，`cancel-by-start-user` 从此必然报
「流程取消失败，流程不处于运行中」——那条单据**永远撤不掉**
（测试环境里已经因此留了 3 条 `status=2` 的记录，本轮一条都没碰）。

**本能力的做法**（照抄加班那条线，判据是**真实审批链**而不是调用方传的 assignees）：

```
POST /bpm/process-instance/preview   body {processDefinitionKey, variables: <本次载荷>, ...}
  → nodes[].type === 'USER_TASK' 的 candidateUsers[] 里逐个比对发起人 id
  → 命中 ⇒ **在 create 之前**抛错，一个写请求都不发
```

比"只防自选节点"强在哪：它覆盖**所有** `USER_TASK`（直属上级 / 部门负责人 / 岗位 / 用户组…），
而本流程压根没有自选节点，旧做法**完全防不住**。顺带它还能答出「这次会打扰谁」。

**两条边界，如实记下：**

- **逃生口**：`skipSelfApprovalGuard: true`，只在预览接口本身不可用时才该用，默认**关着**。
- **这条守卫不能证明**审批人最终一定是预览里那个人。预览是"按当前数据算一遍"，
  真实办理时后端会拿当时的组织数据再算一次。SDK 能保证的是：
  **预览时命中自己就一定拒绝**。

### 6.4 请求顺序（只有最后一条是写）

```
① GET  /sys/user/info                                        只读（submit 里只打一次）
② GET  /hr/overtime-application/record/remaining-hours        只读
③ POST /hr/rest-leave-application/getRequiredStartUserSelectTasks   页面 formSubmit() 的第一步
④ POST /bpm/process-instance/preview                          ★ SDK 加的守卫
⑤ POST /hr/rest-leave-application/create                      写
```

守卫插在 ④ 而不是更早，是为了保持页面上 ①→⑤ 的**相对顺序不变**；
它只多一次**只读**请求，却能把"单据永远撤不掉"挡在写之前。

### 6.5 详情接口里**没有** `processInstanceId`

`RestLeaveApplicationRespVO` 只到 `status` / `statusName`（DO 里有 `processInstanceId`，VO 没带出来）。
⇒ 撤销要先用 `findInstanceByBusinessKey()` 去「我的流程」按 `businessKey` 换流程实例 id。
`businessKey` 是**各业务表自己的主键**，会与会议室/加班撞车，所以还要按
`processDefinitionKey` 再筛一道（有测试钉住，也有一条变异改它，会红）。

### 9.1 抓到两个真的「测试太弱」，都已修

这一轮**不是"一次全红"就收工**——头一次跑出来的是 33 红 / 4 存活，其中两个是**真正的弱测试**：

1. **`事由上限 200 → 300` 存活**：那条用例的期望值是拿 `REASON_MAX` **同一个常量**构造的
   （`'x'.repeat(REASON_MAX + 1)` 配 `new RegExp('最多 ${REASON_MAX} 个字')`），
   常量改了它照样绿 —— 典型的「自己断言自己」。**改成写死 200 / 201 / 500 / 501 字面量**后变红，

2. **`remainingOvertimeHours 缺省填 999` 存活**：载荷用例只喂了"有值"的那条路径，

两个都**先确认改坏了会红**再收工（重跑变异，见 §9.3）。

### 9.2 两个等价变异（**改了不会红，也不该红**，如实说明理由）

1. **`守卫 id 比较改成字符串严格相等`**（`Number(a)===Number(b)` → `String(a)===String(b)`）：
   `selfUserId` 在 `submit` 里**永远是 `Number(derived.userId)`**（数字），而候选人的 id
   实测是数字、用例里补的字符串 `'18243'` 两种比较都判等。
   造一个能分叉的输入只能靠 `' 18243'`（带空格）这种现实中不会出现的值 —— **属于等价变异**。
   它想防的"按字面比字符串"这件事，在当前代码里两种写法行为一致。
2. **`本地校验挪到打接口之后`**：`prepareInternal` 里那行 `normalizeRestLeaveDraft(draft)`
   挪到 `resolveDerivedFields()` 之后**行为完全相同**——因为 `resolveDerivedFields()`
   **自己第一件事就是** `normalizeRestLeaveDraft(draft)`（它就是为这条规矩抽出来的）。
   两处校验互为冗余 ⇒ **等价变异**。要点：这条规矩真正的承重墙是
   `resolveDerivedFields()` 里那一行，不是 `prepareInternal` 里那一行。

## 十、尚未覆盖 / 不确定

### 10.1 确实没做的

- **「重新发起」（reapply）没做**：与加班那条线一样，`isReapply` 分支会从原流程实例抄字段
  再提交（`fetchDetail()` 里 `formState = {...result, id: null}`），是一条**另起的写链路**。
- **驳回后改单重提（`PUT /update`）与删除（`DELETE /delete/{id}`）没做**：
  与加班那条线**不同**——本流程这两个接口**后端是真的开着的**
  （`RestLeaveApplicationController` 里没被注释掉，限 `status=3 已驳回`），
  页面上也有入口（详情/编辑分支）。本能力做的是**用户日常那条路**（新建 → 提交 → 撤销）；
  驳回后改单重提是另一条写链路，**没有验证过就不写**。
- **`/hr/rest-leave-application/page`（分页）没做**：那是**另一个列表页**，不是本流程表单的一部分。
- **详情页的「打印」没做**：只读展示件，打的是通用打印壳，不影响能不能提交。
- **`/hr/overtime-application/record/page` 与 `/record/detail` 没做**：
  属于「加班记录」页面；只有 `record/remaining-hours` 是**本表单自己要用**的，所以收了（§3.4）。

### 10.2 不确定的（**不要读成"已验证"**）

- **「预览里的审批人 = 最终实际审批人」没有独立证实**。本轮只证实了
  "提交后流程 `status=1`、撤销后 `status=4`"，**没有**去证实"待办真的落在乔娜的箱子里"
  ——那要读她的待办列表，属于别人的数据，本轮没碰。
- **后端那条「调休时长不能大于剩余加班时长」的门槛，本轮一次都没有被触发过**
  （两轮的 1.5 小时都远小于余量 4）。所以「被拒时 SDK 的报错长什么样」是**从后端源码读出来的，
  不是实测的**。冒烟脚本里那段把报错翻译成人话的分支同理，**没在真实环境走过**。
- **两个「剩余加班时长」算法会不会真的分叉，没有造过交叉数据去证实**。
  §4.1 的结论是**读两边源码比出来的**（年份口径与 status 口径不同），逻辑上必然可分叉，
  但**本轮实测的那一个数据点上两者恰好都是 4**。
- **`skipSelfApprovalGuard` 这条逃生口一次都没在真实环境用过**。它只是"预览接口挂掉时
  还有没有办法提交"的兜底，本轮没造过预览挂掉的场景。
- **`assertTasksCovered` 的两条分支在真实环境上是死的**：本流程实测恒 0 个自选节点，
  所以"节点没覆盖"与"多给了节点 id"这两条**只在单测里红过，没有在真实环境触发过**。
  它们是**为流程将来被改而留的**，不是"已端到端验证"。
- **附件的 50MB 单件上限 SDK 拦不了**（`size` 是调用方给的，拿它当判据等于自己骗自己），
  这条**如实留给后端**。带附件那一轮用的是 70 字节的 PNG，**没有测过超限的情形**。
- **`applyDate` / 时区**：本表单**没有**「申请日期」字段（与加班那条线不同），所以这条线
  不存在时区问题；`leaveDate` 是纯日期 `YYYY-MM-DD`，SDK 做的是"真实存在的日期"校验。

| rest-leave-application-approval-chain | read | { nodes, processDefinitionId?, processDefinitionKey?, processDefinitionName?, state?, copyUsers? } | 用户已知道当前变量下的审批路径；继续提交前仍需完整 prepare。 |
| rest-leave-application-prepare | prepare | { payload, derived, tasks } | 草稿校验并得到所需自选节点后准备完成；实际发起须再提交。 |
| rest-leave-application-submit | write | number（业务单据 ID；SDK 不返回 code/data 包络） | 回读确认业务记录及其流程后，向用户交付业务 ID 与当前审批状态；提交成功不等于审批完成。 |
| rest-leave-application-detail | read | 业务单据对象（拆包后） | 用户查询详情时交付业务信息与可靠状态即可；需要取消则先确认对应实例仍运行。 |
| rest-leave-application-my-instances | read | { list: 流程实例[], total: number } | 向用户展示流程名称、审批内容、状态与起止时间；有明确目标时只交付匹配实例。 |
| rest-leave-application-cancel | write | boolean（后端成功回执；SDK 原样返回拆包后的值） | 流程实例 status=4，必要时详情也回读已取消，向用户报告撤销结果。 |

数据消费与分支：

- rest-leave-application-definition：展示 name 与 key 核对业务；formFields 为 null 不代表免填，填写规则在 prepare/submit 的 SDK 描述中。
- rest-leave-application-current-user：展示 realName、organizationName、postName；由 SDK 自动填申请人/部门等只读字段，调用方不用回传。 只含白名单字段；不返回 password2/salt 等凭据。
- rest-leave-application-remaining-hours：userId 来自 current-user.id，不能把 staffId 放这里；比较调休明细小时合计与本值。
- rest-leave-application-approval-chain：依次展示节点名称、candidateStrategyName 与 candidateUsers 姓名；节点用 nodeId 区分。 将 USER_TASK 的 candidateUsers[].id 与当前用户 ID 比较，发起人=审批人可能自动通过而无法撤销。 预览不产生任务，nodeId 不能传 task-action 的 taskId。
- rest-leave-application-prepare：给用户核对 payload 的业务值；按 tasks[].id 建立 startUserSelectAssignees 的键，人员来自候选查询，人数、去重与顺序服从任务规则。 准备只读，不建单、不保留名额、不发送待办；任何草稿变更后应重新准备。
- rest-leave-application-submit：保存业务 ID、流程类型及原 requestId；回读业务字段并查询流程实例确认已创建。 取消属于用户改变决定时的可选操作，不是正常提交后的必做步骤。 提交默认预览审批链并拒绝发起人命中 USER_TASK 候选审批人；skipSelfApprovalGuard=true 会绕过该守卫，不应用它掩盖真实自审命中。
- rest-leave-application-detail：展示本次申请的业务字段与附件；原请求业务 ID 必须单独保存，详情不保证能提供流程实例 ID。 状态应区分业务单据与流程实例；需要可撤回性时查 my-instances，而不是只看详情 status。
- rest-leave-application-my-instances：本接口没有自动限定 hr_rest_leave_application，按 processDefinitionKey 与 String(businessKey) 双重匹配；字段缺失时不可把跨业务重号当可靠确认。 页码默认 1、每页默认 20；逐页核对 total，列表局部不能用于全量汇总。
- rest-leave-application-cancel：只取消自己发起且仍运行的流程；保留业务记录，不代表删除历史。 查实际流程 status=4 才认定撤销完成；会议预定则核对占用时间段消失。

本轮以 `test/ai-contract-workflow.test.ts` 核对真实 SDK 描述，复用既有浏览器基准，不重放真实写操作。逐项验证与缺口见 `docs/ai-contract-workflow-evidence.md`。
