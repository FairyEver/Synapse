## 只有两条接口

页面是标准的 `useListPageModule({ styleV2: true, getDataListIsPage: true, customLoad })`：

- **`customLoad` 里那一条**（`review/list.vue:101-107`）：
  `http('/manager/knowledgeChangeRecord/list', { params: form })` —— 注意是**把 axios 实例当函数调**，
  等价于 `http.get(url, {params})`，方法仍是 **GET**。
- 页面上另外两个「写」的入口（弹窗的两个按钮、批量那两个按钮）**都走同一个共享函数**。

## 审核提交的真实 URL：`httpReviewSubmit` → `PUT …/audit`

`review/list.vue:94` 与 `components/review.vue:63` 都写着：

```js
import { httpReviewSubmit } from 'app/portal/components/portal/platform/document/utils/share.js'
// 调用点长这样（看不出 URL）：
await httpReviewSubmit({ reviewId: props.data.id, status })
```

那个文件（`app/portal/components/portal/platform/document/utils/share.js:4-16`）里才是真的：

```js
await http.put('/manager/knowledgeChangeRecord/audit', { id: reviewId, auditStatus: status }, { useJsonPost: true })
```

⚠️ 两个易错点：
1. **只看调用点会以为它是另一个接口**（调用点只写 `{reviewId, status}`）。
2. **`id` 是变更记录的 id**，不是 `fileId` / `knowledgeId`。列表行里两个都有，传错那一个后端
   `selectByPrimaryKey` 取到 null，`AuditFactory.getAuditFacade(...)` 之后直接 NPE → **500**。
3. `useJsonPost: true` 在 `platform.js` 上是**空转**的：那个 flag 只被 `zhdj-cms.js:46` /
   `zhdj-app-lay.js:38` 两个实例读，platform.js 的拦截器里一个字都没提它。所以 body 是
   axios 默认序列化的 JSON —— 与页面发出的一致，但**别以为这个 flag 起了作用**。

## 列表参数的顺序（`REVIEW_LIST_ORDER`）与两条后端行为

`useListPageModule.logicFetch`（`common/libs/renren/list.js:469-482`）拼参数的顺序是
`{order, orderField, ...convertFetchForm(formState)}` 再追加 `pageNo` / `pageSize`；
`convertFetchForm`（`review/list.vue:146-152`）做的是 `omit(form, ['submitTime'])` 再补
`submitStartTime` / `submitEndTime` —— 所以那两项排在**表单 6 项之后、分页之前**，不是插在中间。

```text
order=&orderField=&parentFileName=&fileName=&submitterName=&auditStatus=&auditorName=&auditType=&submitStartTime=&submitEndTime=&pageNo=1&pageSize=20&_t=…
```

页面上表单 6 项的初值全是 `null`（`review/list.vue:112-118`），被 qs 的 `skipNulls` 丢掉 ⇒
**页面刚打开时只发 `order=&orderField=&pageNo=1&pageSize=20&_t=`**（实测的 URL 见下面）。
`order` / `orderField` 是**空串**，不会被丢掉，**一定会发**。

两条后端行为（`KnowledgeChangeRecordMapper.xml` 的 `selectByPage`）：

- **四个名字类的筛选都是 `like concat(#{}, '%')`，前缀匹配**，不是包含匹配
  （`submitterName` / `auditorName` / `fileName` / `parentFileName`）。
- **总是 `order by id desc`**（写死在 XML 里），页面的 `order` / `orderField` 传什么都不改变排序。
- 时间那两项是 `a.submit_time >= #{submitStartTime}` / `<= #{submitEndTime}`，**闭区间**；
  页面上是一个 `a-range-picker show-time`，`value-format="YYYY-MM-DD HH:mm:ss"`，
  **不是**别处那种「结束日 +1 天」的开区间 —— 两个值就是用户选的那两个时刻。
- `pageNo` / `pageSize` 在后端是**独立的 `@RequestParam(defaultValue = "1" / "10")`**，
  而页面按 `styleV2` 发的是 **20**（`list.js:391`）。

## 「审核」按钮什么时候出现（**UI 判据，后端不校验**）

```js
// review/list.vue:154-156
function canReview (record) {
  return record.auditStatus === 2 && String(userStore.state.id) === String(record.auditorId)
}
```

也就是说页面上只有「**待审 + 这单指派给我**」才出现审核按钮，行内那个按钮是这个判据、
批量的那两个按钮也用它过滤（`actionBatchReview` 里 `.filter(canReview)`）。

**后端不校验这一条**：`KnowledgeChangeRecordServiceImpl.audit` 只按记录 id 查出来、
按 `auditType` 找策略执行，没有「你是不是它的审核人」这一步。
⇒ 本能力照抄的是**请求**，不是那条 UI 判据。调用方要自己看 `auditorId`（真机实测里我审的几条
记录原本指派给 `16790`，审完 `auditorId` 变成我 —— 这是后端 `AuditXxx` 里 `setAuditorId(当前登录人)` 的行为）。

## 批量是**循环单条**，不是批量接口

`actionBatchReview`（`review/list.vue:182-199`）对勾选的每一行 `await httpReviewSubmit(...)`，
一条一条串行发。本能力**没有** `auditBatch`：循环调 `audit` 即可（合并成一个方法会掩盖
「一条失败后面还发不发」这个调用方该自己决定的问题）。

## ⚠️ 审核是**终态**，两个方向都有破坏性副作用（读 `strategy/knowledge/**`）

| `auditStatus` | 策略 | 副作用 |
| --- | --- | --- |
| `1` 通过 | `AuditAddFolder` / `AuditAddFile` / `AuditUpdateFolder` / `AuditUpdateFile` | 应用这次变更（改名、置 `audit_status=1`） |
| `1` 通过 | `AuditDeleteFolder` / `AuditDeleteFile` | **硬删**文件行 + 章节 + 权限行（`deleteByPrimaryKey` …）—— ✅ 实测到了 |
| `1` 通过 | `AuditMoveFolder` | 应用移动 **并重写两个目录的权限**（7 种情况的分支） |
| `3` 拒绝 | `AuditAddFolder` | 把文件**改名成 `String(System.currentTimeMillis())`** —— 不是删除，也不是保留原名 |
| `3` 拒绝 | `AuditMoveFolder` | 移回 `history_parent_id`，并把 `audit_status` 改成 1 |
| `3` 拒绝 | `AuditUpdateFolder` | 只记状态，名字不动 |

⇒ 本能力的 `audit` 只接受 **1 / 3**（页面上也只有这两个按钮），传 `2`（待审核）**当场拒绝**：
后端**不校验**这个值，传什么存什么，那纯粹是写坏数据。
**没有 `cancelAudit`** —— 后端没有撤回接口（`KnowledgeChangeRecordController` 只有
`list` / `audit` / `getChangeRecord/{id}` 三个映射）。

## 基准对照（2026-09-21，`baseline/ai-knowledge.browser.json`）

这一页在基准里有 **4 条**，其中**只有 1 条是它自己的契约**：

| 基准里的请求 | 是不是本页契约 |
| --- | --- |
| `GET /admin-api/manager/knowledgeChangeRecord/list?order=&orderField=&pageNo=1&pageSize=20&_t=<ts>`（**同一条出现两次**） | ✅ 列表（页面把它发了两次） |
| `GET /admin-api/org/sensitive/info?_t=<ts>` | ❌ **app 外壳** |
| `GET /admin-api/bpm/task/list-by-category?finished=1&pageNo=1&pageSize=10&_t=<ts>` | ❌ **待办角标**（外壳） |

**对照结论：基准与源码推导不冲突**，能力发出的 URL 与基准**逐字段一致（含键顺序）**。
被基准证实/钉死的三条：

1. **`pageSize=20`** —— 后端这个接口的 `@RequestParam` 默认是 **10**
   （`KnowledgeChangeRecordController:42-43`），20 是页面按 `styleV2` 发出来的。
   现在这条有硬证据了（断言写成 `pageSize=20` 且 `not.toContain('pageSize=10')`）。
2. **`order=&orderField=` 两个空串一定会发**（不被 `skipNulls` 丢掉），表单那 6 项因为初值是 `null` 而不发。
3. **不发 `module-type`** —— 基准这条的 `headers` 里不存在这个键（与规则表匹配不到一致）。

⚠️ 仍然**没有**证据的：`PUT …/audit` 的 body 键序、带筛选的列表请求（含 `auditType=` / `submitStartTime=`）。
抓基准时没点过审核按钮、也没填过筛选。

`test/ai-knowledge.test.ts` 的「与浏览器基准逐字段一致」那一组（10 例）里，
有三条是**刻意**写成断言的：「基准里 0 条写请求」「下钻不在基准里」「外壳请求能力一条都不发」——
将来谁重抓基准补上了，它们会红，提醒来的人把断言补齐而不是删掉。
