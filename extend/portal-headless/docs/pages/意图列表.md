## 列表：**只有一条**，打的是 `/admin-api/system/intent/page`

派单时有一条线索说"只看到 `GET …/tip-template/getConciseTipTemplatePage`"，那是**另一个位置**的请求
（见下面「关联提示词」一节）。真正决定列表的是 `intent/list.vue:62-69` 的
`useListPageModule({ getDataListURL: '/admin-api/system/intent/page', … })`。

**查证过程**（按 conventions 第 28 条的口径逐条排掉"最容易漏的声明形式"）：

- `intent/list.vue` 只 import 了 `common/libs/renren/list.js` 与 `list-ui.js`，**没有**自定义 `http`；
- **没有** `customLoad`（`customLoad` 那一支会绕开 `getDataListURL`，这里没走）；
- `common/libs/renren/presets/platform|product/list.js` **没有**被这一页引用
  （那两个 preset 只服务 `presets` 自己的调用点；这一页是显式 `useListPageModule`）；
- `grep -rn http app/portal/views/…/prompt/intent/`：**只有** `IntentTemplateListSelect.vue`
  （`:76` import 的是 `platform.js`，`:114` 打的是候选接口），`intent/` 目录里没有第二处请求声明。

所以列表**就一条**。**基准独立证实了这一点**：`baseline/ai-prompt.browser.json` 里这一页
只有 3 条请求，其中页面自己的那一条是

```
GET https://biz-api-test.wodecorp.cn/admin-api/system/intent/page?order=&orderField=&name=&pageNo=1&pageSize=20&_t=<ts>
```

**没有**任何 `tip-template` 请求。与源码推导逐字一致，无冲突。
表单初值 `form: { name: '' }`（`intent/list.vue:67-69`），键序来自 `logicFetch`；
后端 `IntentMapper.selectPage` 对 `name` 是 `likeIfPresent` ⇒ `LIKE '%x%'`。

## 写链路：**没有 `prepare`**，撤销就是 `remove`

| 动作 | 请求 | 出处 |
| --- | --- | --- |
| 新建 | `POST /admin-api/system/intent`，body `{ name, content, meaning, templateIdList }` | `[mode]/[id].vue:39-52` 的 `objectURL` + `form.js:131` |
| 修改 | `PUT /admin-api/system/intent`，body `{ id, name, content, meaning, templateIdList }` | 同上另一支 |
| 详情 | `GET /admin-api/system/intent/{id}` | `form.js:176`（编辑模式挂载时真的会调） |
| 删除 | `DELETE /admin-api/system/intent/{id}`，无 body、无 params | `intent/list.vue:66` 的 `deleteURL` + `list.js:516-520` |

**为什么没有 `prepare`**：与考勤组 / 作业管理 / 班次管理同款判断 —— 这一页**没有任何
"提交前先问后端一次"的接口**。会议室那条线的 `prepare` 是因为"这次要人工指定哪些审批人"
会改变提交载荷；这里没有对应物。

`name` / `content` / `meaning` 的必填只在页面 `rules`（`[mode]/[id].vue:47-51`）里，
`IntentSaveReqVO` **一个校验注解都没有** ⇒ 无头侧不拦的话空名字会被真写进去。
能力在发请求前就拦（`assertIntentDraft`）。

## ⚠️ `templateIdList` 是**整组替换**，漏传会静默清空绑定

这是这一页唯一一个"不报错但是错的"，也是本能力唯一一处**比页面更严**的地方。

后端 `IntentServiceImpl`（`:44-70` 新建、`:72-106` 修改）对两份代码都是同一套动作：

```java
intentMapper.insert(intent);            // 或 updateById(updateObj)
// 先清除已有的绑定（标记 deleted = 1），再批量新增新的绑定关系
updateWrapper.eq("intent_id", …); updateWrapper.set("deleted", 1);
intentTemplateRelMapper.update(updateWrapper);
if (createReqVO.getTemplateIdList() != null && !createReqVO.getTemplateIdList().isEmpty()) {
    if (createReqVO.getTemplateIdList().size() > 3) throw exception("意图绑定的提示模板最多只能绑定三个");
    …
}
```

两条结论：

1. **修改时不给 `templateIdList`（null 或空数组）= 把已有的关联提示词全清掉。**
   所以能力的 `updateIntent` 把 `templateIdList` 做成**必填**（空数组合法 —— 那才是"确实要清空"）。
   页面上之所以看不出这个坑，是因为编辑模式的 `formState` 由 `GET /{id}` 灌入，
   而后端 `getInfo`（`:140-158`）**只在存在绑定时才回 `templateIdList`**
   —— 没有绑定时那个键根本不出现，PUT 上去等于清空（而那时本来就是空的）。
   SDK 不模仿"键有时在有时不在"。
2. **最多 3 个**，后端硬校验。能力在发请求前先拦，省掉一次注定失败的写。

另外 `updateById` 只更新非 null 字段，所以**修改时少给某个字段不会把它清空**；
`templateIdList` 的替换是**另一段代码**（上面那段），两者不要混为一谈。

## 「关联提示词」候选：那个 `getConciseTipTemplatePage` 在这里

`[mode]/[id].vue` 里挂了一个 `IntentTemplateListSelect`，它**挂载即拉全量**
（`IntentTemplateListSelect.vue:110-142` 的 `loopFetch`，`:193` 直接 `fetchTemplateList()`）：

```
GET /admin-api/sys/tip-template/getConciseTipTemplatePage?isIntentRecognition=1&pageNo=1&pageSize=100&…
```

每页 100、最多 100 页 ⇒ 无头不能照抄（conventions 第 11 条）：能力
`ai-prompt-intent-template-search` 的 `name` **必填**，`pageSize` 钳到 ≤100。

后端（`TipTemplateMapper.xml:31-42`）支持 `isIntentRecognition`（等值）与 `name`
（**前缀** `LIKE 'x%'`，不是包含）。页面写死传 `isIntentRecognition=1`；
SDK 把它做成可选 —— **不传就不发这个参数**，不替调用方决定。

键序上 SDK 把 `name` **追加在页面原有的 `isIntentRecognition`/`pageNo`/`pageSize` 之后**。

## 删除是逻辑删除，绑定关系不跟着删

`deleteIntent` 只做 `intentMapper.deleteById(id)`（`:108-112`），
`sys_intent_template_rel` 里的关联行**留在原地**（不标记 `deleted`）。
列表与详情都按 `deleted = 0` 过滤，所以从接口上看不出来 —— 但如果哪天有人在库里直接查关联表，
那些行还在。按 conventions「不要用接口返回成功代替验证」：**删完请用 `ai-prompt-intent-list` 复核**，
不要拿"接口没报错"当结论。

## 真实验证：读链路有基准，写链路一次真机请求都没发过

- **读链路（列表）/ 权限与头**：由 `baseline/ai-prompt.browser.json` 逐字段证实（见上面「列表」一节）。
  测试里是 `describe.skipIf(!HAS_BASELINE)` 那一组，现在真的在跑。
- **写链路（`POST` / `PUT` / `DELETE`）**：**没有**任何实测。写这份能力时全程只跑了本地的
  `tsc` / `vitest`（axios 适配器是假的，请求不出进程）：**没有开浏览器、没有起 `bsk` 会话、
  没有跑任何 smoke 脚本、没有向测试环境发过任何一个非 GET 请求。**
  基准里 **0 条非 GET**，所以那几条断言是 `it.skipIf` 挂起的 —— 抓不到就永远不跑，
  **别把"测试全绿"读成"写链路已验证"**。
- **`getConciseTipTemplatePage` 那条候选也没有基准**：它只在**编辑页**挂载时发，
  抓基准那一轮走的是列表页（3 条里没有它）。所以那条能力的参数形态仍是**源码推导**。

真机写验证由**派单方统一跑**，清单见下。跑完把实际请求/响应回填到本节。

## 基准里那两条「外壳请求」不是页面契约

这一页的基准里有 3 条，其中两条是 app 外壳拉的、**本页没有发**：

```
GET /admin-api/org/sensitive/info?_t=<ts>
GET /admin-api/bpm/task/list-by-category?finished=1&pageNo=1&pageSize=10&_t=<ts>
```

它们出现在这一页的 `pagePath` 下，只是"抓的时候停在这一页"；别把它读成"意图列表页也调待办"。
测试里对它们只做"确实在基准里、且不是我们发的"这一条断言，不数条数。

## 基准到位后**仍然**没解决的

基准 2026-09-21 到位，读链路全绿了（列表 URL 逐字段、`module-type` 不存在、候选请求形态的一部分）；
下面这些**基准里没有**（0 条非 GET），或光有基准也判不了：

- **新建 / 修改的 body** 究竟是 `{ name, content, meaning, templateIdList }`，还是像提示词类型那样
  「GET 整包回写」—— 基准里没有 POST/PUT。编辑模式下 `formState` 是被 `formLoad` **整个替换**的，
  `getInfo` 还可能带回 `intentTemplateRelList` / `tipTemplateList` 两个响应专属字段，
  这三个字段会不会被原样 PUT 回去，只能靠真机确认。
- **`DELETE /system/intent/{id}` 的形态**（有没有 body / `_t`）—— 基准里没有 DELETE。
- **`getConciseTipTemplatePage`** 的参数形态：基准抓的是列表页，没有这条；
  "页面循环拉的第一页是 `isIntentRecognition=1&pageNo=1&pageSize=100`"仍是源码推导。
- `module-type` **不发**现在有硬证据（三页三条列表请求），已改成断言 `headers` 里**不存在**该键。
