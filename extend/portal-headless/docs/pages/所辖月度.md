## 参数契约

顺序**不是照表单控件顺序抄的**，是按 `convertFetchForm` 的**返回对象**推出来的
（`others/list.vue:178-189`）：

```js
rrList.convertFetchForm( data => {
  const form = omit(data, ['yearMonth'])
  const year = data.yearMonth ? data.yearMonth.format('YYYY') : ''
  const month = data.yearMonth ? data.yearMonth.format('MM') : ''
  return { ...form, year, month, signatory: data.signatory.join(','), status: data.status.join(',') }
})
```

`form = omit(data, ['yearMonth'])` 给的是 `name, year, status, creator, signatory, organizationCode`；
后面 `{ ...form, year, month, signatory, status }` 里 **`year`/`status`/`signatory` 是覆盖赋值**
（JS 对象展开保留**第一次出现**的位置），只有 **`month` 是新的、追加到最后**。⇒

`order → orderField → name → year → status → creator → signatory → organizationCode → month → pageNo → pageSize → _t`

| 参数 | kind | 说明 |
| --- | --- | --- |
| `name` | text | 协议名称，模糊匹配 |
| `year` | text | 四位年份。由 `splitPerfYearMonth()` 从年月拆出 |
| `status` | text | 协议状态，**多选**（数组或 `"1,2"` 都行，能力会 `join(',')`）。字典 `month_task_review_status`，**取值域未实测** |
| `creator` | text | 创建人，模糊匹配 |
| `signatory` | search | 审核人 id（多人逗号连）。**见下方「刻意偏离」** |
| `organizationCode` | text | 组织 id。**默认不发**（见下） |
| `month` | text | 月份，**两位补零字符串** `09`。⚠️ 与[状态变更](./状态变更.md)那个 1~12 的数字不是一回事 |
| `pageNo` / `pageSize` | number | 默认 `1` / `20` |

## ⚠️ 三个必须记住的差异

### 1. `organizationCode` 默认**根本不在 URL 上**

`form.organizationCode` 的初值是 **`null`**（不是 `''`），而且那个树选择器是 `is-disabled` 的
（用户改不了 ⇒ 永远 `null`）。platform 实例的 GET 参数过
`qs.stringify(merged, { allowDots: true, skipNulls: true })`，**`skipNulls` 会把 `null`
和 `undefined` 整个键丢掉**，而 `''` 会发成 `key=`。

⇒ 本能力的默认值是 `undefined`（不是 `''`），就是为了在 qs 那一层落成"键不存在"，
与浏览器一致。**这与[所辖年度](./所辖年度.md)正好相反**（那边初值是 `''`，键在、值为空）。

### 2. `month` 排在 `organizationCode` **之后**

半年参数顺序的直觉会以为 `month` 紧跟在 `year` 后面。不会 —— 它是唯一的追加键，
落在最后。基准 `[2]` 逐字印证：`…&signatory=<redacted>&month=&pageNo=…`。

### 3. `status` / `signatory` 必须在序列化**之前** `join(',')`

表单里它们是**多选**（`portal-hxr-dict-select multiple`、`portal-hxr-select-signatory multiple`），
到 URL 上却是一个逗号串。**别把数组直接交给 axios/qs**：那会序列化成
`signatory[0]=1&signatory[1]=2`，与浏览器不逐字一致。能力里的 `joinCsv()` 就是干这个的。

## ⚠️ 刻意偏离：`signatory` 的默认值

基准 `[2]` 里 `signatory` 是**当前登录用户的 id**（已脱敏成 `<redacted>`）—— 页面的
`form` 初值写的是 `signatory: [userStore.state.id]`，**页面替用户把「审核人 = 我」填好了**。

无头 SDK **不知道调用者是谁**（凭据在 `createPortalRequest` 创建时绑定，能力读不到），
所以本能力的默认值是**空串 `''`**：键在、值为空，语义从「只看我审核的」变成「不限审核人」。

**这是刻意的，不是漏写。** 要复刻页面的行为：

```ts
// 1) 先拿自己的 userId
const me = await sdk.base.getUserInfo()          // 能力 id: base-user-info
// 2) 再把它当筛选条件传进来
await cap.listMonthAgreementsOthers({ signatory: String(me.userId) })
```

测试里有两条专门盯这件事：一条断言**基准里的 `signatory` 非空**，一条断言**本能力默认发空串**。
逐字段比较里 `signatory` 的值会被归一成 `<uid>`（键的**位置**照旧参与比较），
但那个归一**不会**掩盖这两条 —— 否则就成了恒真断言。
