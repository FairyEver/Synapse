# 理赔配置

## 1. 能力定义

- 菜单归属：门户 → 系统设置 → 销售设置 → 理赔配置。
- 页面路径：`/dashboard/sale/setting/claim-setting/list`。
- 页面权限：`/dashboard/sale/setting/claim-setting`。
- module-type：`60`。
- 请求实例：所有本页请求使用 Portal platform（`VITE_ZHDJ_PLATFORM_API`）。
- 按钮权限：新建 `setting:claim-setting:create`，编辑 `setting:claim-setting:edit`，原因维护 `setting:claim-setting:reason-maintain`，删除 `setting:claim-setting:delete`。
- 页面可达子页：`[mode]/[id]` 新建/编辑页，以及从列表“原因维护”进入的 `reason/[id]`。后端虽然还提供单条理赔原因 get/create/update/delete，但 Portal 页面没有调用，不纳入 SDK。

对应 SDK 能力：

| capability | 作用 | 写入 |
| --- | --- | --- |
| `sale-claim-setting-list` | 分页查询理赔配置 | 否 |
| `sale-claim-setting-get` | 查询编辑/原因维护使用的配置详情 | 否 |
| `sale-claim-setting-category-list` | 按理赔类型加载品类树 | 否 |
| `sale-claim-setting-reason-list` | 按理赔类型加载原因 | 否 |
| `sale-claim-setting-prepare-create` / `sale-claim-setting-create` | 准备并新建理赔配置 | 后者是 |
| `sale-claim-setting-prepare-update` / `sale-claim-setting-update` | 准备并编辑理赔配置 | 后者是 |
| `sale-claim-setting-prepare-remove` / `sale-claim-setting-remove` | 准备并删除配置 | 后者是 |
| `sale-claim-setting-prepare-save-reasons` / `sale-claim-setting-save-reasons` | 准备并覆盖保存全部理赔原因 | 后者是 |

## 2. 参数契约

### 列表、详情和品类树

列表页没有启用理赔类型筛选，Portal 公共列表仍发送空排序字段和分页参数：

```json
{
  "order": "",
  "orderField": "",
  "pageNo": 1,
  "pageSize": 20
}
```

请求为 `POST /admin-api/claim/claim-config/page`，响应是 `{ list, total }`；`pageSize` 只接受 Portal 全局选项 `10/20/50/100`。

- `GET /admin-api/claim/claim-config/get?id=<id>` 返回详情。Portal 会把后端 `categoryId` 的逗号字符串拆成 `categoryId` 数组；SDK 的 `get` 也返回这个页面表单形态。
- `GET /admin-api/claim/claim-config/categories?claimType=<value>` 返回当前理赔类型可用的品类树。没有 `claimType` 时 Portal 清空树且不发请求，SDK 返回空数组。
- `claimType` 是 platform 字典 `claim_type` 的 value，应使用已有 `base-dict-get` 获取标签和候选；不能凭印象把名称提交给后端。
- 品类节点的提交值是 `catId`，不是 `catName`、`label` 或节点名称；SDK保留 Portal `mapTree` 补出的 `key=catId`。

### 理赔配置表单和提交

编辑页的表单规则：

| 字段 | 页面规则 | 请求含义 |
| --- | --- | --- |
| `id` | 新建为空；编辑必须保留当前详情 ID | 只在编辑 PUT 中提交 |
| `claimType` | 必填，平台字典 value | 理赔类型 |
| `categoryId` | 多选品类 ID 数组，可为空 | 提交时各项转字符串并用逗号连接；空数组发送空字符串 |
| `startDays` | 可空，整数，0~999 | 发货后开始理赔天数，单位天 |
| `endDays` | 可空，整数，0~999；输入框最小值为 `(startDays ?? 0) + 1` | 发货后结束理赔天数，单位天 |

Portal 的 `customSubmit` 只构造四个字段：

```json
{
  "claimType": 1,
  "categoryId": "59,66",
  "startDays": 1,
  "endDays": 7
}
```

- 新建：`POST /admin-api/claim/claim-config/create`，请求体不含 `id`。
- 编辑：`PUT /admin-api/claim/claim-config/update`，请求体在上述字段外带当前 `id`。
- 删除：`DELETE /admin-api/claim/claim-config/delete?id=<id>`。
- 新建、编辑、删除后端都返回 `true`；SDK 只接受 `true`，但 `true` 只是业务回执，不是写后详情。创建没有页面消费的新 ID，不能从 `true` 猜测新记录。
- 后端还会校验理赔类型合法性、类型不可重复、时间范围和品类 ID格式；SDK只复刻页面可观察的表单校验，不绕过后端校验。

### 理赔原因维护

原因维护页进入时先调用配置详情取得 `claimType`，再调用：

```text
GET /admin-api/claim/claim-reason/list?claimType=<claimType>
```

保存时发送：

```json
{
  "claimConfigId": 11,
  "claimType": 1,
  "reasons": [
    { "id": 21, "content": "破损" },
    { "id": null, "content": "少件" }
  ]
}
```

请求为 `POST /admin-api/claim/claim-reason/save`。页面和后端共同约束原因数量为 1~20 条、文本非空且最多50字符；Portal 还会按原文本拒绝重复原因。后端保存是覆盖式：按 `claimType` 删除旧原因后按当前顺序重建，不能把它当成按 ID 的局部更新，也不能用空数组清空。

## 3. 逐字段基准

| 字段 | 页面含义 | 空值/归属 |
| --- | --- | --- |
| `id` | 理赔配置主键 | 当前列表/详情记录 ID；编辑、删除、原因维护使用 |
| `claimType` | 理赔类型 | `claim_type` 字典 value；后端按租户校验 |
| `categoryId` | 品类 ID 集合 | 列表原值是逗号字符串，详情表单是 ID 数组，提交再转回字符串 |
| `categoryName` | 品类名称快照 | 后端回填，只展示，不提交 |
| `startDays` | 理赔起始天数 | 单位天；表单可空，范围0~999 |
| `endDays` | 理赔结束天数 | 单位天；表单可空，范围0~999；有起始值时必须更大 |
| 品类节点 `catId` | 品类提交 ID | 取 `catId`，不能取 `catName` |
| 品类节点 `catName` | 品类展示名称 | 只展示 |
| 原因 `id` | 原因记录主键 | 覆盖保存会保留页面值，但后端按类型重建，不能依赖它做单条更新 |
| 原因 `content` | 理赔原因文本 | 1~50字符，非空；不能有原文本重复项 |

`app/portal/views/dashboard/sale/setting/claim-setting/list.vue`、
`[mode]/[id].vue`、`reason/[id].vue`、`constants.js` 和公共列表/表单模块；销售后端
`ClaimSettingController`、`ClaimSettingServiceImpl`、`ClaimSettingSaveReqVO`、
`ClaimSettingRespVO`、`ClaimReasonController`、`ClaimReasonServiceImpl`、
`ClaimReasonSaveReqVO`、`ClaimCategoryTreeRespVO`。

## 4. 操作步骤与证据

1. 调用 `base-dict-get({ dictType: "claim_type" })`，使用字典 value 选择理赔类型；不要把标签当请求值。
2. 调用 `sale-claim-setting-list`，按 `total` 翻页并保留目标行完整字段。
3. 新建或编辑时，按当前 `claimType` 调用 `sale-claim-setting-category-list`；从树节点 `catId` 组成 `categoryId` 数组。
4. 调用 `sale-claim-setting-prepare-create` 或 `sale-claim-setting-prepare-update`，检查时间关系和生成的逗号字符串。用户取消时只丢弃草稿；确认后把同一草稿交给对应写能力。
5. 删除先调用 `sale-claim-setting-prepare-remove`，明确提示会连带删除该理赔类型的原因；确认后调用 `sale-claim-setting-remove`。
6. 原因维护先调用 `sale-claim-setting-get` 和 `sale-claim-setting-reason-list`，编辑为1~20条后调用 `sale-claim-setting-prepare-save-reasons`；取消不发请求，确认后调用 `sale-claim-setting-save-reasons`。
7. 新建、编辑、删除和原因覆盖保存成功、超时或响应丢失后，都要重新读取列表/详情/原因列表逐项核对；不能只凭 `true` 或 HTTP 成功提示报告已生效。

离线证据由 `test/sale-claim-setting.test.ts` 和 AI 说明契约提供，覆盖页面路径、四个按钮权限、platform实例、列表排序/分页、详情品类转换、品类前置短路、表单时间关系、原因数量/重复/长度、prepare → submit → cancel 和坏回执。当前尚未在真实测试环境执行本页列表、详情、品类树、新建、编辑、删除、原因查询、原因保存及写入后的回查闭环；该缺口保持如实记录。
