### 2.1 ★ 两处「一个控件产两个字段」

这是本流程与另外两条线最直观的形状差别，两处都容易做错：

**(a) 时间段 → `startTime` / `endTime`**

`a-range-picker` 的 `value-format="YYYY-MM-DD HH:mm:ss"`，
`handleTimeRangeChange(dates)` 把它拆成两个字段。后端 `@DateTimeFormat(pattern =
FORMAT_YEAR_MONTH_DAY_HOUR_MINUTE_SECOND)` 也是这一个格式。**只认这一种写法**：
实测把时间写成 ISO（`2026-10-01T09:00:00`）会被后端拒：
`Text '2026-10-01T09:00:00' could not be parsed at index 10`。

两条先后校验，**判据相同**（页面与后端各一份）：

| 位置 | 判据 |
| --- | --- |
| 页面 `validateTimeRange` | `end.isBefore(start) \|\| end.isSame(start)` → 拒绝 |
| 后端 `validateTimeRange` | `!(endTime.isAfter(startTime))` → `exception("结束时间必须大于开始时间")` |

⇒ **结束必须严格晚于开始，相等也不行。** SDK 的 `assertTimeOrder()` 逐字复刻，在发请求之前跑。

⚠️ 顺带实测：**「结束早于开始」`getTemporaryRequiredStartUserSelectTasks` 不拦**
（那条校验只在 `create` 里）。所以只靠后端的话，用户要走到最后一步才知道填错了。

**(b) 申请人 → `staffId` / `staffName`**

这是 `docs/process-forms.md` §5.3 第 2 条说的那种「载荷不是表单字段直传」。
逐字来自 `common/index.js` 的 `buildVehicleUsageSubmitData()`：

```js
const selectedUser = userList.find(item => Number(item.value) === Number(formState.applicantId))
if (!selectedUser || selectedUser.disabled || !(selectedUser.staffId || selectedUser.id)) return null
return {
  staffId: selectedUser.staffId || selectedUser.id,   // ← 不是 applicantId
  staffName: selectedUser.name || selectedUser.realName,
  reason, startTime, endTime, destination,
  remark: formState.remark || '',
}
```

三个必须记住的性质：

1. **`staffId` 是字符串。** `getStaffByOrgPage` 返回的 `staffId` 序列化成 `"1163"`，
   页面原样发（抓包实测 `"staffId":"1163"`）。SDK 也发字符串。
2. **选不到人 ⇒ 整个载荷为 `null`**，于是 `canRefreshVehicleUsageApproval()` 为假、
   页面**连审批人节点都不去问**。
3. **空备注是 `''`，不是 `undefined`**（`formState.remark || ''`）。

⚠️ `staffName` **后端会用 `staffId` 自己重查并覆盖**
（`VehicleUsageApplicationServiceImpl.getStaffNameById()` → `application.setStaffName(...)`），
所以填错不会造成数据错，但为了逐字段一致仍然要发。

### 2.2 ★★ 页面上那一次挂载请求是**注定 400 的**，SDK 不发（一处刻意的偏离）

`getTemporaryRequiredStartUserSelectTasks` 的参数是 `@Valid VehicleUsageApplicationCreateReqVO`，
而它继承的 `VehicleUsageSubmitReqVO` 上写着 `@NotBlank reason` / `@NotNull startTime` /
`@NotNull endTime` / `@NotBlank destination`。**只读实测**（2026-09-21）：

```text
全空（浏览器基准里那条，逐字节） → 400 请求参数不正确:结束时间不能为空
只缺 reason                    → 400 请求参数不正确:用车事由不能为空
只缺 startTime/endTime         → 400 请求参数不正确:开始时间不能为空
只缺 destination               → 400 请求参数不正确:用车目的地不能为空
全齐                            → 200，3 个节点
```

而页面挂载时 `refreshApprovalTasks()` 用的闸是 `canRefreshVehicleUsageApproval()`
——**只要选得到人就发**，不要求另外四个字段。抓包证实它确实发了（body 里
`reason`/`startTime`/`endTime`/`destination` 全是空串），也确实被拒了；
页面上那三个「审批人」下拉因此落在「获取审批候选人失败 / 点击重试」的状态。

⇒ SDK 把这个闸**抬到后端的实际要求**：`assertApplicantResolvable()`（页面的闸）
**加** `assertDataComplete()`（字段齐全），两个都过才发请求。与请假的 `assertDraft()`
同一条理由：**能让它红在第一个字节之前，就红在第一个字节之前**。
代价是「SDK 不会重放基准里那一条 body」—— 那条 body 是**被后端拒绝的**，
重放它不是忠实，是照抄一个错误。

### ★ 提交载荷是怎么抓到的

**不是**靠点「提交」（那会给真人推待办）。走的是「查看审批流程」：
它调的 `POST /bpm/process-instance/preview` 的 body 里 `variables`
**逐字段就是**提交载荷。填好表单后抓到的原文：

```json
{"processDefinitionKey":"vehicle_usage_application",
 "variables":{"staffId":"1163","staffName":"姚淼鑫",
   "reason":"SDK-TEST-baseline 用车事由（浏览器基准抓取，不会提交）",
   "startTime":"2026-09-22 09:00:00","endTime":"2026-09-22 15:00:00",
   "destination":"SDK-TEST-baseline 目的地","remark":""},
 "startUserSelectAssignees":{"Activity_0yx86ms":[null],"Activity_0q8l1yc":[null],"Activity_0viq4cx":[null]},
 "copyUserIds":[]}
```

它一次给出四件事：① 时间段的**一个控件产两个字段**；② 三个节点的 **id**
（页面自己也是按 id 发的）；③ `copyUserIds` 是**预览组件自己的参数**、**不是表单字段**
（create 的 body 里没有它）；④ 空备注仍是空串。

`create` 的 body = 上面那 7 个键 + `startUserSelectAssignees`（`handleSubmit` 的最后一步
是 `{ ...submitData, startUserSelectAssignees }`）。**create 的真实请求没抓到**
（抓它必须点一次提交），所以这一层是**同源推断** —— 与另外两条线的基准做法一致，
且另有 SDK 侧的冒烟佐证（§七）。

### 三条顺带记下来的现场

1. **页面在这条路由上不发 `module-type`**：`getStaffByOrgPage`、
   `getTemporaryRequiredStartUserSelectTasks`、`process-definition/get` 的请求头里都没有它。
   与 `resolveModuleType()` 判定一致（规则表里没有 `/dashboard/flow/` 前缀）。
2. **审批人候选走的是另一套 http 实例**：头里多一个 `Authorization`、少一个 `Accept-Language`。
3. **`a-range-picker` 的输入框是 `readOnly`**：抓包时只能点面板
   （`.ant-picker-cell[title=…]` → `.ant-picker-time-panel-column:nth-child(1|2|3) > li` →
   `.ant-picker-ok button`），驱动配方见 `tools/baseline/README.md` §2。

## 四、★★ 申请人：页面**自己的数组入口已经被后端关掉了**

这是本轮最有价值的一条实测，也是 `docs/process-forms.md` §5.3 第 3 条警告的**升级版**：
那个文件说「无头不能照抄按组织全量拉人」，而实测发现 —— **不止是不该抄，是根本抄不动了**。

### 4.1 旧入口的现场

把页面当初算出来的那 10 个二级组织 id 原样 POST 给数组入口【实测】：

```text
POST /org/staff/getStaffByOrg   body: ["35","36","37","71","467","3997","4026","4094","4099","4111"]
→ code 500, ret FAIL, msg: 员工超过1000条，请升级客户端并使用分页选择器，不支持全量数组加载
```

后端源码对得上（`Mall_Platform_Java` 那一支的 `HrStaffServiceImpl`）：

```java
public List<HrStaffDTO> getStaffByOrgLegacyHttp(List<Long> organizationIds) {
    IPage<HrStaffDTO> page = hrStaffDao.selectStaffByOrgLegacyPage(new Page<>(1, 1000), req);
    requireCompleteStaffPickerLegacy(page.getTotal());   // total > 1000 → legacyRen(「员工超过1000条…」)
    return page.getRecords();
}
```

（⚠️ 本项目 `CLAUDE.md` 指定的后端仓库 `Mall_Platform_Java_Dev` 里**没有**这段守卫，
说明它落后于测试环境上跑的那一版 —— 又一处「以实测为准」。）

### 4.2 页面上真正在跑的那一条

```jsonc
POST /admin-api/org/staff/getStaffByOrgPage
{"organizationIds":["35","36","37","71","467","3997","4026","4094","4099","4111"],
 "includeDescendants":true,"keyword":"","pageNo":1,"pageSize":20,"selectedStaffIds":[1163]}
```

- `organizationIds` 来自页面 `getVehicleUsageOrganizationRoots(organizationStore.state)`：
  把组织树的每个**顶层节点**的 `children` 摊平（没有 `children` 就取自己），去重、去空。
  实测本环境顶层只有 `34 沃德辰龙`，它有 10 个孩子 → 就是上面那 10 个（序列化成**字符串**）。
- 页面发了 3 次，只有 `selectedStaffIds` 不同：`[1163]`（回显当前登录员工）→ `[1163]` → `[]`（初次加载）。
- 后端 `HrStaffByOrgPageReqDTO`：`organizationIds` 是 `@NotEmpty @Size(max=50)`、
  `includeDescendants` `@NotNull`、`selectedStaffIds` `@Size(max=100)`；
  继承的 `HrStaffPickerPageReqDTO` 是 `pageNo @Min(1)` / `pageSize @Min(1) @Max(100)` / `keyword @Size(max=100)`。
  **实测**：`pageSize=101` → `400 最大不能超过100`；`pageSize=-1` → `400 最小不能小于1`；空数组 → `400 不能为空`。
- 响应形状：`{ list: HrStaffPickerOptionDTO[], total, selectedItems }`，
  每行 `{ id, staffId, staffCode, username, name, realName, status, organizationId, organizationName }`
  （**`id` 与 `staffId` 同值**，都是员工 id，都是字符串）。
- 页面 `mapVehicleUsageUserOptions()` 只保留 `status ∈ [1,4,5]` 的行
  （`ACTIVE_STAFF_STATUS_LIST`），并合成 `label = 姓名(工号)`、`value = Number(id || staffId)`。

### 4.3 SDK 因此暴露的两条

| 能力 | 做什么 |
| --- | --- |
| `vehicle-application-applicant-scope` | 页面 `ensureScope()` 那两步：`getRoleOrganizationTree` + 摊平。**复刻页面那条「超过 50 个根组织就报错」的守卫** |
| `vehicle-application-applicant-picker` | 包 `getStaffByOrgPage`，参数与守卫逐条对齐后端注解；`pageSize` 默认 20、上限 100 在**本地**就拦 |

### 4.4 候选入口（`lookup`）登记成什么样，以及**为什么 `organizationIds` 那条留空**

`src/catalog` 会校验「任何声明了 `lookup` 的能力，它指向的目标能力必须真的有一个同名参数
作为候选入口」（`validateLookups`，被 `test/attendance-archive-sheet.test.ts` 里
`expect(sdk.catalog.validate().lookups).toEqual([])` 钉住）。三处的最终登记：

| 参数 | `lookup` 指向 | 为什么 |
| --- | --- | --- |
| `prepare.staffId` / `submit.staffId` | `vehicle-application-applicant-picker`（`keywordParam: 'keyword'`） | 申请人（**staffId**）的候选就是按组织分页查出来的那批人，「选择器」= 候选入口 |
| `submit.startUserSelectAssignees` | `vehicle-application-approver-search`（`keywordParam: 'keyword'`） | 审批人（**userId**）的候选，必须带关键字（D6） |
| `applicant-picker.organizationIds` | **（刻意留空）** | 见下 |

**`organizationIds` 为什么没有 `lookup`（这不是漏登记，是它本就不该有）**：

- 组织 id 的唯一来源是 `GET /org/organization/getRoleOrganizationTree`，
  那条接口**不接受任何参数** —— 没有关键字、没有分页，一次返回整棵树。
- 因此 `vehicle-application-applicant-scope` **一个参数都没有**，它没法扮演
  「候选入口」这个角色（`lookup` 表达的语义是「给我一个关键字，还你一页候选」）。
- 候选关系确实存在，但它是**两步**的：「先调 `applicant-scope` 拿一组 id，
  再把它们填进 `organizationIds`」。这与 `lookup` 的语义不同，
  **指一个不合适的入口只会把调用方引进死胡同**。
- ⇒ 引导写进参数描述里（读的人照描述走一样到得了），`lookup` 留空。

⚠️ 这一处**曾经写错过**（三处 `lookup` 全指向 `applicant-scope`），是被目录一致性校验
抓出来的。`test/vehicle-application.test.ts` 现在有两条测试钉住它：
一条逐处核对 `lookup` 的落点**真的存在于目标能力上**，一条明确断言
`organizationIds.lookup` **是 `undefined`**（免得后人"顺手补上"）。

### 4.5 长选项：这里**不是**关键字强制的那一类，理由要写清楚

设计 D6 / H35 说「长选项参数必须先要关键字」。**入口不是关键字的那种不能硬套**：
本控件的第一入口是**组织范围**（页面的搜索只是可选的收窄），而
`getStaffByOrgPage` 是**分页**接口 —— 一次最多 100 条、默认 20 条。
「一次拉 4500 人」在这里**从接口形状上就不可能发生**（后端 `@Max(100)`）。
⇒ 所以 `applicant-picker` **不强制 keyword，但强制分页**。
真正需要关键字强制的是**审批人候选**（§五）。

⚠️ SDK **不**替调用方把 `applicant-scope` 的 10 个根组织当默认值去**翻页翻到底**。
分页的边界由调用方自己按 `total` 决定。

## 五、审批人：3 个「发起人自选」，每个**恰好 1 人**

`POST /hr/vehicle-usage-application/getTemporaryRequiredStartUserSelectTasks`
（body 就是提交载荷）【实测，原样记进基准文件】：

```jsonc
{"code":0,"ret":"SUCCESS","data":[
  {"id":"Activity_0yx86ms","name":"发起人自选","approvalMode":"SINGLE","approvalModeName":"单人审批",
   "executionMode":"SINGLE","completionRule":"ALL_APPROVED","minSelectCount":1,"maxSelectCount":1,
   "selectionOrderRequired":false,"approvalDescription":"仅可选择一名审核人；该人员通过后节点通过"},
  … Activity_0q8l1yc 同上 …
  … Activity_0viq4cx 同上 …]}
```

BPMN 原文完全吻合：`开始 → 发起人自选 → 发起人自选 → 发起人自选 → 结束`，
三个 `userTask` 的 `flowable:candidateStrategy` 都是 **35 = `START_USER_SELECT`**，
而且 **没有网关、没有 `${...}` 条件表达式**（请假有两个网关条件，这里一个都没有 ——
所以这条流程**没有**「按条件少打扰一个人」这种余地）。

⚠️ **三个节点的 `name` 一模一样**（都叫「发起人自选」），**只有 id 不同** ——
调用方不能按名字选，必须按 `id`。

⚠️ **两条接口名字的坑**（`docs/process-forms.md` §5.3 第 1 条）：
后端 `VehicleUsageApplicationController` **两个都写了**
（`/getRequiredStartUserSelectTasks` 与 `/getTemporaryRequiredStartUserSelectTasks`，实测都能通），
**前端用的是后者**。SDK 跟前端走，用后者。

⚠️ `definition()` 返回的 `startUserSelectTasks` 这次**有值**（那三个 id）—— 但它是
**流程定义级**的，与 `prepare` 按当前载荷算出来的节点是两回事，**不要拿它代替 prepare**。

### 5.1 审批人候选的来源（长选项，**必须带关键字**）

页面 `common/libs/flow-form/index.js` 的 `getStartUserSelectTasks()` 是
`GET /system/user/simple-list`（**全量**）。抓包里实测翻成
`/system/user/simple-page?pageNo=1..9&pageSize=500` = **9 页 × 500 = 4500 人**，
与请假那条线的预览组件同一个数量级。**无头下不能照抄** →
`vehicle-application-approver-search` 复用通用审批那套：`GET /system/user/simple-page`，
**必须给 keyword 或 deptId**，拒 `pageSize = -1`。

⚠️ 这里是 **userId**（`/system/user/simple-page` 的 `id`，如 `18243`），
与申请人的 **staffId**（如 `1163`）**不是一个 id 空间**。混用会选到错的人。
`test/vehicle-application.test.ts` 与冒烟脚本都把这条写在显眼处。

### 5.2 ⚠️⚠️ 审批人**绝对不要选发起人本人** —— 本流程比另外两条线危险得多

后端 `BpmTaskServiceImpl`（源码直读）：

```java
Long startUserId   = NumberUtils.parseLong(instance.getStartUserId());
Long taskAssigneeId = NumberUtils.parseLong(task.getAssignee());
if (startUserId != null && startUserId.equals(taskAssigneeId)) {
    autoApproveReqVO.setReason("流程发起人与审批人相同，自动审核通过");
    approveTask(taskAssigneeId, autoApproveReqVO);
}
```

两边比的都是 **userId**。

**为什么本流程特别危险**：请假的审批人是 BPMN 写死的（选不了），通用审批只有 **1 个**自选节点，
而**用车有 3 个**。选错一个 → 那个节点当场通过、**越过真人审批**；
**三个都选到发起人本人 → 整条流程在 `create` 返回之前就走完**，
`cancel-by-start-user` 必然报「流程取消失败，流程不处于运行中」，
于是**永久留下一条撤不掉的单据**（测试环境里已经有 3 条这样的遗留单据）。

⇒ SDK 把判据做成**纯函数** `findSelfApproverConflicts()` / `assertApproversNotSelf()`，
**不在 `submit` 里自动拦**：页面不拦（人自己选得明白），而 `submit` 是「忠实复刻页面」的地方。
拦它的是 `smoke/vehicle-application.mjs` 的**提交前拒绝**，以及任何愿意调用这个纯函数的调用方。
`test/vehicle-application.test.ts` 里有一条明确的测试钉住「`submit` 不拦」这件事本身
—— 免得有人以为它有保护。

【6】  ├─ assertApproversNotSelf(tasks, assignees, 自己的 userId)      ★ 提交前必做

光看「提交成功」说明不了那个人的待办箱里真的进过东西。

### 6.1 撤销：`RespVO` 这次**有** `processInstanceId`

与通用审批 / 请假**不同**：`VehicleUsageApplicationRespVO` 有 `processInstanceId` 字段，

所以它只被流程监听器用到、页面上走不到。撤销一律走通用的

## 九、尚未覆盖 / 不确定

- **「查看审批流程」预览**（`portal-hxr-flow-process-preview`，打
  `/bpm/process-instance/preview`）**没做成能力**。它是**只读的展示件**，不影响能不能提交。
  ⚠️ 但它自己 `GET /system/user/simple-list` +
  `simple-page?pageNo=1..9&pageSize=500` **无关键字拉了 4500 人**，就为了把
  BPMN 里的审批人解析成名字 —— 与请假那条线同一处（设计 D6 / H35）。
  ⚠️ 冒烟脚本**确实用了**它那条 `getWorkflowPath`（不是 `preview`）来给「打扰了谁」取证，
  但那是脚本自己用 HTTP 管道打的，不是能力。
- **「加载更多申请人」那条路径没有浏览器侧证据**：`pageNo > 1` 的翻页
  （`onPopupScroll` / `loadMore`）只有源码依据。SDK 的 `applicantPicker` 支持 `pageNo`
  正是照着源码做的。
- **首页那 20 条之后的候选没有实跑验证**：只读冒烟用 `keyword` 收窄到了 1 条。
  `pageNo=2` 的请求形状是从 `usePagedOptions.loadPage(page + 1, keyword, true)` 读出来的。
- **`PUT /update` 与 `DELETE /delete/{id}` 没做**：后端限定「只有已驳回状态（`status = 3`）
  才能改/删」（`VehicleUsageApplicationServiceImpl` 的两条状态判断），而页面上的编辑分支
  **前端是注释掉的**（`handleSubmit` 里 `isEditMode` 那三行是注释，`apiSubmit` 写死成 `/create`），
  所以**页面上根本走不到这两个入口**。要造一条「已驳回」的单据得先让真人去驳回 ——
  那是第三方的动作，本轮做不到。实现一个页面上不存在、又验证不了的写操作，
  不叫「完整」，叫「多做了没验过的东西」。
- **`VehicleUsageApplicationService.cancelApplication`（service 层那个）没验过**：
  它没有 Controller 映射（实测 `/cancel/{id}` 404），只能被流程监听器之外的东西调用，
  **页面上走不到**。SDK 不把它做成能力。
- **`GET /hr/vehicle-usage-application/page` 分页与导出没做**：页面**没有任何地方调它们**
  （全仓库 grep 只有 `form/031` 那几个调用点，且都是 create / get / required-tasks）。
  要「查用车记录」，本能力给 `detail(id)` 与 `myInstances()` 两条**页面上真的走了**的路。
- **手机端表单（`page/mobile/edit`）没单独做**：它是同一套 `common/index.js`、
  同一个 `create` 接口，字段与校验与 PC 端一致。SDK 是页面无关的，所以**不分端**。
- **【推断】`status` 的语义边界**：`0=待提交` 这个值在页面上其实是**不可达的中间态**
  （一建单流程就起了），但后端没有在 `create` 里 setStatus。是**忘了**还是有意的，
  从源码看不出来 —— 本轮只如实记录了「实测是 0」。
- **【推断】`selectedItems` 的行为没实跑**：后端 `getStaffByOrgPage` 在
  `selectedStaffIds` 非空时才额外回一份 `selectedItems`，页面用它做「已失效或无权限」的
  回显（`mapMissingOption` → `disabled: true`）。SDK 原样透传这个字段，
  但**没有**复刻那个 `disabled` 状态机 —— 那是控件的行为，不是接口语义。

- vehicle-application-applicant-scope：把 organizationIds 原样传 applicant-picker；不把整棵树当人员结果。
- vehicle-application-applicant-picker：用 name \|\| realName 和 staffCode \|\| username 展示消歧；保留 staffId \|\| id 作为员工标识。 不传 organizationIds 时 SDK 自动查权限根组织；pageSize 上限 100、selectedStaffIds 上限 100。
- vehicle-application-approver-search：展示姓名与工号给用户消歧；保存选中行 id 作为 userId。 keyword 或 deptId 至少给一个；pageSize=-1 被拒绝。
- vehicle-application-prepare：给用户核对 payload 的业务值；按 tasks[].id 建立 startUserSelectAssignees 的键，人员来自候选查询，人数、去重与顺序服从任务规则。 准备只读，不建单、不保留名额、不发送待办；任何草稿变更后应重新准备。
- vehicle-application-submit：保存业务 ID、流程类型及原 requestId；回读业务字段并查询流程实例确认已创建。 取消属于用户改变决定时的可选操作，不是正常提交后的必做步骤。
- vehicle-application-detail：展示本次申请的业务字段与附件；原请求业务 ID 必须单独保存，详情不保证能提供流程实例 ID。 状态应区分业务单据与流程实例；需要可撤回性时查 my-instances，而不是只看详情 status。 真实新提交后业务 status 仍可能为 0（待提交），流程已在运行；不能以 0 判断提交失败。
- vehicle-application-my-instances：本接口没有自动限定 vehicle_usage_application，按 processDefinitionKey 与 String(businessKey) 双重匹配；字段缺失时不可把跨业务重号当可靠确认。 页码默认 1、每页默认 20；逐页核对 total，列表局部不能用于全量汇总。
- vehicle-application-cancel：只取消自己发起且仍运行的流程；保留业务记录，不代表删除历史。 查实际流程 status=4 才认定撤销完成；会议预定则核对占用时间段消失。

本轮以 `test/ai-contract-workflow.test.ts` 核对真实 SDK 描述，复用既有浏览器基准，不重放真实写操作。逐项验证与缺口见 `docs/ai-contract-workflow-evidence.md`。
