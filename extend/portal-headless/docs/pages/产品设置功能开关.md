# 产品设置功能开关

页面路径：`/dashboard/product/setting/business-manage/function-use/list`。

菜单归属是 `系统设置 → 生产设置 → 业务管理 → 功能开关`。这里的“生产设置”是 Portal 保留的“系统设置”子菜单，不是范围外的独立生产业务菜单。

## 页面能力定义

| 页面动作 | SDK 能力 / 方法 | Portal 请求 |
| --- | --- | --- |
| 查询功能开关 | `product-setting-function-use-list` / `productSettingFunctionUse.list` | `GET /config/functionUse/list` |
| 准备启用/停用 | `product-setting-function-use-prepare-switch` / `productSettingFunctionUse.prepareSwitch` | 本地按当前status反转，不发请求 |
| 确认启用/停用 | `product-setting-function-use-switch-status` / `productSettingFunctionUse.switchStatus` | `GET /config/functionUse/openOrClose` |

请求使用 `product` HTTP 实例，补 `devicetype=PC`，不发送 `module-type`。菜单权限为 `/dashboard/frame/business/function-use`；页面声明查询权限 `management:function-use:query`，操作按钮还要求 `management:function-use:submit`。SDK不绕过页面或服务端权限。

列表没有筛选表单、分页、详情、删除或导出动作。Portal的 `customLoad` 只发送 `order=""`、`orderField=""`，最终把数组交给表格；SDK返回非分页数组。

## 参数契约与提交规则

Portal列表行字段为：

```json
{
  "id": "租户覆盖记录ID或null",
  "functionCode": "功能编码",
  "functionName": "功能名称或null",
  "remarks": "备注或null",
  "status": 0
}
```

页面按钮显示条件是 `permissionCheck('management:function-use:submit')`。用户点击后先弹出确认框；取消不发请求，确认才按下面四个参数发送GET：

```json
{
  "id": "当前行id，可为null",
  "functionCode": "当前行functionCode",
  "functionName": "当前行functionName",
  "status": 1
}
```

`status`是绝对目标状态：当前为 `1` 时提交 `0`（停用），当前为 `0` 时提交 `1`（启用）。SDK的 `prepareSwitch` 只做同样的反转和字段校验，返回的 `draft`必须在用户确认后原样交给 `switchStatus`。

`id=null`是页面正常分支，不是缺失数据：Java列表把尚未建立当前租户覆盖的系统功能置为 `id=null、status=0`；提交启用时，`openOrClose`按当前租户新建覆盖记录。`id`非空时，Java按ID更新状态。不要把null替换成系统记录ID或任意新ID。

## 逐字段基准

| 字段 | 含义 |
| --- | --- |
| `id` | 当前租户功能覆盖记录ID；系统功能尚无当前租户覆盖时为null。 |
| `functionCode` | 功能编码；后端校验非空，也是新建租户覆盖的业务键。 |
| `functionName` | 功能名称；页面展示并随启停请求透传，可为null。 |
| `remarks` | 功能备注；只读展示，启停请求不发送。 |
| `status` | 当前状态：`0`停用、`1`启用；prepare会生成相反的目标值。 |
| `draft.id` | 提交目标记录ID；必须原样保留列表行的null或非空ID。 |
| `draft.functionCode` | 提交给Java `openOrClose` 的非空功能编码。 |
| `draft.functionName` | 提交时透传的功能名称，可为null。 |
| `draft.status` | 绝对目标状态：`0`停用、`1`启用。 |
| `previous` | prepare时的ID、功能编码、名称和当前状态摘要，不是后端回执。 |

写入返回值是 `true`，只表示请求没有抛错；Java成功包络不返回更新后的记录。SDK必须再调用 `list()`，按同一 `functionCode` 找到行并核对最终 `status`。对于原先 `id=null` 的首次启用，还应确认回查得到非空租户覆盖ID。

## 操作步骤、权限和证据边界

1. 使用当前会话和当前租户调用 `list()`，保留目标行的完整 `id/functionCode/functionName/status`。
2. 对用户明确要启用或停用的行调用 `prepareSwitch({ current })`，用 `previous`生成确认信息；状态不是0/1或功能编码为空时不发请求。
3. 用户确认后把同一份 `draft`交给 `switchStatus`；用户取消则丢弃draft，不调用写接口。
4. 写请求成功或超时后调用 `list()`回查同一 `functionCode`。不要把 `true`直接解释为数据库状态已核实，也不要重复提交旧的 `id=null`草稿。
5. 页面没有独立取消接口；如用户要求恢复，必须基于最新列表行重新prepare并再次确认相反操作。

本轮逐页核对了Portal菜单、路由权限、query/submit权限、列表与确认源码、公共非分页加载实现、Java Controller/Service/Mapper/Entity、SDK请求和离线反证测试。尚未在真实测试环境使用浏览器会话执行查询、`id=null`首次启用、回查和反向停用闭环；因此真实写入证据仍是缺口。
