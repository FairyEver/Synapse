## 页面形态：**树 + 文档**，没有「查询」按钮

左侧不是表格，是一层一层的目录。触发请求的唯一方式是**进目录**：
挂载时（`parentId` 初值 0）、点面包屑、按 ESC 返回上级、点一个文件夹、打开「移动到」弹窗里的树，
打的都是**同一个接口** `GET /manager/knowledgeFile/list?parentId=`，只是 `parentId` 不同。

⚠️ 接口**没有分页**：`KnowledgeFileMapper.xml` 的 `findList` 是

```sql
select … from zhdj_knowledge_file where is_del = 0 and parent_id = #{parentId} order by `type`, `name`
```

一次给全该层，返回 `{list, isAdmin}`，**没有 `total`**。所以本能力**没有** `pageNo` / `pageSize`
（照抄隔壁列表页会凭空多两个参数，D20 会红）。排序是 `type, name`（文件夹在前、按名字），不是时间。

## 三处「用户做不到」的地方（能力里也不提供）

1. **「搜索文件」是个空壳。** `components/search-modal/index.vue` 的 `actionStart()` **函数体是空的**
   （`@search` 与 `@focus` 都调它），一个请求都不发。所以「搜索文档」在这一页上**用户做不到**
   ⇒ 能力里没有（conventions 第 28 条同一精神）。后端 `findList` 其实认一个**精确匹配**的 `name`
   （`dto.name != null and dto.name != ''` → `name = #{dto.name}`），但页面从不发它，本能力也不开放。
2. **根目录不能新建文档**：`list.vue:38-45` 在 `breadcrumbList.length === 1`（还在根）时把按钮
   disabled 掉并提示「请在目录内新建」。**后端没有这条限制** —— 本能力按后端的能力开放了
   `createFile({parentId: 0})`，但要知道那是页面上做不到的事。
3. **权限设置按钮只对 `isAdmin` 显示**（`item-render/index.vue:47` 的 `v-if="isAdmin"`）。
   接口本身不校验 —— 实测本账号 `isAdmin = false`，`getPermission` 与 `setPermission` 都照常成功。

## 写链路：`prepare`（只读）→ `submit`（真写）→ `cancel`（撤销）

知识库**没有审批流**（不像会议室 / 请假单那样走 BPM），所以 conventions 第 13 条里
「prepare 问后端这次要人工指定哪些审批人」这个职责在这两页上不存在。真实存在的是这条形状：

| 写 | prepare（只读） | submit | cancel |
| --- | --- | --- | --- |
| 新建 | `prepareCreate` → 读该层（查重名） | `createFolder` / `createFile` | **没有**，见下 |
| 重命名 | `listChildren`（给出当前名字） | `rename` | `cancelRename`（用旧名字再 update 一次）✅ 实测 |
| 移动 | `prepareMove` → 读**目标**层 | `move` | `cancelMove`（移回原父目录）✅ 实测 |
| 删除 | `listChildren`（确认这层是空的） | `remove` | **没有**，见下 |
| 权限设置 | `getPermission`（整单替换，必须先读） | `setPermission` | `cancelSetPermission`（旧值原样写回）✅ 实测 |

### 为什么「新建 / 删除」没有 cancel（读后端源码 + 实测）

`add` 做两件事：往 `zhdj_knowledge_file` 插一行（`audit_status = 2` 待审核）、
往 `zhdj_knowledge_change_record` 插一条 `audit_type = 1/4` 的待审记录。
之后**没有任何接口**能删掉那条记录或恢复文件行 —— `KnowledgeChangeRecordController` 只有
`list` / `audit` / `getChangeRecord/{id}` 三个映射，一个都不是「撤回」。唯一的出路是让审核人出决定。
`remove` 同理：它自己也只是**提一条待审记录**（`delete` 在 `KnowledgeFileServiceImpl` 里
把最新那条待审记录的 `audit_type` 改成 `3/6`，或另插一条），文件行仍在。

⇒ 这不是「没做」，是「做不出来」。`cancelCreate` / `cancelRemove` 在本能力里不存在。

### `remove` 的两条分支（**只实测到一条**）

`KnowledgeFileServiceImpl.delete` 有两条路：

- **最新一条变更记录还在待审** → 把那条记录的 `audit_type` 改成 `3/6` 然后 return（不再插新的）。
  ⚠️ **这条没有测到**（源码读出来的）。
- **否则** → 另插一条 `audit_type = 3/6` 的新记录，并把文件行打成待审核。✅ 实测到了（见下面的验证记录第 ⑩ 步）。
- 另外它**开头就检查这一层是否为空**：有子项就抛「该文件夹不为空，不能删除」，**不生成任何记录**。
  ⚠️ 这条也**没测到**（没在非空目录上试过）。

## 一条实测澄清：改名的可见性

我原先按源码写下「`list` 对非管理员会把待审的新名字换上去」。
**实测在「新建还没审就改名」这条路径上它不生效**：改名前后的两次 `listChildren` 都返回**旧名**，
新名字只出现在变更记录的 `newContent` 里。

原因是那条替换有三个条件（`KnowledgeFileServiceImpl.list`）：非管理员 + 记录
`audit_type ∈ {2 修改文件夹, 5 修改文档}` + 提交人是我。而 `update` 在「上一次是新建还没审」时
**把 `audit_type` 保留成 1**（源码里那句 `if (auditType != 1 && auditType != 4) setAuditType(2)`），
所以替换分支不触发。

⇒ **判「改名成没成功」只看变更记录的 `newContent`，不看 `listChildren`。** 能力实现里已按这条改写。

## ⚠️ `getPermission` 回显的 `isAllManager` **不可靠**（一定会踩的坑）

**后端从不更新 `zhdj_knowledge_file.is_all_manager` 这个列** —— `setPermission` 的三条分支里
一条都没有写它。而 `getPermission` 回显的 `isAllManager` 是**推出来的**：

```java
// KnowledgeFileServiceImpl.getPermission
result.put("isAllManager", knowledgeFile.getIsAllManager());   // ← 列里的旧值
if (角色权限行非空) { result.put("authRoleIds", …); result.put("isAllManager", 2); }
if (用户权限行非空) { result.put("authManagerIds", …); result.put("isAllManager", 3); }  // ← 无条件覆盖
```

而「全部用户」存的是 `manager_id = 0` 那一行，它的**数组**在出口被
`filter(kfm -> kfm.getManagerId() != 0)` 过滤掉了（所以 `authManagerIds` 是空数组），
但 `knowledgeFileManagers` 这个 list 本身**非空** ⇒ 仍然 `put("isAllManager", 3)`。

**实测（同一个节点 id 2044，连续三次读）：**

| 时刻 | `getPermission` 返回 |
| --- | --- |
| 刚新建 | `{"auditorId":null,"isAllManager":3,"authManagerIds":[18243]}` |
| `setPermission(全部用户)` 之后 | `{"auditorId":null,"isAllManager":3,"authManagerIds":[]}` ← **不是 1** |
| `cancelSetPermission` 写回旧值后 | `{"auditorId":null,"isAllManager":3,"authManagerIds":[18243]}` |

⇒ **「全部用户」与「指定用户但一个都没剩」在这个回显上长得一模一样。**

因此：**别拿它读「当前权限范围」**。要确认一次 `setPermission` 是否生效，看的是
①请求成功 + ②后端走的是你指定的那条分支（本能力按 `isAllManager` 决定发哪两个字段）。
`cancelSetPermission` 的 `previous` 也**必须**来自写之前那次 `getPermission`，
事后再回读一份来「恢复」是不可靠的。

- **「搜索文件」**：页面上的空壳（见上），没有接口可做。
- **`GET /manager/knowledgeFile/getInfo/{id}`**：后端有这个映射，**页面从不调它**，
  所以本能力也没做（conventions 第 28 条同一精神：页面到不了的东西不进能力）。
- **`findList` 的 `name` 精确匹配**：后端认，页面不发，本能力不开放。
- **角色候选**：`authRoleIds` 在页面上是通用的角色选择器（`portal-hxr-select-role-by-system`），
  SDK 里没有对应的检索能力，所以那个参数是 `kind: 'text'`，**没有 lookup** —— 角色 id 要调用方自己给。

## 基准对照（2026-09-21，`baseline/ai-knowledge.browser.json`）

基准只有 **7 条**，而且**全是 GET**。逐条列清楚哪条是页面契约、哪条不是：

| 页面 | 基准里的请求 | 是不是本页契约 |
| --- | --- | --- |
| 知识空间 | `GET /admin-api/manager/knowledgeFile/list?parentId=0&_t=<ts>` | ✅ 挂载时那条 |
| 知识空间 | `GET /admin-api/org/sensitive/info?_t=<ts>` | ❌ **app 外壳**发的（不在本页能力里） |
| 知识空间 | `GET /admin-api/bpm/task/list-by-category?finished=1&pageNo=1&pageSize=10&_t=<ts>` | ❌ **待办角标**（外壳） |
| 知识审核 | `GET /admin-api/manager/knowledgeChangeRecord/list?order=&orderField=&pageNo=1&pageSize=20&_t=<ts>` ×2 | ✅ 页面把它**发了两次**（同一条 URL） |
| 知识审核 | 上面那两条外壳请求各一份 | ❌ 外壳 |

**对照结论：基准与源码推导不冲突。** 两条页面请求与能力发出的 URL **逐字段一致（含键顺序）**：

```text
/admin-api/manager/knowledgeFile/list?parentId=0&_t=<ts>
/admin-api/manager/knowledgeChangeRecord/list?order=&orderField=&pageNo=1&pageSize=20&_t=<ts>
```

所以本页**没有** conventions 第 31 条那种「本地检出与线上不一致」要记。
（顺带被基准证实的两条：① 这一页**只有 `parentId` 一个业务参数**，没有 `order`/`orderField`/`pageNo`/`pageSize`；
② 两页**都不发 `module-type`** —— 7 条的 `headers` 里都不存在这个键。）

⚠️ 仍然**没有**证据的两支（别读成已验证）：

1. **目录下钻**（`parentId=<目录id>`）—— 基准里那条只有 `parentId=0`，下钻没抓到。
2. **五条写能力的契约**（`add` / `update` / `delete/{id}` / `move/{from}/{target}` / `setPermission`）——
   基准里 0 条写请求。它们的 body 键序与路径参数顺序**只有源码 + 真机**两层证据。

`test/ai-knowledge.test.ts` 的「与浏览器基准逐字段一致」那一组（10 例）把上面每一条都钉住了，
包括「基准里 0 条写请求」「下钻不在基准里」「外壳请求能力一条都不发」这三条**刻意的反向断言**——
将来谁重抓基准补上了下钻或写请求，它们会红，提醒来的人把断言补齐而不是删掉。
