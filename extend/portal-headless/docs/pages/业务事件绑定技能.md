# 业务事件绑定技能（`/dashboard/platform/intelligence/prompt/business-event/list`）

> 这一组的**共享机制**（三页都落默认 `platform` 实例、都**不发** `module-type`、
> 三页参数装配各不相同在哪、写链路 `prepare → submit → cancel` 怎么分）
> 写在 [`src/capabilities/ai-prompt-tool.ts`](../../src/capabilities/ai-prompt-tool.ts) 的文件头，
> 这里只记这一页自己的东西。

| 项 | 值 |
| --- | --- |
| 菜单路径 | `/dashboard/platform/intelligence/prompt/business-event/list` |
| 权限码 | `/dashboard/platform-v2/intelligence/prompt/business-event`（路由文件 `meta.permission`；`generated/page-catalog.json` 逐字相同 —— 这一页**只在 v2 菜单里**，见下） |
| 路由文件 | `app/portal/views/dashboard/platform/intelligence/prompt/business-event/list.vue` |
| 表单页（新建 / 编辑） | 同目录 `[mode]/[id].vue`（`EventRegistration` / `EventEdit`） |
| 执行记录页 | 同目录 `detail/[id].vue`（**没有独立菜单项**，从列表「查看记录」进来的） |
| 接口 | 前缀 `BASE_URL = '/admin-api/ai/business-event'`（**展开后**：`/page`、`/get`、`/create`、`/update`、`/update-enabled`、`/delete`、`/available-skill/page`、`/record/page`、`/record/get`、`/skill-record/retry`） |
| module-type | **不发**（规则表里匹配不到，与浏览器一致） |
| http 实例 | `platform`（全局默认：页面不声明、规则表里也没有这条路径） |
| 能力 id | `ai-business-event-list` / `-get` / `-available-skill-list` / `-record-list` / `-record-get` / `-create` / `-update` / `-set-enabled` / `-remove` / `-record-retry` |
| 基准 | `baseline/ai-prompt-tool.browser.json`（**列表那条已逐字段对上**；写请求不在基准里） |

## `BASE_URL` 是常量，先展开再写能力

`business-event/api.js` 第一行就是 `const BASE_URL = '/admin-api/ai/business-event'`，
十条接口全是 `` `${BASE_URL}/xxx` ``。展开时有两件事要记住：

1. **前缀已自带 `/admin-api`** —— `platform.js:18-20` 的前缀拦截器对已带 `/admin-api` 的**透传不补**
   （conventions 25），所以路径里必须原样带上；写成 `/ai/business-event/page` 不会补回来，只会 404。
2. **`/get` 与 `/delete` 的 id 都在 query 上**（`{ params: { id } }`），路径里没有 id ——
   ⚠️ 这与同域的「开放接口」页**不一样**（那边是 `/get/{id}`、`/delete/{id}`）。别互相照抄。

## 这一页**只在 v2 菜单里**（所以权限码是带 `platform-v2` 的那条）

`app/portal/menus/mall.js:444-447` 里**没有**这一页，`mall.v2.js:230` 才有：

```js
{ title: '业务事件绑定技能', path: '/dashboard/platform/intelligence/prompt/business-event/list',
  permission: '/dashboard/platform-v2/intelligence/prompt/business-event' },
```

页面自己的 `<route>` 里 `meta.permission` 也是同一条。两处一致，没有歧义。
（对比：同组的「开放接口」在 v2 菜单里**没有** `platform-v2` 前缀、「工具提示词绑定」两代菜单都有 ——
三条各不一样，这是这一组最容易看错的地方。）

## 列表：键序（源码推导，等基准复核）

`customLoad` **逐个挑字段**，所以 `useListPageModule` 塞进去的 `order`/`orderField` **进不了 URL**：

```js
{
  pageNo, pageSize,
  eventName: String(params.eventName || '').trim() || undefined,
  ownerModule: params.ownerModule || undefined,
  useSystem: params.useSystem === '' || params.useSystem == null ? undefined : Number(params.useSystem),
}
```

⇒ 无筛选时 URL 上只有 `pageNo=1&pageSize=20&_t=<ts>`（默认每页 20：`styleV2: true`）。

后端 `BusinessEventPageReqVO`（`erp-module-ai`）+ `AiBusinessEventMapper.selectPage` 对得上：

| 参数 | 后端做法 | 匹配方式 |
| --- | --- | --- |
| `eventName` | `likeIfPresent(getEventName, …)` | **包含**（MyBatis-Plus `like` ⇒ `%x%`） |
| `ownerModule` | `eqIfPresent` | 等值 |
| `useSystem` | `eqIfPresent` | 等值 |

排序写死 `updateTime desc, id desc`，所以分页是稳定的。

⚠️ `eventName` 是**包含**匹配 —— 与同组「开放接口」那页的 `name`（手写 SQL，**前缀**匹配）
**正好相反**，两页别互相照抄。VO 里还多一个 `enabled` 筛选位，**页面从不发**，能力里也没登记。

## `available-skill/page`：`useSystem` 必填但**今天筛不动**

页面的 `SkillBindingEditor` 在 `useSystem` 为空时**根本不发这个请求**（`if (props.useSystem == null
|| props.useSystem === '') return { list: [], total: 0 }`），所以能力里 `useSystem` 是必填。

但后端 `BusinessEventController.getAvailableSkillPage` 里有一行

```java
//UseSystem不作为条件
reqVO.setUseSystem(null);
```

—— 也就是说**这个过滤条件今天不生效**，传了只是与浏览器一致。SDK 照样传（忠实），
调用方会在返回里拿到**跨越各个使用系统**的技能。⚠️ 这是**后端 dev 分支的代码**；
测试环境部署的那一版没有单独核实。

另一条**只有后端代码能看出来**的事实：候选走的是 `AiSkillV2ConfigMapper.selectPublishedPage`，
它的 wrapper 最后一句是 `.eq(getIsPublish, 1)` —— **只返回已发布的技能**。
所以"未发布技能不能绑定"在候选这一步就已经被后端挡掉了；页面上的 `isPublishedSkill` 判断
（那个「（未发布）」后缀）是为了**编辑已有绑定时**发现历史数据。`skillName` 同样是**包含**匹配。

## 写链路：五个写动作，三个能撤、两个撤不回

| 动作 | 能力 | 请求 | 撤销 |
| --- | --- | --- | --- |
| 新建 | `-create` | `POST /admin-api/ai/business-event/create` | 走 `-remove`（但 create **不回传 id**，得先 `list` 找） |
| 修改 | `-update` | `POST …/update`（**整单替换**：技能绑定传什么就是什么） | `cancel` 把 GET 到的原值重算写回 |
| 启停 | `-set-enabled` | `POST …/update-enabled`，body `{ id, enabled }` | `cancel` 写回当前值 |
| 删除 | `-remove` | `DELETE …/delete?id=` | ⚠️ **撤不回**（逻辑删除、无恢复接口）⇒ `cancel` 抛 |
| 重试技能执行 | `-record-retry` | `POST …/skill-record/retry`，body `{ id }` | ⚠️ **撤不回**（技能真的又跑了一遍）⇒ `cancel` 抛 |

三处与页面不同、但**刻意**的地方：

1. **启停给的是"目标状态"**，不是页面按钮传的 `!record.enabled`。无头里"当前值"是 `prepareSetEnabled`
   读出来的，不是从表格行里捡的。
2. **`prepareUpdate` 会先 `GET`**，把调用方**显式给了**的字段盖在 GET 到的那份上再重算
   （页面也是"GET 灌满表单 → 改几项 → 整张表单提交"）。所以漏传 `skillBindings` **不会清空绑定**。
3. **`enabled` 与技能绑定有关**：页面 `validateSkillBindings` 要求"启用事件至少绑定 1 个已发布技能"，
   后端 `BusinessEventSaveReqVO` 的 `skillBindings` 也真的这么用。**验证轮里要新建一条事件，
   最省事的形状是 `enabled: false` + 空绑定**。

`buildBusinessEventPayload` 的三处细节（都逐字抄页面、别"顺手整理"）：
`ownerModule` 空是**空串**（照发）、`description` 空是 **`null`**、`id` 只在非空时**追加在最后**。

## 重试那条的副作用要单独说

`BusinessEventExecuteServiceImpl.retry` 不是"改个状态"：

```java
if (!executeRecordMapper.claimRetry(recordId, getLoginUserId(), retryTime)) throw …;
NewSkillConfig skillConfig = …;
executeClaimed(record, skillConfig, message, bindingDescription, retryTime);   // ← 同步执行技能
```

它会把 `record.payload` 重新组装成提示词、**同步调用 `newSkillExecutor.execute(...)`**，
技能自己的写操作会真的发生。所以：

- 它编在**写能力**里（`write: true`），并且 `prepareRecordRetry` 会**先 GET 记录检查状态**
  （只允许 3 失败 / 4 跳过 / 5 超时 —— 页面 `RETRYABLE_RECORD_STATUS`），状态不对就当场抛、不发请求；
- 门面上它属于**需要防重**的那一类（重发 = 再跑一次）；
- **验证轮里不要跑它**，除非本来就有一条 failed 的测试记录。

## 基准（`baseline/ai-prompt-tool.browser.json`，2026-09-21 抓到）

这一页在基准里有**三条**请求，其中**只有一条是页面自己发的**：

| 请求 | 是谁发的 |
| --- | --- |
| `GET /admin-api/org/sensitive/info` | ❌ **不是这一页** —— app 外壳的全局敏感词检查，跟着每页一起被抓进来 |
| `GET /admin-api/bpm/task/list-by-category?finished=1&pageNo=1&pageSize=10` | ❌ **不是这一页** —— 外壳的待办角标 |
| `GET /admin-api/ai/business-event/page` | ✅ 这一页的列表请求 |

三条列表契约**全部与源码推导逐字段相符**（含键序），**没有冲突**：

```
GET /admin-api/ai/business-event/page?pageNo=1&pageSize=20&_t=<ts>
```

另外基准给了一条**浏览器实测**（不再是推断）：`headers` 里只有
`Accept` / `Accept-Language` / `tenant-id` / `token` —— **没有 `module-type`**，
与"规则表里匹配不到就不发"完全一致（conventions 2 / D34）。

**基准是什么、不是什么**：这一轮**全是只读 GET**（一个写请求都没发），所以
`get` / `create` / `update` / `delete` / `retry` 的形状**仍然只有源码 + 后端代码两份证据**，
没有浏览器证据。别把"列表对上了"读成"这一页整页都验过了"。

### 基准**没有**覆盖的（仍然只有源码 + 后端代码两份证据）

1. 请求体的键序：`{eventName, ownerModule, useSystem, description, enabled, skillBindings[, id]}`；
2. `DELETE …/delete?id=`（query 传参，路径里没有 id）；
3. `available-skill/page` 到底带不带 `useSystem`（后端会把它置空，但页面确实照发）；
4. `record/page` / `record/get` / `update-enabled` / `skill-record/retry` 的形状
   （页面挂载时不发这些，抓基准那一轮也没点进去）。

## 待派单方真机验证的清单

> 按派单方的要求：**真机写验证由派单方统一跑**，本节只写"跑什么、期望什么、怎么撤、什么风险"。
> 本轮我没有对测试环境发出过任何请求。

> **写验证的红线**（派单方 2026-09-21 的要求，逐条照做）：
> **不要对任何非 `SDK-TEST-` 的行做 create / save / PUT / DELETE**。
> 本节标了「会改到**已有**数据」的那几条，只能拿**同一轮里自建的 `SDK-TEST-` 记录**去跑 ——
> 下面各条的"前置条件"已经按这个写死了，没有自建记录就先跑①的那条自建流程。
> 本轮**我没有对测试环境发出过任何请求**（没有 browser、没有 `bsk`、没有 smoke 脚本）。

### ① 只读冒烟（风险：无）

| # | 请求 | 前置条件 | 期望 |
| --- | --- | --- | --- |
| 1 | `GET /admin-api/ai/business-event/page?pageNo=1&pageSize=20&_t=<ts>` | 账号有 `ai:business-event:query` | `ret=SUCCESS`、`data={list,total}` |
| 2 | `GET …/page?pageNo=1&pageSize=20&eventName=<库里某个事件名的**片段**>&_t=` | 同上，且库里有事件 | 命中**包含**该片段的事件（`likeIfPresent` ⇒ `%x%`；拿中间几个字试，能命中就说明是包含而不是前缀） |
| 3 | `GET …/available-skill/page?pageNo=1&pageSize=20&useSystem=1&_t=` | 有 `ai:business-event:query` | `ret=SUCCESS`；若后端那行 `setUseSystem(null)` 已部署，返回的条数与不带 `useSystem` 一致 |
| 4 | `GET …/record/page?pageNo=1&pageSize=20&eventCode=<库里任意一条事件的 eventCode>&_t=` | 该事件**触发过**（没触发过时 `total=0` 也算通过） | `ret=SUCCESS`、`data={list,total}`；`eventCode` 的确切取值可以从①的第 1 条的某一行里取 |
| 5 | `GET …/record/get?id=<上一条列表里某行的 id>&_t=` | 有记录 | `ret=SUCCESS`、含 `status`/`durationMs`/`payload` |

顺便核对：请求头里**没有** `module-type`；URL 上 `/admin-api` 只出现一次。

### ② 真写一轮：新建 → 撤销（风险：**中**，会真的建一条业务事件）

- **前置**：账号有 `ai:business-event:create` + `delete`；准备一个 `useSystem` 值（1 人力）。
- **prepare**：`prepareCreate({ eventName: 'SDK-TEST-业务事件-<YYYYMMDDHHmm>', ownerModule: '<字典 ai_business_owner_module 的某个值>', useSystem: 1, enabled: false, skillBindings: [] })`
  - 期望：**不发请求**；`enabled: false` + 空绑定**能通过**本地校验
- **submit**：`POST /admin-api/ai/business-event/create`，body = 上面那份（`description: null`）
  - 期望 `ret=SUCCESS`；**响应里没有新 id**（后端 `CommonResult<Long>` 前端没用）
- **确认存在**：`GET …/page?…&eventName=SDK-TEST-业务事件-<YYYYMMDDHHmm>` → 取到新记录的 `id`/`eventCode`
- **撤销**：`prepareRemove(id)` → `submit` → `DELETE …/delete?id=<id>`
  - 撤销后**再查一次列表**确认为空 —— 不要拿"删除接口返回成功"当证据（后端是逻辑删除）

### ③ 真写一轮：修改 + 撤销（风险：**中**，⚠️ **会改到已有数据**）

- **前置（硬性）**：**只能改②里刚建的那条 `SDK-TEST-` 记录** ——
  **不要**拿库里任何非 `SDK-TEST-` 的事件去跑 `update` / `update-enabled` / `delete`。
- `prepareUpdate({ id, description: 'SDK-TEST-改过的说明' })` → `submit`
  - 期望：`prepare` 那次 `GET` 到的**技能绑定条数与顺序**原样出现在 `update` 的 body 里（这是最要紧的一处：
    如果 `skillBindings` 变成空的，说明 `boundSkills → skillBindings` 的换算没生效）
- **撤销**：`cancel(plan)` → `POST …/update`，body 应是 GET 到的那份重算
  - 撤销后再 `GET` 一次，`description` 回到原值

### ④ 真写一轮：启停 + 撤销（风险：**中**，⚠️ **会改到已有数据** —— 同样只拿②里那条自建记录跑**）

- `prepareSetEnabled(<③里同一条 id>, false)` → `submit` → `POST …/update-enabled`，body `{id, enabled:false}`
- **撤销**：`cancel(plan)` → 同一个接口，`enabled` 写回 `true`
- 撤销后列表里那条应显示「启用」

### ⑤ **不要跑**（本清单里明确排除）

- `-record-retry`：会真的再执行一遍技能（可能产生业务副作用），除非本来就有一条 `status ∈ {3,4,5}` 的
  **测试**记录，且确认技能本身只读。
- 删除**非 SDK-TEST-** 的事件：后端是逻辑删除、没有恢复接口。

### ⑥ 撤销不了时怎么收尾

- 新建成功但 `delete` 失败（权限/网络）：**留着**并在报告里给出 `eventCode` + `id`，
  由派单方带走过的路径删 —— **不要**用 `buildBusinessEventPayload` 去改成别的形状再删。
