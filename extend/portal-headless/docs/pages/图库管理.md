# 图库管理（`/dashboard/base/image/list`）

阶段① 的**第三条换域业务线**，也是第二条「普通 CRUD」。四件套的其它三件分别在：
能力定义与参数契约 → `src/capabilities/base-image.ts`；逐字段基准 → `baseline/base-image.browser.json`；
回归测试 → `test/base-image.test.ts`（含默认跳过的 `LIVE` 真机组）；
真机冒烟入口 → `smoke/base-image-crud.mjs`。

它要回答的问题是：

> 作业管理那条线把「普通 CRUD」这个形态跑通了一次，但它**只在一个域、一种后端写法**上成立过。
> 图库管理是同一个形态的**第二个样本**——同一个形态里，哪些性质是形态本身的，
> 哪些只是那一页的巧合？

结论写在「**同族之间的四处硬差别**」一节，那一节比「页面做完了」重要。

## 页面形态：普通 CRUD，但有三处与作业管理不一样

这是本次最要紧的判断。三个动作的来源逐条：

| 动作 | 请求 | 出处 |
| --- | --- | --- |
| 列表 | `GET /sys/imagemanage/page` | `list.vue` 的 `getDataListURL` |
| 详情 | `GET /sys/imagemanage/{id}` | `[mode]/[id].vue` 的 `objectURL` + `common/libs/renren/form.js:176` |
| 新建（保存） | `POST /sys/imagemanage`，**body 是数组** | `create-multiple/create.vue:131` |
| 新建（保存并发布） | `POST /sys/imagemanage/saveAndRelease`，body 同为数组 | 同上，`handleSubmit(1)` |
| 修改 | `PUT /sys/imagemanage` | `form.js:131`（非 create 分支） |
| 改状态 | `PUT /sys/imagemanage`，body `{id, status}` | `list.vue` 的 `actionStatus` |
| 删除 | `DELETE /sys/imagemanage`，body `[id]` | `list.js:517` 的 `deleteIsBatch` 分支 |

**同样没有 `prepare`**：后端 `SysImageManageController` 一共就 5 个方法，没有任何
"提交前先问一次"的接口。写链路的形状是 `get → create/createRelease → update/setStatus → remove`。

### ① 上传不在接口里

这是与作业管理最大的一处形态差别，也是**无头最容易被绊倒的地方**：
页面上有「上传」，但**接口不收字节**。文件先由上传组件直传 OSS，回调只给出 `{ url, fileName }`：

```js
// create-multiple/create.vue:116
function onFileUploadDone ({ url, fileName }) {
  fileList.value.push({ name: fileName, url })
}
```

点「保存」时才把 `fileList` 整个 POST 出去（`http.post(url, fileList.value)`）。
所以 SDK 的 `create` / `createRelease` 收的是 **`url` 字符串**，由调用方给，
并且**明确不覆盖上传**（`docs/usage.md` 的口径一致：SDK 只做 Portal 的接口层）。

### ② `remove` 是**物理删除**（与作业管理正相反）

`SysImageManageEntity` 没有逻辑删除字段（没有 `@TableLogic`），
`CrudServiceImpl.delete` 直接走 `baseDao.deleteBatchIds`。实测：
删完 `list` 查不到，`get(id)` 返回 **null**。

⇒ 这里**可以**用 `get` 复核"删掉了没有"；作业管理那条线**不可以**（那边 `get` 仍返回整行、`isDel=1`）。
两条结论都是实测的，**不要互相套用**——这是同一个形态里最容易做错的判断。

⚠️ 另一条安全相关的事实（源码级）：**删除只删数据库行，不碰 OSS**。
文件是页面自己在上传/编辑时用 `ossDeleteMulti` 清的（`[mode]/[id].vue:62` 的 `afterFormSubmit`）。
所以删一条记录不会删掉别人的文件；反过来说，删了记录也不等于文件被清了。

### ③ `PUT` 不传 `status` 会 500（后端拆箱 NPE）

```java
// SysImageManageServiceImpl.updateInfo
if (dto.getStatus() == 1) { entity.setPublishTime(LocalDateTime.now()); }
```

`status` 是 `Integer`，为 null 时 `== 1` 触发拆箱 NPE。而 `updateById` 本身是**部分更新**
（MyBatis-Plus 只写非 null 字段），所以"只改名字"在后端语义上本来是成立的 ——
卡住它的是那一行拆箱。实测报文（**HTTP 200 + ret FAIL**）：

```
code=500 msg=Cannot invoke "java.lang.Integer.intValue()" because the return value of
  "com.wdbc.erp.module.system.controller.admin.img.dto.SysImageManageDTO.getStatus()" is null
```

失败发生在 `updateById` **之前**，记录一个字都没改（实测比对过）。
⇒ SDK 的 `update` **强制要求 `status`**，缺了当场报错（`normalizeStatus`），
不把 500 丢给调用方，也不替调用方去猜它想要哪个状态。

## 参数契约

### 列表查询（与浏览器逐字节一致）

```
GET /admin-api/sys/imagemanage/page
  ?order=&orderField=&imgName=&status=&name=&createTimeStart=&createTimeEnd=&pageNo=1&pageSize=20&_t=<ts>
```

一次筛选都没填，这些参数照样以空串发出去（renren 列表页的空值默认参数，D20）。
`pageSize` 默认 20（`list.js:391` 的 `styleV2` 分支）。
**参数顺序也是契约**：`list.js:474-481` 拼的是 `order, orderField, ...formState, pageNo, pageSize`。

`src/capabilities/base-image.ts` 里的 `buildListParams()` **把键顺序显式写死**，
而不是用 `{...DEFAULTS, ...query}` 那种写法 —— 后者在调用方只传 `pageSize` 时会把
`pageSize` 插到 `pageNo` 前面，序列化出来的 URL 参数顺序就与浏览器不一样了。
`test/base-image.test.ts` 有一条用例专门传 `{ pageSize: 50 }` 盯这件事，
反证里改坏这一行会同时打红 4 条用例。

### 创建时间区间：**两端都是开区间**

页面的 `convertFetchForm`：`createTimeStart = date[0].startOf('date')`、
`createTimeEnd = date[1].startOf('date').add(1,'day')`；后端 SQL 是
`create_time > #{createTimeStart} and create_time < #{createTimeEnd}`。
两边合起来正好是「含头不含尾」：选 2026-09-20 这一天，查到的是
`(09-20 00:00:00, 09-21 00:00:00)`。与作业管理页逐字节相同，所以**共用** `buildCreateTimeRange()`。

### `imgName` / `name` 是**前缀匹配**，不是模糊匹配

```sql
and t1.name like CONCAT(#{dto.imgName},'%')     -- 图片名称
and t2.real_name like CONCAT(#{dto.name},'%')   -- 上传人姓名（join hr_sys_user）
```

实测：按 `SDK-TEST-图库探针` 前缀查到 2 条，按名字中段「图库探针」查到 **0 条**。
与作业管理那条线（`title` 是模糊匹配）**不一样**，那里踩过的"改名后旧名字被子串命中"的坑
在这里换了形状：查名字只能用名字的开头那一段。

### `status`：接口认 0/1，页面上那个下拉是坏的

后端 `status` 是 `Integer`（`SysImageManageSelectDTO`）。实测 `status=1` 命中 3 条、
`status=0` 命中 2 条（当轮全库共 5 条），**过滤是对的**。

但页面自己那个「发布状态」下拉是**坏的**：它用 `portal-education-dict-select type="status"`，
而 `status` 是全平台共用的字典 key —— 实测 `/sys/dict/type/all` 里
`dictType: "status"` 的 `dictName` 是**「订单状态」**，6 个值是
`WAIT_SELLER_CHECK / WAIT_BUYER_PAY / PROCESSING / TRADE_FINISHED / TRADE_CLOSED / TRADE_CLOSED_BY_SYSTEM`。
选中之后浏览器发的是 `status=TRADE_FINISHED`，后端直接绑定失败：

```
HTTP 200 + {"ret":"FAIL","code":400,
  "msg":"请求参数不正确:Failed to convert property value of type 'java.lang.String'
         to required type 'java.lang.Integer' for property 'status'; For input string: \"TRADE_FINISHED\""}
```

页面上看着像"查不到数据"，是因为它对失败的处理是把列表清空（`list.js` 的 `catch { listReset() }`）。

⇒ SDK 的处理与作业管理那条线**同一条原则、不同的落点**：
- 作业管理那边，错误的候选值来自字典，所以 `status` 如实声明成 `text` 并写明它坏在哪；
- 这一页后端真正认的值是**可实测的 0/1**，所以声明成 `enum`（未发布 / 已发布），
  并在描述里写明"页面上那个下拉是坏的"。
**共同的原则是：不能把错的候选值当契约发给 AI。**

### 后端不认的两个参数

`order` / `orderField` 页面照样发（我们照发，才逐字段一致），但这一页的 SQL 是写死的
`order by t1.publish_time desc, t1.create_time desc`，没有 `${order}` 拼接 —— **排序改不动**。

### 没有数据范围（实测）

`SysImageManageSelectDTO` 继承了 `DataScopeEntity`，但 `SysImageManageDao.xml` 里
**一个字段都没用到**：这条 SQL 没有租户条件、没有数据范围条件、也没有 `project` 过滤。
实测无筛选时全库 5 条，`creator` 分别是 15228 与 18243 —— **跨创建人**。

⇒ 没有"只看我上传的"这种过滤，`creator` 也不是查询参数。要按人筛只能用 `name`（上传人姓名的前缀）。

## 写链路：五个写能力，哪些需要防重

`docs/conventions.md` 第 14 条（后端零幂等）在这个页面上的代价分布如下 ——
**只有 `create` / `createRelease` 会产生第二条记录**：

| 写能力 | 重发一次的后果 | `requestId` | 依据 |
| --- | --- | --- | --- |
| `create` | **多一条图库记录**（后端零幂等） | **要** | 与作业管理同一个理由；反证里没试过重发不带 `requestId` 的那种（那正是要防的） |
| `createRelease` | 同上，而且会多一条**已发布**的记录 | **要** | 同上 |
| `update` | 部分更新再写一次，终态相同 | 不要 | 实测：重复 PUT 不产生新记录 |
| `setStatus` | 写的是**绝对值**不是开关，终态相同 | 不要 | 实测：`setStatus(1)` → get 读回 1 |
| `remove` | 记录已经不在，后端直接返回成功 | 不要 | 实测：重复 DELETE 不报错 |

两个刻意的设计：

- **`setStatus` 收目标状态而不是切换**（页面的 `actionStatus` 就是 `record.status === 0 ? 1 : 0`）。
  做成 toggle 就变成不幂等的 —— 那是 SDK 自己造的坑。
- **`update` 强制带 `status`**（理由见上），但**不代劳 `get` + 合并**：
  后端本来就是部分更新，自动合并反而会把表单不认识的字段写回去。

防重包装（`withIdempotency` 需要会话身份）按惯例放在组装点，能力文件里只声明了
`BaseImageCapabilityWithIdempotency` 的形状：`createIdempotent` 与 `createReleaseIdempotent`
两个方法，**接线由派单方在 `src/index.ts` / `src/server.ts` 做**（本次不碰共享文件）。

⚠️ **「接口返回成功」不等于成功**：`POST` 的返回是 `{"ret":"SUCCESS","code":0,"data":null}`，
**data 是 null，拿不到新建记录的 id**。所以"建成功了没有"只能回列表查
（实测：建完按前缀查到 id 13 / 14）。这与作业管理那条线也不同 —— 那边创建会返回 id。

## 操作步骤（AI 侧）

1. 想查图库：`base-image-list`，`imgName` 用**前缀**（如 `SDK-TEST`），别用中段。
2. 要改/删某一条：先 `base-image-list` 拿 id（数字），必要时 `base-image-get` 看当前值。
3. 只改名字：先 `base-image-get` 读回 `status`，再 `base-image-update { id, name, status }`。**漏 `status` 会 500。**
4. 发布/取消发布：`base-image-set-status { id, status: 1|0 }`。
5. 新建：`url` 必须是**已经存在于 OSS 的地址**（SDK 不上传）；建完**回列表查一次**才算证实。
6. 删除：`base-image-remove { id }` —— 物理删除，删完 `get` 会返回 null，可以用它复核。

### 真实环境的方法学说明（如实记）

- **没有重新抓浏览器基准。** 上一轮留下的草稿基准（`/tmp` 里那份）本轮**逐条对过源码**
  （四条读 + 六条写的形状全部找到出处），并**逐条打过真实后端**，结论写进
  `baseline/base-image.browser.json` 的 `复核` 一节。代价：请求头的逐字节没有重新确认。
- **草稿里有一条归因是错的，已更正**：它说带 `status=TRADE_FINISHED` 时"后端 HTTP 200 但结果为空"。
  观察（空表格）是对的，但原因是后端返回**失败包络** + 页面的 `catch { listReset() }`，
  不是"查出来 0 条"。这条更正写在基准文件的同一条备注里。
- **真机跑在 vitest 里，不是裸 Node。** SDK 是 TS，Node 的类型剥离解析不了
  `src` 里的 `./x.js` 导入（实测 `ERR_MODULE_NOT_FOUND`），而 `pnpm build` 在并行窗口里
  不能跑（会与别的任务抢 `dist/`）。所以 `smoke/base-image-crud.mjs` 包了一层 vitest，
  真正的请求走的是**真实 SDK 请求层**（`createPortalHttp` + `createPageCall` + 能力），
  只是没有经过 `src/index.ts` 的门面 —— 因为**把这一页接进门面是派单方的动作**，
  不在本次的文件范围内。测试文件里也是按 `src/index.ts` 的那三行手动接的线。
- **测试与实现之间的"真值"锚点。** 其余用例全都拿 `BASE_IMAGE_PAGE_PATH` 当输入
  （推 module-type、推 http 实例、当页面上下文），常数改错一个字它们会**一起错却全绿**。
  反证第一轮就抓到了这个洞（两个变体存活），于是补了一条**读 `generated/page-catalog.json`**
  的用例：清单是从 Portal 前端源码扫出来的，是独立的那份真值。

## 同族之间的四处硬差别（本次真正要回答的）

作业管理与图库管理是同一个形态（列表页 + 普通 CRUD），但下面四处**不能互相套用**：

| 维度 | 作业管理 | 图库管理 | 怎么发现的 |
| --- | --- | --- | --- |
| **删除语义** | 逻辑删除（`isDel=1`，`get` 仍返回整行） | **物理删除**（`get` 返回 null） | 源码（有没有 `@TableLogic`）+ 真机各测一次。"删掉了没有"用哪个视角复核，两页答案相反 |
| **id 的类型** | 字符串（`["1071"]`） | **数字**（`[11]`、`"id":11`） | 两条线的浏览器基准。归一化函数必须各写一份 |
| **创建返回** | 返回 id（`"1076"`） | **`data` 是 null**，拿不到 id | 真机实测。所以"建完回列表查"在这一页不是谨慎，是**唯一**手段 |
| **匹配方式** | `title` 模糊匹配 | `imgName` / `name` **前缀匹配** | SQL（`like CONCAT(#{},'%')`）+ 真机对照 |

原样成立的部分也不少，值得记下来（说明它们确实是**形态**的性质、不是那一页的巧合）：

- 四件套的结构，与「一个能力绑一个页面上下文」：`pagePath` 决定 module-type 与 http 实例，换页不动。
- 「列表页要带 renren 的空值默认参数」：这一页同样一条不少，**而且参数顺序同样是契约**。
- 日期区间的 `+1 天` 开区间：两页的 `convertFetchForm` 逐字节相同，函数直接复用。
- `prepare` 依然没有对应物；`requestId` 依然只加在**会多出记录**的写能力上（这里有两个）。

## 尚未覆盖

- **上传那一步不在本能力的职责里**，`url` 由调用方给——SDK 另有上传基础能力（`baseUpload`，见 docs/base/上传.md），
  可以先传文件拿到 url。注意那条线自己的真实链路已实测，但**本页的端到端流程仍未把两者串起来跑过**。所以
  "从零上传一张图片 → 出现在图库里"这条链路**没有测过**；本轮的 `url` 是测试环境 OSS 上
  一个已存在的地址（只作为字符串存下来）。`common-upload-dragger` 的 `beforeUpload` 只校验
  `file.type.indexOf('image') === 0`，那条规则 SDK 侧没有复刻（它属于上传，不属于本页接口）。
- **`project` 字段没有验证。** 后端 `saveImage` 在 `project` 为 null 时填 1，实测读回来也是 1；
  但 `project` 到底影响什么（SQL 里没有过滤它）没有查。传别的值会怎样也没试。
- **多条一起建只测了 body 形状，没有真机验证。** 单测钉住了"一次传两条 → body 是两条"，
  真机上只跑过单条（`create` 与 `createRelease` 各一条）。`insertBatch` 的批大小是 100，
  超过会怎样没有试。
- **`update` 的载荷与浏览器不是逐字节一致（有意为之）。** 页面的编辑态是把 `GET /{id}` 的
  整个响应铺回表单再整份 PUT（body 里带 `creator` / `createTime` / `publishTime`）；
  SDK 只发调用方点名的字段。依据是后端本来就是部分更新、两种载荷终态相同
  （实测过"只改名字 url 不清空"），但**没有做过与浏览器的逐字节比对**。
- **写请求那次"没有 module-type"的现象没有复现也没有证伪。** 草稿抓到过一次 POST 不带这个头，
  本轮所有请求都带了。它的解释（浏览器级 cookie 被并行会话覆写）与作业管理线上实测到的
  同类现象一致，但**这一页本身没有独立证实**。
- **`name`（上传人姓名）这个筛选条件没有真机验证。** 它 join `hr_sys_user.real_name`
  且是前缀匹配，SQL 读得很清楚，但本轮没有构造出对应用户的数据去验证。
- **`status` 删除后的 `publishTime` 语义只测了一半。** 实测 `status=0` 时 `publishTime` 不动；
  `status=1` 时会刷成当前时间（源码如此），但没有对 `publishTime` 的**前后值**做过断言。
