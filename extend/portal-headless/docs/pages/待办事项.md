# 待办事项（`/dashboard/backlog/task-examine/list`）

阶段① 的又一条业务线（`backlog` 域），也是**第一条「一个组件被多条菜单复用」的列表页**；已办标签下另有撤销审批动作。
四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/backlog-task-examine.ts`；
逐字段基准 → `baseline/backlog-task-examine.browser.json`；回归测试 → `test/backlog-task-examine.test.ts`；
真实环境冒烟 → `smoke/read-backlog-task-examine.mjs`。

前面几条线各自回答了一个问题（会议室的写链路、考勤档案的「方法能不能泛化」、作业管理的
「换域之后哪些做法不适用」）。这一页要回答的是：

> **同一个组件挂在三条菜单下，「这一页是哪一页」和「这一页上的一个开关」怎么分开？**

顺带撞见了本阶段第一个**后端自己的 bug**（`processCategory`，见下面专门一节），
它比页面本身更值得记：**「基准里浏览器发了什么」和「后端收下之后干了什么」是两件事。**

## 这一页最要紧的事实：一个组件，三条菜单

`/dashboard/flow/task/todo/list`（待办任务）与 `/dashboard/flow/task/done/list`（已办任务）
各自只有一个模板：

```vue
<!-- app/portal/views/dashboard/hr/flow/task/todo/list.vue -->
<PageView :finished="1" :componentMode="true" key="todo"/>
```

它们 import 的就是本页组件，只是**预置了 `finished` 并关掉了右上角的切换器**
（`list.vue` 的 `<Teleport v-if="showTab && !componentMode">`）。三条菜单打的是同一个接口、
同一个组件的同一段逻辑。

### ⇒ SDK 把列表与撤销动作拆成两个能力，这是刻意的

`backlog-task-examine-list` 负责三条菜单共用的列表查询；`backlog-task-examine-withdraw`
只负责已办标签中满足条件的「撤销审批」动作。`finished` 是列表能力的**参数**，不是三条独立的数据边界。理由见下。

两个直接后果，都要知道：

1. 想要「已办任务」= 调列表能力时给 `finished: 2`，**不是**去开一个 `/dashboard/flow/task/done/list` 的列表能力；撤销审批则调用独立的动作能力。
2. `pnpm next` / 覆盖率报告里，那两条菜单仍会显示「未完成」——它们没有自己的能力文件，
   `capability.pagePath === menuPath` 这条判据不成立。这是**判据的已知盲区**，不是漏做。

### 四个必须记住的点

**1. `selectType` 在「待办事项」下也在请求里，尽管那个控件没渲染。**
`formState.selectType` 的初值恒为 1（`list.vue` 的 `form` 定义），控件只是被 `v-if` 藏起来了。
**「控件没渲染」不等于「参数不存在」**——照抄基准就意味着待办下也发 `selectType=1`。

**2. `createTime` 没有「结束日 +1 天」那种开区间改写。**
作业管理那条线的 `convertFetchForm` 会把结束日改成次日 00:00:00；本页**没有 `convertFetchForm`**，
两个值原样进 qs，序列化成 `createTime[0]` / `createTime[1]`（`qs` 默认的 indices 形式，方括号被编码成 `%5B/%5D`）。
照抄作业管理那套会**静默多查一天**。想要含 9-10 一整天，得自己给 `2026-09-10 23:59:59`。

**3. `module-type` 这一页算不出，所以不发 —— 这与浏览器一致。**
`resolveModuleType('/dashboard/backlog/task-examine/list')` → `{ moduleType: null, matchedBy: 'none' }`
（27 条规则里没有任何一条命中 `/dashboard/backlog/`）。浏览器在**干净状态**下同样不发这个头。

> ⚠️ 抓基准时这条必须拿规则表复核。本轮复核时**真的抓到过 `module-type: 11`**（组织管理），
> 而本页 URL 一个字都没改 —— 同一时刻 cookie `hr-0.0.0-menuPath` 是
> `/dashboard/attendance/attendance-shift/list`，那是**另一个并行代理在同一个浏览器 profile 里
> 导航写进去的**（cookie 全局共享，不分标签页）。等它变回无规则匹配的值再抓，这个头就消失了。
> 与考勤档案 / 作业管理那两条线各自独立撞到的是同一件事。

**4. `processCategory` 这条链路是坏的，而且是后端坏的。**（下一节整节）

## `processCategory` 这一条是坏的（后端 bug，实测三层证据）

### 现象

同一条 URL、同一个会话，**只差 `processCategory` 这个键在不在**：

| 请求 | 后端 |
| --- | --- |
| `…&finished=1&selectType=1&pageNo=1&pageSize=20` | ✅ `code=0`，`data.total=25` |
| `…&finished=1&selectType=1&processCategory=human_process&…` | ✅ `code=0`，`data.total=16` |
| `…&finished=1&selectType=1&processCategory=Task_month&…`（消息中心深链的值） | ❌ `code=500` `Cannot invoke "java.util.List.stream()" because "<local10>" is null` |
| 同上，换成 `Protocol_year` / `Protocol_month` / `protocolMonthScore` / `Task` / `Protocol` | ❌ 全部 500 |
| 同上，换成 `processCategory=`（**空串**） | ❌ 500 |
| 不传这个键 | ✅ 正常 |

注意 500 是**业务 code**，HTTP 状态码仍是 200 —— 只看 HTTP 会误判成成功。

### 根因（后端源码）

`Mall_Platform_Java_Dev/erp-module-hr/.../service/impl/BpmHrTaskServiceImpl.java:2405`
`webGetTaskListByCategory`：

```java
Map<String, List<BpmModelDTO>> modelMapGroupCategory = modelList.stream()…groupingBy(…);
List<BpmModelDTO> bpmModelDTOS = modelMapGroupCategory.get(pageVO.getProcessCategory());
processCategories = bpmModelDTOS.stream()…   // ← get() 返回 null 时这里空指针
```

`get()` 查不到就是 `null`，下一行直接 `.stream()`。**任何不在流程模型分类表里的值都会 500**，
包括空串。它取的是 `BpmModel` 的 `category`（实测 `human_process` 存在），
而**不是**消息中心深链传的 `taskKey`。

### 前端那一侧同样是坏的（不是 SDK 的问题）

`app/portal/views/dashboard/hr/message/components/hooks/useMessageList.js:68-87` 里，
消息中心的卡片往本页推的是 `/dashboard/backlog/task-examine/list?taskKey=Task_month` 这类链接，
而页面把这四个值**原样**塞进 `processCategory`（`list.vue` 的 `processCategory: route.query.taskKey || null`）。
实测后果：**用浏览器从那条深链进来，页面渲染的是「暂无数据 / 共 0 条记录」**（本轮实测行数 0、`共 0 条记录`）。
「重置」之后同样（`actionReset` 会把 `processCategory` 重新填回 `route.query.taskKey`）。

### SDK 怎么处理这一条（决定 + 理由）

- **保留这个参数**：它确实是页面上的一个真实状态，砍掉等于对调用方隐瞒"页面上有这么个过滤器"。
- **但必须是 `text`，不能是 `enum`**：把深链那四个 `taskKey` 列成候选值，等于
  **把一组注定 500 的值当契约发出去**。这条与作业管理那条线把 `status` 从 enum 降级成 text 是同一个判断
  （见 `docs/pages/作业管理.md`「`status` 这个参数在本页上是坏的」）。
- **默认不传**（`null` → qs 丢掉这个键），所以 SDK 的默认调用是好的、和浏览器打开页面的样子一致。
- **说明里写清楚**：能用的取值是**真实存在的流程分类**（实测 `human_process`），不是深链的 `taskKey`。

`test/backlog-task-examine.test.ts` 有一条用例锁住这个决定（`kind === 'text'`、没有 `options`、
说明里必须留着 `human_process` 与 `500` 这两件事）。

## 操作步骤

```text
1. 进入「待办事项」（/dashboard/backlog/task-examine/list）
2. （可选）右上角切「待办事项 / 已办事项」——这是 finished=1 / 2
3. （可选，仅已办）把「时间范围」改成「全部」——这是 selectType=2
4. （可选）填流程名称 / 审批内容 / 发起人（三个都是纯文本模糊匹配）
5. （可选）选发起时间区间
6. 查询
```

待办标签下的「办理 / 批量办理」与「详情 / 跟进」仍由其它页面能力承接；已办标签下的
「撤销审批」由 `backlog-task-examine-withdraw` 承接，使用本页 `platform.js` 请求上下文。
撤销入口只在 `finished === 2 && record.canWithdraw === true` 时展示。

点击撤销后，Portal 原因弹窗会把输入先 `trim`，空值实际发送 `reason: "无"`；请求体是
`{ id: record.id, reason }`，`record.id` 是历史任务 ID，不是流程实例 ID、业务单据 ID 或下一节点任务 ID。
成功后必须重新读取待办、已办和流程详情，旧历史任务 ID 不复用。

## 参数契约

| 参数 | kind | 必填 | 说明 |
| --- | --- | --- | --- |
| `name` | text | 否 | 流程名称，模糊匹配 |
| `title` | text | 否 | 审批内容，模糊匹配 |
| `startUserName` | text | 否 | 发起人姓名，**纯文本**模糊匹配（不是人员选择器，所以本页**没有长选项参数**，D6/H35 在这一页没有触发点） |
| `createTimeStart` / `createTimeEnd` | date | 否 | 必须**成对**给；格式 `YYYY-MM-DD HH:mm:ss`；**没有 +1 天改写** |
| `finished` | enum | 否 | 1=待办事项（默认）/ 2=已办事项 |
| `selectType` | enum | 否 | 1=近30天内（默认）/ 2=全部 |
| `processCategory` | text | 否 | 流程分类。**⚠️ 传不对的值后端会 500**，见上一节 |
| `pageNo` / `pageSize` | number | 否 | 默认 1 / 20 |

请求参数的**顺序是契约的一部分**（D20 逐字段一致）：
`order, orderField, name, title, createTime[0], createTime[1], startUserName, finished, selectType, processCategory, pageNo, pageSize, _t`。
实现按固定表拼参数（`buildListParams`），调用方实参的书写顺序不影响结果。

两条本地校验（都是 `Promise.reject`，**不发请求**）：

- `createTimeStart` / `createTimeEnd` **必须成对**给。页面上是一个 `a-range-picker`，
  它只会把两个值一起写进 `formState`，给单边等于造了一个页面上不存在的状态。
- `assertDateTime`：格式必须是 `YYYY-MM-DD HH:mm:ss`。**比会议室那条线的 `assertTimeSlot` 松** ——
  分钟不限于 00/30、秒不限于 00（那条约束来自会议室表单自己的 `disabledTime` + 后端 `validateTime`，
  本页没有对应物）；也**不做「结束晚于开始」的校验**（先后顺序由 picker 保证，后端未见校验，
  本地硬拦会把后端本来接受的调用挡在门外）。

### 为什么 `finished` 开放，而考勤档案的 `isArchived` 钉死？

两页看起来是同一件事（同一个接口、一个参数决定取哪一批数据），处理**刻意相反**：

| | 考勤档案 `isArchived` | 本页 `finished` |
| --- | --- | --- |
| 页面上有控件吗 | **没有**，用户在这个页面换不了 | **有**，右上角切换器可直接切 |
| 不开放会怎样 | 忠实：用户在这页看不到另一种数据 | **不忠实**：把用户看得见、点得到的标签藏起来 |
| 它是什么 | 「这一页是哪一页」的定义 | 页面内的一个开关 |

判据是**用户能不能在页面上到达那个状态**，不是「换个值会不会拿到别处也有的一批数据」。

反过来说：本页**没有**把 `selectable` / `componentMode` 这类纯 UI 开关开放出去。
`componentMode` 是那两条复用方菜单用来关掉切换器的，不是数据面的参数
（有一条用例专门锁住「硬塞进去也不会进请求」）。

### ② 浏览器基准：**独立重抓了一遍**

上一轮代理抓完后中断，基准没有复核过。本轮用**另一个 bsk 会话**按 `tools/baseline/README.md`
的配方独立重抓，逐条比对（含键顺序）后确认第 1~7 条**完全一致、未作改动**；
第 8 条是本次补抓的（上一版把 `title` / `startUserName` 列为「没抓到」）。

两条抓取上的经验（已写进基准文件的「复核记录」）：

- **深链那条必须用全新文档抓。** 本页 `<script>` 里有一份**模块级 `stateCache`**
  （`onBeforeUnmount` 存 `formState`，setup 时 `Object.assign` 回去并**先于** `logicFetch()`），
  SPA 内切走再切回来会把 `route.query.taskKey` **覆盖掉**——观测到的请求里 `processCategory` 直接没了。
  最后是用 `bsk network` 读 devtools 的网络缓冲（配一次 `bsk reload`）抓到的。
  这条不只是抓基准的坑：**它也是页面自己的行为**，用户在 SPA 内来回切时深链参数就是这样丢的。

### `backlog-task-examine-withdraw`

在待办事项共享组件的已办标签中撤销当前用户已通过且仍允许撤销的审批。

执行：`sdk.backlogTaskExamine.withdraw`；性质：write。在待办事项共享组件的已办标签中撤销当前用户已通过且仍允许撤销的审批。

- 边界：按钮条件是 `finished=2 && canWithdraw===true`；列表快照可能在提交前过期，最终能否撤销以服务端实时校验为准。
- 边界：后端要求当前用户是原审批人、历史任务已完成且通过、是最近完成任务、流程仍运行、只有一条未处理的串行下一节点、下一节点未挂起且业务守卫允许；并行/多实例/会签多个活动任务不支持。
- 边界：不允许时常见业务码为 `1009005015`；应保留后端消息并刷新相关列表，不能把按钮仍在当成成功。撤销只改变流程任务和操作记录，不自动回滚业务模块已写入的数据。
- 边界：后端 DTO 允许省略/空 reason，但 Portal Web 在发送前将空原因替换成「无」；SDK 按 Web 端实际请求而不是后端宽松 DTO 生成载荷。

| 参数 | 意义与来源 |
| --- | --- |
| taskId | 已办列表行的历史任务 ID；不是流程实例 ID、业务单据 ID 或下一节点任务 ID。只能使用对应列表返回的 list[].id。；来源：同一页面列表能力返回的 result.list[].id；仅选择 canWithdraw === true 的行 |
| reason | 撤销原因，可省略。Portal 表单会先 trim，空串或全空白最终发送「无」；SDK 保持该 Web 请求规则。；来源：用户在 Portal 撤销弹窗中填写；不填时沿用 Portal 的默认值「无」 |

返回：`boolean`。正常成功回执不是空值；未收到 true 不能当作撤销成功。


- 消费：调用前必须从同一页面的已办列表取得历史任务 ID，并确认该行 `canWithdraw === true`；这个字段只是 Portal 的按钮 gate，不是调用方可以替代的后端授权。
- 消费：Portal 的 PUT body 固定为 `{ id, reason }`；taskId 映射到 id，reason 先 trim，空值发送「无」。不要把流程实例 ID、业务单据 businessKey 或下一节点任务 ID 放进 id。
- 消费：成功后重新读取待办、已办和流程详情：原历史任务保留但 ID 不复用，下一节点被撤销，原审批节点会产生新的待办任务。

完成条件：收到 true 后重新查询待办、已办和流程详情，并使用新生成的待办任务 ID；旧历史任务 ID 不得再次提交。

- 失败处理：权限或会话错误交由用户恢复登录态；不要用其他页面上下文或其他租户重试。
- 失败处理：收到 `1009005015` 时说明实时流程条件已不满足：展示后端消息并刷新，不要盲目重复提交。
- 失败处理：网络超时无法判定结果时先查询待办/已办/详情；没有 requestId，不能用新幂等键盲目重试。
