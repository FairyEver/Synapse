页面路径：`/dashboard/report/unit-interference-cost-allocation/list`。

## 列表、权限与返回字段

Portal列表筛选实际为姓名、分配部门、接收部门、月份和状态，默认请求参数为：

```json
{
  "order": "",
  "orderField": "",
  "name": null,
  "allocateDeptId": null,
  "receiveDeptId": null,
  "useYearMonth": null,
  "status": null,
  "pageNo": 1,
  "pageSize": 20
}
```

状态为`0=待提交`、`1=审批中`、`2=审批通过`、`3=已驳回`、`4=已取消`。列表每行保留后端明细ID、分配/接收部门、年月、员工、五项金额、状态和`processInstanceId`。查看详情和重新发起传的是流程实例ID；不能把明细ID当作流程实例ID。

Java服务通过`getOrgIdListByModuleType()`取得当前用户在`module-type=14`下的角色组织范围，再通过`roleOrganizationIdList`限制`allocateDeptId`。前端组织树不是权限绕过入口，SDK也不扩展页面没有暴露的后端筛选字段。

动作权限沿用该页面的菜单权限`/dashboard/report/unit-interference-cost-allocation`、`module-type=14`和`platform`实例。Portal处理函数没有额外的前端权限码；请求是否可执行仍由当前会话和后端权限裁决。动作只接受列表最新状态：`submit`要求`status=0`（待提交），`cancel`要求`status=1`（审批中）。SDK在prepare和实际写请求两次复核状态，避免用过期列表状态直接写入。

Portal合计只对当前页的工资、保险、福利费、其他、公积金五列求和，使用`numberFormat(total, 2, true, '0.00')`；SDK返回`summary`五个字符串字段，空页也为`0.00`。

员工组件源码默认无关键字分页拉取，每页200条、最多100页。SDK的`staffSearch`要求先给非空姓名关键字，仅支持20/50/100/200分页，避免无头调用把数千名员工全部拉入内存。

## 表单提交规则

新建流程表单的必填字段为：

- `allocateDeptId`：分配部门ID。
- `useYearMonth`：年月，格式`YYYY-MM`。
- `staffId`：员工ID；`name`由Portal员工组件通过`getNameByValue(staffId)`取得并一起提交。
- `items`：至少一条接收部门明细，每条必须有`receiveDeptId`。

每条明细包含工资、保险、福利费、其他、公积金五个金额。金额可为空；Portal的`normalizeAmount`会把空值转为`0`，非空值必须是有限数字、>=0、<=`9999999999.99`且最多两位小数。接收部门不能与分配部门相同，同一张分摊单内不能重复；前端会禁用标准化单元、分配部门和其他明细已经选中的节点，Java服务仍会再次校验。

实际提交体严格为：

```json
{
  "allocateDeptId": 101,
  "useYearMonth": "2026-09",
  "staffId": 202,
  "name": "张三",
  "onlySave": 0,
  "items": [
    {
      "receiveDeptId": 301,
      "salaryAmount": 100.1,
      "insuranceAmount": 0,
      "welfareAmount": 2,
      "otherAmount": 0,
      "providentFundAmount": 0.46
    }
  ]
}
```

不发送`totalAmount`、`status`、成本中心、组织名称或流程实例字段。Java服务按每个`items`明细拆成后端记录，服务端计算合计；`onlySave=0`表示保存并提交审批，创建成功返回首条明细ID。当前Portal页面没有可达的更新、删除、导入按钮，SDK不把这些虽存在于Controller的端点登记成页面能力。

## 逐页操作步骤与证据边界

1. 先调用`organizationTree()`取得当前会话组织树；需要选员工时用`staffSearch({ keyword })`，用返回的`list[].id`和`list[].name`填入表单。
2. 用`list()`查询并保留行的`id`、`processInstanceId`、状态和五项金额；查看详情调用`detail({ id })`。
3. 新建调用`prepareCreate(form)`，向用户展示规范化后的`draft`；用户明确确认后把同一份`draft`交给`create()`。
4. `create()`返回的ID只代表后端回执。由于`onlySave=0`会启动审批流程，成功或超时都要按年月、员工、分配部门和接收部门重新`list()`，核对明细和流程状态，不能盲目重试。
5. 只有列表行状态为`3=已驳回`时才能调用`prepareRecreate({ id, currentStatus: 3, processInstanceId })`。随后先核对流程实例，再读取详情打开编辑表单；Portal重新提交仍走同一个`create`接口。

对已有草稿的动作按以下顺序执行：

1. `prepareSubmit({ id, currentStatus: 0 })`，用户确认后把返回草稿原样交给`submit()`；或在审批中记录上调用`prepareCancel({ id, currentStatus: 1 })`后交给`cancel()`。
2. `submit()`发送`POST /hr/unit-staff-salary-expense/submit/{id}`，`cancel()`发送`POST /hr/unit-staff-salary-expense/cancel/{id}`；SDK不发送body。
3. 两个Portal处理函数都以请求成功后显示成功消息并刷新列表为成功判据；SDK进一步要求解包后的业务回执严格为`true`，否则抛错。成功只代表动作请求被接受，仍应重新`list()`核对状态是否变为审批中或已取消。

Portal当前固定检出仍保留上述两个处理函数；`submit`/`cancel`按钮曾按状态`0`/`1`接入，后续页面重构移除了当前模板中的按钮绑定，因此本地静态证据能确认请求实现和历史可达条件，但不能把当前模板称为已可点击验证。当前固定的Java `UnitStaffSalaryExpenseController`只声明`create/update/delete/get/page/import`，未声明`submit/{id}`或`cancel/{id}`；这两个动作的Java路由、DTO和权限注解尚未在该检出中得到后端证据，不能据此宣称真实环境已打通。

四个动作方法已写入`REPORT_UNIT_INTERFERENCE_COST_ALLOCATION_METHODS`、能力定义、invoke注册和共享AI契约；
`catalog.describe` 已能返回其 `prepare→submit→回查` 步骤。由于当前固定Java检出没有对应Controller路由，
契约保留“外部后端阻塞”说明，不能把静态接线当成真实环境已打通。
