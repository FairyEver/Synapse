# 菜单管理（`/dashboard/setting/menu/list`）

## 页面范围与证据

门户 → 系统设置 → 菜单管理，权限 `/dashboard/setting/menu`，使用 `platform` HTTP 实例；页面路径不命中 module-type 规则，因此浏览器不发送 `module-type`。

列表接口返回不区分系统的整棵菜单树。Portal 的新增、编辑、批量修改、搜索移动、批量添加子菜单、JSON 导入和删除按钮只在 `VITE_API_ENV_NAME=dev` 时显示；菜单导出 JSON/文本是浏览器本地下载，不是服务端 API，SDK 不伪造导出能力。

Portal 证据：`app/portal/menus/common.js`、`app/portal/views/dashboard/hr/setting/menu/list.vue`、`[mode]/[id].vue`、`components/edit-multiple-value.vue`、`composables/useTreeDelete.js`、`composables/useJsonMenuImport.js`，固定提交 `bbcfc35154`。

Java 证据：`HrSysMenuController`、`HrSysMenuServiceImpl`、`SysMenuDTO`、`SysMenuDao.xml`，固定提交 `b7a359adc9e`。Controller 的旧 `@RequiresPermissions` 是注释状态，但仍由登录会话、后端安全链和服务端业务校验决定实际是否可写；不能把开发环境按钮或注释权限当作越权许可。

## 能力与实际动作

| 页面动作 | SDK 能力 / 方法 | 请求与副作用 |
| --- | --- | --- |
| 读取菜单树 | `setting-menu-list` / `settingMenu.list` | `GET /admin-api/sys/menu/menuListNotBySystem`；非分页树 |
| 读取编辑详情 | `setting-menu-get` / `settingMenu.get` | `GET /admin-api/sys/menu/{id}`；只读 |
| 新建/添加下级 | `setting-menu-create` / `settingMenu.create` | `POST /admin-api/sys/menu`；返回新 ID |
| 新建多条、批量添加子菜单 | `setting-menu-create-many` / `settingMenu.createMany` | 按页面顺序逐条 POST；不是事务批量接口 |
| JSON 导入菜单树 | `setting-menu-import-tree` / `settingMenu.importTree` | 逐节点 POST；父节点失败时跳过其子树，同级继续 |
| 编辑/搜索移动 | `setting-menu-update` / `settingMenu.update` | `PUT /admin-api/sys/menu`；提交完整菜单对象 |
| 批量修改名称/授权标识 | `setting-menu-update-many` / `settingMenu.updateMany` | 只对发生变化的行逐条 PUT |
| 删除节点或子树 | `setting-menu-remove` / `settingMenu.remove` | `DELETE /admin-api/sys/menu/{id}`；传完整 children 时叶子优先逐条删除 |

## 参数、表单与权限规则

- 列表默认请求参数是 `{ order: '', orderField: '' }`；返回根节点数组，不是 `{list,total}`。`children=[]` 表示该节点没有已返回的子节点。
- 菜单 ID 和父菜单 ID 可能以字符串返回，以避免 Long 精度丢失；`pid=0` 表示一级菜单。
- 新建页面默认 `id: ''`、`name: ''`、`pid: '0'`、`permissions: ''`、`useSystem` 为人力系统、`project` 为学习项目。`useSystem`、`project`、`name` 是页面必填项；Java DTO 对 `pid`、`name` 也有校验。SDK 保留 Portal 请求中的 `permissions`、`useSystem` 和 `project`。
- 编辑先通过 `get` 读取完整对象，再提交 `id`、`name`、`pid`、`permissions` 及页面保留字段；搜索移动只是把 `pid` 改成新的父菜单。
- Portal 删除父节点不会调用一个级联删除接口，而是递归收集后序节点，先删叶子、最后删父节点。任何中途失败都可能留下部分已删除结果，不能报告为原子完成。
- JSON 导入逐节点创建，节点失败会记录错误且不继续创建该节点的 children；后续同级节点仍会继续。批量创建和批量修改同样是逐条请求，前序成功不会自动回滚。
- 读写失败、登录/权限问题、父菜单或子菜单约束、名称校验、网络超时均原样报告；写请求超时必须先重新读取菜单树再决定是否重试。

## 操作步骤

1. 调用 `list` 获取当前会话可见的完整树，使用节点 `id` 作为详情、父级和删除目标；不要按名称猜 ID。
2. 新建或添加下级时提交完整 `name/pid/permissions/useSystem/project`，保存返回 ID 后递归回查父级和授权标识。
3. 编辑或移动前先 `get`，保留未修改字段；成功后按 ID 回查 `name/pid/permissions`。
4. 批量动作完成后逐 ID 核对。树导入要分别交付 `created` 和 `failed`，不要把部分成功说成整棵成功。
5. 删除传入当前树节点的完整 `children`，成功或超时后确认所有目标 ID 已消失；只看空成功回执不算完成。
