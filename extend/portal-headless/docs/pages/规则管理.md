# 规则管理

页面路径：`/dashboard/platform/system/express/list`

Portal 菜单权限：`/dashboard/platform/system/express`

HTTP 实例：`platform`

`module-type`：Portal 菜单规则表没有为该路径计算出值，请求不发送该头。

## 1. 能力定义

| 能力 | SDK 方法 | 类型 | 页面动作 |
| --- | --- | --- | --- |
| `platform-rule-management-list` | `platformRuleManagement.list` | 只读 | 列表查询 |
| `platform-rule-management-get` | `platformRuleManagement.get` | 只读 | 详情/编辑页加载 |
| `platform-rule-management-validate` | `platformRuleManagement.validate` | 只读 | “验证规则” |
| `platform-rule-management-prepare-create` | `platformRuleManagement.prepareCreate` | 准备 | 新建表单本地校验 |
| `platform-rule-management-create` | `platformRuleManagement.create` | 写入 | 新建保存 |
| `platform-rule-management-prepare-update` | `platformRuleManagement.prepareUpdate` | 准备 | 编辑表单本地校验 |
| `platform-rule-management-update` | `platformRuleManagement.update` | 写入 | 编辑保存 |

Java Controller 另有删除、规则执行测试、运行引擎测试、类型和分组接口，但当前 Portal 页面没有对应入口，因此不纳入本页能力。

## 2. 参数契约

列表筛选字段：`ruleCode`、`ruleName` 是模糊筛选；`ruleType`、`ruleGroup`、`enabled`、`systemType` 是精确筛选。页面默认 `pageNo=1`、`pageSize=20`，支持 `10/20/50/100`。空字符串、`null` 和 `undefined` 会按 Portal `cleanParams` 过滤；未传 `enabled` 时后端将其默认成 `true`。

`ruleType` 和 `ruleGroup` 的候选分别来自 `base-dict-get` 的 `sales_rule_type`、`sales_rule_group`。`systemType` 是页面本地 `SYSTEM_OPTIONS_ALL`，候选为：科技 `8`、公共 `0`、人力 `1`、财务 `2`、资产 `3`、生产 `4`、采购 `5`、销售 `6`、门户 `7`、平台 `10`。

创建和编辑表单字段：

| 字段 | 规则 | 请求语义 |
| --- | --- | --- |
| `ruleCode` | 必填非空 | 编码；创建时后端还校验唯一性 |
| `ruleName` | 必填非空 | 规则名称 |
| `ruleExpression` | 必填非空 | QLExpress 表达式 |
| `ruleDescription` | 可空 | 缺省按页面空字符串处理 |
| `ruleType` / `ruleGroup` | 必填非空 | 使用对应字典 value |
| `enabled` | 必填布尔值 | `true` 启用、`false` 停用 |
| `priority` / `version` | 必填整数 | 原样提交 |
| `systemType` | 必填 | 使用上述本地候选值 |
| `id` | 仅编辑必填 | 来自 `list` 或 `get`；创建请求会移除 |

`get` 返回的规则表达式会把后端返回的字面 `\\n`、`\\r` 归一为真实换行；提交时不再额外改写用户输入。

## 3. 逐字段基准

Portal 列表调用：

```text
GET /admin-api/rulesManage/listByPage
```

参数由列表模块先放入 `order`、`orderField`、表单字段、`pageNo`、`pageSize`，随后 `cleanParams` 删除空值。返回兼容 `{list,total}`，并保留列表行的 `id`、规则字段、`enabled`、`priority`、`systemType`、`version`、`updateTime`。

详情调用：

```text
GET /admin-api/rulesManage/get?id=<id>
```

规则验证调用：

```text
POST /admin-api/rulesManage/validate
{ "expression": "..." }
```

返回 `{valid, message, errors}`。`valid=false` 是业务校验结果，不是请求失败；只有 `valid=true` 才继续准备写入。

创建请求：

```text
POST /admin-api/rulesManage/create
{ ruleCode, ruleName, ruleExpression, ruleDescription, ruleType, ruleGroup,
  enabled, priority, systemType, version }
```

编辑请求在同样字段前带 `id`，方法为 `PUT /admin-api/rulesManage/update`。Portal 后端对创建和编辑执行超级管理员检查；拥有菜单权限不代表拥有写权限，403 必须作为失败处理。

本轮已核对 Portal 列表/表单源码、Java Controller/DTO/Service、SDK 请求断言和 AI 契约。尚未在真实测试环境执行浏览器读请求，也未执行真实创建/编辑的 `prepare → submit → cancel` 记录；页面没有可达的撤销规则接口，取消只丢弃本地草稿。

## 4. 操作步骤

1. 读取 `list`；需要完整编辑字段时再用 `get({ id })`。
2. 新建或编辑先调用对应 `prepare`，得到 `result.draft`。
3. 提交前调用 `validate({ expression: result.draft.ruleExpression })`；`valid=false` 时修正表达式，不提交。
4. 用户确认且当前身份是超级管理员时，把同一个 `draft` 交给 `create` 或 `update`；用户取消时直接丢弃 `draft`，不调用网络接口。
5. 创建成功或超时后按 `ruleCode` 回查列表，再用 `get` 核对；编辑成功或超时后按 `id` 用 `get` 逐字段核对。写接口没有业务返回体，不能只凭 HTTP 成功判定字段已落库。
