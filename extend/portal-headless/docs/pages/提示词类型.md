## 权限码为什么有两代，而当前目录与能力定义都写 v2

两个菜单文件里都有这一页，权限码不一样（`mall.js` 是 v1、`mall.v2.js` 是 v2）。
**生效的是 v2**：`app/portal/menus/index.js:62-64` 只 import 了 `./mall.v2.js` 的 `all_menus`，
`mall.js` 里那份 `all_menus` 全仓没有任何引用。

`generated/page-catalog.json` 按 `menus/index.js` 的实际 import 记录 `mall.v2.js` 的 **v2**，
与当前线上生效的权限码一致；`mall.js` 只作为历史对照保留。

旧 v1 与 v2 对可见性判定等价：`src/catalog/visibility.ts:122` 的 `normalizeVisibilityKey` 会把
`/dashboard/platform-v2` 归一成 `/dashboard/platform`；能力定义和目录都使用当前生效的 v2。

## 列表：**实测**与基准逐字段一致

`baseline/ai-prompt.browser.json` 里这一页的那一条（2026-09-21 抓到）：

```
GET https://biz-api-test.wodecorp.cn/admin-api/system/tip-type/page?order=&orderField=&label=&name=&pageNo=1&pageSize=20&_t=<ts>
```

**与源码推导逐字一致，没有冲突。** 参数顺序由 `common/libs/renren/list.js:472-483` 的
`logicFetch` 决定，测试里拿基准逐字段比（含键序、含空值参数）。

键序来自 `common/libs/renren/list.js:472-483` 的 `logicFetch`：
`{ order, orderField, ...表单初值, pageNo, pageSize }`，`_t` 由 `platform.js` 的请求拦截器追加。
这一页的表单初值是 `form: { label: '', name: '' }`（`type/list.vue:60-63`），所以：

- `label` = **类型名称**、`name` = **类型值** —— 名字与直觉相反，别搞反；
- 三个空值参数**照发**（`qs.stringify` 的 `skipNulls` 只丢 `undefined`/`null`，不丢空串），
  这就是 conventions 第 4 条那条 renren 默认空值参数。

后端（`TipTypeMapper.selectPage`）对两个都是 `likeIfPresent` ⇒ `LIKE '%x%'`。

## 候选：`/list` 一个筛选参数都不带

技能列表页与技能编辑页的「类型」下拉走的是同一个 `useTypeOptions()`
（`prompt/share.js:95-122`），**页面写的是 `http.get('/admin-api/system/tip-type/list')` —— 没有 config**：

```
GET /admin-api/system/tip-type/list?_t=<ts>
```

所以能力 `ai-prompt-tip-type-options` 在**不传关键字时也只发 `_t`**，与页面逐字一致；
传了 `name`/`label` 才追加（后端 `getTipTypeList` 同样支持这两个 `like` 条件）。

这一页**不是**长选项参数的场景：类型是一张小字典表，页面一次全量拿。

## 写链路：**没有 `prepare`**，撤销就是 `remove`

| 动作 | 请求 | 出处 |
| --- | --- | --- |
| 新建 | `POST /admin-api/system/tip-type`，body `{ name, label }` | `[mode]/[id].vue:32-42` 的 `objectURL` + `form.js:131`（`isCreateMode` 走 post） |
| 修改 | `PUT /admin-api/system/tip-type`，body `{ id, name, label }` | 同上，`form.js:131` 的另一支 |
| 详情 | `GET /admin-api/system/tip-type/{id}` | `form.js:176`（编辑模式挂载时真的会调） |
| 删除 | `DELETE /admin-api/system/tip-type/{id}`，无 body、无 params | `list.vue:59` 的 `deleteURL` + `list.js:516-520` |

**为什么没有 `prepare`**：与 `attendance-team` / 作业管理 / 班次管理同款判断 ——
这一页**没有任何"提交前先问后端一次"的接口**。会议室那条线的 `prepare` 是因为
"这次要人工指定哪些审批人"会改变提交载荷；这里没有对应物。派生出来的写能力是
`create` / `update` / `remove` 三条，**撤销**就是 `remove`。

### ⚠️ 修改的 body 是**推断**，不是实测

页面走 `useFormPageModule` 的编辑模式：先 `GET /{id}` 把**整个响应**灌进 `formState`
（`form.js:176` 的 `formStateSet(await _http.get(...))`），再 `PUT` 回去。
所以浏览器发的 body 应该是 `TipTypeRespVO` 的全部字段
（`{ id, name, label, deleted, createTime }`）。

SDK 只发 `TipTypeSaveReqVO` 认的三个（`{ id, name, label }`），理由是后端
`updateTipType` 是 `tipTypeMapper.updateById(BeanUtils.toBean(VO, DO))`
（`TipTypeServiceImpl.java:43-49`），MyBatis-Plus 的 `updateById` **只更新非 null 字段** ——
少发 `deleted`/`createTime` 不会把它们写空，多发只是把原值回写一遍。
**要绝对逐字复刻得改成"先 GET 再整包 PUT"，那一版故意没做**（一次写变两次请求，
而且 body 随响应字段顺序漂移）。**基准 2026-09-21 到位，但里面 0 条非 GET ⇒ 这条仍然没定**：`test/ai-prompt.test.ts` 里对应那条断言是 `it.skipIf` 挂起的。要定它只有两条路 —— 抓一次带 PUT 的基准，或派单方跑真机时把实际 body 记下来。

### 删除会被后端拦

`TipTypeServiceImpl.deleteTipType`（`:51-60`）先查 `sys_tip_template` 里有没有用这个类型：

```java
if (CollectionUtils.isNotEmpty(tipTemplateDOS)) {
    throw exception("该类型已绑定提示词模版,无法删除!");
}
```

所以"删除失败"最常见的原因是**有技能在用这个类型**，不是权限问题。
（业务冲突按 conventions 第 9 条报 500，别按状态码分类。）

### 新建没有唯一性校验

`createTipType` 直接 `insert`，后端**不查重**（`TipTypeServiceImpl.java:37-41`）。
所以重发一次就多一行 —— 防重要走门面的 `createIdempotent`（conventions 第 14 条）。

`name` / `label` 的必填只在页面的 `rules` 里（`[mode]/[id].vue:38-41`），
`TipTypeSaveReqVO` **没有** `@NotBlank` ⇒ 无头侧不做这一步校验的话，空名字会被真的写进去。
所以能力在发请求前就拦住了（`assertTipTypeDraft`）。

## 真实验证：读链路有基准，写链路一次真机请求都没发过

- **读链路（列表 / 候选）/ 权限与头**：由 `baseline/ai-prompt.browser.json` 逐字段证实
  （见上面「列表」一节）。测试里是 `describe.skipIf(!HAS_BASELINE)` 那一组，现在真的在跑。
- **写链路（`POST` / `PUT` / `DELETE`）**：**没有**任何实测。写这份能力时全程只跑了本地的
  `tsc` / `vitest`（axios 适配器是假的，请求不出进程）：**没有开浏览器、没有起 `bsk` 会话、
  没有跑任何 smoke 脚本、没有向测试环境发过任何一个非 GET 请求。**
  基准里 **0 条非 GET**，所以那几条断言是 `it.skipIf` 挂起的 —— 抓不到就永远不跑，
  **别把"测试全绿"读成"写链路已验证"**。

真机写验证由**派单方统一跑**，清单见下。跑完把实际请求/响应回填到本节。

## 基准里那两条「外壳请求」不是页面契约

这一页的基准里有 3 条，其中两条是 app 外壳拉的、**本页没有发**：

```
GET /admin-api/org/sensitive/info?_t=<ts>
GET /admin-api/bpm/task/list-by-category?finished=1&pageNo=1&pageSize=10&_t=<ts>
```

它们出现在这一页的 `pagePath` 下，只是"抓的时候停在这一页"；别把它读成"提示词类型页也调待办"。
测试里对它们只做"确实在基准里、且不是我们发的"这一条断言，不数条数。

## 基准到位后**仍然**没解决的

基准 2026-09-21 到位，读链路全绿了；下面这些**基准里没有**（0 条非 GET），或光有基准也判不了：

- **修改的 PUT body** 究竟是 `{ id, name, label }` 还是「GET 整包回写」—— 基准里没有 PUT。
- **三页的 `DELETE`** 是不是真的没有 `_t`、没有 body —— 基准里没有 DELETE。
- `/admin-api/system/tip-type/list` 的参数形态**已有基准**：零参数（只有 `_t`），实测证实；
  但"给关键字之后长什么样"没有基准（页面从不带筛选），仍是推断。
- 页面 `allow-clear` 清空后键是空串还是消失（要人工点一次再抓）—— 这条留在 `it.todo` 里。

## 测试方法学：一条**假绿**测试是怎么被反证抓出来的

`ai-prompt-tip-type-create` 的两条必填守卫，最初写成
`await expect(async () => ...).rejects.toThrow(/name/)`。
**故意删掉守卫再跑，它照样绿** —— 因为 `buildTipTypeCreateBody` 里
`[...draft.templateIdList]` 之类展开 `undefined` 会抛 V8 的
`TypeError: draft.xxx is not iterable`，**错误消息里带着源码表达式**，把 `/name/` 这类
"只写字段名"的正则匹配上了。也就是说：断言匹配到的是**别的原因导致的失败**，不是你要拦的那一条。

已经处理：这个文件里所有 `rejects.toThrow` 改成匹配**错误文案里的中文原因**
（如 `/必须显式给 templateIdList/`），然后再删一次守卫确认变红。
**后面加断言的人请注意这条**：`toThrow(/字段名/)` 在这种"守卫可能被删"的场景里是不可靠的。
