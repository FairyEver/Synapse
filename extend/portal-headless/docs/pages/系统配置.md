# 系统配置

## 能力定义与页面范围

平台设置 → 系统配置，菜单 `/dashboard/platform/system/custom/list`，当前 Portal v2 权限为
`/dashboard/platform-v2/system/custom`。页面使用 platform 请求实例，未命中 module-type 规则，因此 SDK 不发送
`module-type`。同名的旧 mall-admin 页面不作为本节点依据；本节点核对的是 Portal `app/portal/views/...` 页面。

Portal 列表只有查询、新增和编辑入口，没有顶层删除。编辑页内的“新增/编辑/保存/取消/删除”只操作 `body` JSON
数组的本地行状态，最终仍由一次系统配置保存/修改请求提交；SDK 不把这些本地行操作伪装成独立 HTTP 能力。

实现与接线：`src/capabilities/platform-system-custom.ts`、`src/capabilities/index.ts`、
`src/capabilities/invoke.ts`、`src/index.ts`、`src/server.ts`；AI 契约由
`src/catalog/contracts-business.ts` 发布。依据 Portal `test/portal/main @ 3622e02147` 的列表/表单源码和 Java
`test/test @ c3348150f42` 的 `ManageSysDiyConfController`、`ManageSysDiyConfService`、`SysDiyConfDTO`。

## 能力和请求

| 能力 | SDK 方法 | 请求 | 页面行为 |
|---|---|---|---|
| `platform-system-custom-list` | `list(query?)` | GET `/mall-manage-api/sys/diyConf/page` | 默认 `{order:'',orderField:'',pageNo:1,pageSize:20}`；页大小为 10/20/50/100 |
| `platform-system-custom-prepare-create` | `prepareCreate(form)` | 不发请求 | 执行页面必填和 body JSON 数组校验，生成创建请求体 |
| `platform-system-custom-create` | `create(form)` | POST `/mall-manage-api/sys/diyConf/save` | 页面保存创建表单；响应业务文字不作为 SDK 业务对象返回 |
| `platform-system-custom-prepare-update` | `prepareUpdate(form)` | 不发请求 | 对列表桥接的编辑表单生成修改请求体 |
| `platform-system-custom-update` | `update(form)` | POST `/mall-manage-api/sys/diyConf/update` | 页面保存编辑表单；不是 PUT |

列表返回 `{list,total}`，行字段投影为 `id/code/name/body/info/modifiedTime`。ID 保留字符串形态避免长整数精度损失；
`modifiedTime` 保留服务端字符串或数字原值。列表不提供筛选表单，SDK 也不额外发送 name/code 等猜测出来的筛选字段。

## 表单提交规则

页面初始表单是 `{id:'', code:'', name:'', info:'', body:''}`，只对 `code` 和 `name` 做 required 校验；空字符串
会在请求前失败，页面没有“不能全空格”或长度限制规则。`info` 未填写时按空字符串提交。

`body` 的页面 computed getter 执行 `JSON.parse(form.body || '[]')`，提交时执行
`JSON.stringify(newBodyState.value)`。因此 SDK 的 `prepareCreate/prepareUpdate` 和实际写方法都：

- 接受页面已有的 JSON 字符串，也接受等价的配置项数组便于无头调用；
- 必须是 JSON 数组，数组元素必须是对象；对象中的未知字段原样保留；
- 重新 `JSON.stringify`，去掉原始 JSON 的空白差异，空字符串/null/省略 body 按 `[]` 处理；
- 创建请求体保持页面初始 `id:''`，更新必须提供正整数 ID；创建和更新都提交 `code/name/info/body`，更新额外提交 `id`；
- 页面表格本地新增的行形态是 `{text:'', value:'', info:'', pid:+new Date()}`。`pid` 只是页面行 key，SDK 不替调用方生成或改写它。

页面编辑从列表行 `pick(record, ['id','code','name','info','body'])` 桥接数据，没有再调用详情接口；SDK 不增加一个
页面不可达的 `get` 能力。取消路由和 body 行的取消都不发请求。创建/更新没有可用的撤销接口；请求超时先重新 list
按完整 `code/name` 核对，再决定是否重试，不能盲目重复创建。

## AI 数据说明和证据边界

AI 描述入口实际返回每个能力的输入、请求前校验、输出字段、body 消费方式、后续核实步骤和写入不确定性处理。
写能力的 `idempotency` 说明后端没有 requestId，不能把重复发送当成安全重试。

离线测试 `test/platform-system-custom.test.ts` 覆盖权限、module-type、默认分页、长 ID、创建/更新 POST 路径、表单
必填、JSON 数组负例、空 body 归一化和未知 body 字段保留。已核对 Java Controller 的 page/save/update 路径以及 DTO
字段。尚未在真实测试环境执行浏览器抓包或真实写入回查，AI 契约保留该证据缺口，不把离线测试宣称为线上行为证据。
