# 待办办理（`/dashboard/flow/form/detail` 与 `/dashboard/backlog/task-examine/batch-process`）

**SDK 的审批侧**，提供本人待办的通过、不通过、转办、委派、回退与批量办理。四件套的另外三件：

| 件 | 文件 |
| --- | --- |
| 能力定义与参数契约 | `src/capabilities/task-action.ts` |
| 逐字段基准 | `baseline/task-action.browser.json` |
| 回归测试 | `test/task-action.test.ts`（65 例） |
| 真实环境冒烟 | `smoke/task-action.mjs` |

前面五条流程线（通用审批 / 请假 / 用车 / 差旅费 / 产品设计文档审核）做的都是**发起侧**：
提交一条单据、把待办推给别人。本模块负责另一侧：读取别人发起、分配给当前用户的任务并办理。写请求已接执行层，但成功办理的双账号端到端验证仍缺失，不能将接口接线等同于线上验证。

## 一、这条能力与流程无关，只与**任务**有关

会议室那条线以后端 controller 为界分能力，流程表单那条线以表单字段为界分能力。
这一条**两者都不是**：它操作的对象是 Flowable 的 **task**，入口是 `/bpm/task/**` 与
`/bpm/process-instance/**`——**对 82 个流程一视同仁**。

所以契约里**一个流程字段都没有**：只有 `taskId` / 审批意见 / 附件 / 抄送人 / 接收人。

| 能力 | 读写 | 接口 | 页面 |
| --- | --- | --- | --- |
| `task-action-instance` | 读 | `GET /bpm/process-instance/get?id=` | 流程详情 |
| `task-action-workflow-path` | 读 | `GET /bpm/process-instance/getWorkflowPath?processInstanceId=` | 流程详情 |
| `task-action-approve` | **写** | `PUT /bpm/task/approve` | 流程详情 |
| `task-action-reject` | **写** | `PUT /bpm/task/reject` | 流程详情 |
| `task-action-transfer` | **写** | `PUT /bpm/task/transfer` | 流程详情 |
| `task-action-delegate` | **写** | `PUT /bpm/task/delegate` | 流程详情 |
| `task-action-return-options` | 读 | `GET /bpm/task/list-by-return?id=` | 流程详情 |
| `task-action-return` | **写** | `PUT /bpm/task/return` | 流程详情 |
| `task-action-batch-approve` | **写** | `PUT /bpm/task/batchApprove` | 批量办理 |
| `task-action-batch-reject` | **写** | `PUT /bpm/task/batchReject` | 批量办理 |

## 三、「办理」这条链实测到的是什么

### 3.1 一个任务从「在我的列表里」到「办完」

```
待办列表   GET  /bpm/hr/task/list-by-category-web?finished=1&…      ← row.id = taskId
   ↓       （只读，backlog-task-examine-list）
办理页     GET  /bpm/process-instance/get?id=<流程实例 id>
   ↓       GET  /bpm/process-instance/getWorkflowPath?processInstanceId=<…>   ← 算出「该我办」的任务
   ↓       页面判据三条：status ∈ {1 审批中, 6 委派中} 且 assigneeUser.id == 我（递归 children）
办理       PUT  /bpm/task/approve  |  /reject  |  /transfer  |  /delegate  |  /return
   ↓
状态变化   task.status 1 → 2（通过）/ 3（不通过）/ 5（回退）；委派中为 6；被取消为 4
          流程实例按下个节点的走向继续，或进终态（status 2 通过 / 3 驳回 / 4 取消）
```

**状态值来自后端 `BpmTaskStatusEnum`**（`erp-module-bpm` 的 `enums/task`）：
`0 待审批（只出现在加签产生的、还没轮到的任务上）`/`1 审批中`/`2 通过`/`3 不通过`/`4 已取消`/
`5 已退回`/`6 委派中`/`7 通过中`。页面的 `loadRunningTask` 只认 1 与 6 —— 这是「该我办」的判据。

### 3.2 请求体（逐字段，源码直读）

单个办理（页面上通过 / 不通过共用一个 `data` 对象，`flow/form/detail/index.vue:503-509`）：

```jsonc
// PUT /bpm/task/approve  或  PUT /bpm/task/reject
{ "id": "<taskId>", "reason": "…", "attachmentUrl": "", "attachmentName": "", "copyUserIds": [] }
```

⚠️ **两个附件键没传时页面发的是空串，不是省略这个键**——`auditForms` 的初值就是空串。SDK 照抄。

转办 / 委派 / 回退（三个弹窗组件）：`{ "id", "assigneeUserId" | "delegateUserId" | "targetTaskDefinitionKey", "reason" }`。

批量（`batch-process/index.vue:219-264`，`buildPayload()` + 展开）：

```jsonc
// PUT /bpm/task/batchApprove
{ "ids": ["…"], "reason": "…", "type": 0, "attachmentUrl": "u1,u2", "attachmentName": "n1,n2",
  "copyUserIds": [], "variables": {} }
// PUT /bpm/task/batchReject —— 与通过只差最后那个 variables
{ "ids": ["…"], "reason": "…", "type": 0, "attachmentUrl": "", "attachmentName": "", "copyUserIds": [] }
```

两处容易看错的地方：`type: 0` 与 `variables: {}` 都是**页面写死的**；附件是**两个逗号拼接的字符串**，
不是单个办理那种 `[{url,name}]`。

### 3.3 为什么**不做** `/bpm/hr/task/approve`（待办事项页那个办理弹窗）

「待办事项」页的办理弹窗（`backlog/components/agreement-examine.vue:44-46`）打的是
`POST /bpm/hr/task/approve`，body `{id, reason, type}`。**它不是一条通用接口**，后端源码里写得很清楚
（`erp-module-hr` 的 `BpmHrTaskServiceImpl.approveTask/rejectTask`）：

- `type == null` → **原样转调**通用的 `bpmTaskApi.approveTask`（就是本能力的 `PUT /bpm/task/approve`），多绕一层；
- `type ∈ {1..6}` → 做 **KPI 协议族专属**的事：回写 `kpi_year_protocol` /
  `kpi_month_protocol` / `kpi_month_protocol_task`、插薪资基础数据、锁评分流程、给签订人**发消息**。

把 `type` 开成参数，等于把「KPI 协议族」这个具体流程族的枚举写进一条声称通用的能力里（正好违反
「契约要通用」），而且它动的是真人的 KPI 与薪资数据。**所以只做通用那一条，KPI 族（category 2..7）的办理没做。**

## 四、自审规则：本单要解决的那个技术问题，以及为什么**解不了**

### 4.1 问题

要验证「办理」，得有一条**留给自己办**的待办。而「自己提交 + 审批人填自己」会触发后端一条规则：

```java
// BpmTaskServiceImpl:886-916  tryAutoApproveWhenStartUserIsAssignee()
if (startUserId == null || !startUserId.equals(taskAssigneeId)) return false;
autoApproveReqVO.setReason("流程发起人与审批人相同，自动审核通过");
approveTask(taskAssigneeId, autoApproveReqVO);
```

`BpmTaskEventListener.taskCreated()`（`:85-94`）的**两条分支都会走到它**（HR 流程直接调，
非 HR 流程经 `updateTaskStatusWhenCreated → scheduleTaskAutoApproveAfterCommit → executeTaskAutoApprove` 调）。
⇒ 流程当场进终态，`cancel-by-start-user` 必然报「流程不处于运行中」，**那条单据就永远撤不掉**。

### 4.2 试过的四条路，全部走不通

| 思路 | 为什么不行 |
| --- | --- |
| 用**第二个测试账号**发起、审批人填本账号 | 环境里没有第二个可用账号（`docs/process-forms.md` §6 也记着「没有第二个测试账号」） |
| 把审批人填自己，但**绕开**自审规则 | 逃生口是流程变量 `BPM_SKIP_AUTO_APPROVE_TASK_DEFINITION_KEY`（`shouldSkipAutoApprove()` 命中一次后自删）。**客户端注入不了流程变量**：五个流程的 `startBpmProcess()` 各自 `new HashMap<>()` 或由服务端 builder 构造，全仓 `.setVariables(` 没有一处吃调用方给的 map |
| 用**多节点**流程：先办第 1 个节点，再撤销整条流程 | 自审规则是**逐节点**判的（`startUserId == assignee` 就秒批），第 2、3 个节点会被链式秒批，流程照样进终态 |
| 办**已有的**待办 | 待办列表里确实有 25 条（其中 14 条流程还是本账号自己发起的），但那些是**真实单据**——不是本单制造的测试数据，一条都不能碰 |

### 4.3 实证（不是推断）

`smoke/task-action.mjs` 第 2.6 节，只读：翻「我的流程」最近 3 页里**没被取消**（`status !== 4`）的
47 个实例，逐条读 `getWorkflowPath` 找理由文案：

```
有效样本 47 个实例（另跳过 13 个已取消）
「自动审核通过」命中：22 条
  ★ key=hr_general_approval task="发起人自选2" status=2 assignee=18243
    reason="流程发起人与审批人相同，自动审核通过"
  ★ key=own_vehicle_transport_expense_request_form task="财务经理" assignee=<null>
    reason="找不到任务的审批人，自动审核通过"   ×N
```

其中第一条正是**本单会用到的那条流程、那个节点**（`hr_general_approval` 的
`Activity_1o1sabd` / 发起人自选2），`assignee` 就是本账号 ⇒ **规则在这套环境上真的在跑，
不是"源码里有、环境上没部署"**。

> 本轮第一版侦察把这个过滤写成了「翻最近 10 条」——那 10 条**全是已取消的实例**，
> 任务记录已被删，于是命中 0 条、看起来像"规则不生效"。这是最典型的
> **假绿样本**（"没测到"被读成"已验证"）。改成只统计未取消的实例才有上面的 47 个有效样本。

### 4.4 ⇒ 结论与代价

**单一账号下造不出「留给自己办」的待办。** 想端到端验证办理链路，只差一样东西：
**第二个测试账号**（用它发起、审批人填本账号）。

这是后端的设计，不是 SDK 的缺陷；本单**如实记录，不绕**，也**没有**为了凑一个"已验证"去多留一条撤不掉的单据
（测试环境里已经有 3 条了）。

## 五、真实验证记录（2026-09-21，测试环境）

### 5.1 实际跑了什么

```bash
smoke/with-portal-token.sh node smoke/task-action.mjs                 # 只读侦察
smoke/with-portal-token.sh node smoke/task-action.mjs --probe-write   # 只读 + 写形状探测
```

浏览器基准：用 `bsk` 在**本账号自己发起的**实例上打开办理页，抓三个读请求（一次会话抓 URL、
一次会话抓 header 集合），会话用完即停。**基准里没有任何写请求**，理由见基准文件。

### 5.2 结果

| 项 | 结果 |
| --- | --- |
| 身份 | 本账号 id = 18243（从「我的流程」最近一条的 `startUser.id` 推出来） |
| 待办列表 | `finished=1` 共 25 条，横跨 13 个流程；其中 14 条的流程由本账号发起 |
| 读链路 | 在一台**自己发起、还在跑**的实例上跑通 `instance → workflowPath → myRunningTasks`，返回 1 个「该我办」的任务（节点名 `发起人自选2`，`status=1`，`assignee=18243`） |
| 自审规则 | 47 个未取消样本里命中 22 条「自动审核通过」（见 §4.3） |
| 五个流程的 BPMN | 通用审批 1 个 userTask（`Activity_1o1sabd`，strategy 35 发起人自选）；用车 3 个（全是 35）；产品文档 3 个（2 个 35 + 1 个 30）；请假 4 个（全是 30，后端按角色算）；差旅费 10 个（30/60/22，无 35）；会议室 **0 个**（所以它不产生待办） |
| **写形状探测** | 8 个端点各打一个**必然不存在**的 task id，**全部**回任务级错误 `code=1009005002 流程任务不存在`，**0 条参数级错误**（见 §5.3） |
| 基准对齐 | 三个读请求的 path / 参数名 / header 集合与浏览器抓到的逐字段一致（`_t` 是一次性时间戳，测试里归一化） |

### 5.3 `--probe-write` 到底证明了什么、没证明什么

**证明了**：路由存在、HTTP 方法正确、**body 的字段名被后端读到了**。
判据是「错误类型」：如果 SDK 把 `id` 写成了别的名字，后端 `@NotEmpty` 会先报
「任务编号不能为空」（**参数级**）；实际拿到的是「流程任务不存在」（**任务级**）——
说明 `id` / `reason` / `assigneeUserId` / `delegateUserId` / `targetTaskDefinitionKey`
这些字段都真的落到后端 VO 上了。转办/委派/回退的 `reason` 是 `@NotEmpty`，
拿不到参数级错误这一条同时也证明了 `reason` 传对了。

**没有证明**：**办理成功**这件事本身。那需要一条真的分配给我的待办（§4）。

### 5.4 动了哪些单据、打扰了谁

| 问题 | 回答 |
| --- | --- |
| 创建了什么 | **什么都没有。** 本轮一次写请求都没有发出（`--probe-write` 打的是不存在的 task id，后端在 `validateTask()` 第一步就抛错） |
| 办理了谁的待办 | **一条都没有。** 脚本没有「真的办理」这个模式 |
| 打扰了谁 | **没有人。** 没有提交流程、没有推待办、没有抄送、没有转办/委派 |
| 读了什么 | 本账号自己的待办列表（25 条，含别人提交给本账号的）；本账号自己发起的流程实例（47 个未取消 + 13 个已取消）。**只打印流程 key / 节点名 / 状态 / 数字 id，没有打印任何审批内容或姓名** |
| 需要复原什么 | **没有**。无副作用，无需复原 |
| 浏览器的使用 | 两次 bsk 会话，各自用完即 `session stop`；打开的是一条**本账号自己的**流程详情（只读），没有点任何按钮 |

## 六、参数契约

| 参数 | kind | 必填 | 说明 |
| --- | --- | --- | --- |
| `taskId` | text | 是 | **任务 id**（请求体里的 `id`）。来自待办列表那一行的 `id`，或 `workflowPath` 里 `assigneeUser.id` 是我的那个任务的 `id` |
| `taskIds` | text | 是（批量） | 任务 id 数组，至少一个 |
| `reason` | text | 通过时否 / **驳回、转办、委派、回退时是** | 审批意见。通过时空串由后端替换成「无」 |
| `attachmentUrl` / `attachmentName` | text | 否 | 页面**没传时发空串**（不是省略），SDK 照抄 |
| `copyUserIds` | search | 否 | 抄送人。⚠️ 会真的通知到人。**必须先按关键字查**（D6/H35） |
| `assigneeUserId` / `delegateUserId` | search | 是 | 新审批人 / 接收人。**会真的把待办推给这个人** |
| `targetTaskDefinitionKey` | enum | 是 | 回退到的节点，取值来自 `returnOptions()` |
| `attachments` | text | 否（批量） | `[{url,name}]`，提交时被拼成两个逗号分隔的字符串 |

**长选项保护**：转办 / 委派 / 抄送人三处的人选一律走 `general-approval-user-search`
（`/system/user/simple-page` + 强制 keyword，拒绝 `pageSize=-1`）。
⚠️ **这是本能力唯一一处刻意偏离浏览器的地方**——页面在这三处自己都是
`simple-page?pageNo=1&pageSize=500` **无关键字翻到底**（基准里记着，十几条请求），
无头下不照抄（设计 D6 / H35）。

**防重**：7 个写操作各配一个 `*Idempotent` 变体（`requestId` 参与，`target` 取 taskId）。
比五条流程线「只包 submit」更宽，因为 `/bpm/task/**` 零幂等且失败形态最坏——
第一次其实成功了，超时重发第二次会拿到「流程任务不存在」，**调用方会把成功读成失败**。

## 七、反证记录（改坏了会不会红）

`test/task-action.test.ts` 65 例，全绿。反证跑了 **27 处变异，27 处全红，等价变异 0 处**

另外两处是**我自己写错的变异**（改的是没被调用到的分支），已换成能真正改变行为的锚点。
=> 「一轮全绿」不等于测试够强；上面这张表就是证据。

## 八、尚未覆盖（如实列出，不要读成「已完成」）

- **写链路没有端到端跑过**（§4）。`PUT /bpm/task/approve` 真的把任务办成 `status=2`、
  流程往下走的**那一次**，本轮没有发生。不要把「形状对」读成「已验证」。
- **加签 / 减签没做**：后端有（`BpmTaskController:258-269` 的 `create-sign` / `delete-sign`），
  但**前端一个调用点都没有**（全仓 grep 命中 0），页面上用户到不了这两个入口。
  按仓库纪律（不实现页面上不存在、又验证不了的东西），不做。
- **KPI 协议族（category 2..7）的办理没做**，理由见 §3.3。
- **`POST /bpm/hr/task/update-assignee` 没做**：同样没有前端调用点，且它要求
  `assignee == 我`（`BpmHrTaskServiceImpl.checkTask()`），与 `transfer` 覆盖面重叠。
- **转办 / 委派 / 回退的「办完长什么样」没见到**：形状探测只到「任务不存在」那一层，
