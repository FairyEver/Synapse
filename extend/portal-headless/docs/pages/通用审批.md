## 三、真实请求序列（浏览器抓包）

基准：`baseline/general-approval.browser.json`。打开表单并填好两个必填字段后，与本流程相关的请求是：

```text
GET  /admin-api/bpm/process-definition/get?key=hr_general_approval&_t=<ts>
GET  /admin-api/system/user/simple-page?pageNo=1&pageSize=500          ← 无关键字，一次 500 条，重复 3 次
POST /admin-api/hr/general-approval/getTemporaryRequiredStartUserSelectTasks
     body {"applicationItem":"SDK-TEST-baseline","applicationContent":"SDK-TEST-baseline content",
           "attachments":[],"copyUserIds":[]}
```

三条要点：

1. **第二条是「长选项」的现场**：页面自己 `pageNo=1&pageSize=500`、**不带任何关键字**地拉人员
   （该账号全量 4225 人，`simple-list` 实测 4225 条）。SDK 的 `searchUsers()` 强制要关键字，
   就是不照抄这条（设计 D6 / H35）。
   > 顺带记一条与源码**不一致**的事实：`035` 的 `fetchCopyUserOptions()` 写的是
   > `GET /admin-api/system/user/simple-list`（全量），而实际抓到的是 `simple-page?pageSize=500`。
   > 两者都是"无关键字的大批量拉取"，结论不变；记在这里免得后人拿着源码那句话去争论。
2. **`getTemporaryRequiredStartUserSelectTasks` 的 body 就是 `buildGeneralApprovalSubmitData()` 的产物**，
   **没有 `id` 字段**（会议室那条线有 `id: null`，这条没有）。键顺序
   `applicationItem → applicationContent → attachments → copyUserIds`。
   `create` 的 body 就是它再加一个 `startUserSelectAssignees`（页面 `handleSubmit` 的最后一步）。
3. **这个 POST 的请求头里没有 `module-type`**（抓包实测），与 SDK 一致。

## 四、审批人节点：本条线最要紧的一段

`prepare()` 打的这个接口**返回非空**——这是会议室那条线从没见过的：

```jsonc
POST /admin-api/hr/general-approval/getTemporaryRequiredStartUserSelectTasks
→ {"code":0,"ret":"SUCCESS","data":[{
     "id":"Activity_1o1sabd", "name":"发起人自选2",
     "approvalMode":"SEQUENTIAL", "approvalModeName":"依次审批",
     "executionMode":"SEQUENTIAL", "completionRule":"ALL_APPROVED",
     "minSelectCount":1, "maxSelectCount":null,
     "selectionOrderRequired":true,
     "approvalDescription":"所选人员按选择顺序依次审批，全部通过后节点通过"}]}
```

**接口名字不能猜**（`docs/process-forms.md` §5.3 第 1 条）：后端 `GeneralApprovalController`
里 **两个都写了**（`/getRequiredStartUserSelectTasks` 与 `/getTemporaryRequiredStartUserSelectTasks`），
**前端用的是后者**。SDK 跟前端走，用后者。

**后端会强校验**（`BpmProcessInstanceServiceImpl.validateStartUserSelectAssignees`）：

| 规则 | 错误码 |
| --- | --- |
| 每个 `START_USER_SELECT` 节点必须有非空 assignees | `…ASSIGNEES_NOT_CONFIG` |
| 列表里不能有 null | `…ASSIGNEE_ID_NULL` |
| 不能重复 | `…ASSIGNEES_DUPLICATE` |
| 人数落在 min/max 内 | `…ASSIGNEES_COUNT_INVALID` |
| 用户必须真实存在 | `…ASSIGNEES_NOT_EXISTS` |

`assertAssigneesForTasks()` 复刻了**前四条**（第五条要另打接口，且查完也可能变），
把必然失败的写请求挡在本地：**写操作会惊动真人，能让它红在前面就红在前面**。

### ⚠️ 顺手挖出来的一个坑：**审批人不能选发起人自己**

后端有一条「**流程发起人与审批人相同，自动审核通过**」（`BpmTaskServiceImpl:913-916`，
`reason` 文案就是这句）。2026-09-20 第一次真实提交时选了本人，
`create` 返回成功后**流程当场走完**，于是 `cancel` 必然报「流程取消失败，流程不处于运行中」——
那条测试单据就永远撤不掉了。**这不是 cancel 的缺陷，是它的正确行为**，
但做测试前必须知道：`submit` 的审批人要选**别人**。
`smoke/general-approval.mjs` 把这条写成了提交前的一次拒绝（从「我的流程」最近一条的
`startUser.id` 推出"我是谁"，再和审批人比对）。

## 五、操作步骤

```ts
// 0) 流程定义（只读，可选）
await sdk.generalApproval.definition()          // → { name: '通用审批', formFields: null, … }

// 1) 选人（长选项：必须先给关键字）
const { list } = await sdk.generalApproval.searchUsers({ keyword: '姚' })

// 2) prepare（只读）：算出这次要人工指定哪些审批人节点
const draft = {
  applicationItem: 'SDK-TEST-申请事项',
  applicationContent: 'SDK-TEST-申请内容',
  attachments: [],        // [{ url, name }]，url 用 sdk.baseUpload.upload({ folder: 'HR/approval', … }) 拿
                          // ⚠️ name 的扩展名必须在表单的 accept 白名单里（`.txt` 会被本地拦下）
                          // ⚠️ 上传能力要 OSS 凭据；冒烟里用 smoke/with-oss-credentials.sh 注入
  copyUserIds: [],        // 抄送会真的通知到人，测试留空
}
const { tasks } = await sdk.generalApproval.prepare(draft)
// → 1 个节点：发起人自选2 / 至少 1 人 / 顺序有意义

// 3) 按后端规则本地预检，再提交（写操作，会推真人待办）
const assignees = { [tasks[0].id]: [list[0].id] }
assertAssigneesForTasks(tasks, assignees)
const businessKey = await sdk.generalApproval.submit(draft, assignees)

// 4) 查（两条独立路径）
await sdk.generalApproval.detail(businessKey)                       // 业务单据
const instance = await sdk.generalApproval.findInstanceByBusinessKey(businessKey)  // 流程实例

// 5) 撤销（写操作）。id 是**流程实例 id**，不是 businessKey —— 给 businessKey 也行，SDK 替你换
await sdk.generalApproval.cancel({ processInstanceId: instance.id, reason: '不申请了' })
```

两条最容易踩的：

- **`cancel` 要的是流程实例 id**，而 `GET /hr/general-approval/get` 的响应 VO 里
  **没有 `processInstanceId`**（虽然 DO 里有）。唯一通路是「我的流程」按 `businessKey` 找
  ——`findInstanceByBusinessKey()`。**这不是绕路**：页面上点「取消流程」用的
  `record.id` 正是 my-page 那一行的 `id`。
- **只按 `businessKey` 认单子会认错**：`businessKey` 是各业务表自己的主键，
  「通用审批 51」与「会议室预定 51」是同一个字符串。所以还要看 `processDefinitionKey`。

**结论：`cancel` 的失败是正确行为**（流程已终结），不是能力缺陷；但「选自己当审批人」

> ⚠️ **这一条没能撤销**：businessKey=66 现在是终态（已通过），`cancel-by-start-user` 对终态
> 单据无能为力，`DELETE /hr/general-approval/delete/{id}` 又只允许「已驳回」状态。
> 它留在测试环境里，标题是 `SDK-TEST-通用审批冒烟 20260920153559`。**如实记在这里。**

#### 第 2 轮：审批人换成**别人**，完整链路跑通

```text

submit  ：成功，业务单据 id（businessKey）= 67
```

| 判据 | 会议室的写法 | 本条线的证据 |
| --- | --- | --- |
| 提交真的落地了 | 占用查询里出现了那条记录 | **两条**：`detail(id)` 字段逐字段一致 + my-page 里 `businessKey` 对得上且 `status=1` |

#### 第 3 轮（补课）：**带附件**的完整链路（2026-09-20 稍晚，上传链路拿到合法凭据之后）

第 2 轮时「带附件的提交」是没测的（上传能力当时没有合法凭据，见 §八）。本轮补上了。

跑法：附件要**两套凭据**，而它们在不同路上（会话 token 从浏览器 cookie 取、
OSS AK/SK 从构建期 env 读），所以是**嵌套**的两层：

```bash
PORTAL_SMOKE_APPROVER_KEYWORD=管理员 \
  smoke/with-oss-credentials.sh smoke/with-portal-token.sh \
    node smoke/general-approval.mjs --submit --attachment
```

```text
      url=https://files-test.wodecorp.cn/HR/approval/2026/09/klmkqlctrzohkdsp.csv
      objectKey=HR/approval/2026/09/klmkqlctrzohkdsp.csv  size=146  acl=public-read
```

三条结论：

- **附件字段真的能落地**：`[{url,name}]` 被后端接受，`saveFile()` 为它建了
  `oss_resource` 行（id=3178），回读时 url/name 与提交的完全一致。
- **上传 → 提交 这条链是通的**：`baseUpload.upload()` 返回的 url（`HR/approval` 目录，
  与表单的 `ossFilePathOptions.hr.approval` 同目录）可以直接当附件用。
- **对象删干净了，且是独立证实的**：DELETE 的 204 只说明 OSS 收下请求；再匿名 GET 一次
  拿到 403 才说明它真的读不到了。

> ⚠️ **第一次附件提交是失败的，而且失败得对**：探针文件名写成 `.txt`，
> 而 `.txt` 不在表单的 `accept` 白名单里，SDK 在 `prepare` 之前就拒了
> （`第 1 件附件的扩展名 .txt 不在本表单的 accept 白名单里`）。
> **那一次没有留下任何东西**：`create` 根本没发出去，且脚本的 `finally` 已经把
> 传上去的对象删掉了。失败路径的清理也走通了 —— 这是它存在的意义。

> ⚠️ **残留一件（如实记）**：`hr_general_approval` 单据 68 上的附件在
> `oss_resource` 表里留了一行（id=3178），它指向的 OSS 对象已经被删掉了。
> 也就是说这一行现在是**悬空的元数据**。没清它的原因：表单页面上**没有任何入口**
> 会删这一行（附件删除只是把元素移出 `formState.attachments`），
> 唯一能删的接口是 `DELETE /file/oss-resource/delete?id=`（全仓只有「流程跟进」在用），
> 那不属于本能力、也没被验证过 —— 用一个没验过的写接口去动共享表，比留一行悬空元数据更糟。
> 要清的话请另行决定。

- **OSS 上只碰过两个对象**，两个都已删除并复核（失败那次的对象在 `finally` 里删掉了，
  成功那次的对象在收尾删掉了）。事后又用 `curl` 匿名各打了一次收尾复核：

  ```text
  HR/approval/2026/09/ztxnytojeulblsgd.txt  → HTTP 403   （第一次尝试的 .txt 探针）
  HR/approval/2026/09/klmkqlctrzohkdsp.csv  → HTTP 403   （成功那次的 .csv 探针）
  ```

### 两条顺带实测出来的事实（写进能力文件了）

- **`detail().status` 会后端回写滞后**：刚 `create` 完立刻查，读到的是 `0`（待提交）——
  状态由 `GeneralApprovalWorkflowListener` 监听流程事件**异步**回写，终态才有值。
  所以「查提交结果」不要只看这一个数字，要看流程实例的 `status`。
- **`statusName` 恒为 `null`**：`GeneralApprovalRespVO` 声明了它但没填。

## 八、尚未覆盖 / 不确定

**测到了的**（真实环境）

- `definition` / `searchUsers` / `prepare` 三个只读能力：真实调用过。
- `submit` / `detail` / `myInstances` / `findInstanceByBusinessKey` / `cancel`：
  第 2 轮端到端跑通，且提交与撤销都有**两条独立证据**。
- 审批人节点**非空**的那条路径（会议室那条线从没验过）——本流程实测 1 个节点。
- **带附件的提交**（2026-09-20 补课）：上传 → 提交 → 回读附件 → 撤销 → 删对象，
  整条链在真实环境跑通，且每一段都有独立证实（§六.3）。
  这一条**原本记在「没测到」里，现在补掉了**。

**没测到的（明确分开）**

- **附件在提交之后还能不能改/删**：页面上的「删除」只是把元素移出 `formState.attachments`，
  没有对应的接口调用；`update` 那一支前端是注释掉的（见下）。
- **那份 `oss_resource` 行（id=3178）没有清理**，理由与替代方案写在 §六.3 的残留说明里。
- **`reviewApproval` / 审批通过 / 驳回没做**：那是待办那一侧的写操作（`POST /bpm/hr/task/approve`），
  不属于「发起通用审批」这条线，而且会让测试单据真的走完流程。做它要单独派单。
- **`getWorkflowPath`（审批链路）没有做成能力**：本轮只用它做了一次**取证**（§六）。
  它是只读的，做成能力价值明确，但不在本单范围内。
- **「查看审批流程」预览没做**：打的是 `/bpm/process-instance/preview`
  （`portal-hxr-flow-process-preview`），只读的展示件，不影响能不能提交。
- **「重新发起」（reapply）没做**：会从原流程实例抄抄送人再走一遍提交，是**另起的写链路**，
  要单独验证。
- **`update` / `delete` 没做**：后端限定「只有已驳回状态」才能改/删，而页面上的编辑分支
  **前端已经注释掉了**（`035` 的 `handleSubmit` 里 `isEditMode` 那三行是注释，
  `apiSubmit` 写死成 `/create`）。造一条"已驳回"的单据得先让真人去驳回，本轮做不到。

**推断（没有实测）**

- 「我的流程」列表的 `processDefinitionKey` 一定存在——SDK 对**它缺失时**的处理是
  "只按 businessKey 认"（代码里是 `undefined` 就放行）。实测的两条都带它，缺失那种情况没遇到过。
- `findInstanceByBusinessKey` 的翻页上限是 5 页 × 50 条。单据多了以后会不会翻不到，
  没有造过那种数据。
- 附件的 50MB 上限：页面拦，SDK **拦不了**（手上只有 url 与 name，算不出字节数）。
  这条依赖后端或人对错。

## 2026-09-22 AI 说明契约同步

权威契约在 `src/catalog/contracts-workflow.ts`，经 `catalog.describe(id)` / `id-llm` 的 `ai` 实际返回；`describePage` 同步用途与功能区别。额外公开门面通过 `catalog.describeMethod(sdkPath)` 下钻，无需调用方读仓库。

| 能力 | 效果 | 最终 SDK 返回 | 完成判据 |
| --- | --- | --- | --- |
| general-approval-definition | read | 流程定义对象（已拆后端包络） | 已确认流程身份；填写流程继续准备，单纯查询定义则交付名称与配置即可。 |
| general-approval-user-search | read | { list: 用户候选[], total: number } | 用户选定正确人员并保留 id 后候选查询完成。 |
| general-approval-prepare | prepare | { payload, tasks }（本流程附加字段见 fields） | 草稿校验并得到所需自选节点后准备完成；实际发起须再提交。 |
| general-approval-submit | write | number（业务单据 ID；SDK 不返回 code/data 包络） | 回读确认业务记录及其流程后，向用户交付业务 ID 与当前审批状态；提交成功不等于审批完成。 |
| general-approval-detail | read | 业务单据对象（拆包后） | 用户查询详情时交付业务信息与可靠状态即可；需要取消则先确认对应实例仍运行。 |
| general-approval-my-instances | read | { list: 流程实例[], total: number } | 向用户展示流程名称、审批内容、状态与起止时间；有明确目标时只交付匹配实例。 |
| general-approval-cancel | write | boolean（后端成功回执；SDK 原样返回拆包后的值） | 流程实例 status=4，必要时详情也回读已取消，向用户报告撤销结果。 |

数据消费与分支：

- general-approval-definition：展示 name 与 key 核对业务；formFields 为 null 不代表免填，填写规则在 prepare/submit 的 SDK 描述中。
- general-approval-user-search：展示姓名与工号给用户消歧；保存选中行 id 作为 userId。 keyword 或 deptId 至少给一个；pageSize=-1 被拒绝。
- general-approval-prepare：给用户核对 payload 的业务值；按 tasks[].id 建立 startUserSelectAssignees 的键，人员来自候选查询，人数、去重与顺序服从任务规则。 准备只读，不建单、不保留名额、不发送待办；任何草稿变更后应重新准备。
- general-approval-submit：保存业务 ID、流程类型及原 requestId；回读业务字段并查询流程实例确认已创建。 取消属于用户改变决定时的可选操作，不是正常提交后的必做步骤。
- general-approval-detail：展示本次申请的业务字段与附件；原请求业务 ID 必须单独保存，详情不保证能提供流程实例 ID。 状态应区分业务单据与流程实例；需要可撤回性时查 my-instances，而不是只看详情 status。
- general-approval-my-instances：本接口没有自动限定 hr_general_approval，按 processDefinitionKey 与 String(businessKey) 双重匹配；字段缺失时不可把跨业务重号当可靠确认。 页码默认 1、每页默认 20；逐页核对 total，列表局部不能用于全量汇总。
- general-approval-cancel：只取消自己发起且仍运行的流程；保留业务记录，不代表删除历史。 查实际流程 status=4 才认定撤销完成；会议预定则核对占用时间段消失。

本轮以 `test/ai-contract-workflow.test.ts` 核对真实 SDK 描述，复用既有浏览器基准，不重放真实写操作。逐项验证与缺口见 `docs/ai-contract-workflow-evidence.md`。
