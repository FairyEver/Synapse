# 作业管理（`/dashboard/assignment/assignment/list`）

阶段① 的**第一条换域 + 普通 CRUD** 业务线。四件套的其它三件分别在：能力定义与参数契约 →
`src/capabilities/assignment.ts`；逐字段基准 → `baseline/assignment-list.browser.json`、
`baseline/assignment-list-daterange.browser.json`、`baseline/assignment-write.browser.json`
（真实环境写记录 → `baseline/assignment-write.verified.json`）；回归测试 → `test/assignment.test.ts`。

它要回答的不是「这个页面能不能做」，而是：

> 会议室预定是**唯一**跑通过、也是唯一被反复插桩过的一条线。参数契约的写法、四件套的结构、
> 基准抓取配方、写链路的形态，全都只在那一个域（HR 流程类）里成型过。
> **换一个域（教育）、换一个形态（普通增删改）之后，哪些做法原样成立、哪些必须改、哪些用不上。**

结论写在最后一节「换域之后哪些做法不适用了」，那一节比「页面做完了」重要。

## 页面标识

| 项 | 值 |
| --- | --- |
| 菜单路径 | `/dashboard/assignment/assignment/list` |
| 权限码 | `/dashboard/assignment/assignment` |
| 路由文件 | `app/portal/views/dashboard/education/assignment/assignment/list.vue` |
| 域 | `assignment`（教育，与会议室那条 HR 线不是同一个域） |
| 形态 | 列表页（声明式 `getDataListURL`）+ 独立的新建/编辑表单页 |
| module-type | **12（学习管理）** —— 实测浏览器发这个头，与会议室那条线（算不出、不发）相反 |
| http 实例 | `platform`（页面没有把 http 传给 `useListPageModule`，走 `main.js` 注入的全局默认） |
| 含写操作 | 是（新建 / 修改 / 改状态 / 删除） |

## 页面形态：这是普通 CRUD，不是流程

这是本次换域最要紧的一条判断，它决定了写链路的形状。

| 动作 | 请求 | 出处 |
| --- | --- | --- |
| 列表 | `GET /study/assignment/studyassignment/page` | `list.vue` 的 `getDataListURL` |
| 详情 | `GET /study/assignment/studyassignment/{id}` | `[mode]/[id].vue` 的 `customLoad` |
| 新建 | `POST /study/assignment/studyassignment` | 同上 `customSubmit`（`isCreateMode`） |
| 修改 | `PUT /study/assignment/studyassignment`（整单替换） | 同上（非 create 分支） |
| 改状态 | `PUT /study/assignment/studyassignment`，body `{id, status}` | `list.vue` 的 `actionStatus` |
| 删除 | `DELETE /study/assignment/studyassignment`，body `[id]` | `list.vue` 的 `actionDelete` |

**没有 `getRequiredStartUserSelectTasks` 这类"提交前先问一次"的接口**，也**没有撤销/审批**。
会议室那条线的 `prepare → submit → cancel` 三步在这里没有对应物。

## 参数契约

### 列表查询

浏览器发出的（`baseline/assignment-list.browser.json`，三个筛选条件全空）：

```
GET /admin-api/study/assignment/studyassignment/page
  ?order=&orderField=&title=&status=&type=&createTimeStart=&createTimeEnd=&pageNo=1&pageSize=20&_t=<ts>
```

三个筛选条件一个都没填，7 个参数照样以空串发出去 —— renren 列表页的空值默认参数
必须一并复刻（D20）。`pageSize` 默认 20（`list.js:391` 的 `styleV2` 分支），不是 renren 配置里的 10。

### 创建时间区间：结束日是**开区间**（本次换域的新花样）

页面的 `convertFetchForm`：

```js
createTimeStart = date[0].startOf('date').format('YYYY-MM-DD HH:mm:ss')
createTimeEnd   = date[1].startOf('date').add(1, 'day').format('YYYY-MM-DD HH:mm:ss')
```

面板上选 2026-09-01 ~ 2026-09-05，浏览器发的是
`createTimeStart=2026-09-01 00:00:00&createTimeEnd=2026-09-06 00:00:00`
（`baseline/assignment-list-daterange.browser.json`）。

**结束日 +1 天、时分秒固定 00:00:00。** 自己拼这个区间会静默少一天（选到 9-05 却查不到
9-05 当天），所以 SDK 单独给了 `buildCreateTimeRange()`，并有 5 条用例钉着它（含跨月、跨年、同一天）。

### `status` 这个参数在本页上是**坏的**（如实记下来，没有粉饰）

页面把「作业状态」的字典写成 `type="status"`，而 `status` 是**全平台共用的字典 key**。
实测它装的是**交易状态**：

- 下拉里的选项是「待确认 / 等待付款 / 处理中 / 已完成 / 已关闭 / 已关闭(卖家或买家主动关闭)」；
- 选中「已完成」后请求里是 `status=TRADE_FINISHED`；
- 而列表里作业自身的状态列**渲染为空**（作业的 status 是 0/1，在这份字典里找不到对应项）。

所以 SDK **没有**把 `status` 声明成 `enum` —— 那等于把一份错误的候选值当契约发给 AI。
它声明成 `text`，并在描述里直接写明"本页的取值来自全平台共用的 status 字典，实测装的是
交易状态"。`test/assignment.test.ts` 专门有一条用例锁这个决定。

### 作业类型（`assignment_type`）：这一处是**实测出来的 enum**

新建表单的单选按钮有 6 项，实测值就是：

| label | value |
| --- | --- |
| 文件 | 1 |
| 图片+文字 | 2 |
| 图片 | 3 |
| 文字 | 4 |
| 视频 | 5 |
| 视频+文字 | 6 |

### module-type：本页**算得出**，而且这个头不是页面属性

`resolveModuleType('/dashboard/assignment/assignment/list')` → 12（学习管理），
命中 `app/portal/menus/index.js:176-192` 的第一条前缀规则 `/dashboard/assignment/`。
实测浏览器同样发 `module-type: 12`，两边闭合。

但这背后有一条必须知道的事实（本次与并行的考勤档案那条线各自独立撞到，互相印证）：

> `getCurrentModuleType()` 读的是 cookie `hr-0.0.0-menuPath`，而 **cookie 是整个浏览器
> profile 共享的**，由路由守卫在每次导航时写。
>
> 实测：本页 URL 一个字没变，只因为并行代理在另一个标签页跳到了别处，本页再发请求时
> `module-type` 就从 12 变成了 11；又抓到过一次变成「完全不发」（cookie 被写成 `/`）。
>
> ⇒ **抓基准时 `module-type` 必须拿规则表复核，不能直接把抓到的那一次当答案抄。**
> SDK 按页面路径推导，给出的恰好就是「单标签页正常导航」下的值。

## 写链路：形态、为什么没有 `prepare`、以及 D12 为什么要收窄

### 只读前置步骤存在，但它不叫 `prepare`

`update` 打的是**整单替换**的 PUT（页面的编辑态也是先 `GET /{id}` 再把结果铺回表单：
`customLoad` → `{...result}` → 整份 PUT）。所以调用方**必须先 `get()` 拿当前值再改**，
否则没传的字段会被默认值写回去。

但它是**独立能力 `get`**，不是 `prepare`：

- `prepare` 在会议室那条线上的职责只有一个 —— 问后端"这次要人工指定哪些审批人"，
  那个答案会**改变提交载荷**。这个页面的后端没有这种接口。
- 在 `update` 内部自动 `get` + 合并反而更危险：`get` 回来的记录里有表单不认识的字段
  （`creator` / `createTime` / `updater` / `isDel` / `isRemind` …），一并回写是**没验证过的形状**。

所以 SDK 只把顺序写进 `update` 的参数说明，不代劳。

### D12（写能力必带 `requestId`）在这个页面上要**收窄**

`docs/conventions.md` 第 14 条说"后端零幂等，AI 超时重发 = 重复单据"。这句话的代价是
「多出一条记录」，而这个页面上**只有 `create` 会产生第二条记录**：

| 写能力 | 重发一次的后果 | `requestId` | 实测依据 |
| --- | --- | --- | --- |
| `create` | **多一条作业**（后端零幂等） | **要** | 刻意没试过重发不带 requestId 的那种（那正是要防的） |
| `update` | 整单替换再写一次，终态相同 | 不要 | 冒烟里原样重发一次：仍只有一条，标题/截止时间不变 |
| `setStatus` | 写的是**绝对值**不是开关，终态相同 | 不要 | 冒烟里 `setStatus(0)` → get 读回 0 |
| `remove` | 逻辑删除，重复删后端直接返回成功 | 不要 | 冒烟里连删两次都不报错 |

两个刻意的设计：

- **`setStatus` 收的是目标状态，不是"切换"**。页面自己算好绝对值再发
  （`record.status === 0 ? 1 : 0`）。做成 toggle 就会变成不幂等的 —— 那是 SDK 自己造的坑，
  不是这个页面的性质。
- **写操作绑定到 `createIdempotent` 而不是 `create`**（`src/capabilities/invoke.ts`），
  缺 `requestId` 当场抛 `CapabilityInvokeError`。另外三个如实透传，**不假装它们被防重保护了**。

## 真实验证记录（2026-09-20）

`smoke/with-portal-token.sh node smoke/assignment-crud.mjs`，20 项检查全绿，
测试环境没有留下任何 `SDK-TEST-` 前缀的残留。完整形状见
`baseline/assignment-write.verified.json`，这里摘关键几行：

```text
起手：按名字查列表 —— 0 条（排除「本来就有一条」这种假阳性）
create：createIdempotent 返回 "1076"
独立证实①：按名字查列表 —— 恰好 1 条，id 与返回值一致
独立证实②：按 id 查详情 —— 标题 / 作业要求 / 作业类型 / 截止时间逐项与提交值一致
同一个 requestId 重试 —— 列表仍 1 条，回放第一次的返回值
setStatus(0) → get：status=0；setStatus(1) → get：status=1
update（先 get 再改）→ get：标题变了；旧名字 0 条、新名字 1 条
update 原样重发一次 —— 仍 1 条，终态不变
remove → 列表查不到；重复 remove 后端返回成功
收尾：列表按两个名字各查一次 —— 0 条
```

浏览器侧也真的走过一遍（三条记录 id 1070 / 1071 / 1072，每条都在同一轮里删掉了），
四条写请求的逐字段基准就是从那里来的。

### 三条实测出来的后端语义（不是推断）

1. **`remove` 是逻辑删除。** remove 之后 `list` 查不到，但 `get(id)` **仍然返回整行**，
   只是 `isDel` 从 0 变成 1；重复 remove 后端直接返回成功。
   ⇒ 「删干净了没有」**只能看列表**，拿 `get` 复核会得到一个看起来像"没删掉"的假象。
   这条差点被误判成"删除没生效"（第一版冒烟就是这么写的）。
2. **后端把 Long 序列化成字符串。** 创建返回 `"1076"`（字符串）；删除 body 是 `["1071"]`；
   改状态 body 是 `{"id":"1071","status":0}`。SDK 的 `normalizeId()` 把数字 id 一律转成字符串，
   与浏览器逐字节一致。
3. **后端会归一化页面的奇怪初值。** 创建时页面发的是
   `isUploadCore:''` / `coreType:''` / `scoreType:''` / `answerType:''` / `imageAnswer:[]`，
   读回来是 `0` / `null` / `0` / `null` / `null`。所以「先 get 再改」时把这些字段原样传回去，
   比让 SDK 拿创建态默认值去填更贴近页面编辑态。

## 换域之后哪些做法不适用了

这一节是这次派单真正要回答的东西。分四类：**原样成立 / 必须改 / 干脆用不上 / 新出现的问题**。

### ① 原样成立

| 做法 | 为什么成立 |
| --- | --- |
| 四件套的结构（能力定义 / 参数契约 / 逐字段基准 / 操作步骤 + 回归测试 + 反证） | 换域不影响它的分工。四份产物在新域里各司其职，没有一份是多余的。 |
| `pagePath` 决定 module-type 与 http 实例 | 这一层与域无关，`resolveModuleType` / `resolveHttpInstance` 直接吃页面路径。 |
| 能力定义里 `id` / `title` / `pagePath` / `permission` / `write` / `params` 六个字段 | 一个字段都不用改。新域没有逼出新的字段。 |
| 「列表页默认要带 renren 的空值参数」 | 这个页面同样发 `order=&orderField=&...`，一条不少。 |
| 「一个能力绑定一个页面上下文，能力内部走 `call(pagePath, ...)`」 | 六个能力全部走 `ASSIGNMENT_PAGE_PATH`，module-type 不会漏。 |
| 反证的做法（改坏实现，确认测试变红） | 12 组变异里 11 组当场变红，一组没有 —— 见「尚未覆盖」。 |

### ② 必须改

| 做法 | 会议室那条线上是 | 这里必须变成 | 为什么 |
| --- | --- | --- | --- |
| **写链路的形态** | `prepare → submit → cancel` 三步，`prepare` 是只读的一步 | `get → create/update → remove`，**没有 `prepare`** | 后端没有"提交前先问一次"的接口。硬造一个 `prepare` 就是给"读"套上"提交流程"的名字，是假的。 |
| **D12 的适用范围** | 写能力全部带 `requestId`（那条线上写就是提交，提交就会产生单据） | **只有 `create` 带** | "重复单据"的代价在这个页面上只由 `create` 产生；另外三个重发一次终态相同（已实测）。写操作全上防重不是更安全，是更慢 + 更难用。 |
| **`setStatus` 的参数语义** | 无对应物 | 必须收**目标状态**（0/1），不能是 toggle | 页面的 `actionStatus` 在客户端算好绝对值再发。SDK 若做成切换，就自己造了一个不幂等的接口。 |
| **长选项的处理方式** | 人员候选几千个 → 强制要关键字（D6） | **这里没有长选项** | 6 个作业类型是小枚举，直接列；`status` 的候选是坏的（交易状态字典），所以**不声明成 enum**，声明成 text 并写明它坏在哪。D6 的"按类型分别处理"这一条原样成立，但"必须先要关键字"这一支在这里**没有触发点**。 |
| **日期参数的形态** | 两个独立日期时间（`startTime`/`endTime`），带 `assertTimeSlot`（分钟 00/30、秒 00、结束晚于开始） | 一个**日期区间**，转成 `createTimeStart`/`createTimeEnd`，且**结束日 +1 天（开区间）** | `assertTimeSlot` 那套规则在这里**完全不适用**（没有 30 分钟粒度约束）；取而代之的是区间语义的 +1 天。这是一个新花样，会议室那条线没有。 |
| **基准的份数** | 读 1 份 + 写 1 份 | 读 2 份（窄条件 / 带日期区间）+ 写 1 份（四条请求） | 参数里有"会改写查询参数"的 `convertFetchForm`，只抓一份空条件基准**看不到它**。 |

### ③ 干脆用不上

- **`prepare` 这个动作**：没有对应的后端接口，也没有需要"提交前先问"的东西。
- **`assertTimeSlot` 那套时间段规则**：这个页面没有 30 分钟粒度的时间窗。
- **流程/审批相关的一切**：发起流程、审批链、`startUserSelectAssignees`、取消预定。
- **"提交后到另一个视图里证实"这种验证手法**：会议室的证据是"占用查询里出现了这条预定"
  ——那是一个**独立于提交接口的第二个视图**。作业管理**没有第二个视图**，
  所以"独立证实"只能退化成**同一接口的两次独立读取**（列表按名字查、详情按 id 取，
  且提交值与读回值逐项比对）。这条差别值得记住：**有第二个视图时证据更强。**
- **`bsk fill` 在 antd 日期面板上走不通**这一条：本页的日期控件同样要面板点击，
  但**失败原因与会议室那条不同**（见 ④）。

### ④ 新出现的问题（会议室那条线上不存在）

**A. `readOnly` 陷阱的根因描述是错的，要更正。**

`tools/baseline/README.md` §2 写的根因是"`showTime` 打开时 rc-picker 把两个输入框设为
`readOnly`"。实测在本页**不成立**：本页的「创建时间」是**不带 `showTime`** 的
`a-range-picker`，两个输入框**同样是 `readOnly: true`**。
⇒ 正确表述是"**rc-picker 的输入框本来就是 readOnly，值只能通过面板写**"，
与 `showTime` 无关。`showTime` 只决定面板里**多不多三列时间**。

**B. 面板的数量与索引不是固定的。**

README §2.1 说"页面里**只有一个** `.ant-picker-panel`（宽 449px）"。在本页实测：

- 列表页那个**不带 `showTime`** 的区间选择器是**两个 panel 并排**（经典两月视图）；
- 新建页的**带 `showTime`** 的日期选择器只有一个 panel，但同一个页面上还留着
  列表页那两个**不可见**的 panel —— `document.querySelectorAll('.ant-picker-panel')[0]`
  拿到的**不是当前打开的那个**。

⇒ 抓基准时不能硬编码 `[0]`，必须筛可见的：
`[...document.querySelectorAll('.ant-picker-panel')].filter(p => p.offsetParent)[0]`。

**C. `ph_pick`（先打标记再点）的标记**不会自动清理。**

README §2.2 给的 `ph_pick` 每次给元素打 `data-ph-t="1"`，但 `bsk click '[data-ph-t="1"]'`
是"文档里第一个带这个属性的元素"。前一次打的标记不清掉，第二次点击就会**点到上一个元素**
（实测：以为点了行内的「编辑」，实际点到了顶部的「新建」）。配方里要加一句
`document.querySelectorAll('[data-ph-t]').forEach(e => e.removeAttribute('data-ph-t'))`。

**D. 时间列仍然会点偏一行（README §2.3 那个坑在别的日期控件上同样存在）。**

实测：`scrollIntoView({block:'center'})` 之后立刻点 `cell[18]`，结果选中的是 **19**。
`scrollIntoView` 触发的是平滑滚动，点击坐标在滚动稳定前就算好了。
⇒ 需要 `behavior: 'instant'` **并等一拍**再点。

**E. `module-type` 是浏览器级 cookie，不是页面属性。**（§「module-type」那一节详述）
抓基准时它必须拿规则表复核；三次抓取里抓到过 12 / 11 / 完全不发三种值。

**F. 列表页的 `title` 是模糊匹配。** 冒烟里"改名之后旧名字查不到了"这条断言，
用 `原名-改后` 当新名字会被子串命中、看起来像没改成功。改后的名字**不能包含原名**。

## 尚未覆盖

- **编辑页的 PUT 没有单独的浏览器基准。** `update` 的载荷形状是按 `create` 推的（多一个 `id`），
  已在测试环境真实调用成功并用 `get` 复核过字段确实变了，但**没有做过与浏览器的逐字节比对**。
  编辑态里 `id` 在 body 里的位置、以及那些被后端归一化过的字段（`isUploadCore` 等）在编辑态
  发出去到底是什么形状，都还没有实测。
- **附件类字段没有开放。** 参考答案的图片 / PDF / 视频、课程核心的对应项都要先上传到 OSS
  才能给 URL。SDK 现在有上传能力（`baseUpload`，见 docs/base/上传.md），但本条线没接；所以这些字段在载荷里固定发页面创建态的默认值。
  `isUploadAnswer: 1` + `answerType` 指向附件的那几条路径**没有被端到端验证过**。
- **`isUploadAnswer === 1` 时的条件必填规则没有强制。** 页面要求此时必须给答案类型与发布时间；
  SDK 只用本地校验拦页面**无条件**要求的那四条（名称 / 要求 / 类型 / 截止时间），
  条件规则只写在文档里。理由：那是前端表单规则，后端未必校验，强制了会把后端本来接受的调用挡在门外。
- **SDK 在 GET 上多发一个 `Content-Type`（值 `undefined`），浏览器不发。**
  这是 `src/http/headers.ts` 的**既有行为**，不是本页引入的：会议室列表那条线的 GET
  同样带这个头（已复核）。写请求上两边都有 `Content-Type`，键集合一致。
  因为它不属于本次任务的文件范围（`src/http/**` 未授权改动），**没有修**，
  而是在 `test/assignment.test.ts` 里**如实锁住"只多这一个"** —— 再多出别的头就会红，
  而不是把整条断言放松掉。
- **多用户门面下 `createIdempotent` 的身份隔离没有测试。** `identity()` 里的 `userId` 是
  「两个用户的同一个 requestId 不能互相命中」的唯一保障，但 `createPortalServer` 没有
  可以桩掉请求的接缝（`sessionOptions` 明确 Omit 掉了 `createRequest`），
  不离网就测不到。**这一条与会议室那条线是同样的覆盖盲区**，不是本次新增的。
  反证时把 `assignment` 的 `identity` 改成 `() => ({})`，39 条用例全绿 ——
  「全绿」在这里**不等于**这条接线是对的。

## SDK AI 说明契约（2026-09-22）

本节由当前 SDK 描述结果整理；说明权威来源为 `src/catalog/contracts-business.ts`。调用 `catalog.describe(id)`（或 `id-llm`）可得到参数来源、返回字段/状态、数据消费与后续映射；`catalog.describePage(页面路径)` 用于选择页面功能。以下更新以本节为准；前文历史请求/实测记录仍保留其记录日期。

### `assignment-list`

按条件查找作业并取得记录 ID；用于展示、选中编辑目标和核实写入结果。

- 执行：`sdk.assignment.list`；通过 `capabilities.invoke('assignment-list', args)` 调用时按 `params` 填参。性质：read。
- 参数：`title` 可选 (string)；`status` 可选 (string)；`type` 可选 (string | number)；`createTimeStart` 可选 (string)；`createTimeEnd` 可选 (string)；`pageNo` 可选 (number)；`pageSize` 可选 (number)。完整来源、枚举、条件必填与默认值由 SDK 同次返回。
- 返回：`{ list: object[], total: number }`。list=[] 为当前页无记录；total=0 表示该筛选无结果。保留筛选条件检查页码，不将空结果解释成权限判定。
- 字段：`list`、`total`、`list[].id`、`list[].title`、`list[].demand`、`list[].type`、`list[].status`、`list[].isDel`、`list[].endTime`、`list[].creatorName`、`list[].createTime`、`list[].isUploadAnswer`、`list[].isTeacherCheck`、`list[].isSelfScoring`、`list[].selfScoringEndTime`、`list[].answerPublishTime`、`list[].textAnswer`、`list[].fileAnswer`、`list[].fileAnswerName`、`list[].imageAnswer`、`list[].isUploadCore`。嵌套字段、可空性及业务含义见同次返回的 `returns.fields`。
- 消费：展示名称与状态，操作定位始终使用 id。名称筛选为模糊匹配；改名复核必须比较完整新名称，不能仅看旧关键字仍命中。
- 完成条件：按用户要求交付本次筛选范围的结果；需要完整清单时继续翻页至覆盖 total，不能把当前页当全集。
- 后续：optional → `assignment-get`：需要完整编辑数据或核实单条记录时读取详情（id ← list[].id）
- 失败/不确定：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。


### `assignment-get`

读取一个作业的完整编辑数据；不自动修改或提交。

- 执行：`sdk.assignment.get`；通过 `capabilities.invoke('assignment-get', args)` 调用时按 `params` 填参。性质：read。
- 参数：`id` 必填 (string | number)。完整来源、枚举、条件必填与默认值由 SDK 同次返回。
- 返回：`object`。逻辑删除后 get 仍返回 isDel=1，必须以列表不再含该 ID 复核。
- 字段：`id`、`title`、`demand`、`type`、`status`、`isDel`、`endTime`、`creatorName`、`createTime`、`isUploadAnswer`、`isTeacherCheck`、`isSelfScoring`、`selfScoringEndTime`、`answerPublishTime`、`textAnswer`、`fileAnswer`、`fileAnswerName`、`imageAnswer`、`isUploadCore`。嵌套字段、可空性及业务含义见同次返回的 `returns.fields`。
- 消费：用 id 识别记录，保留当前业务字段供修改。整单替换；先 get，保留所有业务字段再修改，缺省字段会清空。 逻辑删除后 get 仍返回 isDel=1，必须以列表不再含该 ID 复核。
- 完成条件：按上述数据消费规则交付查询结果；本能力的读取到此结束。
- 后续：optional → `assignment-update`：整单替换；先 get，保留所有业务字段再修改，缺省字段会清空。（id ← id）
- 失败/不确定：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。


### `assignment-create`

真实新建作业。普通 CRUD，没有 prepare 或审批人步骤。

- 执行：`sdk.assignment.createIdempotent`；通过 `capabilities.invoke('assignment-create', args)` 调用时按 `params` 填参。性质：write。
- 参数：`title` 必填 (string)；`demand` 必填 (string)；`type` 必填 (string | number)；`endTime` 必填 (string)；`isUploadAnswer` 可选 (number)；`answerType` 可选 (number | string)（含条件必填）；`answerPublishTime` 可选 (string | null)（含条件必填）；`textAnswer` 可选 (string)；`isUploadCore` 可选 (number | string)；`selfScoringEndTime` 可选 (string | null)（含条件必填）；`isSelfScoring` 可选 (number)；`isTeacherCheck` 可选 (number)；`requestId` 必填 (string)；`coreType` 可选 (number | string)（含条件必填）；`corePublishTime` 可选 (string | null)（含条件必填）；`textCore` 可选 (string)；`scoreType` 可选 (number | string)（含条件必填）。完整来源、枚举、条件必填与默认值由 SDK 同次返回。
- 返回：`string`。创建正常应返回 ID；没有 ID 时用列表按名称核实，不能重建。
- 字段：`$`。嵌套字段、可空性及业务含义见同次返回的 `returns.fields`。
- 消费：创建后按title查列表，匹配完整名称及本次业务字段，再保存该行 id。
- 完成条件：列表出现唯一匹配的新记录且业务字段符合目标，再报告创建完成。
- 后续：required → `assignment-list`：创建响应后或写入结果不确定时，查询核实唯一记录（title ← args.title）；cancel → `assignment-remove`：仅用户确实要求撤销本次创建时删除；不是成功后的必做步骤（id ← context.createdRecordId）
- 失败/不确定：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。 通用 invoke 使用 requestId；相同 SDK 实例与 TTL 内同 requestId 回放结果。后端不提供持久幂等；超时后先查询核实，不能换 requestId 盲目重建。


### `assignment-update`

修改已有作业。整单替换；先 get，保留所有业务字段再修改，缺省字段会清空。

- 执行：`sdk.assignment.update`；通过 `capabilities.invoke('assignment-update', args)` 调用时按 `params` 填参。性质：write。
- 参数：`id` 必填 (string | number)；`title` 必填 (string)；`demand` 必填 (string)；`type` 必填 (string | number)；`endTime` 必填 (string)；`isUploadCore` 可选 (number | string)；`coreType` 可选 (number | string)（含条件必填）；`corePublishTime` 可选 (string | null)（含条件必填）；`textCore` 可选 (string)；`scoreType` 可选 (number | string)（含条件必填）；`isUploadAnswer` 可选 (number)；`isSelfScoring` 可选 (number)；`isTeacherCheck` 可选 (number)；`answerType` 可选 (number | string)（含条件必填）；`answerPublishTime` 可选 (string | null)（含条件必填）；`selfScoringEndTime` 可选 (string | null)（含条件必填）；`textAnswer` 可选 (string)。完整来源、枚举、条件必填与默认值由 SDK 同次返回。
- 返回：`string | number`。未收到回执先 get 核实目标状态或字段。
- 字段：`$`。嵌套字段、可空性及业务含义见同次返回的 `returns.fields`。
- 消费：整单替换；先 get，保留所有业务字段再修改，缺省字段会清空。
- 完成条件：读回目标字段与输入一致才报告修改成功。
- 后续：required → `assignment-get`：更新后读回逐字段比对，超时也先读回再决定是否重试（id ← args.id）
- 失败/不确定：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。 无 requestId；绝对值写入可产生相同终态，但再次发送前应读回以免覆盖他人后续修改。


### `assignment-set-status`

把作业写成指定目标状态；不是切换开关。

- 执行：`sdk.assignment.setStatus`；通过 `capabilities.invoke('assignment-set-status', args)` 调用时按 `params` 填参。性质：write。

- 返回：`string | number`。未收到回执先 get 核实目标状态或字段。
- 字段：`$`。嵌套字段、可空性及业务含义见同次返回的 `returns.fields`。
- 消费：目标状态：0=停用，1=启用；读回 status 对比目标值。
- 完成条件：详情 status 与目标状态一致。
- 后续：required → `assignment-get`：写入后或超时后核实 status（id ← args.id）
- 失败/不确定：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。 绝对值写入，没有 requestId；相同值重发终态相同，不要实现 toggle。


### `assignment-remove`

真实删除作业。逻辑删除后 get 仍返回 isDel=1，必须以列表不再含该 ID 复核。

- 执行：`sdk.assignment.remove`；通过 `capabilities.invoke('assignment-remove', args)` 调用时按 `params` 填参。性质：write。
- 参数：`id` 必填 (string | number)。完整来源、枚举、条件必填与默认值由 SDK 同次返回。
- 返回：`null | undefined`。正常空回执，不含被删记录。
- 字段：`$`。嵌套字段、可空性及业务含义见同次返回的 `returns.fields`。
- 消费：逻辑删除后 get 仍返回 isDel=1，必须以列表不再含该 ID 复核。
- 完成条件：目标 ID 不再出现在对应列表才确认删除完成。
- 后续：required → `assignment-list`：查询并确认目标 id 已不在列表（title ← context.deletedRecordName）
- 失败/不确定：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。 没有 requestId；重复删除不会新建记录。遇到超时先查列表，不为消除关联限制擅自删除关联业务。
