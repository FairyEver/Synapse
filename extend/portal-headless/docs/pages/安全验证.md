## 表单字段和提交规则

Portal 初始表单是 `{ id: '', isDel: 1, mobile: '' }`；挂载后用 `/org/sensitive/info` 返回值覆盖三个字段。SDK 不把这个默认值当成真实配置，读取响应缺少有效 `id` 或 `isDel` 时失败，不回退为关闭保护。

| 字段 | Portal 页面语义 | SDK 规则 |
| --- | --- | --- |
| `id` | 当前 `hr_sensitive` 配置记录 ID | 保留后端字符串或安全整数；保存原样放入 body |
| `isDel` | `0=开启操作保护`；`1=关闭操作保护` | 只接受数值 `0` 或 `1`，不接受字符串或其它状态 |
| `mobile` | 短信验证接收手机号；页面主表单展示脱敏值 | 当前值可为 `null`；修改值必填并匹配 `^1[3456789]\d{9}$`，不能提交脱敏手机号 |

`prepareSave` 只允许用户意图字段 `isDel`、`mobile`。`save` 的 PUT body 严格为：

```json
{
  "id": "当前配置ID",
  "isDel": 0,
  "mobile": "13800138000"
}
```

Java `HrSensitiveDTO` 虽然还声明 `email`、`creator`、`createTime`、`updater`、`updateTime`，这些字段不是本页表单提交字段，SDK 不从读取结果透传到 PUT。成功回执只表示请求未抛错；调用方还应重新 `get`，逐字段核对 `id`、`isDel`、`mobile`。

## 敏感操作和短信规则

Portal 的 `useSensitiveAction` 根据全局敏感配置判断：

- 当前 `isDel === 1` 时，页面动作直接继续，不弹短信验证；因此在保护已关闭时修改手机号也不额外发送短信。
- 当前 `isDel !== 1` 时，点击“关闭”会先把本地 radio 恢复为 `0`，打开短信验证弹窗；只有收到 `verified` 事件后才把本地 `isDel` 改为 `1`。
- 当前 `isDel !== 1` 时点击“修改”手机号也先进入同一短信验证流程；验证成功后才打开修改手机号弹窗。子组件只做本地表单校验并把新手机号交回父页面，直到点击外层“保存”才 PUT。

SDK 对应的安全链是：

```text
get → prepareSave →（verificationRequired 时 sendVerificationCode）
    → 用户提供本次短信 code → save 内部 checkSms → PUT
    → get 回查
```

发送验证码使用当前配置中的 `mobile` 和 Portal 固定值 `templateId=17709`，返回 `requestId`。保存所需的 `verification.requestId` 必须来自本次发送结果，`code` 必须由手机号持有人提供；SDK 不记录验证码、不替换收件手机号。

Portal 的校验请求设置 `original: true`，SDK 等价使用 `sourceResponse: true`，直接检查原始响应的 `ret`：只有 `ret === 'SUCCESS'` 才继续 PUT；失败时保留 `msg` 并阻断配置写入。Java 短信 controller 按手机号和 `hr-sensitive` 做一分钟发送限频，并返回验证码记录 `requestId`；Portal 的 60 秒倒计时是 UI 行为，SDK 不模拟本地计时器。

## prepare → submit → cancel 适用性

本页没有 Java `prepare`、`cancel`、撤销或回滚接口，页面也没有独立的提交确认 API：

- `prepareSave` 是 SDK 本地的表单合并、手机号校验和短信前置判断，不代表后端已经写入。
- `sendVerificationCode` 有短信副作用，不能把它当作配置保存成功。
- `save` 才是实际配置写入；保护开启时它会在 PUT 前完成 `checkSms`。
- 用户在 PUT 之前取消时，只需丢弃本地准备结果和验证码材料；PUT 已发送后，Portal 没有恢复旧配置的撤销动作。
- Java controller 还声明了 `POST /org/sensitive` 和 `DELETE /org/sensitive`，但目标页面从不调用它们，因此没有发布成这页的 SDK 能力。
