## 列表参数与返回字段

列表请求为 `GET /org/hrsalarylevel/page`，SDK 与 Portal 发送相同的协议字段：`order`、`orderField`、`name`、`pageNo`、`pageSize`。默认值为 `order=''`、`orderField=''`、`name=''`、`pageNo=1`、`pageSize=20`；页大小只接受 Portal 分页组件的 `10/20/50/100/200/500`。Java 服务按 `name` 模糊匹配、`sort` 升序，并固定筛选 `is_del=0`。

返回值为 `{ list, total }`：

- `list` 是当前页记录，`total` 是筛选后的总记录数，不是当前页长度；需要全量时必须继续翻页。
- `list[].id` 是薪资等级主键，用于详情、修改和删除；不要用名称替代。
- `list[].name` 是薪资等级名称。
- `list[].sort` 是非负整数排序值。
- `list[].salaryStandard` 是标准工资，单位元；SDK 保留服务端返回的数字或十进制字符串原值。
- `list[].status` 和 `list[].isDel` 是服务端原始状态字段；`isDel=0` 表示未删除，`isDel=1` 表示逻辑删除。页面不把 `status` 当作删除成功标志。

## 创建与编辑表单

编辑页先 `GET /org/hrsalarylevel/{id}`，再提交完整表单到 `POST /org/hrsalarylevel/save`。字段规则以 Portal 输入控件和规则为准：

- `name` 必填，不能全为空格，最多 50 个字符；SDK 保留首尾空格，不擅自 trim。
- `sort` 必填，整数且不小于 0；页面输入精度为 0。
- `salaryStandard` 必填，数值不小于 0，页面输入精度为 2；SDK 接受数字或数字字符串，最多两位小数，单位元。

Java 服务创建时写入 `isDel=0`、`status=0` 和审计字段；创建与更新都检查未删除记录中的名称重复，重复时返回“失败,名称重复”。保存成功是空 CommonResult，不返回新建 ID。创建完成应按精确名称查询并核对 `name`、`sort`、`salaryStandard`；更新完成应按原 ID `get` 回查。

## 删除、权限与敏感验证

Portal 删除动作先向 `POST /org/hrsalarylevel/checkCanDelete` 发送选中 ID 数组，再显示确认框；确认后调用 `useSensitiveAction`。SDK 的 `prepareRemove` 保留这两个前置请求但不产生删除或短信副作用，`remove` 会重新执行它们，避免准备结果过期。

Java `checkCanDelete` 和真正删除都会查询 `hr_staff.salary_level` 且要求 `is_del=0`。只要任一薪资等级被员工使用，就返回“正在被使用”业务错误，整批不应视为已删除。没有引用时，`DELETE /org/hrsalarylevel` 以 JSON ID 数组执行逻辑删除，写入 `is_del=1`。

敏感配置来自 `GET /org/sensitive/info`，与 Portal 分支完全一致：当响应同时没有 `mobile` 和 `isDel`，或 `isDel === 1`（数值）时跳过短信；否则必须使用配置的 `mobile`。发送验证码为 `GET /sys/sms/send?phone=<配置手机号>&templateId=17709`，取得 `requestId`；用户提供验证码后调用 `GET /sys/sms/checkSms?requestId=<requestId>&code=<code>`，验证通过才发 DELETE。不能让调用方替换接收手机号，也不能记录验证码。

## 操作步骤、失败处理与验证边界

1. 先列表查询并由用户选定记录；编辑先 `get`，删除先 `prepareRemove`。
2. 创建或编辑提交完整表单；空回执不等于业务结果，分别按名称或 ID 回查。
3. 删除时先确认没有员工引用；若需要短信，按 `prepareRemove → sendDeleteCode → remove`，`remove` 内部仍重新检查占用和敏感配置。
4. `checkCanDelete`、名称重复、权限/登录/网络错误和验证码错误都原样失败；失败或超时的写操作先回查再决定是否重试。
5. 删除完成的独立证据是分页列表中所选 ID 不再出现在未删除记录中；不能只凭 DELETE 成功或逻辑删除详情仍可读取来判断。

未覆盖真实环境的浏览器网络基准、已启用短信配置下的实际收件和验证，以及线上写入回查；这些缺口已在 AI 契约中明确记录。
