## 这一页**没有** `convertFetchForm`

它是纯声明式那一类：参数顺序就是 `order → orderField → 表单原样 → pageNo → pageSize → _t`。
实测 URL：`?order=&orderField=&name=&type=&studentNumMin=&studentNumMax=&teacherName=&teachingAssistantName=&orgId=&pageNo=1&pageSize=20&_t=…`

⚠️ 与同域那几个带 `convertFetchForm` 的页面相反：**每个空值也照发**，也没有 `date` 被拆成两个标量这回事。

## 它同时是**别处的班级候选入口**

课堂三页、学员统计、学习管理页挂载时都会拉
`GET /study/grade/studygrade/page?pageSize=99999&pageNo=1` 把**全部班级**塞进下拉
（实测：一次 99999 条）。那是页面的做法，**无头不照抄**（D6 / H35）。

`study-grade-search` 是按下拉那一套的替代：**强制要关键字** → 用 `name` 查 →
**再在本地过滤一次** → 按 `limit` 截断。返回 `{ list, total, matched }`：
`total` 是后端报的总数、`matched` 是过滤后的条数（两者不同名是有意的）。

## 真实验证（2026-09-21）

- `list()` → **820 条**，URL 与基准逐字段一致。
- `searchByKeyword({ keyword: '班', limit: 3 })` → `matched=3` / 后端 `total=728`；
  **没有**发那个 `pageSize=99999` 的请求；本地过滤后每条都含关键字。
- 页面挂载时还会打一条 `GET /org/organization/getRoleOrganizationTree?roleId=`（归属组织选择器），
  本能力不覆盖 —— 那是长选项参数，要用请先问用户关键字。

## 已覆盖的写动作

### 班级删除

`study-grade-prepare-remove` → `study-grade-remove` → `study-grade-cancel-remove` 对应
`DELETE /study/grade/studygrade`。submit 的 body 是**裸的非空班级 ID 数组**，不是
`{ ids }`，也没有 query；请求使用 platform、权限 `/dashboard/grade/grade`、module-type 12。
Portal 的 `deleteIsBatch: true` 与 Java `@RequestBody Long[] ids` 都支持这一形状。
后端会拒绝已启用的班级；SDK 不把这个业务规则伪装成本地检查。cancel 只返回本地
`{ cancelled: true }`，不会请求服务器。

### 班级详情的移出学员

班级详情隐藏子页另有 `study-grade-student-prepare-remove` →
`study-grade-student-remove` → `study-grade-student-cancel-remove`，对应
`DELETE /study/grade/student`。body 是**班级学员关联记录 ID 的裸数组**，不是学员主表
ID、staffCode 或 `{ ids }`；无 query，同样使用 platform/module-type 12。Java 服务会拒绝
移出班主任。该动作归属 `study-grade.ts`，不误放进学员主表能力。

证据：Portal `grade/list.vue`、`grade/student/[id]/item-list.vue` 与 Java
`StudyGradeStudentRelController` / `StudyGradeController` 静态核对（Portal 基准检出
`acab69acc7`，Java 基准检出 `0f1a55718eb`）。本轮只做请求契约和本地反证测试，未在真实环境
执行删除。

## 班级启停与独立回查（2026-10-08 补齐）

班级行的启用/停用严格按 Portal 两步执行：

1. `study-grade-status-prepare` 根据当前 `status` 取反生成 `{id, status}`；
2. `study-grade-status-check` 发送 `PUT /study/grade/studygrade/updateStatus`。这一步本身是真实写入：启用时可能创建群聊、调整成员并写入课程关系，不能当只读预检；
3. 若返回确认提示，交由用户决定是否调用 `study-grade-status-submit`，它再发送 `PUT /study/grade/studygrade`；没有提示也要由调用方明确确认后提交；
4. 请求完成或不确定时重新调用 `study-grade-list` 核对同一班级的 `status`。`study-grade-status-cancel` 只丢弃本地草稿，不能回滚第一步。

班级详情学员列表由 `study-grade-student-list` 独立读取 `GET /study/grade/student`，组织结构下的班级由 `study-grade-management-center-list` 读取 `GET /study/grade/studygrade/page`；两者分别绑定自己的页面上下文，不能用班级列表页的筛选或权限替代。删除仍需先读取当前行确认停用，再提交裸 ID 数组；真实环境写入闭环尚未执行。

## SDK AI 说明契约（2026-09-22）

本节由当前 SDK 描述结果整理；说明权威来源为 `src/catalog/contracts-business.ts`。调用 `catalog.describe(id)`（或 `id-llm`）可得到参数来源、返回字段/状态、数据消费与后续映射；`catalog.describePage(页面路径)` 用于选择页面功能。以下更新以本节为准；前文历史请求/实测记录仍保留其记录日期。

### `study-grade-list`

浏览学习班级，按名称等条件查看班级基础信息；需要限量候选时使用 study-grade-search。

- 执行：`sdk.studyGrade.list`；通过 `capabilities.invoke('study-grade-list', args)` 调用时按 `params` 填参。性质：read。
- 参数：`name` 可选 (string)；`type` 可选 (string)；`studentNumMin` 可选 (number)；`studentNumMax` 可选 (number)；`teacherName` 可选 (string)；`teachingAssistantName` 可选 (string)；`orgId` 可选 (string)；`pageNo` 可选 (number)；`pageSize` 可选 (number)。完整来源、枚举、条件必填与默认值由 SDK 同次返回。
- 返回：`{ list: object[], total: number }`。list=[] 为当前页无记录；total=0 表示该筛选无结果。保留筛选条件检查页码，不将空结果解释成权限判定。
- 字段：`list`、`total`、`list[].id`、`list[].serialNumber`、`list[].name`、`list[].status`、`list[].type`、`list[].studentNum`、`list[].teacherName`、`list[].teachingAssistantName`、`list[].orgId`。嵌套字段、可空性及业务含义见同次返回的 `returns.fields`。
- 消费：展示班级编号、名称、讲师、学员数与状态；不要把班级 ID 当课堂 ID。
- 完成条件：按用户要求交付本次筛选范围的结果；需要完整清单时继续翻页至覆盖 total，不能把当前页当全集。
- 失败/不确定：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。


### `study-grade-search`

以必填名称关键字查询班级候选；供学习记录和统计筛选选择班级。

- 执行：`sdk.studyGrade.searchByKeyword`；通过 `capabilities.invoke('study-grade-search', args)` 调用时按 `params` 填参。性质：read。
- 参数：`keyword` 必填 (string)；`limit` 可选 (number)。完整来源、枚举、条件必填与默认值由 SDK 同次返回。
- 返回：`object`。可选字段缺省或 null 时展示为空，不当作数值 0。
- 字段：`list`、`list[].id`、`list[].serialNumber`、`list[].name`、`list[].status`、`list[].type`、`list[].studentNum`、`list[].teacherName`、`list[].teachingAssistantName`、`list[].orgId`、`total`、`matched`。嵌套字段、可空性及业务含义见同次返回的 `returns.fields`。
- 消费：显示 list[].name，使用同条 id；matched 只覆盖当前页。候选不唯一请用户选定或收窄关键字。
- 完成条件：按上述数据消费规则交付查询结果；本能力的读取到此结束。
- 后续：optional → `study-record-list`：选定班级后查询学习记录（gradeId ← list[].id）；optional → `study-statistics-lesson-list`：选定班级后查询班课统计（gradeId ← list[].id）
- 失败/不确定：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。

### 两个能力 id 与派单表建议值不同（接线时注意）

派单表对 `GET /sys/user/getUserListPage` 给的建议 id 是 `base-management-center-person-search`，
但**这个 id 已经被组织结构页用了**（`src/capabilities/base-management-center.ts:455`，
标题「按关键字查员工候选（负责人下拉）」，契约在 `contracts-base-management-center.ts`）——
派单是按 URL 去重生成的，同一条 URL 出现在两页时两边的建议值相同，直接用会**撞 id**
（目录是 id 索引的，`describe`/`invoke` 只会解析到其中一份）。
所以本文件改用页面作用域的名字：`study-grade-staff-search`（关键字分页）与
`study-grade-staff-resolve`（按工号回显）。语义与页面的两个调用点一一对应，没有丢东西。

### 三条最容易写错的语义

1. **两个「关联」写收的是同一个 DTO 类**（`StudyGradeOrganizationRelDTO`），但一个读
   `organizationIdList`、一个读 `postIdList`；而 `addGradeOrganizationRelV2` 那条路由的
   **控制器方法名叫 `addGradeOrganizationRelV1`**（`StudyGradeController`，`@LogRecord.subType`
   也照抄了错名）。按路径猜方法名会读错实现。
2. **两个「关联」写都是集合替换**：不在目标列表里的旧组织/岗位会被软删，**名下班级学员关联
   一并软删**并按被移除学员推送移出消息。两者都**没有 `@Transactional`**（
   `StudyGradeOrganizationRelServiceImpl` 上只有 V1 与另一个方法带注解）。
3. **岗位 ID 有两个 ID 空间**：`getGradePost` / `addGradePostRel` 用的是 `hr_post.id`
   （后者 SQL 写 `t3.id as id`）；而 `getOrganizationPost` 树里岗位节点的 `id` 是
   `organizationId + '' + postId` 拼出来的**合成值**，真实岗位 ID 在那个节点的 `postId` 上。
   弹窗提交的是 `postId`（`post.vue:93-97`）。

### 外部依赖：云信群成员与推送

`addGradeOrganizationRelV2`、`addGradePostRel`、`addGradeStudent` 最终都会落到
`pushGradeMessage`：有学员被移出（或加入）时 `zhdjClient.doPost(ADJUST_MEMBERS_FOR_STUDY, …)`
调云信群成员，随后 `zhdjClient.doPost(PUSH_GRADE_API_URL, …)` 推消息，失败抛
「远程调用接口出现异常！」。**完成判据不能写成「班级已更新」**。

一条实测出来的不对称：`addGradeOrganizationRelV2` 的**新增**分支**不调云信**，云信只在
**移除**分支；旧的 V1 反过来（新增带 `addPhoneList` 调云信）。前端现在调 V2
（`organization.vue:80`；V1 那行是注释掉的），所以 SDK 只按 V2 交付。

### 人员候选：必须先要关键字，且三条匹配方式各不相同

三处人员候选都是几千条量级。SDK **拒绝无关键字调用**，并拒绝 `pageSize <= 0`
（`-1` 是全量拉取）与超过 500（`getUserListPage` 的后端 `validatePage` 本来就抛）。
**这是 SDK 侧策略，不是后端要求** —— 无关键字时后端照样返回 200。

| 端点 | `name`/关键字怎么匹配 |
| --- | --- |
| `getUserListPage` | `real_name LIKE %kw%`（包含） |
| `userNotInGrade` | `real_name LIKE kw%`（**仅前缀**） |
| `getExternalStudentList` | `name LIKE %kw%` **或** `mobile LIKE %kw%`（同时匹配手机号） |

每页条数**两处不同**，SDK 的默认值跟各自的页面一致：

| 调用点 | 页面每页 | SDK 默认 | 依据 |
| --- | --- | --- | --- |
| 班级表单的班主任/班长下拉（`study-grade-staff-search` / `study-grade-staff-resolve`） | **20** | 20 | `use-paged-user-options.js:4` 的 `DEFAULT_PAGE_SIZE = 20`；组件没有传 pageSize 进来 |
| 「添加学员」弹窗的两张候选表（`study-grade-student-candidate` / `study-grade-external-student-list`） | **5** | 5 | `add-student.vue:159` 与 `:239` 写死 `pageSize: 5` |

⚠️ 照抄「候选一律 5 条」会让下拉的默认请求与页面不一致 —— 这两个数来自两个不同的
组件，不是同一个默认值。

### `GET /sys/user/userNotInGrade` 的后端缺陷（读源码实测）

它的 SQL 把「本班学员」子查询 `LEFT JOIN` 进来，却**从没在 `WHERE`/`SELECT` 里使用**
（`SysUserDao.xml:197`）。所以这个名叫「不在该班级的用户列表」的接口**并不过滤已在班级的人**，
`gradeId` 只进那条子查询、对结果集没有任何影响。
⇒ SDK **原样透传**，不替后端补本地过滤；AI 说明里点明了这一点，并提示「要判断是否已在班级
必须用班级学员列表另行核对」。

顺带一条同源的：`StudyGradeStudentRelServiceImpl.addStudentByGradeId` 在**任何**工号已在班级时
整单拒绝（「X已在班级中请移除后再添加学员」），所以"从候选里选出来的人"仍可能被服务端拒绝。

### 凭据形状的字段

`getUserListPage` / `userNotInGrade` 的响应 DTO 带 `password` / `password2` / `salt`。
`password` 上有 `@JsonProperty(WRITE_ONLY)` 不会序列化，但 **`password2` 与 `salt` 会真的发出**。
SDK **裁掉这三个键**再返回（`withoutCredentials`）。排班管理那边遇到同形状时是**干脆不做能力**
（`attendance-team.ts` 文件头）；这两条是本批要补的缺口，不能拒，所以采取同族的另一种处置。

### 与「添加学员」空选有关的一处**刻意偏离**

页面 `submit()` 没有任何"未选"保护：不勾任何人也会 `POST { staffCodeList: [] }`
（服务端随后在 `in ()` 上失败）。SDK 在 `prepareAddStudents` 阶段就拒绝空数组并抛出
带说明的错误。这是**有意不逐字复刻页面**的一处，写在 AI 说明的 `consume` 里。
