## 列表参数契约、权限与返回数据

Portal 列表表单初值为 `salaryMonth: ''`、`status: ''`、`operatorId: userStore.state.id`、`name: ''`、`ledgerId: ''`、`organizationId: ''`、`personCount: ''`、`creatorName: ''`、`createDate: ''`、`operateDate: ''`、`salaryTaxBand: ''`。SDK 保留相同的空串默认值；分页默认为 `pageNo=1`、`pageSize=20`，页大小只接受 Portal 的 `10/20/50/100/200/500`。

示例请求：

```json
{
  "order": "",
  "orderField": "",
  "salaryMonth": "2026-09",
  "status": 0,
  "operatorId": 9,
  "name": "",
  "ledgerId": 201,
  "organizationId": 101,
  "personCount": "",
  "creatorName": "",
  "createDate": "",
  "operateDate": "",
  "salaryTaxBand": "",
  "pageNo": 1,
  "pageSize": 20
}
```

`salaryMonth` 为 `YYYY-MM`；`createDate`、`operateDate` 为 `YYYY-MM-DD`。`status=0` 是未结账，`status=1` 是已结账。ID 必须来自当前用户已看到的组织、账套或单据结果，不接受名称冒充 ID。

Java `getPageData` 使用 `@DataScope(organizationAlias="t1", organizationIdAlias="organization_id")`，并将账套范围限制为当前角色可见账套；选择组织时还会展开后代组织。可见账套为空时返回空页。SDK 不把空页解释为权限绕过或租户全量数据。

列表返回 `{ list, total }`。页面消费的主要字段为：

- `id`：薪资单据 ID；后续步骤、详情、删除、结账和拆分使用。
- `name`：单据名称；第一步由组织、账套、工资月份生成默认值，Portal 第一页名称校验已注释，SDK允许空字符串。
- `organizationId`、`ledgerId`：组织和账套 ID；不可用展示名称替代。
- `salaryMonth`、`costMonth`：工资月份和成本归属月份，均为 `YYYY-MM`。
- `personCount`、`unissuedCount`：单据人数和未发放人数。
- `payableTotal`、`deductionTotal`、`actualTotal`：应发、扣税、实发金额；保留 Java 原始数字/十进制字符串，单位为元。
- `status`、`step`：结账状态和核算步骤；`step=1/2/3/4` 分别表示基础信息、人员、外部数据、完成结果。
- `creator/creatorName`、`operator/operatorName`、`createTime`、`operateTime`：审计字段。

身份证号、银行账号、工资金额以及外部导入数据属于敏感业务数据，不写入无关日志。

## 第一至第三步表单规则

### 第一步：组织、账套和月份

页面先 `GET /salary/document/stepInfo?id=<id>&step=1` 读取编辑值，账套候选来自 `GET /salary/ledgerItem/page`。创建提交为 `POST /salary/document/saveFirstType`，请求字段严格为：

```json
{
  "organizationId": 101,
  "ledgerId": 201,
  "salaryMonth": "2026-09",
  "costMonth": "2026-09",
  "name": "2026年09月总部月薪工资"
}
```

`organizationId`、`ledgerId`、`salaryMonth`、`costMonth` 必填；两个月份必须是合法 `YYYY-MM`。Portal 在变更工资月份时把 `costMonth` 同步为相同月份。`name`沿用页面自动生成值，Portal名称必填校验已注释，因此 SDK 不擅自把它变成必填；若手工填写，保留原字符串。

### 第二步：员工选择与资格

页面读取 `stepInfo(step=2)`，保存时只提交每行的 `{ id, name, staffCode, status }`，接口为 `POST /salary/document/saveSecondType/<documentId>`。名单不能为空、`staffCode`不能重复；Java 会再次检查员工已入职、工资办理记录有效且属于该工资月份。返回的 `processedIds`、`processedStaffCodes`、`processedCount` 是实际处理结果，不是请求数量；`excludedStaffList` 必须逐项展示原因。

候选选择请求为 `POST /org/staff/getStaffPageByOrgWithEligibility`，字段为 `documentId`、`staffName`、`staffCode`、`orgId`、`postName`、`pageNo`、`pageSize`。Portal“全选”分支通过 `loopFetch` 使用 `pageSize=500`、最多100页；SDK的 `staffList` 按同一分页请求形状返回单页，调用方需要全量时逐页请求。组织树为 `GET /org/organization/getTree`，历史复用人员为 `GET /salary/salaryhistoryuser/getHistoryUser`。

人员导入为 multipart `POST /salary/document/secondImportWithEligibility`，字段为 `orgId`、`documentId`、`file`；Portal实际可达校验接受 `.xlsx`，Java读取同时兼容 `.xls`，SDK允许两种扩展名并保留 MIME。模板是两段下载：先 `GET /salary/document/secondDownload` 取得 URL，再下载非空二进制文件。导入成功不等于名单已保存，仍要把处理后的名单交给 `saveStaff`。

### 第三步：外部薪资项目

先调用 `GET /salary/ledgerItem/getAllExternalDataSalaryItem?documentId=<id>`。没有外部项目时，页面直接调用 `POST /salary/document/calculate/<id>`；有外部项目时，匹配类型 `1=身份证号`、`2=员工号`，使用 multipart `POST /salary/document/accountResult` 上传文件或读取已有临时结果。上传返回的字符串数组只是识别出的列名/项目名，不是已完成核算；用户确认后必须继续调用 `POST /salary/document/importResult/<id>`，再消费资格结果并读取详情。

外部模板为 `GET /salary/document/download?documentId=<id>&type=<1|2>`，返回非空文件。重新核算页面还会通过无文件的 `accountResult` 读取已有导入列名。上传文件必须先经过 `prepareExternalImport`，文件内容使用非空标准 Base64。

## 结果详情、发放、拆分和状态规则

结果详情为 `GET /salary/document/<id>`。员工明细为 `POST /salary/document/documentUserPage`，请求默认包含 `order`、`orderField`、`documentId`、`status`、`name`、`staffCode`、`pageNo`、`pageSize`；响应为 `{ summary, pageData: { list, total } }`。明细常用字段为 `id`、`name`、`staffCode`、`status`、`grantTime`、`legalPerson`、`needPaySalary`、`realPaySalary`；其中员工 `status=0` 未发放，`status=1` 已发放，已发放行在 Portal 中不可再次选择。详情导出使用同一表单 POST `/salary/document/documentUserPageExport`，默认文件名为 `单据员工明细表.xlsx`。

- 删除：Java拒绝任何 `status=1` 单据；SDK要求每个最新状态为 `0`，成功后必须用原条件按 ID 回查软删除结果。
- 结账：目标状态为 `1` 时，所有当前单据必须为 `0`；请求为 `POST /salary/document/documentCheckout`，体为 `{ ids, status: 1 }`。
- 取消结账：所有当前单据必须为 `1`；Java若发现任一员工已发放工资会拒绝，不能把取消结账理解成回滚发放。
- 重新核算：页面只对未结账单据开放，SDK `prepareCalculate` 在提供当前状态时要求 `status=0`；提交为 `POST /salary/document/calculate/<id>`。
- 发放工资：页面仅在单据 `status=1` 时显示；请求为 `POST /salary/document/paySalary`，体为 `{ documentId, idList, grantTime }`。SDK还要求每个明细最新 `status=0`、发放日期为 `YYYY-MM-DD`，成功或超时后必须按明细 ID 回查 `status=1` 和 `grantTime`。
- 修改名称（未纳入）：Portal顶部“修改单据名称”触发器被注释；活动行“编辑”调用 `rrList.actionEdit(record)`，但该详情目录没有默认编辑路由文件。虽然死代码函数中仍写有 `PUT /salary/document/${route.params.id}` 与 `{ name }`，Java 当前 `@PutMapping` 位于 `/salary/document` 根路径并接收含 `id/name` 的 `SalaryDocumentDTO`；没有菜单可达且契约不一致的候选端点不发布为 SDK 能力。
- 拆分：页面只对 `status=0` 且 `step=4` 的单据开放；名称不能为空、最多30字符，员工工号来自 `getDocumentUsers` 且不能重复。Java还会检查源单据账套、工资月份、组织、成本月份一致以及员工确实属于源单据。
- 临时明细：编辑弹窗先分页读取 `/salary/salaryDocumentDetailTemporary/page`，只提交变化的 `{ id, value }` 到 `/salary/salaryDocumentDetailTemporary/batchUpdate`；这只是临时导入值修改，不等于最终核算完成。

## 操作步骤、失败处理与验证边界

1. 先以当前会话读取列表，按最新 `id/status/step` 决定进入第一步、第二步、第三步还是详情；不要复用旧页面状态执行写操作。
2. 创建按 `prepareCreate → create → get/stepInfo`；第二步按候选/历史/导入 → `prepareSaveStaff → saveStaff`，逐项消费资格结果。
3. 第三步无外部项目按 `prepareCalculate → calculate`；有外部项目按 `prepareExternalImport → externalAccountResult → importExternalResult → detail/detailUsers`。
4. 删除、结账、取消结账、发放、拆分和临时明细修改都必须 `prepare → submit → 回查`；修改名称候选因入口死代码、路由缺失和 Java 契约不一致而不执行。没有安全撤销能力时，用户取消只停在本地。
5. 非法 ID、月份、日期、状态、重复员工、空名单、错误分页、空文件、非法扩展名或非法 Base64 在请求前失败；401/403、网络错误和 Java 业务错误原样抛出。
6. 线上写操作的完成判据是独立回查到目标状态、人员、金额或临时值；不能用 HTTP 成功、空字符串回执或上传成功替代业务证据。
