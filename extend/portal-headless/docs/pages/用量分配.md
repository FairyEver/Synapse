## 权限与范围

页面按钮权限：

- 查询模型、刷新概览和有效分配：`ai-token:usage:query`。
- 保存平均/指定用户分配、下载模板、导入：`ai-token:allocation:save`。
- 清空单个或全部指定用户分配：`ai-token:allocation:clear`。
- 打开申请记录和查询申请列表：`ai-token:apply:query`。
- 驳回或标记申请已处理：`ai-token:apply:handle`。

Java 当前明确标注的接口权限与页面按钮一致：用量分页查询是 `ai-token:usage:query`，保存是 `ai-token:allocation:save`，清空是 `ai-token:allocation:clear`，申请查询/处理是 `ai-token:apply:query` / `ai-token:apply:handle`。当前 Java 对模板下载、导入、概览、预览、有效分配和待处理数没有显式 `@PreAuthorize`；SDK 不把页面按钮条件改写成虚假的后端权限结论。

页面初始模型候选请求固定 `pageNo=1,pageSize=100`，选中第一项；用户搜索必须带关键词并默认 `pageNo=1,pageSize=20`。SDK 不照抄 Portal 可能触发的全量人员候选请求。

## 表单和操作规则

### 平均分配与预览

Portal 的 `buildAveragePayload` / `buildPreviewPayload` 始终提交 `adjustments: []`。本页没有可填写的逐用户调整数组，SDK 拒绝非空数组。

- `modelId` 必须来自模型候选。
- `allocationMethod` 只能是 `0=未分配`、`1=平均分配`、`2=指定用户分配`。
- 预览在 `allocationMethod=1` 时要求 `averageQuota` 为大于 0 的整数；预览本身不写入。
- 保存平均分配时 `averageQuota` 必填且为大于 0 的整数。
- Portal 下拉实际有 `0=继承全局`、`1=禁止使用`、`2=仅提醒`。Java 的平均保存和用户保存服务只接受 1/2，SDK 对这两个保存能力拒绝 0；预览 VO 未校验策略枚举，导入接口只校验非空且服务不再校验，SDK 按 Portal 允许预览/导入提交 0，并保留后端可能没有策略名称的结果。
- 保存时 `startTime` 必填，格式 `YYYY-MM-DD HH:mm:ss`；`endTime` 可空，有值时必须晚于 `startTime`。
- `reason` 可空，最多 500 个字符。
- `preview` 返回概览对象；`exceeded=true` 是超额业务预警，不是请求失败。

预览可以保留页面下拉的 `overLimitStrategy=0`；这只表示预览请求按页面提交，不代表平均保存或用户保存可以接受 0。

平均保存成功只代表后端接受请求。应重新调用 `overview` 和 `listEffective`，核对分配方式、额度、策略和用户有效行。

### 指定用户保存

`searchUsers` 返回的字段映射为：`id → userId`、`mobile → userPhone`、`realName → userName`。Java 保存 VO 的硬校验是：

- `modelId`、`userId`、`allocatedQuota`、`overLimitStrategy`、`startTime` 必填。
- `userPhone` 必须非空；Portal 表单没有显式校验，但后端 `@NotBlank` 会拒绝空手机号。
- `allocatedQuota` 必须为大于 0 的整数。
- 策略只能为 1 或 2；`startTime` 格式同上，`endTime` 可空但必须晚于开始时间。
- `id` 有值是编辑，无值是新增；`userName`、`reason` 可空，`reason` 最多 500 个字符。

保存用户分配后回查 `listEffective`。申请记录的“去分配”流程是：把 `userId`、`userPhone`、`userName`、`expectedMonthlyQuota` 映射到 `saveUser` 的用户草稿，保存成功后再以原申请 `id` 调用 `handleApply(status=4)`；两个请求都成功才能报告申请已处理。

### Excel 模板和导入

模板默认文件名为 `用户额度分配导入模板.xls`，列顺序是：

1. `手机号`
2. `用户名称`
3. `分配额度`
4. `调整原因`

导入 multipart 字段是 `modelId`、`overLimitStrategy`、`startTime`、可选 `endTime`、可选 `reason` 和 `file`。文件支持 `.xls` / `.xlsx`，SDK 输入使用 `fileName + base64 + contentType`。

导入策略按 Portal/Java 实际规则接受非空 `0/1/2`；Java 导入服务没有像 save-average/save-user 一样做 1/2 枚举校验，因此 `0` 可能写入但返回的策略名称为空，调用方应按 `listEffective`/`overview` 回查并如实处理。

Java 服务会先整体校验：手机号非空、手机号不能重复、用户必须存在、每行额度必须大于 0、总分配额度不能超过租户总额度、时间结束必须晚于开始。任一行失败时不写入，返回 `totalCount`、`successCount`、`failureCount`、`failureMessages`；全部成功时替换该模型的用户指定分配，非空的行级 `调整原因` 覆盖批量原因。导入结果必须再用 `listEffective` 回查，不能只依据 HTTP 成功。

### 申请记录

Portal 查询筛选值保留：`0=待处理`、`1=已忽略`、`2=已填写`、`3=已驳回`、`4=已处理`，日期范围转换为 `startDate/endDate` 原值发送。当前 Java 查询/处理枚举与 Portal 筛选存在差异：处理动作只允许 `3=驳回` 或 `4=已处理`，SDK 的 `handleApply` 也只允许这两个值；`listApply` 不擅自删掉页面的 1/2 筛选值，并在 Java 不接受时原样报告后端错误。

驳回原因最多 500 个字符，Portal 没有必填校验；SDK 同样允许空值。处理成功后回查申请列表和 `pendingApplyCount`，确认 `statusName`、`handlerName`、`handledTime`。

## 返回字段

`overview` / `preview` 保留概览字段：`tenantTotalQuota`、`tenantUserCount`、`averageQuota`、`adjustedUserCount`、`unadjustedUserCount`、`allocatedQuota`、`remainingQuota`、`exceeded`、`allocationMethod/name`、`overLimitStrategy/name`、`startTime`、`endTime`、`reason`。

`listEffective` 使用页面真实消费字段：`id`、`modelId`、`userId`、`userPhone`、`userName`、`allocationMethod/name`、`allocatedQuota`、`usedQuota`、`remainingQuota`、`usageStatus/name`、`overLimitStrategy/name`、`startTime`、`endTime`、`reason`。`id` 为空的平均继承行不能直接调用单条清空。

`listApply` 返回页面展示和后续动作所需的 `id`、模型/用户信息、当前/期望月度额度、当前/期望最大 Token、`reason`、`rejectReason`、`status/name`、`handlerName`、`handledTime`。分页始终返回 `{ list, total }`；空列表是筛选结果，不是权限成功。
