# 权限与绑定：按 Portal 页面交互对齐（2026-09-22）

验收范围遵循用户宗旨：SDK 对齐 Portal 的功能和可见性。页面没有的跨账号测试、整个目录树恢复或全库无绑定证明，不作为 SDK 完成页面操作的附加条件。仍如实说明可见回显的歧义，不虚构业务状态。本轮仅只读 Web/Java 源码，未做线上操作。

## 知识空间权限

Web 固定分支 `test/portal/main`，版本 `d3cf56bdc7`：

- `app/portal/views/dashboard/platform/intelligence/knowledge/document/workspace/components/permission-modal/index.vue:14-31`：显示权限范围、指定角色、指定用户与审核人。范围为 1 全部用户、2 指定角色、3 指定用户；角色或用户仅对应分支显示。
- 同文件 `:87-102`：读取 `getPermission`，只取这四项并将 ID 转为字符串供选择器显示。
- 同文件 `:129-144`：角色/用户数组拼为逗号字符串，另一分支发 null；PUT 成功就发 `ok` 并提示“保存成功”。没有跨账号或子树检查步骤。
- 同文件 `:38-39`：取消仅关闭未保存弹窗，没有撤销已保存权限的按钮。

SDK 的 `catalog.describe('ai-knowledge-workspace-set-permission')` 按这一完成条件说明：保存成功则交付本次表单目标；用户重新查看时调用 `ai-knowledge-workspace-permission-get`；超时或响应丢失时另作恢复查询，不自动重放。角色从 `contract-support-role-search.list[].id` 获取，值填 `authRoleIds`，范围填 2。

已知回显问题仍如实保留：Java `KnowledgeFileServiceImpl.getPermission` 过滤 `managerId=0` 后，全部用户可能回显成范围 3 加空用户数组。Portal 也是直接回显，SDK 不把它改成“无人有权”或擅自恢复成 1。null 审核人不会清除已有审核人。以上是现有页面行为边界，不再记为需要跨账号验证才能完成的缺口。

`aiKnowledge.cancelSetPermission({id, previous})` 是既有兼容辅助方法，实际重新调用同一保存接口，不是 Portal 取消按钮，也不是完整回滚。只有用户要求重新保存旧值时使用；未保存的草案直接放弃。旧值必须符合页面表单校验，范围 2/3 的对应选项非空；不能承诺恢复子项各自的原始权限。

## 开放接口删除

同一 Web 版本 `app/portal/views/dashboard/platform/intelligence/prompt/interface/list.vue:68-75,250-262`：

1. 读取选中列表行 `record.isBound`。
2. 真值则提示“该接口已被提示词绑定，无法删除”并终止。
3. false 或字段缺席时允许走普通删除确认；缺失接口 ID 则终止。

因此 SDK 应保持相同的真值拦截，不应要求用户额外证明全库没有绑定，也不应遍历所有技能推断“没有绑定”。字段缺席时允许继续，是页面操作规则，不表示“已证实未绑定”。删除能力先生成计划，`aiPromptTool.openApiRegistry.submit(plan)` 才真正删除；删除计划 `undo=null`，没有恢复接口。

Java `OpenApiRespVO` 未声明 `isBound`，删除实现也没有绑定检查；这不能被 SDK 解释为页面的保护没有意义。只要运行时列表提供真值标记就应阻止删除。`portal-page-compat.ts` 已在 SDK 公共执行门面接入：同一实例的 list 保存最近读取行标记，prepareRemove 和删除 submit 均拦截真值；刷新列表更新标记，不增加业务请求，不跨用户共享。字段缺席仍按页面允许继续，不将其伪称为无绑定证明。
