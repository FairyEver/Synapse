# 时间节点（`/dashboard/manage/protocol-configuration/list`）

> 本页是绩效管理域「配置类」六页之一。**参数顺序怎么来的、六页之间有哪四处不一样**
> 写在 [`src/capabilities/perf-manage-config.ts`](../../src/capabilities/perf-manage-config.ts)
> 的文件头，这里只记这一页自己的东西。
> ⚠️ **这一页没有列表请求** —— 它是一张纯表单（卡片标题写的是「协议配置」）。

| 项 | 值 |
| --- | --- |
| 菜单路径 | `/dashboard/manage/protocol-configuration/list` |
| 页面标题 | 时间节点（页内卡片标题是**「协议配置」**，字典名是 `protocol_config`） |
| 权限码 | `/dashboard/manage/protocol-configuration` |
| 路由文件 | `app/portal/views/dashboard/hr/manage/protocol-configuration/list.vue` |
| 接口（页面自己发的） | `GET /admin-api/sys/dict/type/page?dictType=…` ×2；保存时 `PUT /admin-api/sys/dict/data/updateList` + `PUT /admin-api/sys/dict/data` |
| 接口（读**值**的） | `GET /admin-api/system/dict-data/grouped-list`（全局字典，**页面不自己发**） |
| module-type | 13 绩效管理 |
| 能力 id | `perf-manage-protocol-config-read`、`perf-manage-protocol-config-update` |
| 能力方法 | `readProtocolConfig(dictType?)`、`getDictTypeId(dictType)`、`updateProtocolConfig({dateEntries, contentEntry})` |
| 基准 | `baseline/perf-manage-config.browser.json` 的**两条** `sys/dict/type/page`（本页只认这两条） |

## 这一页在读写什么

页面显示 8 个时间节点 + 1 段提示文案，保存时写回**字典**。两类请求要分清：

1. **页面挂载时自己发的两条**：`GET /sys/dict/type/page?dictType=protocol_config`
   与 `?dictType=template_prompt_content`（`computedAsync`，两条并发）。
   它们**只为了拿字典类型的 `id`**（保存时当 `dictTypeId` 用）—— **值不在这个接口里**。
   对应能力方法 `getDictTypeId()`。
2. **页面上显示的值**：来自**全局字典 store**（`useDictStore`），
   由 app 外壳的 `fetchAllDicts()` → `GET /system/dict-data/grouped-list` 灌进去的
   （不是这一页自己发的）。对应能力方法 `readProtocolConfig()`。

⚠️ **基准里没有 `grouped-list` 那条**，不是抓漏了：它是**外壳**在进门户时拉的，
而基准抓的是"这一页挂载时那两条"。本能力读它与页面同源。

⚠️ 同一份基准里还有**一条噪声**：`POST /admin-api/homePage/save`（body 是首页部件布局的
`config` 数组）**不属于这一页** —— 那是门户首页自己的布局自动保存，因为抓基准时先在首页
装了钩子、SPA 同文档导航不会卸载它，所以被一起抓了。**本能力不做它**，
测试里也不拿它的行数当判据（那种断言会随重新抓基准而红，与本能力无关）。

## 取值的**位置反直觉**：键在 `value`、值在 `label`

`grouped-list` 返回的一组长这样（`{label, value, id}`），而这一页存的是：

| `value`（键） | `label`（值） | 页面的读法 |
| --- | --- | --- |
| `year_submit_review_time` / `year_protocol_sign_time` | `MM-DD 23:59:59`，如 `01-15 23:59:59` | `dealMonthDate()`：`label.substring(0,5).split('-')` → `['01','15']`，用**年月级联**控件 |
| 其余 6 项（月度提交审核 / 月度签订 / 自评起止 / 评价 / 申诉） | `DD HH:mm:ss`，如 `20 17:00:00` | `dealDay()`：`label.substring(0,2)` → `'20'`，用**日下拉**控件 |

- 自评**起**时间存的是 `08:00:00`，其余（含自评止）存 `17:00:00`（`fetch()` 里逐项拼的）。
- 日下拉里有一个**特殊值 `'99'` = 每月最后一天**（`every-month-date.vue`）——
  所以 `review_score_time` 的 label 可能是 `99 17:00:00`。
- 提示文案那一组（`template_prompt_content`）页面取 `[0]` —— 它是**单条**字典，
  `label` 是文案本身。

**把上面这几条读一遍就知道：要回答"现在月度自评时间是什么"，必须读 `label`，
而且要知道它是 `DD HH:mm:ss` 的形状。** 本能力只负责把两组字典原样返回，不做解码
（解码规则是页面逻辑，且上面那张表就是全部规则）。

## 逐字段基准

（`baseline/perf-manage-config.browser.json` 的两条 `sys/dict/type/page`，`_t` 已归一）

```
GET /admin-api/sys/dict/type/page?dictType=protocol_config&_t=<ts>
GET /admin-api/sys/dict/type/page?dictType=template_prompt_content&_t=<ts>
```

`getDictTypeId(dictType)` 与这两条**逐字段一致（含键顺序）**：只有一个 `dictType`，`_t` 在最后。

`readProtocolConfig(dictType?)` 打的是

```
GET /admin-api/system/dict-data/grouped-list?_t=<ts>
```

**一个筛选参数都不带**（能力在**本地**按 `dictType` 过滤出页面用到的那两组；
枚举外的 `dictType` 当场抛，不静默返回空）。请求本身与页面的 `fetchAllDicts()` 同形。

## 真实验证

本波**没有打真实后端**。验证方式是基准逐字段回归 + 反证（见下）。

**没测到的**：字典的真实内容与真实 `dictType` 是否存在；`fetchAllDicts` 与
`readProtocolConfig` 是否真的同源（我只核了源码里两处都调 `grouped-list`）；
保存后字典的刷新链路。

### 反证记录

| 变异 | 红了几条 |
| --- | --- |
| `getDictTypeId` 把 `dictType` 写死成 `protocol_config` | **1**：《dictType=template_prompt_content 的字典类型请求与基准完全相同》 |
| `readProtocolConfig` 不按 `dictType` 过滤（把 `hen_brand` 也返回） | **1**：《readProtocolConfig 只挑出页面用到的那两组，别的 dictType 不返回》 |

## 保存规则与验证边界

保存改的是协议流程的时间口径，SDK 已接入页面保存按钮的两段请求，但尚未在真实测试环境写入：

- **保存时间节点**：先 `PUT /sys/dict/data/updateList`，body 是**数组**
  `[{id, dictValue, dictLabel, dictTypeId}]`（页面当前字典中的日期项）。
- **保存提示文案**：再 `PUT /sys/dict/data`，body `{id, dictValue, dictLabel, dictTypeId}`。
- 两次请求没有事务或 requestId；第二次失败时第一次可能已成功，SDK 不自动回滚或换请求重试。
- 保存成功后页面会 `dictStore.ready = false` + `fetchAllDicts()` 重新拉字典。
- 页面校验（`validateSelfScore`：自评止不得早于自评起；提示内容必填）由调用方在组装 payload 时保持；SDK 额外校验四字段形状，不擅自重排或补造字典项。

### `perf-manage-protocol-config-read`

读取协议时间节点与定性指标提示内容的动态配置值；可作为保存前的完整基线。

执行：`sdk.perfManageConfig.readProtocolConfig`；性质：read。读取协议时间节点与定性指标提示内容的动态配置值；可作为保存前的完整基线。

- 边界：使用当前 SDK 用户与租户的数据权限；页面上下文由 SDK 绑定，调用方不要另拼 module-type。

| 参数 | 意义与来源 |
| --- | --- |
| dictType | 要读哪一组字典，默认两组都返回。取值只有页面用到的那两个 —— `protocol_config`（8 个时间节点）与 `template_prompt_content`（定性指标提示内容）；来源：用户给出的业务条件；格式和必填性按参数契约。 |

返回：`object`。可选字段缺省或 null 时展示为空，不当作数值 0。


- 消费：value 是配置键，label 才是配置值。时间按字段语义读取：MM-DD 或 DD；DD=99 表示每月最后一天。组缺失与组存在但 [] 不同，缺失是字典未配置。
- optional：需要字典类型标识排查配置 → `perfManageConfig.getDictTypeId`。dictType 传 protocol_config 或 template_prompt_content；取字典类型 ID，返回 id 不包含配置值。 映射：{"dictType":"context.dictType"}
- optional：用户确认新的时间与提示文案后，将每个读取项的 id/value/label 映射为 id/dictValue/dictLabel，并补入对应 dictTypeId；提交后重新读取核实。 → `perf-manage-protocol-config-update`。用户确认新的时间与提示文案后，将每个读取项的 id/value/label 映射为 id/dictValue/dictLabel，并补入对应 dictTypeId；提交后重新读取核实。 映射：{"dateEntries":"result.protocol_config[]","contentEntry":"result.template_prompt_content[0]"}

完成条件：解释读取到的时间节点/提示值；缺失组明确报告未配置。

- 失败处理：权限或会话错误要交由用户恢复权限/登录后再读；不要通过换租户、换页面上下文绕过。业务校验失败按原错误修正参数，网络失败的只读查询可重试。

### `perf-manage-protocol-config-update`

按时间节点页的保存顺序更新协议日期字典项和定性指标提示文案。

执行：`sdk.perfManageConfig.updateProtocolConfig`；性质：write。按时间节点页的保存顺序更新协议日期字典项和定性指标提示文案。

- 边界：先 PUT /sys/dict/data/updateList 提交日期数组，再 PUT /sys/dict/data 提交单个提示对象；两个请求没有事务或 requestId。
- 边界：dateEntries 是数组，contentEntry 是单个对象；每项只允许 id、dictValue、dictLabel、dictTypeId。
- 边界：页面权限是 /dashboard/manage/protocol-configuration；真实后端权限仍由当前会话校验，菜单可见不等于写接口授权。

| 参数 | 意义与来源 |
| --- | --- |
| dateEntries | 日期字典更新项数组；顺序沿用 Portal 当前日期字典顺序；来源：perf-manage-protocol-config-read.protocol_config[] 加 getDictTypeId("protocol_config")；逐项把 value→dictValue、label→dictLabel |
| contentEntry | 定性指标提示字典更新对象，不是数组；来源：perf-manage-protocol-config-read.template_prompt_content[0] 加 getDictTypeId("template_prompt_content")；label 替换为新提示文案 |

返回：`null | undefined`。正常空回执；必须重新读取配置核实，不能把空回执当作业务数据。


- 消费：保存后调用 perf-manage-protocol-config-read，逐项比对 dateEntries 的 dictLabel 与 protocol_config[].label，并比对 contentEntry.dictLabel 与 template_prompt_content[0].label。

完成条件：按上述数据消费规则交付查询结果；本能力的读取到此结束。

- 失败处理：第二个提示文案请求失败时，第一个日期数组可能已经保存；先重新读取判断部分成功，不要把失败当作自动回滚。
- 失败处理：网络超时无法判定结果时先重新读取；接口没有 requestId，不要换新请求盲目重发。

- **仍有缺口**：尚未在真实测试环境执行并读回这两个写请求；当前仅有 Portal/Java 源码对照和 mock 请求测试。
