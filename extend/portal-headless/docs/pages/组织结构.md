# 组织结构（`/dashboard/base/management-center/list`）

阶段① 的**第四条换域业务线**，也是「普通 CRUD」这个形态的**第三个样本**。
四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/base-management-center.ts`；
逐字段基准 → `baseline/base-management-center.browser.json`；回归测试 →
`test/base-management-center.test.ts`；真机写链路冒烟入口 → `smoke/base-management-center-crud.mjs`。

它要回答的问题是：

> 图库管理那条线把「普通 CRUD」跑通第二次之后，留下的结论是「同族之间不能互相套用」。
> 那么第三次呢 —— 这一次遇到的不是"哪条规则不一样"，而是**这一页的接口集合本身就与 CRUD 不同**：
> 它多了一个叫 `updateStatus` 的接口，而那个接口**一个字段都不写**。
> 一个"名字像写、实际是读"的接口，应该怎么进能力定义？

结论写在「**这一页真正的新东西：一个名字骗人的只读接口**」与「**三条只能靠源码得出结论、
没有实测**」两节。**后一节比「页面做完了」重要** —— 它是本次唯一没能用真实环境验证的部分。

### 三个名字指同一个东西（这一页最容易找错后端）

菜单叫「组织结构」、路由叫 `management-center`、后端表叫 `hr_study_management_center`、
接口路径是 `/study/base/studymanagementcenter`。

**它不是 hr 域那棵组织树**（`/org/**` 那套），而是教育模块自己的一级组织，
下面挂的是「班级」（`hr_study_grade`）。Controller 的 Swagger 注释写的是「人-一级组织」。

## 本次补充：关联子页的班级删除

关联子页 `grade/[managementCenterId]/item-list.vue` 不是组织主表 CRUD，但它的行尾删除明确
调用 `DELETE /study/grade/studygrade`。因此该动作由 `study-grade.ts` 以组织结构页面上下文
单独登记：`study-grade-management-center-prepare-remove` →
`study-grade-management-center-remove` → `study-grade-management-center-cancel-remove`。

submit 的 body 是**裸的非空班级 ID 数组**，无 query；请求使用 platform、权限
`/dashboard/base/management-center`、module-type 12。后端 Java `StudyGradeController`
只校验数组非空，并会拒绝已启用班级；cancel 仅本地返回取消标记。组织主表自己的
`DELETE /study/base/studymanagementcenter` 不在本次改动内。

这是对隐藏关联子页的能力补齐，不改变下方七个组织主表 CRUD 能力的归属。

## 这一页真正的新东西：一个名字骗人的只读接口

`list.vue` 的 `actionStatus` 是**两步**的：

```js
async function actionStatus (record) {
  const result = await http.put('/study/base/studymanagementcenter/updateStatus', {
    id: record.id, status: record.status === 0 ? 1 : 0
  })
  const fetch = async () => {
    await http.put('/study/base/studymanagementcenter', {
      id: record.id, status: record.status === 0 ? 1 : 0
    })
    message.success('状态修改成功！'); rrList.actionFetch()
  }
  if (result) { Modal.confirm({ title: '提示', content: result, async onOk() { await fetch() } }) }
  else { await fetch() }
}
```

第一个请求打的是 `updateStatus`，**它不写任何东西**。后端：

```java
// StudyManagementCenterServiceImpl.updateStatus —— 全函数只有一次 select
List<StudyGradeEntity> studyGradeEntityList = studyGradeService.selectByManagementId(list);
Integer status = dto.getStatus();
if (status == 0) {
    if (studyGradeEntityList.size() > 0) {
        return new Result<>().ok("禁用一级组织结构，其下属的班级也会被禁用，是否确认禁用");
    }
}
return new Result();
```

它返回的是一个**提示语字符串**（那个 `ok(...)` 把话放进了 `data`），页面拿它去弹确认框。
所以它是「禁用前的预检」，不是提交。

**决定**：它在 SDK 里声明成 `write: false` 的 `base-management-center-check-status`，
并且**不是写链路的必经一步**。理由是能力定义里的 `write` 是给 AI 看的"这个动作会不会改数据"，
而按接口名字给一个只读接口打上 `write: true`，就会让 AI 以为"调了它就禁用了"。

它的**用途是真的**：调用方在禁用一个大组织前，想知道会不会连带禁掉一批班级。

写链路的形状因此是：

```text
check-status（可选，只读预检）→ get → create/update/set-status → remove
```

## 参数契约

### 列表查询（与浏览器逐字节一致）

```
GET /admin-api/study/base/studymanagementcenter/page
  ?order=&orderField=&name=&status=&pageNo=1&pageSize=20&_t=<ts>
```

两个筛选条件都没填，`name` / `status` 照样以空串发出去（renren 列表页的空值默认参数，D20）。
`pageSize` 默认 20（`list.js:391` 的 `styleV2` 分支）。
**参数顺序也是契约**：`list.js:474-481` 拼的是 `order, orderField, ...formState, pageNo, pageSize`。

`src/capabilities/base-management-center.ts` 里的 `buildListParams()` **把键顺序显式写死**，
而不是用 `{...DEFAULTS, ...query}` 那种写法 —— 后者在调用方只传 `pageSize` 时会把
`pageSize` 插到 `pageNo` 前面，序列化出来的 URL 参数顺序就与浏览器不一样了。
反证里改坏这一行会同时打红 3 条用例。

### `name` 是**模糊匹配**（与图库管理不同，与作业管理相同）

后端自定义 SQL（`StudyManagementCenterDao.xml` 的 `getManagementPage`）：

```sql
<if test="dto.name!=null and dto.name!=''">
    and t1.name like CONCAT('%',#{dto.name},'%')
</if>
```

实测：填 `SDK-TEST-A` 时列表从 19 条变 1 条。

⇒ 沿用作业管理那条线踩过的坑：**判断"改名成没成功"时新名字不能包含原名**，
否则用原名查还是查得到。冒烟脚本因此把两个名字取成 `SDK-TEST-1` / `SDK-TEST-3`
这样的**不同槽位**，互相不包含。

### `status`：接口认 0/1，页面上那个下拉是**坏的**（而且是硬失败）

后端的 `status` 是 `Integer`（`ManagementCenterPageDTO`）。实测：

| 请求里的 status | 后端 |
| --- | --- |
| `1` | `ret=SUCCESS`，`total=18` |
| `0` | `ret=SUCCESS`，`total=0`（当轮全库 18 条都是启用态） |
| `TRADE_FINISHED` | **`ret=FAIL`**：`请求参数不正确:Failed to convert property value of type 'java.lang.String' to required type 'java.lang.Integer' for property 'status'; For input string: "TRADE_FINISHED"` |

页面那个「启用状态」下拉是 `portal-education-dict-select type="status"`，
而 `status` 是**全平台共用的字典 key**，装的是**交易状态**。实测下拉里的选项是
「待确认 / 等待付款 / 处理中 / 已完成 / 已关闭 / 已关闭(卖家或买家主动关闭)」，
选中「已完成」之后浏览器真的发出 `status=TRADE_FINISHED`。

**页面的表现是列表直接变空**：`logicFetch` 的 `catch` 走 `listReset()`，
连一句错误提示都没有（实测：选完之后表格变「暂无数据」、`共 0 条记录`）。

⇒ SDK 的处理：`status` 声明成 `enum`（0 禁用 / 1 启用），传别的值**当场 reject 且不发请求**。
与图库管理同一条原则、同一个落点（那边也是 enum 0/1）。

### 后端不认的两个参数

`order` / `orderField` 页面照样发（SDK 也照发，才逐字段一致），但这一页的 SQL 是写死的
`order by t1.create_time desc` + `select distinct`，没有 `${order}` 拼接 —— **排序改不动**。

### 没有数据范围，而且**跨创建人**（实测）

`pageInfo` 里有这一行：

```java
LoginUser user = SecurityFrameworkUtils.getLoginUser();
dto.setCreator(user.getId());
```

但自定义 SQL **一个字段都没用到 creator**（`ManagementCenterPageDTO` 继承了
`DataScopeEntity`，SQL 里同样一条数据范围条件都没有；ServiceImpl 上的 `@DataScope`
是**注释掉的**）。实测无筛选时返回 19 条，`creator` 分别是 18243 / 18324 / 15228……

⇒ 两个后果：
1. **没有"只看我建的"这种过滤**，`creator` 既不是查询参数也不是过滤条件。要按名字筛只能用 `name`。
2. **这一页上新建的任何记录，所有人都会看到** —— 测试数据必须清理，没有"别人看不见"这回事。

### `get` 与 `list` 的字段差别（实测）

`commanderName` / `creatorName` **只有列表接口会填**（`pageInfo` 用 `hrUserApi.getAllLongUserMap()`
补的），`get(id)` 回来这两个字段**永远是 null**。实测：

```text
list  → commanderName="胡明伟"  creatorName="姚淼鑫"
get   → commanderName=null      creatorName=null
```

另外 `code` 字段页面上根本没有控件，两条路径都是 null。

### id 是**字符串**（与图库管理正相反）

`GET /{id}` 的响应体里是 `"id":"36"`（后端把 Long 序列化成字符串），
PUT body 是 `"id":"36"`，DELETE body 是 `["36"]`。唯一一处是数字的地方是 GET 的
**URL 路径段**（`/studymanagementcenter/36`），而那是模板串拼出来的，字符串化后一模一样。

⇒ `normalizeId()` 一律归一成**字符串**。反证里把它改成返回数字会打红 9 条用例。

### 名称 ≤ **10 字**（页面规则，代价实测过）

`[mode]/[id].vue` 的 `rules.name: [{ required }, { max: 10 }, { validateOnlySpace }]`。

实测的代价：第一次用 `SDK-TEST-BMC-A`（14 字）点保存，页面红字报「最多 10 个字符」，
**请求根本没发出去**（基准里没有那条 POST）；换成 10 字的 `SDK-TEST-A` 才发出来。

⚠️ 这条**只是页面的规则**：后端 DTO 上一条校验注解都没有（`ValidatorUtils.validateEntity`
拦不住超长名）。SDK 跟着页面走（页面上做不到的事，SDK 也不替后端"放开"），
但要清楚它的副作用 —— **`SDK-TEST-` 前缀就用掉 9 个字符，只剩 1 位可用**，
而这一页的重名检查是**全局的、且不过滤已删除行**（见下），所以测试数据只有 9 个槽位。
冒烟脚本因此每轮只消耗 1 个槽位并复用另 1 个（详见脚本文件头）。

## 逐字段基准

`baseline/base-management-center.browser.json`（bsk 抓的真实浏览器请求，token 在页面内脱敏）。
读请求 4 条、写请求 5 条，全部是实抓，没有一条是从另一条推出来的。

写请求的形状有一处值得单独看：**编辑页的 PUT 是把整个 `GET /{id}` 响应铺回表单再整份发出去**：

```json
{"id":"36","name":"SDK-TEST-B","commander":"2023040108","commanderName":null,"status":0,
 "code":null,"isDel":0,"creator":"18243","creatorName":null,
 "createTime":"2026-09-20 22:53:37","updater":"18243","updateTime":"2026-09-20 22:53:37"}
```

SDK 的 `update` 只发 `{id, name}`，是这份 body 的**子集**（依据：后端 `update(dto)` 走
MyBatis-Plus 的 `updateById`，只写非 null 字段）。实测（冒烟第 8 步）：只发 `{id, name}` 之后
`commander` / `creator` / `createTime` / `status` 都没被动过。

### `module-type` 这个头在本轮抓到了三种值

12（正常导航进入本页后的第一个请求）、11（并行会话在别的标签页跳走之后）、
**完全不发**（cookie 被写成 `/`，`bsk evaluate` 实测 `hr-0.0.0-menuPath=/`）。
规则表给出的答案是 12，SDK 按页面路径推导，恒为 12。同一条坑在作业管理 / 图库管理上各记过一次。

## 写链路：哪些需要防重

`docs/conventions.md` 第 14 条（后端零幂等）在这个页面上的代价分布如下 ——
**只有 `create` 会产生第二条记录**：

| 写能力 | 重发一次的后果 | 要不要 `requestId` |
| --- | --- | --- |
| `create` | **多一条组织**（后端零幂等） | **要**（门面上的 `createIdempotent`） |
| `update` | 同样的 PUT 再写一次，**业务字段**终态相同 | 不要 |
| `setStatus` | 写的是**绝对值**不是开关，终态相同 | 不要 |
| `remove` | 逻辑删除，重复删后端直接返回成功 | 不要 |

⚠️ 「`update` 重发终态相同」说的是**业务字段**，不是整行逐字节相同：
后端 `updateInfo` 第一件事就是 `dto.setUpdateTime(now)`，**每次 PUT 都会刷新 `updateTime`**。
第一版冒烟拿 `updateTime` 当不变判据，当场跑红（见「真实验证记录」的方法学一节）。

`setStatus` 收的是**目标状态**不是"切换"：页面自己算好绝对值
（`record.status === 0 ? 1 : 0`）。做成 toggle 就会变成不幂等的 —— 那是 SDK 自己造的坑。

### `remove` 是**逻辑删除**，而且**会被下属班级挡住**

- 实测：删完 `list()` 查不到，但 `get(id)` **仍然返回这一整行**，`isDel` 从 0 变成 1。
  ⇒ 「删干净了没有」**只能看列表**，拿 `get` 复核会得到一个看起来像"没删掉"的假象。
  与图库管理（物理删除、`get` 返回 null）**正相反**，别互相套用。
- 源码级：`StudyManagementCenterController.delete` 先查 `study_grade` 里有没有
  `management_center_id` 指向它、且 `status == 1` 的班级，有就返回业务错误
  「本组织结构下设有已启用班级，不可删除，请先删除班级」，**一条都不删**。
  注意 `selectByManagementId` 的 SQL **没有 `is_del` 条件** ——
  被逻辑删除但 `status` 还是 1 的班级**同样会挡住删除**。
  SDK 不做预检查（预检查要另打一个接口，而且查到"没被挡"也不保证删的时候还没被挡）。

### `create` 的重名检查：全局、不过滤 `is_del`、而且**只在 `create` 上有**（全部实测）

```java
QueryWrapper<StudyManagementCenterEntity> queryWrapper = new QueryWrapper<>();
queryWrapper.eq("name", dto.getName());          // ← 没有 is_del 条件
if (managementCenterList.size() > 0) return new Result().error("组织结构名称不能相同");
```

这一段在 `saveInfo`（新建）里；`updateInfo`（改名）里**没有任何重名检查**。实测：

| 动作 | 观察 |
| --- | --- |
| `create` 一个已被**活记录**占着的名字 | 拒绝：「组织结构名称不能相同」，列表不变 |
| `update` 把 idB 改成 idA **正占着**的名字 | **成功**，列表里出现 **2 条同名活记录** |
| 删掉记录之后，再 `create` 同一个名字 | 拒绝（**不过滤 is_del**），列表不变 |

第二行是**刻意用"活记录撞活记录"做的**：如果改用"已删除记录占着的名字"来试，
就算改名真的做了检查、只是跳过了 `is_del` 的行，观察结果也一模一样（有混淆）。

⇒ 这个不对称有实际后果：**页面上「编辑」能造出 `create` 明确拒绝的同名组织**。
SDK 如实复刻接口行为（`update` 不代做检查），但把这条写在 `update` 的文档与这里。

## 三条只能靠源码得出结论、**没有实测**

这三条都是**读取后端源码得到**的，本次**没有在真实环境里验过**。逐条写清楚为什么没验，
以及它带来什么：

### ① `commander` 为 null 的记录会让**整个列表页 500**

```java
// StudyManagementCenterServiceImpl.pageInfo —— 没有 null 判断
studyManagementCenterDTO.setCommanderName(
    nameMap.get(studyManagementCenterDTO.getCommander().toString()));
```

`commander` 是 `Long`，为 null 时 `.toString()` 直接 NPE，而它发生在**遍历结果集**的时候，
所以**只要库里存在一条 commander 为 null 的行，这页面对所有人都打不开**。
后端 `saveInfo` 又对 commander 一条校验都没有（DTO 上完全没有校验注解），
所以「新建时不给负责人」这条路在后端是通的，代价是别人的列表页挂掉。

**为什么没实测**：验证它要先制造一条 null commander 的数据，而那条数据存在期间
**所有人的列表页都是 500**（这一页的列表是跨创建人的）。这个代价不该由测试环境里的其他人付。

**SDK 怎么办**：`create` **强制要求 `commander`**（缺了当场报错，不发请求）。
这是这次唯一一条"为了不制造坏数据而收紧了契约"的地方。
`test/base-management-center.test.ts` 有一条用例专门锁它，反证里放水会当场变红。

### ② `update` 里改 `commander` 会**给那个员工开账号并授 SUPER_ADMIN**

```java
// StudyManagementCenterServiceImpl.updateInfo
if (dto.getCommander() != null) {
    hrUserApi.createUser(dto.getCommander(), Global.SUPER_ADMIN);
}
```

而 `saveInfo`（新建）里同样的调用是**被注释掉的**（`//sysUserService.createUser(...)`）。
所以新建时给 commander 是安全的，**编辑时改 commander 不是**。

**为什么没实测**：它会去改一个**真实员工**的账号与角色，越过了「只碰自己创建的测试数据」这条线。

**SDK 怎么办**：`update` **不接受 `commander`**（只收 `{id, name}`）。
这是"某个写操作无法在只碰自己数据的前提下测 → 就不做它、并写进文档"的直接应用。

### ③ 删除守卫会算上**已逻辑删除的班级**

`selectByManagementId` 的 SQL 里没有 `is_del` 条件，而 Controller 只按 `status == 1` 过滤。
**为什么没实测**：要验它得先有一个"班级全被删了、但 status 还是 1"的一级组织，
而造班级要动 `hr_study_grade`（另一个页面 / 另一条业务线），不在本次范围。

## 操作步骤（AI 侧）

1. 想查组织：`base-management-center-list`，`name` 用**名字里的一段**（模糊匹配），
   或者 `status` 用 0/1。⚠️ 别用页面上那个「启用状态」下拉的取值（它是交易状态字典）。
2. 要改名/改状态/删除某一条：先 `base-management-center-list` 拿 id（字符串），
   必要时 `base-management-center-get` 看当前值。
   ⚠️ `get` 回来的 `commanderName` / `creatorName` 永远是 null，那是**接口差别不是数据缺失**。
3. 新建：`base-management-center-create { name, commander }` —— **两个都必填**，
   `name` ≤10 字且**全局唯一**（重名会拿到业务错误「组织结构名称不能相同」），
   `commander` 是员工工号形式的 username。
   建完**回列表按名字查一次**才算证实（后端不返回新 id）。
4. 只改名字：`base-management-center-update { id, name }`。
   ⚠️ **它不会检查重名**，改名可能撞出两条同名组织（`create` 会拒绝的事，`update` 放过去）。
   ⚠️ 改负责人**不在契约里**（会触发给该员工授 SUPER_ADMIN），要改请走页面。
5. 启用/禁用：先 `base-management-center-check-status { id, status: 0 }` 看会不会连带禁用班级
   （返回非空字符串就是要弹确认的那种情况），再 `base-management-center-set-status { id, status }`。
   ⚠️ 传 0 会把它下面**所有班级**一并禁用。
6. 删除：`base-management-center-remove { id }` —— **逻辑删除**，
   删完 `get` 仍返回整行（`isDel=1`），**要确认删干净了请看列表**。
   ⚠️ 下属有已启用班级时删不掉。
7. **测试数据只能用 `SDK-TEST-` 前缀 + 在这里清理**：列表跨创建人，所有人都会看到。

### 真实环境的方法学说明（如实记）

- **反证（第 22 条）做了 12 组**，全部当场打红，逐条列在「反证记录」一节。
- **有一条断言写错了，是测试的问题不是实现的问题**：第一版把"update 重发终态不变"
  写成了 `updateTime` 不变，跑出来是红的。查后端源码才明白 `updateInfo` 第一件事就是
  `dto.setUpdateTime(now)`，**每次 PUT 都刷新它**（两次 PUT 落在同一秒时会看起来没变，
  跨秒就前进：实测抓到过 …22:59:25 → …22:59:26 与 …23:01:42 → …23:01:43）。
  改成比业务字段（name / commander / status）之后是绿的，
  并把这条观察单独留成一条断言（`updateTime` **会**前进）。
  **没有为了让测试变绿去放松断言** —— 放松的是那条错的判据，换成了正确的判据，
  而且在冒烟脚本里留了一句注释说明为什么不能用 `updateTime`。
- **"用 `list` 探测可用名字"也是写错过的**：`list` 过滤 `is_del=0`，
  看不见"已删除但名字还占着"的记录，于是脚本每一轮都以为 `SDK-TEST-1` / `SDK-TEST-2` 是空的。
  改成**直接试探 `create`**（失败的 create 在写库前就 return 了，没有副作用）。
  这条错误与更正写进了冒烟脚本的文件头。
- **`checkStatus` 的"返回值是提示语"这一支没有实测**：要拿到那句
  「禁用一级组织结构，其下属的班级也会被禁用，是否确认禁用」，得有一个**带着已启用班级**的组织，
  而造班级要动 `hr_study_grade`（另一条业务线）。实测到的只有"没有班级 → 返回 null"这一支。
- **这一页的 `getAllCenter` 接口没有进能力定义**：`GET /study/base/studymanagementcenter/getAllCenter`
  在后端存在（返回 `status=1` 且 `is_del=0` 的组织，按 id 升序），但**这一页的前端没有调用它**
  （它是别的页面选组织用的下拉数据源）。能力是"页面动作"的单位，不是"接口"的单位（设计 H2），
  所以不收录。
- **`grade/[managementCenterId]/item-list.vue`（行内「管理班级」）不在本次范围**：
  它路由到另一条页面（班级管理），打的是 `/study/grade/studygrade/page`，是另一条业务线。

## 尚未覆盖

- **上面「三条只能靠源码得出结论、没有实测」那一节的全部内容。** 它们不是"没来得及"，
  是**测了就要越线**（把共享环境的列表页弄挂 / 改真实员工的账号 / 动另一条业务线的班级）。

  第三条只写进文档。
- **`update` 没有重名检查这件事没有在 SDK 侧做补偿**。默认行为是如实透传
  （调用方把一个组织改成与另一个组织同名，会成功）。做补偿要么是"改名之前先查一次重名"
  （多打一个接口，而且查到没有也不保证改的时候还没有），要么是本地拒绝
  （那就比接口严了）。两条都超出"如实驱动接口"的范围，所以只写进文档。
- **`commander` 的合法取值没有被校验**。SDK 只校验"非空"，因为页面给的候选是
  `/sys/user/getUserListPage?pageNo=1&pageSize=20` 那一页 20 个人（下拉只加载第一页），
  而后端 DTO 是 `Long`（非数字的 username 会在 Spring 绑定阶段失败）。
  SDK 不做本地白名单：那需要另打接口，而且候选是分页的，本地名单一定是错的。
- **`getAllCenter` 没有收录**（理由见上）。
- **班级管理子页不在本次范围**（`/dashboard/base/management-center/grade/...`，
  另一条业务线）。
- **SDK 在 GET 上多发一个 `Content-Type`（值 `undefined`），浏览器不发。**
  这是 `src/http/headers.ts` 的**既有行为**，不是本页引入的（作业管理 / 图库管理已各记一次）。
  它不属于本次任务的文件范围（`src/http/**` 未授权改动），**没有修**，
  也没有在测试里断言它 —— 那会把一条既存行为锁成契约。
