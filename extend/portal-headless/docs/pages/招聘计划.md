# 招聘计划（`/dashboard/staff/recruitment-plan/list`）

本页覆盖招聘计划列表、计划表单、计划下的简历与面试记录，以及 Portal 页面实际提供的模板下载、Excel 导入、审批和申请入职入口。

证据边界：已逐页核对 Portal 列表、计划表单、简历/面试子页和 Java Controller、VO、Service；SDK 请求投影、表单校验、状态门禁和 AI 说明有离线测试。当前没有启动测试门户，没有把离线测试写成真实环境证据；真实读请求、写入回查、导入和级联删除仍待 smoke。

来源锚点：Portal `CodeReview_Projects_Js@test/portal/main@acab69acc77b6d6c0da21310cdfd26b91a01641e`；Java `CodeReview_Mall_Platform_Java@test/test@0f1a55718ebc1987affb8bf245106e809dd51da4`。

## 一、页面上下文、范围和权限

| 项 | SDK/Portal 事实 |
| --- | --- |
| 菜单与页面 | `hr/人力` → 招聘计划；列表 `/dashboard/staff/recruitment-plan/list` |
| 页面权限 | `/dashboard/staff/recruitment-plan`；列表源码没有额外的按钮级 permission 指令，Java Controller 也没有新增动作级注解 |
| HTTP 实例 | `platform`；SDK 的逻辑路径以 `/hr/...` 写出，由实例规则补 Portal 的 `/admin-api` 前缀 |
| `module-type` | `11`；不省略页面数据范围上下文 |
| 计划流程 | `simple/hr/form/026`，process key `recruitment_plan` |
| 简历入口 | 计划状态 `2=已审批` 时列表行才打开 `/dashboard/staff/recruitment-plan/resume/{planId}` |
| 入职入口 | 简历状态 `1=适合` 时打开 `simple/hr/form/001`，process key `ruzhi`；SDK 只准备跳转参数，不提交入职流程 |

所有能力的 `pagePath`、`permission`、`moduleType` 和 `httpInstance` 都相同。权限、租户、会话 token 和数据范围由 SDK 会话/HTTP 层注入；本页没有凭据或 Cookie 提取逻辑。

页面动作和状态门禁：

- `status=3`（已驳回）才显示编辑/重新提交；`status=1`（审批中）才显示撤销；`status!==1` 才允许删除。
- 计划状态 `2` 才能维护简历。Java 对简历新建、编辑和导入再次校验父计划已审批。
- 简历 `status=1` 才显示申请入职；SDK `prepareOnboarding` 也会拒绝其他状态。
- 页面没有计划、简历或面试的按钮级权限码。SDK 不凭空增加一套权限判断，但不会绕过服务端状态、租户和数据权限。

## 三、参数、表单和提交规则

### 3.1 计划列表

Portal 列表请求始终带 `order=''`、`orderField=''`、`organizationId`、`postId`、`planYear`、`recruitmentType`、`status`、`createTimeStart`、`createTimeEnd`、`pageNo`、`pageSize`。默认 `pageNo=1,pageSize=20`，可用页大小为 10/20/50/100。

- `planYear` 是列表筛选值，历史年度可以查询；它不能套用新建表单“不得早于当前年份”的规则。
- `createTime` 范围不原样发送；调用方传 `createTimeStart` / `createTimeEnd`，页面语义分别是 `YYYY-MM-DD 00:00:00` 和 `YYYY-MM-DD 23:59:59`。
- 组织、岗位、招聘类型、状态均按 ID/枚举传递；空筛选值保留为 `null` 或空字符串，空列表不等于无权限。

### 3.2 计划表单

`prepare`/`prepareUpdate` 接收 `draft`，只投影 Java 保存 DTO 字段；页面使用但不作为 Java 提交字段的 `postTypeName` 等 UI 展示值会被丢弃。

| 字段 | Portal 规则 |
| --- | --- |
| `recruitmentType` | 必填，1=计划内、2=计划外 |
| `planYear` | 必填整数，不能早于当前年份；列表筛选没有此下限 |
| `organizationId` / `postId` | 必填正整数；岗位必须来自所选组织候选，组织变化时清空岗位 |
| `organizationName` / `postName` | 名称快照，可空但不能替代 ID；各最多 100 字 |
| `planNumber` | 必填正整数 |
| `purpose` | 必填：业务扩编、人才储备、岗位新增 |
| `requirementText` / `remark` | 可空，各最多 1000 字 |
| `salaryLevelMin` / `salaryLevelMax` | 两端都必须选择薪资等级 ID；Portal 不比较上下限顺序 |
| `urgency` | 必填：特急、紧急、常规、储备 |
| `arrivalDate` | 必填，`YYYY-MM-DD` |

新建和重新提交都必须先拿到 `tasks`：

```text
prepare(draft)
  → 用户按 tasks[].id 选择审批人
  → create({ draft, tasks, startUserSelectAssignees, overwrite? })
```

`startUserSelectAssignees` 的键只能来自 `tasks[].id`，值为正整数人员 ID 数组，并按节点的最小/最大选择人数校验。人员候选复用 `base-user-search`，不能复制 Portal 无关键字拉取数千人的行为。`prepareUpdate` 只接受当前 `status=3`，更新仍需完整 `draft`、`tasks` 和审批人映射。

创建重复时首次固定 `overwrite=false`；只有服务端明确返回覆盖语义并得到用户确认，才使用同一业务载荷重试 `overwrite=true`。成功或超时都必须按返回计划 ID `get` 回查，不能把 ID 或 `true` 回执当作持久化证据。

### 3.3 计划模板和导入

- 计划模板必须传 `organizationId`，返回 `{ fileName, contentType, byteLength, base64 }`；默认文件名 `招聘计划导入模板.xlsx`。
- 计划导入仅接受 `.xlsx`，输入为 `{ fileName, base64, contentType? }`；multipart 字段只有 `file`，覆盖开关在 query string。
- Java 导入直接落为 `status=2`（已审批），不启动审批流程；成功文本仍需按组织、年度、类型、岗位回查列表。

### 3.4 简历表单、附件和导入

简历子页请求固定带 `planId`、从计划详情带出的 `postId`，以及 `name`、`phone`、`status`、`pageNo`、`pageSize`；默认页大小 20。保存字段如下：

| 字段 | Portal 规则 |
| --- | --- |
| `planId` | 必填父计划 ID；后端要求父计划 status=2 |
| `name` | 必填，最多 10 字 |
| `age` | 必填整数，1–100 |
| `sex` | 必填，1=男、2=女 |
| `education` | 必填：博士研究生、硕士研究生、本科、大专、高中、初中、小学 |
| `major` / `workYears` / `graduateSchool` / `phone` / `intendedPost` / `expectedSalary` | 必填，各最多 20 字；不擅自把工作年限或薪资换算成数字 |
| `attachments` | 必须 1–3 件；SDK 输入数组 `{ name, url }[]`，提交时序列化为 JSON 字符串 |
| `status` | 可省略，后端默认 0=普通；1=适合时才显示申请入职 |

文件先通过 `base-upload-file` 得到 URL；Portal 上传控件限制 `.doc/.docx/.pdf/.jpg/.jpeg`、单个不超过 10MB，SDK 不把本地路径当附件。简历模板默认名 `招聘简历导入模板.xlsx`；简历导入接受 `.xlsx/.xls`，multipart 字段为 `planId` 和 `file`，没有计划导入的 overwrite 二次确认。

`planStatus` 在简历准备/保存方法中是可选的本地上下文校验：传入时必须为 `2`；未传时仍由 Java 的 `validateApprovedPlanExists` 作最终门禁。导入也由 Java 校验父计划状态。

### 3.5 面试表单

面试列表只读当前简历，固定最多请求 100 条。面试准备/保存必须传当前简历 `resumeId`，不能用计划 ID 代替。

必填规则：`interviewDate` 为 `YYYY-MM-DD`；`interviewer` 最多 50 字；`interviewRound` 为初面/复面/终面；以下六项均为整数 1–10：

`professionalKnowledgeScore`、`communicationScore`、`learningAbilityScore`、`executionAbilityScore`、`teamworkScore`、`stabilityScore`。

`personalAdvantage`、`personalShortcoming`、`workExperienceSummary` 可空且最多 500 字；`questionAnswer` 必填且最多 500 字；`conclusion` 必填且为优先录用、考虑备选、待定复试、不予录用之一。Portal 未在本页调用面试详情接口，编辑使用当前列表记录。

### 3.6 申请入职跳转

`prepareOnboarding({ plan, resume })` 只接受 `resume.status=1`，返回：

```text
{
  path: 'simple/hr/form/001',
  processKey: 'ruzhi',
  bpmMode: 'edit',
  customQuery: {
    resumeId, planId, employeeName, sex, phone, workExperience,
    organizationId, organizationName, postId, postName
  }
}
```

这一步只复刻 Portal 的打开表单参数，不代表已提交入职流程；表单 001 的后续字段、审批人和提交由下游流程能力负责。

## 四、统一操作、失败和回查

计划写入统一走 `prepare → 用户确认 → create/update → get/list 回查`。取消和删除不是本地补偿：取消只对最新 `status=1` 调 `cancel`，删除只对最新 `status!=1` 调 `remove`，随后分别回查状态或列表；删除还要核对简历和面试级联结果。

简历和面试的 `prepare*` 是本地校验/载荷准备，不会伪造服务端 prepare 接口；写入后按 `planId`、`resumeId` 或面试列表回查。用户在准备阶段取消时不发写请求；写请求超时先回查，再决定是否重试。

会话失效、租户/权限/module-type 不匹配、服务端状态校验、响应形状错误和文件空响应均抛错。空 `list` 只代表当前筛选没有记录，不解释为权限不足。
