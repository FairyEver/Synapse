# 加班申请（`/simple/hr/form/042`）

流程表单第三条线。`docs/process-forms.md` §2.2 的第一梯队（通用审批 / 请假 / 用车 / 产品文档）
在前四条线里做完之后，人力域里下一条「普通员工日常会用」的流程就是**加班申请 / 调休申请**这一对
（`hr/form/042` 与 `043`）。本单做 **042（加班）**——它的只读联动比调休那条更丰富
（时长自动算 + 结束时间不得早于开始），而且它的**审批链形态与前四条线都不同**（见 §四）。

> 四件套：能力 `src/capabilities/overtime-application.ts` · 测试 `test/overtime-application.test.ts` ·
> 基准 `baseline/overtime-application.browser.json` · 冒烟 `smoke/overtime-application.mjs`。

### 2.1 只读联动（本页面上真的会变的那几处）

1. **申请人 / 申请时间 / 申请部门**：`initUserInfo()` 从 `useUserStore().state` 取，
   而那个 store 由路由 `meta.baseData: ['user-basic']` → `utils/system.js` 的
   `fetchSimpleUserBasic()` → **`GET /sys/user/info`** 填。页面上这三项是**纯文本，没有 input**。
2. **加班时长**：`watch([startTimeValue, endTimeValue, breakHours])` → `calculateOvertimeHours()`。
3. **中途休息时长的上限**：`:max="maxBreakHours"` = 结束−开始 的小时数（同一天内）。
4. **结束时间**：开始未选时整体 `disabled`；同一天时 `disabledHours` 屏蔽 ≤ 开始小时，
   分钟/秒只能选 00（`disabledMinutes`/`disabledSeconds` 屏蔽 1..59）。
5. **开始时间变化后**：若结束 ≤ 新的开始，页面**清空结束时间**并提示「结束时间已清空，请重新选择」。

### 2.2 ★ 加班时长的算法：**逐位复刻，不允许自己发明**

`042/page/pc/edit/index.vue:387-392`：

```js
const diffHours = end.diff(start, 'hour', true)      // 浮点小时
const breakHours = formState.value.breakHours || 0
const overtimeHours = Math.max(0, diffHours - breakHours)
formState.value.overtimeHours = parseFloat(overtimeHours.toFixed(1))
```

**后端不重算**（`OvertimeApplicationServiceImpl.validateAndFillHours()` 只校验
`endTime.isAfter(startTime)` 与 `breakHours >= 0`），所以前端算错就**错着入库**。
SDK 的 `calculateOvertimeHours()` 就是上面那三行，`toFixed(1)` 之后再 `parseFloat` 也照抄
（`3.0` 会变成 `3`，与浏览器发出去的 JSON 一致）。

**`toFixed(1)` 与「四舍五入」在真实输入上是分叉的**：3 小时 3 分 = 3.05，
二进制里是 3.0499999999999998 ⇒ `toFixed(1)` 给 `"3.0"` ⇒ **3**；
而 `Math.round(3.05*10)/10` 给 **3.1**。测试里专门钉了这一组（§七 变异 1）。

### 3.2 ★ 两处容易抄错的类型

| 字段 | 类型 | 为什么 |
| --- | --- | --- |
| `applicantId` | **字符串 `"18243"`** | 来自 `/sys/user/info` 的 `id`，那个接口返回的就是字符串，页面直接赋值不做转换 |

## 四、★ 审批链：本流程与前四条线**形态不同**，这也是本能力最有价值的一段

### 4.1 实测：**没有「发起人自选」节点**

```
POST /hr/overtime-application/getRequiredStartUserSelectTasks   body = 完整载荷
→ { "code": 0, "ret": "SUCCESS", "data": [] }        ← 一个节点都没有
```

三点与前面几条线的差异：

1. **恒返回 `[]`**。通用审批返回 1 个、产品设计文档审核返回 2 个（`candidateStrategy=35`）；
   本流程**一个都没有**。
2. **它要收完整载荷**。`@Valid @RequestBody`——传 `{}` 会被打回
   「请求参数不正确:结束加班时间不能为空」（实测 400）。通用审批那条线的后端
   把请求体整个忽略；这里不是。
3. **所以 `startUserSelectAssignees` 是 `{}`**，与
   `common/libs/flow-form/start-user-select.js` 的 `finalize()` 里
   `if (tasks.value.length === 0) return {}` 一致。

### 4.2 那审批人是谁？—— `bpmnXml` 里的 `candidateStrategy="23"`

```
<userTask id="Activity_158exxp" name="直属上级审批" flowable:candidateStrategy="23" .../>
```

`23 = BpmTaskCandidateStrategyEnum.DIRECT_LEADER（直属上级）`。
`POST /bpm/process-instance/preview` 的响应（实测）：

```
USER_TASK 直属上级审批 [strategy=23 直属上级] → 候选人 乔娜(15012)
```

⇒ **审批人是后端按发起人所在组织算出来的，发起人既不知道、也选不了**（页面上要
点「查看审批流程」才看得到）。

### 4.3 ★★ 提交前的硬守卫：**审批链里不能有发起人本人**（比前四条线强）

**为什么必须有**：后端 `BpmTaskServiceImpl` 有一条「流程发起人与审批人相同，自动审核通过」。
命中时流程**当场走完**，`cancel-by-start-user` 从此必然报
「流程取消失败，流程不处于运行中」——那条单据**永远撤不掉**
（测试环境里已经因此留了 3 条 `status=2` 的记录，本轮一条都没碰）。

**前四条线的做法**：`assertAssigneesForTasks` 之外再看一眼「别把审批人选成自己」。
它只对 `candidateStrategy=35`（发起人自选）有效——**本流程压根没有那种节点，这条拦不住**。

**本能力的做法**：判据换成**真实审批链**。

```
POST /bpm/process-instance/preview   body {processDefinitionKey, variables: <本次载荷>, ...}
  → nodes[].type === 'USER_TASK' 的 candidateUsers[] 里逐个比对发起人 id
  → 命中 ⇒ **在 create 之前**抛错，一个写请求都不发
```

**强在哪，逐条对比：**

| | 前四条线 | 本能力 |
| --- | --- | --- |
| 判据来源 | **调用方传进来的 assignees** | **后端算出来的真实审批链** |
| 覆盖范围 | 只有 `candidateStrategy=35` 的节点 | **所有** `USER_TASK`（直属上级 / 部门负责人 / 岗位 / 用户组…） |
| 防不防得住"猜不到的审批人" | ❌ 防不住（那种流程没有自选节点） | ✅ 正是它的目标 |
| 什么时候发现 | 提交前（但只对自选节点有效） | 提交前（`create` **之前**） |
| 顺带产出 | —— | **"这次会打扰谁"**，报告里能如实写出来 |

预演的实际效果【实测 2026-09-21】：`variables` 用真实载荷打过去，
`Activity_158exxp` 的 `candidateUsers` = `[{id:15012, nickname:'乔娜'}]`，
发起人是 18243 ⇒ 不是同一人 ⇒ 放行。

**两条边界，如实记下：**

- **逃生口**：`skipSelfApprovalGuard: true`，只在预览接口本身不可用时才该用，默认**关着**。
  理由与 `assertAssigneesForTasks` 一样：宁可让调用方显式承认"我在冒险"，也不要静默放过去。
- **这条守卫不能证明**审批人最终一定是预览里那个人。预览是"按当前数据算一遍"，
  真实办理时后端会拿**当时**的组织数据再算一次；组织架构刚变过时两者可能不一致。
  SDK 能保证的是：**预览时命中自己就一定拒绝**。

### 4.4 请求顺序（只有最后一条是写）

```
① GET  /sys/user/info                         (submit 里只打一次)
② POST /hr/overtime-application/getRequiredStartUserSelectTasks   页面 formSubmit() 的第一步
③ POST /bpm/process-instance/preview          ★ SDK 加的守卫（页面上是用户点按钮才发生）
④ POST /hr/overtime-application/create        写
```

守卫插在 ③ 而不是更早，是为了保持页面上 ①→④ 的**相对顺序不变**；
它只多一次**只读**请求，却能把"单据永远撤不掉"挡在写之前。

### 4.5 详情接口里**没有** `processInstanceId`

`OvertimeApplicationRespVO` 只到 `status` / `statusName`（⚠️ 与通用审批不同：
**本流程的 `statusName` 后端真的填了**，实测「已取消」）。
⇒ 撤销要先用 `findInstanceByBusinessKey()` 去「我的流程」按 `businessKey` 换流程实例 id。
`businessKey` 是**各业务表自己的主键**，会与会议室/请假撞车，所以还要按
`processDefinitionKey` 再筛一道（有测试钉住）。

## 五、操作步骤

```bash
smoke/with-portal-token.sh node smoke/overtime-application.mjs
```


`status=4`。撤销放在 `finally` 里，中途任何一步炸了都会兜底再撤一次。

脚本自带的四条自我约束：事由强制 `SDK-TEST-` 前缀；提交前必须过审批链守卫；
只操作自己刚建的那一条；**`baseUrl` 不是 `biz-api-test.wodecorp.cn` 直接拒绝执行**。

### 7.1 「测试太弱」类假绿的排查（这一轮专门留意的三种）

1. **同义反复的常量断言**：`calculateOvertimeHours` 的 9 组输入，
   期望值是**逐个写死的字面量**（`[3, 2.5, 8, 3.3, 1.5, 3, 0, 0, 0.5]`），
   不是 `calculate(...)` 的复算结果。
2. **`[0]` 与 `[last]` 同值**：审批链守卫的用例**故意做成多节点多候选人**——
   `T1(11,12) / T2(21,18243) / T3(31)`，断言命中的是 `T2` 的**第二个**候选人；
   另一条用 `T1/T2/T3` 三处命中，断言 `['T1','T2','T3']` 全在（堵住"找到第一个就 break"）。
3. **提前 break 的分支走不到**：`findSelfInApprovalChain` 只看 `USER_TASK` 这条分支，
   被一条**专门的反向用例**盖住——把发起人塞进 `START_EVENT`/`END_EVENT` 必须**不命中**，
   然后**再补一个 `USER_TASK` 节点证明命中**（否则"不命中"可能只是因为整个函数不工作）。

   另外：校验类用例统一用**不带 `overtimeHours`** 的 `DERIVED`，
   避免"改时间"的用例红在「overtimeHours 被改过」那条一致性检查上——
   那会看起来测到了，其实测的是另一条。

## 八、尚未覆盖 / 不确定

### 8.1 确实没做的

- **「重新发起」（reapply）没做**：`isReapply` 分支会从原流程实例抄字段再提交
  （`fetchDetail()` 里 `formState = {...result, id: null}`），是一条**另起的写链路**，需要单独验证。
- **改动 / 删除单据没做**：`PUT /hr/overtime-application/update` 与
  `DELETE .../delete/{id}` 在**后端源码里整个被注释掉了**
  （`OvertimeApplicationController:55-68`），页面上也没有入口 ⇒ **接口不存在**，谈不上没做。
- **详情页的「打印」没做**：只读展示件，打的是通用打印壳，不影响能不能提交。
- **`/hr/overtime-application/record/*`（加班记录分页/详情/剩余时长）没做**：
  那是**另一个页面**（考勤管理下的「加班记录」），不是本流程表单的一部分。

### 8.2 不确定的（**不要读成"已验证"**）

- **「预览里的审批人 = 最终实际审批人」没有独立证实**。本轮只证实了
  "提交后流程 `status=1`、撤销后 `status=4`"，**没有**去证实"待办真的落在乔娜的箱子里"
  ——那要读她的待办列表，属于别人的数据，本轮没碰。
- **`applyDate` 的时区**：SDK 固定按 `Asia/Shanghai` 算"今天"，与浏览器一致；
  但这**只在测试环境这一个门户上**验过（其它 17 个环境没验）。
- **`skipSelfApprovalGuard` 这条逃生口一次都没在真实环境用过**。它只是"预览接口挂掉时
  还有没有办法提交"的兜底，本轮没造过预览挂掉的场景。
- **`assertTasksCovered` 的两条分支在真实环境上是死的**：本流程实测恒 0 个自选节点，

## 2026-09-22 AI 说明契约同步

权威契约在 `src/catalog/contracts-workflow.ts`，经 `catalog.describe(id)` / `id-llm` 的 `ai` 实际返回；`describePage` 同步用途与功能区别。额外公开门面通过 `catalog.describeMethod(sdkPath)` 下钻，无需调用方读仓库。

| 能力 | 效果 | 最终 SDK 返回 | 完成判据 |
| --- | --- | --- | --- |
| overtime-application-definition | read | 流程定义对象（已拆后端包络） | 已确认流程身份；填写流程继续准备，单纯查询定义则交付名称与配置即可。 |
| overtime-application-current-user | read | 当前登录用户白名单对象 | 确认当前申请身份；若用户仅问本人信息，展示必要字段后结束。 |
| overtime-application-approval-chain | read | { nodes, processDefinitionId?, processDefinitionKey?, processDefinitionName?, state?, copyUsers? } | 用户已知道当前变量下的审批路径；继续提交前仍需完整 prepare。 |
| overtime-application-prepare | prepare | { payload, derived, tasks } | 草稿校验并得到所需自选节点后准备完成；实际发起须再提交。 |
| overtime-application-submit | write | number（业务单据 ID；SDK 不返回 code/data 包络） | 回读确认业务记录及其流程后，向用户交付业务 ID 与当前审批状态；提交成功不等于审批完成。 |
| overtime-application-detail | read | 业务单据对象（拆包后） | 用户查询详情时交付业务信息与可靠状态即可；需要取消则先确认对应实例仍运行。 |
| overtime-application-my-instances | read | { list: 流程实例[], total: number } | 向用户展示流程名称、审批内容、状态与起止时间；有明确目标时只交付匹配实例。 |
| overtime-application-cancel | write | boolean（后端成功回执；SDK 原样返回拆包后的值） | 流程实例 status=4，必要时详情也回读已取消，向用户报告撤销结果。 |

数据消费与分支：

- overtime-application-definition：展示 name 与 key 核对业务；formFields 为 null 不代表免填，填写规则在 prepare/submit 的 SDK 描述中。
- overtime-application-current-user：展示 realName、organizationName、postName；由 SDK 自动填申请人/部门等只读字段，调用方不用回传。 只含白名单字段；不返回 password2/salt 等凭据。
- overtime-application-approval-chain：依次展示节点名称、candidateStrategyName 与 candidateUsers 姓名；节点用 nodeId 区分。 将 USER_TASK 的 candidateUsers[].id 与当前用户 ID 比较，发起人=审批人可能自动通过而无法撤销。 预览不产生任务，nodeId 不能传 task-action 的 taskId。
- overtime-application-prepare：给用户核对 payload 的业务值；按 tasks[].id 建立 startUserSelectAssignees 的键，人员来自候选查询，人数、去重与顺序服从任务规则。 准备只读，不建单、不保留名额、不发送待办；任何草稿变更后应重新准备。
- overtime-application-submit：保存业务 ID、流程类型及原 requestId；回读业务字段并查询流程实例确认已创建。 取消属于用户改变决定时的可选操作，不是正常提交后的必做步骤。 提交默认预览审批链并拒绝发起人命中 USER_TASK 候选审批人；skipSelfApprovalGuard=true 会绕过该守卫，不应用它掩盖真实自审命中。
- overtime-application-detail：展示本次申请的业务字段与附件；原请求业务 ID 必须单独保存，详情不保证能提供流程实例 ID。 状态应区分业务单据与流程实例；需要可撤回性时查 my-instances，而不是只看详情 status。
- overtime-application-my-instances：本接口没有自动限定 hr_overtime_application，按 processDefinitionKey 与 String(businessKey) 双重匹配；字段缺失时不可把跨业务重号当可靠确认。 页码默认 1、每页默认 20；逐页核对 total，列表局部不能用于全量汇总。
- overtime-application-cancel：只取消自己发起且仍运行的流程；保留业务记录，不代表删除历史。 查实际流程 status=4 才认定撤销完成；会议预定则核对占用时间段消失。

本轮以 `test/ai-contract-workflow.test.ts` 核对真实 SDK 描述，复用既有浏览器基准，不重放真实写操作。逐项验证与缺口见 `docs/ai-contract-workflow-evidence.md`。
