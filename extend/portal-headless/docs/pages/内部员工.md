# 内部员工（`/dashboard/staff/staff-list/list`）

## 页面范围与证据

Portal 菜单“人力 → 员工管理 → 内部员工”，权限 `/dashboard/staff/staff-list`，使用 `platform` HTTP 实例，页面按规则携带 `module-type=11`（组织管理）。本页逐项核对了列表、详情表单、批量导入弹窗、职务变动入口和历史记录子页。

Portal 证据：`app/portal/menus/hr.js`、`app/portal/views/dashboard/hr/staff/staff-list.vue`、`list.vue`、`[mode]/[id].vue`、`components/create-multiple.vue`，固定提交 `bbcfc35154`。

Java 证据：`HrStaffController`、`HrStaffInfoDTO`、`HrStaffSelectDTO`、`HrStaffServiceImpl`、`HrStaffChangeLogController` 及相关子表 DTO，固定提交 `b7a359adc9e`。

## 能力与实际可达请求

| 页面动作 | SDK 能力 / 方法 | 请求与副作用 |
| --- | --- | --- |
| 列表 | `hr-internal-staff-list` / `hrInternalStaff.list` | `GET /org/staff/page`；发送 `staffName`、`staffCode`、`postName`、`status`、`orgId`、`mobile`、`sqlParam`、分页参数 |
| 详情 | `hr-internal-staff-get` / `hrInternalStaff.get` | `GET /org/staff/{id}` |
| 新建准备/提交 | `hr-internal-staff-prepare-create` / `hrInternalStaff.prepareCreate`；`hr-internal-staff-create` / `create` | 本地复刻表单校验后 `POST /org/staff`，返回新员工 ID |
| 编辑准备/提交 | `hr-internal-staff-prepare-update` / `prepareUpdate`；`hr-internal-staff-update` / `update` | 基于详情合并明确变更后全量 `PUT /org/staff` |
| 删除准备/验证码/提交 | `prepareRemove`、`sendDeleteCode`、`remove` | 读取 `/org/sensitive/info`；必要时 `GET /sys/sms/send`、`GET /sys/sms/checkSms`，再以 ID 数组 `DELETE /org/staff` |
| 自定义列信息/导出 | `customInfo`、`customExport` | `GET /org/staff/getCustomInfo?tableName=hr_staff`；页面真实按钮调用 `POST /org/staff/customExports` 下载 `人员.xlsx` |
| 员工导入 | `prepareImport`、`importPrecheck`、`importStaff` | 仅接受 `.xlsx`；先 `POST /org/staff/import/precheck`，用户确认后 `POST /org/staff/import`，字段名为 `file` |
| 员工模板 | `downloadTemplate` | `GET /org/staff/downloadTemplate?orgId=...` 取得地址，再下载地址对应二进制 |
| 合同模板/导入 | `downloadContractTemplate`、`prepareContractImport`、`importContract` | 模板 `GET /org/staff/downloadContractTemplate`；导入 `POST /org/staff/importContract`，multipart 字段 `file` 和 `mode`（1 更新、2 新增，默认2） |
| 职务变动模板/导入 | `downloadPostTransferTemplate`、`preparePostTransferImport`、`importPostTransfer` | 模板 `GET /org/staff/post-transfer/import-template`；导入 `POST /org/staff/{staffId}/post-transfer/import`，接受 `.xlsx/.xls` |
| 变更历史 | `historyList`、`historyDetail` | `GET /hr/staff/changeLog/page` 和 `GET /hr/staff/changeLog/{id}`；列表页历史按钮传当前员工 ID |

列表配置虽然声明了普通 `exportURL`，但没有普通导出按钮；SDK 不发布不可达的普通导出。自定义导出是页面实际绑定的列控制器动作，`columnIds` 必须是当前列 ID，`organizationIds` 无选择时发送空数组。

## 查询与权限规则

默认列表请求参数为：

```json
{
  "order": "",
  "orderField": "",
  "staffName": "",
  "staffCode": null,
  "postName": "",
  "status": "",
  "orgId": "",
  "mobile": null,
  "sqlParam": "",
  "pageNo": 1,
  "pageSize": 20
}
```

`staffCode`、`mobile` 保留 Portal 输入框原值；`orgId` 是组织 ID，不是名称；`sqlParam` 原样交给 Java 的安全处理逻辑，SDK 不拼接或放宽 SQL。分页条数只接受 Portal 的 `10、20、50、100`。Java 列表按当前会话、租户和组织数据范围返回可见记录。

列表复选框和行删除都要求 `record.status === 2`；Java 删除服务也拒绝 `status != 2` 的员工并删除主表及子表信息。因此 SDK 的 `records` 参数若提供，逐项执行离职状态校验；不能把隐藏/禁用的删除按钮当作可用权限。

敏感操作链按 Portal 全局配置执行：配置为空或明确关闭时可直接 `remove`；需要保护时必须先 `sendDeleteCode`，再由真人提供验证码和 `smsRequestId` 给 `remove`。短信模板 ID 固定为 `17709`，SDK 不把短信 requestId 当删除幂等键。

职务变动页中的组织、岗位和人员候选没有作为 SDK 的无关键字全量选项接口发布。人员候选可能达到数千条；调用方应使用当前详情中的 ID/名称或用户已确认的候选，不用 SDK 拉取全量人员绕过 Portal 的搜索边界。

## 表单提交规则

Portal 编辑提交是 `transformUndefinedToNull: true` 的完整 DTO PUT，不是差异 PATCH。SDK 的 `prepareCreate`、`prepareUpdate` 在提交前递归把 `undefined` 归一为 `null`，去掉嵌套明细项根部的 UI `_key`，并按页面规则处理字符串数组和子表。

主表校验逐条对齐 Portal：

- `name` 必填、不能全为空格、最多10个字符；`idType`、`sex`、`birthday`、`staffDuties`、`nation`、`organization`、`post`、`salaryLevel`、`salaryStructure`、`employmentType`、`status`、`staffStatus`、`entryTime`、`entrySeniority`、`insureArea`、`education`、`academicDegree`、`isFullTime` 必填。
- `idCard` 必填、不能全为空格、最多20个字符，只能数字和字母。
- `healthConditionProve` 最多100个字符且不能全为空格。
- `cardIssuingBank`、`bankAccount`、`mobile`、`address`、`residenceAddress`、`emergencyContact`、`emergencyMobile`、`university`、`speciality` 必填且不能全为空格。
- `birthday`、`communistTime`、`entryTime`、`enrollmentDate`、`graduationTime` 使用 `YYYY-MM-DD HH:mm:ss`；`downtimePay` 使用 `YYYY-MM-DD`。当 `status=2` 时必须填写 `downtimePay`，其它状态不强制填写。
- `staffDuties` 数组提交为逗号分隔字符串；`otherPosts` 数组提交为逗号分隔字符串。`otherOrganizationList` 不是 ID 数组，而是 `{ organizationId, postIdList }[]`，其中 `postIdList` 是 ID 数组。

嵌套明细规则：

- 工作经历：`companyName`、`department`、`duties`、`salaryRange` 最多50；`description`、`leaveReason` 最多200；有值时均不能全为空格。
- 教育经历：`school`、`speciality` 必填且最多50；`educationalSystem`、`learningStyle` 最多50；有值时不能全为空格。
- 家庭成员：`name` 最多10；`duties`、`mobile`、`unit`、`education` 最多50/15/50/50；`remark` 最多200；有值时不能全为空格。
- 职业资格：`type`、`name` 最多50；`level`、`code`、`highestLevel` 最多20；`unit` 最多50；`remark` 最多200；`code` 只能数字和字母。
- 职称/职务：`name` 最多50；`level`、`reviewMethod` 最多20；`unit` 最多50；`code` 最多20且只能数字和字母。
- 奖惩：`occurDate` 必填且为 `YYYY-MM-DD`；`method` 必填最多50；`content` 必填最多500；`amount` 可空，否则必须符合 `0` 至 `99999999.99`、最多两位小数；`reason`、`remark` 最多200且有值时不能全为空格。
- 合同：页面没有额外必填/长度规则；`termType=2`（无固定期）提交时删除该项 `endTime`，其它字段按 Portal 原值提交。

`postTransferList` 遵循 Portal 的保存边界：普通编辑未明确修改时从 PUT 中删除；只有 `changes` 显式提供它时才发送规范化后的提交字段。显式修改时 `null` 表示后端不覆盖、空数组表示清空、非空数组表示替换；提交项只保留后端字段并补齐 `staffId`。

## 操作步骤、返回值与失败处理

1. 用 `list` 读取当前权限范围，保存目标行 `id`；编辑先 `get`，不要用列表行拼全量 PUT。
2. 新建：填写资料 → `prepareCreate` → 用户确认 → `create`；成功返回 ID，再用 `get` 和 `list` 回查。取消只丢弃草稿。
3. 编辑：`get` → `prepareUpdate` → 用户确认 → `update`；成功或超时按同一 ID 逐字段回查主表和受影响子表。取消不发 PUT。
4. 员工导入：`prepareImport` → `importPrecheck` → 展示冲突并等待用户确认 → `importStaff` → 按员工编号/姓名/组织回查。合同和职务变动导入同样必须用准备结果并在成功后回查详情。
5. 删除：`prepareRemove` → 按结果决定是否 `sendDeleteCode` → 真人提供验证码 → `remove` → 列表回查目标 ID 不再可见。不能只看 HTTP 成功或空回执。
6. 历史列表返回 `list`、`total`；历史详情的 `changeItems` 逐项解释数据类型、动作、字段名、旧值、新值和描述，旧值/新值是历史快照，不自行转换字典。

ID、Long 字段和时间保留服务端原值，避免长整数精度损失和时区误换算。权限、组织数据范围、手机号重复、后端校验、短信失败、网络或响应形状错误均原样报告；不把空列表解释为无权限，不把空写回执解释为已落库。真实测试环境读请求及新建、编辑、导入、敏感删除的 `prepare → submit → 回查` 仍需在具备测试账号时执行。
