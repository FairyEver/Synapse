# 合同模板（`/dashboard/contract/template/list`）

合同域（风控管理）的第一个页面，形态是**普通 REST 增删改**——但写链路上有一条
「发不发审批流」的分叉，这一页真正要判断的东西全在那条分叉上。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/contract-template.ts`；
逐字段基准 → `baseline/contract-template.browser.json`；回归测试 → `test/contract-template.test.ts`；
真实环境写链路 → `smoke/contract-template-crud.mjs`。

## 页面标识

| 项 | 值 |
| --- | --- |
| 菜单路径 | `/dashboard/contract/template/list` |
| 权限码 | `/dashboard/contract/template` |
| 路由文件 | `app/portal/views/dashboard/hr/contract/template/list.vue` |
| 域 | `contract`（风控管理；菜单挂在「风控管理 → 合同管理」下，**但源码目录在 `hr/contract/`**） |
| 形态 | 列表页（声明式 `getDataListURL`）+ **流程表单** `simple/hr/form/007`（不是同目录的 `[mode]/[id].vue`） |
| module-type | **15（风险防控）** —— 实测浏览器在列表页与详情页都发这个头 |
| http 实例 | `platform` —— 页面顶部有 `import { http } from 'app/portal/utils/http/platform.js'`，**显式声明** |
| 含写操作 | 是（新建 / 修改 / 删除；**新建与修改只走「仅保存」那一支**） |

## 页面形态：流程表单只是外壳，接口是普通 REST

「创建模板」跳到 `/dashboard/flow/form/edit?…formCustomCreatePath=simple/hr/form/007`，
看起来像流程类页面。但**它提交时打的是 `/hr/contract-template/create` 这个普通 REST 接口**，
不是 `bpm/process-instance/create`：

```js
// simple/hr/form/007/page/pc/edit/index.vue
if (hasRecord) {
  await http.put('/hr/contract-template/update', { ...submitData, startUserSelectAssignees: tasksData })
} else {
  await http.post('/hr/contract-template/create', { ...submitData, startUserSelectAssignees: tasksData })
}
```

「流程」体现在**后端**：`ContractTemplateServiceImpl.createContractTemplate` 插完库之后
如果 `onlySubmit == 0`，会再调一次 `processInstanceApi.createProcessInstance` 起一条
`contract_template` 流程。**同一份 body、同一个接口，靠 `onlySubmit` 的值分叉。**

| 动作 | 请求 | 出处 |
| --- | --- | --- |
| 列表 | `GET /hr/contract-template/page` | `list.vue` 的 `getDataListURL` |
| 详情 | `GET /hr/contract-template/get?id=` | 后端 `@GetMapping("/get")`；前端调用点在**详情页** `template/detail/[id].vue` 与 `[mode]/preview/share.js` |
| 新建 | `POST /hr/contract-template/create` | `007/page/pc/edit/index.vue` 的 `actionSubmit`（`hasRecord` 为假） |
| 修改 | `PUT /hr/contract-template/update` | 同上（`hasRecord` 为真） |
| 删除 | `DELETE /hr/contract-template/delete?id=` | `list.vue` 的 `actionDelete` |

**没有 `prepare`。** 会议室那条线的 `prepare` 只有一个职责——问后端"这次要人工指定哪些审批人"。
这一页确实有一个形似的调用（`getRequiredStartUserSelectTasks`），但它**在后端不存在**
（见下），而且它属于「保存并提交」那一支，SDK 不实现那一支。硬造一个 `prepare` 就是给
"读"套上"提交流程"的名字。

## 这一页的核心判断：`onlySubmit` 把写链路劈成两支，SDK 只做一支

| 页面按钮 | `onlySubmit` | 后端行为 |
| --- | --- | --- |
| 「仅保存」 | `1` | `status = 1（待提交）`；模板行 + 一条 v1 版本落库；**不起流程** |
| 「保存并提交」 | `0` | `status = 2（审批中）`；**另外起一条 `contract_template` 审批流** |

**SDK 把 `onlySubmit` 钉死成 1**，传别的值当场抛错（`assertNoOnlySubmit`）。三条理由：

1. **「保存并提交」会惊动真人。** 它起的是真实审批流，会往真人的待办箱推单据、发通知。
   本页的写能力只允许碰自己创建的数据，而流程一旦发出去就不再只碰自己了。所以这条路径
   **不做、也不测**。
2. **它在前端本来就是断的（实测）。** `007` 在 `submitFlow` 为真时先打
   `POST /hr/contract-template/getRequiredStartUserSelectTasks`，拿不到数组就
   `throw new Error('获取审批节点失败')`、整条提交中断。后端**没有这个映射**：
   冒烟里的探针实测返回
   `请求资源不存在:No static resource admin-api/hr/contract-template/getRequiredStartUserSelectTasks.`
   （全仓唯一的同名 `@PostMapping` 在 `BusinessRegistrationApplicationController`，路径不同）。
   ⇒ 照抄这个分支 = 照抄一个必然抛错的调用。这条从「源码推断」升级成了「实测」。
3. **钉成常量而不是开放成参数。** 开放它等于给 AI 一个"顺手把流程也发了"的旋钮，
   而那条路径既没被验证过、又会打在真人身上。

⇒ SDK 发出的 body 与浏览器点「仅保存」时**逐字段一致**（含键的书写顺序）。

### 一个自己踩的坑：守卫会走两遍，判据不能写成「存在即拒」

第一版 `assertNoOnlySubmit` 写成「载荷里有 `onlySubmit` 这个键就拒」。冒烟
**第一步就被自己的载荷绊倒**：门面的 `createIdempotent` 是
`send: (_params, { payload }) => create(payload)`（与班次管理那条线逐字同构），
送回来的正是 `buildTemplatePayload()` 的产物，它本来就带 `onlySubmit: 1`。
⇒ 判据只能是「**值不对才拒**」（`!== 1`）。`test/contract-template.test.ts` 里
专门有一条用例锁这件事（传 `onlySubmit: 1` 必须放行），
反证 M8（退回"存在即拒"）当场红 2 条。

顺带：`startUserSelectAssignees` **不加守卫**。`buildTemplatePayload` 从不读它、
输出里那个 `{}` 是常量，加守卫也拦不住任何东西。改成用测试锁「传了也进不了 body」。

## 参数契约

### 列表查询（与浏览器逐字节一致）

```
GET /admin-api/hr/contract-template/page?order=&orderField=&pageNo=1&pageSize=20&_t=<ts>
GET /admin-api/hr/contract-template/page?order=&orderField=&name=SDK-TEST-…&pageNo=1&pageSize=20&_t=<ts>
GET /admin-api/hr/contract-template/page?order=&orderField=&typeId=13&pageNo=1&pageSize=20&_t=<ts>
```

键顺序即 qs 序列化顺序，是契约不是默认值表（D20）。

- `order` / `orderField` 两个**空串一定会发**（renren 列表页的默认空值参数）。
- `name` / `typeId` 的初值是 `null`，被 qs 的 skipNulls 丢掉 —— 页面上不填时浏览器也不发。
- `pageSize` 默认 20（`list.js:391` 的 `styleV2` 分支）。

### `name` 是**模糊匹配**，`typeId` 是精确匹配

后端 `ContractTemplateMapper.xml` 的 `selectByPage`：

```sql
<if test="pageReqVO.name != null and pageReqVO.name != ''">
    and t1.name like concat('%', #{pageReqVO.name}, '%')
</if>
<if test="pageReqVO.typeId != null">
    and t1.type_id = #{pageReqVO.typeId}
</if>
order by t1.id desc
```

⚠️ 与作业管理、班次管理两条线同样的坑：**改名后的新名字不能包含原名**，
否则"旧名字查不到了"这条断言会假绿。冒烟里用的是
`SDK-TEST-合同模板-<stamp>` → `SDK-TEST-模板改-<stamp>`。

### `status` **不是**这一页的参数（连传都传不动）

页面表单区只有「模板」和「类型」两个控件，**没有任何控件绑定 `status`** ——
浏览器发出的请求里从来没有它。

后端 `ContractTemplatePageReqVO` 确实有 `status` 字段，仓库里也确实有一段会消费它的代码
（`ContractTemplateMapper.selectPage` 那个 LambdaQueryWrapperX 的 default 方法写了
`eqIfPresent(getStatus, …)`）—— **但那段是死代码**：

```
WorkflowContractTemplateController:79   → contractTemplateService.selectPage(pageReqVO)
ContractTemplateServiceImpl:380         → contractTemplateMapper.selectByPage(page, pageReqVO)   ← XML
（另一条 ContractTemplateServiceImpl:224 getContractTemplatePage → mapper.selectPage 无人调用）
```

live 路径是 XML 的 `selectByPage`，而**它不消费 status**。
⇒ 就算硬传也筛不动，那比静默忽略更糟：是个看起来成功的空操作。
（`order` / `orderField` 同理：XML 里写死了 `order by t1.id desc`，两个参数发出去也没人读。）

所以 SDK 显式拒绝（`assertNoStatusParam`），并在描述里告诉调用方「先取列表再自行过滤」。

### 长选项：这一页**没有**（D6 在这里不触发）

「类型」是分类字典 `contract_type`，实测两层、叶子是「采购合同」这种业务类型，**小枚举**。
所以 `typeId` 声明成 `kind: 'tree'`（页面上确实是树选择器、`only-leaf`），
但**不给 `lookup`** —— 候选来自通用字典接口
`GET /system/category-dict/getChildNodeTree?code=contract_type`，那是跨页面的通用设施，
不属于本页的能力。

### `useSystem` 的候选是页面那个下拉

`app/portal/utils/define.js` 的 `SYSTEM_OPTIONS_ALL`：公共(0) / 人力(1) / 财务(2) / 资产(3) /
生产(4) / 采购(5) / 销售(6) / 门户(7) / 平台(10)。声明成 `enum`，9 个值全列。

### `content` 是 **JSON 字符串**，不是对象

页面 `formState.content` 是对象，`buildSubmitPayload` 里 `JSON.stringify` 之后才发。
页面默认值是 `{"version":"1.0.0","blocks":[]}`（`EMPTY_TEMPLATE_CONTENT`）——
**实测它过得了前后端两侧的校验**（后端 `ContractContentValidator` 对空 `blocks` 不报错）。

本地只校验后端**无条件**强制的那一层：非空 → 是 JSON 对象 → `version` 非空字符串 →
`blocks` 是数组。**更深的规则不复刻**（封面在首位、自动目录紧随其后、签署信息恰好两方、
段落标题 H1–H4…）：那是前端 `validateTemplateConfig` 与后端校验器共同维护的一整套业务规则，
在 SDK 里复刻一份会两边各自漂移。反证 M9（跳过 version/blocks 校验）红 1 条。

## 写链路：三个写能力，只有 `create` 需要防重

| 写能力 | 重发一次的后果 | 要不要 `requestId` | 依据 |
| --- | --- | --- | --- |
| `create` | **多一条模板**（后端零幂等） | **要**（门面上的 `createIdempotent`） | 没试过重发不带 `requestId` 的那种（那正是要防的） |
| `update` | 整份覆写再写一次，终态相同 | 不要 | **实测**：原样重发一次仍 1 条、名称/所属系统/status 不变 |
| `remove` | 逻辑删除，重复删后端直接返回成功 | 不要 | **实测**：连删两次都返回成功 |

### `update` 会把 `status` 重写成 1（待提交）

后端 `updateContractTemplate` 不分青红皂白：

```java
if (updateReqVO.getOnlySubmit() == 1) {
    contractTemplate.setStatus(PENDING_SUBMIT.getStatus());   // 1
}
```

⚠️ 实测只覆盖了「1 → 1」。**「一个已生效(4) 的模板被改回待提交(1)」是源码读出、未实测**
（要造一条 status=4 的记录得先走完审批流，而那正是本页不碰的东西）。

### `remove` 是逻辑删除，但**删完之后 `get` 会 500**（与班次管理那条线相反）

`deleteContractTemplate` 把 `hr_contract_template.deleted` 置 1。`ContractTemplateDO` 继承的
`BaseDO` 上 `deleted` 带 `@TableLogic`，所以 `selectById` 会补 `deleted = 0` → 查不到 →
`getContractTemplate` 接着在 null 上调 `getTypeId()` → NPE：

```
Cannot invoke "…ContractTemplateRespVO.getTypeId()" because "<local3>" is null
```

⇒ 「删干净了没有」**只能看列表**。

⚠️ 与班次管理那条线**结论相同、理由相反**：那边 `deleted` 是后端自己的字段（没走 `@TableLogic`），
删完 `get` 仍返回整行、只是 `isDel=1`。两条线都把「看列表」写进文档是对的，
但拿"那边 get 还能读到"来推断这边会踩空。

### `remove` 可能被关联合同挡住

后端先查 `hr_contract` 里有没有 `template_id` 指向它、`deleted = 0` 的合同，有就抛业务错误
**「存在关联合同，不能删除」**。SDK **不做预检查**，如实透传这个失败
（预检查要另打接口，而且查到"没被用"也不保证删的时候还没被用）。

## `module-type`：这一页发 15，但写请求那条路上不是

`resolveModuleType('/dashboard/contract/template/list')` → **15（风险防控）**，
与浏览器在**列表页**、**详情页**上实测发的一致。

但这个头读的是 cookie `hr-0.0.0-menuPath`，**整个浏览器 profile 全局共享**，
由路由守卫在每次导航时写。本轮实测到三种值：

| 场景 | 抓到的 module-type |
| --- | --- |
| 列表页挂载 | 15 |
| 详情页 `get` | 15 |
| 流程表单页上发的 `create` / `delete` | **11** |
| 本轮后段（另有 2 个代理并行用同一个浏览器）同一条列表请求 | **11** |

⇒ 抓基准时 `module-type` **必须拿规则表复核，不能把抓到的那一次当答案抄**。
SDK 的能力全部绑在列表页路径上，拿到的是 15。

## 操作步骤（AI 侧）

1. **先列表**：`contract-template-list({ name?, typeId?, pageNo?, pageSize? })` → 拿 `id`。
   列表接口**本身就返回 `content`**（最新一版的 JSON 串），要抄内容不必再 `get`。
2. **要建模板**：
   - 最简单：`content` 用 `EMPTY_TEMPLATE_CONTENT`（一个空壳，先建出来再在页面上填）。
   - 更实用：先 `list` / `get` 抄一份现成模板的 `content` 字符串，改完再提交 ——
     内容结构有一整套跨字段约束，自己拼会撞上一串后端业务错误。
   - 调 `contract-template-create`（**写操作**，门面上是 `createIdempotent`，要带 `requestId`）。
   - **独立证实**：`contract-template-list({ name })` 必须恰好 1 条，且返回的 id 与
     `create` 的返回值一致。
3. **要改模板**：先 `get(id)` 拿当前值 → 改 → `contract-template-update`。
4. **要删模板**：只删自己建的。删完用 `list` 复核（**不要用 `get`**，那里会 500）。
   被关联合同挡住时后端会返回业务错误，如实转告调用方。

## 真实验证记录（2026-09-20，测试环境）

`smoke/with-portal-token.sh node smoke/contract-template-crud.mjs`，**20 项检查全绿**，
测试环境没有留下任何 `SDK-TEST-` 前缀的残留（收尾按前缀扫，0 条）。
完整形状见 `baseline/contract-template.browser.json` 的「真实环境写链路复核」一节。

```text
起手：按名字查列表 0 条；按 SDK-TEST- 前缀扫也是 0 条（排除假阳性）
create：createIdempotent 返回 79；按名字查恰好 1 条、id 也是 79（返回值与独立读到的同一个数字）
get：name / typeId / typeName(采购合同) / useSystem / content 逐项与提交值一致
     status=1（待提交）、processInstanceId=null —— 只保存不发流程的硬证据
同一个 requestId 重试：POST 次数 1 → 1（根本没发出去），列表仍 1 条
update：名称与 useSystem 都变了；旧名字 0 条；原样重发一次仍 1 条、终态不变
remove：列表查不到；重复 remove 后端返回成功；remove 之后 get 抛 NPE（见上）
探针：POST /hr/contract-template/getRequiredStartUserSelectTasks → 404（前端「保存并提交」必挂）
收尾：两个名字 0 / 0，SDK-TEST- 前缀 0 条
```

浏览器侧也真的走过一遍（记录 id 76 / 77，每条都在同一轮里删掉了），
五条请求的逐字段基准就是从那里来的。**只走了「仅保存」**，理由见上。

### 独立证实的强度（如实记）

这一页**没有第二个视图**（不像会议室预定能去占用查询里看），所以证实只能靠
**同一接口的两次独立读取**：建完按名字查列表、再按 id 取详情，且提交值与读回值逐项比对。
这条差别在作业管理、班次管理两条线上已经记过两次，这里同理 —— **有第二个视图时证据更强**。

## 尚未覆盖 / 未做

- **「保存并提交」那一支完全不实现、不测。** 不做的理由有三条（见上），其中"后端没有
  `getRequiredStartUserSelectTasks` 映射"是实测的。**但它不是"这条路径不可能工作"的证明** ——
  万一后端补上那个接口，这一页的结论就要重来。
- **`typeId` 的候选值 SDK 不提供查询入口。** 页面用通用字典接口
  `GET /system/category-dict/getChildNodeTree?code=contract_type`，那是跨页面设施，
  不属于本页。后端另有一个 `GET /hr/contract-template/getCanSelectType` 返回**已在用的**
  typeId（`select t1.type_id … group by t1.id`），但**页面没有调用点**，SDK 也没做成能力。
  ⇒ 调用方要 `typeId` 只能从现有列表行里抄一个（冒烟里用的是 13 = 采购合同）。
- **`update` 把 status=4 打回 1 这件事未实测**（源码读出）。
- **`content` 的深层业务校验没有端到端验证。** SDK 只挡后端无条件强制的那一层；
  「封面必须在首位 / 自动目录紧随其后 / 签署信息恰好两方 / 段落标题 H1-H4」
  这些规则**只由后端如实报错**，SDK 没有为它们写过一条正向验证。
- **`delete` 被关联合同挡住的那条分支没有实测。** 要制造一条关联合同，那是另一件工作，
  而且要往测试环境里写合同（本页的写能力只允许碰自己建的模板）。这条是**后端源码读出**。
- **`get` 在删除之后会 500 这件事，SDK 没有做任何补偿**：`get` 就如实把后端的失败透传出去。
  这是刻意的 —— 给一个后端 NPE 包一层"友好的空值"会让调用方以为"记录不存在"，
  而真实情况可能是别的原因。
- **反证里有一个等价变异没能变红（如实记）。** 把 `get` 的 `params: { id }` 改成
  `params: { id: String(id) }`（班次管理那条线的写法），**47 条用例全绿**。
  查过原因：那个变异**语义等价** —— query 参数序列化后本来都是字符串，
  归不归一看不出来。真正可观测的差异在 **body** 里（`"id":77` vs `"id":"77"`），
  已补一条用例锁住，对应的变异 M15 红 2 条。**「全绿」在这里不等于那条接线是对的。**
