读取讲师评价问卷题目设置；没有分页，也不是评价成绩。

- 执行：`sdk.studyTeacher.listAppraiseSettings`；通过 `capabilities.invoke('study-appraise-setting-list', args)` 调用时按 `params` 填参。性质：read。

## 本轮补齐（2026-09-26）：题目保存（写入口）

页面底部的题目表单（可增删、可上下移动、题干 ≤100 字）提交时打的是：

| 能力 id | 请求 | 说明 |
| --- | --- | --- |
| `study-appraise-setting-prepare-save` | 本地 | 校验条数与题干、按数组顺序重排题号，不发请求 |
| `study-appraise-setting-save` | `POST /study/base/studyappraiseteacher` | **body 是数组**，真写 |

**参数契约**

- `items`：题目数组，**3~5 条**。下限与上限都来自**后端**（`saveInfo`：`size < 3` → 「题目不能少于3个」，
  `size > 5` → 「题目不能多于5个」）；页面的「新增一项」到 5 就停，但页面**允许删到 1 条** ——
  那种状态下点保存会失败，所以 SDK 提前挡住。
- 每条 `content`：必填、不能全是空格（页面 `validateOnlySpace`）、**≤100 字**（页面 `max: 100`）。
- **顺序即题号**：提交时按数组下标重排 `sort = index + 1`（页面 `onSubmit` 就是这么写的），
  调用方自己填的 `sort` 会被覆盖 —— 页面的上下移动按钮改变的只是数组顺序。

**请求形状**：body 是 `[{sort, content}, …]` **数组**，不是 `{ items: [...] }`。
页面会把读回来的整行（`id`/`isDel`/`creator`/时间戳…）一起回传，SDK 只发 `{sort, content}` ——
依据是后端 `saveInfo` 逐行只 `setSort` / `setContent`，其余字段一律由后端填（源码级结论）。

**⚠️ 整份替换**：`saveInfo` 先把现有题目**全部**置 `is_del=1`，再按传入数组重插一遍。
所以"只加一条"必须把**现有的全部**一起传回来；漏掉的题目会被软删（下一次 list 就看不到了）。

**完成判据**：保存后再读一次 `study-appraise-setting-list`，核对条数、题干与顺序。
请求没抛错不等于保存成功（D12）。

**幂等**：没有 requestId；同一份载荷重发终态相同（整份替换），但"漏发条目"与"重复提交"的后果方向不同 —— 超时后先回查列表再决定。

**操作步骤**：读列表 → 在它基础上增删改 → `prepareSaveAppraiseSetting` → 用户确认 → `submitAppraiseSetting` → 回查。

**推断与缺口**：**没有浏览器基准**；body 的字段取舍是"后端只读两个字段"的静态结论；
尚未在真实测试环境执行 prepare→submit→回查闭环。
