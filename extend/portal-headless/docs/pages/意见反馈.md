### 基准的覆盖边界

这一页在基准里只有两条（点过两次「查询」，两条只差 `_t`），而**这一页也就只有这一个接口**
⇒ 它的覆盖是**完整**的（不像同组另外三页：写链路一条都没沾到）。

## 这是四个页面里最简单的一个：**纯只读**

模板里只有：4 个筛选项（昵称 / 姓名 / 手机号 / 反馈时间区间）、查询与重置两个按钮、
一个表格（反馈内容 / 昵称 / 姓名 / 手机号 / 反馈时间）、一个分页条。

**没有任何写入口**：没有新建、没有编辑、没有删除、没有导出、没有行内动作、没有弹窗。
`useListPageModule` 的调用里也**没有** `deleteURL` / `selectable` / `exportURL`。
所以这一页的能力只有一条读能力，`write: false`。

## 列表：键序与逐字段

无筛选时的键序 —— ⭐ **基准证实**：

```
GET /admin-api/manager/feedbackContent/getByPage?order=&orderField=&pageNo=1&pageSize=20&_t=<ts>
```

与能力构造出来的逐字段一致（测试是 `test/ai-interaction-qa.test.ts` 的 B2 组）。
⚠️ 基准里这一页是**两条**完全相同的请求（只差 `_t`）—— 抓的时候点过两次「查询」，
所以断言写的是"**存在**一条逐字段相符的"，不是"只出现一次"。

全部 10 个键的声明顺序（传了值的会插回原位，没传的 `null` 整项不出现）：

```
order, orderField, nickname, userName, phone, pageNo, pageSize, startTime, endTime
```

| 字段 | 来源 | 后端语义（`FeedbackContentMapper.xml` 的 `findListByPage`） |
| --- | --- | --- |
| `order` / `orderField` | `useListPageModule` 固定加的两个空串 | 这一页没有排序入口，恒为 `''` |
| `nickname` | 表单 `nickname` | `zhdj_user.nickname like '内容%'`（**前缀**），且 `!= ''` 才算 |
| `userName` | 表单 `userName` | `zhdj_user.user_name like '内容%'`（**前缀**），且 `!= ''` 才算 |
| `phone` | 表单 `phone` | `zhdj_user.phone like '内容%'`（**前缀**），且 `!= ''` 才算 |
| `startTime` / `endTime` | 表单 `time[0]` / `time[1]` | `zfc.create_time >= / <=`，`YYYY-MM-DD HH:mm:ss`，**不做「结束日 +1 天」** |
| `pageNo` / `pageSize` | 分页 | `styleV2: true` ⇒ 默认每页 20 |

⚠️ 三个文本筛选位在这一页**都是前缀匹配**（与「交互历史」页的 `phone` 那条**等值**匹配相反），
两页长得像、后端写法不同，别互相照抄。

⚠️ `startTime`/`endTime` 排在 `pageNo`/`pageSize` **之后**：页面在 `customLoad` 里写的是
`{ ...omit(form, ['time']), startTime, endTime }` —— `omit` 删掉 `time` 这个键，两端时间是
**追加**上去的。这与同组另外三页是**同一个形状**（都是 `omit` 日期键 + 追加两端）。

后端固定 `order by zfc.create_time desc`，**没有** `_t` 之外的客户端排序入口。

## 空值：`null` 会被丢掉，空串会照发

表单初值是 `null`（不是 `''`）：`{ nickname: null, userName: null, phone: null, time: [] }`。
`platform.js` 的 GET 拦截器用 `qs.stringify(params, { skipNulls: true })` ⇒ 无筛选时 URL 上
**一个筛选位都不出现**，只有 `order=&orderField=&pageNo=1&pageSize=20&_t=<ts>`。
调用方给 `''` 就会发 `nickname=`（空串不被跳过）—— 与"不给"不是一回事，能力原样透传。

## 真实验证（**读路径有基准；无写操作，所以不需要写验证**）

这一页**没有写操作** ⇒ 不需要 `prepare → submit → cancel`，也不需要 `SDK-TEST-` 数据。
它的**唯一**接口有基准背书（见上），所以这是四个页面里"验证得最完整"的一个：

- ✅ 无筛选列表请求逐字段一致；不发 `module-type`；请求头逐键一致。
- ✅ 这一页"页面自己的请求去重后只有那一条"—— 顺带证实了它**确实没有任何写请求**。

⚠️ **仍然没测到的**：带筛选值时的形状（基准只抓了无筛选那一条），
以及**响应体**的形状（基准只记 `url/method/headers/body`，没有响应；
`content`/`nickname`/`userName`/`phone`/`createTime` 五个字段是**读后端 mapper 的 select 列表**得到的）。

要补的话只有一步：`sdk.aiInteraction.listFeedback({ pageNo: 1, pageSize: 5 })`，看返回的
`{list, total}` 里那五个字段在不在。

## 基准兑现了什么 / 还剩什么没判据

**已落成真断言**（B2 组）：无筛选 URL 逐字段一致（含键序与 `_t` 位置）／三个文本位"没传就不出现"／
`startTime`/`endTime` 排 `pageSize` 之后／不发 `module-type`／头逐键一致／页面自己的请求只有那一条。

**仍然没有判据**（留着 `it.todo`）：带筛选值的请求形状；响应体字段（基准不记响应体）。

## 尚未覆盖

- 反馈的**来源**没有展开：`zhdj_feedback_content` 是 App 端（智慧蛋鸡客户端）提交上来的，
  提交入口不在 Portal 里 ⇒ SDK 里**没有**"提交一条反馈"的能力，这一页只能看。
- `create_id` 关联的是 `zhdj_user`（客户端用户），不是 `hr_sys_user`（后台用户）——
  所以这一页的人员相关字段与同组另外三页**不是同一张表**。
- 表格里 `content` 用的是 `common-table-cell-ellipsis`（截断 + 悬浮显示全文），纯前端行为。
