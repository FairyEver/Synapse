## 参数契约

`convertFetchForm` 只做一件事（`others/list.vue:145-150`）：

```js
rrList.convertFetchForm( data => { return { ...data, signatory: data.signatory.join(',') } })
```

**键序原样保留**（覆盖赋值不动位置）⇒ order 表 = `form` 字面量（`:96-103`）：

`order → orderField → name → year → status → creator → signatory → organizationCode → pageNo → pageSize → _t`

| 参数 | kind | 说明 |
| --- | --- | --- |
| `name` | text | 协议名称，模糊匹配 |
| `year` | text | 四位年份 `2026`（`picker="year"` + `value-format="YYYY"`） |
| `status` | text | 协议状态，**单选**（这一页的下拉没有 `multiple`，与[所辖月度](./所辖月度.md)相反）⇒ 只收标量。字典 `protocol_status`，**取值域未实测** |
| `creator` | text | 创建人，模糊匹配 |
| `signatory` | search | 审核人 id（多人逗号连）。**见下方「刻意偏离」** |
| `organizationCode` | text | 组织 id。**默认是空串、键在**（与[所辖月度](./所辖月度.md)相反） |
| `pageNo` / `pageSize` | number | 默认 `1` / `20` |

## ⚠️ 与「所辖月度」的两处相反（别照抄隔壁）

| | 所辖月度 | **所辖年度** |
| --- | --- | --- |
| `organizationCode` 初值 | `null` → 键**不在** URL 上 | **`''` → 键在、值为空** |
| `status` | 多选（`multiple`），要 `join(',')` | **单选**，标量直接发 |
| `month` | 有（两位补零字符串） | **没有这个键** |

`organizationCode` 这一页的树选择器**没有** `is-disabled`（用户能改），
但初值就是 `''`，所以无筛选时 URL 上是 `organizationCode=&`。

## ⚠️ 刻意偏离：`signatory` 的默认值

与[所辖月度](./所辖月度.md)同一处、同一理由：页面 `form.signatory` 的初值是
`[userStore.state.id]`，**基准 `[10]` 里它是当前登录用户的 id**（已脱敏）；
无头不知道调用者是谁，所以本能力默认**空串** = 不限审核人。

复刻页面的办法：`base-user-info` 拿 `userId` → `signatory: String(userId)`。

## 逐字段基准

（`baseline/perf-agreement.browser.json` `[10]`，`_t` 已归一）

```
GET /admin-api/performance/protocol/kpiyearprotocol/othersPage
    ?order=&orderField=&name=&year=&status=&creator=&signatory=<redacted>&organizationCode=&pageNo=1&pageSize=20&_t=<ts>
```

**与源码推导逐字段一致（含键顺序）**，除 `signatory` 的值一处（上节，刻意）。
注意 `organizationCode=` **在这里是在的**（对比[所辖月度](./所辖月度.md)那条没有）。

## ⚠️ 基准确认的两件事（都是"页面发了、本 SDK 不发"）

### 1. 年度页的审核人候选走的是**月度**端点

基准 `[12][13][14]` 是 `GET /performance/protocol/**kpimonthprotocol**/signatoryByPage?pageNo=1..3&pageSize=200`
—— 挂在「所辖年度」名下，却打**月度**那个接口。这不是抓错：源码里两个 `others` 页挂的是
**同一个**组件 `portal-hxr-select-signatory`（`…/select/signatory/index.vue:43` 把 URL 写死成
`kpimonthprotocol/signatoryByPage`），所以**年度页也在翻月度候选**。疑似前端漏改，
但这是线上的真实行为；本 SDK 不照抄它，只是把它记下来。

### 2. 基准 `[9]` 的 `POST /admin-api/homePage/save` **不是这一页的**

那条 POST 的 body 是工作台卡片布局（`hr/learning/*`、`finance/*` 那些 widget 的坐标），
挂在「所辖年度」名下是因为抓基准用的是**只改 hash 的 SPA 导航** —— 同文档导航不会卸载
首页，首页的自动保存被同一次捕获收了进来。它**不是**协议页的读路径，
而且是个**写**请求，本 SDK **不做**。

## ⚠️ 实测：这一页**必报**「用户查询结果超过500条」（2026-09-21）

真机冒烟（`smoke/read-perf-flow.mjs`）实测：`listYearAgreementsOthers()` 返回
**HTTP 200 + `ret: FAIL`**，消息是「用户查询结果超过500条，请缩小name条件或调用已有分页接口」。

**根因与「学习管理域」那边是同一个**：后端在这条路径上要建一张「手机号 → 用户」的映射表，
**无条件**调 `hrUserApi.getUserList(null)`；那个入口在 `HrSysUserServiceImpl:725`
有 `MAX_LEGACY_USER_RESULTS = 500` 的兜底，本租户用户数远超 500 ⇒ 必抛。

**关键字的成败仍然取决于命中与否**（与学习管理域那几页同形）：
不传 `signatory` / `name` 时返回**全量**、走到那段取全量用户的代码；传了关键字可能提前收窄。
调用方拿到这个错时的正确反应是**收窄条件**，不是重试。

冒烟里这条**按预期报错处理**（`expectError`），不是失败。
