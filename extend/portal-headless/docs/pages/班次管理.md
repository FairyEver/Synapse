# 班次管理（`/dashboard/attendance/attendance-shift/list`）

考勤域（阶段① 第三条业务线）的**第三个页面**，也是这个域里第一个**带完整增删改**的页面。
前两个（考勤档案 / 考勤统计）是同一个只读接口的两面；这一页是管理页：列表 → 新建 / 编辑 / 删除。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/attendance-shift.ts`；
逐字段基准 → `baseline/attendance-shift.browser.json`（**读 2 条 + 写 3 条，全是本轮实测**）；
回归测试 → `test/attendance-shift.test.ts`；真实环境冒烟 → `smoke/read-attendance-shift.mjs`、
`smoke/attendance-shift-crud.mjs`（后者会真的写数据，建完在同一轮里删掉）。

## 页面形态：普通 CRUD，不是流程

| 动作 | 请求 | 出处 |
| --- | --- | --- |
| 列表 | `GET /org/hrWorkShift/page` | `list.vue` 的 `getDataListURL` |
| 详情 | `GET /org/hrWorkShift/{id}` | 后端 `HrWorkShiftController` 的 `@GetMapping("{id}")`；**前端没有调用点**（编辑页走 bridge） |
| 新建 | `POST /org/hrWorkShift/save` | `[mode]/[id].vue` 的 `customSubmit`（`form.id` 为空时） |
| 修改 | `PUT /org/hrWorkShift`（整单替换） | 同上（`form.id` 有值时） |
| 删除 | `DELETE /org/hrWorkShift/{id}` | `list.vue` 的 `deleteURL` + renren 通用删除 `${deleteURL}/${id}` |

**没有 `getRequiredStartUserSelectTasks` 这类"提交前先问一次"的接口**，也**没有撤销/审批**。
会议室那条线的 `prepare → submit → cancel` 在这里没有对应物（与作业管理同款判断）。

### 三个必须记住的点

1. **`status` 是页面声明了、却没有任何控件绑定的表单项。**
   `list.vue` 的 `form: { name: null, status: null }` 里有它，但表单区只有一个「班次名称」输入框；
   初值 `null` 被 qs 的 skipNulls 丢掉，所以浏览器**从来没发过它**（基准第 1、2 条都能看到）。
   后端 `getWrapper` 确实支持 `eq("status", …)`，但 `hr_work_shift.status` 在整个后端
   **只被写、从不被读**（全仓 grep 无消费点）。⇒ SDK 不把它放进契约，**硬传会被拒**
   （`assertNoStatusParam`）：静默忽略 = 调用方以为筛过了；静默转发 = 在契约之外开一个
   来路不明的筛选条件。两种"温和"处理都不诚实。

2. **module-type 这个头在新建页取不到值。**
   `getCurrentModuleType()` 读的是 cookie `hr-0.0.0-menuPath`（路由守卫每次导航时写入，
   **同一个浏览器 profile 全局共享**）。实测：列表相关的四条（列表挂载 / 按名称查询 / 修改 / 删除）
   都发 `11`；而**新建页那条 POST 一个 module-type 都没发**（基准第 3 条的请求头里没有它）。
   这不影响 SDK —— 五个能力全部绑在**列表页路径**上，`resolveModuleType` 确定性地给 11，
   与浏览器在列表页上的行为一致。**抓基准时这个头仍然必须拿规则表复核**，
   不能直接把抓到的那一次当答案抄（档案页那条线上已经因为并行标签页踩过一次）。

3. **编辑页不是先 `GET /{id}` 再回填，而是把整行用 bridge 带过去。**
   `list.vue` 的 `actionEdit(record, record)` → `bridgeSet(record)`；表单初始化是
   `{...form, ...bridgeGet(bridgeID)}`。所以浏览器发出的 PUT body 是
   **「五个业务字段 + 被 bridge 带进来的整行服务端字段」**：

   ```json
   {"name":"SDK-TEST-班次改名","morningStartTime":"08:00:00","morningEndTime":"11:30:00",
    "afternoonStartTime":"13:00:00","afternoonEndTime":"17:00:00",
    "id":"9","status":1,"isDel":0,"createTime":"2026-09-20 22:38:06",
    "creator":"18243","updateTime":"2026-09-20 22:38:06","updater":"18243"}
   ```

   `id` 是**字符串**（后端把 Long 序列化成字符串，与作业管理一致）。
   顺带记下：新建出来的行 `status=1` / `isDel=0`。

## 参数契约

### 列表

| 参数 | kind | 必填 | 说明 |
| --- | --- | --- | --- |
| `name` | text | 否 | 班次名称，**模糊匹配**。改名后核对时新名字不能包含原名，否则旧名字也查得到 |
| `pageNo` / `pageSize` | number | 否 | 默认 1 / 20 |

请求参数的**顺序是契约的一部分**（D20 逐字段一致）：
`order, orderField, name, pageNo, pageSize, _t`。初值为 `null` 的 `name` 由 qs 的 `skipNulls` 丢掉。
实现按固定表拼参数（`buildListParams`），调用方实参的书写顺序不影响结果。

**没有 `status`**（理由见上）。

### 写能力

| 能力 | 参数 | 说明 |
| --- | --- | --- |
| `attendance-shift-create` | `name` + 四个时间，全必填 | 名称 ≤20 字（页面规则），时间 `HH:mm:ss` |
| `attendance-shift-update` | `id` + 同上五个 | 整单替换；**先 `get` 拿当前值再改** |
| `attendance-shift-remove` | `id` | 逻辑删除；被占用时后端会拒 |

时间格式 `HH:mm:ss` 来自页面 `a-time-picker` 的 `value-format`，由 `assertClockTime` 挡在本地：
后端 DTO 是 `java.sql.Time`，格式不对会 400，但错误信息是框架的解析异常、看不出是哪个字段，
所以挡在本地（与 `assertTimeSlot` / `assertYearMonth` 同一个来历）。

## 写链路

### 没有 `prepare`

`prepare` 在会议室那条线上的唯一职责是"提交前问后端这次要人工指定哪些审批人"，
那个答案会改变提交载荷。这一页**没有这种接口**，硬造一个就是给"读"套上"提交流程"的名字。

真有一个只读前置步骤，但它不叫 `prepare`：`update` 打的是**整单替换**的 PUT，
所以调用方必须先 `get()` 拿当前值。它是独立能力 `get`，**不在 `update` 内部代劳** ——
自动合并会把表单不认识的服务端字段（`creator` / `createTime` / `updater` / `isDel` …）
一并回写，那是没验证过的形状（与作业管理同款判断）。

### D12 在这里要收窄

| 写能力 | 重发一次的后果 | 要不要 `requestId` | 实测依据 |
| --- | --- | --- | --- |
| `create` | **多一条班次**（后端零幂等） | **要**（门面上的 `createIdempotent`） | 冒烟里同一个 `requestId` 重试：**第二次 POST 根本没发出去**（save 的 POST 次数 1 → 1），列表仍 1 条 |
| `update` | 整单替换再写一次，终态相同 | 不要 | 冒烟里原样重发一次：仍只有一条，名称/时间不变 |
| `remove` | 逻辑删除，重复删后端直接返回成功 | 不要 | 冒烟里连删两次都返回成功 |

### 我们的 PUT 是浏览器那份 body 的**子集**（如实记下，不是"一样"）

SDK 的 `update` 只发「五个业务键 + `id`」，浏览器多带六个服务端字段（见上面第 3 点）。
冒烟实测：这样发之后 `get` 读回 `createTime` / `creator` 与改前**逐字节相同**、
`status` / `isDel` 也没被动过 —— 与 MyBatis-Plus `updateById` 忽略 null 字段的行为一致
（代码是推断，结论是实测）。

**没有做**与浏览器的逐字节比对：编辑态的 PUT 只有这一条基准（浏览器发的是子集之外的形状），
两边不可能逐字节相等，所以 `test/attendance-shift.test.ts` 里锁的是
**"前 6 个键逐字相同 + 少发的正好是那六个服务端字段"**，而不是"一样"。

### `remove` 有两条反直觉的性质（都实测过）

1. **是逻辑删除**：删完 `list` 查不到，但 `get(id)` **仍然返回整行**、`isDel` 变成 1。
   所以"删干净了没有"**只能看列表**，拿 `get` 复核会得到一个看起来像"没删掉"的假象。
2. **可能失败**：后端 `HrWorkShiftServiceImpl.deleteWorkShift` 先查 `hr_attendance_group`
   里有没有 `shift_id` 指向它、且 `is_del=0` 的考勤组，有就返回业务错误
   「该班次正在使用，无法删除!」。SDK **不做预检查**（预检查要另打一个接口，
   而且"现在没被用"也不保证"删的时候还没被用"），如实透传这个失败。
   本轮删的是自己新建的班次（没有考勤组引用它），所以**这条错误路径没有被触发过**。

## 尚未覆盖

- **「被考勤组占用时删不掉」这条错误路径没有实测过。** 只从后端代码
  （`HrWorkShiftServiceImpl.deleteWorkShift`）读出来，本轮删的是自己刚建的班次，
  没有任何考勤组引用它。**不实测是有意的**：要触发它就得先建考勤组 / 改考勤组的 shift_id，
  那已经越出这个页面的范围，而且会动到别人的配置。
- **`update` 与浏览器的 PUT 没有逐字节比对**（形状上就不可能相同，见上文）。
  只比对了前 6 个键，以及实测了"少发服务端字段不会清掉它们"。
- **`GET /{id}` 没有浏览器基准**：前端根本没有调用点（编辑页走 bridge）。
  接口通、字段齐是实测的，但"浏览器会怎么发"这件事不存在答案。
- **`status` 到底是什么意思，没有查清。** 只知道它在后端只被写不被读、页面上没有控件。
  如果将来有人给它接上控件，这一页的参数契约要重新评估。
- **`create` 的返回值没有 id。** 后端 `save` 返回空 `Result`，所以"建出来的是哪一条"
  只能回列表按名字查（冒烟就是这么做的）。名字重复时这条路径不可靠 ——
  但页面本身也没有更强的能力，SDK 如实照做。
- **`page-catalog.json` 给这一页标的 `write: false` 是错的。** 清单的判定规则是
  `tools/generate/generate.mjs:229` 的 `/http\s*\.\s*(post|put|delete)\s*\(/`，
  而这一页的两个写入口分别在 **`list.vue`（通用删除 `${deleteURL}/${id}`）** 和
  **`[mode]/[id].vue`（`customSubmit` 里的 `http({method:'POST'|'PUT'})`）** ——
  前者不是 `http.delete(` 的形式、后者不在 `list.vue` 里，两处都扫不到。
  与考勤档案 / 考勤统计两页的 `write: false` 是同一类误判。

## SDK AI 说明契约（2026-09-22）

本节由当前 SDK 描述结果整理；说明权威来源为 `src/catalog/contracts-business.ts`。调用 `catalog.describe(id)`（或 `id-llm`）可得到参数来源、返回字段/状态、数据消费与后续映射；`catalog.describePage(页面路径)` 用于选择页面功能。以下更新以本节为准；前文历史请求/实测记录仍保留其记录日期。

### `attendance-shift-list`

按条件查找班次并取得记录 ID；用于展示、选中编辑目标和核实写入结果。

- 执行：`sdk.attendanceShift.list`；通过 `capabilities.invoke('attendance-shift-list', args)` 调用时按 `params` 填参。性质：read。
