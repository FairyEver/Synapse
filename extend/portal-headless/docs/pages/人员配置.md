## 参数契约与逐字段基准

### 列表

Portal `useListPageModule` 的默认请求保持以下键和值：

```json
{
  "order": "",
  "orderField": "",
  "legalId": null,
  "name": null,
  "pageNo": 1,
  "pageSize": 20
}
```

请求为 `GET /admin-api/supply/legal-user-config/page`。`list[].id` 是配置主键；`legalId` 是法人组织 ID；`materielTypeIds`、`planUserIds`、`purchaseUserIds` 是 SDK 从后端数组或 CSV 字段归一化出的 ID 数组；`legalName`、`materielTypeName`、`planUserName`、`purchaseUserName` 只能展示，不能反向当作提交值。`total` 是筛选条件下总记录数，不是当前页长度。

### 组织树和人员候选

- `GET /org/organization/getRoleOrganizationTree` 的树节点只有 `isStandardUnit === 1` 或 `isCorporation === 1` 时可选；SDK 返回同 Portal 一致的 `disabled`，提交 `legalId` 前必须选 `disabled=false` 的节点。
- Portal 表单实际用 `/org/staff/page` 无关键字循环拉取人员，SDK 不暴露这个无界全量行为，改为必须提供非空 `keyword` 的 `staffSearch`，并将 `pageSize` 限制为不超过100。端点、`staffName` 参数和返回行 ID 仍与 Portal/Java 相同；这是无头调用的范围保护，已在 AI 说明和测试中明确。
- `staffSearch` 返回 `id`、`name`、`staffCode`、`status`、`organization`、`label`；提交计划员/采购员只使用 `id`，`label` 为 `姓名(工号)`。

### 新建与编辑规则

Portal 表单的必填规则是：`legalId` 必填；`materielTypeIds`、`planUserIds`、`purchaseUserIds` 都必须是至少一项的数组。SDK 接受字符串/数字 ID 和 CSV 详情并在请求前归一化校验，但不把空数组变成“保留旧值”。

新建和编辑只发送以下字段：

```json
{
  "legalId": "法人组织ID",
  "materielTypeIds": ["物料类型ID"],
  "planUserIds": ["计划人员ID"],
  "purchaseUserIds": ["采购人员ID"]
}
```

新建：`POST /admin-api/supply/legal-user-config/create`，返回新配置 ID。编辑：先 `get`，再 `prepareUpdate({ current, changes })`，只允许覆盖上述四个字段，`PUT /admin-api/supply/legal-user-config/update` 返回 `true`。Portal 表单中的 `batchId`、后端兼容的 `userId`、展示名称和审计字段不发送。Java 服务端还会再次校验组织是否合法、三类 ID 非空，以及物料类型是否与其他配置冲突；前端准备通过不等于后端授权通过。

删除：`DELETE /admin-api/supply/legal-user-config/delete?id=<id>`，返回 `true`；页面确认由调用方负责，成功或超时后必须列表回查目标 ID。

## 操作步骤、撤销与验证

1. 读取 `organizationTree`，只选择 `disabled=false` 的法人节点；读取共享 `materiel_type` 字典并用 `staffSearch` 搜索、确认人员 ID。
2. 新建走 `prepareCreate → create → get/list`；取消只丢弃本地草稿，不发 POST。新建响应不确定时先按返回 ID 或唯一表单组合回查，不能盲目重试。
3. 编辑走 `get → prepareUpdate → update → get`；`previous` 只用于展示差异或受控补偿，不会自动回滚。超时先回查再决定是否重试。
4. 删除前由调用方完成确认，调用 `remove → list` 回查；删除没有恢复接口，不能把重复 DELETE 当作撤销。

已完成 Portal 菜单、列表、表单、组织树、人员候选和 Java Controller/VO/Service 的逐页静态核对，并用离线 request stub 覆盖默认分页、提交字段、表单规则、组织禁用、关键字保护和坏响应反证。当前节点尚未调用真实测试环境，因此没有真实 `prepare → submit → cancel` 或写入后回查记录；这一点不以离线测试替代。
