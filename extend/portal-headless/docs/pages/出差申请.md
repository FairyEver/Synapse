## 〇、选型与前置核对

### 0.1 为什么是这一条（**候选是实测筛出来的，不是翻表挑的**）

任务给的候选方向是「补卡 / 转正 / 离职 / 入职 / 调动 / 证明开具这一类」。把 §1.4 清单里
人力域那几条**逐个拉真实审批链**之后，筛掉的原因**不是"看起来不像普通员工用的"，
而是**一提交就会撞上后端那条「发起人=审批人 ⇒ 自动审核通过」**：

| 候选 | key | 实测审批链（`POST /bpm/process-instance/preview`） | 结论 |
| --- | --- | --- | --- |
| **出差** | `hr_business_trip_application` | `直属上级审批` strategy=**23** → 乔娜(15012)，发起人 18243 | ✅ **就是它** |
| 用章 | `seal_application` | `直属上级审批` strategy=**30（用户）candidateUsers=18243 = 发起人本人** | ❌ 守卫必拦 |
| 离职 | `lizhi` | 节点名 `ymx`，strategy=**30（用户）candidateUsers=18243 = 发起人本人** | ❌ 守卫必拦 |
| 转正 | `zhuanzheng` | 唯一节点 strategy=60（流程表达式），`state=PENDING_CONFIRMATION`、**候选人是空的** | ❌ 守卫判不出来（预览算不出人 ⇒ 拦不住也保不住） |
| 信息变更单 | `staff_info_change` | 节点 `HR专员` strategy=60，同样 `PENDING_CONFIRMATION`、候选人空 | ❌ 同上 |
| 调动 / 入职 / 再入职 | `diaodong` / `ruzhi` / `reEmployment` | 预览里**一个 USER_TASK 都没有**（`state=PENDING_CONFIRMATION`） | ❌ 预览给不出判据 |

⇒ 在「**能真的提交、能真的撤销**」这个硬前提下，**出差申请是这批候选里唯一一条**。
顺带一提：`seal_application` 里那个 `strategy=30 + candidateUsers=18243` 是**测试环境的配置脏数据**
（审批人被硬编码成了本测试账号），但它就是真实环境的样子——守卫拦的正是这种配置。
这条实测反例已经写进测试（`SELF_APPROVER_PREVIEW` 那一条），用来证明守卫**真的会拦**。

### 3.1 本表单**没有**的东西（不是漏做，是页面上真的没有）

- **没有附件控件**（后端 `BusinessTripApplicationSaveReqVO` 里也没有附件字段）
- **没有抄送人控件**、**没有人员/组织选择器**、**没有明细行**、**没有算出来的字段**
- 所以这条线**没有** `user-search` / `tree` 那类长选项能力。加一个用不到的
  `user-search` = 凭空多一条没人会调、也没法在页面上对上的接口。
- ⚠️ 「同行人」是唯一容易看错的地方：它**不是**选人控件，就是 `<a-textarea>`，
  抓包里是 `"companions":"SDK-TEST-同行人张三、李四"` 这样一整串字符串。

### 3.2 只读联动：7 个字段全是身份信息，**没有一格是算出来的**

来源链路（源码）：`041/index.vue` 的路由 `meta.baseData: ['user-basic', 'dict-platform']`
→ `utils/router/base-data.js` 的 `'user-basic'` → `fetchSimpleUserBasic()`
→ **`GET /sys/user/info`**（`critical: true, onlySimpleForm: true`）。

| 表单字段 | 来源 | 实测值 |
| --- | --- | --- |
| `applicantId` | `/sys/user/info` 的 `id` | `"18243"` |
| `applicantName` | `realName` | `"姚淼鑫"` |
| `applyDate` | `dayjs().format('YYYY-MM-DD')` | `"2026-09-21"`（门户时区的**今天**） |
| `applyDepartmentId` | `organizationId` | `"101"` |
| `applyDepartmentName` | `organizationName` | `"设计中心1236"` |
| `applyPostId` | `postId` | `"702"` |
| `applyPostName` | `postName` | `"高级产品经理"` |

⚠️ **前 6 个都是字符串**（实测 `"18243"` / `"101"` / `"702"`）。这不是笔误：
页面直接 `formState.applicantId = id`，**原样字符串发出去**。SDK 也发字符串（D20 逐字段一致）。

⚠️ **本能力比前几条线多要 `postId` / `postName` 两个字段**：后端 `fillApplicantInfo()` 里
有 `hrPostService.getAllPostMap().get(postId)` 那一跳，取不到会抛「申请岗位不存在」。
SDK 本地复刻不了那份岗位表，只能照发、让后端如实报错（缺字段时 SDK 会先抛，不发明文 `undefined`）。

⚠️ **`applyDate` 是"今天"（填表那天），不是出差那一天**——这两件事在页面上是两个字段。
无头进程可能跑在 UTC 上，所以 `portalToday()` 固定按 `Asia/Shanghai` 算，
并留了 `now()` 注入口给测试钉日期（测试里有一条跨天的用例：`2026-09-21T17:30:00Z`
在门户时区已经是 09-22）。

⚠️ 页面还额外打了一件**本能力一条都不打**的事：表单外壳挂载时**无关键字翻页拉全量人员目录**
（实测 **9 页 × 500 = 4500+ 人**，`GET /system/user/simple-page`）。本表单根本没有人员控件
——它是设计 D6 / H35「长选项必须先要关键字」的现场证据（记在基线文件里，测试有断言钉住"本能力不打它"）。

## 四、★ 后端**覆盖**那 7 个只读字段，还有一条页面上没有的时间规则

### 4.1 `fillApplicantInfo()`：申请人/部门/岗位全部按登录用户重写

```java
// BusinessTripApplicationServiceImpl.createApplication()
validateTime(createReqVO.getStartTime(), createReqVO.getEndTime());
BusinessTripApplicationDO application = BeanUtils.toBean(createReqVO, BusinessTripApplicationDO.class);
fillApplicantInfo(application);              // ← 申请人/部门/岗位全部重写
application.setApplyDate(LocalDate.now());   // ← 申请时间也重写成"服务端的今天"
applicationMapper.insert(application);
startBpmProcess(application, createReqVO.getStartUserSelectAssignees());
```

`fillApplicantInfo()` 逐条：`setApplicantId(loginUser.getId())` → `sysUserApi.get(userId)` →
`setApplicantName(realName)` / `setApplyDepartmentId(organizationId)` / `setApplyPostId(postId)` →
`hrOrganizationService.get(...).getName()` → `hrPostService.getAllPostMap().get(postId)`。

⇒ 三件事跟着一起来：

1. **SDK 仍然把 7 个字段照页面的值发出去**（D20 逐字段一致），
   但**不声称它们决定了入库结果**——后端全都会覆盖。
2. 它们是 SDK **现查现算**的：6 个来自 `GET /sys/user/info`，`applyDate` 是 `portalToday()`。
   **不接受调用方指定**（页面上没有输入口）。
3. `applyPostId` 的失败方式留给后端（见 §3.2）。

### 4.2 本地校验：6 条页面/后端一致 + 1 条**只在 PC 页缺**

页面 `formRules` 与后端 `@Valid` 在这条流程上**一致**（这一点与前几条线不同：请假那条线是页面 200、后端 500）：

| 字段 | 页面 | 后端 | SDK |
| --- | --- | --- | --- |
| `tripType` | `required` | `@NotNull @Min(0) @Max(2)` | 必填 + 只能是 0/1/2 |
| `companions` | `required` + `max:500` | `@NotBlank @Size(max=500)` | 必填 + ≤500 |
| `origin` | `required` + `max:200` | `@NotBlank @Size(max=200)` | 必填 + ≤200 |
| `destination` | `required` + `max:200` | `@NotBlank @Size(max=200)` | 必填 + ≤200 |
| `reason` | `required` + `max:500` | `@NotBlank @Size(max=500)` | 必填 + ≤500 |
| `startTime` / `endTime` | `required` | `@NotNull` | 必填 + 形状必须是 `YYYY-MM-DD HH:mm:ss` |
| **开始/结束的先后** | PC 页**没有这条**；**移动端有**（见下） | **`validateTime`：`!endTime.isAfter(startTime)` → 「结束时间必须晚于开始时间」** | **拦** |

### 4.2.1 ⚠️ 时间先后这一条：**三处不一致**，不要读成「SDK 比页面严」

初读源码时我按 PC 页写成了「页面上没有这条校验」，**后来查移动端时推翻了自己**——
移动端那一份**有**，而且措辞与后端一字不差。如实记成一张表：

| 处 | 有没有 | 形态 |
| --- | --- | --- |
| `041/page/pc/edit/index.vue`（**基准抓的就是它**） | **没有** | 两个 `a-date-picker` 之间没有任何联动，用户选得出一个结束早于开始的时间 |
| `041/page/mobile/edit/index.vue` | **有** | `onEndTimeConfirm()`：`end.isBefore(start) \|\| end.isSame(start)` → **「结束时间必须晚于开始时间」**（与后端那句一模一样）；`onStartTimeConfirm()` 还会把不再合法的结束时间**清空**并提示「结束时间已清空，请重新选择」；结束时间的**日期**选择器另有 `:min-date`（不能早于开始那天的 0 点） |
| 后端 `BusinessTripApplicationServiceImpl.validateTime()` | **有** | `!endTime.isAfter(startTime)` → 「结束时间必须晚于开始时间」 |

⇒ SDK 这条本地校验的口径**与移动端、后端完全一致**，只有 PC 页缺它。
仍然提前到本地拦的理由：在 PC 页上它是一个**注定 400 的写请求**，
而「本地校验不过 ⇒ 一个请求都不发」是本项目的既有规矩。判据是**严格晚于**（相等也拒）。

> 另外：移动端那两条「开始时间不能早于今天 / 开始时间必须晚于当前时间」是**注释掉的死代码**
> （`041/page/mobile/edit/index.vue` 里被 `//` 整段注释），不构成规则，SDK 也不实现。
> 记在这里，免得下次有人照注释去补一条没人会触发的校验。

### 4.3 ⚠️ 业务 `status` 在提交后**仍然是 0**

- `createApplication()` **没有** `setStatus`；表 `hr_business_trip_application.status` 默认值是 `0`（待提交）。
- 监听器 `BusinessTripApplicationWorkflowListener` 只处理 **APPROVE / REJECT / CANCEL** 三种事件
  （其余走 `default: 忽略的状态`）。

⇒ **不能靠 `detail` 的 `status` 判断"流程在不在跑"**（实测提交成功后回读就是 `status=0`）。
要看「我的流程」里**流程实例**的 `status === 1`。撤销之后两边才会同时变成 4（实测见 §八）。

### 5.2 ★ 三处容易抄错的类型

| 字段 | 类型 | 为什么 |
| --- | --- | --- |
| `applicantId` / `applyDepartmentId` / `applyPostId` | **字符串** `"18243"` / `"101"` / `"702"` | 来自 userStore，页面直接赋值不做转换 |
| `tripType` | **数字**（`0`/`1`/`2`） | `a-select` 的 value 就是数字；与上面三个字符串形成对照 |
| `applyDate` | 字符串 `YYYY-MM-DD`，**是「今天」** | `formState` 的初值 `dayjs().format('YYYY-MM-DD')`——**不是出差那天** |
| `startTime` / `endTime` | 字符串 `YYYY-MM-DD HH:mm:ss` | `formatSubmitDateTime()` 的产物 |
| `companions` / `origin` / `destination` / `reason` | 字符串，**已 trim** | `buildSubmitData()` 里的 `trimSubmitText()` |

### 5.3 抓基准时踩到的两个坑（datetime 选择器，与前几条线的配方不同）

1. **`bsk click` 点面板里的日期格/时间格会被判 `element not visible`**（面板底部超出 645px 的视口）。
   改用 `bsk evaluate` 在**页内** `dispatchEvent(new MouseEvent('click',{bubbles:true,cancelable:true,view:window}))`
   —— React 的合成事件认它，值真的写进表单（每一步都用输入框的值复核过）。
2. **本表单是两个独立的 `a-date-picker show-time`（不是一个 range-picker），
   而它的值只在点「确 定」之后才写进表单状态**：直接去点另一个输入框，前一个的值会被清掉
   （实测：开始时间先显示 `2026-09-24 09:00:00`，点了结束时间输入框之后变回空）。
   所以每一步都必须以「确 定」收尾，而「确 定」按钮同样要用第 1 条的页内点击。

这两条已经写进基线文件的「抓取手法」里，下次做同类表单可以直接抄。

### 6.1 实测：**没有「发起人自选」节点**

### 6.2 那审批人是谁？—— `bpmnXml` 里的 `candidateStrategy="23"`

```xml
<userTask id="Activity_..." name="直属上级审批" flowable:candidateStrategy="23" .../>
```

`23 = BpmTaskCandidateStrategyEnum.DIRECT_LEADER（直属上级）`——审批人是后端按发起人所在组织
**算出来**的，不是发起人选的、发起人也选不了。实测 `POST /bpm/process-instance/preview`：

```

```

发起人是 18243（姚淼鑫）⇒ **不是同一人** ⇒ 放行。

### 6.3 ★★ 提交前的硬守卫：**审批链里不能有发起人本人**

**为什么必须有**：后端 `BpmTaskServiceImpl.tryAutoApproveWhenStartUserIsAssignee()` 有一条
「流程发起人与审批人相同，自动审核通过」。命中时那个节点会被自动批掉；若链上再没有别的待办节点，
流程**当场走完**，`cancel-by-start-user` 从此必然报「流程取消失败，流程不处于运行中」——
那条单据**永远撤不掉**（测试环境里已经因此留了一批 `status=2` 的记录，本轮**一条都没碰**，见 §八.5）。

**判据是真实审批链**，不是调用方传进来的 assignees：

```
POST /bpm/process-instance/preview   body {processDefinitionKey, variables: <本次载荷>, ...}
  → nodes[].type === 'USER_TASK' 的 candidateUsers[] 里逐个比对发起人 id
  → 命中 ⇒ **在 create 之前**抛错，一个写请求都不发
```

| | 只判「别把审批人选成自己」 | 本能力（判真实审批链） |
| --- | --- | --- |
| 判据来源 | 调用方传进来的 assignees | **后端算出来的真实审批链** |
| 覆盖范围 | 只有 `candidateStrategy=35` 的节点 | **所有** `USER_TASK`（直属上级 / 部门负责人 / 岗位 / 用户组…） |
| 防不防得住"猜不到的审批人" | ❌ 防不住 | ✅ 正是它的目标 |
| 顺带产出 | —— | **"这次会打扰谁"**，报告里能如实写出来 |

**这条守卫在本流程上真的会生效，不是摆设**：同一批候选里 `seal_application`（用章）与
`lizhi`（离职）的节点就是 `strategy=30 + candidateUsers=18243`（发起人本人），
`zhuanzheng` / `staff_info_change` 则是 `strategy=60` 且预览算不出候选人——
**那几条本能力都没有选**，正是因为在"能提交 + 能撤销"这个前提下它们过不去（§0.1）。
守卫的真实拦截面已经用 `seal_application` 的真实链形状写进测试（`SELF_APPROVER_PREVIEW`）。

**两条边界，如实记下：**

- **逃生口**：`skipSelfApprovalGuard: true`，只在预览接口本身不可用时才该用，默认**关着**。
  理由：宁可让调用方显式承认"我在冒险"，也不要静默放过去。
- **这条守卫不能证明**审批人最终一定是预览里那个人。预览是"按当前数据算一遍"，
  真实办理时后端会拿**当时**的组织数据再算一次；组织架构刚变过时两者可能不一致。
  SDK 能保证的是：**预览时命中自己就一定拒绝**。

### 6.4 请求顺序（只有最后一条是写）

```
① GET  /sys/user/info                                          (submit 里只打一次)
② POST /hr/business-trip-application/getRequiredStartUserSelectTasks   页面 formSubmit() 的第一步
③ POST /bpm/process-instance/preview                           ★ SDK 加的守卫（页面上是用户点按钮才发生）
④ POST /hr/business-trip-application/create                    写
```

守卫插在 ③ 而不是更早，是为了保持页面上 ①→④ 的**相对顺序不变**；
它只多一次**只读**请求，却能把"单据永远撤不掉"挡在写之前。

### 6.5 详情接口里**没有** `processInstanceId`

`BusinessTripApplicationRespVO` 只到 `status` / `statusName`。
⇒ 撤销要先用 `findInstanceByBusinessKey()` 去「我的流程」按 `businessKey` 换流程实例 id。
`businessKey` 是**各业务表自己的主键**，会与加班/调休撞车，所以还要按 `processDefinitionKey`
再筛一道（有测试钉住：同一页里放一条 `hr_overtime_application` 的 `businessKey=777` 和一条本流程的，
必须取到本流程那条）。

## 十、尚未覆盖 / 不确定

### 10.1 确实没做的

- **「重新发起」（reapply）没做**：`isReapply` 分支会从原流程实例抄字段再提交

  （新建 → 提交 → 撤销），驳回后改单重提属于另一条写链路，没验证过就不写。
- **`POST /hr/business-trip-application/page`（分页）没做**：那是**另一个列表页**
  （`BusinessTripApplicationPageReqVO` 带 applicantName / tripType / status / createTime 区间），

- **`dict-platform` 那条 baseData 没做**：本表单模板里没有任何字典控件（类型是本地常量），
  那条依赖对本表单是空跑，SDK 不发。

### 10.2 不确定的（**不要读成"已验证"**）

- **短信 / 站内消息有没有真的发出去**：观测不到。能确证的只有"待办在 3.04s 内被撤销"和
  "没有调用过任何催办接口"。

  算出来。本账号实测是 15012；换个部门/换个账号会不同。守卫是**按预览结果**判的，不依赖这个结论。

  守卫对任何账号都生效——这正是它存在的意义。

权威契约在 `src/catalog/contracts-workflow.ts`，经 `catalog.describe(id)` / `id-llm` 的 `ai` 实际返回；`describePage` 同步用途与功能区别。额外公开门面通过 `catalog.describeMethod(sdkPath)` 下钻，无需调用方读仓库。

| 能力 | 效果 | 最终 SDK 返回 | 完成判据 |
| --- | --- | --- | --- |
| business-trip-application-definition | read | 流程定义对象（已拆后端包络） | 已确认流程身份；填写流程继续准备，单纯查询定义则交付名称与配置即可。 |
| business-trip-application-current-user | read | 当前登录用户白名单对象 | 确认当前申请身份；若用户仅问本人信息，展示必要字段后结束。 |
| business-trip-application-approval-chain | read | { nodes, processDefinitionId?, processDefinitionKey?, processDefinitionName?, state?, copyUsers? } | 用户已知道当前变量下的审批路径；继续提交前仍需完整 prepare。 |
| business-trip-application-prepare | prepare | { payload, derived, tasks } | 草稿校验并得到所需自选节点后准备完成；实际发起须再提交。 |
| business-trip-application-submit | write | number（业务单据 ID；SDK 不返回 code/data 包络） | 回读确认业务记录及其流程后，向用户交付业务 ID 与当前审批状态；提交成功不等于审批完成。 |
| business-trip-application-detail | read | 业务单据对象（拆包后） | 用户查询详情时交付业务信息与可靠状态即可；需要取消则先确认对应实例仍运行。 |
| business-trip-application-my-instances | read | { list: 流程实例[], total: number } | 向用户展示流程名称、审批内容、状态与起止时间；有明确目标时只交付匹配实例。 |
| business-trip-application-cancel | write | boolean（后端成功回执；SDK 原样返回拆包后的值） | 流程实例 status=4，必要时详情也回读已取消，向用户报告撤销结果。 |

数据消费与分支：

- business-trip-application-definition：展示 name 与 key 核对业务；formFields 为 null 不代表免填，填写规则在 prepare/submit 的 SDK 描述中。
- business-trip-application-current-user：展示 realName、organizationName、postName；由 SDK 自动填申请人/部门等只读字段，调用方不用回传。 只含白名单字段；不返回 password2/salt 等凭据。
- business-trip-application-approval-chain：依次展示节点名称、candidateStrategyName 与 candidateUsers 姓名；节点用 nodeId 区分。 将 USER_TASK 的 candidateUsers[].id 与当前用户 ID 比较，发起人=审批人可能自动通过而无法撤销。 预览不产生任务，nodeId 不能传 task-action 的 taskId。
- business-trip-application-prepare：给用户核对 payload 的业务值；按 tasks[].id 建立 startUserSelectAssignees 的键，人员来自候选查询，人数、去重与顺序服从任务规则。 准备只读，不建单、不保留名额、不发送待办；任何草稿变更后应重新准备。
- business-trip-application-submit：保存业务 ID、流程类型及原 requestId；回读业务字段并查询流程实例确认已创建。 取消属于用户改变决定时的可选操作，不是正常提交后的必做步骤。 提交默认预览审批链并拒绝发起人命中 USER_TASK 候选审批人；skipSelfApprovalGuard=true 会绕过该守卫，不应用它掩盖真实自审命中。
- business-trip-application-detail：展示本次申请的业务字段与附件；原请求业务 ID 必须单独保存，详情不保证能提供流程实例 ID。 状态应区分业务单据与流程实例；需要可撤回性时查 my-instances，而不是只看详情 status。 真实新提交后业务 status 仍可能为 0（待提交），流程已在运行；不能以 0 判断提交失败。
- business-trip-application-my-instances：本接口没有自动限定 hr_business_trip_application，按 processDefinitionKey 与 String(businessKey) 双重匹配；字段缺失时不可把跨业务重号当可靠确认。 页码默认 1、每页默认 20；逐页核对 total，列表局部不能用于全量汇总。
- business-trip-application-cancel：只取消自己发起且仍运行的流程；保留业务记录，不代表删除历史。 查实际流程 status=4 才认定撤销完成；会议预定则核对占用时间段消失。

本轮以 `test/ai-contract-workflow.test.ts` 核对真实 SDK 描述，复用既有浏览器基准，不重放真实写操作。逐项验证与缺口见 `docs/ai-contract-workflow-evidence.md`。
