# 排班管理（`/dashboard/attendance/attendance-team/list`）

考勤域（阶段① 第三条业务线）的**第四个页面**，也是这个域里第一个**带子资源**的页面：
外层是一张普通的 CRUD 表（考勤组），内层挂着一份**排班**（把组织 / 岗位 / 职务 / 人挂到组上）。

四件套的其它三件分别在：能力定义与参数契约 → `src/capabilities/attendance-team.ts`；
逐字段基准 → `baseline/attendance-team.browser.json`（**读 3 条 + 写 4 条，全是本轮实测**）；
回归测试 → `test/attendance-team.test.ts`（40 条）；真实环境冒烟 → `smoke/read-attendance-team.mjs`、
`smoke/attendance-team-crud.mjs`（后者会真的建组、真排班，建完在同一轮里清干净）。

### 四个名字指同一个东西

菜单标题「排班管理」、路由目录 `attendance-team`、接口 `hrAttendanceGroup`、列表列头「考勤组名称」。
SDK 的 capabilityId 用**页面路径**的 slug（`attendance-team-*`），与 `attendance-shift-*` 同规矩。

## 页面形态：两层实体，不是一个表

| 层 | 实体 | 接口 | 能力 |
| --- | --- | --- | --- |
| 外层 | 考勤组 | `/org/hrAttendanceGroup` | list / get / create / update / remove |
| 内层 | 考勤组的**排班** | `/org/hrWorkSchedule` | schedule-get / schedule-save |

内层的入口是行内那个「排班管理」弹窗，**不是独立路由**。两层的资源关系是 `groupId`。

| 动作 | 请求 | 出处 |
| --- | --- | --- |
| 列表 | `GET /org/hrAttendanceGroup/page` | `list.vue` 的 `getDataListURL` |
| 详情 | `GET /org/hrAttendanceGroup/{id}` | `[mode]/[id].vue` 的 `customLoad`（**编辑页真的会调**，基准第 4 条） |
| 新建 | `POST /org/hrAttendanceGroup` | `[mode]/[id].vue` 的 `customSubmit`（`form.id` 为空） |
| 修改 | `PUT /org/hrAttendanceGroup` | 同上（`form.id` 有值）。**URL 与新建是同一个**，只有 method 不同 |
| 删除 | `DELETE /org/hrAttendanceGroup/{id}` | `list.vue` 的 `deleteURL` + renren 通用删除 `${deleteURL}/${id}` |
| 读排班 | `GET /org/hrWorkSchedule/getWorkSchedule?groupId=` | `components/schedual.vue` 的 `init()` |
| 存排班 | `POST /org/hrWorkSchedule` | 同上 `onSubmit` |

**没有 `getRequiredStartUserSelectTasks` 这类"提交前先问一次"的接口**，也**没有撤销/审批**。
会议室那条线的 `prepare → submit → cancel` 在这里没有对应物（与作业管理 / 班次管理同款判断）。

### 三个必须记住的点

1. **`module-type` 这个头被并行标签页污染过，不能照抄抓到的那一次。**
   它读的是 cookie `hr-0.0.0-menuPath`，而 cookie 是**同一个浏览器 profile 全局共享**的、不分标签页。
   本轮第 1、2、4、5 条是 `11`（与规则表对列表页的推导一致），第 3、6、8 条却是 `12 / 15` ——
   抓完复核 cookie，里面躺的是 `/dashboard/base/management-center/list`：既不是本页、
   也不是本轮任何一次导航的目标。**抓基准时这个头必须拿规则表复核。**
   （班次管理那条线记的是这个坑的另一种表现：「新建页取不到值」。）

2. **编辑页这一次是真的 `GET /{id}`，不是走 bridge。** 与班次管理相反 —— 那边的编辑页
   只把整行用 bridge 带过去、没有任何调用点。这里的 `customLoad` 明确打了
   `http('/org/hrAttendanceGroup/' + id)`。

3. **`schedual.vue` 的打开动作会带出两条请求，而不是一条。** 先 `getWorkSchedule`；
   **只有返回的 `hrGroupUserRelEntityList` 非空时**才会再打
   `POST /org/organization/getUserByType`（那句 `if (result.hrGroupUserRelEntityList) { ... getUser() }`）。
   本轮抓的是一个还没排过班的组，所以只抓到前一条。

## 参数契约

### 列表

| 参数 | kind | 必填 | 说明 |
| --- | --- | --- | --- |
| `name` | text | 否 | 考勤组名称，**模糊匹配**。改名后核对时新名字不能包含原名，否则旧名字也查得到 |
| `type` | enum | 否 | 候选只有 `{标准工时: 1}` |
| `pageNo` / `pageSize` | number | 否 | 默认 1 / 20 |

请求参数的**顺序是契约的一部分**（D20 逐字段一致）：
`order, orderField, name, type, pageNo, pageSize, _t`。初值为 `null` 的 `name` / `type`
由 qs 的 `skipNulls` 丢掉。实现按固定表拼参数（`buildListParams`），调用方实参的书写顺序不影响结果。

### 写能力

| 能力 | 参数 | 说明 |
| --- | --- | --- |
| `attendance-team-create` | `name` + `type` + `shiftId` | 名称 ≤20 字；`shiftId` **必填**（页面手写的约束，见下） |
| `attendance-team-update` | `id` + 同上三个 | 整单替换；**先 `get` 拿当前值再改** |
| `attendance-team-remove` | `id` | 逻辑删除；**有排班时会被后端拒** |
| `attendance-team-schedule-save` | `groupId` + `startDate` + 四个列表 | 整组覆盖；四个列表全空 = 清空 |

#### `shiftId` 的必填**不在表单规则里**，是提交前手写的

`[mode]/[id].vue` 的 `customSubmit` 第一句：

```js
if (!form.shiftId) { message.error('请选择班次'); return Promise.reject() }
```

`rules` 里**只有 `name` 和 `type`**，没有 `shiftId`。所以这条约束扫 `rules` 是扫不到的 ——
SDK 把它挡在本地（`buildGroupPayload`），错误文案里也写明了出处。

`type` 则相反：它**有**表单规则（`required`）、表单初值是 `1`、页面上只有一个选项，
所以 SDK 总是把它发出去（不传按 1 发 —— 那是表单初值，不是 SDK 发明的默认值）。

#### `startDate` 的格式来自控件

页面是 `a-date-picker` + `value-format="YYYY-MM-DD"`，后端 DTO 是 `java.time.LocalDate`。
格式不对整条写请求 400，错误信息是框架的解析异常、看不出是哪个控件，所以 `assertIsoDate` 挡在本地。
**只校验形状**，不校验"这天存不存在"（`2026-02-31` 形状是对的，`LocalDate` 会给出明确错误）。

## 写链路

### 没有 `prepare`

同作业管理 / 班次管理：这一页没有"提交前问后端一次"的接口，硬造一个就是给"读"套上"提交流程"的名字。

真的有一个只读前置步骤，但它不叫 `prepare`：`update` 打的是**整单替换**的 PUT，
所以调用方必须先 `get()` 拿当前值。它是独立能力 `get`，**不在 `update` 内部代劳** ——
自动合并会把表单不认识的服务端字段（`creator` / `createTime` / `shiftName` / `workShift` …）
一并回写，那是没验证过的形状。

### D12 在这里要收窄：只有 `create` 需要 `requestId`

| 写能力 | 重发一次的后果 | 要不要 `requestId` | 实测依据 |
| --- | --- | --- | --- |
| `create` | **多一个考勤组**（后端零幂等） | **要**（门面上的 `createIdempotent`） | 冒烟第 3 步：同一个 `requestId` 重试，**第二次 POST 根本没发出去**（建组的 POST 次数 1 → 1），列表仍 1 条 |
| `update` | 整单替换再写一次，终态相同 | 不要 | 冒烟第 10 步：原样重发一次，仍 1 条，名称/shiftId 不变 |
| `remove` | 逻辑删除，重复删后端直接返回成功 | 不要 | 冒烟第 11 步：连删两次都成功 |
| `schedule-save` | 先 `is_del=1` 掉旧的再插新的，终态相同 | 不要 | 冒烟第 6 步：原样重发一次，读回仍**恰好 1 条**挂载项、`startDate` 不变 |

### 我们的 PUT 是浏览器那份 body 的**子集**（如实记下，不是"一样"）

浏览器编辑页的 `customLoad` 把**整个服务端记录**灌进 form（`{...result, shiftId}`），
所以它的 PUT body 是：

```json
{"id":"7","name":"SDK-TEST-改-030131","type":1,"status":1,"isDel":0,
 "creator":"18243","createTime":"2026-09-20 22:54:04",
 "updater":"18243","updateTime":"2026-09-20 22:54:04","shiftId":"6",
 "shiftName":null,
 "workShift":{"id":"6","name":"北京行政班","morningStartTime":"08:00:00", …},
 "sheetUserRelDTOS":null}
```

注意它**多带九个字段**，其中 `workShift` 还是嵌套对象、且 `id` 排在最前面。

SDK 的 `update` 只发 `{"name":…,"type":…,"shiftId":…,"id":…}` —— 是那份 body 的子集。
测试里锁的是**"我们发的每个键都在浏览器那份里 + 少发的正好是那九个"**，不是"一样"。

冒烟实测（第 9 步）：这样发之后 `get` 读回 `createTime` / `creator` / `status` 与改前**逐字节相同**；
`shiftId` 也没被写空（回**列表**看 `shiftName` 仍拼得出来）—— 与 MyBatis-Plus `updateById`
忽略 null 字段一致（代码是推断，结论是实测）。

### `get` 的 `shiftName` **恒为 null**（实测，别踩）

后端 `HrAttendanceGroupServiceImpl.getInfo` 只 `setWorkShift(...)`，**没有**调 `dealShift` ——
`shiftName` 是列表那条路径上由 `dealShift` 拼出来的。所以：

```text
get(3)   → shiftName = null, workShift = {...完整明细...}
list()[0] → shiftName = "沃德博创考勤班次", workShift = null
```

**"班次有没有被写空"要回列表看 `shiftName`，不能看 `get` 的 `shiftName`。**
本轮的冒烟脚本第一版就是在这里写错了一条断言（见「反证」一节）。

### `remove` 有两条反直觉的性质（都实测过）

1. **是逻辑删除**：删完 `list` 查不到，但 `get(id)` **仍然返回整行**、`isDel` 变成 1。
   所以"删干净了没有"**只能看列表**。
2. **有排班时删不掉**：后端 `deleteAttendanceGroup` 先查 `hr_group_user_rel` 里有没有
   `group_id` 指向它、且 `is_del=0` 的行，有就返回业务错误
   **「该考勤组正在使用，无法删除!」**。
   ⇒ **正确顺序是先 `schedule-save` 传空列表把排班清掉，再 `remove`。**
   这条错误路径本轮**真的触发过**（冒烟第 7 步），不是从代码读出来的
   —— 班次管理那条线的同款路径当时只读代码、没触发。

### `schedule-save` 是**整组覆盖**，不是增量

后端先把该组所有 `hr_work_schedule` 与 `hr_group_user_rel` 置 `is_del=1`，再按传入的四类重插一遍。
想"加一个人"必须把**现有的全部**一起传回去（先用 `scheduleGet()` 读当前值）。

⚠️ **四个列表全传空 = 清空该组所有排班**（后端有专门一条分支，连 `startDate` 都不落库 ——
实测冒烟第 8 步：清空后 `scheduleGet` 的 `startDate` 也变回 null）。这是清空的**唯一**正确做法。

⚠️ **可能失败**：选中的对象解析出的用户里，有人已经在**别的**考勤组（`hr_group_user_rel`
有 `is_del=0` 且 `group_id` 不同）时，后端抛「所选人员在别的考勤组存在,请重新选择」。

### `userIdList` 里装的是**工号（username）**，不是 `sys_user.id`

这是这一页最容易搞错的地方，三处互证：

1. 后端 `saveWorkSchedule` 对 user 那一支调的是 `sysUserService.selectByUserName(userIdList)`。
2. 后端 `HrOrganizationServiceImpl.getUserByType` 里的原话注释：「前端传来的是staffCode 需要处理」。
3. 前端 `schedual.vue` 的 `getInitData`：`id: item.type === 4 ? Number(item.staffCode) : Number(item.paramsId)`；
   `staff.vue` 的 `onSubmit` 又把 `id` 设成 `item.username`。

⚠️ 所以从 `scheduleGet()` 读回来的 `paramsId`（sys_user id）**不能**直接塞进 `userIdList`，
要用同一行的 `staffCode`。实测徐曼曼：`paramsId=197916` / `staffCode=2026050801`。

### `attendance-team-get` 比列表多返回什么

`getInfo` 会 `setWorkShift(hrWorkShiftService.get(shiftId))`，所以 `get` 有 `workShift` 明细、
列表没有；反过来列表有 `shiftName`、`get` 没有。两边**不是**同一份形状。

### 一个从代码读出来的风险（**未实测**）

`HrAttendanceGroupServiceImpl.dealShift` 是：

```java
HrWorkShiftDTO dto = hrWorkShiftService.get(shiftId);
hrAttendanceGroupDTO.setShiftName(dto.getName());
```

`shiftId` 为 null 时 `get(null)` 返回 null、`dto.getName()` 会 NPE → 整张列表 500。
**一条没有班次的考勤组会让整个列表页打不开。** 页面的新建表单强制选班次（见上），
所以正常路径进不来；但接口层没有这个校验（`HrAttendanceGroupDTO` 里一个校验注解都没有）。

**本轮没有去实测这条**：要触发它就得 POST 一个 `shiftId` 为空的组，
那会让列表页在那段时间里对所有人报错 —— 代价与收益不成比例，宁可如实标成"从代码读出来的推断"。

## 不放进契约的东西

### `POST /org/organization/getUserByType` —— **它的响应里带密码散列**

这是「添加人员 / 查看人员」弹窗（`schedual.vue` 的 `getUser()`）拉人用的接口。实测响应里
对每个用户返回：

```json
{"id":"197916","username":"2026050801","realName":"徐曼曼",
 "password":"E10ADC3949BA59ABBE56E057F20F883E",
 "password2":"$2a$10$9PnpYCW/mrPoQ7fCNpfUIOdFbj4lyKxh9x.kCYj2FVjHDhaSpjmz.",
 "salt":"$2a$10$9PnpYCW/mrPoQ7fCNpfUIO", …}
```

`password` 是 MD5、`password2` 是 bcrypt、`salt` 也在。**把它做成能力 = 把密码散列塞进 AI 的上下文。**
它又是纯粹的渲染辅助（把已选的人显示成一行行），**不参与任何写载荷** ——
写载荷的 `userIdList` 来自 `getWorkSchedule` 的 `staffCode`。

⇒ **不暴露。** 理由与班次管理拒掉 `status` 同类：宁可少一个能力，也不放一个会带出凭据形状的读接口。
回归测试里有一条锁着这个边界（「这一页没有任何指向 `/org/organization` 的能力」）。

## 操作步骤

```text
1. 进入「组织管理 → 考勤管理 → 排班管理」
2. （可选）填「考勤组名称」、选「考勤类型」
3. 查询
4. 新建：点「新建」→ 填名称 → 「选择班次」弹窗里点一行的「选择」→ 保存
   （不选班次点保存会被页面拦住：「请选择班次」）
5. 编辑：行内「编辑」→ 改 → 保存
6. 排班：行内「排班管理」→ 选「排班日期」→（可选）「添加」人 → 确定
7. 删除：行内「删除」→ 气泡里点「删除」确认
   ⚠️ 组里还有排班时会失败：「该考勤组正在使用，无法删除!」
   —— 先在「排班管理」里把人清掉再删
```

## 尚未覆盖

- **「一条没有班次的考勤组会让整个列表 NPE」没有实测**。理由与代价见上文，
  它是**从代码读出来的推断**，不是实测结论。
- **`schedule-save` 的「所选人员在别的考勤组存在」这条失败路径没有触发过**。
  本轮特意挑了一个没人被占用的组织，所以只走了成功路径。失败路径的判据是从后端代码读的。
- **`schedule-save` 挂**岗位 / 职务 / 人**这三类没有实测**：只实测了 `organizationIdList`。
  四类的插入分支在 `saveWorkSchedule` 里是四段同构的代码，但"同构"是读出来的，不是测出来的。
- **`update` 与浏览器的 PUT 没有逐字节比对**（形状上就不可能相同）。
  只比对了"我们的键是它的子集 + 少发的正好是那九个"，以及实测了"少发服务端字段不会清掉它们"。
- **`page-catalog.json` 给这一页标的 `write: false` 是错的。** 误判规则与班次管理同一处：
  写入口在 `list.vue`（通用删除 `${deleteURL}/${id}`，不是 `http.delete(` 的形式）
  和 `[mode]/[id].vue`（不在 `list.vue` 里）两处，生成器的正则都扫不到。
- **`getUserByType` 的密码散列字段**：只知道它在测试环境的响应里确实存在。
  生产环境是否同样返回、是否被网关过滤，本轮没有、也不该去验证。
- **`module-type` 在测试环境被并行标签页污染这件事**：本轮只观察到现象并复核了 cookie，
  没有去构造一个"独占到 cookie 不被改"的抓取流程。开新 profile 也许能避免，但没有验证。
