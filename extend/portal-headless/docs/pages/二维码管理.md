# 二维码管理

## 能力定义

| 项目 | 内容 |
| --- | --- |
| 菜单归属 | 门户 → 系统设置 → 销售设置 → 二维码管理 |
| 页面路径 | `/dashboard/sale/custom/qr/list` |
| 页面权限 | `/dashboard/sale/frame/custom/qr` |
| 按钮权限 | Portal 子页面源码没有额外的 `permissionCheck` 或独立动作权限码；最终权限由 CRM 后端裁决，SDK 不虚构按钮权限 |
| module-type | `60`（销售系统） |
| HTTP 实例 | `crm`，对应 `app/portal/utils/http/crm.js`；调用 SDK 时必须配置 `httpBaseUrls.crm` |
| SDK 能力文件 | `src/capabilities/sale-custom-qr.ts` |
| AI 契约 | `src/catalog/contracts-sale-custom-qr.ts` |
| 回归测试 | `test/sale-custom-qr.test.ts` |

页面是三层下钻，不是三个独立菜单：供应商分页 → 选择店铺查询商品分类 → 选择商品分类查询引种证明字段。点击“设置”和“返回”只改变 Vue 视图状态，没有额外 HTTP 请求。

| 页面动作 | SDK 能力 | 写入 |
| --- | --- | --- |
| 供应商分页和名称筛选 | `sale-custom-qr-supplier-list` / `saleCustomQr.supplierList` | 否 |
| 按店铺查询商品分类 | `sale-custom-qr-item-kind-list` / `saleCustomQr.itemKindList` | 否 |
| 按店铺和商品分类查询字段 | `sale-custom-qr-field-list` / `saleCustomQr.fieldList` | 否 |
| 读取 `order_field` 字典候选 | `sale-custom-qr-order-field-list` / `saleCustomQr.orderFieldList` | 否 |
| 准备并新建字段 | `sale-custom-qr-prepare-create` → `sale-custom-qr-create` | 后者是 |
| 准备并编辑字段排序 | `sale-custom-qr-prepare-update` → `sale-custom-qr-update` | 后者是 |
| 准备并删除单条字段 | `sale-custom-qr-prepare-remove` → `sale-custom-qr-remove` | 后者是 |

页面没有服务端 cancel 接口。弹窗“取消”只关闭弹窗并丢弃本地表单；SDK 不提供伪造的 cancel 能力。

## 参数契约

### 第一层：供应商分页

Portal `ViewSupplierList.vue` 使用 `styleV2: true`、`getDataListIsPage: true` 和 `fieldNamePageSize: 'pageSize'`。因此首次请求默认 `pageNo=1`、`pageSize=20`；可选分页值为 10、20、50、100。表单只有 `tenantName`，默认空字符串。

```text
GET /vue/config/codeOrder/shopSumPage
params = { pageNo, pageSize, tenantName }
```

虽然公共列表模块会形成 `order`、`orderField`，但 `api/qr.js` 的 `configCodeOrderShopSumPage` 解构时没有接收它们，所以实际 CRM 请求不会发送这两个字段。CRM 返回 `{ list, count }`，SDK 对外返回 `{ list, total }`。

`list[]` 的页面字段：

| 字段 | 含义 |
| --- | --- |
| `tenantId` | CRM 组织ID，页面不展示 |
| `tenantName` | 供应商名称 |
| `shopId` | 店铺ID；进入下一层的上下文ID |
| `shopName` | 店铺名称 |
| `itemKindNum` | 已配置商品分类数量 |
| `updateTime` | 配置汇总更新时间原值 |

用户选择一行后，只把该行的 `shopId` 传给下一层；名称只用于页面标题，不能替代 ID。

### 第二层：商品分类

```text
GET /vue/config/codeOrder/itemKindSumList
params = { shopId }
```

Portal 会把供应商行的 `shopId` 传入。接口源码和 Java Controller 同时允许 `shopId=null`：CRM 会尝试从当前用户租户的关联店铺中取第一家；找不到时返回“无权限查看”。SDK 对外保留这个 null 回退行为，不把它解释为全租户查询。

返回数组的字段：

| 字段 | 含义 |
| --- | --- |
| `itemKind` | 商品分类字典值；下一层请求必须使用它 |
| `itemKindName` | 页面显示名称 |
| `num` | 当前店铺/分类下的字段数量；无配置时为0 |
| `updateTime` | 最后更新时间原值，可为null |

### 第三层：字段列表

```text
GET /vue/config/codeOrder/list
params = { shopId, itemKind }
```

`shopId` 来自供应商列表行，`itemKind` 来自商品分类列表行；两者都必须使用 ID/字典值，不能用显示名称。Java Mapper 按 `sort` 升序返回。

| 字段 | 含义 |
| --- | --- |
| `id` | `config_code_order` 配置记录ID；编辑和删除使用 |
| `shopId` | 所属店铺ID |
| `itemKind` | 所属商品分类字典值 |
| `field` | `order_field` 字典值 |
| `fieldName` | 字典label，页面字段名称列 |
| `fieldType` | 字典 `remarks` 原值：`order` 或 `item` |
| `fieldTypeName` | `order` → “订单信息”，`item` → “商品信息”；未知值页面显示空白 |
| `sort` | 正整数显示顺序 |

### `order_field` 候选

Portal 弹窗挂载时调用：

```text
GET /vue/sys/dict/listData
params = { type: 'order_field' }
```

SDK 返回 `value`、`label`、`remarks`，并按页面 `ModalFormContent.vue` 的 switch 额外给出 `fieldTypeName`。`value` 才是保存时的 `field`；不能把 `label` 当提交值，也不能从 label 猜测类型。

### 新建和编辑

Portal 弹窗初始表单是：

```text
{ shopId: null, itemKind: null, field: null,
  sort: usedSort.length ? Math.max(...usedSort) + 1 : 1,
  id: null }
```

页面规则：

- `field` 必填；候选来自 `order_field`，编辑时 `:disabled="mode === 'edit'"`，不可修改。
- `sort` 必填，输入框最小值为 1；`usedSort` 中已存在的值会被校验器拒绝，错误为“该排序已被使用”。编辑页面先从当前列表的排序集合中排除当前行的 `sort`。
- 新建实际沿用表单的 `id: null`；编辑必须保留当前行 `id`。
- SDK 的 `prepareCreate` / `prepareUpdate` 只做本地整理和校验，不发请求。编辑准备还要求 `currentField === form.field`，这是对Portal禁用字段规则的显式锁定。

用户确认后，两种保存都发送同一个请求：

```text
POST /vue/config/codeOrder/save
Content-Type: application/x-www-form-urlencoded
data = { shopId, itemKind, field, sort, id }
```

`currentField` 是 SDK 本地校验字段，不会进入 HTTP body。Java Controller 捕获重复键并返回“字段已存在”；Mapper 的 update SQL 只更新 `shop_id`、`item_kind`、`sort` 等字段，不更新 `field`，与页面字段禁用规则一致。保存成功无业务数据回执，必须重新调用第三层列表回查。

### 删除

Portal 确认后发送：

```text
DELETE /vue/config/codeOrder/{id}
```

页面源码没有额外删除请求头，也没有批量删除。SDK 的 `prepareRemove` 不发请求；用户确认后调用 `remove`。成功或超时后按同一 `shopId + itemKind` 回查，确认目标 `id` 已消失。

## 操作步骤

### 查询和下钻

1. 调用 `sale-custom-qr-supplier-list`，展示 `list` 并用 `total` 分页。
2. 用户选择一行“设置”后，保存该行 `shopId`，调用 `sale-custom-qr-item-kind-list`。
3. 用户选择一条商品分类后，保存 `itemKind`，调用 `sale-custom-qr-field-list({ shopId, itemKind })`。
4. 编辑或删除时只能使用当前字段列表行的 `id`；新增字段时先调用 `sale-custom-qr-order-field-list` 选择真实 `value`。

### 新建

1. 从当前店铺/商品分类上下文和 `order_field` 候选形成表单，并把当前字段列表的 `sort` 集合作为 `usedSort`。
2. 调用 `sale-custom-qr-prepare-create`；省略sort时使用最大已占用值+1，空列表为1。
3. 若排序已被使用、field为空或上下文ID非法，准备阶段失败，不发送POST。
4. 用户取消时只丢弃草稿；用户明确确认后把同一 `draft` 交给 `sale-custom-qr-create`。
5. 成功或超时后重新调用字段列表，按 `shopId/itemKind/field/sort` 核对；匹配不唯一时报告不确定，不盲目重试。

### 编辑

1. 从当前字段列表取得完整行；将原始 `field` 同时作为 `form.field` 和 `currentField`，将当前行sort从 `usedSort` 中排除。
2. 调用 `sale-custom-qr-prepare-update`；只允许修改sort，field变化会在请求前失败。
3. 用户取消时只丢弃草稿；用户确认后把同一带锁草稿交给 `sale-custom-qr-update`。
4. 成功或超时后按同一 `id` 回查，确认field仍未变化、sort已达到目标值。

### 删除

1. 从当前字段列表取得目标行 `id`，调用 `sale-custom-qr-prepare-remove`。
2. 用户取消时不发送请求；用户确认后调用 `sale-custom-qr-remove`。
3. 用发起删除时保存的 `shopId` 和 `itemKind` 回查字段列表，逐条确认目标ID消失；超时先核实，不自动重删。
