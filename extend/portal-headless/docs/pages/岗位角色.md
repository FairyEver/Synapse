# 岗位角色

## 1. 能力定义

页面路径：`/dashboard/setting/role-post/list`

页面权限：`/dashboard/setting/role-post`

HTTP 实例：`platform`

`module-type`：不发送。

本页属于保留范围内的“系统设置”。它展示岗位及其已分配角色，可查看岗位人员，并在弹窗中按系统选择角色后保存岗位角色关系。系统下拉可以显示门户定义的多个系统类型（包括生产等系统的角色选项），但这仍是岗位角色页面的字段值，不代表SDK实现了独立生产、财务、资产、采购或销售根模块页面。

SDK 登记的能力：

- `setting-role-post-list`：查询岗位角色分页。
- `setting-role-post-role-filter-options`：读取列表“分配角色”筛选树。
- `setting-role-post-roles`：读取指定岗位当前角色。
- `setting-role-post-role-options-by-system`：按系统读取设置角色弹窗候选。
- `setting-role-post-users`：查询岗位人员分页。
- `setting-role-post-prepare-replace` / `setting-role-post-replace`：准备并保存岗位角色全量替换。

## 2. 参数与提交契约

列表请求实际为：

```text
GET /admin-api/org/post/role/page
{ order: "", orderField: "", postName: "", roleId: null|ID, pageNo: 1..., limit: 20|10|50|100 }
```

列表返回 `{ list, total }`；`list[].postId` 是岗位ID，`roleNameList` 没有角色时按空数组处理。角色筛选组件加载时还会发送：

```text
POST /admin-api/sys/role/allProjectRoleListNotBySystem
body = [2, 3]
```

这个 body 是 Portal 组件默认值，当前 Java 接口实际按 query 中的 `useSystem`、`name` 过滤并忽略 JSON body；不能把 `[2,3]` 描述为有效的服务端项目筛选。

设置角色弹窗的读取请求为：

```text
GET /admin-api/org/post/role/role/<postId>
GET /admin-api/sys/role/listByUseSystem?useSystem=<系统值>
```

查看人员请求为：

```text
GET /admin-api/org/post/role/usersListByPost
{ order: "", orderField: "", postId, realName: null|string, organizationId: null|ID, pageNo, limit }
```

组织树是Portal的无界全量控件，SDK不提供该树的独立大结果能力；`organizationId`必须来自已知的组织上下文。

保存不是增量追加，而是一次全量替换。`prepareReplace` 只在本地校验并去重，最终 `replace` 严格发送：

```json
{
  "postId": 10,
  "roleIdList": [20, 21]
}
```

`roleIdList: []` 表示清空该岗位全部角色。页面存在后端单条 DELETE 路由，但当前页面删除行只是本地数组修改，点击保存时统一 POST；SDK不发布该页面不可达的 DELETE 能力。

## 3. 逐字段基准

岗位列表：

| 字段 | 含义 |
| --- | --- |
| `postId` | 岗位ID；后续读取角色、人员和保存关系都使用它 |
| `postName` | 岗位名称；仅用于展示/筛选，不能当ID |
| `roleNameList` | 当前岗位已分配角色名称数组；无角色时为 `[]` |
| `total` | 符合筛选条件的岗位总数，不是当前页长度 |

角色对象的页面消费字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 角色ID；保存时只能放入 `roleIdList` |
| `name` | 角色名称；展示和本地搜索使用 |
| `useSystem` | 角色所属系统类型值；不能和角色ID互换 |

岗位人员对象的页面消费字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 用户ID；后端人员记录主键 |
| `realName` | 人员姓名 |
| `sourceType` | `1` 主岗位，`2` 兼职岗位；未知值不擅自映射 |
| `orgfullpath` | 人员所属组织全路径 |
| `total` | 当前岗位和筛选条件下的在职人员总数 |

## 4. 操作步骤与验证

1. 调用 `setting-role-post-list`，从 `list[].postId` 取得岗位ID；需要按角色筛选时先使用 `setting-role-post-role-filter-options`，提交节点ID而不是名称。
2. 查看角色时调用 `setting-role-post-roles`；设置角色时按 `useSystem` 调用 `setting-role-post-role-options-by-system`，只把候选的 `id` 放入最终数组。
3. 用户确认最终角色集合后调用 `setting-role-post-prepare-replace`；取消时丢弃草稿，不发请求。
4. 确认后调用 `setting-role-post-replace`。保存成功、超时或响应丢失后，都必须按同一 `postId` 再调用 `setting-role-post-roles`，核对返回的角色ID集合与草稿一致；不能只凭空返回或HTTP成功报告完成。
5. 查看人员调用 `setting-role-post-users`；`sourceType`按1/2解释，空列表不能解释为无权限或岗位不存在。
