## 一页读**两个不同的东西**：列表是提示词模板，写的是新版技能配置

这是这一页最容易读错的地方：

- 列表读 `sys_tip_template`（`TipTemplateController`，`@RequestMapping("/sys/tip-template")`）；
- 而新建 / 编辑保存的是 `NewSkillConfig`（`/ai/skill/config/save`），
  库表其实也是 `sys_tip_template` —— `AiSkillV2ConfigDO` 的 `@TableName("sys_tip_template")`，
  另外把节点树写到 `ai_skill_v2_node`；
- 删除走的是列表页的通用删除 ⇒ `DELETE /admin-api/sys/tip-template/{id}`。

所以"读的是模板、写的是技能配置"不是笔误。

## 列表：**实测**与基准逐字段一致

`baseline/ai-prompt.browser.json` 里这一页的那一条（2026-09-21 抓到）：

```
GET https://biz-api-test.wodecorp.cn/admin-api/sys/tip-template/page?order=&orderField=&name=&typeId=&useSystem=&useFeature=&isPublish=&pageNo=1&pageSize=20&_t=<ts>
```

**与源码推导逐字一致，没有冲突。** 表单初值
`form: { name: '', typeId: '', useSystem: '', useFeature: '', isPublish: '' }`
（`prompt/list.vue:149-155`）⇒ 五个筛选位**全部照发空串**（初值是 `''`，不是 `null`）。

⚠️ **这五个空值参数是源码推导最容易漏掉的一处**：模板上的 `typeId` / `useSystem` /
`useFeature` / `isPublish` 都是 `allow-clear` 的下拉，**用户清空之后**控件的值是 `undefined`，
那时那个键会**整个从 URL 上消失**（`qs` 的 `skipNulls`）。
基准抓的是**首屏无筛选**那一版 —— 那时五个键**都在、都是空串**，别因此以为"清空后也照发"。
SDK 不模仿"键有时在有时不在"，统一按表单初值发空串；"清空后到底怎样"留在 `it.todo` 里没硬编。
测试里对这个键序有**逐字断言**（`queryPairs` 比有序对，不是比集合）。

后端的过滤条件（`TipTemplateMapper.selectPage`，`:22-33`）逐个对得上：
`name` 是 `likeIfPresent`（`%x%`），`typeId` / `useSystem` / `useFeature` / `isPublish` /
`isIntentRecognition` / `code` 都是 `eqIfPresent`。

⚠️ **`createTime` 是假的筛选位**：`TipTemplatePageReqVO` 有它（还带 `@DateTimeFormat`），
但 `selectPage` 的 wrapper 里**没有它** ⇒ 传了会被静默忽略。能力里没有登记它。

⚠️ 页面上的 `useFeature` / `isPublish` 都是字典下拉且 `allow-clear`：清空之后控件给的是
`undefined`，那个键会**整个从 URL 上消失**（`qs` 的 `skipNulls`）。SDK 不模仿"键有时在有时不在"，
统一按表单初值发空串；这一条是**待基准复核**的差异点之一。

## 写链路：`prepare → submit → cancel`，三步都是真接口

| 步骤 | 能力 | 请求 | 出处 |
| --- | --- | --- | --- |
| 预览（只读） | `previewSkill` | `POST /admin-api/ai/skill/config/preview`，body = 保存载荷 | `[mode]/[id].vue:367-374` |
| **prepare**（只读） | `prepareSkillReview` | `POST /admin-api/ai/skill/config/execute`，body `{ skillCode, modelConfigId, context }` | `[mode]/[id].vue:399-405` |
| **submit**（写） | `submitSkillSave` | `POST /admin-api/ai/skill/config/save`，body = 保存载荷 | `[mode]/[id].vue:170-178` + `api.js:11-13` |
| **cancel**（写） | `cancelSkillSave` | `DELETE /admin-api/sys/tip-template/{id}` | 列表页 `deleteURL`（`prompt/list.vue:148`）+ `list.js:516-520` |
| 详情（只读） | `getSkill` | `GET /admin-api/ai/skill/config/get?id=` | `api.js:3-9` |

**这是本组唯一一条真有 `prepare` 的链路**：页面的提交顺序是
`execute(skill_review)` → 弹「技能审核结果」→ 用户点「继续保存」才 `formSubmit`
（`[mode]/[id].vue:376-420`）。`approved=false` 时页面**并不阻止**保存，只是让人看一眼 ——
SDK 保持同样语义：**这一步不替调用方做决定**，把 `{approved, content, variables}` 原样返回。

⚠️ 判断"审核到底跑成功没有"不能只看 `approved`：页面在
`variables.executionFailed === true` 或 `variables.parseFailed === true` 时把结果**整个丢掉**
（`utils.js:109-128`）。SDK 不做这层过滤（它只影响弹窗显示），调用方自己看这两个标志。

### 保存载荷：键序与页面 `buildSkillConfigPayload` 逐字对齐

`prompt/utils.js:89-107` 的键序（`buildSkillConfigPayload` 在 SDK 里是**同名复刻**）：

```
id, name, skillIntroduction, tipPromptText, isPublish, isIntentRecognition, isAppExclusive,
useType, typeId, useSystem, useFeature, icon, tipContent, nodes
```

节点（`utils.js:446-479` 的 `cleanNodeForPayload`）：

```
id, nodeType, name, enabled, sort, description, triggerWords, promptContent,
modelConfigId, apiIds, cardConfig, children
```

卡片（`utils.js:428-444`）：`id, enabled, cardNo, cardName, buttonCount, buttons, outputFormatJson`；
按钮：`sort, name, actionType, actionValue, pcActionValue`。
后端 DTO 的字段名逐个对得上（`NewSkillConfig` / `NewSkillNode` / `NewSkillCardConfig` /
`NewSkillCardButton`），所以 `getSkill` 读回来直接喂给 `submitSkillSave` 能往返。

四条页面特有的归一规则，能力里都做了：

1. **模块节点不允许带模型 / 接口 / 卡片** ⇒ `modelConfigId=null`、`apiIds=[]`、`cardConfig=null`
   （`utils.js:452-459`；后端 `NewSkillConfigValidator.validateModule` 也会拒）。
2. **模块下面的子节点被强制当技能**（`utils.js:424` 的 `normalizeNode({...child, nodeType: 1})`）。
3. **卡片没启用时除 `id`/`enabled` 外全部清空**（`utils.js:466-475`）。
4. **`sort` 按数组位置重排**（1 起），不认调用方给的 `sort`（`utils.js:481-486` 的 `normalizeNodeSort`）。

**两处刻意不复刻的页面行为**（都写进了 `buildSkillConfigPayload` 的注释）：

- **按钮数不按卡片上限截断。** 页面拿前端注册表
  `app/portal/views/dashboard/common/chat/utils/xiaohuiCardRegistry.js:1-20` 的 `buttonLimit`
  裁按钮（101/102/107/108 是 0 个、113 是 1 个、其余 3 个）。SDK 不搬那张前端表：
 后端 `NewSkillConfigValidator` / `NewSkillNodeOutputPolicy` **都不校验按钮数**，
 所以超了不会报错，只是页面上看不到多出来的按钮。
- **`code` 不发。** `NewSkillConfig` 有 `code`，后端 `normalizeAndValidateCode`
  （`NewSkillConfigServiceImpl.java:191-205`）要求 `[a-z][a-z0-9_-]{1,63}` 且唯一；
 但页面的载荷构造器不带它 ⇒ 恒为 null ⇒ `updateById` 忽略 null。SDK 保持一致。

### 保存是**覆盖**语义、且后端校验很重

`NewSkillConfigServiceImpl.save`（`:41-57`）：先 `NewSkillConfigValidator.validate`，
不过就抛业务错误；有 id 时 `updateById` 后还要
`nodeMapper.deleteByConfigId(id)` **再按 `nodes` 重插** —— 所以 `nodes` 必须给全，
不能只给要改的那几个节点。

页面上另有三条客户端 `rules`（`[mode]/[id].vue:180-186`）：
`name` / `skillIntroduction` / `icon` / `tipPromptText` / `typeId` 必填。
SDK **不重复这套客户端校验**：后端会拒。缺了会拿到一个业务错误（按 conventions 第 9 条多半是 500）。

### `prompt/api.js` 里两条**没有页面调用**的接口，没做成能力

- `deleteSkillConfig(id)` → `DELETE /admin-api/ai/skill/config/delete?id=`
  （列表页的删除走 renren 的 `DELETE /sys/tip-template/{id}`，**不是**这条）
- `fetchSkillCardDetail(cardNo)` → `GET /admin-api/ai/skill/card/get?cardNo=`

全仓 grep 只有 `api.js` 自己和它的单测提到它们。按 conventions 第 28 条的口径
（"没被用到的入口不搬进 SDK"）**不进能力**，常量记在 `UNUSED_SKILL_API_PATHS` 里备查。

## 真实验证：读链路有基准，写链路一次真机请求都没发过

- **读链路（列表 / 候选）/ 权限与头**：由 `baseline/ai-prompt.browser.json` 逐字段证实
  （列表那一条 + `GET /admin-api/system/tip-type/list?_t=` 那条，都见上面）。
  测试里是 `describe.skipIf(!HAS_BASELINE)` 那一组，现在真的在跑。
- **写链路（`save` / `preview` / `execute` / `DELETE`）**：**没有**任何实测。写这份能力时全程只跑了
  本地的 `tsc` / `vitest`（axios 适配器是假的，请求不出进程）：**没有开浏览器、没有起 `bsk` 会话、
  没有跑任何 smoke 脚本、没有向测试环境发过任何一个非 GET 请求。**
  基准里 **0 条非 GET**，所以那几条断言是 `it.skipIf` 挂起的 —— 抓不到就永远不跑，
  **别把"测试全绿"读成"写链路已验证"**。

真机写验证由**派单方统一跑**，清单见下。跑完把实际请求/响应回填到本节。

## 基准里那两条「外壳请求」不是页面契约

这一页的基准里有 4 条，其中两条是 app 外壳拉的、**本页没有发**：

GET /admin-api/bpm/task/list-by-category?finished=1&pageNo=1&pageSize=10&_t=<ts>

测试里对它们只做"确实在基准里、且不是我们发的"这一条断言，不数条数。
（基准里另外两条是**页面自己的**：`GET /admin-api/sys/tip-template/page` 与

## 基准到位后**仍然**没解决的

基准 2026-09-21 到位，读链路全绿了；下面这些**基准里没有**（0 条非 GET），或光有基准也判不了：

- **写链路三个 POST 的 body**（`save` / `preview` / `execute`）与浏览器逐字段比对 —— 基准里没有 POST。
- **`DELETE /sys/tip-template/{id}` 的形态**（有没有 body / `_t`）—— 基准里没有 DELETE。
- **五个筛选位被 `allow-clear` 清空后**键是空串还是整个消失 —— 首屏基准证明不了，要人工点一次再抓。
- **三个复合控件有没有懒加载请求**：基准抓到了这一页的 4 条**页面请求**（列表 + 类型候选 + 两条外壳），
  与源码里"`SkillTreePanel` / `SkillNodeEditor` / `CardConfigModal` 一处 `http.` 都没有"这个结论
  **方向一致**；但那只覆盖了**列表页**，编辑页的编排动作没抓。
- `module-type` **不发**现在有硬证据（三页三条列表请求 + 16 页 0 条），已改成断言 `headers` 里
  **不存在**该键。
