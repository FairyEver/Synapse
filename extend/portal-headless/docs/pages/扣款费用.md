## 列表、合计与筛选规则

Portal 请求默认参数为：

```text
GET /salary/salarypersontax/pageNew
name=&staffCode=&idCard=&archiveStatus=1&orgId=
pageNo=1&pageSize=20&costDateStart=&costDateEnd=&order=desc&orderField=id
```

Portal 后端响应不是普通 `{ list, total }`，而是：

```text
{
  total: { childEducation, housingRent, housingLoanInterest,
           elderlyCare, continuingEducation, infantCare, sickChildEducation },
  list: { list: object[], total: number }
}
```

SDK 对外返回 `{ summary, list, total }`，其中 `summary` 是7类金额合计，`total` 是分页记录数；不能把合计对象误当成分页总数。列表每行保留员工、组织、岗位、归属月份、归档状态、操作人、创建时间和 `specialList`。Portal 的七个金额列从专项类型 `1` 至 `7` 映射，不是后端独立字段。

`archiveStatus` 默认 `1=未归档`，`2=已归档`；`orgId` 是角色组织树节点 ID，服务端再展开下级组织并叠加当前用户数据权限。`costDate` 月份范围按 Portal 的 `convertFetchForm` 转成 `costDateStart`、`costDateEnd` 的 `YYYY-MM` 字符串；未选择月份发送两个空字符串。排序固定为 `order=desc`、`orderField=id`，不接受调用方改写成其他排序。

## 表单、导入和归档规则

详情加载时，Portal 将后端数值 `staffCode` 转为字符串，并把每个专项的 `costStart`、`costEnd` 投影为 `costTime`；两端不完整时回填空数组。提交时保留根字段和专项归档状态，但移除表单专用 `costTime`：

```text
costTime = [任意日期A, 任意日期B]
→ costStart = A所在月第一天
→ costEnd   = B所在月最后一天

costTime = [] 或两端不完整
→ costStart = null, costEnd = null
```

表单固定七个且不重复的专项类型，金额按 Portal `a-input-number` 规则限制为非负且最多两位小数。保存、删除和归档都必须先准备草稿、用户确认、提交，再重新查询；成功空回执不能替代回查。已归档行在列表中不可勾选归档或删除，归档请求固定为 `{ ids, status: 2 }`。

导入文件字段固定为 `file`，MIME 必须是标准 xlsx 类型；导入和归档都返回员工资格回执。`processedCount` 是实际处理数量，不是请求数量；`excludedStaffList` 的原因必须保留并展示，不能把请求成功描述成全部保存成功。模板名固定为 `个税专项扣款归档导入模板`，导出使用 `selectState.join(',')` 生成 `idList`；空选中状态保持 Portal 的空字符串语义。

## 权限与边界

- 所有请求使用 `platform` axios 实例，并由 SDK 会话注入 `module-type=14`；权限码固定为 `/dashboard/salary/person-tax`。
- Portal 人员选择器会无关键字分页拉取人员，再按当天业务日期分批调用资格检查；SDK 不复制无界全量候选。调用方应先用已有员工搜索能力取得并核实 `staffCode`，再调用表单或显式的 `eligibilityCheck`。
- `id`、`staffCode` 和导出 ID 必须来自当前用户可见且已核实的记录；服务端数据权限仍是最终边界，SDK 不扩大范围。
- `idCard` 是敏感字段，按原值消费并避免写入日志。

## 员工候选（`components/staff-select.vue`）

`GET /admin-api/org/staff/allStaffByPage`，能力 `salary-person-tax-staff-page` / `salaryPersonTax.listStaffCandidates`。

页面自己**无界全量翻页拉**：`loopFetch(..., { pageSize: 200, maxPages: 100 })`（最坏 20 万条），再把结果按 500 一批打到 `/salary/staff-eligibility/check` 过滤出可发薪的人，最后把 `${name}(${staffCode})` 填进 Antd Select。这正是 conventions 第 11 条点名的那类长候选，**SDK 不照抄**：只做有界分页（默认 20、上限 200，拒绝 `-1` 与超额）。

### 这条接口没有关键字可用（所以 SDK 不暴露 `name`）

`HrStaffSelectDataScopeDTO` 上声明了 `name`，但 `HrStaffDao.xml` 的 `allStaffByPage` 的 `<where>` 里**只有** `is_del`、`organizationIdList`、`isFilterLeaveStaff` 和数据范围 —— **压根不拼 `name`**，传了等于没传。SDK 因此不暴露它：暴露一个会被静默忽略的筛选条件，正是本仓库最不想要的那种"不报错但是错的"。

SDK 改为暴露两个后端真正支持、页面自己没用的收窄手段：`organizationId`（后端会展开全部后代）与 `isFilterLeaveStaff`（`=1` 时加 `status in (1,4,5)`）。**这两个键必须写进说明**，否则调用方会以为只能一页页翻。

### 请求与返回

参数顺序：`organizationId`、`isFilterLeaveStaff`、`pageNo`、`pageSize`（页面自己只发后两个）。返回 `{ list, total }`，行只有 SQL select 的六列：`id`（`hr_staff.id`，不是工号）、`name`、`staffCode`（工号，资格检查和表单回填用它）、`idCard`、`organization`（组织ID，不是名称）、`status`（1 在职、2 离职、3 退休、4 返聘、5 在编不在岗）。DTO 上其它字段（薪资等级、成本中心、联系方式等）不是这条 SQL 的产出，SDK 不补齐也不解释。

### 与资格检查的分工

本能力只回答"有哪些员工"；"谁能办个税专项扣款"必须再调 `salary-person-tax-eligibility-check`（同一天的业务日期，页面用 `formatDay()` 当天）。契约里的 `steps` 写死了这条映射：`staffCodes: result.list[].staffCode` + `businessDate: context.businessDate`。

### 验证边界

已核对：页面组件调用形状、DAO XML 的 where 子句（`name` 被忽略的证据就在这里）、DTO 字段、Service 的后代展开。
未做：没有启动浏览器、没有对测试环境请求；`organizationId` 收窄与 `isFilterLeaveStaff` 的实际过滤效果未在真实租户验证；`name` 被忽略这件事没有抓包复核（只有 XML 原文）。
