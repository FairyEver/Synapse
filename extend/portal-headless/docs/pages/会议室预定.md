## 真实请求序列（打开表单时）

基准文件：`baseline/meeting-application-form.browser.json`

| # | 方法 | 路径 | 说明 |
| --- | --- | --- | --- |
| 1 | GET | `/admin-api/org/sensitive/info` | 敏感操作信息（全局） |
| 2 | GET | `/admin-api/bpm/task/list-by-category?finished=1&pageNo=1&pageSize=10` | 与表单无关，来自其它组件 |
| 3 | GET | `/admin-api/bpm/process-definition/get?key=meeting_application` | 流程定义 |
| 4 | GET | `/admin-api/system/user/simple-page?pageNo=N&pageSize=500` | **重复 9 次，共拉约 4500 个用户** |
| 5 | GET | `/admin-api/hr/meeting-application/meeting-room-usage` | 会议室占用 |

### 两个必须记住的点

1. **占用接口的路径属于 `meeting-application`，不是 `meeting-room`。**
   SDK 曾误写成 `/hr/meeting-room-usage`，已修正。表单页 4 处调用（PC/移动 × 表单/弹窗）用的都是
   `/admin-api/hr/meeting-application/meeting-room-usage`。

2. **页面为了填人员选择器，把全部 4500 个用户分 9 页拉了下来。**
   这在浏览器里是"能用但慢"，在无头下**不可接受**——几千条数据会直接冲掉 AI 的上下文。
   这正是设计 D6 / H35 说的"长选项参数"：**必须先由用户给出关键字**。
   SDK 的 `searchUsers()` 因此强制要求 `keyword` 或 `deptId`，并拒绝 `pageSize = -1`。

## 操作步骤

```text
1. 进入「发起流程」→ 选「会议室审批」→ 跳到本表单
2. 填会议名称
3. 选会议室（下拉；可先点「查看会议室预定情况」看当天占用）
4. 选时间段（开始 / 结束）
5. 填参会人数
6. （可选）填参会人
7. （可选）点「查看审批流程」确认审批链
8. 提交
```

## 审批链（实测）

点「查看审批流程」得到的链：

```text
发起流程 → 姚淼鑫（发起人）→ 流程结束
```

**没有任何审批节点**，因此该流程提交时不需要选审批人（服务端 `validateStartUserSelectAssignees` 在无 `START_USER_SELECT` 节点时直接放行）。

但页面自身提示"实际审批流程可能会根据填写内容变化"，所以 SDK 在提交前仍应查一次需要哪些审批人节点，不要假定为空。

## 提交链路

表单的 `handleSubmit()` 是两步：先 `POST getRequiredStartUserSelectTasks` 拿到需要人工
指定审批人的节点，合并成 `startUserSelectAssignees`，再 `POST create`。

SDK 按同样两步拆开，但把第一步单独暴露出来，因为它**只读**：

| 方法 | 请求 | 是否会改数据 |
| --- | --- | --- |
| `prepare(draft)` | `POST /hr/meeting-application/getRequiredStartUserSelectTasks` | 否 |
| `submit(draft, assignees)` | `POST /hr/meeting-application/create` | **是**（创建单据 + 触发流程） |

载荷（与 `buildSubmitData()` 一致，即原样展开 `formState`）：

```json
{
  "id": null,
  "meetingName": "周会",
  "meetingRoomId": 12,
  "startTime": "2026-09-22 14:00:00",
  "endTime": "2026-09-22 15:00:00",
  "attendeeCount": 6,
  "attendees": "",
  "startUserSelectAssignees": {}
}
```

时间段规则（`assertTimeSlot`）：分钟只能是 00 或 30、秒只能是 00、结束必须晚于开始。
前两条来自前端 `disabledTime`，第三条来自后端 `validateTime`。

## 真实验证记录（2026-09-20）

在测试环境跑过一次完整的写链路，记录见 `baseline/meeting-application-write.verified.json`：

```text
提交前：会议室 5 在 2026-09-22 14:00 的占用 —— 空
prepare：需人工指定审批人的节点 0 个
submit：已提交，后端返回 50（新建单据 id）
提交后：会议室 5 在 2026-09-22 14:00 的占用 —— 无头SDK冒烟-可删除(姚淼鑫)
取消后：空
```

三条结论：

- `submit()` 的载荷形状**被后端接受**（不再是"仅由代码推导"）
- `create` 返回的是新单据 id
- `cancelReservation(id)` 可用，且取消后占用查询立刻反映

## 2026-09-22 AI 说明契约同步

权威契约在 `src/catalog/contracts-workflow.ts`，经 `catalog.describe(id)` / `id-llm` 的 `ai` 实际返回；`describePage` 同步用途与功能区别。额外公开门面通过 `catalog.describeMethod(sdkPath)` 下钻，无需调用方读仓库。

| 能力 | 效果 | 最终 SDK 返回 | 完成判据 |
| --- | --- | --- | --- |
| meeting-application-definition | read | 流程定义对象（已拆后端包络） | 已确认流程身份；填写流程继续准备，单纯查询定义则交付名称与配置即可。 |
| meeting-room-usage | read | { organizationId?, date?, meetingRooms: 会议室占用[] } | 查询需求交付占用表；预订需求选定无冲突时间后进入准备。 |
| meeting-user-search | read | { list: 用户候选[], total: number } | 用户选定正确人员并保留 id 后候选查询完成。 |
| meeting-application-prepare | prepare | { payload, tasks }（本流程附加字段见 fields） | 草稿校验并得到所需自选节点后准备完成；实际发起须再提交。 |
| meeting-application-submit | write | number（业务单据 ID；SDK 不返回 code/data 包络） | 回读确认业务记录及其流程后，向用户交付业务 ID 与当前审批状态；提交成功不等于审批完成。 |
| meeting-application-cancel | write | boolean（后端成功回执；SDK 原样返回拆包后的值） | 目标会议室对应时间段已不再占用，向用户报告已取消。 |

数据消费与分支：

- meeting-application-definition：展示 name 与 key 核对业务；formFields 为 null 不代表免填，填写规则在 prepare/submit 的 SDK 描述中。
- meeting-room-usage：按同一会议室比较时段交集；结束等于下一开始不算重叠。展示名称、日期、起止时间，避免用数组长度推空闲房间数。
- meeting-user-search：展示姓名与工号给用户消歧；保存选中行 id 作为 userId。 keyword 或 deptId 至少给一个；pageSize=-1 被拒绝。
- meeting-application-prepare：给用户核对 payload 的业务值；按 tasks[].id 建立 startUserSelectAssignees 的键，人员来自候选查询，人数、去重与顺序服从任务规则。 准备只读，不建单、不保留名额、不发送待办；任何草稿变更后应重新准备。
- meeting-application-submit：保存业务 ID、流程类型及原 requestId；回读业务字段并查询流程实例确认已创建。 取消属于用户改变决定时的可选操作，不是正常提交后的必做步骤。
- meeting-application-cancel：只取消自己发起且仍运行的流程；保留业务记录，不代表删除历史。 查实际流程 status=4 才认定撤销完成；会议预定则核对占用时间段消失。

本轮以 `test/ai-contract-workflow.test.ts` 核对真实 SDK 描述，复用既有浏览器基准，不重放真实写操作。逐项验证与缺口见 `docs/ai-contract-workflow-evidence.md`。
