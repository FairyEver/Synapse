## 参数契约与逐字段基准

列表请求按 Portal 列表模块发送：

```json
{
  "order": "",
  "orderField": "",
  "organizationId": 9,
  "useYearMonth": "2026-09",
  "status": 0,
  "pageNo": 1,
  "pageSize": 20
}
```

`organizationId`是角色组织树选中的ID，不是组织名称；服务端先按当前用户可用的模块组织范围收敛，再查询。`useYearMonth`按月份控件格式化为`YYYY-MM`；`status`沿用页面选项：`0`待提交（草稿）、`1`已提交-审批中、`2`已审批-审批通过、`3`已驳回、`4`已取消。省略或清空三个筛选条件时发送`null`。页大小沿用 Portal 选择项，仅允许`10/20/50/100/200/500`。

列表返回`{ list, total }`。`list[]`包括：`id`汇总表ID、`organizationId`和`organizationName`组织信息、`staffCount`人数、`useYearMonth`工资月份，以及`enterpriseSalary`、`heatingFee`、`holidayAllowance`、`additionalInsurance`、`subsidy`、`transportFee`、`bookFee`、`laborFee`、`laundryFee`、`medicineFee`、`otherFee`、`actualAmount`各金额合计和`status`。金额保持后端原值，不能用浮点数替代服务端精度。

详情请求把汇总行的`list[].id`映射为`retireStaffSalarySummaryId`：

```json
{
  "order": "",
  "orderField": "",
  "retireStaffSalarySummaryId": 101,
  "name": "张",
  "pageNo": 1,
  "pageSize": 20
}
```

详情`list[]`增加退休人员的`name`、`idCard`、`organizationName`和同名金额字段，`status`是底层明细状态：`0`未使用、`1`已使用。`idCard`是敏感字段，按原值消费且不写日志。

页面底部的“合计”是对当前页`listData`逐字段求和，不是跨页总计；SDK返回原始分页结果，不伪造一个未由服务端返回的全量合计。

## 操作步骤、失败处理与验证边界

1. 需要汇总列表时用`.list`，按`total`继续翻页；要看某行人员明细，先取该行`id`再调用`.detail`。
2. `list=[]`且`total=0`只表示当前筛选无记录，不能据此判断没有权限。
3. 非法组织ID、月份、状态、汇总ID、页码或页大小会在请求前失败；401/403、网络和后端错误原样抛出；坏分页响应会失败而不是静默返回空列表。
4. 组织候选由 Portal 角色组织树加载，SDK 不复制全量长候选；调用方应先取得并核实ID。
5. 页面源码、Java 端点/VO/Service/Mapper、请求参数和反例已由离线测试锁定；真实测试环境的列表/详情读请求仍未执行，不能宣称线上已验证。
