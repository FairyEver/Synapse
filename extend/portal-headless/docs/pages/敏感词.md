### 基准的覆盖边界

那一份 14 条里：**0 条非 GET**、没有带 `word` 的筛选请求、也没有 `checkSensitiveWords`。
所以这一页：

- **有基准背书**：无筛选列表请求
  （`getWhitelistByPage?order=&orderField=&pageNo=1&pageSize=20&_t=<ts>`），**且基准里有两条**
  只差 `_t` 的相同请求（抓的时候点过两次「查询」）。
- **仍然只有源码推导**：`add` / `update` / `delete` / `checkSensitiveWords` 四条。

## ⚠️ `checkSensitiveWords` 是**试检**，不是列表

它长得像列表接口（`POST` + 一个 `word` 参数），但语义完全不同：

- `POST /manager/sensitiveWordsWhitelist/checkSensitiveWords`，body `{"word":"<一段文本>"}`；
- 返回 `List<String>` —— 这段文本里**命中的敏感词**（后端 `sensitiveWordBs.findAll(word)`）；
- **只读**：后端没有任何写入，它只是那个「校验白名单」弹窗的按钮（`components/check.vue`）。

所以它是**独立能力** `ai-interaction-sensitive-word-check`、`write: false`，
**没有**混进列表能力里。入参是**待检的文本**，不是"某个白名单词"——名字很容易看反。
空数组 = 一个都没命中，**不是**"查不到"。

## 列表：只有一个真筛选位

无筛选时的键序 —— ⭐ **基准证实**：

```
GET /admin-api/manager/sensitiveWordsWhitelist/getWhitelistByPage?order=&orderField=&pageNo=1&pageSize=20&_t=<ts>
```

⚠️ 这一页在基准里是**两条**完全相同的请求（只差 `_t`）—— 抓的时候点过两次「查询」。
所以断言只能写成"**存在**一条逐字段相符的"，**不能**写"该 URL 只出现一次"。

⚠️ 关键证据：基准里这条 URL 上**没有** `question` / `answer`
—— 这正是下面那段"表单里有这个键但浏览器不发"的实测依据（不是靠读源码推的）。

⚠️ 这一页的 `form` 里**留着** `question` 与 `answer` 两个键，但**模板里没有对应的表单项**
（搜索区只有一个「白名单」输入框）⇒ 它们恒为初值 `null`，`customLoad` 里又被
`omit(form, ['question', 'answer'])` 删掉。所以发出去的只有
`order / orderField / word / pageNo / pageSize`，**没有** `question`/`answer`。
（"表单里有这个键"与"浏览器会发这个键"是两件事，这是最容易被生成器误推的一处。）

`word` 的匹配方式是**等值**：`<if test="params.word != null and params.word != ''"> and z.word = #{params.word}`
—— 不是模糊。想按关键字找，得给完整的词。

## 写链路

| 动作 | 请求 | 出处 | 撤销 |
| --- | --- | --- | --- |
| 新增 | `POST /admin-api/manager/sensitiveWordsWhitelist/add`，body `{"id":null,"word":"…"}` | `[mode]/[id].vue` 的 `customSubmit`（`form.id` 为空那一支） | `DELETE …/delete`，body `[新行 id]` |
| 修改 | `PUT /admin-api/manager/sensitiveWordsWhitelist/update`，body `{"id":…,"word":"…"}` | 同上（`form.id` 有值那一支） | 用**原值**再 `update` 一次 |
| 删除 | `DELETE /admin-api/manager/sensitiveWordsWhitelist/delete`，body `[id, …]` | `list.vue` 的 `deleteURL` + renren 通用删除（`deleteIsBatch: true`） | **没有** |

三条要点：

1. **删除是物理删除**，与「热门问题」那条**相反**：后端是
   `delete from zhdj_sensitive_words_whitelist where id in (…)`（`SensitiveWordsWhitelistMapper.xml`），
   删完就是没了、**没有复原接口**。所以新增的撤销虽然干净，但**删错了也救不回来**。
2. **后端会拦重复**：`checkWord` 里 `selectWord` 命中就抛业务错误「敏感词重复」。
   ⚠️ 源码写的是 `exception("敏感词重复", HttpStatus.SC_BAD_REQUEST)`，但那**不是** 400：
   它命中的是 `ServiceExceptionUtil.exception(String messagePattern, Object... params)`
   这个重载（`erp-common/…/ServiceExceptionUtil.java:39`），那个 `400` 落进了 `params` 里、
   一个字节都没用上 ⇒ **业务码是 500**（`INTERNAL_SERVER_ERROR`），与 conventions 第 9 条
   「业务冲突报 500」一致。别按"重复就是 400"去分类（第 9 条说得很清楚：不要指望靠 code 分类）。
   新增与修改都过这一关；修改时 `selectWord` 用 `id != #{id}` **排除自己**，所以"改成另一个词"
   不会被误判成重复。这一步只有提交时才知道，能力侧**不做预检**（后端没有这种接口）。
3. **列表的创建人/修改人来自 `hr_sys_user`**（`m1.real_name` / `m2.real_name`）——
   与热门问题那个「系统」占位不同，白名单没有 `create_id = 0` 的走法。

新建的 body 里 `id` 是 `null` 而不是"没有这个键"：页面写的是 `pick(form, ['id','word'])`，
`form` 初值 `{ id: null, word: '' }`，`pick` 保留 `null`。能力照抄。

## 删除之后不会立刻生效

后端靠一个**定时任务**重载敏感词库：`@Scheduled(initialDelay = 60000, fixedRate = 300000)`
（`SensitiveWordsWhitelistServiceImpl.refreshWordBs`，5 分钟一轮、且有 `needRefresh` 标记）。
所以"删掉一个白名单词"之后，`checkSensitiveWords` / 线上问答的过滤**要等一轮扫描才跟着变**。
SDK **不做等待、不做轮询**，如实透传——拿 `checkSensitiveWords` 当"删除是否生效"的证据会误判。

## 「校验」弹窗的其它行为

`components/check.vue` 里还有个 `watch`：用户一改「校验问题」输入框，`checkResult` 就被清空
（纯前端）。弹窗里没有别的请求。

## 真实验证（**读路径有基准，写链路未做**，如实记）

- **读**：列表请求有基准背书；`checkSensitiveWords` **没有**基准（基准里没这条，抓的时候没人开那个校验弹窗）。
- **写**：`add` / `update` / `delete` **一次都没发过**。原因是这一单的约束：派单明确
  「不授权用浏览器、不要 `bsk`、不要新建 smoke 脚本」，而取测试环境会话 token 的唯一受控入口是
  `smoke/with-portal-token.sh`（它起的正是 `bsk` 会话，`docs/conventions.md` 第 8 条）；
  基准也只是**只读抓取**（0 条非 GET）。所以这里没有"实际请求 / 响应"可记 —— 是**没发出去**。

要补的话按 `prepare → submit → cancel`：

1. `prepareCreateWhitelistWord({ word: 'SDK-TEST-白名单-<时间戳>' })`；
2. `createWhitelistWord(...)`；
3. `listWhitelist({ word: 'SDK-TEST-白名单-<时间戳>' })` 拿新行 id —— **这一步本身就是独立证据**
   （`word` 是等值匹配，正好用来定位；`add` 不回传 id）；
4. `cancelCreatedWhitelistWord(id)`，再查一次列表确认它真的没了（物理删除 ⇒ 列表就是判据）。

顺序上建议**先做只读的 `checkSensitiveWords`**（它不发写请求），再跑写链路。

## 基准兑现了什么 / 还剩什么没判据

**已落成真断言**（B2 组）：

- ✅ 无筛选列表请求与基准**逐字段一致**（URL、键序、`_t` 位置），且 `question`/`answer`
  **不在** URL 上 —— 这条之前是源码推导，现在是**实测**。
- ✅ 基准里这一页确实是**两条相同请求**（只差 `_t`）：能力侧按"存在一条相符的"断言，
  并单独钉住"这两条去重后只有 1 个 URL"。
- ✅ 不发 `module-type`；请求头逐键一致；这一页"页面自己的请求去重后只有那一条"。

**仍然没有判据**（留着 `it.todo`）：

- ❌ 带 `word` 的筛选请求形状（基准只抓了无筛选那一条）。
- ❌ `add` / `update` / `delete` 的 method / body（0 条非 GET）—— 尤其 `add` 里有没有 `"id":null`。
- ❌ `checkSensitiveWords` 的 method / body 形态（基准里没有这条）。
