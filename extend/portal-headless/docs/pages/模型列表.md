## 逐字段基准（**判据**）

```
GET /admin-api/manager/aiModelConfig/getByPage?order=&orderField=&pageNo=1&pageSize=20&_t=<ts>
GET /admin-api/ai-token/apply/pending-count?statisticsDimension=3&_t=<ts>
```

能力发出的两条与基准**逐字相同**（含键顺序、`_t` 排在最后），断言在
`test/ai-model.test.ts` 的 J 组。基准顺带证实了三件原先只是推导的事：

1. **`modelName` 初值 `null` 真的被丢掉**（URL 上没有 `modelName=`）—— 页面的

3. 基准里同一条列表请求出现了 **2 次** —— 点「查询」会重发一条只差 `_t` 的相同请求。

## ⚠️ `useJsonPost: true` 在这条实例上**是空标志**（真实的坑）

`api.js` 与两个 `.vue` 的写请求都带 `{ useJsonPost: true }`，看着像"要发一个特殊的
`Content-Type: application/json` 请求头"。**实际上 `platform.js` 从头到尾不读这个标志** ——
全仓只有 `zhdj-cms.js:46` 与 `zhdj-app-lay.js:38` 消费它（那两处会手动 `JSON.stringify`
并设 `Content-Type: application/json;charset=UTF-8`）。

`platform.js` 一侧真正发生的是：不设 `Content-Type`（`generateHttpHeaders()` 不设它），
body 是普通对象时走 **axios 自己的默认 JSON 序列化**；只有 `content-type` 已经是
urlencoded 时才 `qs.stringify`（`platform.js:48`）。

⇒ **照抄它的价值只在于"读页面时别以为漏了一个开关"**，SDK 侧不需要对应参数，
更不要把它建模成"发一个特殊请求头"。

## 空值：三个写载荷都会**主动丢掉空值**

额度 / 流速规则的载荷构造器（页面的 `buildQuotaManagementPayload` / `buildFlowManagementPayload`）
走 `cleanQuery`：把 `''` / `null` / `undefined` **整个键丢掉**，但保留 `0` 与 `false`。
所以：

- `quotaCheckEnabled` / `flowCheckEnabled` 是 `x !== false` ⇒ **不给就是 `true`**，只有显式 `false` 才关。
- `enabled` 页面**写死 `true`**。
- 档位字段是**互斥**的：只有 `ruleScope=1` 发 `memberLevel`、`=2` 发
  `targetTenantId`/`targetTenantName`、`=3` 发 `targetUserPhone`/`targetUserName`/`targetUserTypeName`。

模型的载荷则相反：页面 `pick` 出**固定的八个键**（`lodash.pick` 保留 `null`），
所以**新建时 body 的第一个键是 `"id":null`**；编辑态没重输 apiKey 时
`delete submitData.apiKey` 让**那个键整个消失**（其余键相对顺序不变）。

## 写链路（conventions 第 13 条：`prepare → submit → cancel`）

| 写面 | prepare（只读前置） | submit | cancel（撤销） | 站得住吗 |
| --- | --- | --- | --- | --- |
| 模型 新建 | `prepareSaveModel`（无前置读；给出 `warnings`） | `saveModel` → `POST add` | `cancelCreatedModel(modelName)` | **`add` 不返回新 id** ⇒ 只能按名字回查；重名时**拒绝而不是猜** |
| 模型 修改 | `prepareSaveModel`（先 `GET get/{id}` 读旧行） | `saveModel` → `POST update` | `restoreModel(previous)` | 只通过显式 `options.apiKey` 恢复密钥；详情可能返回明文，但 restore 不自动使用它，也不恢复测试元数据 |
| 模型 删除 | — | `deleteModel` | **无** | ⚠️ **撤不掉**，且被「模型选择」引用的模型后端直接拒 |
| 额度规则 新建 | `prepareSaveQuotaRule` | `saveQuotaRule` → `POST create` | `cancelCreatedQuotaRule(id)` | 可行（`create` **返回新 id**） |
| 额度规则 修改 | 同上（先 `GET quota-rule/get?id=`） | 同上 → `POST update` | `restoreQuotaRule(previous)` | 可行（`get` 回完整 RespVO） |
| 额度规则 删除 | — | `deleteQuotaRule` | **无** | ⚠️ 撤不掉 |
| 流速规则 新建 | `prepareSaveFlowRule` | `saveFlowRule` → `POST create` | `cancelCreatedFlowRule(id)` | 可行 |
| 流速规则 修改 | 同上 | `saveFlowRule` → **`PUT update`** | `restoreFlowRule(previous)` | 可行 |
| 流速规则 删除 | — | `deleteFlowRule` | **无** | ⚠️ 撤不掉 |
| 申请处理 | `prepareHandleApply`（**纯函数**：旧状态就在你手上那一行里） | `handleApply` | `cancelHandledApply(id, previousStatus)` | 可退回原状态；"一键填写"顺手建的规则要**另外删** |
| 一键填写 | — | `fillApplyWith*Rule`（**两步真写**：先建规则、再把申请标成已填写） | 删规则 + `cancelHandledApply` | 两步都不幂等 |

### 前置条件（后端代码证实的硬校验）

- `add`：`modelName` / `description` / `apiUrl` / `apiKey` 四条 `isBlank` 检查（缺一条 400
  「请求参数缺失:x」）；**`apiUrl` 必须以 `/chat/completions` 结尾**（"兼容模式下…"）。
  本能力把前四条做成硬校验，**`/chat/completions` 那条只放进 `prepare` 的 `warnings`**
  （它带着"兼容模式"的措辞，是否对所有模型成立没有实测，硬拦会把合法调用挡在门外）。
- `update`：`id` 必须非空；**不**做那四条 isBlank 校验。
- `delete`：`isConfigSelected(id)` 为真 ⇒ 500「当前配置已经被选择，请勿删除」。
- `quota-rule/create`：`modelId`/`ruleScope`/`totalQuota`/`resetCycle`/`shortageStrategy`/`startTime`
  全是 `@NotNull`，`totalQuota` 还 `@Positive`。
- `flow-rule/create`：`tokenLimitPerMinute`/`maxTokenPerRequest` `@NotNull @Positive`，
  `exceedStrategy` `@NotNull`。
- `apply/handle`：`id` / `status` `@NotNull`，且要 **`ai-token:apply:handle`** 权限
  （`apply/page` 要 `ai-token:apply:query`）。

## ⚠️ 三处前后端对不上（都以"真机上再定"结尾）

1. **申请处理的状态码**：页面用 `{pending:0, ignored:1, filled:2, rejected:3}`
   （忽略发 `1`、一键填写发 `2`）；后端 `AiTokenQuotaApplyStatusEnum` 只有
   **`PENDING(0)` / `REJECTED(3)` / `HANDLED(4)`**，而 `AiTokenQuotaApplyHandleReqVO.status`
   带 `@InEnum(…)` ⇒ **1 和 2 很可能被校验拒掉**。本能力放行 0..4 全档、**照抄页面的取值**，
   这是历史实现的透传行为；本轮固定后端 `test/test@dcb3f360194` 复核仍有冲突，SDK描述不宣称1/2成功。
2. **`targetUserId` 后端没有这个字段**：页面的两条"一键填写"链路发的是
   `targetUserId`（`buildQuotaRulePayload` / `buildFlowRulePayload`），而后端两个 SaveReqVO
   里都**没有**它（全 `erp-module-ai` 搜 `targetUserId` **0 命中**）；个人规则的命中判据是
   `targetUserPhone + targetTenantId`（`AiTokenManagementServiceImpl:1524`/`:3024`）。
   ⇒ 个人档"一键填写"很可能**认不到人**。能力照抄页面并**在返回里带 `warnings`**；
   要确保落到人请走 `saveQuotaRule` / `saveFlowRule`（那边发的是 `targetUserPhone`）。
3. **`flow-rule` 的参数表里有 `targetUserId`、后端 VO 里没有** —— 同上，页面也没传它。

### `ai-model-list`

按名称分页查询全部模型配置，取得管理ID与当前可用状态。

使用：查找模型或排查配置；选择实际可用候选用available-list。 行为：read。入口：`invoke('ai-model-list', args)`。

- 包括不可用配置；SDK不做白名单脱敏，当前后端列表可能包含apiKey字段，不展示或记录密钥。

参数：

| 参数 | 类型/格式/条件 | 含义与来源 |

### `ai-model-quota-rule-save`

使用：用户明确配置额度限制；准备草稿与读取旧值用prepareSaveQuotaRule。 行为：write。入口：`invoke('ai-model-quota-rule-save', args)`。

- 有id更新、无id新建；create/update均POST。
- ruleScope仅发送对应目标字段：1会员等级、2租户ID/名、3用户手机号/名/类型，其余目标键丢弃。

- 只POST申请状态；“已填写”状态本身不会分配额度，真正一键填写是另一个SDK方法。
- 后端只接收0待处理/3已驳回/4已处理；页面与SDK历史按钮传1忽略/2填写，需要部署核实。
- rejectReason只有status=3时写入。

参数：

| 参数 | 类型/格式/条件 | 含义与来源 |
| --- | --- | --- |
| `id` | number；必填 | 申请ID；来源：ai-model-apply-record-list.list[].id |
| `status` | number；必填 | 目标申请状态，当前后端枚举0/3/4；历史前端1/2尚未部署验证；来源：明确业务意图与部署确认；不能按旧options盲目发1/2；SDK仅检查数字非空，可发4；当前后端0/3/4，前端历史1忽略/2填写冲突仍需部署核实，不能宣称1/2有效 |
| `rejectReason` | string；可选 | 驳回原因（后端只在 `status=3` 时落库）；来源：用户明确的业务条件；枚举按本参数options填写 |

SDK返回：`boolean`。false不可当成成功；异常由请求层抛出。

| 字段 | 类型/可空/可缺 | 含义/状态 |
| --- | --- | --- |
| `$` | boolean | 后端是否成功的data值；还需回查目标记录核实 |

消费：回查申请列表的同id状态和驳回原因；不能把true当已增加Token。

- required：写前记录旧status；直接调用 `aiModel.prepareHandleApply`
- required：写后按模型/用户查回同id并核实目标状态；调用 `ai-model-apply-record-list`
- cancel：需要恢复状态时传旧previousStatus；不会删除另建规则；直接调用 `aiModel.cancelHandledApply`

完成条件：同id申请状态已独立核实，业务要求的额度配置需单独验证。

失败/防重：本族写入没有SDK requestId防重，超时先回查，不盲目重发。 成功回执不代替独立核实；删除不可恢复，恢复旧配置是另一次真实写入。 401或403先核对会话/租户及实际动作权限；菜单可见性不是权限裁决。 参数和形状错误保留原始消息；空页与请求失败不能混同。 无自动幂等保护；发生不确定结果时先按目标ID/业务键读取确认。

具体缺口：当前前端状态1已忽略/2已填写与后端仅0待处理/3已驳回/4已处理仍冲突；缺部署环境证据，不能宣称1/2可成功。

### `aiModel.fillApplyWithQuotaRule`

把提升申请期望值创建为额度规则，再把申请标成已填写。

使用：用户明确要求一键配置，且已验证目标作用范围与部署状态。 行为：write。入口：`sdk.aiModel.fillApplyWithQuotaRule(...)`。

- 两次独立真写，非事务：createRule→handle(status=2)；第一步成功第二步失败时有部分写入。
- 个人目标旧payload使用targetUserId而后端只接targetUserPhone，建议改用已注册规则save和明确手机号。
- skipApplyStatus只跳过第二步，不是prepare或dry-run。
