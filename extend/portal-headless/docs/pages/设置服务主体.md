# 设置服务主体

## 1. 能力定义

- 菜单归属：门户 → 系统设置 → 销售设置 → 设置服务主体。
- 页面路径：`/dashboard/sale/setting/service-subject/list`。
- 页面权限：`/dashboard/sale/setting/service-subject`。
- module-type：`60`（销售管理）。
- 请求实例：Portal platform（`VITE_ZHDJ_PLATFORM_API`）。
- 动作权限：新增 `sales:setting:service-subject:create`，编辑 `sales:setting:service-subject:edit`，删除 `sales:setting:service-subject:delete`。

对应 SDK 能力：

| capability | 作用 | 写入 |
| --- | --- | --- |
| `sale-service-subject-list` | 查询列表 | 否 |
| `sale-service-subject-get` | 读取编辑页表单底稿 | 否 |
| `sale-service-subject-prepare-create` / `sale-service-subject-create` | 校验并新增 | 后者是 |
| `sale-service-subject-prepare-update` / `sale-service-subject-update` | 校验并编辑 | 后者是 |
| `sale-service-subject-prepare-remove` / `sale-service-subject-remove` | 确认并删除 | 后者是 |

## 2. 参数契约

### 列表

Portal 列表使用公共 `useListPageModule`，因此请求实际发送：

```text
GET /admin-api/system/hr-role/page
```

```json
{
  "order": "",
  "orderField": "",
  "pageNo": 1,
  "limit": 20
}
```

这里的分页键是 `limit`，不是 `pageSize`；页面默认每页 20 条，控件值为 10、20、50、100。页面列读取 `name`、`customerType`、`updateTime`，操作使用 `id`。

### 编辑加载

编辑路由使用 `useFormPageModule({ objectURL: '/admin/dict/type' })`，所以实际请求为：

```text
GET /admin-api/dict/type/{id}
```

编辑表单字段为 `parentId`、`name`、`customerType`，三项均由 Portal 的 `required` 规则校验。当前两个选择框的 `options` 都是空数组；SDK不凭空生成组织或客户分类候选，也不把其它页面的字典值硬套进来。

### 新增和编辑提交

Portal 表单的 `customSubmit` 对新增、编辑都调用同一个请求：

```text
POST /admin-api/customerType
```

新增正文：

```json
{
  "parentId": 3,
  "name": "示例服务主体",
  "customerType": "1"
}
```

编辑正文额外带当前目标 `id`，仍然是 POST，不是 `PUT /admin-api/system/hr-role/update`：

```json
{
  "id": 7,
  "parentId": 3,
  "name": "修改后的服务主体",
  "customerType": "1"
}
```

SDK 的 `prepare → create/update → list` 链只校验 Portal 已知的三项必填字段和正整数 ID，不自行增加长度、字典枚举或组织树规则。空回执不包含新建 ID，也不证明列表已经更新。

### 删除

删除按钮受 `sales:setting:service-subject:delete` 控制，实际请求为：

```text
DELETE /admin-api/system/hr-role/delete?id={id}
```

删除前必须经过 `prepareRemove` 和用户确认；成功或超时后刷新列表核对目标 ID。

## 3. 逐字段基准

| 字段 | 页面含义 | 空值/归属 |
| --- | --- | --- |
| `id` | 当前服务主体记录主键；编辑和删除目标 | 必须来自当前列表或当前编辑路由，不能用名称代替 |
| `parentId` | 上级组织选择值 | Portal 只校验必填；列表可能不返回，不能猜测 |
| `name` | 服务主体名称 | Portal 只拒绝空字符串；保留非空输入原值 |
| `customerType` | 客户分类选择值 | Portal 只校验必填；当前选项为空，不能自行映射其它字典 |
| `updateTime` | 页面更新时间列 | 原值展示；可能缺失或由后端返回 `updateDate` |

## 4. 操作步骤与证据

1. 查询列表并从同一条记录取得 `id`。
2. 新增时填写三项表单；编辑时先按同一 `id` 读取 `/admin-api/dict/type/{id}`，再确认修改后的三项值。
3. 明确确认后调用对应写能力；取消只丢弃准备草稿，不发请求。
4. 写请求完成、超时或响应丢失都刷新列表回查；不能把空回执当成业务结果。

Portal 源码明确证明了列表/删除的 `hr-role` 请求，以及表单的 `dict/type`、`customerType` 请求。固定 `test/test` Java 源码中的 `HrRoleController` 只提供 `page/get/delete` 等 HR 角色路由，`HrRoleSaveReqVO` 没有 `customerType` 字段；当前未找到 `/admin-api/customerType` 的对应 Controller/DTO。因此本页 SDK 保留前端实际请求链，并在 AI 描述中标出该后端证据缺口，未把它误报成标准 HR 角色保存能力。

本节点尚未在真实测试环境执行列表、编辑加载、新增、编辑、删除及写后回查；测试覆盖的是源码片段、请求形状、Portal 表单必填规则、权限元数据和坏参数反证。
