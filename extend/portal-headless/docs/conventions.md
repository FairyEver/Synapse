# 硬约束与约定

这一页只放**会被忘记、而且忘了代价很大**的规则。规则来自实测或用户明确要求，出处随条目注明。
改代码前扫一眼；违反其中任何一条，测试或线上行为会以不显眼的方式出错。

## 请求层

**1. `module-type` 必须按页面推导，不能省。**
它只影响后端的**数据范围**（数据权限），不影响权限码校验。**不传它，后端会取该用户全部模块数据权限的并集** —— 这是放大，不是缩小。（F19 / 决策 D34）

**2. 算不出 `module-type` 时，就不发这个头。**
约 42% 的页面在规则表里匹配不到，浏览器在这些页面上同样不发。这是刻意与浏览器一致，不是缺陷。（§1d / D34）

**3. `tenant-id` 必须显式传。**
后端在部分路径（如登录 SQL 的 `order by id desc limit 1`）省略时会**静默选错租户**，不报错。（F26）

**4. 列表页要带 renren 的默认空值参数。**
浏览器发的是 `order=&orderField=&name=&pageNo=…&pageSize=…`。少发会导致请求与浏览器不逐字段一致。（`baseline/meeting-room-page.browser.json`）

**5. 一个 axios 实例 = 一个用户的一个租户。**
凭据在 `createPortalHttp(config)` 创建时绑定，拦截器闭包读的就是那份 config，没法靠单次请求换人。
多用户必须走 `createPortalServer` 的「一份会话一份请求函数」。（`src/session/portal-http.ts`）

## 凭据

**6. 用的是「会话 token」，不是「私人令牌」。**
私人令牌走 `access_token` 头，且**只能调 `system_open_api` 白名单里登记过的接口**，未登记一律 401。
用它做无头会把范围锁死。（F6）

**7. 改密码不会撤销已签发的 token；用户被停用后最坏仍可用到 JWT 过期（7 天）。**
这是已接受现状（D17），SDK 侧不做额外补偿。**不要**假设"断开连接"能立刻生效。（F21）

**8. 抓基准绝不提取凭据；冒烟走 `smoke/with-portal-token.sh`（唯一例外，且只对测试环境）。**
`tools/baseline/install-hook.js` 的脱敏是**在页面内**完成的（token 头离开浏览器前就被替换成 `<redacted>`），
所以**抓基准不需要凭据——这条仍然没有例外**。

冒烟要打真实后端，需要一次会话 token。用户 2026-09-20 明确授权本项目可以跳过 browser-skill 那条
「绝不从页面提取凭据/cookie/token」的规则，**范围只有测试环境**：

- 用 `smoke/with-portal-token.sh <命令>`。它起一个 `bsk` 会话 → 打开 `webtest01.wodecorp.cn/portal.html`
  → 读 cookie `hr-0.0.0-token` 与 `hr-0.0.0-tenant`（`app/portal/utils/system.js:29` 的 `getToken()`
  读的就是前者）→ 注入环境变量 → 执行命令 → 收会话。
- **不要手工抄 token**：既会因为过期反复返工，也容易在复制粘贴里漏进文件、日志或提交。
- token 只进那个进程的环境变量：**不落盘、不打印、不进任何产物或提交**。
- **生产环境不适用**；其余 17 个实例的 host 同样不适用。
- 这条授权**不要扩大**：不是"现在可以随便抓凭据了"，是"测试环境冒烟这一条路有个受控入口"。

## 错误与失败

**9. 后端的失败信号区分度很差，不要指望靠 code 分类。**
业务冲突报 **500**，令牌类的四种失败（过期 / 未登记 / 无 scope / 不存在）**塌缩成同一个 401「账号未登录」**。（F8 / F16）

**10. `DescribeResult` 是带判别字段的联合类型。**
先判 `ok`，再取 `llmToolId` / `consume`。用 `expect(x.ok).toBe(true)` 不会让 TypeScript 收窄。

## 参数

**11. 长选项参数必须先要关键字。**
人员候选有几千个。Portal 页面自己用 `simple-page?pageNo=1..9&pageSize=500` 全量拉（实测约 4500 人），
**无头不能照抄** —— 会冲掉调用方上下文。SDK 的 `searchUsers()` 会直接拒绝无关键字的调用与 `pageSize=-1`。（D6 / H35）

**12. 时间段的分钟只能是 00 或 30，秒只能是 00。**
来自前端 `disabledTime` 与后端 `validateTime`，两条都有。（`assertTimeSlot`）

## 写操作

**13. 写链路是两步：`prepare()`（只读）→ `submit()`（真写）→ `cancelReservation()`（撤销）。**
`prepare` 问后端"这次需要人工指定哪些审批人"，会议室流程实测返回 0 个节点，但**不要假定为空** ——
页面提示流程可能随填写内容变化。（F14）

**14. 后端零幂等，而 D4 是写操作全部放开。**
AI 超时重发 = 重复单据。见 `src/idempotency/`。

## 目录与可见性

**15. 菜单树不是权限裁决。**
实测：某账号的 `/dashboard/meeting-room/list` 不在它的 `nav?project=2` 里，但该能力是可调的。
拿菜单树预判 403 会**把能用的能力藏起来**。它的定位只能是"下发面收敛"。（`src/catalog/visibility.ts`）

**16. 菜单节点的 `url` 恒为 null**，页面路径实际在 `permissions` 里，且**从不是逗号分隔**（2848 个节点里逗号 0 次，与 DTO 注释不符）。
连接键必须是「目录 `permission` ↔ 菜单 `permissions`」。（`baseline/menu-nav.sample.json`）

**28. Portal 里被注释掉的东西不算数——不推导、不搬进 SDK。**
菜单文件里 `// { path: '/dashboard/course/live-course/list', … }` 这样的行**不是菜单项**。
那一页的路由还在、按 URL 直接打开也能正常渲染，但侧边栏里没有它 ⇒ **用户到不了这一页** ⇒
SDK 里也不该有它。**"能渲染"不等于"用户能做的事"。**（用户 2026-09-21 定的规则）

这条的代价是实测出来的：生成器此前**逐行正则扫菜单文件、不看注释**，
把全仓 **44 条被注释掉的菜单项**（38 个页面 + 6 个 iframe）收进了
`generated/page-catalog.json`（1019 → 975）。已修：`tools/generate/generate.mjs` 的
`blankComments` 先把注释**抹成空格**再扫——行数不变，因为 iframe 的 id 是
`sha1(相对路径#行号#标签)`，删行会让后面所有 id 漂移。

同一条规则适用于**人工维护的表**：`src/catalog/aliases.ts` 里指向这些页面的 target，
以及专门招呼它们的词条（如「直播课程」），一并去掉。留一个指向"什么都没有"的词条，
会把用户的问题**静默路由到隔壁页面**（问"直播课程"被答成视频课程）——那正是这个仓库
最不想要的那种"不报错但是错的"。（`src/capabilities/study-course.ts` 文件头）

## Git（并行工作时最容易出事）

**17. 只提交自己改的东西，禁止 `git add -A` / `git commit -a`。**
这个仓库经常有多个 Agent / 子代理同时改。`git add -A` 会把**别人此刻改了一半的东西**卷进你的提交，
对方的下一轮工作会莫名其妙"已经被提交了"，而你可能提交进去一个构建不过的状态。
**一个阶段做完就提交，别攒**——攒着的工作区在并行场景下会被搅在一起，最后分不清谁改了什么。

同一个文件被两个会话同时改时用 hunk 级暂存：`git diff -- <文件> | git apply --cached --recount`。

**18. 子代理不自己提交。**
派单时要明确写「不要运行任何会写 git 的命令」，由派单方复核后统一提交。
派单方提交前要逐条复核产出——**它说"全绿"不等于全绿**。

**19. 重建生成物前先确认工作区里没有别人的在途改动。**
生成物是从**整个工作区**构建的，但一次提交只含一部分文件。原 `.githooks/pre-commit`
为此设过并行安全闸：检测到 `src/` 或 `tools/generate/` 下有未暂存改动时就**跳过重建**，
而不是把别人的在途工作卷进你的提交。该钩子已随迁入 Synapse monorepo 移除，
这条约束现在靠人工遵守——工作区混着别人的改动时，不要跑 `pnpm generate` 再提交生成物。

## 工程

**20. 不引入新的运行时依赖。** 工具脚本也一样（现有生成器全是零依赖的纯 Node 脚本）。

**21. 改了能力定义就要重新生成文档。**
`pnpm docs` 会重建规格与报告；`pnpm docs:check` 是漂移门禁，生成物与 HEAD 不一致就失败。
原 pre-commit 钩子会自动跑它，该钩子已随迁入 Synapse monorepo 移除，现在需手动执行。

**22. 测试必须在坏的时候会红。**
写完之后故意改坏一次确认它变红，再改回来。项目里已经因此抓出过好几条"恒真"的假测试。
TTL 之类的不要用真实 sleep 测，用可注入的时钟。

**23. 生成物的新鲜度判据是内容哈希，不是时间戳。**
拿 `generatedAt` 当信号会导致"只要重新生成过就被判为过期"——这个坑踩过两次
（漂移门禁、别名推导器各一次）。

## 请求层（续）：页面用哪个 http 实例

**24. Portal 前端不止一个 axios 实例；「页面 → 用哪个实例」是请求层的输入。**
`app/portal/utils/http/` 下 16 个文件、**17 个实例**（`zhdj-cms.js` 一个文件导出 `http` 与 `httpLay` 两个绑定，
`:106-107`）。它决定四件事：**打哪个 baseURL、路径补不补 `/admin-api`、每页条数叫 `pageSize` 还是 `limit`、
发哪些请求头**。"一个实例"的单位是**导出的绑定**，不是文件。（`src/context/http-instance.ts` / `src/context/README.md`）

**25. 只有 `platform.js` 补 `/admin-api`；只有 `sale.js` 改分页参数名。**
补前缀的三个边界条件缺一不可（`platform.js:18-20`）：**必须以前导 `/` 开头**（漏写斜杠的相对路径原样发出）、
命中 `/admin-api` `/adminmanage-api` `/mall-manage-api` 三个之一就**透传不补**、判断发生在 baseURL 拼接之前。
`sale.js:38-41 / 48-51` 把 `pageSize` 改名成 `limit`（params 与 data 各一处）。
全局默认分页名是 **`pageSize`**——`common/libs/renren/config.js:11` 写的是 `limit`，被 `app/portal/main.js:48` 覆写掉了。

**26. 页面没有任何 http 声明时走 `platform.js`；声明了却推导不出来时**拒绝发请求**。**
前者是推导结论（`app/portal/main.js:42-48` 把 platform.js 注入成全局默认），不是猜测。
后者与第 2 条（D34）**刻意相反**：`module-type` 算不出就不发这个头是忠实（浏览器同样不发），
而实例算不出意味着**走错实例 = 打到错的 URL**，失败方式往往只是个 404 或字段不同的 200——静默且难查。
所以 `src/call.ts` 走失败关闭，抛 `HttpInstanceResolutionError`；唯一的退路是显式
`onUnresolvedInstance: 'assume-default'`（`src/context/http-instance.ts` / `src/call.ts`）

**27. 实例的 baseURL 必须由调用方显式给，SDK 不替「同 host 不同前缀」的范围决策做主。**
测试环境下 `sale` / `platform-mall-admin` / `mall-app` / `crm` 与 `platform` **同 host、不同前缀**
（`build/env/.env.build.test`），另外几个是不同 host。`createPageCall` 的 `options.baseUrls` 里没配的实例，
对应页面一律拒绝发请求，而不是拿默认 baseURL 去凑。（`src/call.ts`）

**30. 响应包络按实例自己的规则拆，四档各不相同，不能拿 `ret === 'SUCCESS'` 去套。**
`src/http/client.ts` 的 `applyEnvelope()` 逐字复刻各实例响应拦截器的原文：

| 档 | 实例 | 判据 |
| --- | --- | --- |
| `portal-standard` | 当前归入该档的 13 个实例 | `ret !== 'SUCCESS'` 即失败 |
| `smart-layer` | `smart-layer-admin` / `smart-layer-app` | **不看 `ret`**；`code === undefined` 放行、`code !== 200` 失败；没 `data` 时退到 `pages` |
| `zhdj-sms` | `zhdj-sms` | `ret` 失败**且** `code !== 200` 才失败（`code === 200` 时**不抛**） |
| `mall-app` | `mall-app` | `Number(code) !== 0` 即失败 |

三处最容易照抄错：**`smart-layer` 完全不看 `ret`**；`zhdj-sms` 在 `code === 200` 时不抛；
`smart-layer`/`zhdj-sms` 最后一句是 `return data ? data : pages`（`pages` 是第二选择，不是摆设）。
出处与反证：`test/http-envelope.test.ts`（26 例；另记一处**等价变异** ——
`zhdj-sms` 那两段对调后穷举 7 种组合行为一致，所以"谁先谁后"不是契约）。

**顺带一条同族的坑**：`tokenInParams` 的实例，`token` 必须排在 `_t` **之前**
（各实例拦截器逐字写着 `{ ...params, ...{ token }, ...{ '_t': … } }`）。
这一族是 axios 默认序列化，**对象键序就是 URL 上的顺序** —— 写反了与浏览器不逐字一致。
（2026-09-21 由讲师管理那条基准抓到，`client.ts` 已修正。）

**28. 最容易漏的声明形式是「`useListPageModule` 本身从 preset import」。**
`common/libs/renren/presets/{product,platform}/list.js:3` 把实例写死，调用点上**一个字都看不到 http**。
其余易漏形式：简写属性 `{ http }`、`as` 别名、import 路径省略 `.js`、局部常量转发。
`useListPageView` 只管布局，不决定请求的 http。（`src/context/README.md` §2b，`test/http-instances.test.ts`）

**29. 同一次页面操作里可能有多个实例。**
实测 262 个页面 import 了非默认实例，其中 21 个在走默认实例的列表请求之外还直接打另一个实例。
所以 `httpInstance` 是**逐请求**的输入（`PortalRequestConfig.httpInstance`），页面的推导只给该页列表请求的默认值。
`/dashboard/frame/**`（iframe 内嵌的独立子应用）的实例**推导不到**，必须显式指定。（`src/context/README.md` §2c/§3）


**31. 「从源码推导」的前提是**检出那一版就是线上那一版** —— 这条前提会不成立，必须用基准兜住。**
2026-09-21 实测：`Projects_Js` 的工作区停在特性分支
`fix/portal/4.6.3.22-修改绩效公式配置错误权限声明`，**落后 `origin/test/portal/main` 435 个提交**。
后果：「薪酬结构」与「标准」两页的列表接口，本地源码写的是 `…/page` / `…/standList`，
而**部署到测试环境的版本用的是 `…/treePage`**（`git log --all -S treePage` 找得到那两个提交、
后端 `KpiSalaryStructureController:139` 也有）。子代理按本地源码推，两条接口都是错的。

**所以：源码推导是**第一步**，不是判据。** 判据是浏览器基准 ——
冲突时一律以基准为准，并在文件里注明"本地检出与线上不一致"。
反过来，**没有基准的页面的契约只能算推断**，文档里必须写清楚（别把"推得自洽"当成"验证过"）。
（同一天还有一条同源的教训：一个子代理看到后端已有 `treePage` 却判断"页面还没接" ——
它的推断在它读到的那份源码上是对的，**缺一份"线上是什么"的独立证据**。）

**顺带一条方法学结论（抓基准时踩到的）**：`install-hook.js` 装在 SPA 里、**跨 hash 导航不卸载**，
所以**先访问的页面会把模块级状态漏给后访问的页面**。实测：「已办任务」页因为排在「待办任务」之后抓，
发的是待办页的 `finished=1`（那个共享组件的 `stateCache` 不按路由分）。
⇒ **同域多页要么每页一个新会话，要么按顺序复核**；拿不准时用新会话直开那一页复抓一次。

2026-09-22 起，本 SDK 一律从下面这两个检出读源码，**分支是钉死的，不要换**：

**为什么值得单列一条**：第 31 条记的那次事故，根因就是"读的那一版不是线上那一版"——
子代理按一个落后 435 个提交的检出，推出了两个错接口。现在那两页的源码在新检出里已经是线上版，

**两条随之而来的口径：**

1. **生成物里烘的 `portalRepo` 不是版本锚点。** 它只回答"哪台机器的哪个目录"，
   改路径、换机器都会变；`generated/page-catalog.json` 里也**没有**任何 Portal 版本信息。
   版本锚点只有 `git rev-parse --short HEAD` —— **随用随记**，写进当次文档，别指望从生成物里反推。
2. **`src/invalidation/` 里的 `repo` 字段是"证据出处"，不随来源切换改写。**
   那 6 条写 `Mall_Platform_Java_Dev` 的规则，行号是在旧 `dev` 分支上读的；
   改成新目录名等于**声称**在新检出上读过——那是把声明写成结论。要改标签，先在新检出上真的复核一遍。

## AI 说明契约

**33. AI 说明是功能交付的一部分，必须与实现同时设计、修改、验证和提交。**

（用户 2026-09-22 明确要求：防止后续 AI 新增、修改功能时只改代码，不改介绍信息；设计 A6 / D14。）

**固定格式与逐字段规则见 [SDK 面向 AI 的描述规范](ai-description-contract.md)**，权威类型为
`src/catalog/ai-contract.ts`。该规范明确页面/能力/方法分层、输入输出字段、路径与映射语法、
枚举/单位/空值/动态结构、步骤与失败规则；标准样例在 `docs/ai-description-examples/`。
新增字段须同步类型、规范与检查器，不允许只在某一份提示词里自创格式。

适用于所有新增、修改、删除的能力，包括页面能力、基础能力、批量生成能力与公共目录协议。
这里的「提示词」是 **SDK 返回给 AI 的业务说明和使用契约**，允许用结构化字段表达，
不要求拼成一篇长提示词。只有标题、参数名或通用模板不能替代能力自身的业务语义。

### 范围以 Portal 页面功能性和可见性为准

用户 2026-09-22 明确：**前端没有显示的数据，SDK不需要提供；SDK只负责与Portal页面功能性和可见性对齐。**

- 以对应 Portal 页面及其可达弹窗/详情/编辑操作实际使用的字段、展示转换、按钮条件和权限范围为依据；不能把其他应用同名字段或后端DTO全集当成本页交付范围。
- 页面操作所需的内部ID、候选关联值、状态和提交参数仍属功能契约，不能因不直接显示就删掉，导致页面动作无法完成。
- 不显示且不参与页面操作的后端扩展数据不要求逐字段补语义；已有透传为保持兼容可保留，但必须明确不属于页面消费契约，不引导AI展示、推断或操作。
- 页面原值展示且没有单位/换算时，SDK说明同样原值展示，不猜单位；不因页面本身没有给出的单位或扩展模型阻塞页面等价交付。页面有格式化、枚举标签或单位则必须对齐。
- 写入完成、错误提示和按钮保护按页面真实行为描述。页面没有的跨账号验证、全子树历史恢复、全局无引用证明不是额外交付门槛；超时仍需如实报告不确定，不能编造成功。页面已有的保护条件不得省略。
- 前后端冲突若导致页面可见动作不能执行，记录具体页面功能差距；不能把该动作排除成不需要的功能，也不能擅自映射成另一个动作。

### 每个能力必须交付的说明

| 内容 | 必须回答的问题 |
| --- | --- |
| 用途与边界 | 做什么、什么时候用、与相近能力如何区分；是只读查询、提交前准备还是真实写入，有哪些前置条件与副作用 |
| 调用与输入 | 真实调用入口、参数含义、必填与条件必填、格式/单位/范围/默认值/枚举；ID 从哪里取，长选项如何搜索，不能猜参数 |
| 返回契约 | SDK 最终返回值的结构与字段含义，含嵌套结构、标识符、状态枚举、时间/金额单位、可空性、分页与空结果；不要把后端原始包络当成 SDK 返回值 |
| 数据消费 | 哪些字段用于展示、筛选、判断或后续调用，适用的筛选/汇总规则与数据范围；明确上游字段到下游参数的映射及转换 |
| 后续步骤 | 正常业务顺序、分支触发条件、需要用户补充的信息与完成判据；区分必须下一步、可选操作和撤销，不能把撤销写成成功后的必做步骤 |
| 失败处理 | 已知校验失败、权限不足、能力不支持等结果意味着什么，下一步如何处理；写入的重试/防重约束、结果不确定时如何核实 |

确实没有下游的能力，应明确说明结果如何交付及何时结束；没有返回数据的操作，应说明成功回执与验证方式。
不适用项可以明确说明不适用，**不得为了填满字段编造业务规则、返回字段或未实现能力**。
未经验证的内容必须标明依据、推断与缺口；关键语义仍为 `unknown` /「未登记」时，不能宣称该能力已完整交付。

### 必须接到 AI 实际能读到的入口

- 通过 `catalog.describe(capabilityId)`（也接受 `-llm` 后缀）或该能力明确提供的 SDK 下钻入口返回说明。
  动态表单等需运行时信息时，必须给出真实可调用的入口、所需参数和后续消费规则。
- **不得仅写在源码注释、`docs/pages/*.md` 或本地提示词文件里，也不能只返回文档路径。**
  AI 只拿 SDK 输出，也应能知道如何调用及如何消费结果，不依赖读取本仓库。
- 优先复用能力定义和目录层已有说明机制，维护一份权威定义，再生成或装配对外描述。
  若现有类型或 `describe()` 无法表达所需语义，应在本次任务中补齐契约与接线，不能用通用文案代替。
- 返回结构必须来自实现与验证证据。仅凭 `pageNo` / `pageSize` 推测分页结构不算完成；
  `consume` 只有「不要全量拉取」等通用提醒，也不算已说明这个能力的数据消费方式。

### 修改和删除时的联动

- 改用途、参数、返回值、校验、状态、副作用或操作流程时，同步更新受影响能力的描述、候选来源、字段映射、
  上下游步骤、示例、页面文档与相关测试；纯内部变更也须核对说明是否仍准确。
- 重命名或删除能力/字段时，同步清理引用它的目录链接、lookup、别名及文档示例，不能留下失效指引。
- 修改公共请求层或描述协议时，按实际影响面检查能力说明；不要把某一能力的规则机械套给所有能力。
- 历史缺口在本次触及的能力范围内补齐；不要擅自扩成全库重写。发现范围外缺口如实报告。

### 完成前的验收

1. 实际调用本次能力的描述入口，以「AI 只看到描述与业务结果」为前提，逐项检查以上说明。
2. 契约测试断言 **SDK 对外返回的说明**，覆盖关键参数语义、返回字段、消费映射与步骤条件；
   与业务响应夹具/基准核对。不能只断言 `ok`、标题非空、字段存在或复制实现生成快照。
3. 做有意义的反证：例如删除关键返回字段说明、写错状态含义或把上游 ID 指向错误参数，
   确认对应测试变红，再恢复；按第 22 条记录反证结果。
4. 同步页面文档，能力或生成器改动后运行 `pnpm run docs`；代码、说明与相关测试同一工作单位提交。
5. 交付报告写清已验证的说明及未验证/缺失部分。**页面计入覆盖、请求成功、执行测试全绿，都不能替代 AI 说明验收。**

`pnpm ai:check` 构建后检查结构、注册覆盖及可验证引用，`pnpm ai:check:complete` 另报告描述缺口和不完整项。
检查器回归见 `test/ai-contract-schema.test.ts`，样例回归见 `test/ai-description-examples.test.ts`。
检查不能证明自然语言语义正确或线上行为已验证；现有覆盖统计和提交钩子也不会自动强制所有说明完整。
提交前须报告本次受影响范围的检查结果与范围外历史问题，不得用空模板消除问题或把人工规则说成自动保证。
