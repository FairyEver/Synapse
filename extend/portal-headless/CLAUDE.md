# Portal Headless SDK

让 AI 能以用户本人的身份驱动 Portal（`CodeReview_Projects_Js` 的 `app/portal`，固定分支 `test/portal/main`）的服务端 SDK。
它不是 HTTP 服务，是一个 TypeScript 包；能力的来源是**从 Portal 前端源码推导 + 真实页面观察**，
不是手写接口列表。

## 先读什么

| 你要做的事 | 先读 |
| --- | --- |
| 搞清楚整体设计、每个决策的理由 | `docs/design.md`（**权威设计文档**，含全部决策记录与实测数据） |
| 写代码（任何改动） | `docs/conventions.md`（硬约束，**违反其中任何一条都会以不显眼的方式出错**） |
| 新增或修改能力、参数、返回数据、AI 说明 | `docs/ai-description-contract.md`（固定格式、逐字段语义、路径/映射语法、标准样例与检查要求） |
| 调用这个 SDK | `docs/usage.md`（用例；每个用例都有测试钉住） |
| 知道现在做到哪了、下一步做什么 | `pnpm next` 的产出，见下 |
| 做某个具体页面 | `docs/pages/<页面>.md`（该页的四件套记录） |
| 抓浏览器基准 | `tools/baseline/README.md`（含 antd 日期选择器等难点的可复用配方） |

设计文档的前身是 `docs/discovery-notes.md`（在 Portal 前端仓库上做的静态扫描实测）。

## 怎么知道下一步做什么

**不要凭印象挑页面。** 唯一权威的下一步来源是：

```bash
pnpm next            # 下一批该做的页面（默认 5 个）
pnpm next --why      # 顺带打印队列规则与跳过清单
pnpm next --domain finance
```

- **页面覆盖状态是推导的**，不是手工记的：页面只要有任一能力指向它（`capability.pagePath === menuPath`）就计入覆盖。
  手工维护的只有 `docs/plan.json` 里的「队列规则」与「跳过」。
  **计入覆盖不等于功能交付完成**：还必须满足下面的完成清单，尤其是 AI 说明契约。
- 用户说「**继续实施**」时，默认动作就是：跑 `pnpm next` → 按返回的页面逐个做完 → 提交。
  不要重新推导方法、不要重新挑页面、不要改变队列规则（除非用户要求）。
- 进度总览：`generated/coverage.html`（双击即开）。它有**两节**：
  - 自动统计的分布（页面数、按域、按形态）
  - `docs/roadmap.json` 渲染的**路线图**——「有哪些环节已经建成」只有人能判断，所以它是手工维护的。
    页面覆盖率低**不代表进度慢**（阶段① 的目标是验证方法，不是铺量）。

## 做完一个页面（一个工作单位）

1. 同时设计业务行为与 AI 说明：用途 / 输入 / 输出字段含义 / 数据消费步骤 / 后续操作 / 失败处理（见 `docs/conventions.md` 第 33 条）
2. 能力定义与说明接入 SDK；通过 `catalog.describe(id)` / `-llm` 实际返回给调用方
3. 四件套记到 `docs/pages/<页面>.md`：能力定义 / 参数契约 / 逐字段基准 / 操作步骤；与 SDK 返回的说明一致
4. 真实环境验证：读能力至少冒烟；**写能力必须有 `prepare → submit → cancel` 的完整记录**
5. 基准回归 + AI 说明契约测试 + **反证**（故意改坏说明中的关键语义或操作映射，确认测试会红）
6. `pnpm run docs` 重建规格与报告
7. 代码、AI 说明、相关文档与测试在同一工作单位提交

## AI 说明是功能的一部分（新增、修改、删除都适用）

**禁止只改执行代码，不同步维护给 AI 的介绍和使用说明。** 适用于页面能力、基础能力、
批量生成能力和公共协议；修改既有功能也必须检查受影响能力及其上下游说明。

- 每个能力都必须说明「做什么、何时用、参数怎么填、返回字段什么意思、数据怎么消费、下一步怎么走」。
- 说明必须由 SDK 的描述入口实际返回。只有标题、源码注释、本地 Markdown、文档路径或通用提醒，**不算完成**。
- 返回契约必须描述 SDK 最终返回给调用方的数据；不能只按参数名猜分页结构，也不能用 `unknown` /「未登记」冒充完整说明。
- 从只看到 SDK 描述与调用结果的 AI 视角验收；不得要求 AI 翻仓库或猜 ID、字段含义和操作顺序。
- 详细要求、变更联动与验收方式以 `docs/conventions.md` 第 33 条为准。**说明缺失或过期，功能就未完成**；历史缺口在本次触及的能力范围内补齐，未实测部分如实记录。
- **格式以 `docs/ai-description-contract.md` 和 `src/catalog/ai-contract.ts` 为准**，不得各自发明字段或只套通用文案。数据需解释到嵌套字段、状态/单位、空值和 ID 归属，动作需写明条件、目标参数映射、完成与失败判据。
- 修改后运行 `pnpm ai:check`，用 `pnpm ai:check:complete` 盘点缺口；本次受影响范围必须逐项验收。检查通过不能替代业务证据，范围外历史问题单独报告，不能放松检查来掩盖它们。

## Git 纪律（并行工作时最容易出事的地方）

**这个仓库经常有多个 Agent / 子代理同时在改。** 下面三条是硬规则：

### 1. 一个阶段做完就提交，不要攒

做完一个页面、修完一个 bug、实现完一个模块——**立刻提交**。别攒到最后，
因为并行的情况下，攒着的工作区会被别人的提交搅在一起，到最后分不清谁改了什么。

### 2. 只提交你自己改动的东西，**禁止 `git add -A` / `git commit -a`**

```bash
# ✅ 对：显式列出你这次改的文件
git add src/capabilities/meeting-application.ts test/meeting-application.test.ts
git commit -m "..."

# ❌ 错：会把并行代理正在改的文件一起卷进去
git add -A && git commit -m "..."
```

理由很实际：`git add -A` 会把**别人此刻改了一半的东西**一起提交，
对方的下一轮工作会莫名其妙地"已经被提交了"，而你可能提交进去一个构建不过的状态。
本包已不再自带 pre-commit 钩子，构建不过的提交不会有人替你拦下。

**同一个文件被两个会话同时改**时，用 hunk 级暂存：
`git diff -- <文件> | git apply --cached --recount`，只暂存你这一部分。

### 3. 子代理不要自己提交

派子代理干活时，**在指令里明确写「不要运行任何会写 git 的命令」**，
由派单方在收工后统一复核、接线、提交。子代理只管产出文件。

派单方提交前，要**逐条复核子代理的产出**（它说"全绿"不等于全绿），
再决定这次提交包含哪些文件。

## 并行派工（默认动作，不是例外）

**不相干的任务默认并行派子代理去做，不要串行地一件件自己干。** 串行把每一段的等待时间叠起来，
而这个仓库里绝大多数任务（页面、模块、文档、调查）彼此没有依赖。

「不相干」的判据是**文件集不相交**，不是任务主题不同。

### 切分按文件所有权切，不按任务编号切

派单前先给每个子代理列出**可写文件集**与**禁止触碰的文件集**，写进指令里。
两个子代理共用同一个文件 = 一定会有一方的改动被另一方的写入覆盖或搅浑，事后极难归因。

反面例子（2026-09-20 实际踩过）：按「协议缺口编号」切，会让两个子代理同时改 `src/catalog/types.ts`；
按文件切（一个拿 `src/catalog/**`，一个拿 `src/http/**`，一个拿 `tools/eval/**`）就干净了。

跨界的那一步——把 A 的产出接进 B 的文件——**由派单方在两边都落地之后做**，
不要为了省一步去放宽某个子代理的边界。

### 派单指令必须带上的几条

1. **不要运行任何会写 git 的命令**（见上节 3），由派单方统一复核、接线、提交。
2. **写明「有别的代理正在并行改这个仓库」**：`pnpm typecheck` / `pnpm test` 会报出**不属于它文件的错误**，
   要求它**忽略、不要去修**，在报告里区分「我文件里的」和「别人在途改动导致的」。
   否则它会去"修好"别人的半成品，把两个任务搅在一起。
3. **零新增依赖**，含 devDependencies，与本包一致。
4. **不要启动开发服务器、不要开浏览器、不要 `pnpm dev`。**
5. **测试必须在坏的时候会红**（第 22 条），要求它把反证逐条列在报告里。
6. **如实报告没做成的部分**：半成品比不做更糟，要它明确分开「实测」与「推断」。
7. **把派单的前提写出来，并交代前提不成立时怎么办。** 前提是会过期的——2026-09-20 有一单
   建立在「协议还没修」上，而并行的另一条线正在修它；是子代理自己发现错位、另建了一份
   未修的基线跑对照组，那一单才没白跑。
8. **AI 说明与功能一起交付**（conventions 第 33 条）。明确说明定义、描述接线与契约测试的文件 owner；共享目录文件由派单方接线，不能因子代理无权修改就漏掉。报告要列出实际返回给 AI 的说明与仍缺失的部分。

### 派单方必须做的

- **逐条复核产出。子代理说"全绿"不等于全绿**——收工后自己重跑测试与 typecheck 再说这话。
- 子代理改了既有断言时要单独审：**改断言不等于放松断言**，但必须看清它锁的是不是错误状态。
- 子代理在**别人的文件**里发现了问题，只报告、不代改，由派单方转给那个文件的 owner。

### 报告里要区分「测到」和「没测到」

一条链跑绿不等于它测到了该测的东西。2026-09-20 有一轮评测判分 2/5，但更要紧的是
**它根本没测到被修的那个缺口**——答案契约里模型不需要写出那段信息，两轮 10 次作答里出现 0 次。
要求子代理主动指出自己的测量盲区；**不要把「没测到」读成「已验证」**。

## 硬约束里最容易被忘的几条

完整清单在 `docs/conventions.md`，这里只挑代价最大的：

- **`module-type` 必须按页面推导**。它只影响后端**数据范围**；不传会让范围变成该用户全部模块的并集（是放大，不是缩小）。
  算不出时**不发**这个头——与浏览器一致。
- **一个 axios 实例 = 一个用户的一个租户**。凭据在创建时绑定，多用户必须走 `createPortalServer`。
- **用的是会话 token，不是私人令牌**（后者是 `system_open_api` 白名单，会锁死范围）。
- **长选项参数必须先要关键字**。人员候选几千个，Portal 页面自己全量拉 4500 人——**无头不能照抄**。
- **不要从浏览器页面提取凭据/cookie/token**。抓基准的脱敏是在页面内做的，你不需要凭据。
- **不引入新的运行时依赖**（工具脚本也一样，现有生成器全是零依赖的纯 Node 脚本）。
- **生成物的新鲜度判据是内容哈希，不是时间戳**（拿 `generatedAt` 当信号会永远判为过期，踩过两次）。

## 常用命令

```bash
pnpm test              # vitest（当前 300+ 用例）
pnpm typecheck
pnpm ai:check          # 构建后检查 AI 描述结构与可验证引用
pnpm ai:check:complete # 另检查缺口、参数覆盖、返回说明与写入效果
pnpm next              # 下一步做什么
pnpm generate          # 从 Portal 前端源码重建 generated/ 的三个运行时资源
pnpm smoke:meeting-room / smoke:prepare / smoke:submit   # 对真实测试环境的冒烟
```

本包只保留三个**运行时资源**生成物——`generated/page-catalog.json`、
`generated/module-type-rules.json`、`generated/portal-scope.json`，
由 `pnpm generate` 从 Portal 前端源码重建。改了 `src/`、`docs/plan.json`
或 `tools/generate/` 时需要重跑，并把结果一并提交。

2026-09-26 删除了整套文档生成链（OpenAPI 规格、api-docs 静态页、覆盖与进度报告、
范围审计、漂移门禁）以及依赖它们的三个测试。理由是这些产物面向人读，而本包只服务
AI 调用——需要接口信息时直接问 SDK（`catalog.recommend` / `catalog.describe`），
不必再维护一份会过期的大文件。原 `.githooks/pre-commit`（含它的并行安全闸）
此前已随迁入 monorepo 移除。

## 不要做的事

- **不要为了让测试变绿而放松断言。** 如果一条断言锁的是错误状态，改的是它，不是实现。
- **不要用"接口返回成功"代替验证。** 写操作要有能独立证实的证据（例如占用查询里真的出现了那条记录）。
- **不要把没验证的东西说成已验证。** 文档里写清楚哪些是实测、哪些是推断。
- **不要把 Portal 里注释掉的东西搬过来。** 注释掉 = 已经没意义了：不推导、不进目录、不进能力。
  菜单里注释掉的那一行，那一页就**到不了**——"能渲染"不等于"用户能做的事"。
  连招呼它的词条（别名表里的）也要去掉，否则用户的问题会被静默路由到隔壁页面。
  详见 `docs/conventions.md` 第 28 条。
- **不要顺手重构。** 只改任务范围内的东西。
