# 14.0 第九步执行任务书：自动化入口、Relay、run_as_user 与运维增强

## 0. 阶段定位

本任务书假设 13.0 已经完成。

也就是说，在开始本阶段前，仓库应已经具备：

- Renderer 长任务 stream preview / compact progress。
- 本地引用渲染与安全 `/show`。
- CommandRegistry、Custom Commands、SkillRegistry。
- 命令/技能发布到 Renderer、Bridge、Feishu。
- Agent-native slash allowlist。
- Scheduler、Cron、Heartbeat、Feishu 主动回传。
- Feishu 多工作区、频道绑定、AgentRuntime workspace 隔离。

14.0 的目标是补齐 CC Connect 中偏后置但很关键的无人值守和多 Agent 协作能力：

- run_as_user / OS isolation 安全前置。
- Webhook 自动化入口。
- Bot-to-Bot Relay / Agent-to-Agent 协作。
- 手动 `/compress` 与 Auto-compress。
- 运维增强：状态诊断、日志定位、单实例/运行环境检查、重启提示。

本阶段仍只要求 Feishu 作为真实远程平台，不新增微信、Telegram、Slack、Discord、Lark 等平台。

不要把 CC Connect 的 daemon/self-update 机械照搬到 Electron。Synapse 是 Electron 应用，本阶段迁移的是“运行可靠性与可诊断性”的设计，不是 Go 二进制 daemon 方案。

## 6. 总体实现原则

### 6.1 所有入口仍进入同一 AgentRuntime

Webhook prompt、Relay prompt、Auto-compress 不能绕过 AgentRuntime。

目标链路：

```text
Webhook / Relay / Command -> AgentMessage -> AgentRuntimeService -> session lock / queue / permission -> Agent adapter -> AgentEvent -> ReplyTarget / Outbox / caller
```

exec 类入口可以不进入 Agent，但必须走：

```text
PermissionGuard -> AuditSink -> ControlledProcessRunner -> status/outbox
```

### 6.2 外部入口默认本地绑定

Webhook、Relay side-channel、本地 API 默认只能绑定：

- `127.0.0.1`
- 或当前项目已有的安全本地地址策略。

开放到局域网或公网必须是显式配置，并且最终报告写清楚风险。

### 6.3 强鉴权、限流、审计

Webhook/Relay 都是外部入口，必须具备：

- token 鉴权。
- constant-time token compare。
- rate limit。
- payload size limit。
- request id。
- DataRepository 记录运行状态。
- AuditSink 记录 actor/action/resource/outcome。

### 6.4 UI 使用现有规范

涉及 UI 必须遵守：

- shadcn/ui。
- Radix。
- Tailwind token。
- 项目已有 design baseline。

禁止：

- 自定义颜色。
- hex/rgb/hsl 字面色。
- Tailwind 任意色值。
- 内联 style，动态计算值除外。
- 新 CSS module 或全局 CSS 覆盖。
- 卡片套卡片。
- 渐变、霓虹、emoji heading。
- UI 废话。

## 7. run_as_user / OS isolation 要求

### 7.1 实现目标

本阶段需要为 Agent spawn 和 shell exec 提供可选 OS 用户隔离能力。

不要自动开启。

用户必须在项目设置中显式配置 target user，并通过 preflight 后才能启用。

### 7.2 数据模型

建议新增项目级配置：

- `runAs.enabled`
- `runAs.user`
- `runAs.envAllowlist`
- `runAs.requirePreflight`
- `runAs.lastPreflightAt`
- `runAs.lastPreflightStatus`
- `runAs.lastAuditProbeAt`
- `runAs.lastAuditProbeStatus`

所有配置通过 DataRepository 或现有项目配置服务保存。

不要把 sudo 密码、secret 明文写入配置。

### 7.3 ExecutionIsolationService

建议新增服务：

- `ExecutionIsolationService`

职责：

- 构造隔离 spawn command。
- 过滤 env。
- cheap verify。
- preflight。
- audit probe。
- 返回平台不支持原因。
- 给 Agent spawn 和 ControlledProcessRunner 提供统一包装。

macOS/Linux 建议语义：

```text
sudo -n -iu <targetUser> --preserve-env=<allowed> -- <command>
```

具体实现必须以 CC Connect 源码和 Synapse ProcessRuntime 能力为准。

Windows：

- 本阶段可以标记为 unsupported。
- UI/报告中写清楚。
- 不要写半成品提权逻辑。

### 7.4 Env allowlist

必须实现 env allowlist。

默认只允许必要变量，例如：

- `PATH`
- `HOME` 是否允许要谨慎，以目标用户 HOME 为准。
- Agent CLI 必需的 provider/base URL 变量。
- Side-channel token/URL。
- 项目明确允许的变量。

不允许把整个 `process.env` 透传给目标用户。

### 7.5 Preflight 与 Audit Probe

preflight 至少检查：

- 当前用户是否能 `sudo -n -iu targetUser`。
- target user 是否存在。
- target user 是否能访问 workspace。
- target user 不能免密 sudo 回 supervisor。
- workspace 子目录权限风险。

audit probe 至少记录：

- supervisor user。
- target user。
- effective uid/gid。
- workspace read/write 能力。
- env allowlist 结果。

记录到 DataRepository 和 AuditSink。

### 7.6 接入点

必须接入：

- Agent spawn。
- exec custom command。
- Cron exec job。
- Webhook exec。
- Relay 中如果有 exec 能力，也必须接入。

如果某处已有 `ControlledProcessRunner`，优先扩展 runner 的 spawn option，不要在业务服务里手写 shell。

## 8. Webhook 自动化入口要求

### 8.1 服务设计

建议新增：

- `AutomationIngressService`
- `WebhookRepository`

Webhook HTTP 服务必须通过 `NetworkServiceRegistry` 注册。

不要裸 `http.createServer`。

默认：

- disabled。
- bind `127.0.0.1`。
- token required。
- path `/hook` 或 `/automation/hook`，最终以实现一致性为准。

### 8.2 Webhook request schema

建议字段：

- `event`
- `projectId` 或 `project`
- `sessionKey` 或 `session_key`
- `connectorId`
- `platform`
- `prompt`
- `exec`
- `payload`
- `workDir`
- `timeoutMins`
- `silent`
- `mute`
- `replyMode`
- `metadata`

要求：

- `prompt` 和 `exec` 必须互斥。
- `projectId` 在多项目时必填。
- `sessionKey` 如果要主动回传 Feishu，则必填或可从配置明确推断。
- `payload` 有大小限制。
- JSON parse 错误返回 400。
- auth 错误返回 401/403。

### 8.3 Prompt webhook

prompt webhook 必须构造 synthetic `AgentMessage`：

- `platform: "webhook"`
- `userId: "webhook"`
- `userName: "webhook"`
- `projectId`
- `sessionKey`
- `content`
- `replyCtx` 或可重建 target
- `workspaceKey/workspacePath`
- `metadata`

要求：

- 进入 AgentRuntime queue/lock。
- 保留 workspace 解析。
- 可选择主动回传到 Feishu 原 session。
- 记录 webhook run 状态。

### 8.4 Exec webhook

exec webhook 必须：

- 需要更严格权限。
- 默认 disabled 或 admin-only。
- 走 PermissionGuard。
- 走 AuditSink。
- 走 ControlledProcessRunner。
- 接入 run_as_user。
- 设置 timeout。
- 截断输出。
- 记录状态。
- 非 mute 时按 reply target 回传结果。

不要照搬 CC Connect 的 `sh -c` 直接执行。

### 8.5 Webhook 响应

支持两种模式：

- `async`：立即返回 `runId`。
- `wait`：等待短时间返回结果或部分状态。

默认建议 `async`。

无论 HTTP 是否等待，后台执行状态都要可查。

### 8.6 Webhook UI

如果做 UI，最小支持：

- 启用/禁用。
- bind address。
- port。
- token reset。
- payload size limit。
- 最近 runs。
- last error。

不要把 token 明文长期显示。

## 9. Relay / Agent-to-Agent 协作要求

### 9.1 实现目标

Relay 的目标是让一个 Agent 可以询问另一个项目/工作区的 Agent。

它不是普通聊天转发。它必须满足：

- 项目间可寻址。
- relay session 独立于用户主会话。
- 请求/响应可审计。
- 超时可返回部分结果。
- 超时后 target Agent 后台继续 drain，并保存 relay session。
- 可选把请求/响应以可见记录回传到 Feishu 群聊。

### 9.2 服务设计

建议新增：

- `AgentRelayService`
- `RelayBindingRepository`
- `RelayRunRepository`

DataRepository namespace 建议：

- `relay.bindings`
- `relay.runs`
- `relay.sessions`

不要用业务 `fs.writeFile` 保存 relay JSON。

### 9.3 Binding 数据模型

建议字段：

- `id`
- `projectId`
- `sourceProjectId`
- `targetProjectId`
- `sourceSessionKey`
- `sourceChannelKey`
- `workspaceKey`
- `workspacePath`
- `enabled`
- `createdAt`
- `updatedAt`
- `createdBy`

根据 Synapse 产品形态，可以支持两种寻址：

- project-to-project：`toProjectId`。
- Feishu channel binding：当前群聊绑定多个项目。

本阶段至少实现 project-to-project。

如果实现 Feishu 群聊绑定，命令可以是：

- `/relay bind <project>`
- `/relay list`
- `/relay unbind <project>`

### 9.4 Side-channel `/relay/send`

Agent 侧必须可以通过 side-channel 调用 relay。

建议 endpoint：

- `POST /relay/send`

请求字段：

- `toProjectId` 或 `to`
- `message`
- `sourceProjectId`
- `sourceSessionKey`
- `workspaceKey`
- `timeoutMins`
- `visible`
- `metadata`

要求：

- 使用 side-channel token。
- 从 Agent env 推断 sourceProject/sourceSession 时必须可靠；无法推断就报错。
- 不能允许 Agent 任意伪造 source project。
- 记录 audit。
- 返回 result、partial result 或 run id。

### 9.5 Relay session

target Agent 的 sessionKey 建议遵循：

```text
relay:<sourceProjectId>:<sourceSessionKey 或 runId>
```

要求：

- relay session 不污染 target 项目的用户主会话。
- 同一个 source/target 可以复用 relay session，或按配置 new per run。
- timeout 不杀 target Agent。
- timeout 后后台继续 drain。
- drain 完成后保存 session 和 final result。

### 9.6 Relay 可见记录

如果 source 是 Feishu session，且 `visible=true`：

- 请求发起时可以向 Feishu 发送一条简短可见记录。
- target 返回后可以发送结果摘要。
- mute/silent 语义沿用已有自动化规则。

不要刷屏。

### 9.7 Relay UI

最小支持：

- 查看 relay bindings。
- 查看 relay runs。
- 查看 running/timeout/completed/failed 状态。
- 删除 binding。
- 不需要复杂图谱。

## 10. `/compress` 与 Auto-compress 要求

### 10.1 ContextCompressor 接口

为 Agent adapter 增加压缩能力声明。

建议接口：

- `supportsCompression()`
- `compressionCommand()`
- `runCompression(session, ctx)`

或按仓库现有 adapter 风格实现。

要求：

- Claude Code 支持 `/compact`。
- 如果 Codex 当前不支持明确压缩命令，则返回 unsupported，不要假装支持。
- unsupported 时 `/compress` 给出清楚结果。

### 10.2 手动 `/compress`

新增或完善 built-in `/compress`。

要求：

- 通过 CommandRegistry 执行。
- 在当前 session lock 内执行。
- 不进入普通用户消息 history。
- 执行期间不要 drain queued user turns。
- 完成后继续处理队列。
- 记录 lastCompressedAt。
- 记录 audit。

### 10.3 AutoCompressConfig

新增项目级配置：

- `autoCompress.enabled`
- `autoCompress.maxTokens`
- `autoCompress.minGapMins`
- `autoCompress.lastCompressedAt`

要求：

- 默认 disabled，或保守阈值。
- UI 可启用/禁用和设置阈值。
- min gap 默认参考 CC Connect，建议 30 分钟。

### 10.4 Token 估算

自动压缩需要估算上下文长度。

要求：

- 可以先用保守字符/词估算，不要求精确 tokenizer。
- 必须在最终报告说明估算方法。
- 不能因为估算失败中断正常 turn。

### 10.5 自动触发时机

自动压缩必须在：

- Agent turn final result 后。
- queued messages drain 前。
- 同一 session lock 内。

不得在 session 忙碌中另开一个压缩 turn。

### 10.6 压缩事件处理

要求：

- 压缩过程的内部事件不写入普通聊天 history。
- 压缩失败记录状态，但不丢失后续 queued messages。
- 如果压缩触发 permission request，按 CC Connect 源码策略处理；若 Synapse 安全模型不同，必须在安全设计中说明。

## 11. Hooks 处理要求

本阶段不要求完整实现 CC Connect hooks。

但必须在 `14.0 源码与现状映射.md` 中给出结论：

- Synapse 现有 EventBus 是否已经覆盖 hook 需求。
- HTTP hook 是否应该作为 Webhook 的反向能力后续实现。
- shell hook 是否因权限风险继续后置。

如果实现最小 HookService，必须满足：

- EventBus 驱动。
- HTTP hook 有 timeout 和 allowlist。
- shell hook 走 PermissionGuard、AuditSink、ControlledProcessRunner。
- 不默认启用。

没有足够安全边界时，不要实现 shell hook。

## 12. Observer / STT / TTS 处理要求

本阶段不要求实现 Observer、STT、TTS。

- 如果 Synapse 已经掌控 AgentEvent，Observer 可后置。
- STT/TTS 需要哪些 provider 和平台 audio 能力，继续后置。

不要因为 CC Connect 有这部分源码就强行塞进 14.0。
