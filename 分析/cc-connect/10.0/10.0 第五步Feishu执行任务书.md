# 10.0 第五步执行任务书：Connector 基座与 Feishu 远程控制

## 一、阶段定位

`9.0 第四步B` 已经完成 Bridge adapter、side-channel send、ReplyTarget/Outbox 复用、本地网络服务安全边界和 Agent session env 注入。本阶段进入 `3.1 整体开发顺序.md` 中的第五步：真实远程 connector。

本阶段只支持飞书 Feishu。不要实现 Lark、微信、Slack、Telegram、Discord、Webhook、Cron、Relay、多工作区。

“做到和 CC Connect 对等”的含义是：在飞书这条链路内，对齐 CC Connect 的产品闭环和关键运行逻辑：

1. 扫码或手动绑定飞书应用凭证。
2. 凭证进入 Synapse 的 secrets/connectors 数据模型。
3. 飞书运行时用 app_id/app_secret 建立事件连接。
4. 飞书消息经过去重、旧消息过滤、allowlist、群聊 @ 过滤。
5. 飞书事件转成统一 `AgentMessage`，进入现有 `AgentRuntimeService`。
6. Agent 输出通过 `ReplyTarget` / Outbox 回到飞书。
7. 权限请求能以飞书消息/卡片方式回到飞书，并能把用户操作回写 Agent。
8. 文本、图片、文件的回传策略与 9.0 side-channel/附件策略兼容。

注意：CC Connect 同时支持 `feishu` 和 `lark`，但本阶段只做 `feishu`。如果飞书扫码轮询中识别出 Lark tenant，应返回明确的 `unsupported_lark` 或等价错误状态，不能半实现 Lark。

### 第 3 步：实现 Feishu setup service

对应 CC Connect：`handleSetupFeishuBegin`、`handleSetupFeishuPoll`、`handleSetupFeishuSave`。

建议接口：

- `beginSetup(projectId): Promise<FeishuSetupBeginResult>`
- `pollSetup(setupId): Promise<FeishuSetupPollResult>`
- `saveSetup(setupId, options): Promise<FeishuConnectorSummary>`
- `saveManualCredentials(projectId, appId, appSecret, ownerOpenId?): Promise<FeishuConnectorSummary>`

实现要求：

- HTTP client timeout 15 秒。
- `beginSetup`：
  - 调 `action=init`。
  - 调 `action=begin`。
  - begin form 参数对齐 CC Connect：
    - `archetype=PersonalAgent`
    - `auth_method=client_secret`
    - `request_user_info=open_id`
  - 返回 `setupId`、`qrUrl`、`interval`、`expiresIn`。
  - 不返回 secret。
- `pollSetup`：
  - 用 setupId 查 device_code。
  - 调 `action=poll`。
  - `authorization_pending` -> pending。
  - `slow_down` -> pending + slowDown。
  - `access_denied` -> denied。
  - `expired_token` -> expired。
  - 其它错误 -> error。
  - 返回 `completed` 时，main process 暂存 app_id/app_secret/owner_open_id，不把 app_secret 透给 Renderer。
  - 如果 tenant_brand 是 Lark，返回 `unsupported_lark`，不实现 Lark。
- `saveSetup`：
  - 从 main process 暂存读取 app_id/app_secret。
  - 写 secrets namespace。
  - 写 connectors namespace。
  - audit 记录 setup saved。
  - 清理暂存 secret。
- `saveManualCredentials`：
  - 用于绑定已有飞书应用。
  - appSecret 只进入 secrets namespace。
  - audit 记录 manual bind。

安全要求：

- app_secret 不进 renderer state。
- app_secret 不进日志。
- app_secret 不进 audit metadata。
- setup 临时缓存要有过期时间。
- setupId 要随机且不可猜。

测试：

- begin init/begin 成功。
- begin incomplete response 报错。
- poll pending/slow_down/denied/expired/completed。
- poll Lark tenant -> unsupported_lark。
- saveSetup 写 secretRef + connector，不泄露 secret。
- manual credentials 保存。
- setup cache 过期失败。

### 第 5 步：实现 Feishu runtime service

目标：用保存的 connector + secret 启动飞书事件运行时。

职责：

- 从 ConnectorRepository 读取 feishu connector。
- 从 secrets namespace 读取 app_id/app_secret。
- 创建飞书 SDK client。
- 启动 WebSocket 长连接事件订阅。
- 维护状态：
  - connecting
  - connected
  - degraded
  - error
  - disabled
- 停止时关闭 WS client。
- 失败时写 connector status、lastError、reconnect attempts、audit。

要求：

- 只支持飞书 domain。
- 不实现 Lark domain。
- 不实现 webhook mode。
- 不绕过 AgentRuntime。
- 不把 app_secret 写到日志。
- 不把 tenant_access_token 写到日志。
- 运行时必须能被 bootstrap descriptor 创建，也能按 project start/stop。
- 需要有 `FeishuClient` 接口抽象，方便单测 fake SDK。

建议接口：

- `start(projectId): Promise<void>`
- `stop(projectId): Promise<void>`
- `restart(projectId): Promise<void>`
- `status(projectId): Promise<FeishuConnectorStatus>`
- `handleMessageEvent(event): Promise<void>`
- `handleCardAction(event): Promise<void>`

测试：

- start 成功更新 connected。
- start 缺 secret -> error。
- start SDK 报错 -> error + audit。
- stop 调用 SDK close/cancel。
- reconnect state 记录 attempts/lastError。

### 第 6 步：实现 Feishu 消息标准化

对应 CC Connect：`onMessage` 和 `dispatchMessage`。

必须支持：

- text message。
- group chat @ bot filtering。
- allowlist filtering。
- old message filtering。
- message dedupe。
- session key 生成。
- reply context 生成。

建议暂缓或结构化 unsupported：

- merge_forward。
- audio。
- rich text card extraction。
- multi-level reply chain。
- mention display name resolve。

如果暂缓，必须在最终报告写明和 CC Connect 的差距。

映射要求：

- Feishu `message_id` -> `AgentMessage.messageId`。
- Feishu `chat_id` -> replyCtx.chatId。
- Feishu sender open_id -> `AgentMessage.userId`。
- Feishu sender name -> `AgentMessage.userName`。
- Feishu chat name -> `AgentMessage.chatName`。
- Feishu chat type -> `AgentMessage.chatType`。
- stripped text -> `AgentMessage.content`。
- generated session key -> `AgentMessage.sessionKey`。
- reply context -> `AgentMessage.replyCtx`。
- platform -> `feishu`。

治理要求：

- 旧消息过滤要复用或对齐 `AgentGovernanceService` 的 old message 策略。
- allowlist 要基于 connector allowlist，不要散落在 runtime。
- dedupe state 要写 connector dedupe 或独立服务，不要只放内存；可以先内存 + 定期持久化，但必须测试。

测试：

- 个人文本消息进入 AgentRuntime。
- 群聊未 @ bot 被忽略。
- 群聊 @ bot 进入 AgentRuntime 且内容剥离 bot mention。
- allowlist 拒绝用户。
- duplicate message ignored。
- old message ignored。
- text JSON 解析失败记录 warn。

### 第 7 步：实现 Feishu session key policy

对应 CC Connect：`makeSessionKey`。

本阶段至少支持：

- `per-user`：`feishu:<chatID>:<userID>`。
- `per-channel`：`feishu:<chatID>`。
- `thread`：`feishu:<chatID>:root:<rootID>`。

要求：

- sessionKeyPolicy 来自 connector 配置。
- 默认 `per-user`。
- 不做多工作区绑定。
- 不把 workspace key 混进 session key。
- card action 里如果带 session_key，优先使用。

测试：

- per-user。
- per-channel。
- thread root。
- card action session key override。

### 第 8 步：接入 AgentRuntime

Feishu runtime 收到标准化消息后，必须调用现有 `AgentRuntimeService.send(...)`。

要求：

- 通过 `ProjectContainerRegistry` 找 project container。
- 从 container resolve `agent.runtime`。
- 不直接 spawn CLI。
- 不直接操作 adapter。
- actor 使用 connector 身份：
  - `{ kind: "connector", id: connectorId }`
- message.replyCtx 必须包含：
  - kind: `feishu`
  - connectorId
  - appId 或 connectorId
  - chatId
  - messageId
  - sessionKey
  - replyInThread / noReplyToTrigger 等必要策略
- AgentRuntime 产生的事件继续走 EventBus 和 Outbox。

测试：

- fake AgentRuntime 收到正确 AgentMessage。
- project 不存在时 connector status 变 degraded/error。
- AgentRuntime 返回 error 时能回飞书错误或记录 outbox failed。

### 第 9 步：实现 Feishu ReplyTarget reconstructor

对应 CC Connect：`ReconstructReplyCtx`。

目标：后续 Cron/Heartbeat 只有 sessionKey 时，也能主动回飞书。

要求：

- 从 `feishu:<chatID>:<userID>` 还原 chatID。
- 从 `feishu:<chatID>` 还原 chatID。
- 从 `feishu:<chatID>:root:<rootID>` 还原 chatID 和 messageID/rootID。
- 校验 prefix 必须是 `feishu`。
- 返回可被 Feishu reply service 使用的 replyCtx。
- 不要求当前就实现 Cron，但 reconstructor 必须存在并被 side-channel/ReplyTarget 模型复用。

测试：

- 三种 session key 都能 reconstruct。
- 非 feishu 前缀报错。
- 缺 chatID 报错。

### 第 10 步：实现 Feishu 出站 reply service

对应 CC Connect：`Reply`、`Send`、`SendImage`、`SendFile`、`replyMessage`、`createMessage`。

至少支持：

- text reply。
- text send/create fallback。
- error reply。
- outbox sent/failed 记录。

应支持：

- image upload + send。
- file upload + send。

如果图片/文件不能在本阶段完整实现，必须：

- 保留接口和结构化 unsupported。
- outbox 标记 failed。
- 在最终报告写明原因。

要求：

- Reply 优先使用飞书 reply message API。
- 如果 replyCtx 没有 messageId，则 create message 到 chat。
- tenant token invalid 时尝试刷新或依赖 SDK 内置刷新。
- 失败写 connector lastError、audit 或 structured logger。
- 不把 token 写入日志。

测试：

- reply with messageId。
- create fallback without messageId。
- SDK error -> outbox failed。
- token invalid retry 行为如可 fake，必须覆盖。
- image/file unsupported 或成功路径。

### 第 11 步：权限请求远程处理

目标：Agent 的 `permissionRequest` 能出现在飞书里，并允许用户远程 allow/deny。

要求：

- 如果支持 interactive card：
  - 发送带 allow/deny 按钮的卡片。
  - action value 包含 requestId、sessionKey、connectorId。
  - 不包含敏感 toolInput 原文的大字段；必要时截断。
- 如果第一版无法稳定发送卡片：
  - 发送文本 fallback，明确提示用户可回复固定命令。
  - 但最终成功标准仍要求 allow/deny 能回写 Agent。
- card action / 文本命令最终必须调用 `AgentRuntimeService.respondPermission(...)`。
- 非 owner/admin 用户不能 allow。
- allow 前仍走 PermissionGuard。
- audit 写 actor connector/user。

测试：

- permissionRequest -> card/text message。
- allow action -> respondPermission allow。
- deny action -> respondPermission deny。
- 非授权用户 allow 被拒。
- requestId 不存在返回错误。

### 第 12 步：Feishu setup UI

目标：用户能在桌面端完成飞书连接。

建议位置：

- 设置页新增 “连接器” 分组，或在现有设置里新增 Feishu 连接面板。
- 不新增独立营销页。

UI 必须遵守：

- 使用现有 shadcn/Radix 组件。
- 使用 Tailwind token。
- 禁止自定义颜色、hex/rgb/hsl、内联 style、AI 渐变、装饰 emoji。
- 禁止卡片套卡片。
- 文案只保留必要 label、状态、错误。
- 不展示 app_secret。
- 不展示 token。

最小 UI 流程：

1. 选择当前 project。
2. 点击连接飞书。
3. 调 beginSetup，显示二维码 URL 对应二维码。
4. 按 interval 轮询 pollSetup。
5. pending/slow_down/denied/expired/error/completed 状态显示。
6. completed 后点击保存或自动 saveSetup。
7. 显示 connector status。
8. 提供 start/stop/reconnect。
9. 提供手动 app_id/app_secret 绑定入口。

二维码实现：

- 优先使用已有依赖。
- 如果需要新增 QR 依赖，选择轻量依赖，并在最终报告说明。
- 不用 SVG 手画二维码。

状态文案要克制，例如：

- `等待扫码`
- `已授权`
- `已过期`
- `连接失败`
- `已连接`

不要写“此页面用于帮助你提升效率”之类废话。

### 第 13 步：启动与生命周期

要求：

- connector 保存后默认不一定自动启动，可按产品判断；但必须有 start。
- app 启动时可自动启动 enabled/connected 的 Feishu connector。
- start 失败要写 status error。
- stop 要停止 WS。
- reconnect 失败要更新 attempts/nextRetryAt/lastError。
- 不要无限紧密重试。
- 退出应用时停止 runtime。

建议：

- `core.feishu-connector` 或 `core.connector-runtime` descriptor。
- 依赖：
  - `core.project-containers`
  - `core.data-repository`
  - `core.audit-sink`
  - `core.permission-guard`
  - `core.network-registry` 如使用 webhook/本地服务。本阶段只 WS 客户端，可不注册本地网络端口。

## 十一、完成标准

本阶段完成后，必须满足：

- 用户可以在 Synapse UI 中连接飞书。
- 飞书扫码 begin/poll/save 可用。
- 手动绑定 app_id/app_secret 可用。
- app_secret 只进入 secrets namespace。
- connectors namespace 有 Feishu connector 状态。
- Feishu runtime 可 start/stop/status。
- 飞书文本消息能进入 `AgentRuntimeService`。
- Agent 文本回复能回到飞书。
- 飞书群聊 @ 过滤、allowlist、dedupe、old message filter 有实现和测试。
- 飞书 reply context 可保存和重建。
- 权限请求能从飞书确认或拒绝。
- 图片/文件回传至少有结构化支持或明确 unsupported，不静默失败。
- 所有过程产物在 `分析/cc-connect/10.0/`。
- `pnpm desktop:typecheck`、`pnpm desktop:test`、`pnpm desktop:check:hard-constraints` 通过，或失败原因明确且不是本阶段引入。
- 已提交 commit，建议提交信息：`feat: add feishu connector runtime`。

## 十二、进入 11.0 的条件

只有满足以下条件，才可以进入 `11.0 多工作区与频道绑定`：

- Feishu 作为第一个真实 connector 已经跑通入站和出站。
- sessionKeyPolicy 已可配置或至少可扩展。
- reply context 可重建。
- connector status/reconnect/dedupe 有持久化。
- allowlist/群聊过滤已复用治理边界。
- 不存在 secret 泄露。
- 没有违反 hard constraints。
