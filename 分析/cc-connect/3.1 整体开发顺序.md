## 总判断

Synapse 可以开始做 CC Connect 类能力，但开发顺序不能从飞书、定时任务或 UI 开始。

CC Connect 的核心不是某个平台适配器，也不是某个 CLI 调用，而是这一条统一管线：

```text
入口消息 -> 标准 AgentMessage -> AgentRuntimeEngine -> AgentSession -> 统一 AgentEvent -> UI/Connector/Outbox
```

所以真正的顺序应是：

```text
第零步架构地基
-> 本机 AgentRuntime 闭环
-> 会话、队列、权限、治理
-> Provider 和命令控制
-> Bridge/管理 API/本地 Side-channel
-> Feishu/Lark 远程 connector
-> 多工作区
-> 定时任务与主动回传
-> 长任务体验和扩展能力
```

这个顺序的依据是：

- 所有平台、Web、Bridge、Cron、Heartbeat、Webhook 最终都应进入同一个 Engine，不能各自直接调用 Codex/Claude。
- 飞书只能解决“远程消息从哪里来”，不能解决会话、队列、权限、Agent 子进程和结果回传。
- Cron/Heartbeat 没有新的入站消息，必须依赖 `session_key -> reply_ctx` 重建能力，所以要在 connector 和 session 模型之后做。
- 多工作区依赖频道键、工作区绑定、per-workspace Agent 和 per-workspace session，必须等 Engine 与 connector 的 session key 规则稳定后做。
- UI 应该是薄管理面，先暴露现有运行时能力，不应该先做漂亮页面再倒逼架构。

## 源码复查结论

复查 `/Users/liyang/Documents/code/demo/cc-connect-main` 源码后，当前计划的主顺序成立，但需要补两类前置能力。

第一，第二步不能只写“会话和权限”，还必须包含输入治理：disabled commands、admin allowlist、role、rate limit、banned words、outgoing rate limit、message dedupe。原因是远程入口一旦接入，所有用户消息都会进入 `Engine.handleMessage`，源码中限流和敏感词检查发生在 slash command 与 Agent turn 之前。

第二，第四步不能只写 Management/Bridge，还必须包含本地 side-channel API。原因是 CC Connect 让 Agent 在工具调用中执行 `cc-connect send`、`cc-connect cron add`、`cc-connect relay send`，靠的是 Engine 向 Agent 子进程注入 `CC_PROJECT`、`CC_SESSION_KEY` 和 PATH，再由本地 API Server 接收请求。如果 Synapse 不做这层，本机 Agent 生成文件回传、Agent 自己创建定时任务、Agent 间 relay 都会缺关键入口。

复查后的先后关系仍是：

```text
地基整理
-> AgentRuntime
-> Session/Queue/Permission/Governance
-> Provider/Command
-> Management/Bridge/Side-channel
-> Feishu/Lark
-> Multi-workspace
-> Scheduler/Outbox
-> Experience
-> Automation
```

## 第零步：地基整理

目标：让后续 AgentRuntime、Connector、Scheduler 都能按 Synapse 现有架构接入，而不是为了 CC Connect 另起一套平行系统。

当前仓库已经有 ServiceRegistry、EventBus、DataRepository、ProjectContainer、PermissionGuard、NetworkServiceRegistry、ProcessRuntime 等结构，但它们还有几个落地空洞需要先补齐。

要做的事情：

1. 补齐全局 runtime 服务注册。
   - 将 DataRepository、PermissionGuard/AuditSink、ProcessRuntime、NetworkServiceRegistry、ProjectContainerRegistry 作为真实 service descriptor 注册进 `desktop/electron/bootstrap/registry.ts`。
   - 新业务服务通过 `ServiceRegistry.get<T>()` 获取依赖，不直接 import 全局 singleton。
   - `ServiceContext` 里不要继续只放 placeholder，至少让新增 CC Connect 相关服务拿到真实 EventBus、DataRepository、PermissionGuard。

2. 补齐 project-scoped persistence。
   - 当前 `ProjectScopedDataRepoImpl.namespace()` 仍是 pass-through。
   - 在写入 Agent session、conversation、connector binding、scheduled job 前，必须实现真实 project scope。
   - 最低要求：同一 namespace 下所有项目级数据带 `projectId`，或存储路径按 `projects/<projectId>/...` 隔离。

3. 把占位 schema 升级为可用业务 schema。
   - `providers`：全局 provider、项目 provider ref、active provider/model。
   - `connectors`：platform、secretRef、status、allowlist、sessionKeyPolicy、reconnect/dedupe 状态。
   - `conversations`：本地 session、agent 原生 session id、past agent session ids、history、userMeta。
   - `outbox`：主动消息投递目标、payload、attempts、lastError。
   - `audit`：远程入口、actor、敏感动作、结果。

4. 定义 Agent 子进程启动边界。
   - `ProcessRuntime` 当前只支持 `kind="main"`；Agent CLI 短期可以由 AgentRuntimeService 内部封装 `child_process.spawn()`。
   - 但这个封装必须统一经过 `PermissionGuard.check({ action: "agent.spawn" })` 和 AuditSink。
   - 后续再把该封装下沉为真正的 child process runtime，避免业务服务里到处 spawn。

5. 定义本地网络服务边界。
   - Bridge WebSocket、localhost API、Webhook 都要通过 NetworkServiceRegistry 分配端口、绑定地址和认证策略。
   - 第一版可先只支持 `127.0.0.1` + local token；不要隐式监听 `0.0.0.0`。

完成标准：

- 可以注册一个 project-scoped service，并在其中安全访问 scoped dataRepo、scoped eventBus、PermissionGuard、AuditSink。
- 可以写入 project-scoped conversation/provider/connector 数据，重启后不串项目。
- 可以通过统一封装启动一个受权限检查和审计保护的本机 CLI 子进程。

暂时不做：

- 不做 Feishu。
- 不做 Cron。
- 不做复杂 UI。
- 不做 run_as_user 的完整 OS 用户隔离；只保留扩展点。

## 第一步：本机 AgentRuntime MVP

目标：不接飞书、不做定时任务，先在本机证明 `prompt -> CLI -> event -> reply` 闭环成立。

为什么先做：

- `1.1` 和 `1.5` 都说明平台层不能直接调用 Agent。
- `2.2` 明确当前最缺的是等价于 `core.Engine` 的业务中枢。
- 没有 AgentRuntime，飞书、Bridge、Cron 都只能复制一遍临时逻辑，后面必然返工。

建议模块：

- `desktop/electron/services/agent-runtime/`
- `desktop/electron/services/agent-runtime/types.ts`
- `desktop/electron/services/agent-runtime/agent-runtime-service.ts`
- `desktop/electron/services/agent-runtime/adapters/codex-exec.ts`
- `desktop/electron/modules/agent/ipc.ts`

核心抽象：

- `AgentMessage`：统一输入，至少包含 `projectId`、`sessionKey`、`platform`、`userId`、`content`、`attachments`、`replyCtx`、`modeOverride`。
- `AgentEvent`：统一输出，至少包含 `text`、`thinking`、`toolUse`、`permissionRequest`、`result`、`error`。
- `AgentAdapter`：Agent 类型工厂。
- `AgentSession`：活跃 CLI 会话，负责 `send()`、`events()`、`currentSessionId()`、`close()`。
- `ReplyTarget`：第一版可由 renderer/internal platform 实现，后面 Feishu/Bridge 复用同一概念。

第一版 Agent 选择：

- 先做 Codex exec backend，因为每轮一个进程，生命周期更简单。
- Claude Code 长驻 stream-json 会话放到第二步做，因为它牵涉权限回写、stdin 写入锁和进程长期清理。

成功标准：

- renderer 或 IPC 能发送一条本机 prompt。
- main process 能启动 `codex exec --json ... -`。
- stdout JSON Lines 能映射成统一 `AgentEvent`。
- 最终结果通过 EventBus 或 IPC 回到 renderer。
- 能保存 Codex thread id，为下一轮 resume 做准备。

暂时不做：

- 不做远程 connector。
- 不做多工作区。
- 不做完整 slash command。
- 不做复杂 Chat UI，只需要能验证闭环。

## 第二步：会话持久化、队列、权限和治理闭环

目标：从“能跑一次”升级为“能长期、安全、可恢复地跑”。

为什么排在这里：

- 远程消息的最大风险是同一 session 并发写 stdin 或错乱恢复上下文。
- `1.1` 多次强调 Send 与 Events 必须并发处理，忙碌期间普通消息应排队。
- `2.3` 把 SessionManager、busy queue、permission、audit 列为 P0。

要做的事情：

1. `AgentSessionRepository`
   - 保存本地 session id、`sessionKey`、active session、name、history、userMeta。
   - 单独保存 Agent 原生会话映射：`agentType`、`agentSessionId`、`pastAgentSessionIds`、`resumePolicy`。
   - 切 Agent、切 provider、`/new` 时能清理当前 agent session id，但保留必要历史。

2. session lock 和 pending queue
   - 同一个 `sessionKey` 同时只允许一个普通 turn。
   - 忙碌时普通消息进入队列。
   - 不默认中途写 stdin；只为明确支持的 `/btw` 类能力留扩展。

3. Claude Code adapter
   - 启动长期 `claude --input-format stream-json --output-format stream-json --permission-prompt-tool stdio`。
   - `send()` 写入一行 user JSON。
   - stdout stream-json 映射为 `AgentEvent`。
   - `control_request` 映射为 `permissionRequest`，用户决策再通过 `control_response` 写回。

4. PermissionGuard + AuditSink 接入
   - `agent.spawn`、`shell.exec`、`secret.read/write`、`fs.write` 必须进入权限检查。
   - agent/remote actor 默认不能直接 allow。
   - 每次远程触发敏感动作必须记录 audit。

5. 输入治理和输出治理
   - 支持 disabled commands。
   - 支持 admin allowlist，敏感命令默认只允许管理员。
   - 支持角色、用户限流和默认限流。
   - 支持 banned words。
   - 支持 outgoing rate limit，避免消息平台风控。
   - 平台 connector 侧还要有 dedupe、旧消息过滤、allowlist、群聊 @ 过滤。

成功标准：

- 同一个 session 连续多轮能恢复 Agent 原生上下文。
- 同一 session 忙碌时新消息不会破坏 CLI 协议。
- Claude Code 权限请求能变成可处理的 pending state，并能回写 allow/deny。
- Agent spawn 和 shell exec 有审计记录。
- 远程入口接入前，禁用命令、管理员命令、限流、敏感词和去重策略已经有统一位置。

## 第三步：Provider、模型与基础命令控制

目标：补齐 Agent 运行参数的产品状态，让用户可以在 Synapse 内切换模型、provider、mode，而不是依赖手改配置。

为什么排在这里：

- `/model`、provider 切换会改变下一次 AgentSession 的启动参数。
- 如果先做 Feishu，再补 provider，就会出现远程命令能收但无法可靠改变本机运行时配置的问题。
- `2.3` 把 Provider/Model 生态列为 P0。

要做的事情：

1. `ProviderConfigService`
   - 全局 provider。
   - 项目 provider refs。
   - active provider/model。
   - secretRef，密钥不进 renderer。

2. Agent-specific runtime view
   - Codex：写 `$CODEX_HOME/config.toml`、`auth.json`，并在 CLI args 注入 `model_provider`、`openai_base_url`、`model_reasoning_effort`。
   - Claude Code：注入 env vars，必要时启动本地 provider proxy。

3. 基础 command router
   - 内置 `/model`、`/mode`、`/new`、`/status` 先做。
   - 这些命令由 Engine 内部处理，不发给 Agent。
   - 改 model/mode 后要关闭当前 AgentSession，清理当前 agent session id，让下一轮使用新参数。

成功标准：

- Codex 和 Claude Code 都能从同一份 provider 配置生成各自需要的运行配置。
- `/model` 能修改配置、持久化，并让下一轮 AgentSession 生效。
- 未知 slash command 的策略明确：要么提示后继续发给 Agent，要么拦截，不允许行为含糊。

## 第四步：Management/Renderer API、Bridge 协议与本地 Side-channel

目标：把本机运行时变成可管理、可观察、可被外部 adapter 接入的服务。

为什么排在 Feishu 前：

- Bridge 是平台无关的外部适配器协议，可以先验证 `register/message/reply/update/card_action`。
- Web/renderer chat 可以作为第一个 Bridge adapter，比飞书更容易调试。
- Feishu 只是其中一个具体 connector，不应成为协议设计的唯一来源。

要做的事情：

1. Management API surface
   - 先通过 typed IPC 暴露，不必照搬 CC Connect 的 HTTP Web 管理服务器。
   - 最小包含 `status`、`projects`、`sessions`、`send`、`providers`、`bridge`。
   - 可选 localhost API 必须走 NetworkServiceRegistry 和 token。

2. BridgeAdapterService MVP
   - 支持 adapter `register`。
   - 支持 `message` 输入转 `AgentMessage`。
   - 支持 `reply`、`update_message`、`typing`、`card_action`。
   - 支持 session list/create/switch/delete 的最小协议。

3. Renderer Chat
   - 只做薄 UI，用现有 shadcn/Radix 基线。
   - 不照搬 CC Connect Web 的视觉样式。
   - 不在 UI 中写架构解释和产品废话。

4. 本地 side-channel API
   - 给 Agent 工具调用提供本机受控入口。
   - 至少支持 `send`：Agent 可把生成的文本、图片、文件回传到当前 session。
   - 后续支持 `cron add`、`relay send`。
   - Engine 启动 AgentSession 时注入 `CC_PROJECT`、`CC_SESSION_KEY` 和 CLI/API 路径。
   - side-channel 输出仍必须回到 AgentRuntime/Platform 回传层，不让 Agent 直接耦合 Feishu 或 Bridge。
   - API 只能本机访问；Unix socket、named pipe 或 localhost token 三选一，按 Electron 跨平台能力落地。

成功标准：

- renderer 可以通过 Bridge/IPC 向某个 project/session 发消息。
- AgentEvent 可以回到 renderer timeline。
- 外部 adapter 协议不依赖飞书 SDK。
- Management 状态能看到项目、会话、provider、Bridge adapter。
- Agent 能通过本机 side-channel 把生成文件或补充消息发回当前 session。

## 第五步：Connector 基座与 Feishu/Lark

目标：实现第一个真实远程入口。

为什么现在做：

- 前面已经有 Engine、session、permission、provider、Bridge/management。
- 飞书消息只需要转成 `AgentMessage`，不需要自己处理 Agent 运行时。
- 飞书主动回传依赖 session/reply context，此时已有基础。

要做的事情：

1. ConnectorRepository
   - 保存 platform、secretRef、status、owner、allowlist、sessionKeyPolicy、lastConnectedAt、lastError。
   - app secret 进入 secrets namespace，不进入 renderer 长期状态。

2. Feishu setup
   - `begin`：调用 app registration `action=init/begin`，返回 `device_code`、`qr_url`、`interval`。
   - `poll`：用 `device_code` 轮询，处理 Feishu/Lark 域切换、pending、slow_down、denied、expired、completed。
   - `save`：保存 `app_id/app_secret` 到 secrets/connectors，返回是否需要 restart/reconnect。

3. Feishu runtime
   - 用 app id/secret 建立 WebSocket 长连接。
   - `im.message.receive_v1` 转 `AgentMessage`。
   - 支持去重、旧消息过滤、群聊 @ 过滤、allowlist。
   - 生成稳定 `sessionKey`。
   - 实现 `ReplyContextReconstructor`，为后续 Cron/Heartbeat 主动回传做准备。
   - Reply 优先使用 Feishu Reply API，必要时 Create API。
   - token 失效和网络瞬断要重试。

成功标准：

- 本机能展示 Feishu/Lark 二维码并保存凭证。
- Feishu 消息能进入 AgentRuntime。
- Agent 最终回复能回到 Feishu。
- 权限请求能以按钮或文本方式回到 Feishu，并能回写 Agent。

暂时不做：

- 不做微信/企业微信。
- 不做复杂多平台菜单。
- 不做语音。

## 第六步：多工作区与频道绑定

目标：让一个机器人入口服务多个本地仓库/目录，每个频道或话题绑定独立 workspace、Agent 和 session。

为什么在 Feishu 之后：

- 多工作区依赖真实平台的 `channelKey`、`sessionKey`、群/话题规则。
- Engine、SessionManager、Connector 都稳定后，再加 workspace-aware router，风险更低。

要做的事情：

1. Project 配置增加 `mode`、`baseDir`
   - `mode = "multi-workspace"` 时必须有 `baseDir`。
   - 同时禁止项目 Agent 固定 `workDir`。

2. WorkspaceBindingRepository
   - `project:<projectId>` 和 `shared` 两层绑定。
   - key 必须包含 platform name，避免不同平台频道 ID 碰撞。
   - 支持绑定外部修改刷新，或提供统一管理入口，避免多写方冲突。

3. workspace 解析器
   - 先查绑定。
   - 再按频道名约定匹配 `baseDir/<channel-name>`。
   - 最后进入初始化流。

4. per-workspace runtime
   - workspace pool 懒创建 Agent 和 SessionManager。
   - internal key 使用 `workspace:sessionKey`。
   - 注入给 Agent 的 `CC_SESSION_KEY` 仍然使用原始 sessionKey，不能泄露 internal key。
   - 父 Agent 的 provider、model、mode、run_as 扩展配置必须复制到 workspace Agent。

5. `/workspace` 命令
   - 至少支持查看、bind、route、init、unbind、list。
   - slash command 优先于初始化流。

成功标准：

- 同一个 Feishu 机器人在不同群/话题可以落到不同本地目录。
- 不同 workspace 的 active session、history、agent native session id 不互相污染。
- idle workspace 可以回收 AgentSession，但保留 session 持久化，下次透明恢复。

## 第七步：定时任务与主动回传

目标：实现定时触发 Agent 或受控 shell 命令，并把结果发回原 session。

为什么在 connector 和多工作区之后：

- Cron 没有新的平台入站消息，必须依赖 `sessionKey -> replyCtx` 重建。
- 多工作区会影响 `job.WorkDir`、workspace session、interactive key。
- Shell exec 是高权限能力，必须等 PermissionGuard/AuditSink 可用。

要做的事情：

1. ScheduledJob schema
   - `id/projectId/sessionKey/cronExpr/prompt/exec/workDir/enabled/silent/mute/sessionMode/mode/timeout/lastRun/lastError`。
   - `prompt` 和 `exec` 必须互斥。

2. SchedulerService
   - 启动时恢复 enabled job。
   - 新增/修改/禁用时动态注册或反注册。
   - callback 里只保存 job id，触发时重新读取最新 job。

3. Prompt job
   - 构造 synthetic `AgentMessage`。
   - `UserID/UserName` 标为 scheduler/cron。
   - 仍走 AgentRuntime 的 session lock、queue、permission、event loop。
   - 支持 `reuse` 和 `new_per_run`。

4. Exec job
   - 不进入 Agent。
   - 通过受控 shell runner 执行，必须经过 `shell.exec` 权限检查和 audit。
   - 有 timeout、输出截断、工作目录限制。
   - Windows/macOS/Linux shell 差异要显式处理，不能默认永远有 `sh`。

5. 主动消息回传
   - 平台必须实现 reply context 重建。
   - silent 只隐藏开始通知。
   - mute 隐藏开始和结果，只写运行状态。
   - 失败写 `lastError`，成功写 `lastRun` 并清理错误。

成功标准：

- 重启后 enabled job 自动恢复。
- 到点后重新读取最新配置。
- prompt job 能像普通消息一样进入 AgentRuntime。
- exec job 有权限检查、审计、timeout 和输出截断。
- 结果能主动回到 Feishu/Bridge 原 session。

## 第八步：长任务体验与命令/技能生态

目标：让远程控制从“能用”变成“可观察、可操作、可扩展”。

为什么在主功能之后：

- stream preview、progress、references、skills 都依赖稳定的 AgentEvent、Bridge capabilities 和 command router。
- 这些不应阻塞本机闭环和远程闭环，但会显著提升可用性。

要做的事情：

1. Stream preview
   - Agent 文本增量更新到同一条消息。
   - Bridge 保留 `preview_start`、`update_message`。
   - Renderer timeline 可以直接展示结构化 event，不必完全模拟消息平台。

2. Compact progress
   - thinking/tool/tool result 统一成紧凑进度状态。
   - 平台能力不足时降级为文本。

3. Local references 与 `/show`
   - 解析本地路径、Markdown link、line/column。
   - 按当前 workspace 约束路径，避免泄露任意文件。
   - Renderer 可升级成点击打开文件/定位行。

4. Custom commands 与 skills
   - `CommandRegistry` 管内置命令、自定义 prompt/exec 命令、Agent 原生命令文件。
   - `SkillRegistry` 发现 `SKILL.md`，生成 invocation prompt。
   - `CommandPublisher` 发布到 renderer command palette、Bridge capabilities、远程平台菜单。
   - exec 型 command 必须走 PermissionGuard 和 audit。

成功标准：

- 长任务执行时用户能看到进度，不会以为卡死。
- 远程平台和 renderer 都能使用同一套命令/技能发布机制。
- 本地代码引用可以安全地在当前 workspace 内渲染和打开。

## 第九步：自动化入口与 Agent 协作

目标：在稳定运行时之上补自动化和多 Agent 协作能力。

要做的事情：

1. Heartbeat
   - 周期性向某个 session 发心跳 prompt。
   - 仍走 AgentRuntime，不绕过 session lock。
   - 支持 only_when_idle、pause/resume、立即执行、状态查询。

2. Webhook
   - 外部系统可 POST prompt 或 exec。
   - prompt 进入 AgentRuntime。
   - exec 必须权限检查和审计。
   - 需要 token 认证、限流、payload 记录。

3. Relay
   - 项目间可寻址。
   - relay session 独立于用户主会话。
   - 超时返回部分响应，但不杀 Agent，后台 drain 并保存 session。
   - 请求/响应可审计、可在 UI 中看到。

4. Auto-compress
   - 先做手动 `/compress`。
   - 自动压缩必须在同一 session lock 内执行，且压缩后继续 drain queued messages。

成功标准：

- Heartbeat、Webhook、Relay 都复用同一 AgentRuntime 管线。
- 外部自动化入口不绕过权限、队列和审计。
- 多 Agent 协作不会污染用户主会话。

## 第十步：后置能力

这些能力有价值，但不应该进入前期主线。

后置项：

- Observer：旁路观察现有 Claude JSONL。Synapse 自己掌控 AgentSession 后，优先用内部事件流。
- STT/TTS：保留 Bridge audio schema 即可，语音 provider 可后补。
- run_as_user：企业安全版再做完整 OS 用户隔离、preflight、audit probe。
- daemon/self-update：Synapse 是 Electron 应用，不照搬 CC Connect 二进制自更新；可迁移服务状态页、日志定位、重启提示、单实例锁。
- 更多平台：微信、企业微信、Slack、Telegram、Discord 等应在 Feishu/Lark 模式稳定后再接。

## 建议的里程碑口径

MVP 1：本机 Agent 闭环

- 覆盖第零步、第一步。
- 能在 Synapse 内发 prompt 给 Codex，并拿回结果。

MVP 2：可持续本机会话

- 覆盖第二步、第三步。
- 有 session persistence、busy queue、Claude Code 权限闭环、输入治理、provider/model 切换。

MVP 3：本机管理与 Bridge

- 覆盖第四步。
- Renderer/Bridge 能管理项目、session、provider，并作为外部 adapter 收发消息；Agent 能通过本地 side-channel 主动回传。

MVP 4：Feishu 远程控制

- 覆盖第五步。
- 飞书扫码连接、远程消息进 AgentRuntime、结果回飞书。

MVP 5：团队多仓库与自动化

- 覆盖第六步、第七步。
- 多工作区频道绑定、定时任务、主动回传可用。

完整 CC Connect-like 体验

- 覆盖第八步到第十步中需要的部分。
- 有长任务体验、命令/技能生态、Webhook/Relay/Heartbeat、可选语音和观察能力。

## 不建议的开发顺序

不要先做 Feishu UI。

- 原因：扫码保存凭证只能解决连接配置，不能解决 AgentRuntime、session、permission、reply context。

不要先做 Cron。

- 原因：Cron 需要主动回传和 session 重建，没有 connector/session 底座会变成假功能。

不要让每个平台自己 spawn CLI。

- 原因：会丢掉 session lock、权限、history、provider、audit 和 queue。

不要照搬 CC Connect Web 样式。

- 原因：Synapse 已经有 shadcn/Radix 视觉基线，迁移信息架构和 API 即可。

不要把 shell exec 当普通 prompt。

- 原因：exec 是本机高权限能力，必须有 PermissionGuard、AuditSink、timeout、输出截断和工作目录限制。
