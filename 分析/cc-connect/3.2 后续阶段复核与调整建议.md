## 总结论

原 `3.1` 的大方向仍然正确：

```text
AgentRuntime
-> 会话/队列/权限/治理
-> Provider/命令
-> 管理/Bridge/Side-channel
-> Feishu/Lark
-> 多工作区
-> Scheduler/Cron
-> 体验层和扩展能力
```

但后续阶段需要做三个调整：

1. 原第四步过大，应该拆成两个连续阶段。
2. 在接入外部入口前，必须提前补 `持久化审计`、`ReplyTarget/Outbox`、`命令策略` 三个稳定层。
3. 原第四步里的 `cron add`、`relay send` side-channel 不应提前做；第四步只做 `send`，cron/relay 留到对应阶段。

## 为什么需要调整

### 1. 第四步原范围过大

`3.1` 原第四步同时包含：

- typed IPC / Management API
- Renderer Chat
- BridgeAdapterService
- 本地 side-channel API
- `send/cron/relay` API

这几个能力都依赖 AgentRuntime，但彼此也有先后关系。尤其是 Renderer Chat 和 Management API 是调试 Bridge/Feishu 的最小可视入口；Bridge 和 side-channel 则需要更完整的 reply target、adapter 注册、鉴权、会话列表和附件策略。放在同一步里容易一次改动过大。

### 2. 当前 AuditSink 仍是 in-memory

`4.0`、`5.0`、`6.0` 报告都记录了 `core.audit-sink` 仍是 in-memory。到目前为止问题可接受，因为功能还在本机 main 侧单测内运行。

但从下一阶段开始，renderer、Bridge、side-channel、Feishu 都是外部或半外部入口。远程控制本机 Agent 的行为必须能落到持久化审计，否则出问题后无法追溯 actor/action/resource/outcome。

### 3. ReplyTarget/Outbox 应该早于 Feishu 和 Cron

`1.1` 明确指出 side-channel 的 `send` 最终要回到当前 platform/session；`1.4` 明确指出 Cron 没有新入站消息，必须通过 `sessionKey -> replyCtx` 重建主动回复目标；`1.2` 也要求 Feishu 运行时能保存和重建 reply context。

因此需要先有一个平台无关的回复目标层：

- renderer timeline 可以作为第一个 reply target。
- Bridge adapter 可以注册自己的 reply target。
- Feishu 后续只实现自己的 reconstructor。
- Cron/Heartbeat 最后复用同一层主动回传。

### 4. 命令策略需要在 Bridge/Feishu 前补清楚

`1.5` 说明 CC Connect 的 slash command 有三种结果：

- 内置控制命令由 Engine 处理，不发给 Agent。
- custom command / skill 展开成 prompt 后发给 Agent。
- 未识别 slash command 会提示未知，但随后按普通 prompt 继续发给 Agent。

当前第三步为了安全，选择了未知 slash command 返回 `Unsupported command`，不转发给 Agent。这个策略适合作为远程入口默认值，但它和 CC Connect 对 Agent-native slash command 的兼容行为不同。后续如果 renderer/Bridge/Feishu 需要支持类似 `/plan-status` 的 Agent 原生命令，不能靠隐式放行，应该显式做命令分类和 allowlist。

## 调整后的后续顺序

### 8.0：第四步 A - Management IPC、Renderer Chat、审计和回复目标

目标：先让本机管理和本机聊天可用，并把后续外部入口需要的稳定层补齐。

建议范围：

1. `DataRepositoryAuditSink`
   - 把 `AuditSink.record()` 写入 `audit` namespace。
   - 保留测试用 in-memory sink，但 production bootstrap 默认使用持久化 sink。
   - 敏感 metadata 做最小化，不能记录 secret 明文。

2. `ReplyTarget` / `Outbox` 最小层
   - 定义平台无关的回复目标、主动回传结果和失败记录。
   - renderer/local session 先作为第一个 target。
   - outbox 先支持最小 `pending/sent/failed`，后续 Feishu/Bridge 可扩展 retry。

3. typed IPC / preload API
   - 只暴露窄接口，renderer 仍只能走 `window.synapse.*`。
   - 最小包含 `status`、`sessions`、`send`、`providers`、`pendingPermissions`。
   - 不做 Cron、Relay、Feishu setup。

4. Renderer Chat 薄界面
   - 使用现有 shadcn/Radix 基线。
   - 只做本机 session 列表、消息输入、AgentEvent timeline、权限请求处理。
   - 不做营销文案、不做复杂视觉、不做 Provider 完整配置页。

5. 命令策略补强
   - 把命令路由明确分为 built-in、registered prompt command、agent-native passthrough、unsupported。
   - 远程入口默认不放行未知 slash。
   - 本机 renderer 可以提供明确的“作为普通消息发送”策略，或用 allowlist 支持 Agent-native slash。

成功标准：

- 本机 UI 可以发消息到 AgentRuntime 并看到 AgentEvent timeline。
- `/model`、`/mode`、`/new`、`/status` 在 UI/IPC 入口仍然不进 Agent。
- permission request 能显示并回写。
- 审计落库。
- reply/outbox 基础模型可被 Bridge/Feishu/Cron 复用。

### 9.0：第四步 B - BridgeAdapterService 与本地 side-channel send

目标：让外部 adapter 和 Agent 自己的本地回传先跑通，但不提前做 Feishu/Cron/Relay。

建议范围：

1. BridgeAdapterService MVP
   - 支持 `register`、`message`、`reply`、`update_message`、`typing`、`card_action`。
   - 支持 adapter capabilities。
   - 支持 sessions list/create/switch/delete 的最小协议。
   - WebSocket/localhost 服务必须通过 `NetworkServiceRegistry`，默认只绑本机地址并使用 token。

2. BridgePlatform/ReplyTarget
   - Bridge adapter 看起来像一个 platform/reply target。
   - Bridge 输入统一转 `AgentMessage`。
   - Bridge 输出统一走 ReplyTarget/Outbox。

3. 本地 side-channel `send`
   - 只做 `send`：文本、图片、文件回当前 session。
   - 注入 `CC_PROJECT`、`CC_SESSION_KEY` 和受控 CLI/API 路径。
   - 文件/图片路径读取必须走 main process 权限边界。
   - 不做 `cron add`，不做 `relay send`。

4. 附件策略
   - 定义大小限制、MIME 检测、路径约束、错误回传。
   - Agent 侧传来的本地路径不能直接暴露给 renderer 或远程平台。

成功标准：

- 外部测试 adapter 可以注册并发送消息。
- Bridge adapter 能收到 reply/update/typing。
- Agent 可以通过 side-channel `send` 把文本或文件回传当前 session。
- 不依赖 Feishu SDK。

### 10.0：第五步 - Connector 基座与 Feishu/Lark

目标：实现第一个真实远程入口。

原顺序仍然成立：Feishu 不应早于 Bridge/side-channel。

需要补强的成功标准：

- Feishu setup 的 begin/poll/save 通过 typed IPC 或 Management API 暴露。
- app secret 只进 `secrets` namespace。
- `ConnectorRepository` 必须记录 status、owner、allowlist、sessionKeyPolicy、lastConnectedAt、lastError。
- Feishu WS 入站只做消息标准化，不能绕过 AgentRuntime。
- 旧消息过滤、去重、群聊 @、allowlist 必须复用第二步治理能力。
- Feishu reply context 必须能被 ReplyTarget/Outbox 重建，为 Cron/Heartbeat 做准备。
- token/network retry 的失败要进入 connector status 和 audit。

执行时建议拆成两个提交或两个子任务：

1. setup/credential/status。
2. runtime WS/reply/permission。

### 11.0：第六步 - 多工作区与频道绑定

原顺序仍然成立：多工作区最好放在 Feishu 或至少一个真实平台入口之后，因为需要真实 channel/session 规则验证。

需要补强的点：

- `sessionKey`、`channelKey`、`workspaceKey` 要分清。
- 内部 workspace key 不能泄露给 `CC_SESSION_KEY`。
- `/workspace` 命令必须优先于初始化流。
- per-workspace Agent 必须继承 provider/model/mode/security 配置。
- workspace idle reaper 不能回收正在执行 turn。
- 绝对路径 route 需要 PermissionGuard 或 allowlist 策略，不能直接复刻宽松行为。

### 12.0：第七步 - Scheduler、Cron、Heartbeat 与主动回传

原顺序仍然成立：Cron 必须在 connector/reply target/multi-workspace 之后。

调整点：

- `cron add` side-channel 放到本阶段，不放在 9.0。
- `exec` job 必须有更强权限审计；远程入口创建 exec job 要比 prompt job 更严格。
- `prompt` 和 `exec` 必须互斥。
- `silent` 和 `mute` 语义要区分。
- timeout 后要记录 job 状态，并明确是否取消 Agent turn。
- Cron 触发必须走 AgentRuntime queue/lock，不直接调用 adapter。

### 13.0：第八步 - 体验层、命令/技能生态

这一步不应完全等到所有后续完成才开始，但要分层推进。

应提前到 8.0 做的部分：

- 最小 timeline。
- permission request UI。
- 命令策略分类。

保留在 13.0 的部分：

- stream preview。
- compact progress。
- references/local file jump。
- full CommandRegistry。
- Skills/Custom Commands 发布到 renderer command palette 和 Bridge capabilities。
- Agent-native slash allowlist 的产品化配置。

### 14.0：第九步 - Webhook、Relay、run_as_user、自动压缩和运维增强

这些仍然是后置能力，不阻塞 Feishu/Multi-workspace/Cron MVP。

建议顺序：

1. run_as_user / OS isolation：在开放高权限 exec 或企业使用前补。
2. Webhook：复用 AutomationIngressService，必须强鉴权。
3. Relay：复用多工作区和 ReplyTarget。
4. Auto-compress：必须在 session lock 内执行。
5. Observer/STT/TTS/Hooks：按实际产品需求推进。

## 新旧顺序对照

| 原顺序 | 原大块 | 调整后 |
| --- | --- | --- |
| 4 | Management/Bridge/Side-channel | 拆为 8.0 Management IPC/Renderer/审计/ReplyTarget 和 9.0 Bridge/side-channel send |
| 5 | Feishu/Lark | 保留，但要求先完成 8.0/9.0；执行时建议拆 setup 与 runtime |
| 6 | 多工作区 | 保留，补充 provider/security 继承和 channelKey/workspaceKey 边界 |
| 7 | Scheduler | 保留，`cron add` 从原第四步移动到 Scheduler 阶段 |
| 8 | 体验层 | 拆出最小 timeline/权限 UI 到 8.0，完整体验和命令/技能生态留到 13.0 |

## 后续任务书编写规则

从 8.0 开始，每个新阶段任务书都必须额外包含：

1. 当前阶段是否引入外部入口。
2. 是否需要持久化审计。
3. 是否需要 ReplyTarget/Outbox。
4. 是否会处理 slash command。
5. 是否会读取本地文件或发送附件。
6. 是否会绑定端口、socket 或 named pipe。
7. 是否会让远程用户触发 shell/文件写入/secret 读取。

如果任一项为“是”，任务书必须写清楚 PermissionGuard、AuditSink、NetworkServiceRegistry 和 DataRepository 的接入点。

## 最终判断

不需要推翻 `3.1`，但需要把第四步拆细并提前补强安全和回传基础设施。

推荐下一份执行任务书不要直接叫“第四步全部”，而应叫：

```text
8.0 第四步 A：Management IPC、Renderer Chat、持久化审计与回复目标
```

完成 8.0 后再做：

```text
9.0 第四步 B：BridgeAdapterService 与本地 side-channel send
```

这样后续 Feishu、Multi-workspace、Scheduler 的返工风险最低。
