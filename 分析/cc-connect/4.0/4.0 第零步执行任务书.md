## 任务目标

只执行 `分析/cc-connect/3.1 整体开发顺序.md` 中的“第零步：地基整理”，不要提前实现 AgentRuntime、Feishu、Cron、Bridge UI 或多工作区。

第零步的目标是让后续 AgentRuntime、Connector、Scheduler 都能按 Synapse 当前 Electron/React/Tailwind/shadcn 架构接入，避免为 CC Connect 另起一套平行系统。

必须完成的方向：

1. 补齐全局 runtime 服务注册。
2. 补齐 project-scoped persistence。
3. 把 CC Connect 后续需要的占位 schema 升级成真实可用的业务 schema。
4. 定义并落地 Agent 子进程启动边界。
5. 定义并落地本地网络服务边界。

## 最高优先级约束

### 先读源码，再开发

每开发一个模块或机制，都必须先查 CC Connect 源码中对应逻辑，再决定 Synapse 中怎么实现。

只有两类情况可以不查 CC Connect 对应逻辑：

1. 纯粹使用 Synapse 已有基础设施，例如 ServiceRegistry、IpcRegistry、DataRepository、EventBus、PermissionGuard、ProjectContainer、NetworkServiceRegistry 的本地用法。
2. 只是按 Synapse 当前架构做依赖注入、测试、类型修正，不是在复刻 CC Connect 的业务方法。

只要是在复刻 CC Connect 的方法、边界、状态模型、权限策略、服务装配、网络入口、side-channel、session、provider、connector、scheduler 等思想，就必须去 `/Users/liyang/Documents/code/demo/cc-connect-main` 找原始代码，并在本任务产物中记录：

## 第零步实现范围

### 1. 全局 runtime 服务注册

目标：新增业务服务不再拿 placeholder。

当前 Synapse 里 `ServiceContext` 仍有 placeholder：

- `desktop/electron/runtime/service-registry/types.ts`
- `desktop/electron/bootstrap/registry.ts`

需要检查并处理：

- DataRepository 是否应成为 `core.data-repository` 或类似 service。
- PermissionGuard/AuditSink 是否应成为可注入 service。
- ProcessRuntime 是否应成为可注入 service。
- NetworkServiceRegistry 是否应成为可注入 service。
- ProjectContainerRegistry 是否应成为可注入 service。
- `buildContext()` 是否应从 registry 取真实对象，而不是继续塞 `{ __placeholder: undefined }`。

要求：

- 遵守 AGENTS.md：新代码不要 `export default new XxxService()`。
- 所有服务通过 ServiceRegistry descriptor 装配。
- runtime 目录保持纯基础设施，不 import `desktop/electron/services/*` 业务代码。

### 2. Project-scoped persistence

目标：后续 agent sessions、connectors、scheduled jobs、outbox 不串项目。

当前文件：

- `desktop/electron/runtime/project-container/scoped-data-repo.ts`
- `desktop/electron/runtime/project-container/types.ts`
- `desktop/electron/runtime/data-repo/`

当前问题：

- `ProjectScopedDataRepoImpl.namespace()` 仍是 pass-through。

需要实现真实 project scope。可以选择以下之一，但必须解释取舍：

1. 命名空间路径级隔离：`projects/<projectId>/<namespace>`
2. 数据字段级隔离：统一 schema 带 `projectId`
3. backend adapter 包装：写入时自动补 `projectId`，读取时自动过滤

要求：

- 不破坏已有 config/repository 数据。
- 给 project scope 写专门测试。
- 明确哪些 namespace 是全局，哪些是 project scoped。

### 3. 业务 schema 从 placeholder 升级

目标：第零步先定义后续可用的数据形状和迁移边界，不一定实现所有业务功能。

当前文件：

- `desktop/electron/runtime/data-repo/schemas/placeholders.ts`
- `desktop/electron/runtime/data-repo/schemas/index.ts`

至少需要认真设计这些 schema：

- `providers`
- `projects`
- `connectors`
- `conversations`
- `audit`
- `outbox`

建议新增或完善：

- provider：`id/schemaVersion/kind/display/baseUrl/secretRef/models/activeModel/options`
- connector：`id/schemaVersion/projectId/platform/secretRef/status/allowlist/sessionKeyPolicy/lastConnectedAt/lastError`
- conversation/session：`id/schemaVersion/projectId/sessionKey/agentType/agentSessionId/pastAgentSessionIds/history/userMeta/active/name`
- outbox：`id/schemaVersion/projectId/destination/payload/attempts/lastError/status/createdAt/updatedAt`
- audit：`id/schemaVersion/action/actor/resource/outcome/timestamp/metadata/projectId/sessionId`

要求：

- 每个 schema 有 validator。
- 如果修改现有 schema version，补 migration 或明确还在 v1 兼容期。
- 保证 `pnpm desktop:typecheck` 通过。

### 4. Agent 子进程启动边界

目标：先定义统一边界，后续 AgentRuntime 不能散落 `child_process.spawn()`。

当前文件：

- `desktop/electron/runtime/process/runtime.ts`
- `desktop/electron/runtime/security/permission-guard.ts`

当前问题：

- `ProcessRuntime` 只支持 `kind="main"`。
- 还没有面向 Agent CLI 的统一 spawn runner。

可行策略：

- 第零步先增加一个受控子进程接口或服务边界，不一定完整实现所有 Agent adapter。
- 这个边界必须能表达：
  - actor
  - action: `agent.spawn` 或 `shell.exec`
  - cwd
  - env allowlist
  - command/args
  - timeout/abort
  - stdout/stderr 机器可读约束
  - audit 记录

要求：

- 如果短期仍用 Node `child_process.spawn()`，必须只允许通过统一 runner 使用。
- 不要在 React/renderer 中暴露任何 raw spawn/shell 能力。
- 受控 runner 必须有单元测试，覆盖 allow/deny/audit。

### 5. 本地网络服务边界

目标：Bridge、localhost API、Webhook 以后不能各自随便 bind port。

当前文件：

- `desktop/electron/runtime/network/registry.ts`

当前能力：

- 已有 port allocator skeleton。
- 还未承载实际 HTTP/WS server lifecycle。

第零步至少要做到：

- 明确 `NetworkServiceRegistry` 是否只负责端口分配，还是也负责 start/stop。
- 如果目前不启动真实 server，也要有可扩展 descriptor，能表达：
  - role: `http`/`websocket`
  - bindAddress
  - preferredPort
  - auth strategy
  - lifecycle stop
  - audit hook
- 测试端口冲突、默认 `127.0.0.1`、重复注册、unregister。

## 验收标准

完成后必须满足：

- 新的 runtime/service 依赖不是 placeholder。
- project-scoped persistence 有真实隔离或明确可测试的 projectId 过滤。
- providers/connectors/conversations/audit/outbox schema 能支撑后续 AgentRuntime、Feishu、Scheduler。
- Agent spawn/shell exec 有统一边界，不允许后续业务散落 spawn。
- 本地网络服务边界清楚，默认不会隐式监听公网地址。
- 测试记录、问题修复记录、最终报告都在 `分析/cc-connect/4.0/`。
- 类型检查和相关测试通过；如有失败，必须记录并说明为什么与本任务无关。
