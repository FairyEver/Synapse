# 4.0 源码映射

本文件只覆盖“第零步：地基整理”。所有 CC Connect 依据均来自 `/Users/liyang/Documents/code/demo/cc-connect-main` 原始源码；实际生产代码仍落在 Synapse 的 `desktop/electron/**`。

## 1. 全局 runtime 服务注册

Synapse 当前相关文件：

- `desktop/electron/bootstrap/registry.ts:41-52` 只注册已有 11 个启动服务。
- `desktop/electron/bootstrap/registry.ts:57-68` 的 `buildContext()` 仍给 `dataRepo/eventBus/permissionGuard/processRuntime` 塞 placeholder。
- `desktop/electron/bootstrap/descriptors.ts:53-267` 已有 logging/config/window/event-bus/data-store 等 descriptor。
- `desktop/electron/runtime/service-registry/types.ts:17-45` 仍保留 DataRepository/EventBus/PermissionGuard/ProcessRuntime placeholder 类型。

CC Connect 对应源码：

- `cmd/cc-connect/main.go:163` 先 `config.Load(configPath)`。
- `cmd/cc-connect/main.go:199` 创建 Agent，`:215` 创建 Platform，`:246` 创建每个项目的 `core.NewEngine(...)`。
- `cmd/cc-connect/main.go:338-424` 将 banned words、disabled commands、admin allowlist、roles、rate limit 等配置统一注入 Engine。
- `cmd/cc-connect/main.go:707-721` CronStore/CronScheduler 创建后按项目 `RegisterEngine`。
- `cmd/cc-connect/main.go:768-804` Bridge/Webhook/Management server 都是全局创建，再按项目绑定 Engine。
- `cmd/cc-connect/main.go:957-976` APIServer/RelayManager 也是全局创建，再按项目注册 Engine。

设计依据：

- CC Connect 的装配集中在启动层，不让平台、管理 API、cron 各自 new 自己的 Engine。
- Synapse 应把基础设施对象注册成真实 `ServiceDescriptor`，让后续 CC Connect 业务服务通过 `ServiceRegistry.get<T>()` 或 `ServiceContext` 拿依赖。

采用方案：

- 在 `desktop/electron/bootstrap/descriptors.ts` 增加 `core.data-repository`、`core.permission-guard`、`core.audit-sink`、`core.process-runtime`、`core.network-registry`、`core.project-containers`。
- 在 `desktop/electron/bootstrap/registry.ts` 注册这些 descriptor，并把 `buildContext()` 改为 registry-backed 的真实 typed proxy，避免 placeholder。
- `core.project-containers` 依赖 `core.event-bus` 和 `core.data-repository`，用于后续 project-scoped 服务。

不采用方案及原因：

- 不把 AgentRuntime、Feishu、Cron 放进本次注册：任务明确禁止提前实现。
- 不在 `runtime/*` 里 import 业务 `services/*`：AGENTS.md hard constraints 要求 runtime 保持纯基础设施。

## 2. Project-scoped persistence

Synapse 当前相关文件：

- `desktop/electron/runtime/project-container/types.ts:74-90` 声明 `ProjectScopedDataRepo` 会自动继承 projectId。
- `desktop/electron/runtime/project-container/scoped-data-repo.ts:15-23` 当前 `namespace()` 是 pass-through。
- `desktop/electron/runtime/project-container/registry.ts:47-59` 每个 ProjectContainer 已经构造 scoped dataRepo/eventBus。
- `desktop/electron/runtime/data-repo/types.ts:18-39` 的 `DataNamespace` 已支持 `list(filter?: Partial<T>)`。

CC Connect 对应源码：

- `core/session.go:17-30` `Session` 保存 `AgentSessionID`、`AgentType`、`PastAgentSessionIDs`、`History`。
- `core/session.go:181-204` `sessionSnapshot` 保存 sessions、activeSession、userSessions、sessionNames、userMeta、schema version。
- `core/session.go:225-237` `NewSessionManager(storePath)` 从项目 session file 加载。
- `cmd/cc-connect/main.go:223-228` 每个项目根据 `cfg.DataDir`、项目名和 workDir 生成独立 sessionStorePath。
- `core/engine.go:373-380` `NewEngine` 为单项目创建 `SessionManager`。
- `core/engine.go:2197-2270` 多工作区时创建 workspace agent 和 workspace session manager，继承项目隔离参数。

设计依据：

- CC Connect 用“每项目独立 session 文件”避免串项目；Synapse 已经有统一 DataRepository，更适合做字段级 projectId 隔离。
- 第零步不做多工作区，所以只需要保证项目级业务 namespace 不串项目。

采用方案：

- `ProjectScopedDataRepoImpl.namespace()` 对 `providers/connectors/conversations/outbox/audit` 返回 projectId-aware wrapper。
- wrapper 在 `upsert/setSingleton` 自动补 `projectId`，发现显式不同 `projectId` 时拒绝；`list/get/remove/onChange` 自动按 `projectId` 过滤。
- `projects/secrets/core.*` 等全局 namespace 继续 pass-through。

不采用方案及原因：

- 不采用 `projects/<projectId>/<namespace>` 路径级隔离：当前 `DataRepository` 只能返回已注册 namespace，SQLite table name 也不接受 `/`，强改会扩大范围。
- 不新增后端 adapter 层：字段级过滤已满足第零步最低要求，改动更小。

## 3. 业务 schema 从 placeholder 升级

Synapse 当前相关文件：

- `desktop/electron/runtime/data-repo/schemas/placeholders.ts:43-162` providers/connectors/conversations/audit/outbox 仍是占位形状。
- `desktop/electron/runtime/data-repo/schemas/index.ts:19-33` 对外导出这些 v1 类型。
- `desktop/electron/runtime/data-repo/__tests__/schemas.test.ts:1-121` 目前只验证最小占位字段。

CC Connect 对应源码：

- Provider/项目配置：`config/config.go:85-112` 全局 Config，`:292-337` ProjectConfig，`:339-344` AgentConfig，`:353-366` ProviderConfig。
- Provider 持久化：`config/config.go:758-764` `SaveActiveProvider`，`:770-821` `SaveProviderModel`，`:851-857` `SaveAgentModel`，`:943-970` `ResolveProviderRefs`，`:2822-2844` `SaveProviderRefs`。
- 会话：`core/session.go:17-30` Session，`:181-204` snapshot，`:322-349` `SwitchToAgentSession`。
- Connector/sessionKey/allowlist/dedupe：`platform/feishu/feishu.go:696-708` 消息去重和旧消息过滤，`:728-743` 群聊 @ 和 allow_from，`:2331-2345` session key 策略，`:2585-2597` 重建 reply ctx；`platform/slack/slack.go:46-61` allow_from，`:137-142` session key，`:489-495` 重建 reply ctx；`platform/telegram/telegram.go:141-142` allow_from，`:539-548` session key，`:1225-1238` 重建 reply ctx。
- Outbox/side-channel：`core/api.go:29-36` `/send` 请求体，`:132-175` `handleSend`。
- Audit/敏感动作：`core/runas_audit.go:78-102` `IsolationReport`，`:140-160` `AuditConfig`，`:160-220` `RunIsolationProbe`。

设计依据：

- CC Connect 把 provider refs、active provider/model、session 原生 id、reply ctx 重建、connector allowlist/dedupe、主动消息发送都作为长期状态处理。
- Synapse 第零步只定义可用数据形状，不实现 provider/connector/scheduler 业务流程。

采用方案：

- 保持 schema version 为 v1，收紧 v1 数据形状；因为当前文件本来标注 “placeholder，M1+ replaces”，仓库尚无真实业务数据写入这些 namespace。
- `providers` 支持 global provider 和 project provider state：`scope/kind/baseUrl/secretRef/models/activeProviderId/activeModel/providerRefs/options/projectId`。
- `connectors` 支持 `projectId/platform/secretRef/status/allowlist/sessionKeyPolicy/reconnect/dedupe`。
- `conversations` 支持 `projectId/sessionKey/platform/agentType/agentSessionId/pastAgentSessionIds/history/userMeta/active/name`。
- `outbox` 支持 `projectId/destination/payload/attempts/status/lastError/createdAt/updatedAt`。
- `audit` 支持 `action/actor/resource/outcome/timestamp/projectId/sessionId/metadata`。

不采用方案及原因：

- 不照搬 TOML 文本保存：Synapse 已有 DataRepository，直接复刻 CC Connect 的文本补丁会绕过项目基础设施。
- 不实现 schema v2 migration：保留 v1 并从 placeholder 升级，避免无业务数据时制造空迁移。

## 4. Agent 子进程启动边界

Synapse 当前相关文件：

- `desktop/electron/runtime/process/runtime.ts:1-35` 定义 ProcessRuntime，`:52-90` 只支持 `kind="main"`。
- `desktop/electron/runtime/security/permission-guard.ts:15-24` 已有 `shell.exec`、`agent.spawn` action。
- `desktop/electron/runtime/security/permission-guard.ts:87-115` 已有 in-memory AuditSink。

CC Connect 对应源码：

- Agent 抽象：`core/interfaces.go:231-256` `Agent`/`AgentSession` 统一定义。
- Agent env 注入：`core/interfaces.go:38-42` `SessionEnvInjector`；`core/engine.go:2370-2385` 注入 `CC_PROJECT`、`CC_SESSION_KEY` 和 PATH。
- 进程启动：`agent/codex/session.go:111-128` `codex exec` 使用 `exec.CommandContext`、cwd、env、stdin/stdout；`:199-212` 构造 `codex exec/resume --json` 参数。
- Claude 隔离：`agent/claudecode/session.go:109-120` spawn 前做 run_as cheap check，`:140-153` 通过 `core.BuildSpawnCommand` 和 `FilterEnvForSpawn` 统一构造命令/env。
- run_as 边界：`core/runas.go:99-104` `SpawnOptions`，`:129-148` `BuildSpawnCommand`，`:150-174` `FilterEnvForSpawn`，`:188-221` `VerifyRunAsUserCheap`。
- 启动前隔离审计：`cmd/cc-connect/main.go:174-180` 在构造 engine/agent 前执行 run_as startup checks；`core/runas_check.go:68-82` preflight 设计；`core/runas_audit.go:160-220` 隔离 probe。

设计依据：

- CC Connect 允许 agent 子进程执行 CLI，但所有关键参数/env 都在 Engine/agent adapter 层统一注入。
- Synapse 第零步不能做 AgentRuntime，但必须提供唯一受控 runner，后续 AgentRuntime 不应散落 `child_process.spawn()`。

采用方案：

- 新增 `desktop/electron/runtime/process/controlled-runner.ts`，定义 `ControlledProcessRunner`。
- `run()` 请求必须包含 `actor/action/command/args/cwd/env/envAllowlist/timeout/output`，先走 `PermissionGuard.check({ action: "agent.spawn" | "shell.exec" })`，再 spawn。
- 结果和失败均写 `AuditSink`；默认不暴露给 renderer。

不采用方案及原因：

- 不把 `ProcessRuntime.spawn(kind="child")` 做完整实现：当前 ProcessRuntime 语义是服务进程生命周期，不适合在本步改成 Agent CLI runtime。
- 不做 run_as_user 完整 OS 用户隔离：任务要求第零步只保留扩展点。

## 5. 本地网络服务边界

Synapse 当前相关文件：

- `desktop/electron/runtime/network/registry.ts:1-44` 已有 role/auth/handler descriptor。
- `desktop/electron/runtime/network/registry.ts:45-65` registry 当前只暴露 register/unregister/list 和 conflictPolicy。
- `desktop/electron/runtime/network/registry.ts:82-133` 已有端口分配、默认 `127.0.0.1`、重复注册和端口冲突处理。
- `desktop/electron/runtime/network/ports.ts:39-48` 是唯一允许的 `net.createServer` 探测点。

CC Connect 对应源码：

- Bridge：`core/bridge.go:23-38` BridgeServer 是全局 WS server；`:158-175` 默认端口/path；`:183-192` 按项目 RegisterEngine；`:614-628` WS handler 先鉴权再升级；`:1130-1145` Bearer/Header/query token 验证。
- Management：`core/management.go:33-70` ManagementServer 全局管理 API；`:210-235` REST 路由集中注册；`:321-334` token 验证。
- Webhook：`core/webhook.go:17-26` WebhookServer；`:40-56` 默认端口/path；`:64-76` 启动 HTTP server；`:155-179` token 验证。
- Local side-channel：`core/api.go:16-27` APIServer 用 Unix socket；`:38-75` 创建 socket + 注册 `/send`、cron、relay 路由；`:103-110` server lifecycle。

设计依据：

- CC Connect 所有外部/本地入口都是全局 server，再路由到项目 Engine；并且都有显式 token 或本地 socket 边界。
- Synapse 需要统一 NetworkServiceRegistry 负责端口、bind address、auth、lifecycle，避免后续 Bridge/Webhook/API 随便 bind。

采用方案：

- 扩展 `NetworkServiceDescriptor`，在现有端口分配基础上支持可选 `start(binding)` 返回 lifecycle，以及 `audit(event)` hook。
- Registry 仍不直接创建 HTTP/WS server；它负责分配、安全默认、调用 descriptor lifecycle、unregister stop。
- 默认 bindAddress 继续为 `127.0.0.1`；只有 descriptor 明确写 `0.0.0.0` 才允许外部监听。

不采用方案及原因：

- 不迁移现有 data-store HTTP/MCP server：第零步目标是 CC Connect 地基，不扩大到现有业务 server。
- 不启动真实 Bridge/Webhook/API：任务禁止提前做 Bridge UI/Feishu/Cron/AgentRuntime。
