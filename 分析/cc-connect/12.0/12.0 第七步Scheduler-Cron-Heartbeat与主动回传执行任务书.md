# 12.0 第七步执行任务书：Scheduler、Cron、Heartbeat 与 Feishu 主动回传

## 0. 阶段定位

本阶段接在 11.0 之后执行。

11.0 已经完成 Feishu 连接器、多工作区、频道绑定、`/workspace` 命令、工作区初始化、AgentRuntime 按 workspace 隔离会话，以及 Feishu 回复上下文的保存和重建基础。

12.0 的目标是把 CC Connect 的自动化触发能力迁移到 Synapse：

- 定时任务 Cron。
- Heartbeat。
- Feishu 主动回传。
- Agent 侧通过本地 side-channel 创建定时任务。
- Feishu 侧通过 `/cron` 命令管理定时任务。
- 桌面端可以查看和管理 Feishu 定时任务。

本阶段只支持 Feishu。

不要实现 Lark、微信、Telegram、Slack、Discord、Webhook、Relay、多平台管理、多工作区外的新平台抽象 UI。可以把底层类型设计成将来可扩展，但本阶段的实际运行路径、测试路径、UI 显示范围都只落在 Feishu。

## 5. 总体实现原则

### 5.1 不允许平台绕过 Engine/AgentRuntime

定时任务触发 prompt 时，必须走统一的 AgentRuntime：

```text
Scheduler -> CronExecutionService -> synthetic AgentMessage -> AgentRuntimeService -> Agent CLI/live session -> Agent events -> ReplyTarget/Outbox -> FeishuReplyService
```

不要让 Scheduler 直接调用 Feishu connector 伪造 Agent 输出。

shell job 可以绕过 Agent，但仍必须走统一的 permission、audit、workspace resolution、Feishu active reply 和 job status 记录。

### 5.2 本阶段只支持 Feishu，但不要写死到不可扩展

允许数据模型保留 `platform`、`transport.kind`、`connectorId` 字段。

但本阶段：

- UI 只展示 Feishu。
- 命令只处理 Feishu `/cron`。
- 主动回传只要求 Feishu。
- 测试只要求 Feishu。
- 不要新增微信、Telegram、Lark 等具体实现。

### 5.3 必须保持 Phase 0 硬约束

严禁：

- 在业务服务里裸 `ipcMain.handle/on`。
- 在业务服务里裸 `webContents.send`。
- 裸 `http/net/https.createServer`。
- 用 `fs.writeFile` 存业务数据。
- 新增全局 singleton service。
- Renderer 直接使用 `ipcRenderer`。
- 空 `catch {}`。
- shell、文件写入、网络连接、Agent spawn、secret access 等敏感操作绕过 `PermissionGuard` 和 `AuditSink`。

必须运行：

- `pnpm desktop:check:hard-constraints`

### 5.4 UI 纪律

如果本阶段涉及 UI，必须先阅读：

- `.claude/rules/design.md`
- `.claude/rules/ui-rules.md`

UI 必须使用：

- shadcn/ui
- Radix
- Tailwind token
- 项目已有组件组合

禁止：

- 自定义颜色。
- hex/rgb/hsl 字面颜色。
- Tailwind 任意色值。
- 内联 `style={{...}}`，动态计算值之外不要用。
- 新 CSS module 或全局 CSS 覆盖库组件。
- 蓝紫粉渐变、彩虹字、霓虹 glow、装饰 emoji。
- 卡片套卡片。
- UI 里写“此页面用于...”这类废话。

## 7. Repository 与 Service 设计要求

### 7.1 ScheduledJobRepository

新增 repository，负责所有 job 持久化读写。

必须提供：

- `create(input)`
- `update(id, patch)`
- `delete(id)`
- `get(id)`
- `listByProject(projectId)`
- `listBySession(projectId, sessionKey)`
- `setEnabled(id, enabled)`
- `setMuted(id, mute)`
- `markRun(id, result)`
- `markScheduled(id, nextRunAt)`

要求：

- 所有写入都经过 DataRepository。
- 更新时保留不可变字段，比如 `id`、`createdAt`。
- 删除/禁用 job 后调度器必须取消对应 timer。
- `markRun` 必须同时记录 `lastRunAt`、`lastError`、`lastStatus`、`runCount`。
- Repository 层必须做 schema validation。

### 7.2 SchedulerService

新增 SchedulerService，作为全局调度服务注册到 `ServiceRegistry`。

职责：

- 应用启动时恢复 enabled jobs。
- 新增 job 后立即 schedule。
- update job 后取消旧 schedule 并按最新配置重建。
- disable/delete job 后取消 schedule。
- timer callback 只能捕获 `jobId`。
- 执行时必须重新从 repository 读取最新 job。
- 记录 next run。
- 支持手动 run now。

要求：

- 不要只写 `setInterval` 轮询。
- 必须实现 cron 表达式解析与 next run 计算。
- 如果项目已有 cron 依赖，优先复用。
- 如果必须新增依赖，只选择小而成熟的 cron parser/scheduler，并在最终报告中说明原因。
- timer 要能在服务 shutdown 时清理。
- 不要在 SchedulerService 中直接写 Feishu 业务逻辑，交给 CronExecutionService 或专门执行器。

### 7.3 CronExecutionService

新增执行服务，负责把 job 转成 prompt job、shell job 或 heartbeat 执行。

职责：

- 执行前读取最新 job。
- 校验 job 是否 enabled。
- 解析 workspace。
- 构建 Feishu reply target。
- 根据 `silent`、`mute` 发送开始/结果消息。
- prompt job 进入 AgentRuntime。
- exec job 进入 ControlledProcessRunner。
- 记录 `lastRunAt`、`lastError`、`lastStatus`。

执行结果状态至少包括：

- `success`
- `failed`
- `timeout`
- `skipped`

### 7.4 HeartbeatService

如果不把 Heartbeat 做成 ScheduledJob 的特殊类型，则新增 HeartbeatService。

职责：

- 管理 Feishu Heartbeat 配置。
- 启动时恢复 enabled heartbeat。
- pause/resume。
- run now。
- 到点时走和 Cron prompt job 相同的 AgentRuntime/Feishu active reply 链路。

Heartbeat 不应该绕过 AgentRuntime。

## 8. Cron 表达式与调度语义

本阶段至少支持 CC Connect 当前使用的 cron 表达式能力。

要求：

- 支持 5 段 cron：`minute hour day month weekday`。
- 必须校验非法表达式并返回可读错误。
- 必须能计算 `nextRunAt`。
- `list` 和 UI 中显示 `nextRunAt`。
- timezone 使用本机时区即可，但需要在最终报告中说明。
- job 修改后，下一次触发必须使用新配置。

不要只做“保存 cron 字符串但不真正执行”。

## 9. Feishu 主动回传要求

### 9.1 ReplyTarget 构造

Cron 和 Heartbeat 不是由一条新的 Feishu 入站消息触发，所以必须主动重建 reply target。

执行时必须得到：

- `projectId`
- `sessionKey`
- `transport.kind = "feishu"`
- `transport.connectorId`
- `replyCtx`
- `channelKey`
- `workspaceKey`
- `workspacePath`

`replyCtx` 优先使用 job 保存的上下文；如果缺失，则用 `sessionKey` 和 connector 信息重建。

必须验证：

- 普通 Feishu 群聊 sessionKey 能回到同一 chat。
- Feishu thread/root sessionKey 不丢失 root/thread 语义。
- 单聊如果当前实现支持，也要保持。
- connector 未运行时，job 标记失败并记录可读错误。

### 9.2 silent 与 mute

必须对齐 CC Connect 语义：

- `silent=false` 且 `mute=false`：发送开始消息和结果消息。
- `silent=true` 且 `mute=false`：不发送开始消息，但发送结果消息。
- `mute=true`：不发送开始消息，也不发送结果消息，只记录状态。

如果 CC Connect 源码中的实际行为与以上不同，以源码为准，并写入映射文档。

### 9.3 消息内容

Feishu 回传文案要克制，只写用户需要的信息。

建议：

- 开始：`定时任务已开始：<description 或 id>`
- 成功：`定时任务完成：<description 或 id>`
- 失败：`定时任务失败：<错误摘要>`
- 超时：`定时任务超时：<timeout>`

不要写架构解释、路线图、调试废话。

shell 输出过长时必须截断。建议对 Feishu 展示不超过 3000 字符，并说明已截断。

## 10. Prompt Job 执行要求

Prompt job 必须构造 synthetic `AgentMessage`，然后调用 AgentRuntime。

- `projectId`
- `sessionKey`
- `channelKey`
- `platform: "feishu"`
- `userId: "cron"`
- `userName: "cron"`
- `content: job.prompt`
- `replyCtx`
- `modeOverride: job.modeOverride`
- `workspaceKey`
- `workspacePath`
- `createdAt`

要求：

- 必须进入现有 AgentRuntime queue。
- 必须保留 permission flow。
- 必须保留 live session / exec mode 的现有处理。
- 必须让 Agent 输出通过现有 outbox/reply target 回到 Feishu。
- 必须注入正确的 `CC_SESSION_KEY`，值仍然是原始 Feishu sessionKey，不要换成 workspaceKey。

### 10.1 sessionMode=reuse

`reuse` 使用当前 `sessionKey + workspaceKey` 对应的活跃会话。

要求：

- 不改变现有 11.0 的 workspace 隔离语义。
- 同一 Feishu 频道、同一 workspace 的定时 prompt 可以续接对应 Agent 上下文。

### 10.2 sessionMode=new_per_run

`new_per_run` 必须为每次运行创建独立 side session。

要求：

- 不能覆盖用户当前活跃会话。
- 不能把当前频道的 active session 改掉。
- 不同 run 之间的 history 不能混在一起。
- Feishu 回传仍然回到原始 sessionKey/channel。
- 最终报告必须说明你如何实现 side session。

如果现有 AgentRuntime 没有这个能力，本阶段必须补齐。

## 11. Exec Job 执行要求

Exec job 只执行本地 shell 命令，不进入 Agent。

要求：

- 必须使用 `ControlledProcessRunner`。
- 必须通过 `PermissionGuard.check()`。
- 必须记录 `AuditSink`。
- 不能直接用 `child_process.exec`、`spawn` 或裸 shell。
- 必须设置 cwd。
- 必须支持 timeout。
- 必须截断输出。
- 必须把成功、失败、超时写回 job 状态。
- 非 mute 时，必须主动回传结果到 Feishu。

### 11.1 shell 选择

需要明确跨平台 shell 策略：

- macOS/Linux：`/bin/sh -lc <command>`。
- Windows：使用项目现有约定；如果没有，明确选择 `cmd.exe /d /s /c <command>` 或 PowerShell，并在最终报告说明。

不要把用户输入拆成不可靠的空格数组。

### 11.2 工作目录

workdir 解析优先级：

1. `job.workDir`
2. `job.workspacePath`
3. 通过 `channelKey/sessionKey` 查到的 workspace binding。
4. project 默认目录。

必须校验目录存在。

如果目录不可用：

- job 标记失败。
- 非 mute 时回传失败。
- 不要静默 fallback 到别的目录，除非任务书或源码明确允许。

### 11.3 exec 权限

通过 Feishu 创建 `addexec` 必须严格限制。

要求：

- 对齐 CC Connect 的 admin 语义。
- 如果当前项目已有 Feishu 用户 allowlist/admin 配置，复用。
- 如果没有，必须新增最小配置或通过现有 connector config 标识 admin。
- 记录 audit。
- 在最终报告中写清楚谁能创建 exec job。

## 12. Feishu `/cron` 命令要求

Feishu connector 必须支持 `/cron` 命令。命令应在进入 AgentRuntime 前拦截，和 `/workspace` 一样属于内部命令。

必须支持：

- `/cron`
- `/cron help`
- `/cron add <cron_expr> <prompt>`
- `/cron addexec <cron_expr> <command>`
- `/cron list`
- `/cron delete <id>`
- `/cron del <id>`
- `/cron rm <id>`
- `/cron enable <id>`
- `/cron disable <id>`
- `/cron mute <id>`
- `/cron unmute <id>`

如果 CC Connect 还支持其他别名，以源码为准尽量补齐。

### 12.1 命令行为

- `/cron` 和 `/cron help` 返回简短帮助。
- `/cron add` 创建 prompt job，绑定当前 Feishu sessionKey/channel/workspace。
- `/cron addexec` 创建 shell job，必须经过 admin/permission/audit。
- `/cron list` 列出当前项目/当前 session 相关 job。
- `/cron delete` 删除 job 并取消 schedule。
- `/cron enable` 启用并立即 schedule。
- `/cron disable` 禁用并取消 schedule。
- `/cron mute` 只切换 mute，不删除 job。
- `/cron unmute` 只切换 mute。

### 12.2 Cron 表达式解析

为了避免中文空格和命令正文歧义，建议支持：

```text
/cron add "*/30 * * * *" 每 30 分钟检查一下当前项目状态
/cron add */30 * * * * 每 30 分钟检查一下当前项目状态
```

必须在测试里覆盖带引号和不带引号两种情况。

### 12.3 绑定当前 workspace

从 Feishu 消息创建 job 时：

- 如果当前频道已经绑定 workspace，job 保存 `workspaceKey/workspacePath/channelKey`。
- 如果当前频道未绑定 workspace，遵循 11.0 的初始化/绑定逻辑，不能盲目创建无法执行的 job。
- 如果当前消息本身触发了 init flow，先完成 workspace 绑定，再创建 job。

## 13. Side-channel Cron Add 要求

CC Connect 支持 Agent/CLI 通过本地 API 创建 Cron。Synapse 本阶段必须提供等价能力。

建议扩展现有 side-channel：

- 保留现有 `/send`。
- 新增 `/cron/add` 或等价 endpoint。
- 不破坏现有 `SYNAPSE_SIDE_CHANNEL_URL`。
- 如有必要，新增 `SYNAPSE_SIDE_CHANNEL_BASE_URL` 或 `SYNAPSE_CRON_ADD_URL`。

请求字段建议：

- `projectId` 或 `project`
- `sessionKey` 或 `session_key`
- `cronExpr` 或 `cron_expr`
- `prompt`
- `exec`
- `workDir`
- `description`
- `silent`
- `mute`
- `sessionMode`
- `mode`
- `timeoutMins`

要求：

- 使用和 `/send` 一样的 token 鉴权。
- 如果 request 没传 `projectId/sessionKey`，优先从 side-channel target 或环境约定中推断；无法可靠推断时返回错误，不要猜。
- 创建出来的 job 必须和 Feishu 当前 session 绑定，后续可以主动回传到 Feishu。
- exec job 仍需 permission/audit。
- 返回 job id 和 nextRunAt。

必须为 Agent 环境注入写测试，确保 Agent 可以拿到创建 cron 所需 URL/token/session 信息。

## 14. Heartbeat 要求

本阶段需要实现 Feishu 范围内的 Heartbeat。

最低要求：

- 可以为项目/Feishu session 配置 heartbeat。
- 可以启用/暂停/恢复。
- 可以 run now。
- 到点后构造 synthetic heartbeat message 进入 AgentRuntime。
- user 标识使用 `heartbeat`。
- 使用和 Cron 相同的 workspace 解析、reply target、silent/mute、lastRun/lastError 记录。

如果实现 `/heartbeat` Feishu 命令，至少支持：

- `/heartbeat`
- `/heartbeat status`
- `/heartbeat pause`
- `/heartbeat resume`
- `/heartbeat run`

如果 UI 中支持 Heartbeat，必须和 Cron 放在同一个自动化管理区域，不要做成新的孤立系统。

## 15. 桌面端管理 UI 要求

本阶段需要提供最小可用的 Feishu 定时任务管理入口。

建议位置：

- 复用当前 settings/Feishu connector 页面。
- 新增 Feishu 自动化区域或 tab。
- 只展示当前项目的 Feishu jobs。

必须支持：

- 查看 job 列表。
- 查看 enabled/mute/silent/sessionMode/nextRun/lastRun/lastError。
- 新建 prompt job。
- 新建 exec job 时必须清楚标识权限限制。
- 启用/禁用。
- mute/unmute。
- 删除。
- run now。

可以不在本阶段做复杂 cron builder，但必须有可输入 cron 表达式的表单。

UI 文案必须克制：

- 标题可以是 `定时任务`、`Heartbeat`。
- label 保留必要字段。
- 错误状态说清楚下一步。
- 不要写“本功能可以帮助你...”。

### 15.1 UI 技术要求

### 15.2 IPC/Preload
