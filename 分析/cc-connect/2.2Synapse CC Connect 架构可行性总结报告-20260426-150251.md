# Synapse CC Connect 架构可行性总结报告

生成时间：2026-04-26 15:02:51

## 1. 结论

当前 Synapse 仓库已经具备开始实现 CC Connect 类能力的架构前提，可以进入第一阶段开发。

但这里的“可以开始”不等于可以直接一次性做完整远程控制、飞书扫码、Agent 会话、权限审批、定时任务和主动回传。当前状态更适合先做一个本机 Agent 控制闭环，然后逐步接入远程 connector 和 scheduler。

推荐开工顺序：

1. 先做本机 Agent Engine 最小闭环。
2. 再做 Feishu/Lark connector。
3. 最后做定时任务和主动消息回传。

一句话判断：地基够了，业务层还没建；现在可以开工，但第一刀应该落在 Agent Engine，而不是直接做完整 CC Connect 套装。

## 2. CC Connect 的核心要求

从本目录已有文档可归纳出 CC Connect 的本质不是调用某个单独 CLI，而是这条链路：

```text
Platform
  -> Unified Message
  -> Engine
  -> Agent Session
  -> Local CLI Process
  -> Unified Events
  -> Platform Reply
```

关键要求包括：

- 平台层只负责收发消息，不直接调用 Codex 或 Claude Code。
- 所有入口统一成 Message，至少需要 `session_key`、`platform`、`user_id`、`content`、`attachments`、`reply_ctx`。
- Engine 负责命令路由、会话绑定、忙碌队列、权限确认、状态持久化和结果回传。
- Agent 适配器负责启动或复用本地 CLI 子进程，并把 stdout/stdin、JSON Lines、JSON-RPC 或 stream-json 映射成统一事件。
- 定时任务不是依赖打开的 Agent 窗口，而是由后台主进程把任务构造成合成用户消息，再走同一条 Engine -> Agent 路径。
- 飞书远程控制依赖本机主动连接飞书 WebSocket，不要求用户机器有公网 IP。

## 3. Synapse 当前已满足的前提

### 3.1 常驻主进程

Electron 主进程已经通过单实例、托盘和服务启动流程承载长期运行能力。

相关位置：

- `desktop/electron/main.ts`
- `desktop/electron/bootstrap/registry.ts`
- `desktop/electron/bootstrap/descriptors.ts`

这满足 CC Connect 对“本机后台进程存活”的基础要求。

### 3.2 IPC 边界已收口

当前 Electron 能力通过 `IpcModule` 和 `IpcRegistry` 注册，避免 renderer 直接接触 Electron 能力。

相关位置：

- `desktop/electron/runtime/ipc/types.ts`
- `desktop/electron/runtime/ipc/registry.ts`
- `desktop/electron/bootstrap/ipc-registry.ts`
- `desktop/electron/preload.ts`

这适合后续新增：

- `agent` IPC module
- `connector` IPC module
- `scheduler` IPC module

### 3.3 EventBus 已预留核心域

EventBus 已经包含这些域：

- `agent`
- `connector`
- `scheduler`
- `project`
- `system`

相关位置：

- `desktop/electron/runtime/event-bus/types.ts`
- `desktop/electron/runtime/event-bus/bus.ts`
- `desktop/electron/runtime/event-bus/broadcaster.ts`

这说明上一轮架构改造已经把远程控制和 Agent 事件流需要的事件通道预留出来了。

### 3.4 ProjectContainer 方向正确

`ProjectContainerRegistry` 的注释和类型明确指出：

- Agent runtime
- session manager
- connector binding
- cron scheduler

这些都应该作为项目级服务存在。

相关位置：

- `desktop/electron/runtime/project-container/types.ts`
- `desktop/electron/runtime/project-container/registry.ts`
- `desktop/electron/runtime/project-container/idle-reaper.ts`

这与 CC Connect 的“一个 project 绑定 agent 和多个平台入口”一致。

### 3.5 DataRepository 已预留业务命名空间

当前已经有这些命名空间：

- `secrets`
- `providers`
- `projects`
- `connectors`
- `conversations`
- `audit`
- `outbox`

相关位置：

- `desktop/electron/runtime/data-repo/schemas/placeholders.ts`
- `desktop/electron/runtime/data-repo/types.ts`
- `desktop/electron/runtime/data-repo/backends/json.ts`
- `desktop/electron/runtime/data-repo/backends/sqlite.ts`
- `desktop/electron/runtime/data-repo/backends/jsonl.ts`

这些正好对应远程控制需要的配置、密钥、连接器、会话、审计和主动消息队列。

### 3.6 权限与审计方向正确

`PermissionGuard` 已经包含以下敏感动作：

- `shell.exec`
- `network.connect`
- `network.listen`
- `agent.spawn`
- `secret.read`
- `secret.write`
- `fs.write`

相关位置：

- `desktop/electron/runtime/security/permission-guard.ts`

这符合 CC Connect 中“远程控制本机 Agent 必须有权限边界”的要求。

### 3.7 调度基础设施已存在

当前 runtime 已有：

- `TaskQueue`
- `RateLimiter`
- `CircuitBreaker`
- timeout / retry / AbortSignal

相关位置：

- `desktop/electron/runtime/scheduling/scheduling.ts`

这不是完整 cron scheduler，但可以作为后续 scheduler 的执行层。

## 4. 当前还不满足的部分

### 4.1 还没有 Agent Engine

仓库目前没有等价于 CC Connect `core.Engine` 的业务中枢。

缺少：

- 统一 `AgentMessage`
- 统一 `AgentEvent`
- `AgentSession`
- session key 到本地 agent session 的映射
- busy lock / pending queue
- slash command 路由
- permission request 回写
- Agent 输出事件到 UI/connector 的回传逻辑

这是第一阶段必须补的核心。

### 4.2 还没有真实 Agent 子进程管理

`ProcessRuntime` 当前只支持 `kind="main"`，`utility/worker/child` 还没有实现。

相关位置：

- `desktop/electron/runtime/process/runtime.ts`

因此第一版可以先在业务服务里直接用 `child_process.spawn()` 包装 Codex/Claude CLI，但中长期应该沉到统一 process runtime 或 agent runtime。

### 4.3 ProjectScopedDataRepo 还没有真实项目隔离

`ProjectScopedDataRepoImpl.namespace()` 当前只是返回 underlying namespace。

相关位置：

- `desktop/electron/runtime/project-container/scoped-data-repo.ts`

这对 MVP 可接受，但不能直接支撑多项目、多会话、远程入口长期使用。做正式 connector 和 scheduler 前应补真实 project scope。

### 4.4 Connector 只是数据模型占位

`connectors` namespace 目前只有最小字段：

- `id`
- `schemaVersion`
- `platform`
- `secretRef`

还没有：

- 飞书 app id / secret 配置结构
- connector 启停状态
- allow list
- session key 策略
- reconnect/backoff
- message dedupe
- reply context 重建

### 4.5 Scheduler 还不是 cron 系统

现有 scheduling 只是通用任务队列，不是 CC Connect 式定时任务。

缺少：

- `ScheduledJob` 模型
- cron 表达式注册
- 持久化 store
- enabled/disabled
- silent/mute
- last_run/last_error
- prompt/exec 互斥
- session_mode
- 触发时重新读取 job

### 4.6 NetworkServiceRegistry 尚未承载实际服务

`NetworkServiceRegistry` 目前是 skeleton，现有 data-store HTTP/MCP server 仍在自己的模块中直接创建服务。

相关位置：

- `desktop/electron/runtime/network/registry.ts`
- `desktop/electron/data-store/http-server.ts`
- `desktop/electron/data-store/mcp-server.ts`

做飞书 connector 时不一定阻塞，但做本地 bridge/API/server 时应该走统一网络注册。

## 6. 推荐开发路线

### Phase 1：本机 Agent 控制闭环

目标：不接飞书、不做定时任务，先在本机把“输入 prompt -> 调 CLI -> 回传事件”跑通。

建议新增：

- `desktop/electron/modules/agent/ipc.ts`
- `desktop/electron/services/agent/agent-engine.ts`
- `desktop/electron/services/agent/types.ts`
- `desktop/electron/services/agent/adapters/codex-exec.ts`

最小类型：

```ts
type AgentMessage = {
  projectId: string
  sessionKey: string
  userId: string
  content: string
  replyCtx?: unknown
}

type AgentEvent =
  | { type: "text"; content: string }
  | { type: "tool"; name: string; input?: unknown }
  | { type: "permission"; requestId: string; action: string; resource: string }
  | { type: "result"; content: string; nativeSessionId?: string }
  | { type: "error"; message: string }
```

成功标准：

- UI 或 IPC 能发送一条 prompt。
- 主进程能启动 Codex 或 Claude CLI。
- stdout 被解析为统一事件。
- 最终结果通过 EventBus 或 IPC 回到 renderer。
- 会话能保存 native session id。

### Phase 2：Engine 会话与权限

目标：从“能跑一次”升级为“可持续会话”。

需要补：

- `SessionManager`
- `session_key -> active session`
- busy lock
- pending queue
- permission request pending state
- conversation 持久化
- model/mode 配置最小路由

成功标准：

- 同一个 session key 能延续上下文。
- 同一 session 忙碌时不会乱写 stdin。
- Agent 权限请求能变成可处理状态。

### Phase 3：Feishu/Lark connector

目标：实现远程入口。

建议拆为：

- setup service：begin/poll/save
- connector runtime：WebSocket 长连接
- message normalizer：飞书事件转 AgentMessage
- reply service：AgentEvent 转飞书回复

成功标准：

- 本机能展示飞书授权二维码。
- 扫码后凭证进入 secrets/connectors。
- 飞书消息能进入 Agent Engine。
- Agent 最终回复能回到飞书。

### Phase 4：Scheduler

目标：实现定时任务触发 Agent 或 shell 命令。

需要补：

- `ScheduledJob` schema
- cron store
- cron scheduler service
- prompt job 走 Agent Engine
- exec job 走受控 shell runner
- last_run / last_error
- silent / mute
- outbox 主动回传

成功标准：

- 重启后能恢复 enabled job。
- 到点后重新读取 job 最新配置。
- prompt job 能生成合成 AgentMessage。
- exec job 经过 PermissionGuard。
- 结果能主动发回原 session。

## 7. 风险边界

### 7.1 远程控制是高权限能力

飞书远程入口一旦接通，本质是“外部消息能触发本机命令和文件操作”。必须默认保守：

- connector 默认只允许绑定用户或 allow list。
- shell.exec 默认需要明确授权。
- agent.spawn 需要 PermissionGuard。
- secrets 不允许进入 renderer。
- audit 必须记录远程入口、actor、action、resource、outcome。

### 7.2 不能让平台绕过 Engine

飞书、Web Bridge、未来 Telegram/微信都不能直接调用 Codex/Claude。否则会丢失：

- session lock
- permissions
- history
- command routing
- audit
- outbox

### 7.3 不要一开始做复杂多 Agent

第一版只选一个 Agent：

- Codex exec 更容易做单轮 MVP。
- Claude Code 更适合长期会话和权限回写。

建议先做 Codex exec 验证链路，再补 Claude Code 长驻 session。

### 7.4 不要先做 UI

UI 可以很薄。第一阶段应先证明：

```text
AgentMessage -> AgentEngine -> CLI -> AgentEvent
```

这个闭环成立后，再做 connector 和管理页。

## 8. 最终判断

当前 Synapse 的架构改造方向与 CC Connect 的核心方案一致：

- runtime 层保持纯基础设施；
- bootstrap 负责装配；
- Electron 能力通过 typed IPC 暴露；
- EventBus 负责事件扩散；
- ProjectContainer 承载项目级 runtime；
- DataRepository 为 connectors/conversations/outbox/audit 预留持久化位置；
- PermissionGuard 为远程高危操作预留安全边界。

因此，可以开始做 CC Connect 类功能。

建议立项名称：

```text
M1 Agent Runtime MVP
```

第一阶段不要承诺“飞书远程控制完整上线”，而是承诺：

```text
在 Synapse 主进程中，通过统一 Agent Engine 控制一个本地 CLI Agent，并把输出事件回传到 renderer。
```

这个目标完成后，再进入：

```text
M2 Feishu Connector
M3 Remote Permission and Outbox
M4 Scheduler
```
