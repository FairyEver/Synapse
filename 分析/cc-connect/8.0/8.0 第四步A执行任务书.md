# 8.0 第四步 A 执行任务书：Management IPC、Renderer Chat、持久化审计与回复目标

## 一、阶段定位

第四步原计划覆盖范围偏大，容易把本地管理界面、Bridge side-channel、飞书接入、定时调度混在一起开发。根据 `3.2 后续阶段复核与调整建议.md` 的复核结果，第四步拆成两段：

- `8.0 第四步 A`：先做本地 Management IPC、Renderer Chat、审计持久化、回复目标与 outbox 基础层。
- `9.0 第四步 B`：再做 `BridgeAdapterService` 与本地 side-channel send。

本阶段是第一个“用户可以在界面上感知”的阶段，但它仍然只服务于本地 Electron 应用内的 Agent 会话管理。不要在本阶段实现飞书、Relay、Cron/Scheduler、多工作区编排、Bridge WebSocket 或远端消息发送。

## 四、开发顺序

### 第 1 步：建立 8.0 执行记录

在 `分析/cc-connect/8.0/` 下创建并维护这些文件：

- `8.0 执行计划.md`
- `8.0 源码映射.md`
- `8.0 测试记录.md`
- `8.0 问题修复记录.md`
- `8.0 最终报告.md`

每次遇到源码差异、测试失败、架构取舍，都要写到对应记录里。

### 第 2 步：实现持久化审计

目标：让 `AuditSink.record(...)` 不再只写内存，而是写入 DataRepository 的 `audit` namespace。

要求：

- 保留 `InMemoryAuditSink` 作为测试或兜底实现。
- 新增持久化实现时优先放在 `desktop/electron/runtime/security/`，不要放进业务模块。
- 通过 `ServiceRegistry` 和 bootstrap descriptor 注入，不允许新增全局单例。
- 审计记录不得保存明文 token、secret、Authorization header、完整 prompt 中的敏感字段。
- 需要覆盖成功写入、敏感字段脱敏、写入失败时记录 warn 或向上抛出这几类行为。

验收：

- `coreAuditSinkDescriptor` 使用持久化 AuditSink。
- `pnpm desktop:check:hard-constraints` 不新增违规。
- 有测试覆盖或在 `8.0 测试记录.md` 中说明无法覆盖的原因。

### 第 3 步：实现 ReplyTarget 与 Outbox 基础层

目标：为“本地 Renderer 发送消息”和后续 Bridge/飞书/定时器复用同一套回复目标模型。

要求：

- 抽象平台无关的 `ReplyTarget`，至少能表达：
  - local renderer session
  - conversation/session id
  - optional thread/message id
  - transport kind
- 基于已有 `outboxSchema` 实现最小 outbox 写入能力：
  - `pending`
  - `sent`
  - `failed`
- 本阶段只需要支持本地 renderer 目标，不实现外部平台重试队列。
- 失败必须能被记录和查询，不能只 `console.log`。

验收：

- Agent 运行结果能够落到可复用的 reply/outbox 表达里。
- 后续 `9.0 BridgeAdapterService` 不需要重写回复目标模型。

### 第 4 步：实现 Agent Management IPC

目标：把 CC Connect `management.go` 中和本地管理有关的能力，映射成 Electron 内部窄 IPC API。

必须参考 CC Connect：

- `handleStatus`
- `handleProjectSessions`
- `handleProjectSend`
- `handleProjectProviders`

Synapse 实现要求：

- 不允许在新代码中直接使用 `ipcMain.handle/on`，只能通过 `IpcRegistry.register(...)`。
- IPC 只暴露必要能力，建议最小集合：
  - agent status
  - list sessions
  - send message
  - subscribe/list timeline events
  - list/respond pending permissions
  - provider state summary
- IPC handler 不得直接暴露 filesystem、shell、raw provider secret。
- 需要复用现有 `AgentRuntimeService`、`ProjectContainer`、`EventBus`、`PermissionGuard`，不要复制一套运行时。

验收：

- Renderer 只通过 `window.synapse.*` 调用。
- main/preload/renderer 类型一致。
- IPC 错误有归一化返回，不吞错。

### 第 5 步：扩展 preload 与 renderer 类型

目标：给 Renderer 提供窄的 `window.synapse.agent` 或同等命名 API。

要求：

- 修改 `desktop/electron/preload.ts` 和对应 `desktop/src/types/bridge` 类型。
- 不暴露 raw `ipcRenderer`。
- 不提供“大而全”的通用 invoke 方法。
- API 名称要稳定，后续 Bridge/飞书/UI 都能复用，不因为 9.0 重写。

验收：

- TypeScript 能从 Renderer 正确识别新 API。
- 不破坏现有 repository/update/data-store API。

### 第 6 步：实现 Renderer Chat 薄界面

目标：在现有 App Shell 中增加一个本地 Agent 会话入口，让用户能看到会话、发送消息、看到 Agent 事件、处理权限请求。

硬性 UI 要求：

- 因为本阶段触碰 UI，必须遵守 `.claude/rules/design.md` 和 `.claude/rules/ui-rules.md`。
- 使用现有 shadcn/Radix 组件和 Tailwind token。
- 禁止自定义颜色、hex/rgb/hsl 字面色、内联 style、AI 渐变、装饰 emoji。
- 不要卡片套卡片。
- UI 文案只保留标题、必要 label、错误/空状态，不写功能介绍废话。
- 新业务模块放在 `desktop/src/modules/`，不要新建 `desktop/src/features/`。

建议实现范围：

- 新增一个顶层 tab，例如 `Agent` 或 `会话`。
- 左侧或顶部 session list。
- 主区域显示消息和 `AgentEvent` timeline。
- 输入框 + 发送按钮。
- 权限请求用现有 dialog/alert/dialog button 组合处理。
- provider 状态只展示最小必要信息，不做完整配置页。

验收：

- 本地界面能发起一条 Agent message。
- AgentRuntime 事件能在界面上更新。
- 权限请求能被用户确认或拒绝。
- 无多余营销文案或架构说明文案出现在 UI。

### 第 7 步：补齐 slash command 策略

目标：避免本地 UI 把未知 slash command 误当成远端命令注入。

必须参考 CC Connect：

- `engine.go` 中 unknown command、custom command、skill command 的处理分支。
- `分析/cc-connect/1.5 ...` 中关于命令能力的分析。

本阶段只需要建立策略边界：

- built-in command：明确支持。
- registered prompt command：明确支持。
- agent-native passthrough：需要显式 allowlist。
- unsupported slash：本地 UI 可提示“不支持”或按普通消息发送，但必须行为明确。

不要在本阶段实现完整自定义命令系统。

### 第 8 步：测试、记录、修复、重复测试

必须执行测试闭环：

1. 先运行和本阶段相关的单测/typecheck。
2. 发现问题后记录到 `8.0 问题修复记录.md`。
3. 修改问题。
4. 重复测试。
5. 直到没有已知失败，或明确记录无法解决的外部阻塞。

建议命令：

```bash
pnpm desktop:typecheck
pnpm desktop:test
pnpm desktop:check:hard-constraints
```

如果只运行了更小范围测试，必须在 `8.0 测试记录.md` 说明原因。

注意：本仓库规则要求不要主动启动 dev server、浏览器预览、Chrome DevTools、Playwright 或运行 App 页面，除非用户明确要求。

## 五、本阶段不得做的事

- 不实现 Bridge WebSocket server/client。
- 不实现 `BridgeAdapterService` 的 side-channel send。
- 不实现飞书/Lark bot。
- 不实现 Cron/Scheduler。
- 不实现 Relay。
- 不实现多工作区路由。
- 不重构 UI 视觉体系。
- 不引入新组件库。
- 不新增 `@base-ui/react`。
- 不把业务逻辑写进 JSX。
- 不在组件里散落 `fetch()`、`ipcRenderer` 或 provider secret。

## 六、完成标准

本阶段完成后，应满足：

- 本地 UI 已经能感知 Agent 会话能力。
- Renderer 能通过窄 preload API 发送消息和读取事件。
- 审计记录进入持久化 DataRepository。
- ReplyTarget/outbox 基础模型已经存在，能被后续 Bridge/飞书复用。
- slash command 策略有明确代码边界和测试。
- `8.0/` 下有完整执行计划、源码映射、测试记录、问题修复记录、最终报告。
- `pnpm desktop:typecheck`、`pnpm desktop:test`、`pnpm desktop:check:hard-constraints` 通过，或失败原因被明确记录且不是本阶段引入的代码问题。

## 七、进入下一步的条件

只有满足以下条件，才允许进入 `9.0 第四步 B：BridgeAdapterService 与本地 side-channel send`：

- `window.synapse.*` 的 Agent 本地管理 API 稳定。
- Renderer Chat 能产生真实发送入口，不只是静态界面。
- AgentRuntime 的结果、错误、权限请求能被本地 UI 看见。
- outbox/reply target 已经能表达本地回复目标。
- AuditSink 已经持久化。
- 没有违反 Phase 0 hard constraints。
