# 11.0 第六步执行任务书：Feishu 多工作区与频道绑定

## 一、阶段定位

`10.0 第五步` 已经完成 Feishu connector runtime：飞书 setup、凭据保存、WebSocket 长连接、消息标准化、ReplyTarget/Outbox 回传、权限卡片和设置页入口已经具备。本阶段进入 `3.1 整体开发顺序.md` 中的第六步：多工作区与频道绑定。

本阶段只支持飞书 Feishu。不要实现 Lark、微信、Slack、Telegram、Discord、Webhook、Cron、Relay、多平台多工作区，也不要把本阶段做成新的通用 connector 产品。可以抽平台无关的核心服务，但运行路径、命令、UI、测试只要求 Feishu 可用。

“做到和 CC Connect 对等”的含义是：在飞书这条链路内，对齐 CC Connect 多工作区的核心行为：

1. 一个 Feishu bot 可以服务同一个 Synapse project 下的多个本地 workspace。
2. 用飞书群聊、话题或会话的 `channelKey` 路由到 workspace，而不是用用户级 `sessionKey` 路由。
3. 支持项目级绑定和 shared 绑定，项目级优先，shared 兜底。
4. 支持绑定优先、频道名约定匹配、未绑定初始化流三层解析。
5. 每个 workspace 有隔离的工作目录、会话状态、Agent live session 和队列状态。
6. 内部 runtime key 可以包含 workspace，但 `CC_SESSION_KEY` 和飞书 reply context 必须保持原始平台 sessionKey。
7. `/workspace` 和 `/ws` 命令可在飞书中查看、绑定、路由、初始化、解绑、列出 workspace。
8. workspace idle 回收不能打断正在执行的 turn。
9. per-workspace Agent 必须继承当前 project 的 provider、model、mode、权限和治理配置。
10. 所有敏感操作必须经过现有 PermissionGuard、AuditSink、DataRepository 和 IPC 边界。

## 六、目标架构

本阶段建议实现以下模块。文件名可按实际代码风格调整，但职责边界不能混乱。

### 1. WorkspaceBindingRepository

建议位置：

- `desktop/electron/services/workspaces/workspace-binding-repository.ts`
- 或 `desktop/electron/services/connectors/workspaces/...`，如果你认为本阶段只为 connector 服务。

职责：

- 持久化 channelKey -> workspacePath。
- 支持 project scope 和 shared scope。
- 查询时 project scope 优先，shared scope 兜底。
- 支持 list/bind/unbind。
- normalize workspace path。
- 校验目录存在。
- 对项目级缺失目录自动解绑并 audit。
- shared 缺失目录保留，并返回明确 invalid/missing 状态。

成功标准：

- 同一个 `channelKey` 在 project 和 shared 都存在时，project 胜出。
- `feishu:C1` 与未来平台的 `slack:C1` 不会碰撞。
- 绑定记录不保存 secret。
- 所有写入走 DataRepository，不直接 `fs.writeFile` 保存业务数据。

### 2. FeishuWorkspaceConfigService

职责：

- 读取/更新当前 project 的 Feishu multi-workspace 配置。
- 开启时必须有 `baseDir`。
- `baseDir` 需要存在或通过受控路径创建；涉及创建目录时必须经过 PermissionGuard 和 AuditSink。
- 非多工作区时，Feishu runtime 使用 10.0 原路径。

配置建议：

```ts
type FeishuWorkspaceConfig = {
  enabled: boolean
  baseDir?: string
  autoBindByChannelName?: boolean
  idleTimeoutMs?: number
}
```

### 3. FeishuChannelKeyResolver

职责：

- 从 Feishu event/normalized message 生成稳定 `channelKey`。
- 从 Feishu event 中尽量取得 `channelName`。
- 如果 SDK 可稳定获取群名/话题名，则实现 Feishu channel name resolver，用于 `baseDir/<channelName>` convention 自动绑定。
- 如果当前 Feishu SDK 或事件结构无法稳定提供 channelName，则必须支持显式 `/workspace bind|route|init`，并在 `11.0 问题修复记录.md` 记录 convention 自动绑定的限制。

规则：

- channelKey 不得包含 userId。
- sessionKey 继续由 `sessionKeyPolicy` 决定。
- thread policy 下，sessionKey 可以按 thread 隔离；workspace channelKey 是否按 root/topic 隔离必须与 CC Connect `Message.ChannelKey` 的语义对齐，并写入源码映射。

### 4. WorkspaceResolver

职责：

1. 检查 multi-workspace 是否开启。
2. 根据 `channelKey` 查 project/shared binding。
3. 如果绑定存在且目录有效，返回 workspace context。
4. 如果 project 绑定目录缺失，自动解绑并 audit。
5. 如果允许 channelName convention，尝试 `baseDir/<channelName>`。
6. 如果 convention 匹配成功，自动写入 project binding。
7. 未解析时返回 unresolved，并交给 init flow 或 `/workspace` 命令。

注意：

- resolver 不能直接启动 Agent。
- resolver 不应发送飞书消息。
- resolver 输出结构需要足够表达：
  - `status: "resolved" | "unresolved" | "disabled" | "invalid"`
  - `workspacePath`
  - `workspaceKey`
  - `channelKey`
  - `channelName`
  - `bindingScope`
  - `reason`

### 5. WorkspaceRuntimePool

职责：

- 按 `projectId + workspacePath` 懒创建/复用 workspace runtime。
- 每个 workspace runtime 使用对应 workspace path 作为 Agent workDir。
- 每个 workspace 拥有隔离的 live session、queue 和 active conversation。
- 支持 active turn 计数。
- 支持 idle 回收。
- 回收时不能终止正在执行的 turn。
- 回收时只清内存或关闭 live session，不删除持久化 conversation。

必须继承：

- Agent type。
- provider 配置。
- active provider。
- active model。
- mode。
- governance。
- PermissionGuard。
- AuditSink。
- ReplyTarget/Outbox。
- registered prompt commands。
- agent-native slash allowlist。
- unknown slash behavior。

注意：

- 如果通过 ProjectContainerRegistry 取 project 级 service，不能让所有 workspace 继续共享同一个 fixed workDir。
- 如果选择修改 AgentRuntimeService 支持 workspace context，则 `runtimeKey(...)`、`conversationId(...)`、`getActive(...)`、`resetSession(...)`、`pendingPermissions` 都要带 workspace 维度。

### 6. WorkspaceInitFlow

职责：

- 未绑定频道收到普通消息时，不进入 Agent，而是进入初始化流。
- init flow state 以 `projectId + platform + channelKey` 为 key，而不是 sessionKey。
- 支持用户输入：
  - baseDir 下已有目录名。
  - 绝对本地目录。
  - git URL。
- 对本地路径：
  - 必须 normalize。
  - 必须检查路径存在、是否目录、是否允许访问。
  - 绝对路径需要 PermissionGuard 和 audit。
- 对 git URL：
  - clone 属于 `network.connect`、`shell.exec`、`fs.write` 组合敏感操作。
  - 必须使用现有受控进程/权限边界，不得在业务服务里裸调 shell。
  - 测试中用 fake process runner，不做真实网络 clone。
- 如果用户输入 slash command，slash command 必须优先，init flow 不得吞掉命令。

Feishu 文案要求：

- 远程回复可以说明缺少绑定和可用命令，但要简短。
- 不写长篇说明或内部实现细节。

### 7. WorkspaceCommandHandler

职责：

- 处理 Feishu 中的 `/workspace`、`/ws` 命令。
- 命令必须进入 AgentRuntime 之前处理。
- 命令结果通过当前 Feishu reply context 返回。

最低命令集：

```text
/workspace
/workspace bind <workspace-name>
/workspace route <absolute-path>
/workspace init <local-dir-or-git-url>
/workspace unbind
/workspace list
/workspace shared bind <workspace-name>
/workspace shared route <absolute-path>
/workspace shared init <local-dir-or-git-url>
/workspace shared unbind
/workspace shared list
/ws ...
```

权限要求：

- 查看当前绑定可以允许普通 allowlist 用户。
- `bind`、`route`、`init`、`unbind`、`shared ...` 必须要求 Feishu admin。
- admin 判定优先复用 `isFeishuAdmin(...)`。
- 权限失败必须记录 audit，并返回明确的 Feishu 消息。

### 8. Feishu 设置页扩展

职责：

- 在现有 Feishu 设置面板中增加多工作区配置。
- 支持开启/关闭 multi-workspace。
- 支持选择或输入 baseDir。
- 显示当前 project binding 列表。
- 支持删除 project binding。
- shared binding 可以只做列表和删除；如果 UI 写入成本过高，可先通过 `/workspace shared ...` 完成写入，但 IPC/service 需要完整。

UI 边界：

- 不展示 secret。
- 不展示内部 workspace runtime key。
- 不写实现说明型文案。
- 不做复杂 dashboard。
- 使用现有 `Card`、`Field`、`Input`、`Button`、`Badge`、`Alert`、`Table` 或项目已有组件。

## 八、必须满足的成功标准

完成后必须满足：

1. Feishu connector 可以开启 multi-workspace 并设置 baseDir。

3. `sessionKey`、`channelKey`、`workspaceKey` 三者边界清楚。
4. 绑定查找 project 优先，shared 兜底。
