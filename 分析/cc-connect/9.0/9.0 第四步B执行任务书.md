# 9.0 第四步 B 执行任务书：BridgeAdapterService 与本地 side-channel send

## 一、阶段定位

`8.0 第四步 A` 已经完成本地 Agent Management IPC、Renderer Chat、持久化审计、ReplyTarget/Outbox 基础层和 slash command 策略边界。`9.0 第四步 B` 的任务是在这些地基上继续做外部 adapter 接入和 Agent 主动回传能力。

本阶段只做两件大事：

1. `BridgeAdapterService` MVP：让外部 adapter 能注册、发送消息、接收 Agent 回复/更新/typing，并能做最小 session 管理。
2. 本地 side-channel `send`：让正在运行的 Agent 能通过本机受控入口，把文本、图片或文件回传当前 session。

本阶段仍然不做 Feishu/Lark、Cron/Scheduler、Relay、多工作区路由，也不做 Provider 完整配置页。

### 第 4 步：评估并补强 runtime/network 承载层

当前 `NetworkServiceRegistry` 只提供 descriptor 注册、端口选择、审计和生命周期。若本阶段要启动 HTTP/WebSocket 服务，必须遵守：

- `http.createServer`、`net.createServer`、`https.createServer` 只能出现在 `desktop/electron/runtime/network/`。
- 业务服务只能提供 handler/protocol 逻辑，不能自己裸建 server。
- Bridge/side-channel 的服务注册必须经过 `NetworkServiceRegistry.register(...)`。
- 默认绑定 `127.0.0.1`。
- 默认使用 `local-token` 或等价鉴权。

如果现有 runtime/network 不足，需要先在 `desktop/electron/runtime/network/` 中新增最小 host：

- 支持 localhost HTTP handler。
- 支持 WebSocket upgrade 或明确接入最小 WebSocket host。
- 返回 `NetworkServiceLifecycle.stop()`。
- 把绑定地址、端口、服务 id 交给 `NetworkServiceRegistry` 统一记录。
- 有单元测试覆盖注册、启动、停止、端口冲突、鉴权失败。

如果实现 WebSocket server 需要新增依赖：

- 先确认现有依赖没有可用 WebSocket server。
- 只允许添加最小依赖，例如 `ws` 及必要类型。
- 不引入 Express/Koa/Nest/Fastify 这类框架。
- 在 `9.0 最终报告.md` 说明新增依赖原因和替代方案为什么不合适。

### 第 6 步：实现 BridgeAdapterService MVP

职责：

- 管理 adapter 注册、断开、替换。
- 保存 platform、capabilities、metadata、连接状态、最近连接时间。
- 提供 `listAdapters()` 给 Management/UI 查询。
- 支持向指定 adapter 发送出站消息。
- 支持从 adapter 入站消息转发到对应 project 的 `AgentRuntimeService`。

要求：

- 不新增全局单例，通过 `ServiceRegistry` descriptor 注入。
- 依赖 `ProjectContainerRegistry`、`NetworkServiceRegistry`、`AuditSink`、`PermissionGuard`、`StructuredLogger`。
- adapter 同名重复注册时，新连接替换旧连接，并记录 audit。
- adapter 断开时状态可查询。
- 注册失败、鉴权失败、协议错误都要记录 audit 或 warn。
- 不把 provider secret、文件路径、raw token 暴露给 adapter。

建议接口：

- `start(): Promise<void>`
- `stop(): Promise<void>`
- `listAdapters(): BridgeAdapterSummary[]`
- `handleRegister(...)`
- `handleMessage(...)`
- `handleCardAction(...)`
- `sendReply(target, payload)`
- `sendUpdate(target, payload)`
- `sendTyping(target, payload)`
- `getStatus()`

### 第 7 步：Bridge 入站 message 转 AgentMessage

对应 CC Connect：`bridgeAdapter.handleMessage`。

Synapse 映射要求：

- `project`：
  - 如果 Bridge message 显式带 `project`，使用它。
  - 如果未带 project，但当前只有一个可用 project，可以 fallback。
  - 如果无法唯一确定 project，返回结构化错误，不能随便选择。
- `session_key` -> `AgentMessage.sessionKey`。
- `platform` -> adapter platform name。
- `msg_id` -> `AgentMessage.messageId`。
- `user_id` -> `AgentMessage.userId`。
- `user_name` -> `AgentMessage.userName`。
- `content` -> `AgentMessage.content`。
- `reply_ctx` -> `AgentMessage.replyCtx`，并包装为 bridge reply ctx：
  - adapter platform
  - project id
  - session key
  - raw reply ctx
  - capabilities snapshot

入站附件：

- Bridge message 中的 base64 image/file 不得直接交给 renderer。
- 如果当前 Agent adapter 不支持这类附件，必须返回明确 unsupported 错误，不能静默丢弃。
- 如果实现附件落盘，必须落到 main process 受控临时目录，文件名要净化，大小和 MIME 必须校验。
- 不允许把外部 adapter 提供的任意路径当成本机路径读取。

### 第 8 步：Bridge 出站 reply/update/typing

目标：AgentRuntime 产生的输出不仅写入 outbox，还要真正发送给连接中的 Bridge adapter。

要求：

- 继续保留 8.0 的 outbox 持久化。
- Bridge 出站必须基于 `ReplyTarget`：
  - `transport.kind` 建议使用 `bridge` 或 adapter platform，但要统一。
  - `transport.connectorId` 使用 adapter platform。
  - `replyCtx` 保存 Bridge reply context。
- Agent event 转出站消息时，至少支持：
  - `text/result` -> `reply`
  - `thinking` -> 可选 `typing` 或进度事件
  - `error` -> `error` 或 `reply` 错误文本
  - `permissionRequest` -> card 或 fallback text
  - `toolUse/toolResult` -> 可选 update/progress
- 如果 adapter 缺少某 capability：
  - `card` 缺失时 fallback 到 text。
  - `update_message` 缺失时用 reply。
  - `typing` 缺失时忽略 typing，但不要报错。
- 出站发送失败要记录 outbox failed 或 audit/warn。

不要只写 outbox 不发 adapter。9.0 的成功标准要求外部 adapter 能收到实际出站消息。

### 第 9 步：Bridge card_action 处理

对应 CC Connect：`bridgeAdapter.handleCardAction`。

最小支持：

- `perm:<requestId>:allow`
- `perm:<requestId>:deny`
- 普通 card action 可转成一条 AgentMessage 或返回 unsupported。

要求：

- 权限回复必须走现有 `AgentRuntimeService.respondPermission(...)`。
- actor 要标记为 bridge adapter/user，不要伪装成 renderer。
- 记录 audit。
- 找不到 pending permission 时返回结构化错误。

### 第 10 步：Bridge session 最小协议

对应 CC Connect `/bridge/sessions` 和 `/bridge/sessions/`。

最小能力：

- list sessions
- create session
- switch active session
- delete session 或 mark inactive

实现要求：

- 复用 `AgentRuntimeService.listSessions()` 和已有 session repository 能力。
- 不直接操作 DataRepository 绕过 AgentRuntime/SessionRepository。
- 所有请求必须鉴权。
- project/session_key 缺失时返回 400 类结构化错误。
- 不做多工作区路由。

如果当前 session repository 缺少 delete/switch 能力：

- 只补本阶段最小需要。
- 不做大范围重构。
- 在 `9.0 最终报告.md` 写清楚支持范围。

### 第 11 步：实现 side-channel send 服务

对应 CC Connect `APIServer.handleSend` 和 `SendToSessionWithAttachments`。

目标：

- Agent 进程可以通过本机受控 API，把文本、图片、文件发送回当前 session。
- 本阶段只实现 `send`，不实现 `cron add`、`relay send`。

请求结构建议：

- `project`
- `sessionKey`
- `message?`
- `images?`
- `files?`

本地 API 要求：

- 只能绑定本机地址或等价本地通道。
- 必须有 token。
- 必须经过 `NetworkServiceRegistry`。
- 不允许裸 `createServer` 出现在业务 service。
- 请求 body 必须限制大小。
- message、images、files 至少一个非空。
- project 不存在返回 not found。
- session 不存在返回明确错误。
- 失败不能吞掉。

发送逻辑要求：

- 文本发送到当前 reply target。
- 图片/文件走附件策略。
- 成功/失败写 outbox。
- 失败写 audit 或 structured warn。
- 不让 side-channel 直接耦合 Feishu、Bridge 或 Renderer。

### 第 12 步：附件策略

必须有独立策略模块，例如 `attachment-policy.ts`。

至少定义：

- 单文件最大大小。
- 单次请求最大总大小。
- 允许的 image MIME。
- 允许的普通 file MIME 或默认 deny/allow 策略。
- 文件名净化。
- 路径约束：
  - 只允许读取当前 workspace 内、受控临时目录内，或 PermissionGuard 明确允许的路径。
  - 不允许读取系统敏感路径。
  - 不允许跟随危险 symlink 逃逸边界。
- 错误回传格式。

图片和文件路径读取必须在 Electron main process 中做，Renderer 或远程 adapter 不得拿到本机真实路径。

### 第 13 步：Agent env 注入

对应 CC Connect `CC_PROJECT`、`CC_SESSION_KEY`。

当前 Synapse adapter env 主要来自 provider runtime view，且 `AgentExecutionContext` 暂时没有 per-session env 字段。需要补最小能力：

- 给 Agent 执行上下文增加 per-session env，或用等价方式把 env 传给 adapter。
- `CodexExecAdapter` 和 `ClaudeCodeAdapter` 都要合并这些 env。
- env allowlist 必须包含新增变量，不能把全部 process env 放开。

建议注入：

- `CC_PROJECT`
- `CC_SESSION_KEY`
- `SYNAPSE_PROJECT`
- `SYNAPSE_SESSION_KEY`
- `SYNAPSE_SIDE_CHANNEL_URL`
- `SYNAPSE_SIDE_CHANNEL_TOKEN`

如果实现了 CLI wrapper，再注入：

- `SYNAPSE_SEND_COMMAND`
- 或把 wrapper 所在目录加入受控 PATH。

注意：

- token 不得写入日志、审计 metadata 或 UI。
- 如果当前 adapter 没有系统 prompt 注入点，不要用大段隐藏 prompt 污染用户消息。
- 可以先通过 env + 测试 adapter 验证 side-channel send。
- 如需加入 send 使用提示，只加入 send 相关短提示，不加入 cron/relay 内容。

### 第 14 步：最小 CLI/API 触发方式

CC Connect 是 `cc-connect send ...`。Synapse 本阶段可以选择：

1. 先实现本地 API，并把 URL/token 注入给 Agent。
2. 如仓库已有 CLI 安装机制可复用，再实现 `synapse send` 或等价 wrapper。

要求：

- 不要假装 CLI 已经存在。
- 如果只实现 API，不要在提示词或报告里写成已经支持命令行工具。
- 如果实现 CLI，必须有测试覆盖参数解析：
  - `--project`
  - `--session`
  - `--message`
  - `--image`
  - `--file`
  - `--stdin`

### 第 15 步：UI 最小状态展示

如果本阶段需要 UI，范围只限 Agent tab 或设置中的最小 Bridge 状态。

可展示：

- Bridge 状态：未启动/已启动。
- 本机地址：只显示 host/port/path，不显示 token。
- adapter 列表：platform、capabilities、connected/disconnected、lastSeen。
- side-channel 状态：enabled/disabled。

禁止：

- 展示 token。
- 展示完整本机敏感路径。
- 写功能介绍、架构解释、营销文案。
- 自定义视觉体系。
- 卡片套卡片。

技术要求：

- 通过窄 `window.synapse.*` preload API 获取状态。
- 不直接访问 `ipcRenderer`。
- 业务逻辑抽到 hook/service，不写进 JSX。
- 使用现有 shadcn/Radix 组件和 Tailwind token。

### 第 16 步：IPC 与 preload

如果 Renderer 需要读取 Bridge 状态：

- 新增或扩展窄 IPC module。
- 必须通过 `IpcRegistry.register(...)`。
- 不允许裸 `ipcMain.handle/on`。
- 更新 `desktop/electron/generated/ipc-channels.generated.ts` 的生成结果。
- 更新 `desktop/electron/preload.ts`。
- 更新 `desktop/src/types/bridge.ts`。
- Renderer 只使用 `window.synapse.*`。

如果改了 IPC codegen，必须运行：

```bash
pnpm --filter @synapse/desktop generate:ipc
pnpm --filter @synapse/desktop check:ipc-codegen
```

### 第 17 步：测试闭环

必须覆盖的测试：

- Bridge protocol schema：
  - register 成功。
  - register 缺 platform 失败。
  - message 缺 session/user 失败。
  - unknown type 不崩溃。
- Bridge adapter service：
  - adapter 注册。
  - 同名 adapter 替换旧连接。
  - adapter 断开后状态更新。
  - inbound message 转 AgentMessage。
  - card_action 权限 allow/deny。
  - outbound reply/update/typing 能发到 fake adapter。
  - capability fallback。
- Bridge session：
  - list/create/switch/delete。
  - auth required。
  - missing project/session_key。
- Network：
  - 通过 `NetworkServiceRegistry` 注册。
  - 默认 bind `127.0.0.1`。
  - token 鉴权失败。
  - stop lifecycle。
- side-channel send：
  - text send 成功。
  - message/attachment 全空失败。
  - project not found。
  - session not found。
  - attachment size limit。
  - image MIME 校验。
  - path escape/symlink 拒绝。
  - 成功/失败写 outbox 或 audit。
- Agent env：
  - Codex adapter 收到 `CC_PROJECT`、`CC_SESSION_KEY`。
  - Claude adapter 收到 `CC_PROJECT`、`CC_SESSION_KEY`。
  - token 不出现在日志 metadata。
- UI 如有变更：
  - typecheck。
  - 静态搜索无内联 style、无硬编码颜色、无渐变、无自定义色值。

至少运行：

```bash
pnpm desktop:typecheck
pnpm desktop:test
pnpm desktop:check:hard-constraints
```

如改 IPC codegen：

```bash
pnpm --filter @synapse/desktop generate:ipc
pnpm --filter @synapse/desktop check:ipc-codegen
```

不要启动 dev server、浏览器预览、Chrome DevTools、Playwright 或运行 App 页面，除非用户明确要求。

## 八、本阶段不得做的事

- 不做 Feishu/Lark。
- 不做 Cron/Scheduler。
- 不做 Relay。
- 不做多工作区路由。
- 不做 Provider 完整配置页。
- 不做大规模 UI 重构。
- 不引入新 UI 库。
- 不新增 `@base-ui/react`。
- 不把业务 service 写成全局单例。
- 不裸用 `ipcMain.handle/on`。
- 不裸用 `webContents.send`。
- 不在业务目录裸用 `http.createServer`、`net.createServer`、`https.createServer`。
- 不把 token、secret、Authorization、provider key 写进日志、UI 或审计明细。
- 不把远程 adapter 传入的路径当成本机路径读取。
- 不让 Renderer 或远程 adapter 直接拿到本机真实文件路径。

## 九、完成标准

完成后必须满足：

- `BridgeAdapterService` 可启动、停止、查询状态。
- 外部测试 adapter 可以注册。
- 同名 adapter 重连会替换旧连接。
- Bridge message 可以进入现有 `AgentRuntimeService`。
- Agent 输出可以发送回 Bridge adapter。
- Bridge adapter 能收到 reply/update_message/typing 中的最小可用子集。
- card_action 能处理权限 allow/deny。
- Bridge session list/create/switch/delete 有最小实现和测试。
- side-channel `send` 可以把文本回传当前 session。
- side-channel `send` 对图片/文件有明确策略；支持或不支持都要有结构化结果，不能静默丢弃。
- `CC_PROJECT`、`CC_SESSION_KEY` 或等价 env 已注入 Agent 运行上下文。
- 出站结果继续走 `ReplyTarget` / `Outbox`。
- 所有网络入口都通过 `NetworkServiceRegistry`。
- `pnpm desktop:typecheck`、`pnpm desktop:test`、`pnpm desktop:check:hard-constraints` 通过，或失败原因明确且不是本阶段引入。
- `分析/cc-connect/9.0/` 下过程产物完整。
- 已提交 commit，建议提交信息：`feat: add bridge adapter side channel runtime`。

## 十、进入 10.0 的条件

只有满足以下条件，才允许进入 `10.0 Connector 基座与 Feishu/Lark`：

- Bridge 协议不依赖飞书 SDK。
- Bridge adapter 输入输出闭环已跑通。
- side-channel `send` 已能复用当前 session reply target。
- 本地网络服务已有安全边界、token、审计和停止能力。
- UI 如有展示，只展示必要状态，不泄露 token/secret/path。
- 没有违反 hard constraints。
