# Synapse 文档站文案规范

本规则在编写或修改文档站（`document/`）内容时生效。

## 1. 产品定位基线

Synapse 文档站面向开发者和技术团队。所有文案必须基于当前仓库实现、`PRODUCT.md`、`docs/reference/product-context.md` 和 capability registry。

- Synapse 是跨编辑器的 AI capability 管理桌面应用。
- 桌面端公开能力包括 Resource Repository、Rule、Skill、Prompt、编辑器安装、Agent、Workflow、Automation、Knowledge Base、Drive、Database、Usage Analysis、Model Price、Git、Diagnostics、系统 App 和 Synapse MCP。
- 编辑器安装目标包括 Antigravity、Claude Code、Codex、Cursor、Hermes、Windsurf 和 WorkBuddy；WorkBuddy 仅支持 Skill，Cursor 不支持全局 Rule。
- 内容仓库可以是本地目录或 Git 仓库；云盘、账号、分享等能力按当前桌面端公开入口描述。

不得描述产品尚未实现的功能。涉及 server、dashboard、管理员后台或未来规划时，除非当前文档页面明确需要，否则不要写入文档正文。

## 2. 语气与调性

### 目标调性

专业、克制、可信。像一份开发者文档，而非营销材料。

参考标杆：Stripe Docs、Tailwind CSS Docs、Vercel Docs — 简洁、精确、尊重读者智商。

### 具体要求

- 使用陈述句，直接说明事实和功能
- 第二人称"你"可以用，但不要过度亲昵（不要"你只需要"、"你会发现"这类引导式语气）
- 技术术语保持原文（Rule、Skill、Prompt、Agent、Workflow、Automation、MCP、Git、CLI），不做不必要的翻译或解释
- 假设读者具备基本的开发工具使用经验

## 3. 禁止清单

### 3.1 禁止口语化 / 大白话

| 禁止 | 替代 |
|------|------|
| "很简单" / "很朴素" / "五分钟可以读完" | 删除，直接进入正文 |
| "先用起来再说" | "适合初期试用" |
| "点几下按钮就行" | "通过界面操作完成" |
| "软件代劳" / "软件会替你" | "Synapse 自动处理" |
| "一眼看清" / "顺畅地流到" | 删除或改为客观描述 |
| "拿到即装即用" / "拿去用" | "安装后即可使用" |

### 3.2 禁止夸大与营销腔

- 不用"最"、"极致"、"颠覆"、"革命性"、"前所未有"、"强大"
- 不用"赋能"、"助力"、"打通"、"闭环"、"生态"、"沉淀"（作动词）
- 不用"自由流动"、"无缝衔接"、"开箱即用"等空洞修饰
- 不写"让 XX 变得简单" — 直接说它做什么

### 3.3 禁止功能介绍性废话

- 不写"这是 Synapse 最核心的能力"
- 不写"看到这里你应该已经有完整印象了"
- 不写"准备好了？接下来请看…"
- 不写"理解了这四个词，你就已经掌握了…"
- 不在段落开头做情感铺垫（"团队里每个人都在积累…"）

### 3.4 禁止类比式排比

不要用排比句式堆砌产品愿景：

```
❌ 连接知识与使用者
   连接个人沉淀与团队复用
   连接 AI 能力与真实工作环境
```

如需说明产品定位，用一句精确的陈述句。

## 4. 结构规范

### 首页（index.md）

- hero.tagline：一句话说清产品是什么 + 核心能力，不超过 40 字
- features：每项 title 用名词短语，details 用一句完整的功能描述，不加感叹词和语气词

### 指南页面（guide/*.md）

- 标题用动宾结构或名词短语，不用疑问句做标题（FAQ 除外）
- 每个章节开头直接进入主题，不做"接下来我们来看看…"式的过渡
- 操作步骤用有序列表，保持指令式语气（"配置仓库目录"而非"你需要配置一个仓库目录"）
- 章节末尾的导航链接用简洁格式：`了解更多：[页面名](/path)` 或 `继续：[页面名](/path)`

### FAQ 页面

- 问题用用户视角的自然疑问句
- 回答第一句直接给结论（是/否/支持/不支持），再展开说明
- 不用"不需要担心"、"完全不需要"等安抚式措辞

## 5. 用词一致性

全站统一使用以下术语，不做同义替换：

| 统一用词 | 不要用 |
|----------|--------|
| Rule | 规则（作为产品概念时） |
| Skill | 能力包（作为产品概念时） |
| Prompt | 提示词（作为产品概念时） |
| Agent | 智能体（作为产品概念时） |
| Workflow | 工作流（作为产品概念时） |
| Automation | 自动化（作为产品概念时） |
| Knowledge Base | 知识库（作为产品概念时） |
| Drive | 云盘（作为产品概念时） |
| Database | 数据库（作为产品概念时） |
| 仓库 | 数据源、内容库 |
| 项目 | 工作目录（作为产品概念时） |
| 安装 | 部署、写入、放置 |
| 编辑器 | IDE、开发工具（指 AI 编辑器时） |

首次出现时可加括号注释：`Rule（规则）`、`Skill（能力包）`，后续直接使用英文。

## 6. 格式规范

- 产品名 `Synapse` 首字母大写，不缩写
- 编辑器名称使用官方写法：Antigravity、Claude Code、Codex、Cursor、Hermes、Windsurf、WorkBuddy
- 文件格式用 code 标记：`.md`、`.zip`、`.dmg`
- 路径和命令用 code 标记：`git clone`、`Settings`
- 中英文之间加空格：`支持 Claude Code 的全局安装`
- 不使用 emoji

## 7. 自检清单

每次修改网站内容后，对照以下问题检查：

1. 是否有描述了产品实际不具备的功能？
2. 是否有口语化表达或大白话？
3. 是否有营销腔或夸大修饰？
4. 是否有多余的情感铺垫或过渡句？
5. 术语使用是否与第 5 节一致？
6. 首页 features 的 details 是否都是客观的功能描述？
