# Edge-Case Audit — 非常规用户行为静态审计

## 目标

模拟真实用户的非预期操作，通过代码静态分析推演系统响应，发现未处理的边界情况和设计缺陷。

## 核心原则

1. **行为先行**：先设计用户操作场景，再去代码中验证系统如何响应。不是从代码出发找 bug，而是从用户行为出发暴露 bug。
2. **纯静态分析**：不启动应用、不运行测试、不执行任何 runtime 操作。所有推演基于代码阅读。
3. **偏向非常规**：重点关注用户"不按套路出牌"的操作——中途取消、并发操作、外部干扰、时序竞争、资源突然消失等。

## 执行流程

### Phase 1：代码结构理解（5 分钟）

快速扫描目标模块的：
- 组件树和状态管理方式
- 异步操作和副作用
- IPC 通信链路
- 错误处理边界

### Phase 2：场景设计（10 个场景）

设计 10 个非常规用户操作场景，覆盖以下类别（每类至少 2 个）：

| 类别 | 描述 | 典型模式 |
|------|------|----------|
| 时序竞争 | 用户操作速度超过系统响应速度 | 快速连击、在异步操作完成前触发下一步 |
| 中途放弃 | 用户在流程中间退出 | 关闭对话框、切换页面、Cmd+Q |
| 外部干扰 | 系统外部环境变化 | 文件被删、网络断开、磁盘满、权限变更 |
| 状态污染 | 前一个操作的残留影响后续操作 | 缓存过期、state 未清理、ref 泄漏 |
| 并发冲突 | 多个操作或多个用户同时作用于同一资源 | 多窗口编辑、远端推送冲突 |
| 超时/挂起 | 长时间操作无进展反馈或无终止机制 | 网络 stall、Git 操作 hang、stream 无数据 |

每个场景必须包含：
- **触发条件**：用户具体做了什么（精确到点击哪个按钮、在什么时机）
- **预期行为**：系统应该如何响应
- **实际推演**：代码实际会怎么执行

### Phase 3：代码推演（逐场景）

对每个场景：

1. **追踪调用链**：从用户交互入口（onClick/onSubmit/onOpenChange）开始，沿着调用链追踪到最终的副作用（文件写入/IPC 调用/状态变更）
2. **标记关键节点**：标注异步边界、状态转换点、错误处理分支
3. **验证防护措施**：检查是否有 guard clause、cancelled flag、loading lock、cleanup function
4. **二次确认**：对于看似有问题的路径，追踪完整调用链确认是否有上层防护（如 Dialog 的 `onOpenChange` 已阻止关闭、loading 状态已禁用按钮等）。避免误报。
5. **判定结果**：
   - ✅ 已正确处理
   - ⚠️ 部分处理（有防护但不完整）
   - ❌ 未处理（会导致异常状态、数据丢失或 UI 错乱）

### Phase 4：输出报告

按严重程度排序输出：

```
## 发现 #{n}：[简短标题]

**严重程度**：高/中/低
**场景**：[用户做了什么]
**代码路径**：[file:line → file:line → ...]
**问题**：[系统实际会怎样]
**影响**：[用户会看到什么 / 数据会怎样]
**建议修复**：[一句话方向]
**修复模式**：[适用的已知修复模式，见下方]
```

### Phase 5：常用修复模式参考

审计发现问题后，建议修复时优先套用以下已验证的模式：

| 模式 | 适用场景 | 实现要点 |
|------|----------|----------|
| 乐观入队 | 操作 A 成功后需要记录，但 A 和记录之间进程可能中断 | 先写记录 → 执行操作 → 成功后清除记录 |
| 自动 abort 恢复 | Git 操作（rebase/merge/cherry-pick）冲突后卡住 | catch 后检测 `.git/rebase-merge` 等标志目录，自动 `--abort` |
| stall 超时 | 网络 stream 不断开但无数据 | 定时检查 lastDataReceivedAt，超阈值主动 abort |
| 目录监听 + 通知 | 外部删除/移动了应用依赖的目录 | `fs.watch` + error 事件 → 通知 renderer 刷新状态 |
| useDeferredValue | 输入驱动的昂贵计算（搜索/过滤） | 输入值即时更新，计算用 deferred 值，避免阻塞输入 |
| 缓存失效重取 | 外部状态可能变化但 UI 缓存了旧值 | 去掉"已有缓存则跳过"的 guard，每次打开时重新获取 |

## 场景设计指南

好的场景应该是：

- **具体的**：不是"用户操作很快"，而是"用户在 Dialog 动画完成前点击了背景遮罩"
- **可推演的**：能从代码中找到确切的执行路径
- **有破坏力的**：如果确实未处理，会导致可观测的问题（不是理论上的、永远不会触发的）
- **非显而易见的**：不是"传入 null 会崩溃"这种一眼能看出的问题

避免的场景类型：
- 纯 UI 样式问题（不属于逻辑缺陷）
- 需要 runtime 才能验证的性能问题（除非代码中有明显的 O(n²) 或无 debounce）
- 已有明确错误处理且处理正确的路径

## 范围控制

- 如果用户指定了模块/文件，只审计该范围
- 如果未指定，选择最近有变更的模块（通过 git status/diff 判断）
- 每次审计聚焦一个功能域，不要试图覆盖整个应用

## 输出格式

直接在对话中输出，不生成文件。除非用户明确要求"写入文件"或"生成报告"。
