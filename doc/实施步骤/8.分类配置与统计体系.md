# 步骤 8：分类配置与统计体系

## 目标

建立 Rules 和 Skills 的独立分类配置体系，并把“分类定义”和“分类统计”明确拆开。这是产品设计文档第 20、41 节的实现，也是列表页筛选的基础。

## 要做的事

### 8.1 建立两套分类配置

- 提供两份内置分类配置：
  - `rulesCategories`
  - `skillsCategories`
- 分类配置建议放在独立目录，例如：

```text
src/
  config/
    categories/
      rules.ts
      skills.ts
```

- 每个分类至少包含：
  - `id`
  - `label`
  - `description`
  - `icon`（可选）
  - `order`

### 8.2 分类 ID 作为稳定主键

- `meta.json` 中写入的 `category` 应该存分类 `id`，不要存展示文案
- UI 展示时再根据 `id` 映射为中文名称
- 后续如果分类文案调整，不应影响已存在内容

### 8.3 分类统计逻辑

- 分类集合来源于配置文件，不再从 `meta.json` 扫描反推
- 分类数量来源于当前仓库实际扫描结果
- 统计维度按模块分开：
  - Rules 只统计 Rule 数量
  - Skills 只统计 Skill 数量

### 8.4 未识别分类的兜底策略

- 如果某个历史数据的 `meta.category` 在当前配置中找不到：
  - 不要让该内容消失
  - 归入一个系统兜底分类，例如“未识别分类”或“其他”
  - 同时记录日志，方便后续修复数据

### 8.5 排序与展示规则

- 左侧分类栏顺序由配置中的 `order` 决定，不按数量排序
- 分类数量显示为当前仓库实时统计值
- 可额外提供“全部”分类，用于展示当前模块全部内容

### 8.6 对外暴露统一接口

- 给渲染进程提供统一的数据结构，例如：

```typescript
interface CategoryViewItem {
  id: string;
  label: string;
  count: number;
  order: number;
  isFallback?: boolean;
}
```

- Rules 和 Skills 都复用同一套统计拼装逻辑，避免两边各写一套

## 注意事项

- 分类定义必须是开发者维护的内置配置，不能重新退回到“扫描 meta 自动生成分类集合”
- Rules 和 Skills 的分类体系必须独立，不要混成一套枚举
- 分类配置应放在前端可直接使用的位置，但不要散落到各模块内部多个文件里
- 统计结果跟随当前激活仓库变化，切换仓库后应重新计算
- 创建表单中使用的分类选项，也应直接复用这套配置，避免列表页和创建页不一致

## 验收标准

1. Rules 和 Skills 各自有一份独立分类配置
2. 左侧分类栏来源于配置文件，而不是扫描结果
3. 每个分类能显示当前仓库下的数量
4. 未识别分类的数据不会消失，而是进入兜底分类
5. 列表页和创建表单使用同一套分类定义
