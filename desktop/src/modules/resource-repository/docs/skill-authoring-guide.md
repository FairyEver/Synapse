## 执行原则

1. 先阅读当前项目的 `AGENTS.md`、规则文件、现有 Skill、模板、脚本和测试，优先复用已有约定与公共能力。
2. 从当前上下文中提取 Skill 的职责、触发场景、输入、输出、限制和成功标准。只有会显著改变结果且无法从项目中确认的信息缺失时，才向用户提问。
3. 做外科手术式修改。只改完成当前 Skill 任务所需的文件，不做无关重构，不新增没有明确用途的目录或依赖。
4. 不编造 API、文件路径、配置值或工具能力。遇到无法验证的外部事实时，明确说明限制。
5. 修改已有 Skill 时保持原有名称、入口和兼容行为，除非用户明确要求改变。

## 目录结构

Skill 文件夹名称使用小写字母、数字和短横线，并与 `SKILL.md` 中的 `name` 一致。只创建实际需要的资源目录。

```text
my-skill/
├── SKILL.md
├── .env.example     # 仅在需要外部配置时创建
├── scripts/         # 可重复、确定性执行的脚本
├── references/      # 按需读取的详细资料
└── assets/          # 输出时复制或修改的模板、图片等素材
```

不要在 Skill 内额外创建 README、快速参考、安装指南或变更日志。Agent 执行任务所需的核心规则写在 `SKILL.md`，详细资料按需放入 `references/`。

## SKILL.md

- YAML frontmatter 只写 `name` 和 `description`。
- `description` 必须同时说明 Skill 能做什么，以及哪些用户表述、文件、链接或任务场景应触发它。所有触发说明都放在 `description` 中。
- 正文使用简洁、直接的祈使句，说明执行流程、工具选择、关键限制、失败处理和输出要求。
- 使用渐进式披露：常用流程保留在 `SKILL.md`，只在特定场景需要的详细内容放入 `references/`，并在正文中明确何时读取。
- `SKILL.md` 应保持聚焦，接近 500 行时优先拆分参考资料，不要让无关背景长期占用 Agent 上下文。

## 文件职责

- `scripts/` 存放需要稳定执行、经常重复编写或适合确定性处理的程序。优先修复和复用现有脚本，不重复实现同一逻辑。
- `references/` 存放仅在特定任务中读取的规范、API 资料和长篇说明。大型参考文件应提供清晰目录。
- `assets/` 存放生成结果时使用的模板、图片、字体等资源，不存放操作说明。
- 测试或评估文件只在能验证 Skill 行为时创建，并遵循当前项目已有的测试结构。

## 外部配置与敏感信息

只有 Skill 确实需要外部配置时，才在根目录创建或完善 `.env.example`。

- 使用标准 Dotenv `KEY=value` 格式，键名必须匹配 `[A-Za-z_][A-Za-z0-9_]*`，并保持稳定、清晰。
- 必填值留空；非敏感配置可以提供默认值。每组和每个配置项都添加必要注释，说明用途或影响范围。
- `.env.example`、`SKILL.md`、脚本、日志、测试夹具和生成文件中不得包含真实 token、密码、API Key、私钥或生产连接信息。
- 本地 `.env` 不属于 Skill 发布内容，必须确保它被 Git 忽略。不要要求 Agent 读取、展示或复制 `.env`。
- 消费配置的脚本必须根据脚本自身位置定位 Skill 根目录，不能依赖启动命令的当前工作目录。
- Node.js 20.12 及以上优先使用内置的 `process.loadEnvFile()`；其他运行时优先复用已有原生能力或项目依赖。没有明确必要时不要新增依赖。
- 缺少必需配置时，只报告缺失的键名和修复动作；不要打印完整环境变量或把敏感值写入命令参数、日志、错误详情和缓存。
- 检查 `spawn`、`exec`、`curl` 等实际调用参数；事后把日志脱敏不能消除进程参数中的敏感信息。旧兼容行为与安全要求冲突时，停止使用不安全入口并明确说明，不要静默保留。
- dry-run、格式检查和载荷预览不得读取非必要密钥，也不得构造包含密钥的命令参数。

Node.js 示例：

```js
import path from "node:path"
import { fileURLToPath } from "node:url"

const scriptDirectory = path.dirname(fileURLToPath(import.meta.url))
const skillRoot = path.resolve(scriptDirectory, "..")
process.loadEnvFile(path.join(skillRoot, ".env"))

const token = process.env.API_TOKEN
if (!token) throw new Error("缺少必需配置：API_TOKEN")
```

## 创建新 Skill

1. 根据用户需求确定单一职责、触发场景、预期输出、必要工具和成功标准。
2. 检查当前项目是否已有相近 Skill、模板、脚本或公共能力，避免重复建设。
3. 创建最小可用的 `SKILL.md`，只有任务确实需要时才添加 `scripts/`、`references/`、`assets/` 或 `.env.example`。
4. 对可客观验证的 Skill 添加最小测试或 2 至 3 个真实使用场景；主观输出至少完成一次代表性检查。
5. 验证 frontmatter、目录名称、引用路径、脚本入口和输出格式均符合当前项目约定。

## 修改已有 Skill

1. 先阅读现有 `SKILL.md`、脚本、参考资料、资源、配置文件和测试，确认当前触发方式、执行入口、数据流和兼容边界。
2. 保持 Skill 文件夹名称和 `name` 不变；除非任务明确要求，否则不要更换入口、删除受支持场景或扩大职责范围。
3. 根据用户需求修改触发描述、执行流程和必要资源。正文与参考资料、脚本或测试存在对应关系时同步更新，避免规则与实现不一致。
4. 删除不再使用的重复规则和失效引用，但不要覆盖用户数据或进行未经确认的破坏性清理。
5. 如果任务涉及从正文变量替换或硬编码配置迁移到 ENV：
   - 找出真正消费配置的程序和全部敏感值来源。
   - 在 `.env.example` 中只声明必要键名、注释和非敏感默认值。
   - 让运行入口从 Skill 根目录 `.env` 读取配置。
   - 删除正文和代码中的真实敏感值及安装时写入正文的敏感占位符。
   - 无法确定的值保持为空，不得编造。
6. 运行现有测试并补充覆盖本次修改的最小验证。修改配置加载时，还要从非 Skill 工作目录启动一次，验证缺少必需键时会安全失败，并确认 dry-run 不依赖 `.env`、子进程参数不含敏感值。

## 完成标准

- 实际文件已创建或修改，功能与用户要求一致。
- Skill 名称、触发描述、正文指令和资源引用相互一致。
- 没有新增无关文件、依赖、重复文档或敏感信息泄漏。
- 已运行与改动相称的测试或最小验证，并处理发现的问题。
- 最终统计并总结所有实际文件变更，包括本地 `.env` 等未发布文件；只说明文件用途、行为变化、声明的配置键名和验证结果，不展示任何配置值，不复述敏感信息。
