# auto Prompt 编写指南

这份文档用于复制给 AI，帮助它为 `auto/prompts/*.md` 编写适合并行轮询执行的 Prompt。

## auto 是什么

`auto` 是本地 Codex 并行运行控制台。它会按页面或保存配置启动 `codex exec`，把同一个 Prompt 分发给多个 worker，并按批次循环运行。

它适合做：

- 对一个大方向进行并行小步修复。
- 让多个 Agent 独立审查不同候选问题。
- 周期性补齐测试、日志、类型、文档或低风险缺陷。

它不适合做：

- 需要单一全局设计判断的大重构。
- 需要多个 worker 修改同一组核心文件的任务。
- 需要人工连续确认、运行图形界面或依赖浏览器调试的任务。
- 没有明确边界的“全面优化”“尽可能多修”。

## 运行环境

编写 Prompt 时，默认假设它会在下面的环境中执行：

- 多个 worker 会在同一个工作目录中并行运行同一个 Prompt。
- 每个 worker 会收到自己的编号，例如 `worker 1/5`。
- 每个 worker 都可以读写工作区文件，并运行 Prompt 允许的命令。
- `auto` 不创建 git worktree，不做文件锁，不自动合并冲突。
- `auto` 不理解任务语义，只负责启动进程、传入 Prompt、收集日志和按间隔继续下一批。
- 一批结束后，scheduler 可能等待配置的 interval，然后再次启动下一批。
- 页面里的 `Stop after current` 只会阻止下一批，当前批次会继续跑完。
- worker 日志会写入 `auto/logs/<batch>/worker-N.md`，批次摘要写入 `summary.md`。

runner 会自动在用户 Prompt 前追加基础并行约束，包括：

- 不要回滚或覆盖自己没有明确修改的内容。
- 如果提交，只能 stage 和 commit 本轮亲自修改的文件。
- 不要使用 `git add .`。
- 提交前检查 `git diff` 和 `git status`。

这些基础约束不够覆盖复杂任务。凡是会改代码的 Prompt，都应该额外写清楚并行协作规则。

## Prompt 设计原则

### 1. 每轮只做一个小目标

不要让一个 worker 同时修多个问题。推荐写法：

- 每轮最多修复 1 个可证明缺陷。
- 或补齐 1 组同一链路上的日志、测试、类型或文档缺口。
- 如果找不到符合条件的问题，本轮可以只输出调查结果，不强行修改。

### 2. 先证据，后修改

Prompt 应要求 worker 在动手前写出证据链：

```text
用户操作或触发入口
→ 经过的代码链路
→ 当前错误结果或缺口
→ 为什么这是正常使用会遇到的问题
```

每一环尽量引用具体文件和行号。需要运行 App、打开浏览器或靠猜测才能确认的问题，应放弃。

### 3. 明确写入范围

并行任务必须让 worker 先声明要修改的文件或符号。推荐策略：

- 默认文件级 claim。
- 大文件只在不改 imports、exports、props、共享类型时，才允许符号级 claim。
- 发现目标文件已被其他 worker 占用时，可以短暂等待；等待后仍被占用，再换一个候选问题。
- 等待锁时要有上限，推荐 1 到 3 分钟；不要长时间阻塞整个 worker。
- 不做全文件格式化，不批量重排 imports，不顺手重构邻近代码。

如果任务需要严格并行安全，Prompt 应提供共享状态文件和锁协议，例如：

```text
auto/state/fix-log.md
auto/state/coverage-map.json
auto/state/focus.md
auto/state/parallel/claims.jsonl
auto/state/parallel/locks/
auto/state/parallel/agent-notes/
```

### 4. 禁止事项要写具体

不要只写“谨慎修改”。应该明确禁止：

- 新增依赖。
- 大重构、新功能、新页面、新架构层。
- 破坏性 git 操作。
- `git add .`、`git add -A`、`git commit -a`。
- 启动 dev server、Electron app、浏览器、Playwright，除非任务明确需要且允许。
- 修改无关文件。
- 把 secret、token、完整 prompt、完整 message、完整路径或敏感日志写进输出。

### 5. 验证要小而直接

Prompt 应指定允许的验证方式，优先从小到大：

1. 与本轮改动直接相关的测试。
2. 目标文件 typecheck 或 lint。
3. 项目已有硬约束检查。
4. 必要时再运行更大范围测试。

如果验证失败来自既有问题，worker 应记录证据，不要顺手修无关问题。

### 6. 输出格式要稳定

为了后续批次能读懂历史，Prompt 应要求 worker 以固定格式收尾：

- 本轮选择的问题。
- 修改文件。
- 验证命令和结果。
- 未解决风险。
- 是否更新共享状态。

需要写日志型状态文件时，先写 worker 自己的 note，再在持有 state lock 后更新共享索引。

## 推荐工作模式

写 Prompt 前先选择一种主要工作模式。一次运行最好只选 1 到 2 种，不要把发现问题、修复问题、补日志、补测试和收敛整理全塞进同一个 Prompt。

### 巡检模式

适合还不确定问题在哪里的任务。

- 每个 worker 只找 1 个候选问题。
- 重点输出证据链、影响范围和建议方案。
- 只有发现高置信、低冲突的问题时才修改。
- 找不到高置信问题时，只输出调查结果，不强行改代码。

### 小步修复模式

适合已有明确模块或链路的任务。

- 每轮只修 1 个 P0/P1/P2 问题。
- 修改前声明文件或符号范围。
- 优先写聚焦测试或给出静态证据。
- 修改限制在少量直接相关文件内。
- 修完后更新状态记录，避免下一批重复处理。

### 日志补齐模式

适合提升失败复盘能力。

- 每个 worker 选择一个边界，例如 renderer、IPC、main service、scheduler、SDK bridge。
- 只补能回答复盘问题的日志。
- 明确记录关联字段，例如 taskId、runId、conversationId、messageId、sessionId。
- 必须写清脱敏规则。
- 禁止“进入函数”式噪声日志。

### 测试补齐模式

适合给脆弱链路补保护网。

- 每轮只补 1 组同主题测试。
- 优先覆盖已有缺陷、边界行为或高风险链路。
- 不为了测试大改生产代码。
- 如果测试暴露真实 bug，再按小步修复模式处理。

### 收敛模式

适合 auto 已经跑过多轮之后做整理。

- 不主动寻找新问题。
- 只读 fix-log、coverage-map、focus、worker 日志和 git diff。
- 合并重复记录，标注已解决和未解决项。
- 输出下一轮建议或停止建议。
- 默认不改业务代码。

## 退出条件

Prompt 应写清 worker 何时停止本轮行动，避免为了产出而硬改：

- 找不到符合优先级的问题时，只输出调查结果。
- 目标文件被占用时，短暂等待；超过等待上限仍不可用，就换候选或结束本轮。
- 证据链不完整时，不进入实施。
- 验证失败但属于既有无关问题时，记录证据，不扩修。
- 连续多批没有新发现时，下一轮应改用收敛模式。

## 推荐 Prompt 结构

编写新的 `auto/prompts/*.md` 时，优先使用这个结构：

````markdown
# <任务名称>

你正在对 <项目/模块/链路> 做一次并行安全的小步处理。

本 Prompt 可能会被 N 个 Agent 在同一工作目录中并行循环执行。每个 Agent 每轮只处理一个真实问题。不要做大重构，不要做新功能。

## 本轮总目标

- <目标 1>
- <目标 2>
- <目标 3>

## 工作模式

本轮使用 <巡检模式 / 小步修复模式 / 日志补齐模式 / 测试补齐模式 / 收敛模式>。

## 并行原则

- 外部已经有 N 个 Agent 并行。单个 Agent 不得再启动子 Agent。
- 每轮最多处理 1 个问题。
- 修改前先声明写入范围。
- 如果目标文件已被其他 Agent claim 或 lock，最多等待 <1 到 3 分钟>；仍不可用就换一个问题。
- 宁可本轮无修复，也不要抢同一处代码。

## 禁止事项

- <禁止事项 1>
- <禁止事项 2>
- <禁止事项 3>

## 必读入口

先按候选方向阅读，不要一次性展开无关文件。

- `<path>`
- `<path>`
- `<path>`

## 优先级

1. P0：<最严重问题>
2. P1：<高优先级问题>
3. P2：<中优先级问题>
4. P3：<低优先级问题>

## 候选选择方法

每个候选都必须先写出证据链：

```text
触发入口
→ 代码链路
→ 错误结果或缺口
```

如果证据不足，放弃该候选。

## 实施规则

- 先写聚焦测试或最小可验证证据。
- 再实现最小修复。
- 改动限制在已声明范围内。
- 不新增依赖，不做无关重构。
- 修改后重新阅读改动文件，确认没有误碰。

## 验证

允许：

- `rg`、`sed`、`git diff`、`git status`
- 与本轮修改直接相关的测试
- 目标文件 typecheck 或 lint

禁止：

- <本任务不允许的验证方式>

完成前至少尝试：

1. <验证命令 1>
2. <验证命令 2>
3. <验证命令 3>

## 退出条件

- <无高置信候选时如何结束>
- <锁等待超时后如何处理>
- <验证遇到既有问题时如何记录>

## 收尾

最终输出：

- 问题：
- 修改：
- 验证：
- 风险：
- 后续建议：
````

## 让 AI 帮你写 Prompt 时，可以这样要求

把本 GUIDE 和任务背景一起发给 AI，然后补充：

```text
请根据 GUIDE，为 auto/prompts/<name>.md 编写一个可直接运行的 Prompt。

要求：
- 面向 N 个并行 Codex worker。
- 每个 worker 每轮只处理一个小问题。
- 先选择推荐工作模式，并写清退出条件。
- 明确禁止事项、写入范围、验证命令和收尾格式。
- 不要写空泛口号，不要鼓励大重构。
- 如果任务涉及 UI，必须遵守 Synapse 的 UI 样式纪律和产品文案纪律。
- 如果任务涉及日志，必须写清脱敏规则。
- 如果任务涉及并行修改，必须包含 claim/lock 或避让规则。
```

## 常见坏 Prompt

避免这类写法：

```text
请全面优化 Synapse 的 Agent 模块，发现问题就修，尽可能多改。
```

问题：

- 目标过大，worker 会互相抢文件。
- 没有优先级，容易做低价值改动。
- 没有证据要求，容易凭感觉改。
- 没有验证边界，容易跑长耗时命令。

更好的写法：

```text
请并行审查 Agent 消息发送链路。每个 worker 每轮只选择 1 个可证明的 P0/P1 缺陷或 1 组同链路日志缺口。修改前声明文件范围；如果文件已被占用，换候选。优先补测试，做最小修复，完成后运行聚焦测试和硬约束检查。
```

## 最小检查清单

写完 Prompt 后，确认它回答了这些问题：

- 这次并行任务的目标是什么？
- 每个 worker 一轮最多能做多少事？
- worker 如何选择候选问题？
- 哪些文件或目录是优先阅读入口？
- 哪些行为被禁止？
- 是否允许提交？
- 是否允许启动 App、dev server、浏览器或 Playwright？
- 是否需要 claim/lock？
- 文件锁被占用时允许等多久？
- 本轮使用哪种工作模式？
- 退出条件是什么？
- 验证命令是什么？
- 失败或无修复时应该怎么输出？
- 是否需要更新共享状态文件？
