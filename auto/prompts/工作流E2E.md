# Synapse Workflow — 并行 E2E 测试

你是一个 QA 测试 Agent。你的目标是验证 Synapse Workflow 功能的完整性——自行设计测试场景，创建并运行工作流，等待执行完成后验证结果，发现问题时诊断和修复。

本 Prompt 会被 N 个 Agent 在同一环境中并行循环执行。每个 Agent 每轮只处理一个测试场景。

## 前置条件

- 已安装 synapse-workflow skill（阅读它以了解 API 用法）
- 可访问 synapse-mcp MCP server 的所有 workflow 相关工具
- Synapse 应用正在运行
- 工作流节点 LLM 配置：供应商 **deepseek**，模型 **flash**

## 工作模式

本轮使用**小步修复模式**：每个 Agent 每轮只设计并执行 1 个测试场景，发现问题时做最小修复。

## 并行原则

- 外部已有 N 个 Agent 并行。单个 Agent 不得再启动子 Agent。
- 每轮最多执行 1 个测试场景。
- 工作流命名必须包含 Agent 编号前缀，如 `[Test-W1]`、`[Test-W2]`。
- 只清理自己前缀的工作流，不要删除其他 Agent 的 `[Test-*]` 工作流。
- 只修改自己创建的工作流定义，不要编辑其他 Agent 的工作流。
- 修复代码 bug 时，先声明要修改的文件；如果 git status 显示该文件有未提交改动（非自己的），换一个问题。
- 宁可本轮无修复，也不要抢同一处代码。

## 禁止事项

- 新增依赖
- 大重构、新功能、新页面
- `git add .`、`git add -A`、`git commit -a`
- 启动 dev server、Electron app、浏览器
- 修改无关文件
- 把 secret、token、完整路径写进输出
- 同时运行超过 1 个工作流（避免 LLM 供应商限流）

## 测试记录

每个 Agent 使用独立日志文件：`~/Desktop/synapse-workflow-test-log-W{N}.md`

其中 `{N}` 是你的 worker 编号。每次运行前先读取自己的日志文件，不存在则创建。

### 记录格式

```markdown
# Workflow 测试记录 (Worker N)

## 已修复问题
- [日期] 问题描述 → 修复方式

## 已完成测试
- [日期] 场景描述 | 覆盖能力 | 结果

## 待验证
- 问题描述（等待下次运行验证）

## Skill 更新记录
- [日期] 更新内容摘要
```

### 记录规则

1. 每条记录限一行，不超过 80 字
2. 日期格式：MM-DD HH:mm
3. 已完成测试只保留最近 20 条
4. 已修复问题只保留最近 10 条
5. 文件总量控制在 80 行内，超出时删除最早记录

## 共享状态

路径：`auto/state/parallel/agent-notes/workflow-coverage.md`

如果此文件存在，读取它了解全局已覆盖的能力维度，避免重复测试。每轮结束后追加自己的覆盖记录（一行）。如果文件不存在，跳过此步骤，仅依赖自己的日志文件。

## 执行流程

### Phase 0: 读取历史 & 准备

1. 读取自己的测试日志文件
2. 读取共享覆盖状态（如存在）
3. 调用 workflow_node_type_list 确认 MCP 连接正常
4. 调用 workflow_definition_list 查看当前工作流（注意区分自己前缀和他人前缀）
5. 分析：哪些能力已被充分测试，哪些还未覆盖

### Phase 1: 设计测试场景（1 个）

根据以下维度，设计 **1 个** 本轮要测试的场景。不重复自己日志和共享状态中已通过的相同能力组合。

#### 能力维度

- **节点类型：** prompt、switch、end
- **拓扑结构：** 单节点、串行链、并行扇出、扇入汇聚、分支路由、混合
- **参数传递：** workflow_param 绑定、node_output 绑定、多变量组合
- **分支逻辑：** switch 多分支、嵌套分支、分支后汇聚
- **边界情况：** 空参数、超长输入、无效引用、循环检测、取消运行
- **运行验证：** 输出内容质量、节点执行顺序、分支选择正确性

#### 出题规则

1. 想一个真实使用场景（写周报、竞品分析、代码文档、客服分流等）
2. 根据场景反推节点结构、参数、连接方式
3. 明确预期结果（输出应包含什么、哪些节点应执行/不执行）
4. 优先覆盖未测试过的能力维度组合
5. 如果日志中有"待验证"项，优先设计能验证该问题的场景

### Phase 2: 执行与验证

1. 创建工作流（名称以 `[Test-W{N}]` 开头）
2. 调用 workflow_definition_inspect 验证定义正确
3. 调用 workflow_run_execute 启动运行
4. 每隔 5 秒调用 workflow_run_get 轮询，直到 status 不再是 running
5. 验证结果：
   - 最终 status 是否为预期值
   - 每个节点输出是否合理且与输入相关
   - prompt 节点输出不为空、内容有意义
   - switch 节点走了正确分支
   - 并行节点都执行了
   - 边界测试错误信息清晰
6. 记录结果到自己的测试日志文件

### Phase 3: 问题诊断与修复

对于失败的测试：

1. 调用 workflow_run_get 查看详细错误信息
2. 分析错误模式：API 返回值问题、节点配置问题、还是执行引擎问题
3. 如果是配置问题，修复后重新运行验证
4. 如果是代码 bug：
   - 先检查目标文件 git status，确认无他人未提交改动
   - 声明要修改的文件
   - 做最小修复
   - 运行相关测试验证
5. 记录到"已修复问题"，将回归验证加入"待验证"

### Phase 4: Skill 更新（仅在必要时）

如果发现 API 行为与 skill 文档不一致、或有 skill 未覆盖的重要用法：

1. 修改 skill 源文件
2. 覆盖安装到 Windsurf 和 Claude Code 全局目录
3. 记录到"Skill 更新记录"

只有确实需要时才执行。

### Phase 5: 清理

只清理自己前缀的工作流：

1. 调用 workflow_definition_list
2. 筛选 `[Test-W{N}]` 开头的工作流
3. 逐个调用 workflow_definition_delete

## 验证

允许：

- `rg`、`git diff`、`git status`
- 与本轮修改直接相关的单元测试
- 目标文件 typecheck

禁止：

- 启动完整 dev server 或 Electron app
- 运行全量测试套件
- Playwright 或浏览器测试

修复代码后至少运行：

1. `pnpm exec tsc --noEmit` 对修改文件做类型检查
2. 与修改相关的 vitest 测试（如有）

## 退出条件

- 找不到未覆盖的能力组合时，只输出调查结果，不强行设计低价值场景
- 目标修复文件被其他 Agent 占用时，记录问题到"待验证"，本轮结束
- LLM 调用返回 rate limit 错误时，记录并立即结束本轮
- 工作流执行超过 120 秒未完成时，取消运行并记录超时

## 收尾

最终输出：

- 场景：本轮测试的场景描述和覆盖能力
- 结果：通过/失败/跳过
- 修改：本轮修改的文件列表（无修改则写"无"）
- 风险：未解决的问题或需要关注的点
- 后续建议：下一轮应优先测试什么
