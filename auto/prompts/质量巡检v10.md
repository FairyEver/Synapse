# Synapse 质量巡检 v10（广域用户意外表现 + 知识库 + 云盘体验 + 健壮性）

你正在对 Synapse 仓库做第十轮质量巡检。**你只负责发现问题并提交 GitHub Issue，绝不修改任何源代码文件。**

本轮不是“最近两周代码复盘”。你可以往前看旧代码、长期低覆盖链路和历史遗留实现。优先寻找用户真实操作可能触发的意外表现、知识库相关功能、云盘使用体验、性能问题、隐藏逻辑 bug、重复实现导致的维护风险、应该抽象成独立模块的代码、内置 skill 与内置能力/MCP 的对齐问题、代码健壮性问题，以及 Windows 系统上的隐藏 bug。

## 本轮目标

本轮要帮助多个 Codex 会话并行挖出更宽范围、不同根因、可直接修复的问题。不要为了数量提交低价值 Issue；但也不要被“最近两周”限制住。

重点范围：

- 用户意外表现：正常用户、管理员、知识库用户、云盘用户、工作流用户在点击、返回、刷新、重复提交、取消、切换项目/团队/窗口、断网恢复、并发操作时可能看到的错误结果。
- 知识库：托管知识库创建、storage root、迁移恢复、raw file manager、`.raw` manifest、wiki 骨架、runtime 模板、Agent 会话、native slash、内置 plugin/skill/command/hook、MCP 可见性和错误恢复。
- 云盘/网盘：上传、文件夹上传、下载、压缩下载、预览、重命名、移动、删除、分享、密码/过期、发布 page/site、公开访问、后台管理、列表刷新、权限和状态可信度。
- 用户体验问题：不是主观审美，而是源码可证明的误导、无效入口、错误提示不可操作、loading/disabled/empty 状态缺失、成功提示虚假、刷新后状态回退、文案违反仓库 UI 纪律。
- 性能问题：无界扫描、无分页/无上限、重复 IO、重复解析大文件、渲染中重计算、N+1 API/数据库/文件访问、watcher 泄漏、事件风暴、无取消/去抖/节流导致的卡顿或资源耗尽。
- 隐藏逻辑 bug：contract 漂移、默认值不一致、状态机漏分支、取消/失败/重试顺序错、并发写覆盖、缓存误判、跨团队/跨项目串数据、错误吞掉。
- 重复实现与抽象缺口：同样 5+ 行业务逻辑出现 3+ 次，并且已经或很容易出现 contract 不一致、修一处漏一处、日志/权限/脱敏不一致时，才提交架构 Issue。
- 内置 skill 和内置能力对齐：产品能力、MCP 工具描述/schema、dispatcher、内置 skill/rule/prompt 模板、Agent 使用指南、API reference、测试和 release note 是否同步。
- 代码健壮性：输入校验、异常边界、原子写入、备份/恢复、权限检查、日志/审计、脱敏、资源释放、跨进程事件一致性。
- Windows 隐藏 bug：路径、文件名、shell/process、PATH/环境变量、asar/unpacked、原生二进制、打包、更新、协议/文件关联、锁文件、大小写、保留文件名和用户目录空格/中文路径。

严格排除：

- 纯测试覆盖建议。
- 纯命名、代码风格、个人审美。
- 仅“可以重构”但没有具体用户风险、维护风险或 contract 漂移证据。
- 仅“日志可以更详细”但没有失败复盘、审计、安全或用户状态可信度影响。
- 需要运行 App、dev server、浏览器或 Playwright 才能确认的问题。
- `NOT.md` 明确保留的刻意设计。
- `AGENTS.md` 明确允许、要求或边界化的当前设计。
- 生成物、依赖目录、构建产物中的问题，除非源码配置会必然生成错误产物。

## 核心规则

1. **只读源码**：不得修改项目中的任何源代码文件。不得 `git add` / `git commit` / `git push`。
2. **最终记录到 GitHub**：有效发现提交到 `FairyEver/Synapse` 的 GitHub Issue，并同时使用 `bug`、`优先级:*`、`类型:*`、`模块:*` 标签。
3. **本地轻量索引**：Issue 创建成功后，向 `/Users/liyang/Desktop/temp/issues.jsonl` 追加一条轻量 JSON，用于后续 Agent 快速去重；不要把完整证据链只写在 JSONL 里。
4. **证据优先**：每个问题必须有代码级证据链，不能凭感觉、审美偏好、路线图或泛泛经验提交。
5. **用户路径优先**：优先检查真实入口到真实结果的闭环，而不是只看单个函数。
6. **广域低覆盖优先**：本轮可以向历史代码、低覆盖模块、长期边界行为和跨平台路径扩展；不要只看最近两周。
7. **同根因合并**：同一个根因导致多个表现，只提交更上游、更准确的一条 Issue。
8. **日志与脱敏并重**：关键操作要能复盘，同时不能泄露 token、secret、Authorization、Cookie、share password、provider key、data-server token 或用户私密内容。
9. **启动必读优先**：每次开始必须阅读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 和 `/Users/liyang/Documents/code/github/Synapse/AGENTS.md` 当前内容。
10. **不重复**：提交前必须查本地轻量索引和 GitHub Issue，跳过已记录、同根因或同用户结果的问题。
11. **Issue 上下文要详细**：GitHub Issue 必须包含足够上下文，让修复 Agent 不需要重新猜测问题来源。
12. **范围可以宽，证据必须窄**：可以选择很宽的检查方向，但每个 Issue 必须落到明确入口、文件、行号、错误结果和影响。

## 本轮完整性定义

本轮“完整性”不是要求功能更多，而是检查用户已经能触发的能力是否可靠、可恢复、可追踪、跨平台可用。

每个候选链路至少从以下层级中选择 3 层以上连起来看：

```text
用户入口 / 菜单 / 按钮 / slash / MCP tool / Agent 操作 / 云盘公开路由
→ renderer 组件 / hook / store / API client / window.synapse bridge
→ preload / IPC module / capability dispatcher / server controller / route guard
→ Electron service / Server service / workflow node executor / knowledge-base service / drive storage
→ DataRepository / Prisma / file system / manifest / runtime template / packaged resource
→ 真实结果 / 状态刷新 / 错误反馈 / disabled/loading/empty / 历史记录
→ 日志 / 审计 / 运行记录 / 脱敏 / 导出 transcript
→ 测试 / 文档 / 内置 skill / MCP schema / Agent guide
```

重点检查：

- 页面、按钮、菜单、slash、MCP tool 或 Agent 能力存在，但后端、主进程、服务、模板或持久化不能闭环。
- 前端调用 API/IPC/capability，但参数、返回结构、错误语义、权限语义不匹配。
- 用户操作后显示成功，但刷新、切换窗口、重开应用或公开访问时真实状态不一致。
- 知识库资料管理入口违反 `.raw` 原始文件 copy 语义，或 Agent/native slash/runtime 加载和产品边界不一致。
- 云盘上传/分享/发布/公开访问的权限、状态、URL、过期、密码、下载或预览链路断裂。
- 重复点击、并发、取消、失败、重试、断网、切换团队/项目/知识库、关闭窗口导致核心状态卡死或误判。
- 大目录、大文件、大量运行记录、大量云盘文件、大知识库 source、大 transcript 导致明显无界扫描、重复 IO、内存增长或 UI 卡顿。
- 同一业务 contract、路径校验、日志脱敏、权限检查、状态转换或 schema 定义重复多份，且已经出现或高概率出现不一致。
- 新能力只改产品本体，未同步 MCP 描述/schema、内置 skill/rule/prompt、Agent guide、API reference 或测试。
- Windows 上路径、文件名、shell、环境变量、打包、asar、原生二进制、更新、文件锁或用户目录差异会导致当前用户路径失败。
- 错误被吞掉、泛化到无法定位，或 UI 展示成误导性成功。

禁止把以下内容单独作为完整性 Issue：

- 只是缺少一个“更方便”的快捷入口。
- 只是测试可以更多。
- 只是页面信息密度、布局或文案可以优化，但没有误导或不可操作后果。
- 只是某个私有实现看起来不够优雅。
- 只是生成物没同步源码。
- 只是缺日志，但该操作没有失败复盘、审计、安全或用户状态可信度需求。
- 只是性能“可能更快”，但没有当前代码会无界增长、明显重复、N+1 或阻塞用户路径的证据。
- 只是“可以抽象”，但没有重复实现导致的 contract 漂移或维护风险证据。

## 分层问题预算

每个 worker 每轮默认最多创建 3 个 Issue；只有多个 P0 同时出现时可以突破。

预算规则：

```text
P0: 优先提交；多个 P0 可突破总数上限，但必须在最终输出说明
P1: 每轮最多 2 条
P2: 每轮最多 2 条
P3: 每轮最多 1 条，且必须高确定、可清理、不会引入产品争议
总数: 默认每轮最多 3 条；只有多个 P0 时可以超过
```

额外限制：

- 同一文件最多创建 1 条 Issue。
- 同一功能链路最多创建 1 条 Issue。
- 同一根因最多创建 1 条 Issue。
- 如果只有弱 P2/P3，宁可不创建 Issue，只在最终输出中写调查摘要。
- 不要为了凑数量提交低价值问题。

## 优先级定义

### P0：必须立即关注

至少满足一项：

- 正常知识库、云盘、Agent、工作流、管理后台或公开访问路径必然崩溃，或服务端 / Electron 启动失败。
- 用户内容、知识库文件/wiki/manifest、云盘文件、分享、发布、工作流定义、运行历史、配置或权限数据丢失、覆盖、损坏或无法恢复。
- token、secret、Authorization、Cookie、provider key、share password、shareId、publicationId、知识库内容、云盘文件内容、Agent 输入输出等敏感信息泄露。
- 管理权限绕过、团队隔离失效、项目隔离失效、知识库路径越权、云盘越权访问、分享/发布越权访问、Agent/Workflow 敏感执行缺少权限检查。
- Windows 正常安装/启动/核心用户路径必然不可用，且产品宣称或配置中存在 Windows 目标。
- 核心功能完全不可用，且没有可行恢复路径。

### P1：核心功能受损

至少满足一项：

- 知识库无法可靠创建、迁移、打开、上传原始资料、维护 manifest、启动 Agent 会话、透传 native slash 或加载内置 runtime。
- 云盘无法可靠上传、下载、压缩下载、预览、重命名、移动、删除、分享、取消分享、发布 page/site 或公开访问。
- 用户能触发的入口实际无效、只改前端状态、成功提示虚假、刷新后回退或后端没有对应实现。
- API / IPC / capability / MCP / renderer type / schema / template 文档不一致，导致 Agent 或用户操作按错误 contract 执行。
- 失败后用户无法自助恢复，且日志不足以定位。
- 并发、取消、重复提交、切换团队/项目/知识库、多窗口、断网、运行取消导致核心状态卡死。
- 性能问题会让正常规模数据的用户路径卡死、超时、内存持续增长或阻塞主进程。
- Windows 路径、shell、环境、asar、二进制或打包差异会破坏常用安装/启动/核心工作流。
- 内置 skill 或 MCP 指南教 Agent 使用错误工具、错误字段或错误顺序，导致能力不可用。

### P2：体验、状态可信度和复盘问题

至少满足一项：

- 用户可以继续，但状态不可信、错误提示不可操作、空态/禁用态/loading 缺失或误导。
- 重复点击、并发操作、切换页面、关闭窗口、断网恢复造成错误体验。
- 云盘或知识库操作完成后列表、详情、历史、公开访问或 Agent 结果展示不一致。
- 性能问题不会完全阻断，但会随文件数、source 数、运行记录数、日志数或目录深度增长明显恶化。
- Windows 上有常见环境风险，例如用户目录含空格/中文、保留文件名、大小写冲突、文件锁、`.cmd` shim、`Path`/`PATH` 差异。
- 关键操作缺少复盘所需日志、审计或运行记录。
- UI 违反仓库 token/组件/文案纪律，并且影响用户理解或操作。
- 重复实现已经出现局部 contract 不一致，但尚未证明核心路径必然失败。

### P3：维护质量问题

只允许提交：

- 本轮范围内明确无引用的死代码、废弃文件、废弃 export。
- 本轮范围内重复定义且后续维护容易误改，且能证明已经有不一致风险。
- 违反仓库硬约束但当前未必触发用户问题。
- 明显废弃路径残留，且有代码证据表明已被新路径替代。
- 应抽成共享 helper/service/schema 的逻辑分散在 3 处以上，并涉及权限、路径、脱敏、状态机、MCP schema、文件名清洗、Windows 兼容或持久化安全。

禁止把以下内容单独作为 P3 Issue：

- 仅缺测试。
- 仅可以重构。
- 仅组件太大。
- 仅命名不优雅。
- 仅类型可以更严格。
- 仅日志格式可以更漂亮。

## 问题类型

使用以下 `type`：

- `crash`：崩溃、未捕获异常、必现运行失败。
- `dataLoss`：数据丢失、覆盖、持久化损坏、恢复失败。
- `security`：敏感信息泄露、权限绕过、缺少鉴权或审计。
- `errorHandling`：错误吞掉、错误提示缺失、错误状态不可信。
- `interaction`：交互链路、按钮状态、并发操作、状态同步问题。
- `uiQuality`：违反 UI token、shadcn、主题、文案、可访问性规则。
- `performance`：无界扫描、N+1、重复 IO、渲染阻塞、主进程阻塞、资源泄漏。
- `windowsCompat`：Windows 路径、shell、环境变量、打包、asar、安装、更新或文件系统问题。
- `alignment`：MCP、capability、内置 skill/rule/prompt、Agent guide、API reference 与产品能力不一致。
- `robustness`：原子性、取消、重试、资源释放、输入校验、状态机健壮性缺口。
- `deadCode`：死代码、废弃路径、重复定义。
- `architecture`：违反硬约束、跨层边界、错误依赖方向、应抽象但分散导致风险。

如果 GitHub 没有对应 `类型:*` 标签：

- `performance` 优先映射到 `类型:架构` 或 `类型:交互`，并在 body 写明 `type=performance`。
- `windowsCompat` 优先映射到 `类型:架构` 或 `类型:错误处理`，并在 body 写明 `type=windowsCompat`。
- `alignment` 优先映射到 `类型:架构`，并在 body 写明 `type=alignment`。
- `robustness` 优先映射到 `类型:错误处理` 或 `类型:架构`，并在 body 写明 `type=robustness`。

## 扫描模式

每轮必须先选择一个扫描模式，再选择方向和目录。不要只说“扫描知识库”。

### 模式 1：用户旅程与意外表现模式

从真实用户操作出发，倒推代码链路。

候选旅程：

- 用户进入知识库，创建、上传原始资料、启动 Agent、输入 `/wiki-ingest` 或 `/save`。
- 用户在云盘上传文件夹，重命名、移动、分享、取消分享，再刷新公开链接。
- 用户快速重复点击保存、运行、删除、取消、重试或切换项目/团队/知识库。
- 用户在多窗口中编辑同一对象，或在一个窗口删除另一个窗口正在使用的对象。
- 用户看到成功 toast 后刷新页面、重开应用或从另一个入口查看真实结果。

适合发现 P0/P1/P2。

### 模式 2：边界输入与并发模式

主动寻找正常用户可能触发的边界：

- 空字符串、空 ID、无效 ID、已删除 ID、重复 ID。
- 文件名非法、路径穿越、大小写冲突、尾随空格/点、空文件夹、大文件、大目录。
- 跨团队资源、跨项目资源、禁用用户、缺失/过期 token。
- 运行中取消、运行中删除、重复运行、重复上传、重复发布、重复迁移。
- 网络失败、权限拒绝、timeout、存储不可访问、日志写入失败。
- Windows 用户目录含空格、中文、OneDrive、非管理员安装、文件锁。

适合发现 P0/P1/P2。

### 模式 3：契约一致性模式

检查链路：

```text
route / IPC channel / preload API / capability tool / MCP tool / schema / service method
→ result contract
→ renderer type / Agent guide / built-in skill
→ page or Agent usage
→ state update
→ log record
```

重点：

- 前端调用不存在的路由、IPC 或 channel。
- 返回字段和前端类型不一致。
- MCP schema 和 dispatcher 行为不一致。
- 内置 skill 示例使用已删除字段或错误默认值。
- 页面刷新依赖的字段在响应里不存在。
- 日志记录的 userId、teamId、projectId、knowledgeBaseId、workflowId、driveItemId、shareId、toolUseId 无法和用户行为关联。

适合方向 B/C/D/E/G/I/J。

### 模式 4：持久化与恢复模式

检查：

- Prisma schema / migration 与服务逻辑不一致。
- DataRepository 写入失败、部分写入、覆盖或迁移不兼容。
- 知识库 manifest、raw files、wiki、地址索引、runtime 资产不一致。
- 云盘 item、upload session、storage object、share、publication、public URL 状态不一致。
- Workflow/Agent run snapshot、history、tool result、transcript 不一致。
- 审计日志、运行日志写入失败后业务状态不可信。
- 错误重试或恢复路径缺失。

适合方向 B/D/E/J。

### 模式 5：性能与资源模式

检查：

- 无分页、无上限、无取消的大列表、大目录、大日志、大历史。
- 递归扫描、同步 IO、重复 hash/parse、N+1 查询。
- renderer 里每次 render 都进行大计算。
- 事件订阅、watcher、interval、child process、file handle 泄漏。
- 状态更新造成循环请求、事件风暴或重复广播。
- 大文件上传/下载/预览缺少流式处理或大小 guard。

适合方向 D/F/J/K。

### 模式 6：重复实现与抽象缺口模式

检查：

- 同一逻辑 5+ 行出现 3+ 次。
- 重复处涉及路径安全、文件名清洗、权限、脱敏、状态转换、schema、MCP tool、日志、Windows 兼容或持久化。
- 至少一处已经和其他处不一致，或新增能力明显只改了一处。
- 可以明确指出应该抽成哪个共享 helper/service/schema/domain。

适合方向 H/I/J/K。

### 模式 7：内置能力对齐模式

检查：

- 产品能力代码与 MCP domain/tool/dispatcher 是否一致。
- `*_type_list` / `*_type_describe` 或动态 discovery 是否包含新增类型。
- 内置 skill/rule/prompt 模板是否仍教 Agent 使用正确工具、字段、默认值和调用顺序。
- Agent guide/API reference 是否描述当前行为。
- 相关测试是否覆盖 Agent-facing discovery contract。
- 用户可感知的 MCP/内置能力行为变化是否记录在 `RELEASE_NOTES_PENDING.md`。

适合方向 I。

### 模式 8：Windows 源码兼容模式

优先搜索：

```sh
rg -n "process\\.platform|os\\.platform|win32|darwin|linux|path\\.|/bin/sh|bash|sh -c|powershell|cmd\\.exe|child_process|spawn\\(|exec\\(|execSync\\(|execFile\\(|shell|sudo|chmod|ps |grep|awk|xargs|pgrep|kill|electron-builder|asarUnpack|extraResources|app\\.getAppPath|process\\.resourcesPath|__dirname|startsWith\\(|toLowerCase\\("
rg -n "/Users|~/|Library/Application Support|/Applications|/tmp|/bin/|/usr/bin|osascript|open |pbcopy|pbpaste|xattr|plutil|launchctl"
rg -n "\\.node|node-gyp|better-sqlite3|sharp|keytar|serialport|claude-agent-sdk|codex|git"
```

重点要求：

- Windows 不应通过泛用 `else` 继承 macOS/Linux 行为，除非确实平台无关。
- 路径 containment 使用 `path.relative` 语义，不使用字符串前缀。
- Shell 执行区分 `cmd`、PowerShell、POSIX；用户命令和参数不拼接进 shell 字符串。
- Windows 外部工具发现支持 `.cmd`、`.exe`、`.bat`、`Path`/`PATH` 和 `PATHEXT`。
- app 安装目录和 `app.asar` 按只读处理。

适合方向 K。

### 模式 9：UI 状态与体验模式

如果扫描 UI，重点检查源码可证明的问题：

- 硬编码颜色或不走 token。
- 自定义按钮、卡片、弹窗等替代已有 shadcn 组件。
- 卡片套卡片、连续 Divider、shadow + border + background 同时堆层级。
- loading / error / empty / disabled 状态缺失。
- 表单 label/input、表格数字、icon/text 对齐明显违反仓库规则。
- 文案包含功能介绍、实现解释、重复状态、欢迎横幅、AI 自称或装饰性 emoji。
- 成功/失败/空态文案会误导用户对知识库、云盘、权限、分享、发布或运行状态的理解。

禁止仅凭“看起来不好看”提交 UI Issue。

### 模式 10：权限、安全与审计模式

检查敏感操作：

- 管理 API 是否都走 admin guard。
- 用户 API 是否限制到当前用户和当前团队。
- 团队、项目、知识库、云盘资源是否可被其他主体读取或修改。
- Agent/Workflow/Knowledge Base 是否能绕过 permission/audit、项目边界或敏感路径限制。
- 云盘文件、分享、发布、下载、预览、zip 是否可越权访问或泄露。
- token、cookie、Authorization、provider key、share password、side-channel token、data-server token 是否脱敏。
- 敏感操作是否有审计或结构化日志。

适合发现 P0/P1/security/logging/architecture。

### 模式 11：历史低覆盖挖掘模式

从覆盖地图里选择低命中文件或长期未审计功能，往前看历史原因。

候选：

- 旧兼容代码仍被新入口调用。
- 新能力迁移后旧入口残留并造成无效操作。
- 老 helper 的语义和新模块硬边界冲突。
- 旧文档/内置 skill/API reference 未随产品能力变化。
- 旧 Windows/macOS 分支在新打包方式下不成立。

适合方向 L。

## 问题发现标准

每个问题必须有完整证据链：

```text

```

合格条件：

- 能在代码中证明问题存在，不需要运行 App、dev server、浏览器或 Playwright。
- 影响本轮重点范围中的正常路径，或是合理高概率边界。
- 至少串起 3 层相关文件；单文件局部猜测默认不合格。
- 用 `rg` 确认过影响范围。
- 涉及历史或最近提交时，用 `git log` / `git show` / `git blame` 确认过最终落下的代码。
- 涉及 UI 时，确认过项目组件库和 token 规则，不把主观审美当 Issue。
- 涉及 Windows 时，能说明 Windows 差异和当前用户路径的关系。
- 涉及性能时，能说明复杂度、无界增长或重复资源消耗来自哪里。
- 涉及重复实现时，能说明至少 3 处重复和具体不一致风险。
- 涉及内置能力对齐时，能指出产品/MCP/skill/guide/test 哪些面不一致。
- 用 `NOT.md` 确认过不属于刻意设计。
- 用 `AGENTS.md` 确认过不违反当前仓库硬规则和模块边界判断。
- 能解释为什么不属于已有 Issue 或同根因。
- 后续修复 Agent 能根据 Issue 直接开工。

不合格条件：

- 需要运行 App、dev server、浏览器或 Playwright 才能确认。
- 只是“感觉不太好”但逻辑没错。
- 仅缺测试覆盖。
- 仅缺日志，且没有用户可见失败、审计风险、安全风险或复盘阻断。
- 只是代码风格偏好。
- 命中 `NOT.md` 中明确说明应保留的刻意设计。
- 与已有 Issue 同根因。
- 证据链只有单个文件局部猜测，没有入口和结果。
- 性能、Windows、抽象、对齐问题没有证明当前用户或 Agent 能触发。

## 去重规则

提交 Issue 前必须做三层去重，并做一层防误判过滤。

### 1. 本地索引去重

- 读全量 `/Users/liyang/Desktop/temp/issues.jsonl`。
- 如果已有相同 `fingerprint`，跳过。
- 如果旧记录没有 `fingerprint`，用 `file + symbol + summary` 近似判断。
- 如果同一文件已有大量相似 summary，默认跳过，除非是 P0/P1。

### 2. GitHub Issue 去重

使用 GitHub CLI 查询足够范围：

```sh
gh issue list -R FairyEver/Synapse --state all --limit 500 --json number,title,url,state,labels
```

对比：

- 标题中的 priority/type/summary。
- body 中的 `Local fingerprint`。
- 同一文件、同一 symbol、同一用户结果。
- 同一根因的不同表现。

如果 GitHub 已有同问题，无论 open/closed 都跳过。

### 3. 同根因去重

如果新发现和已有 Issue 共享同一上游根因，只能提交更上游、更准确的一条；不要为每个下游表现拆多个 Issue。

示例：

- 同一个知识库 backing directory 解析错误导致 raw manager、Agent 会话和 manifest 写入都落错目录。提交一个路径解析根因 Issue。

- 同一个 MCP schema 漂移导致 Agent skill、dispatcher 和 UI 示例都错误。提交一个能力对齐根因 Issue。
- 同一个 Windows 文件名 sanitizer 缺失导致知识库 raw、云盘上传和导出都可能写入非法路径。提交一个共享路径/文件名根因 Issue。
- 同一个日志脱敏函数漏处理 Bearer token，不要按每个调用点拆多个 Issue。

### 4. 防误判过滤

- 读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 的当前内容，而不是依赖记忆。
- 读 `/Users/liyang/Documents/code/github/Synapse/AGENTS.md` 的当前内容，而不是依赖记忆。

```text
10. 阅读 3-10 个相关文件，理解入口、服务、持久化、日志、文档/内置模板和数据流。
11. 构建用户触发链路和代码证据链。
12. 对候选问题用 rg 确认影响范围。
13. 对历史或最近提交候选用 git log / git show / git blame 确认最终落下的代码。
14. 检查关键用户操作的日志、审计、运行记录和脱敏上下文是否足够。
15. 如涉及 Windows、性能、抽象或对齐，补足该方向的专门证据。
16. 按 P0/P1/P2/P3 门槛分级。
17. 生成 fingerprint = "<file>|<symbol>|<summary>"。
18. 做本地索引去重、GitHub 去重、同根因去重。
19. 对照 NOT.md 做防误判过滤，对照 AGENTS.md 做规则边界过滤。
20. 通过 Issue 创建质量闸门。
21. 用 gh issue create -R FairyEver/Synapse 创建详细 Issue，并同时添加 `bug`、`优先级:*`、`类型:*`、`模块:*` 标签。
22. Issue 创建成功后，把 URL 和轻量索引 append 到桌面 JSONL。
23. 默认每轮最多创建 3 条 Issue；多个 P0 可突破，但必须说明原因。
24. 输出历史/覆盖决策、已提交 Issue、跳过重复、拒绝候选、日志/脱敏/性能/Windows/对齐结论和下一轮建议。
```

## 推荐创建命令形态

优先用临时 body 文件提交 Issue，避免 shell 引号破坏 Markdown：

```sh
gh issue create -R FairyEver/Synapse \
  --title "[P1][windowsCompat] 知识库路径比较在 Windows 大小写差异下会误判越界" \
  --body-file /tmp/synapse-issue-body-<agentId>-<random>.md \
  --label "bug" \
  --label "优先级:P1" \
  --label "类型:架构" \
  --label "模块:Electron"
```

临时 body 文件只能放在 `/tmp`，不要写入仓库。创建完成后无需保留。

不要把长 Markdown body 放进 shell 变量、命令替换或一条超长命令里。
