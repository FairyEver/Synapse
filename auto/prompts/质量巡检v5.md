## 核心规则

1. **只读源码**：不得修改项目中的任何源代码文件。不得 `git add` / `git commit` / `git push`。
2. **最终记录到 GitHub**：有效发现提交到 `FairyEver/Synapse` 的 GitHub Issue，并同时使用 `bug`、`优先级:*`、`类型:*`、`模块:*` 标签。
3. **本地轻量索引**：Issue 创建成功后，向 `/Users/liyang/Desktop/temp/issues.jsonl` 追加一条轻量 JSON，用于后续 Agent 快速去重；不要把完整证据链只写在 JSONL 里。
4. **证据优先**：每个问题必须有代码级证据链，不能凭感觉、审美偏好或泛泛经验提交。
5. **后台完整性优先**：优先检查管理后台的端到端闭环，而不是只看单个函数或单个页面。
6. **最近变更优先**：优先检查最近 7 天内变更过的 `server/` 模块，以及当前工作区未提交的 `server/` 变更。
7. **防误判优先**：提交前必须阅读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 当前内容，确认候选问题不是仓库明确保留的产品或工程设计。
8. **不重复**：提交前必须查本地轻量索引和 GitHub Issue，跳过已记录、同根因或同用户结果的问题。
9. **Issue 上下文要详细**：GitHub Issue 必须包含足够上下文，让修复 Agent 不需要重新猜测问题来源。

## 后台管理完整性定义

本轮“完整性”不是泛泛要求功能更多，而是检查一个后台功能是否形成可靠闭环。

每个候选链路至少从以下层级中选择 3 层以上连起来看：

```text
Prisma schema / migration
→ Nest module / controller / service / guard
→ auth、team、权限、审计、分页、错误处理
→ API response contract
→ server/admin/src/lib/api.ts
→ admin route / sidebar / page
→ 表格、表单、操作按钮、loading、error、empty、disabled 状态
→ 测试或既有调用点
```

重点检查：

- 后端已提供能力但管理界面没有入口或没有可完成路径。
- 管理界面调用了 API client，但服务端路由、参数、返回结构或错误语义不匹配。
- 服务端创建、更新、删除、邀请、切换团队、备份、日志等操作缺少必要鉴权或团队隔离。
- 管理端页面存在入口但关键操作没有 loading / error / empty / disabled 状态，导致用户误以为成功或无法恢复。
- 列表分页、筛选、导出、详情、刷新和操作后状态同步不完整。
- 邀请链接、注册、登录、团队切换、成员权限这类跨页面链路断裂。
- 审计日志应该记录的管理操作没有记录，或记录内容无法支持追溯。
- 错误响应在服务端被吞掉、被泛化到无法定位，或管理端展示成误导性成功。

禁止把以下内容单独作为完整性 Issue：

- 只是缺少一个“更方便”的快捷入口。
- 只是测试可以更多。
- 只是页面信息密度、布局或文案可以优化。
- 只是某个私有实现看起来不够优雅。
- 只是生成物 `dist` 或 `admin-dist` 没同步源码。

## 分层问题预算

每个 worker 每轮默认最多创建 3 个 Issue；只有多个 P0 同时出现时可以突破。

预算规则：

```text
P0: 优先提交；多个 P0 可突破总数上限，但必须在最终输出说明
P1: 每轮最多 2 条
P2: 每轮最多 2 条
P3: 每轮最多 1 条，且必须高确定、可清理、不会引入产品争议
总数: 默认每轮最多 3 条；只有多个 P0 时可以超过
```

额外限制：

- 同一文件最多创建 1 条 Issue。
- 同一后台功能链路最多创建 1 条 Issue。
- 同一根因最多创建 1 条 Issue。
- 如果只有弱 P2/P3，宁可不创建 Issue，只在最终输出中写调查摘要。
- 不要为了凑数量提交低价值问题。

## 优先级定义

### P0：必须立即关注

至少满足一项：

- 正常管理路径必然崩溃或服务端启动失败。
- 用户、团队、邀请、备份、日志、激活码、账号等后台数据丢失、覆盖、损坏或无法恢复。
- token、secret、邀请链接、备份路径、本地绝对路径、用户内容等敏感信息泄露。
- 管理权限绕过、团队隔离失效，或敏感操作缺少鉴权。
- 核心后台功能完全不可用。
- 持久化数据损坏后导致后台整体不可用。

### P1：核心功能受损

至少满足一项：

- 管理员或用户无法完成主要后台流程。
- 失败后用户无法自助恢复。
- 登录、注册邀请、团队、账号、设备、备份、日志、系统状态等核心后台能力产生错误结果。
- 服务端和管理端 API contract 不一致，导致功能误判。
- 错误被吞掉，用户以为成功但实际失败。
- 并发、删除、重命名、重复提交、过期邀请、切换团队等正常边界导致核心状态卡死。

### P2：体验和状态可信度问题

至少满足一项：

- 用户可以继续，但管理端状态、反馈、按钮、列表、历史记录不可信。
- 重复点击、并发操作、切换团队或切换页面会造成错误体验。
- 错误提示不可操作、误导用户或暴露不该展示的信息。
- loading / error / empty / disabled 状态缺失，影响当前操作判断。
- UI 文案、空态、禁用态让用户误解当前后台功能。
- 深浅主题、token、组件使用问题造成可读性、一致性或可操作性缺陷。

### P3：维护质量问题

只允许提交：

- 明确无引用的死代码、废弃文件、废弃 export。
- 重复定义且后续维护容易误改。
- 违反仓库硬约束但当前未必触发用户问题。
- 明显废弃路径残留，且有代码证据表明已被新路径替代。
- 服务端和管理端存在明确重复的 contract 常量或状态定义，且已经出现不一致风险。

禁止把以下内容单独作为 P3 Issue：

- 仅缺少测试。
- 仅可以重构。
- 仅组件太大。
- 仅命名不优雅。
- 仅类型可以更严格。
- 仅看起来不够好。

除非它们已经造成具体用户路径问题，否则不要提交。

## 问题类型

使用以下 `type`：

- `crash`：崩溃、未捕获异常、必现运行失败。
- `dataLoss`：数据丢失、覆盖、持久化损坏、恢复失败。
- `security`：敏感信息泄露、权限绕过、缺少鉴权或审计。
- `errorHandling`：错误吞掉、错误提示缺失、错误状态不可信。
- `interaction`：交互链路、按钮状态、并发操作、状态同步问题。
- `uiQuality`：违反 UI token、shadcn、主题、文案、可访问性规则。
- `deadCode`：死代码、废弃路径、重复定义。
- `architecture`：违反硬约束、跨层边界、错误依赖方向。

## 扫描模式

每轮必须先选择一个扫描模式，再选择方向和目录。不要只说“扫描方向 A”。

### 模式 1：后台用户旅程模式

从真实管理员或用户操作出发，倒推代码链路。

候选旅程：

- 管理员登录后查看系统状态。
- 创建邀请、复制邀请链接、用户通过邀请注册。
- 用户登录后查看或切换团队。
- 管理员查看用户、账号、设备、激活码、审计日志。
- 管理员创建、下载、删除备份。
- 管理员在列表中筛选、分页、刷新、执行行操作。

适合发现 P1/P2。

### 模式 2：边界输入模式

主动寻找正常用户可能触发的边界：

- 空数组、空字符串、空 ID。
- 无效 ID、已删除 ID、重复 ID。
- 过期邀请、已使用邀请、跨团队资源。
- 缺失 token、过期 token、普通用户访问管理员 API。
- 损坏 JSON、文件不存在、目录被删除。
- 网络失败、权限拒绝、timeout。
- 重复点击、并发请求、快速切换团队或页面。

适合发现 P0/P1/P2。

### 模式 3：契约一致性模式

检查链路：

```text
controller route → service result → api client type → page usage → state update
```

重点：

- 管理端调用不存在的路由。
- 服务端返回字段和前端类型不一致。
- 前端认为成功但服务端只返回部分结果。
- 服务端错误码和前端错误处理不匹配。
- 页面刷新依赖的字段在响应里不存在。
- 删除、创建、邀请、备份后列表状态不同步。

适合方向 A/B/C/D。

### 模式 4：持久化与恢复模式

检查：

- Prisma schema / migration 与服务逻辑不一致。
- 写入失败。
- 迁移后旧数据不兼容。
- 并发写入。
- 文件路径越权。
- 备份生成、下载、清理失败。
- 审计日志写入失败后业务状态不可信。
- 错误重试或恢复路径缺失。

适合服务端、备份、审计、邀请、团队。

### 模式 5：权限与安全模式

检查敏感操作：

- 管理 API 是否都走 admin guard。
- 用户 API 是否限制到当前用户和当前团队。
- 团队资源是否可被其他团队读取或修改。
- 邀请链接是否泄漏不该展示的信息。
- 日志、备份、系统信息是否暴露敏感字段。
- token、cookie、Authorization 处理是否一致。
- CSV / 文件下载是否有路径或权限风险。

适合发现 P0/P1/security/architecture。

### 模式 6：管理端 UI 状态完整性模式

如果扫描 `server/admin` UI，重点检查源码可证明的问题：

- 硬编码颜色或不走 token。
- 自定义按钮、卡片、弹窗等替代已有 shadcn 组件。
- 深浅主题下类名明显不可适配。
- loading / error / empty / disabled 状态缺失。
- 用户文案包含实现说明、开发阶段说明、架构解释。
- 表格数字、状态、操作按钮、表单 label/input 对齐或可访问性明显缺陷。
- 交互元素缺少可达的 disabled/focus/keyboard 路径。

禁止仅凭“看起来不好看”提交 UI Issue。

## 问题发现标准

每个问题必须有完整证据链：

```text
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口
```

合格条件：

- 能在代码中证明问题存在，不需要运行 App 或启动服务。
- 影响正常后台管理路径，或是合理高概率边界。
- 至少串起服务端或管理端中的多个相关文件；单文件局部猜测默认不合格。
- 用 `rg` 确认过影响范围。
- 用 `NOT.md` 确认过不属于刻意设计。
- 能解释为什么不属于已有 Issue 或同根因。
- 后续修复 Agent 能根据 Issue 直接开工。

不合格条件：

- 需要运行 App、dev server、浏览器或 Playwright 才能确认。
- 只是“感觉不太好”但逻辑没错。
- 仅缺测试覆盖。
- 仅缺日志，且没有用户可见失败或复盘阻断。
- 只是代码风格偏好。
- 命中 `NOT.md` 中明确说明应保留的刻意设计。
- 与已有 Issue 同根因。
- 证据链只有单个文件局部猜测，没有入口和结果。

## Issue 创建质量闸门

创建 Issue 前必须回答 10 个问题：

```text
1. 用户从哪里触发？
2. 代码链路是什么？
3. 当前错误结果是什么？
4. 为什么这是正常后台路径或合理边界，而不是极端猜测？
5. 是否查过最近 7 天 server 变更地图？
6. 是否查过 NOT.md，确认不是刻意设计？
7. 是否查过本地索引？
8. 是否查过 GitHub 已有 Issue？
9. 是否和已有 Issue 同根因？
10. 后续修复 Agent 能否按这个 Issue 直接开工？
```

任一答不出来：

- 不创建 Issue。
- 在最终输出列为 `rejected candidate`。

## GitHub Issue 格式

每个有效发现创建一个 GitHub Issue。

每个 Issue 必须至少打 4 个分类标签：

```text
bug
优先级:<P0|P1|P2|P3>
类型:<崩溃|数据丢失|安全|错误处理|交互|UI质量|死代码|架构>
模块:<工作流|Agent|调度器|数据库|设置|内容|应用壳|Electron|UI|基础设施|Server|管理后台|MCP>
```

**不要打任何 `状态:*` 或无前缀状态标签。** 巡检 Agent 只负责分类标签；Issue 创建后没有状态标签即为「待确认」隐含状态，后续由修复 Agent 认领时添加状态标签。

标签必须使用仓库现有标签。v5 可用的模块标签包括：

```text
模块:<工作流|Agent|调度器|数据库|设置|内容|应用壳|Electron|UI|基础设施|Server|管理后台|MCP>
```

后台管理 Issue 的模块标签选择：

- `server/src/**`、`server/prisma/**`、`server/scripts/**`、Nest module、controller、service、guard、DTO、Prisma 迁移、后端配置、Docker/compose、server runtime：优先 `模块:Server`。
- `server/admin/src/**`、管理面板页面、表格、表单、导航、shadcn、文案、可访问性、管理端 API client、Vite 构建：优先 `模块:管理后台`。
- MCP server、MCP tool 注册、MCP 调用链路、MCP 权限、MCP provider/connector 接入和 MCP 配置生效问题：优先 `模块:MCP`。
- 数据库桌面模块、Data Store 表/字段/行、非 server 的数据库 MCP/CLI 数据语义问题：优先 `模块:数据库`。
- 设置页面自身的 provider、repository、connector 表单或配置 UI 问题：优先 `模块:设置`；如果根因是 MCP 工具注册或调用失败，改用 `模块:MCP`。
- 跨模块 UI、通用 shadcn 组件、全局主题、全局文案或跨页面可访问性问题：优先 `模块:UI`；不要因为 `server/admin` 是前端就默认打 `模块:UI`。
- 构建脚本、runtime 基础设施、bootstrap、硬约束等不属于 `server/` 后端服务本身的问题：优先 `模块:基础设施`。
- 如果问题本质是桌面端模块能力影响后台能力，按最直接根因选择对应桌面模块标签。

Issue body 的 `Priority` 或 `Scope` 必须明确写出后台范围，例如 `Direction: server-api`、`Direction: server-admin-ui`、`Scope: server/src/teams + server/admin/src/pages/user-team-page.tsx`。

## 去重规则

提交 Issue 前必须做三层去重，并做一层防误判过滤。

### 1. 本地索引去重

- 读全量 `/Users/liyang/Desktop/temp/issues.jsonl`。
- 如果已有相同 `fingerprint`，跳过。
- 如果旧记录没有 `fingerprint`，用 `file + symbol + summary` 近似判断。
- 如果同一文件已有大量相似 summary，默认跳过，除非是 P0/P1。

### 2. GitHub Issue 去重

使用 GitHub CLI 查询足够范围：

```sh
gh issue list -R FairyEver/Synapse --state all --limit 500 --json number,title,url,state,labels
```

对比：

- 标题中的 priority/type/summary。
- body 中的 `Local fingerprint`。
- 同一文件、同一 symbol、同一后台用户结果。
- 同一根因的不同表现。

必要时查看候选 Issue：

```sh
gh issue view -R FairyEver/Synapse <number> --json title,body,url,state
```

如果 GitHub 已有同问题，无论 open/closed 都跳过。

### 3. 同根因去重

如果新发现和已有 Issue 共享同一上游根因，只能提交更上游、更准确的一条；不要为每个下游表现拆多个 Issue。

示例：

- 同一个 team guard 漏校验导致用户列表、团队页、邀请页三个地方越权。应提交一个权限根因 Issue，而不是三个页面 Issue。
- 同一个 API response 字段名漂移导致多个管理页状态错误。应提交一个契约漂移 Issue。
- 同一个错误脱敏函数漏处理 Bearer token，不要按每个调用点拆多个 Issue。

并行 Agent 仍可能在极短时间内同时提交同一问题。提交前最后再查一次 GitHub Issue；如果发现刚刚已有同标题、同 fingerprint 或同根因，跳过创建。

### 4. 防误判过滤

- 读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 的当前内容，而不是依赖记忆。
- 如果候选问题命中 `NOT.md` 明确保留的行为，跳过。
- 如果候选问题只是在刻意设计的实现附近，但根因和影响不属于 `NOT.md` 说明范围，可以继续提交。
- 如果需要提交附近问题，Issue body 必须说明 `NOT.md` 已检查，且本问题不是该文件列出的保留行为。
