## 本轮完整性定义

本轮“完整性”不是泛泛要求功能更多，而是检查一个功能链路是否可用、可追踪、可恢复。

每个候选链路至少从以下层级中选择 3 层以上连起来看：

```text
用户入口 / 导航 / 按钮 / 命令
→ renderer 组件 / hook / API client
→ preload window.synapse API / IPC module / capability
→ Electron service / Server controller / service / guard
→ 数据仓库 / Prisma / 文件系统 / 工作流定义 / 知识库 manifest
→ 运行结果 / 状态刷新 / 错误反馈 / disabled/loading/empty
→ 操作日志 / 审计日志 / 运行日志 / 错误日志
→ 测试或既有调用点
```

重点检查：

- 后端、主进程或服务已提供能力，但界面没有入口或没有可完成路径。
- 界面调用了 API，但服务端路由、IPC、参数、返回结构或错误语义不匹配。
- 工作流保存、导入、运行、重跑、调度、历史或报告链路断裂。
- 知识库创建、托管路径解析、source 导入、暂存、manifest、Agent 会话、内置资源加载链路断裂。
- 管理后台的团队、邀请、权限、审计、备份、日志、系统状态链路不能完成或完成后状态不可信。
- 新功能缺少必要日志，导致失败后无法知道用户做了什么、系统做了什么、哪一步失败。
- 最近一周提交只完成了某一层，遗漏了入口、权限、状态、日志、错误处理或测试。
- 错误被吞掉、被泛化到无法定位，或 UI 展示成误导性成功。

禁止把以下内容单独作为完整性 Issue：

- 只是缺少一个“更方便”的快捷入口。
- 只是测试可以更多。
- 只是页面信息密度、布局或文案可以优化。
- 只是某个私有实现看起来不够优雅。
- 只是生成物没同步源码。
- 只是缺日志，但该功能没有用户操作、敏感状态、运行失败或复盘需求。

## 分层问题预算

每个 worker 每轮默认最多创建 3 个 Issue；只有多个 P0 同时出现时可以突破。

预算规则：

```text
P0: 优先提交；多个 P0 可突破总数上限，但必须在最终输出说明
P1: 每轮最多 2 条
P2: 每轮最多 2 条
P3: 每轮最多 1 条，且必须高确定、可清理、不会引入产品争议
总数: 默认每轮最多 3 条；只有多个 P0 时可以超过
```

额外限制：

- 同一文件最多创建 1 条 Issue。
- 同一功能链路最多创建 1 条 Issue。
- 同一根因最多创建 1 条 Issue。
- 如果只有弱 P2/P3，宁可不创建 Issue，只在最终输出中写调查摘要。
- 不要为了凑数量提交低价值问题。

## 优先级定义

### P0：必须立即关注

至少满足一项：

- 正常管理后台、工作流或知识库路径必然崩溃，或服务端 / Electron 启动失败。
- 用户、团队、邀请、备份、日志、账号、工作流定义、运行历史、知识库文件、manifest 或索引数据丢失、覆盖、损坏或无法恢复。
- token、secret、邀请链接、备份路径、本地绝对路径、用户内容、知识库内容、工作流输入输出等敏感信息泄露。
- 管理权限绕过、团队隔离失效、知识库路径越权、工作流敏感操作缺少权限检查。
- 核心后台、工作流或知识库功能完全不可用。
- 持久化数据损坏后导致相关模块整体不可用。

### P1：核心功能受损

至少满足一项：

- 管理员或用户无法完成主要后台流程。
- 工作流无法可靠保存、运行、重跑、导入导出、查看结果或恢复失败。
- 知识库无法可靠创建、导入、暂存、索引、加载内置资源或启动 Agent 会话。
- 失败后用户无法自助恢复，且日志不足以定位。
- 管理后台、工作流、知识库、主进程或服务端 API contract 不一致，导致功能误判。
- 错误被吞掉，用户以为成功但实际失败。
- 并发、删除、重命名、重复提交、过期邀请、切换团队、切换项目或多窗口导致核心状态卡死。

### P2：体验、状态可信度和复盘问题

至少满足一项：

- 用户可以继续，但状态、反馈、按钮、列表、历史记录或运行报告不可信。
- 重复点击、并发操作、切换团队、切换项目、切换页面或关闭窗口会造成错误体验。
- 错误提示不可操作、误导用户或暴露不该展示的信息。
- loading / error / empty / disabled 状态缺失，影响当前操作判断。
- 新功能缺少关键日志，导致常见失败无法复盘或无法判断是否执行成功。
- UI 文案、空态、禁用态让用户误解当前后台、工作流或知识库功能。
- 深浅主题、token、组件使用问题造成可读性、一致性或可操作性缺陷。

### P3：维护质量问题

只允许提交：

- 明确无引用的死代码、废弃文件、废弃 export。
- 重复定义且后续维护容易误改。
- 违反仓库硬约束但当前未必触发用户问题。
- 明显废弃路径残留，且有代码证据表明已被新路径替代。
- 管理后台、工作流、知识库或日志存在明确重复 contract 常量或状态定义，且已经出现不一致风险。

禁止把以下内容单独作为 P3 Issue：

- 仅缺测试。
- 仅可以重构。
- 仅组件太大。
- 仅命名不优雅。
- 仅类型可以更严格。
- 仅日志格式可以更漂亮。

除非它们已经造成具体用户路径问题，否则不要提交。

## 问题类型

使用以下 `type`：

- `crash`：崩溃、未捕获异常、必现运行失败。
- `dataLoss`：数据丢失、覆盖、持久化损坏、恢复失败。
- `security`：敏感信息泄露、权限绕过、缺少鉴权或审计。
- `errorHandling`：错误吞掉、错误提示缺失、错误状态不可信。
- `interaction`：交互链路、按钮状态、并发操作、状态同步问题。
- `uiQuality`：违反 UI token、shadcn、主题、文案、可访问性规则。
- `logging`：新功能或关键操作缺少必要日志、审计、运行记录或复盘上下文。
- `deadCode`：死代码、废弃路径、重复定义。
- `architecture`：违反硬约束、跨层边界、错误依赖方向。

- 检查最近提交是否只改了实现层，遗漏了 preload、renderer 调用、导航入口、测试、日志或发布说明。
- 检查最近提交是否引入新 contract，但旧调用点仍按旧 contract 使用。
- 检查最近提交是否新增权限、路径、文件写入、Agent spawn、网络访问或 secret 读取，却没有 permission/audit/log 保障。
- 检查最近提交是否完成了计划文档中的一部分，但最终代码落点没有形成可用链路。

### 方向 F：跨模块功能链路

重点链路：

```text
用户入口 → renderer 状态 → window.synapse API → IPC module → Electron service / Server API → 持久化 → 日志 → UI 反馈
```

重点：模块之间 contract 漂移、错误边界断裂、状态刷新遗漏、事件订阅遗漏、窗口生命周期问题、权限检查遗漏、日志无法关联、测试只覆盖单层但真实链路不可用。

## 扫描模式

每轮必须先选择一个扫描模式，再选择方向和目录。不要只说“扫描方向 A”。

### 模式 1：后台用户旅程模式

从真实管理员或用户操作出发，倒推代码链路。

候选旅程：

- 管理员登录后查看系统状态。
- 创建邀请、复制邀请链接、用户通过邀请注册。
- 用户登录后查看或切换团队。
- 管理员查看用户、账号、设备、激活码、审计日志。
- 管理员创建、下载、删除备份。
- 管理员查看服务日志或审计日志。

适合发现 P1/P2。

### 模式 2：工作流旅程模式

从真实工作流操作出发，倒推代码链路。

候选旅程：

- 创建工作流、添加节点、连接节点、保存并重新打开。
- 导入工作流、校验、修复配置、运行。
- 配置运行参数、启动运行、查看节点结果、复制运行报告。
- 调度器触发工作流，工作流调用 Agent/MCP/文件转换节点。
- 运行失败后查看错误、日志、历史，并尝试重跑。

适合发现 P0/P1/P2。

### 模式 3：知识库旅程模式

从真实知识库操作出发，倒推代码链路。

候选旅程：

- 新建托管知识库，确认虚拟路径与 backing directory 关系。
- 添加本地文件、URL、图片或原始文件，进入暂存和导入。
- 生成/更新 manifest、wiki snapshot、地址和切片结果。
- 打开知识库 source manager，查看扫描、冲突、错误和完成状态。
- 从知识库项目启动 Agent 会话，确认内置资源和允许的 hook 生效。

适合发现 P0/P1/P2。

### 模式 4：边界输入模式

主动寻找正常用户可能触发的边界：

- 空数组、空字符串、空 ID。
- 无效 ID、已删除 ID、重复 ID。
- 过期邀请、已使用邀请、跨团队资源。
- 缺失 token、过期 token、普通用户访问管理员 API。
- 损坏 JSON、文件不存在、目录被删除、manifest 部分写入。
- 网络失败、权限拒绝、timeout。
- 重复点击、并发请求、快速切换团队、项目、页面或窗口。
- 工作流节点缺配置、循环出口缺失、断边、无上游数据。
- 知识库导入中断、重复导入、同名文件、OCR/embedding 部分失败。

适合发现 P0/P1/P2。

### 模式 5：契约一致性模式

检查链路：

```text
route / IPC channel / preload API / service method → result contract → renderer type → page usage → state update → log record
```

重点：

- 前端调用不存在的路由或 IPC。
- 返回字段和前端类型不一致。
- 前端认为成功但服务端或主进程只返回部分结果。
- 错误码、错误类型和前端错误处理不匹配。
- 页面刷新依赖的字段在响应里不存在。
- 删除、创建、导入、运行、备份后列表状态不同步。
- 日志记录的对象 ID、run ID、project ID、knowledge base ID 或 team ID 无法和用户行为关联。

适合方向 A/B/C/D/F。

### 模式 6：持久化与恢复模式

检查：

- Prisma schema / migration 与服务逻辑不一致。
- DataRepository 写入失败、部分写入、覆盖或迁移不兼容。
- 工作流定义、运行快照、运行历史、导入导出文件不一致。
- 知识库 manifest、raw files、staging、snapshot、地址索引不一致。
- 并发写入、删除、重命名、重复导入。
- 文件路径越权。
- 备份生成、下载、清理失败。
- 审计日志、运行日志写入失败后业务状态不可信。
- 错误重试或恢复路径缺失。

适合管理后台、工作流、知识库、日志。

### 模式 7：权限、安全与审计模式

检查敏感操作：

- 管理 API 是否都走 admin guard。
- 用户 API 是否限制到当前用户和当前团队。
- 团队资源是否可被其他团队读取或修改。
- 工作流是否能访问不该访问的项目、文件、provider、secret 或外部命令。
- 知识库 backing directory 是否可能越权到用户可见项目或其他知识库。
- 日志、备份、系统信息、工作流输出、知识库内容是否暴露敏感字段。
- token、cookie、Authorization 处理是否一致。
- CSV / 文件下载是否有路径或权限风险。
- 敏感操作是否有审计或结构化日志。

适合发现 P0/P1/security/logging/architecture。

### 模式 8：UI 状态完整性模式

如果扫描 UI，重点检查源码可证明的问题：

- 硬编码颜色或不走 token。
- 自定义按钮、卡片、弹窗等替代已有 shadcn 组件。
- 深浅主题下类名明显不可适配。
- loading / error / empty / disabled 状态缺失。
- 用户文案包含实现说明、开发阶段说明、架构解释。
- 表格数字、状态、操作按钮、表单 label/input 对齐或可访问性明显缺陷。
- 交互元素缺少可达的 disabled/focus/keyboard 路径。

禁止仅凭“看起来不好看”提交 UI Issue。

## 问题发现标准

每个问题必须有完整证据链：

```text
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口 → 用户影响或复盘阻断
```

合格条件：

- 能在代码中证明问题存在，不需要运行 App、dev server、浏览器或 Playwright。
- 影响正常管理后台、工作流、知识库路径，或是合理高概率边界。
- 至少串起 3 层相关文件；单文件局部猜测默认不合格。
- 用 `rg` 确认过影响范围。
- 涉及最近提交时，用 `git log` / `git show` 确认过最终落下的代码。
- 涉及 UI 时，确认过项目组件库和 token 规则，不把主观审美当 Issue。
- 用 `NOT.md` 确认过不属于刻意设计。
- 能解释为什么不属于已有 Issue 或同根因。
- 后续修复 Agent 能根据 Issue 直接开工。

不合格条件：

- 需要运行 App、dev server、浏览器或 Playwright 才能确认。
- 只是“感觉不太好”但逻辑没错。
- 仅缺测试覆盖。
- 仅缺日志，且没有用户可见失败、审计风险或复盘阻断。
- 只是代码风格偏好。
- 命中 `NOT.md` 中明确说明应保留的刻意设计。
- 与已有 Issue 同根因。
- 证据链只有单个文件局部猜测，没有入口和结果。

## Issue 创建质量闸门

创建 Issue 前必须回答 12 个问题：

```text
1. 用户从哪里触发？
2. 代码链路是什么？
3. 当前错误结果或复盘阻断是什么？
4. 为什么这是正常功能路径或合理边界，而不是极端猜测？
5. 是否查过最近 7 天相关变更地图？
6. 是否复盘了最近提交最终落下的代码，而不是只看提交标题？
7. 是否查过 NOT.md，确认不是刻意设计？
8. 是否查过本地索引？
9. 是否查过 GitHub 已有 Issue？
10. 是否和已有 Issue 同根因？
11. 如果涉及新功能，日志/审计/运行记录是否足够支撑复盘？
12. 后续修复 Agent 能否按这个 Issue 直接开工？
```

任一答不出来：

- 不创建 Issue。
- 在最终输出列为 `rejected candidate`。

## GitHub Issue 格式

每个有效发现创建一个 GitHub Issue。

每个 Issue 必须至少打 4 个分类标签：

```text
bug
优先级:<P0|P1|P2|P3>
类型:<崩溃|数据丢失|安全|错误处理|交互|UI质量|日志|死代码|架构>
模块:<工作流|Agent|调度器|数据库|设置|内容|应用壳|Electron|UI|基础设施|Server|管理后台|MCP>
```

**不要打任何 `状态:*` 或无前缀状态标签。** 巡检 Agent 只负责分类标签；Issue 创建后没有状态标签即为「待确认」隐含状态，后续由修复 Agent 认领时添加状态标签。

标签必须使用仓库现有标签。如果仓库没有 `类型:日志`，日志补全类问题改用最贴近的 `类型:错误处理`、`类型:交互`、`类型:安全` 或 `类型:架构`，并在 Issue body 的 `Type rationale` 写明 `type=logging` 的原始判断。

模块标签选择：

- `dashboard/src/**` 管理后台页面、路由、API client、表格、表单、导航、shadcn、文案、可访问性、Vite 构建：优先 `模块:管理后台`。
- `server/src/**`、`server/prisma/**`、Nest module、controller、service、guard、DTO、Prisma 迁移、后端配置、Docker/compose、server runtime：优先 `模块:Server`。
- `desktop/src/modules/workflow/**`、`desktop/electron/services/workflow/**`、`desktop/electron/modules/workflow/**`、工作流运行器、编辑器、节点、运行历史、导入导出、MCP 写操作：优先 `模块:工作流`。
- `desktop/src/modules/knowledge-base/**`、`desktop/electron/services/knowledge-base/**`、`desktop/resources/knowledge-base/**`：如果仓库没有 `模块:知识库`，按最直接根因选择 `模块:Agent`、`模块:Electron`、`模块:内容` 或 `模块:基础设施`，并在 Issue body 写明 `Scope: knowledge-base`。
- MCP server、MCP tool 注册、MCP 调用链路、MCP 权限、MCP provider/connector 接入和 MCP 配置生效问题：优先 `模块:MCP`。
- 日志能力本身、日志导出、日志存储、审计日志基础设施：按根因选择 `模块:管理后台`、`模块:Server`、`模块:工作流`、`模块:Electron` 或 `模块:基础设施`。
- 设置页面自身的 provider、repository、connector 表单或配置 UI 问题：优先 `模块:设置`；如果根因是 MCP 工具注册或调用失败，改用 `模块:MCP`。
- 跨模块 UI、通用 shadcn 组件、全局主题、全局文案或跨页面可访问性问题：优先 `模块:UI`。
- 构建脚本、runtime 基础设施、bootstrap、硬约束等不属于具体模块的问题：优先 `模块:基础设施`。

Issue body 的 `Priority` 或 `Scope` 必须明确写出范围，例如 `Direction: workflow-usability`、`Direction: knowledge-base-usability`、`Direction: logging-completeness`、`Scope: dashboard/src/pages/logs-page.tsx + server/src/admin/log-file.controller.ts`。

[P1][logging] 知识库导入失败缺少可关联的 source 记录导致无法复盘

## 去重规则

提交 Issue 前必须做三层去重，并做一层防误判过滤。

### 1. 本地索引去重

- 读全量 `/Users/liyang/Desktop/temp/issues.jsonl`。
- 如果已有相同 `fingerprint`，跳过。
- 如果旧记录没有 `fingerprint`，用 `file + symbol + summary` 近似判断。
- 如果同一文件已有大量相似 summary，默认跳过，除非是 P0/P1。

### 2. GitHub Issue 去重

使用 GitHub CLI 查询足够范围：

```sh
gh issue list -R FairyEver/Synapse --state all --limit 500 --json number,title,url,state,labels
```

对比：

- 标题中的 priority/type/summary。
- body 中的 `Local fingerprint`。
- 同一文件、同一 symbol、同一用户结果。
- 同一根因的不同表现。

必要时查看候选 Issue：

```sh
gh issue view -R FairyEver/Synapse <number> --json title,body,url,state
```

如果 GitHub 已有同问题，无论 open/closed 都跳过。

### 3. 同根因去重

如果新发现和已有 Issue 共享同一上游根因，只能提交更上游、更准确的一条；不要为每个下游表现拆多个 Issue。

示例：

- 同一个 team guard 漏校验导致用户列表、团队页、邀请页三个地方越权。应提交一个权限根因 Issue，而不是三个页面 Issue。
- 同一个工作流 result contract 漂移导致运行报告、历史页和重跑按钮都失败。应提交一个契约漂移 Issue。
- 同一个知识库 managed path 解析错误导致 source manager、Agent 会话和 manifest 写入都落错目录。应提交一个路径解析根因 Issue。
- 同一个日志脱敏函数漏处理 Bearer token，不要按每个调用点拆多个 Issue。

并行 Agent 仍可能在极短时间内同时提交同一问题。提交前最后再查一次 GitHub Issue；如果发现刚刚已有同标题、同 fingerprint 或同根因，跳过创建。

### 4. 防误判过滤

- 读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 的当前内容，而不是依赖记忆。
- 如果候选问题命中 `NOT.md` 明确保留的行为，跳过。
- 如果候选问题只是在刻意设计的实现附近，但根因和影响不属于 `NOT.md` 说明范围，可以继续提交。
- 如果需要提交附近问题，Issue body 必须说明 `NOT.md` 已检查，且本问题不是该文件列出的保留行为。
