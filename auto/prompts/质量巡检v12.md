# Synapse 质量巡检 v12（最近 30 天新能力专项）

你正在对 Synapse 仓库做第十二轮质量巡检。**你只负责发现问题并提交 GitHub Issue，绝不修改任何源代码文件。**

本轮是“最近 30 天代码专项复盘”。**最高优先级是最近 30 天新增或大幅改动的能力是否真的闭环可用**，尤其是 Synapse Skill 独立安装器、密钥工具（secrets system app），以及最近云盘/网盘相关提交里可从源码证明的真实问题。其它模块如果在最近 30 天变更中发现明确问题，也可以顺道提交；但不要偏离本轮重点去泛扫历史旧账。

## 本轮目标

本轮要帮助多个 Codex 会话并行挖出最近 30 天变更中更宽范围、不同根因、可直接修复的问题。不要为了数量提交低价值 Issue；也不要只看提交标题，必须复盘最终落到当前源码里的代码。

重点范围：

- Synapse Skill 独立安装器：系统 App、安装源准备、批量安装、全局/编辑器目标、版本/更新检测、路径展示、状态刷新、IPC/service、独立 skill-package、MCP/Agent 使用指南和测试对齐。
- 密钥工具（secrets）：密钥系统 App、加密存储、迁移、显示/复制/替换、installer substitution、MCP actions、IPC/service、日志脱敏、导出/诊断、权限和 UI 状态可信度。
- 云盘/网盘问题查找：最近 30 天云盘上传任务、文件夹上传、删除快捷入口、公开访问、密码/过期、Drive Browser、同步、版本/评论/编辑和 MCP/skill 指南中可从源码证明的真实问题。
- 最近提交跨能力对齐：App capability package、MCP capability/schema/tool、Workflow node、preload bridge、renderer app manifest、系统 App 注册、release note、内置 Synapse skill-package 是否随产品能力同步。
- 用户体验问题：不是主观审美，而是源码可证明的误导、无效入口、错误提示不可操作、loading/disabled/empty 状态缺失、成功提示虚假、刷新后状态回退、权限/同步/版本状态让用户产生错误预期、文案违反仓库 UI 纪律。
- 性能问题：无界扫描、无分页/无上限、重复 IO、重复解析大文件、渲染中重计算、N+1 API/数据库/文件访问、watcher 泄漏、事件风暴、无取消/去抖/节流导致的卡顿或资源耗尽。
- 隐藏逻辑 bug：contract 漂移、默认值不一致、状态机漏分支、取消/失败/重试顺序错、并发写覆盖、缓存误判、跨团队/跨项目串数据、错误吞掉。
- 重复实现与抽象缺口：同样 5+ 行业务逻辑出现 3+ 次，并且已经或很容易出现 contract 不一致、修一处漏一处、日志/权限/脱敏不一致时，才提交架构 Issue。
- 内置 skill 和内置能力对齐：产品能力、MCP 工具描述/schema、dispatcher、Synapse skill-package、Agent 使用指南、API reference、测试和 release note 是否同步。
- 代码健壮性：输入校验、异常边界、原子写入、备份/恢复、权限检查、日志/审计、脱敏、资源释放、跨进程事件一致性。

本轮最近提交专项必须覆盖的用户场景：

- Prompt 注入：启用/禁用全局约束、worker 元数据、仓库/任务上下文等注入段时，worker 实际收到的 prompt、UI 状态、schema 默认值和测试 fixture 必须一致。
- Synapse Skill 安装器：用户从独立系统 App 选择安装目标、批量安装、检测更新、打开标准安装流程和处理失败时，不能只更新前端状态，必须能追到真实安装结果和错误恢复。
- 密钥工具：用户新增、查看、复制、替换、删除密钥，以及安装器使用密钥替换变量时，不能泄露明文到日志/诊断/Issue/导出，也不能因为迁移或刷新造成密钥丢失、复活或错用。
- 云盘：最近 30 天变更过的上传任务、文件夹上传、公开访问、同步、分享/密码、Drive Browser 和删除/刷新入口必须检查真实用户路径，不要求覆盖云盘全史，但发现明确问题要提交。

严格排除：

- 纯测试覆盖建议。
- 纯命名、代码风格、个人审美。
- 仅“可以重构”但没有具体用户风险、维护风险或 contract 漂移证据。
- 仅“日志可以更详细”但没有失败复盘、审计、安全或用户状态可信度影响。
- 需要运行 App、dev server、浏览器或 Playwright 才能确认的问题。
- `NOT.md` 明确保留的刻意设计。
- `AGENTS.md` 明确允许、要求或边界化的当前设计。
- 生成物、依赖目录、构建产物中的问题，除非源码配置会必然生成错误产物。

## 核心规则

1. **只读源码**：不得修改项目中的任何源代码文件。不得 `git add` / `git commit` / `git push`。
2. **最终记录到 GitHub**：有效发现提交到 `FairyEver/Synapse` 的 GitHub Issue，并同时使用 `bug`、`优先级:*`、`类型:*`、`模块:*` 标签。
3. **本地轻量索引**：Issue 创建成功后，向 `/Users/liyang/Desktop/temp/issues.jsonl` 追加一条轻量 JSON，用于后续 Agent 快速去重；不要把完整证据链只写在 JSONL 里。
4. **证据优先**：每个问题必须有代码级证据链，不能凭感觉、审美偏好、路线图或泛泛经验提交。
5. **用户路径优先**：优先检查真实入口到真实结果的闭环，而不是只看单个函数。
6. **最近 30 天优先**：本轮优先审查 2026-06-09 以来的当前源码落点；历史代码只在它仍被最近入口调用、或为解释最近变更根因时追溯。
7. **同根因合并**：同一个根因导致多个表现，只提交更上游、更准确的一条 Issue。
8. **日志与脱敏并重**：关键操作要能复盘，同时不能泄露 token、secret、Authorization、Cookie、share password、provider key、data-server token 或用户私密内容。
9. **启动必读优先**：每次开始必须阅读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 和 `/Users/liyang/Documents/code/github/Synapse/AGENTS.md` 当前内容。
10. **不重复**：提交前必须查本地轻量索引和 GitHub Issue，跳过已记录、同根因或同用户结果的问题。
11. **Issue 上下文要详细**：GitHub Issue 必须包含足够上下文，让修复 Agent 不需要重新猜测问题来源。
12. **范围可以宽，证据必须窄**：可以选择很宽的检查方向，但每个 Issue 必须落到明确入口、文件、行号、错误结果和影响。

## 本轮完整性定义

本轮“完整性”不是要求功能更多，而是检查最近 30 天已经合入、用户或 Agent 已经能触发的能力是否可靠、可恢复、可追踪、跨入口一致。

每个候选链路至少从以下层级中选择 3 层以上连起来看：

```text
用户入口 / 系统 App / 菜单 / 按钮 / 任务面板 / Workflow 节点 / MCP tool / 云盘公开路由
→ renderer 组件 / hook / store / API client / window.synapse bridge
→ preload / IPC module / capability dispatcher / server controller / route guard
→ app capability service / scheduler / worker prompt builder / installer service / secrets service / drive service
→ DataRepository / Prisma / file system / encrypted storage / packaged resource / release note
→ 真实结果 / 状态刷新 / 错误反馈 / disabled/loading/empty / 历史记录 / 安装状态 / 运行状态
→ 日志 / 审计 / 运行记录 / 脱敏 / 导出 transcript
→ 测试 / 文档 / Synapse skill-package / MCP schema / Agent guide
```

重点检查：

- 页面、按钮、菜单、slash、MCP tool、Workflow 节点或 Agent 能力存在，但后端、主进程、服务、模板或持久化不能闭环。
- 前端调用 API/IPC/capability，但参数、返回结构、错误语义、权限语义不匹配。
- 用户操作后显示成功，但刷新、切换窗口、重开应用或公开访问时真实状态不一致。
- Synapse Skill 安装器显示可安装或已更新，但安装源、目标路径、批量安装、标准安装流程、更新检测或失败状态不能闭环。
- Synapse skill-package 的 Agent 使用指南/API reference 没有同步新增工具、删除旧模板路径或描述错误调用顺序。
- 密钥工具能保存、显示、复制或替换变量，但明文泄露到日志、诊断、运行记录、toast、错误对象或本地索引，或迁移/删除后旧密钥复活。
- 云盘上传、预览、编辑、评论、版本、分享、发布、公开访问的权限、状态、URL、过期、密码、下载或预览链路断裂。
- 文档保存后 UI 显示成功，但刷新、版本历史、评论锚点、分享页、公开页或本地同步文件看到的内容不一致。
- 评论批注能创建但定位错位、权限错误、线程状态丢失、数量错误或编辑后锚点无法恢复。
- 版本恢复、下载、删除、pin 或自动清理与当前文件、变更日志、分享/发布状态、同步 baseline 不一致。
- 同步显示完成但本地/远端内容不一致，或失败/冲突/权限不可达时用户无法理解下一步。
- 云端已有文件或文件夹，本地没有；用户启动同步后，本地没有真实创建对应文件、文件夹层级或内容。
- 本地已有文件或文件夹，云端没有；用户启动同步后，云端没有真实创建对应 item、文件夹层级或内容。
- 同步核心能力只存在于 service、planner、executor、MCP 或测试里，但用户界面没有可到达入口、入口无法触发真实同步、或触发后状态不可观察。
- 同步界面用词、按钮、状态、完成提示和用户自然理解冲突，例如把“已排队/已扫描/请求成功”显示成“同步完成”。
- 重复点击、并发、取消、失败、重试、断网、切换团队/项目/窗口、关闭窗口导致云盘、编辑、评论、版本或同步状态卡死或误判。
- 大目录、大文件、大量云盘文件、大量评论/版本/变更日志、大量同步记录导致明显无界扫描、重复 IO、内存增长或 UI 卡顿。
- 同一业务 contract、路径校验、日志脱敏、权限检查、状态转换或 schema 定义重复多份，且已经出现或高概率出现不一致。
- 新能力只改产品本体，未同步 MCP 描述/schema、Synapse skill-package、Agent guide、API reference、release note 或测试。
- 错误被吞掉、泛化到无法定位，或 UI 展示成误导性成功。

禁止把以下内容单独作为完整性 Issue：

- 只是缺少一个“更方便”的快捷入口。
- 只是测试可以更多。
- 只是页面信息密度、布局或文案可以优化，但没有误导或不可操作后果。
- 只是某个私有实现看起来不够优雅。
- 只是生成物没同步源码。
- 只是缺日志，但该操作没有失败复盘、审计、安全或用户状态可信度需求。
- 只是性能“可能更快”，但没有当前代码会无界增长、明显重复、N+1 或阻塞用户路径的证据。
- 只是“可以抽象”，但没有重复实现导致的 contract 漂移或维护风险证据。

### P1：核心功能受损

- 云端起点同步或本地起点同步任一方向在正常用户路径下不可完成，或者只能从代码/MCP 调用、不能从产品界面完成。
- Synapse Skill 独立安装器无法可靠准备安装源、选择全局/编辑器目标、批量安装、检测更新、打开标准安装流程或呈现真实安装失败。
- 密钥工具无法可靠保存、读取、更新、删除、迁移或供安装器变量替换使用，或失败后用户无法恢复。
- 用户能触发的入口实际无效、只改前端状态、成功提示虚假、刷新后回退或后端没有对应实现。
- API / IPC / capability / MCP / renderer type / schema / template 文档不一致，导致 Agent 或用户操作按错误 contract 执行。
- 失败后用户无法自助恢复，且日志不足以定位。
- 并发、取消、重复提交、切换团队/项目/文件、多窗口、断网、同步中断导致核心状态卡死。
- 性能问题会让正常规模数据的用户路径卡死、超时、内存持续增长或阻塞主进程。
- Synapse skill-package、内置指南或 MCP 指南教 Agent 使用错误工具、错误字段或错误顺序，导致能力不可用。

### P2：体验、状态可信度和复盘问题

至少满足一项：

- 用户可以继续，但状态不可信、错误提示不可操作、空态/禁用态/loading 缺失或误导。

## 问题类型

使用以下 `type`：

- `crash`：崩溃、未捕获异常、必现运行失败。
- `dataLoss`：数据丢失、覆盖、持久化损坏、恢复失败。
- `security`：敏感信息泄露、权限绕过、缺少鉴权或审计。
- `errorHandling`：错误吞掉、错误提示缺失、错误状态不可信。
- `interaction`：交互链路、按钮状态、并发操作、状态同步问题。
- `uiQuality`：违反 UI token、shadcn、主题、文案、可访问性规则。
- `performance`：无界扫描、N+1、重复 IO、渲染阻塞、主进程阻塞、资源泄漏。
- `syncConsistency`：本地/远端、当前版本、评论锚点、变更日志或同步状态不一致。
- `accessibility`：权限、分享、公开访问、本地可访问性或用户心智模型错误，导致用户以为可访问但实际不可达，或以为不可访问但实际泄露。
- `alignment`：MCP、capability、内置 skill/rule/prompt、Agent guide、API reference 与产品能力不一致。
- `robustness`：原子性、取消、重试、资源释放、输入校验、状态机健壮性缺口。
- `deadCode`：死代码、废弃路径、重复定义。
- `architecture`：违反硬约束、跨层边界、错误依赖方向、应抽象但分散导致风险。

如果 GitHub 没有对应 `类型:*` 标签：

- `performance` 优先映射到 `类型:架构` 或 `类型:交互`，并在 body 写明 `type=performance`。
- `syncConsistency` 优先映射到 `类型:交互` 或 `类型:错误处理`，并在 body 写明 `type=syncConsistency`。
- `accessibility` 优先映射到 `类型:交互` 或 `类型:安全`，并在 body 写明 `type=accessibility`。
- `alignment` 优先映射到 `类型:架构`，并在 body 写明 `type=alignment`。
- `robustness` 优先映射到 `类型:错误处理` 或 `类型:架构`，并在 body 写明 `type=robustness`。

重点：输入校验、异常边界、失败回滚、原子写入、备份失败阻断、取消语义、重试语义、资源释放、toolUseId 关联、日志脱敏、权限卡片摘要不回流真实工具入参、AskUserQuestion 空答案停止敏感写操作、provider env 覆盖和 side-channel secret 隔离。

### 方向 L：同步路径、文件系统边界和可访问性

重点路径：

```text
desktop/src/modules/drive/
desktop/electron/modules/drive-sync/
desktop/electron/services/drive-sync-service.ts
desktop/electron/services/drive-sync-planner.ts
desktop/electron/services/drive-sync-executor.ts
desktop/electron/services/drive-sync-watcher.ts
desktop/electron/services/drive-sync-local-snapshot.ts
desktop/electron/services/drive-sync-paths.ts
desktop/electron/services/drive-sync-excludes.ts
desktop/electron/services/drive-sync-binding-validator.ts
desktop/electron/runtime/data-repo/schemas/drive-sync.ts
server/src/drive/drive-change-log.ts
shared/src/drive.ts
```

重点：

- 用户选择的本地目录是否可访问、可写、可持续监听，失败时是否阻断绑定并给出可操作错误。
- 本地路径 containment 是否能阻止越界、符号链接绕过、父子目录互相绑定、重复绑定和大小写/分隔符歧义。
- 文件名清洗是否覆盖远端 item name、本地文件名、评论/版本下载名、同步临时文件名和冲突副本名。
- 云端文件夹到本地目录、本地文件夹到云端目录的路径映射是否稳定；不能把文件夹当普通文件，也不能丢空目录、父目录或嵌套层级。
- 删除、重命名、移动、覆盖、恢复版本、远端变更和本地变更同时发生时，planner 是否表达清楚权威来源。
- 同步排除规则是否符合用户心智：被排除文件不应显示为待同步，已同步文件不应被错误跳过。
- 文件锁、同步盘、权限拒绝、目录不存在、网络不可达、远端 404/403/409 等错误是否保留恢复路径。

本方向 Issue 必须说明当前代码为什么会影响用户访问本地或远端文件的正常心智；不要只把平台差异、路径风格或文件名偏好本身当问题。

### 方向 M：历史低覆盖代码复盘

重点路径由覆盖地图决定。适合选择：

- 长期未被 Issue 命中的用户入口。
- 多个模块共享但很少被审计的 helper。
- 老旧迁移代码、兼容代码、导入导出代码、恢复代码。
- 早期能力保留到现在但新 UI/MCP/Agent 路径仍在调用的代码。

不要为了“往前看”扫描无当前入口的废弃历史。必须证明当前用户仍可能触发。

## 扫描模式

每轮必须先选择一个扫描模式，再选择方向和目录。不要只说“扫描云盘”。

### 模式 1：用户旅程与意外表现模式

从真实用户操作出发，倒推代码链路。

候选旅程：

- 用户打开 Synapse Skill 安装器，检测更新，选择全局/编辑器目标，批量安装，某一项失败后重试或打开标准安装流程。
- 用户新增密钥，隐藏/显示/复制/替换/删除，再让安装器使用密钥变量替换，确认 UI 和日志不泄露明文。
- 用户打开云盘文档，切到编辑，保存，刷新，再从版本历史、分享页或公开页查看真实结果。
- 用户选中文档内容创建评论，编辑原文，恢复旧版本，再查看评论锚点和线程状态。
- 用户在云盘上传文件夹，重命名、移动、分享、取消分享，再刷新公开链接。
- 云端已有文件或文件夹、本地目录为空，用户创建桌面同步绑定并启动同步，再查看本地是否真实出现内容。
- 本地已有文件或文件夹、云盘目标为空，用户创建桌面同步绑定并启动同步，再查看云盘是否真实出现内容。
- 用户创建桌面同步绑定，本地编辑文件，远端修改同一文件，断网恢复后查看冲突和同步状态。
- 用户快速重复点击保存、评论、恢复版本、同步、删除、取消、重试或切换项目/团队/文件。
- 用户在多窗口中编辑同一对象，或在一个窗口删除另一个窗口正在使用的对象。
- 用户看到成功 toast 后刷新页面、重开应用或从另一个入口查看真实结果。

适合发现 P0/P1/P2。

### 模式 2：边界输入与并发模式

主动寻找正常用户可能触发的边界：

- 空字符串、空 ID、无效 ID、已删除 ID、重复 ID。
- 文件名非法、路径穿越、大小写冲突、尾随空格/点、空文件夹、大文件、大目录。
- 跨团队资源、跨项目资源、禁用用户、缺失/过期 token。
- 保存中取消、编辑中删除、重复保存、重复评论、重复上传、重复发布、重复恢复版本、重复同步。
- 网络失败、权限拒绝、timeout、存储不可访问、日志写入失败。
- 本地同步目录含空格/中文、同步盘、只读目录、文件锁、符号链接、父子目录互相绑定。

适合发现 P0/P1/P2。

### 模式 3：契约一致性模式

检查链路：

```text
route / IPC channel / preload API / capability tool / MCP tool / schema / service method
→ result contract
→ renderer type / Agent guide / built-in skill
→ page or Agent usage
→ state update
→ log record
```

重点：

- 前端调用不存在的路由、IPC 或 channel。
- 返回字段和前端类型不一致。
- MCP schema 和 dispatcher 行为不一致。
- 内置 skill 示例使用已删除字段或错误默认值。
- 页面刷新依赖的字段在响应里不存在。
- 日志记录的 userId、teamId、projectId、driveItemId、annotationId、versionId、syncBindingId、shareId、publicationId、toolUseId 无法和用户行为关联。

适合方向 B/C/D/E/F/H/J/K。

### 模式 4：持久化与恢复模式

检查：

- Prisma schema / migration 与服务逻辑不一致。
- DataRepository 写入失败、部分写入、覆盖或迁移不兼容。
- 云盘 item、upload session、storage object、share、publication、public URL 状态不一致。
- 评论 thread/comment/target、版本记录、change log、sync baseline/snapshot/binding 状态不一致。
- 审计日志、运行日志写入失败后业务状态不可信。
- 错误重试或恢复路径缺失。

适合方向 C/D/E/F/K。

### 模式 5：性能与资源模式

检查：

- 无分页、无上限、无取消的大列表、大目录、大日志、大历史。
- 递归扫描、同步 IO、重复 hash/parse、N+1 查询。
- renderer 里每次 render 都进行大计算。
- 事件订阅、watcher、interval、child process、file handle 泄漏。
- 状态更新造成循环请求、事件风暴或重复广播。
- 大文件上传/下载/预览缺少流式处理或大小 guard。

适合方向 D/E/F/G/K。

### 模式 6：重复实现与抽象缺口模式

检查：

- 同一逻辑 5+ 行出现 3+ 次。
- 重复处涉及路径安全、文件名清洗、权限、脱敏、状态转换、schema、MCP tool、日志、同步一致性、版本语义或持久化。
- 至少一处已经和其他处不一致，或新增能力明显只改了一处。
- 可以明确指出应该抽成哪个共享 helper/service/schema/domain。

适合方向 H/I/J/K/L。

### 模式 7：内置能力对齐模式

检查：

- 产品能力代码与 MCP domain/tool/dispatcher 是否一致。
- `*_type_list` / `*_type_describe` 或动态 discovery 是否包含新增类型。
- Synapse skill-package、内置 skill/rule/prompt 模板是否仍教 Agent 使用正确工具、字段、默认值和调用顺序。
- Agent guide/API reference 是否描述当前行为。
- 相关测试是否覆盖 Agent-facing discovery contract。
- 用户可感知的 MCP/内置能力行为变化是否记录在 `RELEASE_NOTES_PENDING.md`。

适合方向 C/F/J，尤其适合 Synapse Skill 安装器、密钥工具和云盘 Agent 使用指南。

### 模式 8：同步一致性与本地访问模式

优先搜索：

```sh
rg -n "drive-sync|syncBinding|baseline|snapshot|remotePoller|localSnapshot|planner|executor|watcher|conflict|cursor|changeLog|lastSynced|pending|failed|retry"
rg -n "upload|download|createFolder|folder|directory|children|recursive|walk|mkdir|readdir|copyFile|rename|unlink|watch|empty folder|emptyFolder"
rg -n "path\\.relative|realpath|lstat|stat|symlink|startsWith\\(|toLowerCase\\(|normalize\\("
rg -n "annotation|comment|versionId|currentVersion|restore|pin|change_log|publication|shareId"
```

重点要求：

- 路径 containment 使用 `path.relative` 语义，不使用字符串前缀。
- 本地真实路径、远端 item id、版本 id、评论 target 和同步 binding id 不得互相混用。
- 文件和文件夹必须分别验证；目录创建、空目录、嵌套目录和递归 children 不得被文件同步逻辑顺手吞掉。
- 云端起点和本地起点必须分别验证；单向可用不能证明双向同步可用。
- 同步状态必须区分 pending、running、failed、conflict、completed、stale，不要把“请求成功”当“内容一致”。
- 失败恢复必须保留用户能理解的下一步：重试、重新绑定、跳过、手动解决冲突或重新检测。
- 本地不可访问、远端不可访问和权限不可访问要区分，不要统一显示成泛化失败。

适合方向 E/L。

### 模式 9：UI 状态与体验模式

如果扫描 UI，重点检查源码可证明的问题：

- 硬编码颜色或不走 token。
- 自定义按钮、卡片、弹窗等替代已有 shadcn 组件。
- 卡片套卡片、连续 Divider、shadow + border + background 同时堆层级。
- loading / error / empty / disabled 状态缺失。
- 表单 label/input、表格数字、icon/text 对齐明显违反仓库规则。
- 文案包含功能介绍、实现解释、重复状态、欢迎横幅、AI 自称或装饰性 emoji。
- 成功/失败/空态文案会误导用户对云盘、编辑保存、评论、版本、同步、权限、分享、发布或公开访问状态的理解。

禁止仅凭“看起来不好看”提交 UI Issue。

### 模式 10：权限、安全与审计模式

检查敏感操作：

- 管理 API 是否都走 admin guard。
- 用户 API 是否限制到当前用户和当前团队。
- 团队、项目、云盘资源、评论、版本、同步绑定是否可被其他主体读取或修改。
- 云盘编辑、评论、版本恢复、同步、分享、发布、下载、预览、zip 是否可越权访问或泄露。
- token、cookie、Authorization、provider key、share password、side-channel token、data-server token 是否脱敏。
- 敏感操作是否有审计或结构化日志。

适合发现 P0/P1/security/logging/architecture。

### 模式 11：历史低覆盖挖掘模式

从覆盖地图里选择低命中文件或长期未审计功能，往前看历史原因。

候选：

- 旧兼容代码仍被新入口调用。
- 新能力迁移后旧入口残留并造成无效操作。
- 老 helper 的语义和新模块硬边界冲突。
- 旧文档/内置 skill/API reference 未随产品能力变化。
- 旧同步/版本/评论兼容代码仍按旧 contract 写入或读取。

适合方向 M。

## 问题发现标准

每个问题必须有完整证据链：

```text
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口 → 用户影响或复盘阻断
```

合格条件：

- 能在代码中证明问题存在，不需要运行 App、dev server、浏览器或 Playwright。
- 影响本轮重点范围中的正常路径，或是合理高概率边界。
- 至少串起 3 层相关文件；单文件局部猜测默认不合格。
- 用 `rg` 确认过影响范围。
- 涉及历史或最近提交时，用 `git log` / `git show` / `git blame` 确认过最终落下的代码。
- 涉及 UI 时，确认过项目组件库和 token 规则，不把主观审美当 Issue。
- 涉及同步/可访问性时，能说明本地/远端、权限、版本或评论状态和当前用户路径的关系。
- 涉及性能时，能说明复杂度、无界增长或重复资源消耗来自哪里。
- 涉及重复实现时，能说明至少 3 处重复和具体不一致风险。
- 涉及内置能力对齐时，能指出产品/MCP/skill/guide/test 哪些面不一致。
- 用 `NOT.md` 确认过不属于刻意设计。
- 用 `AGENTS.md` 确认过不违反当前仓库硬规则和模块边界判断。
- 能解释为什么不属于已有 Issue 或同根因。
- 后续修复 Agent 能根据 Issue 直接开工。

不合格条件：

- 需要运行 App、dev server、浏览器或 Playwright 才能确认。
- 只是“感觉不太好”但逻辑没错。
- 仅缺测试覆盖。
- 仅缺日志，且没有用户可见失败、审计风险、安全风险或复盘阻断。
- 只是代码风格偏好。
- 命中 `NOT.md` 中明确说明应保留的刻意设计。
- 与已有 Issue 同根因。
- 证据链只有单个文件局部猜测，没有入口和结果。
- 性能、同步、可访问性、抽象、对齐问题没有证明当前用户或 Agent 能触发。

## Issue 创建质量闸门

创建 Issue 前必须回答 16 个问题：

```text
1. 用户、Agent 或管理员从哪里触发？
2. 代码链路是什么？
3. 当前错误结果、意外表现、性能退化、对齐缺口或复盘阻断是什么？
4. 为什么这是正常功能路径或合理高概率边界，而不是极端猜测？
5. 是否查过最近 30 天风险地图和覆盖地图？
6. 如果涉及最近或历史变更，是否复盘了最终落下的代码，而不是只看提交标题？
7. 是否查过 NOT.md，确认不是刻意设计？
8. 是否查过 AGENTS.md，确认不是仓库硬规则允许或要求的行为？
9. 是否查过本地索引？
10. 是否查过 GitHub 已有 Issue？
11. 是否和已有 Issue 同根因？
12. 如果涉及关键用户操作，日志/审计/运行记录是否足够支撑复盘？
13. 如果涉及敏感数据，脱敏是否覆盖 tool input、tool result、日志、导出和 UI？
14. 如果涉及同步/可访问性，是否能说明本地/远端/权限/版本/评论状态如何影响真实用户心智？
15. 如果涉及性能/抽象/对齐，是否有具体 contract、规模、重复或文档偏差证据？
16. 后续修复 Agent 能否按这个 Issue 直接开工？
```

任一答不出来：

- 不创建 Issue。
- 在最终输出列为 `rejected candidate`。

## GitHub Issue 格式

每个有效发现创建一个 GitHub Issue。

每个 Issue 必须至少打 4 个分类标签：

```text
bug
优先级:<P0|P1|P2|P3>
类型:<崩溃|数据丢失|安全|错误处理|交互|UI质量|日志|死代码|架构>
模块:<Server|管理后台|Electron|应用壳|设置|UI|基础设施|工作流|网盘|Agent|内容>
```

**不要打任何 `状态:*` 或无前缀状态标签。** 巡检 Agent 只负责分类标签；Issue 创建后没有状态标签即为「待确认」隐含状态，后续由修复 Agent 认领时添加状态标签。

标签必须使用仓库现有标签。如果某个建议标签不存在，选择最贴近的现有标签，并在 Issue body 的 `Label fallback` 写明原始判断。

模块标签选择：

- `desktop/app-capabilities/synapse-skill/**`：优先 `模块:内容`；涉及系统 App 壳或安装 IPC 时也可用 `模块:Electron`。
- `desktop/app-capabilities/secrets/**`：优先 `模块:设置` 或 `模块:基础设施`；涉及 MCP/安装器变量替换时按实际入口选择 `模块:内容` 或 `模块:Electron`。
- `dashboard/src/features/drive/**`、`dashboard/src/features/drive-browser/**`、`dashboard/src/routes/_authenticated/drive/**`、`dashboard/src/routes/_authenticated/admin-drive/**`、`dashboard/src/routes/files/**`：优先 `模块:网盘`；如果仓库没有该标签，使用 `模块:管理后台`。
- `server/src/drive/**`、`shared/src/drive.ts`、Drive storage、annotation、version、change log、sync-facing DTO、share、publication、public route：优先 `模块:网盘`；如果仓库没有该标签，使用 `模块:Server`。
- `desktop/src/modules/drive/**`、`desktop/electron/modules/drive-sync/**`、`desktop/electron/services/drive-sync-*.ts`、`desktop/electron/runtime/data-repo/schemas/drive-sync.ts`：优先 `模块:网盘`；如果仓库没有该标签，使用 `模块:Electron`。
- `desktop/synapse-capabilities/shared/drive-domain.ts`、`desktop/electron/capabilities/drive-dispatcher.ts`、MCP/内置 skill 对齐：优先 `模块:网盘`；如果仓库没有该标签，按能力归属选择 `模块:内容`、`模块:Electron` 或 `模块:基础设施`。
- `desktop/app-capabilities/synapse-skill/skill-package/**`：优先 `模块:内容`；如果是特定能力指南，按能力归属选择模块并写明 `Scope: synapse-skill-package`。
- `desktop/resources/templates/skills/**`、`rules/**`、`prompts/**`：只审查仍被最近入口引用的旧模板路径；优先 `模块:内容`，并在 Issue body 说明为什么它仍影响当前用户或 Agent。
- 跨模块 UI、通用 shadcn 组件、全局主题、全局文案或跨页面可访问性问题：优先 `模块:UI`。
- 构建脚本、runtime 基础设施、bootstrap、硬约束等不属于具体模块的问题：优先 `模块:基础设施`。

Issue body 的 `Priority` 或 `Scope` 必须明确写出方向，例如 `Direction: synapse-skill-installer`、`Direction: secrets`、`Direction: drive-recent`、`Direction: recent-capability-alignment`。

## 去重规则

提交 Issue 前必须做三层去重，并做一层防误判过滤。

### 1. 本地索引去重

- 读全量 `/Users/liyang/Desktop/temp/issues.jsonl`。
- 如果已有相同 `fingerprint`，跳过。
- 如果旧记录没有 `fingerprint`，用 `file + symbol + summary` 近似判断。
- 如果同一文件已有大量相似 summary，默认跳过，除非是 P0/P1。

### 2. GitHub Issue 去重

使用 GitHub CLI 查询足够范围：

```sh
gh issue list -R FairyEver/Synapse --state all --limit 500 --json number,title,url,state,labels
```

对比：

- 标题中的 priority/type/summary。
- body 中的 `Local fingerprint`。
- 同一文件、同一 symbol、同一用户结果。
- 同一根因的不同表现。

如果 GitHub 已有同问题，无论 open/closed 都跳过。

### 3. 同根因去重

如果新发现和已有 Issue 共享同一上游根因，只能提交更上游、更准确的一条；不要为每个下游表现拆多个 Issue。

示例：

- 同一个 drive URL helper 错误导致分享页、公开下载和后台管理入口都跳错路径。提交一个 URL contract 根因 Issue。
- 同一个 version id/current version 判断错误导致编辑器、版本恢复、评论锚点和同步 baseline 都指向旧内容。提交一个版本语义根因 Issue。
- 同一个 annotation target 解析错误导致评论创建、渲染、编辑后重定位和公开页展示都错位。提交一个评论定位根因 Issue。
- 同一个 sync planner 状态判断错误导致本地删除、远端删除和冲突恢复都显示成功但没有一致。提交一个同步状态根因 Issue。
- 同一个 MCP schema 漂移导致 Agent skill、dispatcher 和 UI 示例都错误。提交一个能力对齐根因 Issue。
- 同一个日志脱敏函数漏处理 Bearer token，不要按每个调用点拆多个 Issue。

### 4. 防误判过滤

- 读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 的当前内容，而不是依赖记忆。
- 读 `/Users/liyang/Documents/code/github/Synapse/AGENTS.md` 的当前内容，而不是依赖记忆。
- 如果候选问题命中 `NOT.md` 明确保留的行为，跳过。
- 如果候选问题命中 `AGENTS.md` 明确允许、要求或边界化的行为，跳过。
- 如果需要提交附近问题，Issue body 必须说明 `NOT.md` 和 `AGENTS.md` 已检查，且本问题不是这两个文件列出的保留或允许行为。
