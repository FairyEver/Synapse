# Synapse 夜间健壮性与品质巡检

你正在对 Synapse 桌面应用做一次并行安全的全局品质巡检与小步修复。目标是让软件更健壮、更美观、更完善。

本 Prompt 会被 10 个 Agent 在同一工作目录中并行循环执行，整夜持续运行数百轮。每轮只做一个有实际价值的改进。

## 核心理念

你不是在补测试、补日志、补文档。你是一个同时具备产品经理洞察力、资深测试工程师严谨性和架构师代码品味的角色。你的每一次改动都应该让真实用户受益：要么减少一次崩溃，要么消除一个报错，要么让界面更好看，要么让交互更顺畅，要么让代码更干净。

**判断标准：如果这个改动拿给用户看，用户会不会说"这个有用"？如果不会，不要做。**

## 本轮总目标

按优先级从高到低：

1. **健壮性**：消除崩溃、未捕获异常、静默失败、状态卡死、资源泄漏、竞态条件。
2. **错误处理**：把空 catch、吞掉的 Promise rejection、缺少 error boundary、缺少用户可见错误提示的地方补完整。
3. **死代码与冗余**：删除未使用的 imports、未调用的函数、重复定义的类型/常量/工具函数、废弃的旧路径代码。
4. **UI 美观与一致性**：修复视觉不一致、间距错乱、颜色不走 token、组件未用 shadcn 现有的、深浅主题切换后样式异常。
5. **交互完整性**：补齐缺失的 loading/error/empty/disabled 状态、修复键盘无法操作的场景、修复 hover/focus 态缺失、修复滚动异常。

工作流是最近新增的功能，代码成熟度最低，是最需要关注的区域。每轮至少花 **50%** 扫描时间在工作流相关代码上。

- Renderer 编辑器：`desktop/src/modules/workflow/editor/`
- Renderer 运行器：`desktop/src/modules/workflow/runner/`
- Renderer Hooks：`desktop/src/modules/workflow/hooks/`

- MCP 能力定义：`desktop/synapse-capabilities/shared/workflow-domain.ts`

## 工作模式

本轮使用「深度扫描 + 小步修复模式」。Token 预算不受限，鼓励充分阅读。

每轮有两种模式，根据条件自动选择：

### 模式 A：侦察轮（Scout）

当以下任一条件成立时，进入侦察模式：

- 本 Agent 是本次运行的第 1 轮（需要建立全局理解）
- 问题积压池 `auto/state/issue-backlog.jsonl` 为空或少于 5 条未认领条目
- `coverage-map.json` 中有整个方向（A/B/C/D）超过 20 轮未被任何 Agent 扫描

侦察轮流程：

1. **深度阅读**：选择一个方向，从入口文件开始，沿调用链**完整阅读**该方向的核心模块。不设时间限制，读到理解整个数据流为止。
2. **全链路走查**：以用户身份走完该模块所有主要操作路径的代码。对每个路径思考：正常流、异常流、边界流各会发生什么。
3. **批量记录候选**：将发现的所有问题写入 `auto/state/issue-backlog.jsonl`（通过 claims.lock 保护），每个问题一条 JSON。
4. **选择最高价值的 1 个自行修复**（如果有的话）。
5. **更新 coverage-map**。

侦察轮的价值在于：一个 Agent 花 token 深读后的发现，可以被其他 9 个 Agent 直接使用，避免 10 个 Agent 重复读同一批文件。

### 模式 B：修复轮（Fix）

默认模式。流程：

1. **检查积压池**：先读 `auto/state/issue-backlog.jsonl`，看是否有未认领的高价值候选。如果有，优先从池中认领（省去扫描时间）。
2. **自主扫描**（如果池中无合适候选）：选择一个方向，读模块入口和类型定义，理解功能全貌和数据流。
3. **产品视角走查**：以用户身份走代码关键路径，思考"如果我是用户，在这一步会遇到什么问题？"
4. **深度验证候选**：选定候选后，不急于修复。先阅读该符号的**所有调用方**和**所有被调用方**（用 `rg` 找引用），确认问题真实存在且修复不会产生连锁影响。
5. **写完整证据链**：包含触发入口 → 完整调用链 → 错误结果，以及修复后所有调用方的预期行为。
6. **最小修复**。
7. **扩展验证**：除常规验证外，额外阅读所有 import 了被修改文件的文件，确认修复没有副作用。

### 问题积压池格式

路径：`auto/state/issue-backlog.jsonl`

通过 `claims.lock` 保护读写。每条格式：

```json
{"id":"issue-<timestamp>-<4位随机>","discoveredBy":"<agentId>","iteration":N,"direction":"A|B|C|D","priority":"P0|P1|P2|P3","type":"crash|errorHandling|deadCode|uiQuality|interaction","summary":"一句话","evidenceChain":"触发入口 → 代码链路 → 错误结果","files":["file1","file2"],"status":"open|claimed|fixed|wontfix","claimedBy":null,"fixedIteration":null}
```

type 键统一使用 camelCase（与 `panel/data.js` 的 `typeStats` 键一致）：

| type 值 | 含义 |
|---------|------|
| `crash` | 崩溃修复 |
| `errorHandling` | 错误处理 |
| `deadCode` | 死代码 |
| `uiQuality` | UI品质 |
| `interaction` | 交互完整性 |

认领问题时：更新 `status` 为 `claimed`，写入 `claimedBy`。修复后更新为 `fixed`。放弃时更新为 `open`（释放给其他 Agent）。

## 并行原则

- 外部已有 10 个 Agent 并行。单个 Agent 不得再启动子 Agent。
- 每轮最多处理 1 个问题。
- 修改前先声明写入范围并按 claim/lock 协议加锁。
- 默认文件级 claim。大文件只有在不改 imports、exports、props、共享类型时，才允许符号级 claim。
- 如果目标文件已被其他 Agent claim 或 lock，最多等待 2 分钟；仍不可用就换候选或结束本轮。
- 宁可本轮无修复，也不要抢同一处代码。
- 不做全文件格式化，不批量重排 imports，不顺手重构邻近代码。

### 方向分散

为避免 10 个 Agent 全部挤在同一批文件上，每轮开始时用以下策略选择扫描方向：

1. 读 `claims.jsonl` 最近 20 条，统计当前各方向的活跃 Agent 数。
2. 如果工作流方向（A）的活跃 Agent ≥ 5，本轮切到 B/C/D 方向。
3. 如果 B/C/D 某方向活跃 Agent ≥ 3，避开该方向。
4. 相同方向内，优先选择 `coverage-map.json` 中 `lastReviewedIteration` 最旧或 `healthScore = "needs-attention"` 的文件区域。
5. 随机性：在符合以上规则的候选中，随机选取一个开始扫描，不要总从同一入口文件开始。

## 优先级

1. **P0**：崩溃、白屏、主进程未捕获异常、状态卡死、数据丢失、无限循环、资源泄漏（未清理的 listener/timer/subscription）。

3. **P2**：死代码和冗余——未使用的 exports/imports/函数/类型/常量、重复定义、废弃路径、空 catch 块。
4. **P3**：UI 品质——颜色不走 token、间距不一致、组件未用 shadcn 现有的、深浅主题异常、hover/focus 态缺失、loading/error/empty 状态缺失。

**同优先级下，工作流相关问题始终优先于其他模块。**

## 候选选择方法

每个候选都必须先写出**完整证据链**（token 不受限，链路写详细）：

```text
1. 触发入口：<用户操作或系统事件>
2. 调用链（全链路，不省略中间步骤）：
   → <文件A:行号> <函数名> — <做了什么>
   → <文件B:行号> <函数名> — <做了什么>
   → <文件C:行号> <函数名> — <问题发生在这里>
3. 错误结果：<用户会看到什么 / 系统会进入什么状态>
4. 影响范围：用 rg 查过，<X 个文件> 引用了问题符号
5. 修复后预期：所有调用方的行为变化 <逐一说明>
```

**不能仅凭"看起来不太好"或"理论上可能有问题"来选择候选。必须有代码层面的具体证据。**

候选合格条件：

- 能在代码中证明问题存在，不需要运行 App。
- 影响正常使用路径，不是只有极端边界才触发。
- 修复范围在 1-5 个文件内（已通过完整调用链确认影响范围可控）。
- 不和其他 Agent 可能在改的文件冲突。
- 已读过所有调用方，确认修复不会产生副作用。

候选不合格条件：

- 需要运行 App 或打开浏览器才能确认。
- 只是"感觉不太好"但代码逻辑本身没错。
- 修复需要改动 6 个以上文件或涉及核心数据模型变更。
- 仅仅是缺少测试覆盖（测试不是目的）。
- 仅仅是缺少日志（日志不是目的）。

## 各类改动的具体标准

### 健壮性修复

合格示例：
- `catch` 块为空或只有 `console.error`，异常被吞掉，用户看不到错误 → 补上用户可见的错误处理。
- `async` 函数返回的 Promise 没有 `.catch` 也没有 `try-catch`，rejection 会变成 unhandled → 加上错误处理。
- `useEffect` 中的异步操作没有清理，组件卸载后仍在写 state → 加上 abort 或 unmount 守卫。
- 事件监听注册了但没有清理（addEventListener 无对应 removeEventListener）→ 加上清理。
- `setTimeout`/`setInterval` 没有在组件卸载时清理 → 加上清理。

### 死代码清理

合格示例：
- 一个 export 的函数/类型/常量，在整个项目中没有任何 import → 删除。
- 一个 import 引入了但文件中未使用 → 删除。
- 一段被注释掉的旧实现，且有新实现已经在用 → 删除注释块。
- 一个类型定义和另一个几乎一样，且其中一个没有被使用 → 删除多余的那个。
- 废弃的文件（如旧的 Codex/Hermes 适配器残留）确认没有被引用 → 标记或删除。

验证方法：用 `rg` 确认该符号在项目中确实没有其他引用。

### UI 品质修复

合格示例：
- 使用了硬编码颜色（hex/rgb）而不是 token（bg-background、text-foreground 等）→ 替换为 token。
- 一个按钮/卡片/输入框手写了 div + 样式，但 shadcn/ui 有现成组件 → 替换为 shadcn 组件。
- 某个组件在深色主题下文字看不清、背景混为一色 → 修复 token 使用。
- 间距明显不一致：相邻元素用了不同的 gap/padding 规格 → 统一。
- 缺少 loading 态（操作后无反馈）、缺少 error 态（失败后无提示）、缺少 empty 态（空列表无说明）→ 补齐。

必须遵守 `.claude/rules/design.md` 和 `.claude/rules/ui-rules.md`：
- 使用 shadcn/ui + Radix + Tailwind token。
- 禁止内联 `style={{}}`（动态计算除外）。
- 禁止 hex/rgb/hsl 字面色和 Tailwind 任意色。
- 禁止渐变、装饰性 emoji、卡片套卡片。
- 文案必须面向用户、简短可操作，不是开发备注。

### 交互完整性修复

合格示例：
- 一个表单没有 disabled 态：正在提交时按钮仍可重复点击 → 加上 loading/disabled。
- 一个列表没有键盘导航支持 → 如果 shadcn 组件自带，换用之。
- 一个对话框没有无障碍描述（aria-describedby 缺失）→ 补上。
- 滚动容器没有用 ScrollArea → 如果内容可能溢出，换用 shadcn ScrollArea。
- 操作成功/失败后没有 toast 或状态变化 → 补上最小反馈。

## 实施规则

- 不新增依赖，不扩散 `any`，不做无关重构。

## Claim / Lock 协议

### Agent ID 与轮次追踪

```text
agentId = AUTO_AGENT_ID 环境变量；否则 "agent-" + 当前时间戳 + "-" + 4 位随机后缀
```

**轮次追踪**：每个 Agent 需要在整个运行期间维护自己的 `iteration` 计数器。

- 初始化方式：`ls auto/state/parallel/agent-notes/ | grep <agentId>` 找到自己最后一轮的 note 文件，从文件名提取最大轮次号 + 1。如果没有历史 note，从 1 开始。
- 每完成一轮（无论是否修复），`iteration += 1`。
- `iteration` 决定何时触发定期任务（摘要写入、claims 清理等）。

**初始状态文件容错**：以下文件在首次运行时可能为空，Agent 必须处理文件为空或不存在的情况：

- `issue-backlog.jsonl` — 空文件 = 池为空
- `claims.jsonl` — 空文件 = 无活跃 claim
- `nightly-summary.md` — 空文件 = 首次运行
- `coverage-map.json` — 如果已有数据则保留现有格式（含 `version` 字段），如果不存在则按本文档格式创建

### 共享状态文件

- `auto/state/fix-log.md`
- `auto/state/coverage-map.json`
- `auto/state/focus.md`
- `auto/state/nightly-summary.md`
- `auto/state/issue-backlog.jsonl` — 问题积压池，侦察轮写入，修复轮消费
- `auto/state/panel/data.js` — 实时监控面板数据（state.lock 下更新）

### 锁目录命名

路径哈希算法（`<path-hash>`）：将文件相对路径中的 `/` 替换为 `__`，`.` 替换为 `_`。例如：

```text
desktop/src/modules/workflow/editor/canvas.tsx
→ desktop__src__modules__workflow__editor__canvas_tsx
```

锁目录路径：

- `auto/state/parallel/locks/file__<path-hash>.lock/`
- `auto/state/parallel/locks/symbol__<path-hash>__<symbol名>.lock/`
- `auto/state/parallel/locks/claims.lock/` — 保护 claims.jsonl 和 issue-backlog.jsonl 读写
- `auto/state/parallel/locks/state.lock/` — 保护 fix-log、coverage-map、nightly-summary、panel/data.js
- `auto/state/parallel/locks/git.lock/` — 保护 git 操作

### Claim 生命周期

每个 claim 有四个状态：

```text
planned → active → done → (释放锁)
                 → abandoned → (释放锁)
```

claim 格式：

```json
{"agentId":"...","iteration":N,"status":"planned|active|done|abandoned","scope":"file|symbol","path":"...","symbol":"...","reason":"...","startedAt":"ISO","expiresAt":"ISO（= startedAt + 90 分钟）"}
```

`expiresAt` 在写入 claim 时计算：取当前时间 + 90 分钟。其他 Agent 可据此判断锁是否过期。

### 加锁流程（编辑前）

```text
1. 读 focus.md → 了解当前优先方向
2. 读 claims.jsonl 最近 20 条 → 了解哪些方向/文件正被占用（方向分散）
3. 读 fix-log.md 最后 2000 行 → 避免重复修复已处理的问题
4. 读 coverage-map.json → 找冷门文件优先扫描
5. 选定候选后，检查 locks/ 目录确认目标文件无活跃锁
6. 用原子 mkdir 获得 claims.lock/
7.   再次读 claims.jsonl 最后 20 条（二次确认，防止步骤 5 后有人抢先）
8.   如果目标文件已被 claim 且状态为 planned 或 active → 释放 claims.lock，换候选
9.   追加 status=planned 的 claim
10.  释放 claims.lock（rmdir）
11. 用原子 mkdir 获得目标文件 lock（file__<hash>.lock/）
12.   如果 mkdir 失败 → 等待最多 2 分钟，每 15 秒重试一次
13.   如果 2 分钟后仍失败 → 更新 claim 为 abandoned，换候选或结束
14. mkdir 成功 → 更新 claim 为 active（通过 claims.lock 保护写入）
15. 重新读取目标文件内容，确认与步骤 5 时一致（防止无锁窗口内被改）
```

**关键：步骤 6-10 是在 claims.lock 内的二次检查。** 这消除了"两个 Agent 同时看到文件空闲然后同时去抢"的竞态窗口。真正的互斥由步骤 11 的文件锁 mkdir 保证，claims.lock 内的二次检查是为了减少无效重试。

### 释放锁流程（编辑完成后）

```text
1. 完成文件修改和验证
2. 获得 claims.lock
3.   追加 status=done 的 claim
4.   释放 claims.lock（rmdir）
5. 删除目标文件锁（rmdir file__<hash>.lock/）← 立即释放，不要等 90 分钟过期
```

**必须主动释放。** 一次修复通常 5-10 分钟，不释放意味着其他 9 个 Agent 在接下来 80+ 分钟内无法碰该文件。

### state.lock 写入流程

写共享状态（fix-log、coverage-map、nightly-summary）需要 state.lock：

```text
1. 尝试 mkdir state.lock/
2. 如果失败 → 等待最多 30 秒，每 5 秒重试一次
3. 如果 30 秒后仍失败 →
   a. 将 state 写入内容暂存到 agent-notes 中（追加一节 "## 待写入 state"）
   b. 下一轮开始时检查是否有暂存内容需要补写
   c. 不阻塞当前轮的文件锁释放
4. 获得 state.lock 后：
   a. 写 fix-log.md（追加）
   b. 读-改-写 coverage-map.json
   c. 如果是第 10/20/30... 轮，写 nightly-summary.md
   d. 读-改-写 panel/data.js
   e. 释放 state.lock（rmdir）
```

**state.lock 的等待时间只有 30 秒，远小于文件锁的 2 分钟。** 因为 state 写入操作很快（追加几行），不应该长时间持有。如果超时，说明有异常，暂存到 agent-notes 即可。

### 过期锁处理

- 锁默认 90 分钟过期。
- 判断过期方法：读锁目录的 mtime，或读 claims.jsonl 中对应的 `expiresAt`。
- 如果一个锁已过期：
  - 将旧锁 rename 为 `<锁名>.stale-<agentId>/`
  - 然后 mkdir 新锁
- **不确定是否过期就避开。** 误删活跃锁比等一轮损失更大。

### claims.jsonl 清理

claims.jsonl 会随轮次增长。每个 Agent 在自己的第 50、100... 轮时（`iteration % 50 === 0`），获得 claims.lock 后：

1. 读取全部 claims
2. 只保留最近 200 条
3. 重写 claims.jsonl（原子：先写 .tmp 再 mv）

## 退出条件

- 找不到符合标准的高价值候选时：**转为侦察轮**，深读一个方向并将发现写入问题积压池。绝不为了有产出而强行做低价值改动。
- 证据链不完整时：不实施修复，但将不完整的线索写入积压池供后续调查。
- 目标文件被占用且等待 2 分钟仍不可用时：换候选；没有候选就转为侦察轮。
- 修复会触及 6 个以上业务文件、改变核心模型、引入新 IPC 或新架构时：不实施，记录到积压池并标记 `"status":"wontfix"`，注明需要人工设计。
- 积压池中所有条目都是 `fixed` 或 `wontfix`，且 `coverage-map.json` 中所有文件的 `healthScore` 都是 `stable`：说明"全面巡检完成"，建议暂停。（这比之前的"最近 50 条覆盖"标准严格得多，确保真正扫完才停。）

## State 收尾

**每一轮（无论是否有修复）都必须记录。** 这是早上查看夜间运行成果的唯一途径。

### 1. 个人 note（每轮必写）

路径：`auto/state/parallel/agent-notes/<agentId>-iteration-N.md`

无论本轮是否有修复，都必须写这个文件。内容简短，一个问题一个文件：

```markdown
# <agentId> 第 N 轮

- 时间：YYYY-MM-DD HH:mm
- 方向：<工作流引擎 / 工作流 UI / Agent 对话 / 模块 UI / 代码清理>
- 结果：<修复 / 仅调查 / 跳过（文件被占用）>
- 问题：<一句话描述，或"未发现合格候选">
- 修改文件：<文件列表，或"无">
- 验证：<通过 / 失败 / 未运行>
```

### 2. fix-log（有修复时必须追加）

路径：`auto/state/fix-log.md`

获得 `state.lock` 后追加。格式固定，便于早上快速扫读：

```markdown
---

## [YYYY-MM-DD HH:mm] Agent <agentId> 第 N 轮

### 问题
- <一句话定性>
- 类型：<崩溃修复 / 错误处理 / 死代码 / UI品质 / 交互完整性>
- 优先级：<P0/P1/P2/P3>

### 修改
- `<文件路径>`：<一行说明改了什么>
- `<文件路径>`：<一行说明改了什么>

### 用户受益
- <用户现在会看到什么不同>

### 验证
- <命令>：<结果>

### 风险
- <剩余风险，没有写"无">
```

### 3. coverage-map（有修复或深度扫描时更新）

路径：`auto/state/coverage-map.json`

获得 `state.lock` 后更新。记录每个文件的巡检状态：

```json
{
  "totalIterations": N,
  "lastUpdated": "YYYY-MM-DD HH:mm",
  "files": {
    "<文件路径>": {
      "lastReviewedIteration": N,
      "issuesFound": 0,
      "issuesFixed": 0,
      "healthScore": "stable|active|needs-attention",
      "lastUpdated": "YYYY-MM-DD HH:mm"
    }
  }
}
```

- 修改过的文件：`issuesFound += 1`，`issuesFixed += 1`，`healthScore = "active"`。
- 深读但未修复的文件：可标记为 `"stable"`。
- 发现问题但放弃修复的文件：`issuesFound += 1`，`healthScore = "needs-attention"`。

### 4. 晨间速览摘要（每 10 轮追加一次）

路径：`auto/state/nightly-summary.md`

每个 Agent 在自己的第 10、20、30... 轮时（即 `iteration % 10 === 0`），获得 `state.lock` 后在此文件末尾追加一段摘要：

```markdown
---

## 截至 YYYY-MM-DD HH:mm 的夜间巡检摘要

- 累计轮次：~N（基于 fix-log 和 agent-notes 估算）
- 有效修复数：M
- 修复分布：
  - 崩溃修复：X
  - 错误处理：X
  - 死代码清理：X
  - UI 品质：X
  - 交互完整性：X
- 重点修复区域：<哪些模块/文件被改得最多>
- 仍需关注：<尚未解决的高优先级候选>
- 建议：<继续当前方向 / 换方向 / 已饱和建议暂停>
```

读 `fix-log.md` 最近的条目来生成此摘要。**这个文件是你早上醒来第一个看的文件。**

### 5. 实时监控面板数据（每轮必更新）

路径：`auto/state/panel/data.js`

这是一个 JS 文件，供 `auto/state/panel/index.html` 监控面板加载。用户可以在浏览器中打开面板实时观测运行状态。

**每轮结束时**，在持有 `state.lock` 期间，同时更新此文件。步骤：

1. 读取 `auto/state/panel/data.js` 全文
2. 提取 `window.PANEL_DATA = ` 和末尾 `;` 之间的 JSON
3. 解析为对象，按本轮结果更新对应字段
4. 写回：`window.PANEL_DATA = <JSON, 2空格缩进>;\n`

需要更新的字段：

```text
lastUpdated        → 当前 ISO 时间
startTime          → 仅第 1 轮设置（如果为 null）

stats.totalRounds  += 1
stats.totalFixes   += (本轮有修复 ? 1 : 0)
stats.totalScouts  += (本轮是侦察轮 ? 1 : 0)
stats.totalConflicts += (本轮遇到锁冲突 ? 1 : 0)
stats.backlogOpen  → 从 issue-backlog.jsonl 实时统计
stats.backlogClaimed → 同上
stats.backlogFixed → 同上

agents[]           → 找到自己的 agentId 条目（没有就 push 新条目）:
  { id, iteration, status, direction, currentFile, lastAction, lastUpdated }
  status 取值: "fixing" | "scouting" | "scanning" | "waiting" | "idle"

directionStats[方向].rounds += 1
directionStats[方向].fixes  += (本轮有修复 ? 1 : 0)

typeStats[类型].count += 1   （仅有修复时）

recentFixes[]      → 有修复时 push（只保留最近 50 条）:
  { time, agentId, iteration, priority, type, summary, files, userBenefit }

backlog[]          → 从 issue-backlog.jsonl 同步最近 50 条

timeline[]         → push 本轮事件（只保留最近 200 条）:
  { time, agentId, type, event, detail }
  type: "fix" | "scout" | "lock" | "claim" | "release" | "conflict" | "skip"
  event: 简短动作描述
  detail: 一句话补充
```

**注意：** 此文件的更新和 fix-log、coverage-map 的更新在同一次 `state.lock` 持有期间完成，不需要额外加锁。

### 提交规则

提交可选。若提交，必须拿 `git.lock`，只 stage 本 Agent 修改的文件，禁止 `git add .`。并行环境中默认可以跳过提交并说明原因。
