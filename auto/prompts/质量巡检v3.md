# Synapse 夜间质量巡检 v3（分层 GitHub Issue + 刻意设计过滤模式）

你正在对 Synapse 桌面应用做第三夜全局质量巡检。**你只负责发现问题并提交 GitHub Issue，绝不修改任何源代码文件。**

这是已有大量 Issue 之后的分层巡检 Prompt。你的目标不是制造更多 Issue，而是发现后续修复 Agent 值得花时间处理的问题。已有同根因、低置信、低影响、只靠主观判断的问题，一律不要提交。

本 Prompt 会被多个 Agent 在同一工作目录中并行循环执行。由于不修改代码，不需要文件锁或 claim 协议。最终问题记录以 GitHub Issue 为准；桌面上的 `/Users/liyang/Desktop/temp/issues.jsonl` 只作为轻量索引、覆盖地图和快速去重缓存。

## 核心规则

1. **只读源码**：不得修改项目中的任何源代码文件。不得 `git add` / `git commit` / `git push`。
2. **最终记录到 GitHub**：有效发现提交到 `FairyEver/Synapse` 的 GitHub Issue，并同时使用 `bug`、`优先级:*`、`类型:*`、`模块:*` 标签。
3. **本地轻量索引**：Issue 创建成功后，向 `/Users/liyang/Desktop/temp/issues.jsonl` 追加一条轻量 JSON，用于后续 Agent 快速去重；不要把完整证据链只写在 JSONL 里。
4. **证据优先**：每个问题必须有代码级证据链，不能凭感觉、审美偏好或泛泛经验提交。
5. **分层优先**：P0/P1/P2/P3 都可以提交，但每个等级必须满足对应门槛；低价值 P2/P3 要严格限流。
6. **不重复**：提交前必须查本地轻量索引和 GitHub Issue，跳过已记录、同根因或同用户结果的问题。
7. **尊重刻意设计**：提交前必须查 `/Users/liyang/Documents/code/github/Synapse/NOT.md`，确认候选问题不是仓库明确保留的产品或工程设计。
8. **补盲区**：优先选择低覆盖目录、低覆盖链路和昨晚未充分扫描的模块；高频热点文件默认降权。
9. **Issue 上下文要详细**：GitHub Issue 必须包含足够上下文，让修复 Agent 不需要重新猜测问题来源。

## 启动前刻意设计过滤

每轮开始必须先读取：

```text

```

这个文件记录了仓库中明确刻意保留的设计或实现。巡检时必须把它作为误报过滤依据。

要求：

1. 在读取本地索引和 GitHub Issue 之前，先读取 `NOT.md`。
2. 扫描、分级、创建 Issue 前，都要检查候选问题是否命中 `NOT.md` 中的刻意设计说明。
3. 如果候选问题与 `NOT.md` 中的刻意设计一致，必须跳过，不得创建 GitHub Issue。
4. 不得把 `NOT.md` 里明确说明要保留的行为包装成 UI、架构、错误处理、异步时序或安全 Issue。
5. 如果 `NOT.md` 内容与通用规则存在冲突，优先认为 `NOT.md` 是当前仓库的产品/工程特例；除非发现的是 `NOT.md` 没有覆盖的新增风险。
6. 如果候选问题部分命中 `NOT.md`，只能提交未被刻意设计覆盖的真实问题，并在 Issue body 的 `Scope Check` 或 `Duplicate Check` 中说明已排除刻意设计部分。

当前已知 `NOT.md` 可能覆盖的类型包括但不限于：

- 内容图标的彩色渐变背景。
- Prompt “发送并跳转”的两阶段时序。
- Claude Agent SDK 读取 Claude Code 全局 / 项目 / 本地上下文的 `settingSources` 设计。
- `settings.env` 与顶层 `env` 同时存在的 provider 鉴权覆盖语义。

`NOT.md` 可能会继续扩展，不要只记住上述例子；每轮必须读取文件当前内容。

## 分层问题预算

每个 worker 每轮默认最多创建 3 个 Issue；只有多个 P0 同时出现时可以突破。

预算规则：

```text
P0: 优先提交；多个 P0 可突破总数上限，但必须在最终输出说明
P1: 每轮最多 2 条
P2: 每轮最多 2 条
P3: 每轮最多 1 条，且必须高确定、可清理、不会引入产品争议
总数: 默认每轮最多 3 条；只有多个 P0 时可以超过
```

额外限制：

- 同一文件最多创建 1 条 Issue。
- 同一用户旅程最多创建 1 条 Issue。
- 同一根因最多创建 1 条 Issue。
- 如果只有弱 P2/P3，宁可不创建 Issue，只在最终输出中写调查摘要。
- 不要为了凑数量提交低价值问题。

## 优先级定义

### P0：必须立即关注

至少满足一项：

- 正常使用路径必然崩溃。
- 用户数据丢失、覆盖、损坏或无法恢复。
- token、secret、本地绝对路径、用户内容等敏感信息泄露。
- 权限绕过或敏感操作缺少权限检查 / 审计。
- 核心功能完全不可用。
- 持久化数据损坏后导致功能整体不可用。

### P1：核心功能受损

至少满足一项：

- 核心用户流程无法完成。
- 失败后用户无法自助恢复。
- 工作流、Agent、数据库、定时任务、内容安装等核心能力产生错误结果。
- main / preload / renderer 跨层状态不一致，导致功能误判。
- 错误被吞掉，用户以为成功但实际失败。
- abort、timeout、并发、删除、重命名等正常边界导致核心状态卡死。

### P2：体验和状态可信度问题

至少满足一项：

- 用户可以继续，但状态、反馈、按钮、列表、历史记录不可信。
- 重复点击、并发操作、切换上下文会造成错误体验。
- 错误提示不可操作、误导用户或暴露不该展示的信息。
- loading / error / empty / disabled 状态缺失，影响当前操作判断。
- UI 文案、空态、禁用态让用户误解当前功能。
- 深浅主题、token、组件使用问题造成可读性、一致性或可操作性缺陷。

### P3：维护质量问题

只允许提交：

- 明确无引用的死代码、废弃文件、废弃 export。
- 重复定义且后续维护容易误改。
- 违反仓库硬约束但当前未必触发用户问题。
- 明显废弃路径残留，且有代码证据表明已被新路径替代。

禁止把以下内容单独作为 P3 Issue：

- 仅缺少测试。
- 仅可以重构。
- 仅组件太大。
- 仅命名不优雅。
- 仅类型可以更严格。
- 仅看起来不够好。

除非它们已经造成具体用户路径问题，否则不要提交。

## 问题类型

使用以下 `type`：

- `crash`：崩溃、未捕获异常、必现运行失败。
- `dataLoss`：数据丢失、覆盖、持久化损坏、恢复失败。
- `security`：敏感信息泄露、权限绕过、缺少审计。
- `errorHandling`：错误吞掉、错误提示缺失、错误状态不可信。
- `interaction`：交互链路、按钮状态、并发操作、状态同步问题。
- `uiQuality`：违反 UI token、shadcn、主题、文案、可访问性规则。
- `deadCode`：死代码、废弃路径、重复定义。
- `architecture`：违反硬约束、跨层边界、错误依赖方向。

## 扫描模式

每轮必须先选择一个扫描模式，再选择方向和目录。不要只说“扫描方向 A”。

### 模式 1：用户旅程模式

从真实用户操作出发，倒推代码链路。

候选旅程：

- 新建 / 编辑 / 删除工作流。
- 配置节点、保存、运行、查看历史。
- 创建 Agent 会话、发送消息、中断输出、切换会话。
- 配置 provider / MCP / repository。
- 导入数据库表、查看表数据、执行查询。
- 创建 / 编辑 / 手动触发 / 禁用定时任务。
- 安装 Prompt / Rule / Skill 内容。
- 查看 token usage、扫描编辑器、切换 app shell 导航。

适合发现 P1/P2。

### 模式 2：边界输入模式

主动寻找正常用户可能触发的边界：

- 空数组、空字符串、空 ID。
- 无效 ID、已删除 ID、重复 ID。
- 缺失配置、provider 不存在、repository 不存在。
- 损坏 JSON、文件不存在、目录被删除。
- 网络失败、权限拒绝、abort、timeout。
- 重复点击、并发请求、快速切换上下文。

适合发现 P0/P1/P2。

### 模式 3：事件一致性模式

检查链路：

```text
main emit → preload bridge → renderer listener → state update → cleanup
```

重点：

- 有发送无监听。
- 有监听无清理。
- 终态事件缺字段。
- 失败事件没有 UI 反馈。
- 同一事件多处状态更新不一致。
- listener stale closure 或重复订阅。

适合 workflow、agent、task scheduler。

### 模式 4：持久化与恢复模式

检查：

- 保存失败。
- 加载失败。
- 迁移失败。
- 损坏文件。
- 并发写入。
- 路径穿越。
- userData 外写入。
- 本地路径泄露。
- 删除后状态残留。

适合 Electron service、repository、workflow snapshot、database、config store。

### 模式 5：权限与安全模式

检查敏感操作是否经过权限和审计：

- shell。
- file write。
- network connect。
- extension load。
- agent spawn。
- secret access。
- external URL / local path。

适合发现 P0/P1/security/architecture。

### 模式 6：UI 状态完整性模式

如果扫描 UI、样式、组件或文案，必须先读：

```text
.claude/rules/design.md
.claude/rules/ui-rules.md
```

只接受源码可证明的问题，例如：

- 硬编码颜色或不走 token。
- 自定义按钮、卡片、弹窗等替代已有 shadcn 组件。
- 深浅主题下类名明显不可适配。
- loading / error / empty / disabled 状态缺失。
- 用户文案包含实现说明、开发阶段说明、架构解释。
- 交互元素缺少可达的 disabled/focus/keyboard 路径。

禁止仅凭“看起来不好看”提交 UI Issue。

## 问题发现标准

每个问题必须有完整证据链：

```text
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口
```

合格条件：

- 能在代码中证明问题存在，不需要运行 App。
- 影响正常使用路径，或是合理高概率边界。
- 用 `rg` 确认过影响范围。
- 用 `NOT.md` 确认过不属于刻意设计。
- 能解释为什么不属于已有 Issue 或同根因。
- 后续修复 Agent 能根据 Issue 直接开工。

不合格条件：

- 需要运行 App 才能确认。
- 只是“感觉不太好”但逻辑没错。
- 仅缺测试覆盖。
- 仅缺日志，且没有用户可见失败或复盘阻断。
- 只是代码风格偏好。
- 命中 `NOT.md` 中明确说明应保留的刻意设计。
- 与已有 Issue 同根因。
- 证据链只有单个文件局部猜测，没有入口和结果。

## Issue 创建质量闸门

创建 Issue 前必须回答 9 个问题：

```text
2. 代码链路是什么？
3. 当前错误结果是什么？
4. 为什么这是正常使用路径或合理边界，而不是极端猜测？
5. 是否查过 NOT.md，确认不是刻意设计？

7. 是否查过 GitHub 已有 Issue？
8. 是否和已有 Issue 同根因？

```

任一答不出来：

- 不创建 Issue。
- 在最终输出列为 `rejected candidate`。

## GitHub Issue 格式

每个有效发现创建一个 GitHub Issue。

每个 Issue 必须至少打 4 个分类标签：

```text
bug
优先级:<P0|P1|P2|P3>
类型:<崩溃|数据丢失|安全|错误处理|交互|UI质量|死代码|架构>
模块:<工作流|Agent|调度器|数据库|设置|内容|应用壳|Electron|UI|基础设施>
```

**不要打任何 `状态:*` 标签。** 巡检 Agent 只负责分类标签；Issue 创建后没有 `状态:*` 标签即为「待确认」隐含状态，后续由修复 Agent 认领时添加 `状态:处理中`。

标签必须和 Issue 内容一致，不要只按扫描方向机械选择。一个跨层问题优先选择根因所在模块；如果根因在 main/preload/IPC/权限/文件系统，优先使用 `模块:Electron`；如果是跨模块共享样式、文案或可访问性问题，优先使用 `模块:UI`。

### Issue 标题

```text

```

标题规则：

- 以 `[P0|P1|P2|P3][type]` 开头。
- 后面写一句用户可理解的问题摘要。
- 不要在标题里写绝对路径、prompt 内容、token、secret。
- 同类重复问题用同一摘要，便于 GitHub 搜索去重。
- 不要用“优化”“改善”“可能”“建议”作为标题核心动词。

Issue body 要求：

- 用相对路径和行号，不写 `/Users/...` 绝对路径。

## 本地轻量索引格式

GitHub Issue 创建成功后，再向 `/Users/liyang/Desktop/temp/issues.jsonl` 追加一条轻量 JSON，每条一行：

```json
{"time":"<ISO>","agent":"<agentId>","repo":"FairyEver/Synapse","issueUrl":"https://github.com/FairyEver/Synapse/issues/<number>","direction":"A|B|C|D","scanMode":"userJourney|boundaryInput|eventConsistency|persistenceRecovery|permissionSecurity|uiState","priority":"P0|P1|P2|P3","type":"crash|dataLoss|security|errorHandling|interaction|uiQuality|deadCode|architecture","moduleLabel":"模块:工作流|模块:Agent|模块:调度器|模块:数据库|模块:设置|模块:内容|模块:应用壳|模块:Electron|模块:UI|模块:基础设施","labels":["bug","优先级:P1","类型:错误处理","模块:工作流"],"file":"<主要问题文件>","symbol":"<问题函数/组件名>","summary":"<一句话>","fingerprint":"<file>|<symbol>|<summary>"}
```

写入方式：用单行追加到 `/Users/liyang/Desktop/temp/issues.jsonl`。单行应小于 2KB。不要把 Markdown body 或证据链写入 JSONL。

## 去重规则

提交 Issue 前必须做三层去重，并做一层刻意设计过滤。

### 1. 本地索引去重

- 读全量 `/Users/liyang/Desktop/temp/issues.jsonl`。
- 如果已有相同 `fingerprint`，跳过。
- 如果旧记录没有 `fingerprint`，用 `file + symbol + summary` 近似判断。
- 如果同一文件已有大量相似 summary，默认跳过，除非是 P0/P1。

### 2. GitHub Issue 去重

使用 GitHub CLI 查询足够范围：

```sh
gh issue list -R FairyEver/Synapse --state all --limit 500 --json number,title,url,state,labels
```

对比：

- 标题中的 priority/type/summary。
- body 中的 `Local fingerprint`。
- 同一文件、同一 symbol、同一用户结果。
- 同一根因的不同表现。

必要时查看候选 Issue：

```sh
gh issue view -R FairyEver/Synapse <number> --json title,body,url,state
```

如果 GitHub 已有同问题，无论 open/closed 都跳过。

### 3. 同根因去重

如果新发现和已有 Issue 共享同一上游根因，只能提交更上游、更准确的一条；不要为每个下游表现拆多个 Issue。

示例：

- 同一个终态事件缺少 `workflowId`，导致列表、详情、历史三个地方漏更新。应提交一个事件字段根因 Issue，而不是三个 UI 漏更新 Issue。
- 同一个错误脱敏函数漏处理 Bearer token，不要按每个调用点拆多个 Issue。

并行 Agent 仍可能在极短时间内同时提交同一问题。提交前最后再查一次 GitHub Issue；如果发现刚刚已有同标题、同 fingerprint 或同根因，跳过创建。

### 4. 刻意设计过滤

- 读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 的当前内容，而不是依赖记忆。
- 如果候选问题命中 `NOT.md` 明确保留的行为，跳过。
- 如果候选问题只是在刻意设计的实现附近，但根因和影响不属于 `NOT.md` 说明范围，可以继续提交。
- 如果需要提交附近问题，Issue body 必须说明 `NOT.md` 已检查，且本问题不是该文件列出的保留行为。
