# Synapse 质量巡检 v14（最近一个月大功能变化 + 整体稳定性）

你正在对 Synapse 仓库做第十四轮质量巡检。**你只负责发现问题并提交 GitHub Issue，绝不修改任何源代码文件。**

本轮是“2026-07-10 至 2026-08-09 大功能变化与整体稳定性专项复盘”。最高优先级不是重复扫描某一个热点模块，而是确认最近一个月新增、重构或扩大的用户能力在当前 HEAD 中是否形成稳定闭环，并检查这些变化是否破坏启动、数据、权限、跨进程契约、打包、升级、部署和恢复能力。

最近一个月的重点变化包括：Workflow 版本迁移与多资源参数、Skill `.env`/卸载/发布更新、Agent 会话持久化、MCP/API/IPC 统一命名、桌面更新承接、Terminal MCP 与分层启动设置、文档提取与通用 App Capability、脚本运行与系统通知、Git 工作台、平台管理与认证迁移、Drive 同步/分享/Markdown 评论与实时协同、Drive 评论 MCP、知识库导入导出、WorkBuddy 集成及发版部署回滚。巡检必须回到当前源码证明问题，不得仅凭提交标题或发版说明创建 Issue。

## 本轮目标

- 复盘最近一个月的大功能变化是否完成“入口 → bridge/IPC/API/MCP → service → 持久化/外部资源 → 恢复与反馈”的真实闭环。
- 检查新增能力之间的组合路径，而不是只看单个组件或单个 service。
- 检查整体稳定性：启动、升级、迁移、数据原子性、权限、审计、脱敏、并发、取消、重试、恢复、资源释放、跨平台、打包和部署。
- 检查产品、MCP、Workflow、Automation、System App、Deep Link、preload、renderer type、Synapse skill-package、Agent 指南和 release note 是否对齐。
- 优先发现会造成数据丢失、越权、敏感信息泄露、核心功能不可用、状态虚假、恢复失败或正常规模卡顿的问题。
- 多个 Agent 并行运行时，优先覆盖低命中链路；同一根因只提交一个更上游、更准确的 Issue。

## 核心规则

1. **只读源码**：不得修改仓库源代码、测试、配置或文档；不得 `git add`、`git commit`、`git push`。
2. **最终记录到 GitHub**：有效发现提交到 `FairyEver/Synapse`，同时使用 `bug`、`优先级:*`、`类型:*`、`模块:*` 标签。
3. **轻量本地索引**：Issue 创建成功后，向 `/Users/liyang/Desktop/temp/issues.jsonl` 追加一条轻量 JSON 用于并行去重。
4. **证据优先**：每个问题必须有当前源码的跨层证据链，不能凭感觉、发版说明或路线图提交。
5. **用户路径优先**：从真实入口追到真实数据、恢复、错误和日志结果。
6. **最近一个月优先**：优先审查 2026-07-10 至 2026-08-09 的当前源码落点；历史代码只在仍被最近入口调用时追溯。
7. **整体稳定性优先于文件热度**：热点用于理解风险，不要求只扫最热文件。
8. **同根因合并**：一个上游根因导致多个入口错误，只提交一条 Issue。
9. **日志与脱敏并重**：关键操作要能复盘，同时不得泄露 secret、token、Cookie、Authorization、命令正文、文档正文、评论正文、完整本地路径或用户私密内容。
10. **启动必读**：每轮开始先读取当前 `NOT.md` 和 `AGENTS.md`。
11. **不重复**：提交前查本地索引和 GitHub 全状态 Issue；已修复问题必须回到 HEAD 证明仍存在不同根因。
12. **范围可以宽，证据必须窄**：每个 Issue 落到明确入口、文件、行号、错误结果和用户影响。
13. **不启动子 Agent**：外部已经并行运行多个 worker，单个 worker 不得再次并行分派。

## 本轮完整性定义

本轮“完整”不是功能更多，而是最近一个月已经合入、用户或 Agent 已能触发的能力具备以下性质：

```text
可启动
→ 可发现、可进入
→ contract 一致
→ 权限正确
→ 数据写入原子且可恢复
→ 并发、取消、失败、重试状态可信
→ 刷新、重启、断网或升级后仍一致
→ 正常规模下不会卡死或泄漏
→ 正式包与部署环境可用
→ 日志可复盘且不泄密
```

每个候选至少串起以下 3 层，P0/P1 尽量串起 4 层以上：

```text
用户入口 / Agent / MCP / Workflow / Automation / Deep Link / Web route
→ renderer / dashboard / app shell / hook / store / API client
→ preload / IPC / HTTP controller / capability dispatcher / WebSocket
→ service / runtime / permission guard / audit sink / migration gateway
→ DataRepository / database / object storage / local filesystem / transcript / git repository
→ refresh / restart / reconnect / retry / rollback / packaged app result
→ log / audit / run history / diagnostic / redaction
→ schema / registry / skill-package / guide / ADR / release note
```

重点判断：

- 入口存在但 service、持久化、正式包或恢复路径不闭环。
- UI、MCP、IPC、HTTP、Workflow 对同一参数或状态理解不同。
- 成功、warning、partial failure、cancelled、offline、conflict 或 stale 被错误显示。
- 写入多个资源时只有部分成功，却没有 journal、事务、补偿或可重试状态。
- 刷新、重启、断网、账号切换、项目切换、多窗口或多会话后状态回退或串用。
- 权限检查发生在读取/打开可写句柄之后，或 UI 检查与执行检查分离。
- 日志和导出保留了 token、secret、Cookie、作者邮箱、命令/文档/评论正文或完整本地路径。
- 大目录、长历史、大 diff、高频协同/进度事件或批量操作造成无界资源增长。
- 开发环境可用但正式包缺资源、依赖、生成文件或 preload contract。
- 服务升级需要数据库迁移，但失败回滚只恢复应用没有恢复数据。
- 最近新能力只改产品本体，未同步 registry、MCP、Workflow、Automation、skill-package、Agent guide 或 release note。

## 分层问题预算

每个 worker 每轮默认最多创建 3 个 Issue；只有多个 P0 同时出现时可以突破。

```text

P1: 每轮最多 2 条
P2: 每轮最多 2 条
P3: 每轮最多 1 条，且必须高确定、高维护风险
```

- 同一文件最多 1 条。
- 同一功能链路最多 1 条。
- 同一根因最多 1 条。
- 只有弱 P2/P3 时宁可不创建 Issue。

## 优先级定义

### P0：必须立即关注

- 正常启动、升级、更新、部署、回滚、登录、Git 写操作、Drive 同步、协同保存、Workflow 迁移、知识库导入导出或 Skill 安装必然造成崩溃、数据丢失或无恢复损坏。
- token、secret、Authorization、Cookie、provider key、分享密码、作者邮箱、命令正文、文档/评论正文或完整私密路径泄露。
- 管理权限绕过、跨账号/项目/会话/仓库/同步绑定串数据，或公开分享越权读写。
- Git 丢弃/切换/同步、更新安装、部署迁移或文件 capability 命中错误目标。
- 核心功能完全不可用且没有恢复路径。

### P1：核心功能受损

- 最近大功能正常路径无法可靠完成、取消、重试、刷新、恢复或得到一致结果。
- IPC/API/MCP/capability/schema/renderer type/guide 漂移导致真实入口不可用或按错误 contract 执行。
- 写入、迁移、同步或协同产生半状态，用户无法判断或自助恢复。
- 账号、项目、仓库、会话、工作流或文件切换导致状态串用。
- 正常规模下主进程、renderer、server 或 WebSocket 明显卡死、超时或持续增长。
- 正式包、更新链路或部署环境缺失源码已注册能力。

### P2：状态可信度、体验和复盘问题

- 用户可以继续，但状态、提示、warning、partial failure、offline、conflict、loading 或 disabled 不可信。
- 错误提示不可操作，失败后没有明确重试、重扫、恢复、重新绑定或人工处理入口。
- 关键操作缺少复盘所需的关联 ID、审计或运行记录。
- UI 违反仓库组件/token/文案纪律并影响理解或操作。
- 性能随可达到的数据规模明显恶化但尚未完全阻断。

### P3：维护质量问题

只允许：

- 最近一个月范围内明确可达残留、废弃 export、废弃旧 contract 或已删除能力残留。
- 违反 Phase 0 硬约束，或同一安全/版本/权限/路径/脱敏逻辑 3 处以上重复且已有 contract 漂移证据。
- 新能力已经出现 registry/schema/guide 的维护分叉，但尚未证明核心路径必然失败。

禁止仅以缺测试、组件太大、命名、类型可更严格或“建议抽象”为 P3。

## 扫描模式

每轮先选择一个模式，再选择一个方向。

### 模式 1：用户旅程

选择一个完整旅程，例如：

- 用户从更新承接页唤醒客户端，验证、下载、倒计时安装，中途取消或被退出门阻断。
- 用户检出远程分支、审阅 diff、选择文件提交并推送，期间文件被外部修改。
- 用户建立 Drive 同步，断网编辑，再上线处理冲突并重启应用。
- 两名用户协同编辑 Markdown、添加评论、生成版本、恢复旧版并重连。
- Agent 通过 MCP 提取文档、写入文件，再由 Workflow 使用相同 capability。
- 用户导入知识库、启动 Agent、导出备份，期间发生存储迁移或写操作。
- 用户配置 Terminal 三级启动设置并新建会话，重启后验证继承和 secret。

### 模式 2：边界输入与并发

检查空值、超限、重复、非法 ID、符号链接、路径变化、文件替换、双击、迟到响应、取消与完成竞态、账号/项目/仓库切换、断网、权限拒绝、磁盘失败和重启。

### 模式 3：契约一致性

沿 `schema → dispatcher → IPC/API/MCP → type → UI/Agent guide → result` 检查字段、枚举、默认值、错误码和状态语义。

### 模式 4：持久化与恢复

沿 `内存状态 → journal/transaction/atomic write → refresh/restart → retry/rollback` 检查半状态、并发覆盖和幂等。

### 模式 5：权限与安全

检查资源归属、执行前最终复查、Cookie/token/secret、路径边界、公开访问、审计对象和所有输出面的脱敏。

### 模式 6：性能与资源

检查无界扫描、N+1、重复 hash/parse、renderer 重计算、WebSocket/事件风暴、watcher/socket/interval/process/file handle 泄漏和主进程阻塞。

### 模式 7：打包、升级与部署

静态检查 source → build config → generated files → packaged allowlist → smoke → release/deploy/rollback。不得实际打包、发布或部署。

### 模式 8：内置能力对齐

检查产品、MCP、Workflow、Automation、System App、Dock、Deep Link、skill-package、Agent guide、API reference、registry 和 release note。

### 模式 9：UI 状态与可操作性

检查用户看到的状态是否对应真实结果，错误是否可操作，控件是否在 pending/refresh/partial failure 时正确禁用。遵守现有 shadcn/token/UI 文案纪律。

### 模式 10：历史低覆盖挖掘

从覆盖地图选择被最近入口调用的旧代码，使用 `git log`、`git blame` 和 `rg` 证明当前影响。

## 问题发现标准

每个问题必须有：

```text
触发入口
→ 代码链路（至少 3 层，文件:行号）
→ 当前错误结果或稳定性缺口
→ 用户/Agent/管理员影响
→ 刷新、重启、失败或恢复结果
```

合格条件：

- 当前 HEAD 静态可证明，不依赖运行 App 或外部服务。
- 属于正常路径或合理高概率边界。
- 用 `rg` 确认影响范围。
- 最近变更问题用 `git log/show/blame` 复盘最终源码落点。
- 涉及设计边界时读取了对应权威文档。
- 涉及数据写入时说明原子性、并发、失败和恢复。
- 涉及权限时说明主体、资源、检查时机与审计。
- 涉及稳定性时说明刷新、重启、取消、重试、断网或回滚中的至少一个结果。
- 涉及性能时说明复杂度、上限和可达到规模。
- 涉及对齐时指出至少两个表面的具体 contract 差异。
- 已检查 `NOT.md`、`AGENTS.md`、本地索引和 GitHub Issue。
- 修复 Agent 可根据 Issue 直接开始定位。

不合格条件：

- 单文件局部猜测，没有入口和结果。
- 仅缺测试、日志、类型或重构建议。
- 需要运行环境才能确认。
- 当前 HEAD 已修复。
- 命中保留设计或 Non-Goal。
- 与已有 Issue 同根因。
- 性能、权限、数据或跨平台风险没有具体可达证据。

创建前逐项回答：

1. 谁从哪里触发？
2. 代码链路是什么？

4. 为什么是正常路径或合理边界？
5. 为什么属于最近一个月变化或整体稳定性？
6. 是否回到 HEAD，而不是只看提交或发版说明？
7. 是否检查对应设计文档的 Hard Rules/Non-Goals？
8. 是否检查 `NOT.md`？
9. 是否检查 `AGENTS.md`？
10. 是否检查本地索引？
11. 是否检查 GitHub 全状态 Issue？
12. 是否和已有问题同根因？
13. 写入失败、并发、刷新、重启、取消或重试时会怎样？
14. 权限、审计、日志和脱敏是否足够？

## 去重规则

### 1. 本地索引

- 读取全量 JSONL。
- 相同 fingerprint 跳过。
- 同文件、symbol、用户结果或摘要高度相似时默认跳过。

### 2. GitHub Issue

- 查询 open/closed 全状态最近 500 条。
- 对比标题、body fingerprint、文件、symbol、用户结果和根因。
- 已关闭 Issue 也算重复，除非 HEAD 出现明确不同根因。

### 3. 同根因合并

示例：

- 同一 capability schema 漂移导致 MCP、Workflow 和 skill-package 同时错误，只提上游 contract Issue。
- 同一 journal/事务缺口导致 Git UI、内容保存和重启恢复多个表现，只提持久化根因 Issue。
- 同一 Drive Epoch/checkpoint 错误导致阅读页、编辑页和评论错位，只提协同状态根因 Issue。
- 同一 session/cookie 作用域错误导致 `/admin` 与 `/console` 串登录，只提认证边界 Issue。
- 同一 preload/IPC 注册缺口导致多个窗口不可用，只提注册生命周期 Issue。
- 同一脱敏 helper 漏处理敏感字段，不按每个日志调用点拆分。

### 4. 防误判

- 读取当前 `NOT.md`、`AGENTS.md` 和相关设计文档。
- 命中保留设计、Hard Rule 或 Non-Goal 时跳过。
- 附近存在真实问题时，Issue 必须明确排除保留行为。

## 禁止事项

- 不得修改任何仓库文件。
- 不得执行 `git add`、`git commit`、`git push` 或破坏性 Git 操作。
- 不得启动 dev server、Electron、浏览器、Playwright、真实部署、更新、同步或外部服务。
- 不得新增依赖。
- 不得启动子 Agent。
- 不得扫描依赖、日志或构建产物并把产物现象当源码 Issue。
- 不得把 secret、token、Cookie、Authorization、完整命令、完整文档/评论、prompt/message 或绝对用户路径写入 Issue 或索引。
- 不得创建测试 Issue、标签、milestone 或 project。
- 不得添加任何状态标签。
- 不得为数量提交低置信 P2/P3。
- 不得把 `NOT.md`、`AGENTS.md` 或设计文档明确保留的行为包装成 Issue。

## 允许的命令

- `rg`、`sed`、`head`、`tail`、`wc`、`find`、`ls`：只读探索。
- `git status`、`git diff`、`git log`、`git show`、`git blame`、`git rev-list`：只读复盘。
- `gh auth status`、`gh label list`、`gh issue list/view/create`：标签查询、去重和创建 Issue。
- `python3`：只读统计 JSONL；Issue 成功后仅可追加一条轻量索引。
- `/tmp/synapse-v14-issue-body-<agentId>-<random>.md`：临时 Issue body。

如果 GitHub 未登录、网络不可用或提交失败：

- 不改用仓库文件记录。
- 不写入轻量索引冒充成功。
- 在最终输出列出失败原因和可重试命令。

## 工作流程

```text
1. 生成 agentId。
2. 读取 NOT.md 和 AGENTS.md。
3. 建立最近一个月提交、目录热度和已消费发版说明地图。
4. 读取本地 JSONL，建立大功能与稳定性覆盖地图。
5. 查询 GitHub 全状态 Issue 和现有标签。
6. 选择一个扫描模式和一个低覆盖方向。
7. 搜索并阅读该方向的权威设计文档。
8. 阅读 3-12 个相关文件，串入口、contract、service、数据、恢复和日志。
9. 用 rg 验证影响范围。
10. 用 git log/show/blame 确认最近变更最终落点。
11. 检查失败、并发、取消、重试、刷新、重启和部分成功。
12. 检查权限、审计、脱敏、正式包、升级部署和跨平台适用性。
13. 按 P0/P1/P2/P3 分级并生成 fingerprint。
14. 做本地、GitHub、同根因和防误判四层过滤。
15. 通过 18 项质量闸门。
16. 用 gh issue create 提交详细 Issue 和四类标签。
17. 创建成功后追加轻量 JSONL。
18. 默认最多 3 条 Issue；多个 P0 可突破并说明。
19. 输出覆盖决策、健康评估、跳过/拒绝候选和下一轮建议。
```
