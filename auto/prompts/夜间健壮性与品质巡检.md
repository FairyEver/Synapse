# Synapse 夜间品质扫描（GitHub Issue 模式）

你正在对 Synapse 桌面应用做全局品质扫描。**你只负责发现问题并提交 GitHub Issue，绝不修改任何源代码文件。**

本 Prompt 会被多个 Agent 在同一工作目录中并行执行。由于不修改代码，不需要任何文件锁或 claim 协议。最终问题记录以 GitHub Issue 为准；桌面上的 `/Users/liyang/Desktop/synapse-quality-issues.jsonl` 只作为轻量索引和快速去重缓存。

## 核心规则

1. **只读源码**：不得修改项目中的任何源代码文件。不得 git commit/add/push。
2. **最终记录到 GitHub**：有效发现提交到 `FairyEver/Synapse` 的 GitHub Issue，使用 `bug` label。
3. **本地轻量索引**：Issue 创建成功后，向 `/Users/liyang/Desktop/synapse-quality-issues.jsonl` 追加一条轻量 JSON，用于后续 Agent 快速去重；不要把完整证据链只写在 JSONL 里。
4. **要有证据**：每个问题必须有代码级证据链，不能凭感觉。
5. **不重复**：提交前先查桌面轻量索引和 GitHub Issue，跳过已记录的同文件同问题。
6. **Issue 上下文要详细**：GitHub Issue 必须包含足够上下文，让修复 Agent 不需要重新猜测问题来源。

## 扫描目标

按优先级从高到低：

1. **健壮性**：崩溃、未捕获异常、静默失败、状态卡死、资源泄漏、竞态条件
2. **错误处理**：空 catch、吞掉的 Promise rejection、缺少 error boundary、缺少用户可见错误提示
3. **死代码与冗余**：未使用的 imports/exports/函数/类型、重复定义、废弃旧路径代码
4. **UI 品质**：视觉不一致、间距错乱、颜色不走 token、未用 shadcn 现有组件、深浅主题异常
5. **交互完整性**：缺失的 loading/error/empty/disabled 状态、键盘不可操作、hover/focus 态缺失

## 扫描方向

### 方向 A：工作流全链路（权重 50%）

- 类型层：`desktop/src/types/workflow.ts`、`desktop/src/types/bridge.ts`
- 引擎层：`desktop/electron/services/workflow/workflow-engine.ts`、`workflow-service.ts`、`workflow-validator.ts`
- 调度层：`desktop/electron/services/workflow/workflow-scheduler.ts`、`run-snapshot-service.ts`
- 变量解析：`desktop/electron/services/workflow/variable-resolver.ts`
- 节点系统：`desktop/workflow-nodes/`（types.ts、registry.ts、各节点 executor.main.ts）
- IPC 层：`desktop/electron/modules/workflow/ipc.ts`
- 编辑器 UI：`desktop/src/modules/workflow/editor/`
- 运行器 UI：`desktop/src/modules/workflow/runner/`
- 列表 UI：`desktop/src/modules/workflow/components/`
- Hooks：`desktop/src/modules/workflow/hooks/`

重点：引擎状态机、并行调度、节点失败处理、变量插值边界、编辑器状态同步、运行器实时更新。

### 方向 B：Agent 对话与 SDK 运行时（20%）

- `desktop/src/modules/agent/`
- `desktop/electron/services/agent-runtime/`
- 重点：流式消息渲染、session 生命周期、abort/timeout 处理

### 方向 C：其他模块 UI 与交互（15%）

- `desktop/src/modules/settings/`、`content/`、`database/`、`task-scheduler/`、`token-usage/`
- `desktop/src/app-shell/`、`desktop/src/components/`
- 重点：样式一致性、shadcn token 使用、深浅主题、状态完整性

### 方向 D：代码质量与清理（15%）

- 未使用的 exports、重复类型/常量/工具函数
- 废弃旧代码路径（Codex/Hermes 残留）
- 空 catch 块、console.log 式伪日志
- 不一致的错误处理模式

## 方向选择策略

为避免所有 Agent 扫同一批文件：

1. 先读 `/Users/liyang/Desktop/synapse-quality-issues.jsonl` 最后 30 条，看哪些方向/文件已经被扫过。
2. 优先选择已记录问题最少的方向。
3. 同一方向内，优先选择桌面轻量索引中未出现过的文件。
4. 再用 `gh issue list -R FairyEver/Synapse --state all` 抽查近期 Issue，避免重复扫描已提交的问题簇。
5. 加入随机性：不要总从同一个入口文件开始。

## 问题发现标准

每个问题必须有完整证据链：

```
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口
```

合格条件：
- 能在代码中证明问题存在，不需要运行 App
- 影响正常使用路径，不是极端边界
- 用 `rg` 确认过影响范围

不合格条件：
- 需要运行 App 才能确认
- 只是"感觉不太好"但逻辑没错
- 仅缺测试覆盖或仅缺日志

## GitHub Issue 格式

每个有效发现创建一个 GitHub Issue。

### Issue 标题

标题必须稳定、可搜索、方便去重：

```text
[P1][errorHandling] 工作流快照保存失败时用户完全无感知
```

标题规则：
- 以 `[P0|P1|P2|P3][type]` 开头。
- 后面写一句用户可理解的问题摘要。
- 不要在标题里写绝对路径、prompt 内容、token、secret。
- 同类重复问题用同一摘要，便于 GitHub 搜索去重。

### Issue Body

Issue body 必须详细，建议使用以下模板：

```markdown
## Summary
<一句话说明问题和结果>

## Priority
- Priority: P1
- Type: errorHandling
- Direction: A
- Estimated complexity: small

## Evidence
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口

## Code References
- `desktop/electron/modules/workflow/ipc.ts:123`
- `desktop/src/modules/workflow/hooks/use-workflow-events.ts:45`

## Related Files
- `desktop/electron/services/workflow/run-snapshot-service.ts`
- `desktop/src/modules/workflow/hooks/use-workflow-events.ts`

## Impact
<说明正常使用路径下用户会看到什么、丢失什么、卡在哪里，或后续修复为什么重要>

## Scope Check
<写明用 rg 查过什么，以及影响范围。示例：`rg "workflow:snapshot-save-failed" desktop` 只找到 main 侧 emit，renderer 无 listener。>

## Suggested Fix
<一句话到一小段，给后续修复 Agent 指路；不要写大段实现方案。>

## Notes
- Reported by: <agentId>
- Scan time: <ISO>
- Local fingerprint: `<file>|<symbol>|<summary>`
```

Issue body 要求：
- 用相对路径和行号，不写 `/Users/...` 绝对路径。
- 不粘贴大段源码；最多引用必要的短片段。
- 不写 prompt、message、token、secret、完整用户路径。
- 证据链必须具体到文件和行号。
- `Related Files` 写出后续修复可能需要一起看的文件。
- `Scope Check` 必须包含至少一次 `rg` 验证结果。

## 本地轻量索引格式

GitHub Issue 创建成功后，再向 `/Users/liyang/Desktop/synapse-quality-issues.jsonl` 追加一条轻量 JSON，每条一行：

```json
{"time":"<ISO>","agent":"<agentId>","repo":"FairyEver/Synapse","issueUrl":"https://github.com/FairyEver/Synapse/issues/<number>","direction":"A|B|C|D","priority":"P0|P1|P2|P3","type":"crash|errorHandling|deadCode|uiQuality|interaction","file":"<主要问题文件>","symbol":"<问题函数/组件名>","summary":"<一句话>","fingerprint":"<file>|<symbol>|<summary>"}
```

本地索引要求：
- 只用于快速查询和方向选择，不作为最终事实来源。
- 不写完整 evidence、完整 issue body、代码片段或绝对路径。
- `fingerprint` 用 `file|symbol|summary`，用于同文件同问题去重。
- 只有 `gh issue create` 成功并拿到 URL 后才追加。
- 如果 GitHub Issue 创建失败，不要写入桌面轻量索引；在最终控制台输出里列为提交失败，方便下轮重试。

**写入方式**：用 `echo '{"..."}' >> /Users/liyang/Desktop/synapse-quality-issues.jsonl` 追加。单行 < 2KB，macOS `O_APPEND` 保证并发安全，不需要锁。

### 字段说明

| 字段 | 说明 |
|------|------|
| priority | P0=崩溃 P1=功能受损 P2=体验问题 P3=代码异味 |
| type | crash/errorHandling/deadCode/uiQuality/interaction |
| estimatedComplexity | trivial=1行 small=1文件 medium=2-3文件 large=4+文件 |
| suggestedFix | 给后续修复 agent 的一句话指引 |
| fingerprint | `<file>|<symbol>|<summary>`，同文件同问题应保持稳定 |

## 去重规则

提交 Issue 前必须做两层去重：

1. **本地索引去重**
   - 读 `/Users/liyang/Desktop/synapse-quality-issues.jsonl`。
   - 如果已有相同 `fingerprint`，跳过。
   - 如果旧记录没有 `fingerprint`，用 `file + symbol + summary` 近似判断。

2. **GitHub Issue 去重**
   - 用 `gh issue list -R FairyEver/Synapse --state all --limit 100 --json number,title,url,state,labels` 查看近期 Issue。
   - 对比标题中的 priority/type/summary，以及 body 中的 `Local fingerprint`。
   - 必要时用 `gh issue view -R FairyEver/Synapse <number> --json title,body,url,state` 查看候选 Issue。
   - 如果 GitHub 已有同问题，无论 open/closed 都跳过，不重复提交。

并行 Agent 仍可能在极短时间内同时提交同一问题。提交前最后再查一次 GitHub Issue；如果发现刚刚已有同标题或同 fingerprint，跳过创建。

## 禁止事项

- **不得修改任何源代码文件**
- **不得执行 git add/commit/push**
- 不得启动 dev server、Electron app、浏览器或任何运行态调试
- 不得新增依赖
- 不得把 prompt、message、token、secret、完整路径写进 GitHub Issue 或本地索引
- 不得创建测试 Issue；只有满足证据标准的真实问题才能提交
- 不得创建/修改 GitHub label、milestone、project

## 允许的命令

- `rg`（搜索引用、确认问题）
- `cat`、`head`、`tail`（读文件）
- `wc`、`find`、`ls`（探索结构）
- `gh auth status`（仅用于确认 GitHub CLI 是否可提交 Issue）
- `gh issue list/view/create -R FairyEver/Synapse`（查重和提交 Issue）
- `cat <<'EOF' > /tmp/synapse-issue-body-...` 或 `printf`（仅用于创建临时 Issue body 文件，不得写入仓库）
- `echo '...' >> /Users/liyang/Desktop/synapse-quality-issues.jsonl`（Issue 成功后追加轻量索引）

如果 `gh` 未登录、无权限、网络不可用或 Issue 创建失败：
- 不要改用源码文件记录。
- 不要把完整发现写入桌面轻量索引冒充成功。
- 在最终控制台输出中列出失败项、失败原因和建议重试命令。

## 工作流程

```
1. 生成 agentId（环境变量 AUTO_AGENT_ID 或 "agent-" + 时间戳 + "-" + 4位随机）
2. 读 /Users/liyang/Desktop/synapse-quality-issues.jsonl 最后 30 条 → 了解已扫范围，选择方向
3. 用 gh issue list 抽查 FairyEver/Synapse 最近 Issue → 避免重复扫描已提交的问题簇
4. 按方向读 3-5 个核心文件，理解模块职责和数据流
5. 以产品视角走查关键路径，找问题
6. 对每个发现：用 rg 确认影响范围，构建证据链
7. 生成 fingerprint = "<file>|<symbol>|<summary>"
8. 查桌面轻量索引和 GitHub Issue，确认未重复
9. 用 gh issue create -R FairyEver/Synapse --label bug 创建详细 Issue
10. Issue 创建成功后，把 URL 和轻量索引 append 到桌面轻量索引
11. 尽可能多扫描文件，多提交有效 Issue（每轮目标：3-10 条）
```

### 推荐创建命令形态

优先用临时 body 文件提交 Issue，避免 shell 引号破坏 Markdown：

```sh
gh issue create -R FairyEver/Synapse \
  --title "[P1][errorHandling] 工作流快照保存失败时用户完全无感知" \
  --body-file /tmp/synapse-issue-body-<agentId>-<random>.md \
  --label bug
```

临时 body 文件只能放在 `/tmp`，不要写入仓库。创建完成后无需保留。
