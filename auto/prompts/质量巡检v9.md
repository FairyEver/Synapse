本轮是今晚运行的定向巡检。除本文件明确收窄的范围外，v8 的执行纪律保持不变：只读源码、证据优先、链路可用性优先、最近变更优先、查重后提交 GitHub Issue、同步写入桌面轻量索引。

## 本轮唯一检查范围

本轮只检查以下模块和链路中的隐藏 bug、死逻辑、边界情况、代码健壮性、状态可信度、错误恢复、权限安全、日志/审计/运行记录缺口：

- 管理后台用户可达链路：登录后从导航、列表、详情、筛选、分页、团队/权限/邀请/在线客户端等入口到真实结果的全部正确性。
- 管理后台无效操作：按钮、菜单、链接、表单、批量操作、复制、刷新、导出、查看详情等用户能触发但实际没有作用、状态不刷新、只改前端不落后端、或成功提示与真实结果不一致的问题。
- 工作流能力，尤其是新增的 Code X / Codex 节点：节点注册、面板配置、变量绑定、命令构造、执行器、产物、运行状态、取消/失败/重跑、结果展示和历史记录。
- 网盘能力：文件上传、文件夹上传、下载、压缩下载、预览、管理、重命名、移动、删除、分享、密码/过期访问、发布 page/site、公开访问、后台管理和路由跳转。
- 最近约两周内提交或当前工作区未提交的相关变更，重点找隐藏 bug、逻辑缺陷、链路断裂、契约漂移和只改一层导致的真实功能不可用。

严格排除：

- 知识库、备份、内容仓库、官网、普通 Agent 会话、模型供应商、Usage Analysis、数据库 Data Store、编辑器扫描、自动化、Webhook、客户端登录、WebSocket、发布打包等独立问题。
- 仅当上述排除模块直接参与本轮管理后台用户链路、工作流 Code X 或网盘链路，且缺陷会影响本轮范围时，才允许作为证据链的一部分附带检查；不得把它们作为独立 Issue。
- 不得因为 v8 曾覆盖登录注册、客户端状态、WebSocket、Webhook 或自动化，就继续扫描这些旧方向。

## 核心规则

1. **只读源码**：不得修改项目中的任何源代码文件。不得 `git add` / `git commit` / `git push`。
2. **最终记录到 GitHub**：有效发现提交到 `FairyEver/Synapse` 的 GitHub Issue，并同时使用 `bug`、`优先级:*`、`类型:*`、`模块:*` 标签。
3. **本地轻量索引**：Issue 创建成功后，向 `/Users/liyang/Desktop/temp/issues.jsonl` 追加一条轻量 JSON，用于后续 Agent 快速去重；不要把完整证据链只写在 JSONL 里。
4. **证据优先**：每个问题必须有代码级证据链，不能凭感觉、审美偏好、路线图或泛泛经验提交。
5. **链路可用性优先**：优先检查真实功能链路是否从入口到结果可靠闭环，而不是只看单个函数或单个页面。
6. **最近变更优先**：优先检查最近 14 天内变更过的管理后台用户链路、工作流 Code X / Codex 节点、工作流基础链路、网盘上传/下载/管理/分享/发布链路，以及当前工作区未提交的相关变更。
7. **日志补全优先**：如果本轮范围内的新功能涉及管理后台用户操作、工作流节点执行、Code X / Codex 命令或产物、网盘文件操作、分享、发布、公开访问或失败恢复，必须检查是否有足够日志支持追踪和复盘。
8. **启动必读优先**：每次开始必须阅读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 和 `/Users/liyang/Documents/code/github/Synapse/AGENTS.md` 当前内容，确认候选问题既不是保留设计，也没有误解仓库硬规则。
9. **不重复**：提交前必须查本地轻量索引和 GitHub Issue，跳过已记录、同根因或同用户结果的问题。
10. **Issue 上下文要详细**：GitHub Issue 必须包含足够上下文，让修复 Agent 不需要重新猜测问题来源。
11. **范围不漂移**：候选问题如果不能归入本轮三类重点链路，默认拒绝，不创建 Issue。

## 本轮完整性定义

本轮“完整性”不是泛泛要求功能更多，而是检查本轮三类重点功能链路是否可用、可追踪、可恢复。

每个候选链路至少从以下层级中选择 3 层以上连起来看：

```text
管理后台用户入口 / 工作流入口 / Code X 节点入口 / 网盘入口 / 分享发布公开入口
→ renderer 组件 / hook / API client / state store
→ route guard / window.synapse API / IPC module / capability dispatcher
→ Electron workflow service / workflow node executor / Server controller / service / guard
→ Prisma / DataRepository / Drive storage / workflow run repository / publication or share record
→ 真实结果 / 状态刷新 / 错误反馈 / disabled/loading/empty
→ 操作日志 / 审计日志 / 运行日志 / 错误日志
→ 测试或既有调用点
```

重点检查：

- 页面、按钮、菜单、表单或入口存在，但 API、IPC、服务端路由、工作流执行或网盘文件链路不能闭环。
- 前端调用了 API，但服务端路由、参数、返回结构、错误语义、权限语义不匹配。
- 用户管理、团队、权限、邀请、在线客户端、工作流定义、Code X 配置、网盘文件、分享、发布状态被错误缓存、误判或无法恢复。
- 管理后台存在用户能点击或提交但实际无效的入口：没有请求、请求参数错误、响应被忽略、状态不刷新、成功提示虚假、或后端没有对应实现。
- 工作流 Code X / Codex 节点的注册、面板配置、变量绑定、命令构造、执行器、产物、运行状态、取消/失败/重跑、历史展示链路断裂。
- 网盘上传、下载、压缩下载、预览、重命名、移动、删除、分享、密码/过期访问、发布 page/site、公开访问或后台管理链路断裂。
- 管理后台、工作流、Code X、网盘中的权限、团队隔离、用户隔离、token/password/shareId/publicationId 脱敏存在风险。
- 错误被吞掉、被泛化到无法定位，或 UI 展示成误导性成功。
- 新功能缺少必要日志，导致失败后无法知道用户做了什么、系统做了什么、哪一步失败。

禁止把以下内容单独作为完整性 Issue：

- 只是缺少一个“更方便”的快捷入口。
- 只是测试可以更多。
- 只是页面信息密度、布局或文案可以优化。
- 只是某个私有实现看起来不够优雅。
- 只是生成物没同步源码。
- 只是缺日志，但该操作没有管理后台用户操作、工作流执行、网盘文件、分享、发布、权限或复盘需求。
- 本轮范围外模块的独立问题。

每个 worker 每轮默认最多创建 3 个 Issue；只有多个 P0 同时出现时可以突破。

预算规则：

```text

P2: 每轮最多 2 条
```

- 同一功能链路最多创建 1 条 Issue。
- 同一根因最多创建 1 条 Issue。
- 如果只有弱 P2/P3，宁可不创建 Issue，只在最终输出中写调查摘要。
- 不要为了凑数量提交低价值问题。

## 优先级定义

### P0：必须立即关注

至少满足一项：

- 正常管理后台用户操作、工作流 Code X 节点运行或网盘上传/下载/分享/发布路径必然崩溃，或服务端 / Electron 启动失败。
- 用户、团队、邀请、权限、工作流定义、Code X 运行产物、网盘文件、分享、发布或运行历史丢失、覆盖、损坏或无法恢复。
- token、secret、邀请链接、Authorization、Cookie、用户内容、网盘文件内容、share password、shareId、publicationId、Code X 输入输出等敏感信息泄露。
- 管理权限绕过、团队隔离失效、用户隔离失效、网盘越权访问、分享/发布越权访问、Code X 敏感执行缺少权限检查。
- 核心用户管理、工作流 Code X、网盘文件操作、分享或发布功能完全不可用。
- 持久化数据损坏后导致相关模块整体不可用。

### P1：核心功能受损

至少满足一项：

- 管理员无法可靠查看、筛选、分页、编辑、禁用、授权用户，或用户/团队/权限/邀请状态与服务端不一致。
- 管理后台存在用户可触发但无实际效果的按钮、菜单、链接、表单、批量操作或刷新操作。
- 工作流无法可靠创建、编辑、保存、运行、取消、重跑、查看运行历史或展示节点结果。
- Code X / Codex 节点无法可靠添加、配置、保存、执行、取消、产生产物、记录输出或把错误反馈给 Runner。
- 网盘无法可靠上传、下载、压缩下载、预览、重命名、移动、删除、分享、取消分享、发布 page/site 或公开访问。
- 失败后用户无法自助恢复，且日志不足以定位。
- API / IPC / capability / renderer type / workflow node schema / drive DTO contract 不一致，导致功能误判。
- 错误被吞掉，用户以为成功但实际失败。
- 并发、删除、重命名、重复提交、过期邀请、切换团队、切换页面、多窗口、断网、上传失败、运行取消导致核心状态卡死。

### P2：体验、状态可信度和复盘问题

至少满足一项：

- 用户可以继续，但用户管理列表、权限状态、邀请状态、工作流运行历史、Code X 节点结果、网盘文件状态、分享或发布状态不可信。
- 重复点击、并发操作、切换团队、切换页面、关闭窗口、断网恢复会造成错误体验。
- 错误提示不可操作、误导用户或暴露不该展示的信息。
- loading / error / empty / disabled 状态缺失，影响当前操作判断。
- 新功能缺少关键日志，导致常见失败无法复盘或无法判断是否执行成功。
- UI 文案、空态、禁用态让用户误解当前用户、权限、工作流、Code X、网盘、分享或发布状态。
- 深浅主题、token、组件使用问题造成可读性、一致性或可操作性缺陷，且影响本轮链路。

### P3：维护质量问题

只允许提交：

- 本轮范围内明确无引用的死代码、废弃文件、废弃 export。
- 本轮范围内重复定义且后续维护容易误改。
- 违反仓库硬约束但当前未必触发用户问题。
- 明显废弃路径残留，且有代码证据表明已被新路径替代。
- 管理后台用户链路、工作流、Code X 或网盘存在明确重复 contract 常量或状态定义，且已经出现不一致风险。

禁止把以下内容单独作为 P3 Issue：

- 仅缺测试。
- 仅可以重构。
- 仅组件太大。
- 仅命名不优雅。
- 仅类型可以更严格。
- 仅日志格式可以更漂亮。

除非它们已经造成具体用户路径问题，否则不要提交。

## 问题类型

使用以下 `type`：

- `crash`：崩溃、未捕获异常、必现运行失败。
- `dataLoss`：数据丢失、覆盖、持久化损坏、恢复失败。
- `security`：敏感信息泄露、权限绕过、缺少鉴权或审计。
- `errorHandling`：错误吞掉、错误提示缺失、错误状态不可信。
- `interaction`：交互链路、按钮状态、并发操作、状态同步问题。
- `uiQuality`：违反 UI token、shadcn、主题、文案、可访问性规则。
- `logging`：新功能或关键操作缺少必要日志、审计、运行记录或复盘上下文。
- `deadCode`：死代码、废弃路径、重复定义。
- `architecture`：违反硬约束、跨层边界、错误依赖方向。

## 扫描模式

每轮必须先选择一个扫描模式，再选择方向和目录。不要只说“扫描方向 A”。

### 模式 1：管理后台用户旅程模式

从真实用户操作出发，倒推代码链路。

候选旅程：

- 管理员进入用户列表，分页、搜索、筛选后打开用户详情或在线客户端抽屉。
- 管理员调整用户模块权限，刷新页面后服务端状态仍一致。
- 管理员创建邀请、撤销邀请、复制邀请链接，并确认列表和服务端状态一致。
- 切换团队后查看用户、邀请、权限，确认没有串团队数据。
- 普通用户访问管理后台用户/团队/邀请 API 或页面时被正确拦截。

适合发现 P0/P1/P2。

### 模式 2：无效操作链路模式

候选旅程：

- 从管理后台导航逐个追踪可点击入口，确认每个入口都有页面、请求和结果。
- 对列表行操作、批量操作、菜单项、复制、刷新、筛选、弹窗提交逐个追踪到真实 API 或状态变化。
- 检查按钮 disabled/loading/error 是否与请求状态一致，避免重复点击或失败后显示成功。
- 检查“查看详情”“管理”“发布”“分享”等入口是否只是占位 UI 或死路由。
- 检查后端路由已删除或 contract 改名后，前端是否还保留旧入口。

适合发现 P1/P2/interaction/deadCode。

### 模式 3：Code X 节点旅程模式

候选旅程：

- 在工作流编辑器添加 Code X / Codex 节点，打开配置面板并保存。
- 配置 provider、model、sandbox、approval、prompt/command、变量绑定和输出引用。
- 运行包含 Code X 的工作流，确认执行器、取消、失败、重跑和 Runner 状态一致。
- 检查 Code X 产物、stdout/stderr、错误、token 或路径是否脱敏后进入运行快照和历史展示。
- 下游节点读取 Code X 输出，确认字段名和 schema 一致。

适合发现 P0/P1/P2。

### 模式 4：工作流基础旅程模式

候选旅程：

- 新建工作流，添加多个节点和边，保存后重新打开。
- 修改参数、变量绑定和节点配置，确认 validate/save/run 使用同一 contract。
- 删除节点或边后确认 DAG 校验、布局和运行器不引用残留节点。
- 运行、取消、重跑、查看历史和节点结果，确认运行快照可复盘且不泄露敏感内容。
- MCP/capability 工具修改工作流时，确认 get -> mutate -> validate -> save 路径完整。

适合发现 P0/P1/P2。

### 模式 5：网盘文件旅程模式

候选旅程：

- 用户在网盘上传单文件或文件夹，等待完成后刷新列表。
- 用户预览文本/图片/Markdown/HTML source，无法预览时下载路径仍可用。
- 用户下载文件、下载文件夹 zip，并检查 URL 构造和权限。
- 用户重命名、移动、删除文件或文件夹，刷新或切换路径后结果一致。

适合发现 P0/P1/P2/security/logging。

### 模式 6：网盘分享发布旅程模式

候选旅程：

- 用户为文件或文件夹创建分享链接，设置密码或过期时间，然后用公开路由访问。
- 分享页浏览子目录、下载文件、压缩下载文件夹，确认权限和 URL 一致。
- 用户取消分享或分享过期后，公开访问必须失效。
- 用户发布 page/site，确认发布状态、公开访问、资源路由和禁用逻辑闭环。
- 管理员从云盘管理入口查看或管理网盘内容，确认权限和状态刷新一致。

适合发现 P0/P1/P2。

### 模式 7：边界输入模式

主动寻找正常用户可能触发的边界：

- 空字符串、空 ID、无效 ID、已删除 ID、重复 ID。
- 过期邀请、已使用邀请、跨团队资源、禁用用户。
- 缺失 token、过期 token、错误 token、普通用户访问管理员 API 或网盘管理 API。
- Code X 配置为空、变量绑定缺失、provider 缺失、sandbox/approval 非法、命令为空、执行中取消或重复运行。
- 工作流节点 ID 重复、边引用已删除节点、循环、缺 end 节点、运行中修改或删除。
- 网盘文件名非法、路径穿越、文件过大、空文件夹、重复文件名、父目录已删除、分享密码错误、分享过期、发布资源缺失。
- 网络失败、权限拒绝、timeout、刷新期间切换页面。

适合发现 P0/P1/P2。

### 模式 8：契约一致性模式

检查链路：

```text
route / IPC channel / preload API / capability tool / workflow node schema / drive DTO / service method
→ result contract
→ renderer type
→ page usage
→ state update
→ log record
```

重点：

- 前端调用不存在的路由、IPC 或 channel。
- 返回字段和前端类型不一致。
- 前端认为成功但服务端或主进程只返回部分结果。
- 错误码、错误类型和前端错误处理不匹配。
- 页面刷新依赖的字段在响应里不存在。
- 删除、创建、登录、刷新、投递、运行后列表状态不同步。
- 日志记录的 userId、teamId、workflowId、workflowRunId、nodeId、driveItemId、shareId、publicationId 无法和用户行为关联。

适合方向 A/B/C/D/E/F/G。

### 模式 9：持久化与恢复模式

检查：

- Prisma schema / migration 与服务逻辑不一致。
- 用户、团队、邀请、权限与管理后台展示不一致。
- 工作流定义、节点配置、Code X config、运行快照、运行历史和 Runner 展示不一致。
- 网盘 item、upload session、storage object、share、publication、public URL、enabled/status 状态不一致。
- 并发写入、删除、重命名、移动、重复上传、重复发布、运行取消、重复运行。
- 审计日志、运行日志写入失败后业务状态不可信。
- 错误重试或恢复路径缺失。

适合方向 A/B/C/D/E/F。

### 模式 10：权限、安全与审计模式

检查敏感操作：

- 管理 API 是否都走 admin guard。
- 用户 API 是否限制到当前用户和当前团队。
- 团队资源是否可被其他团队读取或修改。
- 工作流和 Code X 是否能绕过 permission/audit、项目边界或敏感路径限制。
- 网盘文件、分享、发布、下载、预览、zip 是否可越权访问或泄露。
- token、cookie、Authorization、share password、shareId、publicationId、Code X 输入输出处理是否一致。
- 敏感操作是否有审计或结构化日志。

适合发现 P0/P1/security/logging/architecture。

### 模式 11：UI 状态完整性模式

如果扫描 UI，重点检查源码可证明的问题：

- 硬编码颜色或不走 token。
- 自定义按钮、卡片、弹窗等替代已有 shadcn 组件。
- 深浅主题下类名明显不可适配。
- loading / error / empty / disabled 状态缺失。
- 用户文案包含实现说明、开发阶段说明、架构解释。
- 表格数字、状态、操作按钮、表单 label/input 对齐或可访问性明显缺陷。
- 交互元素缺少可达的 disabled/focus/keyboard 路径。

禁止仅凭“看起来不好看”提交 UI Issue。

## 问题发现标准

每个问题必须有完整证据链：

```text
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口 → 用户影响或复盘阻断
```

合格条件：

- 能在代码中证明问题存在，不需要运行 App、dev server、浏览器或 Playwright。
- 影响本轮七类链路中的正常路径，或是合理高概率边界。
- 至少串起 3 层相关文件；单文件局部猜测默认不合格。
- 用 `rg` 确认过影响范围。
- 涉及最近提交时，用 `git log` / `git show` 确认过最终落下的代码。
- 涉及 UI 时，确认过项目组件库和 token 规则，不把主观审美当 Issue。
- 用 `NOT.md` 确认过不属于刻意设计。
- 用 `AGENTS.md` 确认过不违反当前仓库硬规则和模块边界判断。
- 能解释为什么不属于已有 Issue 或同根因。
- 后续修复 Agent 能根据 Issue 直接开工。

不合格条件：

- 需要运行 App、dev server、浏览器或 Playwright 才能确认。
- 只是“感觉不太好”但逻辑没错。
- 仅缺测试覆盖。
- 仅缺日志，且没有用户可见失败、审计风险或复盘阻断。
- 只是代码风格偏好。
- 命中 `NOT.md` 中明确说明应保留的刻意设计。
- 与已有 Issue 同根因。
- 证据链只有单个文件局部猜测，没有入口和结果。
- 不属于本轮七类链路。

## Issue 创建质量闸门

创建 Issue 前必须回答 14 个问题：

```text
1. 用户从哪里触发？
2. 代码链路是什么？
3. 当前错误结果或复盘阻断是什么？
4. 为什么这是本轮七类链路内的正常功能路径或合理边界，而不是极端猜测？
5. 是否查过最近 7 天相关变更地图？
6. 是否复盘了最近提交最终落下的代码，而不是只看提交标题？
7. 是否查过 NOT.md，确认不是刻意设计？
8. 是否查过 AGENTS.md，确认不是仓库硬规则允许或要求的行为？
9. 是否查过本地索引？
10. 是否查过 GitHub 已有 Issue？
11. 是否和已有 Issue 同根因？
12. 如果涉及登录、用户、客户端状态、Webhook 或自动化，日志/审计/运行记录是否足够支撑复盘？
13. 后续修复 Agent 能否按这个 Issue 直接开工？
14. 是否确认没有漂移到知识库、工作流、备份等本轮排除范围？
```

任一答不出来：

- 不创建 Issue。
- 在最终输出列为 `rejected candidate`。

## GitHub Issue 格式

每个有效发现创建一个 GitHub Issue。

每个 Issue 必须至少打 4 个分类标签：

```text
bug
优先级:<P0|P1|P2|P3>
类型:<崩溃|数据丢失|安全|错误处理|交互|UI质量|日志|死代码|架构>
模块:<Server|管理后台|Electron|应用壳|设置|UI|基础设施|自动化(若仓库存在)|调度器(仅自动化根因需要)>
```

**不要打任何 `状态:*` 或无前缀状态标签。** 巡检 Agent 只负责分类标签；Issue 创建后没有状态标签即为「待确认」隐含状态，后续由修复 Agent 认领时添加状态标签。

标签必须使用仓库现有标签。如果仓库没有 `类型:日志`，日志补全类问题改用最贴近的 `类型:错误处理`、`类型:交互`、`类型:安全` 或 `类型:架构`，并在 Issue body 的 `Type rationale` 写明 `type=logging` 的原始判断。

模块标签选择：

- `dashboard/src/features/auth/**`、`dashboard/src/routes/(auth)/**`、dashboard 登录/注册/邀请/桌面回调：优先 `模块:管理后台`。

## 去重规则

提交 Issue 前必须做三层去重，并做一层防误判过滤。

### 1. 本地索引去重

- 读全量 `/Users/liyang/Desktop/temp/issues.jsonl`。
- 如果已有相同 `fingerprint`，跳过。
- 如果旧记录没有 `fingerprint`，用 `file + symbol + summary` 近似判断。
- 如果同一文件已有大量相似 summary，默认跳过，除非是 P0/P1。

### 2. GitHub Issue 去重

使用 GitHub CLI 查询足够范围：

```sh
gh issue list -R FairyEver/Synapse --state all --limit 500 --json number,title,url,state,labels
```

对比：

- 标题中的 priority/type/summary。
- body 中的 `Local fingerprint`。
- 同一文件、同一 symbol、同一用户结果。
- 同一根因的不同表现。

必要时查看候选 Issue：

```sh
gh issue view -R FairyEver/Synapse <number> --json title,body,url,state
```

如果 GitHub 已有同问题，无论 open/closed 都跳过。

### 3. 同根因去重

如果新发现和已有 Issue 共享同一上游根因，只能提交更上游、更准确的一条；不要为每个下游表现拆多个 Issue。

示例：

- 同一个 team guard 漏校验导致用户列表、邀请页、Webhook 页三个地方越权。应提交一个权限根因 Issue，而不是三个页面 Issue。
- 同一个 account state contract 漂移导致账号按钮、设置页和 live connection 都显示错误。应提交一个契约漂移 Issue。
- 同一个 WebSocket registry 清理错误导致在线客户端、Webhook 投递和客户端状态都不可信。应提交一个 registry 根因 Issue。
- 同一个日志脱敏函数漏处理 Bearer token，不要按每个调用点拆多个 Issue。

并行 Agent 仍可能在极短时间内同时提交同一问题。提交前最后再查一次 GitHub Issue；如果发现刚刚已有同标题、同 fingerprint 或同根因，跳过创建。

### 4. 防误判过滤

- 读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 的当前内容，而不是依赖记忆。
- 读 `/Users/liyang/Documents/code/github/Synapse/AGENTS.md` 的当前内容，而不是依赖记忆。
- 如果候选问题命中 `NOT.md` 明确保留的行为，跳过。
- 如果候选问题命中 `AGENTS.md` 明确允许、要求或边界化的行为，跳过。
- 如果候选问题只是在刻意设计的实现附近，但根因和影响不属于 `NOT.md` 说明范围，可以继续提交。
- 如果候选问题只是在仓库硬规则附近，但根因和影响确实违反 `AGENTS.md` 当前规则，可以继续提交。
- 如果需要提交附近问题，Issue body 必须说明 `NOT.md` 和 `AGENTS.md` 已检查，且本问题不是这两个文件列出的保留或允许行为。
