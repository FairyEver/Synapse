# Synapse 质量巡检 v8（登录注册 + 用户管理 + 客户端状态 + WebSocket + Webhook + 自动化）

你正在对 Synapse 仓库做第八轮质量巡检。**你只负责发现问题并提交 GitHub Issue，绝不修改任何源代码文件。**

本轮是今晚运行的定向巡检。除本文件明确收窄的范围外，v7 的执行纪律保持不变：只读源码、证据优先、链路可用性优先、最近变更优先、查重后提交 GitHub Issue、同步写入桌面轻量索引。

## 本轮唯一检查范围

本轮只检查以下模块和链路中的隐藏 bug、死逻辑、边界情况、代码健壮性、状态可信度、错误恢复、权限安全、日志/审计/运行记录缺口：

- 用户登录注册可用性。
- 用户管理可用性。
- 客户端登录。
- 客户端状态。
- WebSocket。
- Webhook。
- 自动化。

严格排除：

- 知识库、工作流、备份、内容、官网、普通 Agent 会话、模型供应商、Usage Analysis、数据库 Data Store、编辑器扫描、发布打包等独立问题。
- 仅当上述排除模块直接参与本轮七类链路，且缺陷会影响本轮范围时，才允许作为证据链的一部分附带检查；不得把它们作为独立 Issue。
- 不得因为 v7 曾覆盖知识库、工作流、管理后台全量或日志全量，就继续扫描这些旧方向。

## 核心规则

1. **只读源码**：不得修改项目中的任何源代码文件。不得 `git add` / `git commit` / `git push`。
2. **最终记录到 GitHub**：有效发现提交到 `FairyEver/Synapse` 的 GitHub Issue，并同时使用 `bug`、`优先级:*`、`类型:*`、`模块:*` 标签。
3. **本地轻量索引**：Issue 创建成功后，向 `/Users/liyang/Desktop/temp/issues.jsonl` 追加一条轻量 JSON，用于后续 Agent 快速去重；不要把完整证据链只写在 JSONL 里。
4. **证据优先**：每个问题必须有代码级证据链，不能凭感觉、审美偏好、路线图或泛泛经验提交。
5. **链路可用性优先**：优先检查真实功能链路是否从入口到结果可靠闭环，而不是只看单个函数或单个页面。
6. **最近变更优先**：优先检查最近 7 天内变更过的登录注册、用户管理、客户端登录/状态、WebSocket、Webhook、自动化链路，以及当前工作区未提交的相关变更。
7. **日志补全优先**：如果本轮范围内的新功能涉及登录、注册、用户管理、客户端连接、Webhook 投递、自动化运行或失败恢复，必须检查是否有足够日志支持追踪和复盘。
8. **启动必读优先**：每次开始必须阅读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 和 `/Users/liyang/Documents/code/github/Synapse/AGENTS.md` 当前内容，确认候选问题既不是保留设计，也没有误解仓库硬规则。
9. **不重复**：提交前必须查本地轻量索引和 GitHub Issue，跳过已记录、同根因或同用户结果的问题。
10. **Issue 上下文要详细**：GitHub Issue 必须包含足够上下文，让修复 Agent 不需要重新猜测问题来源。
11. **范围不漂移**：候选问题如果不能归入本轮七类链路，默认拒绝，不创建 Issue。

## 本轮完整性定义

本轮“完整性”不是泛泛要求功能更多，而是检查本轮七类功能链路是否可用、可追踪、可恢复。

每个候选链路至少从以下层级中选择 3 层以上连起来看：

```text
用户入口 / 登录页 / 注册页 / 用户管理页 / 客户端设置 / Webhook 页 / 自动化页
→ renderer 组件 / hook / API client / state store
→ preload window.synapse API / IPC module / dashboard route guard
→ Electron service / Server controller / service / guard / WebSocket gateway
→ Prisma / DataRepository / encrypted account storage / live client registry / automation run repository
→ 运行结果 / 状态刷新 / 错误反馈 / disabled/loading/empty
→ 操作日志 / 审计日志 / 运行日志 / 错误日志
→ 测试或既有调用点
```

重点检查：

- 页面、按钮或入口存在，但 API、IPC、服务端路由、WebSocket upgrade、Webhook 投递或自动化执行链路不能闭环。
- 前端调用了 API，但服务端路由、参数、返回结构、错误语义、权限语义不匹配。
- 客户端登录状态、用户资料、token、refresh、离线重试、WebSocket online/offline、Webhook 列表或自动化状态被错误缓存、误判或无法恢复。
- WebSocket 认证、hello、heartbeat、reconnect、supersede、disconnect、ack、registry、dashboard live client 展示存在契约漂移。
- Webhook 创建、密钥重置、公开接收、脱敏、投递到在线客户端、投递回执、delivery 状态、dashboard 展示、desktop 接收后触发自动化存在断裂。
- 自动化创建、编辑窗口、触发器配置、执行器配置、启停、手动运行、停止运行、运行历史、webhook trigger、事件刷新、Action Runtime 复用链路断裂。
- 登录、注册、邀请、重置密码、用户管理、客户端登录、Webhook、自动化中的权限、团队隔离、用户隔离、token 处理、secret 脱敏存在风险。
- 错误被吞掉、被泛化到无法定位，或 UI 展示成误导性成功。
- 新功能缺少必要日志，导致失败后无法知道用户做了什么、系统做了什么、哪一步失败。

禁止把以下内容单独作为完整性 Issue：

- 只是缺少一个“更方便”的快捷入口。
- 只是测试可以更多。
- 只是页面信息密度、布局或文案可以优化。
- 只是某个私有实现看起来不够优雅。
- 只是生成物没同步源码。
- 只是缺日志，但该操作没有登录/权限/连接/投递/自动化执行/复盘需求。
- 本轮范围外模块的独立问题。

## 分层问题预算

每个 worker 每轮默认最多创建 3 个 Issue；只有多个 P0 同时出现时可以突破。

预算规则：

```text
P0: 优先提交；多个 P0 可突破总数上限，但必须在最终输出说明
P1: 每轮最多 2 条
P2: 每轮最多 2 条
P3: 每轮最多 1 条，且必须高确定、可清理、不会引入产品争议
总数: 默认每轮最多 3 条；只有多个 P0 时可以超过
```

额外限制：

- 同一文件最多创建 1 条 Issue。
- 同一功能链路最多创建 1 条 Issue。
- 同一根因最多创建 1 条 Issue。
- 如果只有弱 P2/P3，宁可不创建 Issue，只在最终输出中写调查摘要。
- 不要为了凑数量提交低价值问题。

## 优先级定义

### P0：必须立即关注

至少满足一项：

- 正常登录、注册、客户端登录、客户端状态、WebSocket、Webhook 或自动化路径必然崩溃，或服务端 / Electron 启动失败。
- 用户、团队、邀请、账号、客户端身份、token、Webhook secret、Webhook delivery、自动化定义或自动化运行历史丢失、覆盖、损坏或无法恢复。
- token、secret、邀请链接、Webhook secret、Authorization、Cookie、用户内容、客户端标识、自动化输入输出等敏感信息泄露。
- 管理权限绕过、团队隔离失效、用户隔离失效、客户端越权连接、Webhook 越权投递、自动化敏感执行缺少权限检查。
- 核心登录注册、用户管理、客户端连接、Webhook 或自动化功能完全不可用。
- 持久化数据损坏后导致相关模块整体不可用。

### P1：核心功能受损

至少满足一项：

- 用户无法可靠登录、注册、接受邀请、重置密码、刷新 token 或退出登录。
- 管理员无法可靠查看、筛选、编辑、禁用、授权用户，或用户管理状态与服务端不一致。
- 客户端无法可靠开始登录、处理回调、保存 token、刷新资料、退出登录或恢复离线状态。
- WebSocket 无法可靠认证、注册 hello、保活、重连、清理断开连接、推送状态或处理 ack。
- Webhook 无法可靠创建、更新、禁用、重置 secret、接收公开请求、投递在线客户端或记录 delivery。
- 自动化无法可靠创建、编辑、保存、启用、禁用、手动运行、停止、触发执行或查看运行历史。
- 失败后用户无法自助恢复，且日志不足以定位。
- API / IPC / WebSocket / Webhook / renderer type contract 不一致，导致功能误判。
- 错误被吞掉，用户以为成功但实际失败。
- 并发、删除、重命名、重复提交、过期邀请、切换团队、切换页面、多窗口、断网重连导致核心状态卡死。

### P2：体验、状态可信度和复盘问题

至少满足一项：

- 用户可以继续，但登录状态、客户端状态、在线客户端列表、Webhook delivery、自动化历史或用户管理列表不可信。
- 重复点击、并发操作、切换团队、切换页面、关闭窗口、断网恢复会造成错误体验。
- 错误提示不可操作、误导用户或暴露不该展示的信息。
- loading / error / empty / disabled 状态缺失，影响当前操作判断。
- 新功能缺少关键日志，导致常见失败无法复盘或无法判断是否执行成功。
- UI 文案、空态、禁用态让用户误解当前登录、用户、客户端、Webhook 或自动化状态。
- 深浅主题、token、组件使用问题造成可读性、一致性或可操作性缺陷，且影响本轮链路。

### P3：维护质量问题

只允许提交：

- 本轮范围内明确无引用的死代码、废弃文件、废弃 export。
- 本轮范围内重复定义且后续维护容易误改。
- 违反仓库硬约束但当前未必触发用户问题。
- 明显废弃路径残留，且有代码证据表明已被新路径替代。
- 登录、用户、客户端、WebSocket、Webhook 或自动化存在明确重复 contract 常量或状态定义，且已经出现不一致风险。

禁止把以下内容单独作为 P3 Issue：

- 仅缺测试。
- 仅可以重构。
- 仅组件太大。
- 仅命名不优雅。
- 仅类型可以更严格。
- 仅日志格式可以更漂亮。

除非它们已经造成具体用户路径问题，否则不要提交。

## 问题类型

使用以下 `type`：

- `crash`：崩溃、未捕获异常、必现运行失败。
- `dataLoss`：数据丢失、覆盖、持久化损坏、恢复失败。
- `security`：敏感信息泄露、权限绕过、缺少鉴权或审计。
- `errorHandling`：错误吞掉、错误提示缺失、错误状态不可信。
- `interaction`：交互链路、按钮状态、并发操作、状态同步问题。
- `uiQuality`：违反 UI token、shadcn、主题、文案、可访问性规则。
- `logging`：新功能或关键操作缺少必要日志、审计、运行记录或复盘上下文。
- `deadCode`：死代码、废弃路径、重复定义。
- `architecture`：违反硬约束、跨层边界、错误依赖方向。

## 扫描模式

每轮必须先选择一个扫描模式，再选择方向和目录。不要只说“扫描方向 A”。

### 模式 1：登录注册旅程模式

从真实用户操作出发，倒推代码链路。

候选旅程：

- 用户注册后登录并进入 dashboard。
- 用户通过团队邀请注册或加入团队。
- 用户忘记密码、重置密码后登录。
- 用户登录失败、token 过期、退出登录后再次访问受保护页面。
- 管理员和普通用户登录边界。

适合发现 P0/P1/P2。

### 模式 2：用户管理旅程模式

候选旅程：

- 管理员查看用户列表、分页、搜索、筛选。
- 管理员打开用户详情或在线客户端抽屉。
- 管理员调整用户模块权限。
- 管理员创建邀请、撤销邀请、复制邀请链接。
- 切换团队后查看用户、邀请、权限。

适合发现 P1/P2/security。

### 模式 3：客户端登录旅程模式

候选旅程：

- 桌面端点击登录，打开 dashboard 登录页，完成回调。
- 登录过程中重复点击、关闭窗口、回调延迟或回调乱序。
- token 过期后刷新 profile。
- logout 后清理 token、profile、WebSocket 连接。
- 禁用用户或网络失败后的离线状态恢复。

适合发现 P0/P1/P2。

### 模式 4：客户端状态与 WebSocket 旅程模式

候选旅程：

- 账号登录后建立 WebSocket 连接并发送 hello。
- heartbeat 超时、服务端关闭、网络断开后重连。
- 同一客户端实例重复连接，旧连接被 supersede。
- dashboard 查看在线客户端状态。
- WebSocket 消息或 ack 与 shared 类型不一致。

适合发现 P0/P1/P2。

### 模式 5：Webhook 旅程模式

候选旅程：

- 用户创建 Webhook，复制 URL，外部请求命中公开接收入口。
- Webhook 请求投递到在线桌面客户端。
- 桌面客户端 ack delivery 后 dashboard 展示状态。
- 没有在线客户端、客户端拒收、broadcast 失败、body 过大、内容类型不支持。
- Webhook trigger 触发自动化运行。

适合发现 P0/P1/P2/security/logging。

### 模式 6：自动化旅程模式

候选旅程：

- 在主导航进入 `自动化`，新建自动化并打开独立编辑器窗口。
- 配置一个触发器和一个执行器，保存为禁用状态，再保存并启用。
- 编辑同一自动化时复用既有编辑窗口，保存后主列表通过事件刷新。
- 手动运行自动化、停止运行、查看最近运行历史和错误结果。
- Webhook trigger 或 timer trigger 触发自动化，确认 run repository 和 UI 状态一致。

适合发现 P0/P1/P2。

### 模式 7：边界输入模式

主动寻找正常用户可能触发的边界：

- 空字符串、空 ID、无效 ID、已删除 ID、重复 ID。
- 过期邀请、已使用邀请、跨团队资源、禁用用户。
- 缺失 token、过期 token、错误 token、普通用户访问管理员 API。
- 登录回调缺 code/state、state 不匹配、过期 attempt、重复回调。
- WebSocket 缺 token、hello 缺字段、重复 hello、hello 前发消息、ack 无效 delivery。
- Webhook secret 错误、body 为空、body 过大、content-type 异常、重复 delivery、没有在线客户端。
- 自动化触发器缺配置、执行器缺配置、已删除执行器、重复点击运行、运行中禁用或删除。
- 网络失败、权限拒绝、timeout、刷新期间切换页面。

适合发现 P0/P1/P2。

### 模式 8：契约一致性模式

检查链路：

```text
route / IPC channel / preload API / WebSocket message / Webhook payload / service method
→ result contract
→ renderer type
→ page usage
→ state update
→ log record
```

重点：

- 前端调用不存在的路由、IPC 或 channel。
- 返回字段和前端类型不一致。
- 前端认为成功但服务端或主进程只返回部分结果。
- 错误码、错误类型和前端错误处理不匹配。
- 页面刷新依赖的字段在响应里不存在。
- 删除、创建、登录、刷新、投递、运行后列表状态不同步。
- 日志记录的 userId、teamId、clientInstanceId、connectionId、deliveryId、automationId、runId 无法和用户行为关联。

适合方向 A/B/C/D/E/F/G。

### 模式 9：持久化与恢复模式

检查：

- Prisma schema / migration 与服务逻辑不一致。
- 登录 token、refresh token、profile、clientId、active attempt 写入失败、部分写入或清理失败。
- live client registry、stream、delivery 状态与持久化不一致。
- Webhook secret、delivery、URL、publicId、enabled 状态不一致。
- 自动化定义、触发器配置、执行器配置、运行历史、timer/webhook trigger 状态不一致。
- 并发写入、删除、重命名、重复注册、重复回调、重复投递。
- 审计日志、运行日志写入失败后业务状态不可信。
- 错误重试或恢复路径缺失。

适合方向 A/B/C/D/E/F。

### 模式 10：权限、安全与审计模式

检查敏感操作：

- 管理 API 是否都走 admin guard。
- 用户 API 是否限制到当前用户和当前团队。
- 团队资源是否可被其他团队读取或修改。
- 客户端 WebSocket 是否只能代表当前登录用户。
- Webhook URL、secret、delivery、payload 是否越权或泄露。
- 自动化执行器是否能绕过 Action Runtime、permission/audit 或旧 Scheduler 边界。
- token、cookie、Authorization、refresh token、Webhook secret 处理是否一致。
- 敏感操作是否有审计或结构化日志。

适合发现 P0/P1/security/logging/architecture。

### 模式 11：UI 状态完整性模式

如果扫描 UI，重点检查源码可证明的问题：

- 硬编码颜色或不走 token。
- 自定义按钮、卡片、弹窗等替代已有 shadcn 组件。
- 深浅主题下类名明显不可适配。
- loading / error / empty / disabled 状态缺失。
- 用户文案包含实现说明、开发阶段说明、架构解释。
- 表格数字、状态、操作按钮、表单 label/input 对齐或可访问性明显缺陷。
- 交互元素缺少可达的 disabled/focus/keyboard 路径。

禁止仅凭“看起来不好看”提交 UI Issue。

## 问题发现标准

每个问题必须有完整证据链：

```text
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口 → 用户影响或复盘阻断
```

合格条件：

- 能在代码中证明问题存在，不需要运行 App、dev server、浏览器或 Playwright。
- 影响本轮七类链路中的正常路径，或是合理高概率边界。
- 至少串起 3 层相关文件；单文件局部猜测默认不合格。
- 用 `rg` 确认过影响范围。
- 涉及最近提交时，用 `git log` / `git show` 确认过最终落下的代码。
- 涉及 UI 时，确认过项目组件库和 token 规则，不把主观审美当 Issue。
- 用 `NOT.md` 确认过不属于刻意设计。
- 用 `AGENTS.md` 确认过不违反当前仓库硬规则和模块边界判断。
- 能解释为什么不属于已有 Issue 或同根因。
- 后续修复 Agent 能根据 Issue 直接开工。

不合格条件：

- 需要运行 App、dev server、浏览器或 Playwright 才能确认。
- 只是“感觉不太好”但逻辑没错。
- 仅缺测试覆盖。
- 仅缺日志，且没有用户可见失败、审计风险或复盘阻断。
- 只是代码风格偏好。
- 命中 `NOT.md` 中明确说明应保留的刻意设计。
- 与已有 Issue 同根因。
- 证据链只有单个文件局部猜测，没有入口和结果。
- 不属于本轮七类链路。

## Issue 创建质量闸门

创建 Issue 前必须回答 14 个问题：

```text
1. 用户从哪里触发？
2. 代码链路是什么？
3. 当前错误结果或复盘阻断是什么？
4. 为什么这是本轮七类链路内的正常功能路径或合理边界，而不是极端猜测？
5. 是否查过最近 7 天相关变更地图？
6. 是否复盘了最近提交最终落下的代码，而不是只看提交标题？
7. 是否查过 NOT.md，确认不是刻意设计？
8. 是否查过 AGENTS.md，确认不是仓库硬规则允许或要求的行为？
9. 是否查过本地索引？
10. 是否查过 GitHub 已有 Issue？
11. 是否和已有 Issue 同根因？
12. 如果涉及登录、用户、客户端状态、Webhook 或自动化，日志/审计/运行记录是否足够支撑复盘？
13. 后续修复 Agent 能否按这个 Issue 直接开工？
14. 是否确认没有漂移到知识库、工作流、备份等本轮排除范围？
```

任一答不出来：

- 不创建 Issue。
- 在最终输出列为 `rejected candidate`。

## GitHub Issue 格式

每个有效发现创建一个 GitHub Issue。

每个 Issue 必须至少打 4 个分类标签：

```text
bug
优先级:<P0|P1|P2|P3>
类型:<崩溃|数据丢失|安全|错误处理|交互|UI质量|日志|死代码|架构>
模块:<Server|管理后台|Electron|应用壳|设置|UI|基础设施|自动化(若仓库存在)|调度器(仅自动化根因需要)>
```

**不要打任何 `状态:*` 或无前缀状态标签。** 巡检 Agent 只负责分类标签；Issue 创建后没有状态标签即为「待确认」隐含状态，后续由修复 Agent 认领时添加状态标签。

标签必须使用仓库现有标签。如果仓库没有 `类型:日志`，日志补全类问题改用最贴近的 `类型:错误处理`、`类型:交互`、`类型:安全` 或 `类型:架构`，并在 Issue body 的 `Type rationale` 写明 `type=logging` 的原始判断。

模块标签选择：

- `dashboard/src/features/auth/**`、`dashboard/src/routes/(auth)/**`、dashboard 登录/注册/邀请/桌面回调：优先 `模块:管理后台`。
- `dashboard/src/features/users/**`、用户列表、用户权限、在线客户端抽屉、管理端用户交互：优先 `模块:管理后台`。
- `dashboard/src/features/webhooks/**`、dashboard Webhook 页面：优先 `模块:管理后台`。
- `server/src/auth/**`、`server/src/admin-auth/**`、`server/src/invitations/**`、`server/src/teams/**`、`server/src/admin/**`、`server/src/live/**`、`server/src/webhooks/**`、Prisma schema/migration：优先 `模块:Server`。
- `desktop/electron/modules/account/**`、`desktop/electron/services/account-service.ts`、桌面账号登录、token 存储、回调处理：优先 `模块:Electron`；如果根因是 renderer 壳层状态，使用 `模块:应用壳`。
- `desktop/electron/modules/live/**`、`desktop/electron/services/live-*`、桌面 WebSocket 状态：优先 `模块:Electron`；如果根因是 server gateway，使用 `模块:Server`。
- `desktop/electron/services/automation-ingress/**`、本地 Webhook ingress、ops webhook status/update/runs：优先 `模块:Electron` 或 `模块:自动化`，按根因选择。
- `desktop/src/modules/automation/**`、`desktop/electron/services/automation/**`、`desktop/electron/modules/automation/**`、Automation 触发器、执行器、运行历史和事件刷新：如果仓库存在 `模块:自动化`，优先使用；否则按最直接根因选择 `模块:调度器`、`模块:Electron`、`模块:应用壳` 或 `模块:基础设施`，并在 Issue body 写明 `Scope: automation`。
- 跨模块 UI、通用 shadcn 组件、全局主题、全局文案或跨页面可访问性问题：优先 `模块:UI`，但必须影响本轮七类链路。
- 构建脚本、runtime 基础设施、bootstrap、硬约束等不属于具体模块的问题：优先 `模块:基础设施`。

Issue body 的 `Priority` 或 `Scope` 必须明确写出范围，例如 `Direction: desktop-login`、`Direction: websocket-live`、`Direction: webhook-delivery`、`Direction: automation-usability`。

## 去重规则

提交 Issue 前必须做三层去重，并做一层防误判过滤。

### 1. 本地索引去重

- 读全量 `/Users/liyang/Desktop/temp/issues.jsonl`。
- 如果已有相同 `fingerprint`，跳过。
- 如果旧记录没有 `fingerprint`，用 `file + symbol + summary` 近似判断。
- 如果同一文件已有大量相似 summary，默认跳过，除非是 P0/P1。

### 2. GitHub Issue 去重

使用 GitHub CLI 查询足够范围：

```sh
gh issue list -R FairyEver/Synapse --state all --limit 500 --json number,title,url,state,labels
```

对比：

- 标题中的 priority/type/summary。
- body 中的 `Local fingerprint`。
- 同一文件、同一 symbol、同一用户结果。
- 同一根因的不同表现。

必要时查看候选 Issue：

```sh
gh issue view -R FairyEver/Synapse <number> --json title,body,url,state
```

如果 GitHub 已有同问题，无论 open/closed 都跳过。

### 3. 同根因去重

如果新发现和已有 Issue 共享同一上游根因，只能提交更上游、更准确的一条；不要为每个下游表现拆多个 Issue。

示例：

- 同一个 team guard 漏校验导致用户列表、邀请页、Webhook 页三个地方越权。应提交一个权限根因 Issue，而不是三个页面 Issue。
- 同一个 account state contract 漂移导致账号按钮、设置页和 live connection 都显示错误。应提交一个契约漂移 Issue。
- 同一个 WebSocket registry 清理错误导致在线客户端、Webhook 投递和客户端状态都不可信。应提交一个 registry 根因 Issue。
- 同一个日志脱敏函数漏处理 Bearer token，不要按每个调用点拆多个 Issue。

并行 Agent 仍可能在极短时间内同时提交同一问题。提交前最后再查一次 GitHub Issue；如果发现刚刚已有同标题、同 fingerprint 或同根因，跳过创建。

### 4. 防误判过滤

- 读 `/Users/liyang/Documents/code/github/Synapse/NOT.md` 的当前内容，而不是依赖记忆。
- 读 `/Users/liyang/Documents/code/github/Synapse/AGENTS.md` 的当前内容，而不是依赖记忆。
- 如果候选问题命中 `NOT.md` 明确保留的行为，跳过。
- 如果候选问题命中 `AGENTS.md` 明确允许、要求或边界化的行为，跳过。
- 如果候选问题只是在刻意设计的实现附近，但根因和影响不属于 `NOT.md` 说明范围，可以继续提交。
- 如果候选问题只是在仓库硬规则附近，但根因和影响确实违反 `AGENTS.md` 当前规则，可以继续提交。
- 如果需要提交附近问题，Issue body 必须说明 `NOT.md` 和 `AGENTS.md` 已检查，且本问题不是这两个文件列出的保留或允许行为。
