## 本轮完整性定义

本轮“完整性”不是要求功能更多，而是检查最近 7 天已经合入、用户或 Agent 已经能触发的能力是否可靠、兼容、可恢复、可追踪、跨入口一致。

每个候选链路至少从以下层级中选择 3 层以上连起来看：

```text
用户入口 / 系统 App / 菜单 / 参数编辑器 / Workflow 节点 / MCP tool / Agent 对话
→ renderer 组件 / hook / store / API client / window.synapse bridge
→ preload / IPC module / capability dispatcher / Workflow migration gateway
→ workflow service / installer service / skill-env service / secrets service / Agent runtime / regression service
→ DataRepository / JSON 原文件与备份 / encrypted storage / editor Skill 目录 / session transcript
→ 真实结果 / 刷新与重启恢复 / 错误反馈 / disabled/loading/empty / 重试与冲突处理
→ 日志 / 审计 / 迁移诊断 / 运行记录 / 脱敏 / 原样导出
→ fixture / contract / ADR / AGENTS.md / Synapse skill-package / MCP schema / Agent guide
```

重点检查：

- 页面、按钮、菜单、slash、MCP tool、Workflow 节点或 Agent 能力存在，但后端、主进程、服务、模板或持久化不能闭环。
- 前端调用 API/IPC/capability，但参数、返回结构、错误语义、权限语义不匹配。
- 用户操作后显示成功，但刷新、切换窗口、重开应用或公开访问时真实状态不一致。
- Workflow 文档读取绕过统一迁移入口，导致本地数据、旧内容仓库、导入包、运行快照、MCP、Automation 或子工作流得到不同兼容结果。
- `meta.schemaVersion` 与保存修订哈希、DataRepository 外层版本或包 `formatVersion` 混用，或 schema 变化未同步版本、迁移注册、历史 fixture 和 contract。
- 迁移未在克隆上逐级执行、未做最终结构校验、备份不是当前原文件精确字节、写入前不复查源摘要，或失败后仍覆盖/移动原文件。
- 单个损坏或未来版本工作流阻断整个列表，未来版本被降级/裁剪/运行，迁移失败被转为空工作流，或专用原样导出改变正文。
- 旧内容仓库自动找回覆盖同 ID 当前数据、失败不隔离、成功/冲突标记不永久幂等，或用户删除已找回工作流后旧来源再次复活。
- `VersionedDataMigrator` 的版本解析、排序、选择、克隆、校验或错误行为改变，却未检查全部调用方和历史迁移注册表。
- 多选文件/文件夹参数不是有序、非空、去重且最多 100 项的资源引用数组；UI、预设、MCP、导入包、变量解析和执行器对基数理解不同。
- 单选与多选自动互转，切换 `allowMultiple` 保留不兼容默认值，或子工作流绑定不校验资源类型与基数，直到运行时才失败。
- Skill `.env.example` 声明、仓库密钥配置、安装确认、重新安装合并、已安装项扫描和密钥更新队列任一环断裂，导致值丢失、旧值写回、状态虚假或无恢复入口。
- Skill `.env` 超过 1 MiB 仍被处理、文件权限被放宽、并发变化后仍覆盖、Windows 静默写入，或密钥值进入日志、诊断、toast、错误对象、本地索引和发布产物。
- Skill 卸载扫描越过受信任根、取消后继续积累结果、执行前不复查名称/真实路径/符号链接，或某个入口绕过公共卸载服务直接删除。
- Skill 发布错误包含 `.env`/隐藏项/符号链接，混用 `.synapse.json` 与 `.synapse.repository.json`，或把本地提交、身份关联、后台同步和远端完成显示成同一个成功状态。
- Synapse Skill 批量安装/更新把 source ready 当作 installed、单项目失败污染其它项目、warning 被吞、重试成功项，或某个编辑器扫描失败隐藏其它编辑器状态。
- Agent 自动标题覆盖手动标题、串到错误会话、重连后重复改名；AskUserQuestion 的回答/未答/超时/停止状态在事件、transcript、timeline、刷新和重启之间漂移。
- 侧边栏宽度的存储 key 未按模块/实例隔离、无效值破坏布局，或一个页面调整宽度影响其它页面。
- 蜂群任务、云盘上传/同步、密钥删除和安装状态的本周修复留下邻接状态分支、竞态或性能问题；必须基于 HEAD 的新证据，不能复述已关闭 Issue。
- 重复点击、并发、取消、失败、重试、切换窗口或重启应用导致最近新增能力卡死、串状态、误判成功或失去恢复路径。
- 大量旧工作流、大型参数预设、大目录 Skill 扫描、大批量安装/更新、长 transcript 或高频进度事件导致无界扫描、重复 IO、内存增长、事件风暴或 UI 卡顿。
- 同一业务 contract、路径校验、日志脱敏、权限检查、状态转换或 schema 定义重复多份，且已经出现或高概率出现不一致。
- 新能力只改产品本体，未同步 MCP 描述/schema、Synapse skill-package、Agent guide、API reference、release note 或测试。
- 错误被吞掉、泛化到无法定位，或 UI 展示成误导性成功。

禁止把以下内容单独作为完整性 Issue：

- 只是缺少一个“更方便”的快捷入口。
- 只是测试可以更多。
- 只是页面信息密度、布局或文案可以优化，但没有误导或不可操作后果。
- 只是某个私有实现看起来不够优雅。
- 只是生成物没同步源码。
- 只是缺日志，但该操作没有失败复盘、审计、安全或用户状态可信度需求。
- 只是性能“可能更快”，但没有当前代码会无界增长、明显重复、N+1 或阻塞用户路径的证据。
- 只是“可以抽象”，但没有重复实现导致的 contract 漂移或维护风险证据。

## 分层问题预算

每个 worker 每轮默认最多创建 3 个 Issue；只有多个 P0 同时出现时可以突破。

预算规则：

```text
P0: 优先提交；多个 P0 可突破总数上限，但必须在最终输出说明
P1: 每轮最多 2 条
P2: 每轮最多 2 条
P3: 每轮最多 1 条，且必须高确定、可清理、不会引入产品争议
总数: 默认每轮最多 3 条；只有多个 P0 时可以超过
```

额外限制：

- 同一文件最多创建 1 条 Issue。
- 同一功能链路最多创建 1 条 Issue。
- 同一根因最多创建 1 条 Issue。
- 如果只有弱 P2/P3，宁可不创建 Issue，只在最终输出中写调查摘要。
- 不要为了凑数量提交低价值问题。

## 优先级定义

### P0：必须立即关注

至少满足一项：

- 正常 Workflow 升级、Skill 安装/更新/卸载、Agent 会话恢复、云盘或蜂群回归路径必然崩溃，或 Electron 启动失败。
- Workflow 原文/备份/快照、Skill 目录/`.env`、会话记录、云盘文件、同步状态、配置或权限数据丢失、覆盖、损坏或无法恢复。
- token、secret、Authorization、Cookie、provider key、share password、shareId、publicationId、云盘文件内容、评论内容、同步本地路径或用户私密内容等敏感信息泄露。
- 管理权限绕过、团队隔离失效、云盘越权访问、分享/发布越权访问、评论/版本越权访问、同步绑定越权读写或敏感执行缺少权限检查。
- Workflow 迁移覆盖原文或未来版本、Skill 卸载命中错误目录、安装/发布覆盖用户内容、Agent 状态串会话、密钥明文泄露或加密存储损坏。
- 核心功能完全不可用，且没有可行恢复路径。

### P1：核心功能受损

至少满足一项：

- Workflow 无法可靠读取、迁移、隔离、找回、编辑、保存、运行、导入、导出或恢复旧数据。
- Workflow 多资源参数在 UI、预设、MCP、导入导出、Workflow Call、变量解析和执行器之间丢项、乱序、误转基数或错误接受不兼容绑定。
- Skill 无法可靠从 `.env.example` 配置密钥、安装并保留 `.env`、扫描受影响实例、确认更新、处理冲突或失败后恢复。
- Skill 卸载器无法可靠发现、取消、限制扫描、复查目标并移入废纸篓，或 IDE 管理等入口行为不一致。
- Skill 发布身份、文件排除、本地关联、远端同步、Synapse Skill 批量安装/更新、warning 或部分失败状态不可信。
- Agent 自动标题或 AskUserQuestion 持久化在正常会话路径下丢失、串会话、覆盖用户选择或恢复错误状态。
- 本周回归区的蜂群任务、云盘上传/同步、公开分享、密钥删除或安装更新在当前代码中仍无法可靠取消、重试、恢复或呈现真实结果。
- 用户能触发的入口实际无效、只改前端状态、成功提示虚假、刷新后回退或后端没有对应实现。
- API / IPC / capability / MCP / renderer type / schema / template 文档不一致，导致 Agent 或用户操作按错误 contract 执行。
- 失败后用户无法自助恢复，且日志不足以定位。
- 并发、取消、重复提交、切换团队/项目/文件、多窗口、断网、同步中断导致核心状态卡死。
- 性能问题会让正常规模数据的用户路径卡死、超时、内存持续增长或阻塞主进程。
- Synapse skill-package、内置指南或 MCP 指南教 Agent 使用错误工具、错误字段或错误顺序，导致能力不可用。

### P2：体验、状态可信度和复盘问题

至少满足一项：

- 用户可以继续，但状态不可信、错误提示不可操作、空态/禁用态/loading 缺失或误导。
- 重复点击、并发操作、切换页面、关闭窗口、断网恢复造成错误体验。
- Workflow 迁移状态、隔离原因、未来版本限制、多资源选择/排序/清空或预设兼容提示让用户误判数据是否安全、能否运行或需要怎样恢复。
- Skill `.env` 是否已配置、哪些安装项受影响、扫描/排队/写入/冲突/重试状态，或卸载扫描/选择/废纸篓结果让用户误判真实文件状态。
- Skill 发布的预检、本地保存、关联、后台同步、远端完成、批量安装/更新 warning 和部分失败状态让用户误判操作是否完成。
- 自动标题来源、AskUserQuestion 实际选择和终态、侧边栏宽度恢复不可信，但用户仍可继续操作。
- 蜂群任务或云盘回归区的列表、任务面板、运行状态、公开访问或同步状态与真实结果不一致。
- 性能问题不会完全阻断，但会随文件数、评论数、版本数、变更日志数、同步记录数或目录深度增长明显恶化。
- 关键操作缺少复盘所需日志、审计或运行记录。
- UI 违反仓库 token/组件/文案纪律，并且影响用户理解或操作。
- 重复实现已经出现局部 contract 不一致，但尚未证明核心路径必然失败。

### P3：维护质量问题

只允许提交：

- 本轮范围内明确无引用的死代码、废弃文件、废弃 export。
- 本轮范围内重复定义且后续维护容易误改，且能证明已经有不一致风险。
- 违反仓库硬约束但当前未必触发用户问题。
- 明显废弃路径残留，且有代码证据表明已被新路径替代。
- 应抽成共享 helper/service/schema 的逻辑分散在 3 处以上，并涉及权限、路径、脱敏、状态机、MCP schema、文件名清洗、同步一致性、版本语义或持久化安全。

禁止把以下内容单独作为 P3 Issue：

- 仅缺测试。
- 仅可以重构。
- 仅组件太大。
- 仅命名不优雅。
- 仅类型可以更严格。
- 仅日志格式可以更漂亮。

## 问题类型

使用以下 `type`：

- `crash`：崩溃、未捕获异常、必现运行失败。
- `dataLoss`：数据丢失、覆盖、持久化损坏、恢复失败。
- `security`：敏感信息泄露、权限绕过、缺少鉴权或审计。
- `errorHandling`：错误吞掉、错误提示缺失、错误状态不可信。
- `interaction`：交互链路、按钮状态、并发操作、状态同步问题。
- `uiQuality`：违反 UI token、shadcn、主题、文案、可访问性规则。
- `performance`：无界扫描、N+1、重复 IO、渲染阻塞、主进程阻塞、资源泄漏。
- `syncConsistency`：本地/远端、当前版本、评论锚点、变更日志或同步状态不一致。
- `accessibility`：权限、分享、公开访问、本地可访问性或用户心智模型错误，导致用户以为可访问但实际不可达，或以为不可访问但实际泄露。
- `alignment`：MCP、capability、内置 skill/rule/prompt、Agent guide、API reference 与产品能力不一致。
- `robustness`：原子性、取消、重试、资源释放、输入校验、状态机健壮性缺口。
- `deadCode`：死代码、废弃路径、重复定义。
- `architecture`：违反硬约束、跨层边界、错误依赖方向、应抽象但分散导致风险。

如果 GitHub 没有对应 `类型:*` 标签：

- `performance` 优先映射到 `类型:架构` 或 `类型:交互`，并在 body 写明 `type=performance`。
- `syncConsistency` 优先映射到 `类型:交互` 或 `类型:错误处理`，并在 body 写明 `type=syncConsistency`。
- `accessibility` 优先映射到 `类型:交互` 或 `类型:安全`，并在 body 写明 `type=accessibility`。
- `alignment` 优先映射到 `类型:架构`，并在 body 写明 `type=alignment`。
- `robustness` 优先映射到 `类型:错误处理` 或 `类型:架构`，并在 body 写明 `type=robustness`。

- 未来版本不得编辑、保存、运行、被 Automation/子工作流调用或解释正文；仅允许符合条件时专用原样导出。
- 本地存储、旧仓库目录、导入包、运行快照、IPC、MCP、Automation 和子工作流不得绕过统一迁移 gateway。
- 旧内容仓库找回只扫描已配置仓库的 workflows 目录，不覆盖同 ID 当前数据；成功/冲突标记永久幂等，用户删除后旧数据不得复活。
- 修改通用 `VersionedDataMigrator` 的公开行为时，必须检查仓库内全部调用方、注册表和历史版本测试，不能只验证迁移器自身。

## 扫描模式

每轮必须先选择一个扫描模式，再选择方向和目录。不要只说“扫描云盘”。

### 模式 1：用户旅程与意外表现模式

从真实用户操作出发，倒推代码链路。

候选旅程：

- 用户打开蜂群任务 App，创建任务，配置 worker 和 prompt 注入，启动运行，取消，再查看历史和 worker conversation。
- 用户通过 MCP 或 Workflow 节点触发蜂群任务，再回到系统 App 查看运行状态和历史。
- 用户打开 Synapse Skill 安装器，检测更新，选择全局/编辑器目标，批量安装，某一项失败后重试或打开标准安装流程。
- 用户新增密钥，隐藏/显示/复制/替换/删除，再让安装器使用密钥变量替换，确认 UI 和日志不泄露明文。
- 用户打开云盘文档，切到编辑，保存，刷新，再从版本历史、分享页或公开页查看真实结果。
- 用户选中文档内容创建评论，编辑原文，恢复旧版本，再查看评论锚点和线程状态。
- 用户在云盘上传文件夹，重命名、移动、分享、取消分享，再刷新公开链接。
- 云端已有文件或文件夹、本地目录为空，用户创建桌面同步绑定并启动同步，再查看本地是否真实出现内容。
- 本地已有文件或文件夹、云盘目标为空，用户创建桌面同步绑定并启动同步，再查看云盘是否真实出现内容。
- 用户创建桌面同步绑定，本地编辑文件，远端修改同一文件，断网恢复后查看冲突和同步状态。
- 用户快速重复点击保存、评论、恢复版本、同步、删除、取消、重试或切换项目/团队/文件。
- 用户在多窗口中编辑同一对象，或在一个窗口删除另一个窗口正在使用的对象。
- 用户看到成功 toast 后刷新页面、重开应用或从另一个入口查看真实结果。

适合发现 P0/P1/P2。

### 模式 2：边界输入与并发模式

主动寻找正常用户可能触发的边界：

- 空字符串、空 ID、无效 ID、已删除 ID、重复 ID。
- 文件名非法、路径穿越、大小写冲突、尾随空格/点、空文件夹、大文件、大目录。
- 跨团队资源、跨项目资源、禁用用户、缺失/过期 token。
- 保存中取消、编辑中删除、重复保存、重复评论、重复上传、重复发布、重复恢复版本、重复同步。
- 网络失败、权限拒绝、timeout、存储不可访问、日志写入失败。
- 本地同步目录含空格/中文、同步盘、只读目录、文件锁、符号链接、父子目录互相绑定。

适合发现 P0/P1/P2。

### 模式 3：契约一致性模式

检查链路：

```text

→ result contract
→ renderer type / Agent guide / built-in skill
→ page or Agent usage
→ state update
→ log record
```

重点：

- 前端调用不存在的路由、IPC 或 channel。
- 返回字段和前端类型不一致。
- MCP schema 和 dispatcher 行为不一致。
- 内置 skill 示例使用已删除字段或错误默认值。
- 页面刷新依赖的字段在响应里不存在。
- 日志记录的 userId、teamId、projectId、driveItemId、annotationId、versionId、syncBindingId、shareId、publicationId、toolUseId 无法和用户行为关联。

适合方向 B/C/D/E/F/H/J/K。

### 模式 4：持久化与恢复模式

检查：

- Prisma schema / migration 与服务逻辑不一致。
- DataRepository 写入失败、部分写入、覆盖或迁移不兼容。
- 云盘 item、upload session、storage object、share、publication、public URL 状态不一致。
- 评论 thread/comment/target、版本记录、change log、sync baseline/snapshot/binding 状态不一致。
- 审计日志、运行日志写入失败后业务状态不可信。
- 错误重试或恢复路径缺失。

适合方向 C/D/E/F/K。

### 模式 5：性能与资源模式

检查：

- 无分页、无上限、无取消的大列表、大目录、大日志、大历史。
- 递归扫描、同步 IO、重复 hash/parse、N+1 查询。
- renderer 里每次 render 都进行大计算。
- 事件订阅、watcher、interval、child process、file handle 泄漏。
- 状态更新造成循环请求、事件风暴或重复广播。
- 大文件上传/下载/预览缺少流式处理或大小 guard。

适合方向 D/E/F/G/K。

### 模式 6：重复实现与抽象缺口模式

检查：

- 同一逻辑 5+ 行出现 3+ 次。
- 重复处涉及路径安全、文件名清洗、权限、脱敏、状态转换、schema、MCP tool、日志、同步一致性、版本语义或持久化。
- 至少一处已经和其他处不一致，或新增能力明显只改了一处。
- 可以明确指出应该抽成哪个共享 helper/service/schema/domain。

适合方向 H/I/J/K/L。

### 模式 7：内置能力对齐模式

检查：

- 产品能力代码与 MCP domain/tool/dispatcher 是否一致。
- `*_type_list` / `*_type_describe` 或动态 discovery 是否包含新增类型。
- Synapse skill-package、内置 skill/rule/prompt 模板是否仍教 Agent 使用正确工具、字段、默认值和调用顺序。
- Agent guide/API reference 是否描述当前行为。
- 相关测试是否覆盖 Agent-facing discovery contract。
- 用户可感知的 MCP/内置能力行为变化是否记录在 `RELEASE_NOTES_PENDING.md`。

适合方向 C/F/J，尤其适合 Synapse Skill 安装器、密钥工具、蜂群任务 MCP/Workflow 节点和云盘 Agent 使用指南。

### 模式 8：同步一致性与本地访问模式


重点要求：

- 路径 containment 使用 `path.relative` 语义，不使用字符串前缀。
- 本地真实路径、远端 item id、版本 id、评论 target 和同步 binding id 不得互相混用。
- 文件和文件夹必须分别验证；目录创建、空目录、嵌套目录和递归 children 不得被文件同步逻辑顺手吞掉。
- 云端起点和本地起点必须分别验证；单向可用不能证明双向同步可用。
- 同步状态必须区分 pending、running、failed、conflict、completed、stale，不要把“请求成功”当“内容一致”。
- 失败恢复必须保留用户能理解的下一步：重试、重新绑定、跳过、手动解决冲突或重新检测。
- 本地不可访问、远端不可访问和权限不可访问要区分，不要统一显示成泛化失败。

适合方向 E/L。

### 模式 9：UI 状态与体验模式

如果扫描 UI，重点检查源码可证明的问题：

- 硬编码颜色或不走 token。
- 自定义按钮、卡片、弹窗等替代已有 shadcn 组件。
- 卡片套卡片、连续 Divider、shadow + border + background 同时堆层级。
- loading / error / empty / disabled 状态缺失。
- 表单 label/input、表格数字、icon/text 对齐明显违反仓库规则。
- 文案包含功能介绍、实现解释、重复状态、欢迎横幅、AI 自称或装饰性 emoji。
- 成功/失败/空态文案会误导用户对云盘、编辑保存、评论、版本、同步、权限、分享、发布或公开访问状态的理解。

禁止仅凭“看起来不好看”提交 UI Issue。

### 模式 10：权限、安全与审计模式

检查敏感操作：

- 管理 API 是否都走 admin guard。
- 用户 API 是否限制到当前用户和当前团队。
- 团队、项目、云盘资源、评论、版本、同步绑定是否可被其他主体读取或修改。
- 云盘编辑、评论、版本恢复、同步、分享、发布、下载、预览、zip 是否可越权访问或泄露。
- token、cookie、Authorization、provider key、share password、side-channel token、data-server token 是否脱敏。
- 敏感操作是否有审计或结构化日志。

适合发现 P0/P1/security/logging/architecture。

### 模式 11：历史低覆盖挖掘模式

从覆盖地图里选择低命中文件或长期未审计功能，往前看历史原因。

候选：

- 旧兼容代码仍被新入口调用。
- 新能力迁移后旧入口残留并造成无效操作。
- 老 helper 的语义和新模块硬边界冲突。
- 旧文档/内置 skill/API reference 未随产品能力变化。
- 旧同步/版本/评论兼容代码仍按旧 contract 写入或读取。

适合方向 M。

## 问题发现标准

每个问题必须有完整证据链：

```text
触发入口 → 代码链路（文件:行号 → 文件:行号） → 错误结果/品质缺口 → 用户影响或复盘阻断
```

合格条件：

- 能在代码中证明问题存在，不需要运行 App、dev server、浏览器或 Playwright。
- 影响本轮重点范围中的正常路径，或是合理高概率边界。
- 至少串起 3 层相关文件；单文件局部猜测默认不合格。
- 用 `rg` 确认过影响范围。
- 涉及历史或最近提交时，用 `git log` / `git show` / `git blame` 确认过最终落下的代码。
- 涉及 UI 时，确认过项目组件库和 token 规则，不把主观审美当 Issue。
- 涉及 Workflow 迁移时，能说明原文、备份、版本、迁移步骤、失败隔离或 legacy 找回怎样影响当前用户数据。
- 涉及多资源参数时，能说明类型、基数、顺序和跨入口 contract 怎样产生真实错误。
- 涉及文件系统/可访问性时，能说明受信任根、realpath、符号链接、权限、原子写入或废纸篓和当前用户路径的关系。
- 涉及 Agent 持久化时，能说明 conversation、toolUseId、事件终态、transcript 或存储 key 怎样影响会话隔离。
- 涉及性能时，能说明复杂度、无界增长或重复资源消耗来自哪里。
- 涉及重复实现时，能说明至少 3 处重复和具体不一致风险。
- 涉及内置能力对齐时，能指出产品/MCP/skill/guide/test 哪些面不一致。
- 用 `NOT.md` 确认过不属于刻意设计。
- 用 `AGENTS.md` 确认过不违反当前仓库硬规则和模块边界判断。
- 能解释为什么不属于已有 Issue 或同根因。
- 后续修复 Agent 能根据 Issue 直接开工。

不合格条件：

- 需要运行 App、dev server、浏览器或 Playwright 才能确认。
- 只是“感觉不太好”但逻辑没错。
- 仅缺测试覆盖。
- 仅缺日志，且没有用户可见失败、审计风险、安全风险或复盘阻断。
- 只是代码风格偏好。
- 命中 `NOT.md` 中明确说明应保留的刻意设计。
- 与已有 Issue 同根因。
- 证据链只有单个文件局部猜测，没有入口和结果。
- 迁移、资源基数、文件系统、会话隔离、性能、抽象或对齐问题没有证明当前用户或 Agent 能触发。

## Issue 创建质量闸门

创建 Issue 前必须回答 16 个问题：

```text
1. 用户、Agent 或管理员从哪里触发？
2. 代码链路是什么？
3. 当前错误结果、意外表现、性能退化、对齐缺口或复盘阻断是什么？
4. 为什么这是正常功能路径或合理高概率边界，而不是极端猜测？
5. 是否查过最近 7 天风险地图和覆盖地图？
6. 如果涉及最近或历史变更，是否复盘了最终落下的代码，而不是只看提交标题？
7. 是否查过 NOT.md，确认不是刻意设计？
8. 是否查过 AGENTS.md，确认不是仓库硬规则允许或要求的行为？
9. 是否查过本地索引？
10. 是否查过 GitHub 已有 Issue？
11. 是否和已有 Issue 同根因？
12. 如果涉及关键用户操作，日志/审计/运行记录是否足够支撑复盘？
13. 如果涉及敏感数据，脱敏是否覆盖 tool input、tool result、日志、导出和 UI？
14. 如果涉及迁移/资源基数/文件系统/会话隔离，是否能说明数据、路径、身份、版本或状态如何影响真实用户？
15. 如果涉及性能/抽象/对齐/回归，是否有具体 contract、规模、重复、文档偏差或 HEAD 当前证据？
16. 后续修复 Agent 能否按这个 Issue 直接开工？
```

任一答不出来：

- 不创建 Issue。
- 在最终输出列为 `rejected candidate`。

### 2. GitHub Issue 去重

```sh

```

对比：

- 标题中的 priority/type/summary。
- body 中的 `Local fingerprint`。
- 同一文件、同一 symbol、同一用户结果。
- 同一根因的不同表现。

如果 GitHub 已有同问题，无论 open/closed 都跳过。

### 3. 同根因去重

如果新发现和已有 Issue 共享同一上游根因，只能提交更上游、更准确的一条；不要为每个下游表现拆多个 Issue。

示例：

- 同一个 Workflow 读取入口绕过 migration gateway，导致编辑、MCP、Automation 和快照展示表现不同。提交一个统一读取根因 Issue。
- 同一个 `allowMultiple` 归一化错误导致 UI 预设、MCP 和 Workflow Call 都丢失资源。提交一个参数基数根因 Issue。
- 同一个 Skill 身份或原子替换校验缺口同时影响重新安装和密钥更新。提交一个安装写入根因 Issue。
- 同一个卸载目标 realpath 校验缺口影响系统 App 与 IDE 管理入口。提交一个公共卸载服务根因 Issue。
- 同一个 conversation/toolUseId 路由错误导致自动标题和问题答案串会话。提交一个会话路由根因 Issue。
- 同一个 MCP schema 漂移导致 Synapse skill-package、dispatcher 和 UI 示例都错误。提交一个能力对齐根因 Issue。
- 同一个日志脱敏函数漏处理密钥或本地路径，不要按每个调用点拆多个 Issue。
