# 飞书远程连接方案

更新时间：2026-04-23

## 1. 目标

基于 `cc-connect-main` 的现有实现，梳理一套可迁移的“飞书扫码创建应用并连接本地客户端”的方案，要求满足：

- 用户在本地运行一个命令或打开一个页面后，可以看到二维码。
- 用户用手机飞书扫码后，在手机上完成飞书 APP 的创建/授权。
- 本地客户端自动拿到飞书 `app_id/app_secret`。
- 本地客户端保存凭证并在重启或热加载后与飞书建立长连接。
- 后续飞书消息可以进入客户端内部的统一会话/消息路由层。

这份文档既面向 Synapse，也面向其他软件。核心目标不是复刻 UI，而是抽出可以复用的协议、状态机、数据模型和模块边界。

## 2. 核心结论

一句话结论：

这套能力的核心不是“服务端生成二维码图片”，而是“调用飞书官方应用注册设备流，拿到 `verification_uri_complete`，再由本地客户端把这个 URL 渲染成二维码”。

完整链路分成两段：

1. Setup 平面
   - 调飞书注册接口
   - 拿 `device_code`
   - 拿 `verification_uri_complete`
   - 本地渲染二维码
   - 轮询直到换回 `client_id/client_secret`
   - 写入本地配置

2. Runtime 平面
   - 用保存好的 `app_id/app_secret`
   - 启动飞书 SDK 客户端
   - 建立长连接 WebSocket
   - 接收飞书事件
   - 归一化消息
   - 交给内部会话引擎

重点认知：

- 扫码成功后回来的不是“用户登录态”，而是“飞书应用凭证”。
- 二维码内容本质上就是一个 URL，所以 CLI、Web、Electron 都可以本地出码。
- 运行时连接飞书时，真正需要的是 `app_id/app_secret`，不是前面扫码时的 `device_code`。
- Lark 国际版和 Feishu 国内版需要做域名切换兼容。

## 5. 端到端流程

### 5.1 扫码建应用流程

1. 用户执行 `setup`。
2. 客户端调用飞书注册接口 `action=init`。
3. 客户端确认服务端支持 `client_secret` 注册方式。
4. 客户端调用飞书注册接口 `action=begin`。
5. 飞书返回：
   - `device_code`
   - `verification_uri_complete`
   - `interval`
   - `expire_in`
6. 客户端把 `verification_uri_complete` 渲染成二维码。
7. 用户用手机飞书扫码并确认。
8. 客户端用 `device_code` 轮询 `action=poll`。
9. 飞书返回以下之一：
   - `authorization_pending`
   - `slow_down`
   - `access_denied`
   - `expired_token`
   - `client_id/client_secret`
10. 成功后，客户端将：
   - `client_id` 映射为 `app_id`
   - `client_secret` 映射为 `app_secret`
   - 保存 `platform_type`
   - 可选保存 `owner_open_id`
11. 客户端提示重启或执行热加载。
12. 运行时连接器使用 `app_id/app_secret` 启动。

### 5.2 绑定已有应用流程

1. 用户直接输入已有 `app_id/app_secret`。
2. 客户端调用：
   - `https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal`
   - 或 `https://open.larksuite.com/open-apis/auth/v3/tenant_access_token/internal`
3. 校验凭证是否可用。
4. 根据响应判断平台是 `feishu` 还是 `lark`。
5. 保存配置。
6. 重启或热加载运行时连接器。

### 5.3 运行时消息链路

1. 运行时连接器启动。
2. 用 `app_id/app_secret` 初始化飞书 SDK。
3. 调 `/open-apis/bot/v3/info` 取 bot 自己的 `open_id`。
4. 建立长连接 WebSocket。
5. 收到 `im.message.receive_v1`。
6. 做去重、鉴权、群消息 @bot 过滤。
7. 把消息转成统一 `Message`。
8. 根据 session key 投递给内部 Agent 会话。
9. Agent 输出结果后，通过 `Reply` 或 `Send` 回发飞书。

## 6. 飞书注册协议

### 6.1 接口

- Feishu：`POST https://accounts.feishu.cn/oauth/v1/app/registration`
- Lark：`POST https://accounts.larksuite.com/oauth/v1/app/registration`
- `Content-Type: application/x-www-form-urlencoded`

### 6.2 init

请求：

```text
action=init
```

响应示意：

```json
{
  "supported_auth_methods": ["client_secret"]
}
```

约束：

- 如果返回了 `supported_auth_methods`，且其中不包含 `client_secret`，则流程终止。

源码位置：

- `runRegistrationFlow()` 中的 init 调用：`cmd/cc-connect/feishu.go:544`

### 6.3 begin

请求：

```text
action=begin
archetype=PersonalAgent
auth_method=client_secret
request_user_info=open_id
```

响应示意：

```json
{
  "device_code": "xxx",
  "verification_uri_complete": "https://....",
  "interval": 5,
  "expire_in": 600
}
```

关键点：

- `verification_uri_complete` 就是二维码内容。
- 不需要服务器返回图片。

源码位置：

- CLI begin：`cmd/cc-connect/feishu.go:555`
- Web begin：`core/setup.go:64`

### 6.4 poll

请求：

```text
action=poll
device_code=<device_code>
```

可能响应：

```json
{ "error": "authorization_pending" }
```

```json
{ "error": "slow_down" }
```

```json
{ "error": "access_denied" }
```

```json
{ "error": "expired_token" }
```

```json
{
  "client_id": "cli_xxx",
  "client_secret": "sec_xxx",
  "user_info": {
    "open_id": "ou_xxx",
    "tenant_brand": "feishu"
  }
}
```

轮询状态机：

- `authorization_pending`：继续等待
- `slow_down`：轮询间隔增加 5 秒
- `access_denied`：用户拒绝
- `expired_token`：二维码过期
- 有 `client_id/client_secret`：成功结束

源码位置：

- CLI poll：`cmd/cc-connect/feishu.go:596`
- Web poll：`core/setup.go:96`

## 11. `owner_open_id` 与 `allow_from`

扫码成功后，飞书会返回一个 `user_info.open_id`。

`cc-connect` 的处理方式是：

- 可以把它作为 `owner_open_id` 保存流程中的输入
- 可以 best-effort 合并进 `allow_from`
- 但同时也提醒：这个值未必总能直接当作最终 ACL 真值

CLI 的提醒逻辑：

- `/Users/liyang/Documents/code/demo/cc-connect-main/cmd/cc-connect/feishu.go:237`

文档里的提醒：

- `/Users/liyang/Documents/code/demo/cc-connect-main/docs/feishu.md:117`

迁移建议：

- 不要把扫码返回的 `open_id` 当作绝对可信的唯一授权依据。
- 更稳妥的做法是：
  - 先作为默认 owner 或 allowlist seed
  - 后续让用户在 IM 中执行 `/whoami`
  - 再人工确认是否要限制访问

## 14. session key 与 reply context

这部分对“远程连接是否真的可用”非常关键。

### 14.1 session key

`cc-connect` 的默认规则：

- 普通模式：`feishu:<chatID>:<userID>`
- channel 共享模式：`feishu:<chatID>`
- thread 隔离模式：`feishu:<chatID>:root:<rootID>`

源码：

- `makeSessionKey()`：`platform/feishu/feishu.go:2331`

### 14.2 reply context

飞书的 `replyContext` 至少包含：

- `messageID`
- `chatID`
- `sessionKey`

这样后续回复时，平台层可以决定：

- 调 `Reply`
- 或调 `Create`
- 或按 thread 回复

### 14.3 从 session key 重建 reply context

函数：

- `ReconstructReplyCtx()`：`platform/feishu/feishu.go:2585`

这项能力的作用：

- 让定时任务、重启通知、主动消息也能找到正确会话目标

迁移要求：

- 你的平台连接器最好也支持 `sessionKey -> replyCtx` 重建
- 否则后续很多“无来信主动推送”功能会受限

## 15. 发送回复的策略

发送回复时，`cc-connect` 不是一律发新消息，而是区分：

- 有原始 `messageID`：优先调用 Reply

## 16. 必须实现的模块边界

如果要迁移到其他软件，建议拆成以下 5 个模块。

### 16.1 Registration Client

- 调 `init`
- 调 `begin`
- 调 `poll`

- 输出统一状态枚举

```ts

  deviceCode: string;
  qrUrl: string;
  interval: number;
  expiresIn: number;

type PollResult =
  | { status: "pending"; baseUrl: string; interval: number }
  | { status: "slow_down"; baseUrl: string; interval: number }
  | { status: "denied" }
  | { status: "expired" }
  | {
      status: "completed";
      platform: RegistrationBrand;
      appId: string;
      appSecret: string;
      ownerOpenId?: string;
    };
```

### 16.2 QR Setup Orchestrator

职责：

- 调 begin
- 触发二维码显示
- 轮询 poll
- 失败重试
- 成功后调 save

### 16.3 Credential Store

职责：

- 保存 `platform_type/app_id/app_secret`
- 可选保存 `allow_from`
- 如果软件有 workspace/project 概念，负责自动补齐项目结构

### 16.4 Feishu Runtime Connector

职责：

- SDK 初始化
- bot self info
- WebSocket / webhook
- 事件分发
- 消息归一化
- 回复发送

### 16.5 Internal Message Bridge

职责：

- 接收平台层 `Message`
- 映射到软件内部会话
- 调 agent / tool / command core
- 回写平台回复

## 17. 可直接交给其他模型的实现任务书

下面这段可以直接作为另一个大模型的编码任务输入。

```text
请在现有软件中实现“飞书扫码创建应用并连接本地客户端”的能力。

目标：
1. 用户点击“连接飞书”或运行 setup 命令后，客户端展示二维码。
2. 用户用手机飞书扫码后，在手机上完成飞书 APP 创建/授权。
3. 客户端自动拿到 app_id/app_secret 并持久化。
4. 客户端重启或热加载后，用这组凭证建立飞书长连接。
5. 飞书消息进入软件内部统一会话层。

必须遵守的协议：

A. 飞书注册接口
- POST https://accounts.feishu.cn/oauth/v1/app/registration
- Content-Type: application/x-www-form-urlencoded

1) init
action=init

2) begin
action=begin
archetype=PersonalAgent
auth_method=client_secret
request_user_info=open_id

begin 成功后，服务端会返回：
- device_code
- verification_uri_complete
- interval
- expire_in

二维码内容就是 verification_uri_complete。

3) poll
action=poll
device_code=<device_code>

可能返回：
- authorization_pending
- slow_down
- access_denied
- expired_token
- client_id/client_secret

如果 user_info.tenant_brand == "lark"，后续 poll 域名切到：
- https://accounts.larksuite.com

B. 绑定已有应用
- 如果用户已经有 app_id/app_secret，则直接调用：
  - https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal
  - 或 https://open.larksuite.com/open-apis/auth/v3/tenant_access_token/internal
- 用返回结果校验凭证并判断 platform_type

C. 运行时连接器
- 用 app_id/app_secret 初始化飞书 SDK
- 启动时先请求 /open-apis/bot/v3/info 获取 bot open_id
- 默认走 WebSocket 长连接
- 至少接以下事件：
  - im.message.receive_v1
  - card.action.trigger（如果支持交互卡片）
- 收到消息后必须做：
  - 去重
  - 群聊 @bot 过滤
  - allowlist 校验
  - session key 推导
  - 统一消息结构转换

D. 统一消息结构至少包含：
- sessionKey
- platform
- messageID
- userID
- chatID
- content
- replyCtx

E. replyCtx 至少包含：
- chatID
- messageID
- sessionKey

F. 发送回复规则
- 有 messageID 时优先 reply
- 没有 messageID 时 fallback create/send
- 图片和文件先上传，再发送消息

G. 持久化规则
- 保存 platform_type, app_id, app_secret
- 如果软件有 project/workspace 概念：
  - project 不存在则自动创建
  - connector 不存在则自动补齐

H. 验收标准
- 可以完整走一遍扫码 -> 手机确认 -> 本地拿凭证 -> 重启 -> 飞书发消息 -> 客户端收到 -> 回复飞书
```

## 18. 在 Synapse 中的建议落位

基于当前 Synapse 的项目约束，建议这样落位：

### 18.1 Electron 主进程

建议放在 `desktop/electron/` 下，职责包括：

- 飞书注册设备流网络调用
- 凭证落盘
- 重启或热加载控制
- 运行时长连接管理

原因：

- 这是带凭证的外部平台接入能力
- 不应把 `app_secret` 和平台长连接逻辑直接放到 renderer
- 更符合当前仓库“主进程负责特权能力，renderer 只通过窄 preload API 调用”的边界

### 18.2 Renderer

建议放在 `desktop/src/modules/feishu-remote/`，若目录不存在则创建。

Renderer 只负责：

- 点击“开始连接”
- 展示二维码
- 展示轮询状态
- 收集错误信息

不要在 React 组件里直接：

- 请求飞书官方接口
- 保存凭证
- 管理 WebSocket 长连接

### 18.3 Preload / IPC

建议暴露最小接口：

```ts
beginFeishuSetup(): Promise<BeginResult>
pollFeishuSetup(deviceCode: string, baseUrl?: string): Promise<PollResult>
saveFeishuCredentials(input: SaveInput): Promise<{ restartRequired: boolean }>
restartAppOrService(): Promise<void>
```

### 18.4 运行时消息桥

如果 Synapse 后续也要支持“飞书消息驱动本地 agent 会话”，建议内部同样定义统一平台层接口，而不是让飞书逻辑直接耦合到某一个 chat view。

## 19. 风险与注意事项

### 19.1 官方接口依赖

这套方案依赖飞书的应用注册接口：

- `accounts.feishu.cn/oauth/v1/app/registration`

这是核心前提。迁移时要先实际验证当前账号和网络环境是否还能稳定使用该接口。

### 19.2 Lark/Feishu 双域名

如果只写 Feishu 域名，不处理 Lark，国际版用户会卡死在 setup 阶段。

### 19.3 交互卡片事件

如果你支持卡片但没有配置 `card.action.trigger`，用户会看到按钮点击无响应。

### 19.4 `owner_open_id` 不宜过度信任

它可以作为默认 seed，但不建议把它当成最终唯一 ACL 真值。

### 19.5 必须有重启或热重载策略

凭证保存成功不等于运行时已经连接成功。因为运行时连接器通常只在应用启动时创建一次。

## 20. 验收标准

最小可交付验收：

1. 用户在本地点击“连接飞书”后能看到二维码。
2. 二维码内容来自 `verification_uri_complete`。
3. 用户扫码并在手机确认后，客户端能拿到 `app_id/app_secret`。
4. 凭证能被持久化到本地配置或数据库。
5. 客户端重启或热加载后，可以与飞书建立长连接。
6. 用户从飞书发一条消息，客户端能收到并路由到内部会话。
7. 客户端能把回复发回飞书。
8. 群聊里未 @bot 的消息默认不会误触发。
9. 配置了 allowlist 时，未授权用户消息不会进入内部会话层。

增强验收：

1. 支持 Feishu 和 Lark 自动识别。
2. 支持二维码过期后的自动重试。
3. 支持绑定已有 `app_id/app_secret`。
4. 支持交互卡片及 `card.action.trigger`。
5. 支持从 `sessionKey` 重建 `replyCtx`，用于主动消息和定时消息。

## 21. 最终建议

如果只是要在 Synapse 里快速落地，建议按这个顺序做：

1. 先做 setup 平面
   - begin
   - poll
   - save
   - 本地二维码展示

2. 再做最小 runtime connector
   - app_id/app_secret 初始化
   - `/bot/v3/info`
   - WebSocket 长连接
   - 文本消息收发

3. 最后再补增强能力
   - 交互卡片
   - 文件/图片
   - thread 隔离
   - allowlist 管理
   - 主动消息 / 定时消息

对 Synapse 来说，第一阶段最重要的不是把 UI 做复杂，而是把这条“扫码拿凭证 -> 保存 -> 运行时连上飞书”的主链跑通。
