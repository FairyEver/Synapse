## Agent 检查报告 - API完整性+CLI/MCP健壮性+Service安全边界

检查时间：2026-04-23 17:57

### 缺陷列表

#### [严重程度: 🔴 严重]

**建表和加列未运行时校验字段类型，SQL 片段直接拼接**
- 位置：`desktop/electron/data-store/service.ts:233`, `desktop/electron/data-store/service.ts:316`, `desktop/electron/data-store/http-server.ts:82`
- 问题：`columns[].type` 和 `column.type` 只依赖 TypeScript 断言/MCP schema，进入 service 后直接拼进 `CREATE TABLE` / `ALTER TABLE`。
- 预期行为：设计文档只允许 `TEXT | INTEGER | REAL | BLOB | JSON`，外部 HTTP/CLI/MCP 输入必须运行时校验。
- 实际行为：HTTP dispatch 只是 `as { type: ... }`，service 未校验枚举；恶意或错误类型可以写入任意 SQL 类型片段。
- 影响：可创建不符合设计的 schema；在 `db.exec()` 多语句场景下存在破坏表结构或数据的风险。

**数据字段名、where、orderBy 未统一校验，存在 SQL 注入/畸形 SQL 风险**
- 位置：`desktop/electron/data-store/service.ts:40`, `desktop/electron/data-store/service.ts:340`, `desktop/electron/data-store/service.ts:417`, `desktop/electron/data-store/service.ts:519`, `desktop/electron/data-store/service.ts:535`
- 问题：`q()` 只包双引号但不转义双引号；`insert/update` 的 `data` key、`where[].field`、对象 where key、`orderBy.field` 均未调用列名校验；`where[].op` 和 `orderBy.dir` 也未运行时校验。
- 预期行为：设计文档要求表名/列名规则正确，所有生成 SQL 的表名列名安全引用，where 操作符仅允许 `= != > < >= <= LIKE`，orderBy dir 仅允许 `asc/desc`。
- 实际行为：外部请求可传入任意字段名、操作符、排序方向，导致 SQL 语义被篡改或直接报错。
- 影响：查询/更新/删除边界不可靠；本地 token 泄露或 MCP/CLI 误传参数时可能造成越权查询、批量更新失败或数据破坏。

**导入数据库流程缺少失败回滚，可能删除当前数据库后无法恢复**
- 位置：`desktop/electron/data-store/service.ts:493`, `desktop/electron/data-store/service.ts:496`, `desktop/electron/data-store/service.ts:498`, `desktop/electron/data-store/service.ts:500`
- 问题：`importDatabase()` 验证源文件后先关闭当前连接，再 `unlinkSync(this.dbPath)`，随后 `copyFileSync(sourcePath, this.dbPath)` 和重新打开；中间任一步失败都没有备份/回滚。
- 预期行为：设计文档要求“验证 → 关闭 → 替换 → 重新打开”，替换流程应保证失败不丢当前库，至少先备份/原子替换。
- 实际行为：目标路径删除后复制失败会留下无数据库或半导入状态，service 也可能保持关闭。
- 影响：导入路径不可读、磁盘满、权限错误或源文件损坏时会造成当前数据丢失和数据服务不可用。

#### [严重程度: 🟡 中等]

**rawSQL 只拦截 `_meta_tables`，没有禁止所有 `_` 前缀表**
- 位置：`desktop/electron/data-store/service.ts:436`
- 问题：限制逻辑实际只匹配 `_meta_tables`，并未拦截任意 `_` 前缀系统表名。
- 预期行为：设计文档要求 `rawSQL` 禁止操作 `_` 前缀表，例子只是 `_meta_tables`。
- 实际行为：`DROP TABLE "_other_system"`、`CREATE TABLE "_shadow"` 这类 `_` 前缀表操作不会被当前正则拒绝。
- 影响：系统保留命名空间可被 rawSQL 污染，后续新增系统表时会直接暴露给外部 SQL。

**JSON 列无法按整体等值条件正确查询**
- 位置：`desktop/electron/data-store/service.ts:44`, `desktop/electron/data-store/service.ts:511`, `desktop/electron/data-store/service.ts:523`
- 问题：`insert/update` 会把 JSON 列序列化，但 `buildWhere()` 不知道当前表的 JSON 列，where value 为对象时会走 `String(v)` 变成 `[object Object]`。
- 预期行为：设计文档说明 JSON 列对调用方透明，where 不支持内部字段但支持整体等值匹配。
- 实际行为：`query({ where: { json_col: { a: 1 } } })` 无法匹配已存储的 JSON 字符串。
- 影响：JSON 列“透明”语义不完整，AI/MCP 侧按对象查询会稳定查不到数据。

**HTTP API 缺少请求参数运行时校验，缺参错误不友好且可能误入 service**
- 位置：`desktop/electron/data-store/http-server.ts:64`, `desktop/electron/data-store/http-server.ts:82`, `desktop/electron/data-store/http-server.ts:101`, `desktop/electron/data-store/http-server.ts:111`
- 问题：dispatch 对 `name/table/data/rows/id/sql` 只做类型断言，不验证必填、对象/数组形态、数字范围、limit/offset 合法性。
- 预期行为：参数缺失、类型错误、畸形 JSON 应返回明确错误，不应让 service 层抛 TypeError 或 SQLite 错误。
- 实际行为：例如 `columns` 缺失、`data` 为 null、`limit` 为 NaN 都会进入后续逻辑后再失败。
- 影响：HTTP/CLI/MCP 三端得到的错误信息不可预测，也会扩大 SQL 构造边界风险。

**addColumn 的 DDL 与元数据更新不在同一事务**
- 位置：`desktop/electron/data-store/service.ts:324`, `desktop/electron/data-store/service.ts:325`
- 问题：`ALTER TABLE` 成功后才单独更新 `_meta_tables.updated_at`，两步之间没有显式事务。
- 预期行为：设计文档要求写操作使用事务，结构变更和 `_meta_tables` 维护应同步。
- 实际行为：如果元数据更新失败，实际表结构已改变但 `_meta_tables` 未同步。
- 影响：表结构和元数据时间戳可能不一致，管理界面/CLI 展示会误导。

**MCP tools/call 对 params 形态未校验，部分无效请求会变成未处理 Promise**
- 位置：`desktop/data-store/mcp/index.ts:231`, `desktop/data-store/mcp/index.ts:232`, `desktop/data-store/mcp/index.ts:264`, `desktop/data-store/mcp/index.ts:267`
- 问题：`params` 在进入 `try` 前被强制读取 `.name` / `.arguments`；`handleRequest()` 又以 `void` 调用，外层没有捕获 async reject。
- 预期行为：JSON-RPC 无效请求应返回规范错误对象，包含 `error.code` 和 `error.message`。
- 实际行为：`{"method":"tools/call"}` 这类请求会抛 TypeError，可能没有 JSON-RPC 响应并污染 stderr/进程状态。
- 影响：AI 编辑器侧会遇到挂起或不可解释的 MCP 调用失败。

**MCP inputSchema 对 query 的 where/orderBy 没有真实 schema**
- 位置：`desktop/data-store/mcp/index.ts:127`, `desktop/data-store/mcp/index.ts:128`
- 问题：`where` 和 `orderBy` 只有 description，没有 `oneOf`、对象/数组结构、操作符枚举或 dir 枚举。
- 预期行为：MCP tool schema 应与实际 API 参数一致，帮助客户端生成和校验参数。
- 实际行为：客户端无法从 schema 知道 where 数组表达式、orderBy 字符串/对象形式的合法结构。
- 影响：AI 通过 MCP 更容易生成错误参数，错误会延迟到 HTTP/service 层才暴露。

**CLI JSON 参数解析和 --where 解析不健壮**
- 位置：`desktop/data-store/cli/index.ts:133`, `desktop/data-store/cli/index.ts:141`, `desktop/data-store/cli/index.ts:157`, `desktop/data-store/cli/index.ts:179`
- 问题：`--data/--batch` 缺值或 JSON 畸形只返回底层 JSON.parse 文案；`--where` 使用 `split("=")`，值中包含 `=` 会被截断，空值条件会被静默忽略。
- 预期行为：参数缺失和 JSON 解析失败应有面向 CLI 用户的明确提示；`--where k=v` 应至少保留第一个 `=` 后的完整值并报告非法条件。
- 实际行为：`--where token=a=b` 会变成 `token=a`；`--where title=` 不报错但过滤条件消失。
- 影响：脚本化调用会出现静默误查询/误更新前置查询，排查成本高。

**CLI/MCP 的 app 存活检测只看 PID，且网络请求没有超时**
- 位置：`desktop/data-store/shared/resolve-user-data.ts:33`, `desktop/data-store/shared/resolve-user-data.ts:42`, `desktop/data-store/mcp/index.ts:198`
- 问题：`process.kill(pid, 0)` 只能证明 PID 存在，不能证明是 Synapse；MCP 还会缓存 `serverInfo`，后续不重新检查；`fetch()` 未设置 timeout。
- 预期行为：设计文档要求 CLI/MCP 通过 PID 检查兜底 app crash 残留文件，并在 app 未运行时正确提示。
- 实际行为：PID 被复用时会误判 app 运行；端口不可达时只能等待底层 fetch 失败或挂起，错误文案不稳定。
- 影响：`data-server.json` 残留时 CLI/MCP 体验不可靠，并发脚本可能长时间卡住。

#### [严重程度: 🟢 轻微]

## Agent 检查报告 - Service 深审 + 三端能力对等 + CLI/MCP 健壮性

检查时间：2026-04-23 18:02

### 缺陷列表

#### [严重程度: 🔴 严重]

**运行时输入未做校验，SQL 片段直接由外部参数拼接**
- 位置：`desktop/electron/data-store/service.ts:233`、`desktop/electron/data-store/service.ts:316`、`desktop/electron/data-store/service.ts:343`、`desktop/electron/data-store/service.ts:417`、`desktop/electron/data-store/service.ts:519`、`desktop/electron/data-store/service.ts:536`、`desktop/electron/data-store/http-server.ts:81`
- 问题：`createTable` / `addColumn` 直接插入 `column.type`，`insert` / `update` 直接插入请求里的 key，`query.where` / `query.orderBy` 直接插入 `field` / `op` / `dir`，而 HTTP/MCP/IPC 边界只是把 `unknown` 强转成 TypeScript 类型，没有任何运行时白名单校验。
- 预期行为：按设计文档对表名、列名、类型、操作符、排序方向做运行时校验；查询字段应限定为合法列名，`dir` 只能是 `asc|desc`，`op` 只能是设计文档列出的 7 种操作符。
- 实际行为：任意字符串都能进入 SQL 模板；缺参数时也会以 `TypeError` 或 SQLite 语法错误的形式暴露给调用方。
- 影响：HTTP / MCP / IPC 都存在 SQL 注入和异常请求打崩单次调用的风险，接口错误信息也会变成内部实现细节而不是友好校验错误。

#### [严重程度: 🔴 严重]

**`rawSQL` 会绕过 `_meta_tables` 和 `jsonColumns` 的一致性维护**
- 位置：`desktop/electron/data-store/service.ts:433`
- 问题：`rawSQL` 只拦截 `_meta_tables`，但没有拦截其他 `_` 前缀表，也没有在执行 `CREATE TABLE` / `DROP TABLE` / `ALTER TABLE` 后同步 `_meta_tables` 和 `jsonColumns` 缓存。
- 预期行为：按设计文档禁止所有 `_` 前缀表操作；如果允许 schema 级 raw SQL，就必须同步维护元数据和 JSON 列缓存，或者显式禁止这类 DDL。
- 实际行为：`rawSQL` 可以创建/删除/修改用户表结构，但 `listTables` / `describeTable` / `query` 仍然只相信 `_meta_tables` 和旧缓存。
- 影响：会出现“真实表存在但列表不可见”“表已删除但元数据仍残留”“JSON 列缓存过期”的状态漂移，三端看到的数据服务状态会不一致。

#### [严重程度: 🔴 严重]

**导入流程不是原子替换，失败时可能删除当前数据库并让服务停在关闭状态**
- 位置：`desktop/electron/data-store/service.ts:474`
- 问题：导入只做了 `_meta_tables` 存在性和列名检查，然后直接 `close()` 当前库、`unlinkSync()` 删除旧库、`copyFileSync()` 覆盖新库并重新打开；中间任何一步失败都没有回滚。
- 预期行为：按设计文档先完整验证导入库 schema，再用临时文件和回滚路径做原子替换；替换失败时应恢复旧库并保持服务可用。
- 实际行为：复制失败、目标文件损坏、重新打开失败时，当前数据库已经被删除，`this.db` 也已经被关闭。
- 影响：导入失败可直接造成数据丢失和服务不可用，属于高风险故障路径。

#### [严重程度: 🔴 严重]

**“数据库损坏恢复”过于激进，普通打开错误也会触发重建**
- 位置：`desktop/electron/data-store/service.ts:64`
- 问题：`open()` 把打开数据库、切 WAL、`integrity_check` 的所有异常都当成“损坏”，然后重命名主库并新建空库；同时没有一起处理 `-wal` / `-shm` sidecar。
- 预期行为：只在确认损坏时才执行恢复；权限错误、临时 I/O 错误、磁盘满等场景不应直接重建；WAL/SHM 也要一起隔离。
- 实际行为：任何异常都会进入“corrupted or unreadable, creating fresh database”分支。
- 影响：一次暂时性的打开失败就可能触发不可逆的数据重建，且遗留的 WAL/SHM 文件还可能继续污染新库。

#### [严重程度: 🔴 严重]

**WAL 模式下导出只复制 `.db` 主文件，无法保证导出一致性**
- 位置：`desktop/electron/data-store/service.ts:470`
- 问题：当前导出实现只是 `copyFileSync(this.dbPath, targetPath)`，没有 checkpoint，也没有复制 `-wal` / `-shm`。
- 预期行为：在 WAL 模式下应使用 SQLite backup/checkpoint 方案，或显式处理 sidecar 文件，保证导出快照完整。
- 实际行为：导出得到的只是主库文件。
- 影响：最近写入的数据可能只在 WAL 中，导出的 `.db` 恢复后会丢失最新事务。

#### [严重程度: 🟡 中等]

**JSON 列在 `query.where` 中不会透明序列化，文档承诺的整体等值匹配实际上不可用**
- 位置：`desktop/electron/data-store/service.ts:378`、`desktop/electron/data-store/service.ts:511`
- 问题：插入和更新 JSON 列时会 `JSON.stringify`，但 `buildWhere()` 对 JSON 条件值走的是通用 `toSqlValue()`，对象会变成 `\"[object Object]\"`。
- 预期行为：按设计文档，JSON 列查询应支持“整体等值匹配”，调用方无需手动 stringify。
- 实际行为：`where: { meta: { a: 1 } }` 或数组式条件里的对象值都无法匹配到已存储的 JSON 字符串。
- 影响：HTTP / MCP / IPC 的 JSON 列查询契约不成立，调用方会遇到“写得进去、查不出来”的行为偏差。

#### [严重程度: 🟡 中等]

**CLI 的 `--where k=v` 解析不健壮，值中包含 `=` 会被截断，非法条件会被静默忽略**
- 位置：`desktop/data-store/cli/index.ts:152`
- 问题：CLI 用 `args[i].split(\"=\")` 解析条件，只取前两个片段；没有 `=` 的条件也不会报错。
- 预期行为：按设计要求，CLI 至少应可靠解析 `k=v`；值里包含 `=` 时不能被截断，非法输入应有明确报错。
- 实际行为：`title=a=b` 会被解析成 `title=a`，其余部分被丢弃；`foo` 这样的条件会被直接忽略。
- 影响：CLI 查询结果会和调用者预期不一致，且问题难以定位。

### 缺陷列表

#### 严重程度: 🔴 严重

**rawSQL 绕过 `_meta_tables` 和 JSON 列缓存维护，导致结构化能力失真**
- 位置：`desktop/electron/data-store/service.ts:155`, `desktop/electron/data-store/service.ts:180`, `desktop/electron/data-store/service.ts:433`
- 问题：`rawSQL()` 直接执行任意 SQL，没有在 `CREATE TABLE` / `DROP TABLE` / `ALTER TABLE` 后同步 `_meta_tables`，也不会刷新 `jsonColumns` 缓存。
- 预期行为：设计文档要求 `_meta_tables` 自动维护所有用户表元数据，JSON 列缓存也要在建表、加列、删表、导入后保持一致。
- 实际行为：只有 `createTable` / `dropTable` / `addColumn` / `importDatabase` 会维护元数据或缓存，`rawSQL` 完全旁路。
- 影响：经 `rawSQL` 创建或修改的表可能不会出现在 `listTables`，后续 `query` / `update` / `delete` / `describeTable` 也会因为 `assertTableExists()` 失败而不可用；JSON 列会出现序列化/反序列化失配。

**`importDatabase()` 在替换失败时会丢失当前数据库**
- 位置：`desktop/electron/data-store/service.ts:474`
- 问题：导入流程在验证后直接 `close()` + `unlinkSync(this.dbPath)` 删除现有数据库，再执行 `copyFileSync()` 和重新打开，没有回滚路径。
- 预期行为：设计要求“验证 → 关闭 → 替换 → 重新打开”，但替换过程应保证失败时保留原库，至少不能先删后拷。
- 实际行为：目标路径不可写、磁盘满、源文件读失败、重新打开失败时，旧库已被删除，服务也处于关闭或半初始化状态。
- 影响：导入失败可直接造成用户数据丢失，是高风险数据破坏缺陷。

**SQL 组装对运行时输入缺少白名单校验，存在注入和非法 SQL 风险**
- 位置：`desktop/electron/data-store/service.ts:40`, `desktop/electron/data-store/service.ts:233`, `desktop/electron/data-store/service.ts:316`, `desktop/electron/data-store/service.ts:343`, `desktop/electron/data-store/service.ts:417`, `desktop/electron/data-store/service.ts:517`, `desktop/electron/data-store/service.ts:533`
- 问题：`q()` 只做双引号包裹、不转义内部引号；`createTable` / `addColumn` 把 `type` 直接拼进 SQL；`buildWhere()` / `buildOrderBy()` 对 `field` / `op` / `dir` 没有任何运行时校验；`insert` / `update` 的列名也未校验。
- 预期行为：设计文档要求表名/列名只允许字母数字下划线，操作符仅允许 `= != > < >= <= LIKE`，排序方向仅允许 `asc/desc`，字段类型仅允许 `TEXT/INTEGER/REAL/BLOB/JSON`。
- 实际行为：HTTP、CLI、MCP 进入 service 后基本依赖 TypeScript 类型断言，外部 JSON 输入可以把任意字符串直接带进 SQL 模板。
- 影响：恶意请求可注入额外 SQL、构造非法 DDL/DML、绕过结构约束，属于服务端输入校验缺失。

#### 严重程度: 🟡 中等

**JSON 列的 `where` 等值查询不透明，对象值会被转成 `[object Object]`**
- 位置：`desktop/electron/data-store/service.ts:44`, `desktop/electron/data-store/service.ts:378`, `desktop/electron/data-store/service.ts:517`
- 问题：`query()` 对结果集会按 JSON 列做 `JSON.parse`，但 `buildWhere()` 对对象值调用的是 `toSqlValue()`，会退化成 `String(v)`。
- 预期行为：设计文档要求 JSON 列“对调用方完全透明”，`where` 对 JSON 列整体等值匹配时应自动序列化后比较。
- 实际行为：`{ where: { payload: { a: 1 } } }` 在 SQL 层会变成 `payload = '[object Object]'`。
- 影响：JSON 列查询命中率错误，调用方只能手动 `JSON.stringify` 规避，与接口设计不一致。

**`rawSQL` 仅封禁 `_meta_tables`，没有封禁所有 `_` 前缀系统表**
- 位置：`desktop/electron/data-store/service.ts:433`
- 问题：限制规则写成了 `/_meta_tables/` 特判，而不是设计要求的“禁止操作所有 `_` 前缀表”。
- 预期行为：任何 `_` 开头的系统表都不应允许被 `rawSQL` 访问。
- 实际行为：当前只拦截 `_meta_tables`，未来新增系统表或其他 `_` 前缀内部表都会暴露给 `rawSQL`。
- 影响：系统元数据保护面不完整，后续扩展时容易被误操作或恶意操作破坏。

**删除最后一张表后，下次启动会强制重建 bookmarks demo 表**
- 位置：`desktop/electron/data-store/service.ts:123`
- 问题：`ensureDemoTable()` 以 `_meta_tables` 行数是否为 0 作为唯一判断条件，只要没有任何表元数据就重新插入 `bookmarks` 和示例数据。
- 预期行为：设计文档已经定义“demo 表被删除后”的空状态，说明用户应能把系统清空并保持空状态。
- 实际行为：只要 app 重新打开，空库就会被再次填充 demo 数据。
- 影响：用户无法真正删除默认示例表，产品定义的空状态在重启后不可达。

**CLI 的 `status`、未知命令和大部分参数错误都被全局“app 未运行”短路**
- 位置：`desktop/data-store/cli/index.ts:68`, `desktop/data-store/cli/index.ts:76`, `desktop/data-store/cli/index.ts:206`
- 问题：CLI 在进入 `switch` 前就强制读取 `data-server.json` 并检查 PID，只要 app 未运行，`status`、未知命令提示、很多本地用法错误提示都不会执行。
- 预期行为：`synapse status` 至少应能输出“未运行/端口文件残留”等状态，未知命令和本地参数错误也应独立于 app 存活。
- 实际行为：实测 `synapse status` 和 `synapse unknown` 都直接返回 `Synapse app is not running. Please start Synapse first.`。
- 影响：排障体验差，无法用 `status` 观察残留端口文件场景，也削弱了 CLI 的自解释能力。

**CLI 的 `--where` / `--limit` 解析不健壮**
- 位置：`desktop/data-store/cli/index.ts:147`
- 问题：`--where` 直接 `split("=")`，值中包含 `=` 会被截断；`--limit` 直接 `parseInt()`，缺失或非法值不会报错。
- 预期行为：设计要求 `--where k=v` 可用，至少应完整保留值部分并在 `--limit` 非法时给出明确错误。
- 实际行为：`title=a=b` 会被解析成 `title=a`，`--limit not-a-number` 会静默传出 `NaN`。
- 影响：CLI 查询条件会被错误解析，脚本化调用结果不可预测。

**CLI / MCP 只做 PID 探测且共享 HTTP 客户端无超时，死进程与半挂起都不够稳健**
- 位置：`desktop/data-store/shared/resolve-user-data.ts:33`, `desktop/data-store/shared/resolve-user-data.ts:42`, `desktop/data-store/mcp/index.ts:200`
- 问题：`isAppRunning()` 仅基于 `process.kill(pid, 0)`，无法确认该 PID 一定是 Synapse，也不会校验 HTTP 端口是否可达；`apiCall()` 没有超时或 AbortSignal。
- 预期行为：设计要求 CLI/MCP 用 PID 检测兜底，但真正调用前还应确认端口可用，并在网络异常时快速失败。
- 实际行为：本次环境中 `data-server.json` 残留、PID 已死，HTTP 已拒绝连接；若 PID 被其他进程复用，CLI/MCP 仍可能误判“app 在运行”，且请求可能长时间挂起。
- 影响：端口文件残留、PID 复用、端口半开等场景下，CLI/MCP 的错误诊断不可靠，脚本调用可能无期限卡住。

**MCP tool schema 与实际 API 不完全一致，空行输入也会被当作协议错误**
- 位置：`desktop/data-store/mcp/index.ts:77`, `desktop/data-store/mcp/index.ts:231`, `desktop/data-store/mcp/index.ts:264`
- 问题：`add_column` 的 `inputSchema` 没有暴露 API 已支持的 `column.default`；stdio 读取对空行不做忽略，直接返回 `-32700 Parse error`。
- 预期行为：tool schema 应与 HTTP/API 参数一致；line-based 输入应忽略空行或噪音行。
- 实际行为：MCP 客户端无法从 schema 发现 `default` 能力，且空行会制造额外协议错误响应。
- 影响：MCP 能力面被低估，部分客户端集成会收到不必要的 parse error 噪音。

### 缺陷列表

#### 🔴 严重

**结构化查询与更新路径存在 SQL 注入面**
- 位置：`desktop/electron/data-store/service.ts:40-42`, `desktop/electron/data-store/service.ts:341-345`, `desktop/electron/data-store/service.ts:417-420`, `desktop/electron/data-store/service.ts:511-536`

- 位置：`desktop/electron/data-store/service.ts:470-502`

### 缺陷列表

#### 🔴 严重

**字段类型未做运行时白名单校验，DDL 拼接存在 SQL 结构破坏风险**
- 位置：`desktop/electron/data-store/service.ts:233`、`desktop/electron/data-store/service.ts:316`、`desktop/electron/data-store/http-server.ts:82`
- 问题：`createTable` / `addColumn` 只校验列名，不校验 `type` 是否属于 `TEXT | INTEGER | REAL | BLOB | JSON`，HTTP 层只是 TypeScript 断言，CLI `parseColDef` 也直接 `toUpperCase()` 后透传。
- 预期行为：设计文档要求字段类型只支持 TEXT、INTEGER、REAL、BLOB、JSON。
- 实际行为：任意字符串可进入 `CREATE TABLE ... ${col.type}` 或 `ALTER TABLE ... ${column.type}`，且使用 `db.exec()` 执行 DDL。
- 影响：外部 HTTP/CLI/MCP 输入可制造非法 schema，严重时可通过 DDL 字符串破坏 SQL 结构；这是核心数据服务入口的安全边界缺失。

#### 🔴 严重

**where/orderBy/data 字段名和操作符未校验，存在标识符/操作符注入风险**
- 位置：`desktop/electron/data-store/service.ts:40`、`desktop/electron/data-store/service.ts:340`、`desktop/electron/data-store/service.ts:417`、`desktop/electron/data-store/service.ts:517`、`desktop/electron/data-store/service.ts:533`
- 问题：`q(name)` 只是直接包双引号，不转义 `"`；`insert`/`update` 的 data keys、`where.field`、对象 where 的 key、`orderBy.field`、`where.op`、`orderBy.dir` 都未经过运行时校验。
- 预期行为：设计文档要求表名/列名校验正确，where 操作符仅支持 `=`, `!=`, `>`, `<`, `>=`, `<=`, `LIKE`，orderBy 方向仅支持 asc/desc。
- 实际行为：HTTP/MCP JSON 可传入任意字段名、任意 op/dir；`prepare()` 只保护值参数，不能保护 SQL 片段。
- 影响：查询/更新可被构造为语法错误、绕过条件或改变 SQL 结构；即使多语句被 SQLite 拒绝，也会造成 API 不稳定和安全边界缺失。

#### 🔴 严重

**导入数据库先关闭并删除当前库，复制失败会导致服务无库可用**
- 位置：`desktop/electron/data-store/service.ts:493`
- 问题：`importDatabase()` 校验源文件后立即 `close()`，随后 `unlinkSync(this.dbPath)`，再 `copyFileSync(sourcePath, this.dbPath)`；复制失败没有回滚，也没有在 catch/finally 中重新打开旧库。
- 预期行为：导入应验证通过后安全替换，失败则拒绝导入并保持原数据库可用。
- 实际行为：目标库可能已被删除且连接已关闭，后续 service 调用会报 `Data store is not open` 或数据文件缺失。
- 影响：源文件在验证后被移动/权限变化/磁盘满/复制中断时，会造成数据服务不可用甚至本地数据丢失。

#### 🔴 严重

**WAL 模式下导出只复制主 db 文件，可能漏掉未 checkpoint 的数据**
- 位置：`desktop/electron/data-store/service.ts:66`、`desktop/electron/data-store/service.ts:470`
- 问题：服务启用 `PRAGMA journal_mode=WAL`，但 `exportDatabase()` 仅 `copyFileSync(this.dbPath, targetPath)`，没有 checkpoint，也没有使用 SQLite backup API 或同时处理 `-wal`/`-shm`。
- 预期行为：导出为完整 SQLite 数据库文件。
- 实际行为：WAL 中尚未 checkpoint 的写入可能不在复制出的 `.db` 文件中。
- 影响：用户导出的备份可能缺数据，导入后表现为数据回退或缺行。

## Agent 检查报告 - API/Service/CLI/MCP 对等性与健壮性

检查时间：2026-04-23 18:20

实现覆盖结论：11 个结构化接口、CLI 命令和 MCP tools 都已接入，主要缺陷集中在运行时参数校验、导入导出安全性、CLI/MCP 鲁棒性，以及 `addColumn` 的三端参数不对等。

### 缺陷列表

#### 严重程度: 🔴 严重

**查询/更新路径直接拼接未校验的字段名、操作符和排序方向**
- 位置：`desktop/electron/data-store/service.ts:40`, `desktop/electron/data-store/service.ts:343`, `desktop/electron/data-store/service.ts:417`, `desktop/electron/data-store/service.ts:511`, `desktop/electron/data-store/service.ts:533`
- 问题：`q()` 只做双引号包裹，不做转义；`buildWhere()` 直接信任 `field/op`，`buildOrderBy()` 直接信任 `field/dir`，`insert/update` 也直接使用请求体里的 key 生成 SQL。
- 预期行为：按设计文档只允许合法列名、固定操作符（`=`, `!=`, `>`, `<`, `>=`, `<=`, `LIKE`）和 `asc/desc` 排序方向，并在生成 SQL 前做严格校验。
- 实际行为：HTTP/CLI/MCP 传入的任意字符串都会进入 SQL 拼接路径，最轻是语法错误，最重会形成 SQL 注入面。
- 影响：`query` / `insert` / `update` 的边界输入不安全，与“表名/列名校验规则正确”“where/orderBy 语法受控”的设计要求不一致。

**DDL 类型字符串未做运行时白名单校验**
- 位置：`desktop/electron/data-store/service.ts:233`, `desktop/electron/data-store/service.ts:316`
- 问题：`createTable()` 和 `addColumn()` 直接把 `col.type` / `column.type` 拼进 DDL，没有任何运行时白名单校验。
- 预期行为：只允许设计文档列出的 `TEXT`、`INTEGER`、`REAL`、`BLOB`、`JSON` 五种类型。
- 实际行为：类型约束只存在于 TypeScript 静态类型里；HTTP、CLI、MCP 传入非法字符串时仍会进入 SQL。
- 影响：会导致非法 schema、执行期异常，甚至把额外 SQL 片段带入 DDL。

**WAL 模式下导出只复制主库文件**
- 位置：`desktop/electron/data-store/service.ts:470`
- 问题：导出逻辑仅 `copyFileSync(this.dbPath, targetPath)`，没有做 checkpoint，也没有处理 `-wal` / `-shm`。
- 预期行为：导出的 `.db` 应该完整包含当前已提交数据。
- 实际行为：数据库在 WAL 模式下长期打开时，最新事务可能只存在于 `synapse-data.db-wal`，导出文件可能落后于当前状态。
- 影响：用户拿到的备份可能是旧数据或不完整快照，导出功能不可靠。

**导入流程先删活库再复制，失败时无回滚**
- 位置：`desktop/electron/data-store/service.ts:474`
- 问题：`importDatabase()` 在验证后立刻 `close()` 并 `unlinkSync(this.dbPath)`，随后才复制新文件并重新打开。
- 预期行为：导入失败时应保留当前可用数据库，至少要做到原库可回退。
- 实际行为：只要复制或重新打开过程中失败，当前数据库已经被删除；同时验证阶段只检查 `_meta_tables` 存在和列名，不校验 schema 细节是否真的“正确”。
- 影响：导入失败会造成真实数据丢失，也可能接受结构不完整的外部数据库。

**CLI/MCP 共享 HTTP 客户端没有超时控制**
- 位置：`desktop/data-store/shared/resolve-user-data.ts:42`
- 问题：`apiCall()` 直接调用 `fetch()`，没有 `AbortSignal`、没有超时、也没有对网络异常做统一转换。
- 预期行为：当 app 未启动、端口黑洞、网络连接异常时，应在可预期时间内返回友好错误。
- 实际行为：当前只能依赖底层网络栈何时失败；如果命中“端口可连但不返回”的场景，CLI/MCP 会一直挂住。
- 影响：脚本化调用不稳定，自动化场景会卡死。

**MCP `tools/call` 缺少 `params` 时会直接崩溃进程**
- 位置：`desktop/data-store/mcp/index.ts:231`, `desktop/data-store/mcp/index.ts:264`
- 问题：`handleRequest()` 在 `tools/call` 分支里先访问 `params.name`，访问发生在 `try/catch` 之外。
- 预期行为：无效请求应返回 JSON-RPC `error`（例如 `-32602 Invalid params`）或至少返回 MCP `isError` 结果。

- 影响：单个畸形请求即可杀死 MCP server，鲁棒性不足。

#### 严重程度: 🟡 中等

## Agent 检查报告 - Service 安全性 + CLI/MCP 契约

### 缺陷列表

#### [严重程度: 🔴 严重]

**`where` / `orderBy` / 列类型缺少运行时校验，service 层允许未验证 SQL 片段进入拼接**
- 位置：`desktop/electron/data-store/service.ts:233`、`desktop/electron/data-store/service.ts:316`、`desktop/electron/data-store/service.ts:519`、`desktop/electron/data-store/service.ts:536`
- 问题：`createTable`/`addColumn` 直接把 `col.type` 拼进 SQL；`buildWhere` 直接拼 `cond.field`、`cond.op`；`buildOrderBy` 直接拼 `field`、`dir`。这些约束只存在于 TypeScript 类型里，HTTP/CLI/MCP 的运行时输入没有真正校验。
- 预期行为：设计文档只允许 `TEXT/INTEGER/REAL/BLOB/JSON` 列类型，`where.op` 只允许 `= != > < >= <= LIKE`，`orderBy.dir` 只允许 `asc/desc`，字段名也应遵守表/列命名规则。
- 实际行为：非法值会一路进入 SQL 组装层，最轻是返回底层 SQL 错误，最重会让调用方构造出超出设计约束的语句片段。
- 影响：service 是 HTTP/CLI/MCP/IPC 共用底座，这个缺口会同时影响三端，并且属于注入面。

**WAL 模式下导出只复制主库文件，导出的 `.db` 可能丢最近写入**
- 位置：`desktop/electron/data-store/service.ts:66`、`desktop/electron/data-store/service.ts:470`
- 问题：数据库在 `open()` 里明确启用了 `PRAGMA journal_mode=WAL`，但 `exportDatabase()` 仅执行 `copyFileSync(this.dbPath, targetPath)`，没有先做 checkpoint，也没有包含 `-wal` / `-shm`。
- 预期行为：设计文档要求导出是可恢复的全量 `.db` 文件；在 WAL 模式下应先把最新事务刷回主库，或使用 SQLite backup 机制。
- 实际行为：导出的主库文件可能不包含仍停留在 WAL 中的最新事务。
- 影响：导出的备份不完整，导入后会出现“刚写过的数据消失”的数据完整性问题。

#### [严重程度: 🟡 中等]

**JSON 列的等值查询不透明，`where` 传对象时不会按设计做 JSON 序列化**
- 位置：`desktop/electron/data-store/service.ts:384`、`desktop/electron/data-store/service.ts:523`
- 问题：写入和查询结果阶段都对 JSON 列做了透明处理，但 `buildWhere()` 完全不知道当前表的 `jsonColumns`，直接把对象交给 `toSqlValue()`，最终会变成 `"[object Object]"`。
- 预期行为：设计文档要求 JSON 列对调用方透明，`where` 至少支持“整体等值匹配”。
- 实际行为：`query({ where: { meta: { a: 1 } } })` 无法匹配以 JSON 字符串存储的真实值；数组形式的表达式查询也有同样问题。
- 影响：JSON 列一旦需要过滤，HTTP/IPC/MCP 三端都会失真，调用方只能退回 `rawSQL`。

**导入流程不是原子替换，验证也只做了浅检查**
- 位置：`desktop/electron/data-store/service.ts:474`、`desktop/electron/data-store/service.ts:482`、`desktop/electron/data-store/service.ts:493`、`desktop/electron/data-store/service.ts:500`
- 问题：`importDatabase()` 只检查 `_meta_tables` 是否存在以及 4 个列名是否在；随后直接 `close() -> unlinkSync() -> copyFileSync() -> new DatabaseSync()`，中途没有回滚路径。
- 预期行为：设计文档要求“验证 -> 关闭 -> 替换 -> 重新打开”的流程是安全的，至少应验证导入库完整性、元数据与真实表的一致性，并在替换失败时保留旧库。
- 实际行为：只要复制或重新打开失败，当前数据库就已经被关闭或替换；畸形但满足浅校验的数据库也可能被导入。
- 影响：导入失败会把服务留在不可用状态，或把不一致元数据带入运行态。

**CLI 的 `query --where` / `--limit` 解析不健壮，实测会截断值并把非法 limit 送成 `null`**
- 位置：`desktop/data-store/cli/index.ts:152`、`desktop/data-store/cli/index.ts:157`、`desktop/data-store/cli/index.ts:163`
- 问题：`args[i].split(\"=\")` 只保留第一段 key 和第二段 value，值里再出现 `=` 会被静默截断；`parseInt()` 的结果不做校验，`NaN` 在请求体里会变成 `null`。
- 预期行为：设计文档要求 `--where k=v` 对特殊字符、多个条件和值里包含 `=` 的场景都能稳健处理；`--limit` 非数字时应直接报 usage 错误。
- 实际行为：本地 mock 验证 `query demo --where title=a=b status=active --limit foo` 最终发出的请求体是 `{\"action\":\"query\",\"table\":\"demo\",\"where\":{\"title\":\"a\",\"status\":\"active\"},\"limit\":null}`。
- 影响：CLI 的查询条件会 silently 失真，用户以为查的是 `a=b`，服务端收到的却是 `a`。

**CLI 在校验命令前就要求 app 运行，未知命令和参数错误会被“app 未运行”掩盖**
- 位置：`desktop/data-store/cli/index.ts:68`、`desktop/data-store/cli/index.ts:76`、`desktop/data-store/cli/index.ts:82`、`desktop/data-store/cli/index.ts:214`
- 问题：`readServerInfo()` 和 `isAppRunning()` 发生在 `switch (command)` 之前，导致命令本身是否合法、参数是否缺失，都要等“app 正在运行”这个前置条件通过后才有机会报出来。
- 预期行为：未知命令、缺少 `--data` / `--batch`、错误参数格式等 CLI 语法问题，应优先返回 CLI 自己的 usage 或 unknown command。

- 影响：真正的参数问题被运行态问题掩盖，用户和脚本都拿不到可操作的错误信息。

**MCP 服务没有做基本 JSON-RPC 请求校验，非 2.0 请求和缺失 `id` 的请求仍会被当成正常调用**

### 缺陷列表

#### [严重程度: 🔴 严重]

**`createTable` / `addColumn` 未对白名单类型做运行时校验，DDL 可被任意 `type` 串污染**
- 位置：`desktop/electron/data-store/service.ts:233`, `desktop/electron/data-store/service.ts:316`, `desktop/electron/data-store/http-server.ts:81`, `desktop/data-store/cli/index.ts:36`
- 问题：service 直接把 `column.type` 拼进 `CREATE TABLE` / `ALTER TABLE`，HTTP 侧只是类型断言，CLI 侧只是 `toUpperCase()`，没有任何运行时白名单校验。
- 预期行为：设计文档只允许 `TEXT` / `INTEGER` / `REAL` / `BLOB` / `JSON` 五种类型。
- 实际行为：任意字符串都会进入 SQL；在 `db.exec(...)` 语义下，这不只是“接受非法类型”，还给额外 DDL 片段留出了注入面。
- 影响：可破坏 schema，绕过设计约束，严重时可能执行额外 DDL，属于高风险输入面。

**`query` 的 `where` / `orderBy` 直接拼接未校验的字段名、操作符和排序方向**
- 位置：`desktop/electron/data-store/service.ts:40`, `desktop/electron/data-store/service.ts:384`, `desktop/electron/data-store/service.ts:517`, `desktop/electron/data-store/service.ts:533`
- 问题：`q()` 只做双引号包裹，不转义引号；`buildWhere()` 信任 `field` / `op`，`buildOrderBy()` 信任 `field` / `dir`，都没有复用建表阶段的名称校验和固定枚举。
- 预期行为：查询阶段应只接受合法列名，`op` 只能取文档列出的操作符，`dir` 只能是 `asc` / `desc`。
- 实际行为：HTTP/MCP 调用方可以构造带引号、注释或额外表达式的参数，改变单条 SQL 的语义或直接制造语法错误。
- 影响：筛选/排序结果可被篡改，错误输入会直接打到 SQL 层，安全边界明显弱于设计要求。

**WAL 模式下的导入导出流程不安全，失败时可能把服务留在不可用状态**
- 位置：`desktop/electron/data-store/service.ts:470`, `desktop/electron/data-store/service.ts:474`
- 问题：`exportDatabase()` 只复制主 `.db` 文件；`importDatabase()` 关闭当前连接后只替换主 `.db`，既不 checkpoint，也不处理 `-wal` / `-shm`，如果复制或重新打开失败也没有回滚路径。
- 预期行为：导入导出应在 WAL 模式下生成一致的 `.db`，并在失败时保证现有服务可恢复。
- 实际行为：导出可能遗漏仍停留在 WAL 中的最新提交；导入可能混入旧 sidecar 文件，或者在失败后留下“HTTP 还活着但 `db` 已关闭”的半故障状态。
- 影响：存在数据丢失、导入后库不一致、服务不可用的高风险。

#### [严重程度: 🟡 中等]

**`rawSQL` 只禁止 `_meta_tables`，没有真正落实“禁止所有 `_` 前缀表操作”**
- 位置：`desktop/electron/data-store/service.ts:433`
- 问题：限制逻辑只匹配 `_meta_tables`，并没有按设计阻断全部 `_` 前缀系统表。
- 预期行为：任何 `_` 前缀表都不应被 `rawSQL` 访问或修改。
- 实际行为：当前只拦 `_meta_tables`；未来若增加 `_jobs`、`_meta_columns` 等系统表，会直接暴露给 `rawSQL`。
- 影响：系统表保护是不完整的，后续扩展时很容易被绕过。

**JSON 列查询不是“透明”的：`where` 条件不会按 JSON 列规则序列化**
- 位置：`desktop/electron/data-store/service.ts:383`, `desktop/electron/data-store/service.ts:517`
- 问题：插入和更新路径会根据 `jsonColumns` 把值 `JSON.stringify()`，但 `buildWhere()` 完全不知道字段是否为 JSON 列，普通对象最终会走 `String(v)` 变成 `[object Object]`。
- 预期行为：设计文档要求 JSON 列对调用方透明，查询时也应支持“整体等值匹配”。

#### 严重程度: 🔴 严重

**DDL 列类型只靠 TypeScript 约束，HTTP/CLI/MCP 运行时可写入任意 SQL 类型片段**
- 位置：`desktop/electron/data-store/service.ts:233`、`desktop/electron/data-store/service.ts:316`、`desktop/electron/data-store/http-server.ts:82`、`desktop/data-store/cli/index.ts:36`

- 实际行为：外部 JSON 请求可传入任意 `type` 字符串；SQLite 还会接受未知类型，`db.exec()` 场景下恶意片段风险更高。
- 影响：可创建非设计类型的 schema，严重时可能通过 DDL 拼接破坏数据库结构。

**动态列名、where 操作符、orderBy 方向未做运行时校验，存在 SQL 拼接风险**
- 位置：`desktop/electron/data-store/service.ts:340`、`desktop/electron/data-store/service.ts:417`、`desktop/electron/data-store/service.ts:517`、`desktop/electron/data-store/service.ts:533`

- 预期行为：列名遵守命名规则；where 只支持 `= != > < >= <= LIKE`；orderBy `dir` 只支持 `asc/desc`。
- 实际行为：非法字段名会进入 SQL 字符串，非法操作符/方向也会进入 SQL 字符串。
- 影响：轻则请求因 SQL 语法错误失败，重则形成 SQL 注入面；该风险同时暴露给 HTTP、CLI、MCP、IPC。

**WAL 模式下导出只复制主 `.db` 文件，导入失败也缺少回滚保护**
- 位置：`desktop/electron/data-store/service.ts:66`、`desktop/electron/data-store/service.ts:470`、`desktop/electron/data-store/service.ts:493`
- 问题：服务启用 WAL，但 `exportDatabase()` 只 `copyFileSync(this.dbPath, targetPath)`；`importDatabase()` 先关闭并删除当前 db，再复制新文件，没有备份/恢复，也没有处理 `-wal` / `-shm` 文件。
- 预期行为：导出是当前数据库的完整一致备份；导入验证后安全替换，失败时保留原数据库。
- 实际行为：导出可能漏掉 WAL 中尚未 checkpoint 的事务；导入复制失败或目标文件异常时，当前数据库可能已经被删除且服务未重新打开。
- 影响：数据丢失或导入后数据库状态不可恢复，是数据服务最核心的可靠性风险。

- 位置：`desktop/electron/data-store/service.ts:233`
- 问题：`createTable()` / `addColumn()` 直接把 `col.type` / `column.type` 拼进 SQL，没有运行时白名单校验。
- 预期行为：设计文档限定可用字段类型为 `TEXT, INTEGER, REAL, BLOB, JSON`。
- 实际行为：HTTP / MCP / IPC 调用方只要绕过 TS 类型，就能创建任意 SQLite 类型。
- 影响：文档与真实行为不一致，也会让 JSON 列缓存逻辑和上层 schema 假设失效。

**CLI 参数友好错误会被更早的运行态检查吞掉**
- 位置：`desktop/data-store/cli/index.ts:68`
- 问题：CLI 在进入 `switch(command)` 之前就强制读 `data-server.json` 并检查 `isAppRunning()`。
- 预期行为：设计文档要求缺参数时给出友好用法提示。
- 实际行为：当 PID 判活失败或 app 未运行时，`synapse create`、`synapse insert --data '{bad}'`、`synapse query ...` 都先报 “app is not running”，连用法 / JSON 错误都到不了。
- 影响：CLI 调试体验差，且把真实参数错误掩盖成运行态错误。

**CLI 的 `--where k=v` 解析对值中的 `=` 不健壮**
- 位置：`desktop/data-store/cli/index.ts:152`
- 问题：`args[i].split("=")` 只取前两段，后面的内容直接丢弃。
- 预期行为：设计文档要求 `--where k=v` 解析健壮，至少不能把合法值截断。
- 实际行为：用 stub `fetch` 复现后，`title=a=b` 被发送成 `{"where":{"title":"a"}}`，`note=x=y=z` 被发送成 `"x"`。
- 影响：包含 `=` 的 URL、token、表达式值无法正确查询，CLI 与 HTTP 原生 API 行为不一致。

**CLI / MCP 的 HTTP 调用没有超时控制**
- 位置：`desktop/data-store/shared/resolve-user-data.ts:42`
- 问题：`fetch()` 没有 `AbortSignal` / timeout。
- 预期行为：设计文档显式要求关注网络请求超时处理。
- 实际行为：如果本地服务半开、卡住或只建立连接不返回，CLI / MCP 会一直挂起。
- 影响：脚本调用和编辑器 tool 调用都可能无界等待，难以恢复。

**MCP 没有做 JSON-RPC 基本校验，协议兼容性不足**
- 位置：`desktop/data-store/mcp/index.ts:210`
- 问题：`handleRequest()` 完全不校验 `jsonrpc` 是否等于 `"2.0"`、`id` 是否存在、`method` / `params` 是否为合法类型；`readline` 收到空行直接返回 `Parse error`。
- 预期行为：设计文档要求遵守 JSON-RPC 2.0，并对非法请求返回规范错误对象。
- 实际行为：实测 `{"jsonrpc":"1.0","id":1,"method":"tools/list"}` 仍被当成合法请求处理；`{"jsonrpc":"2.0","method":"tools/list"}` 会返回一个缺少 `id` 的响应；单独输入空行也会触发 parse error。
- 影响：严格实现 JSON-RPC 的客户端可能出现兼容性问题，且错误边界不稳定。

**MCP `inputSchema` 与实际 API 参数不一致**
- 位置：`desktop/data-store/mcp/index.ts:77`
- 问题：`add_column` 的 schema 没有 `default`，`query.where` / `query.orderBy` 只有描述，没有结构化 schema。
- 预期行为：设计文档要求 tool schema 与真实 API 参数一致，便于 AI 客户端正确构造参数。
- 实际行为：tool 真实会把 `default` 透传给 HTTP（已用 stub `fetch` 复现），但 `tools/list` 无法让客户端发现这一能力。
- 影响：Claude / Codex 等 MCP 客户端会低估或错误理解 tool 能力，影响可发现性和参数生成准确度。
