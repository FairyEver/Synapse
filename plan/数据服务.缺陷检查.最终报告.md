## 摘要

数据服务的 HTTP API、CLI、MCP、IPC 基础能力基本齐全，11 个结构化数据操作均已接入。主要风险集中在 Service 层运行时校验不足、WAL 模式下导入导出不安全、rawSQL 与元数据一致性漂移，以及 CLI/MCP 在异常环境下的鲁棒性不足。当前最优先应先修数据安全与 SQL 片段边界，再修三端契约和命令行/MCP 体验。

## 🔴 严重缺陷

### DS-001: Service 层允许未校验 SQL 片段进入 DDL/DML

- 模块：Service 层、HTTP API、CLI、MCP、IPC
- 位置：`desktop/electron/data-store/service.ts:40`、`desktop/electron/data-store/service.ts:233`、`desktop/electron/data-store/service.ts:316`、`desktop/electron/data-store/service.ts:343`、`desktop/electron/data-store/service.ts:417`、`desktop/electron/data-store/service.ts:519`、`desktop/electron/data-store/service.ts:536`
- 问题：`column.type`、`data` key、`where.field`、`where.op`、`orderBy.field`、`orderBy.dir` 都可从外部输入直接进入 SQL 拼接；`q()` 只包双引号，不转义内部双引号，也没有在动态列名路径复用名称校验。
- 影响：可创建设计外 schema，或构造畸形 SQL / SQL 片段注入；该风险会同时影响 HTTP、CLI、MCP、IPC 四个入口。
- 建议修复：在 Service 层集中增加运行时白名单校验，字段类型限定为 `TEXT | INTEGER | REAL | BLOB | JSON`，列名/表名先按统一规则校验，`where.op` 和 `orderBy.dir` 使用枚举校验；`q()` 只接收已校验标识符。
- 来源：多数报告合并，覆盖 17:57、18:02、18:04、18:07、18:08、18:16、18:20、18:24、18:25、18:27。

### DS-002: WAL 模式下导出只复制主库文件，备份可能不完整

- 模块：Service 层、IPC
- 位置：`desktop/electron/data-store/service.ts:66`、`desktop/electron/data-store/service.ts:470`
- 问题：数据库开启 `PRAGMA journal_mode=WAL`，但 `exportDatabase()` 只执行 `copyFileSync(this.dbPath, targetPath)`，未 checkpoint，也未通过 SQLite backup API 生成一致快照。
- 影响：最近提交的数据可能仍在 `synapse-data.db-wal`，导出的 `.db` 文件可能缺少最新事务，用户恢复备份后出现数据回退。
- 建议修复：导出前执行安全 checkpoint，或使用 SQLite backup API 生成单文件一致快照；导出路径也应明确失败错误。
- 来源：18:02、18:07、18:08、18:16、18:20、18:24、18:25、18:27。

### DS-003: 导入数据库先关闭并删除当前库，失败无回滚

- 模块：Service 层、IPC
- 位置：`desktop/electron/data-store/service.ts:474`、`desktop/electron/data-store/service.ts:493`、`desktop/electron/data-store/service.ts:496`、`desktop/electron/data-store/service.ts:498`、`desktop/electron/data-store/service.ts:500`
- 问题：`importDatabase()` 浅校验源库后先 `close()` 当前连接，再删除当前主库文件并复制源文件；复制失败、重新打开失败或 sidecar 文件污染时没有回滚。
- 影响：导入失败可能导致当前数据库被删除、服务停在关闭状态，属于真实数据丢失风险。
- 建议修复：先复制到临时文件并完整校验，保留当前库备份，使用原子替换；失败时恢复旧库并重新打开；同时处理或清理 `-wal` / `-shm`。
- 来源：多数报告合并，覆盖 17:57、18:02、18:04、18:07、18:08、18:16、18:20、18:24、18:25、18:27。

### DS-004: 数据库打开失败被一律当作损坏并重建空库

- 模块：Service 层
- 位置：`desktop/electron/data-store/service.ts:64`、`desktop/electron/data-store/service.ts:72`、`desktop/electron/data-store/service.ts:82`、`desktop/electron/data-store/service.ts:85`
- 问题：`open()` 将打开数据库、切 WAL、`integrity_check` 的所有异常都归为“corrupted or unreadable”，直接重命名旧库并新建空库。
- 影响：权限错误、临时 I/O 错误、磁盘满等非损坏场景也可能触发“恢复”流程，掩盖真实故障并造成用户误以为空库是正常状态。
- 建议修复：区分 `integrity_check` 失败与打开/权限/IO 错误；只有确认损坏时隔离重建，其他异常应向上抛出并阻止服务启动；隔离损坏库时同步处理 WAL/SHM。
- 来源：18:02、18:25。

## 🟡 中等缺陷

### DS-005: rawSQL 系统表限制过窄，且 DDL 会绕过元数据和 JSON 缓存维护

- 模块：Service 层、三端对等性
- 位置：`desktop/electron/data-store/service.ts:155`、`desktop/electron/data-store/service.ts:180`、`desktop/electron/data-store/service.ts:433`、`desktop/electron/data-store/service.ts:436`、`desktop/electron/data-store/service.ts:452`
- 问题：rawSQL 只实际拦截 `_meta_tables`，没有拦截所有 `_` 前缀系统表；同时允许 `CREATE TABLE` / `DROP TABLE` / `ALTER TABLE` 用户表，却不更新 `_meta_tables` 或 `jsonColumns` 缓存。
- 影响：会出现真实表与 `listTables` / `describeTable` 不一致，或 JSON 列缓存失效；未来新增系统表也默认暴露给 rawSQL。
- 建议修复：按设计禁止访问所有 `_` 前缀表；对 rawSQL DDL 要么禁止，要么执行后刷新/同步元数据和 JSON 缓存，并记录清晰契约。
- 来源：17:57、18:02、18:04、18:07、18:08、18:16、18:20、18:24、18:25。

### DS-006: JSON 列整体等值查询不透明

- 模块：Service 层、三端对等性
- 位置：`desktop/electron/data-store/service.ts:383`、`desktop/electron/data-store/service.ts:384`、`desktop/electron/data-store/service.ts:520`、`desktop/electron/data-store/service.ts:525`
- 问题：写入和读取结果时会根据 `jsonColumns` 做 JSON 处理，但 `buildWhere()` 不知道当前表 JSON 列，`where: { meta: { a: 1 } }` 会变成 `[object Object]`。
- 影响：设计文档承诺的“JSON 列整体等值匹配”不可用，调用方会遇到写得进去但查不到。
- 建议修复：让 `buildWhere()` 接收当前表的 JSON 列集合，JSON 列条件值先按写入规则 `JSON.stringify()`，并覆盖对象式和表达式数组两种 where。
- 来源：多数报告合并，覆盖 17:57、18:02、18:04、18:16、18:20、18:24、18:25、18:27。

### DS-007: HTTP API 只做类型断言，缺少请求形态校验

- 模块：HTTP API
- 位置：`desktop/electron/data-store/http-server.ts:64`、`desktop/electron/data-store/http-server.ts:76`、`desktop/electron/data-store/http-server.ts:82`、`desktop/electron/data-store/http-server.ts:97`、`desktop/electron/data-store/http-server.ts:111`、`desktop/electron/data-store/http-server.ts:126`
- 问题：`dispatch()` 对 `name`、`columns`、`column`、`table`、`data`、`rows`、`id`、`sql` 等参数使用 TypeScript 断言，没有运行时验证必填、对象/数组形态和数值范围。
- 影响：缺参或类型错误会进入 Service 后变成 TypeError 或 SQLite 错误，错误信息不稳定，也放大 DS-001 的 SQL 拼接边界风险。
- 建议修复：为每个 action 增加最小运行时 schema 校验，先返回明确 `{ ok:false, error }`，再调用 Service。
- 来源：17:57、18:02。

### DS-008: addColumn 的 DDL 与元数据更新时间不在同一事务

- 模块：Service 层
- 位置：`desktop/electron/data-store/service.ts:316`、`desktop/electron/data-store/service.ts:324`、`desktop/electron/data-store/service.ts:325`
- 问题：`ALTER TABLE` 成功后再单独更新 `_meta_tables.updated_at`，没有显式事务包裹两步。
- 影响：如果更新元数据失败，真实表结构已改变但更新时间未同步，管理界面和外部工具看到的结构元数据不可靠。
- 建议修复：用事务包住 `ALTER TABLE` 和 `_meta_tables` 更新；失败时回滚并保持 schema/metadata 同步。
- 来源：17:57、18:16、18:27。

### DS-010: CLI/MCP 存活检测只看 PID，HTTP 客户端无超时和非 JSON 包装

- 模块：CLI、MCP、共享客户端
- 位置：`desktop/data-store/shared/resolve-user-data.ts:33`、`desktop/data-store/shared/resolve-user-data.ts:42`、`desktop/data-store/shared/resolve-user-data.ts:53`、`desktop/data-store/mcp/index.ts:200`
- 问题：`isAppRunning()` 只执行 `process.kill(pid, 0)`，无法防 PID 复用，也会把某些 `EPERM` 场景当作未运行；`apiCall()` 没有 `AbortController` 超时，也没有处理非 JSON 响应。
- 影响：残留 `data-server.json`、端口半开、代理/错误页、PID 复用等场景下，CLI/MCP 可能误判、卡住或输出底层异常。
- 建议修复：判活时结合端口探测或健康检查；`apiCall()` 增加超时、`response.ok` 和非 JSON 错误包装；MCP 缓存刷新单独见 DS-014。
- 来源：17:57、18:02、18:04、18:08、18:16、18:20、18:24、18:25、18:27。

### DS-011: CLI 在命令校验前强制要求 app 运行，status 和错误提示被短路

- 模块：CLI
- 位置：`desktop/data-store/cli/index.ts:68`、`desktop/data-store/cli/index.ts:76`、`desktop/data-store/cli/index.ts:81`、`desktop/data-store/cli/index.ts:206`、`desktop/data-store/cli/index.ts:214`
- 问题：除了 help 外，CLI 在进入 `switch` 前就读取 `data-server.json` 并检查 PID，导致 `status`、未知命令、参数缺失和 JSON 错误都可能先被 “app is not running” 覆盖。
- 影响：端口文件残留时最需要诊断的 `synapse status` 反而不可用；脚本无法区分命令错误、参数错误和运行态错误。
- 建议修复：先做命令和参数形态校验；`status` 独立于 app 存活执行，并输出端口文件、PID、running 状态和可达性。
- 来源：18:04、18:07、18:20、18:24、18:25、18:27。

### DS-012: CLI 参数解析不健壮

- 模块：CLI
- 位置：`desktop/data-store/cli/index.ts:36`、`desktop/data-store/cli/index.ts:131`、`desktop/data-store/cli/index.ts:141`、`desktop/data-store/cli/index.ts:157`、`desktop/data-store/cli/index.ts:163`、`desktop/data-store/cli/index.ts:179`
- 问题：`parseColDef()`、`--where` 使用裸 `split()`；`--where title=a=b` 会截断；`--limit` 的 `NaN`、负数、小数未校验；`--data` / `--batch` 缺值或 JSON 畸形只冒泡底层 parse 错误。
- 影响：CLI 查询条件可能静默失真，非法 limit 继续发到 HTTP，脚本化调用排错困难。
- 建议修复：只按首个分隔符切分或支持 JSON 参数；显式校验 limit 为非负整数；包装 JSON parse 错误并指出具体 flag。
- 来源：多数报告合并，覆盖 17:57、18:02、18:04、18:07、18:08、18:16、18:20、18:24、18:25、18:27。

### DS-013: MCP JSON-RPC 边界校验不完整，tools/call 缺 params 可触发未处理 rejection

- 模块：MCP
- 位置：`desktop/data-store/mcp/index.ts:210`、`desktop/data-store/mcp/index.ts:231`、`desktop/data-store/mcp/index.ts:232`、`desktop/data-store/mcp/index.ts:264`、`desktop/data-store/mcp/index.ts:267`
- 问题：请求未校验 `jsonrpc === "2.0"`、`id`、`method` 和 `params` 形态；`tools/call` 在 try/catch 前读取 `params.name`；stdin handler 以 `void handleRequest(request)` 调用异步函数，没有捕获 reject。
- 影响：非 2.0 或缺 id 的请求会被当成合法请求；缺 `params` 的合法 JSON 请求可能导致 MCP 进程未处理 rejection 或退出，客户端等待无响应。
- 建议修复：增加 JSON-RPC envelope 校验；无效请求返回 `-32600` 或 `-32602`；把 `tools/call` 参数解包放入 try/catch；stdin handler 捕获 async reject。
- 来源：17:57、18:02、18:07、18:16、18:20、18:24、18:25、18:27。

### DS-014: 长驻 MCP 进程缓存 serverInfo，app 重启后不会刷新端口/token

- 模块：MCP
- 位置：`desktop/data-store/mcp/index.ts:198`、`desktop/data-store/mcp/index.ts:200`、`desktop/data-store/mcp/index.ts:202`
- 问题：`serverInfo` 只在首次 tool call 时读取，之后一直复用旧 port/token。
- 影响：Synapse 重启后同一个 MCP 进程可能持续请求旧端口或旧 token，用户需要重启编辑器/MCP 进程才能恢复。
- 建议修复：每次调用前校验端口文件 mtime / PID / token，或在网络失败、401、连接拒绝后清空缓存并重读。
- 来源：18:02、18:27。

### DS-015: MCP inputSchema 未完整表达真实 API 参数

### DS-016: addColumn 表名参数在 HTTP/CLI/MCP 与 IPC 间不一致

- 模块：HTTP API、CLI、MCP、IPC、三端对等性
- 位置：`desktop/electron/data-store/http-server.ts:96`、`desktop/data-store/cli/index.ts:122`、`desktop/data-store/mcp/index.ts:83`、`desktop/electron/data-store/ipc-handlers.ts:40`、`desktop/src/types/bridge.ts:199`

## 测试结果汇总

- `pnpm desktop:typecheck`：有报告显示通过。
- `pnpm desktop:build:data-store`：多份报告显示成功生成 CLI/MCP bundle；个别早期报告遇到 `desktop/dist-data-store/mcp/index.js` 不存在，属于测试时间点不一致。
- HTTP live CRUD：未形成可信通过结果。多数报告遇到 `data-server.json` 残留、端口连接失败、或当前审计环境限制 loopback 访问，因此没有完成真实 CRUD / 并发写入 / 边界 HTTP 测试。
- CLI：`synapse help` 可输出帮助；`synapse status`、`synapse tables` 在残留端口文件或 PID 判活失败时返回 `Synapse app is not running. Please start Synapse first.`；hook/mock 测试复现了 `--where` 截断和非法 `--limit` 发送问题。
- MCP：`initialize` 和 `tools/list` 可返回，tool 数量为 11；畸形 JSON 返回 `-32700`；未知 method 返回 `-32601`；`tools/call` 在 app 未运行时返回 tool-level `isError`；缺 `params` 的 `tools/call` 在多份报告中复现为崩溃或未处理 rejection。
- 环境结论：原始测试环境多次处于 `data-server.json` 残留、PID 死亡、PID 探测 EPERM 或 loopback 被限制的状态，不能用这些测试证明 HTTP CRUD 正常，只能证明 CLI/MCP 需要更稳健的判活和超时处理。

## 误报列表

### 误报-001: exportDB / importDB / installCLI / registerMCP 未暴露给 HTTP/CLI/MCP

- 原始报告：多份能力矩阵中标记为 ❌。
- 误报原因：产品设计将这些能力定义为管理界面/设置页能力，当前仅 IPC 暴露是合理边界；真实缺陷在 export/import 的 Service 实现安全性，而不是三端缺接口。

### 误报-002: getStatus 未暴露给 HTTP/MCP 是缺接口

- 原始报告：多份能力矩阵中标记 HTTP/MCP ❌。
- 误报原因：产品文档明确 `getStatus` 仅 IPC；CLI `status` 是本地诊断命令，不等价于 IPC 的结构化状态。应修的是 CLI status 被运行态检查短路，而不是要求 HTTP/MCP 增加 getStatus。

### 误报-003: CLI 缺少表达式 where / orderBy / offset 是实现缺陷

- 原始报告：多份能力矩阵中标记 CLI query 部分缺失。
- 误报原因：CLI 设计命令只承诺 `synapse query <table> [--where k=v] [--limit N]`，未承诺表达式 where、orderBy、offset。可在矩阵中标为部分对等，但不应作为违反当前设计的缺陷。

### 误报-004: IPC 与 HTTP 响应包装不同必然是缺陷

- 原始报告：17:57、18:16 等报告。
- 误报原因：HTTP 是外部 RPC 包装 `{ ok, data }`，IPC bridge 类型当前定义为直接返回 service 结构。除非产品决定所有入口统一 envelope，否则这属于契约差异说明，不是已验证功能缺陷。

### 误报-005: insert / update / delete 未显式事务化等同于违反“所有写操作包事务”

- 原始报告：18:27 报告。
- 误报原因：单条 SQLite 写语句本身具备原子性，真实可验证问题集中在 `addColumn` 的 DDL 与元数据更新两步未事务化；不应把所有单语句写操作都列为同等级缺陷。

## 建议修复优先级

1. 修复 DS-001：在 Service 层建立统一运行时校验，封住 SQL 片段边界，这是所有入口共用的安全底座。
2. 修复 DS-002 和 DS-003：用 SQLite backup/checkpoint 与原子替换重做导入导出，避免备份缺数据和导入丢库。
3. 修复 DS-004：区分数据库损坏与普通打开失败，避免误重建空库。
4. 修复 DS-005 和 DS-006：明确 rawSQL DDL 契约并保持元数据/JSON 缓存一致，补齐 JSON where 透明查询。
5. 修复 DS-010 到 DS-014：集中改善 CLI/MCP 的判活、超时、参数解析和 JSON-RPC 边界，降低外部入口不可用概率。
6. 修复 DS-015 和 DS-016：统一 MCP schema 与 addColumn 参数契约，降低三端维护成本。
7. 最后处理 DS-018 和 DS-019：名称规则与空行 parse error 属于低风险一致性/体验问题。
