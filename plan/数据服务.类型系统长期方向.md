# 数据服务 · 类型系统长期方向（Intent-Based Schema）

> 状态：**草案 / 暂不实施**
> 最后更新：2026-04-24
> 触发：`desktop/electron/data-store/service.ts` 中 `assertSemanticallyCorrectColumn` 的关键词白名单属于权宜之计，需要记录真正通用的替代方案以备将来取用。

---

## 1. 背景

### 1.1 现状快照（2026-04-24）

数据服务的 MCP 工具接受 10 个列类型：

```
TEXT, INTEGER, REAL, BLOB, JSON, DATE, DATETIME, BOOLEAN, ENUM, MULTI_ENUM
```

AI 在建表时需要从这 10 个值里为每一列选一个。现实中观察到的失败模式是：

- 单选枚举（priority 等级）被选成 `TEXT`
- 多选枚举（category 分类）被选成 `JSON`
- 布尔（done 是否完成）被选成 `INTEGER`

### 1.2 描述级治理不够

我们对 `create_table` / `add_column` 的 description 迭代过 3 轮：

- Round 0：基础说明
- Round 1：加入类型优先级规则与反例
- Round 2：规则前置、补中文正向示例、在 `type` 与 `enumValues` 两个 schema 属性上重复关键规则

在 kimi-k2.5 和 Opus 4.7 上均测试失败。Opus 4.7 更特殊——它不仅忽略规则，还在被追问时**伪造 schema**（声称 enum 只有 5 个值）来自圆其说。

### 1.3 服务端守护已上线（兜底层）

`assertSemanticallyCorrectColumn` 以列名关键词表为依据，硬拒绝明显错误的组合（`category + JSON`、`priority + TEXT`、`done + INTEGER` 等）。AI 收到错误后会在下一轮自动纠正。

**效果**：Opus 4.7 在第二次重试时成功传入 `MULTI_ENUM / ENUM / BOOLEAN`。

**局限**：

- 关键词覆盖不全（新领域词汇会漏）
- 存在假阳性风险（比如 `state` 真的指美国州名时也会被拦）
- 治标不治本——AI 的 SQL 先验并没有被纠正，只是撞墙后绕路

---

## 2. 诊断：为什么描述与关键词都是打补丁

### 2.1 `type` 字段混淆了两个正交维度

| 维度 | 今天挤在 `type` 里 |
|------|---|
| 存储格式（底层怎么存） | TEXT / INTEGER / REAL / BLOB / DATE / DATETIME / JSON |
| 语义约束（值的性质） | ENUM / MULTI_ENUM / BOOLEAN |

AI 的 SQL 先验直指第一维。把 `ENUM` 放进同一个下拉选项里，等价于强行让两种正交概念抢同一块注意力，AI 优先服从它已经内化过的"SQL 类型"心理模型。

### 2.2 这个结构性冲突 description 治不了

无论 description 写得多详细，只要字段叫 `type` 且取值里既含 `TEXT` 又含 `ENUM`，AI 的先验就会把 `ENUM` 当成"特殊 TEXT"（或者干脆忽略）。问题不在 AI 多笨，在 schema 设计本身。

---

## 3. 提案：Intent-Based Schema

### 3.1 核心思路

把单一的 `type` 字段替换为显式的**意图**字段。AI 描述的是**用户想要什么**，服务端决定**底层怎么存**。

### 3.2 Schema 对比

```ts
// 今天
{
  name: "priority",
  type: "ENUM",
  enumValues: ["高", "中", "低"]
}

// 新设计
{
  name: "priority",
  intent: {
    kind: "single_choice",
    values: ["高", "中", "低"]
  }
}
```

### 3.3 `kind` 值集

| kind | 服务端映射 | 使用场景 |
|------|---|---|
| `single_choice` | ENUM | 固定值集中单选 |
| `multi_choice`  | MULTI_ENUM | 固定值集中多选 |
| `yes_no` | BOOLEAN | 布尔 |
| `text` | TEXT | 自由字符串 |
| `integer` | INTEGER | 整数 |
| `decimal` | REAL | 小数 |
| `date` | DATE | 日期 YYYY-MM-DD |
| `timestamp` | DATETIME | 时间戳 YYYY-MM-DD HH:mm:ss |
| `structured` | JSON | 任意嵌套对象 |
| `binary` | BLOB | 二进制 |

关键约束：

- `single_choice` / `multi_choice` 必须附带 `values`（非空字符串数组）
- `yes_no` 不允许 `values`
- 其它 kind 不允许 `values`

### 3.4 为什么 intent 能解决描述解决不了的问题

1. **去除词汇冲突**：`kind` 的取值（`single_choice`、`yes_no`、`structured` 等）不与 SQL 类型同名，AI 看到后无法直接触发 SQL 先验。`"json"` 改名为 `"structured"`，AI 不会再把"分类"误标成它。
2. **强制显式决策**：没有"SQL 默认值"可退——`freeform text` 叫 `text`，`fixed choice set` 叫 `single_choice`，两者必须二选一。
3. **服务端校验从猜列名升级为规则校验**：关键词表从主防线降为辅助 lint，假阳性风险下降。
4. **存储策略解耦**：将来想把 MULTI_ENUM 从 JSON 序列化改为关联表，AI 不需要重新训练——它只管说 `multi_choice`，怎么存是服务端的事。

### 3.5 仍然解决不了的部分

- 提示词含糊时 AI 可能把 priority 填成 `kind: "text"`——但概率大幅下降
- 关键词守护仍需保留作为第二层防线
- 列描述元数据（`description`）AI 仍然可能不填

## 4. 迁移路径

### 4.1 Option A：增量兼容（推荐起点）

- 保留 `type` + `enumValues` 旧 API
- 新加 `intent` 字段，与 `type` 互斥（同次调用二选一）
- 服务端内部将 `intent` 规范化为现有的 `DataStoreColumnDef`
- MCP description 里优先推荐 `intent`，`type` 保留但标记"legacy"

**估算代价**

- `service.ts`：~200 行（intent → 现有字段的映射器 + 校验）
- `mcp-server.ts` / `desktop/data-store/mcp/index.ts`：~100 行（schema 声明 + description 改写）
- 测试：覆盖 10 个 kind 的典型场景，以及 kind + values 的所有非法组合
- 风险：两条代码路径长期共存，易产生不一致

### 4.2 Option B：破坏性重构（clean but costly）

- 废弃 `type`，只暴露 `intent`
- 写数据库迁移脚本，对 `_meta_columns` 做一次性改造
- 所有 MCP 客户端必须升级

**估算代价**

- 更干净的最终形态
- 迁移脚本 + 回滚方案
- 外部调用方（如果有）必须同步升级
- Git 历史里 `create_table` 的调用形态会跟既往文档对不上

### 4.3 Option C：两阶段交互（改流程，不改 schema）

新增 `plan_table` 工具：

```
plan_table(name, fields_description: "备注、分类多选、优先级单选、完成布尔")
  → 服务端解析 / AI 再推理 → proposed_columns
  → 用户或 AI 确认 / 修改
  → create_table_from_plan(planId)
```

**估算代价**

- ~400 行（新工具 + plan 草稿状态管理）
- 交互从 1 步变 2 步——AI 工具使用成本上升
- 好处：任何新维度都能先在 plan 阶段澄清，不污染 create_table 的 schema

## 5. 什么时候真的去做

记录触发信号，避免过早重构（Karpathy 原则：没证据不动）：

| 信号 | 建议走哪条路径 |
|------|---|
| 真实用户在 5+ 个新领域词汇上被守护误拦（例如 `rank` / `类目` / `grade`） | Option A |
| 多个主流模型持续在守护范围外系统性犯错 | Option A |
| 产品开始支持第三方 MCP 调用方，外部开发者抱怨 `type` 混淆 | Option B |
| 用户频繁要求建复杂结构（嵌套 + 多约束），一次 `create_table` 描述不完 | Option C |
| 数据服务要升级多选存储策略（如引入关联表） | Option B（借机重构） |

在以上任何信号单独出现前，**不动**。当前的关键词守护 + description 组合在 Opus 4.7 和 kimi-k2.5 上均能达到"第一次错 → 第二次纠正"的水准，够用。

---

## 6. 不动的理由（当前快照）

1. 守护已覆盖观察到的 80% 错误模式，Opus 的自动纠错链路已验证
2. 重构范围不是"~200 行 service"那么轻——涉及 MCP 工具 schema、客户端示例、所有既有文档
3. 现有表（`bookmarks` / `todo` / 未来用户表）都用 `type`，迁移有风险
4. 新设计在 AI 先验上的真实收益需要跨模型验证，成本高

## 8. 决策日志

### 2026-04-24 · Stateless Tool Schemas（已落地）

#### 触发

Codex 作为严格 MCP 客户端对 tool `inputSchema` 中的 `enum` 字段做客户端侧 JSON Schema 校验。此前 `tableNameProp` 把"当前存在哪些表"烧进 `enum: [...]`，DDL 后新建的表立即失配旧 snapshot，`insert` 等调用被 Codex 在 wire 之前就拒发。AI 侧收到的信号是"工具不支持该表"，并自圆其说"schema 还没同步"。

#### 诊断

`tools/list` 是协议层的**静态能力清单**。把运行时状态（表名、列摘要等）烧进静态声明等于主动违约：客户端按声明执行完全合规，只是我们的声明在不断作废。Claude Code 宽松放行掩盖了问题，Codex 严格校验暴露了问题——Codex 没有错。

#### 决策

采用 **"stateless tool schemas + state-revealing tools"** 原则：

> Tool schema 只描述"能做什么"，永远不内嵌"现在有什么"。任何运行时状态只能通过显式数据调用获得。

落地改动：

- `mcp-server.ts` 和 `desktop/data-store/mcp/index.ts` 两处 `tableNameProp` 去掉 `enum`，改为静态 `type: "string"` + list_tables 发现提示
- 完全移除 `buildTableSummary()` 和 `fetchTableSchemas()`；`buildTools()` 改为纯函数，不接受任何参数
- 所有涉及 table 参数的工具描述末尾补 describe_table 发现提示
- 简化 `tools/list` handler：移除 try/catch，直接 `{ tools: buildTools() }`
- 清理同步失效的类型：`TableInfo` / `ColumnInfo` / `TableSchema`

#### 副决策：不实现 `notifications/tools/list_changed`

评估后否决。理由：

1. 重构后 `buildTools()` 是纯函数，每次返回完全相同的清单。tool list 不会变化，发"它变了"是违约信号。
2. `initialize` 响应的 `capabilities.tools = {}` 没声明 `listChanged`。当前声明和行为自洽，无需补通知。
3. 当前 HTTP MCP 服务为纯 req/resp，要支持 push 需新增 SSE + session 管理（~150 行），收益却是永久发出"nothing actually changed"的空信号。
4. 当未来引入 Resources / 订阅式数据变更时，届时配合**新 capability 声明**一次性设计通知机制，而不是为一个伪场景先搭好半套基础设施。

#### 与长期 intent 方向的关系

两者同源：都来自"schema 不该装运行时状态"的推论。本次 stateless 清理把"表名 enum"这块 snapshot 废料先处理掉，未来推进 intent-based schema 时：

- 路径 A / B 不会再踩同样的"动态内容烧进 schema"陷阱
- 列 metadata（如 enum 允许值的当前列表）同样走 describe_table 查询，而不是 tool 声明

#### 实测佐证

- MCP curl `tools/list` 返回中，`insert` 工具的 `table` prop 现在是：`{"type": "string", "description": "Table name. If you do not know which tables exist, call list_tables first."}`，无 `enum` 字段
- 描述末尾有 `...call describe_table first.` 发现提示，无 `Available tables:` 动态 summary
- Codex 建表 → 立刻 insert 新表场景预期一次通过，不再受客户端侧 enum gate 阻挡（提交时待用户实测确认）
