# 编辑器集成位置深度分析

生成时间：2026-04-24
分析范围：`cursor`、`codex`、`claude-code`

## 结论

当前仓库已经有一套明确的编辑器适配主干，但还不是完全单点配置。

- 真正的核心集中点是 `desktop/electron/services/editor-adapters/`
- 真正的注册入口是 `desktop/electron/services/editor-adapters/index.ts`
- 真正的统一解析入口是 `desktop/electron/services/editor-adapter-service.ts`
- 但展示顺序、图标、扫描分支、安装分支、CLI 检测、MCP 注册仍然散落在多个文件里

因此，这套实现更准确的描述是：

> “主干已集中，旁路未收口”

如果后续要扩展第四个编辑器，当前架构是可以继续扩的，但改动点不会只落在 adapter 文件夹里。

## 目标澄清：这里的“编辑器”只等于工具页里的 IDE

本文后续把“编辑器”统一改称为 **IDE 集成**。它只对应系统设置 / 工具里的 `IDE` 区域，不等于 `命令行工具`。

当前产品里有两套平级能力：

- IDE：Cursor、Codex、Claude Code，用来安装 / 扫描 Rule 和 Skill
- 命令行工具：Claude Code、Codex，用来检测本机 CLI 是否存在

这两套能力可以同名，但不能混为一个抽象。比如：

- 一个 IDE 可以没有配套 CLI
- 一个 CLI 可以不对应 IDE
- 同名的 `codex` IDE 和 `codex` CLI 也应该通过显式关联连接，而不是默认认为同名就是同一个东西

所以最终目标应该表述为：

> 新增一个 IDE，例如 `windsorf`，只需要在 `ide-definitions/windsorf/` 这个文件夹里补齐文件；如果它没有 CLI，就不写 CLI 定义；如果它有配套 CLI，就在同一个 IDE 文件夹下增加一个可选 CLI 定义文件。

## 最终目标可行性判断

结论：**可以实现，但不是在当前架构上直接新增一个文件夹就能实现。**

要达到“新增 `windsorf` 时只改 `ide-definitions/windsorf/`，其他任何地方都不改代码”，必须先完成一轮基础设施改造，让 IDE、CLI、MCP、安装、扫描都能从定义目录自动发现。

最终开发体验应该是：

```text
desktop/src/ide-definitions/
  windsorf/
    icon.png
    ide.ts
    adapter.ts
    scan.ts
    install.ts
    cli.ts        # 可选；没有配套 CLI 就不创建
    mcp.ts        # 可选；没有 MCP 就不创建
```

新增一个只支持 IDE、不支持 CLI 的 `windsorf` 时，只需要：

```text
desktop/src/ide-definitions/windsorf/icon.png
desktop/src/ide-definitions/windsorf/ide.ts
desktop/src/ide-definitions/windsorf/adapter.ts
desktop/src/ide-definitions/windsorf/scan.ts
desktop/src/ide-definitions/windsorf/install.ts
```

如果 `windsorf` 还有配套 CLI，再额外添加：

```text
desktop/src/ide-definitions/windsorf/cli.ts
```

如果它还支持 MCP，再额外添加：

```text
desktop/src/ide-definitions/windsorf/mcp.ts
```

这样 CLI 和 IDE 仍是两套东西，只是允许 IDE 文件夹声明“我有一个配套 CLI”。没有 `cli.ts` 就代表没有配套 CLI。

## 必须先解决的关键问题

### 1. 不能再手写 `SYNAPSE_EDITOR_IDS` 作为唯一来源

当前 `desktop/src/types/editor.ts` 手写：

```ts
export const SYNAPSE_EDITOR_IDS = ["cursor", "codex", "claude-code"] as const
```

这会导致新增 `windsorf` 必须改 `types/editor.ts`，不满足“只改 windsorf 文件夹”。

最终要改成：

- IDE id 从定义注册表派生
- 或者把 IDE id 放宽成 branded string
- 再用运行时 definition registry 校验是否存在

推荐更稳的做法：

```ts
type SynapseEditorId = string & { readonly __brand: "SynapseEditorId" }
```

然后所有合法性由 `ideDefinitionRegistry.has(id)` 判断。这样新增 IDE 不需要改联合类型。

### 2. 不能再手写 `editor-adapters/index.ts`

当前 adapter 注册是手写数组：

```ts
const editorAdapters = [cursorAdapter, codexAdapter, claudeCodeAdapter] as const
```

这会导致新增 `windsorf` 必须改 `editor-adapters/index.ts`。

最终要改成自动发现：

- renderer 侧用 Vite `import.meta.glob` 发现 `ide-definitions/*/ide.ts`
- Electron 侧不能直接用 Vite，需要用构建期生成 registry，或用约定文件 + 生成脚本

因为 Electron 当前用 `tsc -p tsconfig.electron.json` 构建，不走 Vite，所以主进程不能直接使用 `import.meta.glob`。

最稳方案是新增生成脚本：

```text
desktop/scripts/generate-ide-registry.mjs
```

它扫描：

```text
desktop/src/ide-definitions/*/
```

然后生成两个文件：

```text
desktop/src/ide-definitions/generated/renderer-registry.ts
desktop/electron/services/ide-definitions/generated/main-registry.ts
```

生成文件可以被构建系统 import，但开发者新增 IDE 时不手改生成文件。

### 3. CLI 必须是 IDE 的可选配套定义，不是 IDE 本体字段硬绑定

正确抽象不是：

```ts
ide: {
  id: "codex",
  cliBin: "codex",
}
```

因为这会暗示每个 IDE 都应该有 CLI。

更合理的是：

```text
ide-definitions/codex/
  ide.ts
  cli.ts

ide-definitions/cursor/
  ide.ts
  # 没有 cli.ts
```

`cli.ts` 示例：

```ts
export const cliDefinition = {
  id: "codex",
  label: "Codex",
  binaries: ["codex"],
}
```

这样系统设置 / 工具里的 `命令行工具` 区域只展示所有存在 `cli.ts` 的定义。

### 4. MCP 也应该是可选配套定义

MCP 和 IDE 也不要强绑定。当前 Claude Code 的 MCP target 是 `claude`，不是 `claude-code`。这说明 MCP target 有自己的命名空间。

建议：

```text
ide-definitions/claude-code/
  ide.ts
  mcp.ts
```

`mcp.ts` 示例：

```ts
export const mcpDefinition = {
  target: "claude",
  label: "Claude Code",
}
```

没有 `mcp.ts` 就代表这个 IDE 没有 MCP 注册能力。

### 5. 安装和扫描也必须插件化

只把图标和 label 放到 IDE 文件夹里，不足以实现“新增 IDE 不改别处”。因为当前最硬的耦合在：

- `content-install-service.ts` 里的 editor id 分支
- `editor-scan-service.ts` 里的 scan switch
- `content-install-dialog.tsx` 里的安装前表单分支

最终每个 IDE 文件夹必须声明：

```text
adapter.ts  # 目标路径解析
install.ts  # Rule / Skill 写入策略
scan.ts     # 扫描策略
forms.ts    # 可选；安装前表单定义或 form kind
```

通用服务只做：

1. 根据 `editorId` 找 definition
2. 调 definition.adapter.resolveTarget()
3. 调 definition.install.write()
4. 调 definition.scan.scanRules()

服务层不能再写：

```ts
if (editorId === "cursor") ...
if (editorId === "claude-code") ...
if (editorId === "codex") ...
```

## 最终是否能做到“只改 windsorf 文件夹”

可以，但最终目录应从“单个 definition.ts”升级为“IDE 插件文件夹”：

```text
desktop/src/ide-definitions/windsorf/
  icon.png
  ide.ts
  adapter.ts
  install.ts
  scan.ts
  cli.ts     # 可选
  mcp.ts     # 可选
  forms.ts   # 可选
```

达到这个状态后，新增 `windsorf` 的行为是：

- IDE 区域自动出现 Windsorf
- 内容安装菜单自动出现 Windsorf
- IDE 扫描页自动扫描 Windsorf
- 如果存在 `cli.ts`，命令行工具区域自动出现 Windsorf CLI
- 如果不存在 `cli.ts`，命令行工具区域不出现 Windsorf
- 如果存在 `mcp.ts`，MCP 设置区自动出现对应注册项
- 如果不存在 `mcp.ts`，MCP 设置区不出现 Windsorf

这才满足你说的：

> 软件支持多少个 IDE，就有多少个这种文件夹；新增 IDE 只改这个 IDE 自己的文件夹。

## 可行但要分两层达成

### 第一层：配置收口

先把展示信息收口到 IDE 文件夹：

- icon
- label
- order
- 支持内容类型
- 支持 global / project
- 可选 CLI 定义
- 可选 MCP 定义

这一步能减少散点，但还不能做到“只改一个文件夹”。

### 第二层：执行策略插件化

再把执行逻辑也收口到 IDE 文件夹：

- adapter
- install strategy
- scan strategy
- preinstall form strategy

这一步完成后，才能真正做到新增 IDE 不改别处。

### 当前文档推荐路线

当前更安全的路线仍然是分阶段：

1. 先做 renderer 展示定义目录，不改行为
2. 再做 CLI / MCP 可选定义，保持它们和 IDE 是平级能力
3. 再做安装 / 扫描策略插件化
4. 最后做自动发现 / 生成 registry，取消手写注册点

只有第 4 步完成后，才能达到“新增 `windsorf` 只改 `windsorf/` 文件夹”。

## 一、核心集中位置

### 1. 类型定义

编辑器域的共享类型集中在：

- `desktop/src/types/editor.ts`

这里定义了：

- `SYNAPSE_EDITOR_IDS`
- `SynapseEditorId`
- `SynapseEditorAdapterSummary`
- `SynapseResolveEditorTargetPayload`
- `SynapseEditorResolvedTarget`
- Cursor / Claude Code 规则 frontmatter 类型

这份文件是“类型层”的中心，但不是完整的运行时 source of truth。

### 2. Adapter 接口

Adapter 规范集中在：

- `desktop/electron/services/editor-adapters/types.ts`

这里定义了 `EditorAdapter` 接口，要求每个编辑器提供：

- `resolveGlobalDirectoryPaths()`
- `resolveGlobalTarget()`
- `resolveProjectTarget()`
- `getScanPathConfig()`

这说明仓库已经明确把“编辑器差异”收敛到 adapter 模式里了。

### 3. Adapter 实现文件夹

当前最重要的集中目录是：

- `desktop/electron/services/editor-adapters/`

当前包含：

- `cursor-adapter.ts`
- `codex-adapter.ts`
- `claude-code-adapter.ts`
- `cursor-mdc.ts`
- `claude-code-frontmatter.ts`
- `rule-section.ts`
- `skill-identity.ts`
- `skill-slug.ts`
- `skill-frontmatter.ts`
- `utils.ts`

这里已经不仅是“路径解析”，还承载了：

- Rule frontmatter 的读写格式
- Codex AGENTS.md 的规则块注入方式
- Skill slug / identity / conflict 处理

所以从真实实现上看，这个目录已经是“编辑器安装协议层”。

### 4. Adapter 注册入口

真正的运行时注册点在：

- `desktop/electron/services/editor-adapters/index.ts`

当前注册：

- `cursorAdapter`
- `codexAdapter`
- `claudeCodeAdapter`

并导出：

- `editorAdapters`
- `editorAdapterById`

这是新增编辑器时必须修改的第一入口。

### 5. 统一服务入口

统一服务层在：

- `desktop/electron/services/editor-adapter-service.ts`

负责两件事：

- `listAdapters()`
- `resolveTarget()`

这里已经做了两层统一处理：

- 校验 `editorId`
- 校验 `supportedContentTypes`

因此“解析安装位置”这件事已经很好地被 adapter service 收口。

## 二、三家编辑器分别在哪里定义

### Cursor

核心定义：

- `desktop/electron/services/editor-adapters/cursor-adapter.ts`

当前策略：

- 全局 Rule：`unsupported`
- 全局 Skill：`~/.cursor/skills/<skill-name>/`
- 项目 Rule：`<project>/.cursor/rules/<contentId>.mdc`
- 项目 Skill：`<project>/.cursor/skills/<skill-name>/`

Cursor Rule frontmatter 读写：

- `desktop/electron/services/editor-adapters/cursor-mdc.ts`

对应的安装前 UI：

- `desktop/src/modules/content/components/cursor-frontmatter-dialog.tsx`

### Codex

核心定义：

- `desktop/electron/services/editor-adapters/codex-adapter.ts`

当前策略：

- 全局 Rule：`$CODEX_HOME/AGENTS.md` 或 `~/.codex/AGENTS.md`
- 全局 Skill：`~/.agents/skills/<skill-name>/`
- 项目 Rule：`<project>/AGENTS.md`
- 项目 Skill：`<project>/.agents/skills/<skill-name>/`

Codex Rule 写入并不是“覆盖整文件”，而是往同一份 Markdown 中按 rule block 合并：

- `desktop/electron/services/editor-adapters/rule-section.ts`

### Claude Code

核心定义：

- `desktop/electron/services/editor-adapters/claude-code-adapter.ts`

当前策略：

- 全局 Rule：`~/.claude/rules/<rule-name>.md`
- 全局 Skill：`~/.claude/skills/<skill-name>/`
- 项目 Rule：`<project>/.claude/rules/<rule-name>.md`
- 项目 Skill：`<project>/.claude/skills/<skill-name>/`

Claude Code Rule frontmatter 读写：

- `desktop/electron/services/editor-adapters/claude-code-frontmatter.ts`

对应的安装前 UI：

- `desktop/src/modules/content/components/claude-code-frontmatter-dialog.tsx`

## 三、编辑器相关的调用链

当前主调用链如下：

1. Renderer 侧打开安装菜单
2. `desktop/src/modules/content/hooks/use-content-download-actions.tsx`
3. 调 `desktop/src/app-shell/content.ts`
4. 通过 `desktop/electron/preload.ts`
5. 进入 `desktop/electron/ipc/content-handlers.ts`
6. 调 `desktop/electron/services/editor-adapter-service.ts`
7. 最终进入具体 adapter

实际安装时再走：

1. `content-install-service.ts`
2. 根据解析好的 target 写文件或目录
3. 针对不同编辑器追加特定格式处理

这说明：

- “路径解析”已经集中
- “落盘格式”还只有一部分集中

## 四、扫描相关的位置

编辑器扫描的核心集中在：

- `desktop/electron/services/editor-scan-service.ts`
- `desktop/src/modules/editor-scan/`

其中：

- `editor-scan-service.ts` 负责扫描全局与项目目录
- `modules/editor-scan/` 负责渲染 IDE 扫描页

扫描服务已经复用 adapter 的 `getScanPathConfig()`，这是好事，说明路径来源已经尽量统一。

但扫描规则解析仍然有编辑器分支：

- Claude Code：`scanClaudeCodeRules()`
- Cursor：`scanCursorRules()`
- Codex：`scanCodexRules()`
- 分发位置：`scanRulesForEditor()`

也就是说，扫描路径已集中，扫描内容解析仍是按编辑器分叉。

## 五、哪些地方已经集中，哪些地方还散

### 已集中

- 编辑器安装路径解析：`editor-adapters/`
- 编辑器统一服务入口：`editor-adapter-service.ts`
- 编辑器 IPC 暴露：`content-handlers.ts` / `preload.ts` / `app-shell/content.ts`
- 编辑器扫描路径来源：adapter 的 `getScanPathConfig()`

### 未集中

#### 1. 展示顺序和文案

单独放在：

- `desktop/src/lib/editor-registry.ts`

这里维护：

- `EDITOR_ORDER`
- `EDITOR_LABELS`

它没有直接从 `editorAdapters` 派生，因此是额外维护点。

#### 2. 图标映射

单独放在：

- `desktop/src/lib/editor-icons.ts`

新增编辑器时必须手动补图标映射。

#### 3. 安装时的编辑器特判

仍散在：

- `desktop/electron/services/content-install-service.ts`

当前有明确分支：

- Cursor Rule：写入 `.mdc` frontmatter
- Claude Code Rule：写入 `paths` frontmatter
- Codex Rule：把 rule merge 到 `AGENTS.md`

这部分还没有完全下沉到 adapter。

#### 4. 扫描时的编辑器特判

仍散在：

- `desktop/electron/services/editor-scan-service.ts`

当前通过 `switch(editorId)` 选择不同扫描器。

#### 5. 安装弹窗里的编辑器特判

仍散在：

- `desktop/src/modules/content/components/content-install-dialog.tsx`

当前有明确 UI 分支：

- Cursor 项目 Rule 安装前弹 Cursor frontmatter dialog
- Claude Code 项目 Rule 安装前弹 Claude Code frontmatter dialog

这意味着“编辑器需要哪些额外表单”还没有做成声明式配置。

#### 6. CLI 检测单独维护

CLI 检测不走 editor adapter，而是单独维护：

- `desktop/src/types/cli.ts`
- `desktop/electron/services/cli/cli-detect-service.ts`
- `desktop/src/modules/cli/lib/cli-icons.ts`

当前只检测：

- `claude-code`
- `codex`

Cursor 不在这条链路里。

#### 7. MCP 注册单独维护

Data Store 的 MCP 目标单独维护：

- `desktop/src/types/data-store.ts`
- `desktop/electron/data-store/mcp-installer.ts`
- `desktop/src/modules/settings/components/data-store-settings-panel.tsx`

注意这里的 target 不是：

- `claude-code`

而是：

- `claude`

这和编辑器域的命名不一致，后续做统一注册表时必须处理映射。

## 六、是否存在一个“真正完整的集中定义文件”

结论：没有。

当前最接近“集中定义”的只有两处：

- `desktop/src/types/editor.ts`
- `desktop/electron/services/editor-adapters/index.ts`

但它们都不完整：

- `types/editor.ts` 只定义类型，不定义图标、顺序、CLI、MCP、UI 行为
- `editor-adapters/index.ts` 只注册 adapter，不定义 renderer 展示元数据

所以仓库里目前不存在一个类似下面这种真正的单一注册表：

```ts
{
  id,
  label,
  icon,
  order,
  cliBin,
  mcpTarget,
  adapter,
  scanStrategy,
  installStrategy,
  frontmatterUi
}
```

这也是后期扩展的主要瓶颈。

## 七、后期扩展时的真实改动面

如果现在新增第四个编辑器，至少要检查这些位置：

- `desktop/src/types/editor.ts`
- `desktop/electron/services/editor-adapters/<new>-adapter.ts`
- `desktop/electron/services/editor-adapters/index.ts`
- `desktop/src/lib/editor-registry.ts`
- `desktop/src/lib/editor-icons.ts`
- `desktop/electron/services/content-install-service.ts`
- `desktop/electron/services/editor-scan-service.ts`
- `desktop/src/modules/content/components/content-install-dialog.tsx`
- 如果有 CLI：`desktop/src/types/cli.ts`、`desktop/electron/services/cli/cli-detect-service.ts`
- 如果有 MCP：`desktop/src/types/data-store.ts`、`desktop/electron/data-store/mcp-installer.ts`、`desktop/src/modules/settings/components/data-store-settings-panel.tsx`

所以“新增一个 adapter 就够了”目前并不成立。

## 八、当前架构里最适合继续扩展的地方

如果短期内继续沿用现有设计，最推荐的扩展落点是：

- 继续把编辑器协议差异放进 `desktop/electron/services/editor-adapters/`

原因：

- 这里已经有清晰接口
- 路径解析已经统一
- 规则 frontmatter / rule block / skill identity 等也已经在这里
- 仓库自己的文档和规则也明确要求新增编辑器通过 adapter 模式接入

也就是说，短期正确方向不是另起一个平行目录，而是继续强化这个目录的职责。

## 九、当前最值得优先收口的点

### 1. 建一个分层 editor definitions 体系

建议新增分层定义体系，先收口 renderer 静态信息，再逐步收口 Electron 能力信息。不要一开始就做跨进程巨型 manifest。第一层只收口这些 renderer 静态信息：

- `id`
- `label`
- `icon`
- `order`

后续阶段再逐步收口：

- 是否需要 Rule frontmatter UI
- frontmatter UI 类型
- 是否支持 CLI 检测
- CLI 可执行名
- MCP target 映射

这样可以把以下文件先转为派生兼容层，确认稳定后再考虑是否合并：

- `editor-registry.ts`
- `editor-icons.ts`
- `cli-detect-service.ts` 中的静态定义
- `data-store-settings-panel.tsx` 中的 MCP_SERVER_META

### 2. 把安装分支继续下沉到 adapter

现在 `content-install-service.ts` 还在按 `payload.editorId` 分支。

更理想的结构是让 adapter 自己声明：

- Rule 写入策略
- 是否需要 merge 到单文件
- 是否需要 frontmatter serializer
- Skill identity / replacement 规则

这样 `content-install-service.ts` 就只负责：

- 读取内容
- staging
- 原子替换

而不是知道每家编辑器的规则格式。

### 3. 把扫描分支继续下沉到 adapter

现在 `editor-scan-service.ts` 还知道：

- Cursor 规则是 `.mdc`
- Claude Code 规则是 `.md`
- Codex 规则在 `AGENTS.md` 里按注释块拆

更合适的做法是让 adapter 提供：

- `scanRules(...)`
- `readRulePreview(...)`
- `identifySynapseRule(...)`

这样新增编辑器时就不会继续扩大 `switch(editorId)`。

### 4. 把“需要什么安装前弹窗”改成声明式

现在安装弹窗直接写死：

- Cursor Rule -> 打开 CursorFrontmatterDialog
- Claude Code Rule -> 打开 ClaudeCodeFrontmatterDialog

这会导致每加一个编辑器都改 UI 主组件。

更合理的方式是由 renderer 侧 editor definition 声明：

- `ruleInstallForm: "cursor-mdc" | "claude-code-paths" | null`

这样安装弹窗只做分发，不做硬编码判断。

## 九点五、目标形态：每个 IDE 一个插件文件夹

你的最终诉求不是“集中展示元数据”，而是：

> 新增一个 IDE，例如 `windsorf`，只需要新增 / 修改 `ide-definitions/windsorf/` 这个文件夹，其他任何地方都不用手改代码。

这个目标可以实现，但最终形态必须是 **IDE 插件文件夹**，而不是一个简单的 `definition.ts`。

### 1. 最终目录结构

最终建议目录如下：

```text
desktop/src/ide-definitions/
  cursor/
    icon.png
    ide.ts
    adapter.ts
    install.ts
    scan.ts
    forms.ts      # 可选；需要安装前 UI 时才有
    cli.ts        # 可选；有配套 CLI 时才有
    mcp.ts        # 可选；有 MCP 注册能力时才有
  codex/
    icon.png
    ide.ts
    adapter.ts
    install.ts
    scan.ts
    cli.ts
    mcp.ts
  claude-code/
    icon.png
    ide.ts
    adapter.ts
    install.ts
    scan.ts
    forms.ts
    cli.ts
    mcp.ts
  generated/
    renderer-registry.ts
```

主进程侧需要一个生成出来的入口：

```text
desktop/electron/services/ide-definitions/generated/main-registry.ts
```

`generated/*` 文件由脚本生成，不由开发者手写。开发者新增 `windsorf` 时只创建：

```text
desktop/src/ide-definitions/windsorf/
  icon.png
  ide.ts
  adapter.ts
  install.ts
  scan.ts
```

如果没有 CLI，就不创建 `cli.ts`。如果没有 MCP，就不创建 `mcp.ts`。

### 2. IDE 和 CLI 的关系

IDE 和 CLI 必须是两套平级能力。`cli.ts` 只是 IDE 文件夹里的可选配套声明，不代表 IDE 本体一定有 CLI。

正确模型：

```text
ide-definitions/cursor/
  ide.ts
  # 没有 cli.ts，所以命令行工具区域不显示 Cursor

ide-definitions/codex/
  ide.ts
  cli.ts
  # 有 cli.ts，所以命令行工具区域显示 Codex
```

`cli.ts` 示例：

```ts
export const cliDefinition = {
  id: "codex",
  label: "Codex",
  binaries: ["codex"],
}
```

命令行工具区域只读取所有存在 `cli.ts` 的定义。这样可以同时满足：

- IDE 列表里有 Cursor
- 命令行工具列表里没有 Cursor
- IDE 列表里有 Codex
- 命令行工具列表里也有 Codex
- 两个 Codex 通过显式定义关联，而不是靠同名硬猜

### 3. MCP 也是可选配套定义

MCP 也不能和 IDE id 强绑定。当前 Claude Code 的 MCP target 是 `claude`，不是 `claude-code`，说明 MCP 有自己的命名空间。

`mcp.ts` 示例：

```ts
export const mcpDefinition = {
  target: "claude",
  label: "Claude Code",
}
```

没有 `mcp.ts` 就代表这个 IDE 没有 MCP 注册能力。

### 4. `ide.ts` 负责什么

`ide.ts` 是 IDE 本体定义，只放和 IDE 本身有关的元数据：

```ts
import icon from "./icon.png"

export const ideDefinition = {
  id: "windsorf",
  label: "Windsorf",
  order: 40,
  icon,
  supportedContentTypes: ["rule", "skill"],
  supportsGlobal: true,
  supportsProject: true,
}
```

注意：

- `ide.ts` 不写 CLI bin
- `ide.ts` 不写 MCP target
- CLI 放 `cli.ts`
- MCP 放 `mcp.ts`
- 安装逻辑放 `install.ts`
- 扫描逻辑放 `scan.ts`
- 路径解析放 `adapter.ts`

### 5. 为什么必须有 `adapter.ts` / `install.ts` / `scan.ts`

如果只把 icon 和 label 放进 IDE 文件夹，仍然无法做到“只改 windsorf 文件夹”。因为当前还有这些硬编码分支：

- `content-install-service.ts` 里按 `payload.editorId` 区分 Cursor / Claude Code / Codex
- `editor-scan-service.ts` 里按 `editorId` switch 扫描规则
- `content-install-dialog.tsx` 里按 editor id 打开不同安装前弹窗
- `editor-adapters/index.ts` 里手写 adapter 数组
- `types/editor.ts` 里手写 `SYNAPSE_EDITOR_IDS`

要消除这些外部改动点，每个 IDE 文件夹必须自己提供执行策略：

```text
adapter.ts  -> 解析全局 / 项目安装路径
install.ts  -> 写 Rule / Skill 的格式
scan.ts     -> 扫描 Rule / Skill 的格式
forms.ts    -> 可选安装前表单
```

通用服务只负责 orchestration：

```text
resolve editor id -> get IDE plugin -> call adapter / install / scan / forms
```

通用服务不再知道 `cursor`、`codex`、`claude-code` 的细节。

### 6. 自动发现是关键

要做到新增 IDE 不改任何注册文件，不能再手写：

```ts
const editorAdapters = [cursorAdapter, codexAdapter, claudeCodeAdapter]
```

也不能再手写：

```ts
export const SYNAPSE_EDITOR_IDS = ["cursor", "codex", "claude-code"] as const
```

需要改成自动发现。

Renderer 侧可以用 Vite：

```ts
const ideModules = import.meta.glob("./*/ide.ts", { eager: true })
const cliModules = import.meta.glob("./*/cli.ts", { eager: true })
const mcpModules = import.meta.glob("./*/mcp.ts", { eager: true })
```

Electron 主进程当前用 `tsc` 构建，不能直接依赖 Vite 的 `import.meta.glob`。所以主进程侧建议用生成脚本：

```text
desktop/scripts/generate-ide-registry.mjs
```

脚本扫描：

```text
desktop/src/ide-definitions/*/
```

生成：

```text
desktop/electron/services/ide-definitions/generated/main-registry.ts
```

构建前运行生成脚本。开发者新增 IDE 时只改 IDE 文件夹，生成文件由脚本维护。

### 7. `SynapseEditorId` 也要改造

当前 `SynapseEditorId` 是联合类型，新增 IDE 必须改类型文件。要达到“只改 windsorf 文件夹”，这里必须改。

推荐最终改成 branded string：

```ts
export type SynapseEditorId = string & { readonly __brand: "SynapseEditorId" }
```

合法性不再靠 TypeScript union，而是靠运行时 registry：

```ts
if (!ideRegistry.has(editorId)) {
  throw new Error("未知 IDE。")
}
```

这样新增 `windsorf` 不需要修改 `desktop/src/types/editor.ts`。

### 8. 最终用户效果

完成后，新增：

```text
desktop/src/ide-definitions/windsorf/
  icon.png
  ide.ts
  adapter.ts
  install.ts
  scan.ts
```

软件自动得到：

- 工具 / IDE 区域出现 Windsorf
- 内容安装菜单出现 Windsorf
- IDE 扫描页支持 Windsorf
- Rule / Skill 按 Windsorf 自己的协议写入
- 没有 `cli.ts`，命令行工具区域不会出现 Windsorf
- 没有 `mcp.ts`，MCP 设置里不会出现 Windsorf

如果后续补充：

```text
desktop/src/ide-definitions/windsorf/cli.ts
```

软件才会自动在命令行工具区域出现 Windsorf CLI。

### 9. 能不能实现最终效果

可以。

但必须满足四个前提：

1. IDE id 不能再靠手写 union 扩展
2. renderer 和 Electron 都要支持自动发现 / 生成 registry
3. CLI / MCP 必须是可选配套文件，不是 IDE 必填字段
4. 安装、扫描、路径解析必须插件化，不能留在中心服务里按 editor id 分支

如果只做第一阶段的 `ide.ts + icon.png`，只能减少 UI 元数据散点，不能达到你的最终目标。

### 10. 安全落地顺序

为了不改变现有功能，建议按这个顺序做：

1. 建立 `ide-definitions/<id>/ide.ts + icon.png`，先只派生 label / order / icon
2. 增加可选 `cli.ts`，让命令行工具区域从所有 `cli.ts` 派生，但保持 Claude Code / Codex 结果不变
3. 增加可选 `mcp.ts`，让 MCP 展示从所有 `mcp.ts` 派生，但保持 target 不变
4. 把安装前表单迁到 `forms.ts`，保持 payload 字段不变
5. 把 adapter 注册迁到生成 registry，保持路径解析结果不变
6. 把扫描策略迁到 `scan.ts`，保持 scan result shape 不变
7. 把安装策略迁到 `install.ts`，保持写入文件内容不变
8. 最后把 `SynapseEditorId` 从 union 改成 branded string

每一步都应该先让现有 Cursor / Codex / Claude Code 输出完全一致，再进入下一步。

### 11. 这个方案和当前第一阶段文档的关系

当前文档前面提出的“先收口展示元数据”仍然成立，但它只是第一步，不是终局。

终局不是：

```text
icon.png + definition.ts
```

终局是：

```text
icon.png + ide.ts + adapter.ts + install.ts + scan.ts + 可选 cli.ts + 可选 mcp.ts + 可选 forms.ts
```

只有这样，新增 `windsorf` 才能真正做到不改其他地方。

## 十、当前发现的明显问题

### 1. 文档与实现有漂移

`editor.md` 中关于 Claude Code 全局 Rule 的说明仍写的是：

- `~/.claude/CLAUDE.md`

但当前代码实际走的是：

- `~/.claude/rules/<rule-name>.md`

对应实现：

- `desktop/electron/services/editor-adapters/claude-code-adapter.ts`

这会影响后续扩展时对“已有规范”的判断，建议单独修正文档。

### 2. Cursor Rule 的 Synapse 来源识别不稳定

`editor-scan-service.ts` 当前用：

- `metadata.description?.includes("synapse")`

来判断 Cursor 规则是不是 Synapse 写入。

这不是稳定标记，容易误判：

- 用户自己写的 description 也可能包含 synapse
- Synapse 写的 description 不一定永远包含 synapse

相比之下：

- Skill 已经有 `.synapse.json`
- Codex Rule 已经有 `<!-- synapse-rule:... -->`

Cursor Rule 这块还缺一个稳定的身份标记策略。

### 3. 有未使用的旧工具痕迹

三个 adapter 都还 import 了：

- `resolveSkillTargetPath`

但当前代码路径解析实际使用的是：

- `checkSkillNameConflict()`
- 手动 `path.join(...)`

`resolveSkillTargetPath()` 目前没有真实调用点，属于可疑旧痕迹。

这不是当前功能 bug，但说明扩展相关代码经历过重构，后续继续扩时要小心沿着旧文档或旧函数走偏。

## 十一、建议的扩展策略

### 短期

如果只是再接一个编辑器，不做大重构：

1. 先新增 adapter
2. 在 `editor-adapters/index.ts` 注册
3. 补 renderer 的顺序和图标
4. 补扫描分支
5. 补安装分支
6. 如果涉及 CLI 或 MCP，再补对应独立链路

这样成本最低，但会继续增加分散定义。

### 中期

如果准备把编辑器能力做成长期可扩展体系，建议先做一轮“注册表收口”：

1. 新建 renderer 侧 `ide-definitions/`，只收口 label、order、icon
2. 让 `editor-registry.ts`、`editor-icons.ts` 从 definitions 派生并保持旧导出
3. 稳定后再加入安装前 UI、CLI、MCP 的展示元数据
4. 最后再把安装策略和扫描策略下沉到 Electron 侧定义 / adapter

### 长期

理想状态是形成三层清晰边界：

1. renderer `ide-definitions/`
   - 负责图标、label、顺序、安装前 UI 元数据
2. Electron `editor-adapters/` / `ide-definitions/`
   - 负责路径解析、扫描策略、写入协议、CLI/MCP 主进程能力
3. `content-install-service` / `editor-scan-service`
   - 只做通用 orchestration

这样新增编辑器才可能真正接近：

> “新增一个文件 + 注册一次”

## 十二、最终判断

### 现在有没有一个集中的文件夹或文件定义？

有，但只集中了一半。

最核心的集中位置是：

- `desktop/electron/services/editor-adapters/`

最核心的集中注册文件是：

- `desktop/electron/services/editor-adapters/index.ts`

最核心的统一服务文件是：

- `desktop/electron/services/editor-adapter-service.ts`

### 它够不够支撑后期扩展？

可以支撑，但还不够优雅。

当前适合“继续做”，但还不适合“低成本持续扩很多编辑器”。

如果未来编辑器会继续增加，下一步最值得做的不是推翻 adapter 体系，而是：

- 继续以 adapter 体系为主干
- 把散在外面的顺序、图标、扫描、安装 UI、CLI/MCP 元数据统一收口

这样才能把“编辑器支持”真正变成一个稳定的扩展面。
