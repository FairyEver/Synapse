# CC Connect 迁移到 3S 的整体标准

## 目标

把 CC Connect 的全部功能迁移到 3S。这里的“全部功能”不靠反复主观检查定义，而靠可追溯的功能全集定义：

> 只要 `artifacts/1.2-feature-manifest.md` 中的正式功能项全部闭合，并且每一项都有迁移结果和验收证据，迁移即完成。

CC Connect 正式项目资产路径：

```text
/Users/liyang/Desktop/code-guide/cc-connect-main
```

功能全集盘点必须以该路径下的完整项目资产作为正式来源证据，包括 Go、Web、npm、daemon、config、core、README、测试、配置和运行入口。不要只扫描 Go。

## 核心原则

1. 先盘点，再设计，再开发。
2. 任何正式功能都必须有来源证据。
3. 没有证据的猜测不能进入正式功能全集。
4. AI 不能无限追加“可能遗漏”，只能追加“有证据的新功能项”。
5. 每个功能项必须有唯一 ID、迁移位置、验收标准和完成证据。
6. 最终开发计划必须从功能全集、产品设计、迁移映射和验收账本生成，不能凭主观想象编写。

## 停止条件

迁移工作在同时满足以下条件时停止：

1. `artifacts/1.2-feature-manifest.md` 中所有正式功能项状态都不是 `todo`。
2. 每个 `done` 功能项都有验收证据。
3. 每个 `replaced`、`merged`、`dropped` 功能项都有明确原因和用户确认。
4. `artifacts/1.1-source-inventory.md` 中记录的源码入口、文档入口、配置入口、运行入口均已映射到功能项或明确排除。
5. `artifacts/4.1-verification-ledger.md` 中的验收项全部通过，或有用户确认的豁免。
6. `artifacts/5.1-development-plan.md` 的阶段任务全部完成。
7. `artifacts/5.2-development-plan-review.md` 结论为 `pass`，或所有 `needs-user-confirmation` 项已由用户确认。
8. `artifacts/7.2-reverse-coverage-check.md` 中所有新增入口都能追溯到 CC ID 或 `artifacts/5.3-decision-log.md`。
9. 数据兼容、权限安全、golden 样本、人工验收、发布回滚相关阻塞项均已关闭或有用户确认豁免。

## 端到端追踪规则

最终执行前，必须能从任意一个 CC Connect 来源入口追踪到完整链路：

```text
source inventory entry
→ CC ID
→ glossary/concept map
→ Synapse product baseline
→ product design location
→ migration map target
→ data compatibility/security map
→ verification ledger item
→ golden/manual acceptance item
→ development plan phase
→ decision/release plan
```

如果链路中任一节点缺失，该项不能进入开发执行。

`artifacts/1.1-source-inventory.md` 中每个入口都必须有覆盖状态：

```text
mapped：已映射到一个或多个正式 CC ID
candidate：证据不足，进入 open questions
excluded：明确不是用户功能或迁移范围，需记录原因
blocked：无法判断，阻塞下一阶段
```

禁止留下空白覆盖状态。

## 功能全集规则

每个正式功能项必须包含：

```text
ID
来源证据
功能或行为
入口
输入
输出
副作用
用户可见结果
错误或异常行为
3S 迁移方式
验收标准
状态
验收证据
```

来源证据可以是：

```text
源码文件路径 + 行号
文档文件路径 + 段落
测试文件路径 + 用例名
运行观察记录
配置项或数据结构定义
```

来源证据不可以是：

```text
AI 猜测
“应该有”
“通常会有”
“看起来可能”
```

## 状态定义

```text
candidate：有线索但证据不足，不阻塞完成
todo：正式功能项，尚未迁移
mapped：已经确定 3S 落点
in_progress：正在迁移
done：已迁移并有验收证据
merged：已合并到另一个功能项，需记录目标 ID
replaced：被 3S 中等价能力替代，需记录替代方案
dropped：明确不迁移，需用户确认
blocked：无法继续，需记录阻塞原因
```

## 迁移策略

默认采用三类迁移方式：

```text
产品行为迁移：保证用户在 3S 中能完成同等流程。
核心逻辑移植：把 Go 逻辑迁到 TypeScript，并用 golden tests 对比输入输出。
Go sidecar 过渡：复杂或高风险 Go 能力先作为本地 sidecar 接入 3S，再逐步替换。
```

优先级：

```text
1. 用户可见主流程
2. 数据和配置兼容
3. 核心逻辑一致性
4. 异常和边界行为
5. 运维、日志、诊断、导入导出等辅助能力
```

## 3S 工程约束

迁移到 3S 时必须遵守本仓库规则：

1. Electron 能力只能通过 main process、preload 和 typed API 暴露。
2. Renderer 只能访问 `window.synapse.*`。
3. 不在 React 组件中直接做文件系统、git、安装、下载、进程、端口等特权操作。
4. UI 使用现有 shadcn/ui、Radix、Tailwind token，不写自定义颜色和装饰性样式。
5. 新业务模块优先放在 `desktop/src/modules/`。
6. 网络、存储、权限、日志、IPC 必须复用项目已有基础设施。
7. 不做顺手重构，不迁移 manifest 外的功能。

## 审计规则

后续 AI 审计只能输出两类问题：

```text
A. manifest 中已有 ID 未闭合。
B. 有证据的新候选项，需要用户确认是否纳入正式范围。
```

禁止输出泛泛建议，例如：

```text
可能还需要完善用户体验
建议补充更多异常情况
也许还有配置项遗漏
可以进一步优化架构
```

如果没有证据，必须放入 `candidate` 或 `open questions`，不能阻塞迁移完成。

## 推荐执行顺序

1. 阅读 `使用方式.md`。
2. 如果需要自动编排，使用 `orchestrator/START_HERE.md`。
3. 如果手动执行，使用 `prompts/01-功能全集盘点.md` 生成功能全集。
4. 使用 `prompts/00-阶段验收门.md` 验收阶段 01。
5. 如果同一阶段 3 次 fail，使用 `prompts/00A-验收争议裁决.md` 裁决。
6. 使用 `prompts/02-产品设计与信息架构.md` 生成产品设计。
7. 使用 `prompts/00-阶段验收门.md` 验收阶段 02。
8. 如果同一阶段 3 次 fail，使用 `prompts/00A-验收争议裁决.md` 裁决。
9. 使用 `prompts/03-迁移映射设计.md` 生成迁移映射。
10. 使用 `prompts/00-阶段验收门.md` 验收阶段 03。
11. 如果同一阶段 3 次 fail，使用 `prompts/00A-验收争议裁决.md` 裁决。
12. 使用 `prompts/04-验收账本设计.md` 生成验收账本。
13. 使用 `prompts/00-阶段验收门.md` 验收阶段 04。
14. 如果同一阶段 3 次 fail，使用 `prompts/00A-验收争议裁决.md` 裁决。
15. 使用 `prompts/05-最终开发计划.md` 生成最终开发计划。
16. 使用 `prompts/00-阶段验收门.md` 验收阶段 05。
17. 使用 `prompts/05A-开发计划完整性复核.md` 复核最终开发计划。
18. 使用 `prompts/00-阶段验收门.md` 验收 05A。
19. 如果同一阶段 3 次 fail，使用 `prompts/00A-验收争议裁决.md` 裁决。
20. 使用 `prompts/06-分批执行迁移.md` 按开发计划执行。
21. 每批执行后使用 `prompts/00-阶段验收门.md` 验收。
22. 使用 `prompts/07-收口审计.md` 做闭环审计。
