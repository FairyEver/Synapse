# CC Connect 迁移到 3S 的整体标准

## 目标

把 CC Connect 的全部功能迁移到 3S。这里的“全部功能”不靠反复主观检查定义，而靠可追溯的功能全集定义：

> 只要 `artifacts/1.2-feature-manifest.md` 中的正式功能项全部闭合，并且每一项都有迁移结果和验收证据，迁移即完成。

CC Connect 正式项目资产路径：

```text
/Users/liyang/Desktop/code-guide/cc-connect-main
```

功能全集盘点必须以该路径下的完整项目资产作为正式来源证据，包括 Go、Web、npm、daemon、config、core、README、测试、配置和运行入口。不要只扫描 Go。

CC Connect Admin 可运行后台也是正式来源证据。重新规划或重跑开发前，必须先执行：

```text
待办/cc-connect-migration/prompts/08-CC-Connect-Admin-实测盘点.md
```

并把以下文件作为产品设计、迁移映射、开发计划和验收账本的强制输入：

```text
artifacts/8.1-cc-connect-admin-walkthrough.md
artifacts/8.2-cc-connect-admin-screen-map.md
artifacts/8.3-cc-connect-admin-interaction-ledger.md
artifacts/8.4-cc-connect-admin-to-3s-gap-list.md
artifacts/8.5-cc-connect-admin-layout-and-flow-map.md
```

## 用户通知规则

用户已授权本迁移项目使用 Bark 手机通知提醒后续处理事项。凡是编排器、阶段提示词或代码执行器遇到以下情况，必须先更新对应 state/log/resume/summary 文件，再发送手机通知：

1. 进入 `needs-user-confirmation`。
2. 进入 `blocked` 或生成 `6.x-blocker.md`。
3. 需要用户提供路径、账号、token、secret、二维码扫码、第三方授权、依赖批准、范围取舍、豁免确认或是否继续执行的决定。
4. 无人值守运行结束后，需要用户查看最终结果、人工验收、处理跳过项或继续补做阻塞项。

Bark endpoint：

```text
https://api.day.app/B3H8T6rF2p5Mj6z6oha82K
```

推荐发送方式：

```bash
curl --silent --show-error --fail -X POST "https://api.day.app/B3H8T6rF2p5Mj6z6oha82K" \
  -H "Content-Type: application/json; charset=utf-8" \
  --data "{\"title\":\"Synapse CC Connect 需要处理：<阶段或批次>\",\"body\":\"<需要用户决定什么；推荐先看哪个文件；下一步可直接回复什么>\",\"group\":\"Synapse CC Connect 迁移\"}"
```

通知文案必须简短、可执行，至少包含：当前阶段/批次、为什么停下、用户下一步先看哪个文件、建议直接回复什么。不得把 API key、secret、token、Raw TOML、二维码内容或敏感配置写入通知正文。通知发送成功或失败都必须记录到当前 log；通知失败不得阻止状态文件落盘。

## 跨对话交接规则

用户可能通过远程控制软件操作，不方便滚动、右键复制或在多个 Codex 对话之间转述长文本。所有跨对话消息传递必须优先使用本地文件“纸条”，不要依赖用户手动搬运长段聊天内容。

固定协议文件：

```text
待办/cc-connect-migration/orchestrator/HANDOFF_PROTOCOL.md
```

固定最新纸条：

```text
待办/cc-connect-migration/artifacts/0.0-latest-handoff.md
```

凡是阶段完成、批次完成、暂停、阻塞、需要用户确认、无人值守完成、需要另一个对话继续，都必须在最终回复前更新 `0.0-latest-handoff.md`。如果用户说“检查最新状态”“去看另一个对话的结果”“看纸条”，当前对话必须先读取 `0.0-latest-handoff.md`，再读取其中列出的状态文件和报告文件。

给另一个 Codex 对话的传话应尽量短，只要求它读取 `HANDOFF_PROTOCOL.md` 和 `0.0-latest-handoff.md`，不要让用户复制大段上下文。

## 当前对话完成通知规则

用户已明确要求：每一次阶段性工作完成后，都要发送 Bark 手机通知，提醒用户回来查看当前对话结果。此规则适用于当前 Codex 对话和后续迁移执行对话。

触发条件包括但不限于：

1. 完成一次分析、报告、提示词修改、代码修改、验证或审计。
2. 写入或更新了关键 artifact。
3. 给出下一步建议。
4. 阻塞、暂停、等待用户确认。

通知必须在最终回复前发送。通知正文只写简短结果和建议回来查看，不写敏感信息。

## 核心原则

1. 先盘点，再设计，再开发。
2. 任何正式功能都必须有来源证据。
3. 没有证据的猜测不能进入正式功能全集。
4. AI 不能无限追加“可能遗漏”，只能追加“有证据的新功能项”。
5. 每个功能项必须有唯一 ID、迁移位置、验收标准和完成证据。
6. 最终开发计划必须从功能全集、产品设计、迁移映射和验收账本生成，不能凭主观想象编写。
7. 用户可见功能不能只根据源码或计划抽象实现，必须对照 CC Connect Admin 实测结果，保证 3S 中有真实入口、真实页面、真实表单、真实二级流程和可验收交互。

## 停止条件

迁移工作在同时满足以下条件时停止：

1. `artifacts/1.2-feature-manifest.md` 中所有正式功能项状态都不是 `todo`。
2. 每个 `done` 功能项都有验收证据。
3. 每个 `replaced`、`merged`、`dropped` 功能项都有明确原因和用户确认。
4. `artifacts/1.1-source-inventory.md` 中记录的源码入口、文档入口、配置入口、运行入口均已映射到功能项或明确排除。
5. `artifacts/4.1-verification-ledger.md` 中的验收项全部通过，或有用户确认的豁免。
6. `artifacts/5.1-development-plan.md` 的阶段任务全部完成。
7. `artifacts/5.2-development-plan-review.md` 结论为 `pass`，或所有 `needs-user-confirmation` 项已由用户确认。
8. `artifacts/7.2-reverse-coverage-check.md` 中所有新增入口都能追溯到 CC ID 或 `artifacts/5.3-decision-log.md`。
9. 数据兼容、权限安全、golden 样本、人工验收、发布回滚相关阻塞项均已关闭或有用户确认豁免。
10. `artifacts/8.4-cc-connect-admin-to-3s-gap-list.md` 中阻塞迁移完成的入口缺失、页面空壳、逻辑缺失、表单缺失、二级流程缺失、状态缺失、错误处理缺失、数据兼容缺失均已关闭或有用户确认豁免。

## 端到端追踪规则

最终执行前，必须能从任意一个 CC Connect 来源入口追踪到完整链路：

```text
source inventory entry
→ CC ID
→ glossary/concept map
→ CC Connect Admin observed screen / interaction, if user-visible
→ Synapse product baseline
→ product design location
→ migration map target
→ data compatibility/security map
→ verification ledger item
→ golden/manual acceptance item
→ development plan phase
→ decision/release plan
```

如果链路中任一节点缺失，该项不能进入开发执行。

`artifacts/1.1-source-inventory.md` 中每个入口都必须有覆盖状态：

```text
mapped：已映射到一个或多个正式 CC ID
candidate：证据不足，进入 open questions
excluded：明确不是用户功能或迁移范围，需记录原因
blocked：无法判断，阻塞下一阶段
```

禁止留下空白覆盖状态。

## 功能全集规则

每个正式功能项必须包含：

```text
ID
来源证据
功能或行为
入口
输入
输出
副作用
用户可见结果
错误或异常行为
3S 迁移方式
验收标准
状态
验收证据
```

来源证据可以是：

```text
源码文件路径 + 行号
文档文件路径 + 段落
测试文件路径 + 用例名
运行观察记录
CC Connect Admin 实测页面、路由、交互和字段记录
配置项或数据结构定义
```

来源证据不可以是：

```text
AI 猜测
“应该有”
“通常会有”
“看起来可能”
```

## 状态定义

```text
candidate：有线索但证据不足，不阻塞完成
todo：正式功能项，尚未迁移
mapped：已经确定 3S 落点
in_progress：正在迁移
done：已迁移并有验收证据
merged：已合并到另一个功能项，需记录目标 ID
replaced：被 3S 中等价能力替代，需记录替代方案
dropped：明确不迁移，需用户确认
blocked：无法继续，需记录阻塞原因
```

## 迁移策略

默认采用三类迁移方式：

```text
产品行为迁移：保证用户在 3S 中能完成同等流程。
核心逻辑移植：把 Go 逻辑迁到 TypeScript，并用 golden tests 对比输入输出。
Go sidecar 过渡：复杂或高风险 Go 能力先作为本地 sidecar 接入 3S，再逐步替换。
```

优先级：

```text
1. 用户可见主流程
2. 数据和配置兼容
3. 核心逻辑一致性
4. 异常和边界行为
5. 运维、日志、诊断、导入导出等辅助能力
```

## 3S 工程约束

迁移到 3S 时必须遵守本仓库规则：

1. Electron 能力只能通过 main process、preload 和 typed API 暴露。
2. Renderer 只能访问 `window.synapse.*`。
3. 不在 React 组件中直接做文件系统、git、安装、下载、进程、端口等特权操作。
4. UI 使用现有 shadcn/ui、Radix、Tailwind token，不写自定义颜色和装饰性样式。
5. 新业务模块优先放在 `desktop/src/modules/`。
6. 网络、存储、权限、日志、IPC 必须复用项目已有基础设施。
7. 不做顺手重构，不迁移 manifest 外的功能。

## 审计规则

后续 AI 审计只能输出两类问题：

```text
A. manifest 中已有 ID 未闭合。
B. 有证据的新候选项，需要用户确认是否纳入正式范围。
```

禁止输出泛泛建议，例如：

```text
可能还需要完善用户体验
建议补充更多异常情况
也许还有配置项遗漏
可以进一步优化架构
```

如果没有证据，必须放入 `candidate` 或 `open questions`，不能阻塞迁移完成。
