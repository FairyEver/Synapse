# CC Connect 迁移提示词使用方式

## 推荐方式

可以开新对话执行每个阶段。每个阶段提示词已经写明要读取的上一阶段文件路径，所以新对话里通常只需要复制当前阶段提示词。

所有阶段生成的正式文件都放在：

```text
待办/cc-connect-migration/artifacts/
```

文件名使用 `阶段编号.产物序号-英文短名.md`，例如：

```text
1.1-source-inventory.md
1.2-feature-manifest.md
1.4-glossary-and-concept-map.md
2.1-synapse-product-baseline.md
2.2-product-design.md
3.2-data-compatibility-plan.md
3.3-permission-and-security-map.md
4.2-golden-test-cases.md
4.3-manual-acceptance-script.md
5.1-development-plan.md
5.3-decision-log.md
5.4-release-and-rollback-plan.md
```

推荐流程：

```text
01 功能全集盘点
→ 阶段验收门
→ 02 产品设计与信息架构
→ 阶段验收门
→ 03 迁移映射设计
→ 阶段验收门
→ 04 验收账本设计
→ 阶段验收门
→ 05 最终开发计划
→ 阶段验收门
→ 05A 开发计划完整性复核
→ 阶段验收门
→ 06 分批执行迁移
→ 每批执行后验收门
→ 07 收口审计
```

如果同一阶段连续 fail，不要无限循环。第 3 次 fail 后，使用：

```text
待办/cc-connect-migration/prompts/00A-验收争议裁决.md
```

## 同一对话还是新对话

优先使用同一对话完成 01 到 04，因为上下文连续，来回解释少。

如果开新对话，当前阶段提示词已经内置以下内容：

```text
1. 待办/cc-connect-migration/整体标准.md
2. 上一阶段已经生成的正式产物路径
3. 本阶段要生成的产物路径
4. 阶段验收门提示词路径
```

例如执行 02 时，提示词中已经包含这些路径：

```text
待办/cc-connect-migration/整体标准.md
prompts/02-产品设计与信息架构.md
待办/cc-connect-migration/artifacts/1.1-source-inventory.md
待办/cc-connect-migration/artifacts/1.2-feature-manifest.md
待办/cc-connect-migration/artifacts/1.4-glossary-and-concept-map.md
待办/cc-connect-migration/artifacts/1.3-open-questions.md
prompts/00-阶段验收门.md
```

例如执行 03 时，提示词中已经包含这些路径：

```text
待办/cc-connect-migration/整体标准.md
prompts/03-迁移映射设计.md
待办/cc-connect-migration/artifacts/1.1-source-inventory.md
待办/cc-connect-migration/artifacts/1.2-feature-manifest.md
待办/cc-connect-migration/artifacts/2.1-synapse-product-baseline.md
待办/cc-connect-migration/artifacts/2.2-product-design.md
待办/cc-connect-migration/artifacts/1.3-open-questions.md
prompts/00-阶段验收门.md
```

## 不要直接信任一次输出

每个阶段完成后，都要让 Codex 自己或另一个新对话执行 `prompts/00-阶段验收门.md`。

验收门的作用不是继续发散分析，而是检查：

```text
1. 必需文件是否存在。
2. 必需字段是否齐全。
3. 是否覆盖上一阶段所有正式 ID。
4. 是否混入无证据猜测。
5. 是否生成了不该在本阶段生成的内容。
6. 是否存在阻塞下一阶段的问题。
```

## 最可信的方式

更稳的方式是“双 Codex”：

```text
Codex A：执行阶段任务
Codex B：只做阶段验收门，不写实现、不扩展范围
```

Codex B 的审查结果只能是：

```text
pass：进入下一阶段
fail：列出必须修复的问题
needs-user-confirmation：需要用户确认范围或取舍
```

不要让审查 Codex 输出泛泛建议。

## 失败上限

同一阶段不要无限循环。推荐固定为：

```text
A 执行
B 验收
A 修复
B 复验
A 修复
B 复验
仍然 fail → 使用 prompts/00A-验收争议裁决.md
```

`00A` 的结果只能是：

```text
continue-fix：确实阻塞，继续修
pass-with-notes：不阻塞，带备注进入下一阶段
needs-user-confirmation：需要用户决定范围或取舍
```

这可以通过提示词约束 Codex，但用户仍需要对 `needs-user-confirmation` 做最终决策。

## 可信度来自哪里

这个流程不能保证 AI 永远不犯错。真正的可信度来自六层约束：

```text
证据约束：每个功能必须有源码、文档、测试或运行证据。
概念约束：术语和概念必须先对齐，避免同一能力被重复设计。
覆盖约束：每个阶段必须覆盖上一阶段所有正式 ID。
基线约束：产品设计必须先分析当前 3S 产品结构、功能结构、导航、app shell 和 UI 规范。
产品约束：每个功能必须有菜单、页面、入口或后台归属。
兼容约束：数据、配置、导入导出和旧用户状态必须有兼容与回滚方案。
安全约束：敏感操作必须映射 PermissionGuard、AuditSink、secret 处理和日志脱敏要求。
验收约束：每个功能必须有可判断通过或失败的验收项。
样本约束：核心逻辑必须有 golden test 样本，人工流程必须有人工验收脚本。
发布约束：开发计划必须包含灰度、fallback 和回滚策略。
反查约束：新增代码入口必须能反向追溯到 CC ID 或 decision-log。
停止约束：只有 manifest、glossary、product baseline、product design、migration map、data/security plan、verification ledger、golden/manual acceptance、development plan、decision log、release plan 全部闭合才算完成。
复核约束：development plan review 必须 pass，才能开始分批执行迁移。
```

不要问：

```text
还有没有遗漏？
```

要问：

```text
manifest 中是否有正式 ID 未闭合？
source inventory 中是否有入口没有映射？
verification ledger 中是否有验收项未通过？
```
