## 旧 CC Connect QR 核心逻辑

### Feishu / Lark

旧 Web API：

```text
setupFeishuBegin()
  POST /setup/feishu/begin
  -> device_code, qr_url, interval, expires_in

setupFeishuPoll(device_code, base_url?)
  POST /setup/feishu/poll
  -> status: pending | completed | denied | expired | error
  -> slow_down 可增加 interval
  -> completed 时返回 app_id, app_secret, platform, owner_open_id, base_url

setupFeishuSave(...)
  POST /setup/feishu/save
  -> 保存 app_id/app_secret/platform/owner_open_id/work_dir/agent_type
  -> restart_required
```

旧状态机：

```text
idle -> loading -> scanning -> saving -> completed
                      |          |
                      |          -> error
                      -> denied
                      -> expired
                      -> error
```

旧 Go 逻辑要点：

- 调 `https://accounts.feishu.cn/oauth/v1/app/registration`。
- `init` 必须支持 `client_secret`。
- `begin` 使用 `archetype=PersonalAgent`、`auth_method=client_secret`、`request_user_info=open_id`。
- `poll` 遇到 `tenant_brand=lark` 时切换到 `https://accounts.larksuite.com`。
- `slow_down` 时轮询间隔增加。
- `access_denied` -> denied。
- `expired_token` -> expired。
- 成功后保存 app id/secret，owner open id 可合并到 allow_from。

### Weixin

旧 Web API：

```text
setupWeixinBegin(api_url?)
  POST /setup/weixin/begin
  -> qr_key, qr_url

setupWeixinPoll(qr_key, api_url?)
  POST /setup/weixin/poll
  -> status: wait | scaned | confirmed | expired
  -> confirmed 时返回 bot_token, ilink_bot_id, base_url, ilink_user_id

setupWeixinSave(...)
  POST /setup/weixin/save
  -> 保存 token/base_url/ilink_bot_id/ilink_user_id/work_dir/agent_type
  -> restart_required
```

旧状态机：

```text
idle -> loading -> scanning(wait) -> scanned(scaned) -> saving -> completed
                         |                                |
                         -> expired -> refresh/new QR     -> error
```

旧 Go 逻辑要点：

- 默认 API URL：`https://ilinkai.weixin.qq.com`。
- 获取二维码：`/ilink/bot/get_bot_qrcode?bot_type=3`。
- 轮询状态：`/ilink/bot/get_qrcode_status?qrcode=<qr_key>`。
- 轮询请求带 `iLink-App-ClientVersion: 1`。
- `confirmed` 必须含 `bot_token` 和 `ilink_bot_id`。
- `baseurl` 字段映射到 `base_url`。
- `ilink_user_id` 可合并到 allow_from。
- 过期时旧 CLI 会刷新二维码，有最大刷新次数。

## 3S 完整迁移定义

### 必须完成

1. Feishu/Lark/Weixin 选择后必须能真实开始 QR onboarding，而不是只切本地 state。
2. UI 必须显示可扫描二维码。
3. UI 必须按旧状态机轮询：等待、已扫码、保存中、完成、过期、拒绝、错误。
4. 成功后必须保存平台连接，平台列表可见，项目平台数更新。
5. Feishu/Lark 成功后必须保存 `app_id` 和 `app_secret`，但 `app_secret` 不得明文进 renderer config、Raw TOML、日志、报告。
6. Weixin 成功后必须保存 `token`、`base_url`、`account_id/ilink_bot_id`，但 token 不得明文泄漏。
7. Lark 必须支持从 Feishu poll 结果中自动识别并切换 platform。
8. Weixin 过期必须能刷新或明确重试。
9. 手动平台表单不能只覆盖 Telegram；应尽量基于现有 connector descriptors 或旧 `platformMeta.ts` 覆盖旧 Web Admin 的手动平台字段。
10. 所有网络请求必须在 Electron main 侧服务中执行，renderer 只能走 typed preload/IPC。
11. 敏感 secret 必须进入安全 secret 存储或明确可恢复 secret 写入链路，只在业务配置中保存 secretRef。
12. 必须补自动化测试和 Computer Use 复测。

### 不接受

- 不接受“等待扫码”但没有二维码。
- 不接受“保存成功”但只是 draft，不是真实成功结果。
- 不接受 app_secret/token 明文出现在普通 UI、Raw TOML、日志、report、git diff 或 artifacts。
- 不接受 renderer 直接访问外部网络完成敏感流程。
- 不接受只改文案绕过功能缺失。
- 不接受 source trace 没有旧源码证据就写实现。

## 真实扫码验收边界

自动化测试可以通过 mock HTTP client 完整覆盖 begin/poll/save、过期、拒绝、错误、slow_down、Lark 切换、Weixin confirmed 等状态。

但真实手机扫码不能由 AI 凭空完成。如果真实外部服务需要用户用手机扫二维码，执行者必须：

1. 把二维码显示出来。
2. 发 Bark 通知用户回来扫码。
3. 等待用户扫码确认。
4. 用户不在时，不得把真实扫码验收写成已完成，只能标为 `waiting_user_scan`。
5. mock 自动化通过不等于真实扫码通过。
