# 8.7 产品视角范围裁剪与可用性分析

## 一句话结论

当前问题不是“少补几个按钮”，而是产品迁移策略错位：旧计划把很多 CC Connect 能力标成 `done / merged / replaced`，但没有验证用户在 3S 里能否完成同等任务。下一步应该先冻结产品范围，再重建 02/03/04/05/05A，而不是继续旧 stage 06 写代码。

## 产品判断原则

CC Connect 全量融合到 3S，不等于复制 CC Connect Web Admin 的所有页面、商店、菜单和视觉结构。

更合理的定义是：

```text
保留用户任务闭环
融入 3S 信息架构
不复制旧 Web Admin 外壳
不迁移与 3S 已有能力重复的商店/展示型功能
对后台、诊断、发布、CLI 能力做设置化或隐藏化承接
```

因此每个功能应被判定为以下一种处理方式：

| 处理方式 | 含义 | 是否必须有 UI |
| --- | --- | --- |
| 主流程迁移 | 用户高频使用，必须在 3S 中有真实入口和闭环 | 是 |
| 融入现有模块 | 3S 已有相近模块，保留能力但不复制旧页面 | 是，放到现有模块 |
| 设置化承接 | 低频配置、权限、安全、运维、系统项 | 是，放设置/诊断 |
| 后台/API 承接 | 给内部或外部工具使用，不是普通用户主流程 | 不一定，但要有状态/文档/诊断 |
| 暂缓 | 价值低、风险高、需要外部条件，可后置 | 可无首版 UI |
| 不迁移 | 旧产品外壳、营销/商店/发布渠道等不适合 3S | 无 |

## 产品北极星

真正要迁移的是这条用户价值链：

```text
选择项目
→ 配置 agent / provider
→ 配置平台连接
→ 从平台或本地 Chat 进入会话
→ 查看历史、发送消息、执行命令、处理权限
→ 配置自动化任务
→ 在设置里管理安全、日志、系统参数和诊断
```

任何不能服务这条链路的功能，都不应该优先做成 3S 主入口。

## 当前 3S 失败原因

| 问题 | 证据 | 产品影响 |
| --- | --- | --- |
| 只做了入口，没有任务闭环 | `desktop/src/app-shell/tabs.ts:4` 只新增 `会话/连接/自动化`；`desktop/src/App.tsx:39` 到 `41` 只挂载模块 | 用户能看到菜单，但不能完成 CC Connect 的真实任务 |
| 会话页是静态空壳 | `desktop/src/modules/agent-sessions/index.tsx:20` 状态全是 `0`；`index.tsx:34` 和 `67` 的“新建会话”没有业务动作；`index.tsx:54` 到 `80` 固定空状态 | 用户无法查看历史、发送消息、切换 session、打开命令面板 |
| 连接页是静态能力介绍 | `desktop/src/modules/connectors/index.tsx:20` 到 `25` 是固定分类；`index.tsx:35` 的“添加连接”没有表单；`index.tsx:55` 到 `75` 固定暂无连接 | 用户无法新增平台、扫码、填 token、查看连接状态 |
| 自动化页是空表面 | `desktop/src/modules/automation/index.tsx:36` 到 `69` 只有 Tabs 和空态；`index.tsx:112` 的按钮没有创建任务流程 | 用户无法创建 Cron、配置 Heartbeat、管理 Hooks |
| 设置未承接 CC Connect 配置 | `desktop/src/modules/settings/data.ts:19` 到 `74` 只有通用分类；`data.ts:76` 到 `122` 只有主题、语言、仓库、项目列表 | Provider、安全、限流、附件、Raw config、reload/restart 都没有产品闭环 |
| Skills 被误认为已承接 | `desktop/src/modules/skills/index.tsx:6` 使用 3S 内容模块 | 3S Skills 不是 CC Connect 的项目化扫描/推荐流程，不能直接算等价 |

## 应该迁移为主流程的能力

这些是 CC Connect 对用户有直接价值、且当前 3S 不可用的核心能力。它们必须进入新开发计划的 P0/P1。

| 产品能力 | 对应 8.6 功能 | 应放在 3S 哪里 | 为什么必须迁移 |
| --- | --- | --- | --- |
| 项目中心 | F-005 到 F-023 | 新建 `连接/项目` 或独立项目视图；至少在连接模块内有项目列表和项目详情 | Project 是平台、会话、Provider、Heartbeat、权限的父对象，没有它所有模块都会散 |
| 平台连接向导 | F-011 到 F-016 | 连接模块 | 用户必须能添加 Feishu/WeChat/Telegram 等平台，看到 QR/手动表单和连接状态 |
| Provider 管理和项目绑定 | F-017 到 F-028 | 设置 > 服务商 + 项目详情 Provider Tab | Agent 能否运行依赖 provider，不能只有 service/test |
| Chat 列表和详情 | F-031 到 F-039 | 会话模块 | 这是 CC Connect 的核心使用入口，必须有历史、输入、发送、命令面板、会话抽屉 |
| Cron/Heartbeat/Hooks | F-040 到 F-045 | 自动化模块 | 自动化不能只显示空态，必须有列表、表单、启停、运行结果 |
| 项目级权限与访问控制 | F-014、F-021、F-022 | 项目详情设置 + 设置 > 安全 | 远程聊天平台接入必须能控制谁能用、哪些命令禁用 |
| 关键系统设置 | F-046 到 F-053 | 设置 > CC Connect 或 设置 > 管理员/调试 | 附件、预览、限流、日志、reload/restart 影响运行可用性 |

## 应融入现有 3S，而不是复制旧页面的能力

| CC Connect 能力 | 产品判断 | 推荐承接方式 |
| --- | --- | --- |
| Web Admin 左侧导航和登录页 | 不复制 | 3S 是本地 Electron，不应迁移旧 Web 登录/侧边栏。只迁移真实管理能力 |
| Skills 本地扫描 | 需要承接，但不能直接说现有 Skills 已等价 | 在 3S Skills 里增加“按项目/agent 扫描来源”和与项目详情的关联入口 |
| Skills 推荐/商店 | 可不迁移为 CC Connect 专属功能 | 如果 3S 已有内容市场/技能模块，只保留必要推荐来源；不再复制一个 CC Connect 技能商店 |
| Provider 推荐预设 | 不做“商店”，做配置助手 | 只保留常用 preset、导入和 per-agent 字段，避免做外部生态页面 |
| CLI 命令体系 | 不复制 CLI 页面 | 映射成 UI 动作、typed API、诊断文档和自动化能力 |
| Local API / Management API | 不做普通工作页 | 放设置 > 管理员/工具，显示启用状态、端点、权限和诊断 |
| Daemon / logs / update / npm wrapper | 不做 CC Connect 独立模块 | 融入 3S 关于、调试、管理员和发布治理 |
| Bridge adapter | 不做顶层页面 | 放连接模块高级区，和 Webhook/平台连接统一管理 |
| Terminal Observer | 后置到 IDE/诊断 | 不是大多数用户的主流程，首轮不应阻塞核心 Chat/连接 |
| STT/TTS | 后置或作为平台能力 | 没有基础 Chat/连接前，语音能力没有使用场景 |

## 可以暂缓或不迁移的能力

| 能力 | 建议 | 理由 |
| --- | --- | --- |
| 旧 Web Admin 视觉、路由结构、登录体验 | 不迁移 | 3S 有自己的 App Shell，复制旧 Web 只会形成双系统 |
| Skills 推荐商店完整体验 | 不迁移或合并到 3S Skills | 用户提到的“skill 商店”更像生态展示，不是 CC Connect 核心远程 agent 能力 |
| Provider 外部生态商店 | 不迁移，保留 preset/导入 | 迁移目标是让用户配置 provider，不是经营服务商市场 |
| Raw TOML 完整编辑 | 暂缓，只做脱敏查看和导入 | 直接编辑 Raw TOML 风险高，Electron 里应以结构化设置为主 |
| 全平台一次性完整支持 | 分批 | Feishu/WeChat/Telegram 可先做，其他平台按 connector descriptor 扩展 |
| 系统 daemon 安装/卸载 | 暂缓或管理员设置中显式授权 | 涉及系统写入和权限，不应阻塞 P0 主流程 |
| 终端观察转发 | P2 | 属于高级用户/诊断能力，不应优先于 Chat、连接、项目 |
| npm wrapper 发布细节 | 不作为产品功能 | 在 3S 里最多显示安装来源 |

## 必须修正的旧产品设计误判

旧 `2.2-product-design.md` 的总体方向“不要复制 Web Admin”是对的，但以下判断需要重做：

| 旧判断 | 问题 | 新判断 |
| --- | --- | --- |
| 只新增会话、连接、自动化三个入口 | 缺少项目中心，导致平台、会话、Provider、自动化无共同父对象 | 必须引入项目维度，可以是连接模块内项目中心，也可以是独立二级视图 |
| Provider 放设置即可 | Provider 同时是全局配置和项目运行依赖，只放设置会断开项目绑定 | 设置管理全局 Provider，项目详情负责绑定/切换 |
| Skills 复用现有技能模块 | 没验证 CC Connect 的项目化扫描和推荐是否等价 | 需要专项等价设计：本地项目 skill scan 必须承接，推荐商店可合并/不迁移 |
| System 配置放通用设置 | 当前设置项没有 CC Connect 的附件、预览、限流、日志、reload/restart | 需要 CC Connect 专属设置分组或管理员分组 |
| CLI/Management/Local API 隐藏为后台能力 | 隐藏可以，但必须有状态、授权、诊断和用户可发现的入口 | 放设置 > 管理员/工具，至少提供状态和文档化入口 |
| Web Admin replacement 标为 replaced | 只有入口不是 replacement | replacement 必须以用户任务闭环为准，不能以组件可渲染为准 |

## 新的信息架构建议

不建议完全恢复 CC Connect 的 7 个一级菜单，也不建议继续只有 3 个空入口。建议 3S 中按工作任务组织：

```text
会话
  - 会话列表
  - 会话详情
  - 会话抽屉
  - 命令面板
  - 附件/引用/权限请求

连接
  - 项目列表
  - 项目详情
  - 平台连接
  - QR/手动配置
  - Webhook/Bridge

自动化
  - Cron
  - Heartbeat
  - Hooks

设置
  - 服务商
  - CC Connect 系统设置
  - 安全与访问控制
  - 管理员/API/daemon
  - 日志/诊断/关于

技能
  - 3S 原技能库
  - 项目扫描来源
  - 推荐来源，若 3S 需要
```

其中“项目”必须在连接和会话中可见，因为 CC Connect 的核心对象不是单纯 connector，而是：

```text
project = work_dir + agent + provider + platforms + sessions + automation + policy
```

## 新开发优先级

| 优先级 | 目标 | 完成后用户能做什么 | 是否阻塞迁移完成 |
| --- | --- | --- | --- |
| P0 | 项目中心 + 项目详情 | 看到项目、平台、会话、provider、heartbeat、设置的统一入口 | 是 |
| P0 | Chat 真实闭环 | 打开会话、看历史、发送消息、处理事件/错误 | 是 |
| P0 | 平台连接向导 | 配置至少一类 QR 平台和一类手动 token 平台 | 是 |
| P1 | Provider 管理与绑定 | 新增/导入 provider，并绑定到项目 | 是 |
| P1 | Cron/Heartbeat/Hooks UI | 创建和管理自动化任务 | 是 |
| P1 | CC Connect 系统设置 | 配置附件、预览、限流、日志、reload/restart | 是，但可分批 |
| P2 | Skills 项目化扫描 | 在 3S Skills 中看到项目相关 skills | 部分阻塞，推荐商店不阻塞 |
| P2 | Bridge/Webhook 高级诊断 | 管理 adapter、endpoint 和鉴权 | 不阻塞 P0，但属于完整迁移 |
| P2 | Daemon/Terminal/STT/TTS | 高级能力和诊断能力 | 不应阻塞首轮可用版本 |

## 下一步推荐流程

我建议新增一个“产品范围裁剪门”，不要直接重跑旧 02/03/04/05：

```text
8.7 产品范围裁剪
→ 用户确认 must / merge / defer / drop
→ 9.1 v2 产品设计
→ 9.2 v2 迁移映射
→ 9.3 v2 验收账本
→ 9.4 v2 开发计划
→ 9.5 v2 计划复核
→ 新 stage 06 代码执行
```

原因：

1. 旧 `2.2` 已经证明会把功能“合并”得过度乐观。
2. 旧 `1.2` 的 `done` 状态不能再作为产品可用证据。
3. 直接写代码会继续产出 skeleton。
4. 必须先让用户确认哪些功能确实不迁移，例如旧 Skill 商店、旧 Web Admin 外壳、npm wrapper、Raw TOML 完整编辑。

## 给后续 Codex 的执行边界

后续 Codex 不应再问“是否把 CC Connect 全部功能迁移”，而应按这个口径执行：

```text
逐项处理 8.6 的 F-001 到 F-058。
每项给出 must / merge / defer / drop。
must 和 merge 必须有用户可操作路径。
defer 和 drop 必须有产品理由。
任何 done 必须对应真实 UI/API/验收证据，不允许只凭 service/test。
```

## 需要用户确认的产品取舍

| 问题 | 推荐选择 | 影响 |
| --- | --- | --- |
| 是否复制 CC Connect Web Admin 旧菜单 | 不复制 | 保持 3S 信息架构，但必须补齐任务闭环 |
| Skill 推荐商店是否迁移 | 不作为 CC Connect 专属迁移；并入 3S Skills | 减少重复模块，保留本地项目 skills 扫描 |
| Provider 预设是否迁移为商店 | 不做商店，只做 preset/导入助手 | 保留配置效率，不引入生态页面 |
| Raw TOML 是否完整编辑 | 首轮只做脱敏查看/导入，不做直接编辑 | 降低误改敏感配置风险 |
| Terminal Observer、STT/TTS 是否阻塞首轮 | 不阻塞首轮 | 先完成项目、连接、Chat、Provider、自动化 |
| 是否保留当前空壳入口 | 暂时可保留，但后续批次必须逐步替换为空壳不可见或真实可用 | 避免用户误以为功能可用 |

## 简短建议

我建议下一步先让另一个 Codex 执行“v2 规划重建”，不要直接写代码。输入必须包含 `8.1` 到 `8.7`，输出必须先给出一张 must / merge / defer / drop 表。用户确认后，再生成新的开发计划。

如果用户想省一步，也可以由 Codex 先按本报告推荐默认值生成 v2 计划，但所有 `drop` 和高风险 `defer` 必须在计划里标成待用户确认，不能直接当作最终取舍。
