# 8.6 CC Connect 功能到 3S 当前实现差距矩阵

## 结论

当前 3S 不能视为已完成 CC Connect 融合。

Stage 06/07 里很多 CC ID 已被标为 `done`、`merged` 或 `replaced`，但这些证据主要落在 Electron service、类型、单测、覆盖报告或顶层空入口上。按 Stage 08 对 CC Connect Admin 的实测结果对照后，当前 3S 的产品层仍主要是空壳：有 `会话`、`连接`、`自动化` 三个入口，但缺少项目中心、项目详情、平台配置向导、Provider 管理、真实 Chat、命令面板、Cron 表单、系统设置等用户可操作闭环。

换句话说：底层迁移有碎片，产品功能没有完整承接。

## 判定口径

| 状态 | 含义 |
| --- | --- |
| 可用 | 3S 中有对应入口、真实数据、可执行动作、错误处理和验证证据 |
| 部分可用 | 3S 中有一部分入口或服务，但缺关键流程 |
| 服务层有，产品不可用 | Electron service/type/test 存在，但 renderer 没有可用 UI 或 preload/API 未接通 |
| 入口空壳 | 用户能看到页面/按钮，但列表为空、按钮无动作、没有真实数据 |
| 3S 通用能力，不等价 | 3S 有类似能力，但没有承接 CC Connect 的项目化/平台化语义 |
| 缺失 | 当前仓库没有可见实现 |

## 下一步开发必须遵守的收口顺序

| 顺序 | 必须先补齐的能力 | 原因 |
| --- | --- | --- |
| 1 | CC Connect 概览 + 项目列表 + 项目详情 | 这是平台、会话、provider、heartbeat、设置的共同父对象 |
| 2 | 项目创建/编辑 + 平台添加向导 | 没有项目和平台，连接模块不可用 |
| 3 | Provider 全局管理 + 项目绑定 | Agent 运行和项目配置依赖 provider |
| 4 | Chat 列表/详情 + 会话抽屉 + 输入发送 | 这是 CC Connect 的核心用户价值 |
| 5 | 命令面板 + 命令结果 | Slash commands 是 Chat、Cron、Provider、Skills 的连接器 |
| 6 | Cron/Heartbeat/Hooks 真实表单和列表 | 当前自动化入口只是空壳 |
| 7 | System 设置 + Raw TOML 安全查看 + reload/restart | 运行配置必须可管理，但要做脱敏和权限保护 |
| 8 | Bridge/Webhook/Local API/Daemon/Doctor 等运维入口 | 放在主流程闭合后补齐，避免再次只做服务层碎片 |

## 对当前状态的判断

当前仓库已经有不少“可复用的底层零件”，但还没有把 CC Connect Admin 的功能组织方式迁移到 3S。后续不能再按 `CC-xxx done` 继续推进，而应该按上面的 F-001 至 F-058 逐项闭合：每闭合一项，都要同时有原功能位置、原源码位置、3S UI 入口、3S 业务代码、验证证据和用户可操作路径。
