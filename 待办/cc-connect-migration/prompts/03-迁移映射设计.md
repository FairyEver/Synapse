# 提示词 03：迁移映射设计

把下面提示词完整发送给 Codex。

```text
目标：基于功能全集和产品设计，为 CC Connect 的每个正式功能项设计迁移到 3S 的工程映射方案。本阶段只做工程设计，不写业务代码。

角色与职责：
你是 Electron + TypeScript 架构负责人。你的职责是把已确认的 CC ID 和产品设计映射到 3S 的 main、preload、renderer、service、repository、hook、component 和 test 边界。你不能改变产品归属，不能新增功能，不能实现代码。你的输出必须让验收账本和最终开发计划能精确知道每个功能改哪里、怎么验。

请直接在当前仓库中读取和写入下面列出的路径，不要要求用户手动粘贴文件内容。

请读取：

1. 待办/cc-connect-migration/整体标准.md
2. 待办/cc-connect-migration/artifacts/1.1-source-inventory.md
3. 待办/cc-connect-migration/artifacts/1.2-feature-manifest.md
4. 待办/cc-connect-migration/artifacts/2.1-synapse-product-baseline.md
5. 待办/cc-connect-migration/artifacts/2.2-product-design.md
6. 待办/cc-connect-migration/artifacts/1.3-open-questions.md
7. 当前仓库 AGENTS.md
8. 如果涉及 UI，读取 .claude/rules/design.md 和 .claude/rules/ui-rules.md

请生成：

待办/cc-connect-migration/artifacts/3.1-migration-map.md

如果 `待办/cc-connect-migration/artifacts/` 不存在，先创建该目录。

要求：

1. 待办/cc-connect-migration/artifacts/1.2-feature-manifest.md 中每个正式 ID 都必须出现在迁移映射中。
2. 待办/cc-connect-migration/artifacts/2.2-product-design.md 中每个正式 ID 的产品归属都必须被工程映射承接。
3. 不允许删除、合并、跳过任何 ID，除非在映射中明确标记并说明原因。
4. 每个 ID 必须写清楚 3S 中的落点：
   - Electron main process
   - preload API
   - renderer module
   - data repository
   - service
   - hook
   - UI component
   - test
5. 必须选择迁移方式：
   - 产品行为迁移
   - TypeScript 重写
   - Go sidecar 过渡
   - 合并到已有 3S 能力
   - 不迁移，等待用户确认
6. 如果功能涉及 Go 核心逻辑，优先设计 golden tests，对比 Go 原实现和 3S 实现的输入输出。
7. 如果功能涉及 Electron 特权能力，必须说明 main/preload/renderer 边界。
8. 如果功能涉及 UI，必须承接 待办/cc-connect-migration/artifacts/2.2-product-design.md 的菜单、页面、入口和状态设计。
9. UI 必须使用现有 shadcn/ui、Radix、Tailwind token，不允许自定义颜色、装饰性渐变、卡片套卡片和界面废话。
10. 不写业务代码。
11. 不生成最终开发计划。

待办/cc-connect-migration/artifacts/3.1-migration-map.md 的表格字段至少包含：

CC ID
3S 模块
迁移方式
main/preload/renderer 边界
数据存储方式
需要新增或复用的文件
测试方式
依赖 ID
风险
用户确认项

本阶段完成标准：

1. manifest 中所有正式 ID 都有映射。
2. 每个 ID 都能看出迁到 3S 哪里。
3. 需要用户确认的项被明确列出。
4. 没有进行任何迁移实现。
```
