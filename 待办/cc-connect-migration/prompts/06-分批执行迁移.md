# 提示词 06：分批执行迁移

把下面提示词完整发送给 Codex。

重要：stage 06 分为两个模式。**第一次进入 stage 06 时，只允许执行“模式 A：拆分批次计划”，不得修改任何业务源码。** 只有在用户后续明确点名“开始执行 Dev-P0.x / Dev-P1.x / ...”时，才允许进入“模式 B：执行指定小批次”。

如果用户只说“执行 stage 06”“读取 06-分批执行迁移.md”“进入 Dev-P0”，但没有明确指定小批次编号，则必须按模式 A 处理并暂停。

```text
目标：按照 待办/cc-connect-migration/artifacts/5.1-development-plan.md 进入 stage 06，但必须先把开发计划拆成可独立验收的小批次，不能直接开始写代码。

角色与职责：
你是 CC Connect 迁移执行负责人。你的职责是控制实现节奏，确保每次只做可独立验收的小批次。你不能扩展范围，不能顺手重构，不能修改无关功能，不能偏离当前 3S 的工程和 UI 约束。

请直接在当前仓库中读取和写入下面列出的路径，不要要求用户手动粘贴文件内容。

## 运行模式选择

先判断用户指令属于哪个模式：

### 模式 A：拆分批次计划

适用条件：

1. 用户第一次进入 stage 06。
2. 用户只要求“执行 stage 06”或“读取 06-分批执行迁移.md”。
3. 用户要求“先把 Dev-P0 拆成可独立验收的小批次”。
4. 用户没有明确指定某个小批次编号，例如 `Dev-P0.1`。

模式 A 只允许做这些事：

1. 读取 stage 06 输入文件。
2. 把 `5.1-development-plan.md` 中的 Dev-P0 到 Dev-P4 拆成更小的可独立验收批次。
3. 生成或更新 `待办/cc-connect-migration/artifacts/6.0-dev-batch-plan.md`。
4. 更新 `0.0-orchestrator-state.md`、`0.0-orchestrator-log.md`、`0.0-resume-prompt.md`，说明当前停在待用户确认具体小批次。
5. 汇报下一步可选的小批次编号。

模式 A 禁止事项：

1. 禁止修改 `desktop/` 下任何源码。
2. 禁止修改业务测试文件。
3. 禁止把 `1.2-feature-manifest.md` 中任何 CC ID 改为 done / merged / replaced。
4. 禁止把 `4.1-verification-ledger.md` 中任何验收项改为 pass。
5. 禁止生成 `6.x-execution-report-*`，因为尚未执行实现。
6. 完成 `6.0-dev-batch-plan.md` 后必须停止，等待用户明确指定小批次。

模式 A 的完成输出必须包含：

1. 已生成或更新的 `6.0-dev-batch-plan.md`。
2. 每个小批次的编号、覆盖 CC ID、修改范围、验收方式、前置条件和预计风险。
3. 下一步提示词模板，例如：`请执行 Dev-P0.1，只实现 <名称>，不得执行其他批次。`
4. 明确说明：本次没有写业务代码。

### 模式 B：执行指定小批次

适用条件：

1. 用户明确指定一个小批次编号，例如 `Dev-P0.1`。
2. `待办/cc-connect-migration/artifacts/6.0-dev-batch-plan.md` 已存在。
3. 用户明确允许执行该小批次。

本次执行小批次：

【只有用户明确指定后才填写，例如 Dev-P0.1 / CC-035 安装来源元数据】

模式 B 只允许实现被点名小批次覆盖的 CC ID。不得同时执行下一个小批次。

请读取：

2. 待办/cc-connect-migration/artifacts/5.1-development-plan.md
3. 待办/cc-connect-migration/artifacts/1.2-feature-manifest.md

7. 待办/cc-connect-migration/artifacts/3.2-data-compatibility-plan.md

15. 当前仓库 AGENTS.md
16. 如果涉及 UI，读取 .claude/rules/design.md 和 .claude/rules/ui-rules.md

模式 B 执行要求：

1. 只迁移本小批次列出的 CC ID。
2. 不迁移 development plan 以外的功能。
3. 不做顺手重构。
4. 遵守 3S 的 Electron main/preload/renderer 边界。
5. UI 使用现有 shadcn/ui、Radix、Tailwind token，不写自定义颜色、装饰性渐变、卡片套卡片和界面废话。
6. 业务逻辑不要写在 JSX 内联里。
7. 网络、存储、权限、日志、IPC 必须复用项目已有基础设施。
8. 按本阶段的验收方式补充或更新测试。
9. 涉及敏感操作时，必须按 待办/cc-connect-migration/artifacts/3.3-permission-and-security-map.md 落实 PermissionGuard、AuditSink 和日志脱敏要求。
10. 涉及旧数据、配置、导入导出时，必须按 待办/cc-connect-migration/artifacts/3.2-data-compatibility-plan.md 落实兼容和回滚策略。
11. 涉及 Go 核心逻辑时，必须按 待办/cc-connect-migration/artifacts/4.2-golden-test-cases.md 补充或执行等价验证。
12. 涉及 UI 流程时，必须按 待办/cc-connect-migration/artifacts/4.3-manual-acceptance-script.md 更新人工验收结果。
13. 完成后更新：
   - 待办/cc-connect-migration/artifacts/1.2-feature-manifest.md 中相关 ID 的状态和验收证据
   - 待办/cc-connect-migration/artifacts/4.1-verification-ledger.md 中相关验收项状态
   - 待办/cc-connect-migration/artifacts/5.1-development-plan.md 中本阶段状态
   - 如有取舍或范围变化，更新 待办/cc-connect-migration/artifacts/5.3-decision-log.md
14. 生成本批执行报告，文件名使用 `待办/cc-connect-migration/artifacts/6.x-execution-report-<阶段短名>.md`，其中 `x` 是执行批次序号。
15. 完成一个小批次后必须停止，不得自动进入下一个小批次。
16. 如果发现当前小批次依赖前置批次未完成，必须暂停并写明缺口，不得跳过前置批次硬做。

如果发现疑似遗漏：

1. 必须提供来源证据。
2. 有证据则写入 candidate，并说明是否需要用户确认纳入正式范围。
3. 没有证据则写入 open questions。
4. 不允许因此扩大本小批次实现范围。

模式 B 完成标准：

1. 本小批次覆盖的 CC ID 已完成或明确阻塞。
2. 对应验收项已通过或记录阻塞原因。
3. 相关状态文件已更新。
4. 本批执行报告已写入 artifacts 目录。
5. 没有修改无关功能。
6. 已明确下一小批次编号，但没有自动执行。
```
