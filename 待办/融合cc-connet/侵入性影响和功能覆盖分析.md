# 融合 CC Connect 对 Synapse 的侵入性影响与功能覆盖分析

## 概要

一句话结论：**融合是"垂直叠加"式的，不是"横向替换"式的**。

- 现有 6 个顶层模块（规则、Skill、Prompt、数据库、IDE、设置）、仓库体系、身份体系、内容体系**全部保留且行为不变**。
- 顶层 Tab 从 6 个扩展到 10 个（新增"会话 / 项目 / 连接 / 自动化"），是纯追加。
- 主进程新增一整组服务（agent-runtime、providers、sessions、connectors、scheduler 等），都是新目录，不触碰现有服务。
- preload/IPC 纯追加命名空间，旧通道保留。
- 新增 15 个左右持久化数据对象（Project、AgentSession、Conversation、ProviderProfile、Connector 等），与现有 data-store 正交。
- 设计基线不变：继续用 shadcn/radix-nova + Tailwind token，不迁移 CC Connect 的 Web UI。
- CC Connect 所有**用户可见功能**（11 个平台、11 个 Agent、全部 slash 命令、Provider 体系、自动化、Bridge/Webhook/本地 API、权限、语音、诊断）在产品设计第 9 章映射表中**全部有对应归属**，没有功能遗漏。
- 部分**实现层细节**（ProviderProxy、prompt 占位符语法、ModeOverride、runas preflight 缓存等）颗粒度较粗，需要在每个阶段的技术方案中展开，但不是功能缺失。
- 打包体积是最大的真实风险，取决于平台 SDK 引入数量，应按阶段（M3/M5）分批引入。

## 一、对现有 Synapse 的侵入性影响

按 "当前实际结构 → 设计动作 → 侵入等级" 给出判断。

### 1. 顶层导航（中等侵入）

当前 `desktop/src/App.tsx` 的 `tabs` 定义：

```text
规则 | Skill | Prompt | 数据库 | IDE | 设置
```

设计要求变为：

```text
规则 | Skill | Prompt | 会话 | 项目 | 连接 | 自动化 | 数据库 | IDE | 设置
```

影响：

- 新增 4 个顶层 Tab，`App.tsx` 的 `AppTabId`、`tabs`、`activeTab` 渲染分支都要扩展。
- 会出现"10 个顶层 Tab"，需要重新评估空间与信息密度，沿用 `.claude/rules/design.md`。
- 原 6 个 Tab 的行为与定位**不变**，是追加式扩展。

### 2. 现有模块的语义变化（低侵入但需要扩展）

| 现有模块 | 是否保留 | 语义变化 |
|---|---|---|
| `desktop/src/modules/rules` | 保留 | 新增"安装到 Agent 项目 / 作为远程会话强制规则"的附加能力 |
| `desktop/src/modules/skills` | 保留 | 需兼容 CC `SKILL.md` frontmatter，新增 skill dirs 扫描与 presets |
| `desktop/src/modules/prompts` | 保留 | 增加"作为本地会话启动模板 / cron / heartbeat prompt"的引用 |
| `desktop/src/modules/editor-scan` | 保留 | 扩展识别 Codex/Cursor/Claude Code config + cc-switch providers |
| `desktop/src/modules/settings` | 保留 | 内部新增 Provider / 安全 / 管理 API 子页面 |
| `desktop/src/modules/data-store` | 保留 | 完全不动 |
| `desktop/src/modules/content` | 保留 | 完全不动 |
| `desktop/src/modules/cli` | 保留 | 作为"本地 API / CLI send"的承载点复用 |

**关键结论：没有现有模块被删除或被改写核心行为。** 变化都是"追加能力"而非"替换能力"。

### 3. 主进程服务层（高增量，零破坏）

当前 `desktop/electron/services` 只有内容/仓库/IDE/config 相关服务。设计需要新增一整组服务：

```text
services/agent-runtime/
services/providers/
services/sessions/
services/commands/
services/skills/
services/scheduler/         (cron + heartbeat)
services/connectors/bridge/
services/connectors/webhook/
services/connectors/platforms/
services/hooks/
services/observer/          (Terminal Observer)
services/stt/  services/tts/
services/management-api/
```

影响：

- 这些都是**新增目录**，不触碰 `desktop/electron/services/repository-*` 等现有服务。
- `desktop/electron/main.ts`、`desktop/electron/preload.ts` 需要注册新 IPC 通道，但旧通道完全保留。
- `desktop/electron/ipc/` 新增文件即可。

### 4. 数据与配置层（中等侵入）

当前 `desktop/electron/services/config-store.ts` 存储的是仓库 + 用户身份相关的 Synapse 自身配置，`data-store` 是用户数据库。

设计新增的数据对象（产品设计文档第 10 章）：

```text
Project / Workspace / AgentProfile / AgentSession / Conversation / Message
Connector / ProviderProfile / CommandDefinition / SkillDefinition
ScheduleJob / HeartbeatConfig / RelayBinding / HookRule / AuditEvent / OutboxMessage
```

影响：

- 这是当前最大的真正的"新增面"——需要新建多个持久化存储（JSON 或 SQLite）。
- 不会改写 `config.json` 已有字段。可行性文档建议"每段数据独立版本、迁移脚本可重复"。
- **会话历史** 体积最大，需要提前规划存储位置（建议 `app.getPath('userData')/agent-sessions/`），避免污染现有 data-store。

### 5. preload 表面（中等侵入）

`desktop/electron/preload.ts` 会显著扩张：新增 `agentRuntime.*`、`providers.*`、`sessions.*`、`connectors.*`、`scheduler.*`、`commands.*` 等命名空间。

影响：

- 现有导出**一律保留**（renderer 侧 `desktop/src/lib/electron-bridge.ts` 调用方式不变）。
- 需要严格遵守"窄接口、不暴露 `ipcRenderer`"（可行性文档相关章节）。

### 6. 仓库与身份体系（零侵入）

当前 `desktop/src/app-shell/repository-manager.ts`、`use-repository-manager.ts`、`identity-context.tsx` 的"多仓库 + 用户身份"体系与 CC Connect 的"多项目 + 多 workspace"是**独立正交的两层**：

- Synapse 仓库：用户的内容资产存储位置（Rule/Skill/Prompt 的 git 仓库）。
- CC project / workspace：Agent 运行的目标工作目录。

设计未要求改变前者，也没有试图用后者替换前者。`App.tsx` 的"无仓库空状态"流程完全不受影响。

### 7. UI 组件与设计基线（零侵入）

三份文档都明确要求**不迁移 CC Connect Web UI**：

- 可行性文档："必须用 shadcn/ui 和 Tailwind token"。
- 架构文档："不要照搬 Web 管理端自定义 UI 组件和样式"。
- 产品设计："文案要克制"。

结论：不会引入新的视觉基线、不会改 `desktop/src/components/ui/` 的 shadcn 体系。

### 8. 打包与依赖（低到中）

潜在新依赖（取决于阶段）：

- Agent runtime：需要与 Codex/Claude Code/Cursor CLI 交互（纯 spawn，无 SDK）。
- Bridge：WebSocket server（`ws` 或 Node 原生）。
- Scheduler：cron 解析（`cron-parser`）。
- 平台 SDK（Feishu/Telegram/Slack 等）——**这是最大的依赖引入风险**，设计建议分阶段、先 Bridge 外接再补原生。
- 可选重量级依赖：`ffmpeg`（STT/TTS 转码）——列为 M5 延后。

### 侵入性总评

| 维度 | 等级 | 说明 |
|---|---|---|
| 删除/改写现有功能 | 无 | 现有 6 个模块、仓库体系、身份体系、内容体系全部保留 |
| 顶层 UI 结构 | 中 | 顶层 Tab 从 6 → 10，仅追加 |
| 主进程服务 | 大增量 | 全部新增目录，零破坏 |
| 数据存储 | 大增量 | 多个新数据对象 + 存储，但与现有 data-store 正交 |
| preload/IPC | 中 | 纯追加新通道 |
| 打包体积 | 中到高 | 取决于平台 SDK 引入数量 |
| 设计基线 | 零 | 沿用 shadcn/radix-nova |

**整体结论：融合是"垂直叠加"式的，而不是"横向替换"式的。** 产品设计文档和可行性文档在边界保护上非常自觉，没有试图改写现有的仓库/内容/身份体系——它把 Agent/会话/连接/自动化整体**作为一个新层**叠加上去。

## 二、CC Connect 功能在设计中的覆盖检查

逐项核对 `ccc的方案和架构.md` 所有 CC Connect 能力与产品设计的映射表（第 9 节）、模块设计（第 6 节）。

### 2.2 产品设计中表达较弱但 CC Connect 中存在的细节

以下都是**实现层细节**，产品设计没有遗漏功能本身，但颗粒度较粗，建议在阶段性技术方案中补全：

| CC Connect 细节 | 产品设计中的归属 | 建议补强 |
|---|---|---|
| `ModeOverride`（单条消息临时覆盖权限模式） | §6.1 对话区隐含支持 | 在命令面板中增加"本条消息使用 plan 模式"的快捷 |
| `ContinueSession = "__continue__"` 启动哨兵 | §6.1 状态机隐含 | 属于迁移兼容项，可在"数据迁移"阶段处理 |
| `NewSideSession`（cron `new_per_run` 专用） | §6.4 Cron "会话模式" | 已有"每次新会话"选项，覆盖充分 |
| `UserMeta`（远程用户名和群名缓存） | §6.1 检查器 "信息" 字段 | 字段已列出，实现时补缓存策略 |
| `CronExprToHuman` 多语言显示 | §6.4 Cron "人类可读时间" | 字段已列出 |
| Provider 重名处理 | §6.5 cc-switch 导入流程 | "处理重名" 已列出 |
| `runas_check` / `runas_audit` preflight 缓存 | §6.12 Doctor "run_as_user 是否通过检查" | Doctor 中已覆盖 |
| `restart_notify` 跨进程文件 | §6.12 "Restart" | Electron 不需要照搬，架构文档已说明 |
| Daemon / systemd / launchd / logrotate | 不迁移 | 架构文档明确不适用 Electron |
| `dataDir/run/` 运行时文件布局 | 实现细节 | Electron 用 `app.getPath('userData')` 替代 |

**这些都不是功能遗漏**——产品设计文档是用户视角的功能覆盖，这些细节属于架构文档"可直接复用的设计模式"，应在每个阶段的小范围技术方案中落实（正是可行性文档"开工前检查清单"的用途）。

### 2.3 严格意义上的"有意不做"清单

产品设计中明确延后或不做（可行性文档、架构文档）：

- CC Connect 的 Go daemon / systemd / launchd → 在 Electron 里用更新器 + 主进程生命周期替代。
- CC Connect Web 管理端的视觉组件 → 只迁移信息架构，视觉用 shadcn。
- `core/engine.go` 巨型单文件 → 拆成多个主进程服务。
- 自升级 `/upgrade` 下载替换二进制 → 用 Electron updater。
- 一次性迁移所有平台 → 分阶段 M3/M5。

这些都是**主动决策**，不是遗漏。

### 功能对齐总评

**CC Connect 的全部用户可见功能在产品设计中都有明确归属。**

逐项核对后：

- 11 个平台、11 个 Agent、所有 slash 命令、所有 Provider 能力、所有自动化（Cron/Heartbeat/Relay/Hooks/Outbox）、所有外部入口（Bridge/Webhook/本地 API/Management API）、权限体系、语音/附件、诊断/升级/Terminal Observer —— **全部有对应页面或 tab 位置**，并在第 9 章"全功能映射表"中一一列出。
- 没有发现"CC Connect 有、产品设计没有"的用户级功能。
- 部分**实现细节**（ProviderProxy、prompt template 占位符语法、ModeOverride、runas preflight 缓存等）颗粒度较粗，但属于架构文档已覆盖的迁移模式，应在每个阶段的小范围技术方案中展开。
