# 重构执行协议（无人值守模式）

> 本文档是**给人看的总览**。AI 执行的规则已迁移到两个独立的提示词文件。

## 1. 文档家族全景

四份文件配合工作，分工清晰：

| 文件 | 面向 | 角色 | 是否修改 |
|---|---|---|---|
| `架构前置改造建议.md` | 人 + AI | **SPEC**：设计唯一真相，2012 行详细设计 | 只读，AI 不动 |
| `REFACTOR-START-PROMPT.md` | 给 AI 复制用 | **启动提示词**：首次运行的完整指令集 | 只读 |
| `REFACTOR-RESUME-PROMPT.md` | 给 AI 复制用 | **恢复提示词**：中断后续接 | 只读 |
| `重构执行协议.md`（本文） | 人 | **总览**：说明怎么用、怎么看结果、常见问题 | 只读 |
| `REFACTOR-PROGRESS.md` | AI 写 / 人看 | **进度文件**：任务清单 + 当前状态 | 运行时生成，AI 频繁更新 |
| `REFACTOR-COMPLETION-REPORT.md` | AI 写 / 人看 | **最终报告**：变更、决策、问题、建议 | 运行时生成，AI 增量追加 |

**只需要手动操作两份**：`REFACTOR-START-PROMPT.md`（首次）和 `REFACTOR-RESUME-PROMPT.md`（断线续接）。

## 2. 运行模式核心特性

本协议设计为**全自主、连续、自检**：

- **不暂停**：从 T1.1 到自检循环结束，中间不等待任何用户指令。
- **不询问**：遇到任何疑问都按决策规则自主决策，写进 REPORT。
- **决策分级**：
  - Level 1 自主（风格、命名）→ 不记录
  - Level 2 记录（SPEC 未覆盖的选择）→ 写进 REPORT
  - Level 3 保守（SPEC 与代码矛盾、涉用户数据）→ 保留现有行为 + 标红
- **放弃策略**：单任务 3 次失败→blocked 跳过；Phase 30% blocked→跳过剩余；整体 50% blocked→停下写最终报告。
- **自检循环**：所有 Phase 做完后跑五类检查（typecheck / lint / tests / 硬约束 grep / 接口总览核对），有问题就修，最多 10 轮。
- **高频 snapshot**：PROGRESS 每任务更新、REPORT 增量追加，任何断点都不会丢上下文。
- **鲁棒恢复**：每原子任务一个 commit，新 AI 会话粘贴恢复提示词即可续接。

## 3. 使用流程（你要做的事）

### 3.1 首次启动（出门前）

```text
[1] 确认工作区：
    cd /Users/liyang/Documents/code/github/Synapse
    git status
    # 建议工作区干净；不干净 AI 会自动 stash

[2] 打开新的 AI 对话（Claude Code / Windsurf / Cursor Agent 等）

[3] 打开 REFACTOR-START-PROMPT.md
    复制里面 fenced code block（```text ... ````）整段

[4] 粘贴到 AI 对话框、回车

[5] 离开
```

AI 首次启动做的事：

1. 读完整 SPEC（2012 行）
2. `git checkout -b feat/phase-0/architecture-foundation-YYYYMMDD`
3. 创建 `REFACTOR-PROGRESS.md`（含 71 任务清单）
4. 创建 `REFACTOR-COMPLETION-REPORT.md` 骨架
5. 开始 T1.1 → T1.2 → ... → T6.17
6. 完成后跑自检循环最多 10 轮
7. 最终刷新 REPORT 并停下

全程你**不需要干预**。

### 3.2 回来后查看结果（几小时后）

按严重性顺序扫结果：

```text
[1] git log --oneline <起始 hash>..HEAD
    # 看 commit 数和节奏，了解改动规模

[2] REFACTOR-PROGRESS.md 顶部 YAML
    # 看 status: completed / completed_with_issues
    # 看 task_counts: completed / blocked / pending

[3] REFACTOR-COMPLETION-REPORT.md §1 执行摘要
    # 一眼看整体状态

[4] REFACTOR-COMPLETION-REPORT.md §3.2 Level 3 保守决策 ⚠
    # 你必须复核的关键点

[5] REFACTOR-COMPLETION-REPORT.md §5 跳过/Blocked 任务
    # 了解哪些任务没完成、原因

[6] REFACTOR-COMPLETION-REPORT.md §6 对 SPEC 的偏离
    # AI 建议 SPEC 修订的地方

[7] REFACTOR-COMPLETION-REPORT.md §8 遗留问题清单
    # 剩余工作，按严重性排序

[8] REFACTOR-COMPLETION-REPORT.md §9 验证指南
    # AI 给你的后续步骤建议
```

### 3.3 中断续接（网络断 / 对话丢失）

```text
[1] 打开新的 AI 对话（全新 AI 实例也行）

[2] 确认 REFACTOR-PROGRESS.md 仍在
    cat 待办/融合cc-connet/REFACTOR-PROGRESS.md | head -20

[3] 打开 REFACTOR-RESUME-PROMPT.md
    复制里面 fenced code block 整段

[4] 粘贴到 AI 对话框、回车

[5] 离开
```

AI 恢复流程做的事：

1. 读 PROGRESS → 拿到 current_task
2. 检查 git 状态 → 处理 WIP（干净则直接继续；脏则判断回滚/暂存）
3. 校验 git commit 与 PROGRESS 一致性
4. 在 REPORT 追加"恢复节点"段
5. 按启动提示词的规则继续执行到完成

### 3.4 主动停止（AI 跑飞了）

如果你发现 AI 执行异常（例如反复修同一个错误），直接**关闭 AI 对话**即可。

AI 写的所有 commit 都在 git 里，PROGRESS 和 REPORT 都在磁盘上。下次你可以：

- 用恢复提示词接着跑（如果只是偶发异常）
- 手工 `git reset --hard <某 commit>` 回到安全点，再用恢复提示词
- 或者手工检查 PROGRESS / REPORT，决定下一步

## 4. 关键参数速查

### 4.1 71 个原子任务分布

- **Phase 0.1** ServiceRegistry：T1.1 - T1.9（9 任务，约 2-3 天）
- **Phase 0.2** DataRepository：T2.1 - T2.14（14 任务，约 3-4 天）
- **Phase 0.3** IPC Codegen + WindowManager + NetworkServiceRegistry：T3.1 - T3.16（16 任务，约 4-5 天）
- **Phase 0.4** EventBus：T4.1 - T4.8（8 任务，约 2 天）
- **Phase 0.5** ProjectContainer + ProcessRuntime：T5.1 - T5.7（7 任务，约 2-3 天）
- **Phase 0.6** 工程规范与可观测性：T6.1 - T6.17（17 任务，约 2 天）

**总工作量约 18-21 工程日**（人工实施）；AI 执行速度未知，估计几小时到一个工作日。

### 4.2 commit 命名规则

- 任务 commit：`refactor(phase-0.X): T<N>.<M> <简述>`
- 自检修复 commit：`refactor(audit-R<轮数>): <简述>`

### 4.3 五类自检

1. **编译**：`pnpm desktop:typecheck`
2. **lint**：`pnpm desktop:lint`
3. **测试**：`pnpm desktop:test`
4. **硬约束 grep**：7 条扫描（见 START-PROMPT §6）
5. **接口总览核对**：SPEC §15.13 列出的 13 个 runtime 子目录是否全建立

### 4.4 11 条硬约束（SPEC §1.硬约束）

所有 commit 前 AI 都会自检：

1. 不允许 `export default new XxxService()` 全局单例
2. 不允许裸 `ipcMain.handle/on`
3. 不允许裸 `webContents.send`
4. 不允许裸 `fs.writeFile` 持久化业务数据
5. 不允许裸 `http.createServer` / `net.createServer`
6. 不允许 `modules/A` 直接 import `modules/B` 实现
7. 不允许裸 `fs.writeFile(config-like-path)`
8. 渲染层只允许 `window.synapse.*` 访问 Electron
9. `runtime/*` 不依赖 `modules/*` 和业务代码
10. 敏感操作必须走 `PermissionGuard` + `AuditSink`
11. 新 content type / editor adapter / connector / provider / hook 必须通过 `ExtensionPoint` 注册

## 7. 常见问题

### Q: AI 把 SPEC 改了怎么办？

**不会**。提示词明确禁止改 SPEC。AI 只能在 REPORT §6 记录反馈建议。

### Q: AI 误 push 到远程怎么办？

**不会**。提示词明确禁止 `git push`。回来后所有 commit 都在本地。

### Q: 如果 AI 把代码搞坏了，应用启动不了？

所有 commit 在本地 git，你可以：

```bash
# 看完整改动
git log --oneline <起始 hash>..HEAD

# 完全回滚所有 AI 改动
git reset --hard <起始 hash>

# 或者只回退到某个你信任的 commit
git reset --hard <某 commit>
```

因为 AI 不 push，**任何时候都可以完全回滚**。

### Q: 会不会 AI 自己改了进度文件欺骗我？

提示词要求"不欺骗"。但最终你要验证时：

- `git log --oneline` 实际 commit 数 vs PROGRESS 声称的 completed 数
- 任意 commit 的 diff 是否真的做了声称的事
- Phase 的 `pnpm desktop:test` 跑一遍看有没有失败的

这是你要做的最低限度的复核。

### Q: 依赖缺失（比如 zod、ts-morph）AI 会自己装吗？

提示词 §13（START-PROMPT）允许 AI 自己选最新 stable 版本安装。它会 `pnpm add` 并记录到 REPORT §7。回来后你可以复核 `package.json` 的新增依赖。

### Q: 如果有 17 个 Phase 0.6 任务 AI 跑完要多久？

按 AI 常规速度，**2-8 小时**。具体看：

- AI 读代码速度（每 Phase 读几千行）
- 测试运行速度（typecheck + vitest）
- 是否频繁遇到 blocked

### Q: AI 卡在某个任务上怎么知道？

两个信号：

1. PROGRESS 的 `last_updated` 超过 10 分钟没更新
2. `git log -1` 的 commit 时间戳停在很久以前

这时可能 AI 真的卡死了。你可以关闭对话，用恢复提示词重开。

### Q: 我能中途看它做得怎么样吗？

可以。打开 `REFACTOR-PROGRESS.md` 任意时刻都能看到当前状态（AI 每分钟至少刷新一次心跳）。不要干扰 AI 对话本身。

### Q: 第一次跑完发现 REPORT 有很多 Level 3 决策怎么办？

这很正常。SPEC 是设计蓝图，实际代码总有 AI 拿不准的地方。你审查 §3.2：

- 决策合理 → 接受
- 决策错误 → 找到对应 commit，手工修改或 `git revert <commit>`，然后继续 M1 工作

### Q: 所有 Phase 都跑完了但 `completed_with_issues` 是什么意思？

两种情况：

1. 有任务 blocked（3 次尝试失败）→ 看 REPORT §5
2. 自检循环 10 轮后仍有问题 → 看 REPORT §4 最后一轮的未解决问题

两种情况都不阻塞后续工作，但你需要自己修复遗留问题后才算真正完成 Phase 0。

### Q: 那 Phase 0 没真正完成能开始 M1 吗？

不建议。如果 blocked 的是关键基础设施（ServiceRegistry / DataRepository），M1 会撞墙。建议先解决 blocked 再进 M1。

## 9. 开工清单

出门前按顺序做一遍：

- [ ] 工作区干净：`git status` 无未提交改动（或接受 AI 自动 stash）
- [ ] 在正确分支：`git branch --show-current` 显示稳定的开发分支
- [ ] 依赖已装：`pnpm install`
- [ ] 打开 AI 编辑器，新对话
- [ ] 复制 `REFACTOR-START-PROMPT.md` 里的 code block 整段
- [ ] 粘贴、回车
- [ ] 看到 AI 开始读 SPEC → 说明启动成功
- [ ] 关掉电脑（或别的屏保/不干扰即可）

## 10. 验收清单（回来后）

- [ ] PROGRESS status = `completed` 或 `completed_with_issues`
- [ ] REPORT §1 执行摘要已填
- [ ] REPORT §3.2 Level 3 决策逐条审查
- [ ] REPORT §5 blocked 任务逐条审查
- [ ] REPORT §8 遗留问题逐条记入 backlog
- [ ] 本地跑一次 `pnpm desktop:typecheck` + `pnpm desktop:test` 验证
- [ ] 启动应用 `pnpm desktop:dev` 验证主窗口能开、基本功能正常
- [ ] 决定：接受所有改动（保留分支）/ 部分回滚（`git revert` 某些 commit）/ 全部回滚（`git reset --hard` 起始 hash）
- [ ] 如接受，在本地 commit 自己的 REPORT 审查笔记，然后 `git push` 到远程

## 11. 进入 M1 之前的准备

Phase 0 完成后（无论 completed 还是 completed_with_issues），在开始 M1 之前：

1. 把 REPORT §6 的 SPEC 偏离建议整理成 SPEC 的 Revision 3 更新
2. 把 REPORT §8 遗留问题加入 M1 的 backlog 或先手工解决
3. 如果 Phase 0.5 的 ProjectContainer 或 Phase 0.6 的 TaskQueue 有 blocked，**优先手工解决**——这两个是 M1 的核心前置
4. 在 AGENTS.md 固化本轮建立的硬约束（AI 应该已经在 T6.15 做了，你复核）
5. 开始设计 M1 的 Agent runtime 融合计划
