# Synapse 全量融合 CC Connect 开发方案

## 0. 目标与边界

本方案用于指导把 CC Connect 的全部用户可见能力融合进当前 Synapse。融合后的产品目标是：

```text
Synapse = Agent 控制台 + 远程连接中枢 + 自动化调度器 + 规则/技能资产库
```

本方案的覆盖口径：

- 对 `产品设计.md` 第 2 章硬性覆盖范围和第 9 章全功能映射表逐项给出落点。
- 对 `功能覆盖.md` 的侵入性边界逐项遵守：追加式扩展，不替换现有规则、Skill、Prompt、数据库、IDE、设置、仓库、身份体系。
- 对 `架构方案.md` 的核心抽象逐项吸收：平台接口、Agent 接口、统一消息模型、Engine 编排、Provider、多项目多工作区、Bridge、Management API、命令、Skill、权限、Cron、Heartbeat、Relay、Hooks、文件引用、语音、Terminal Observer。
- 对 `约束与风险.md` 的迁移原则逐项落实：先模型后功能、特权逻辑在主进程、UI 只迁移信息架构、每阶段有可验收闭环。

本方案不做代码实现，不启动 dev server，不迁移 CC Connect Web UI，不把 CC Connect Go 代码作为子进程整体嵌入。

## 1. 总体实施原则

1. 垂直叠加，不横向替换。
   当前 6 个顶层模块全部保留，只新增“会话 / 项目 / 连接 / 自动化”四个顶层入口，并在既有模块上追加 Agent 运行时能力。

2. 吸收架构，重建服务。
   CC Connect 的 Go Engine 不能逐行翻译成 TypeScript 巨型服务。Synapse 侧按当前 Phase 0 runtime 拆成多个主进程服务，通过 `ServiceRegistry`、`ProjectContainer`、`IpcModule`、`EventBus`、`DataRepository`、`PermissionGuard`、`NetworkServiceRegistry` 组合。

3. 主进程承载特权能力。
   Agent 子进程、Provider 密钥、文件读写、平台 SDK、Bridge/Webhook/Management API、Cron/Heartbeat、run-as-user、STT/TTS 转码全部在 `desktop/electron/`。Renderer 只通过 `window.synapse.*` 的 typed preload API 交互。

4. 统一模型先于功能。
   先定义 `SessionKey`、`AgentSessionId`、`ConversationId`、`WorkspaceId`、`ProviderProfile`、`ConnectorCapability`、`AgentEvent`，再做 Codex、Claude、平台、Cron、Relay 等功能。

5. 每阶段必须闭环。
   每个阶段都要能从 UI 或 IPC 发起操作、进入主进程服务、持久化状态、返回事件、可测试验证。禁止只铺接口不打通端到端。

6. UI 使用 Synapse 当前基线。
   继续使用 `desktop/components.json` 的 `radix-nova`、neutral、CSS variables、Radix/shadcn。禁止照搬 CC Connect Web UI、自定义色、渐变、营销文案、卡片套卡片。

## 3. 核心数据模型

### 3.1 ID 与关系

必须先固定三层会话 ID，避免后续平台和历史混乱：

```text
SessionKey        外部入口上下文，例如 local:user、feishu:chat:user、cron:job
ConversationId    Synapse 侧命名会话，归属 SessionKey，可新建/切换/删除
AgentSessionId    Agent 后端真实会话 ID，例如 Codex thread id、Claude session id
```

关系：

```text
Project
  -> Workspace
  -> ProviderRef
  -> ConnectorBinding
  -> ScheduleJob / HeartbeatConfig
  -> Conversation
       -> AgentSessionId
       -> Message[]
       -> AgentEvent[]
       -> AuditEvent[]
```

### 3.2 DataRepository namespaces

新增 namespace 使用版本化 schema，密钥 namespace 标记 encrypted 或通过 secret ref 存储：

| Namespace | 数据 | 说明 |
| --- | --- | --- |
| `agent.projects` | Project、Workspace、WorkspaceBinding | 项目、工作区、频道绑定 |
| `agent.providers` | ProviderProfile、ProviderSecretRef | 全局 Provider，密钥不进 renderer |
| `agent.providerRefs` | ProjectProviderRef | 项目引用和 active provider |
| `agent.sessions` | Conversation、AgentSessionMeta | 会话元数据 |
| `agent.messages` | Message、AttachmentRef | 会话消息，可按会话分片存储 |
| `agent.commands` | CommandDefinition、Alias | builtin/custom/skill/agent-file |
| `agent.skills` | SkillDefinition、SkillPresetRef | 运行时发现结果和缓存 |
| `agent.connectors` | Connector、ConnectorBinding、CapabilitySnapshot | 平台、Bridge、Webhook、本地 API |
| `agent.scheduler` | ScheduleJob、HeartbeatConfig、RunRecord | Cron、Heartbeat |
| `agent.relay` | RelayBinding、RelayMessage | 多 Agent 协作 |
| `agent.hooks` | HookRule、HookRunRecord | 生命周期集成 |
| `agent.outbox` | OutboxMessage | 主动发送记录 |
| `agent.audit` | AuditEvent | 高危操作审计 |
| `agent.attachments` | AttachmentManifest | 附件元数据，二进制落 userData |

### 3.3 类型最小集合

第一批必须定义：

```text
AgentRuntimeType = codex | claude-code | cursor | gemini | kimi | opencode | iflow | qoder | pi | devin | acp
PlatformType = feishu | lark | telegram | slack | discord | dingtalk | wecom | weixin | qq | qqbot | line | weibo | bridge | webhook | local-api
AgentEventType = text | thinking | tool_use | tool_result | permission_request | ask_user_question | result | error | usage | file | patch
PermissionMode = default | plan | auto | bypassPermissions | acceptEdits | dontAsk
ConnectorCapability = text | image | file | audio | card | buttons | typing | preview | update_message | delete_message | reconstruct_reply
CommandSource = builtin | custom-prompt | custom-exec | skill | agent-file
ScheduleSessionMode = reuse | new_per_run
```

## 4. 主进程服务设计

### 4.1 `agent-projects`

职责：

- Project CRUD。
- Workspace CRUD。
- channel/workspace binding、shared binding、idle reaping 元数据。
- 项目级 Agent、Provider、安全、连接、自动化引用。
- 与当前 Synapse 仓库体系保持正交，不替换 repository。

实现要求：

- 注册到 `ServiceRegistry`，项目运行态放 `ProjectContainer`。
- workspace path 规范化，处理软链和尾斜杠。
- 所有持久化走 `DataRepository`。

### 4.2 `providers`

职责：

- 全局 provider CRUD。
- provider presets。
- cc-switch 导入。
- project provider refs。
- active provider、model、reasoning、agent-specific overrides。
- Codex 专属 `wire_api`、`http_headers`、`env_key`。
- ProviderProxy 或请求适配层，用于 provider 兼容。

实现要求：

- API key 只在主进程保存，renderer 只能拿到 masked 状态。
- 删除 provider 时检查项目引用并给出处理结果。
- `ResolvedProviderForAgent` 由主进程生成，React 不拼 CLI env 或 header。

### 4.3 `agent-runtime`

职责：

- 统一 `AgentRuntime`、`AgentSession`、`AgentEvent`。
- 支持 Codex、Claude Code、Cursor、Gemini、Kimi、OpenCode、IFlow、Qoder、Pi、Devin、ACP。
- 管理 spawn、resume、stop、cancel、stdout/stderr、事件归一化。
- 处理 provider 注入、model/reasoning/mode、usage/context。
- 接收 permission response。

阶段顺序：

1. Codex exec/resume。
2. Claude Code stream-json 和 permission loop。
3. Cursor。
4. ACP。
5. 其他 CLI Agent。

实现要求：

- Agent 子进程启动前走 `PermissionGuard.check({ action: "agent.spawn" })`。
- shell/文件/网络能力必须记录审计。
- 各 Agent 适配器独立文件，不写大 switch。
- fake Agent runtime 作为测试适配器先行。

### 4.4 `agent-sessions` / `session-orchestrator`

职责：

- SessionKey 到 Conversation 的映射。
- named sessions：`/new`、`/list`、`/switch`、`/name`、`/current`、`/history`、`/delete`、`/stop`。
- busy lock、队列上限、`/btw` 补充。
- 权限 pending state、AskUserQuestion。
- 事件消费循环，把 AgentEvent 写入消息历史、同步 EventBus、推送 renderer。

实现要求：

- queue 上限默认 5，可项目级配置。
- stop/cancel 必须能终止当前 turn。
- 会话历史分片保存，提供清理策略。
- 任何权限请求不得被吞掉。

### 4.5 `commands` 与 `skill-runtime`

职责：

- 内置命令注册。
- 自定义 prompt command。
- 自定义 shell command。
- aliases。
- Agent command dirs。
- `SKILL.md` 扫描、frontmatter、缓存、invalidate。
- Skill invocation prompt 构造。

必须覆盖内置命令：

```text
/new /list /switch /name /current /history /delete /stop
/status /usage /whoami /doctor /version
/model /reasoning /mode /allow /provider
/lang /quiet /config /memory
/cron /heartbeat /compress
/commands /skills /alias
/dir /show /search /shell /diff
/web /upgrade /restart
/bind /workspace
/tts
```

实现要求：

- shell command 默认关闭，远程用户默认不可用。
- prompt template 支持 `{{1}}`、`{{1:default}}`、`{{2*}}`、`{{args}}`、`{{args:default}}`。
- 命令执行统一进入 session orchestrator，不绕过权限和审计。

### 4.6 `connectors`

职责：

- 平台连接 CRUD、状态、凭据、能力矩阵。
- Feishu/Lark、Telegram、Slack、Discord、DingTalk、WeCom、Weixin、QQ、QQBot、Line、Weibo。
- Bridge WebSocket 外部适配器。
- Webhook。
- 本地 API / CLI send。
- reply context reconstruct、preview、buttons、card、attachments、typing、rate limit。

实现顺序：

1. Bridge 最小 text 协议。
2. Webhook 和本地 API。
3. Telegram 或 Slack 原生试点。
4. Feishu/Lark 和 Discord 富交互。
5. Weixin/WeCom。
6. QQ、QQBot、DingTalk、Line、Weibo。

实现要求：

- 所有监听端口通过 `NetworkServiceRegistry.register`，默认 `127.0.0.1`。
- 外部连接器必须 token + scope。
- Connector 必须声明 capabilities，renderer 和远程平台都按 capability 降级。
- 不能假设所有平台都能主动发送，必须通过 `reconstruct_reply` 能力声明。

### 4.7 `scheduler`

职责：

- Cron。
- Heartbeat。
- Run records。
- missed run 策略。
- `silent`、`mute`、`new_per_run`、`timeout_mins`、权限模式覆盖。

实现要求：

- 第一阶段只保证 app 运行期间执行。
- 任务触发必须复用 session orchestrator。
- Cron prompt 和 exec 互斥。
- Heartbeat 与 Cron 保持两个概念，Heartbeat 支持 `HEARTBEAT.md`。

### 4.8 `hooks`、`outbox`、`audit`

职责：

- Hook event：`message.received`、`message.sent`、`session.started`、`session.ended`、`cron.triggered`、`permission.requested`、`error`。
- Handler：HTTP、Command。
- Outbox 记录所有主动发送。
- Audit 记录 shell、文件写入、provider 修改、cron 创建、webhook 调用、Bridge adapter 注册、run_as_user、权限 allow/deny、远程接管。

实现要求：

- 先支持 HTTP hook，command hook 延后且默认关闭。
- Audit 不记录完整密钥和大文件内容。
- Outbox 支持失败重试和错误摘要。

### 4.9 `references` 与 `media`

职责：

- 文件路径识别：绝对路径、相对路径、`file://`、Markdown link、`:line`、`:line:col`、`:line-line`、`#Lline`、`#LlineCcol`。
- `/show`、`/search`、`/diff`。
- 附件落盘和 manifest。
- STT/TTS 和 ffmpeg 转码。

实现要求：

- 文件预览和搜索在主进程执行，renderer 不直接读任意文件。
- 远程发送本地路径前应支持隐私显示策略。
- STT/TTS 放 M5，不阻塞核心闭环。

### 4.10 `management-api`

职责：

- 本地管理 API，默认关闭。
- token 保护。
- 资源：status、projects、sessions、providers、skills、cron、bridge adapters、setup、reload、restart。

实现要求：

- 通过 `NetworkServiceRegistry` 监听。
- 与 renderer 使用同一服务层，不另写平行逻辑。
- 默认只绑定 `127.0.0.1`。

## 6. IPC 与事件设计

新增 preload 命名空间：

```text
window.synapse.agentProjects.*
window.synapse.agentRuntime.*
window.synapse.agentSessions.*
window.synapse.providers.*
window.synapse.connectors.*
window.synapse.scheduler.*
window.synapse.commands.*
window.synapse.audit.*
```

所有新增 IPC：

- 在 `desktop/electron/modules/<module>/ipc.ts` 定义 `IpcModule`。
- 使用 zod schema 校验 request/response。
- 注册到 `desktop/electron/bootstrap/ipc-registry.ts`。
- 运行 `pnpm desktop:generate:ipc` 更新 generated channels。
- 扩展 `desktop/electron/preload.ts` 和 `desktop/src/types/bridge.ts`。

事件通道：

```text
agent-session:event
agent-session:status
agent-session:permission-requested
agent-session:message-appended
connector:state-changed
connector:adapter-changed
scheduler:job-updated
outbox:message-updated
audit:event-recorded
```

事件发送必须走 `EventBus` / `WindowBroadcaster`，不能直接 `webContents.send`。

## 9. 验收标准

全量融合完成时必须满足：

1. 用户能在 Synapse 中直接创建 Codex、Claude Code、Cursor 等本地 Agent 会话。
2. 用户能导入 cc-switch Provider，并绑定到项目。
3. Rule、Skill、Prompt 能作为 Agent 运行时资产使用。
4. 会话中心能统一展示本地、远程、定时、Relay、Webhook 会话。
5. 远程平台消息能创建或恢复 session。
6. Synapse 能观察和接管远程会话。
7. 权限请求不会丢失，能在本地 UI 和支持的平台端处理。
8. Cron、Heartbeat、Webhook、本地 API 都复用同一套会话和权限模型。
9. Bridge adapter 能用 capabilities 接入，并按能力降级。
10. 11 个平台和 11 个 Agent 都有明确入口、状态、错误和降级策略。
11. 附件、语音、文件引用、diff、流式预览、卡片按钮都有统一模型。
12. 所有高危操作都有权限、审计、错误摘要。
13. Provider 密钥不进入 renderer 长期状态，日志和导出默认脱敏。
14. `pnpm desktop:typecheck`、`pnpm desktop:check:hard-constraints`、相关单元/集成测试通过。
15. UI 不出现 CC Connect Web 风格、自定义色、渐变、卡片套卡片、界面废话。

## 10. 每阶段固定检查清单

每个阶段开工前：

- 是否只改该阶段必要文件。
- 是否已有类型和数据版本。
- 是否明确主进程/renderer/preload 边界。
- 是否复用 `ServiceRegistry`、`IpcModule`、`DataRepository`、`EventBus`、`PermissionGuard`。
- 是否没有新增平行架构。
- 是否没有直接 `ipcMain.handle/on`、`webContents.send`、裸 `http/net/https.createServer`、业务 `fs.writeFile`。
- 是否避免新增依赖，若必须新增，是否有阶段理由和替代评估。
- UI 是否已遵守 `.claude/rules/design.md` 和 `.claude/rules/ui-rules.md`。

每个阶段完成前：

- 跑 `pnpm desktop:typecheck`。
- 涉及 runtime 硬约束时跑 `pnpm desktop:check:hard-constraints`。
- 涉及 IPC 时跑 `pnpm desktop:generate:ipc` 和 `pnpm desktop:check:ipc-codegen`。
- 涉及服务行为时补单元测试。
- 涉及端到端编排时用 fake Agent/fake connector 做集成测试。
- 不启动 dev server，不打开浏览器，除非用户明确要求。

## 11. 关键风险与控制

| 风险 | 控制 |
| --- | --- |
| TypeScript 巨型 Engine | 按服务拆分，Agent、Session、Provider、Connector、Scheduler 分离 |
| 会话 ID 混淆 | 阶段 0 固定 SessionKey、ConversationId、AgentSessionId |
| 权限请求丢失 | AgentEvent 必须包含 permission_request，UI 和平台都订阅 pending state |
| 子进程泄漏 | AgentRuntime 统一持有 AbortController、进程句柄、stop/cancel |
| Provider 密钥泄露 | 密钥只在主进程，renderer 只显示 masked 状态 |
| 平台依赖膨胀 | 先 Bridge，再一个原生平台，SDK 分阶段引入 |
| 定时任务误解 | 第一版明确只保证 app 运行期间，后续再做系统级后台策略 |
| 远程 shell 失控 | shell command 默认关闭，role/admin/PermissionGuard/audit 四层控制 |
| UI 失控 | 使用 shadcn 组件和 token，不迁移 CC Connect Web UI |
| 旧数据污染 | 新 namespace 与现有 config/data-store 正交，迁移脚本可重复 |

## 12. 最终交付形态

完成后 Synapse 的产品结构是：

```text
内容资产层
  Rule / Skill / Prompt / Command

Agent 运行层
  本地会话 / 远程会话 / Agent Runtime / Provider / 权限

连接与自动化层
  平台连接 / Bridge / Webhook / 本地 API / Cron / Heartbeat / Relay / Hooks / Outbox

治理层
  项目 / 工作区 / 安全 / 审计 / Doctor / 日志 / 更新 / Management API
```

工程结构是：

```text
React modules 只负责展示和交互
Typed preload 只暴露窄能力
IpcModule 负责校验和分发
Electron services 负责业务能力
Runtime infrastructure 负责服务、网络、权限、事件、数据、调度
```

这条路线能完整覆盖 CC Connect 的功能，同时保持 Synapse 当前 Electron、React、Tailwind、shadcn、Phase 0 runtime 架构不被破坏。
