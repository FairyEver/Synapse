# Synapse 全量融合 CC Connect 开发方案

## 0. 目标与边界

本方案用于指导把 CC Connect 的全部用户可见能力融合进当前 Synapse。融合后的产品目标是：

```text
Synapse = Agent 控制台 + 远程连接中枢 + 自动化调度器 + 规则/技能资产库
```

本方案只改 Synapse，不把 CC Connect Go 进程作为黑盒子嵌入，不迁移 CC Connect Web UI，不启动 dev server，不打开浏览器预览。每个实施任务都必须先阅读对应的 CC Connect 源码，再在 Synapse 中按 Electron + React + TypeScript + shadcn/ui 的架构重建能力。

源码根目录固定为：

```text
/Users/liyang/Desktop/code-guide/cc-connect-main
```

硬性要求：

- 后续任何 AI 执行本方案时，开发前必须阅读本步骤列出的 `CC Connect 先读源码`。
- 不能只根据 `产品设计.md` 自行发挥实现。
- 新代码必须能说明它对照 CC Connect 的哪个目录、哪个函数、哪个测试或哪个协议文档。
- 步骤必须扁平执行。本文实施步骤只使用 `步骤 01`、`步骤 02` 这种同级编号，不使用 1.1、1.2、子任务树。
- 当前 Synapse 的规则、Skill、Prompt、数据库、IDE、设置、仓库、身份体系全部保留。融合是追加式扩展，不替换现有功能。

## 3. 核心模型

必须先固定三层会话 ID：

```text
SessionKey      外部入口上下文，例如 local:user、feishu:chat:user、cron:job
ConversationId  Synapse 侧命名会话，归属 SessionKey，可新建/切换/删除
AgentSessionId  Agent 后端真实会话 ID，例如 Codex thread id、Claude session id
```

AgentRuntimeType = codex | claude-code | cursor | gemini | kimi | opencode | iflow | qoder | pi | devin | acp

### 3.2 CC Connect 配置 parity

产品设计写的是用户视角；源码里的用户可见配置也必须迁移。实现类型和 UI 时至少覆盖 `config/config.go` 的这些字段，不能因为产品文档只写了大类就省略：

| CC Connect 配置 | Synapse 覆盖要求 |
| --- | --- |
| `data_dir`、`attachment_send`、`idle_timeout_mins` | 数据目录、附件发送策略、Agent 事件空闲超时必须有设置或项目级只读状态 |
| `quiet`、`display.thinking_messages`、`display.thinking_max_len`、`display.tool_messages`、`display.tool_max_len` | 会话显示设置和项目默认显示设置必须能表达开关与截断长度 |
| `stream_preview.enabled`、`disabled_platforms`、`interval_ms`、`min_delta_chars`、`max_chars` | 流式预览不能只有开关，必须支持平台禁用、节流和长度上限 |
| `provider_presets_url` | Provider 预设来源可配置，默认来源和自定义 URL 要可诊断 |
| `webhook.port/path/token`、`bridge.port/path/token/cors_origins`、`management.port/token/cors_origins` | 网络监听必须通过 `NetworkServiceRegistry`，端口、路径、token、CORS 都要有配置、权限和审计 |
| `reset_on_idle_mins`、`inject_sender`、`filter_external_sessions` | 项目 Agent 设置必须覆盖空闲重置、发送者注入、外部 session 过滤 |
| `references.normalize_agents/render_platforms/display_path/marker_style/enclosure_style` | 文件引用归一化和远程渲染策略必须可配置，不能只做本地点击 |
| `speech.language`、各 STT/TTS provider 的 api key/base URL/model/voice/max_text_len | 语音设置必须覆盖 provider 子字段、语言、voice、长度跳过策略和密钥脱敏 |
| `rate_limit`、`outgoing_rate_limit.platforms`、`users.default_role/roles` | 入站/出站限流必须支持全局和平台覆盖；角色默认值和 role 级 disabled commands/rate limit 必须可测 |

## 11. 每一步开工前检查

每个步骤开工前必须确认：

- 已阅读该步骤的 `CC Connect 先读源码`，并在实现说明或提交说明里写明对照文件。
- 已对照本方案 §3.1 和 §3.2，确认没有把产品设计字段或 CC Connect 用户可见配置降级成“后续再说”。
- 已查当前 Synapse 现有 `lib/`、`hooks/`、`services/`、`router/`、`utils/`、`modules/`，先复用再扩展。
- 需要 UI 时已阅读 `.claude/rules/design.md` 和 `.claude/rules/ui-rules.md`。
- 不新增 `desktop/src/features/`。
- 不引入 `@base-ui/react`。
- 不在 React 组件里直接操作 CLI、密钥、文件系统、平台 SDK、网络监听。
- 不写自定义颜色、内联 style、卡片套卡片、欢迎横幅、界面废话；新增文案必须通过步骤 85 的文案检查。
- 不绕过 `ServiceRegistry`、`IpcModule`、`DataRepository`、`EventBus`、`PermissionGuard`、`NetworkServiceRegistry`。

## 12. 每一步完成前检查

每个步骤完成前必须确认：

- 新功能有 CC Connect 源码对照，不存在“只按产品设计实现”的代码。
- 涉及 IPC 时已更新 generated channels，并检查 preload 类型。
- 涉及持久化时有 schema 版本、迁移或兼容策略。
- 涉及高危能力时有权限检查和审计。
- 涉及远程平台时有 capability 和 fallback。
- 涉及连接、自动化、Provider、显示、语音、引用、管理 API 时已复核步骤 89-91 的字段完整性。
- 涉及 UI 时只用 shadcn/ui、Tailwind token 和现有布局组件。
- 涉及产品流程时确认步骤 86-88 的阶段验收、用户主路径、关键流程和页面布局没有被破坏。
- 涉及全量验收时确认步骤 92 的 10 条成功标准都有测试或人工验收记录。
- 涉及 runtime 硬约束时运行 `pnpm desktop:check:hard-constraints`。
- 常规检查运行 `pnpm desktop:typecheck`。
- 新增服务行为有单元测试；端到端编排用 fake Agent 或 fake connector 做集成测试。

## 13. 风险控制

| 风险 | 控制 |
| --- | --- |
| TypeScript 巨型 Engine | 按 Agent、Session、Provider、Connector、Scheduler、Command、Media 拆服务 |
| 会话 ID 混淆 | 严格区分 SessionKey、ConversationId、AgentSessionId |
| 脱离 CC Connect 源码 | 每个步骤强制列出并阅读源码对照 |
| 权限请求丢失 | permission_request 和 AskUserQuestion 必须持久化、推 UI、可回写 |
| 子进程泄漏 | AgentRuntime 统一持有 AbortController、进程句柄、stop/cancel |
| Provider 密钥泄露 | 密钥只在主进程，renderer 只拿 masked 状态 |
| 平台依赖膨胀 | 先 Bridge，再 Telegram/Slack/Feishu，其他平台分批 |
| 远程 shell 失控 | shell 默认关闭，role/admin/PermissionGuard/audit 四层控制 |
| 定时任务误解 | 第一版明确只保证 app 运行期间，后续再做系统级后台策略 |
| UI 失控 | 只迁移信息架构，不迁移 CC Connect Web 样式 |
| 旧数据污染 | 新 namespace 与现有 config/data-store 正交 |
| 功能项存在但路径走不通 | 用步骤 86-88 的阶段验收、四类用户主路径、关键流程和页面布局做阻断检查 |
| 数据对象口径漂移 | 用步骤 83 固化 ER 对象、schema、关系测试 |
| 权限口径不一致 | 用步骤 84 把产品权限表落到 PermissionGuard、角色配置和测试 |

## 14. 最终验收标准

全量融合完成时必须满足：

- 用户能在 Synapse 中直接创建 Codex、Claude Code、Cursor、Gemini、Kimi、OpenCode、IFlow、Qoder、Pi、Devin、ACP 会话。
- 用户能导入 cc-switch Provider，并绑定到项目。
- Rule、Skill、Prompt 能作为 Agent 运行时资产使用。
- 会话中心统一展示本地、远程、定时、Relay、Webhook 会话。
- Feishu/Lark、Telegram、Slack、Discord、DingTalk、WeCom、Weixin、QQ、QQBot、Line、Weibo 都有连接入口、状态、错误和降级策略。
- 远程平台消息能创建或恢复 session，Synapse 能观察和接管远程会话。
- 权限请求不会丢失，能在本地 UI 和支持的平台端处理。
- Cron、Heartbeat、Webhook、本地 API 都复用同一套会话和权限模型。
- Bridge adapter 能用 capabilities 接入，并按能力降级。
- 附件、语音、文件引用、diff、流式预览、卡片按钮都有统一模型。
- 连接状态、masked credential、能力矩阵、Bridge/Webhook/本地 API 字段、Cron/Heartbeat/Relay/Hooks/Outbox 字段均满足 §3.1，不存在只有服务没有页面字段的遗漏。
- CC Connect `config/config.go` 中用户可见配置满足 §3.2，有 schema、UI、诊断或明确的桌面化替代。
- 所有高危操作都有权限、审计、错误摘要。
- Provider 密钥不进入 renderer 长期状态，日志和导出默认脱敏。
- `pnpm desktop:typecheck`、`pnpm desktop:check:hard-constraints`、相关单元/集成测试通过。
- UI 不出现 CC Connect Web 风格、自定义色、渐变、卡片套卡片、界面废话。
- 产品设计第 6 章产品字段、第 7、8 章关键流程和页面布局、第 10 章数据对象、第 11 章权限模型、第 13 章阶段验收、第 14 章四类用户主路径、第 15 章成功标准均有测试或验收记录。
