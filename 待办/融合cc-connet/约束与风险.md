# 融合 CC Connect 可行性分析和注意点

关联文档：`待办/融合cc-connet/ccc的方案和架构.md`

源码路径：`/Users/liyang/Desktop/code-guide/cc-connect-main`

本文目标：判断“把 CC Connect 的能力迁移到 Synapse”是否可行，并提前列出架构、工程、安全、产品、UI、测试和迁移节奏上的注意点。它不是具体实现方案，具体模块设计应在每个阶段开始前另写小范围技术方案。

## 总体结论

可行，但不适合“整体搬运”。

更准确的判断是：CC Connect 的核心抽象和编排思路非常值得迁移，Go 代码本身不应直接移植到 Synapse。Synapse 是 Electron + React + TypeScript + shadcn/ui，CC Connect 是 Go 后端 + 嵌入式 Web 管理端 + CLI/平台桥接器。两者运行模型不同，所以正确路线应是“吸收架构，重建服务”，而不是把 CC Connect 当成一个子进程或把 Go 代码逐行翻译成 TypeScript。

最值得迁移的是：

- Agent 会话抽象：`Agent`、`AgentSession`、事件流、权限请求。
- 消息编排：session key、busy lock、消息队列、事件消费、流式预览。
- Provider 体系：全局 provider、项目引用、agent-specific overrides。
- 多项目/多工作区：project、workspace、channel/session binding。
- Command/Skill：命令注册、prompt 模板、skill 发现和调用。
- 主动任务：cron、heartbeat、webhook、relay。
- Bridge/Management API：外部连接器协议和管理资源模型。

不建议直接迁移的是：

- CC Connect 的 Web UI 样式和组件。
- `core/engine.go` 那种超大单文件组织方式。
- Go daemon/systemd/launchd 机制。
- 所有聊天平台一次性迁移。
- 把 provider、Agent、平台差异写进 React 组件。

## 可行性分层

| 范围 | 可行性 | 建议 |
|---|---:|---|
| Agent 抽象与事件模型 | 高 | 优先迁移，放 Electron 主进程服务层 |
| Codex/Claude 适配 | 高 | 与 Synapse 现有 IDE/Agent 定义关系最近 |
| Provider 管理 | 高 | 可与现有设置/数据存储融合 |
| 会话编排 | 高 | 需要先设计 Synapse 内部 session 模型 |
| Command/Skill | 高 | Synapse 已有 rules/skills 基础，适合融合 |
| Cron/Heartbeat | 中高 | 需要结合 Electron 后台生命周期和系统休眠处理 |
| Bridge 协议 | 中高 | 适合作为外部连接器长期方向 |
| 聊天平台接入 | 中 | 平台差异大，应分批做 |
| 语音/TTS | 中 | 依赖 ffmpeg 和第三方 API，先延后 |
| run-as-user 隔离 | 中 | macOS/Electron 打包、权限和 sudo 配置复杂 |
| Web 管理端照搬 | 低 | 不符合 Synapse UI 栈和设计纪律 |
| Go 代码原样复用 | 低 | 架构可参考，代码不宜直接嵌入 |

## 和 Synapse 当前架构的匹配度

Synapse 当前结构大致是：

- 主进程：`desktop/electron/`
- 主进程服务：`desktop/electron/services/`
- IPC 通道：`desktop/electron/ipc/`
- preload：`desktop/electron/preload.ts`
- 渲染层：`desktop/src/`
- 业务模块：`desktop/src/modules/`
- UI 基线：`desktop/src/components/ui/` + shadcn/ui + Tailwind token
- IDE 定义：`desktop/src/ide-definitions/`、`desktop/electron/services/ide-definitions/`
- 当前已有模块：content、rules、skills、settings、prompts、editor-scan、cli、data-store

匹配点：

- Synapse 已经有 IDE/Agent 定义和内容安装体系，适合接入 CC Connect 的 Agent/provider/session 思路。
- Electron 主进程适合承载 Agent 子进程、文件系统、配置、网络和平台连接。
- 渲染层适合做管理 UI，但必须通过 typed preload API 调主进程服务。
- `desktop/src/modules/skills`、`desktop/src/modules/rules` 可以吸收 CC Connect 的 Skill/Command 概念。

冲突点：

- CC Connect 的核心运行时是 Go 长驻服务；Synapse 是桌面 app，生命周期、休眠、窗口关闭、自动更新都不同。
- CC Connect 的平台 bot 面向远程聊天入口；Synapse 目前更像本地内容/IDE 管理工具，需要先明确产品入口。
- CC Connect 的 Web UI 自定义样式不能直接搬进 Synapse。
- CC Connect 的配置中心是 TOML 文件；Synapse 当前有自己的 data-store 和 IPC 模型，需要统一来源。

## 推荐迁移原则

### 1. 先迁移模型，再迁移功能

先建立 Synapse 内部的统一模型：

- `AgentRuntime`
- `AgentSession`
- `AgentEvent`
- `SessionKey`
- `WorkspaceBinding`
- `ProviderProfile`
- `CommandDefinition`
- `SkillDefinition`

不要一开始就迁移 Feishu、Telegram、cron、relay 等功能。没有统一模型时，功能越多越容易散。

### 2. 所有特权逻辑放主进程

以下逻辑必须在 Electron 主进程或主进程服务中：

- Agent 子进程启动、停止、resume。
- 读写文件系统。
- 读写 provider 密钥。
- 网络请求、webhook、Bridge server。
- 定时任务、后台任务。
- 权限决策结果回写 Agent。
- run-as-user 或进程隔离。

渲染层只做 UI 和用户交互，不直接操作 CLI、密钥、文件系统或平台 SDK。

### 3. UI 只迁移信息架构，不迁移视觉实现

CC Connect Web 管理端可以参考页面功能：

- 项目列表
- Provider 列表
- 会话列表
- Cron 列表
- Skill 列表
- 系统设置

但 Synapse 实现时必须使用现有 shadcn/ui 组件和主题 token，不写自定义色、不写内联样式、不做卡片套卡片、不写内部工具废话文案。

### 4. 每阶段都要有可独立验收的最小闭环

每个阶段都应能跑通一个闭环，例如：

- Agent runtime 阶段：启动 Codex session、发送消息、收到事件、停止 session。
- Provider 阶段：新增 provider、绑定项目、切换模型、持久化。
- Session 阶段：新建、切换、恢复、删除会话。
- Cron 阶段：创建任务、触发、记录 last_run/last_error。

不要做“铺一堆接口但没有任何端到端能力”的迁移。

以下是建议的 Synapse 目录落点，后续可根据实际代码再调整。

## 模块可行性分析

### Agent Runtime

可行性：高。

原因：

- Synapse 已经有 Codex、Claude Code、Cursor 等 IDE/Agent 定义基础。
- Electron 主进程天然适合管理子进程。
- CC Connect 的 `AgentSession` 抽象很清晰。

注意点：

- 不要把不同 Agent 的参数、输出解析、provider 注入写成一个大 switch。
- Agent 事件必须归一化为稳定类型，避免 UI 直接依赖 Codex/Claude 原始 JSON。
- 子进程 stdout/stderr 读取要处理背压、超时、退出码和取消。
- session resume 语义必须明确：Synapse session 和 Agent backend session 是两层 ID。
- 权限请求不能被吞掉，必须能到达 UI 或平台连接器。

建议最小闭环：

```text
创建 Codex runtime
  -> start session
  -> send text
  -> stream events
  -> final result
  -> stop session
```

### Provider 管理

可行性：高。

原因：

- CC Connect 的 provider 模型成熟。
- Synapse 本身需要跨 IDE/Agent 管理模型和密钥。

注意点：

- 密钥不要进入渲染层长期状态。
- 不要在 React 组件里拼环境变量或 CLI 参数。
- provider 需要支持 agent-specific 配置，例如 Codex 的 `wire_api`、headers、env key。
- 全局 provider 和项目引用要分开，否则项目配置会膨胀。
- provider 删除要处理引用清理和 active provider 失效。

建议模型：

```text
GlobalProvider
ProjectProviderRef
ResolvedProviderForAgent
```

### 会话编排

可行性：高，但需要先定模型。

注意点：

- `sessionKey` 表示外部入口上下文，不等于 Agent session id。
- 一个 session key 下可能有多个 named sessions。
- 需要 busy lock 和排队，否则用户连续发送消息会打乱 Agent turn。
- 队列必须有上限。
- stop/cancel 要能停止当前 Agent 子进程或当前 turn。
- 历史记录保存要考虑体积、隐私和可清理策略。

建议先支持本地 UI session，再考虑聊天平台 session。

### Command/Skill

可行性：高。

原因：

- Synapse 已有 rules/skills 模块。
- CC Connect 的命令模板和 `SKILL.md` 发现机制可以直接参考。

注意点：

- 命令执行分为 prompt command 和 shell command，shell command 是高风险能力，必须有权限边界。
- Skill prompt 注入要保留来源和版本，便于排查。
- 命令列表应有 source：builtin、custom、skill、agent-file。
- 命令和 skill 不要直接写死到 UI 菜单里。

### Cron / Heartbeat

可行性：中高。

注意点：

- 桌面 app 可能退出、休眠、被系统挂起，不能假设长驻服务永远在线。
- macOS 打包后后台运行策略与普通 Go daemon 不同。
- 定时任务要记录 missed run 策略：错过后补跑还是跳过。
- `silent`、`mute`、`new_per_run`、`timeout_mins` 这些语义需要保留，否则任务行为会不可预测。
- 定时任务涉及 Agent 执行，要复用同一套 session/permission 逻辑。

建议先实现 app 运行期间的 scheduler，再考虑系统级后台唤醒。

### Bridge / 外部连接器

可行性：中高。

价值：

- 能让外部平台用任意语言接入 Synapse。
- 能避免 Synapse 主仓库快速膨胀出大量平台 SDK。

注意点：

- 需要明确 token、CORS、本地监听地址、端口冲突策略。
- 协议版本要写进 handshake。
- 能力声明要可扩展。
- reply context 是不透明数据，必须防止外部连接器伪造跨 session 操作。
- 外部连接器断开后，要清理平台状态和 pending preview。

建议先做最小协议：

```text
register
message
reply
error
ping/pong
```

再逐步增加：

```text
buttons
card
preview_start
update_message
audio
file
```

### 聊天平台接入

可行性：中。

原因：

- CC Connect 已经证明平台接入可行。
- 但每个平台鉴权、消息格式、主动发送、限流和审核规则差异很大。

注意点：

- 不要一口气接所有平台。
- 优先接一个平台验证抽象。
- 平台 SDK 和 token 处理必须在主进程。
- 消息长度、Markdown 格式、附件限制、API 限流都要平台单独处理。
- session key 规范必须先定。

建议优先级：

1. Bridge 外接平台
2. Telegram 或 Slack 这类 API 清晰的平台
3. Feishu/Discord 这种富交互平台
4. Weixin/WeCom 这种协议和风控更复杂的平台

### Web 管理 UI

可行性：中。

说明：

- 功能结构可迁移。
- 视觉和组件不可迁移。

注意点：

- Synapse 内部工具不要写营销式文案。
- 不要把架构说明写进界面。
- 页面应使用 shadcn/ui 原语。
- 表格、表单、状态、空态要克制。
- 不要用 CC Connect Web 的自定义 `Card/Button/Input` 体系。

### run-as-user / 进程隔离

可行性：中。

价值：

- Agent 有文件系统写权限，隔离非常重要。
- 多用户或高危目录操作时尤其有意义。

注意点：

- `sudo -n -iu` 依赖用户手动配置 sudoers。
- macOS app sandbox、notarization、GUI app 环境和 shell login 环境差异较大。
- Windows 不适用同样机制。
- 错误提示必须清楚，否则用户会以为 Agent 坏了。
- 不应作为第一阶段能力。

替代路线：

- 第一阶段先做工作目录白名单和权限确认。
- 第二阶段做进程环境隔离。
- 第三阶段再考虑 run-as-user。

## 关键风险矩阵

| 风险 | 影响 | 概率 | 应对 |
|---|---:|---:|---|
| 直接翻译 Go Engine 导致 TypeScript 巨型服务 | 高 | 高 | 按服务拆分，禁止超大单文件 |
| Agent session 与 UI session 混淆 | 高 | 高 | 明确 sessionKey、sessionId、agentSessionId 三层 |
| 子进程生命周期泄漏 | 高 | 中 | 统一 runtime manager，集中 stop/cancel |
| 权限请求丢失 | 高 | 中 | AgentEvent 必须包含 permission_request，UI 必须有 pending state |
| provider 密钥泄露到渲染层 | 高 | 中 | 主进程保存，preload 只暴露最小字段 |
| 平台主动发送上下文不可恢复 | 中高 | 中 | 平台必须声明 `reconstruct_reply` 能力 |
| 定时任务在 app 退出后不执行 | 中高 | 高 | 明确第一阶段只保证 app 运行中 |
| UI 变成 CC Connect Web 风格 | 中 | 中 | 严格使用 shadcn/ui 和现有 token |
| 一次性迁移过多平台 | 高 | 中 | 先 Bridge，再一个原生平台 |
| 旧配置/旧数据迁移不清 | 中 | 中 | 每阶段定义数据版本和迁移脚本 |
| 网络平台 SDK 引入过多依赖 | 中 | 中 | 优先外部 Bridge adapter |
| shell command 自定义命令失控 | 高 | 中 | 默认关闭或强权限确认 |
| 本地文件引用暴露隐私路径 | 中 | 中 | UI 显示相对路径，发送前确认 |
| TTS/STT 依赖 ffmpeg 或 API 配置失败 | 中 | 中 | 延后，不阻塞核心迁移 |

## 数据与配置注意点

### 配置来源

CC Connect 使用 TOML，Synapse 应避免再引入一个平行配置中心。建议：

- Synapse 自有设置继续走现有 data-store。
- 导入 CC Connect 配置时只作为一次性 import。
- Provider、project、session、scheduler 等数据进入 Synapse 自己的数据模型。

### 密钥处理

注意点：

- API key 不要在 renderer store 中长期存在。
- 导出配置时默认脱敏。
- 日志中必须 redaction。
- 错误消息不要带完整 Authorization header、token、base URL query。

### 数据版本

需要为这些数据设计版本：

- provider profile
- agent session metadata
- scheduler job
- workspace binding
- connector registration

迁移脚本要可重复执行，失败后不能破坏原数据。

## IPC 和 preload 注意点

所有渲染层调用主进程的接口都要窄：

```text
agentRuntime.startSession(...)
agentRuntime.sendMessage(...)
agentRuntime.stopSession(...)
providers.list()
providers.save(...)
scheduler.listJobs()
scheduler.createJob(...)
```

不要暴露：

- raw `ipcRenderer`
- 任意 shell 执行
- 任意文件读取
- 任意 HTTP proxy
- 完整环境变量
- 完整 provider secret

事件流建议通过订阅式 IPC：

```text
agent:onEvent(sessionId, event)
agent:onStatus(sessionId, status)
scheduler:onJobUpdated(jobId, status)
connector:onAdapterChanged(adapterId, state)
```

注意解绑监听，避免窗口关闭后仍然推送。

## UI 注意点

必须遵守 Synapse 当前 UI 纪律：

- 使用 shadcn/ui 和现有 `desktop/src/components/ui/`。
- 使用 Tailwind 默认 token 和主题 token。
- 禁止自定义色值、任意色值、AI 渐变风格。
- 禁止卡片套卡片。
- 禁止把功能说明、架构说明、路线图写进界面。
- 表单 label、输入、按钮、表格对齐要规矩。
- 数字、token usage、时间等适合表格右对齐或等宽展示。

建议页面：

- Agent Sessions：会话列表、当前状态、停止、删除、历史。
- Providers：全局 provider、项目引用、模型列表。
- Commands/Skills：注册来源、启用状态、测试调用。
- Scheduler：cron/heartbeat 列表、状态、上次运行、错误。
- Connectors：Bridge adapter、平台连接状态、能力列表。

不要做：

- “欢迎使用智能连接平台”之类横幅。
- “此页面用于帮助您管理...”。
- 装饰性图标和营销卡片。
- 大面积品牌渐变。

## 安全注意点

### 高危能力

这些能力必须加权限控制：

- shell command 自定义命令。
- Agent 文件写入。
- 删除会话。
- 删除/修改 provider。
- 启动 webhook/bridge server。
- 暴露外部监听端口。
- run-as-user。
- 发送附件到外部平台。
- 定时任务执行 shell。

### 权限模型

建议最小模型：

- 本地用户操作：需要 UI 确认。
- 外部 connector 操作：需要 token + scope。
- 高危命令：需要显式 allow。
- 定时任务：创建时确认权限，执行时按任务策略。

### 审计日志

高危操作至少记录：

- 时间
- 操作类型
- 来源：UI / connector / scheduler / webhook
- project/workspace/session
- 是否成功
- 错误摘要

不要记录完整密钥和完整大文件内容。

## 测试注意点

### 单元测试

优先覆盖：

- provider resolve
- session manager
- command template expansion
- skill discovery
- event normalization
- scheduler job state
- workspace binding
- reference parser

### 集成测试

优先覆盖：

- fake Agent runtime 的 send/result 流程。
- fake permission request 流程。
- fake platform/connector 的 message/reply 流程。
- provider 切换后新 session 生效。
- busy session queue。

### UI 测试

如果改 UI，先做源码级验证即可。项目规则明确：未获用户要求，不启动 dev server、不打开浏览器、不做 Playwright/DevTools 验证。

### 回归风险

每阶段至少跑：

```text
pnpm desktop:typecheck
```

如涉及主进程服务，再补对应单元测试或局部脚本验证。

## 阶段建议

### 阶段 0：只做设计对齐

目标：

- 确认产品入口：Synapse 是先做本地 Agent 控制台，还是先做外部聊天连接器。
- 确认数据模型命名。
- 确认哪些 CC Connect 功能进入第一版。

输出：

- 类型设计草稿。
- 服务边界。
- 不做清单。

### 阶段 1：Agent Runtime 最小闭环

目标：

- 主进程启动一个 Codex/Claude 类 Agent session。
- 渲染层能发送消息。
- 渲染层能看到事件流和最终结果。
- 能停止 session。

注意：

- 先不做平台。
- 先不做 cron。
- 先不做 TTS/STT。

### 阶段 2：Provider 与项目绑定

目标：

- 全局 provider CRUD。
- 项目引用 provider。
- Agent 启动时 resolve provider。
- 模型切换持久化。

注意：

- 密钥不进 renderer。
- provider 删除要检查引用。

### 阶段 3：会话与权限

目标：

- session 列表、新建、切换、删除。
- busy lock 和消息队列。
- permission request UI。
- AskUserQuestion UI。

注意：

- 这一步是后续平台和定时任务的地基。

### 阶段 4：Command/Skill

目标：

- builtin command registry。
- custom prompt command。
- skill discovery。
- skill invocation。

注意：

- shell exec command 暂缓或默认关闭。

### 阶段 5：Scheduler

目标：

- cron job 数据模型。
- app 运行期间触发。
- last_run / last_error。
- heartbeat 项目巡检。

注意：

- 明确退出/休眠不保证执行。

### 阶段 6：Bridge

目标：

- WebSocket register。
- message -> Agent session。
- reply -> adapter。
- token 鉴权。

注意：

- 先只做 text。
- 协议要带 version。

### 阶段 7：平台和高级能力

目标：

- 选择一个原生平台试点。
- 加 preview、buttons、file/image。
- 再考虑 Feishu/Discord rich card。

注意：

- 不要因平台 UI 反向污染 Synapse renderer 组件。

## 不做清单

第一阶段不建议做：

- 全量迁移所有平台。
- 迁移 CC Connect Web UI。
- TTS/STT。
- run-as-user。
- 自升级/daemon。
- shell exec 自定义命令默认开放。
- Bridge 的 card/audio/file 全能力。
- 复杂多 Agent relay。

这些不是没价值，而是会显著扩大风险面，应该等核心会话模型稳定后再做。

## 开工前检查清单

每个迁移阶段开始前，先确认：

- 是否只改该阶段需要的文件。
- 是否有明确数据模型。
- 是否明确主进程和渲染层边界。
- 是否复用现有 `desktop/src/modules/` 和 `desktop/electron/services/` 结构。
- 是否避免新增依赖。
- 是否有最小验收路径。
- 是否有错误处理和取消路径。
- 是否不触碰无关工作区改动。
- 如果涉及 UI，是否已读 `.claude/rules/design.md` 和 `.claude/rules/ui-rules.md`。

## 结论

融合 CC Connect 是可行的，而且对 Synapse 有明显增益：它能把 Synapse 从“本地内容/IDE 配置管理工具”扩展成“Agent 会话运行、调度、连接和协作平台”。

但迁移必须克制：先把 Agent runtime、session、provider、command/skill 这些骨架做好，再逐步接 Bridge、scheduler 和平台。只要避免整体搬运和 UI 照搬，CC Connect 的架构价值可以较平滑地进入 Synapse。
