# 无人值守模式

> 来源：基于 `重构执行协议.md`、`REFACTOR-START-PROMPT.md`、`REFACTOR-RESUME-PROMPT.md`、`REFACTOR-PROGRESS.md`、`REFACTOR-COMPLETION-REPORT.md`、`REFACTOR-SELF-AUDIT.md`、`完善报告.md` 的复盘。

## 1. 一句话定义

无人值守模式不是简单地让 AI 连续干活，而是把一次大型开发任务改造成一个**可恢复、可审计、可自检、有终局报告的自动执行系统**。

它的关键做法是：

- 用一份稳定的 SPEC 定义目标。
- 用启动提示词把执行协议一次性注入 AI。
- 用 PROGRESS 文件把当前状态外化到磁盘。
- 用 REPORT 文件把决策、失败、偏离、遗留问题实时记录下来。
- 用 git commit 把每个阶段固化成可回滚检查点。
- 用恢复提示词在中断后重建上下文并继续执行。
- 用自检循环让 AI 反复审查自己的改动，直到没有可自动修复的问题。

这套模式的本质是：**让 AI 不依赖对话上下文记忆，而依赖文件系统和 git 历史来记忆。**

## 2. 这次实际跑通的结果

这次 Phase 0 架构重构使用无人值守模式持续运行约一个半小时，产出了完整的 runtime 基础设施。

初次无人值守执行结束时：

- 总任务：71
- 自动完成：60
- Blocked / deferred：11
- 自检轮数：1
- 测试：298 个通过
- 类型检查：通过
- 硬约束检查：通过
- IPC codegen drift：无
- `main.ts`：326 行收敛到 107 行
- 结果报告：`REFACTOR-COMPLETION-REPORT.md`

后续复查和完善后：

- 测试增加到 311 个
- 重复 helper、幂等 disposer、schema import 校验、EventBus 测试竞态等问题被继续修复
- gate 继续保持通过：typecheck / test / hard-constraints / codegen-drift / build

最重要的经验不是“AI 没有遇到问题”，而是它遇到高风险任务时能按规则推迟、记录原因、保留后续入口，而不是冒险改坏核心链路。

## 3. 文件系统设计

无人值守模式依赖一组固定角色的文件。

| 文件 | 角色 | 是否由 AI 修改 |
|---|---|---|
| `架构前置改造建议.md` | SPEC，目标和约束的唯一真相 | 否 |
| `REFACTOR-START-PROMPT.md` | 首次启动提示词 | 否 |
| `REFACTOR-RESUME-PROMPT.md` | 中断恢复提示词 | 否 |
| `重构执行协议.md` | 给人看的总览说明 | 否 |
| `REFACTOR-PROGRESS.md` | 运行时进度快照 | 是 |
| `REFACTOR-COMPLETION-REPORT.md` | 运行时报告和最终报告 | 是 |
| `REFACTOR-SELF-AUDIT.md` | 完成后的自检复查记录 | 是 |
| `完善报告.md` | 二次审查后的修复记录 | 是 |

这里最核心的是 `PROGRESS` 和 `REPORT`。

`PROGRESS` 解决“做到哪了”的问题：

- 当前分支
- 当前任务
- 当前 Phase
- 总任务数 / 已完成 / blocked / pending
- 自检轮数
- 任务清单
- task 到 commit 的映射
- 最后心跳时间

`REPORT` 解决“为什么这么做”的问题：

- 每个 Phase 改了什么
- Level 2 / Level 3 决策
- 哪些任务被跳过
- 哪些 SPEC 需要修订
- 环境问题
- 自检日志
- 遗留问题
- 用户回家后的验证指南

这两个文件必须在执行过程中增量写入，不能等最后一次性补。因为一旦上下文丢失，最后补写就不可靠。

## 4. 执行协议

无人值守模式把大型任务拆成可重复执行的原子任务循环。

```text
读取 SPEC 和当前任务
  -> 实施改动
  -> 运行相关测试
  -> 修复失败，最多 3 次
  -> 跑硬约束检查
  -> 提交 git commit
  -> 更新 PROGRESS
  -> 追加 REPORT
  -> 进入下一个任务
```

原子任务的要求：

- 有明确编号，例如 `T3.12`
- 有明确目标
- 能独立提交
- 能独立测试
- 失败不会阻塞整个项目
- 结果能写入 `PROGRESS` 和 `REPORT`

这次的任务被拆成 6 个 Phase、71 个任务：

- Phase 0.1：ServiceRegistry
- Phase 0.2：DataRepository
- Phase 0.3：IPC Codegen + WindowManager + NetworkServiceRegistry
- Phase 0.4：EventBus
- Phase 0.5：ProjectContainer + ProcessRuntime
- Phase 0.6：工程规范与可观测性

## 5. 决策分级

无人值守模式的关键不是让 AI “永远正确”，而是明确它什么时候可以自己决定，什么时候必须保守处理。

### Level 1：直接决定，不记录

适合低风险选择：

- 变量名
- 函数名
- 测试 fixture 数值
- 错误消息措辞
- 局部实现细节

### Level 2：自主决定，但必须记录

适合 SPEC 没写清楚，但不会破坏用户数据或核心行为的选择。

记录内容包括：

- 决策点
- 候选方案
- 最终选择
- 理由
- 关联任务
- 关联 commit

### Level 3：保守决定，标记用户复核

适合高风险场景：

- SPEC 与现有代码行为冲突
- 会影响用户数据格式
- 会影响向后兼容
- 会影响安全、权限、网络、IPC、渲染链路
- 无法在无人值守环境下做 GUI smoke test

这次最典型的 Level 3 是推迟 11 个任务：

- 7 个 IPC handler 迁移
- 2 个 WindowManager 消费者迁移
- 2 个 EventBus 现有事件迁移

它们不是忘了做，而是被识别为“runtime 已就位，但消费者迁移需要 GUI 验证”。AI 按规则保守处理，把任务放入 REPORT 和后续行动计划。

## 6. 失败处理策略

无人值守模式必须允许失败，否则 AI 会卡死或为了完成而伪造成功。

这次采用的失败策略：

- 单任务最多尝试 3 次。
- 3 次失败后标记为 blocked。
- blocked 任务必须写入 `PROGRESS` 和 `REPORT`。
- blocked 后立即继续下一个任务。
- Phase 内 blocked 比例过高时跳过剩余高风险任务。
- 全部 Phase 完成后统一进入自检循环。
- 自检最多 10 轮，仍有问题则标记 `completed_with_issues`。

这让无人值守模式从“必须一次完美做完”变成“尽可能推进，并把不能安全推进的部分显式交还给人”。

## 7. 中断恢复机制

恢复提示词的作用是让一个全新的 AI 会话能接住上一个会话的工作。

恢复流程：

```text
读取 PROGRESS
  -> 检查 status
  -> 切到 PROGRESS 记录的分支
  -> 检查 git status
  -> 检查最近 commit
  -> 对齐 git log 与 PROGRESS
  -> 处理 WIP
  -> 在 REPORT 追加恢复节点
  -> 从 current_task 继续执行
```

WIP 的处理规则：

- 工作区干净：直接按 `current_task` 继续。
- commit 已有但 PROGRESS 落后：从 git log 反推并补齐 PROGRESS。
- 工作区有当前任务相关改动：回滚当前任务，重新执行。
- 工作区有无关改动：stash，并记录 stash 名称。
- 无法判断：保守 stash，并记录到 REPORT。

这套机制要求每个原子任务完成后尽快 commit，并更新 PROGRESS。否则恢复时无法判断“代码、进度、报告”三者哪个是真的。

## 8. 自检循环

无人值守模式的最后阶段不是“写一句完成了”，而是进入审计循环。

这次自检覆盖五类：

- 编译与测试：`typecheck`、`test`
- 硬约束扫描：IPC、webContents、fs.writeFile、createServer、空 catch 等
- SPEC 接口总览核对：runtime 目录和文件是否齐备
- 硬约束清单核对：SPEC 中的架构红线是否落地
- PROGRESS / REPORT 一致性：任务、commit、blocked、决策是否互相对得上

自检发现的问题应该继续按 mini task 修复，并形成新的 commit。

这次在初次完成后又做了 `REFACTOR-SELF-AUDIT.md` 和 `完善报告.md`，说明无人值守模式可以分两层：

- 第一层：执行任务并自检到没有明显 gate 问题。
- 第二层：从 reviewer 视角复查质量问题，能修的继续修，不能修的留档。

后续做成 skill 时，应把第二层也内置进去，而不是只生成初次完成报告。

## 9. 为什么这次能成功

### 9.1 上下文被外化

AI 不需要靠对话上下文记住 71 个任务。任务清单、当前任务、blocked、commit hash 都写在文件里。

### 9.2 每个任务都有检查点

git commit 是真实状态，PROGRESS 是声明状态，REPORT 是解释状态。三者互相校验，降低“口头完成”的风险。

### 9.3 不要求 AI 事事请示

用户不在场时，提示词明确“不暂停、不询问”。疑问进入 REPORT，不阻塞执行。

### 9.4 又给了 AI 明确边界

无人值守不是放任。提示词明确禁止：

- push
- 修改 SPEC
- 冒险改用户数据格式
- 遇到高风险还硬做
- 测试失败却声称完成

### 9.5 最终产物面向用户复核

REPORT 不是流水账，而是让用户回来后可以优先看：

- 执行摘要
- Level 3 决策
- blocked 任务
- SPEC 偏离
- 遗留问题
- 验证指南

用户不需要从几万行 diff 里猜发生了什么。

## 10. 适用场景

适合：

- 大型重构
- 多阶段架构改造
- 自动化测试较完整的后端 / Electron main / infra 代码
- 可用 git commit 分割的任务
- 用户能接受 AI 先推进、回来后复核报告

谨慎使用：

- UI 细节强依赖主观审美的任务
- 需要登录真实账号验证的任务
- 需要线上环境权限的任务
- 会迁移真实用户数据格式的任务
- 缺少测试、缺少可运行 gate 的代码库

不适合：

- 生产直接发布
- 数据不可回滚的迁移
- 必须实时产品判断的需求
- 没有 SPEC、没有任务边界的“帮我优化一下”

## 11. 后续做成 skill 的设计

这个文件后续可以转成一个 Codex skill。建议 skill 名称：

```text
unattended-dev-mode
```

触发场景：

- 用户说“无人值守”
- 用户说“我要出门，让 AI 自己做完”
- 用户需要“中断可恢复的开发流程”
- 用户有大型计划，希望生成启动提示词和恢复提示词
- 用户要把一个长 SPEC 变成可自动执行的任务系统

### 11.1 skill 输入

skill 应询问或自动识别：

- SPEC 文件路径
- 工作目录
- 输出目录
- 任务目标
- 是否允许 commit
- 是否允许安装依赖
- 是否允许启动 dev server / GUI
- 最大自检轮数
- 每个任务最大重试次数
- 哪些命令是 gate

### 11.2 skill 输出

skill 应生成：

- `START-PROMPT.md`
- `RESUME-PROMPT.md`
- `EXECUTION-PROTOCOL.md`
- `PROGRESS.md` 初始模板
- `COMPLETION-REPORT.md` 初始模板
- 可选：`SELF-AUDIT.md` 模板
- 可选：`FOLLOW-UP-PLAN.md` 模板

### 11.3 skill 工作流

```text
1. 读取 SPEC
2. 提取硬约束
3. 拆 Phase
4. 拆原子任务
5. 定义 gate 命令
6. 定义决策分级
7. 定义 blocked 策略
8. 定义恢复算法
9. 定义最终报告结构
10. 生成启动提示词和恢复提示词
```

### 11.4 skill 必须内置的规则

- 状态必须写文件，不依赖聊天上下文。
- 报告必须增量写，不等最后补。
- 每个可完成任务必须对应 commit 或明确说明为什么不 commit。
- 高风险任务必须允许 deferred，而不是强行完成。
- 自检必须循环，不是一轮命令跑完就结束。
- 恢复提示词必须能处理 PROGRESS 落后、git 落后、WIP、分支不一致、REPORT 损坏。
- 终局状态必须区分 `completed` 和 `completed_with_issues`。

## 12. 可复用提示词骨架

后续生成具体项目提示词时，可以用这个结构：

```text
你是 <项目名> 的无人值守开发执行者。
用户不会在线回应。你必须自主、连续完成任务、自检、写报告。

绝对原则：
1. 不暂停。
2. 不询问。
3. 不伪造成功。
4. 不 push。
5. 不修改 SPEC。
6. 高风险选择保守处理并记录。

关键文件：
- SPEC: <path>
- PROGRESS: <path>
- REPORT: <path>
- 工作目录: <path>

启动流程：
1. 检查 PROGRESS 是否已存在。
2. 检查 git status。
3. 记录起始 commit。
4. 创建工作分支。
5. 通读 SPEC。
6. 创建 PROGRESS 和 REPORT。
7. 从第一个任务开始。

原子任务循环：
1. 更新 PROGRESS current_task。
2. 读相关 SPEC 和代码。
3. 实施。
4. 测试。
5. 失败最多重试 3 次。
6. 硬约束检查。
7. commit。
8. 更新 PROGRESS。
9. 追加 REPORT。
10. 进入下一个任务。

完成后：
1. 执行自检循环，最多 <N> 轮。
2. 修复能自动修复的问题。
3. 剩余问题写入 REPORT。
4. 标记 completed 或 completed_with_issues。
5. 输出最终摘要和 REPORT 路径。
```

## 13. 这次经验的核心结论

无人值守模式能跑通，靠的不是更长的提示词，而是把 AI 变成一个遵守协议的执行器：

- SPEC 负责目标。
- START prompt 负责启动。
- RESUME prompt 负责恢复。
- PROGRESS 负责状态。
- REPORT 负责解释。
- git 负责检查点。
- tests / gates 负责真实性。
- audit loop 负责收尾质量。

后续把它做成 skill 时，不要只做“生成一个长提示词”的工具，而要做一个**生成无人值守执行系统**的工具。

## 14. 可复用化升级：引入 Run 工作区

如果要让无人值守模式适用于任何项目，不能把所有中间文件散落在业务目录里。应该为每次执行创建一个独立的 run 工作区。

推荐默认目录：

```text
<repo>/.ai-runs/<task-slug>-<YYYYMMDD-HHMMSS>/
```

示例：

```text
.ai-runs/
  phase-0-runtime-refactor-20260425-113000/
    manifest.yml
    README.md
    RUNNING.lock
    prompts/
      START-PROMPT.md
      RESUME-PROMPT.md
    input/
      SPEC.md
      constraints.md
      task-plan.md
    state/
      PROGRESS.md
      heartbeat.json
      decisions.ndjson
      blocked.ndjson
      checkpoints.ndjson
    reports/
      COMPLETION-REPORT.md
      SELF-AUDIT.md
      FOLLOW-UP-PLAN.md
    logs/
      commands.log
      test-runs.log
      failures.ndjson
      recovery.log
    artifacts/
      diff-stats/
      patches/
      screenshots/
      generated/
    tmp/
      scratch/
      cache/
```

这个目录是一次无人值守任务的“黑匣子”。AI 的所有运行时状态、提示词、输入快照、决策、日志、报告都在这里。

好处：

- 不污染项目根目录。
- 多次无人值守任务可以并存。
- 中断恢复只需要指向 run 目录。
- 回来后可以直接读 `reports/`。
- 后续做 skill 时，run 目录就是稳定的数据模型。

## 15. Run 目录文件设计

### 15.1 `manifest.yml`

`manifest.yml` 是 run 的总索引，机器和人都应该能读。

建议字段：

```yaml
schema_version: 1
mode: unattended
run_id: phase-0-runtime-refactor-20260425-113000
task_slug: phase-0-runtime-refactor
project_root: /path/to/repo
created_at: 2026-04-25T11:30:00+08:00
updated_at: 2026-04-25T13:02:00+08:00

status: running
phase: executing
current_task: T3.12

git:
  base_branch: main
  work_branch: codex/unattended-phase-0-runtime-refactor
  base_commit: 8dd87c1
  head_commit: 739bcaa
  commit_policy: per_task
  push_allowed: false

inputs:
  spec: input/SPEC.md
  constraints: input/constraints.md
  task_plan: input/task-plan.md

state:
  progress: state/PROGRESS.md
  heartbeat: state/heartbeat.json
  decisions: state/decisions.ndjson
  blocked: state/blocked.ndjson
  checkpoints: state/checkpoints.ndjson

reports:
  completion: reports/COMPLETION-REPORT.md
  self_audit: reports/SELF-AUDIT.md
  follow_up: reports/FOLLOW-UP-PLAN.md

gates:
  typecheck: pnpm desktop:typecheck
  test: pnpm desktop:test
  lint: pnpm desktop:lint
  hard_constraints: pnpm desktop:check:hard-constraints

limits:
  max_task_attempts: 3
  max_audit_rounds: 10
  heartbeat_interval_seconds: 60
```

`manifest.yml` 让恢复提示词不用猜路径，也不用重新理解项目结构。

### 15.2 `RUNNING.lock`

锁文件用于防止两个 AI 同时执行同一个 run。

建议内容：

```json
{
  "run_id": "phase-0-runtime-refactor-20260425-113000",
  "owner": "claude-code",
  "pid": 12345,
  "started_at": "2026-04-25T11:30:00+08:00",
  "last_heartbeat": "2026-04-25T11:40:00+08:00"
}
```

恢复时的判断：

- lock 存在且 heartbeat 新鲜：不要启动第二个执行者。
- lock 存在但 heartbeat 过期：标记为 stale，写入 `recovery.log`，接管。
- run 完成后删除 `RUNNING.lock`，创建 `COMPLETED` 或 `COMPLETED_WITH_ISSUES` 标记文件。

### 15.3 `state/heartbeat.json`

心跳文件给人和恢复流程快速判断 AI 是否还活着。

```json
{
  "last_updated": "2026-04-25T13:02:00+08:00",
  "status": "running",
  "current_task": "T6.14",
  "last_commit": "0a73cdf",
  "last_command": "pnpm desktop:test"
}
```

这个文件应该比 `PROGRESS.md` 更小、更频繁更新。

### 15.4 `state/*.ndjson`

决策、失败、checkpoint 建议用 ndjson，而不是只写 Markdown。

原因：

- AI 可以逐行追加，不容易破坏整个文件。
- 恢复时可以稳定解析。
- 后续 skill 可以做 UI 面板或汇总工具。

示例：

```jsonl
{"time":"2026-04-25T12:20:00+08:00","task":"T3.4","level":3,"type":"defer","reason":"IPC handler migration needs GUI smoke test","commit":"e99b60c"}
{"time":"2026-04-25T12:30:00+08:00","task":"T4.1","level":2,"type":"design","choice":"coalesce window 16ms","commit":"ceec93f"}
```

Markdown 报告负责给人读，ndjson 负责给机器恢复和统计。

## 16. 输入快照：不要只引用原始文件

为了跨项目可复用，run 启动时应该把关键输入复制或索引到 `input/`。

推荐：

- `input/SPEC.md`：SPEC 的快照，保证执行过程中目标不漂移。
- `input/constraints.md`：项目约束，例如 AGENTS.md、CLAUDE.md、UI 规则、工程规则。
- `input/task-plan.md`：AI 拆出来的任务清单。
- `input/source-map.md`：AI 读到的关键文件索引和行号。

如果 SPEC 很大，不一定要完整复制，可以记录：

```yaml
source_path: /path/to/original/SPEC.md
source_commit: 8dd87c1
sha256: <hash>
snapshot_path: input/SPEC.md
```

这样恢复时能发现：原始 SPEC 是否被人改过，当前 run 应该继续按旧 SPEC，还是显式开启一个新 run。

## 17. 状态机设计

无人值守模式应该有明确状态机，而不是只靠自然语言描述。

推荐状态：

```text
initialized
  -> planning
  -> ready
  -> executing
  -> auditing
  -> reporting
  -> completed
```

异常状态：

```text
blocked
completed_with_issues
failed_environment
failed_inconsistent_state
aborted_by_user
stale_lock
```

每次状态变化都写入：

- `manifest.yml`
- `state/heartbeat.json`
- `state/checkpoints.ndjson`
- `reports/COMPLETION-REPORT.md`

这样恢复提示词可以先判断状态，再决定下一步，而不是重新“猜”。

## 18. Git 策略

跨项目复用时，git 策略需要参数化。

推荐默认：

- 创建新分支：`codex/unattended-<task-slug>`
- 每个原子任务一个 commit
- 自检修复单独 commit
- 不 push
- 不 rebase
- 不 squash
- 不碰用户已有 WIP，必要时 stash 并记录

但有些项目不希望 AI 自动 commit，因此 skill 应支持三种模式：

| 模式 | 适用场景 | 行为 |
|---|---|---|
| `commit_per_task` | 大重构，强恢复需求 | 每个任务 commit |
| `commit_per_phase` | 中型任务，commit 不想太碎 | Phase 结束 commit |
| `no_commit` | 用户只想看 diff | 不 commit，但必须写 patch snapshot |

如果选择 `no_commit`，必须把每个任务的 diff 保存到：

```text
artifacts/patches/T1.1.patch
artifacts/diff-stats/T1.1.txt
```

否则中断恢复能力会大幅下降。

## 19. 临时数据与持久数据分层

run 工作区里应该区分三类数据。

### 19.1 必须保留

- `manifest.yml`
- `prompts/`
- `input/`
- `state/PROGRESS.md`
- `state/*.ndjson`
- `reports/`

这些是恢复和复盘的核心。

### 19.2 可以保留

- `logs/commands.log`
- `logs/test-runs.log`
- `artifacts/diff-stats/`
- `artifacts/patches/`

这些有助于排查，但不是恢复的唯一来源。

### 19.3 可以清理

- `tmp/`
- `artifacts/generated/` 中可重复生成的内容
- 大体积截图、trace、coverage html

建议在 run 结束后生成：

```text
reports/CLEANUP.md
```

列出哪些可以删除，哪些应该保留到 PR 合并后再删。

## 20. 通用化后的启动流程

未来 skill 的启动流程应该是：

```text
1. 识别项目根目录和 git 状态。
2. 读取 AGENTS.md / CLAUDE.md / README / package scripts。
3. 询问或推断 SPEC 文件。
4. 创建 .ai-runs/<run-id>/。
5. 写 manifest.yml。
6. 复制输入快照到 input/。
7. 生成 START-PROMPT.md 和 RESUME-PROMPT.md 到 prompts/。
8. 生成 PROGRESS.md / COMPLETION-REPORT.md 初始模板。
9. 创建工作分支。
10. 写 RUNNING.lock。
11. 执行任务。
```

恢复流程则只需要一个参数：

```text
run_dir = .ai-runs/<run-id>/
```

然后：

```text
1. 读 manifest.yml。
2. 检查 RUNNING.lock 和 heartbeat。
3. 切换到 manifest.git.work_branch。
4. 对齐 git 状态与 checkpoints。
5. 处理 WIP。
6. 在 reports/COMPLETION-REPORT.md 追加恢复节点。
7. 从 manifest.current_task 继续。
```

## 21. 跨项目适配层

无人值守模式要适配任何项目，不能假设命令都是 `pnpm desktop:test`。

skill 应该先探测项目类型：

- Node / pnpm / npm / yarn / bun
- Python / uv / poetry / pip
- Rust / cargo
- Go / go test
- Java / Maven / Gradle
- Monorepo / 单包
- Web / Electron / CLI / 后端服务

然后生成项目本地 gate：

```yaml
gates:
  install: pnpm install --frozen-lockfile
  typecheck: pnpm typecheck
  test: pnpm test
  lint: pnpm lint
  build: pnpm build
```

如果找不到命令，不能编造。应该写：

```yaml
gates:
  test:
    command: null
    status: missing
    note: package.json has no test script
```

REPORT 里必须说明哪些 gate 缺失，避免“看起来完成，其实没验证”。

## 22. 风险预算

每个 run 应该声明风险预算，决定 AI 能做到什么程度。

建议维度：

```yaml
risk_budget:
  allow_dependency_install: false
  allow_schema_migration: false
  allow_destructive_file_ops: false
  allow_dev_server: false
  allow_gui_smoke_test: false
  allow_network_access: false
  allow_large_refactor: true
```

这比在提示词里写一句“谨慎点”更可靠。

例如这次 11 个 deferred 任务，本质上是：

```yaml
allow_gui_smoke_test: false
```

所以 IPC、WindowManager、EventBus 消费者迁移被保守推迟。这个逻辑应该显式写进 manifest，而不是只靠 AI 临场判断。

## 23. 通用报告模板升级

最终报告应该固定包含这些章节：

```text
1. 执行摘要
2. 输入与约束快照
3. 任务完成情况
4. 变更摘要
5. 决策记录
6. Blocked / Deferred
7. 验证结果
8. 自检循环
9. 风险与偏离
10. 人工复核清单
11. 回滚指南
12. 后续行动计划
13. 附录：commit / patch / 文件统计
```

其中“人工复核清单”很关键。无人值守的终点不应该是“用户自己去看 diff”，而应该是 AI 告诉用户：

- 先看哪 3 个决策
- 哪些文件最值得 review
- 哪些测试必须本地再跑
- 哪些任务不能合并前跳过
- 如何回滚到起点

## 24. 归档与清理

run 完成后，应该把状态从执行目录转成归档目录。

推荐：

```text
.ai-runs/<run-id>/
  COMPLETED
  manifest.yml
  reports/
  state/
  prompts/
```

并可选生成压缩包：

```text
.ai-runs/archive/<run-id>.zip
```

清理策略：

- `completed` 且 PR 已合并：可以删除 `tmp/`、大日志、coverage html。
- `completed_with_issues`：保留全部，直到人工处理完。
- `failed_*`：保留全部，方便诊断。
- `aborted_by_user`：保留 `manifest`、`report`、`patches`，清理 `tmp`。

## 25. 升级后的核心原则

无人值守模式下一版应该从“提示词协议”升级为“运行系统协议”：

- 一个 run 一个目录。
- 一个 run 一个 manifest。
- 一个 run 一个 lock。
- 状态机显式。
- 输入快照固定。
- 决策机器可读。
- 报告人可读。
- 临时数据可清理。
- 恢复只依赖 run_dir。
- 任何项目都通过 gates 和 risk_budget 适配。

这会让它真正变成跨项目可复用的工作模式，而不是只适合 Synapse 这一次重构。
